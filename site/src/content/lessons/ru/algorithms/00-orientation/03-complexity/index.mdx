<Hook>
Представьте, что у вас есть два способа найти имя в телефонной книге:  
Вариант A: Начинать со страницы 1 и проверять каждое имя, пока не найдёте нужное.  
Вариант B: Открыть посередине, определить, находится ли имя до или после, затем повторить на правильной половине.  
Оба работают, но если в телефонной книге 1 000 000 имён, вариант A может потребовать до 1 000 000 проверок, а вариант B — максимум 20.  
Разница не в том, какой код вы напишете — а в том, как число шагов меняется при росте входа. Это изменение мы называем **сложностью**.
</Hook>

<Idea>
Когда мы говорим о "стоимости" алгоритма, обычно интересуют два показателя:  
- **Время** — сколько шагов он делает (или как долго работает)  
- **Память** — сколько дополнительной памяти он требует  

Для начинающих мы фокусируемся на **временной сложности**, потому что она чаще всего становится узким местом.  
Вместо подсчёта точного числа шагов (который зависит от железа, компилятора и т.д.), мы смотрим, как изменяется число шагов при изменении размера входа *n*.  
Мы выражаем это с помощью **нотации Big O**, которая даёт верхнюю границу скорости роста.

Примеры:
- **O(1)** — постоянное время: алгоритм делает одинаковое количество шагов независимо от размера входа.  
  Пример: доступ к элементу массива по индексу.
- **O(log n)** — логарифмическое время: число шагов растёт медленно при росте n.  
  Пример: бинарный поиск в отсортированном массиве.
- **O(n)** — линейное время: число шагов растёт пропорционально n.  
  Пример: проход по списку в поиске максимума.
- **O(n log n)** — линейно-логарифмическое время: характерно для эффективных сортировок типа сортировки слиянием и быстрой сортировки (в среднем случае).
- **O(n²)** — квадратичное время: число шагов растёт квадратом от n.  
  Пример: вложенные циклы, где каждый цикл выполняется n раз (проверка всех пар).
- **O(2ⁿ)** — экспоненциальное время: число шагов удваивается при каждом добавлении к входу.  
  Пример: перебор всех подмножеств множества (грубая сила).

Мы отбрасываем constantes и низшие порядки, потому что для больших n доминирующим является самый быстрорастущий член.  
Итак, алгоритм, который выполняет 5n² + 3n + 7 шагов, всё ещё находится в **O(n²)**.
</Idea>

<Code>
Давайте посмотрим на несколько простых алгоритмов и запишем их сложность.

**1. Константное время – O(1)**
```
algorithm getFirst(list):
    return list[0]
```
Неважно, насколько длинный список — мы делаем один шаг: возвращаем первый элемент.

**2. Линейное время – O(n)**
```
algorithm sumList(list):
    total ← 0
    for value in list:
        total ← total + value
    return total
```
Цикл выполняется один раз на каждый элемент → n шагов → O(n).

**3. Квадратичное время – O(n²)**
```
algorithm hasDuplicate(list):
    for i from 0 to list.length - 1:
        for j from i + 1 to list.length - 1:
            if list[i] == list[j]:
                return true
    return false
```
Внешний цикл выполняется n раз, внутренний — до n раз для каждой итерации внешнего цикла → примерно n²/2 сравнений → O(n²).

**4. Логарифмическое время – O(log n)**
```
algorithm binarySearch(list, target):
    left ← 0
    right ← list.length - 1
    while left <= right:
        mid ← (left + right) // 2
        if list[mid] == target:
            return true
        else if list[mid] < target:
            left ← mid + 1
        else:
            right ← mid - 1
    return false
```
Каждая итерация уменьшает диапазон поиска пополам → количество итераций равно log₂(n) → O(log n).
</Code>

<Trace>
Давайте проследим работу `sumList` на входе `[2, 4, 6]`, чтобы увидеть линейную работу:

| Шаг | value | total (до) | total (после) |
|-----|-------|------------|---------------|
| Старт | –     | 0          | 0             |
| Цикл1 | 2     | 0          | 2             |
| Цикл2 | 4     | 2          | 6             |
| Цикл3 | 6     | 6          | 12            |
| Конец | –     | –          | 12            |

Мы посетили каждый элемент ровно один раз → 3 шага для n=3 → O(n).

Теперь проследим `hasDuplicate` на `[1, 2, 3]` (без дубликатов), чтобы увидеть квадратичную работу:

| Внешний i | Внутренний j | Сравнение | Действие |
|-----------|--------------|-----------|----------|
| 0         | 1            | 1==2?     | ложно    |
| 0         | 2            | 1==3?     | ложно    |
| 1         | 2            | 2==3?     | ложно    |
| (циклы закончены) | | | возвращаем ложь |

Мы сделали 3 сравнения = n*(n-1)/2 для n=3 → O(n²).
</Trace>

<Complexity>
Чтобы оценить сложность алгоритма в нотации Big O:
1. Определите базовую операцию, которая повторяется (обычно внутри самых глубоких вложенных циклов).
2. Посчитайте, сколько раз эта операция выполняется как функция размера входа n.
3. Оставьте только самый быстрорастущий член, отбросив constantes и коэффициенты.

Примеры из кода выше:
- `getFirst`: базовая операция = доступ к массиву → выполняется 1 раз → O(1).
- `sumList`: базовая операция = сложение внутри цикла → выполняется n раз → O(n).
- `hasDuplicate`: базовая операция = сравнение внутри внутреннего цикла → выполняется примерно n²/2 раз → O(n²).
- `binarySearch`: базовая операция = сравнение внутри цикла while → выполняется log₂(n) раз → O(log n).

Почему мы отбрасываем constantes:  
Если алгоритм выполняет 5n шагов, мы всё равно говорим O(n), потому что при n → ∞ множитель 5 не меняет класс роста.
</Complexity>

<Recap lang="ru">
Анализ сложности позволяет предсказать, как алгоритм будет масштабироваться, не запуская его на каждом возможном входе.  
Мы используем нотацию Big O для описания верхней границы скорости роста времени работы (или использования памяти) при увеличении размера ввода.  
Распространённые классы: O(1) (постоянное время), O(log n) (логарифмическое время), O(n) (линейное время), O(n log n) (линейно-логарифмическое время), O(n²) (квадратичное время) и O(2ⁿ) (экспоненциальное время).  
Анализируя циклы — особенно вложенные циклы — мы часто можем определить сложность прямо по структуре кода.
</Recap>
