<Step n={1}>
**Компоненты игрушечного CPU.** Наш игрушечный CPU содержит следующее:

- **Два регистра общего назначения**: R0 и R1. Каждый хранит одно 8-битное значение
  (0–255).
- **Счётчик команд (СК)**: хранит адрес памяти следующей инструкции для выборки. Тоже
  8-битный, поэтому может адресовать ячейки памяти 0–255.
- **Память**: 256 ячеек, каждая хранит одно 8-битное значение. Адреса 0–9 будут хранить
  нашу программу (инструкции). Адреса 200 и 201 — наши данные (входные числа). Адрес
  202 — результат.
- **Арифметико-логическое устройство (АЛУ)**: схема, которая складывает два 8-битных
  значения и сохраняет результат в регистре.

Игрушечный CPU не умеет много — он создан, чтобы продемонстрировать основы, а не быть
практичным. Реальные CPU имеют 16–31 регистр общего назначения, могут адресовать
гигабайты памяти и системы команд с сотнями опкодов. Но принципы те же.
</Step>

<Step n={2}>
**Игрушечная система команд.** Наш CPU понимает ровно четыре инструкции. Каждая
инструкция занимает ровно один байт. Старшие 2 бита — опкод; оставшиеся 6 бит — операнд.

| Опкод (биты 7–6) | Название | Смысл |
|---|---|---|
| `00` | LOAD Ra, addr | Загрузить значение из адреса памяти `addr` в регистр Ra (бит 5 выбирает R0 или R1) |
| `01` | STORE addr, Ra | Сохранить значение регистра Ra по адресу памяти `addr` |
| `10` | ADD R0, R1 | Сложить R0 и R1; результат в R0. Операндные биты не используются. |
| `11` | JUMP addr | Установить СК на `addr` (6-битный адрес в операндных битах) |

Поскольку каждая инструкция — один байт, адреса в инструкциях LOAD и STORE занимают
всего 6 бит — они могут адресовать только ячейки 0–63. Для реального CPU они были бы
шире, но однобайтовые инструкции упрощают трассировку.

Для нашей программы мы запишем инструкции на обычном языке:

```
LOAD R0, 200    ; R0 ← память[200]
LOAD R1, 201    ; R1 ← память[201]
ADD  R0, R1     ; R0 ← R0 + R1
STORE 202, R0   ; память[202] ← R0
```

Программа загружает два числа из памяти, складывает их и сохраняет результат.
</Step>

<Inset kind="why" lang="ru">
**Почему только четыре инструкции?** В реальных системах команд сотни опкодов. Но для
демонстрации всего существенного достаточно горстки: перемещение данных (LOAD/STORE),
вычисление (ADD) и управление потоком (JUMP). Каждая более сложная инструкция — это
комбинация или расширение этих идей. Курс nand2tetris использует столь же минимальную
систему команд (называемую «Hack») для построения полностью рабочего компьютера с нуля;
весь язык умещается в 16 бит.
</Inset>

<Step n={3}>
**Начальное состояние памяти.** Перед запуском программы ОС загружает байты инструкций
в память, начиная с адреса 0, и помещает входные данные по адресам 200 и 201. СК
устанавливается на 0.

```
Адрес  Содержимое     Смысл
0      LOAD R0, 200   ← первая инструкция (СК начинает здесь)
1      LOAD R1, 201   ← вторая инструкция
2      ADD R0, R1     ← третья инструкция
3      STORE 202, R0  ← четвёртая инструкция
...
200    25              ← первое входное число
201    17              ← второе входное число
202    0               ← слот для результата (пусто)
```

Регистры до выполнения: R0 = 0, R1 = 0.

Теперь CPU запускает свой цикл.
</Step>

<Step n={4}>
**Счётчик команд управляет всем.** Прежде чем подробно трассировать каждый цикл, обрати
внимание на ключевую роль СК:

- СК начинается с 0 — значит, первая выбранная инструкция находится по адресу 0.
- После каждой не-JUMP инструкции СК увеличивается на 1 (поскольку каждая инструкция
  в нашем игрушечном CPU занимает 1 байт).
- Если программа содержала бы JUMP, СК устанавливался бы на адрес перехода вместо этого.

СК — это курсор, проходящий через последовательность инструкций. Именно он — единственная
причина, по которой CPU знает, какая инструкция «следующая».
</Step>

<WorkedExample lang="ru">
**Полная трассировка программы из четырёх инструкций.**

Отслеживаем: СК, R0, R1 и содержимое адреса памяти 202 после каждого цикла.

---

**Цикл 1**

Состояние до: СК = 0, R0 = 0, R1 = 0, память[202] = 0.

- **Выборка**: читаем инструкцию по адресу СК = 0. Инструкция = `LOAD R0, 200`.
- **Декодирование**: опкод `00` → LOAD. Бит 5 операнда → назначение = R0. Поле адреса = 200.
- **Исполнение**: читаем память[200]. Результат = 25. Записываем 25 в R0.
- **Продвижение СК**: СК = 0 + 1 = 1.

Состояние после: СК = 1, **R0 = 25**, R1 = 0, память[202] = 0.

---

**Цикл 2**

Состояние до: СК = 1, R0 = 25, R1 = 0, память[202] = 0.

- **Выборка**: читаем инструкцию по адресу СК = 1. Инструкция = `LOAD R1, 201`.
- **Декодирование**: опкод `00` → LOAD. Назначение = R1. Адрес = 201.
- **Исполнение**: читаем память[201]. Результат = 17. Записываем 17 в R1.
- **Продвижение СК**: СК = 1 + 1 = 2.

Состояние после: СК = 2, R0 = 25, **R1 = 17**, память[202] = 0.

---

**Цикл 3**

Состояние до: СК = 2, R0 = 25, R1 = 17, память[202] = 0.

- **Выборка**: читаем инструкцию по адресу СК = 2. Инструкция = `ADD R0, R1`.
- **Декодирование**: опкод `10` → ADD. Нет операнда-адреса. Источники = R0, R1.
  Назначение = R0.
- **Исполнение**: АЛУ вычисляет R0 + R1 = 25 + 17 = 42. Записываем 42 в R0.
- **Продвижение СК**: СК = 2 + 1 = 3.

Состояние после: СК = 3, **R0 = 42**, R1 = 17, память[202] = 0.

---

**Цикл 4**

Состояние до: СК = 3, R0 = 42, R1 = 17, память[202] = 0.

- **Выборка**: читаем инструкцию по адресу СК = 3. Инструкция = `STORE 202, R0`.
- **Декодирование**: опкод `01` → STORE. Источник = R0. Адрес-назначение = 202.
- **Исполнение**: записываем значение R0 (42) в память[202].
- **Продвижение СК**: СК = 3 + 1 = 4.

Состояние после: СК = 4, R0 = 42, R1 = 17, **память[202] = 42**.

---

Программа завершена. Адрес памяти 202 теперь хранит 42 — сумму двух входных чисел
(25 + 17). CPU попытается выбрать инструкцию по адресу 4, но нашей программе не нужна
пятая инструкция, поэтому в реальной системе ОС завершила бы процесс до достижения
адреса 4.

Всё вычисление потребовало ровно четыре цикла выборки–декодирования–исполнения. Каждый
цикл имел одну и ту же трёхшаговую структуру. CPU никогда не нужно было «понимать», что
именно он вычисляет — он просто выполнял свой цикл.
</WorkedExample>

<Inset kind="edgecase" lang="ru">
**Что происходит, когда СК выходит за конец программы?** В нашем примере СК достигнет
адреса 4 и попытается выбрать байт, который там находится, — мусор или, возможно, код
другой программы. Реальные ОС предотвращают это: двоичный файл программы содержит
метаданные, сообщающие ОС, где заканчивается программа (или есть явная инструкция HALT,
или системный вызов для завершения). ОС настраивает защиту памяти так, чтобы программа
не могла выполняться за пределами своей области. На практике последняя инструкция почти
каждой программы — вызов системного вызова «exit», который корректно завершает процесс.
</Inset>

<Recap lang="ru">
Минимальный CPU требует: **регистров** (быстрое рабочее хранилище — R0, R1), **счётчика
команд** (регистра, хранящего адрес следующей инструкции), **памяти** (байтовых ячеек
для инструкций и данных) и **АЛУ** (схемы, вычисляющей арифметику). Поведение CPU
полностью описывается циклом выборки–декодирования–исполнения: выбрать инструкцию по
СК, декодировать её опкод и операнды, исполнить соответствующее действие, продвинуть
СК. Программа из четырёх инструкций (LOAD, LOAD, ADD, STORE) выполняется за четыре
цикла и вычисляет сумму без того, чтобы CPU когда-либо «знал», что он складывает — он
просто выполнял свой цикл. Каждая более крупная программа — какой бы сложной она ни
была — это тот же цикл, работающий дольше, на большем количестве инструкций, с большим
регистровым файлом и большей памятью. Механизм никогда не меняется.
</Recap>
