<Crux>Бэкенд — программа на сервере: принимает запросы, выполняет логику, читает и пишет в базу, возвращает ответы клиенту.</Crux>

К концу урока у тебя будет восемь терминов, которые каждый senior-юнит считает само собой разумеющимися — и когда они встретятся в контексте, ты уже будешь знать, какую роль каждый из них играет.

## Единственная проблема, которую решает бэкенд

Браузер умеет отображать HTML и запускать JavaScript, но не может безопасно хранить пароли, списывать деньги с карты или держать общую базу, в которую пишут все пользователи сразу. Кому-то нужно жить за пределами браузера, помнить данные между сессиями, соблюдать правила и отвечать на вопросы всех клиентов согласованно. Этот кто-то — бэкенд: программа в дата-центре, доступная по сети, ждущая запросов и отвечающая данными.

Всё, чему учит этот трек — middleware (промежуточные обработчики запроса), async I/O (неблокирующий ввод-вывод), пулы соединений, circuit breaker'ы (предохранители от каскадных сбоев) — это детали поверх одной задачи: **принять запрос, сделать полезную работу, вернуть ответ, выдержать нагрузку.** Когда встретишь любой из этих терминов дальше по треку, ты уже будешь знать, на каком шаге этого цикла он живёт.

## Как они складываются вместе

Прочитанные по порядку, слова рассказывают одну историю: **запрос** приходит с **HTTP-методом** и URL; **роутер** сервера сопоставляет URL с **endpoint'ом** и вызывает функцию-**обработчик**; обработчик читает или пишет в **базу данных** и формирует ответ; ответ уходит обратно с **кодом статуса**, который проверяет клиент. Потому что сервер **без состояния**, он ничего не помнит между вызовами — весь контекст либо приходит в самом запросе, либо живёт в базе. Этот один абзац — весь трек в миниатюре; каждый следующий юнит увеличивает один из шагов.

<Inset kind="why" lang="ru">
Зачем нужна statelessness, если она просто перекладывает нагрузку на базу данных? Потому что stateful-сервер — это узкое место: второй запрос пользователя обязан попасть к той же машине, что обработала первый, иначе данные сессии потеряются. Stateless-сервер не имеет такого ограничения — любой инстанс отвечает на любой запрос, поэтому при скачке трафика добавляешь инстансы, при спаде убираешь, без лишней координации. База держит общую истину; сервер остаётся одноразовым.
</Inset>

## Это не нужно зубрить

Две честные ремарки перед восхождением. Первая: никто не держит всё это в голове сразу в первый день — ты встретишь каждое слово снова, в своём юните, глубже, и тогда оно уляжется. Эта страница — вешалка для деталей, а не экзамен. Вторая: не каждый бэкенд нуждается в каждой фиче. Крошечный пет-проект может быть одним сервером с тремя маршрутами без балансировщика. Трек учит полной картине, потому что этого требует продакшен под нагрузкой, — но «начни просто, добавляй сложность, когда заболит» и есть senior-инстинкт.

<Recap lang="ru">
Бэкенд — одна идея с кучей навешанной механики: программа на сервере принимает запросы, выполняет логику, читает или пишет в базу и возвращает ответы — всё это без памяти между вызовами, чтобы любой инстанс мог обработать любой запрос. Восемь слов картируют всю поверхность: сервер слушает; запрос несёт метод и URL; роутер сопоставляет его с endpoint'ом и запускает обработчик; обработчик говорит с базой; ответ с кодом статуса уходит обратно; а statelessness делает всё это масштабируемым. Теперь, когда в senior-юните встретится любой из этих терминов, ты будешь знать, какой шаг цикла он описывает — и что именно ломается, когда этот шаг идёт не так.
</Recap>
