## Обмен 1 — рукопожатие ревалидации

```http
# Первый запрос
GET /api/config HTTP/1.1
Host: api.example.com

HTTP/1.1 200 OK
ETag: "a3f5c901"
Content-Length: 8192
... 8 КБ JSON-тело ...

# Через 30 с, контент не изменился
GET /api/config HTTP/1.1
Host: api.example.com
If-None-Match: "a3f5c901"
```

## Обмен 3 — докачка загрузки

```http
GET /video.mp4 HTTP/1.1
Host: media.example.com
Range: bytes=1000000-
If-Range: W/"clip-build-9"

# текущий валидатор сервера:
#   ETag: W/"clip-build-9"
```

## Обмен 4 — поюнитная регрессия

```http
# Запрос попадает на под A, который выпустил кэшированный тег клиента
GET /api/config HTTP/1.1
If-None-Match: "pod-a-counter-7"

HTTP/1.1 304 Not Modified

# Следующий опрос round-robin направляет на под B
GET /api/config HTTP/1.1
If-None-Match: "pod-a-counter-7"

HTTP/1.1 200 OK
ETag: "pod-b-counter-3"
Content-Length: 8192
```

<Recap lang="ru">
Каждый инцидент ETag читается в обмене: совпавший If-None-Match даёт 304 с пустым телом, но круговой обход всё равно платится; If-None-Match сравнивает слабо, поэтому W/ и сильная форма одного значения совпадают; If-Range — единственное место, требующее сильный валидатор, поэтому слабый тег вынуждает полный 200 вместо 206; а когда идентичный контент даёт разные токены на разных подах, баг — в локальном для узла ETag: лечится выводом тега из контента, а не из машины. Теперь, когда откроешь DevTools и увидишь сплошные 200 на редко меняющемся эндпоинте, — первым делом смотри на столбец ETag: лог покажет, согласован ли тег между узлами.
</Recap>
