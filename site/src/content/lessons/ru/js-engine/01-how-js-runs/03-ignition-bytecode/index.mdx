<Hook>
Когда в 2017 году Ignition стал основным интерпретатором V8, одной из главных причин была память. Старый базовый компилятор порождал машинный код даже для функций, которые исполнялись считанные разы. Ignition хранит более компактный байт-код и интерпретирует его, пока не станет выгоден более быстрый уровень исполнения. Чтобы понять этот компромисс, проследим одно сложение через аккумулятор, регистры аргументов и обратную связь о типах.

## Байт-код: компактен по замыслу, и причина — память

После построения AST для функции, которую нужно скомпилировать (вспомните ленивый парсинг), **генератор байт-кода** переводит дерево в **байт-код Ignition**: компактный поток инструкций виртуальной машины. Инструкция состоит из опкода и, возможно, операндов; её длина зависит от команды. По исходным замерам V8 весь поток байт-кода занимал около **25–50% объёма соответствующего старого базового машинного кода**.

Компактность и была целью. Старый базовый машинный код занимал заметную часть памяти, в том числе для функций, выполненных лишь раз. При первом внедрении на Android-устройствах с малым объёмом RAM V8 сообщил о **девятикратном сокращении памяти для базового, неоптимизированного кода на ARM64**. Это историческое измерение для конкретной категории кода и платформы, а не экономия всей кучи. Ускорение горячего кода дают уровни JIT.

## Регистровая машина, а не стековая

Когда читаешь вывод `d8 --print-bytecode` и видишь незнакомые операнды, регистровая модель — это ключ к их расшифровке. Есть два классических способа построить VM байт-кода. **Стековая машина** (JVM, CPython) держит операнды на неявном стеке операндов: `PUSH a; PUSH b; ADD` снимает два, кладёт сумму. **Регистровая машина** держит операнды в именованных регистрах, и операции ссылаются на них напрямую: `ADD r1, r2`. Ignition — это **регистровая машина**.

Аккумулятор сокращает многие распространённые инструкции: один вход и результат не нужно указывать явно. Последовательные шаги выражения могут обойтись без дополнительных загрузок и сохранений. Точное число инструкций зависит от выражения; регистровый байт-код не гарантирует меньше диспетчеризаций для любой программы.

Регистровая модель Ignition — это конкретно **аккумулятор + регистровый файл**:

- **Аккумулятор** — единственный неявный регистр, из которого большинство байт-кодов читают и в который пишут. Он протягивает промежуточные значения от одной инструкции к следующей, так что не всем операндам нужно явное имя. Многие операции берут *один* явный операнд и неявно используют аккумулятор как другой вход и как выход.
- **Регистровый файл** включает регистры аргументов `a0`, `a1` и регистры локальных или временных значений `r0`, `r1` во фрейме функции.

## Читаем настоящий байт-код

Возьмите простейшую функцию и посмотрите, что исполняет Ignition. Запустите `d8 --print-bytecode add.js` на:

```js
function add(a, b) { return a + b; }
add(1, 2);
```

Вы получите что-то близкое к этому (операнды и индексы слотов сокращены):

```text
Ldar a1          // загрузить аргумент b в аккумулятор
Add a0, [0]      // аккумулятор = a0 (a) + аккумулятор (b); слот обратной связи 0
Return           // вернуть аккумулятор
```

Заметьте аккумулятор-центричную форму: `Ldar` (**L**oa**d** **A**ccumulator from **R**egister) кладёт `b` в аккумулятор; `Add a0, [0]` прибавляет регистр `a0` (аргумент `a`) к аккумулятору и оставляет сумму в аккумуляторе; `Return` возвращает аккумулятор. Нет `Push`/`Pop` — аккумулятор и есть общая рабочая область.

## `[slot]` — это место, где JIT получает информацию о типах

Посмотрите снова на `Add a0, [0]`. `[0]` указывает **слот вектора обратной связи** для этой операции сложения. Инструкции, собирающие обратную связь, в том числе арифметика, доступ к свойствам и вызовы, используют слоты для наблюдений о типах операндов, формах объектов или целях вызова. Вектор связан с исполняемой функцией, может выделяться лениво и хранится отдельно от байт-кода. `Add` обновляет слот во время сложения, без отдельной инструкции.

Это мост к оптимизатору. Когда функция становится горячей, уровень JIT может прочитать её обратную связь и специализировать операцию под наблюдавшиеся типы, добавив проверки или путь деоптимизации. Сбор обратной связи расходует время и память, поэтому V8 выделяет векторы лениво для функций, исполнивших достаточно байт-кода.

<Misconception id="mc-bytecode-fast">
  <p><strong>«Байт-код нужен, чтобы сделать JS быстрее машинного кода».</strong> Изначальная цель Ignition — уменьшить память под код. Интерпретация добавляет затраты на диспетчеризацию; уровни JIT компилируют горячие участки, когда дополнительный машинный код оправдан.</p>
</Misconception>

## Общие обработчики байт-кода

Каждый байт-код вызывает **обработчик**, выполняющий соответствующую операцию. V8 описывал генерацию обработчиков из низкоуровневых, независимых от архитектуры инструкций TurboFan в машинный код целевой платформы. Скомпилированный обработчик опкода общий для разных функций; каждая функция подставляет свои операнды и значения фрейма. Следующий урок разбирает диспетчеризацию обработчиков.

В `add(a, b)` инструкция `Ldar a1` загружает аккумулятор, `Add a0, [0]` вычисляет сумму и обновляет обратную связь, а `Return` возвращает результат. V8 ввёл Ignition прежде всего ради памяти под базовый код; позднее JIT может использовать наблюдения для специализации горячего кода.</KeyTakeaway>

<Recap lang="ru">
V8 переводит разобранные функции в компактный байт-код Ignition. Память была одной из главных причин появления интерпретатора: ранний поток байт-кода занимал около 25–50% объёма соответствующего базового машинного кода. Ignition использует регистровый файл и аккумулятор, неявно участвующий во многих командах. `add(a, b)` может превратиться в `Ldar a1; Add a0, [0]; Return`: загрузить `b`, прибавить `a` к аккумулятору и вернуть значение. Во время `Add` слот `[0]` может записать типы операндов для последующей специализации JIT. Вектор обратной связи выделяется при необходимости и хранится отдельно от байт-кода. Общие обработчики исполняют опкоды, а отдельные функции передают им свои операнды и состояние фрейма. `d8 --print-bytecode` показывает поток инструкций; для просмотра самой обратной связи нужны другие инструменты.
</Recap>
