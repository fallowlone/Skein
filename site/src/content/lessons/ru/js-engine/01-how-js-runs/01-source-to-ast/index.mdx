## Две стадии до того, как что-либо запустится

Когда рантайм передаёт V8 исходник JavaScript, код, нужный для выполнения, проходит две отдельные стадии:

1. **Сканирование (лексинг).** Сканер читает **UTF-16-представление** исходника и группирует кодовые единицы в **токены** — слова языка. Сам исходник может поступить в Latin1, UTF-8 или UTF-16; поток символов предоставляет сканеру единое представление. `const x = 42;` превращается в `Keyword(const)`, `Identifier(x)`, `Punctuator(=)`, `Number(42)`, `Punctuator(;)`. Пробелы и комментарии пропускаются, но значимые переводы строк учитываются.

2. **Парсинг.** Парсер собирает токены компилируемого кода в **абстрактное синтаксическое дерево (AST)** — вложенное представление грамматики. Условно, `const x = 42;` становится объявлением с именем переменной (`x`) и начальным значением (`42`). Дерево строится для кода, который компилируется.

Функции, которые пока не нужны, V8 может **предварительно разобрать**, а полностью распарсить при первом вызове. Как V8 решает, что откладывать, — в следующем уроке.

## Как парсер строит дерево: рекурсивный спуск и приоритет

Парсер V8 написан вручную и использует **рекурсивный спуск**. Его функции вызывают друг друга по мере вложенности грамматики: блок содержит операторы, а они — выражения. Поэтому парсер должен защищаться от патологической вложенности ещё до исполнения кода.

У выражений есть **приоритет**: в `a + b * c` сначала должно связаться `b * c`. Парсер бинарных выражений V8 использует приоритет операторов, чтобы решить, когда правую часть нужно разобрать на более тесном уровне. Так из плоской последовательности токенов получается вложенная структура ниже.

```js
// a + b * c парсится в такую форму дерева (* связывает крепче, чем +):
//        (+)
//       /   \
//      a    (*)
//          /   \
//         b     c
```

## AST временное — это НЕ то, что исполняется

Это ключевая поправка к наивной модели. Можно представить, что движок обходит AST для исполнения программы, как древовидный интерпретатор. **V8 так не делает.** Генератор байт-кода использует AST, выпускает байт-код Ignition, после чего V8 освобождает временную память парсера. С этого момента *исполняется байт-код* — AST больше нет. (Следующие уроки разбирают байт-код и цикл интерпретатора.)

Итак, AST — это **промежуточное представление**: удобная структурированная форма, существующая лишь для того, чтобы быть пониженной во что-то, что интерпретатор может исполнять эффективно. Хранить его — пустая трата памяти.

Обходить его как дерево было бы намного медленнее, чем исполнять плоский байт-код.

<Misconception id="mc-ast-runs">
  <p><strong>«Движок исполняет AST, обходя дерево».</strong> Нет — генератор байт-кода использует AST, а V8 освобождает эту временную структуру после компиляции. Затем исполняется байт-код Ignition.</p>
</Misconception>

## Размер исходника важен, но путь выполнения важнее

Размер исходника влияет на объём сканирования и предварительного разбора, но не добавляет постоянную стоимость за каждый байт при каждом посещении страницы. Ленивый парсинг может отложить AST и байт-код функции до первого вызова; кэш байт-кода и фоновая компиляция меняют критический путь. Большие литералы, нужные при старте, всё же требуют работы.

Прежде чем связывать пустой экран с парсером, проверьте парсинг и компиляцию в профиле запуска. Ключевое различие: AST существует для компилируемого кода, а более лёгкий предварительный разбор покрывает функцию, которая может вообще не запуститься.

## Режим отказа: гигантский литерал данных, разобранный жадно

Вот боевая ловушка. Команда встраивает большой набор данных прямо в JS-модуль как литерал объекта или массива — многомегабайтный «JSON-в-JS»:

```js
// data.js — 3 МБ такого, встроено в бандл
export const LOOKUP = { "0001": { name: "...", coords: [] }, /* ещё 50k */ };
```

Поскольку это литерал JavaScript на верхнем уровне модуля, V8 должен разобрать выражение и сгенерировать байт-код до завершения вычисления модуля. Если модуль нужен при старте, эта работа увеличивает стоимость запуска.

Один вариант — вынести данные в файл `.json` и загружать его тогда, когда он нужен:

```js
const LOOKUP = JSON.parse(await fetch("/data.json").then(r => r.text()));
```

`JSON.parse` работает с более простой грамматикой и не строит AST JavaScript. По измерениям команды V8, крупные JSON-подобные данные в виде строки JSON обрабатывались быстрее, чем эквивалентный литерал объекта.

Отдельный запрос позволяет отложить работу, но добавляет сетевую задержку; сам `JSON.parse` синхронен. Измеряйте весь путь загрузки перед выбором формата.

<Recap lang="ru">
Для компилируемого кода сканер V8 выдаёт токены из UTF-16-представления исходника, парсер собирает AST, а генератор выпускает байт-код Ignition. V8 освобождает временное дерево, и интерпретатор исполняет байт-код. Функция, которая пока не нужна, может пройти предварительный разбор и компилироваться позднее. Большие литералы на верхнем уровне добавляют работу при старте, но ленивый парсинг, фоновая компиляция и кэш байт-кода меняют её стоимость. Измерьте профиль перед сменой формата данных; сравните выигрыш от JSON.parse с задержкой и моментом дополнительного запроса.
</Recap>
