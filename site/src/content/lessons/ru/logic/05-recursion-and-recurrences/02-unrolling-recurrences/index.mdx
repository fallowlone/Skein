## Что считает рекуррента

В прошлом уроке рекурсия была про то, *что* вычисляется. Теперь посчитаем, *сколько это стоит*. Обозначим `T(n)` число базовых шагов, которые функция выполняет на входе размера n. Поскольку рекурсивная функция — это «один слой моей работы плюс меньший себя», её стоимость подчиняется той же форме — **рекурренте**:

```
T(n) = T(меньшее) + (работа этого слоя)
```

Возьмём рекурсивную сумму списка. Каждый вызов делает одно сложение и одно сравнение — константу, пусть 1 шаг — и рекурсит на списке короче на единицу:

```
T(n) = T(n-1) + 1,    T(0) = 1
```

Чтобы решить, **развернём**: подставим рекурренту в саму себя несколько раз и посмотрим, как проступает закономерность.

```
T(n) = T(n-1) + 1
     = (T(n-2) + 1) + 1  = T(n-2) + 2
     = (T(n-3) + 1) + 2  = T(n-3) + 3
       …закономерность: T(n-k) + k
     = T(0) + n  =  n + 1        (берём k = n, чтобы дойти до базы)
```

Линейно: список в миллион стоит около миллиона шагов. Разумно. Метод, который вы только что применили, — всё ремесло целиком, и оно не меняется: **разверни 3–4 шага, поймай закономерность, просуммируй, сверь на маленьком n вручную.** Проверка: `T(2)` должно быть 3 — и правда, `sum([a, b])` делает три вызова: два элемента и один пустой список.

Эта проверка заслуживает стать кодом. Формула предсказывает число вызовов — посчитаем вызовы:

```js
let calls = 0;
function sum(list) {
  calls++;
  if (list.length === 0) return 0;
  return list[0] + sum(list.slice(1));
}
sum([5, 2, 9]);
console.log(calls); // 4 — совпадает с T(3) = 3 + 1
```

Настолько дешёвая эмпирическая проверка должна сопровождать каждую решённую рекурренту: формула говорит, что *должно* случиться; счётчик — что *случилось*.

## Маляр, перекрашивающий всё: T(n) = T(n-1) + n

Теперь импортёр из пролога. Каждый вызов обрабатывает одну запись — но сначала заново сканирует *все* оставшиеся, чтобы отфильтровать список. Работа слоя не константа; она пропорциональна текущему размеру:

```
T(n) = T(n-1) + n
```

Это маляр, который каждое утро перекрашивает все уже покрашенные доски забора, прежде чем добавить одну новую. Развернём:

```
T(n) = T(n-1) + n
     = T(n-2) + (n-1) + n
     = T(n-3) + (n-2) + (n-1) + n
       …закономерность: T(0) + 1 + 2 + … + n
```

Итак, цена — сумма `1 + 2 + … + n`. Девятилетний Карл Фридрих Гаусс, которому велели сложить числа от 1 до 100, чтобы занять его, увидел ответ мгновенно: спарить концы. 1 + 100 = 101, 2 + 99 = 101, 3 + 98 = 101 — пятьдесят пар по 101, итого 50 · 101 = 5050. В общем виде n чисел образуют n/2 пар по n + 1:

```
1 + 2 + … + n  =  n(n + 1) / 2
```

Это примерно n²/2 — **квадрат**. Числовое чутьё безжалостно: n = 200 стоит ~20 000 шагов (стейджинг пожимает плечами); n = 100 000 стоит ~5 000 000 000 шагов (ночь запуска умирает). Рекуррента предсказала разбор инцидента из кресла: цена слоя в n шагов превращает линейную на вид рекурсию в квадратичный счёт.

```js
function process(items) {
  if (items.length === 0) return;
  handle(items[0]);
  const rest = items.filter((x) => x.id !== items[0].id); // n работы на слой
  process(rest);                                          // T(n-1)
}
```

Лечение — снова сделать работу слоя константной (идти по индексу или срезать один раз), и рекуррента схлопывается обратно в `T(n-1) + 1`.

## Деление пополам: T(n) = T(n/2) + 1

Двоичный поиск смотрит на средний элемент и отбрасывает половину диапазона. Одно сравнение — и задача вдвое меньше:

```
T(n) = T(n/2) + 1
     = T(n/4) + 2
     = T(n/8) + 3
       …закономерность: T(n/2ᵏ) + k
```

База наступает, когда `n/2ᵏ` доходит до 1 — то есть когда k равно числу делений n пополам: `k = log₂ n`. Посчитаем конкретно, потому что логарифмы заслуживают пальцев:

```
1000 → 500 → 250 → 125 → 62 → 31 → 15 → 7 → 3 → 1     ≈ 10 делений (2¹⁰ = 1024)
1 000 000 → … → 1                                      ≈ 20 делений (2²⁰ ≈ 1 048 576)
```

Миллион отсортированных записей — найдено за двадцать проб. Удвоение данных добавляет *один* шаг. Вот почему «отсортировано плюс пополам» — самая ценная форма в инженерии, а рекуррента — её чек.

## Два вызова на половинках: посуммируем уровни merge sort

Самая знаменитая сортирующая форма делит список пополам, рекурсивно сортирует *обе* половины и сливает их за n шагов застёжки-молнии:

```
T(n) = 2·T(n/2) + n
```

Развёртывание сработает, но картинка работает лучше. Нарисуем вызовы по уровням и просуммируем каждый уровень:

| Уровень | Подзадач | Размер каждой | Работа уровня |
| ------- | -------- | ------------- | ------------- |
| 0       | 1        | n             | n             |
| 1       | 2        | n/2           | 2 · n/2 = n   |
| 2       | 4        | n/4           | 4 · n/4 = n   |
| …       | …        | …             | n             |
| log₂ n  | n        | 1             | n             |

Каждый уровень стоит ровно n: задачи множатся, но сжимаются с той же скоростью. Значит, итог — *работа уровня × число уровней*:

```
T(n) ≈ n · log₂ n
```

Для миллиона элементов: 1 000 000 · 20 = 20 000 000 шагов — ближе к линейному, чем к пятимиллиардному квадрату. Картинка с суммой уровней — главный ключ к ценам «разделяй и властвуй». (Для этих паттернов есть знаменитая справочная таблица — мастер-теорема; вы встретите её в треке алгоритмов. Это ровно эта таблица в обобщённом виде; не пользуйтесь ею, пока не умеете рисовать уровни, которые она сворачивает.)

<Inset kind="practice" lang="ru">
Ремесло чек-листом на скорости код-ревью: (1) выпишите рекурренту прямо из кода — сколько стоит один вызов и на чём он рекурсит; (2) механически разверните три-четыре шага; (3) поймайте закономерность и запишите k-й шаг; (4) подберите k так, чтобы попасть в базу, и просуммируйте накопившееся; (5) сверьте маленькое n вручную или счётчиком вызовов. Пять минут арифметики — и сюрприз ночи запуска становится комментарием в ревью: этот filter делает импортёр квадратичным — 5·10⁹ шагов на проде.

## Заблуждение: «два рекурсивных вызова = вдвое медленнее»

Догадка разумная — и неверная в обе стороны. Сравним две функции, каждая из которых делает **два** рекурсивных вызова:

```
A:  T(n) = 2·T(n/2) + 1          (два вызова на ПОЛОВИНКАХ)
B:  T(n) = T(n-1) + T(n-2) + 1   (два вызова на n-1 и n-2 — фибоначчи)
```

Дерево вызовов A короткое и сбалансированное: log₂ n уровней, всего около 2n вызовов — едва хуже одного вызова. Дерево B сжимается лишь на 1 или 2 за уровень, оставаясь глубоким *и* продолжая ветвиться: оно взрывается экспоненциально. Посчитаем B для n = 6 — каждый узел ниже это один вызов:

```
fib(6)
├─ fib(5)
│  ├─ fib(4)
│  │  ├─ fib(3) …5 вызовов
│  │  └─ fib(2) …3 вызова
│  └─ fib(3) …5 вызовов
└─ fib(4) …9 вызовов
                    итого: 25 вызовов для n = 6
```

Двадцать пять вызовов ради fib(6) = 8 — причём один только `fib(3)` вычислен трижды. Счётчик делает взрыв осязаемым:

```js
let calls = 0;
function fib(n) {
  calls++;
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
}
fib(6);  console.log(calls); // 25
calls = 0;
fib(30); console.log(calls); // 2 692 537 — для n = 30!
```

Число вызовов задаётся не количеством рекурсивных вызовов в исходнике — его задаёт **форма дерева вызовов**: как быстро сжимается вход против того, насколько он ветвится. Два вызова на половинках — дёшево. Два пересекающихся вызова, едва сжимающих вход, — экспонента. Рекуррента видит разницу мгновенно; исходный код не показывает её вовсе.

<KeyTakeaway>Рекуррента — ценник рекурсии: работа слоя плюс стоимость меньшего себя. Четыре формы покрывают большую часть кода — T(n-1)+1 линейна, T(n-1)+n квадратична через Гаусса, T(n/2)+1 логарифмична, 2T(n/2)+n даёт n·log n по сумме уровней. Счёт решает форма дерева, а не число вызовов в исходнике.</KeyTakeaway>

Рекуррента считает работу рекурсии: T(n) равно работе одного слоя плюс стоимости меньшего себя, которого он вызывает. Ремесло решения неизменно — разверните три-четыре шага подстановкой, поймайте закономерность k-го шага, подберите k до базового случая, просуммируйте накопившееся и сверьте маленькое n вручную или счётчиком вызовов в коде. Четыре формы покрывают большую часть инженерии. T(n) = T(n-1) + 1 разворачивается в n + 1: линейность, честный перебор. T(n) = T(n-1) + n — маляр, перекрашивающий забор: сумма 1 + 2 + … + n, которую спаривание концов по Гауссу сворачивает в n(n+1)/2 — квадрат, форма, которая порхает по 200 строкам стейджинга и сжигает пять миллиардов шагов на 100 000 продовых записей. T(n) = T(n/2) + 1 — двоичный поиск: цена равна числу делений пополам, log₂ n — десять проб для тысячи, двадцать для миллиона. А T(n) = 2T(n/2) + n — merge sort, решаемый картинкой суммы уровней: каждый уровень стоит n, уровней log₂ n, итого n·log n; мастер-теорема, которую вы встретите позже, — эта таблица в обобщённом виде. Заблуждение в утиль: два рекурсивных вызова не означают двойную цену — дерево, делящее пополам, остаётся мелким (около 2n вызовов), а дерево фибоначчи почти не сжимается и перерешивает пересекающиеся подзадачи, взрываясь до 25 вызовов при n = 6 и 2,7 миллиона при n = 30. Счёт выставляет форма дерева вызовов, а не количество вызовов в исходнике — и одна строка арифметики читает его раньше, чем ночь запуска.
