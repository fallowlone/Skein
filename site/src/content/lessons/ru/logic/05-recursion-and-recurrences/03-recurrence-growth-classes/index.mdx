<Step title="Деление пополам: T(n) = T(n/2) + 1">

Двоичный поиск смотрит на средний элемент и отбрасывает половину диапазона. Одно сравнение на вызов — и задача вдвое меньше:

```
T(n) = T(n/2) + 1
```

Развернём:

```
T(n) = T(n/2) + 1
     = T(n/4) + 2
     = T(n/8) + 3
       …закономерность: T(n/2ᵏ) + k
```

База наступает, когда `n/2ᵏ` доходит до 1 — то есть когда k равно числу делений n пополам: `k = log₂ n`. Посчитаем конкретно, потому что логарифмы заслуживают пальцев:

```
1000 → 500 → 250 → 125 → 62 → 31 → 15 → 7 → 3 → 1     ≈ 10 делений (2¹⁰ = 1024)
1 000 000 → … → 1                                      ≈ 20 делений (2²⁰ ≈ 1 048 576)
```

Миллион отсортированных записей — найдено за двадцать проб. Удвоение данных добавляет *один* шаг. Вот почему «отсортировано плюс пополам» — самая ценная форма в инженерии, а рекуррента — её квитанция.

<Step title="Сумма уровней: T(n) = 2T(n/2) + n">

Merge sort делит список пополам, рекурсивно сортирует *обе* половины и сливает их за n шагов застёжки-молнии:

```
T(n) = 2·T(n/2) + n
```

Развёртывание сработает, но картинка работает лучше. Нарисуем вызовы по уровням и просуммируем каждый уровень:

| Уровень | Подзадач | Размер каждой | Работа уровня |
| ------- | -------- | ------------- | ------------- |
| 0       | 1        | n             | n             |
| 1       | 2        | n/2           | 2 · n/2 = n   |
| 2       | 4        | n/4           | 4 · n/4 = n   |
| …       | …        | …             | n             |
| log₂ n  | n        | 1             | n             |

Каждый уровень стоит ровно n: подзадачи множатся ровно с той скоростью, с которой сжимаются. Значит, итог — *работа уровня × число уровней*:

```
T(n) ≈ n · log₂ n
```

Для миллиона элементов: 1 000 000 · 20 = 20 000 000 шагов — ближе к линейному, чем к пятимиллиардному квадрату из прошлого урока.

<Inset kind="note" lang="ru">
Для этих паттернов суммы уровней существует знаменитая справочная таблица — **мастер-теорема**. Вы встретите её в треке алгоритмов. Это ровно эта таблица в обобщённом виде. Сначала картинка, потом таблица — таблица полезна только тогда, когда вы умеете рисовать уровни, которые она сворачивает.
</Inset>

</Step>

<Step title="Экспонента: T(n) = T(n-1) + T(n-2) + 1">

Наивная функция фибоначчи делает два рекурсивных вызова — но входы сжимаются лишь на 1 и 2:

```
T(n) = T(n-1) + T(n-2) + 1
```

Дерево остаётся глубоким *и* продолжает ветвиться. `fib(3)` вычисляется трижды внутри `fib(6)`:

```
fib(6)
├─ fib(5)
│  ├─ fib(4)
│  │  ├─ fib(3) …5 вызовов
│  │  └─ fib(2) …3 вызова
│  └─ fib(3) …5 вызовов
└─ fib(4) …9 вызовов
                    итого: 25 вызовов для n = 6
```

Счётчик делает взрыв осязаемым:

```js
let calls = 0;
function fib(n) {
  calls++;
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
}
fib(6);  console.log(calls); // 25
calls = 0;
fib(30); console.log(calls); // 2 692 537 — для n = 30!
```

Двадцать пять вызовов ради fib(6) = 8. При n = 30 это 2,7 миллиона вызовов. Дерево почти не сжимается, удваиваясь на каждом уровне — экспонента.

</Step>

<Step title="Форма дерева решает счёт">

Не поддавайтесь желанию считать вызовы в исходнике. Две функции могут делать по **два** рекурсивных вызова и давать совершенно разные цены:

```
A:  T(n) = 2·T(n/2) + 1          (два вызова на ПОЛОВИНКАХ)
B:  T(n) = T(n-1) + T(n-2) + 1   (два вызова на n-1 и n-2)
```

Дерево A короткое и сбалансированное: log₂ n уровней, около 2n вызовов суммарно. Дерево B сжимается лишь на 1 или 2 за уровень, оставаясь глубоким и продолжая ветвиться — экспонента.

Два вопроса, которые классифицируют любую рекурренту:
1. **Как быстро сжимается вход?** Деление пополам — быстро (log₂ n уровней). Вычитание 1 или 2 — медленно (n уровней).
2. **Сколько вызовов на каждом уровне?** Один — нет ветвления. Два на половинках — мелкое ветвление. Два на почти-одинаковых входах — взрывное ветвление.

Эти два параметра — скорость сжатия против коэффициента ветвления — полностью определяют класс роста. Количество вызовов в исходном коде не определяет его.

<WorkedExample title="Merge sort на n = 8 элементах" lang="ru">

Проследим таблицу суммы уровней для n = 8 (log₂ 8 = 3 уровня разбиения):

| Уровень | Подзадач | Размер | Работа |
| ------- | -------- | ------ | ------ |
| 0       | 1        | 8      | 8      |
| 1       | 2        | 4      | 8      |
| 2       | 4        | 2      | 8      |
| 3       | 8        | 1      | 8      |

Итого: 4 уровня × 8 = 32 шага.

По формуле: n · log₂ n = 8 · 3 = 24 (формула считает уровни разбиения, не базовый уровень — точный счёт для этой формы n · (log₂ n + 1) = 32). В любом случае при n = 8 цена в районе тридцати, а не сотен, которые даст квадратичная сортировка на тех же данных (8 · 9 / 2 = 36 — здесь близко, но разрыв взрывается при n = 1000: n·log n ≈ 10 000 против n² = 1 000 000).

Ключевое прозрение: **каждый уровень стоит одинаково n работы**, поэтому итог — просто n умножить на число уровней.

</WorkedExample>

<Recap lang="ru">
Три класса роста завершают карту рекуррент. T(n) = T(n/2) + 1 логарифмична: цена равна числу делений пополам, log₂ n — десять проб для тысячи отсортированных записей, двадцать для миллиона. T(n) = 2T(n/2) + n даёт n·log n: картинка суммы уровней показывает, что каждый уровень стоит n и уровней log₂ n, итого n·log n; мастер-теорема, с которой вы познакомитесь в треке алгоритмов, — эта таблица в обобщённом виде. T(n) = T(n-1) + T(n-2) + 1 экспоненциальна: вход почти не сжимается при двойном ветвлении, одни и те же подзадачи решаются повторно, и 25 вызовов при n = 6 превращаются в 2,7 миллиона при n = 30. Объединяющий урок: форма дерева вызовов — скорость сжатия входа против ширины ветвления — выставляет счёт. Два рекурсивных вызова в исходнике сами по себе ничего не значат: два вызова на половинках почти линейны, два вызова на почти-неизменных входах — взрыв. Рекуррента видит разницу мгновенно; исходный код не показывает её вовсе.
</Recap>
