<Crux>Валидность — это форма, запрещающая истинные посылки при ложном выводе. Modus ponens и modus tollens проходят проверку; их двойники — нет.</Crux>

## Посылки, выводы и что на самом деле значит «валидный»

**Аргумент** — это не спор. В логике это просто список утверждений: несколько **посылок** (то, что вы предполагаете или наблюдаете) и один **вывод** (то, что, по-вашему, из них следует). В релизную ночь посылок было две — «если кеш работает, латентность низкая» и «латентность низкая» — и один вывод: «кеш работает».

Аргумент **валиден**, когда его *форма* делает невозможной ситуацию, где все посылки истинны, а вывод ложен. Валидность — свойство формы, а не темы: «если идёт дождь, улица мокрая; дождь идёт; значит, улица мокрая» и «если кеш работает, латентность низкая; кеш работает; значит, латентность низкая» — один и тот же аргумент в разной одежде. Подставьте любые утверждения вместо P и Q — валидная форма продолжит работать.

Валидность ничего не говорит о том, истинны ли посылки на самом деле. Для этого есть второе слово: аргумент **корректен** (sound), когда он валиден *и* все его посылки истинны. «Все пятничные деплои падают; сегодня пятница; значит, сегодняшний деплой упадёт» — совершенно валидно и совершенно бесполезно, потому что первая посылка ложна. Валидная форма плюс ложные посылки не доказывают о мире ничего. В отладке нужны оба компонента: правило, которому вы действительно доверяете, и форма вывода, которая не способна вас предать.

<Inset kind="why" lang="ru">
Почему такая одержимость формой, а не содержанием? Потому что форма — единственное, что можно проверить механически, не зная ничего про кеши или погоду. Валидная форма — это контракт: подайте на вход истинные посылки, и она *гарантированно* выдаст истинный вывод, о чём бы ни шла речь. Именно эта гарантия позволяет проверке типов в компиляторе, планировщику запросов в базе и вашей собственной голове в три часа ночи использовать один и тот же набор правил вывода. Содержание может вам соврать; валидная форма — никогда: ей можно лишь скормить ложь.
</Inset>

## Два надёжных хода: modus ponens и modus tollens

Оба правила начинаются с условного утверждения — правила вида «если P, то Q», записывается P → Q. Дальше ровно два наблюдения дают право на вывод.

**Modus ponens** («утверждающий модус»): из P → Q и *истинного P* заключаем Q. Если кеш работает, латентность низкая; кеш работает (вы проверили флаг, видели, как растёт счётчик попаданий); значит, латентность низкая. Вы подтвердили часть «если» — часть «то» следует.

**Modus tollens** («отрицающий модус»): из P → Q и *ложного Q* заключаем не-P (записывается ¬P). Если кеш работает, латентность низкая; латентность *высокая*; значит, кеш **не** работает. Это скелет почти каждого реального шага отладки: *если бы моя гипотеза была верна, я бы увидел X; я не вижу X; гипотеза мертва.* Каждое несбывшееся предсказание валидно вычёркивает одного подозреваемого.

Обе формы можно проверить перебором — пройти все комбинации истины и лжи и поискать случай, где посылки выполняются, а вывод проваливается:

```js
// P → Q ложно только в одном мире: P истинно, Q ложно.
const implies = (p, q) => !p || q;

// Форма валидна, если НИ ОДНО присваивание не делает все посылки истинными, а вывод ложным.
function isValid(premises, conclusion) {
  for (const p of [true, false]) {
    for (const q of [true, false]) {
      const premisesHold = premises.every((f) => f(p, q));
      if (premisesHold && !conclusion(p, q)) return false; // контрпример найден
    }
  }
  return true;
}

// Modus ponens: из (p → q) и p заключаем q.
isValid([(p, q) => implies(p, q), (p, _q) => p], (_p, q) => q);   // true

// Modus tollens: из (p → q) и ¬q заключаем ¬p.
isValid([(p, q) => implies(p, q), (_p, q) => !q], (p, _q) => !p); // true

// Подтверждение консеквента: из (p → q) и q заключаем p.
isValid([(p, q) => implies(p, q), (_p, q) => q], (p, _q) => p);   // false!
// Контрпример: p = false, q = true. Кеш сломан, но латентность низкая по другой причине.
```

Четыре строки цикла делают то, что Аристотель делал вручную: первые две формы выдерживают любой мир; у третьей есть контрпример — она не доказывает ничего.

## Два самозванца: подтверждение консеквента и отрицание антецедента

**Подтверждение консеквента**: из P → Q и *истинного Q* заключить P. Это и есть релизная ночь: латентность низкая, значит, кеш работает. Невалидно — правило обещало лишь, что работающий кеш *даёт* низкую латентность; оно никогда не обещало, что у низкой латентности нет других причин. Низкий трафик, CDN, удачно прогретая база — Q может быть истинным при ложном P, и форма рушится.

**Отрицание антецедента**: из P → Q и *ложного P* заключить ¬Q. «Если кеш работает, латентность низкая; кеш сломан; значит, латентность обязана быть высокой». Тоже невалидно, по той же причине в зеркальном отражении: сломав одну причину низкой латентности, вы не запретили все остальные.

Обе ошибки ощущаются валидными, потому что используют те же три ингредиента, что и настоящие правила — условие и два факта, — только собранные в неправильном порядке. Полезная мысленная сигнализация: условие P → Q даёт опору ровно в двух случаях — *P подтверждено* или *Q опровергнуто*. Два других наблюдения — Q подтверждено, P опровергнуто — не дают **ничего**. Когда дашборд показывает хороший исход, вы узнали лишь, что гипотеза *выжила*, а не что она верна. Свидетельство, совместимое с теорией, — не свидетельство в её пользу, если оно и не могло выйти иначе.

## Отладка — это прикладной modus tollens

Сессия отладки — это цепочка условий: *если бы баг был в парсере, падающий ввод был бы битым; если бы база лежала, падали бы все эндпоинты, а не один; если бы кеш работал, этот ключ был бы на месте.* Каждый запускаемый тест пытается опровергнуть консеквент. Когда предсказание проваливается — ввод корректный, падает только один эндпоинт, ключа нет — modus tollens валидно вычёркивает подозреваемого. Хорошая отладка — это дисциплинированное накопление ¬P за ¬P, пока не останется одна гипотеза.

Дисциплина режет в обе стороны. Когда предсказание *сбывается*, сопротивляйтесь тёплому чувству: вы подтвердили консеквент, а это не вычёркивает ничего. Привычка сениора — проектировать проверки, чей *провал* был бы информативен: предсказания достаточно конкретные, чтобы у мира был реальный шанс их опровергнуть. «Если мой фикс работает, тест зеленеет» плюс зелёный тест — это утешение, а не доказательство; флаки-тесты тоже зеленеют. «Если мой фикс работает, тест зеленеет, *а откат фикса снова делает его красным*» — вот теперь у опровержения есть зубы, и пережить его что-то значит.

<Recap lang="ru">
Аргумент — это посылки плюс вывод, и слова «валидный» он заслуживает, когда его форма запрещает единственную фатальную комбинацию — все посылки истинны, вывод ложен — независимо от темы; слова «корректный» он заслуживает, лишь когда форма валидна и посылки вдобавок действительно истинны, и только этот вердикт гарантирует что-то о реальном мире. Условное правило P → Q поддерживает ровно два валидных хода: modus ponens (P подтверждено — заключаем Q) и modus tollens (Q опровергнуто — заключаем ¬P), и второй из них — скелет отладки: если бы моя гипотеза была верна, я бы видел X; я не вижу X; гипотеза вычеркнута. Два оставшихся наблюдения — ловушки с классическими именами: подтверждение консеквента (Q истинно, значит P — кешевая ошибка релизной ночи, игнорирующая другие причины низкой латентности) и отрицание антецедента (P ложно, значит и Q провалится). Зелёный дашборд или прошедший тест означают лишь, что гипотеза выжила, а не что она верна; проектируйте проверки, чей провал был бы информативен, накапливайте валидные опровержения и держите валидность и корректность раздельно на код-ревью — красивый вывод из ложной посылки не доказывает ровно ничего. Теперь, когда встретишь команду, которая заключает «кеш работает, ведь латентность низкая», у тебя есть имя этой ошибки и безопасная альтернатива — прямо рядом.
