## Четыре таблицы, которые определяют всё

**Связка** склеивает высказывания в более крупные высказывания. Истинность составного зависит *только* от истинности частей — и **таблица истинности** перечисляет все комбинации. Для двух входов строк всего четыре, так что полный смысл каждой связки виден одним взглядом:

| `p` | `q` | `p AND q` (`&&`) | `p OR q` (`\|\|`) | `p XOR q` |
|-----|-----|------------------|------------------|-----------|
| И   | И   | **И**            | И                | Л         |
| И   | Л   | Л                | **И**            | **И**     |
| Л   | И   | Л                | **И**            | **И**     |
| Л   | Л   | Л                | Л                | Л         |

И одновходовая таблица для **NOT** (`!`): НЕ И — это Л, НЕ Л — это И.

Три вещи, которые надо впитать. **AND** — самая строгая связка: истинна ровно в одной строке, когда истинны обе части. **OR** — *включающее*: истинно, когда истинна хотя бы одна часть, включая строку, где истинны обе. Это расходится с бытовой речью, где «суп или салат» обычно значит «не оба сразу». Исключающее прочтение — отдельная связка, **XOR**: истинна, когда части *различаются*. Перепутать их — реальный баг: «доступ получают премиум- ИЛИ триал-пользователи» почти всегда должно быть включающим (тот, кто и то и другое, очевидно должен пройти), а «вход A или вход B» на билете — XOR. Ключевого слова XOR в большинстве языков нет; для булей работает `a !== b`.

Таблицы — это *вся* дефиниция. В AND нет скрытого смысла сверх его колонки — а значит, любой вопрос о составном условии решается механически перебором строк. Четыре строки для двух переменных, восемь для трёх. Когда условие сбивает с толку, перестаньте рассуждать прозой и выпишите таблицу: проза — это ровно то место, откуда взялся баг из пролога.

## Де Морган: как НЕ проходит сквозь И и ИЛИ

Отрицание составного условия — место, где интуиция отказывает надёжнее всего, и **законы де Моргана** — механическое лекарство. Оба направления, в форме кода:

```js
!(a && b)  ===  (!a || !b)   // NOT (both)        = at least one fails
!(a || b)  ===  (!a && !b)   // NOT (at least one) = both fail
```

Паттерн: когда `!` распределяется по частям, связка *переворачивается* — И становится ИЛИ, ИЛИ становится И. Интуиция первого закона: «не оба» не требует, чтобы провалились оба; одного провала достаточно, чтобы сломать «оба». Баг из пролога, исправленный тремя эквивалентными способами:

```js
// Spec: block unless (verified AND active)
if (!(user.verified && user.active)) block(req);   // direct: negate the whole thing
if (!user.verified || !user.active) block(req);    // De Morgan: same table, flatter
if (!user.verified && !user.active) block(req);    // BUG: blocks only when BOTH fail
```

Багованная строка и правильные различаются ровно в двух строках таблицы из четырёх — там, где проваливается ровно одна проверка. А это в точности полуотозванные, полунастроенные, недомигрированные пользователи, которыми полон продакшен. Потому этот класс багов и переживает ревью: на лёгких строках (полностью «хороший» и полностью «плохой» пользователь) неверное условие ведёт себя правильно. Профессиональная привычка: всякий раз, когда пишете или ревьюите `!(...)`, мысленно примените де Моргана и проверьте смешанные строки — либо назовите условие позитивно (`const inGoodStanding = user.verified && user.active`) и отрицайте *имя*, чтобы отрицание вообще не касалось структуры.

## Короткое замыкание: таблица истинности слева направо

Рантайм не вычисляет обе стороны `&&`, чтобы потом свериться с таблицей. Он вычисляет *слева направо и останавливается, как только ответ определён*. Посмотрите на колонку AND: если `p` ложно, результат Л независимо от `q` — значит, `q` вообще не вычисляется. Симметрично для OR: истинное `p` уже даёт И, и `q` пропускается. Это **короткое замыкание** — тень таблицы истинности в исполняющем движке.

Прежде всего это инструмент безопасности: левая сторона может *охранять* правую:

```js
if (user && user.name.length > 0) { ... }
// user === null → left side falsy → right side never runs → no crash
```

А в JavaScript `&&` и `||` возвращают решающий *операнд*, а не буль — на этом держатся идиомы вроде `const port = config.port || 3000`. Но у того же пропуска есть острая кромка: всё, что стоит справа, *молча не происходит*, когда левая сторона уже всё решила. Если справа есть побочный эффект, он становится условным — хотели вы того или нет:

```js
let auditCount = 0;
function audit(u) { auditCount++; return true; }

function canAccess(u) {
  return u.isAdmin || audit(u);   // admins short-circuit past the audit
}

canAccess({ isAdmin: true });   // audit skipped!
canAccess({ isAdmin: false });  // audit runs
// auditCount === 1 — admin access was never logged
```

XOR, напротив, замкнуться накоротко не может никогда: ему всегда нужны оба входа, потому что результат зависит от того, различаются ли они.

<Inset kind="why" lang="ru">
Зачем языкам короткое замыкание, если в нём есть ловушка? Две причины. Производительность: правая сторона может быть дорогой (запрос к базе, сетевая проверка), и пропускать её, когда левая уже всё решила, — бесплатная скорость. Безопасность: идиома-охранник — слева проверка на null, справа разыменование — работает только потому, что правая сторона гарантированно не выполнится. Цена: порядок начинает иметь значение. У a &amp;&amp; b и b &amp;&amp; a одинаковые таблицы истинности, но разное поведение, когда одна из сторон может упасть или несёт побочный эффект. Таблица симметрична; исполнение — нет. Практическое правило: держите правую сторону &amp;&amp; и || чистой (без побочных эффектов), дешёвые проверки ставьте слева, дорогие — справа.
</Inset>

<Recap lang="ru">
Связки строят составные высказывания, истинность которых зависит только от частей, а таблицы истинности — их полная дефиниция: AND истинно ровно в одной строке из четырёх (обе части истинны), включающее OR ложно ровно в одной (обе ложны), XOR истинно при различии частей, NOT меняет единственное значение. Бытовое «или» часто исключающее, но || в коде — включающее; когда важно «не оба сразу», это XOR, для булей — a !== b. Отрицанием правят законы де Моргана: НЕ (a И b) равно (НЕ a) ИЛИ (НЕ b), а НЕ (a ИЛИ b) равно (НЕ a) И (НЕ b) — связка переворачивается, когда отрицание заходит внутрь. Распределить НЕ без переворота — канонический баг составных условий: он совпадает с правильным условием на однородных строках, которые гоняют ревью и happy-path-тесты, и расходится ровно на смешанных (одна проверка прошла, одна нет), которыми полон продакшен. Лечится перебором четырёх строк или именованием позитивного условия с отрицанием имени. В рантайме таблица исполняется слева направо с коротким замыканием: falsy слева решает И и пропускает правую сторону, truthy слева решает ИЛИ — это позволяет левой стороне охранять правую от падений и экономить дорогие вызовы, но молча отбрасывает любой правый побочный эффект, поэтому держите правые операнды чистыми. В JavaScript эти операторы возвращают сам решающий операнд: отсюда идиомы значений по умолчанию — и периодический сюрприз в виде null там, где ждали false.
</Recap>
