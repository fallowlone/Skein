<Explanation>
<strong>Пакетная обработка в продюсере Kafka</strong>
Продьюсер Kafka накапливает сообщения для каждой пары (топик, партиция) в памяти. Когда выполняется одно из условий:
- накопилось batch.size байт сообщений (по умолчанию 16 КБ), ИЛИ
- с момента последней отправки прошло linger.ms миллисекунд (по умолчанию 0, отключено)
...продьюсер отправляет один ProduceRequest, содержащий все накопившиеся сообщения.

<strong>Почему это помогает</strong>
Без пакетной обработки (linger.ms=0): каждое сообщение требует сетевого кругооборота (TCP-рукопожатие, TLS, запрос/ответ). При скорости 50 тыс сообщений/сек это даёт 50 тыс кругооборотов/сек — процессор загружен системными вызовами.
С пакетной обработкой (linger.ms=10мс, batch.size=64 КБ): продьюсер ждёт до 10 мс или 64 КБ, затем отправляет один запрос. Количество кругооборотов падает до 100-1000/сек — снижение в 50-500 раз.

<strong>COPY vs INSERT в Postgres</strong>
Postgres предлагает три способа вставки множества строк:
1. Одиночный INSERT: INSERT INTO tbl VALUES (1, 'a'); — один парс, один план, один коммит на строку
2. Многострочный INSERT: INSERT INTO tbl VALUES (1,'a'), (2,'b'), ...; — один парс, один план, один коммит для N строк
3. COPY: COPY tbl FROM STDIN; — собственный протокол, обходящий парс/план на строку, один коммит для N строк

<strong>Сравнение производительности</strong>
Для 1 млн строк по ~100 байт каждая:
- Одиночный INSERT: ~1 000-5 000 строк/сек (ограничен накладными расходами парс+план+коммит)
- Многострочный INSERT: ~5 000-50 000 строк/сек (лучше амортизация)
- COPY: ~50 000-500 000 строк/сек (лучшая амортизация, минимальные накладные расходы на строку)

<strong>Общий принцип</strong>
Оба примера показывают один и тот же принцип пакетной обработки:
- Фиксированная стоимость на операцию: сетевой кругооборот (Kafka), парс/план/коммит (Postgres)
- Переменная стоимость на байт: сетевая передача, запись на диск
- Когда фиксированная стоимость доминирует (маленькие сообщения/строки), пакетная обработка даёт ускорение в N раз
- Главный вопрос для старших инженеров: какой размер окна (batch.size + linger.ms, или размер пакета COPY) максимизирует пропускную способность, не нарушая SOL хвостовой латентности?

Для Postgres Bea использует одиночные INSERT; Sven использует COPY или многострочные INSERT.
</Explanation>

<KeyTakeaway>Продьюсер Kafka с linger.ms + batch.size и команда COPY в Postgres амортизируют фиксированную стоимость на многие операции. Настраивайте окно под потолок SLO, а не на максимальную пропускную способность.</KeyTakeaway>

<Recap lang="ru">
Пакетная обработка в продюсере Kafka (linger.ms + batch.size) и команда COPY в Postgres демонстрируют, как пакетная обработка амортизирует фиксированную стоимость. Kafka экономит на сетевых кругооборотах; Postgres экономит на накладных расходах парс/план/коммит. Во обоих случаях размер окна торгует пропускной способностью на хвостовую латентность, и старшие инженеры настраивают его под потолок SLO.
</Recap>
