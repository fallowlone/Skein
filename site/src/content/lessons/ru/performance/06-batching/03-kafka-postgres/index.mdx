<Hook>
Интересно, как Kafka обрабатывает миллионы сообщений в секунду или как Postgres быстро загружает терабайты данных? Ответ — в пакетировании: группировка операций для амортизации фиксированных затрат. В Kafka это batch.size и linger.ms; в Postgres — COPY против INSERT.
</Hook>

<Crux>
Пакет producer в Kafka собирает сообщения по размеру или времени; Postgres COPY быстрее INSERT за счет амортизации парсинга/коммита. Комплементарно выигрывает компрессия.
</Crux>

<Explanation>
У каждой операции есть фиксированная стоимость (сетевой round-trip, системный вызов, ACK) и переменная (размер полезной нагрузки). Когда фиксированная стоимость доминирует, пакетирование амортизирует ее по N операциям. Двумерное окно (max-size + max-wait) определяет, когда отправить пакет.

<strong>Пакеты в Kafka producer</strong>
Kafka producer аккумулирует сообщения на партицию (topic, partition). Пакет отправляется, когда выполняется одно из условий:
  • достигнут лимит batch.size (по умолчанию 16 КБ), или
  • истек таймер linger.ms (по умолчанию 0 мс — выключено).
Для повышения пропускной способности настраивают linger.ms (5-100 мс) и увеличивают batch.size (64-512 КБ). Компрессия (compression.type = lz4/snappy) применяется к пакету целиком — большие пакеты компрессируются лучше, снижая сетевые и дисковые издержки. Например, пакет 128 КБ с lz4 обычно сжимается в 2-4 раза, уменьшая трафик и стоимость fsync на брокере.

<strong>Массовые вставки в Postgres</strong>
Postgres INSERT VALUES (..., (...), ...) парсит и планирует один раз, затем коммитит один раз — значительно быстрее, чем построка INSERT. COPY самый быстрый: потоково передает данные в специальном протоколе, обходя парсер по строкам и используя один коммит. Бенчмарки:
  • Построка INSERT: ~1-5к строк/сек
  • INSERT VALUES (1000 строк): ~5-50к строк/сек
  • COPY: ~50-500к строк/сек
Используйте COPY для массовой загрузки; INSERT VALUES для умеренных пакетов; избегайте построка INSERT в горячих путях. ORMs предоставляют это: Django bulk_create, SQLAlchemy executemany.

<strong>Почему компрессия помогает в Kafka</strong>
Комплементарность снижает размер полезной нагрузки (переменную стоимость), делая фиксированную стоимость относительно большей и пакетирование более эффективным. Для повторяющихся данных (логи, события) lz4/snappy достигают 2-4x сжатия на пакетах 64-128 КБ. Затраты на CPU низки (~50-100 МБ/с/ядра) по сравнению с экономией сети/диска. Без пакетирования маленькие сообщения сжимаются плохо; пакетирование сначала позволяет эффективную компрессию.
</Explanation>

<KeyTakeaway>
Пакеты в Kafka используют batch.size и linger.ms; Postgres COPY выигрывает у INSERT за счет амортизации парсинга/коммита. Комплементарность усиливает выгоды пакетирования.
</KeyTakeaway>

<Recap lang="ru">
Пакет producer в Kafka собирает сообщения по размеру (batch.size) или времени (linger.ms); whichever happens first отправляет пакет. Postgres COPY эффективнее INSERT за счет отсутствия парсинга/планирования по строкам и единого коммита. Комплементарность (lz4/snappy) примененная к пакету увеличивает выгоды — большие пакеты компрессируются лучше. Обе технологии амортизируют фиксированные затраты: Kafka уменьшает сетевые round-trips, Postgres уменьшает SQL издержки. Настройте batch.size и linger.ms чтобы попасть в SLO по задержке, максимизируя пропускную способность; для Postgres используйте COPY для массовой загрузки, INSERT VALUES для умеренных пакетов.
</Recap>
