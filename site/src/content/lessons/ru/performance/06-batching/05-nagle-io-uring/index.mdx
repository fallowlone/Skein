<Explanation>
Основное понимание пакетирования вне времени: когда фиксированная стоимость на операцию доминирует (заголовки, системные вызовы, ACK), группируйте операции, чтобы платить эту стоимость один раз вместо N раз. Единственный вопрос проектирования — размер окна — как долго ждать или насколько расти.

<strong>Алгоритм Нагле: исходный компромисс пакетирования</strong>
RFC 896 (1984) Джона Нагла вводит то, что сейчас называется алгоритмом Нагле: TCP буферизует маленькие исходящие сегменты до получения ACK или пока буфер не заполнится до максимального размера сегмента (MSS) байт.
  • Мотивация: однобайтовые нажатия клавиш telnet → 40-байтовый TCP/IP-заголовок на байт данных → 97.5% накладных расходов
  • Механизм: задержка маленьких записей, надежда, что придут больше, чтобы заполнить сегмент
  • Компромисс: интерактивные приложения ждут следующей записи или ACK, ухудшая хвостовую латентность
  • Путь отступления: опция сокета TCP_NODELAY отключает Нагле; современные протоколы (HTTP/2, gRPC) обычно устанавливают TCP_NODELAY и выполняют пакетирование на уровне приложения вместо этого

<strong>Граница Парето латентность-пропускная способность</strong>
Каждая пакетирующая система описывает кривую: ось x = время ожидания пакета, ось y-1 = пропускная способность, ось y-2 = латентность.
  • Без пакетирования: наименьшая латентность, пропускная способность ограничена фиксированной стоимостью
  • Бесконечное пакетирование: максимальная теоретическая пропускная способность, латентность = ∞ для первого элемента
  • Старший рабочий процесс: определите потолок латентности SLO → найдите наибольшее окно пакетирования ниже него → точка التشغيل, максимизирующая пропускную способность
  • Адаптивные системы отслеживают эту кривую динамически; статические системы настраивают один раз

<strong>Coalescing пакетов и deduplication запросов</strong>
Специализированный паттерн для рабочих нагрузок кеш/поиск: когда конкурентные запросы спрашивают об одном и том же ключе, объедините их в один пакет.
  • Классический пример: обработка промаха кеша
  • Работник А промахивается в кеше по ключу K, начинает загрузку из БД
  • Работник Б также промахивается по K → присоединяется к ожидающему запросу А вместо дублирования работы
  • Возвращает одинаковый результат обоим
  • Реализации: singleflight (Go), AsyncLoadingCache Caffeine (Java), request collapsing в Varnish/CDN
  • Produktionsе влияние: горячий промах кеша с 100 одновременными запросами → 1 запрос к БД вместо 100 → предотвращает thundering-herd
  • Комбинированный с пакетной загрузкой (шаблон DataLoader): "все запросы в этом окне 10 мс для любой комбинации ключей → один пакетный запрос к БД"

<strong>Почему это важно сегодня</strong>
Линия от Нагле 1984 → Kafka linger.ms (2011) → io_uring submission queues (2019) представляет собой одну непрерывную закономерность:
  • Фиксированная стоимость: TCP-заголовок → сетевой round-trip → переход в системный вызов
  • Рычаг: амортизировать фиксированную стоимость на N операций
  • Вопрос: какой размер окна максимизирует пропускную способность, не нарушая SLO хвостовой латентности?
  • Ответ: измерьте фиксированную и переменную стоимость, настройте окно до потолка SLO по латентности
</Explanation>
