<Explanation>
Традиционный POSIX ввод-вывод — это один системный вызов за операцией: read(), write(), recv(), send(). Каждый стоит ~1-5 мкс переключения контекста. Для сервиса, выполняющего 100k операций ввода-вывода в секунду, это 100-500 мс/сек, потраченных únicamente на переходы в системные вызовы. Пакетные системные вызовы уменьшают эти накладные расходы.

<strong>Основы io_uring</strong>
io_uring (ядро Linux 5.1+) использует два кольцевых буфера, отображаемые в память между пользовательским пространством и ядром:
- Очередь подачи (SQ): пользователь помещает сюда дескрипторы операций
- Очередь завершения (CQ): ядром здесь публикуются результаты
В режиме опроса (IORING_SETUP_SQPOLL) отдельный поток ядра непрерывно опрашивает SQ — пользователь может отправлять операции с нулевым количеством системных вызовов. Результат: при 1M операций/сек традиционные read/write тратят ~1 мс/сек только на системные вызовы; режим опроса io_uring уменьшает это до почти нуля.

<strong>Примитивы пакетирования во время выполнения</strong>
Каждый основной runtime поставляется с API-пакетированием:
- Node.js: stream.cork()/uncork() для пакетной записи, setImmediate/process.nextTick для микропакетов
- Go: bufio.Writer для буферизованной записи, каналы + ticker для пакетирования по временному окну
- Java: BufferedOutputStream, очередь записи async-profiler
- Python: asyncio.Queue с потребителями-пакетировщиками
- Rust: каналы tokio mpsc с адаптерами пакетирования
Каждый предоставляет ограниченный буфер, параметры max-size + max-wait и явный flush.

<strong>Наблюдаемость для пакетирования</strong>
Готовая к production наблюдаемость отслеживает четыре метрики на партию:
1. Гистограмма размера пакети — действительно ли пакеты заполняются или срабатывает таймер? p50/p99 в записях/байтах
2. Время ожидания пакета — как долго элементы ждали перед отправкой
3. Датчик глубины буфера — текущее количество элементов в памяти буфера ( spikes = обратное давление downstream)
4. Счетчик отброшенных — элементы, отброшенные из-за переполнения буфера (должно быть 0; ненулевое значение = сигнал обратного давления)
Панель управления: временные ряды всех четырех с оповещениями при drop count > 0 и buffer depth > 80% пределе.

<strong>Почему io_uring имеет значение</strong>
Помимо чистой производительности, io_uring обеспечивает новые паттерны:
- Связанные операции: следующая SQE выполняется после завершения предыдущей
-Выбор буфера: ядро выбирает из зарезервированного пула буферов (избегая регистрации буфера на операцию)
- Фиксированные файлы: пропуск поиска дескриптора файла на системный вызов
Принятие: PostgreSQL 17 добавил бекенд io_uring, у Ceph есть экспериментальная поддержка, async-profiler Netflix сообщает о снижении CPU на 5-15% на TLS-прокси.
Примечание по безопасности: у io_uring были CVE (CVE-2023-2598, CVE-2024-0582); некоторые рантаймы контейнеров отключают его по умолчанию через seccomp.
</Explanation>

<KeyTakeaway>
io_uring устраняет накладные расходы на системный вызов на операцию через кольцевые буферы подачи/завершения; наблюдаемость отслеживает гистограмму размера пакета, время ожидания, глубину буфера и счетчик отброшенных для обнаружения обратного давления и потребностей в настройке.
</KeyTakeaway>

<Recap lang="ru">
io_uring использует два отображаемых в память кольцевых буфера (подача + завершение) для пакетирования системных вызовов; режим опроса достигает почти нулевого накладного расхода на системные вызовы. Примитивы пакетирования во время выполнения (bufio.Writer, stream.cork() и т.д.) обеспечивают пакетирование с параметрами max-size + max-wait. Наблюдаемость требует четырех метрик: гистограмма размера пакета (поведение заполнения), время ожидания (latency), глубина буфера (обратное давление), счетчик отброшенных (переполнение). Вместе они позволяют настраивать окна пакетирования, чтобы попадая в потолок SLO по задержке, максимизируя пропускную способность.
</Recap>
