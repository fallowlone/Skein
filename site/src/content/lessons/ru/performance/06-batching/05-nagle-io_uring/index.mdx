<Crux>Алгоритм Нагла буферизует записи TCP; io_uring буферизует системные вызовы. Оба обменивают латентность на пропускную способность, амортизируя фиксированную стоимость (заголовок, переключение контекста).</Crux>

<Explanation>
<strong>Алгоритм Нагла</strong>
RFC 896 Джона Нагеля (1984) ввёл то, что сейчас называется алгоритмом Нагла: TCP буферизует маленькие исходящие сегменты до выполнения одного из условий:
- получен ACK за предыдущий сегмент, ИЛИ
- буфер заполнился до размера Maximum Segment Size (MSS) байт

Мотивация: однобайтовые нажатия клавиш Telnet создавали пакеты TCP/IP в 41 байт (1 байт данных + 40 байт заголовка), тратя 97.5% пропускной способности на заголовки.

Как это работает:
1. Приложение записывает() данные в сокет
2. Реализация TCP проверяет: есть ли незаACKED данные, ожидающие отправки?
   - Если да: буферизует новые данные до прибытия ACK ИЛИ пока буфер не достигнет MSS
   - Если нет: отправляет немедленно (без буферизации для первой записи)
3. При выполнении условий: отправляет буферизованные данные как один TCP-сегмент

Компромисс: интерактивные приложения (Telnet, SSH) испытывают zvýšenou latenci, потому что ждут ACK или полного буфера перед отправкой. Опция TCP_NODELAY сокета отключает алгоритм Нагла для протоколов, чувствительных к латентности.

<strong>Глубокий анализ io_uring</strong>
io_uring (Linux 5.1+) — современный асинхронный интерфейс ввода-вывода, использующий два кольцевых буфера:
- Очередь отправки (SQ): пользователь отправляет дескрипторы операций
- Очередь завершения (CQ): ядро публикует результаты

Режимы:
1. По умолчанию: приложение вызывает io_uring_enter() для уведомления ядра → ядро пакетирует обработку всех записей SQ
2. Опрос (IORING_SETUP_SQPOLL): ядро continuously опрашивает SQ → приложение может отправлять с нулевыми системными вызовами
3. Буферизация ввода-вывода приложения: пользовательские буферы в пользовательском пространстве для уменьшения записей SQ

Влияние на производительность:
- Традиционные read()/write(): ~0.5-2 мкс на системный вызов переключения контекста
- При 500k операций/сек: 250-1000 мкс/сек тратится на системные вызовы (1-2 ядра процессора)
- io_uring по умолчанию: 1 системный вызов на пакет → 500k/100 = 5k системных вызовов/сек → 2.5-10 мкс/сек
- io_uring с опросом: ~0 системных вызовов/сек → пренебрежимо мало накладных расходов переключения контекста

Старшие команды наблюдают снижение CPU на 5-15% на TLS-прокси и базах данных. Уязвимости безопасности заставили некоторые среды выполнения контейнеров отключать io_uring по умолчанию — взвешивайте компромиссы для вашего развёртывания.

<strong>Связь</strong>
И алгоритм Нагла, и io_uring решают одну и ту же проблему: фиксированная стоимость на операцию доминирует при высоких скоростях.
- Алгоритм Нагла: фиксированная стоимость = 40-байтовый TCP/IP-заголовок на пакет
- io_uring: фиксированная стоимость = переключение пользовательское→ядро→пользовательское на системный вызов
Оба буферизуют операции, чтобы амортизировать эту фиксированную стоимость на N единиц работы.

<PersonaTag id="bea" lang="ru"/> имеет включённую опцию TCP_NODELAY и использует традиционные системные вызовы; низкая латентность, высокий расход CPU на системные вызовы. <PersonaTag id="sven" lang="ru"/> использует алгоритм Нагла (по умолчанию) и io_uring; более высокая латентность, но намного меньший расход CPU.
</Explanation>

<KeyTakeaway>Алгоритм Нагла и io_uring оба применяют принцип пакетной обработки на разных уровнях (TCP, системные вызовы) для амортизации фиксированной стоимости. Обменивайте латентность на пропускную способность; настраивайте под потолок SLO.</KeyTakeaway>

<Recap lang="ru">
Алгоритм Нагла (TCP) и io_uring (системные вызовы) оба демонстрируют, как пакетная обработка амортизирует фиксированную стоимость на разных уровнях. Алгоритм Нагла экономит на TCP/IP-заголовках; io_uring экономит на накладных расходах переключения контекста. Оба обменивают увеличенную латентность на рост пропускной способности, и главный вопрос для старших инженеров всегда таков: какой размер окна максимизирует пропускную способность, не нарушая SOL хвостовой латентности?
</Recap>
