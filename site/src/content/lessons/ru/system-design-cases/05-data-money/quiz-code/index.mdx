## Сниппет 3 — дебет кошелька

```python
def debit(wallet_id, amount):
    bal = db.query("SELECT balance FROM wallets WHERE id = ?", wallet_id)
    if bal >= amount:
        db.execute("UPDATE wallets SET balance = ? WHERE id = ?", bal - amount, wallet_id)
        return "ok"
    return "insufficient"
```

## Сниппет 4 — многоночная бронь

```python
def reserve(room_type, nights):  # nights = [Dec31, Jan1, Jan2]
    for night in nights:
        db.execute(
          "UPDATE inventory SET booked = booked + 1 "
          "WHERE room_type = ? AND date = ? AND booked < total",
          room_type, night)
    return "reserved"   # каждая ночь обновлена независимо, без транзакции
```

<Recap lang="ru">
Каждый баг данных-и-денег читается прямо с кода. Неограниченный **лейбл метрики** (user_id) форкает ряд на значение и OOM'ит TSDB — кардинальность рядов, не темп запросов, ограничение, так что убери его из лейблов. **Списание**, что клиент повторяет без **ключа идемпотентности**, списывает дважды, когда первый ответ потерян — передай клиентом отчеканенный ключ с атомарным check-and-store. **Дебет кошелька**, что читает баланс, затем пишет обратно, имеет зазор чтения-записи, что эксплуатируют два конкурентных дебета (**потерянное обновление**) — схлопни в один атомарный условный UPDATE. И **многоночная бронь**, что декрементит каждую ночь вне транзакции, может оставить **частичную бронь** — оберни весь диапазон в одну транзакцию всё-или-ничего. Senior-привычка одна для всех четырёх: найди угрозу, назови её и сделай операцию ограниченной (кардинальность) или атомарной (идемпотентность, потерянное обновление, частичная запись) — починку, что требует механизм, не ту, что её прячет.
</Recap>
