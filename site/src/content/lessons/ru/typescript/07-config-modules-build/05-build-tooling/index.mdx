## Две совершенно разные задачи: проверка против транспиляции

`tsc` делает **две** вещи: *проверяет типы* (анализирует всю программу на ошибки типов) и *генерирует* JavaScript. Бандлеры разделяют их и оставляют только вторую:

<div data-lesson-visual class="overflow-x-auto my-6">

| инструмент | проверяет типы? | emit | скорость | видит другие файлы? |
| --- | --- | --- | --- | --- |
| `tsc` | да (вся программа) | JS + `.d.ts` | медленно | да — межфайловый анализ |
| `esbuild` | **нет** | JS | очень быстро | нет — по одному файлу |
| `swc` | **нет** | JS | очень быстро | нет — по одному файлу |
| `babel` (preset-typescript) | **нет** | JS | быстро | нет — по одному файлу |
| `tsc --noEmit` | да | ничего | медленно | да — CI-гейт типов |

</div>

Причина, по которой бандлеры в 10–100× быстрее `tsc`, *именно* в том, что они не проверяют типы. Анализ типов требует построения графа всей программы; транспиляция просто удаляет синтаксис типов токен за токеном в одном файле. Ошибка типа им невидима — это просто синтаксис, который они стирают.

## `isolatedModules`: делаем однофайловую транспиляцию безопасной

Если твоя команда использует esbuild или swc для emit, есть целый класс валидного TypeScript, который молча сгенерирует неправильный JavaScript — не ошибку, а просто сломанный бандл. `isolatedModules` — флаг, который ловит такие конструкции в редакторе, а не в рантайме.

Поскольку esbuild/swc/babel компилируют **по одному файлу за раз**, не зная о других файлах, некоторые конструкции TypeScript *небезопасно* так транспилировать — им нужна информация о всей программе. `isolatedModules: true` заставляет `tsc` помечать именно такие конструкции, чтобы твой код был портируем на однофайловый транспилятор:

```ts
// с isolatedModules эти конструкции дают ошибку в tsc:

// 1. type-only реэкспорт, ВЫГЛЯДЯЩИЙ как реэкспорт значения:
export { SomeType } from "./types";
//       ^^ ~TS1205: однофайловый компилятор не может понять, SomeType — это
//          тип (стереть экспорт) или значение (оставить). Фикс:
export type { SomeType } from "./types"; // теперь однозначно — стереть

// 2. const enum между файлами — нужны значения enum, вшитые из другого файла:
import { Color } from "./enums";
const c = Color.Red; // const enum нельзя вшить без межфайловой информации
```

`isolatedModules` не меняет emit; он *ограничивает то, что можно писать*, чтобы пофайловая транспиляция давала корректный вывод. Две главные вещи, которые он фактически запрещает: **`const enum`, потребляемый между файлами** (однофайловый компилятор не может вшить значения, которых не видит) и **неоднозначные type-only реэкспорты** (вынуждая `export type` / `import type`).

<Inset kind="why" lang="ru">
Почему однофайловый транспилятор не справляется с `export { SomeType } from "./types"`? Потому что для генерации корректного JS он должен решить, `SomeType` — это *тип* (стереть реэкспорт целиком — типы не существуют в рантайме) или *значение* (оставить реэкспорт). Это решение требует открыть `./types` и проверить, что такое `SomeType` — межфайловое знание, которое транспилятор ради скорости собирать отказывается. `export type { SomeType }` говорит ему однозначно «это тип, сотри», поэтому `isolatedModules` (и `verbatimModuleSyntax`) подталкивают к явным модификаторам `type`.
</Inset>

## Паттерн: бандлер собирает, `tsc --noEmit` гейтит

Production-настройка развязывает две задачи. Бандлер быстро производит артефакт; `tsc --noEmit` (часто `tsc -b --noEmit` для монорепо) запускается параллельно или в CI чисто чтобы *проверить типы* — он ничего не генерирует, лишь валит сборку, если тип неверен:

```jsonc
// скрипты package.json
{
  "scripts": {
    "build": "vite build",            // esbuild транспилирует — БЕЗ проверки типов
    "typecheck": "tsc --noEmit",      // настоящий гейт типов — ничего не генерирует
    "ci": "npm run typecheck && npm run build"
  }
}
```

`verbatimModuleSyntax` (TS 5.0) усиливает это: он делает emit import/export буквальным, так что обычный `import` всегда сохраняется, а стираются только `import type`/`export type`. Эта предсказуемость и нужна транспилятору — никакого угадывания, был ли импорт «использован как значение». Он заменяет старый `importsNotUsedAsValues` и закрывает те же однофайловые заботы, которые помечает `isolatedModules`. (Заметь: сам `tsc` всё ещё делает declaration emit — генерацию `.d.ts` — чего транспилятор не делает никогда, поэтому сборки библиотек оставляют `tsc` для типов, даже когда JS производит esbuild.)

<KeyTakeaway>
`tsc` и **проверяет типы** (анализ всей программы), и **генерирует** JS; бандлеры (esbuild, swc, babel) оставляют только половину с emit — они **транспилируют каждый файл изолированно и никогда не проверяют типы**, поэтому они в 10–100× быстрее и поэтому настоящая ошибка типа проходит сквозь сборку нетронутой (аннотация *стирается*, а не *проверяется*). Поскольку у однофайловых транспиляторов нет межфайлового знания, `isolatedModules: true` заставляет `tsc` помечать конструкции, которым нужна информация о всей программе: он фактически запрещает **`const enum`, потребляемый между файлами** (значения нельзя вшить, не видя исходник) и **неоднозначные type-only реэкспорты** (надо писать `export type` / `import type`). Production-паттерн развязывает задачи: бандлер быстро собирает, а **`tsc --noEmit` работает отдельным гейтом** (в CI), который ничего не генерирует и существует только чтобы упасть на ошибках типов. `verbatimModuleSyntax` (TS 5.0) делает стирание импортов буквальным и предсказуемым — срезаются только `import type`/`export type` — именно это нужно транспилятору; а declaration emit `.d.ts` по-прежнему за `tsc`, чего не делает ни один транспилятор.
</KeyTakeaway>

<Recap lang="ru">
Теперь ты знаешь разделение труда, определяющее современную сборку TypeScript: транспиляторы генерируют JS пофайлово и никогда не проверяют типы, `isolatedModules` держит код безопасным для этой модели (нет межфайловых const enum, явный `export type`), а `tsc --noEmit` — гейт, реально обеспечивающий безопасность типов, пока бандлер отвечает за скорость. Это закрывает юнит config/modules/build. Дальше, в **TypeScript на практике**, мы применяем всё это — частые ловушки, где эти тонкости конфига и emit бьют команды в production-коде. Теперь, когда видишь ошибку типа, проскользнувшую в production через Vite-сборку, знаешь, чего не хватало: `tsc --noEmit` никогда не был в CI-пайплайне.
</Recap>
