A database can only truly execute as many queries at once as it has CPU cores (plus a little headroom for I/O-stalled queries); every connection beyond that is waiting, not running, and that waiting is not free. Surplus connections pay context-switch cost time-slicing across few cores, super-linear lock and latch contention on shared internal structures, and per-connection memory where Postgres work_mem is allocated per operation per connection. So past the useful count more connections buy contention, and throughput falls while latency rises. The formula is connections = (core_count x 2) + effective_spindle_count: double the cores so a freed core can run another query through an I/O stall, plus one per independent disk. A 4-core, one-SSD box lands at (4 x 2) + 1 = 9, and a pool of about 10 routinely beats a pool of 100 on the same hardware." },

Set far too short (e.g. 50 ms) it fails benign micro-bursts. A bigger pool is a poor fix because a leak is a rate, not a fixed cost — it drains any pool at the speed the buggy branch runs — so size only changes the timeline, and worse, the larger pool hides the cause by delaying the symptom hours past the deploy. You cannot just raise max_connections to 1,000 — that recreates the sizing lesson's contention at the server's scale. <Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: a pool amortises expensive setup and bounds concurrency; its size is small and derived from cores, not guessed large; the acquisition timeout decides fail-fast vs thread starvation; connections go stale behind the pool's back and must be rotated by maxLifetime (under the DB timeout) and validated on borrow; the most common outage is a leak or a hoard, fixed by guaranteeing the return rather than enlarging the pool; and at scale many pools fan into one max_connections, forcing a transaction-pooling multiplexer that trades session state for the ratio. The connection is a hard, shared, expensive resource — bound it deliberately at every layer.
</Recap>
