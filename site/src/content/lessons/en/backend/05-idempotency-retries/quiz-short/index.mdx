    { q: "Give the full-jitter backoff formula, explain why jitter is non-negotiable, and say why a per-request retry cap is not enough.", a: "delay = random(0, min(cap, base × 2^attempt)); base is the minimum wait (100–500ms), cap the maximum (30–60s), attempt the zero-indexed try. Jitter is non-negotiable because without it every client that failed at the same instant picks the identical delay and retries in the same tick — a synchronised thundering herd that re-kills the recovering service, turning a 30-second blip into a long outage. A per-request cap of 3–6 attempts limits one caller but not the fleet: 10k concurrent callers each burning 6 attempts is 60k retries in a short window. A retry budget — a token-bucket of allowed retries per second across the whole call site — imposes a fleet-wide ceiling and opens a circuit when exhausted, so callers fail fast instead of amplifying the outage. There is no atomic 'two separate writes'. The outbox pattern writes the event into an outbox table inside the same transaction as the business write, so atomicity becomes Postgres's job — the outbox row exists if and only if the business write committed. A relay (polling, or Debezium tailing the WAL) publishes unpublished rows at-least-once, marking them on broker ACK; if it crashes after publishing but before marking, it re-publishes. The consumer applies the inbox pattern — INSERT the event_id into processed_events ON CONFLICT DO NOTHING inside its own transaction — so a duplicate delivery is skipped. Composition: Postgres atomicity + at-least-once relay + idempotent consumer = effectively-once." },

The winner gets a row back and processes; the loser gets an empty RETURNING, re-reads the row, and returns 409 (in_progress) or replays (completed). pg_advisory_xact_lock is an alternative but holds the lock for the whole transaction including slow external calls, risking pool exhaustion.
