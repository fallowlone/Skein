One is an ordered pipeline a request travels; the other is an object graph assembled before any request arrives.     { q: "State the Express middleware contract and the two ways it is broken.", a: "An Express middleware (req, res, next) must do exactly one of three things: call next() to pass control to the next layer; terminate by sending a response (res.json, res.end) without calling next, short-circuiting the chain; or call next(err) to jump to error-handling middleware. It is broken in two ways. Doing both — sending a response and also calling next(), or letting two paths each respond — causes a double-send and the 'Cannot set headers after they are sent' error. Doing neither — no response and no next() — hangs the request until it times out. Error middleware additionally must declare four parameters (err, req, res, next) and be registered last, or Express treats it as ordinary middleware and never routes errors to it." },
    { q: "What is inversion of control, what does the composition root do, and why is a service locator an anti-pattern?", a: "Inversion of control means a class declares what it needs (an abstraction like a PaymentGateway) instead of constructing the concrete implementation with new; something external supplies the concrete instance. Constructor injection is the honest form — dependencies are visible in the signature and a missing one fails at startup. The composition root is the single place near the entry point where the whole object graph is assembled and the only place that names concrete implementations, so wiring lives at the edge and logic in the middle stays dependency-free. A service locator also avoids new but has the class fetch dependencies from a global registry (Container.get), which re-hides them from the signature and defers failure to runtime deep in a code path. It is legitimate only inside the framework or composition root, not scattered through business logic." },
    { q: "Name the three DI scopes, the trap each invites, and the rule that avoids both main traps.", a: "Singleton creates one instance for the whole process, shared by every request — the default, ideal for stateless services, clients, and pools; its trap is holding per-request state, which leaks data across concurrent users because the field is shared. Request-scoped creates one instance per request; its trap is scope bubbling — a single shared consumer cannot hold a per-request dependency, so the request lifetime propagates up the injection chain and the container reinstantiates a large slice of the graph on every request, adding allocation and latency. Transient creates a fresh instance per injection and does not bubble, since a singleton can safely keep one transient. The rule: default to stateless singletons and pass per-request data as method arguments; escalate to request scope only when per-request identity genuinely cannot be passed." },
    { q: "What is the test seam, and what is the difference between a fake and a mock?", a: "The seam is the injection point where production wiring is swapped for test wiring — it exists precisely because a class receives a collaborator (a PaymentGateway) rather than constructing a StripeClient, so a test can pass in a substitute. A fake or stub provides realistic state — for example an in-memory-Map-backed repository you can save to and read back — and your assertions check the outcome (the order is persisted, the total is right), so it only breaks when behavior actually changes. A mock is programmed with expectations about calls and asserts the interaction (charge was called once with this amount); because a mock expectation is itself an assertion about the implementation, it breaks on any change to call shape even when behavior is preserved. The discipline: mock the boundaries you do not own (payment, email, clock), fake what you own, and read 'needs ten mocks' as a design smell." },

It is the composition root mechanized. A topological sort exists only for an acyclic graph, so a cycle (A needs B, B needs A) has no leaves-first order and the container refuses; it can pass in dev and crash in prod because resolution follows module load order, making a true cycle a nondeterministic latent bug. The real fix is to extract a shared third class, not to paper over it with forwardRef. Eager instantiation builds the whole singleton graph at boot, so a missing env var or unresolvable dependency crashes the boot — loud, deploy-time, caught by CI — instead of a quiet first-request failure later; servers should prefer it, and for tiny graphs hand-wiring in a composition root is often clearer than a container at all." },
