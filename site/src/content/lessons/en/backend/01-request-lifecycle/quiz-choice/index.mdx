<Quiz
  id="01-request-lifecycle-choice-1"
  lessonSlug="01-request-lifecycle"
  lang="en"
  question="Under a traffic burst, clients get connection timeouts and resets, but the application logs are completely empty — no 500s, no handler traces. Which stop, and why are the logs empty?"
  choices={[
    { label: "Accept. The kernel accept queue — bounded by min(listen backlog, somaxconn), often still 128 — filled because the process stopped calling accept() fast enough, so the kernel dropped completed connections before they ever reached your code. No code ran, so nothing logged.", correct: true },
    { label: "Handle. An uncaught exception in the handler crashed the request.", misconception: "An exception runs inside your code, so it appears in the logs and usually returns a 500. Empty logs mean the request never reached the application at all — the drop is upstream, in the kernel accept queue." },
    { label: "Serialize. JSON.stringify on a large response blocked the event loop.", misconception: "Serialization happens long after accept(), on requests that did reach your code. If connections are refused before any handler runs, serialization is irrelevant and there would still be logs for requests that got through." },
    { label: "Drain. Backpressure was ignored and the response buffered in memory.", misconception: "Ignored backpressure OOMs on responses being actively written — that produces a crash with heap-growth symptoms, not silent connection refusals with empty logs during the burst." },
  ]}

  question="A security review finds one admin endpoint serves unauthenticated requests, even though the auth middleware is implemented, tested, and registered. What is the most likely cause?"
  choices={[
    { label: "The route was registered before the auth middleware, so the handler short-circuited the request to a response before auth ever got control. Middleware order is a security boundary: protective layers must be registered ahead of the routes they guard.", correct: true },
    { label: "The radix-trie router matched the wrong path pattern.", misconception: "Reaching the correct admin handler means routing worked. The failure is that nothing authenticated the request before the handler ran — an ordering bug, not a matching bug." },
    { label: "The auth token format changed and the middleware can no longer parse it.", misconception: "A parse/format problem would reject valid users (deny access), not grant access to unauthenticated ones. Allowing everyone through points to auth never executing, which is an ordering issue." },
    { label: "Routing is O(n) so the request timed out before auth could run.", misconception: "Routing is microseconds regardless of route count, and a timeout would not silently skip auth — it would fail the request. The handler simply ran ahead of the auth layer in registration order." },

  question="An endpoint is 40% slower after its result set grew from 50 to 5,000 rows, yet the database query time is unchanged at 8 ms. Where did the time go, and what is the first fix?"
  choices={[
    { label: "Serialize. JSON.stringify is synchronous and scales with object size, so the 100×-larger payload now costs several ms of CPU and blocks the event loop. First fix: paginate, and consider a precompiled schema serializer (2–4× faster) on the hot path.", correct: true },
    { label: "Route. The larger response made route matching slower.", misconception: "Route matching cost is independent of response size (and is microseconds anyway). Result-set size affects producing the response, not finding the handler." },
    { label: "Accept. The bigger payload overflowed the accept queue.", misconception: "The accept queue bounds pending connections, not response size. It refuses connections under load; it does not make a successful response slower in proportion to its row count." },
    { label: "Drain. Keep-alive was disabled, adding handshake cost per request.", misconception: "Keep-alive affects connection-setup cost, which does not scale with the number of rows in one response. A 40% slowdown tracking payload size points at serialization." },

<Quiz
  id="01-request-lifecycle-choice-4"
  lessonSlug="01-request-lifecycle"
  lang="en"
  question="A streaming export OOMs only when a client downloads over a slow link. The code calls res.write() in a loop and ignores the return value. What is the precise mechanism?"
  choices={[
    { label: "res.write() returns false when the writable buffer crosses the high-water mark (16 KB default) — a flow-control signal that the consumer is behind. Ignoring it and writing anyway piles unread bytes into the process heap, the one layer with no flow control, until the kernel OOM-kills it.", correct: true },
    { label: "false means the write failed, so the loop retries and duplicates data until memory fills.", misconception: "false does not mean failure — the data was accepted into the buffer. It is a backpressure signal meaning 'slow down', not 'retry'. The growth is unread data buffered in userland, not duplicated writes." },
    { label: "The garbage collector cannot run while a connection is open, so the heap grows.", misconception: "GC runs normally; it simply cannot reclaim buffers still referenced by the pending write queue. The bytes are live data the consumer has not read, not garbage." },
    { label: "Slow links corrupt TCP checksums, forcing retransmits that consume memory.", misconception: "Retransmits are normal and bounded by the TCP stack; they do not cause unbounded heap growth. The growth is application-level: production rate decoupled from the client's read rate." },
  ]}
/>

<Quiz

  lang="en"
  question="A product page fans out to 100 independent services in parallel and waits for all. Each has a p99 of 10 ms (1% chance a call exceeds it). Roughly what fraction of page loads exceed 10 ms on at least one call, and what is the durable fix?"
  choices={[
    { label: "About 63%: you wait for all, so you are slow if any one is slow — 1 − 0.99^100 ≈ 0.63. The durable fix attacks the tail itself: hedge slow requests at ~p95 to a second replica, which collapses p99.9 for only a few percent extra load.", correct: true },
    { label: "About 1% — the same as a single service, since each call is independent.", misconception: "1% is the per-call rate. With 100 independent calls and a wait-for-all join, the chance that none is slow is 0.99^100, so the slow fraction compounds to ≈63%. Independence does not protect you when you wait for all." },
    { label: "About 10% — tail probability scales linearly with the fan-out count.", misconception: "Tail amplification is not linear. The compounding 1 − (1 − p)^N grows far faster than a linear estimate; at p=1%, N=100 it is ≈63%, not 10%." },
    { label: "0% — parallel calls overlap, so they cannot all be slow at the same time.", misconception: "You are slow if any one is slow, not only if all are. Waiting for all means a single slow dependency among 100 sets the whole page's latency — which is exactly what amplifies the tail." },
  ]}

  question="A request has a 1 s SLA. Service A (client timeout 1 s) calls service B (client timeout 1 s). When B hangs, A keeps working for the full second after the client has already given up. Why, and what fixes it?"
  choices={[
    { label: "Independent per-hop timeouts do not compose: nothing tells A how much of the budget is left, so A spends its own full second doing work nobody awaits.     { label: "A's timeout is simply set too long; lowering it to 500 ms fixes the composition.", misconception: "Length is not the root issue — composition is. Even well-chosen local values sum past the SLA without a shared, propagated budget; the fix is a deadline, not a smaller constant." },
    { label: "Database and RPC clients cannot have timeouts, so A waits forever.", misconception: "Clients do support timeouts — both A and B set 1 s here. The flaw is that isolated timeouts do not roll up into one deadline carried down the call chain." },

<Recap lang="en">
The through-line of the unit is one reflex: given a symptom, jump to the stop that owns it. Empty logs under a burst means the accept queue (somaxconn) dropped connections before any code ran; an unauthenticated endpoint means middleware order, not auth logic; a slowdown that tracks payload size means serialization; an OOM under slow clients means ignored backpressure; and a slow page despite healthy services means tail amplification under fan-out, fixed with propagated deadlines and hedging. Latency is the sum across all seven stops plus queueing — so the map turns blind debugging into a single jump.
</Recap>
