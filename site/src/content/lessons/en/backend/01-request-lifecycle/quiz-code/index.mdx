## Snippet 1 — the middleware chain

```js
const app = express();

app.use(express.json());                 // body parser, no size limit
app.post("/admin/wipe", wipeHandler);     // <-- registered here
app.use(rateLimit({ max: 100 }));         // rate limiter
app.use(requireAuth);                     // auth: 401 if no valid token
app.use(errorHandler);                    // catches downstream throws
```

## Snippet 2 — the streaming export

```js
function exportCSV(rows, res) {
  res.setHeader("Transfer-Encoding", "chunked");
  for (const row of rows) {
    res.write(toCSVLine(row));   // return value ignored
  }
  res.end();
}
```

<Quiz
  id="01-request-lifecycle-code-2"
  lessonSlug="01-request-lifecycle"
  lang="en"
  question="This passes every test but OOMs in production under one slow client. What is the bug and the correct rewrite?"
  choices={[
    { label: "It ignores backpressure: res.write() returns false once the buffer passes the high-water mark, but the loop keeps writing, so unread bytes pile up in the heap when the client reads slowly. Rewrite with pipeline(rowStream, res) (or pause until the 'drain' event), which couples production to the consumer's rate.", correct: true },
    { label: "Transfer-Encoding: chunked is invalid for CSV; set Content-Length instead.", misconception: "Chunked is correct for a streamed body of unknown total size; setting Content-Length would force buffering the whole export first. The bug is ignoring the write() backpressure signal, not the framing." },
    { label: "res.end() is called too early and truncates the output.", misconception: "res.end() runs after the loop completes, so it does not truncate. The defect is that the loop never honours write() returning false, so memory grows unbounded under a slow consumer." },
    { label: "toCSVLine allocates strings, so the fix is to raise the heap limit.", misconception: "Raising the heap only delays the OOM; the growth is unbounded because production is decoupled from the client's read rate. Honouring backpressure keeps memory flat at ~the high-water mark regardless of allocation." },
  ]}

## Snippet 3 — the response builder

```js
app.get("/orders", async (req, res) => {
  const orders = await db.query("SELECT * FROM orders"); // unbounded
  res.status(200).json({ ok: true, data: orders });      // JSON.stringify
});
```

<Quiz
  id="01-request-lifecycle-code-3"
  lessonSlug="01-request-lifecycle"
  lang="en"
  question="As the orders table grows, this endpoint degrades and occasionally stalls all other requests. Which two lifecycle stops are at fault, and what is the fix?"
  choices={[
    { label: "Handle (unbounded query pulls the whole table) and Serialize (res.json runs synchronous JSON.stringify over a huge array, blocking the event loop for every other request). Fix: paginate / LIMIT the query, and use a schema serializer on the hot path.", correct: true },
    { label: "Only Serialize — the database query is cheap regardless of row count.", misconception: "An unbounded SELECT is itself a Handle-stage problem: it pulls more rows as the table grows, which is what then feeds the oversized serialization. Both stops compound; capping the query is the upstream fix." },
    { label: "Accept — the endpoint overflows the accept queue as the table grows.", misconception: "Table size has no effect on the accept queue, which bounds pending connections. The degradation tracks result-set size, which points at the query (Handle) and serialization (Serialize), not connection acceptance." },
    { label: "status(200) is wrong; using 204 would avoid serializing the body.", misconception: "204 means no body, which would break the endpoint's contract — clients need the orders. The fix is to bound and paginate the body, not to drop it; the status code is correct for a successful read." },
  ]}
/>

## Snippet 4 — the deadline that is not propagated

```js
async function getProfile(userId) {
  // each client sets its own fixed 1s timeout; nothing is passed down
  const user = await usersClient.get(userId, { timeoutMs: 1000 });
  const prefs = await prefsClient.get(userId, { timeoutMs: 1000 });
  const feed = await feedClient.get(userId, { timeoutMs: 1000 });
  return { user, prefs, feed };
}
```

Fix: propagate a deadline (a wall-clock cutoff), and set each call's timeout to min(local, remaining budget); run independent calls concurrently where possible.", correct: true },
    { label: "Nothing is wrong; three 1 s timeouts still cap the total at 1 s.", misconception: "Fixed per-hop timeouts do not compose. Sequential calls each consuming up to 1 s sum to ~3 s; isolated timeouts cannot enforce a request-wide budget — only a propagated deadline can." },
    { label: "The only fix is to lower each timeout to 333 ms so they sum to 1 s.", misconception: "Static splitting wastes budget — a fast first call should leave more time for later ones. A propagated deadline with min(local, remaining) adapts to actual elapsed time instead of a fixed 1/N split." },
    { label: "Run them concurrently and the SLA is automatically guaranteed.", misconception: "Concurrency caps the total at the slowest single call (~1 s), which helps — but without a propagated deadline a slow hop can still hang past the budget, and fan-out then exposes tail amplification. You need both concurrency and a deadline." },
  ]}

<Recap lang="en">
Every lifecycle incident is read in the wiring or the hot path: middleware registered after a route never runs, so order is a security boundary; a write() loop that ignores the false return OOMs under slow clients, so use pipeline(); an unbounded query plus generic JSON.stringify blocks the loop, so paginate and use a schema serializer; and fixed per-hop timeouts do not compose, so propagate a deadline with min(local, remaining). Diagnose the stop, apply the highest-leverage fix, then verify under the same load.
</Recap>
