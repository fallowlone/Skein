## Snippet 1 — the synchronous login

```js
import bcrypt from "bcrypt";
import fs from "fs";

app.post("/login", (req, res) => {
  const policy = fs.readFileSync("./password-policy.json", "utf8"); // sync read
  const hash = bcrypt.hashSync(req.body.password, 12);              // ~250 ms CPU
  // ...verify and respond...
});
```

## Snippet 2 — the resize on the libuv pool

```js
// Team's "fix" after profiling a slow image endpoint:
process.env.UV_THREADPOOL_SIZE = "32";

app.post("/resize", (req, res) => {
  const out = resizeImageSync(req.body.buffer, 1024, 768); // pure-JS pixel loop
  res.send(out);
});
```

    { label: "UV_THREADPOOL_SIZE must be set before the process starts, so the assignment was ignored.", misconception: "Even if it took effect, the pool does not execute JavaScript, so it could never run the JS pixel loop. The fix is a worker thread, not the pool." },
    { label: "32 exceeds the core count, so the extra threads contend and cancel out.", misconception: "Over-provisioning the pool does cause contention, but that is not why this is broken — the pool never runs JS at all. The resize needs a worker thread." },
    { label: "resizeImageSync is I/O-bound, so it belongs on the libuv pool once it is big enough.", misconception: "A pixel loop is CPU-bound, not I/O; that is exactly why it blocks the loop and why a worker thread (or chunking) is the answer." },

## Snippet 3 — the worker-pool starvation

```js
// Worker pool sized to the machine's 4 cores:
const pool = new WorkerPool({ size: 4 });

app.get("/report/:id", async (req, res) => {
  // Each report = one CPU-heavy aggregation task on the pool.
  const result = await pool.run("aggregate", req.params.id); // may take ~2 s
  res.json(result);
});
```

<Quiz

  lang="en"
  question="Under a burst of report requests, every endpoint — including cheap ones that also use the pool — sees latency climb into seconds, then time out. What is the failure mode?"
  choices={[
    { label: "Thread-pool starvation: with only 4 workers and ~2 s tasks, a burst of report requests occupies all workers, so every later pool.run queues behind them. The fix is to bound the queue and shed/timeout excess, and to keep fast tasks off the same saturated pool.", correct: true },
    { label: "The worker pool has a memory leak that grows with each report.", misconception: "Nothing here leaks; the symptom is queueing, not growth. A fixed pool of 4 simply cannot run more than 4 heavy tasks at once, so the rest wait." },
    { label: "await on pool.run blocks the event loop while a worker computes.", misconception: "await yields the loop; the loop stays free. The bottleneck is the bounded set of workers, not the loop thread." },
    { label: "Raising the worker count to 64 on a 4-core box would clear it cleanly.", misconception: "More workers than cores does not add CPU; 64 workers on 4 cores just time-slice and add overhead. You need bounded queueing with timeouts/shedding, and ideally more cores or instances." },
  ]}
/>

## Snippet 4 — measuring the freeze

```js
import { monitorEventLoopDelay } from "node:perf_hooks";

const h = monitorEventLoopDelay();
h.enable();
setInterval(() => {
  console.log("loop delay p99 (ms):", h.percentile(99) / 1e6);
}, 1000);
// Sample output during a bad reporting request:
// loop delay p99 (ms): 812
```

<Recap lang="en">
Every freeze is read in handlers and in the lag histogram: synchronous I/O and sync crypto on the request path stall the loop and must move to async APIs (which use the libuv pool); CPU-bound JS cannot be helped by a bigger libuv pool and belongs in a worker thread; a fixed worker pool starves under a burst of heavy tasks, so bound the queue with timeouts and keep fast work off it; and event-loop delay — not CPU — is the metric that matches the timeouts users feel. Diagnose from the signal, fix the blocking span, then re-measure.
</Recap>
