    { q: "Why is code splitting a latency trade rather than a free size cut?", a: "Splitting does not delete any code — it carves the module graph into chunks, turning one download into several. Each chunk is a separate HTTP request, and a request carries connection scheduling, round-trip latency, decompression, and a parse that can only start once the bytes arrive. On a fast desktop link that overhead vanishes into the noise, but on a 4G phone with a 100–200 ms RTT it becomes the dominant cost. So the senior question is never 'is the bundle smaller?' but 'how many sequential round trips did splitting add to the critical path?' Less initial JavaScript helps parse, TTI, and LCP — but only if you did not replace bytes with a chain of dependent requests." },
    { q: "Why is route-based splitting the safe default while component-level splitting is a scalpel?", a: "Route-based splitting ships one chunk per page: the initial route carries only its own code and the rest arrives as the user navigates. It is the highest-leverage, lowest-risk split because each navigation is a deliberate user action with a natural loading moment, so the waterfall is bounded — and frameworks (Next.js, Remix, React Router) do it for free. Component-level splitting via React.lazy is a scalpel with a strict rule: split only things that are both heavy (roughly 30–50 KB and up) and off the first paint — a 200 KB editor behind a button, a chart on one tab. A small or above-the-fold component should never be split, because the round trip and spinner cost more than the bytes saved." },
    { q: "Explain the request waterfall and why HTTP/2 multiplexing does not save you from it.", a: "With React.lazy, the parent route renders, React hits the lazy boundary, and only then requests the child chunk — sequentially. Nest two or three lazy boundaries and you get a dependent chain: chunk A must arrive and parse before the browser even learns chunk B exists, so on a 150 ms RTT link three sequential chunks add ~450 ms of pure latency before any execute. HTTP/2 multiplexing lets independent requests share one connection in parallel, removing the HTTP/1.1 head-of-line penalty — but it can only parallelize requests the browser knows about at the same time. A waterfall is sequential by construction, so there is nothing to parallelize until each parent parses. Multiplexing also cannot recover the compression lost when one asset is split into slivers, because gzip/brotli need a window of repeated bytes." },
    { q: "How does isolating a vendor chunk help caching, and how does it accidentally backfire on every deploy?", a: "node_modules code (React, a date or chart lib) changes far less often than your app code, so a separate, content-hashed vendor chunk lets returning users keep it cached across deploys while only app chunks re-download. The backfire is when something volatile leaks into that chunk's bytes — most commonly the webpack runtime and the module-id map, which shift whenever you add or reorder modules. If that map is inlined into the vendor file, the vendor hash and URL change on every build and every user re-downloads React on every release even though the dependency never changed. The fix is granular chunking: pull the runtime into its own tiny file, give vendor a stable boundary, and content-hash filenames so only chunks whose bytes actually changed get a new URL." },
    { q: "When do you use rel=preload (modulepreload) versus rel=prefetch for a chunk?", a: "Use preload for a chunk the current page will definitely need but that would otherwise be discovered late: it tells the browser to fetch now, in parallel with the document, flattening the waterfall before it forms. Use prefetch for a chunk the user will likely need on a future navigation: it fetches at low priority so it does not compete with the current page — for example, prefetch the dashboard chunk on hover over its link so the click feels instant. Frameworks automate both: Next.js prefetches in-viewport Link targets and injects a preload for next/dynamic chunks before render. The split is current-critical (preload) versus likely-future (prefetch)." },
    { q: "Why is lazy-loading an above-the-fold component a classic production accident, and which Core Web Vitals does it attack?", a: "If you wrap a hero or primary panel in React.lazy, the user first sees the Suspense fallback (a spinner or blank box), then the real component pops in and shifts everything below it. That is a Cumulative Layout Shift hit; one documented case went from CLS 0.85 to 0.1 just by not lazy-loading above the fold and reserving space for what does load. It attacks all three thresholds at once: the deferred fetch delays the Largest Contentful Paint (target under 2.5s), the late mount harms responsiveness (INP under 200 ms), and the pop-in shifts layout (CLS under 0.1). Above-the-fold, first-paint content belongs in the route chunk, not behind a lazy boundary." },

<Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: splitting trades one download for many requests, so the metric is sequential round trips added, not bytes saved. Route-based splitting is the bounded, high-leverage default; component-level is a scalpel for heavy, off-first-paint widgets only. The waterfall is what loses on mobile and HTTP/2 cannot save it; a content-hashed vendor chunk with the runtime split out keeps caches warm across deploys; and preload defends current-critical chunks while prefetch warms likely-next ones — never lazy-load above the fold. Now when you encounter a code-splitting decision in production, you will reach for the waterfall count first — how many sequential round trips, not how many kilobytes — and that question will point you to the right fix every time.
</Recap>
