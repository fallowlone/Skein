## What "frontend" actually means

The **frontend** is the part of a system the user sees and touches: the buttons, text, lists, and forms on a screen. Everything else — the database, the servers, the logic that runs far away — is the **backend**. The frontend's job is to take data and turn it into something a person can look at and act on, then send their actions back.

So a frontend is really two flows running forever:

- **Data &rarr; screen.** Take the current data and *render* it: draw the cart count, the product list, the error message.
- **Screen &rarr; data.** A click or keystroke happens; change the data to match (add an item, type a name).

The whole difficulty lives in the loop between those two.

## The one problem to carry up: keeping them in sync

The data your app holds is called its **state** — the cart contents, who is logged in, whether a menu is open. **Rendering** is the act of turning that state into what you see. The hard part is this: when state changes, every part of the screen that depended on it must change too, and nothing else should.

Do it by hand and you get bugs: a number that's stale, two panels that disagree, a "saved" badge that lingers after the save failed. Modern frontend tools exist almost entirely to automate this one thing — you describe *what the screen should look like for a given state*, and the tool figures out *what to redraw* when state changes.

## What this climb covers

Once you accept that sync is the core problem, the rest of the track is the toolbox for it: how to **shape state** so it's easy to keep in sync, how to **fetch data** from the backend without freezing the screen, how to build **forms** everyone can use, and how to **ship** all of it fast. Each topic is one more answer to the same question — how do I keep the screen and the data in agreement?

<Recap lang="en">
The frontend is the part of a system the user sees and touches — the UI — while the backend is everything behind it. A frontend runs a forever loop: render data to the screen, then change the data when the user acts. Its one core problem is sync: when state (the app's current data) changes, every part of the screen that depended on it must update, and nothing else. The rest of this track is the toolbox for winning that loop on purpose.
</Recap>
