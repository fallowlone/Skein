## Snippet 1 — the task graph

```jsonc
// turbo.json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": []
    }
  }
}
```

<Quiz

  lessonSlug="05-monorepo"
  lang="en"
  question="What ordering does this config produce, and what is the difference between the two dependsOn entries?"
  choices={[
    { label: "^build means build all of a package's dependencies first (the caret crosses package boundaries upstream); build (no caret) in test means a package's own build must finish before its own test runs. So the graph builds leaves first, then dependents, then tests each package after its build.", correct: true },
    { label: "Both dependsOn entries mean the same thing; the caret is cosmetic.", misconception: "The caret is load-bearing. ^build = the build task of this package's DEPENDENCIES; build = the build task of THIS package. Dropping the caret would skip building upstream libraries before the app that consumes them." },
    { label: "^build runs every build in the repo before anything else, ignoring the graph.", misconception: "^build is scoped to the current package's own dependency subtree, not the whole repo. Turborepo walks the graph and only orders the upstream packages this one actually depends on." },
    { label: "test with empty outputs means test results are never cached.", misconception: "Empty outputs means there are no file artifacts to restore, but the task is still cached: a hit replays the recorded success and logs and skips re-running. outputs lists files to save, not whether caching happens." },
  ]}

## Snippet 2 — the cache key

```jsonc
// turbo.json — build task inputs
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "inputs": ["src/**/*.ts", "src/**/*.tsx"],
      "outputs": ["dist/**"]
    }
  }
}
```

<Quiz
  id="05-monorepo-code-2"
  lessonSlug="05-monorepo"
  lang="en"
  question="A change to the shared root tsconfig.json alters compiler output, but every build still cache-hits and ships stale dist. Reading these inputs, what is the bug and the fix?"
  choices={[
    { label: "The inputs glob only captures src TypeScript files, so tsconfig.json is not part of the hash — a false hit. The build's real inputs include the tsconfig (and any extends chain) and the compiler version; add them to inputs (or use globalDependencies for the root tsconfig) so a config change invalidates the cache.", correct: true },
    { label: "outputs is wrong; dist should be cached differently.", misconception: "outputs is correct — dist is the artifact to save and restore. The defect is on the INPUT side: an input that changes output (tsconfig) is missing from the hash, so the key never changes when it should." },
    { label: "dependsOn is missing test, so builds run out of order.", misconception: "Ordering is fine for a build task; this is a stale-output false-hit problem, not an ordering problem. The fix is to widen the inputs to cover every file and tool that affects compiled output." },
    { label: "Just disable caching for build to be safe.", misconception: "That throws away the entire benefit of the cache to dodge one missing input. The senior fix is to make the key correct — add tsconfig and toolchain to the hash — so hits stay fast AND safe." },
  ]}
/>

## Snippet 3 — affected detection

```bash
# CI: only build/test what this PR could have broken
npx nx affected -t build test --base=origin/main --head=HEAD
```

<Quiz
  id="05-monorepo-code-3"
  lessonSlug="05-monorepo"
  lang="en"
  question="On a long-lived release branch this command suddenly reports the whole repo as affected for a tiny diff. Most likely cause?"
  choices={[
    { label: "The base is wrong: --base=origin/main on a long-lived release branch diffs against a far-back merge-base, so a large accumulated delta makes nearly everything affected. Point --base at the correct branch point (the PR's true base or the last release tag) so the diff reflects only this PR.", correct: true },
    { label: "Nx affected is non-deterministic and occasionally returns everything.", misconception: "affected is deterministic: it is a graph walk over a git diff. A whole-repo result for a small change is a signal that the diff (the base and head range) is wrong, not that the algorithm is flaky." },
    { label: "The remote cache is full, so affected falls back to building all.", misconception: "Affected scope is computed from the git diff and the project graph, entirely independent of cache fullness. A full cache causes misses (rebuilds), never an inflated affected set." },
    { label: "build and test should be run in separate invocations.", misconception: "Running multiple targets in one affected call is fine and intended. The inflated set comes from the base revision spanning too large a diff, not from combining targets." },
  ]}
/>

## Snippet 4 — module boundaries

```jsonc
// .eslintrc — @nx/enforce-module-boundaries
{
  "depConstraints": [
    { "sourceTag": "type:feature", "onlyDependOnLibsWithTags": ["type:ui", "type:util"] },
    { "sourceTag": "type:ui",      "onlyDependOnLibsWithTags": ["type:util"] },
    { "sourceTag": "type:util",    "onlyDependOnLibsWithTags": ["type:util"] }
  ]
}
```

<Quiz

  lang="en"
  question="Which import does this config reject at lint time, and what graph problem does the rejection prevent?"
  choices={[
    { label: "A util library importing from a feature or a ui library is rejected — util may only depend on util. This prevents low-level shared code from gaining a huge fan-in or forming a cycle, which is exactly what turns affected sets and cache invalidation into whole-repo events.", correct: true },
    { label: "A feature importing from a ui library is rejected.", misconception: "That edge is explicitly ALLOWED: type:feature lists type:ui in onlyDependOnLibsWithTags. The config permits the downward direction feature → ui → util and rejects upward edges." },
    { label: "The rule rejects nothing; it only warns on style.", misconception: "enforce-module-boundaries fails lint on a violating dependency edge. It is a hard constraint on graph shape, not a style warning, which is what keeps the boundaries from eroding." },
    { label: "It rejects two util libraries importing each other.", misconception: "util → util is permitted by the config, so that specific edge passes this rule. Direct cycles are caught separately; what this snippet rejects is the upward util → feature/ui direction." },
  ]}
/>

<Recap lang="en">
Every monorepo pipeline problem is read in config and a git range: the caret in dependsOn decides whether upstream packages build first; the inputs glob is the cache key, where a missing tsconfig is a false hit and a volatile path is a false miss; affected scope is a graph walk over a diff, so a wrong --base inflates it to the whole repo; and depConstraints keep low-level libraries from gaining the fan-in that makes every change global. Read the config, fix the key or the boundary, then re-run and confirm the affected set and hit rate behave.
</Recap>
