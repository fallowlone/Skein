<Goal lang="en">
Confirm you can connect the dependency graph, affected detection, remote caching, and module boundaries into one decision: build what changed and its dependents, cache the rest, and never let a hub package make every PR rebuild the world.
</Goal>

    { label: "The directly changed projects plus every project that transitively depends on one of them, found by walking the dependency graph from the diff.", correct: true },
    { label: "Every project in the repo, just scheduled in parallel.", misconception: "That is build-everything. Affected exists precisely to skip untouched projects; running them all in parallel still scales with repo size, not change size." },
    { label: "Only the exact files in the git diff, with no graph walk.", misconception: "Files are not the unit — projects are — and dependents must be included: a change to a library can break the apps that import it, so they must be retested too." },

  question="A PR served a stale build from the remote cache and shipped a bug, even though hit rate was high. Most likely cause?"
  choices={[
    { label: "A false hit: an input that affects output — a shared tsconfig, an env var, a tool version — was left out of the cache key, so a genuinely changed build hashed to an old entry and the stale artifact was served.", correct: true },
    { label: "The cache was too small and evicted the correct entry.", misconception: "Eviction causes a miss and a rebuild, not a stale-but-served artifact. A stale hit means the hash matched when it should not have — a missing input in the key." },
    { label: "Affected scoping skipped the project entirely.", misconception: "If affected skipped it, nothing was served for that project at all. A stale served artifact means a task ran, checked the cache, hit, and got the wrong entry — a key problem." },
    { label: "The hit rate was simply too high, which is inherently unsafe.", misconception: "A high hit rate is not the bug; an incorrect key is. A correct key gives correct hits. The goal is exactly a high hit rate with a key that captures every real input." },
  ]}

  choices={[

<Recap lang="en">
The through-line across the unit is one pipeline: the dependency graph sets ordering and blast radius, affected detection narrows each PR to the changed projects plus their dependents, remote caching turns most of those into instant hits — and the cache key is the whole game, where a missing input is a dangerous false hit and a volatile one is a wasteful false miss. None of it survives a bad graph, so enforced module boundaries (Nx tags, the enforce-module-boundaries rule, package exports) keep a hub from forming. And the monorepo-vs-polyrepo call is about coupling: shared code that changes together favours the monorepo; truly independent teams favour polyrepo.
</Recap>
