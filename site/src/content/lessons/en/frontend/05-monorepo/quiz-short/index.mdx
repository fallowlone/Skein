The thing that determines speed is the dependency graph: the directed graph of which package imports which, built by tools like Turborepo and Nx from your imports and workspace package.json files. The tool uses it for two jobs: ordering (build a library before the app that consumes it) and scoping (compute the blast radius of a change). A healthy graph is wide and shallow — many leaf libraries, few things depending on any one of them. A sick graph has a hub: one node with huge fan-in on the path between everything. Because affected scoping and cache invalidation both walk this graph, the graph's shape, not the directory tree, decides whether a one-line change rebuilds one project or all of them." },
    { q: "What does affected detection compute, and how does it differ from build-everything?", a: "Build-everything runs build and test across every package on every PR, so cost scales with repo size — at 40 packages a full run is 30–45 minutes and the merge queue backs up. Affected detection (Nx 'affected' / Turborepo 'filtered') instead diffs the PR against the base branch to find the directly changed projects, then walks the dependency graph to add every project that transitively DEPENDS on a changed one. Tasks run only for that set. The unit of affected is the project, not the file, and dependents must be included because a change to a library can break the apps that import it. The whole bet of a monorepo rests on this: most PRs touch a small slice, so most PRs should pay for a small slice — commonly dropping a 20-package workspace from ~14 minutes to 3–5, or under a minute when the change is local to a leaf." },
    { q: "What goes into a remote-cache key, and what are the two failure modes of getting it wrong?", a: "The cache key is a hash of everything that determines a task's output: its source files, the outputs of its dependencies, relevant config (tsconfig, the task definition), env vars, and tool versions. On a hit, the stored output (build artifacts, test result, logs) is downloaded instead of recomputed. Two failure modes: a FALSE HIT happens when you leave out an input that affects output — a shared tsconfig or an env var — so a genuinely changed build hashes to an old entry and the cache serves a stale, possibly buggy artifact. A FALSE MISS happens when you include too much — a volatile file (timestamp, log path) or an over-broad glob — so the hash never repeats, the cache is useless, and you pay storage for nothing. Tuning cache hit rate is mostly tuning what counts as an input: capture every real input, exclude every volatile one." },
    { q: "How do affected scoping and remote caching divide the work, and why do you need both?", a: "They solve different halves. Affected scoping answers 'which projects could this change have broken?' — it diffs against base and walks dependents, so untouched projects never run at all. Remote caching answers 'of the in-scope projects, which actually need to run?' — it hashes each task's inputs and, if that hash was already built by you, a teammate, or a prior CI run, downloads the stored output instead of recomputing. You need both because each leaves a gap the other fills: affected alone still rebuilds an in-scope project even when its inputs are identical to a previous run; caching alone still treats every project as a candidate, wasting time hashing projects the diff proves irrelevant. Together — affected narrows to the blast radius, the cache turns most of those into instant hits — a clean monorepo serves an 80–90% hit rate and finishes most PRs in seconds." },
    { q: "Why does a single 'shared utils' package wreck the affected graph, and what is the structural fix?", a: "It is a hub. If 30 of 38 projects import @acme/utils, then by definition any change to utils puts all 30 in the affected set and must rebuild and retest them. Caching cannot save you either: utils is an input to all those builds, so its hash change makes every dependent a legitimate cache miss. The result is that a one-line change near utils rebuilds nearly the whole repo — the classic 40-minute job. The fix is structural, not a tooling tweak: split the god-package into narrow leaf packages (@acme/format-date, @acme/http, @acme/result), each with a small fan-in, so a change to date formatting invalidates only the handful of projects that format dates. Then enforce module boundaries — Nx tags with depConstraints, the enforce-module-boundaries lint rule, or package.json exports — so the graph cannot re-collapse into a hub or form cycles." },

The cost is real: you need graph-aware tooling (Nx/Turborepo/Bazel), remote caching, and enforced boundaries, or the repo collapses under its own CI. Polyrepo flips it: each repo is trivially fast and independent, but shared code travels through a registry, so a breaking change means coordinated version bumps, drift, and 'which service is on the old version' spelunking. The honest framing: monorepo trades higher tooling complexity for lower coordination cost; polyrepo trades lower tooling complexity for higher coordination cost.
