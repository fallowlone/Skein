## Snippet 1 — where the keystroke lives

```tsx
// global store
const useStore = create((set) => ({
  search: "",
  setSearch: (v) => set({ search: v }),
}));

function SearchBox() {
  const setSearch = useStore((s) => s.setSearch);
  return <input onChange={(e) => setSearch(e.target.value)} />;
}

function Dashboard() {
  // Chart, Table, Filters, Sidebar all call useStore(...) somewhere
  return <><SearchBox /><Chart /><Table /><Sidebar /></>;
}
```

<Quiz
  id="08-putting-it-together-code-1"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="Typing in the search box janks the whole dashboard. From this code, what is the cause and the fix?"
  choices={[
    { label: "The keystroke value is high-frequency local UI state stored globally, so every store subscriber in the tree re-renders on each character. Colocate `search` in SearchBox's own useState (or a narrowly-scoped context) so only the search subtree re-renders.", correct: true },
    { label: "Zustand re-renders every consumer on any state change regardless of selector.", misconception: "Selector-based stores re-render only subscribers whose selected slice changed. The jank is real because Chart/Table/Sidebar subscribe to state that shares update notifications with `search` — the cure is to not put per-keystroke state in the shared store at all." },
    { label: "Wrap Chart and Table in React.memo to stop the re-renders.", misconception: "memo guards against prop changes, but these components re-render because they subscribe to the store that updates on every keystroke. You would memo-wrap the whole tree and still pay; the fix is moving the state, not memoising every consumer." },
    { label: "Debounce setSearch so the store updates less often.", misconception: "Debouncing reduces frequency but keeps the keystroke in global state, so typing still feels laggy and the architecture is still wrong. Colocation removes the blast radius entirely; debounce is a patch on a misplaced piece of state." },
  ]}
/>

## Snippet 2 — the fetch graph

```tsx
function ProductPage({ id }) {
  const product = useQuery(["product", id], () => fetchProduct(id));
  // these two do NOT depend on product, yet they wait for it:
  const reviews = useQuery(["reviews", id], () => fetchReviews(id), {
    enabled: !!product.data,
  });
  const related = useQuery(["related", id], () => fetchRelated(id), {
    enabled: !!product.data,
  });
  // ...renders after all three resolve
}
```

<Quiz
  id="08-putting-it-together-code-2"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="Reviews and related products do not depend on the product payload, yet LCP is slow. What is the defect and the fix?"
  choices={[
    { label: "An artificial waterfall: `enabled: !!product.data` gates two independent fetches behind the first, serialising three round-trips that could run in parallel. Drop the gating so reviews and related fire immediately alongside product — or fetch all three on the server in one pass.", correct: true },
    { label: "TanStack Query is fetching too eagerly; the enabled flags are correct.", misconception: "The enabled flags are exactly the bug — they create a dependency that does not exist in the data. reviews and related need only `id`, which is available immediately, so gating them on product.data adds two needless sequential round-trips." },
    { label: "The fix is to cache the responses so the second visit is fast.", misconception: "Caching helps repeat visits but does nothing for the first paint, which is where the waterfall hurts LCP. The structural fix is to parallelise the independent fetches, not to rely on a warm cache." },
    { label: "Move all three into a single useQuery to reduce hooks.", misconception: "Collapsing hooks is cosmetic; if that single query still awaits product before reviews/related, the waterfall survives. Removing the false dependency — not merging hooks — is what parallelises the trips." },
  ]}
/>

## Snippet 3 — the lazy import

```tsx
import { HeavyChart } from "./HeavyChart"; // pulls in a 400 KB charting lib

function Analytics() {
  const [open, setOpen] = useState(false);
  return (
    <>
      <button onClick={() => setOpen(true)}>Show charts</button>
      {open && <HeavyChart />}
    </>
  );
}
```

<Quiz
  id="08-putting-it-together-code-3"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="The 400 KB charting library ships in the initial bundle even though most users never click 'Show charts'. Why, and what is the fix?"
  choices={[
    { label: "A static `import` is resolved at build time, so HeavyChart and its 400 KB dependency land in the initial chunk regardless of the `open` guard — the guard only delays render, not download. Use `const HeavyChart = lazy(() => import('./HeavyChart'))` with Suspense so the chunk loads on demand.", correct: true },
    { label: "The `{open && ...}` guard already prevents the library from loading until clicked.", misconception: "A conditional render controls when the component mounts, not whether its module is bundled. The static import is evaluated at build time, so the 400 KB ships up front — only a dynamic import() splits it into a separate chunk." },
    { label: "Tree-shaking should remove HeavyChart since it is conditionally rendered.", misconception: "Tree-shaking removes provably unused exports, but HeavyChart is used (it is rendered when open), so it cannot be shaken out. Deferring its download requires code-splitting via dynamic import, not tree-shaking." },
    { label: "Move HeavyChart into its own monorepo package to keep it out of the bundle.", misconception: "A separate package still gets statically imported into this chunk the same way; the package boundary does not split the bundle. Runtime code-splitting with lazy()/import() is what keeps it out of the initial download." },
  ]}
/>

## Snippet 4 — the token reference

```css
/* Button.css */
.btn-danger {
  background: #d33; /* brand red, hardcoded */
  color: #fff;
}
/* repeated across ~40 components: #d33, #fff, #1a1a1a ... */
```

<Quiz
  id="08-putting-it-together-code-4"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="Dark mode needs `.btn-danger` to read differently on a dark surface, and a rebrand will change the red. What does this CSS reveal, and what is the structural fix?"
  choices={[
    { label: "It references a raw primitive value, not a semantic token. Introduce a semantic layer — `background: var(--surface-danger); color: var(--text-on-danger)` — mapped to primitives per theme. Then dark mode swaps the semantic mapping and a rebrand swaps the primitive, with the component untouched.", correct: true },
    { label: "Add a `.dark .btn-danger { background: ... }` override for each component.", misconception: "Per-component dark overrides re-create the hardcoding problem in a second place and scale linearly with components. A semantic token resolved per theme means the component declares intent once and the theme supplies the value." },
    { label: "Use a Sass variable `$danger: #d33` and compile both themes.", misconception: "A build-time Sass variable cannot switch at runtime for dark mode the way a CSS custom property can, and it still binds the component to a primitive rather than a semantic role like surface-danger. The fix is a runtime semantic token layer." },
    { label: "It is fine — `#d33` is already the single brand red used everywhere.", misconception: "Using the same hex everywhere is exactly the trap: there is no indirection, so the rebrand is a find-and-replace and dark mode has no switch. The value being consistent does not make it a token; a token carries meaning the theme can remap." },
  ]}
/>

<Recap lang="en">
Four snippets, four layers, one habit: per-keystroke state belongs colocated, not in a global store; an `enabled` gate on an independent fetch is an artificial waterfall; a static import bundles eagerly while only a dynamic import() splits; and a hardcoded hex is a missing semantic token. In each case the highest-leverage fix lives at the layer that owns the bug — moving the state, removing the false dependency, splitting the chunk, adding the semantic layer — never a patch one layer up.
</Recap>
