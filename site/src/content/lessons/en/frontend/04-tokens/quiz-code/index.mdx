<Goal lang="en">
Practise reading token code the way you debug it: follow a reference through its tiers, predict what a theme override re-resolves, and spot the one line that locks a component out of theming.
</Goal>

## Snippet 1 — the tier reference

```css
:root {
  --color-blue-600: #0052CC;                  /* primitive */
  --color-interactive: var(--color-blue-600); /* semantic  */
}

.button { background: var(--color-blue-600); }
.link   { color: var(--color-interactive); }
```

  choices={[
    { label: "Only .link follows — it reads the semantic token the theme overrides. .button is bugged: it references the primitive directly, so it stays blue-600. Fix: change .button to background: var(--color-interactive).", correct: true },
    { label: "Both follow, because both ultimately resolve to blue-600.", misconception: "Resolving to the same value today does not mean both track the override. The theme redefines the semantic name; .button reads the primitive, so it never sees the change." },
    { label: "Neither follows — redefining a semantic token cannot affect already-declared rules.", misconception: "Custom properties cascade live: redefining --color-interactive re-resolves every var(--color-interactive) reference. .link recolors in one repaint; .button does not because it skipped the semantic tier." },
    { label: ".button follows and .link does not, since .button names the underlying value.", misconception: "It is the opposite. Naming the primitive locks .button to that value; the theme overrides the semantic token, which only .link reads." },
  ]}

## Snippet 2 — the DTCG source

```json
{
  "color": {
    "blue": { "600": { "$value": "#0052CC", "$type": "color" } },
    "interactive": { "$value": "{color.blue.600}", "$type": "color" }
  },
  "space": {
    "4": { "$value": "16px", "$type": "dimension" }
  }
}
```

<Quiz
  id="04-tokens-code-2"
  lessonSlug="04-tokens"
  lang="en"
  question="Style Dictionary builds this DTCG source for web and Android. What is true about how color.interactive and space.4 emerge per platform?"
  choices={[
    { label: "color.interactive resolves its {color.blue.600} alias to #0052CC, then transforms run: CSS emits --color-interactive: #0052CC and --space-4: 1rem, while Android emits an 8-digit ARGB color and a snake_case dimension — one source, platform-correct outputs.", correct: true },
    { label: "The {color.blue.600} alias is copied verbatim into each output, so Android ships a literal string {color.blue.600}.", misconception: "The build resolves aliases before formatting; no platform receives the {ref} syntax. Android gets the resolved, transformed value, not the alias string." },
    { label: "space.4 stays 16px on every platform because $type is dimension.", misconception: "$type tells the transform how to convert the value, not to keep it fixed. CSS commonly transforms px to rem (1rem), and Android uses its own dimension format." },
    { label: "Because both are $type color and dimension, no transform is needed — the JSON is the final artifact.", misconception: "JSON is the source, never the runtime artifact. Transforms adapt each value (px to rem, hex to ARGB) and formatters emit the actual CSS and XML files." },
  ]}
/>

## Snippet 3 — the theme override

```css
:root              { --color-surface: #FFFFFF; --color-text: #111111; }
[data-theme="dark"]{ --color-surface: #0B0B0F; --color-text: #F5F5F5; }

.card {
  background: var(--color-surface);
  color: var(--color-text);
  border: 1px solid #E5E7EB;   /* hardcoded */
}
```

<Quiz
  id="04-tokens-code-3"
  lessonSlug="04-tokens"
  lang="en"
  question="Toggling data-theme to dark recolors most of .card but leaves one visible defect. What is it and the fix?"
  choices={[
    { label: "The border stays light-gray #E5E7EB in dark mode — it is a hardcoded literal, not a token, so the cascade has nothing to re-resolve. Fix: add a semantic --color-border, set it under both selectors, and reference it.", correct: true },
    { label: "Nothing is wrong — borders should not change between themes.", misconception: "A light-gray border on a near-black surface is a visible two-tone defect. Borders are a themed surface decision and need a semantic token like the rest." },
    { label: "background and color also fail to update because the override is on a different selector.", misconception: "[data-theme=dark] redefines the same custom-property names; the cascade re-resolves every var() that reads them. Only the hardcoded border, which is not a var(), fails to follow." },
    { label: "The fix is to move the border into JavaScript and set it on theme change.", misconception: "That reintroduces JS for something the cascade does for free. Define a semantic border token under both selectors and the border themes itself in one repaint." },
  ]}
/>

## Snippet 4 — the fallback

```css
.badge {
  /* --brand-accent is set by some host pages, missing on others */
  color: var(--brand-accent);
  padding: var(--space-2, 8px);
}
```

<Quiz
  id="04-tokens-code-4"
  lessonSlug="04-tokens"
  lang="en"
  question="On a host page that never defines --brand-accent, how does each property behave, and what does the var() fallback teach?"
  choices={[
    { label: "color is invalid-at-computed-value and falls back to inherited/initial (text looks unthemed); padding safely uses 8px because var() takes a second arg as a fallback. Always give a sensible fallback for tokens a consumer might not define.", correct: true },
    { label: "Both properties break the whole rule, so the badge renders with no styles at all.", misconception: "One invalid custom-property reference does not nuke the rule. color becomes invalid-at-computed-value (uses inherited/initial), and padding resolves fine via its fallback." },
    { label: "color falls back to black by default, because var() always defaults to the initial color.", misconception: "var() with no fallback yields the guaranteed-invalid value, triggering invalid-at-computed-value handling — inherited for color, not a hardcoded black. The reliable default is an explicit fallback." },
    { label: "padding fails because var() does not accept a fallback argument.", misconception: "var(--name, fallback) is exactly the supported syntax; the second argument is used when the property is unset. That is why padding stays at 8px." },
  ]}
/>

<Recap lang="en">
Token bugs are read in the CSS and the JSON: a component that names a primitive falls out of theming while its semantic-referencing sibling recolors; the DTCG build resolves aliases then transforms values so one source is correct per platform; a single hardcoded literal survives a theme toggle as a visible two-tone defect; and var() with a fallback is the seatbelt for tokens a consumer might not define. Trace the reference through its tiers, and the fix is almost always 'reference the semantic token, with a fallback.'
</Recap>
