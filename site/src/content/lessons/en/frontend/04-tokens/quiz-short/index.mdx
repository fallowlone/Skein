The point is that the name carries intent, and intent is what you change during a rebrand, a theme switch, or an accessibility fix. Merely aliasing color.blue.600 = #0052CC only renames the value; it adds no intent. If components then reference that primitive name directly, the palette has leaked into product code and a rebrand still has to touch every reference. The value of tokens comes from one definition with many references plus a layer that carries meaning, not from naming hex values." },
    { q: "Describe the three tiers and state which one a component is allowed to reference.", a: "Primitive (global) tokens are the raw palette — color.blue.600 = #0052CC, space.4 = 16px — with no meaning, just options; nothing in product code should reference them directly. Semantic (alias) tokens carry intent — color.interactive.default = {color.blue.600}, color.surface.base, color.text.primary — and this is the layer themes override. Component tokens are the most specific — button.background = {color.interactive.default} — optional, used only when one component must diverge without disturbing the semantic layer. The rule: a component references a semantic token (or its own component token), never a primitive and never a literal." },
    { q: "How does dark mode recolor every component on the web with no JavaScript?", a: "You define semantic tokens on :root, then redefine the same semantic names under a theme selector like [data-theme=dark] with the dark values. Because CSS custom properties cascade and inherit, redefining a name re-resolves every var() that references it, and every component recolors in a single repaint. The components are never touched and never mention dark mode — they only read semantic tokens. This works precisely because components reference semantics, not primitives or literals; the moment one hardcodes a hex, it falls out of the theme and you have recreated a forked rule." },
    { q: "How does one token end up correct on web, iOS, and Android without anyone copying values by hand?", a: "Tokens are authored once as a single source in DTCG JSON, where each token has a $value and a $type and aliases use {group.token} syntax. A build tool — Style Dictionary is the reference implementation — reads the source, resolves the aliases, then runs per-platform transforms and formatters. Transforms convert each value to what the platform needs: a space token goes px to rem for CSS, a snake_case number for Android, camelCase for Swift; a color stays hex for CSS but becomes a UIColor for iOS and an 8-digit ARGB hex for Android. Formatters emit the actual files (CSS custom properties, colors.xml, a Swift file). Because all outputs are generated from one definition, they cannot drift — the rebrand-from-hell happened because there was no build step, so each platform was a manual fork." },
    { q: "A team rolls out tokens, then weeks later hardcoded hex reappears in new components. Why, and what is the durable fix?", a: "Tokens are a convention, and a convention without an enforced gate decays: under deadline someone pastes a hex, it works, it ships, and the drift restarts. The durable fix is a build-time lint rule — for example a stylelint rule that makes any raw color outside the primitive file a build error. The gate runs in CI so the system cannot erode through good intentions; training and code review help but fade, whereas an automated failure holds the line. The same idea applies to forbidding component references to primitive token names." },
    { q: "When are three tiers and a full pipeline justified, and when are they over-engineering?", a: "The cost of a token system is indirection — each tier is a hop a new engineer must trace and a place a bug can hide — and a build to maintain. For a small product with one web target and one theme, two tiers (primitive + semantic) as CSS variables is plenty; component tokens and a Style Dictionary pipeline are over-engineering until a real need appears. The calculus flips the moment you have more than one output target — web plus iOS plus Android, or light plus dark plus high-contrast, or per-client white-label themes — because drift surface grows with platforms times themes. Introduce the pipeline before the second target lands, not after a rebrand bills eleven weeks." },
