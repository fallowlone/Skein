<Goal lang="en">

  lessonSlug="01-state-shape"
  lang="en"
  question="A client-side editor holds threads, posts, and users nested as the API returned them, and users get renamed constantly. After a rename, some views still show the old name. Why, and what shape fixes it?"
  choices={[
    { label: "A nested shape copies each user into every post they touch, so a rename must rewrite every embedded copy — miss one and views drift. Normalize into a flat byId map per entity so a rename is one O(1) write that every join sees.", correct: true },
    { label: "The rename mutation forgot to trigger a re-render; add a forceUpdate.", misconception: "The views did re-render — they read a stale embedded copy that was never updated. The defect is the shape duplicating one user across the tree, not a missing render." },

    { label: "Switch to a deep-merge library so spread updates reach every copy.", misconception: "Deep-merging every embedded copy reinvents normalization badly and stays error-prone. Storing each entity once in a byId map removes the duplication that causes the drift." },
  ]}

<Quiz
  id="01-state-shape-choice-6"
  lessonSlug="01-state-shape"
  lang="en"
  question="A team stores selectedUser as the full user object in state. After an edit elsewhere updates that user, the selection still shows the old fields. What is the shape lesson?"
  choices={[
    { label: "The object is derivable from selectedId plus the cache, so storing the whole object made a stale snapshot. Store the id as the real state and join byId[selectedId] at read time, so the selection always reflects current data.", correct: true },
    { label: "Storing the object is fine; the edit handler just needs to also update selectedUser.", misconception: "That is the derived-state trap again: now every edit path must remember to rewrite the snapshot. Storing the id and joining at read time removes the invariant entirely." },
    { label: "selectedId is too little information; you must keep the object for the UI to render.", misconception: "The UI joins the id against the cache (byId[selectedId]) to get current fields. The id is the minimal real state; the object is a derived view of it." },
    { label: "Deep-clone the object on selection so it cannot be mutated underneath you.", misconception: "A frozen clone is precisely the stale snapshot problem — it never reflects later edits. The fix is to store the id and re-join, not to capture a copy." },
  ]}
/>

<Recap lang="en">
The through-line of the unit is one decision tree: if a value is derivable (count, the selected object), do not store it — compute it during render or join it from the id. If it is state, ask who owns it — server-fetched data is cache (React Query/SWR), client view-state that is shareable goes in the URL, and the rest colocates at the lowest common ancestor of its readers to keep the re-render blast radius small. Normalize relational client data into a byId map only when you mutate it. Now when you see any of the distractors above in a real PR — a derived value stored alongside its source, fetched data in a Redux slice, a single-reader flag at the root, a snapshotted object that should be a joined id — you know the shape name, the failure mode it causes, and the structural fix that removes it.
</Recap>
