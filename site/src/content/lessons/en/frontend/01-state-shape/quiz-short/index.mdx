    { q: "What is the test for whether a value is state or derived, and why does storing a derived value cause bugs?", a: "The test: if you can compute the value from existing state during render, it is not state — it is derived. count is results.length; the selected object is byId[selectedId]; a cart total is items.reduce(...). Storing a derived value creates a second source of truth, and now every code path that changes the source must also rewrite the copy: the happy path, an error handler, an optimistic update, a websocket patch. The framework will not enforce that invariant for you, so one missed path makes the two drift — the badge says 127 while the list shows 9. The fix is to derive during render, where a value cannot drift from itself. useMemo is only a performance optimisation for an expensive computation; a memoized copy is still a second source of truth." },
    { q: "Why is 'server cache vs client state' the most important shape question, and how does it change your tooling?", a: "Fetched data has properties client state never has: it goes stale, it can be refetched, it needs deduping when many components want the same resource, it has loading and error states, and a mutation elsewhere can invalidate it. Load it into useState or a plain Redux slice and you hand-roll all of that — usually shipping double fetches, stale views after a mutation, and no dedupe. Recognising it as server cache means reaching for React Query / SWR / RTK Query, which are cache libraries keyed by request, not state libraries. That leaves your real client state small — open/closed UI, draft input, selection — plus the URL for anything shareable." },
    { q: "What does colocation mean, why does it make an app faster, and how is it different from 'lift state up'?", a: "Colocation means a piece of state lives at the lowest common ancestor of everything that reads it — and no higher. It makes the app faster because React re-renders the subtree that owns the state: keep a tooltip's open flag in the tooltip and a toggle re-renders the tooltip, not a dashboard. 'Lift state up' is correct but routinely over-applied — people lift to the root 'so it is available', which subscribes the whole app and creates re-render storms. The mirror-image rule, 'push state down', is what colocation actually is in practice: lift only to the lowest shared reader, not to the top." },
    { q: "Which kinds of state belong in the URL, and what breaks when you keep them only in useState?", a: "Anything shareable or bookmarkable belongs in the URL as its source of truth: filters, search query, sort, pagination, the open detail id, active tab. The URL is the one place that survives a refresh and travels in a copied link. Keep those only in useState and two things break: a refresh resets them to defaults (the user loses their place), and a link a user copies opens the default empty view for a teammate because the view-state never left that user's memory. localStorage fixes the refresh but is per-device, so it still does not make the link shareable — only the URL does both." },
    { q: "When should client state be normalized, and what exactly is the tradeoff against a nested shape?", a: "Normalize relational client data you mutate frequently: store each entity once in a flat byId map per type (users.byId, posts.byId) with allIds for order, and have references hold ids (post.authorId) joined at read time. The tradeoff: a nested shape (users embedded in posts) is ergonomic to read (post.author.name) but a trap under mutation, because one entity is copied across the tree, so a rename must rewrite every copy and one miss causes drift at scale. Normalized shape makes updates O(1) — one write to byId[id] that every join sees — at the cost of joining at read time and a little ceremony, which Redux Toolkit's createEntityAdapter removes. For read-mostly server data, do not normalize: let the cache library hold the raw response." },
    { q: "Walk through the ordered questions a senior asks to decide where any value belongs.", a: "(1) Is it derivable from existing state? If yes, do not store it — compute it during render. (2) If it is genuinely state, who owns it — the server (fetched) or the client (UI/draft/selection)? (3) Server-owned → a cache library keyed by request (React Query/SWR/RTK Query), which handles staleness, dedupe, refetch, and invalidation. (4) Client-owned and shareable or bookmarkable → the URL as source of truth. (5) Client-owned and private → the lowest common ancestor of its readers (colocate; do not hoist to the root). (6) If it is relational client data you mutate often, normalize it into a byId map. This ladder removes most 'state-management problems' before any library is chosen." },

<Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: derive what is derivable so it cannot drift, recognise fetched data as server cache and give it to a cache library, colocate private client state at its lowest reader instead of hoisting it, put shareable view-state in the URL, and normalize relational data only when you mutate it. Now when you open a PR and see a value stored next to its source, or a fetched payload in useState, or filters that vanish on refresh — you reach for the decision tree first, not the library docs.
