## Snippet 1 — the stored derived value

```tsx
function Cart({ items }: { items: Item[] }) {
  const [total, setTotal] = useState(0);

  useEffect(() => {
    setTotal(items.reduce((s, i) => s + i.price * i.qty, 0));
  }, [items]);

  return <Badge>{total}</Badge>;
}
```

  lang="en"
  question="What is the shape bug here, and the senior fix?"
  choices={[
    { label: "total is derived from items but stored in state and synced via an effect — a second source of truth plus an extra render. Compute it during render: const total = items.reduce(...). No state, no effect, never stale.", correct: true },
    { label: "The reduce should be wrapped in useCallback to avoid re-creating it.", misconception: "useCallback memoizes a function identity; it does not address the real problem, which is storing a value you can compute. The reduce belongs inline in render, not behind state." },
    { label: "items should be in state too so the component owns its data.", misconception: "items is a prop passed in — copying it into local state would add yet another source of truth that drifts from the parent. The fix is fewer stored values, not more." },
    { label: "Nothing is wrong; effect-syncing derived state is the standard pattern.", misconception: "Syncing derived state with an effect is a documented anti-pattern: it renders once with the stale value, then again after the effect. Deriving during render removes both the staleness window and the extra render." },
  ]}

## Snippet 2 — nested vs normalized

```ts
// state.users[].posts[] — users embedded inside each post's author field too
function renameUser(state, id: string, name: string) {
  return {
    ...state,
    users: state.users.map(u => u.id === id ? { ...u, name } : u),
    // posts still carry post.author = {...the old user...}
  };
}
```

<Quiz
  id="01-state-shape-code-2"
  lessonSlug="01-state-shape"
  lang="en"
  question="A rename updates the users array but the post list still shows the old name. What shape change is the real fix?"
  choices={[
    { label: "Each post embeds a copy of its author, so renaming in the users array leaves every post.author stale. Normalize: store users once in users.byId and have posts hold authorId, joining byId[authorId] at read time — then rename is one write.", correct: true },
    { label: "Also map over posts and patch each post.author with the new name in renameUser.", misconception: "That patches the symptom and keeps the duplication — every future field that changes needs the same fan-out, and one missed path drifts again. Removing the embedded copies is the durable fix." },
    { label: "Deep-freeze the state so the old author objects cannot be read.", misconception: "Freezing prevents mutation, not staleness — the frozen post.author still holds the old name. The problem is duplicated data, which normalization eliminates." },
    { label: "Move users into React Query so the rename refetches them.", misconception: "These are client-mutated entities, not server cache to refetch. A cache library does not fix a client shape that duplicates one user across many posts; a byId map does." },
  ]}
/>

## Snippet 3 — the hoisted, over-broad state

```tsx
// app store
const useStore = create((set) => ({
  mouseX: 0, mouseY: 0,
  setMouse: (x, y) => set({ mouseX: x, mouseY: y }),
}));

function Dashboard() {
  const { mouseX, mouseY } = useStore();   // subscribes to the whole store
  return <ExpensiveCharts /* re-renders on every mousemove */ />;
}
```

<Quiz
  id="01-state-shape-code-3"
  lessonSlug="01-state-shape"
  lang="en"
  question="Why does scrolling the mouse tank this dashboard's frame rate, and what is the fix?"
  choices={[
    { label: "High-frequency mouse position is hoisted into the global store and Dashboard subscribes to the whole store, so every mousemove re-renders ExpensiveCharts. Colocate the mouse state in the small component that needs it (or use a selector subscribing to only its slice).", correct: true },
    { label: "Zustand is slow with numbers; switch to Redux for primitive state.", misconception: "The store library is not the bottleneck — over-broad subscription is. A component reading the entire store re-renders on any change; the fix is narrower scope, not a different library." },
    { label: "ExpensiveCharts needs React.memo and the problem goes away.", misconception: "memo helps only if props are stable, but Dashboard itself re-renders on every mousemove because it subscribes to the changing store. Fix the subscription scope first; memo is a band-aid." },
    { label: "mouseX/mouseY should be in the URL so they persist.", misconception: "Mouse position is ephemeral, per-frame UI state — never shareable view-state. Putting it in the URL would thrash history. It should be colocated in the one component that reads it." },
  ]}
/>

## Snippet 4 — server data as client state

```tsx
function Orders() {
  const [orders, setOrders] = useState<Order[]>([]);
  useEffect(() => { fetch('/api/orders').then(r => r.json()).then(setOrders); }, []);
  // also rendered in a sibling <OrdersSummary/> with its own identical fetch
}
```

<Quiz
  id="01-state-shape-code-4"
  lessonSlug="01-state-shape"
  lang="en"
  question="Two components run this same fetch-into-useState pattern. Which set of problems does the shape create, and what is the fix?"
  choices={[
    { label: "Fetched data is modeled as client state, so you get duplicate fetches, no dedupe, no shared cache, no staleness/refetch, and views drift after a mutation. Move it to a server-cache library keyed by the request so both components share one cached, invalidatable result.", correct: true },
    { label: "The only issue is the missing loading flag; add isLoading state to each.", misconception: "A loading flag is the smallest part. The shape problem is treating server cache as client state, which also costs dedupe, shared caching, and invalidation — all of which a cache library provides at once." },
    { label: "Lift orders to a global store so both components read one copy.", misconception: "A global store dedupes the in-memory copy but you still hand-roll fetching, staleness, refetch, and invalidation. The data is server cache; a cache library keyed by request handles all of that." },
    { label: "It is fine as long as the two fetches hit the same endpoint.", misconception: "Identical endpoints still mean two network requests, two cache copies, and independent staleness — exactly the drift and waste a server-cache library exists to remove." },
  ]}
/>

<Recap lang="en">
Every shape bug above is read straight from code: an effect syncing a value you can derive (compute in render instead), authors embedded in posts so a rename goes stale (normalize to byId + join), high-frequency state hoisted into a global store that re-renders the world (colocate or select a slice), and a fetch dragged into useState that should be server cache (use a cache library keyed by the request). Read the component, find the second source of truth or the state placed wrong for its readers, and fix the shape before reaching for a library.
</Recap>
