The two correct forms are explicit (a label with for/htmlFor matching the input's id, so the label can sit anywhere in the DOM) and implicit (the input wrapped directly inside the label). This is WCAG 1.3.1 Info and Relationships plus 4.1.2 Name, Role, Value, and the WebAIM Million 2025 scan found 34.2% of form inputs across the top million home pages fail it — the single most common error category on the web." },

Part one is announcement: put each error in a region with role=alert (assertive: aria-live=assertive plus aria-atomic=true) so it is read the moment it appears, satisfying WCAG 4.1.3 Status Messages. The critical subtlety is that the live region must already exist in the DOM before you write text into it; mounting the region and its message in the same render is missed by many AT, so render an empty region up front and inject text only on error. Part two is association: set aria-invalid=true on the field and aria-describedby pointing at the message id, so landing on the input reads label, value, 'invalid', and the message together (WCAG 3.3.1 Error Identification). Stating how to fix it, not just that it is wrong, also meets 3.3.3 Error Suggestion." },
    { q: "On a failed submit with custom validation, why is moving focus the highest-leverage step, and where should focus go?", a: "After e.preventDefault(), focus is still on the submit button at the bottom of the form. A sighted mouse user sees the red fields and clicks one; a keyboard or screen-reader user has no idea anything failed and would have to tab backward through the whole form hunting for the broken control. Moving focus to the first invalid field (firstInvalid.focus()) drops the user exactly where the work is, and because that field carries aria-invalid + aria-describedby, the screen reader immediately reads what is wrong and how to fix it. Scrolling the viewport is not enough — it helps only the sighted mouse user; you must move focus, not just the page. This single behavior is the difference between a form that works with a keyboard and one that is dead to it." },
    { q: "Native constraint validation does focus, scroll, and the error bubble for free. What exactly do you inherit the moment you call e.preventDefault()?", a: "Native constraint validation (required, type=email, pattern, min/max) makes the browser focus and scroll to the first invalid control on submit and show a built-in bubble — all automatically. The instant you intercept submit with e.preventDefault() to run custom messages or async checks, every one of those behaviors stops firing. You now own: focusing the first invalid field, announcing the problem through a live region, associating each message with its field via aria-describedby, and setting aria-invalid. Most real apps do preventDefault for custom and async validation, which is exactly why so many ship the 'works with a mouse, dead with a keyboard' form — they took over submit but did not take over the accessibility responsibilities that came with it." },
    { q: "Why is a div-based control a worse bug than a missing label, and what does 'use the native element' actually buy you?", a: "A missing label is one wrong attribute — annoying, but the control is still reachable, focusable, and operable. A div-based control is invisible as a control: a div has no implicit role, is not in the tab order, and has no keyboard behavior, so a screen reader reads it as plain text and a keyboard user cannot reach or operate it at all. To make a div behave like a button you must add role=button, tabindex=0, and a keydown handler for both Enter and Space with preventDefault, plus replicate disabled and focus semantics; for a select/combobox you owe the full APG pattern (arrow keys, type-ahead, Escape, Home/End, aria-activedescendant). People remember the click handler and forget all of it, so the widget works with a mouse and is dead to keyboard and AT. The native button/select/input ships role, focusability, keyboard handling, and OS-level form integration you cannot fully replicate and will not maintain — which is why the senior default is native first, ARIA-rebuilt only when the native genuinely cannot do the job." },

<Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: every control needs a programmatically associated name (a placeholder is not one, and a third of the web fails this); errors must be announced through a pre-existing live region and tied to their field with aria-invalid + aria-describedby and stated as suggestions; a failed submit must move focus to the first invalid field, not just scroll; native elements ship the role, focusability, and keyboard handling you cannot fully replicate; the moment you preventDefault you inherit all of that; and controlled-vs-uncontrolled is a state decision, orthogonal to accessibility.
