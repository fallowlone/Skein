<Quiz

  lang="en"
  question="A field shows its label as placeholder text only. A teammate argues it is fine because the text is visible. Why is this still a WCAG failure?"
  choices={[
    { label: "A placeholder is not a programmatically associated name: it vanishes on focus, fails contrast minimums, and several screen readers ignore it. WCAG 1.3.1 / 4.1.2 require the label-control relationship be exposed to AT, not merely visible.", correct: true },
    { label: "It is fine — visible text adjacent to the input satisfies the requirement.", misconception: "Visually adjacent or placeholder text is not a programmatic association. The accessibility tree needs an explicit for/id or implicit wrapping; pixels on screen do not create the name AT reads." },
    { label: "Only an aria-label on the input is ever acceptable.", misconception: "aria-label works but gives sighted users no visible label, so it is a last resort for icon-only fields. A real <label> is the default; the failure here is having no associated name at all." },
    { label: "The placeholder is fine as long as it has high enough color contrast.", misconception: "Even at perfect contrast the placeholder disappears on focus and is not a reliable accessible name. Contrast does not turn a placeholder into a programmatic label." },
  ]}

<Quiz
  id="03-forms-a11y-choice-2"
  lessonSlug="03-forms-a11y"
  lang="en"
  question="Custom JS validation runs on submit and finds three invalid fields. The team paints them red and scrolls to the first. A keyboard/screen-reader user still hears nothing. What is the highest-leverage missing step?"
  choices={[
    { label: "Move keyboard focus to the first invalid field (firstInvalid.focus()). Focus is still on the submit button at the bottom; only moving focus drops the user on the broken field, where aria-describedby + aria-invalid are read immediately.", correct: true },
    { label: "Scrolling to the first error is enough once it is painted red.", misconception: "Scrolling helps a sighted mouse user only. Color is invisible to a screen reader and useless to a colorblind user, and focus never moved, so nothing is announced. You must move focus, not just the viewport." },
    { label: "Show a single alert() dialog listing all three errors.", misconception: "alert() interrupts everyone, loses the per-field aria-describedby association, and does not place focus where the fix happens. It is a worse experience for keyboard and AT users." },
    { label: "Add aria-required to the fields so the browser re-validates.", misconception: "Once you preventDefault and validate yourself, aria-required changes no behavior. The gap is focus management plus announcement, not a re-trigger of native validation." },
  ]}
/>

<Quiz
  id="03-forms-a11y-choice-3"
  lessonSlug="03-forms-a11y"
  lang="en"
  question="You add a div with role=button and a click handler that styles exactly like the design. A keyboard user reports the button does nothing. Beyond role, what was forgotten?"
  choices={[
    { label: "tabindex=0 to put it in the tab order, and a keydown handler for both Enter and Space (with preventDefault on Space to stop scrolling), plus disabled and focus semantics. role alone does not add focusability or keyboard activation.", correct: true },
    { label: "Nothing — role=button makes a div fully operable.", misconception: "role=button only changes how AT announces the element. It does not add it to the tab order or wire up Enter/Space activation; those are exactly what <button> gives you for free and a div does not." },
    { label: "An aria-label, because a div cannot have an accessible name otherwise.", misconception: "A div with text content does get an accessible name; the missing piece is keyboard operability (tabindex + key handlers), not the name. This is why the native <button> is the senior default." },
    { label: "An onMouseDown handler in addition to onClick.", misconception: "Mouse handlers do not help keyboard users at all. The fix is keyboard activation (Enter and Space) and tab-order membership, which is why reinventing a button is rarely worth it." },
  ]}
/>

<Quiz
  id="03-forms-a11y-choice-4"
  lessonSlug="03-forms-a11y"
  lang="en"
  question="You inject an error message into a div with role=alert in the same render that first mounts that div. Sighted users see it; many screen-reader users hear nothing. Why?"
  choices={[
    { label: "A live region must already exist in the DOM before its text changes for AT to detect the change. Mounting the region and its message together is missed by many screen readers. Render the empty role=alert region up front and inject text only on error.", correct: true },
    { label: "role=alert is the wrong role; you must use role=status for errors.", misconception: "role=status is polite and waits for a pause, which is right for non-urgent updates. Errors warrant assertive role=alert; the bug here is timing of when the region exists, not the choice of role." },
    { label: "aria-live regions only work on the document body, not a div.", misconception: "Any element can be a live region. The constraint is that it must be present before the content changes, so the change is observed rather than the region simply appearing already-populated." },
    { label: "Screen readers never announce dynamically inserted text.", misconception: "They do announce changes inside a pre-existing live region. The failure is mounting the region and its text in one pass, so there is no change to observe." },
  ]}
/>

  lang="en"
  question="Design needs a styled dropdown the native select cannot match visually. Which implementation is the senior default, and why?"
  choices={[
    { label: "Style the native select as far as CSS allows and accept the OS picker. It ships role, focusability, type-ahead, keyboard open/close, and OS-native option rendering you do not have to build or maintain — correct in every browser and AT by default.", correct: true },
    { label: "Build a div-based listbox with role and tabindex but skip the full keyboard pattern for now.", misconception: "A half-built role=listbox is worse than the native select it replaces: arrow keys, type-ahead, Escape/Home/End, and aria-activedescendant are all missing, so it is unreachable or broken for keyboard and AT users." },
    { label: "Hide the native select and overlay a fake div the mouse interacts with.", misconception: "Focus, value, and the visible widget drift apart; keyboard focus lands on an invisible control while the mouse sees a fake one. You get the maintenance cost of both with the correctness of neither." },
    { label: "Use a div with onClick and matching CSS — it looks identical.", misconception: "A div has no role, is not in the tab order, and has no keyboard behavior, so it is invisible to screen readers and unreachable by keyboard. It is the classic silent WCAG 1.3.1 / 4.1.2 failure." },
  ]}

<Recap lang="en">
The through-line is one decision tree: every control needs a programmatically associated name (real label, not placeholder); errors must live in a pre-existing live region and be tied to their field with aria-invalid + aria-describedby; on a failed submit you must move focus to the first invalid field, not just scroll; native elements ship role, focusability, and keyboard handling you cannot fully replicate; and the moment you preventDefault you inherit the focus and announcement responsibilities the browser handled for free. Reach for ARIA-rebuilt widgets last, and only when the native element genuinely cannot do the job. Now when you encounter a PR adding a custom dropdown or a submit handler, you know which five questions to ask before approving it.
</Recap>
