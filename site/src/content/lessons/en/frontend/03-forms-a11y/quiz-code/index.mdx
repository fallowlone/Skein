## Snippet 1 — the label that associates with nothing

```jsx
function EmailField() {
  return (
    <div className="field">
      <label>Email</label>
      <input type="email" name="email" placeholder="you@example.com" />
    </div>
  );
}
```

    { label: "The placeholder is enough; the screen reader just needs aria-hidden removed.", misconception: "A placeholder is not a programmatic name and vanishes on focus. There is no aria-hidden here; the real gap is the absent htmlFor/id association." },
    { label: "Add aria-label=\"Email\" to the div wrapper.", misconception: "aria-label on a non-interactive div does nothing for the input's name. Put the association on the control: htmlFor/id, or wrap the input in the label." },
    { label: "type=email already exposes the name 'Email' to AT.", misconception: "type=email controls validation and keyboard, not the accessible name. The name comes from an associated <label>, which is missing." },

## Snippet 2 — the error region that announces nothing

```jsx
function Form() {
  const [error, setError] = useState("");
  return (
    <form onSubmit={validate}>
      <input id="zip" name="zip" aria-describedby="zip-err" />
      {error && <div id="zip-err" role="alert">{error}</div>}
      <button>Submit</button>
    </form>
  );
}
```

<Quiz
  id="03-forms-a11y-code-2"
  lessonSlug="03-forms-a11y"
  lang="en"
  question="Sighted users see the error; many screen-reader users hear nothing. Why, and what is the minimal fix?"
  choices={[
    { label: "The role=alert region only mounts when error becomes truthy, so the live region and its text appear together — many screen readers miss that. Render the region unconditionally and put only the text behind the condition, so the region is always present and its text changes.", correct: true },
    { label: "role=alert is wrong; switch the whole region to role=status.", misconception: "role=status is polite and right for non-urgent updates, but errors warrant assertive role=alert. The defect is that the region is conditionally mounted, not the role." },
    { label: "aria-describedby points at an element that may not exist, so it should be removed.", misconception: "Removing aria-describedby breaks the field-to-message link. Keep it and make the target persistent; the describedby is correct, the conditional mount is not." },
    { label: "useState cannot drive a live region; you need a ref.", misconception: "State updates the DOM fine. The issue is the element entering the DOM together with its text rather than the text changing inside an already-present region." },
  ]}
/>

## Snippet 3 — the submit handler that forgets focus

```jsx
function handleSubmit(e) {
  e.preventDefault();
  const invalid = fields.filter((f) => !f.valid);
  invalid.forEach((f) => {
    f.el.setAttribute("aria-invalid", "true");
    setMessage(f.id, f.error); // writes into a persistent live region
  });
  // ...nothing else
}
```

<Quiz
  id="03-forms-a11y-code-3"
  lessonSlug="03-forms-a11y"
  lang="en"
  question="aria-invalid is set and the messages are announced, yet keyboard users say the form 'does nothing' on a failed submit. What is missing?"
  choices={[
    { label: "Focus is never moved, so it stays on the submit button at the bottom of the form. Add invalid[0].el.focus() so the user lands on the first invalid field, where its aria-describedby error is read immediately.", correct: true },
    { label: "setAttribute is unreliable; use a controlled aria-invalid prop instead.", misconception: "Whether you set aria-invalid via attribute or prop, the user still never reaches the field. The missing step is moving focus, not the mechanism for the attribute." },
    { label: "The fields need autofocus so the browser focuses them.", misconception: "autofocus only fires on initial page load, not on a submit-time validation failure. You must imperatively focus the first invalid field after validating." },
    { label: "preventDefault should be removed so native validation focuses the field.", misconception: "Removing preventDefault discards the custom messages and async checks this handler exists for. Keep it and take ownership of focus: call focus() on the first invalid field." },
  ]}
/>

## Snippet 4 — the controlled input that drops its name

```jsx
function NameField({ value, onChange }) {
  return (
    <>
      <span className="lbl">Full name</span>
      <input
        value={value}
        onChange={(e) => onChange(e.target.value)}
      />
    </>
  );
}
```

  lessonSlug="03-forms-a11y"
  lang="en"

  choices={[
    { label: "Controlled state is fine, but the visible text is a span, not an associated label, so the input has no accessible name. Make it a label with htmlFor=\"name\" and id=\"name\" on the input (or wrap the input). Controlled-vs-uncontrolled is orthogonal to label association.", correct: true },
    { label: "Controlled inputs cannot have labels; switch to an uncontrolled input with a ref.", misconception: "Controlled and uncontrolled inputs both associate with a label identically. The control mode is unrelated to the missing label; making it uncontrolled would not add a name." },
    { label: "value without defaultValue makes the field read-only, breaking AT.", misconception: "An onChange handler is present, so the input is editable, not read-only. The accessibility gap is the missing label association, not the value/defaultValue choice." },
    { label: "The fragment wrapper hides the input from the accessibility tree.", misconception: "A React fragment renders nothing and does not affect the tree. The input is exposed; what it lacks is a programmatically associated name." },
  ]}

<Recap lang="en">
Every form accessibility bug is visible in the markup or the submit handler: a label must be associated by htmlFor/id or wrapping (a placeholder or sibling span is not a name); a live region must be persistent so its text change is observed; a failed submit must imperatively move focus to the first invalid field, not just set aria-invalid; and controlled-vs-uncontrolled is orthogonal to whether the input has an accessible name. Read the markup, find the broken association or the un-moved focus, then fix that before anything else.
</Recap>
