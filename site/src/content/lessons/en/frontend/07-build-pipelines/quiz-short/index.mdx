Resolve turns every import into a real file on disk (walking node_modules, honouring exports maps and tsconfig aliases). Transform rewrites each file independently — TS to JS, JSX to createElement, syntax down-leveling. Bundle stitches the module graph into chunks, decides code-splitting, and tree-shakes. Minify renames locals and prunes dead branches. Emit writes content-hashed files plus source maps to dist. The key mental model: transform is per-file and embarrassingly parallel, so compiled tools like esbuild and SWC scale across cores there; bundle is a whole-graph, largely serial dependency walk, which is why it parallelises far less and why transform-stage speedups do not carry over to it." },
    { q: "Tree-shaking only works on static ES modules. What three things defeat it, and how do you fix each?", a: "First, CommonJS: module.exports is assembled at runtime, so the bundler cannot prove which keys are unused and keeps the whole module — importing one helper from lodash's CJS build can cost ~24 KB versus ~46 bytes from lodash-es. Fix: use the ESM build or deep imports like lodash/debounce. Second, side effects: if importing a module does observable work (injects CSS, registers a polyfill, mutates a global) the bundler must keep it unless package.json honestly declares sideEffects: false. Fix: set the field, listing genuinely impure files like '*.css'. Third, ESM-to-CommonJS down-leveling: a transform such as @babel/preset-env can rewrite import/export into require/module.exports before the bundler sees it, silently turning a shakeable graph opaque. Fix: keep modules as ESM through the transform stage and target a modern baseline." },
    { q: "Why do 'works in dev, breaks in prod' bugs happen with tools like Vite, and how does a senior prevent them?", a: "Because dev and prod are not the same code path. In dev, Vite serves source as native ES modules straight to the browser — no bundling, instant start, millisecond HMR — while in prod it bundles with Rollup, because thousands of unbundled module requests would be far too slow over the network. Two different tools doing resolution, code-splitting, and side-effect handling means the output can legitimately differ: a circular import the browser tolerates but the bundler reorders, or a module tree-shaken in prod but fully present in dev. The prevention is to stop trusting the dev server as a proxy for prod: run a real production build locally with vite build and vite preview, and gate merges in CI on a smoke test against the built output, not the dev server." },
    { q: "Explain content hashing and the vendor-chunk mistake it exposes.", a: "The emit stage names files by a hash of their contents — index-a1b2c3.js — so a filename changes only when the bytes change. That lets you serve assets with Cache-Control: max-age=31536000, immutable (a year), and the browser never re-downloads an unchanged chunk; change one line and only that chunk's hash changes while everything else stays cached. The classic mistake is letting vendor code (React, big deps) share a chunk with app code: then every app deploy changes the combined chunk's bytes, busts the vendor hash, and forces returning users to re-download megabytes that never actually changed. Fix: split vendor into its own chunk so its hash stays stable across your frequent app deploys." },
    { q: "What do source maps do, what setting should production use, and why?", a: "A source map maps minified, bundled dist code back to original source, so a stack trace points at Button.tsx:42 instead of index-a1b2c3.js:1:88431. They are debugging metadata only — they never change how the code runs. In production the right setting is hidden source maps: the map is generated and uploaded to your error tracker, but no sourceMappingURL comment is emitted into the public bundle, so you get readable traces in the tracker without exposing your source to anyone with devtools. Disabling source maps entirely leaves every prod error unreadable; emitting them publicly leaks your source." },
    { q: "How does build caching speed up CI, and what is the difference between content-hash caching and a persistent build cache?", a: "Build caching avoids redoing work whose inputs have not changed. A persistent build cache (esbuild incremental, Vite's dep pre-bundle cache, webpack filesystem cache, Turbopack/Nx caches) keys transformed or bundled outputs by a hash of their inputs — source plus config plus tool version — so an unchanged module is reused instead of re-transformed, which is what turns a cold multi-minute CI build into a warm few-second one. That is distinct from content hashing in the emit stage, which hashes the final output bytes to produce stable, cache-bustable filenames for the browser. One is an internal build-time cache that speeds up producing the artifact; the other is an output-naming scheme that controls the browser's HTTP cache. To trust either, make the cache key include the tool version so a tool upgrade invalidates stale entries." },
