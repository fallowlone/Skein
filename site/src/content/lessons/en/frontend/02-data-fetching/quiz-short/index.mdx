    { q: "Why does the location of a data fetch decide LCP more than network speed?", a: "LCP fires when the page's largest content element becomes visible, and that element sits at the end of a critical path of sequential round-trips. A client fetch can only start after the HTML arrives, the JS bundle downloads and parses, React mounts, and the effect fires — adding 2 to 4 sequential trips before the data even leaves the browser. A server fetch happens while generating the HTML, so the browser receives the content already inside the markup: one effective round-trip. Same network, same database — the location changes the number of trips on the critical path, which is what sets LCP. The rule: put the LCP element's data on the server, leave interactive state on the client." },
    { q: "Why do component-level useEffect fetches form a waterfall even when the data is independent, and what three patterns dissolve it?", a: "React renders top-down, and each component fires its effect only after it mounts. A child cannot mount until its parent re-renders with data, so even logically independent fetches are serialised by the render cascade — total time becomes the sum, not the max. The fix is parallel dispatch: (1) hoist the fetches to a common parent and Promise.all them, so total drops to the slowest single fetch; (2) on the client, useQueries to run multiple queries from one hook; (3) in RSC, keep the fetches as sibling async Server Components so the server resolves them concurrently. The structural twin is the database N+1 query — same antipattern, same cure: lift and batch." },
    { q: "What is the 'use client' boundary rule, and what does marking everything 'use client' cost?", a: "Server Components run only on the server, ship zero JS, and have no state or effects; Client Components are marked 'use client', run on both sides, and ship their code to the browser. The rule is Server Component by default, push 'use client' to the leaves that genuinely need interactivity — onClick, useState, useEffect, browser APIs. Marking everything 'use client' out of habit defeats the whole point: the browser bundle balloons back to SPA size (a real app can be the difference between ~60KB and ~240KB) and you carry RSC's complexity for none of its benefit. Streaming reduces TTFB; the bundle win comes only from components that actually stay server-side." },
    { q: "Explain stale-while-revalidate and single-flight deduplication in TanStack Query / SWR.", a: "Stale-while-revalidate (from RFC 5861) serves cached data immediately even if it might be stale, then refetches in the background and updates the UI if the data changed. staleTime controls how long a result is considered fresh (no background refetch); gcTime controls how long an unused entry lives before garbage collection (default 5 minutes). Single-flight deduplication means that when N components mount and all call the same queryKey, the library fires exactly one network request and shares the result — collapsing N identical in-flight requests into one, avoiding wasted bandwidth and cache races. Together they make revisits feel instant and make it safe to call the same query from many components." },
    { q: "What is the canonical optimistic-update pattern, and what is the classic bug?", a: "In onMutate: cancel outgoing refetches for the key, snapshot the current value with getQueryData, apply the full optimistic state with setQueryData, and return the snapshot as context. In onError: restore the snapshot. In onSettled: invalidate the key to reconcile with canonical server state. Two classic bugs: (1) a partial optimistic shape — e.g. setting liked:true but forgetting to increment likeCount — so the server's correctly-shaped response replaces it and the UI flickers; (2) skipping the getQueryData snapshot, so an error rollback writes undefined instead of the real previous state (the Spotify playlist-vanish bug). The optimistic shape must mirror the server response, and you must always snapshot before mutating." },
    { q: "Name the cache layers in a Next.js 15 app and why a mutation must invalidate more than one.", a: "There are roughly five: the CDN edge cache (URL-keyed), the Next.js fetch cache for RSC fetch() calls, a database/Redis query cache, the browser HTTP cache (Cache-Control), and the client library cache (TanStack Query / SWR, keyed by queryKey). A mutation that changes data must invalidate every relevant layer — revalidatePath/revalidateTag on the server, queryClient.invalidateQueries on the client. The most common production bug is invalidating only the server layers while the client query cache keeps serving the old response for its full staleTime/gcTime window, so users stare at stale data even though the server is already correct." },
