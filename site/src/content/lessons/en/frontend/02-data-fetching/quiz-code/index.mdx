## Snippet 1 — the server component loop

```tsx
// Server Component — renders a 50-item order list
async function OrderList({ ids }: { ids: string[] }) {
  const orders = [];
  for (const id of ids) {
    orders.push(await fetchOrder(id));   // one await per iteration
  }
  return <ul>{orders.map(o => <Order key={o.id} data={o} />)}</ul>;
}
```

## Snippet 2 — the query key

```typescript
function useProduct(id: string, currency: string) {
  return useQuery({
    queryKey: ['product', id],                 // currency is NOT in the key
    queryFn: () => fetchProduct(id, currency),
  });
}
```

    { label: "It double-fetches because the currency change invalidates the key.", misconception: "The key did not change — currency is not in it — so nothing invalidates. The bug is the opposite: a stale cache hit, not an extra fetch." },
    { label: "The fix is to lower staleTime to 0.", misconception: "staleTime=0 forces refetch-on-mount but still returns the stale cached USD value first, and conflates two currencies in one entry. Identity belongs in the key; every input that changes the response must be part of queryKey." },

## Snippet 3 — the RSC layout

```tsx
// Server Component page
async function ProductPage({ id }) {
  const product = await fetchProduct(id);        // fast, ~50ms
  return (
    <main>
      <h1>{product.name}</h1>
      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews productId={id} />               {/* slow, ~800ms */}
      </Suspense>
    </main>
  );
}
```

    { label: "At ~850ms — the server must finish all fetches before sending any HTML.", misconception: "That is blocking SSR without Suspense. Here the Suspense boundary around Reviews lets the server stream the title immediately and send the reviews chunk later." },
    { label: "At ~800ms — Suspense waits for all children before revealing the parent.", misconception: "Suspense isolates only its subtree behind the fallback. The h1 is outside the boundary and streams with the shell; only Reviews waits behind the skeleton." },
    { label: "Never on the server — the title needs client hydration to appear.", misconception: "The title is server-rendered HTML and is visible before any JS runs. Hydration attaches interactivity afterward; it is not required for the title to paint." },

## Snippet 4 — the search box

```typescript
function useSearch(query: string) {
  const [results, setResults] = useState([]);
  useEffect(() => {
    fetch(`/api/search?q=${query}`)
      .then(r => r.json())
      .then(setResults);                  // no cleanup, no cancellation
  }, [query]);
  return results;
}
```

  choices={[

    { label: "Wrap setResults in a setTimeout to delay the update.", misconception: "A delay does not order responses — the stale 'reac' response can still land last. Only cancellation (or queryKey versioning) guarantees the latest query wins." },
    { label: "Memoise the query string with useMemo.", misconception: "useMemo avoids recomputing a value; it does nothing about out-of-order network responses. The race is in fetch timing, not in recomputation." },
    { label: "Move the fetch out of useEffect into the render body.", misconception: "Fetching during render is a worse anti-pattern — it fires on every render and still has no cancellation. The fix is an AbortController in the effect cleanup, or a query library that cancels stale keys." },
  ]}

<Recap lang="en">
Every fetching bug is visible in the code: an await inside a loop is a server-side waterfall — Promise.all bounds it to the slowest call; a queryKey must contain every input that changes the response or the cache serves the wrong entry; a Suspense boundary lets the shell stream at TTFB while slow children resolve independently; and an uncancelled effect fetch races on fast input — an AbortController in the cleanup, or a library that cancels stale keys, makes the latest query win. Read the code, trace the round-trips, fix the structure before reaching for a knob.
</Recap>
