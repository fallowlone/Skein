<Explanation>

## The engine does not have an event loop

The browser overview lessons treat the event loop as one machine — [browser/01-event-loop/01-loop-model](/learn/browser/01-loop-model) is the runtime view. Here we separate its parts. ECMAScript defines jobs and host hooks such as `HostEnqueuePromiseJob`; it does not define a browser event loop. The HTML Standard defines task selection and microtask checkpoints. V8 implements JavaScript execution and provides a microtask queue and checkpoint API to its embedder.

So the division of labour is:

- **The browser host** selects tasks, requests checkpoints, and decides when to update rendering. In the HTML model, the event loop has both task queues and a microtask queue.
- **V8** executes JavaScript and provides microtask handling, including `PerformMicrotaskCheckpoint`, for its embedder to use. ECMAScript jobs, HTML microtasks, and a particular V8 queue are related layers, not identical names for one specification object.

When people say "microtasks run after the current task," they describe a checkpoint in the host's processing model. V8 runs the JavaScript jobs involved, but the host controls the scheduling boundary.

## One browser turn: task, checkpoint, possible rendering

Imagine a timer task whose callback queues a Promise reaction. The browser runs the task's steps, calling into V8 for the callback. The callback runs to completion and returns. In the HTML event-loop processing model, the browser then clears the current task and **performs a microtask checkpoint**. That checkpoint runs queued microtasks until the queue is empty, including microtasks they enqueue. The browser may update rendering when there is a rendering opportunity; it is not required to render after every task.

<EventLoopTurnFig lang="en" />

The ordering comes from the host's checkpoint step, not from a promise reaction being part of the original callback. The reaction is a microtask, separate from the timer task. It runs before the next selected task and before any later rendering opportunity. A different checkpoint can also occur when a script finishes and its execution context stack is empty.

## Predict the canonical ordering

The mechanism above is easy to nod at and easy to get wrong, so make it concrete. Four lines: log a line, arm a zero-millisecond timer, queue a Promise reaction, log another line. Intuition says the timer fires "immediately" at 0ms, or that the Promise wins because "promises are faster." Neither is the mechanism. The script task runs to completion — both logs print — and only then does the host perform the microtask checkpoint, which runs the queued reaction before the browser ever selects the armed timer task. The ordering belongs to the host's lanes, not to the objects themselves.

<EventLoopPredict lang="en" />

Read the stepper's final state as a rule of thumb: anything queued as a microtask during a task runs at that task's checkpoint; anything queued as a task waits for the host to select it. When you profile a page and the callback order surprises you, the explanation is almost always which lane something landed in — and when that lane drains.

## Who provides the checkpoint, and who calls it

`PerformMicrotaskCheckpoint` is a V8 API. An embedder can use V8's automatic or explicit microtask policy; the browser integration must satisfy HTML's observable ordering. Node has its own scheduling rules, including its `nextTick` queue, covered in the next lesson. Do not infer an exact C++ call stack from the conceptual diagram: the portable lesson is that the host defines *when*, while V8 supplies execution machinery.

<Misconception id="mc-js-has-loop">
  <p><strong>"The engine chooses when Promise callbacks run."</strong> The host sets checkpoint boundaries. V8 executes the queued JavaScript jobs when a checkpoint is performed. In a browser, HTML specifies the observable task and microtask ordering.</p>
</Misconception>

## Run-to-completion is the load-bearing rule

Within one ordinary callback, JavaScript runs to completion: another task or microtask does not pre-empt it. `await` is an explicit suspension point. The async function yields; when the awaited value settles, a queued reaction can resume it at a later microtask checkpoint. That is different from the operating system pausing a running JavaScript stack at an arbitrary instruction.

<Recap lang="en">
The event loop belongs to the host, not the JavaScript engine. In a browser, HTML specifies task selection and checkpoint ordering; V8 runs JavaScript and supplies microtask machinery. A timer callback can queue a Promise reaction, return, and then have that reaction run at the host's checkpoint before another task is selected. The browser may render later when it has an opportunity. This distinction explains both the reliable ordering of microtasks and the absence of a guaranteed paint after each task.
</Recap>
