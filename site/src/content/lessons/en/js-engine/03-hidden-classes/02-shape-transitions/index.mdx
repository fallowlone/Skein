## Transitions are edges in a shared tree

Recall the one-line version from `browser/03-v8-internals/03-hidden-classes`: adding `x` then `y` reaches a different leaf than adding `y` then `x`, so order matters. Now the mechanism. Every Map stores a forward **TransitionArray** keyed by `{property name, attributes}`. Adding a property:

1. Looks up the `{name, attributes}` edge in the current Map's TransitionArray.
2. If an edge exists, **follows** it — no allocation, you reuse the existing child Map and its (shared) DescriptorArray.
3. If no edge exists, **creates** a new child Map (extending the parent's DescriptorArray by one descriptor), records the edge, and points the object at the new Map.

Objects that start from the same initial Map can share transition paths. Once a path exists, later objects with the same construction order follow it without creating new Maps. A different order may create another branch; repeated use of that order can reuse it too.

```js
const a = {}; a.x = 1; a.y = 2;   // empty -> +x -> +x,y   (creates 2 edges)
const b = {}; b.x = 3; b.y = 4;   // empty -> +x -> +x,y   (follows them; 0 new Maps)
const c = {}; c.y = 5; c.x = 6;   // empty -> +y -> +y,x   (new branch; 2 new Maps)
```

## Three more ways to transition (not just adding properties)

The overview implied transitions come only from adding properties. They do not. There are three other triggers, and they bite in production:

- **Elements-kind change.** Writing a float into a `PACKED_SMI_ELEMENTS` array, or creating a hole, transitions the array's Map to a wider elements kind (`PACKED_SMI → PACKED_DOUBLE → PACKED_ELEMENTS`, and the HOLEY variants). One-way, like the property tree.
- **Field representation generalization.** This is the big one. A field starts narrow — say `Smi`. If any instance later stores a value that does not fit (`2.5`, or a string), the field's representation must **widen** to `Double` or `Tagged`. But the representation is a property of the *Map*, shared by all instances. So V8 cannot just change one object; it must generalize the Map.
- **Constness loss.** A field can be marked `const` when instances initialize it without later reassigning it. Different instances may hold different initial values. A later write to an existing field can make the descriptor mutable and invalidate code that relied on constness.

These changes affect V8’s shape and feedback machinery even though the set of property names may stay the same. Whether they create a new Map, generalize a descriptor in place, or invalidate optimized code depends on the specific transition.

## Deprecation and migration: one widening path

Suppose many objects share Map `M1`, where `temp` has `Smi` representation. One object stores `98.6`. V8 needs a representation that can hold that value. Some generalizations can update metadata in place; the figure shows the case where V8 creates a replacement transition chain and deprecates the old Map:

1. V8 creates a new path with `temp` represented as `Double` and marks the old path deprecated.
2. Existing objects can still point to the old Map. V8 does not scan the heap to rewrite them all immediately.
3. When an affected object is accessed through a path that checks its deprecated Map, V8 migrates that object to the current layout before continuing.

This is a V8 implementation mechanism, not JavaScript semantics. The transition is one-way for this field representation: alternating integer and floating-point values after widening does not repeatedly recreate the original narrow Map.

<ShapeMigrationFig lang="en" />

To inspect this behavior in a V8 build that exposes the flags, use `--trace-generalization` for field changes and `--trace-migration` for object migration. Check the flags in your runtime with `node --v8-options`.


## Why varying key orders can cost more

A builder that adds the same keys in many orders can create several branches from one initial Map. Repeated orders reuse their paths, but a load site receiving objects from many branches sees more receiver Maps. That can make its inline cache polymorphic or megamorphic and reduce opportunities for shape-specific optimization.

For a stable record shape, initialize fields in a consistent order with defaults that match their expected value types. For genuinely dynamic key sets, a `Map` collection may be a better fit. Measure the hot path before changing a data model.

</Misconception>

<Recap lang="en">
A Map transition tree lets objects with the same starting Map reuse a property-addition path. Different insertion orders can produce different final Maps, while repeated orders reuse their own paths. Elements-kind changes, field-representation generalization, and constness changes can affect the shape or optimized code without adding a property. In the illustrated V8 deprecation path, a wider field representation creates a replacement Map and old instances migrate lazily; other generalizations can happen in place. A load site that sees many receiver Maps may lose shape-specific fast paths, but the performance effect should be measured rather than assumed.
</Recap>
