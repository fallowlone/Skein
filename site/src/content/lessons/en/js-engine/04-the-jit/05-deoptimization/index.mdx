## A guard protects the fast path

Optimized V8 code can specialize a property access for a particular object Map. A guard checks that assumption at runtime. If the Map differs, V8 cannot keep using that specialized instruction; it transfers execution to less specialized code. This is **eager deoptimization**: the guard fails while optimized code runs. The operation does not restart from the beginning, because earlier statements may already have changed program state.

Follow one eager deopt as a chain, not a verdict. The optimized code carries an **assumption** — `receiver.map → M_Point`, compiled into a guarded fast load. At runtime the **guard** checks the live receiver against that assumption. The actual receiver arrives with `receiver.map → M_Rect`: the **guard fails**, the speculation is invalidated, and V8 **deopts** — abandons the specialized path for this activation. It then **reconstructs** the general execution state the lower tier expects (next section) and **continues** from the corresponding bytecode position, returning the correct value. Nothing restarts and nothing is replayed: the chain runs assumption → guard → fail → deopt → reconstruct → continue, in that order, within one activation.

The framing matters for how you read traces: **deoptimization is a correctness mechanism** — the engine abandons an invalidated assumption and reconstructs a safe, general execution state — not merely a slowdown. A deopt is the price of keeping speculative code honest; the slowdown is a side effect of the tier change, not the point of the mechanism.

V8 also has **lazy deoptimization points** around operations such as calls. An assumption may be invalidated by work outside a particular optimized frame, for example a dependency on a changed prototype. V8 can invalidate dependent optimized code and arrange a safe continuation at an appropriate point. “Lazy” describes the kind of deopt point and continuation; it is not a promise that every invalidation waits until the next call of the function. Exact behavior depends on the compiled code and V8 version.

## Rebuild the state that the interpreter needs

Optimized code may keep a live value in a machine register, another in a stack slot, and a number in an unboxed representation. Ignition's interpreter frame expects its own register values and a bytecode position. At compilation time, V8 records deoptimization metadata for points where it might need to leave optimized code. The deoptimizer uses that metadata to materialize the values and frames needed to continue, including inlined calls and representation changes when applicable.

## When repeated deopts matter

One deopt is expected in a speculative system. Repeated deopts can waste compilation work and time in slower tiers, but V8 can adapt its feedback or stop optimizing a troublesome path. There is no universal “forever loop,” fixed microsecond cost, or guaranteed slowdown ratio. Measure a real workload before changing code for a deopt.

Possible causes to investigate include a shape guard seeing an unexpected Map, a numeric guard seeing a value outside its assumption, or an array access encountering a different elements kind or bounds case. None guarantees a deopt by itself: the generated guards depend on feedback and the compiler tier. Use `--trace-deopt` to see actual bailout reasons. Pair it with a profiler or benchmark that reproduces the workload; a trace says *what happened*, not how much wall time it cost.

A useful fix is to keep input contracts stable at a measured hot path. For instance, validate nullable input before numeric work if traces show that the mixed input repeatedly defeats a useful specialization. Keep the general path correct, and compare before and after under the same workload.

<Misconception id="mc-deopt-fatal">
  <p><strong>“A deopt means my function is permanently slow.”</strong> V8 can continue in a lower tier and may optimize again. A deopt trace is a clue; sustained performance impact requires measurement.</p>
</Misconception>

<Recap lang="en">
Optimized code can rely on assumptions only while guards or dependencies protect them. When an assumption fails, V8 deoptimizes: metadata recorded at compile time lets it reconstruct the live state and continue in less specialized code without replaying earlier effects. Eager deopts occur at failing guards; lazy deopt points support continuations around operations such as calls and invalidated dependencies. A single bailout is expected. For repeated bailouts, inspect `--trace-deopt`, reproduce the workload, and measure before changing code.
</Recap>
