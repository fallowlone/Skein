<Hook>
A bundle can define many functions that a user never calls in one visit. Building an AST and bytecode for every body at startup would spend time and memory on code that may remain untouched. V8 can make a narrower first pass over a function, then finish the work when that function is needed. The subtle part is that the first pass cannot simply ignore the body: an inner function may capture a variable from its outer scope.
</Hook>

<Crux>V8 can defer a function's AST and bytecode, but its PreParser still checks syntax and records enough scope information for surrounding code to compile correctly.</Crux>

<Explanation>

## What V8 defers

The full parser builds an **abstract syntax tree** and resolves the information needed to generate Ignition bytecode. For a function that is not needed immediately, V8 can instead use its **PreParser**. It walks the syntax without building that function's full AST or compiling its body to bytecode. If the function is later called, V8 fully parses and compiles it then. This is an engine strategy, not a JavaScript language guarantee: syntax and V8's heuristics decide which functions are eager.

A preparse is cheaper than a full parse, but it is still real work. It must check syntax and early errors; a never-called function with invalid syntax cannot wait until its first invocation to fail. It also records the source range and metadata needed by an outer function. “Skim” is useful intuition, but **the PreParser does more than find the closing brace**.

## The scope information that cannot be skipped

Consider an outer function that returns an inner function referring to `id`. The inner function may run after `outer` has returned. V8 must know that `id` has to survive in a heap context, instead of living only in a stack frame that disappears on return.

```js
function outer(id) {
  function inner() { return id; }
  return inner;
}
```

Even while deferring `inner`'s AST, the PreParser tracks relevant variable **declarations and references**. That lets the full parse of `outer` allocate variables correctly and detect conflicts. V8 also retains compact variable-allocation metadata so a later parse of `inner` need not re-preparse nested bodies merely to reconstruct outer scope decisions.

## Two outcomes after the first pass

If `inner` is **never called**, its full AST and bytecode need not be built during this execution. If it **is called**, V8 returns to its source span, fully parses it, and compiles bytecode. That function has paid for both a preparse and a full parse, but this is **not a universal 2× penalty**: the preparser is cheaper, and costs vary with the code and compilation path. Lazy parsing trades some later work for lower initial work and memory use across code that may never run.

Modern V8 also avoids repeatedly preparsing the same nested function just because enclosing functions are compiled at different times. The compact metadata from the first pass helps it skip nested bodies while resolving scopes. This matters in deeply nested bundles, where repeated scans used to compound the cost.

## When eager parsing can help

V8 recognizes some **possibly invoked function expressions** (PIFEs). A parenthesized expression such as `(function(){…})` is a hint that the function may be called immediately, so V8 may eagerly parse and compile it. The old `optimize-js` tool exploited this pattern. V8's own measurements later found that the broad wrapper strategy offered much less benefit after parser improvements; eagerly compiling too much increases memory and can worsen startup. Measure the actual startup path before changing source or bundler output for this heuristic.

```js
(function bootstrap() {
  startApp();
})();

function maybeLater() {
  showOptionalFeature();
}
```

The first form gives the parser an early signal. The second is eligible for lazy treatment, subject to V8's other decisions. Parentheses do not change JavaScript semantics or guarantee a speedup.

<Misconception id="mc-lazy-free">
  <p><strong>“Lazy parsing skips a function entirely until it runs.”</strong> The first pass still validates syntax and tracks information needed by surrounding scopes. The saved work is the deferred full AST and bytecode for functions that are not yet needed.</p>
</Misconception>

<Recap lang="en">
V8 can preparse a function rather than build its full AST and bytecode immediately. The PreParser checks syntax and early errors, records the source range, and tracks variable declarations and references so enclosing scopes can allocate captured values correctly. For `outer(id)` returning `inner`, this matters even before `inner` runs: `id` must survive in a context. An unused `inner` may never need full compilation; on its first call V8 fully parses and compiles it. The second pass adds work, but its cost is not a universal multiplier. V8's parenthesized-function heuristic can make likely immediate calls eager, while excessive eager compilation increases startup and memory costs. This prepares the next lesson: once a function is compiled, Ignition has bytecode to execute.
</Recap>
