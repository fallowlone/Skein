## Bytecode: compact by design, and the reason was memory

After the parser builds an AST for a function that needs compilation (recall lazy parsing), the **bytecode generator** lowers it into **Ignition bytecode**: a compact instruction stream for a virtual machine. An instruction has an opcode and may have operands; its total size varies. In V8's original Ignition measurements, the complete bytecode stream occupied about **25–50% of the corresponding old baseline machine code**.

That compactness was the point. The old baseline machine code consumed substantial memory, including for functions that executed only once. Ignition reduced that footprint; V8 reported a **ninefold reduction in baseline, non-optimized code memory on ARM64 low-memory Android devices** in its initial rollout. This is a historical measurement for that category and platform, not a universal saving for the entire heap. JIT tiers recover speed for hot code.



## Register machine, not stack machine

When you read bytecode output from `d8 --print-bytecode` and see unfamiliar operand patterns, the register model is the key to decoding them. There are two classic ways to build a bytecode VM. A **stack machine** (the JVM, CPython) keeps operands on an implicit operand stack: `PUSH a; PUSH b; ADD` pops two, pushes the sum. A **register machine** keeps operands in named registers and operations reference them directly: `ADD r1, r2`. Ignition is a **register machine**.

The accumulator makes many common instructions short because one input and the result need no explicit operand. It can avoid repeated loads and stores between successive expression steps. The exact instruction count depends on the expression; register bytecode does not guarantee fewer dispatches for every program.

Ignition's register model is specifically an **accumulator + register file**:

- The **accumulator** is a single implicit register that most bytecodes read from and write to. It threads intermediate values from one instruction to the next, so operands do not all need an explicit name. Many ops take *one* explicit operand and implicitly use the accumulator as the other input and as the output.
- The **register file** includes argument registers such as `a0`, `a1` and local or temporary registers such as `r0`, `r1`, allocated in the function frame.

## Reading real bytecode

Take the simplest function and look at what Ignition runs. Run `d8 --print-bytecode add.js` on:

```js
function add(a, b) { return a + b; }
add(1, 2);
```

You get something close to this (operands and slot indices abbreviated):

```text
Ldar a1          // load argument b into the accumulator
Add a0, [0]      // accumulator = a0 (a) + accumulator (b); feedback slot 0
Return           // return the accumulator
```

Notice the accumulator-centric shape: `Ldar` (**L**oa**d** **A**ccumulator from **R**egister) puts `b` in the accumulator; `Add a0, [0]` adds register `a0` (the argument `a`) to the accumulator and leaves the sum in the accumulator; `Return` returns the accumulator. There is no `Push`/`Pop` — the accumulator is the shared workspace.

## The `[slot]` is where the JIT gets its type information

Look again at `Add a0, [0]`. That `[0]` identifies a **feedback-vector slot** for this addition site. Instructions that collect feedback, including arithmetic, property access, and calls, use slots to record observations such as operand types, object shapes, or call targets. The feedback vector is associated with an executing function and can be allocated lazily; it is separate from the bytecode stream. `Add` updates its slot as part of the addition, not in a separate bytecode step.

This is the bridge to the optimiser. When a function gets hot, a JIT tier can read its feedback and specialize an operation for types observed so far, guarded by checks or a deoptimization path. Feedback collection has runtime and memory costs; V8 therefore allocates feedback vectors lazily for functions that execute enough bytecode to benefit.

<Misconception id="mc-bytecode-fast">
  <p><strong>"Bytecode exists to make JavaScript faster than machine code."</strong> Ignition's original motivation was a smaller code footprint. Interpreting an operation adds dispatch overhead; JIT tiers compile hot code when the extra machine code is worthwhile.</p>
</Misconception>

## Shared bytecode handlers

Each bytecode dispatches to a **handler** that performs its operation. V8 described generating these handlers from TurboFan's low-level, architecture-independent instructions into machine code for each target architecture. The compiled handler for an opcode is shared across functions; individual functions supply bytecode operands and frame values. The next lesson examines how the interpreter dispatches among handlers.

<Recap lang="en">
V8 lowers parsed functions into compact Ignition bytecode. Memory was a central reason for introducing the interpreter: the original bytecode stream was about 25–50% of equivalent baseline machine code. Ignition uses a register file plus an accumulator that acts as an implicit operand for many instructions. `add(a, b)` can compile to `Ldar a1; Add a0, [0]; Return`: load `b`, add `a` to the accumulator, then return its value. During `Add`, feedback slot `[0]` can record the operand types for later JIT specialization. Feedback vectors can be allocated lazily and are distinct from bytecode. Shared handlers execute the opcodes, while each function provides its own operands and frame state. `d8 --print-bytecode` exposes the instruction stream; inspecting feedback itself requires separate tools.
</Recap>
