<Explanation>

## Follow one instruction, not an abstract loop

Ignition is a **register-based interpreter**. Its virtual registers live in the function's interpreter frame; many bytecodes use a dedicated **accumulator** as an implicit input or output. That keeps common instructions compact: a bytecode can name one register and leave the other operand implicit.

Consider a conceptual `Add r0, [slot]` instruction with `r0 = 7` and accumulator `5`. The bytecode pointer identifies `Add`; the dispatch table supplies the address of its handler. The handler reads the operands, performs JavaScript addition, places the result in the accumulator, and transfers control to the next handler. For these numeric inputs, the result is `12`. The feedback slot can record what operand kinds this operation observed.

<InterpreterDispatchFig lang="en" />

The figure separates three things that are easy to conflate: **the bytecode stream** says what to do, **the dispatch table** locates the code that does it, and **the frame** holds the values being changed. `Return` ends this function's bytecode execution; most other handlers eventually dispatch again. Real instruction sizes and specializations vary, so the row labels in the figure show order rather than byte offsets.

## Why the handlers dispatch directly

A simple interpreter could return to one central `switch` after every instruction. Ignition instead uses **threaded dispatch**: each handler fetches the next bytecode, indexes the dispatch table, and jumps to that handler. This gives different bytecodes distinct dispatch sites, which can improve CPU branch prediction compared with one shared indirect branch. It is a performance choice, not a change in JavaScript semantics. Some bytecode pairs can also be handled through specialized shortcuts, so the figure describes the usual mechanism rather than a mandatory branch for every bytecode.

<Misconception id="mc-switch">
  <p><strong>“An interpreter is just a large switch.”</strong> A switch is one valid design. Ignition's handlers dispatch to the next handler through a table, avoiding a return to one central switch on the general path.</p>
</Misconception>

## Execution produces feedback

Selected operations carry an index into the function's **feedback vector**. As property accesses, calls, and arithmetic run, handlers and their support code can record the observed object Maps or operand kinds. Later tiers use that evidence to specialize machine code. Feedback records observations at particular sites; it does not prove that future inputs will always have the same type or shape.

The accumulator is separate from this feedback. It is a live value register that lets adjacent bytecodes pass results cheaply. The feedback vector is a record of past behavior used by tiering and optimization.

## The budget is checked at meaningful points

V8 does not decrement a tier-up counter for every bytecode. A function has an **interrupt budget** in its feedback cell. Ignition reduces it at **loop back-edges** and **function returns**, weighted to reflect work done. A long loop can therefore exhaust the budget before the function returns; repeated calls can contribute through repeated returns.

When the budget is exhausted, V8 enters runtime code and the tiering manager checks whether and how to compile the function. Exhausting the budget is a **decision point**, not a promise that the very next instruction runs optimized code. Compilation may happen in the background, and a future call may enter the new tier. For a hot loop still executing, **on-stack replacement (OSR)** can enter optimized code at a loop header without waiting for the function to return.

<Recap lang="en">
An Ignition instruction is a handoff. The bytecode pointer selects an opcode, the dispatch table locates its handler, and the handler operates on the interpreter frame's virtual registers and accumulator before dispatching the next instruction. This threaded path avoids funneling all opcodes through one central switch. Selected operations also update feedback slots, giving later compilers evidence about observed values without promising that future values match. Separately, loop back-edges and function returns spend a budget stored with the function's feedback cell. When the budget runs out, the tiering manager decides whether compilation is warranted; a future call may use new code, or a long-running loop may enter it through OSR. The next unit follows the values and object layouts that these handlers manipulate.
</Recap>
