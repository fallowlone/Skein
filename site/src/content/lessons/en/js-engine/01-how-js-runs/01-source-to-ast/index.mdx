## Two stages before anything runs

When the runtime hands V8 JavaScript source, the code needed for execution passes through two distinct stages:

1. **Scanning (lexing).** The scanner reads a **UTF-16 view** of the source and groups code units into **tokens**: the words of the language. The underlying source may arrive as Latin1, UTF-8, or UTF-16; V8's character stream presents one view to the scanner. `const x = 42;` becomes `Keyword(const)`, `Identifier(x)`, `Punctuator(=)`, `Number(42)`, `Punctuator(;)`. Whitespace and comments are skipped while relevant line breaks are tracked.

2. **Parsing.** The parser pulls tokens from the scanner and assembles code it compiles into an **Abstract Syntax Tree (AST)** — a nested representation of the program's grammar. Conceptually, `const x = 42;` becomes a declaration with a binding name (`x`) and an initializer (`42`). The flat token stream becomes a tree only for code that is compiled.

Functions not yet needed may instead be **preparsed** and fully parsed when called. The next lesson shows how V8 decides that.

## How the parser builds the tree: recursive descent and precedence

V8's parser is a hand-written **recursive-descent** parser. Its parsing functions call one another as grammar constructs nest; a block can contain statements, which can contain expressions. The parser therefore has to guard against pathological nesting before code executes.

Expressions also have **precedence**: `a + b * c` must bind `b * c` first. V8's binary-expression parser uses operator precedence to decide when to parse a right-hand expression at a tighter level. That is how the nested structure below emerges from a flat sequence of tokens.

```js
// a + b * c parses to this tree shape (the * binds tighter than +):
//        (+)
//       /   \
//      a    (*)
//          /   \
//         b     c
```

## The AST is transient — it is NOT what runs

This is the key correction to a naive model. People imagine the engine walking the AST to execute the program, like a tree-walking interpreter. **V8 does not do this.** The bytecode generator consumes the AST, emits Ignition bytecode, and V8 releases the temporary parse memory after compilation. From that point on, *the bytecode runs* — the AST is gone. (The next lessons cover bytecode and the interpreter loop.)

So the AST is an **intermediate representation**: a convenient structured form that exists only to be lowered into something the interpreter can execute efficiently. Keeping it around would waste memory. Tree-walking it would be far slower than running flat bytecode.

<Misconception id="mc-ast-runs">
  <p><strong>"The engine executes the AST by walking the tree."</strong> No — the bytecode generator consumes the AST and V8 releases that temporary structure after compilation. Ignition bytecode executes instead.</p>
</Misconception>

## Source size affects startup, but the path matters

Source size affects how much scanning or preparsing V8 may do, but it is not a fixed cost per byte on every visit. Lazy parsing can defer a function's AST and bytecode until it is called; code caching and background compilation can change the critical path. Large literals needed at startup still create real work.

Measure parsing and compilation in a startup trace before attributing a blank page to them. The useful distinction: the AST exists for code being compiled, while the lighter preparsing work covers a function that may never run.

## Failure mode: a giant data literal parsed eagerly

Here is the production trap. A team inlines a large dataset directly into a JS module as an object or array literal — a multi-megabyte "JSON-in-JS":

```js
// data.js — 3 MB of this, inlined into the bundle
export const LOOKUP = { "0001": { name: "...", coords: [] }, /* 50k more */ };
```

Because this is a top-level JavaScript literal, V8 must parse the object expression and generate bytecode before the module finishes evaluating. If the module is needed at startup, that work contributes to its startup cost.

One option is to move the data into a `.json` file and load it when needed:

```js
const LOOKUP = JSON.parse(await fetch("/data.json").then(r => r.text()));
```

`JSON.parse` handles a simpler grammar without building a JavaScript AST. V8 has measured faster parse, compile, and execution for large JSON-like data represented as a JSON string than as an equivalent object literal.

A separate request can also defer the work, but adds network latency; `JSON.parse` itself is synchronous. Measure the complete loading path before choosing where the data belongs.

<Recap lang="en">
For code V8 compiles, the scanner supplies tokens from a UTF-16 view of the source; the parser turns them into an AST; the bytecode generator emits Ignition bytecode. V8 releases the temporary AST, and the interpreter runs the bytecode. A function that is not yet needed can be preparsed and compiled later. Large top-level data literals may add startup work, but lazy parsing, background compilation, and code caching change the cost. Use a performance trace before changing data delivery; compare any JSON.parse gain with the cost and timing of an additional request.
</Recap>
