<Hook>
An object graph is full of references: an object's Map, its object-valued properties, and the elements of an object array. On a 64-bit machine, full addresses take eight bytes each. V8 can store many of those references in four-byte tagged slots because the objects they name share the same high address bits.
</Hook>

<Crux>What must the engine reconstruct before a four-byte slot can identify a heap object?</Crux>

<Explanation>

## First, read the tag

In a common pointer-compressed V8 heap slot, the **lowest bit** distinguishes a small integer (**Smi**, `0`) from a heap reference (`1`). Heap objects are aligned, leaving low address bits available for tags. A second low bit can distinguish strong from weak references. The tag is representation metadata; it is not a JavaScript type code.

A tagged reference is not yet the aligned address of an object. The engine must recover the full pointer and remove the tag to access object fields. A Smi follows a different path: its integer payload lives in the tagged value itself.

## Then, restore the shared high bits

With pointer compression enabled, V8 reserves a **typically 4 GB** cage of virtual address space for compressed objects. A 4 GB aligned cage base supplies the high address bits. Each compressed tagged slot keeps only 32 low bits. Conceptually, a heap reference is reconstructed by adding those stored bits to the cage base; the low tag bit is then removed to get the aligned object address.

<CageAddressFig lang="en" />

The addresses in the figure are illustrative. The stored `0x0000_1001` combines offset `0x1000` and tag bit `1`. Adding the aligned base gives a *tagged* full-width pointer ending in `1001`; clearing the tag reaches the object ending in `1000`. The cage base is shared, rather than repeated in every tagged heap slot. V8 can keep it available in a register, and its compiler can eliminate or combine some decompression work.

This describes **compressed tagged heap storage**, not every pointer in a V8 process. Current V8 also has configurations with shared or separate cages and special handling for trusted objects, code, and external references. Nor does reserving a 4 GB virtual range allocate 4 GB of physical memory.

## What actually gets smaller

V8's 2020 study found that tagged values occupied about **70%** of the V8 heap on its sampled websites. Halving those stored values therefore mattered far more than shrinking a rare structure. In those browsing tests, pointer compression reduced V8 heap size **by up to 43%**. That is a measured upper result for those workloads, not a promise that every Node process or page loses 40% of its heap. Some code also benefits from denser cache lines; decompression still has a cost, which V8 worked to reduce in generated code.

The 32-bit offset limits how far one compressed reference can reach **within its cage**. It does not say that a process can use only 4 GB of memory: backing stores, code, other regions, and possibly other isolates or cages can live elsewhere. Whether isolates share a cage is a build and embedding choice. Treat a runtime's maximum heap size as something to inspect in that runtime, not infer from this diagram alone.

<Recap lang="en">
Pointer tagging and pointer compression answer different questions. The low bit says whether a tagged slot carries a Smi or a heap reference. Compression says how a heap reference can be stored in 32 bits: its cage supplies the shared high address bits, while the slot keeps a tagged offset. A full-width tagged pointer is reconstructed before the tag is removed and the object is accessed. V8 measured substantial savings on pointer-heavy browser workloads, but those measurements and the cage's address range need their context. When a Node service approaches a memory limit, inspect the live V8 configuration and allocation profile before blaming the cage.
</Recap>
