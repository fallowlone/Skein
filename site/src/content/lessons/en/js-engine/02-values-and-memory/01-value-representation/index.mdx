<Hook>
You write `let x = 42`, then assign an object, then `null`. V8 cannot store the whole object inside a local slot. In its common tagged representation, the slot holds a small integer directly or a reference to a heap object. The low bits tell the engine which case it has. Pointer compression adds a second twist: on 64-bit builds, tagged values stored in the heap can occupy four bytes even though a full address is wider.
</Hook>

<Crux>A V8 tagged value can be an inline Smi or a tagged heap reference. The low bit distinguishes them; compressed heap slots store either form in 32 bits.</Crux>

<Explanation>

## One tagged slot, two interpretations

V8 uses **tagged values** wherever a location may hold different JavaScript values. The two main cases are a **Smi** (a small signed integer encoded directly) and a **heap reference** (a tagged pointer to an object). This describes a representation, not a complete list of JavaScript types: strings, objects, and special values can all use the reference path.

The width depends on where the value lives. On a 64-bit build with pointer compression, a tagged field **stored in the V8 heap is 32 bits**, holding either a Smi or an offset into a 4 GB pointer-compression cage. V8 reconstructs a full pointer using the cage base when needed. Values in registers can be wider. Optimized code and specialized storage can also use **untagged** representations, such as raw doubles. So “every JS value is one 64-bit word” is not a reliable memory model.

<TaggedValueFig lang="en" />

## The low bit separates Smi from heap reference

Heap objects are aligned, leaving low address bits available as tags. In the common strong-reference case, a low bit of **0** identifies a Smi; **1** identifies a heap reference. A Smi stores its integer payload inline, without allocating a separate number object. A heap reference needs pointer reconstruction if compressed and then a load from the target object. The second low bit can distinguish strong from weak references inside V8; JavaScript code usually sees strong references.

```text
compressed tagged slot (32 bits, pointer-compressed build)
... integer payload ... 0       → Smi
... offset in cage ... 1         → tagged heap reference
```

This is a decision *when code needs to distinguish representations*. A JIT can often prove a representation and omit the test. It is also not always a single instruction followed by exactly one dereference: pointer reconstruction, bounds, type checks, and cache behavior depend on the operation.

## Following the heap path to a Map

A heap reference may lead to an object, string, function, **HeapNumber**, or special value. A HeapNumber stores a non-Smi numeric value. V8 can also keep some doubles unboxed in optimized code or suitable fields and element stores, avoiding a separate HeapNumber; those are deliberate exceptions to the tagged-slot picture.

A V8 **HeapObject begins with a Map field at offset 0**. Its Map describes the object's instance kind and layout. For a plain JS object, that layout helps the engine locate named properties. A property load can use a known Map as a shape guard and then read a field at a known offset. The tagged pointer, the HeapObject, and its Map are three distinct things.

```text
tagged reference → HeapObject
                    +0  Map field → Map (kind and layout)
                    +…  object-specific fields or data
```

## Special values still use the heap path

`true`, `false`, `null`, and `undefined` are represented by dedicated V8 **Oddball** objects. The internal **hole** is another sentinel used in places such as sparse array storage and uninitialized bindings. A check for an uninitialized binding can turn that sentinel into a `ReferenceError`; merely reading its bits is not itself the exception. These values use heap references in tagged locations even though several are JavaScript primitives.

<Misconception id="mc-typeof-cost">
  <p><strong>“A tag bit directly tells V8 every JavaScript type.”</strong> The low bit distinguishes a Smi from a heap reference. To identify the kind of a referenced object, V8 can inspect its Map or use faster known-object checks. Optimized code may avoid either step when it already knows the representation.</p>
</Misconception>

<Inset kind="why" lang="en">
Why compress tagged heap fields? A full pointer needs eight bytes on a 64-bit machine, but objects in a V8 compression cage can be referenced by 32-bit offsets. Compressing the many tagged fields in the heap saves memory; the engine reconstructs pointers when necessary. This is a storage trade-off, not a claim that all runtime values occupy four bytes.
</Inset>

<Recap lang="en">
V8's tagged representation distinguishes an inline Smi from a heap reference using a low bit. On 64-bit builds with pointer compression, many tagged heap fields occupy four bytes; a compressed reference is an offset within a 4 GB cage, reconstructed with a base when needed. A referenced HeapObject starts with a Map field at offset 0, leading to metadata about its kind and layout. `true`, `false`, `null`, and `undefined` use special heap objects in tagged locations. These rules describe a common storage path, not every value: optimized code and specialized numeric fields or arrays can use untagged forms. The next lessons examine Smi limits, doubles, and pointer tagging in more detail.
</Recap>
