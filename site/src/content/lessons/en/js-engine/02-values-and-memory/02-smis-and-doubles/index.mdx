<Crux>Where does a number live: inside a tagged slot, behind a heap pointer, or as raw double bits?</Crux>

<Explanation>

## One Number type, several storage layouts

At the language level, ordinary JavaScript numbers follow IEEE-754 double semantics. V8 can choose a cheaper internal representation when the value and its **storage location** allow it. In a common 64-bit V8 build with pointer compression, a tagged heap slot occupies **32 bits**. Its lowest bit distinguishes two cases: `0` for a **Smi** (small integer stored in the slot) and `1` for a tagged heap reference. The Smi payload is a **31-bit signed integer**, from −2³⁰ through 2³⁰−1.

This describes *compressed tagged storage*, not every JS value or machine register. Uncompressed builds and optimized code may use other representations. A Smi needs no separate heap object; arithmetic can use specialized integer operations, though an entire JavaScript `+` is not literally one CPU instruction.

<NumericStorageFig lang="en" />

The upper path in the drawing keeps `42` in the tagged slot. A `3.14` cannot fit that integer format. If it must occupy a **tagged** slot, V8 can use a tagged reference to a **HeapNumber** object. The object has a Map field and a 64-bit IEEE-754 payload. The reference and the payload are distinct pieces of storage. It does **not** follow that evaluating a fraction allocates a new HeapNumber on every iteration: optimized code can keep intermediate doubles in machine registers.

## Raw doubles in numeric arrays

The lower strip shows a different placement. V8 can store an array with `PACKED_DOUBLE_ELEMENTS` in a backing store of raw double slots. A `Float64Array` likewise stores 64-bit floating-point elements in its buffer. The array or buffer has its own allocation, but each stored element does not need a separate HeapNumber. When a value leaves that storage for a generic tagged location, boxing may be needed; optimized code can sometimes avoid that boundary.

```js
const readings = [1, 2, 3]; // typically PACKED_SMI_ELEMENTS
readings.push(3.14);        // transition to PACKED_DOUBLE_ELEMENTS
readings.push(4);           // this element now lives in double storage too

const samples = new Float64Array([1, 3.14, 4]);
// Buffer elements are 64-bit doubles; this does not describe
// every temporary value produced while using the array.
```

V8's element-kind transition from packed Smis to packed doubles broadens the backing store. This transition is generally one-way for that array; adding an arbitrary object can broaden it again to `PACKED_ELEMENTS`. It is the **array's element layout** that changes, not the ECMAScript type of `1`.

## What an overflow actually changes

Crossing the compressed Smi range means a value **cannot remain a Smi in that slot**. It does not automatically deoptimize a function, allocate one HeapNumber per arithmetic step, or impose a permanent slowdown. A deoptimization occurs if *optimized code relied on a narrower assumption* and a guard for that assumption fails. The resulting path depends on the compiled code, surrounding storage, and later optimization decisions.

```js
function accumulate(values) {
  let total = 0;
  for (const value of values) total += value;
  return total;
}

accumulate([1, 2, 3]);
accumulate([2 ** 30, 1]); // result is outside compressed Smi range
```

The second call supplies a useful *hypothesis* for an investigation, not a promise that this exact program deopts. Warm-up history and V8 version matter. If this path is hot, measure the real workload, inspect allocation profiles, and use V8's optimization/deoptimization traces to see which assumption actually failed. Avoid changing arithmetic semantics merely to retain a representation: `| 0` truncates to a signed **32-bit** integer, which can still be outside the **31-bit** compressed Smi range; `Math.fround` rounds to float32 and is not a boxing-control switch.

<Inset kind="edgecase" lang="en">
`-0` and `NaN` are not Smis. Adding `-0`, `NaN`, or a fraction to a packed Smi array can move it to double elements. Named object properties are another storage path: current V8 documentation says a `kDouble` property uses a boxed HeapNumber, potentially mutable in place on stores; in-object raw-double unboxing is no longer supported. Do not generalize the array layout to object fields.
</Inset>

<Recap lang="en">
A Smi is an integer carried by a tagged value rather than a separate heap object. In common pointer-compressed V8 heap slots it has a 31-bit signed range, with low tag bit 0. A non-Smi number in a tagged location can be represented through a HeapNumber containing a 64-bit double. Other storage locations tell a different story: packed double arrays and Float64Array buffers store raw double elements, and optimized code may keep temporary doubles unboxed. An array that widens from Smi elements to double elements changes its backing-store layout, not the JavaScript meaning of its values. Crossing the Smi limit is a representation fact; deoptimization and allocation costs are runtime outcomes to measure, not automatic consequences. When profiling a numeric hot path, locate the boundary where an unboxed value must enter tagged storage or where an optimized assumption fails.
</Recap>
