## Snippet 1 — the health check

```yaml
upstream api {
  server 10.0.1.10:8080;
  server 10.0.1.11:8080;
}
# health check
location /healthz { return 200 "ok"; }   # static 200, touches nothing
# node 10.0.1.11's DB pool is exhausted; every real request returns 500
```

## Snippet 2 — the algorithm choice

```nginx
# cache tier: each node holds a hot subset of keys in memory
upstream cache_tier {
  least_conn;                 # balance by fewest active connections
  server cache-1; server cache-2; server cache-3; # ... 12 nodes
}
# observed: hit ratio is terrible (~10%); almost every request misses
```

<Quiz
  id="03-traffic-code-2"
  lessonSlug="quiz-code"
  lang="en"
  question="The cache tier uses least_conn and the hit ratio is ~10%. What's wrong, and what algorithm should it use?"
  choices={[
    { label: "least_conn balances load evenly but ignores the key, so a given key lands on a different node each time and almost always misses. Use consistent hashing (hash on the cache key) so the same key reliably hits the node that cached it.", correct: true },
    { label: "Nothing's wrong; 10% hit ratio is normal for a cache.", misconception: "10% is catastrophic for a hot cache — it means keys aren't sticking to nodes. The cause is balancing by connections instead of by key; consistent hashing fixes the locality." },
    { label: "Add more cache nodes to raise the hit ratio.", misconception: "More nodes make it worse with least_conn — keys scatter even more widely. The problem is the algorithm ignoring the key, not the node count; switch to consistent hashing." },
    { label: "Switch to round-robin for even distribution.", misconception: "Round-robin also ignores the key, so the locality problem stays and the hit ratio stays low. You need key affinity — consistent hashing — not another load-balanced-by-count algorithm." },
  ]}
/>

## Snippet 3 — the gateway deployment

```yaml
# kubernetes deployment for the API gateway (fronts 15 services)
kind: Deployment
metadata: { name: api-gateway }
spec:
  replicas: 1                 # single instance
  strategy: { type: Recreate } # kill old pod, then start new
# all 15 services are reachable only through this gateway
```

    { label: "No risk — one gateway is simpler and Kubernetes restarts it fast.", misconception: "Even a fast restart is a full outage of all 15 services while the single pod is down, and Recreate guarantees a gap on every deploy. A single replica is a textbook SPOF; run multiple behind the LB." },
    { label: "Switch to a StatefulSet.", misconception: "A StatefulSet doesn't address availability here — the gateway is stateless. The fix is multiple replicas with a rolling update, not stable identities/storage." },
    { label: "Increase the pod's CPU and memory limits.", misconception: "More resources help throughput, not availability. One bigger pod is still a single point of failure; you need more than one replica with a rolling deploy." },
  ]}

## Snippet 4 — the cache header

```http
# response for GET /account/orders  (shows the logged-in user's orders)
HTTP/1.1 200 OK
Cache-Control: public, max-age=600
# served through a shared CDN; no Vary header
```

<Quiz
  id="03-traffic-code-4"
  lessonSlug="quiz-code"
  lang="en"
  question="This authenticated, per-user response carries Cache-Control: public on a shared CDN. What's the consequence and the fix?"
  choices={[
    { label: "The shared edge keys on the URL and caches User A's orders, then serves them to User B requesting the same path — a data leak. Fix: Cache-Control: private (browser-only) or no-store, and Vary: Cookie/Authorization so no shared cache stores it.", correct: true },
    { label: "It just makes the page fast; the CDN separates users automatically.", misconception: "A shared cache keys on the URL, not the user. public + no Vary means it can serve one user's orders to another at the same path. Personalized responses must never be public on a shared cache." },
    { label: "Lower max-age to 1 to be safe.", misconception: "A short TTL still serves the cached copy to whoever hits that URL in the window — including a different user. The problem is public on a shared cache, not the freshness window; use private/no-store." },
    { label: "It's fine because orders rarely change.", misconception: "Change frequency is irrelevant; the issue is that the response is per-user. Even unchanging data leaks if User B gets User A's cached orders. Mark it private/no-store and Vary on auth." },
  ]}
/>

</Explanation>

<Recap lang="en">
Every traffic decision in this unit reduces to a setting you can read straight off the config. A **health check** that returns a static 200 (or just opens a socket) lies — it never touches the dependency chain, so a 500-returning node stays in rotation; make it probe the real DB/cache and add passive ejection. An **algorithm** must match the goal: least-connections/round-robin balance by count and destroy a cache tier's hit ratio, where **consistent hashing** on the key preserves locality. A **gateway** at `replicas: 1` is a textbook **single point of failure** with downtime on every deploy — run multiple replicas behind the balancer with a rolling update. And a per-user response with `Cache-Control: public` on a shared CDN is a **data leak** waiting to happen — use `private`/`no-store` and `Vary`. The senior habit is to find the setting, reason about how it behaves under load and failure, and choose the fix the behavior supports — not the one that papers over it.
</Recap>
