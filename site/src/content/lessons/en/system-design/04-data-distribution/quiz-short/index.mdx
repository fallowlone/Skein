    { q: "Contrast synchronous and asynchronous replication, and explain how a failover loses acknowledged writes.", a: "Synchronous: the leader waits for a follower to confirm before acking the client, so an acknowledged write is durable on ≥2 nodes — but a slow/down follower blocks the write (write availability tied to the slowest replica). Asynchronous: the leader acks immediately and ships in the background, so it's fast and available but followers lag and an ack may exist only on the leader. Failover loss: if the leader acks writes it hasn't shipped, then crashes, the promoted follower is behind and those acknowledged writes vanish — an ack under async replication is NOT a durable write. Defenses: a synchronous replica (ack = on two nodes), and fencing/quorum promotion against split-brain." },
    { q: "What is read-your-writes, and how do you preserve it under replication lag?", a: "Read-your-writes (read-after-write): a user who just wrote should see their own write on the next read. Lag breaks it when the read lands on an async follower that hasn't applied the write, so the change appears to vanish. Fixes are routing, not speed: read the user's own recent data from the leader for a short window, route to a follower known to have caught up to the write's log position (a version token), or pin the user to one replica. It's a per-client freshness guarantee, weaker than global linearizability." },
    { q: "Why does an even key count still create a hot shard, and how do you mitigate it?", a: "Because even partitioning by key COUNT is not even by LOAD: one celebrity key (user/product/video) can get orders of magnitude more traffic than average and saturate its single shard while others idle — skew. Hashing doesn't help because all of one hot key's traffic still routes to the one shard owning it. Mitigations spread the hot key: split it with a random suffix and fan reads back in, cache it in front of the shard, or isolate it on a dedicated shard (trivial with directory partitioning). The reflex: uniform key distribution ≠ uniform load." },
    { q: "Why does hash(key) mod N doom a reshard, and how does a hash ring fix it (with virtual nodes)?", a: "Mod-N bakes N into routing, so changing the node count remaps nearly every key at once — a near-total data move for a sharded DB, and an instant cache wipeout where every lookup misses. Consistent hashing hashes nodes and keys onto a ring and routes a key to the next node clockwise; each node owns a contiguous arc, so adding/removing a node touches only one arc — ~1/N of keys move. Virtual nodes place each physical node at many ring points (~150), which balances load via many small arcs and spreads a dead node's load across many successors instead of crushing one neighbour." },
    { q: "State the quorum inequality and contrast CAP with PACELC.", a: "Quorum: with N replicas, if R + W > N the read and write sets overlap in at least one node, so a read sees the latest acknowledged write (e.g. N = 5, W = 3, R = 3). CAP: during a network partition you must choose Consistency (linearizability) or Availability — P is mandatory, so 'pick two' is wrong, and the choice is often per-operation. PACELC extends it: if Partition → A vs C (CAP); Else → Latency vs Consistency — because even with a healthy network a strong read must coordinate (leader or quorum), costing latency. The else-branch dominates in practice since every read pays it, while partitions are rare. Pick per use case along the linearizable→eventual spectrum." },

<Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: **replication** copies data for reads and survival, but async replication acks before durability so a **failover** loses acknowledged writes (keep a synchronous replica; route a user's own reads to a current node for read-your-writes). **Sharding** by a partition key still produces a **hot shard** under skew, because even key counts aren't even load — split, cache, or isolate the celebrity key. **Consistent hashing** rings nodes and keys so adding one moves only ~1/N (virtual nodes balance the arcs and spread failure), where `mod N` would remap nearly all and wipe a cache. **Quorums** guarantee a fresh read when **R + W > N**. And **CAP** is only the partition-time C-vs-A choice while **PACELC** adds the everyday latency-vs-consistency trade — so you pick per use case across the **linearizable→eventual** spectrum. The thread tying them together: at this depth, distribution is a deliberate choice of which inconsistency is acceptable for each piece of data, not a behavior you discover in production.
</Recap>
