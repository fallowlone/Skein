    { q: "Why does fetching 100 rows in one query beat 100 single-row queries, even when each query is fast?", a: "Every round-trip carries a fixed cost independent of how fast the query executes: network RTT (1–5 ms intra-DC, 10–50 ms cross-region), query parse, planner overhead, and result encoding. One query of 100 rows pays that fixed cost once; 100 queries pay it 100 times. So a list page firing 51 queries at 0.4 ms execution each can still take ~765 ms wall-clock, because the dominant term is round-trip latency × trip count, not server-side execution. The optimisation lever is reducing the number of trips, not making each trip faster. This is also why a CPU profile looks flat — the time is spent off-CPU waiting on the socket between trips." },
    { q: "Name the four N+1 fix families and the data shape each one fits.", a: "(1) JOIN — fetch parent and child in one SQL query; one round-trip; best for one-to-one or small one-to-many, because for heavy one-to-many it duplicates parent columns on every child row. (2) IN-based batching (selectinload / prefetch) — two queries, no duplication; best for one-to-many heavy fan-out. (3) ORM preload (.includes / select_related / include) — declares the relationship at the query site and lets the ORM pick JOIN or IN; best when you know the shape at one construction point. (4) DataLoader — request-scoped batching that queues IDs across many code paths and fires one query per type per event-loop tick; best for GraphQL resolvers and multi-source fan-out where there is no single query site. Cardinality and where the lookups originate drive the choice." },
    { q: "Explain how DataLoader works and why ORM eager loading cannot replace it for GraphQL.", a: "A DataLoader is created once per request. Calling loader.load(id) returns a Promise and queues the id internally without firing a query. When the current synchronous work finishes and the event loop ticks, the loader fires one batched query — SELECT ... WHERE id IN (all queued ids) — and distributes results to each waiting Promise, positionally matched to the input ids. It also caches per request so repeat loads of the same id cost nothing. ORM eager loading declares relationships at a single query construction site; in GraphQL there is no such site — each of N author resolvers runs independently with no shared place to attach .includes. DataLoader moves batching from query scope to request scope, which is what GraphQL's scattered resolver tree requires. It needs an async/event-loop runtime and adds a sub-millisecond batch-window latency and request-scope cache complexity." },
    { q: "Why do CPU profiles miss N+1, and what three instruments surface it?", a: "A CPU profiler samples stacks of running threads. N+1 burns no CPU in any one function: each query dispatches in microseconds, then the program waits off-CPU on the database socket, then the next dispatches. The profiler sees fast blips and nothing wide. Three instruments surface it: (1) the database query log (Postgres log_min_duration_statement=0, MySQL slow log, ORM logging) — signature is dozens of similar SELECTs differing only in WHERE id = ?; (2) APM waterfall traces (Datadog, Tempo, Honeycomb) — a tall column of short DB spans within one request; (3) a per-request query counter exposed as a histogram by endpoint, alerting when p99 exceeds ~20. The most leveraged prevention is a CI gate — Rails bullet or Django assertNumQueries — that fails PRs introducing lazy-load regressions before they ship." },
    { q: "How does N+1 cascade into connection-pool exhaustion, and what signals reveal it?", a: "An N+1 endpoint holds one database connection across its whole sequence of serial queries. With a pool of 25 and 50 queries per request at ~2 ms each, each request pins a connection for ~100 ms, so pool throughput caps near pool_size / hold_time ≈ 250 req/s. Beyond that, requests queue for a connection; wait time inflates latency; tails spiral; 503s appear and health checks may pull pods from rotation, concentrating load on the survivors. The tell is: pool saturation (active/max) near 100% sustained, connection wait time rising (pgbouncer cl_waiting), per-endpoint query count high, yet individual query latency stable and the DB healthy. The fix is the N+1 fix: cut hold-time from ~100 ms to ~4 ms and the same pool sustains roughly 10× the traffic." },
    { q: "When is denormalisation (counter cache, materialised view, CQRS read model) the right answer for N+1, and when is it premature?", a: "It is right only when measurement shows even 2–3 well-batched queries cannot meet an extreme latency SLO — read p99 below ~50 ms on heavy joins AND read load roughly 1000× the write load. Counter caches fit scalar aggregations (counts, sums); materialised views fit complex joins/aggregations read far more than written; CQRS read models fit cases where read and write shapes differ sharply. Each adds write-side complexity, staleness (ms to seconds), storage duplication, and ongoing maintenance as the schema evolves. It is premature when the SLO is 100+ ms (eager loading meets it), when read and write loads are comparable, or when nobody has yet confirmed by measurement that eager loading is the bottleneck. The common mistake is reaching for CQRS at a 10× read/write ratio when one .includes directive would have solved it in 30 minutes." },
