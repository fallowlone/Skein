## Snippet 1 — the growing slice

```go
func collect(rows []Row) []byte {
    var out []byte                  // nil slice, zero capacity
    for _, r := range rows {
        line := fmt.Sprintf("%d,%s\n", r.ID, r.Name)
        out = append(out, line...)  // repeatedly grows + copies
    }
    return out
}
```

    { label: "The garbage is the input `rows`; copy it less.", misconception: "`rows` is passed in, not allocated here. The garbage is created inside the loop — Sprintf strings and the repeatedly-grown `out` backing array." },
    { label: "Nothing significant — append reuses the same array.", misconception: "append reuses capacity only while it lasts; a zero-cap slice reallocates (typically doubling) many times over 100k rows, copying everything each time." },
    { label: "Raise GOGC so the loop allocates less.", misconception: "GOGC changes when GC runs, not how much the loop allocates. The fix is to allocate less: pre-size the buffer and drop Sprintf." },

## Snippet 2 — the pool

```go
var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}

func render(w io.Writer, v *View) error {
    b := bufPool.Get().(*bytes.Buffer)
    defer bufPool.Put(b)
    // ... write a lot into b ...
    _, err := w.Write(b.Bytes())
    return err
}
```

<Quiz
  id="04-gc-code-2"
  lessonSlug="04-gc"
  lang="en"
  question="This pooled-buffer code has a correctness bug that a load test will eventually expose. What is it?"
  choices={[
    { label: "The buffer is returned to the pool without b.Reset(). The next Get() yields a buffer still holding the previous render's bytes, so output gets corrupted with stale data under reuse.", correct: true },
    { label: "sync.Pool is not safe for concurrent use.", misconception: "sync.Pool is explicitly safe for concurrent Get/Put across goroutines. The bug is hygiene — the buffer is not Reset before reuse." },
    { label: "defer bufPool.Put runs too early.", misconception: "defer runs at function return, after w.Write completes — the ordering is fine. The missing Reset is the defect." },
    { label: "new(bytes.Buffer) leaks memory.", misconception: "The New func only runs when the pool is empty, and the GC can drain sync.Pool between cycles. No leak — the issue is stale state on reuse." },
  ]}
/>

## Snippet 4 — escape analysis

```go
func newPoint(x, y int) *Point {   // returns a pointer...
    p := Point{x, y}
    return &p                      // ...so p escapes to the heap
}

func sumLocal(x, y int) int {
    p := Point{x, y}               // never escapes
    return p.X + p.Y               // stays on the stack
}
```

<Quiz
  id="04-gc-code-4"
  lessonSlug="04-gc"
  lang="en"
  question="Which call allocates on the heap (adding GC work), and what is the general rule?"
  choices={[
    { label: "newPoint heap-allocates because its result (&p) escapes the function; sumLocal stays on the stack. Rule: a value escapes when a reference to it outlives the frame — returning its address, storing it in a heap object, or passing it to something that retains it.", correct: true },
    { label: "Both allocate because both create a Point.", misconception: "Stack-allocated values cost no GC work. sumLocal's Point never escapes, so escape analysis keeps it on the stack." },
    { label: "sumLocal allocates because it does arithmetic.", misconception: "Arithmetic on stack values allocates nothing. It is escape (a reference outliving the frame), not computation, that forces heap allocation." },
    { label: "Neither allocates — Go always uses the stack.", misconception: "Go uses the stack only when escape analysis proves the value does not escape. Returning &p forces newPoint's Point onto the heap." },
  ]}
/>

<Recap lang="en">
Every GC incident is read in code and traces: zero-capacity slices and per-iteration Sprintf are classic allocation hotspots; pooled objects must be Reset before reuse; a gctrace line tells you GC CPU share and mark time at a glance; and escape analysis decides stack vs heap based on whether a reference outlives its frame. Diagnose from the profile, fix the allocation, then re-profile to confirm.
</Recap>
