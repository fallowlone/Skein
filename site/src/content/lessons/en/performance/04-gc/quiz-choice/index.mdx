  lang="en"
  question="Why does a concurrent collector need a write barrier, and what breaks without one?"
  choices={[
    { label: "It maintains the tri-color invariant: a black (scanned) object must not hold the only reference to a white (unscanned) object. Without the barrier the collector can finish marking and reclaim a live object — silent heap corruption.", correct: true },
    { label: "It speeds up marking by parallelising the scan.", misconception: "The barrier adds per-write overhead (2–10% CPU); it does not parallelise marking. Its job is correctness during concurrent mutation, not speed." },
    { label: "It compacts the heap to remove fragmentation.", misconception: "Compaction is a separate phase. The write barrier is about not losing live objects when the mutator rewires references mid-mark." },
    { label: "It is only needed for generational collectors.", misconception: "Any concurrent collector needs it, generational or not — Go is non-generational and still uses a write barrier." },
  ]}
/>

  choices={[

    { label: "Normal warm-up — GC% always rises as caches fill.", misconception: "A healthy service holds GC CPU under ~5%. A monotonic climb to 39% with growing mark time is pathological, not warm-up." },
    { label: "Raise GOGC to 400 to stop the cycles.", misconception: "Deferring GC trades memory for fewer cycles and can push you into OOM during a spiral; it masks the cause. Reduce allocations first, then consider tuning." },

<Recap lang="en">
Across the unit the through-line is one decision tree: allocation rate sets GC frequency, the live set sets cycle cost, the collector sets pause shape, and the knobs (GOMEMLIMIT first, GOGC/pause-target second, algorithm last) defend the bounds. Production failures — OOM under spikes, ZGC tradeoffs, finalizer storms, death-spirals, allocation DoS — all resolve back to the same lever: reduce allocations before you tune anything.
</Recap>
