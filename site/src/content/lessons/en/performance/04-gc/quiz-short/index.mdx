    { q: "Why does allocation rate drive GC-driven tail latency more than total heap size?", a: "Heap size is how much memory the program holds at any moment; allocation rate is how fast new memory is requested. A tracing GC runs a cycle each time enough garbage accumulates — which is governed by allocation rate, not absolute heap size. A 4 GB cache allocating 50 MB/s may cycle once a minute with tiny pauses; a 100 MB service allocating 1 GB/s churns GC constantly, pausing every fraction of a second. So the lever for tail latency is the allocation profile; heap size is the lever for footprint. Every byte you do not allocate is GC work that never has to happen." },
    { q: "State the generational hypothesis and give one counterexample collector.", a: "The generational hypothesis is the empirical observation that most objects die young — request handlers allocate many short-lived temporaries and few long-lived objects. Generational collectors exploit this by splitting the heap into a small, frequently-collected young generation and a large, rarely-collected old generation; survivors are promoted. If 95% of objects die young, one cheap young-gen pass reclaims 95% of bytes. Counterexample: Go's collector is non-generational — a single heap with concurrent tri-color marking. The Go team bet that escape analysis and runtime simplicity reduced heap pressure enough to skip generational complexity, and achieves sub-ms pauses on most workloads. JVM, V8, and .NET are all generational." },
    { q: "What is the difference between RSS and the live set, and why does it matter for tuning?", a: "RSS (resident set size) is total physical memory the process holds — including garbage awaiting the next cycle, heap fragmentation, and runtime-reserved arenas. The live set is only the bytes actually reachable after a GC cycle. Marking time scales with the live set; cycle frequency scales with allocation rate; RSS is neither. The canonical tuning target is to size the heap to ~1.5–2× the live set: below 1.5× the collector runs almost continuously and throughput collapses; above ~3× memory is wasted and each cycle can take longer. You read the live set post-GC — HeapLive in Go, old-gen used after a full GC in the JVM — not RSS." },
    { q: "Explain the tri-color invariant and what the write barrier does to preserve it.", a: "Tri-color marking labels objects white (unvisited), grey (visited, children pending), or black (fully scanned). The invariant: a black object must never hold the only reference to a white object. During concurrent marking the mutator can rewire references; if it stores a white-object reference into an already-scanned black object, the white object becomes invisible to the collector and would be wrongly reclaimed — silent corruption. The write barrier intercepts every reference write to prevent this. SATB marks the old (overwritten) reference (Go, G1, ZGC, Shenandoah); incremental-update marks the new reference (CMS, classic V8). The cost is ~2–10% CPU on reference writes — the price of avoiding stop-the-world marking." },
    { q: "What does GOMEMLIMIT do, and why is it the first knob for a containerised Go service?", a: "GOMEMLIMIT (Go 1.19+) is a soft cap on total runtime memory that integrates into the pacer's control loop. As the process approaches the limit, the pacer pulls GC cycles forward — accepting higher GC CPU — to keep RSS under the cap; when usage is well below the limit it backs off and uses the normal GOGC-derived goal. It is the first knob for containers because the default pacer does not know about the cgroup limit, so under a traffic spike the heap can grow past the container's memory and the pod gets OOM-killed. Setting GOMEMLIMIT to ~90% of the container limit defends the bound with no code change; you only reach for GOGC after that." },

(3) Let escape analysis stack-allocate — keep values scope-local so no reference escapes the frame. (4) Shrink the allocation — smaller struct, pre-sized container, smaller buffer. (5) Move it off the hot path — compute once and cache. (6) Tune the collector — GOMEMLIMIT/GOGC, MaxGCPauseMillis, max-old-space-size. (7) Switch the collector algorithm — ParallelGC → G1 → ZGC.
