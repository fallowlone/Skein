## Snippet 1 — the per-row build

```go
func renderCSV(rows []Row) string {
    out := ""                                 // empty string
    for _, r := range rows {
        out += fmt.Sprintf("%d,%s\n", r.ID, r.Name)  // Sprintf + concat each row
    }
    return out
}
```

## Snippet 2 — the shared counter line

```go
type Stats struct {
    hits   uint64
    misses uint64   // adjacent field — same 64-byte cache line as hits
}
var s Stats

// goroutine A, hot loop:   atomic.AddUint64(&s.hits, 1)
// goroutine B, hot loop:   atomic.AddUint64(&s.misses, 1)
```

<Quiz

  choices={[
    { label: "False sharing: hits and misses sit on the same 64-byte line, so each core's atomic write invalidates the other's cached copy via MESI — the writes serialise as if locked. Fix: separate the two counters onto distinct cache lines with padding (or per-CPU sharded counters summed on read).", correct: true },
    { label: "True lock contention on the atomics — switch to a sync.Mutex.", misconception: "There is no lock here and a mutex would be slower. The IPC collapse + high miss rate + worsening-with-cores signature is cache-line bouncing, not scheduler blocking." },
    { label: "The struct is too big for cache — shrink the fields.", misconception: "Two uint64 is 16 bytes; size is not the issue. The issue is two independently-written fields sharing one coherency unit (the 64-byte line)." },
    { label: "Allocation-bound — pool the Stats struct.", misconception: "Stats is a single global; nothing is being allocated in the hot loop. The cost is coherency traffic on writes, not GC." },
  ]}

## Snippet 3 — the perf stat block

```
# perf stat -e cycles,instructions,cache-misses,LLC-load-misses ./svc --bench score
   8,400,000,000  cycles
   3,360,000,000  instructions     #  0.40 insns per cycle (IPC)
     900,000,000  cache-misses     # 10.7% of all memory refs
     700,000,000  LLC-load-misses  # 78% of cache misses also miss L3 → DRAM
# hot leaf from flame graph: score_embeddings()  — 42% self-time
```

## Snippet 4 — the native bridge

```js
// Node service, called ~10,000 times/second
function hashAll(items) {
  return items.map(item => nativeHmac(item))  // one N-API crossing per item
}
// nativeHmac (Rust): ~40 ns of actual work
// N-API stub overhead: ~160 ns per crossing
// CPU profile: 40% in napi_call_function, 8% in the Rust HMAC
```

<Quiz
  id="02-hot-paths-code-4"

  question="The native HMAC is fast (40 ns) but the N-API stub (160 ns) dominates the CPU profile. What is the diagnosis and the right fix?"
  choices={[
    { label: "Native-bridge overhead: the fixed per-crossing cost dwarfs the cheap native call, so the stub is wider than the function it calls. Fix: batch — pass the whole slice in one crossing and loop inside Rust, amortising 160 ns over N items (e.g. /64 ≈ 2.5 ns each).", correct: true },
    { label: "Rewrite the HMAC in JavaScript to remove the bridge entirely.", misconception: "The Rust routine exists for speed/safety; rewriting it in JS removes that value and is usually slower. The diagnosis is crossing overhead, fixed by batching, not by deleting the native code." },
    { label: "Use worker threads to parallelise the N-API calls.", misconception: "Concurrency raises aggregate throughput but each call still pays the full 160 ns crossing. Per-item overhead is unchanged; only batching reduces crossings per unit of work." },
    { label: "It is CPU-bound in the crypto — optimise the HMAC.", misconception: "The crypto is only 8% of CPU; the stub is 40%. Optimising a function that is already cheap relative to the bridge is the wrong target." },
  ]}

<Recap lang="en">
Every shape is read from the evidence in front of you, not the flame-graph width alone: wide GC frames + per-iteration Sprintf/concat is allocation-bound (build into a pre-sized buffer); IPC ~0.4 with high miss rate plus worsening-with-cores on adjacent atomic fields is false sharing (pad to separate cache lines); IPC 0.4 with DRAM-dominated misses is memory-bound (data layout, AoS→SoA); and a bridge stub wider than its cheap native callee is FFI overhead (batch per crossing). Classify first, fix the matching cause, then re-profile to confirm.
</Recap>
