## Slow has one main cause, and it hides

When something is slow, the time is almost never spread evenly. Usually one step — one query, one loop, one network call — is responsible for most of the wait. That step is the **bottleneck**. Fixing anything else barely moves the total, because the slow part still dominates.

The trap is that your intuition about *where* the bottleneck lives is frequently wrong. The code that looks ugly is often fast. The innocent-looking line is often the one eating all the time. You cannot tell by reading — you have to measure.

## Measure first, change second

To **measure** means to run the program and record where the time actually goes, using a tool called a **profiler**. A profiler watches your code run and reports which parts took the longest. Only then do you know the real bottleneck — and only then is it worth changing anything.

## The loop that protects you from guessing

Real performance work is a small loop you repeat: measure to find the bottleneck, change only that one thing, then measure again to confirm it actually got faster. The final measurement matters as much as the first — a change that *feels* faster sometimes isn't, and only the numbers can tell you. This loop is the single mental model to carry up through the whole climb.

<Recap lang="en">
Performance work is not about rewriting whatever code looks ugly. Slow time almost always hides in a single bottleneck, and your intuition about where it is tends to be wrong. So you measure first with a profiler, change only the bottleneck, and measure again to confirm the win. That measure&rarr;change&rarr;measure loop is the mental model the rest of this track builds on: profiling, hot paths, caches, and more.
</Recap>
