    { q: "Why does batching help, what is the cost model, and where does it NOT pay off?", a: "Every operation has a fixed cost F (paid per call regardless of payload: a syscall transition, a network round-trip plus ACK, a transaction commit, an fsync) and a variable cost V per item (the data itself). Doing N items separately costs N·(F + V); batching pays F once: F + N·V. Batching turns the dominant repeated fixed cost into a single amortized one — which is why a slow ingest can look completely idle (idle CPU, disk, network) yet be slow: the bottleneck is latency, threads parked waiting for round-trips, not utilization a flame graph can see. It pays off when (1) fixed cost dominates variable cost, (2) the rate is high enough to create queue depth to amortize across, and (3) there is latency slack to spend. It does NOT pay off for rare operations (no queue depth — a batch of one is slower than no batch), a hard sub-millisecond SLO (any wait blows it), causally dependent operations (N+1 needs N's acknowledged result), or a failure model that cannot tolerate partial-batch loss or batch-granular rollback." },
    { q: "Derive the speedup formula and explain where it goes to N versus 1.", a: "Model a per-item op as fixed cost F plus variable cost V·n (work proportional to payload size n). N items separately cost N·(F + V·n); batched they cost F + V·(N·n), paying F once. Speedup is (N·F + N·V·n) / (F + V·N·n). When fixed cost dominates — F > V·n, typical of small payloads — the N·F term dominates and speedup → N (batch 100, go ~100×). When variable cost dominates — F < V·n, large payloads — the V·N·n term dominates and speedup → 1: there's no fixed cost left to amortize, batching only adds latency. Break-even is per item at F = V·n. Concretely: 1 KB packets, 50 µs RTT fixed cost, 100-item batch — 100 round-trips at 50 µs = 5 ms collapse to one round-trip plus the bytes (~150 µs), about a 33× win. This is why batching tiny messages (logs, metrics, key lookups) is huge while batching large blobs (video chunks, big uploads) is pointless." },
    { q: "Why does a batching window need both a max-size and a max-wait, and what does which-trigger-fires diagnose?", a: "They cover opposite failure modes and the batch flushes when EITHER fires (an OR, not an AND). Size-only: a slow or quiet producer never fills the buffer, so the batch never flushes and its oldest item waits unboundedly — a head-of-line stall whose latency scales inversely with load. Time-only: a fast producer floods the buffer inside the window and builds a batch too big for downstream — larger than the broker's max message size, or enough to OOM the consumer or blow a transaction. Size protects throughput, time protects latency; you need both. Which trigger fires also diagnoses the regime: at high load the buffer hits max-size before the timer (size dominant, throughput-bound); at low load the timer fires first (time dominant, latency-bound). The honest tune is to derive max-wait from the latency SLO, size the buffer to fill near that timer at peak load, then validate by replaying real bursty production traffic in staging." },

Per-row INSERT with autocommit pays parse, plan, execute, and a WAL-flushing commit on every row — ~1–5k rows/s. Multi-row INSERT ... VALUES amortizes parse/plan/commit across the rows in one statement — ~5–50k rows/s, but capped by parameter and statement-size limits so you chunk it. COPY streams over a dedicated wire protocol that bypasses the per-row SQL parser and planner entirely and commits once — ~50–500k rows/s. The senior move is recognizing which rung a code path is silently on: an ORM loop calling save() per object is per-row INSERT wearing a nicer API. Compression needs batching because codecs (lz4, zstd) find repetition only within their input window: a single small message has almost no internal repetition and barely compresses, but a 128 KB batch of similar records shares field names and structure and compresses 2–4×. Kafka runs the codec per batch, so compression.type does almost nothing with linger.ms=0 and a lot with fat batches — batch first, compress second." },
