<Explanation>
<strong>The backpressure problem</strong>
When a batching producer buffers operations faster than the consumer can process them, the in-memory buffer grows without bound. Two failure modes emerge:
1. **Out-of-memory (OOM)**: buffer consumes all available RAM → process crashes
2. **Latency explosion**: items wait increasingly longer in buffer → tail latency violates SLOs

Real-world incidents:
- Lyft 2019: Kinesis consumer with unbounded batch size → OOM during peak traffic
- Stripe 2020: Postgres COPY batch with one invalid row → entire 50k-row batch rolls back
- Pinterest 2018: Kafka producer with linger.ms=100 → p99 SLO violation during low-traffic periods (1 item/sec waits 100ms for timer)

<strong>Three production-grade bounded queue patterns</strong>
1. **Block when full**: producer stops accepting new work until buffer has space
   - Apply back-pressure upstream via flow control
   - Used by: Reactive Streams, Akka Streams, RxJava
   - Best for: interactive paths where latency spikes are worse than temporary unavailability
2. **Drop when full**: producer discards new work, increments drop counter
   - Lost work is preferable to crashing or latency spikes
   - Used by: metrics agents, telemetry systems, UDP-based ingestion
   - Best for: fire-and-forget workloads where occasional loss is acceptable
3. **Spill to disk when full**: producer flushes oldest items to persistent queue
   - Durability over latency; spill carries performance cost
   - Used by: Fluentd, Vector, Filebeat for log shipping
   - Best for: audit/logging paths where loss is unacceptable

<strong>Observability is non-negotiable</strong>
Without metrics, you're flying blind. Essential batching observability:
- Batch size histogram (are you size-limited or time-limited?)
- Batch wait time (p50, p99, max — are items waiting too long?)
- Buffer depth gauge (current occupancy — spikes = backpressure)
- Drop count (should be 0; >0 indicates backpressure)

Dashboard: time series + alerts on drop count > 0 and buffer depth > 80% capacity.

<strong>Adaptive batching for variable load</strong>
Static windows fail under diurnal variation (e.g., 10x traffic day vs night). Adaptive algorithm:
- Monitor: fill rate (batches/sec × records/batch) and downstream latency
- If downstream latency low AND fill rate high → increase window (more throughput)
- If downstream latency rising → decrease window (back off before saturation)
- If fill rate low → keep window small (low latency for sparse traffic)
- Hard caps prevent oscillation and snowball effects

<PersonaTag id="bea" lang="en"/> uses unbounded batching buffer; experiences OOM or latency spikes under load variation. <PersonaTag id="sven" lang="en"/> uses bounded buffer with drop pattern + observability; graceful degradation under backpressure.
</Explanation>

<Recap lang="en">
Unbounded batching leads to OOM or latency spikes. Production systems use three bounded queue patterns: block (apply back-pressure), drop (prefer loss over blocking), or spill to disk (durability over latency). Essential observability includes batch size histogram, wait time, buffer depth, and drop count to tune windows and detect backpressure early.
</Recap>
