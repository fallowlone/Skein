<Explanation>
Every operation has a fixed cost (network round-trip, syscall, ACK) and variable cost (payload size). When fixed cost dominates, batching amortizes it across N operations. The two-dimensional window (max-size + max-wait) decides when to send the batch.

<strong>Kafka producer batching</strong>
The Kafka producer accumulates messages per (topic, partition). A batch is sent when either:
  • batch.size limit is reached (default 16 KB), or
  • linger.ms timer expires (default 0 ms — disabled).
For throughput, tune linger.ms (5-100 ms) and increase batch.size (64-512 KB). Compression.type (lz4/snappy) applies per batch — bigger batches compress better, reducing network and disk cost. Example: 128 KB batch with lz4 often compresses 2-4x, cutting bytes on wire and broker fsync cost.

<strong>Postgres bulk inserts</strong>
Postgres INSERT VALUES (..., (...), ...) parses and plans once, then commits once — far faster than per-row INSERT. COPY is fastest: streams data in a custom protocol, bypassing per-row parser and using a single commit. Benchmarks:
  • Single-row INSERT: ~1-5k rows/sec
  • INSERT VALUES (1000 rows): ~5-50k rows/sec
  • COPY: ~50-500k rows/sec
Use COPY for bulk loads; INSERT VALUES for moderate batches; avoid per-row INSERT in hot paths. ORMs expose this: Django bulk_create, SQLAlchemy executemany.

<strong>Why compression helps in Kafka</strong>
Compression reduces the payload size (variable cost), making the fixed cost proportionally larger and batching more effective. For repetitive data (logs, events), lz4/snappy achieve 2-4x compression on 64-128 KB batches. CPU cost is low (~50-100 MB/s/core) compared to network/disk savings. Without batching, small messages compress poorly; batching first enables effective compression.
</Explanation>

<Recap lang="en">
Kafka producer batches messages by size (batch.size) or time (linger.ms); whichever triggers first sends the batch. Postgres COPY outperforms INSERT by avoiding per-row parse/plan overhead and committing once. Compression (lz4/snappy) applied per batch improves gains — bigger batches compress better. Both technologies amortize fixed costs: Kafka reduces network round-trips, Postgres reduces SQL overhead. Tune batch.size and linger.ms to hit latency SLOs while maximizing throughput; for Postgres, use COPY for bulk ingest, INSERT VALUES for moderate batches.
