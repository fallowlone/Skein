<Explanation>
<strong>Kafka producer batching</strong>
The Kafka producer accumulates messages per (topic, partition) in memory. When either:
- batch.size bytes of messages accumulate (default 16KB), OR
- linger.ms milliseconds pass since the last batch (default 0, disabled)
...the producer sends one ProduceRequest containing all batched messages.

<strong>Why this helps</strong>
Without batching (linger.ms=0): each message incurs a network round-trip (TCP handshake, TLS, request/response). At 50k msg/sec, that's 50k round-trips/sec — CPU bound on syscalls.
With batching (linger.ms=10ms, batch.size=64KB): the producer waits up to 10ms or 64KB, then sends one request. Round-trips drop to 100-1000/sec — 50-500x reduction.

<strong>Postgres COPY vs INSERT</strong>
Postgres offers three ways to insert multiple rows:
1. Single INSERT: INSERT INTO tbl VALUES (1, 'a'); — one parse, one plan, one commit per row
2. Multi-row INSERT: INSERT INTO tbl VALUES (1,'a'), (2,'b'), ...; — one parse, one plan, one commit for N rows
3. COPY: COPY tbl FROM STDIN; — custom protocol, bypasses parser/plan per row, one commit for N rows

<strong>Performance comparison</strong>
For 1M rows of ~100 bytes each:
- Single INSERT: ~1,000-5,000 rows/sec (limited by parse+plan+commit overhead)
- Multi-row INSERT: ~5,000-50,000 rows/sec (better amortisation)
- COPY: ~50,000-500,000 rows/sec (best amortisation, minimal per-row overhead)

<strong>The pattern</strong>
Both Kafka and Postgres show the same batching principle:
- Fixed cost per operation: network round-trip (Kafka), parse/plan/commit (Postgres)
- Variable cost per byte: network transmission, disk write
- When fixed cost dominates (small messages/rows), batching gives Nx speedup
- Senior question: what window size (batch.size + linger.ms, or COPY batch size) maximises throughput without breaking SLO tail latency?

<PersonaTag id="bea" lang="en"/> uses Kafka producer with default settings (linger.ms=0): low throughput, high CPU. <PersonaTag id="sven" lang="en"/> uses linger.ms=10, batch.size=64KB: high throughput, reasonable latency. For Postgres, Bea uses single-row INSERT; Sven uses COPY or batched multi-row INSERT.
</Explanation>

<KeyTakeaway>Kafka linger.ms + batch.size and Postgres COPY both amortise fixed cost across many operations. Tune window to SLO ceiling, not max throughput.</KeyTakeaway>
