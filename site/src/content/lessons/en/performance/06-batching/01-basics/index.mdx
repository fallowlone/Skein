<Hook>
Imagine sending 10,000 thank-you notes one by one, walking to the mailbox each time. Now imagine bundling them into 100 envelopes and making just 100 trips. Same notes, far less effort. Batching works the same way for computations.
</Hook>

<Crux>Per-op fixed cost dominates? Batch. Window = batch size and max wait; bigger batches buy throughput, charge tail-latency.</Crux>

<Explanation>
Every operation has a fixed cost (header, ACK, syscall transition, log flush, planner overhead) and a variable cost (payload size). When the fixed cost dominates and the operation rate is high, the per-op throughput floor is the fixed cost. Batching collapses N operations' fixed cost into one operation's fixed cost. Production systems use this everywhere: TCP Nagle's algorithm, Kafka linger.ms, Postgres COPY, Redis pipelining, io_uring submission queues, syslog buffering. The senior question is never "batch or not" but "what window size maximises throughput without breaking the SLO tail latency?".

<PersonaTag id="bea" lang="en" /> ships a Kafka producer flushing each message individually; throughput tops at 8k msg/sec, CPU high. <PersonaTag id="sven" lang="en" /> sets linger.ms=10 and batch.size=64KB; producer waits up to 10 ms or 64 KB, ships one request. Throughput jumps to 150k msg/sec; CPU drops. Items at the front of a window wait ≤10 ms — acceptable.

<strong>One scenario.</strong> A monitoring agent does one HTTP POST per metric = 50k POSTs/sec to the backend. Backend chokes. Agent switches to one POST every 10 seconds with all accumulated metrics. POSTs to backend drop to 0.1/sec/agent. If the agent crashes mid-batch, up to 10 s of data is lost — accepted for 100x reduction in load.
</Explanation>

<KeyTakeaway>Batching amortises a fixed cost across N operations. Window = max-size + max-wait. Bigger batches buy throughput, cost tail-latency. Tune to SLO ceiling, not max throughput.</KeyTakeaway>

<Recap lang="en">
Batching reduces per-operation cost by sharing fixed overhead across multiple operations. The batch window balances throughput (bigger batches) against tail latency (longer wait for early items). Real-world systems like Kafka and databases use this pattern to achieve 10-100x throughput gains when fixed costs dominate.
</Recap>
