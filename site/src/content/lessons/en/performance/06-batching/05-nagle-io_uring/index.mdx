<Explanation>
<strong>Nagle's algorithm</strong>
John Nagle's RFC 896 (1984) introduced what's now called Nagle's algorithm: TCP buffers small outbound segments until either:
- An ACK is received for the previous segment, OR
- The buffer fills to Maximum Segment Size (MSS) bytes

Motivation: 1-byte Telnet keystrokes were creating 41-byte TCP/IP packets (1 byte data + 40 byte header), wasting 97.5% of bandwidth on headers.

How it works:
1. Application writes() data to socket
2. TCP implementation checks: is there un-ACKed data waiting?
   - If yes: buffer new data until ACK arrives OR buffer reaches MSS
   - If no: send immediately (no buffering for first write)
3. When conditions met: send buffered data as one TCP segment

Tradeoff: Interactive applications (Telnet, SSH) experience increased latency because they wait for ACK or full buffer before sending. TCP_NODELAY socket option disables Nagle for latency-sensitive protocols.

<strong>io_uring deep dive</strong>
io_uring (Linux 5.1+) is a modern async I/O interface that uses two ring buffers:
- Submission Queue (SQ): user submits operation descriptors
- Completion Queue (CQ): kernel posts results

Modes:
1. Default: application calls io_uring_enter() to notify kernel → kernel processes all SQ entries in batch
2. Polled (IORING_SETUP_SQPOLL): kernel thread continuously polls SQ → application can submit with zero syscalls
3. Application I/O buffering: custom buffers in user space to reduce SQ entries

Performance impact:
- Traditional read()/write(): ~0.5-2 μs per syscall context switch
- At 500k ops/sec: 250-1000 ms/sec spent on syscalls (1-2 CPU cores)
- io_uring default mode: 1 syscall per batch → 500k/100 = 5k syscalls/sec → 2.5-10 ms/sec
- io_uring polled mode: ~0 syscalls/sec → near zero context switch overhead

Senior teams see 5-15% CPU reduction on TLS proxies and databases. Security CVEs have led some container runtimes to disable io_uring by default — weigh tradeoffs per deployment.

<strong>Connection</strong>
Both Nagle and io_uring solve the same problem: fixed cost per operation dominates at high rates.
- Nagle: fixed cost = 40-byte TCP/IP header per packet
- io_uring: fixed cost = user→kernel→user context switch per syscall
Both buffer operations to amortise that fixed cost across N units of work.

<PersonaTag id="bea" lang="en"/> has TCP_NODELAY enabled and uses traditional syscalls; low latency, high CPU/syscall overhead. <PersonaTag id="sven" lang="en"/> uses Nagle's algorithm (default) and io_uring; higher latency, much lower CPU overhead.
</Explanation>

<KeyTakeaway>Nagle's algorithm and io_uring both apply batching at different levels (TCP, syscall) to amortise fixed cost. Trade latency for throughput; tune to SLO ceiling.</KeyTakeaway>

<Recap lang="en">
Nagle's algorithm (TCP) and io_uring (syscalls) both demonstrate how batching amortises fixed cost at different levels. Nagle saves on TCP/IP headers; io_uring saves on context switch overhead. Both trade increased latency for throughput gains, and the senior engineering question is always: what window size maximises throughput without breaking SLO tail latency?
</Recap>
