    { q: "State Amdahl's law, and explain why a 10x microbenchmark win can produce a 1.05x application speedup.", a: "total_speedup = 1 / ((1 − p) + p/s), where p is the fraction of total time spent in the section and s is the local speedup. The ceiling (s → ∞) is 1 / (1 − p). A microbenchmark measures s in isolation but says nothing about p. If the optimised function is only ~5% of total time, then even s = 10 gives 1 / (0.95 + 0.05/10) ≈ 1.05x — the application barely moves because the function was a small share. The lesson: a profile gives p, the benchmark gives s, and you need both to predict the real win. Optimising a function with a small share is wasted engineering no matter how large the local speedup." },
    { q: "What is the difference between self-time and cum-time, and what action does each reading suggest?", a: "Self-time is the time spent in a function's own instructions, excluding the functions it calls. Cum-time (cumulative) includes the entire call subtree below it. If self-time is large, the function itself is doing the costly work — fix it there. If cum-time is large but self-time is tiny, the function is a thin routing or dispatch layer (HTTP handler, middleware) and the real cost sits in a callee — walk down the flame graph to the wide leaf with large self-time. Confusing the two leads to rewriting a wrapper while the cost stays in the callee, or vice versa." },
    { q: "Why must you verify the profiler's overhead is within ~5% of the baseline headline metric before trusting a profile (the observer effect)?", a: "Every profiler perturbs the system it measures. A sampling profiler at 100 Hz adds 0.5–2% — acceptable. An instrumentation profiler that times every entry/exit adds 20–100% in JIT runtimes because it disables the optimiser's inlining, so it measures a slower, differently-shaped program than production runs. If latency or throughput with the profiler on differs from the off-profiler baseline by more than ~5%, the profile's hotspots may be artefacts of the measurement, not real production costs. So: take the headline metric without the profiler first, then confirm the profiler run is within 5% before trusting where it points. Use sampling profilers for production; reserve instrumentation for tight microbenchmarks where exact call counts matter." },
    { q: "Why is a single benchmark run never a measurement, and what should be reported instead?", a: "Two runs of identical code typically differ by 5–10% from sources unrelated to the change: GC timing (stop-the-world windows shift), OS scheduler decisions, cache warmth at start, transient disk/network contention, and CPU frequency scaling on laptops. A single-run '15% faster' cannot be distinguished from this noise floor. Report instead: median, p95, and p99 across at least 5 runs for a macrobench (30+ for a short microbench), with the spread (standard deviation or 95% CI) explicit. Mean is the wrong central statistic because it is dominated by outliers and hides the tail; the median is robust and p99 captures the user-felt tail. A win is real only if the median improved AND p95/p99 did not regress." },
    { q: "What do hardware performance counters add on top of a flame graph, and how does IPC change the fix you choose?", a: "A flame graph names which function is on the CPU; it does not say what the CPU is doing inside it. Hardware counters expose the silicon-level cost. IPC (instructions per cycle) is the key reading: IPC below ~1.0 with a high cache-miss rate means the function is memory-stalled — the CPU is idle waiting for RAM, so the lever is data layout (smaller structs, struct-of-arrays, cache-friendly traversal, prefetch), not the algorithm. IPC above ~2.5 with low cache-misses means compute-bound — the lever is vectorisation/SIMD or a smarter algorithm. The flame graph shows a memory-bound and a compute-bound function as identical wide leaves; only the counters reveal which fix will actually move it. A classic trap is swapping in a faster parser for a memory-stalled function and seeing no improvement." },
