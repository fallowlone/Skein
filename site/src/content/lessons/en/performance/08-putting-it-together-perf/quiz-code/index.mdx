## Artifact 2 — the hot path

```go
// app.scoreAll — called once per search request, ~10k candidates
func scoreAll(q []float32, candidates []Doc) []Result {
    var results []Result                    // nil slice
    for _, d := range candidates {
        v := append([]float32{}, d.Vector...) // fresh copy per candidate
        results = append(results, Result{d.ID, cosineSim(q, v)})
    }
    return results
}
```

Both cut allocation on the hot path the profile flagged.", correct: true },
    { label: "Raise GOGC so the loop's allocations trigger GC less often.", misconception: "GOGC changes when GC runs, not how much this loop allocates. The profile shows the cost is in the path itself; eliminate the per-candidate copy and pre-size the slice instead of deferring collection." },
    { label: "Parallelise the loop across goroutines — that is the only way to speed it up.", misconception: "Parallelism multiplies the same wasteful per-candidate copies across cores and adds coordination overhead. Remove the wasted allocation first; only then consider parallelism if cosineSim is genuinely CPU-bound." },

Eliminating the copy reduces both the allocation the profile shows and the data cosineSim must stream." },

## Artifact 3 — the query log

```
SELECT id, total FROM orders WHERE user_id = $1                 -- 1 row set, 50 rows
SELECT name FROM customers WHERE id = $1   -- params: 11
SELECT name FROM customers WHERE id = $1   -- params: 12
SELECT name FROM customers WHERE id = $1   -- params: 13
... (47 more identical-shape queries) ...
-- total: 51 queries, 1 request
```

<Quiz
  id="08-putting-it-together-perf-code-3"
  lessonSlug="08-putting-it-together-perf"
  lang="en"
  question="This log is one request. Name the pattern and the fix that removes it at the source."
  choices={[
    { label: "Classic N+1: 1 query for the list, then N queries (one per row) for the related customer. Fix at the data-access layer — a JOIN, a single `WHERE id IN (...)` over the collected ids, or a batch-loader — collapsing 51 round-trips into 2.", correct: true },
    { label: "Connection-pool exhaustion — raise the max pool size.", misconception: "The 51 queries run on one request and reuse the connection; the cost is the round-trip count, not pool size. A bigger pool lets more requests issue the same wasteful 51-query pattern in parallel." },
    { label: "Slow customer lookups — add an index on customers.id.", misconception: "customers.id is the primary key; the lookups are already fast. The waste is doing 50 separate round-trips instead of one batched query — an index does not change that." },
    { label: "Use a read replica so the 50 lookups hit a different node.", misconception: "A replica spreads the same 50 round-trips to another machine; the structural N+1 remains and the latency of 50 sequential trips persists. Batch the access instead of relocating it." },
  ]}

<Recap lang="en">
Four artifacts, one discipline. A `top -cum` profile distinguishes the root frame (huge cumulative, no leverage) from the real hotspot (high flat); the hot-path snippet shows allocation waste the profile predicted; the query log exposes N+1 by its repeated single-row shape; the bundle report turns bytes into device-CPU cost. In each case the fix lives at the cost's own layer — eliminate the allocation, batch the round-trips, trim the bytes — never one knob removed from where the evidence points.
</Recap>
