<Quiz

  lessonSlug="08-putting-it-together-perf"
  lang="en"
  question="A checkout page feels slow. A senior engineer is told the JSON serializer is 'obviously' the bottleneck. What do they do first, and why?"
  choices={[
    { label: "Profile the request under representative load before changing anything. Intuition about bottlenecks is wrong more than half the time, and Amdahl's law caps any speedup by the fraction of time actually spent there — optimising a 3% serializer cannot move the page.", correct: true },
    { label: "Rewrite the serializer immediately — it is the named suspect, so fixing it is the fastest path.", misconception: "Acting on a named suspect without measurement is exactly the failure the track opens with. If the serializer is 3% of wall time, even eliminating it entirely yields a 3% ceiling by Amdahl's law." },
    { label: "Add a cache in front of the page — caching always helps.", misconception: "A cache helps only if the dominant cost is recomputation or repeated I/O. Caching a page whose cost is one slow downstream call adds invalidation complexity for no win, and you still do not know where the time went." },
    { label: "Switch the service to a faster language runtime.", misconception: "Replacing the runtime is the most expensive, lowest-information move possible before profiling. You would rewrite everything to chase a cost you have not located." },
  ]}

  question="A flame graph shows one function dominating CPU, and within it the time is spent in memory allocation and the subsequent GC. Where does the durable fix live?"
  choices={[
    { label: "At the allocation, not the collector. The hot path is allocation-shaped; GC pause is the symptom and allocation rate is the cause. Eliminate or pre-size the allocations on that path first, and tune or switch the collector only if the bound still is not met.", correct: true },
    { label: "In the garbage collector's tuning knobs — raise GOGC so it runs less often.", misconception: "Deferring GC trades memory for fewer cycles and can push you toward OOM; it masks an allocation hotspot the profiler already located. The fix ladder eliminates allocation before it tunes the collector." },
    { label: "In the algorithm's big-O — pick a lower-complexity data structure.", misconception: "The profile points at allocation, not at asymptotic growth. A lower-O structure that allocates per element can make GC pressure worse; match the fix to the cost shape the profiler shows." },
    { label: "In the request handler's concurrency — add more worker goroutines.", misconception: "More workers multiply allocation rate and GC pressure on the same hot path; parallelising an allocation-bound function spreads the problem rather than removing it." },
  ]}
/>

<Quiz
  id="08-putting-it-together-perf-choice-3"
  lessonSlug="08-putting-it-together-perf"
  lang="en"
  question="A dashboard endpoint issues 1 fast query to list 50 orders, then 50 more queries to fetch each order's customer. Each query is 2 ms. Profiling the queries themselves shows nothing slow. What is the dominant cost and the right fix?"
  choices={[
    { label: "Round-trip count, not per-query time — this is N+1. The dominant cost is 50 sequential round-trips, so collapse them at the data-access layer (a JOIN, an IN-list, or a batch-loader), turning 51 round-trips into 2.", correct: true },
    { label: "Each query is too slow at 2 ms — add an index to speed up the per-row lookup.", misconception: "An index shaves microseconds off queries that are already fast; it does not remove the 50 round-trips. The cost is fan-out, not per-query latency." },
    { label: "The database is overloaded — scale it vertically.", misconception: "Vertical scaling buys headroom for the same 51 round-trips; the structural waste of one-query-per-row remains and reappears at the next traffic level. Fix the access pattern, not the box." },
    { label: "Add a cache in front of the customer table.", misconception: "A cache can hide the symptom on warm hits but still pays N round-trips cold, adds invalidation, and leaves the N+1 pattern in the code to bite the next endpoint. Batch the access first." },
  ]}
/>

<Quiz
  id="08-putting-it-together-perf-choice-4"
  lessonSlug="08-putting-it-together-perf"
  lang="en"
  question="An ingestion service makes one network call per event with ~3 ms of fixed per-call overhead (connection, auth, serialization) and ~0.1 ms of useful work. Throughput is capped. Batching events into groups of 100 is proposed. What is the real tradeoff to state up front?"
  choices={[
    { label: "Batching amortizes the fixed per-call cost across 100 events, so throughput rises sharply — but it charges tail latency: an event now waits for the batch window to fill or the max-wait timer to fire. You must set batch size and max-wait against the latency SLO.", correct: true },
    { label: "Batching is pure win — it lowers both latency and cost with no downside.", misconception: "Batching trades latency for throughput. The first event in a batch waits for the window; under low load the max-wait timer dominates. There is always a tail-latency charge to budget against the SLO." },
    { label: "Batching helps only if the per-event useful work is large.", misconception: "It is the reverse: batching pays most when fixed per-op overhead dominates the useful work, exactly this 3 ms vs 0.1 ms case. Large per-event work would dilute the fixed-cost amortization." },
    { label: "Cache the responses instead — that removes the calls.", misconception: "Ingestion events are distinct writes, not repeated reads; there is nothing to cache. The fixed per-call overhead is amortized by batching, not by caching." },
  ]}
/>

<Recap lang="en">
Every question reduced to the same loop the track is built on: profile before you guess (Amdahl caps the payoff of optimising the wrong thing), classify the dominant cost into its shape — allocation/GC, N+1 round-trips, per-op fixed cost, client CPU bytes — fix it at the layer where that cost actually lives, then verify under identical load and enforce the gain in CI. Performance is not a project you finish; it is this loop you keep running.
</Recap>
