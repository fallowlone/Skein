If a slow query already holds ACCESS SHARE, the ALTER cannot acquire its lock and joins the wait queue. Postgres grants locks FIFO per object, so it will not let a later, lighter ACCESS SHARE request skip ahead of the waiting ALTER — otherwise the DDL could be starved forever on a busy table. So every new SELECT that arrives after the ALTER also queues, behind the ALTER's pending ACCESS EXCLUSIVE. The table is frozen for new queries for the entire duration of the original slow query, even though the migration itself runs in milliseconds once it finally gets the lock." },
    { q: "How does PG 11+ make ADD COLUMN with a constant default instant, and what is the difference for a volatile default?", a: "For a non-volatile (constant or stable) default, PG 11 stores the value in the catalog — pg_attribute.atthasmissing = true and attmissingval = the value — instead of writing it into every row. Existing rows keep their original physical storage; when a query reads an old row, the executor injects the missing value at read time. The lock-hold drops from minutes (full rewrite) to milliseconds (catalog update). A volatile default like clock_timestamp() or gen_random_uuid() produces a different value per row, so no single shared missing value can represent it — Postgres must visit and rewrite every row under ACCESS EXCLUSIVE, exactly as before PG 11. The safe path for a volatile default is: add the column with no default (instant), backfill in batches, then SET DEFAULT for future inserts." },
    { q: "Explain the NOT VALID + VALIDATE CONSTRAINT pattern and why it is production-safe where a plain ADD CONSTRAINT is not.", a: "A plain ADD CONSTRAINT (CHECK or FOREIGN KEY) takes ACCESS EXCLUSIVE and scans the whole table inside that lock, blocking all reads and writes for the scan duration. NOT VALID adds the constraint enforced only for rows inserted or updated from this moment; existing rows are not scanned, so the add is instant under a brief lock. VALIDATE CONSTRAINT then scans the existing rows to confirm they pass, but it takes SHARE UPDATE EXCLUSIVE — which conflicts only with other DDL and autovacuum, not with INSERT/UPDATE/DELETE/SELECT. So DML continues during the scan. The two-step form reaches the same final consistency as the one-step, with no write blocking. The same pattern adds NOT NULL safely via CHECK (col IS NOT NULL) NOT VALID + VALIDATE + SET NOT NULL." },
    { q: "State the core invariant of expand-contract and walk the six phases of a column rename (username to handle).", a: "The invariant: at every moment during a rolling deploy, the live schema must be simultaneously compatible with both the previous and the next application version, because old and new pods run at the same time. A one-step rename breaks this — old pods reference the old name and fail the instant it is renamed. The six phases: (1) Expand — ADD COLUMN handle (instant). (2) Dual-write — deploy code that writes both username and handle. (3) Backfill — UPDATE handle = username in batches. (4) Cut over reads — deploy code that reads handle, still writing both. (5) Stop old writes — deploy code that writes only handle. (6) Contract — DROP COLUMN username. Each phase is a separate PR and is independently reversible; rollback is easiest during dual-write because both columns exist and are populated." },
    { q: "Why does a single-statement backfill flood WAL, what breaks downstream, and what is the batch-size guideline?", a: "Every row an UPDATE modifies generates a WAL record before the change hits the heap, and Postgres cannot suppress WAL for DML — WAL is the source of truth for crash recovery and replication. A single UPDATE over 100M rows emits ~100M WAL records, tens of GB in minutes. Streaming replicas replay WAL sequentially; they fall behind, replication lag climbs to minutes, and standby reads return stale data (and if lag exceeds max_standby_streaming_delay, conflicting standby queries get cancelled). The fix is to batch in 1k–10k rows per transaction with pg_sleep(0.1) between batches: each batch emits a bounded amount of WAL and the sleep lets replicas catch up. Monitor pg_stat_replication.replay_lag during the backfill and slow the batches if lag exceeds 5–10 s." },

So production rollback is always forward: write a new migration that corrects the problem and deploy it. Separately, multiple pods booting at once can each run pending migrations and race — pg_advisory_lock serialises the runners so only one applies at a time (better still, a gated pre-deploy job removes the race entirely). And CREATE INDEX CONCURRENTLY builds across two scan phases over multiple transactions, so it cannot run inside a BEGIN..COMMIT block; the migration file must carry a non-transactional annotation (Atlas: -- atlas:txmode none; golang-migrate: -- migrate:notransaction) and you must verify indisvalid afterwards, dropping and retrying any INVALID index with DROP INDEX CONCURRENTLY." },
