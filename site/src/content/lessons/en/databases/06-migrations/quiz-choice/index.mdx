  question={`On PG 16 a deploy runs the statement below and it completes in 8 ms, yet the users table returns 503s for 70 seconds. A 60-second analytics SELECT was already in flight on users when the ALTER fired. What actually froze the table?

\`\`\``}
  choices={[
    { label: "The ALTER needs ACCESS EXCLUSIVE, which conflicts with the analytics query's held ACCESS SHARE, so it joins the FIFO lock queue.     { label: "The ADD COLUMN rewrote all rows to materialise the 'active' default, and the rewrite took 70 seconds.", misconception: "A constant default is instant since PG 11 — it is stored in pg_attribute.attmissingval, no rows are written.     { label: "Postgres prioritises DDL over reads, so it killed the analytics query and made new readers wait for cleanup.", misconception: "Postgres never pre-empts another session for a migration. The ALTER waits behind the held ACCESS SHARE; it cannot cancel it. The freeze is the FIFO queue, not a priority pre-emption." },
    { label: "The connection pool exhausted on its own; the migration was a coincidence.", misconception: "The pool exhausted because new SELECTs were stuck waiting in the lock queue behind the ALTER. The migration is the proximate cause, via the lock queue — not a coincidence." },

<Quiz
  id="06-migrations-choice-2"
  lessonSlug="06-migrations"
  lang="en"
  question="The same instant ALTER from question 1 keeps timing out behind long queries. Which single change turns 'migration freezes the database' into 'migration logs an error and retries'?"
  choices={[
    { label: "SET lock_timeout = '2s' on the migration session. If the lock is not acquired within 2 s the ALTER aborts cleanly, releases its queue position so waiting SELECTs unblock, and the migration tool retries with exponential backoff until a quiet window opens.", correct: true },
    { label: "SET statement_timeout = '2s' on the migration session.", misconception: "statement_timeout caps how long a statement runs after it holds the lock — it does nothing about waiting in the queue. The queue-freeze is a lock-acquisition problem, so lock_timeout is the lever. A migration wants both, for different reasons." },
    { label: "Run the migration inside a tighter BEGIN..COMMIT to shorten the lock hold.", misconception: "Wrapping in a transaction does not shorten the wait for the lock; the ALTER still queues behind the held ACCESS SHARE for the blocking query's full duration. It only controls hold time after acquisition, which was already 8 ms." },
    { label: "Add more connections to the pool so requests do not exhaust it.", misconception: "More connections just means more sessions pile up behind the ALTER in the lock queue — the table is still frozen for new readers. This masks the symptom and can worsen the pile-up." },
  ]}
/>

<Quiz
  id="06-migrations-choice-3"
  lessonSlug="06-migrations"
  lang="en"
  question="You must add a FOREIGN KEY to a 100M-row orders table without blocking writes. Which approach is production-safe?"
  choices={[
    { label: "ADD CONSTRAINT ... FOREIGN KEY ... NOT VALID (instant, enforces new rows only), then VALIDATE CONSTRAINT in a separate statement — VALIDATE scans existing rows under SHARE UPDATE EXCLUSIVE, which does not block INSERT/UPDATE/DELETE.", correct: true },
    { label: "ADD CONSTRAINT ... FOREIGN KEY ... in one statement during an off-peak window.", misconception: "A plain ADD CONSTRAINT takes ACCESS EXCLUSIVE and scans the whole table inside that lock — writes are blocked for the scan duration regardless of the hour. Off-peak shrinks the blast radius but does not remove the block." },
    { label: "Enforce the relationship with an application-level check instead of a DB constraint.", misconception: "App-level checks race under concurrency and drift from the schema; they do not give the same guarantee. The NOT VALID + VALIDATE pattern adds the real constraint without blocking writes, so there is no reason to weaken the guarantee." },
    { label: "Wrap ADD CONSTRAINT in a short transaction to bound the lock time.", misconception: "The ACCESS EXCLUSIVE lock is held for the entire validating scan whether or not it is inside an explicit transaction. A short transaction does not help; splitting into NOT VALID + VALIDATE does." },
  ]}
/>

<Quiz
  id="06-migrations-choice-4"
  lessonSlug="06-migrations"
  lang="en"
  question="A rolling deploy is renaming users.username to users.handle. To keep both the old and new app versions working at every moment, which step ordering is correct?"
  choices={[
    { label: "Expand (ADD COLUMN handle), then deploy dual-write code (writes both), then backfill in batches, then cut reads to handle while still dual-writing, then stop writing username, then contract (DROP COLUMN username) — each step independently deployable and reversible.", correct: true },
    { label: "Run ALTER TABLE ... RENAME COLUMN username TO handle, then deploy the new code that uses handle.", misconception: "During the rolling deploy old pods still reference username; the instant the rename commits they get 'column does not exist' errors. A rename is fast but breaks the both-versions-compatible invariant — that is exactly the outage expand-contract avoids." },
    { label: "Deploy dual-write code first, then ADD COLUMN handle, then drop username right after the backfill.", misconception: "Dual-writing to a column that does not exist yet fails, and dropping username right after backfill kills old pods still reading it. The contract must wait until no running code references the old column." },
    { label: "ADD COLUMN handle and DROP COLUMN username in the same migration, then deploy new code.", misconception: "Dropping username while old pods still read it breaks them immediately — this is the single-step rename failure with extra steps. Expand and contract must be separated by full code rollouts." },
  ]}
/>

  question={`A backfill ships as one statement on a 100M-row table. On a primary + 2 replicas, what is the first thing that breaks and what is the durable fix?

\`\`\``}
  choices={[
    { label: "The single UPDATE emits one WAL record per row — tens of GB in minutes. Replicas cannot replay that fast, so replication lag climbs and standby reads go stale. Fix: batch in 1k–10k-row chunks with pg_sleep between batches and watch pg_stat_replication.replay_lag.", correct: true },
    { label: "The primary deadlocks against itself and the UPDATE rolls back.", misconception: "A single UPDATE does not deadlock against itself. The blast radius is the WAL flood and the resulting replication lag on standbys, not a deadlock on the primary." },
    { label: "Postgres refuses the UPDATE because it would overload the replicas.", misconception: "Postgres has no mechanism to throttle DML based on replication impact — it runs the UPDATE and floods WAL. Bounding the blast radius is the engineer's job, via batching." },
    { label: "Nothing breaks; replicas replay WAL instantly regardless of volume.", misconception: "Replicas replay WAL sequentially; tens of GB cannot be consumed instantly. Lag climbs and standby reads return stale data — the exact failure batching prevents." },
  ]}

  question="Three Kubernetes replicas boot at once and each runs migrate up on startup. One succeeds; two crash with duplicate-object errors. What was missing, and what is the cleaner production pattern?"

    { label: "Migrations are idempotent by default, so the crash is a bug in the tool.", misconception: "Migrations are not idempotent by default — CREATE TABLE or ADD COLUMN fails if applied twice. The crash is the expected result of three runners racing without a lock, not a tool bug." },
    { label: "Postgres should have queued the three DDL statements and run them serially on its own.", misconception: "Postgres has no idea the three sessions are logically the same migration set; it runs each independently and they collide.     { label: "Add a unique constraint on schema_migrations and let the losers fail silently.", misconception: "A unique constraint stops double-inserts in the ledger, but the actual DDL still errors on the losing pods and crash-loops them. <Recap lang="en">
The unit's through-line is one defensive checklist for every schema change. Locks: most DDL needs ACCESS EXCLUSIVE and the FIFO queue turns one slow query into a table freeze — SET lock_timeout so a failed attempt aborts and retries. Rewrites: a constant default is instant since PG 11, volatile defaults still rewrite. Constraints and indexes: NOT VALID + VALIDATE and CREATE INDEX CONCURRENTLY take SHARE UPDATE EXCLUSIVE and leave DML running. Breaking changes: expand-contract keeps old and new code compatible at every moment, never a single-step rename. Backfills: batch to bound the WAL flood and replica lag. Runners: serialise with an advisory lock and gate a pre-deploy job before the rollout. Every answer resolves back to the same invariant — the schema must stay compatible with both code versions, at every moment, without freezing the table.
</Recap>
