<Quiz
  id="02-indexes-choice-2"
  lessonSlug="02-indexes"
  lang="en"
  question="A 100M-row tasks table is 80% status = 'done' (never queried by the dashboard). The dashboard only reads open and in_progress tasks. Which index strategy minimizes both size and write overhead?"
  choices={[
    { label: "A partial index WHERE status IN ('open','in_progress') keyed on the dashboard's filter and sort columns. It indexes ~20% of rows, so it is several times smaller, and inserts/updates of done rows never touch it.", correct: true },
    { label: "A full composite on (status, created_at) — it covers both the filter and the sort.", misconception: "A full index covers all 100M rows including the 80M done rows the dashboard never reads — roughly 5× larger than needed, and every write to a done row still maintains it. The partial predicate eliminates that waste." },
    { label: "No index — only 20% of rows match, so the planner will seq-scan anyway.", misconception: "20% of 100M is 20M rows, but the dashboard filters further (per-workspace, per-project) to a tiny selective slice. A partial index on the hot subset is exactly what the planner wants there." },
    { label: "A BRIN index on status — it is tiny and ignores the leading-column rule.", misconception: "BRIN stores min/max per block range and only helps when data is physically ordered by the indexed column. status is low-cardinality and unordered on disk; every block range spans all statuses, so BRIN gives no pruning." },
  ]}
/>

  lang="en"
  question="EXPLAIN (ANALYZE, BUFFERS) shows Index Only Scan with Heap Fetches: 12000 on an orders table, and the query is slow despite the right covering index. What is happening and what is the durable fix?"
  choices={[
    { label: "The Visibility Map is stale — for those 12,000 TIDs the all-visible bit is clear, so Postgres must fetch the heap page to check tuple visibility. Fix: VACUUM now, then lower autovacuum_vacuum_scale_factor (e.g. to 0.05) and kill long-running transactions that block VACUUM.", correct: true },
    { label: "The index is missing some projected columns, so it falls back to heap reads.", misconception: "If columns were missing the plan node would be Index Scan, not Index Only Scan. An index-only scan with heap fetches is a Visibility Map problem, not a covering problem." },
    { label: "The index is INVALID after a failed CREATE INDEX CONCURRENTLY.", misconception: "An INVALID index is invisible to the planner — the plan would show a Seq Scan, not an Index Only Scan. The scan type proves the index is valid and chosen." },
    { label: "Too many result rows — index-only scans degrade above a row threshold.", misconception: "Row count does not decide heap fetches; the Visibility Map bit per page does. An append-mostly table returning millions of rows can still show Heap Fetches: 0 if VACUUM keeps the VM current." },
  ]}

<Quiz
  id="02-indexes-choice-4"
  lessonSlug="02-indexes"
  lang="en"
  question="A DELETE FROM posts WHERE id = 42 with ON DELETE CASCADE takes 7 minutes and holds locks the whole time, on a posts/comments schema. What is the root cause?"
  choices={[
    { label: "comments(post_id) — the referencing FK column — is not indexed. Postgres indexes the referenced PK posts(id) automatically but never the child's FK column, so the cascade sequential-scans all comments to find rows to delete.", correct: true },
    { label: "posts(id) needs an index for the cascade to be fast.", misconception: "posts(id) is the primary key and is already indexed. The cascade scans the child table comments by post_id; it is the unindexed referencing column, not the referenced one, that forces the O(n) scan." },
    { label: "The CASCADE is inherently O(n) and cannot be sped up.", misconception: "Indexing comments(post_id) turns the cascade lookup into an index scan. The slowness is a missing index, not an intrinsic property of cascades." },
    { label: "MVCC dead tuples — the table needs VACUUM.", misconception: "VACUUM reclaims dead tuples and helps visibility, but it does not give the cascade a way to find child rows by post_id. Only an index on comments(post_id) fixes the scan." },
  ]}
/>

<Quiz

  lessonSlug="02-indexes"
  lang="en"
  question="orders.user_id is BIGINT with an index on orders(user_id). A query runs SELECT * FROM orders WHERE user_id = '42' (the literal is TEXT) and does a Seq Scan. Why, and what is the fix?"
  choices={[
    { label: "Implicit type coercion: to compare BIGINT with TEXT, Postgres casts the column on every row, so the B-tree (sorted by the raw BIGINT) cannot be walked. Fix: pass the correctly typed parameter, e.g. a bigint cast or bigint literal.", correct: true },
    { label: "The index is bloated and the planner gave up on it.", misconception: "Bloat slows an index but does not flip the plan to Seq Scan for a selective equality. The cause here is the cast disabling index use; EXPLAIN shows the coercion in the filter." },
    { label: "B-tree indexes cannot answer equality on numeric columns.", misconception: "B-tree handles BIGINT equality perfectly. The problem is the TEXT literal forcing a per-row cast of the column, not the index type." },
    { label: "Add an expression index on user_id cast to text.", misconception: "That works around the symptom by indexing the wrong thing. The correct fix is to send the right type so the existing index is used — don't add an index to compensate for a type bug in the query." },
  ]}
/>

  question="A search feature runs WHERE title ILIKE '%invoice%' on a 50M-row table and takes 12 seconds. The query is keyword-style search over document text. What is the right index choice?"
  choices={[
    { label: "A GIN index on a tsvector of the text (e.g. a STORED GENERATED tsvector column). It is a word-level inverted index with stemming and ts_rank — the Postgres-native answer for keyword full-text at this scale.", correct: true },
    { label: "A plain B-tree on title.", misconception: "A leading wildcard '%invoice%' has no known prefix, so a B-tree (which needs a prefix to navigate) cannot help — it is always O(n). That is exactly why the query is slow." },
    { label: "pgvector HNSW on an embedding of title.", misconception: "HNSW does semantic similarity and needs an embedding pipeline per document and query. For exact keyword search it is the wrong tool and far more expensive; tsvector GIN is the default." },
    { label: "A BRIN index on title.", misconception: "BRIN summarizes min/max per block range for physically-ordered numeric or time data. It cannot answer substring or keyword containment on text at all." },

<Recap lang="en">
The unit's through-line is one design loop: a composite is usable only from a leading prefix, so design it around the always-present filter; partial predicates cut a hot-subset index to a fraction of full size and skip writes for cold rows; INCLUDE plus a current Visibility Map make an index-only scan skip the heap; the index type must match the data shape (B-tree for ordered values, GIN for text and JSONB, HNSW for semantic); and the recurring failures — missing FK index, type coercion, stale stats, leading-wildcard ILIKE — all resolve back to matching the index to the exact question the query asks, verified with EXPLAIN (ANALYZE, BUFFERS).
</Recap>
