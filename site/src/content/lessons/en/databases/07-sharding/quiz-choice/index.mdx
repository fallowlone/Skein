  choices={[

  lang="en"
  question="A team adds `PARTITION BY RANGE (created_at)` to their largest table and reports they have 'sharded the database'. A month later write throughput is unchanged. Why?"
  choices={[
    { label: "Partitioning splits one table into sub-tables on a single Postgres instance — it buys partition pruning and instant retention DROP, not throughput. All writes still contend for one primary's WAL, CPU, and IO.", correct: true },
    { label: "The partitions need a few weeks to warm their caches before throughput improves.", misconception: "Cache warming does not change the structural fact: every partition lives on the same primary. There is no extra write capacity to warm into." },
    { label: "They forgot an index on the partition key, which would have unlocked the throughput gain.", misconception: "An index speeds lookups but adds no write capacity. Partitioning never multiplies throughput because it never adds machines — that is what sharding does." },
    { label: "Partitioning and sharding are the same thing; throughput should have improved automatically.", misconception: "They are different: partitioning is single-instance pruning and retention; sharding is multi-instance throughput scaling. Conflating them is exactly this team's mistake." },
  ]}
/>

<Recap lang="en">
The through-line of the unit is one decision chain: pick a shard key that is selective, uniform, stable, and present at routing time; partition for pruning and retention but shard for throughput; co-locate every tenant-scoped table so 99% of joins stay single-node; expect hot shards on power-law tenants and answer them with tenant isolation, not rebalancing; keep transactions single-shard to dodge 2PC's in-doubt risk; and lean on logical-replication-based online resharding — while remembering that a shard-key change is a months-long decision lived with for years.
</Recap>
