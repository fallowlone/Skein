<Quiz
  id="08-putting-it-together-db-choice-1"
  lessonSlug="08-putting-it-together-db"
  lang="en"
  question="A query filters orders by tenant and date and you add a composite index. Both plans below run on the same table; only the index column order differs. Why does the planner skip the index in plan A?

```sql
-- query
SELECT * FROM orders WHERE tenant_id = 42 AND created_at >= '2026-01-01';
-- A: CREATE INDEX ON orders (created_at, tenant_id);   -> Seq Scan
-- B: CREATE INDEX ON orders (tenant_id, created_at);   -> Index Scan
```"
  choices={[
    { label: "The leading-column rule: a B-tree can only seek efficiently on a prefix of its columns. Index A leads with created_at, so tenant_id can't drive the probe and the planner falls back to a seq scan; index B leads with the equality column tenant_id, then ranges on created_at.", correct: true },
    { label: "Index A is simply larger on disk, so the planner avoids it.", misconception: "Both indexes cover the same two columns and are near-identical in size. Selection is driven by whether the leading column matches the query's access pattern, not raw index size." },
    { label: "Postgres never uses composite indexes for mixed equality-plus-range predicates.", misconception: "It does — that is exactly what index B is for. Equality on the leading column then a range on the next is the canonical composite-index win." },
    { label: "You must list index columns in the same order they appear in the WHERE clause text.", misconception: "WHERE-clause text order is irrelevant. What matters is matching equality columns first, then the range column — the leading-column rule, not source order." },
  ]}
/>

<Quiz
  id="08-putting-it-together-db-choice-2"
  lessonSlug="08-putting-it-together-db"
  lang="en"
  question="A nightly batch runs one transaction that stays open for three hours. Over the same window an OLTP table that is heavily UPDATEd grows from 8 GB to 40 GB on disk even though the live row count barely changes. What links the long transaction to the bloat?"
  choices={[
    { label: "MVCC keeps every row version visible to the oldest snapshot. The 3-hour transaction holds an old snapshot, so VACUUM can't reclaim dead tuples created by the OLTP updates — they pile up as bloat until that transaction ends.", correct: true },
    { label: "The batch job is inserting 32 GB of new rows.", misconception: "The live row count barely changes, so this is not insert growth. It is dead-tuple accumulation: updates create new versions and the old ones can't be vacuumed while the long snapshot is held." },
    { label: "UPDATE rewrites the whole table once per transaction.", misconception: "UPDATE creates a new tuple version per changed row, not a full-table rewrite. The bloat comes from those dead versions being unreclaimable, not from rewriting." },
    { label: "Raising isolation to SERIALIZABLE would have prevented the bloat.", misconception: "A stricter isolation level holds snapshots at least as long, if not longer. The fix is to not hold one transaction open for hours — not to tighten isolation." },
  ]}
/>

<Quiz
  id="08-putting-it-together-db-choice-3"
  lessonSlug="08-putting-it-together-db"
  lang="en"
  question="A reporting query was fast for months, then suddenly picked a nested-loop join over a hash join and went from 200 ms to 40 s after a data-import spike. EXPLAIN ANALYZE shows the planner expected 12 rows from one branch but got 2.1 million. Root cause and first durable fix?"
  choices={[
    { label: "A row-estimate error: stale or insufficient statistics made the planner think one branch was tiny, so it chose a nested loop. First fix: ANALYZE the table (and raise the column statistics target / add extended statistics if the misestimate comes from correlated columns) so the estimate matches reality.", correct: true },
    { label: "Nested-loop joins are always wrong and the planner has a bug.", misconception: "A nested loop is optimal when one side really is tiny. The defect is not the join algorithm — it is the row estimate that fed the join choice. Fix the statistics, not the join." },
    { label: "Add an index hint to force the hash join permanently.", misconception: "Postgres has no hint syntax, and pinning one plan masks the real problem. The misestimate will distort other queries too; refreshing statistics fixes the input the planner reads." },
    { label: "The query needs more work_mem so the hash join fits in memory.", misconception: "work_mem affects whether a chosen hash spills to disk, but the planner never chose the hash join here. The trigger is the cardinality misestimate — a statistics problem." },
  ]}
/>

<Quiz
  id="08-putting-it-together-db-choice-4"
  lessonSlug="08-putting-it-together-db"
  lang="en"
  question="You move the app behind PgBouncer in transaction mode to survive a connection storm. Immediately the app errors that prepared statements do not exist, and a SET search_path you ran at connect time no longer sticks. Why?"
  choices={[
    { label: "In transaction mode a client holds a server connection only for one transaction, then it returns to the pool. Session state — server-side prepared statements and session-level SET — does not survive across transactions, so it breaks. Fixes: PgBouncer 1.21+ protocol-level prepared-statement support, or run per-session setup inside each transaction.", correct: true },
    { label: "PgBouncer corrupts the wire protocol for prepared statements.", misconception: "It corrupts nothing. The behaviour is by design: transaction mode multiplexes many clients over few server connections, so anything assuming a stable session connection breaks." },
    { label: "The pool is too small, so prepared statements get evicted.", misconception: "Pool size controls concurrency, not statement lifetime. The statements vanish because the client doesn't keep the same server connection between transactions in transaction mode." },
    { label: "Switching to session mode gives the same multiplexing with no downside.", misconception: "Session mode preserves session state but pins one server connection per client for the whole session, defeating the multiplexing that solved the connection storm. It is a real tradeoff, not a free fix." },
  ]}
/>

<Quiz
  id="08-putting-it-together-db-choice-5"
  lessonSlug="08-putting-it-together-db"
  lang="en"
  question="You must rename a hot column from `email` to `email_address` on a 500M-row table with zero downtime while old and new app code run side by side during a rolling deploy. Which sequence is correct?"
  choices={[
    { label: "Expand-contract: (1) add the new column, (2) dual-write both columns from the app and backfill the new one in batches, (3) switch reads to the new column once backfill is verified, (4) stop writing the old column, (5) drop the old column in a later release. Both columns exist throughout, so old and new code coexist safely.", correct: true },
    { label: "Run ALTER TABLE ... RENAME COLUMN in one migration; it is metadata-only and instant.", misconception: "RENAME is fast on the catalog, but it is a breaking change: the instant it commits, old app code referencing the old name errors. With two versions live during a rolling deploy you need expand-contract, not an atomic rename." },
    { label: "Take a brief maintenance window, rename, and redeploy everything at once.", misconception: "The requirement is zero downtime with versions coexisting. A window plus big-bang deploy violates both constraints; expand-contract is what lets the two code versions overlap." },
    { label: "Add the new column with a volatile DEFAULT and NOT NULL in a single ALTER on the 500M-row table.", misconception: "A NOT NULL plus volatile default forces a full table rewrite under an ACCESS EXCLUSIVE lock, freezing the table and queueing every waiting query — the lock-queue failure mode. Backfill in batches instead." },
  ]}
/>

<Quiz
  id="08-putting-it-together-db-choice-6"
  lessonSlug="08-putting-it-together-db"
  lang="en"
  question="A multi-tenant SaaS hits write limits on a single Postgres. The team proposes hash-sharding on a `country` column. Three tenants in one country drive 70% of traffic. What goes wrong, and what is the better shard key?"
  choices={[
    { label: "Hashing on country creates a hot shard: the three whale tenants share a country and hash into the same shard, so one node takes 70% of writes and sharding buys little. Shard on tenant_id — high-cardinality and co-locating each tenant's rows for local joins; a single tenant too large for one shard needs its own isolation, not a coarser key.", correct: true },
    { label: "Nothing — hashing always spreads load evenly because the hash function is uniform.", misconception: "A uniform hash spreads keys evenly, but load is per-key, not per-distinct-value. A low-cardinality, skewed key like country concentrates real traffic into one shard regardless of hash uniformity." },
    { label: "Shard on a random UUID per row to guarantee even distribution.", misconception: "Random per-row sharding does spread writes, but it scatters each tenant's rows across every shard, turning every tenant query and join into a cross-shard fan-out. Co-location by tenant_id is the point." },
    { label: "Sharding is the right first move the moment writes get heavy.", misconception: "Sharding is the last resort after schema, indexing, plan tuning, pooling, and read-replica options are exhausted — it adds cross-shard joins, rebalancing, and operational cost. Confirm the single-node ceiling is truly hit first." },
  ]}

<Recap lang="en">
The track is one decision tree applied to a growing product: model the schema for integrity first, add the index whose leading column matches the access pattern, read the plan to catch row-estimate errors before they cascade, keep transactions short so MVCC can vacuum, size and mode the pool to survive connection storms, decompose every breaking change into expand-contract phases, and reach for sharding only after a high-cardinality, co-locating shard key is chosen and every cheaper lever is spent. Each failure mode resolves back to one question: which layer is the bottleneck, and what is the cheapest lever that fixes it?
</Recap>
