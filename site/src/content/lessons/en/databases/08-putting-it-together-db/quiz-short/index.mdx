You bend it deliberately when the read pattern pays for it: denormalize a counter or rollup when the join to recompute it is on the hot path and the write amplification is acceptable; store JSONB or arrays when the shape is genuinely variable or sparse and you never need to constrain or index its internals as first-class columns.     { q: "How does the planner decide between an index scan and a sequential scan, and why does the leading column of a composite index matter so much?", a: "The planner estimates the cost of each access path from table statistics: a sequential scan reads every page once (cheap per row, expensive in total); an index scan does random I/O per matching row plus a heap fetch, which only wins when the predicate is selective enough that few rows match. Selectivity comes from statistics (n_distinct, histograms, MCV lists). A B-tree can only seek on a prefix of its columns, so a composite index helps a query only if the query constrains the leading column(s); index (a, b) serves WHERE a = ? and WHERE a = ? AND b = ?, but not WHERE b = ? alone. That is why the leading-column rule is the most violated principle in production — people add the index but order the columns for the wrong access pattern, and the planner quietly seq-scans." },
    { q: "Why do row-estimate errors cascade into catastrophically bad plans, and how do you stabilize a plan under traffic?", a: "The planner builds a plan bottom-up: the estimated row count of each node feeds the cost and join-algorithm choice of the node above it. If a scan's estimate is off by 1000x — stale statistics, correlated columns the planner treats as independent, or a value outside the histogram — that error multiplies up the join tree, so the planner might pick a nested loop expecting 12 rows and execute it two million times. Stabilize it by fixing the input, not pinning the output: run ANALYZE, raise the statistics target on skewed columns, add CREATE STATISTICS for correlated columns, and rewrite queries so estimable predicates drive the plan. Plan management or forcing a plan is a last resort that masks the misestimate rather than curing it." },
    { q: "What does PostgreSQL's MVCC snapshot isolation protect against, what does it not, and how does a long transaction cause table bloat?", a: "Under MVCC each transaction sees a consistent snapshot, so readers never block writers and writers never block readers; the default READ COMMITTED takes a fresh snapshot per statement, REPEATABLE READ takes one per transaction. Snapshot isolation prevents dirty reads and (at REPEATABLE READ) non-repeatable reads, but it does not prevent write skew — for that you need SERIALIZABLE, which adds predicate-tracking and may abort transactions with a serialization failure you must retry. Bloat: every UPDATE/DELETE leaves the old tuple version in place, reclaimable only once no snapshot can still see it. A transaction held open for hours pins an old snapshot, so VACUUM cannot remove dead tuples created meanwhile, and the table (and its indexes) grow unboundedly until that transaction ends." },
    { q: "Give the pool-sizing reasoning for PgBouncer in front of Postgres: why are backends heavy, how big should the server-side pool be, and what is the transaction-mode prepared-statement trap?", a: "Each Postgres backend is a full OS process with its own memory and is expensive to create and to keep idle, so you cannot let thousands of app connections map 1:1 to backends. PgBouncer multiplexes many client connections onto a small server-side pool; in transaction mode a server connection is borrowed only for one transaction, so a handful of busy backends can serve thousands of clients. A useful starting point for the server pool is roughly (core_count * 2 + effective_spindle_count) for CPU-bound work, then measured against actual concurrency — far smaller than most teams expect, because a connection doing nothing still costs. The trap: transaction mode breaks anything assuming a stable session — server-side prepared statements and session SET vanish between transactions; PgBouncer 1.21+ adds protocol-level prepared-statement support, otherwise disable them or move setup into each transaction." },

A low-cardinality or skewed key (country, status, a date bucket) maps disproportionate real traffic onto one shard: even a uniform hash spreads distinct values evenly, but if a few values carry most of the load, those land on one node and you get a hot shard that defeats the point. Safe order of operations: exhaust single-node levers first — schema and index fixes, plan stabilization, connection pooling, read replicas for read load — because sharding adds cross-shard joins, distributed transactions, rebalancing, and operational weight. Then choose declarative partitioning for time-series-style data on one node, or Citus / a directory layer for true horizontal write scale, and plan online resharding from day one." },
