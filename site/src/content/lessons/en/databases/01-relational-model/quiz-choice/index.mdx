<Quiz
  id="01-relational-model-choice-1"
  lessonSlug="01-relational-model"
  lang="en"
  question="A customer table uses email as its PRIMARY KEY. Marketing now wants users to be able to change their email. What is the core problem, and the standard fix?"
  choices={[
    { label: "The PK is a mutable natural key — changing it cascades through every foreign key that references it, which is operationally expensive and often impossible at scale. Fix: surrogate PK (BIGSERIAL or UUIDv7) plus UNIQUE NOT NULL on email.", correct: true },
    { label: "Email is too long to index efficiently — switch to a hash of the email as the PK.", misconception: "Index width is not the issue; a TEXT email indexes fine. The problem is mutability: a changing PK must cascade through every referencing FK. A hash is still derived from the mutable email." },
    { label: "Nothing is wrong — just run UPDATE customers SET email = ... and Postgres updates the references automatically.", misconception: "Postgres only cascades a PK change if every FK is declared ON UPDATE CASCADE, and even then the rewrite touches every child row under lock. The durable answer is to never put a mutable value in the PK." },
    { label: "Add a second UNIQUE constraint on email and keep email as the PK.", misconception: "A duplicate uniqueness guarantee does not remove the mutability problem — email is still the PK, so changing it still cascades. You must demote email out of the PK role entirely." },
  ]}
/>

<Quiz
  id="01-relational-model-choice-2"
  lessonSlug="01-relational-model"
  lang="en"
  question="A table stores `orders(order_id, customer_id, customer_city)` where `order_id` alone is the primary key. Which normal form does it violate, and what breaks in production?"
  choices={[
    { label: "3NF — customer_city depends transitively on customer_id, not on order_id. When a customer moves, some historical orders show the old city and some the new one, so two rows disagree about the same fact.", correct: true },
    { label: "2NF — customer_city partially depends on a composite key.", misconception: "2NF partial dependency only applies to composite primary keys. Here order_id alone is the PK, so there is no partial-key dependency to violate." },
    { label: "1NF — customer_city holds a non-atomic value.", misconception: "A city name is a single atomic value. 1NF is about repeating groups and multi-valued cells, not transitive dependencies." },
    { label: "None — caching the city on the order is a valid denormalization.", misconception: "It is only valid denormalization if the duplicate is reconciled by something (trigger, job) AND the intent is a point-in-time snapshot. Here it is an unreconciled transitive dependency, which is exactly the 3NF failure mode." },
  ]}
/>

<Quiz

  lessonSlug="01-relational-model"
  lang="en"
  question="A marketplace needs free-form product tags supporting four queries: show a product's tags, list all products with tag X, count products per tag, and rename a tag globally. Which storage shape satisfies all four cheaply at scale?"
  choices={[
    { label: "A side table: a tags catalogue (id, name UNIQUE) plus a product_tags join table with composite PK (product_id, tag_id), FKs, and an index on tag_id. It queries from both directions, aggregates by tag, and renames in one UPDATE.", correct: true },
    { label: "A TEXT[] array column on products with a GIN index.", misconception: "The array handles 'tags on this product' and (via GIN) 'products with tag X', but aggregating per tag is expensive and a global rename means rewriting every row that contains the tag. It fails two of the four queries at scale." },
    { label: "A JSONB column holding the tag list, indexed with GIN.", misconception: "JSONB is strictly worse than the array here — higher parse overhead, no uniqueness or FK to a canonical tag list — and still cannot cheaply count-per-tag or rename globally." },
    { label: "Denormalize the tag names onto every order that references the product so reports are fast.", misconception: "That duplicates the tag fact across orders with no reconciliation, recreating the 3NF disagreement problem, and still does not give you a count-per-tag or single-row rename." },
  ]}
/>

  question="A senior engineer proposes disabling foreign keys across a typical B2B SaaS schema (tables under 100M rows) to 'improve write performance'. How should you read this proposal?"
  choices={[
    { label: "Reject it — disabling FKs is justified only under specific conditions (cross-shard relationships, multi-million-row cascades holding locks, FK validation blocking online DDL).     { label: "Accept it — FKs are a known major write bottleneck and removing them is standard practice for performance.", misconception: "The FK check is ~5-50 μs per row, negligible for a sub-100M-row SaaS.     { label: "Accept it — application code enforces the same integrity, so the FK is redundant.", misconception: "Application-level enforcement is implemented inconsistently and breaks during refactors and across services. The FK is the single boundary every caller gets for free." },
    { label: "Accept it only if you add an index on every FK column to compensate.", misconception: "An FK-column index helps query performance, not FK-check cost, and it does not address the real question of whether disabling the constraint is warranted at this scale. It is not." },

<Quiz

  lessonSlug="01-relational-model"
  lang="en"
  question="`SELECT * FROM events ORDER BY created_at DESC LIMIT 100` on a 50M-row table with an index on created_at is 3× slower than expected. The table has an 8KB-average JSONB payload column. Most likely cause and fix?"
  choices={[
    { label: "Each of the 100 returned rows triggers a TOAST side-table fetch for the wide payload, because SELECT * reads every TOASTed column. Fix: select only the columns you need (id, event_type, created_at) so the payload is never fetched.", correct: true },
    { label: "The ORDER BY ... DESC defeats the B-tree index, forcing a sequential scan.", misconception: "A B-tree on created_at supports a reverse index scan for ORDER BY ... DESC LIMIT 100; the scan is cheap. The cost is the per-row TOAST fetch from SELECT *." },
    { label: "A 50M-row table always sequential-scans regardless of the index.", misconception: "A selective index returning 100 rows uses an index scan on any table size. Selectivity, not row count, drives the planner's choice here." },
    { label: "JSONB columns cannot be returned in an ORDER BY query, so Postgres falls back to a slow path.", misconception: "JSONB can be returned in any query. There is no special slow path; the extra cost is fetching the TOASTed payload for each row." },
  ]}
/>

    { label: "Add an updatable VIEW aliasing user_name to display_name and call it done.", misconception: "A view eases reads, but writes through it need INSTEAD OF triggers or updatable-view rules, and it is only a transitional bridge — not a substitute for the full expand-then-contract migration." },
    { label: "Take a 2-hour maintenance window and rename in place.", misconception: "Downtime may be acceptable for an internal tool, but the prompt requires zero downtime, and the window still forces all consumers to deploy updated code simultaneously. <Recap lang="en">
The through-line across the unit is one decision discipline: put identity in an immutable surrogate key and guard business keys with UNIQUE NOT NULL; normalize to 3NF so no two rows can disagree, and denormalize only with explicit reconciliation; reach for a side table the moment you query from the other direction; keep FK constraints unless a measured sharding or cascade constraint forces otherwise; remember that physical storage (TOAST, page layout) makes SELECT * expensive on wide rows; and change a live schema with expand-then-contract, never an in-place break. Every answer here resolves back to "design for the queries and the lifetime, not the first insert."
</Recap>
