You go above it to BCNF only when a table has multiple overlapping candidate keys, which is rare in production. You go below it via deliberate denormalization — a stored aggregate refreshed by a trigger, a wide read model fed from normalized sources, a point-in-time snapshot like the unit price captured on an order line — but only when a read path is measured as the bottleneck and the duplicate is reconciled by something explicit. And when you need to query a many-to-many relationship from both directions, aggregate across it, rename a shared value globally, or enforce uniqueness between two entities, use a side table — product tags become a tags catalogue plus a product_tags join table with a composite PK and FKs, not an array or JSONB blob. Disabling FKs is defensible only under specific scale conditions: the data is sharded and the relationship crosses shard boundaries (FKs cannot span shards), a cascade would create a multi-million-row transaction holding locks for minutes, or the FK validation pass during an online column-type change is the operational bottleneck. When a value would push a row over roughly 2KB, TOAST first compresses it (LZ4 or pglz); if it is still oversized, it slices the value into ~2KB chunks stored in a separate TOAST side table, leaving an 18-byte pointer in the main row. The two implications: (1) reading a TOASTed column requires an extra fetch from the TOAST table, so SELECT * on a table with a large JSONB/TEXT/BYTEA column fetches every wide value — selecting only the columns you need keeps hot list queries cheap; (2) updating a TOASTed value rewrites the side-table chunks, so updates to large payloads are more expensive than updates to narrow typed columns. It is required because a single RENAME COLUMN, though instant and metadata-only, atomically breaks every consumer still referencing the old name — application code, ORM models, views, BI dashboards, analytics scripts. On a large table shared by many services that cannot all deploy simultaneously, that is an immediate outage.
