The planner picks the cheapest plan using row estimates fed into the cost formula at every level, and those estimates also decide the choice of plan above. A bad estimate at a leaf node cascades upward: the join above picks the wrong algorithm because it expects a smaller input, the sort above picks the wrong method, and the Limit above does not push down. A 10x gap is suspicious; a 1000x gap is usually why a 50ms query takes 8 minutes. So you read the plan node by node, compute actual / estimated, and trace the largest gap to its predicate. Cost values are in arbitrary units, not milliseconds, so the estimate-vs-actual gap — not the cost number — is where you start." },
    { q: "How does the planner choose among Seq Scan, Index Scan, Bitmap Heap Scan, and Index Only Scan?", a: "By cost, driven by selectivity and the cost constants. Seq Scan reads the whole heap sequentially (relpages x seq_page_cost + reltuples x cpu_tuple_cost) and wins when the predicate is unselective — most rows match. Index Scan walks the B-tree and does one random heap fetch per matching row (matching_rows x random_page_cost, default 4.0), so it wins only when few rows match, roughly under 5-15% of the table. Bitmap Heap Scan builds a sorted TID bitmap from the index and reads the heap in physical order, turning scattered random reads into a near-sequential pass — it wins in the middle range. Index Only Scan skips the heap entirely when all needed columns are in the index and the Visibility Map marks the pages all-visible; a high Heap Fetches count means the VM is stale. On SSD, set random_page_cost = 1.1 so the planner correctly prefers index access for selective predicates." },
    { q: "Explain the row-estimate cascade and why it makes Nested Loop catastrophic.", a: "Nested Loop costs outer_rows x inner_cost_per_lookup, so it is cheap only when the outer side is small and the inner has an index. If the planner underestimates the outer side — say 50 rows when reality is 520,000 — it chooses Nested Loop, and the inner index scan runs 520,000 times instead of 50: a four-orders-of-magnitude blowup. The diagnostic is the loops count on the inner node. The wrong algorithm is the symptom; the wrong outer-side estimate is the cause. Underestimates come from stale statistics, correlated columns the planner assumes are independent, or non-sargable predicates that prevent an index from narrowing the row count. Fix the estimate (ANALYZE, extended statistics, sargable rewrite) and the planner picks Hash Join or Merge Join on its own." },
    { q: "Why does the planner's independence assumption fail on correlated columns, and what fixes it?", a: "For WHERE A='x' AND B='y' the planner estimates P(A) x P(B), assuming the columns are statistically independent. When A determines B — country determines region, zip determines city — the joint probability is closer to the more selective column's probability alone, so multiplying underestimates selectivity, sometimes by 1000x. Raising default_statistics_target or per-column SET STATISTICS only refines single-column histograms and MCV lists; the planner still multiplies. CREATE STATISTICS (dependencies, mcv) ON col1, col2 FROM tbl measures the functional dependency factor and stores the most-common multi-column tuples during ANALYZE, replacing the independence assumption for that group. Use dependencies when one column implies another, mcv for frequent specific combinations, and ndistinct for accurate GROUP BY cardinality. Verify with EXPLAIN ANALYZE that estimated now tracks actual within 2x." },
    { q: "What is the generic-plan trap on prepared statements, how do you detect it, and how do you fix it?", a: "A parameterised query is planned with the actual parameters for its first 5 executions (custom plans). After the 5th, Postgres compares the average custom-plan cost to a parameter-agnostic generic plan; if the generic cost is within roughly 10% of the average, it switches to the generic plan permanently. For skewed parameter distributions — a workspace_id where some workspaces hold 8% of rows and others 0.01% — the generic plan is tuned for a typical parameter and catastrophically wrong for outliers, producing bimodal latency: low mean, huge stddev_exec_time. Detect it with high stddev_exec_time in pg_stat_statements and EXPLAIN (GENERIC_PLAN) (PG 16+) on the prepared form. Fix with plan_cache_mode = 'force_custom_plan' on the role so every execution replans with the real parameters; the extra 0.4-2ms of planning is negligible against multi-second tail latency." },
