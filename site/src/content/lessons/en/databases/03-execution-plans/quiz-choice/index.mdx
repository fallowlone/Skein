  question="A predicate filters on WHERE country='US' AND region='CA' AND status='shipped'. The planner predicts 500 rows; the node actually emits 50,000. Single-column statistics are fresh. What fixes the estimate?"
  choices={[
    { label: "CREATE STATISTICS (dependencies, mcv) ON country, region, status; then ANALYZE. Country determines region, so the planner's independence assumption multiplies probabilities that are not independent.", correct: true },
    { label: "ALTER TABLE ... ALTER COLUMN region SET STATISTICS 1000; then ANALYZE.", misconception: "A higher per-column target gives finer single-column histograms and MCV lists, but the planner still multiplies P(country) x P(region).     { label: "Add a composite index on (country, region, status).", misconception: "An index changes execution paths, not the planner's multi-column row-estimate model. The estimate stays wrong until extended statistics teach it the correlation." },
    { label: "Raise default_statistics_target globally to 1000.", misconception: "Same problem at the global level: finer per-column stats, but cross-column correlation is still unmodeled. CREATE STATISTICS is the only tool that captures functional dependencies." },

<Recap lang="en">
The through-line across the unit is one reading discipline: at every plan node compare rows-estimated to actual rows, find where the gap opens, and trace it upward — a bad estimate cascades into wrong scan choices, wrong join algorithms, and wrong sort methods above it. Scan choice follows selectivity, join choice follows the outer-side estimate, and the durable fixes attack the cause: fresh statistics via ANALYZE, extended statistics for correlated columns, force_custom_plan for skewed prepared statements, and SSD-tuned cost constants. Forcing an algorithm or rebuilding an index treats the symptom; fixing the estimate corrects the whole plan.
</Recap>
