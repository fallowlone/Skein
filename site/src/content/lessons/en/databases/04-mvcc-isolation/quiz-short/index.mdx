The rule, applied per tuple with no locks: a tuple is visible if its t_xmin is committed and not in xip (the inserting transaction is in the past relative to the snapshot), AND its t_xmax is zero, rolled back, or in xip (the deleting transaction has not committed relative to the snapshot). REPEATABLE READ takes one snapshot at the first statement and holds it for the whole transaction, so repeated reads are stable and phantoms cannot appear (Postgres RR is snapshot isolation, stronger than the SQL standard's RR). The cost: RR raises SQLSTATE 40001 if a concurrent transaction updated a row it also writes, and the application must retry the whole transaction." },
    { q: "Distinguish a lost update from write skew, and name the fix for each.", a: "A lost update is two transactions writing the SAME row based on a value they both read; the second write clobbers the first (final stock 9 instead of 8). Fix at READ COMMITTED with SELECT ... FOR UPDATE or an optimistic UPDATE ... WHERE col = old_value; REPEATABLE READ also catches it via 40001. Write skew is two transactions reading the same SET, each writing a DIFFERENT row, jointly breaking an invariant the set was meant to protect (both doctors go off-call). REPEATABLE READ allows it; the fix is SERIALIZABLE (SSI), which tracks the read set, or rewriting the logic so each transaction modifies a row it also read (e.g. a guard row)." },
    { q: "What is the global oldest xmin, and why does a long transaction or orphan replication slot cause unbounded bloat through it?", a: "The global oldest xmin is the minimum backend_xmin across all active sessions, also constrained by replication-slot xmin values — the oldest snapshot anything in the cluster still holds. Autovacuum may only reclaim dead tuples whose deletion is older than this value, because anything newer might still be visible to that oldest snapshot. A 6-hour analytics query or an orphan logical/physical replication slot holds a very old xmin, so every dead tuple created since pins on disk; autovacuum logs 'dead but not yet removable' and the table grows without bound until the transaction ends or the slot is dropped. Defend with idle_in_transaction_session_timeout and slot-lag alerts." },
    { q: "What two conditions make an UPDATE a HOT update, and why does it matter for write cost?", a: "Both must hold: (1) no indexed column changes, and (2) the new tuple fits on the same heap page as the old. When they do, the new version is a heap-only tuple — the index keeps pointing at the original tuple and the t_ctid chain carries the lookup, so zero index entries are written instead of one per index. On update-heavy tables this saves 30–70% WAL. The chain breaks when an indexed column changes or the page is full (fillfactor exhausted), after which every subsequent update pays full index cost; set fillfactor below 100 to reserve same-page headroom and keep the HOT ratio (n_tup_hot_upd / n_tup_upd) above ~80%." },

At commit it looks for a dangerous structure — a cycle of rw-antidependencies between transactions — and aborts one participant with SQLSTATE 40001 'could not serialize access due to read/write dependencies'. The check is conservative: a cycle is sufficient but not necessary for a non-serializable schedule, so SSI has false positives (safely aborting some transactions that would have committed) but never false negatives. A healthy false-positive rate is 0.1–1%; above 5% means predicate locks are coarsening under memory pressure (raise max_pred_locks_per_transaction) or the workload has genuine conflict needing partitioning." },

<Recap lang="en">
If you reconstructed each answer from memory, you hold the unit's spine: a snapshot plus a tuple header is the entire visibility mechanism; the isolation level you pick decides which anomalies you own — RC leaves lost updates to the app, REPEATABLE READ stabilises reads and catches concurrent row updates but allows write skew, SERIALIZABLE adds SSI to catch write-skew cycles via predicate-lock dependencies; HOT updates cut write cost when no indexed column changes and the page has room; and the global oldest xmin is the lever behind almost every bloat incident — a long transaction or orphan slot pins it and autovacuum goes quietly futile.
