  question="A scroll handler animates a list item by writing element.style.top each frame, and the page judders on a mid-range phone. A colleague says it is on the compositor, so it must be the GPU. Why are they wrong?"

    { label: "The GPU is genuinely the bottleneck; scrolling is always a composite operation.", misconception: "Off-main-thread scroll handles the viewport translate, but writing top inside a handler is a layout-invalidating mutation that runs on the main thread, not the GPU." },
    { label: "top and transform cost the same; the jank is just the phone being slow.", misconception: "transform on a promoted layer is composite-only; top invalidates layout. The cost difference is an order of magnitude, which is exactly why the phone janks on one and not the other." },
    { label: "The handler should be wrapped in requestAnimationFrame, which moves the work to the GPU.", misconception: "rAF batches the invocation to the frame boundary but still runs on the main thread; it does not move layout-invalidating writes off the main thread." },
  ]}

    { label: "The fix is to lower CLS, since INP and CLS track the same problem.", misconception: "CLS measures unexpected layout shift; INP measures input-to-next-paint latency. They are different vitals; the forced sync layout in the handler is an INP problem." },

<Recap lang="en">
Across the unit the through-line is one decision chain: the property you change picks the stage you invalidate (transform = composite, color = paint, top/width = layout), dirty bits flow downstream, and containment or content-visibility caps the blast radius. Compositor layers are cheap to move but expensive to hold, the overlap rule promotes neighbours you never asked for, layout thrash comes from reading geometry after a write, and INP plus LoAF close the loop from production telemetry back to a specific stage. Predict the stage, rank the fix, then reach for the compositor.
</Recap>
