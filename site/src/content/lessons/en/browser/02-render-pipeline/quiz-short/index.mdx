    { q: "What does the overlap rule do, and why does one will-change promote a dozen neighbours?", a: "A compositor layer is a pre-painted GPU bitmap. To keep correct stacking, any element that paints on top of a promoted layer must also be promoted (or squashed into a shared layer) — otherwise the promoted layer would draw over an element that is supposed to sit above it. So a single will-change: transform on a card mid-feed forces the browser to promote overlapping siblings it never asked you about. Each layer costs width × height × 4 bytes of GPU memory, so implicit promotions can quietly exhaust a mobile GPU budget (~256 MB) and trigger tile eviction." },
    { q: "Explain forced synchronous layout and the two-pass fix.", a: "Layout is dirty-flag driven: the browser batches style writes and flushes them only when fresh geometry is demanded. Reading a geometry property (offsetWidth, offsetTop, getBoundingClientRect, scrollTop) after a style write forces an immediate layout flush. In a loop that interleaves read-then-write, this runs one full layout per iteration — N rows, N layouts, blocking the main thread for N × layout_cost. The fix is structural: a two-pass batch — read every geometry value into an array in pass one, then apply all writes in pass two — so the browser flushes layout once. Wrapping the loop in rAF does not help: rAF moves the invocation boundary, not the invalidation boundary." },
    { q: "What is the order of events inside one frame, and why does rAF differ from ResizeObserver?", a: "Per the HTML spec: input events, then due timers (setTimeout/setInterval), then microtasks drain to empty, then requestAnimationFrame callbacks, then ResizeObserver/IntersectionObserver, then style + layout, then paint, then composite, then yield to vsync. rAF runs before style/layout, so a write there is followed by exactly one layout pass — but a geometry read there forces a flush. ResizeObserver fires after layout but before paint, so you can read a freshly computed size and react without a second forced layout. A self-scheduling microtask loop starves rendering because the microtask queue must drain to empty before the frame can reach style/layout." },
    { q: "How do INP and LoAF close the production loop, and what two pipeline problems usually cause a poor INP?", a: "INP (Interaction to Next Paint, a Core Web Vital since March 2024) measures the latency from a user input to the next paint that visibly responds — what the user actually felt, captured by RUM on real devices. LoAF (Long Animation Frame Timing) reports any frame over 50 ms with a breakdown of what dominated (blocking JS, render, forced layout) — the diagnostic. A poor INP (>200 ms p75) almost always traces to one of two pipeline problems: a long JS task in the input handler delaying rAF, or a forced synchronous layout from reading geometry inside the handler. LoAF attributes the slow frame; INP is the metric you defend." },
