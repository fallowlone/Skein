## Snippet 1 — the reorderable list

```jsx
function TodoList({ todos }) {
  // todos can be reordered by drag, and each row has an
  // uncontrolled <input> the user types notes into
  return (
    <ul>
      {todos.map((todo, i) => (
        <li key={i}>
          <span>{todo.title}</span>
          <input type="text" placeholder="notes…" />
        </li>
      ))}
    </ul>
  );
}
```

## Snippet 2 — work in the function body

```jsx
function Chart({ points }) {
  // build a derived dataset and log an analytics event
  const series = expensiveTransform(points);
  analytics.track('chart_rendered', { count: series.length });

  return <svg>{series.map(p => <Dot key={p.id} {...p} />)}</svg>;
}
```

    { label: "expensiveTransform(points) is the bug — heavy computation is forbidden in render.", misconception: "Pure computation in render is allowed; if it is slow, you memoise it with useMemo, but it is not a correctness bug. The correctness bug is the impure analytics call, which produces observable effects on every replay." },
    { label: "Spreading {...p} onto Dot is the bug — it breaks reconciliation.", misconception: "Spreading props is fine and does not affect reconciliation identity, which is driven by the key. It has nothing to do with the render-purity violation." },
    { label: "There is no bug; React guarantees each component renders exactly once per update.", misconception: "React 18 explicitly does not guarantee one call per update — render can be replayed or discarded. That is precisely why side effects in the function body are unsafe." },

## Snippet 3 — the priority split

```jsx
function Search({ allItems }) {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState(allItems);
  const [isPending, startTransition] = useTransition();

  function onChange(e) {
    startTransition(() => {
      setQuery(e.target.value);                          // (A)
      setResults(filter(allItems, e.target.value));      // (B)
    });
  }
  return <><input value={query} onChange={onChange} />{isPending && <Spinner/>}<List items={results}/></>;
}
```

<Quiz
  id="05-react-fiber-code-3"
  lessonSlug="05-react-fiber"
  lang="en"
  question="Typing feels laggy even though the expensive filter is inside startTransition. What is wrong with this priority split?"
  choices={[
    { label: "Line (A) — the input's own value — is inside startTransition, so the query update runs at transition priority and can be deferred or interrupted, making the field lag behind the keystroke. Only the expensive (B) belongs in the transition; setQuery must stay a synchronous update outside it so the input reflects each keystroke immediately.", correct: true },
    { label: "useTransition cannot wrap two setState calls; split them into two transitions.", misconception: "startTransition can wrap any number of updates. The problem is which updates belong there: the urgent input value must not be deferred, while the expensive list update should be." },
    { label: "The filter should be wrapped in useDeferredValue instead — startTransition does not time-slice.", misconception: "startTransition does put the update in the time-sliced transition lane. The lag is not about which API; it is that the urgent query update was wrongly placed in the low-priority lane." },
    { label: "isPending must be checked before calling setResults or the spinner never shows.", misconception: "isPending is derived by React from the pending transition; you do not gate setResults on it. The spinner renders fine — the actual defect is the deferred input value." },
  ]}
/>

## Snippet 4 — the defeated bailout

```jsx
const Row = React.memo(function Row({ item, onSelect }) {
  return <li onClick={() => onSelect(item.id)}>{item.label}</li>;
});

function List({ items, onSelect }) {
  return (
    <ul>
      {items.map(item => (
        <Row key={item.id} item={item} onSelect={() => onSelect(item.id)} />
      ))}
    </ul>
  );
}
```

<Quiz
  id="05-react-fiber-code-4"
  lessonSlug="05-react-fiber"
  lang="en"
  question="Every Row re-renders whenever List re-renders, even though React.memo wraps Row and the items are unchanged. Why, and what is the minimal fix?"
  choices={[
    { label: "onSelect={() => onSelect(item.id)} creates a fresh arrow function for every Row on every List render. React.memo compares props with Object.is, and a new function is never equal to the last, so the bailout never fires. Fix: pass the stable onSelect down and move the item.id binding into Row's own click handler, so Row receives the same function reference each render.", correct: true },
    { label: "React.memo does not work on components that render an <li>; it only memoises leaf text.", misconception: "React.memo works on any function component regardless of what it renders. It is being defeated by the unstable inline arrow prop, not by the element type." },
    { label: "key={item.id} forces a re-render of every row; remove the key.", misconception: "The key is correct and required — it is what gives each row stable identity. Removing it would cause warnings and worse reconciliation. The defeat is the inline function prop, not the key." },
    { label: "items is a new array each render, so memo cannot help.", misconception: "Row is memoised on its own props (item, onSelect), not on the parent's items array. Even if items is new, each item reference can be stable; the real culprit is the fresh onSelect arrow created per row." },
  ]}
/>

<Recap lang="en">
Four fiber-level reads: an index key follows position, so uncontrolled state on a fiber drifts to the wrong item on reorder — use a stable id; a side effect in the function body runs an unpredictable number of times under replay — move it to useEffect or the event; the urgent input value must stay out of startTransition while only the expensive update goes in; and an inline arrow prop is a fresh reference every render that silently defeats React.memo. Read the code, predict how the reconciler treats it, fix the identity or the reference before reaching for any other lever.
</Recap>
