  question="A component increments a module-level counter in its function body. It worked in React 17; in React 18 StrictMode the counter is double what you expect, and in production under load it occasionally triple-counts. What is the root cause?"
  choices={[
    { label: "The render phase is not pure. React 18 can replay, pause, or discard a render, so a side effect in the function body runs an unpredictable number of times; StrictMode double-invokes to surface exactly this. Move the mutation to useEffect or an event handler.", correct: true },
    { label: "A race condition between two threads incrementing the counter.", misconception: "React's reconciler runs on the single main thread — there is no second thread racing. The non-determinism comes from the render phase being replayable, not from concurrency across threads." },

    { label: "The counter needs to be wrapped in useState to be safe.", misconception: "useState would not fix a side effect that fires during render; the fix is to stop performing the effect in the function body at all. Render must be pure regardless of where the value is stored." },
  ]}

  lang="en"
  question="A render is 30 ms in when a higher-priority keystroke arrives. React abandons the in-progress workInProgress tree and starts over. Why does discarding the half-built tree cost nothing visible?"
  choices={[
    { label: "The workInProgress tree never committed, so the current tree — the one matching what is on screen — is untouched. No DOM mutation happened, so there is nothing to revert. Double buffering is what makes a thrown-away render free.", correct: true },
    { label: "React checkpoints the partial tree to memory and rolls it back transactionally.", misconception: "There is no rollback transaction. The cost is zero because nothing was applied — commit, not render, is what touches the DOM, and commit never started." },
    { label: "The alternate pointer lets React replay and undo the mutations cheaply.", misconception: "The alternate pointer links each fiber to its twin for cheap cloning and bailout — it is not an undo log. There are no mutations to undo because the render phase produces no DOM changes." },
    { label: "It does cost — the user briefly sees a half-rendered frame.", misconception: "The user never sees workInProgress. Only the current tree is painted, and it stays consistent because the abandoned tree is purely in-memory." },
  ]}
/>

  question="A search input filters a 5,000-row list. Typing is janky. You wrap the filtered-list setState in startTransition. Typing now feels instant — but why does the list itself not freeze the page when it finally renders?"
  choices={[
    { label: "The transition update runs in the transition lane: time-sliced into ~5 ms chunks with a shouldYield check between them, and interruptible by any keystroke.     { label: "startTransition moves the list render onto a background thread.", misconception: "There is no background thread — React renders on the main thread. startTransition lowers the update's priority so it is interruptible and time-sliced, not parallelised." },

    { label: "The list render now happens in the commit phase, which is faster.", misconception: "Time-slicing applies to the render phase, not commit. Commit is always atomic and uninterruptible; what startTransition makes interruptible is the render work, not the commit." },

<Recap lang="en">
The unit's through-line is one machine seen from six angles: render computes the diff (interruptible, must be pure) and commit applies it (atomic); the fiber double-buffer makes interruption free; reconciliation keys bind state to identity, not position; lanes and time-slicing keep urgent input ahead of expensive work; the bailout — gated by Object.is referential stability — keeps large trees cheap; and useSyncExternalStore keeps external stores from tearing under concurrent rendering. Every production symptom here resolves back to one of those six levers.
</Recap>
