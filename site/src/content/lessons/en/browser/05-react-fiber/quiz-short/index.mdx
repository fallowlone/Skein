The commit phase applies the queued DOM mutations; pausing mid-commit would leave the page in a half-updated, internally inconsistent state the user could observe. So commit runs as one synchronous, uninterruptible burst. This split — interruptible render, atomic commit — is the spine of the whole unit: time-slicing and transitions exploit the interruptible render, while keeping the commit small (virtualisation, fewer mutations) is the lever for commit-phase performance." },
    { q: "What is the fiber double-buffer, and why does it make an abandoned render free?", a: "React always holds two fiber trees. The current tree matches what is painted on screen; the workInProgress tree is the update being built, cloned from current via each fiber's alternate pointer so unchanged subtrees are reused by reference. React mutates only workInProgress, never current, so the on-screen tree is never observed half-updated. When a render commits, the two swap roles. When a higher-priority update interrupts, React simply discards the in-progress workInProgress tree: because it never committed, no DOM mutation occurred, so there is nothing to revert and the cost is zero. That is what lets time-slicing throw away and restart renders cheaply." },
    { q: "How does reconciliation reduce O(n³) tree diffing to O(n), and what role do keys play?", a: "A general tree diff is O(n³); React makes it O(n) with two heuristics. First, same element type means update the existing fiber in place (state preserved); a different type means tear down the whole subtree and rebuild fresh (state destroyed) — React never diffs across type boundaries. Second, within a list React matches new children to old fibers by key, building a key→fiber map and pairing by identity rather than position. A fiber carries everything stateful — useState values, refs, uncontrolled DOM state, the DOM node itself — so a correct key binds that state to the right logical item. key={index} is positional, so any reorder, insert, or delete shifts which fiber an item gets, silently corrupting uncontrolled state while controlled props (re-passed fresh) still look right." },
    { q: "Explain the lane model and how time-slicing keeps input responsive.", a: "React 18 assigns every update a lane — a priority bucket in a 31-bit bitmask. Discrete input (click, keypress) lands in a synchronous lane and renders immediately and blocking, because the user is waiting on it; ordinary updates use the default lane; work wrapped in startTransition or read via useDeferredValue lands in the transition lane, which is interruptible; idle is lowest. For concurrent (non-urgent) renders, the scheduler time-slices: after ~5 ms of reconciliation it checks shouldYield(), and if true it posts a continuation task via MessageChannel and lets the browser run input handlers and painting before resuming from the stored fiber pointer. A 50 ms render becomes ten 5 ms slices interleaved with browser work; when a keystroke arrives mid-transition, React abandons that render, handles the keystroke at sync priority, then restarts the transition." },
    { q: "What is the bailout, what gates it, and why does an inline object as a prop defeat it?", a: "When React reaches a fiber during render it checks: did props change (Object.is per prop), did state change, is there a pending context update it consumes? If none, it bails out — clones the fiber from its alternate, reuses the entire child subtree by reference, and never calls the component function. Re-rendering a parent does not force children to re-render; it offers them the chance to bail out, and referential stability is what lets them take it. React.memo makes a child's render conditional on Object.is-equal props. An inline object, array, or arrow function created in JSX is a fresh reference every render, so Object.is always reports a change and the bailout never fires — even with React.memo. useMemo and useCallback exist to preserve those references; the React Compiler automates the same memoisation at build time without changing the mechanism." },
    { q: "What is tearing, why does only concurrent rendering expose it, and how does useSyncExternalStore prevent it?", a: "Tearing is a committed UI that is internally inconsistent: some components rendered with an old value of an external store and others with a new one. It only appears under interruptible rendering, because a concurrent render runs in slices and an external store can mutate between two slices — early components read the old value, later ones read the new one. React-internal state cannot tear, because React controls exactly when it changes; external stores can, because React does not. useSyncExternalStore gives React a subscribe and a getSnapshot function. React reads the snapshot, and if it detects the snapshot changed during the concurrent render, it restarts the render so every component in one commit observed the same value. Every serious React 18 state library (Redux, Zustand, Jotai) routes through it for this reason." },
