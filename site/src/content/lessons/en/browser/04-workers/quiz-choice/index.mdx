<Quiz

  lessonSlug="04-workers"
  lang="en"
  question="A teammate moves a slow React list re-render into a web worker to fix scroll jank, and nothing improves. Why, and what actually fixes it?"
  choices={[
    { label: "A worker has no DOM — React's commit phase mutates real nodes and can only run on the main thread. Move only the data derivation (filter/sort/aggregate) to a worker and return a small result; fix the commit by virtualising the list and time-slicing reconciliation.", correct: true },
    { label: "The worker is too slow to keep up with React's render loop.", misconception: "Speed is not the issue — the worker literally cannot touch the DOM. React's commit writes real elements, which only the main thread owns. Compute can move; the commit cannot." },
    { label: "React does not support running inside workers without a polyfill.", misconception: "There is no polyfill that gives a worker a DOM. The constraint is architectural: WorkerGlobalScope has no document. You move derivation off-thread and keep the commit on the main thread." },
    { label: "The worker needs OffscreenCanvas to render the list.", misconception: "OffscreenCanvas renders pixels, not a DOM list of elements. A virtualised React list is DOM nodes — the commit stays main-thread; only pure compute offloads." },
  ]}
/>

<Quiz
  id="04-workers-choice-2"
  lessonSlug="04-workers"
  lang="en"
  question="You postMessage a 40 MB Float32Array to a worker and the sending thread still freezes for ~40 ms before the worker even starts. Best fix?"
  choices={[
    { label: "Transfer the buffer: postMessage(arr, [arr.buffer]). Ownership moves in O(1), the sender's view detaches (byteLength becomes 0), and the ~40 ms structured-clone copy disappears.", correct: true },
    { label: "Serialise it to JSON first so the clone is cheaper.", misconception: "JSON.stringify of a 40 MB typed array is far slower than structured clone and produces a much larger string — it makes the block worse, not better." },
    { label: "Split it into 40 separate 1 MB postMessage calls.", misconception: "Total clone cost is the same 40 MB, now spread across 40 task hops with 40× the scheduling overhead. Transfer eliminates the copy entirely." },
    { label: "Use a SharedArrayBuffer so no copy happens.", misconception: "SAB also avoids the copy, but it is for concurrent shared access and needs COOP+COEP. If the sender hands the data off and stops using it, transfer is the simpler, header-free fit." },
  ]}
/>

<Quiz
  id="04-workers-choice-5"
  lessonSlug="04-workers"
  lang="en"
  question="A button triggers a 400 ms image job. Users click rapidly; the tab spawns a new worker per click, climbs to 400 MB, and gets killed on mobile. What is the right architecture?"
  choices={[
    { label: "A reusable worker pool sized to hardwareConcurrency − 1, with a bounded queue (backpressure) and priority routing — reuse threads, cap memory, and reject or drop work when the queue is full so callers can back off.", correct: true },
    { label: "Spawn the workers but call terminate() right after each result.", misconception: "Terminating after every job throws away the worker and forces a fresh 5–20 ms startup on the next click. A persistent pool amortises startup; per-job spawn-and-kill does not." },
    { label: "Move the work back to the main thread in 50 ms chunks.", misconception: "Chunking keeps input alive but the 400 ms still competes with rendering on one thread, and unbounded clicks still pile up. Pool + backpressure offloads the compute AND bounds the queue." },
    { label: "Raise the per-tab memory limit so 400 MB is acceptable.", misconception: "You cannot raise the mobile memory ceiling, and leaking workers is the real bug. Bound the worker count with a pool and cap the queue with backpressure." },
  ]}
/>

<Recap lang="en">
The through-line of the unit is one decision tree: pick the primitive by job — web worker for off-main-thread compute, service worker for the network proxy, SharedArrayBuffer for shared memory — then pay the right transport cost (clone for small data, transfer for large binary, SAB for concurrent access behind COOP+COEP). Around that, three traps recur: a worker cannot touch the DOM (so DOM mutation never offloads), a service worker waits before activating and is hard to recover when it breaks navigation, and pools need backpressure or they leak. None of the primitives fixes a main-thread DOM bottleneck — that work stays where the DOM lives.
</Recap>
