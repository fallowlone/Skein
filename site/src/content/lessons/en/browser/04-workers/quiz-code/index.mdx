## Snippet 1 — the clone that did not move

```js
// main.js — offloading a heavy image filter to a worker
const worker = new Worker('filter.js', { type: 'module' });
const pixels = new Uint8ClampedArray(width * height * 4); // ~32 MB

worker.postMessage({ pixels, width, height });   // (A)
applyOtherUiWork();                                // (B) runs ~32 ms late
```

## Snippet 2 — the buffer used after transfer

```js
// main.js
const buf = new Float32Array(1_000_000);
fillSamples(buf);

worker.postMessage(buf, [buf.buffer]);   // transferred
const sum = buf.reduce((a, x) => a + x); // (C) reads buf again
```

<Quiz
  id="04-workers-code-2"
  lessonSlug="04-workers"
  lang="en"
  question="What happens at line (C), and what does it tell you about transfer semantics?"
  choices={[
    { label: "buf is detached after the transfer — its byteLength is 0 and length is 0, so the reduce sees an empty array (or throws on access in strict paths). Transfer moves exclusive ownership; the sender must not touch the buffer afterward. If you still need the data, transfer is the wrong tool — use SharedArrayBuffer.", correct: true },
    { label: "buf still holds its values — transfer copies, so both sides keep a usable view.", misconception: "Transfer is the opposite of copy. It hands the underlying memory to the receiver and detaches the sender's view. There is no second usable copy on the sender." },
    { label: "Line (C) sums whatever the worker has written back so far.", misconception: "There is no shared memory here — transfer is a one-way ownership move, not a live shared view. The sender's buffer is simply detached and empty." },
    { label: "The reduce runs on the worker's thread automatically.", misconception: "reduce runs synchronously on the calling thread. The point is that the buffer it would read is detached, not relocated computation." },
  ]}
/>

## Snippet 3 — the install handler that loses its cache

```js
// sw.js
self.addEventListener('install', () => {
  caches.open('shell-v3').then(cache =>
    cache.addAll(['/index.html', '/app.4f3a1c.js'])
  );
});
```

<Quiz
  id="04-workers-code-3"
  lessonSlug="04-workers"
  lang="en"
  question="Under load this service worker sometimes activates with an empty or half-populated cache. What is the defect and the fix?"
  choices={[
    { label: "The install handler does not call event.waitUntil, so the browser can advance the lifecycle (or kill the idle worker) before the cache.addAll promise settles. Fix: install handler takes event and calls event.waitUntil(caches.open('shell-v3').then(c => c.addAll([...]))).", correct: true },
    { label: "addAll is not atomic, so partial caches are expected — retry on activate.", misconception: "addAll rejects as a unit if any request fails; partial population here comes from the unawaited promise, not addAll. Wrapping it in event.waitUntil keeps the worker alive until it settles." },
    { label: "shell-v3 collides with an older cache and gets cleared.", misconception: "Version-tagged names are exactly how you avoid collisions, and nothing deletes shell-v3 here. The bug is the missing waitUntil letting the worker advance early." },
    { label: "The asset URLs need to be relative, not absolute.", misconception: "Absolute same-origin paths cache fine. The non-determinism is the unawaited promise, fixed by event.waitUntil." },
  ]}
/>

## Snippet 4 — the OffscreenCanvas handoff

```js
// main.js
const canvas = document.querySelector('#viz');
const offscreen = canvas.transferControlToOffscreen();
worker.postMessage({ offscreen }, [offscreen]);

// later, on the main thread:
const ctx = canvas.getContext('2d');   // (D)
ctx.fillRect(0, 0, 100, 100);          // (E)
```

<Quiz
  id="04-workers-code-4"
  lessonSlug="04-workers"
  lang="en"
  question="The worker renders fine, but lines (D)–(E) on the main thread misbehave. What happens and why?"
  choices={[
    { label: "Control was transferred to the worker, so the canvas is detached on the main thread — getContext / draw calls throw (or no-op into nothing). OffscreenCanvas ownership is exclusive: once transferred, only the worker may draw. If both threads must draw, use two canvases.", correct: true },
    { label: "Both the worker and the main thread can draw into the same bitmap.", misconception: "The platform forbids two threads racing on one bitmap. transferControlToOffscreen makes ownership exclusive — the main thread can no longer draw into that canvas." },
    { label: "The main-thread draws are queued until the worker releases the canvas.", misconception: "There is no release-and-reclaim mechanism. Transfer is permanent for the canvas's lifetime; the main-thread context is simply unavailable." },
    { label: "getContext('2d') returns a fresh independent context for the main thread.", misconception: "After transferControlToOffscreen the element has no own rendering context to hand out — the worker owns the bitmap. You would need a separate canvas element." },
  ]}
/>

<Recap lang="en">
Every worker incident is read at the boundary, not in the algorithm: a by-value postMessage of a large buffer blocks the sender on a synchronous structured clone, so transfer the ArrayBuffer; a transferred buffer is detached on the sender, so never read it afterward (use SharedArrayBuffer if you must share); a service-worker install must wrap async cache population in event.waitUntil or the worker advances or dies early; and transferControlToOffscreen makes canvas ownership exclusive, so the main thread can no longer draw. Read the message and lifecycle handlers first — that is where the cost and the bugs live.
</Recap>
