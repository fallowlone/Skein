## Snippet 1 — the un-sized hero

```html
<!-- hero, the LCP element, injected after the article text -->
<section class="article">
  <p>Paragraph one of the article…</p>
  <img src="/hero.avif" class="hero" alt="Product hero" />
  <p>Paragraph two…</p>
</section>
```

```css
.hero { width: 100%; }   /* height auto, no intrinsic ratio known */
```

## Snippet 2 — the lazy hero

```html
<img
  src="/hero-2400.jpg"
  width="1200" height="800"
  loading="lazy"
  class="hero"
  alt="Product hero"
/>
```

    { label: "width/height force a re-layout that slows LCP.", misconception: "Dimensions prevent CLS and do not add LCP cost — they let the browser reserve space. The regression is loading='lazy', which delays the start of the hero's download." },

    { label: "Lazy loading speeds up the hero once it appears, so LCP cannot regress.", misconception: "Lazy loading does nothing to render speed; it delays the start of the load. On the LCP element that directly delays the metric." },

## Snippet 3 — the click handler

```js
button.addEventListener('click', () => {
  const filtered = hugeList.filter(matchesQuery);  // ~180 ms, 50k items
  renderResults(filtered);                          // re-renders the list
  highlightActiveTab();                             // tiny DOM update
});
```

    { label: "Input delay — the thread was busy when the tap arrived.", misconception: "The stem says the thread is idle at tap time, so input delay is near zero. The 180 ms cost is inside the handler — processing time — not a queue delay." },
    { label: "Presentation delay — the re-render is the whole cost.", misconception: "The re-render contributes to presentation delay, but the dominant 180 ms is the synchronous filter in the handler (processing time). Move that off the critical path first." },
    { label: "Nothing is wrong; 210 ms is good INP.", misconception: "Good INP is ≤200 ms at p75; 210 ms is over the threshold. And a 180 ms synchronous handler is a clear, fixable processing-time problem." },

```
[INP] value: 38 ms  rating: good
[CLS] value: 0.02  rating: good
```

<Recap lang="en">
Every vitals regression is read in code or an attributed log: an img without width/height is a CLS shift; loading='lazy' on the hero is a self-inflicted LCP load-delay regression; a heavy synchronous handler is INP processing time you move off the critical path with startTransition or scheduler.yield; and a web-vitals line's phase split tells you which LCP phase to fix and which fix would be wasted. Read the attribution first, fix the dominant phase or part, then re-measure to confirm.
</Recap>
