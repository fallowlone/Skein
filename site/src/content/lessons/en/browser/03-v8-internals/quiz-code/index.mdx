## Snippet 1 — the late property

```js
class Point {
  constructor(x, y) {
    this.x = x;
    this.y = y;
  }
}

function build(coords) {
  const out = [];
  for (const c of coords) {
    const p = new Point(c.x, c.y);
    if (c.label) p.label = c.label;   // only sometimes
    out.push(p);
  }
  return out;
}

// later, in a hot loop:
function sumX(points) {
  let s = 0;
  for (const p of points) s += p.x;   // the hot IC site
  return s;
}
```

## Snippet 2 — the dictionary trap

```js
function makeConfig(overrides) {
  const cfg = { host: 'localhost', port: 8080, retries: 3 };
  for (const key of Object.keys(overrides)) {
    cfg[key] = overrides[key];
  }
  delete cfg.retries;          // "clean up" an unused default
  return cfg;
}

function readPort(cfg) {
  return cfg.port;             // hot path, called per request
}
```

  choices={[
    { label: "delete forces cfg into dictionary mode — a hashmap-backed layout where every property read, including cfg.port, takes ~50–100 cycles through a generic lookup instead of a fixed-offset load. Fix: assign cfg.retries = undefined (or omit it) instead of delete.", correct: true },
    { label: "delete just frees a little memory and has no effect on readPort.", misconception: "The tiny memory saving is dwarfed by the cost: delete drops the object out of fast-property mode permanently, so every subsequent read of any property goes through the slow generic path." },
    { label: "delete makes readPort faster because cfg now has fewer properties to scan.", misconception: "Fast-property objects read at a precomputed offset regardless of property count; there is no scan. delete replaces that with a hashmap lookup, which is strictly slower." },
    { label: "The dynamic Object.keys loop is the only problem; delete is fine.", misconception: "The keyed assignment loop can churn hidden classes, but delete is the decisive defect: it tips cfg into dictionary mode, from which V8 cannot recover without a fresh object." },
  ]}

## Snippet 3 — the Smi overflow

```js
function checksum(ids) {
  let acc = 0;
  for (let i = 0; i < ids.length; i++) {
    acc = (acc * 31 + ids[i]);     // grows fast for large arrays
  }
  return acc;
}
```

<Quiz
  id="03-v8-internals-code-3"
  lessonSlug="03-v8-internals"
  lang="en"
  question="checksum is TurboFan-optimised and fast for small inputs, but on large arrays it suddenly deopts and slows down. What is the V8-level cause and the fix?"
  choices={[
    { label: "acc starts as a Smi and TurboFan specialises the arithmetic on Smi. As acc * 31 + ids[i] grows past the Smi range (±2³¹), the value becomes a HeapNumber, the Smi guard fails, and V8 deopts. Fix: keep the accumulator in 32-bit integer range with acc = (acc * 31 + ids[i]) | 0.", correct: true },
    { label: "The for-loop bounds check on ids.length is what triggers the deopt.", misconception: "An in-bounds indexed loop is exactly the pattern TurboFan optimises well. The deopt reason here is the Smi-to-HeapNumber transition of acc, not bounds checking." },
    { label: "Multiplying by 31 forces floating-point math from the start, so it was never optimised.", misconception: "Integer multiply stays Smi while the result fits ±2³¹; V8 does optimise it. The deopt happens only once acc overflows that range and boxes into a HeapNumber." },
    { label: "Large arrays cause a GC pause mid-loop; that is the slowdown.", misconception: "The slowdown localises to this function after a deopt event, not a global pause. The trigger is the numeric-type transition of acc, which the | 0 coercion prevents." },
  ]}
/>

<Recap lang="en">
Every V8 incident reads the same way in code and traces: a conditionally-added property splits one array into two hidden classes and pushes a hot site polymorphic; delete tips an object into permanent dictionary mode; an accumulator that overflows the Smi range boxes into a HeapNumber and deopts a TurboFan loop; and a repeating 'wrong map' deopt at one source position is the deopt-loop signature. Diagnose from the trace, then fix upstream in the data model — unify the shape, drop the delete, clamp the numeric range — before you ever reach for a flag.
</Recap>
