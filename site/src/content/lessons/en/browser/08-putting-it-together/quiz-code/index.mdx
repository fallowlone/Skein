## Snippet 1 — queue ordering

```js
console.log("A");
setTimeout(() => console.log("B"), 0);
Promise.resolve().then(() => console.log("C"));
queueMicrotask(() => console.log("D"));
console.log("E");
```

## Snippet 2 — the resize loop

```js
function fitAll(boxes) {
  for (const box of boxes) {
    const w = box.offsetWidth;     // READ — forces layout
    box.style.width = w + 10 + "px"; // WRITE — invalidates layout
  }
}
```

<Quiz
  id="08-putting-it-together-code-2"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="With 500 boxes this handler is a long task that wrecks INP. What is the defect and the fix?"
  choices={[
    { label: "Layout thrash (forced synchronous reflow): each iteration reads offsetWidth after a write invalidated layout, so the browser must recompute layout every pass — O(n) reflows. Fix: batch all reads first, then all writes (or cache widths), turning n reflows into one.", correct: true },
    { label: "offsetWidth is deprecated and slow; use getBoundingClientRect.", misconception: "getBoundingClientRect also forces layout — swapping the API does not help. The defect is interleaving reads and writes, which forces a reflow per iteration regardless of which read API is used." },
    { label: "The loop allocates too much and triggers GC.", misconception: "There is little allocation here; the cost is repeated forced layout, not garbage collection. The trace shows recalculate-style/layout bars, not GC." },
    { label: "style.width should be set via a CSS class for speed.", misconception: "A class would still invalidate layout and, read back in the same loop, still thrash. The fix is separating the read phase from the write phase, not the styling mechanism." },
  ]}
/>

## Snippet 3 — the server/client render

```jsx
function Price({ cents }) {
  // runs on both server and client during hydration
  const formatted = new Intl.NumberFormat(navigator.language, {
    style: "currency", currency: "USD",
  }).format(cents / 100);
  return <span id="price">{formatted}</span>;
}
```

Fix: render a deterministic value on the server and apply the locale-specific format in a post-hydration useEffect.", correct: true },
    { label: "Intl.NumberFormat is too slow and blocks the main thread.", misconception: "Intl is fast enough here; the failure is non-determinism, not cost. The server and client produce different strings, which is what triggers the mismatch re-render and the shift." },
    { label: "The id='price' collides with another element.", misconception: "A duplicate id is invalid but is not what flashes the value. The flash is React reconciling a server/client text mismatch — a determinism bug, not an id bug." },
    { label: "cents / 100 loses precision and corrupts the value.", misconception: "Float division is not the cause of an intermittent flash on hydration. The intermittency tracks the locale differing between server and client — a render-determinism problem." },

## Snippet 4 — the click handler

```js
button.addEventListener("click", () => {
  cart.add(item);
  renderCartBadge();                  // small DOM update
  const report = JSON.parse(hugeBlob); // ~120 ms on a mid-range phone
  analytics.sendSync(report);          // synchronous beacon
});
```

<Recap lang="en">
Four snippets, four layers. The event loop drains all microtasks (promise, queueMicrotask) before the next macrotask (setTimeout), so synchronous-then-microtasks-then-macrotask is the order. Interleaving DOM reads and writes forces a reflow per iteration — batch reads then writes. A component that renders a locale- or browser-only value on the server is a hydration mismatch — make the server render deterministic and defer client-only formatting to useEffect. And any synchronous heavy work in a handler before the paint counts against INP — update the UI minimally, then yield. The skill is reading code straight back to the track it stresses.
</Recap>
