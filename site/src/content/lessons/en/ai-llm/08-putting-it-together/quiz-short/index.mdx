The naive composition builds one system block of rules + tool schemas + the retrieved RAG chunks. In a demo with one repeated question it looks cached, but in prod the retrieved chunks differ on every query, so the prefix differs from the first byte and the read rate collapses to near zero — you pay full input price on the long prefix every call, exactly where caching mattered. The fix is seam-aware layout: keep the static prefix (rules, tool schemas) before the breakpoint and the per-request RAG context after it, in the messages. If the frontend treats the stream as 'tokens until message_stop,' it renders the partial text and then resolves the spinner — but the real continuation is another request you haven't sent (the tool result, fed back). The states are text, tool_use_requested, awaiting_tool_result, resumed; the tool-use stop is a transition, not an end. Two field failure modes make this worse: a network blip can truncate the stream with a tool_use stop but zero tool_use blocks, so the agent goes idle silently; and a crash mid-tool-execution orphans the result, so the next request is rejected with 'unexpected tool_use_id found in tool_result block.' The cited postmortem: four uncapped agents looped for 11 days and burned $47,000 before anyone noticed. Enforcement is a hard gate before every model call: assert step ≤ MAX_STEPS and spent ≤ BUDGET_USD and refuse the call when a ceiling is hit, and dedupe by hash(tool_name, args) to kill repeat-the-same-call loops. <Recap lang="en">
If you could reconstruct each answer from memory, you hold the track's spine: caching is a byte-for-byte prefix match, so dynamic RAG context belongs after the breakpoint; the stream is a state machine where tool_use is a transition and every id must be paired; agent loops need enforced step/dollar caps, not alerts; evals must run the live retrieval path or retrieval regressions ship green. And the meta-lesson over all of it: the bug lives in the seam — trace one real request end to end and model the whole flow. Now when you encounter an unexpected cost spike or a silent regression after shipping, you know to look at the boundary, not the component.
</Recap>
