Who is the caller, who is the callee, and what makes each iteration expensive?", a: "Tool calling inverts the usual contract: the model is the caller and your code is the callee. You send the request with a tools array; the model responds with stop_reason: \"tool_use\" and one or more tool_use blocks, each holding a tool name and a JSON arguments object. Your code executes each tool and formats the outputs as tool_result blocks, then sends a brand-new request with the full history plus those results. The loop repeats while stop_reason stays \"tool_use\" and exits on \"end_turn\" (or max_tokens, stop_sequence, refusal). Each iteration is expensive because step four is a fresh model call that re-sends the entire growing transcript plus the full tools array, so input tokens and cost compound with every step — a five-tool task is roughly six model invocations." },
    { q: "Why must you validate tool arguments, and what does 'validate' actually mean for a mutating endpoint like cancel_order?", a: "The model emits plausible JSON, not guaranteed-correct JSON: it can hallucinate an id, invent an enum value the schema never listed, drop a required field, or pass the wrong type. The input_schema guides the model but does not bind it, so tool arguments are untrusted input crossing a trust boundary, exactly like a raw form post. Validate means three ordered layers. One: schema-validate the arguments against the tool's input_schema with a real validator (Pydantic, jsonschema) and reject malformed shapes — never eval or blindly destructure them. Two: authorize and existence-check the referenced entity, because a well-formed id is still untrusted — confirm the order exists and belongs to this caller before mutating. Three: on any rejection return a tool_result with an error rather than throwing out of the loop, so the model reads the error and self-corrects on the next turn. Skipping any layer is how a fabricated ord_9f3c cancels the wrong customer's order." },
    { q: "Why is an unguarded tool-use loop both a correctness risk and a cost risk, and what two guards do you add?", a: "The loop re-invokes the model after every tool result, so a confused model can get stuck: it calls a tool, gets an error, and calls the same tool with the same arguments again, forever. Each iteration is a full model call that re-sends the entire transcript plus the tools array, so a single stuck turn can quietly burn several dollars and never terminate — that is the cost risk. The correctness risk is that nothing stops the model from re-firing a partially-effective or destructive call. Two guards, both mandatory in production: first, a hard iteration cap — a for-loop over MAX_STEPS, typically 8–15, never while True — that exits gracefully when hit; second, loop/repeat detection — if the model calls the same tool with identical arguments twice in a row, treat it as stuck and break or inject a message telling it the call already failed so it stops repeating." },
    { q: "When can the model parallelize tool calls, and when is a chain inherently serial?", a: "Modern models will, when several independent tools are needed, emit multiple tool_use blocks in a single response. You execute them concurrently and return all the tool_result blocks together, collapsing several sequential round trips into one — a real latency win because each round trip is a fresh model call of hundreds of milliseconds to seconds. Parallelism only helps when the calls are independent, like get_weather(NYC) and get_weather(SF). A chain where call two needs call one's output — find_user then cancel_user_order — is inherently serial: the model cannot fill the second tool's arguments until it has seen the first result, so it must wait. If your execution layer cannot safely run things concurrently, set disable_parallel_tool_use: true to force one tool per turn." },

<Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: the model is the caller and your code the callee, so every round trip is a fresh, transcript-re-sending model call; arguments are untrusted input you schema-validate then authorize and existence-check, returning errors as tool_result; an unguarded loop runs away, so cap iterations and detect repeats; parallelism helps only independent calls; tool_choice (auto/any/tool/none) sets whether and which tool fires; and the re-sent tools array is the token cost prompt caching exists to absorb. Now when you ship a tool-calling agent, you'll reach for the iteration cap and the validator before the first production deploy — not after the first runaway bill.
</Recap>
