  question="What is the precise mechanism of a regression gate, and what is the senior discipline that makes it tighten over time rather than rot?"
  choices={[
    { label: "The suite re-runs the golden set on every prompt edit, model bump, or retrieval change and emits a score; the gate fails the build when the score drops below baseline or the previous release.     { label: "It pins each output to an exact expected string and fails on any diff.", misconception: "LLM output isn't a fixed string even at temperature 0; a string-pin gate would fail on legitimate variation. A gate scores a distribution against a baseline threshold, not byte-equality." },
    { label: "It only runs on a manual schedule, so engineers review scores weekly.", misconception: "A gate that doesn't block the merge isn't a gate — it's a dashboard. The point is to fail the build automatically on the change that caused the regression, before it ships." },

<Recap lang="en">
The through-line of the unit is one pipeline: a golden set built from real traffic (coverage over count), scored with the cheapest honest method — programmatic where output has structure, a *calibrated* judge only for open-ended quality — then gated offline in CI and sampled online for drift. The two ways a green suite still lies are a dataset that no longer matches the live distribution and a judge you never validated against humans. Consistency is not accuracy; position, self-preference, and verbosity bias are real; and the discipline that keeps the gate honest is turning every production failure into a golden case the same day. Now when you see a green eval suite before a deploy, you know to ask: does this golden set still match live traffic, and was the judge calibrated against human labels — or am I looking at a number generator with a pass threshold?
</Recap>
