An LLM gives you no such contract — the same prompt at the same temperature can return different text each call, and even at temperature 0 output isn't guaranteed identical across model versions or requests, because providers batch and route non-deterministically. So you can't pin one expected string. An eval instead asserts that the output is 'good enough' on the dimensions you care about — correct, on-format, on-policy, grounded in the retrieved context — and it scores a distribution of behaviour over many examples rather than one case. The failure mode is silent: a model swap, prompt edit, new system message, or changed retrieval index can drop quality ~15% with no exception, no failed test, no log line saying 'worse.'     { q: "How do you build a golden set that actually catches regressions, and what is the discipline that keeps it honest?", a: "An eval is only as honest as its dataset. The senior mistake is seeding it with the clean, on-distribution examples you used while building — those already work. A useful golden set is built from production: real user queries, deliberately oversampling edge cases, past failures, and high-value flows, each paired with a known-good output or a rubric where there's no single right answer. Coverage beats raw count — 80 cases spanning your real query categories catch more than 2,000 near-duplicate easy ones — and the number that matters is how much of your live input distribution the set represents, not its size. The discipline that pays for itself: every production failure becomes a golden case the same day, so the fix is provable and that bug can never regress silently again." },
    { q: "When do you use a programmatic check vs an LLM-as-judge, and why prefer programmatic?", a: "Score each case with the cheapest method that works. Programmatic checks — regex, JSON-match, schema validation, code execution — are essentially free, run in milliseconds, and are deterministic, so they never lie or go flaky. Use them wherever the output has structure: valid JSON, a number, a class label, a parseable format. Reach for an LLM-as-judge only for genuinely subjective dimensions — helpfulness, tone, faithfulness, 'did it answer the question' — because a judge costs one extra model call per case, runs in seconds, and is itself a noisy, biased model. For a mixed output (structured fields plus free text), split it: programmatic on the fields, a calibrated judge only on the prose. Never hand a structured assertion to a stochastic grader." },
    { q: "Name the documented LLM-as-judge biases and the one step that makes a judge trustworthy.", a: "A judge is not ground truth — it's another stochastic model with reproducible biases. Position bias: in pairwise comparison, swapping which answer is first can flip the verdict, with the judge model itself the largest driver; mitigate by running both orders and averaging. Self-preference: a model rates its own generations higher, correlated with how well it recognizes its own text, so avoid grading a model's output with a judge from the same family. Verbosity bias: judges systematically prefer longer answers regardless of correctness. The one step that makes a judge trustworthy is calibration: hand-label a sample, measure the judge's agreement with those human labels, and only promote it to a gate once agreement clears your bar — teams target ~75–90%, around the level humans agree with each other. Critically, consistency (low variance across runs) is not accuracy; a confidently biased judge is more dangerous than a noisy one because its stability reads as trustworthiness." },
    { q: "What's the difference between offline and online evaluation, and what does each catch that the other can't?", a: "Offline runs the eval suite in CI against the golden set on every prompt edit, model bump, or retrieval change; it emits a score and a regression gate fails the build when the score drops below baseline or the previous release. That's what blocks a bad deploy before it ships. But offline is keyed to your repo, so it structurally cannot see a silent provider-side model update (no diff triggers a re-run) or a shift in what users are actually asking. Online closes that gap: you sample a slice of real production traffic (say 1–5%), score it with the same automated methods, and watch the trend, catching provider drift, input-distribution drift, and retrieval index drift. A/B tests then compare a candidate against the live version on real users and tie quality to business metrics. You need both layers — neither alone is sufficient." },

The eval faithfully measures a world that no longer matches the one users are in, so it stays green while a real category fails. Defense: online monitoring — track the embedding distribution of real inputs and alert when production queries land far from anything in the golden set, then pull those cases in. Second: you trusted a noisy judge. <Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: non-determinism means an eval scores a distribution of 'good enough' rather than asserting one exact value; a golden set is built from real traffic with coverage over count and fed by every production failure; programmatic checks score structure for free while a judge handles only open-ended quality; a judge is biased (position, self-preference, verbosity) and must be calibrated against human labels — consistency is not accuracy; and you gate offline in CI while sampling online for the drift offline can't see. A green suite still lies two ways — a stale dataset and an uncalibrated judge — so defend against both. Now when you see a teammate skip calibration because "the judge looked consistent," you know exactly where the trust breaks down — and what to check first.
</Recap>
