You add an "AI assistant" to your app. You type a question, and it answers in fluent sentences. It feels like magic, or like a tiny mind living in your server. <Crux>An LLM is a text-prediction engine you call like an API: it guesses the next text, so its output is useful but never guaranteed correct.</Crux>

<Explanation>

## What the engine actually does

An LLM (large language model) is a program trained on a huge amount of text. It learned one narrow skill extremely well: given some text so far, predict what text comes next. It does this in small pieces called **tokens** (roughly word-fragments). To answer you, it predicts one token, adds it to the text, predicts the next, and repeats. The fluent paragraph you read is thousands of these guesses chained together.

Two facts fall out of this and shape everything you build:

- It is **probabilistic**. The model picks likely next tokens, not the one true answer. The same prompt can produce different outputs, and a wrong-but-plausible answer (a "hallucination") looks exactly as confident as a right one.
- It has **no live knowledge or memory**. It only knows patterns from its training data, frozen at some past date, plus whatever text you put in the current request. It does not look things up unless you wire that in.

## You call it like an API

You do not run the model in your head or in your function. It lives on a server somewhere. Your code sends a request with your text (the **prompt**) and gets back a response with predicted text. That is the same shape as any other web API call: request in, response out, costs money, can be slow, can fail.

## Why "design around an unreliable component"

A normal function returns the same answer every time and is right by construction. An LLM does neither. So you never treat its output as a fact you can trust blindly. You design the system around it: keep prompts clear, give it the facts it needs in the request, check or constrain what comes back, and have a plan for when it is wrong, slow, or expensive. The whole pillar is patterns for doing exactly that — caching to cut cost, tool calls to give it real abilities, retrieval to feed it real facts, and evals to measure if it is actually working.

<Recap lang="en">
An LLM is a program trained to predict the next token of text, one piece at a time — fluent output is thousands of guesses chained together. That makes it probabilistic (it can be confidently wrong) and forgetful (it only knows its training data plus what you send). You use it by calling it like any API: prompt in, predicted text out, paying per token. So you build around it as an unreliable component — clear prompts, supplied facts, checked output. The rest of this pillar is how: caching, tool calls, retrieval, and evals.
</Recap>
