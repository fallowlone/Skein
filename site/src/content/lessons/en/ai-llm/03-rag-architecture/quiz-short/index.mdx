    { q: "Explain the chunking size-vs-recall knife-edge and the role of overlap.", a: "A chunk is embedded into one vector and is the atomic unit retrieval can ever return, so chunking caps the ceiling. Small chunks (128–256 tokens) embed precisely — one tight idea, sharp similarity targeting — but fragment any rule that spans a boundary, so a top-k that grabs only one piece returns a half-truth. Large chunks (800–1000+ tokens) keep context intact but dilute the embedding: one vector averages several ideas and the signal for a specific sub-fact washes out, hurting narrow-query recall. A common start is 300–800 tokens for prose, tuned on an eval set. Overlap (~10–15%) is cheap insurance: repeat the tail of each chunk at the head of the next so a fact straddling the seam survives whole in at least one chunk — but too much overlap fills the index with near-duplicates that eat top-k slots and context budget." },
    { q: "How is embedding dimensionality a cost lever, and what's the Matryoshka trade?", a: "An embedding maps text to a vector whose geometry encodes meaning; close vectors mean similar meaning. Dimensionality is a real cost lever, not a detail: text-embedding-3-small defaults to 1536 dims, text-embedding-3-large to 3072. Bigger vectors generally retrieve more accurately but inflate the index and slow ANN search — dropping from ~1536 to ~768 dims can cut search latency from around 50ms toward 20ms. With Matryoshka-style truncation you can run text-embedding-3-large at 1024 dims and land near 3072-dim quality at roughly one-third the storage (≈4KB vs ≈12KB per vector). When storage and p99 latency matter, truncating to ~1024 dims is a senior's default trade." },
    { q: "Describe the two-stage retrieve-wide-then-rerank-narrow pattern, and why one embedding top-k isn't enough.", a: "A single embedding search scores each chunk against the query independently as a bi-encoder dot-product — fast and ANN-friendly but coarse, because chunk and query were embedded separately and never compared token-to-token. Stage one casts a wide net: retrieve k=20–50 candidates to maximise the chance the right passage is somewhere in the set (recall-first). Stage two runs a cross-encoder reranker that reads the query and each candidate together in one pass, scoring true relevance far more accurately, and keeps the top 3–8. You can't run the cross-encoder over the whole corpus — too slow per item — which is exactly why it operates on the shortlist. The payoff: precision rises and you carry far fewer chunks into the window, saving tokens and cost and dodging lost-in-the-middle." },
    { q: "What is 'lost in the middle', and how should you assemble the final context because of it?", a: "LLMs show a U-shaped attention bias: they attend best to the start and end of the context and worst to the middle, regardless of relevance. When the answer-bearing chunk lands in the middle of a long stuffed prompt, measured accuracy can drop 30%+ versus the same chunk at the edges. So a big window is not a substitute for reranking. The practical assembly move: rerank, keep few chunks, and place the strongest evidence at the very start or very end of the assembled context — never dump 50 chunks in raw retrieval order with the decisive one buried mid-prompt." },

Two cousins worsen it: a stale index (the source changed but the embeddings didn't, so a query returns last quarter's policy with no error) and a poisoned index (a single injected or contradictory passage can flip an answer, and the model won't flag the conflict — it picks one and presents it as settled fact). The mitigations are all about admitting ignorance: gate on the retrieval/rerank similarity score, instruct the model to answer only from the provided context and to say 'I don't know' when nothing clears the bar, and keep the index fresh and access-controlled." },
