## Snippet 1 — the Alt-Svc advertisement

```
$ curl -v https://api.example.com/health
* ALPN: server accepted h2
< HTTP/2 200 OK
< alt-svc: h3=":443"; ma=86400
< x-quic-version: draft-29
< content-type: application/json
{"status":"ok"}

$ curl --http3-only https://api.example.com/health
* QUIC handshake fail: protocol violation: invalid initial packet
```

## Snippet 2 — the cached user profile

```
GET /api/user/profile HTTP/2
authorization: Bearer eyJ...userA

HTTP/2 200 OK
content-type: application/json
cache-control: max-age=300
{"id":"userA","email":"a@example.com"}
```

<Quiz
  id="06-http-versions-code-2"
  lessonSlug="06-http-versions"
  lang="en"
  question="Users report seeing each other's profiles intermittently. Reading only these headers, what is the bug and the correct fix?"
  choices={[
    { label: "The response is user-specific but marked publicly cacheable (max-age=300, no private/no-store, no Vary: Authorization). A shared cache or CDN stores userA's body and serves it to userB. Fix: Cache-Control: private (or no-store for sensitive data); add Vary: Authorization if a shared cache must vary per token.", correct: true },
    { label: "The bug is that HTTP/2 multiplexing crosses streams between users.", misconception: "HTTP/2 streams never cross request bodies between connections or users. The leak is a caching-semantics bug: a per-user response marked publicly cacheable." },
    { label: "The Bearer token in the header leaks the data; move it to a query string.", misconception: "Tokens belong in the Authorization header precisely because URLs leak via Referer and access logs. The bug is the missing private/Vary on the response, not the token's location." },
    { label: "max-age=300 is too short and causes stale reads across users.", misconception: "A short TTL does not mix users; any TTL on a publicly-cacheable per-user response leaks. The fix is scoping the cache (private/no-store), not changing max-age." },
  ]}
/>

## Snippet 3 — the gRPC response

```
HTTP/2 200 OK
content-type: application/grpc

(DATA frames: serialized protobuf message)

(trailing HEADERS frame)
grpc-status: 5
grpc-message: user not found
```

<Quiz
  id="06-http-versions-code-3"
  lessonSlug="06-http-versions"
  lang="en"
  question="The HTTP status is 200 but grpc-status is 5 (NOT_FOUND). Why is the result in a trailer, and what breaks if a browser calls this directly?"
  choices={[
    { label: "gRPC always returns HTTP 200 and carries the real outcome in a trailing HEADERS frame, because the status is only known after the whole message stream is sent — trailers arrive after the body. A browser can't read HTTP trailers via fetch/XHR, so it needs gRPC-Web, which a proxy rewrites trailers into a final body frame.", correct: true },
    { label: "The 200 is a bug; gRPC should map grpc-status 5 to HTTP 404.", misconception: "By design gRPC keeps HTTP status at 200 and signals the RPC outcome in grpc-status trailers; this is correct, not a bug. The trailer placement reflects end-of-stream timing." },
    { label: "Trailers are used to bypass CORS, which is why browsers can't read them.", misconception: "Trailers are about end-of-stream metadata timing, not CORS. Browsers simply don't expose HTTP trailers to JS, hence gRPC-Web." },
    { label: "The body frame should carry grpc-status; trailers are HTTP/1.1-only.", misconception: "HTTP/2 supports trailing HEADERS frames, and gRPC relies on them. The body holds the protobuf message; the status legitimately lands in the trailer." },
  ]}
/>

## Snippet 4 — the priority hints

```
:method = GET
:path = /hero.jpg
priority = u=5

:method = GET
:path = /critical.css
priority = u=1
```

<Quiz
  id="06-http-versions-code-4"
  lessonSlug="06-http-versions"
  lang="en"
  question="Both requests arrive at once over HTTP/3. Reading the RFC 9218 Priority headers, which does the server send first, and what is the rule?"
  choices={[
    { label: "critical.css (u=1) is scheduled ahead of hero.jpg (u=5): in RFC 9218 a lower urgency value means more urgent, so the server orders DATA-frame transmission to favour render-blocking CSS over a decorative image. The i (incremental) flag would let a large body yield between higher-urgency work.", correct: true },
    { label: "hero.jpg first, because u=5 is a higher number and higher means higher priority.", misconception: "RFC 9218 inverts that intuition: lower u is more urgent. u=1 (CSS) outranks u=5 (image), so the CSS is sent first." },
    { label: "Order is undefined — the server streams in arrival order regardless of priority.", misconception: "That was the failure mode RFC 9218 fixed. With Priority headers honoured by modern servers and CDNs, the server reorders DATA frames by urgency." },
    { label: "They are sent strictly simultaneously since HTTP/3 multiplexes equally.", misconception: "Multiplexing allows interleaving, but priorities tell the server how to weight DATA-frame bandwidth — favouring the lower-urgency-value (more urgent) stream." },
  ]}
/>

<Recap lang="en">
Every HTTP incident is read in headers and traces: an Alt-Svc h3 hint backed by a draft-QUIC stack wastes an RTT per client; a per-user response missing private/no-store and Vary leaks across a shared cache; gRPC's real outcome lives in a trailing HEADERS frame (200 at the HTTP level) and needs gRPC-Web for browsers; and RFC 9218 urgency is inverted — lower u is more urgent. Read the wire, predict the protocol behaviour, then apply the structural fix.
</Recap>
