    { q: "Why did HTTP/2 and HTTP/3 get invented if HTTP/1.1 already worked?", a: "HTTP/1.1 carries one in-flight request-response per TCP connection, so to load a modern page with dozens of sub-resources fast, browsers had to open 6 to 8 parallel connections per origin — each paying its own TCP and TLS handshake and starting congestion control from scratch. Even then, a slow response blocked further requests on its connection. HTTP/2 collapses that into one connection multiplexing many streams, cutting handshakes and removing application-layer head-of-line blocking. HTTP/3 goes further: it moves off TCP onto QUIC so a lost packet no longer stalls every stream, and it survives IP changes — addressing the transport-layer HOL blocking that HTTP/2 still inherited." },
    { q: "Explain the two layers of head-of-line blocking and which version fixes each.", a: "Application-layer HOL blocking: in HTTP/1.1 each connection processes one request-response at a time, so a slow response holds up everything queued behind it on that connection. HTTP/2 fixes this by multiplexing independent streams on one connection. Transport-layer HOL blocking: TCP delivers a single in-order byte stream, so one lost segment forces TCP to buffer all later bytes until retransmission — stalling every HTTP/2 stream multiplexed on that connection. HTTP/2 cannot fix this because it sits on TCP. HTTP/3 fixes it by running on QUIC, which tracks loss per packet and recovers per stream, so a lost packet stalls only the streams whose data it carried." },
    { q: "Why does HTTP/3 use QPACK instead of HPACK, and how does QPACK preserve stream independence?", a: "HPACK's dynamic table is ordered and shared across streams: a HEADERS frame referencing entry index N must be processed after the frame that inserted index N. On TCP this is invisible because delivery is in order. On QUIC, streams deliver frames independently, so a HEADERS frame on one stream could reference a table entry whose insertion frame, carried on another stream or packet, has not arrived — re-introducing HOL blocking at the header layer. QPACK decouples this: dynamic-table insertions go on a dedicated encoder control stream (delivered in order), a decoder stream acknowledges processed entries, and regular HEADERS frames reference only acknowledged entries. So one stream's headers can never block another's, preserving QUIC's stream isolation up at the compression layer. QPACK also keeps a larger static table (99 entries vs HPACK's 61)." },
    { q: "What is QUIC connection migration and why does it matter for mobile?", a: "A QUIC connection is identified by a connection ID chosen at setup, not by the 4-tuple of source/destination IP and port. When a device's local IP changes — for example switching from Wi-Fi to cellular — the client sends a PATH_CHALLENGE from the new address and the server validates with PATH_RESPONSE, and the existing connection continues without re-handshaking. On HTTP/2 over TCP the 4-tuple change destroys the connection and forces a new TCP plus TLS handshake (1 to 2 RTT), visible as a hiccup. For mobile users crossing networks frequently, migration is a real latency and continuity win." },
    { q: "Why is HTTP/2 Server Push dead, and what replaced it?", a: "Server Push let the server send resources the browser had not requested, betting it would need them. It failed in production for three reasons: the server cannot see what the browser already cached, so it re-pushes fresh cached assets and wastes bandwidth; push only helps on cold first navigations, not warm loads; and middleboxes and CDNs handled it inconsistently, causing duplicate transfers. Chrome removed it in 2022 and RFC 9113 deprecates PUSH_PROMISE. The replacement is 103 Early Hints plus link rel=preload: the server sends an informational 103 response listing critical sub-resources before the 200, and the browser — which can check its own cache — decides whether to fetch each one." },
    { q: "How is HTTP/3 discovered and selected, and what production signal tells you UDP is being blocked?", a: "HTTP/1.1 and HTTP/2 are selected via ALPN inside the TLS handshake at no extra round-trip. HTTP/3 cannot be negotiated that way because QUIC rides UDP, which firewalls may block. Discovery is two-stage: the first connection uses TCP-based /1.1 or /2, and the server advertises h3 via an Alt-Svc header or an HTTPS/SVCB DNS record. On the next visit the browser tries QUIC on UDP/443; if that fails it silently falls back to HTTP/2 with no user-visible error. The operational signal is ALPN distribution and the h3-to-h2 fallback rate broken down by region and ASN — a spike in fallback for one ASN means a path started dropping UDP/443 (a firewall, DDoS-scrubber, or routing change)." },
