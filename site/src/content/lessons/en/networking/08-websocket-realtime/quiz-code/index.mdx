## Snippet 2 — the broadcast loop

```js
function broadcast(clients, message) {
  for (const ws of clients) {
    ws.send(message);            // enqueue, returns immediately
  }
}
// called every 10 ms with a 100 KB payload, 10k clients
```

<Quiz
  id="08-websocket-realtime-code-2"
  lessonSlug="08-websocket-realtime"
  lang="en"
  question="A few hundred clients are on slow links. With this loop, what happens under sustained load, and what is the highest-leverage fix?"
  choices={[
    { label: "ws.send() enqueues into a per-connection buffer and returns even when the socket cannot drain; slow clients' queues grow unbounded until the process OOMs. Fix: check ws.bufferedAmount against a high-water mark and evict (close 1013) or drop messages for clients over the cap.", correct: true },
    { label: "Nothing — send() blocks until each client receives, so memory is bounded.", misconception: "send() in this style does not block; it buffers and returns. That is what lets one slow client's queue grow without bound — bounded memory requires an explicit high-water-mark check." },
    { label: "The fast clients are the risk because the loop sends to them first.", misconception: "Fast clients drain in milliseconds and hold almost nothing. The unbounded growth is entirely on the slow clients whose queues never empty." },
    { label: "Raise the kernel send buffer (SO_SNDBUF) to absorb the slow clients.", misconception: "A bigger kernel buffer delays the cliff by a few KB per socket; the application queue is where megabytes pile up. The fix is capping the application queue, not enlarging the kernel one." },
  ]}
/>

## Snippet 3 — the reconnect routine

```js
let attempt = 0;
function reconnect() {
  const delay = Math.min(1000 * 2 ** attempt, 60000);
  setTimeout(() => { attempt++; connect(); }, delay);
}
```

<Quiz
  id="08-websocket-realtime-code-3"
  lessonSlug="08-websocket-realtime"
  lang="en"
  question="A deploy drops 5 million clients at once and they all run this routine. What goes wrong, and what is the one-line fix?"
  choices={[
    { label: "Every client computes the identical delay (1 s, then 2 s, then 4 s) because there is no per-client randomness, so the retries arrive in synchronized waves that keep overrunning the SYN backlog. Fix: multiply delay by a random jitter factor, e.g. delay *= 0.5 + Math.random().", correct: true },
    { label: "The 60 s cap is too low and cuts off recovery.", misconception: "The cap protects the server by bounding retry frequency; lowering or raising it does not address the core defect, which is that all 5 M clients fire at the same instants." },
    { label: "2 ** attempt overflows and the delay becomes negative.", misconception: "Math.min with 60000 bounds the value long before any overflow; the delays are correct numbers. The defect is that they are identical across clients — no jitter." },
    { label: "setTimeout is the wrong primitive; use a tight retry loop.", misconception: "A tight loop would hammer the server far harder. setTimeout with backoff is correct; it just needs jitter added so clients desynchronize." },
  ]}
/>

## Snippet 4 — the Nginx location block

```nginx
location /ws {
  proxy_pass http://backend;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection "Upgrade";
}
```

<Quiz

    { label: "The Upgrade and Connection headers are wrong and must be removed.", misconception: "Those headers are exactly what makes the upgrade work — removing them breaks the handshake. The missing piece is the read/send timeout, which governs idle long-lived connections." },
    { label: "proxy_pass must point at an https:// backend for WebSocket.", misconception: "The scheme of the backend is unrelated to the idle-timeout failure; ws works over an http:// upstream behind TLS termination. The 60 s death is the default proxy_read_timeout." },
    { label: "Nothing is missing — the 60 s drops are the client's fault.", misconception: "The symptom (death after ~60 s of silence) is the textbook Nginx default proxy_read_timeout closing quiet connections; it is a proxy-config gap, not a client bug." },
  ]}

<Recap lang="en">
Every WebSocket incident is read in artifacts: a frame's opcode nibble tells you ping (answer with pong) versus data; an unbounded send loop OOMs on slow clients unless a high-water mark caps the queue; a reconnect routine without jitter turns a deploy into a thundering herd; and an Nginx block without a raised proxy_read_timeout silently kills idle connections at 60 s. Diagnose from the artifact, apply the top-of-ladder fix, then confirm under the same load.
</Recap>
