Masking forces the client to XOR every payload byte with a fresh random 4-byte key carried in the frame; because the key is random per frame, the attacker cannot pre-craft bytes that both decode correctly and look like a valid HTTP response to a naive proxy. Server-to-client frames need no mask because the same-origin policy already blocks JavaScript from reading those bytes, so there is no equivalent attack to defend against." },

    { q: "Walk through the backpressure failure mode on a broadcast server and the high-water-mark fix.", a: "To avoid blocking, the server enqueues each broadcast into a per-connection application send queue and returns immediately; a background writer drains each queue as fast as the client's TCP window allows. Fast clients drain in milliseconds, but slow clients (mobile links, blocked read threads) never empty their queue, so it grows unbounded in RAM — e.g. 100 KB every 10 ms is 10 MB/s per slow client — until the process OOMs. The fix is a high-water mark: a per-connection cap (say 100 messages or 10 MB). When breached, the server either evicts the client with close code 1013, drops stale messages (for idempotent state like price snapshots), or pauses the producer (for peer-to-peer streams). Monitor slow-client count (target below 0.1%) and total queued bytes (below 5% of heap) as the early warning." },

The fix is per-client jitter: pick a random base (100-500 ms), double each attempt, cap at 30-60 s, and multiply each delay by a random factor (e.g. 0.5 to 1.5). That spreads ten million retries across a continuous window so the server accepts a few hundred per second and recovers within one or two windows.
