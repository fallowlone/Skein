  question="A dashboard pushes ~5 updates per minute to 100k users who never send data back. An engineer reaches for WebSocket. What is the better default and why?"
  choices={[
    { label: "SSE: the data flow is server-to-client only, so bidirectionality buys nothing. The browser's EventSource reconnects automatically via Last-Event-ID, it passes any HTTP proxy, and at 5 updates/min the WebSocket latency edge is irrelevant.", correct: true },
    { label: "WebSocket is still better because it always has lower latency.", misconception: "WebSocket's 0-5 ms vs SSE's 3-8 ms is real but meaningless at 5 updates per minute. It costs you custom reconnection logic and proxy-compatibility risk with no payoff for a server-push-only feed." },
    { label: "Long-polling, because it works through every proxy.", misconception: "Long-polling also works everywhere, but at 100k users it holds 100k open requests and pays ~500 bytes of headers per poll.     { label: "WebSocket over HTTP/2, to multiplex the channels.", misconception: "There is one channel per user here; multiplexing many streams per client solves a problem this feature does not have. It is needless complexity over plain SSE." },
  ]}

<Quiz

  lessonSlug="08-websocket-realtime"
  lang="en"
  question="A broadcast server's memory climbs steadily under load until the OOM killer fires; 100 of 10,000 clients are on slow mobile links. What is the mechanism, and what is the first durable fix?"
  choices={[
    { label: "Backpressure: slow clients drain their TCP windows slowly, so the per-connection application send queues grow unbounded in RAM. First fix: a high-water mark per connection that evicts (close 1013) or drops messages once the queue exceeds a cap.", correct: true },
    { label: "A memory leak in the broadcast code; restart the process on a schedule.", misconception: "The 'leak' is unbounded send queues for clients that cannot keep up — bounded, intentional buffers with no eviction policy. Scheduled restarts mask the symptom; the high-water mark fixes the cause." },
    { label: "GC pauses are too long; switch to a low-pause collector.", misconception: "GC pauses lengthen because the heap is bloated by queued messages — a symptom, not the cause. Capping queue growth removes the bloat; the collector choice is downstream." },
    { label: "The 100 slow clients are too many connections; add servers.", misconception: "More servers spread the same flaw; each still bloats from its slow clients. Without a high-water mark and eviction, scaling out just delays the OOM." },
  ]}
/>

  question="You deploy a new build; all 10 million connected clients drop with code 1006 and reconnect. Your client uses exponential backoff but no jitter. Why does the server still struggle to recover?"
  choices={[
    { label: "Exponential backoff alone keeps retries synchronized: every client doubles from the same base, so the waves still arrive together at 1 s, 2 s, 4 s. The fix is per-client random jitter so 10 M retries spread across a continuous window instead of synchronized bursts.", correct: true },
    { label: "Backoff is fine; the server simply needs a bigger SYN backlog.", misconception: "A larger backlog raises the cliff but synchronized 10 M waves still overrun it. The structural fix is desynchronizing the clients with jitter, not absorbing the synchronized burst." },
    { label: "Code 1006 means the clients should not reconnect at all.", misconception: "1006 is an abnormal close (no close frame) — exactly the case where clients should reconnect. The problem is how they reconnect, not whether." },
    { label: "Exponential backoff already includes jitter by definition.", misconception: "Plain exponential backoff is deterministic doubling; jitter is a separate, explicit randomization (e.g. delay times random(0.5,1.5)) that you must add on top." },

  choices={[

    { label: "Sticky sessions already route A's message to Server 2 automatically.", misconception: "Stickiness routes a given client consistently to its own server; it has no mechanism to deliver A's message to B's different server. Cross-server fan-out needs pub/sub." },
    { label: "You should drop sticky sessions and load-balance every frame per-request.", misconception: "Per-frame balancing would scatter a single client's state across servers and break in-flight unACK'd state.     { label: "Pub/sub is unnecessary if both servers share the same database.", misconception: "A shared database stores messages but does not push them; a server has no signal that a new row appeared without polling. Pub/sub (or streams with consumers) provides the real-time fan-out signal." },

<Recap lang="en">
The unit's through-line is one operational model: the upgrade reuses the existing connection so shared infrastructure still routes it; framing and mandatory client masking defend the wire; transport choice (WebSocket vs SSE vs long-polling) follows the direction of data flow; backpressure is the canonical failure mode, answered by a high-water mark; reconnection must be jittered or it becomes a thundering herd; and horizontal scale needs pub/sub for fan-out plus sticky sessions for per-connection state. Every production incident in this unit resolves back to those levers.
</Recap>
