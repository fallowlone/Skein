## Snippet 1 — openssl s_client chain verification

```
% openssl s_client -connect api.example.com:443 -tls1_3
depth=0 CN = api.example.com
verify error:num=20:unable to get local issuer certificate
verify error:num=21:unable to verify the first certificate
---
Certificate chain
 0 s:CN = api.example.com
   i:CN = R3 Issuing CA
---
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
Verify return code: 21 (unable to verify the first certificate)
```

    { label: "The client is missing SNI, so the server returned the wrong certificate.", misconception: "openssl s_client sends SNI by default and the returned CN matches the host. The chain is for the right host — it is simply missing the intermediate the client needs to reach a root." },

## Snippet 2 — Nginx session-ticket key config

```nginx
server {
    listen 443 ssl;
    ssl_protocols TLSv1.3;
    ssl_session_ticket_key /etc/nginx/ticket.key;   # generated once at install
    ssl_early_data on;
    # ...
}
```

<Quiz
  id="05-tls-handshake-code-2"
  lessonSlug="05-tls-handshake"
  lang="en"
  question="This config has been running unchanged for a year. What is the most serious security defect, given ssl_early_data is on?"
  choices={[
    { label: "The session-ticket encryption key (STEK) is static and persisted to disk, never rotated. A single leaked key file lets an attacker decrypt every resumed session and all 0-RTT early data it ever protected — there is no forward secrecy on resumption. Rotate the STEK at least hourly, keep keys in memory, and distribute via authenticated channels.", correct: true },
    { label: "ssl_early_data on is itself the vulnerability and must be disabled.", misconception: "0-RTT early data is acceptable for idempotent routes with replay defenses. The deeper defect here is the never-rotated, disk-persisted STEK, which undermines resumption forward secrecy regardless of early data." },
    { label: "TLSv1.3 only is too restrictive and will break old clients, which is the main issue.", misconception: "Restricting to TLS 1.3 is a hardening choice, not a security defect. The security problem is the static, disk-stored ticket key." },
    { label: "The key path is absolute, which leaks the filesystem layout in error messages.", misconception: "The path being absolute is irrelevant to TLS security. The real problem is that the key is static and on disk — STEKs must rotate and stay in memory." },
  ]}
/>

## Snippet 3 — an Early-Data request handler

```js
app.post("/transfer", (req, res) => {
  // money movement
  if (req.headers["early-data"] === "1") {
    // request arrived in TLS 0-RTT early data
  }
  doTransfer(req.body);
  res.send("ok");
});
```

<Quiz
  id="05-tls-handshake-code-3"
  lessonSlug="05-tls-handshake"
  lang="en"
  question="The Early-Data header is read but the handler still calls doTransfer regardless. What goes wrong under a replay, and what is the correct fix?"
  choices={[
    { label: "An attacker can capture and resend the 0-RTT request, so doTransfer runs twice — a duplicate money movement. The handler must, when Early-Data is 1 on a mutating route, return 425 Too Early so the client retransmits after the handshake completes; only then call doTransfer.", correct: true },
    { label: "Nothing — reading the Early-Data header automatically makes the request replay-safe.", misconception: "Reading the header changes nothing on its own; the code still executes the mutation. You must reject with 425 Too Early on mutating routes when Early-Data is 1, forcing a post-handshake retry." },
    { label: "The body will be undefined in early data, so the transfer silently no-ops.", misconception: "Early data carries the full request including the body; it is processed normally. The danger is precisely that it processes — and can be replayed to process twice." },
    { label: "TLS will reject the POST at the record layer before it reaches the handler.", misconception: "TLS delivers early data to the application; it does not know your route is non-idempotent. Enforcing idempotency is an application-layer responsibility via 425 Too Early." },
  ]}
/>

## Snippet 4 — a client key_share trace

```
ClientHello key_share: x25519 (0x001d), X25519MLKEM768 (0x11ec)
ServerHello: HelloRetryRequest, selected_group = secp256r1 (0x0017)
```

<Quiz
  id="05-tls-handshake-code-4"
  lessonSlug="05-tls-handshake"
  lang="en"
  question="The client offered x25519 and the hybrid X25519MLKEM768, yet the server sent HelloRetryRequest asking for secp256r1. What happened and what is the cost?"
  choices={[
    { label: "The server supports neither offered group, so it sent HelloRetryRequest naming secp256r1 (P-256). The client must resend a fresh ClientHello with a P-256 key_share plus the HRR cookie, costing one extra RTT. Offering P-256 up front alongside x25519 would have pre-empted the retry.", correct: true },
    { label: "HelloRetryRequest means the certificate failed to validate, so the client must re-authenticate.", misconception: "HRR is purely about key_share group negotiation, not authentication. It is sent when none of the client's offered groups match what the server will use." },
    { label: "The hybrid group X25519MLKEM768 is invalid, so the whole handshake aborts.", misconception: "X25519MLKEM768 is a valid hybrid named group; the server simply does not support it. The handshake continues via HRR with a group both sides accept, costing one RTT, not aborting." },
    { label: "HelloRetryRequest downgrades the connection to TLS 1.2.", misconception: "HRR stays within TLS 1.3 and only renegotiates the key_share group. It does not change the protocol version; downgrade attempts would break the Finished transcript check." },
  ]}
/>

<Recap lang="en">
Every TLS incident is read in artifacts: an openssl verify code 20/21 means an incomplete chain — send the intermediates; a static disk-stored ssl_session_ticket_key destroys resumption forward secrecy — rotate STEKs hourly in memory; an Early-Data handler that mutates without returning 425 Too Early is replayable — gate mutating routes on the Early-Data header; and a HelloRetryRequest naming a different group means your offered key_shares missed — offer x25519 plus P-256 up front to avoid the extra RTT. Read the artifact, find the violated invariant, fix the cause.
</Recap>
