    { q: "Why does TCP need three messages and not two, and what does each step accomplish?", a: "TCP is bidirectional, so both sides must exchange and acknowledge each other's Initial Sequence Number before data flows. The SYN carries the client's ISN; the SYN-ACK carries the server's ISN and acknowledges the client's; the third ACK acknowledges the server's ISN. A two-step handshake would leave the server's sequence number unconfirmed and would not prove the client is genuinely alive — a stale or spoofed SYN could make the server allocate state for a peer that never responds. The third ACK closes the loop and bounds half-open connections. The cost is one full round-trip before the first application byte." },
    { q: "Why are Initial Sequence Numbers randomised per connection, and how does RFC 6528 do it?", a: "Predictable ISNs let an off-path attacker guess the next sequence number, forge a segment that lands inside the receive window, and inject data or an RST into an established connection — the classic sequence-prediction attack. RFC 6528 computes ISN = M + F(saddr, sport, daddr, dport, secret_key), where M is a fine-grained time counter and F is a keyed cryptographic hash of the 4-tuple. The value is unguessable without knowing the secret or eavesdropping on the actual SYN-ACK, so blind injection becomes infeasible. This is integrity/anti-spoofing, not confidentiality — TCP payload is still cleartext until TLS wraps it." },
    { q: "What is TIME-WAIT, why does it exist, and what are the production fixes when it causes EADDRNOTAVAIL?", a: "TIME-WAIT is the state the connection-closing side enters after the final ACK, lasting 2*MSL (~120 s). It exists so a delayed retransmission of the old connection's FIN or data lands harmlessly instead of being mistaken for a new connection on the same 4-tuple. A busy client opening many short-lived connections to one origin can exhaust ephemeral ports held in TIME-WAIT, and connect() then returns EADDRNOTAVAIL. The fixes, in order: use a keep-alive connection pool so one connection serves many requests (the real fix); enable net.ipv4.tcp_tw_reuse=1, which safely reuses TIME-WAIT entries when Timestamps prove the new SYN is newer (RFC 6191/PAWS); and widen ip_local_port_range. Never use tcp_tw_recycle — removed in Linux 4.12 for breaking NAT — and never just lower MSL, which risks stale-segment corruption." },
    { q: "Explain how a SYN cookie works, and what legitimate connections lose during a flood.", a: "When the half-open SYN queue exceeds tcp_max_syn_backlog, the kernel stops allocating a request_sock per SYN. Instead it sets the SYN-ACK's ISN to a token: the top 5 bits encode the MSS index, the next 6 bits a minute counter, and the low 21 bits an HMAC over the 4-tuple plus a rotating secret. The connection is then forgotten. When the ACK returns, the kernel recomputes and validates the cookie before allocating a full socket, so a spoofed flood that never ACKs costs only CPU, not memory. The cost to genuine clients: only the MSS survives in the cookie — Window Scaling, SACK, and Timestamps offered in the SYN are silently dropped, so on a long-RTT high-bandwidth path the window caps at 64 KiB and throughput suffers while the flood is active." },
    { q: "Why does BBR sustain throughput on a path with ~1% random loss where CUBIC collapses?", a: "CUBIC treats every packet loss as a congestion signal and cuts the congestion window (~0.7x), then probes back along a cubic curve. On a path with ~1% random loss — cellular, satellite, long-haul WAN — the loss rate is high enough that CUBIC spends most of its time in recovery and never reaches the link's real capacity. BBR abandons loss-based signalling: it estimates the bottleneck bandwidth from the delivered-byte rate and the minimum RTT from packet timestamps, then paces sends to match bandwidth*RTT. Random drops do not perturb those estimates, so BBR holds near line rate. The guidance is to keep CUBIC on standard low-loss datacenter/regional paths and switch to BBR where random loss is normal." },
    { q: "What is TCP's relationship to QUIC, and why did QUIC reinvent TCP's mechanisms over UDP instead of extending TCP?", a: "QUIC re-implements TCP's core ideas — sequence numbers, ACKs, reliable in-order delivery, congestion control, slow start, fast retransmit — in user space on top of UDP. It was built this way because evolving TCP means changing kernels worldwide, which takes 5–15 years due to the long tail of un-updated systems, and because middleboxes ossify TCP by stripping or rejecting unfamiliar options (the same ossification that stalled TCP Fast Open). UDP passes through middleboxes unchanged, so QUIC ships as a library update in a browser or server and iterates at application speed. HTTP/3 runs on QUIC; HTTP/1.1 and HTTP/2 run on TCP. Because the mechanisms are the same, understanding the TCP handshake makes QUIC mechanistically transparent." },
