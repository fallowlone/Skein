Layer-3 NAT forwards raw packets unchanged and cannot inspect or modify the payload, so it can route on IP and port only. The two-connection model is the price of HTTP-aware routing, and it is also why the backend sees the proxy's IP rather than the client's — which is what X-Forwarded-For, RFC 7239, and PROXY protocol exist to restore." },
    { q: "Compare round-robin, least-connections, and power-of-two-choices on cost, fairness, and herding.", a: "Round-robin is O(1) but load-blind — it distributes request count, not load, so a slow backend drowns in its fair share. Least-connections routes to the fewest active connections (adapts to load) but needs an O(log N) scan and herds: when a recovered backend's count drops, every client sees the same minimum simultaneously and stampedes it. Power-of-two-choices samples two backends at random and routes to the less loaded one — O(1), ~12% imbalance (Adler 1996) versus ~100% for pure random, and the per-request randomness desynchronizes the herd. It is the production default in nginx, Envoy, and AWS ALB." },
    { q: "Why do you need both active and passive health checks, and what does each miss alone?", a: "Active checks send probes (HTTP GET /healthz, TCP SYN, gRPC) every 10–30 s and eject after 2–3 failures — they catch total failures like a crashed process or network partition, but a TCP SYN probe misses an app that accepts TCP yet returns 500 on every request, and a trivial /healthz that always returns 200 masks a broken app. Passive outlier detection watches real traffic and ejects after repeated 5xx (Envoy: 5 consecutive, ejection 30 s doubling to ~300 s) — it catches silent degradation like a drained DB pool, but has no coverage during low traffic. Use both: active is the safety net, passive catches the common live-failure modes." },
    { q: "Why are sticky sessions an anti-pattern, and what is the correct fix? Contrast with consistent hashing.", a: "Sticky sessions pin each client to one backend (via a cookie or IP hash) to hide session state stored in that backend's memory. This causes 1.5–2.5× load imbalance because the LB can no longer rebalance, and it creates a per-session SPOF: if the pinned backend crashes, the session is lost with no failover. The correct fix is externalizing session state to a distributed store (Redis) keyed by session ID, so any backend can serve any request and the LB routes freely with power-of-two-choices. Consistent hashing is a different tool — for CACHE locality, not user state: it maps a key to the same backend with only ~1/N keys remapping on membership change (using 150–300 virtual nodes per backend to even the ring), maximizing cache hits across shards." },
    { q: "Explain retry amplification across microservice layers and the mitigations that bound it.", a: "When a backend is overloaded, retries add the exact load that caused the overload, so it falls further behind. With N clients × 1 retry that is 2× load; across K service layers each retrying once, worst-case amplification approaches 2^K (≈1024× at K=10). The mitigations: a circuit breaker returns 503 immediately after N failures so the backend gets no new load and can drain (states: closed → open → half-open); a global retry budget caps total retries at ~10% of RPS so amplification stays bounded no matter how many clients retry; exponential backoff with jitter (delay = min(base·2^attempt + rand(0,base), max)) desynchronizes the retry burst to avoid a thundering herd; and load shedding drops new requests with a fast 503 when queue depth exceeds a threshold. Alert on retry rate above 0.1% as the earliest storm warning." },

If an LB stored per-flow state (TLS session, HTTP/2 stream state) locally, a re-hashed flow lands on an LB with no memory of it and the client must reconnect. So the LBs must be stateless — each connection self-contained — or share session state in a distributed cache. Google's Maglev relaxes this by using consistent hashing of the 5-tuple so the same flow maps to the same LB even as machines join and leave: when one LB is removed only ~1/N flows remap, the rest continue uninterrupted." },
