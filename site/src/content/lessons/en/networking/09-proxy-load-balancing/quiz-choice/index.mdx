  lang="en"
  question="A fleet of 50 backends serves requests whose cost varies wildly (1 ms API calls mixed with 200 ms uploads). Which balancing algorithm is the right default, and why?"
  choices={[
    { label: "Power-of-two-choices: sample two random backends per request and route to the less loaded one — O(1), ~12% imbalance, and the randomness desynchronizes the herd when a slow backend recovers.", correct: true },
    { label: "Round-robin: it distributes requests perfectly evenly across all 50 backends.", misconception: "Round-robin distributes request COUNT evenly, not load. A 200 ms upload and a 1 ms call each consume one turn, so a backend handling uploads falls behind despite getting its fair share." },
    { label: "Pure least-connections: always route to the backend with the fewest active connections, so load is perfectly even.", misconception: "Least-connections adapts to load but herds: when a recovered backend's count drops, every client sees the same minimum at once and stampedes it. It also needs an O(log N) scan per request." },
    { label: "IP-hash: hashing the client IP pins each client to one backend, spreading load deterministically.", misconception: "IP-hash is a session-affinity tool, not a load balancer. It clusters badly behind NAT and ignores real-time load entirely." },
  ]}

    { label: "An active-passive hot standby — it fails over instantly with zero connection loss.", misconception: "Active-passive failover takes 10–30 s to detect and promote, long enough for users to notice. Anycast + ECMP converges in under a second across an active cluster." },
    { label: "DNS round-robin across the LB IPs — clients pick a live one automatically.", misconception: "DNS TTLs of 60–300 s mean clients keep hitting the dead LB until the cache expires; DNS has no per-request health awareness. DNS does geo-routing, not LB failover." },
    { label: "Just give the LB more CPU and memory so it never crashes.", misconception: "Vertical scaling does not eliminate a single point of failure — the machine, NIC, rack, or power can still fail. Redundancy across machines is the only fix." },

<Recap lang="en">
The through-line of the unit is one tradeoff triangle — speed, fairness, and state — resolved at every layer. Power-of-two-choices is the fair O(1) default; L7 buys content routing and 5xx retries at 100× the L4 latency; active plus passive health checks cover both crashes and silent 5xx; sticky sessions are a stateful-backend workaround that Redis replaces; retry budgets, circuit breakers, and jitter bound the cascade; and anycast + BGP ECMP removes the LB's own single point of failure at the cost of statelessness.
</Recap>
