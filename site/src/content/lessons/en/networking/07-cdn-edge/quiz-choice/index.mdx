<Quiz

  lang="en"
  question="A site sets Cache-Control: public, max-age=3600 but CDN hit rate sits at 5% with thousands of distinct entries per URL. The most likely single cause?"
  choices={[
    { label: "A Vary: User-Agent (or Vary: Cookie) header fragments every URL into one entry per browser/version/OS or per session — almost none ever reused. Drop the high-cardinality Vary dimension.", correct: true },
    { label: "max-age=3600 is too short, so entries expire before reuse.", misconception: "One hour is plenty for reuse on a busy URL; expiry would lower hit rate uniformly, not explode entry count into thousands per URL. Per-URL cardinality is the Vary footgun signature." },
    { label: "The origin shield is disabled, so edges miss more often.", misconception: "A missing shield raises origin load on misses but does not multiply cache entries per URL. Thousands of entries per single URL points squarely at a high-cardinality Vary header." },
    { label: "Anycast is routing users to the wrong POP.", misconception: "POP selection affects latency, not how many cache slots a URL has. The thousands-of-entries-per-URL symptom is cache-key fragmentation, i.e. Vary." },
  ]}

<Quiz
  id="07-cdn-edge-choice-2"
  lessonSlug="07-cdn-edge"
  lang="en"
  question="A logged-in user loads /account and sees their name; an hour later a different anonymous user hits the same URL and sees the first user's name. CDN logs show cache hits for both. Root cause?"
  choices={[
    { label: "The endpoint reads a session cookie and returns personalised HTML but was not marked Cache-Control: private (nor Vary: Cookie). Cookies are not in the default cache key, so the first response was cached under just the URL and replayed to everyone.", correct: true },
    { label: "Anycast routed both users to the same POP, so they shared a connection.", misconception: "Sharing a POP does not share response bodies — each request is keyed independently. The leak is that cookies are absent from the cache key and the response was not marked private." },
    { label: "The session cookie expired, so the CDN substituted another user's session.", misconception: "CDNs do not swap sessions. The personalised response was simply cached under a cookie-blind key and served to the next requester of that URL." },
    { label: "stale-while-revalidate served a stale copy of the wrong user.", misconception: "SWR controls freshness over time for one keyed entry; it never crosses users. The defect is that a cookie-reading endpoint is cacheable at the shared CDN at all." },
  ]}
/>

<Quiz
  id="07-cdn-edge-choice-3"
  lessonSlug="07-cdn-edge"
  lang="en"
  question="A popular article's edge entry expires across 200 POPs in a region at the same instant; 1000 users request it that second, origin starts returning 503s, and those 503s get cached. Which two layers together would have prevented this?"
  choices={[
    { label: "Origin shield collapses all 200 edge misses in the region into one origin request; stale-while-revalidate serves the stale copy to every user while a single background revalidation runs. Together: one origin request, no user-visible miss.", correct: true },
    { label: "A higher max-age plus Vary: Accept-Encoding.", misconception: "A longer max-age only delays the same synchronous expiry cliff, and Accept-Encoding does nothing for stampedes. The fix is collapsing concurrent misses (shield) and serving stale during revalidation (SWR)." },
    { label: "Switching from GeoDNS to Anycast routing.", misconception: "Routing chooses which POP answers; it does not change what happens when a cached entry expires. Stampede defence is a cache-tier concern, not a routing concern." },
    { label: "Marking the article Cache-Control: private.", misconception: "private disables shared caching entirely, sending every request to origin — the opposite of stampede protection. SWR plus origin shield keep the herd off origin." },
  ]}
/>

  lang="en"
  question="A product page needs hour-stable chrome, a 10-minute-stale description, and a per-user price that must be real-time. no-store gives 300 ms p95; max-age=3600 shows stale prices. What is the senior move?"
  choices={[
    { label: "Edge-side composition: cache chrome and description at the edge with long TTLs, and have an edge worker fetch the price fragment fresh per request (~30 ms) and inject it via HTMLRewriter or ESI.     { label: "no-store the whole page — correctness beats latency.", misconception: "no-store throws away the 90%+ of bytes that are perfectly cacheable just to keep one fragment fresh. Compose the page from per-TTL fragments instead of caching at one granularity." },
    { label: "max-age=5 so the price is at most 5 seconds stale.", misconception: "A 5 s TTL on the whole page still serves stale prices for up to 5 s and re-fetches everything constantly, hammering origin. Real-time price needs a fresh fragment, not a short whole-page TTL." },
    { label: "Put the price in Vary so each price gets its own entry.", misconception: "Vary keys on request headers, not response data, and a per-price entry would be uncacheable noise. The price is fetched live by an edge worker, not encoded in the cache key." },
  ]}

<Recap lang="en">
The unit's through-line is one delivery pipeline: routing (Anycast for scale and DDoS absorption, GeoDNS for control, smart routing to correct BGP's latency blindness) puts the user on the right edge; the cache key (URL + method + Vary) decides what is reusable, and high-cardinality Vary or cookie-blind keys are the classic footguns; the tiered cache plus origin shield and stale-while-revalidate keep the herd off origin; edge workers and edge-side composition assemble per-TTL fragments for fast pages with fresh data; and operations close the loop with cache-tag purge, deploy-triggered invalidation, and per-region observability.
</Recap>
