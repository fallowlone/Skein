  lang="en"
  question="A resolver queries the .com TLD for shop.example.com and gets a response with an empty Answer section but NS and A records present. A junior calls it broken. Why is it actually correct?"
  choices={[
    { label: "It is a referral. A TLD server is iterative — it does not own example.com, so it returns the next-hop nameservers as NS records in Authority plus their glue A/AAAA in Additional, with AA=0 and no Answer. The resolver follows it to the authoritative server.", correct: true },
    { label: "It is broken — a TLD must return the A record for any name under it.", misconception: "A TLD owns only the delegation, not the leaf data. It knows which authoritative server runs example.com and refers the resolver there; it never holds the shop.example.com A record." },
    { label: "The TLD recursed on the resolver's behalf and the answer is just delayed.", misconception: "TLD servers never recurse for callers — RD is cleared on these iterative queries. They return only what they know plus a referral." },
    { label: "The glue records in Additional ARE the final answer for shop.example.com.", misconception: "Glue in Additional is the A/AAAA of the next-hop nameservers (so the resolver can reach them without a circular lookup), not the address of shop.example.com itself." },
  ]}

  lang="en"
  question="You change an A record. A colleague sees the new value; you still get the old one for 40 more minutes, then it flips. Your manager says to wait 24-48 hours for 'propagation'. What is actually happening?"
  choices={[
    { label: "Nothing propagates — DNS has no push. Each downstream cache independently holds its copy until its own TTL counts to zero, then re-queries. Your resolver cached the old value with time left on its TTL; your colleague's cache had already expired. The worst-case wait is the old TTL, not a fixed 24-48 h.", correct: true },
    { label: "The authoritative server pushes the update outward and it reaches resolvers in waves over 24-48 hours.", misconception: "There is no push and no wave. Authoritative servers never notify recursive caches; caches pull the new value only when their TTL expires." },
    { label: "Your ISP is throttling the update and a different ISP delivered it faster.", misconception: "It is not throttling — it is just that your resolver's cache entry still had TTL remaining while your colleague's had expired. Same mechanism, different cache age." },
    { label: "Restarting your browser would have forced the new value immediately.", misconception: "The stale entry lives in the upstream recursive resolver, not the browser. The browser cache is separate and short; restarting it does not flush the resolver." },
  ]}

  lessonSlug="04-dns-resolution"
  lang="en"
  question="A flood of lookups hits an authoritative server for thousands of non-existent subdomains during an attack. Why does this barely raise authoritative load on a healthy setup?"
  choices={[
    { label: "Negative caching (RFC 2308). NXDOMAIN and NODATA answers are cached for min(SOA.MINIMUM, SOA.TTL), so repeated lookups for the same non-existent names are served from the resolver, not the authoritative. SERVFAIL is also briefly cached to prevent tight retry loops.", correct: true },
    { label: "Authoritative servers ignore queries for names that do not exist, so they cost nothing.", misconception: "They do answer — with a signed NXDOMAIN/NODATA. The reason load stays low is that resolvers cache those negative answers, not that the server drops them." },
    { label: "The resolver refuses to forward queries for names it has never seen before.", misconception: "Resolvers forward unknown names normally — that is how anything new resolves. It is the cached negative answer that absorbs the repeat traffic." },
    { label: "TTL applies only to positive answers, so each NXDOMAIN does hit the authoritative every time.", misconception: "TTL applies to negative answers too. NXDOMAIN/NODATA caching duration is governed by SOA.MINIMUM precisely so typo storms do not flood the authoritative." },
  ]}
/>

<Quiz

  lang="en"
  question="A privacy product wants both to hide which domains users resolve from network observers AND to prevent an off-path attacker from injecting a forged answer. Which combination actually delivers both?"
  choices={[
    { label: "Encrypted transport (DoH/DoT/DoQ) plus DNSSEC validation. Encryption hides the query from observers on the path; DNSSEC authenticates the answer cryptographically. They are orthogonal — neither alone gives both properties.", correct: true },
    { label: "DoH alone is enough — TLS both hides the query and proves the answer is genuine.", misconception: "DoH hides and authenticates the channel to the resolver, but the resolver's own upstream answer can still be forged or wrong; only DNSSEC authenticates the record data end-to-end." },
    { label: "DNSSEC alone is enough — a signed answer cannot be observed.", misconception: "DNSSEC signs data but sends it in plaintext over UDP/53; an eavesdropper still sees every domain queried. It gives integrity, not confidentiality." },
    { label: "EDNS Client Subnet plus a low TTL.", misconception: "ECS leaks the client's subnet to upstream servers (the opposite of privacy) and TTL is about freshness, not confidentiality or integrity. Neither addresses the requirement." },
  ]}

<Recap lang="en">
The through-line of the unit is one resolution model: a recursive resolver walks root to TLD to authoritative following referrals (NS in Authority, glue in Additional); every cache holds answers — positive and negative — only as long as the TTL permits, so "propagation" is just independent expiry; DNSSEC layers a signature chain from the root trust anchor down through DS/KSK/ZSK, and a broken link splits users along the validating/non-validating line; and encrypted transport (DoH/DoT/DoQ) hides queries but is orthogonal to DNSSEC's integrity. Most production failures — stale records, NXDOMAIN floods, post-rollover SERVFAIL, blocked-TCP truncation — resolve back to one of those four mechanisms.
</Recap>
