## Snippet 1 — a +trace referral

```
$ dig +trace shop.example.com A

;; received referral from the .com TLD:
example.com.   172800  IN  NS  ns1.example.net.
example.com.   172800  IN  NS  ns2.example.net.
;; (Additional section empty)

;; query to ns1.example.net times out
;; query to ns2.example.net times out
;; SERVFAIL
```

  id="04-dns-resolution-code-1"

  lang="en"
  question="The .com referral lists the nameservers but the lookup SERVFAILs. The NS names are ns1/ns2.example.net. What is the most useful first read?"
  choices={[
    { label: "The nameservers are out-of-bailiwick (example.NET, not example.com), so no glue is needed or sent — the empty Additional is normal. The resolver must separately resolve ns1.example.net, which is timing out. The real fault is reachability/resolution of the example.net nameservers, not missing glue.", correct: true },
    { label: "It is missing glue: the empty Additional section proves the delegation is broken.", misconception: "Glue is only required for in-bailiwick nameservers (ns1.example.com). These are in example.net, an out-of-bailiwick zone the resolver can resolve independently, so empty Additional is expected, not a bug." },
    { label: "The TTL of 172800 is too high and is causing the timeout.", misconception: "172800 s (2 days) is a normal NS TTL and has nothing to do with a timeout. The lookup fails because both example.net nameservers are unreachable, not because of TTL." },
    { label: "The .com TLD should have returned the A record directly.", misconception: "A TLD never holds leaf A records; it returns the delegation (NS) and refers onward. The failure is downstream at the example.net nameservers." },
  ]}

## Snippet 2 — a zone file edit

```dns
$ORIGIN example.com.
@   IN  SOA  ns1.example.com. admin.example.com. (
            2026051300  ; serial  (was 2026051905)
            7200        ; refresh
            3600        ; retry
            1209600     ; expire
            300 )       ; minimum (negative-cache TTL)
@       IN  NS    ns1.example.com.
@       IN  CNAME shop.cdnprovider.net.
www     IN  CNAME shop.cdnprovider.net.
```

<Quiz
  id="04-dns-resolution-code-2"
  lessonSlug="04-dns-resolution"
  lang="en"
  question="This zone edit has TWO defects that will bite in production. What are they?"
  choices={[
    { label: "(1) The serial was decremented (2026051905 to 2026051300), so secondaries treat the zone as older and silently skip the update — replication breaks. (2) A CNAME sits at the apex (@) alongside SOA and NS, which RFC 1034 forbids because CNAME would override every other record type there; use ALIAS/ANAME or an HTTPS record instead.", correct: true },
    { label: "The minimum (300) is too low for negative caching and the NS record is missing glue.", misconception: "300 s is a fine negative-cache TTL, and an in-zone NS like ns1.example.com gets glue from the parent .com delegation, not from this file. The real defects are the decremented serial and the apex CNAME." },
    { label: "The refresh and retry are swapped; everything else is valid.", misconception: "Refresh (7200) above retry (3600) is the normal ordering. The actual breakers are the decremented serial and the forbidden apex CNAME." },
    { label: "www CNAME pointing off-domain is illegal.", misconception: "A CNAME on a non-apex label like www pointing to another domain is completely legal and common for CDNs. The illegal one is the apex (@) CNAME; the other defect is the decremented serial." },
  ]}
/>

## Snippet 3 — a DNSSEC diagnosis

```
$ dig @1.1.1.1 +dnssec api.bank.example A
;; ->>HEADER<<- opcode: QUERY, status: SERVFAIL, id: 41832
;; flags: qr rd ra; QUERY: 1, ANSWER: 0

$ dig @1.1.1.1 +cd api.bank.example A     # +cd = checking disabled
;; ->>HEADER<<- status: NOERROR; flags: qr rd ra cd; ANSWER: 1
api.bank.example.   60   IN   A   203.0.113.42
```

<Quiz
  id="04-dns-resolution-code-3"
  lessonSlug="04-dns-resolution"
  lang="en"
  question="Validating resolver returns SERVFAIL, but the same query with +cd returns a clean A record. What does this prove, and what is the customer impact?"
  choices={[
    { label: "The data exists and is correct on the authoritative server (+cd disables DNSSEC checking), so the failure is in the DNSSEC chain — most often a DS at the parent that no longer matches the zone's KSK after a rollover. Validating resolvers mark it BOGUS and SERVFAIL; non-validating resolvers serve it, so roughly 30-40% of users are down while the rest are fine. SERVFAIL clears within the DS cache TTL once the chain is fixed.", correct: true },
    { label: "The authoritative server is down; +cd is reading from a stale cache.", misconception: "+cd returns a live NOERROR answer, so the authoritative is up and serving correct data. The failure is validation, not availability." },
    { label: "The A record points to the wrong IP and DNSSEC is correctly rejecting it.", misconception: "DNSSEC verifies signatures, not whether an IP is 'right'. +cd shows the signed-or-not data is present; the break is in the signature chain (DS/KSK), not a wrong IP." },
    { label: "1.1.1.1 is rate-limiting the query; retry from 8.8.8.8 will succeed.", misconception: "Any DNSSEC-validating resolver (8.8.8.8, Quad9 included) returns the same SERVFAIL because the chain is broken upstream. The +cd success rules out rate limiting." },
  ]}
/>

## Snippet 4 — a resolver config and a latency reading

```
# /etc/unbound/unbound.conf (excerpt)
server:
    serve-expired: yes
    serve-expired-ttl: 86400

$ dig +short @127.0.0.1 whoami.cloudflare TXT CH
"AMS"
$ dig +short @127.0.0.1 example.com A
;; Query time: 70 msec      # every query, never cached lower
```

<Quiz
  id="04-dns-resolution-code-4"
  lessonSlug="04-dns-resolution"
  lang="en"
  question="serve-expired is on, the resolver's nearest Cloudflare PoP is AMS, yet example.com costs 70 ms on every query and never drops to sub-ms. Which two readings are correct?"
  choices={[
    { label: "(1) serve-expired (RFC 8767, stale-while-revalidate) only kicks in when the upstream is unreachable past TTL — it improves availability during outages, not steady-state latency, so it does not explain the constant 70 ms. (2) A constant 70 ms with no cached fast path means the answer is not being cached: likely TTL=0, a very short TTL expiring between queries, or DNSSEC validation discarding the response.", correct: true },
    { label: "serve-expired is the cause of the 70 ms — disabling it will make queries fast.", misconception: "serve-expired serves stale data faster during outages; it never adds latency to a healthy query. The constant 70 ms is a caching failure (TTL=0 or validation discard), unrelated to this directive." },
    { label: "whoami.cloudflare returning AMS means the resolver is misrouted and that is the 70 ms.", misconception: "AMS is just the PoP that answered (Amsterdam); a single anycast hop is fine. The 70 ms recurring on every query is about the answer not being cached, not PoP selection." },
    { label: "70 ms is normal for a warm cache; nothing is wrong.", misconception: "A warm cache returns in sub-ms to low-ms. A steady 70 ms means every query is doing the full upstream walk — the answer is not landing in cache (TTL=0, expiry, or DNSSEC discard)." },
  ]}
/>

<Recap lang="en">
Every DNS incident is read in artefacts: a +trace referral tells you whether glue is even required (in-bailiwick vs out-of-bailiwick) and where the walk stalls; a zone file exposes decremented serials and forbidden apex CNAMEs at a glance; a SERVFAIL that clears under +cd is a DNSSEC chain break, almost always a DS-vs-KSK mismatch after a rollover; and a constant query time means the answer is not being cached, while serve-expired only helps during outages. Diagnose from the artefact, name the broken link, then fix the one mechanism it points to.
</Recap>
