Glue breaks the cycle by handing over ns1's IP directly. Missing glue causes intermittent SERVFAIL or referral loops. Out-of-bailiwick nameservers (ns1.someprovider.net) need no glue because the resolver can resolve them via a different zone." },
    { q: "Why is 'DNS propagation' a misleading term, and what is the correct operational SOP for a planned record change?", a: "Nothing propagates: DNS has no push. The authoritative never notifies caches; each downstream cache independently holds its copy until its own TTL counts to zero, then pulls the new value. So a change appears at different times purely because caches were populated at different moments and expire on their own clocks — the worst case is the old TTL, not a fixed 24-48 hours. The SOP: about a week before the change, lower the TTL (e.g. to 60 s) and wait for the old high TTL to expire everywhere; make the change (max staleness is now 60 s); after it stabilises, raise the TTL back up to cut query load." },
    { q: "What is negative caching, what durations govern it, and why does it matter under load?", a: "Negative caching stores the fact that a name does not exist (NXDOMAIN) or has no record of the requested type (NODATA), so repeated lookups for the same non-existent name are answered from the resolver instead of hitting the authoritative. The duration is min(SOA.MINIMUM, SOA.TTL) per RFC 2308, typically 1-3 hours. SERVFAIL is cached only briefly (roughly 30 s to 5 min per RFC 9520) — short enough not to amplify an outage, long enough to stop a tight retry loop. Without negative caching, a typo storm or an attack flood of bogus subdomains would hit the authoritative on every query and could overwhelm it." },
    { q: "Describe the DNSSEC chain of trust, the ZSK/KSK split, and the single most common rollover failure.", a: "Every validating resolver hardcodes one trust anchor: the root KSK fingerprint. Validation walks down: the root KSK signs the root DNSKEY, the root ZSK signs the .com DS, the .com KSK (matched against that DS) signs .com's DNSKEY, the .com ZSK signs example.com's DS, and so on to the leaf, whose ZSK signs the A record via an RRSIG. Two key roles: the ZSK signs actual data and rotates often; the KSK signs only the DNSKEY RRset and rotates rarely, with its hash published as a DS at the parent. The split keeps frequent ZSK rotation cheap (no parent coordination). The classic failure: roll the KSK but forget to update the DS at the parent registrar — the parent still hashes the old KSK, the chain snaps, validating resolvers return SERVFAIL (BOGUS) while non-validating ones still serve, so roughly 30-40% of users break." },

Encrypted transport hides the query from network observers on the path between client and resolver — DoH on port 443 is indistinguishable from HTTPS and resists port-blocking censorship; DoT on 853 is trivially blocked by one firewall rule; DoQ adds QUIC connection migration and 0-RTT for mobile. But encryption says nothing about whether the answer is genuine. DNSSEC authenticates the record data cryptographically end-to-end, proving it was signed by the legitimate zone, but sends it in plaintext so the query is still visible. DoH without DNSSEC hides the query but cannot verify the answer; DNSSEC without encryption verifies the answer but leaks the query. Full protection — confidentiality plus integrity — needs both, and it is the pair that closes off-path cache poisoning (Kaminsky, SAD DNS)." },
