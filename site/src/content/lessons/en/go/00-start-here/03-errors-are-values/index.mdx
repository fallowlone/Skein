<Hook>
In most languages, when something goes wrong, the code throws an exception that flies up the call stack until something catches it — possibly far away, possibly never. Go deleted that entire mechanism. There is no `try`, no `catch`, no `throw`. Instead, a function that can fail simply returns its error alongside its result, and you look at it. Right there. Every time.
</Hook>

<Crux>Errors are ordinary return values: a fallible function returns <code>(result, err)</code>, and the caller checks <code>if err != nil</code> immediately — no exceptions, no hidden control flow.</Crux>

<Explanation>

## The two-line if

A function that reads a file does not return just the content. It returns two things:

That pattern — call, check, return early — is roughly a third of all Go code ever written. You will type it a thousand times, and after the fiftieth it becomes invisible: your eyes slide past the `if err != nil` frames straight to the lines where things actually happen.

## Three rules that replace exceptions

**One: handle it where it happens.** The check sits next to the call, not ten frames up the stack. When you read Go, every failure is handled at the exact line that could fail — there is no "where was this caught?" archaeology.

**Two: `nil` means fine.** An error value of `nil` means nothing went wrong. This is the only convention: you never check a boolean flag, never catch by type. `err != nil` is the complete test, everywhere.

**Three: return it if it is not yours.** Most error handling in Go is just passing the problem up: `return err`. Only the layer that knows what to do — retry, fall back, tell the user — converts the error into action. Everything in between forwards it unchanged. Unit `01-language-core` builds real machinery on top of this habit; the habit itself never changes.

<Inset kind="why" lang="en">
Isn't writing `if err != nil` after every call horribly verbose? It looks that way for exactly one week. Then two things happen: `gofmt`-aligned error frames become visually silent, and you realize what the verbosity bought — every function documents its failure in its signature (`string, error`), and no failure can silently teleport past you the way an uncaught exception does. Go traded three saved lines for zero invisible control flow, and teams that maintain code for years consider it a bargain.
</Inset>

<KeyTakeaway>An error is a value like any other: check <code>err != nil</code> next to the call, use the data only on <code>nil</code>, and otherwise <code>return err</code> upward. <Recap lang="en">
Go has no exceptions: fallible functions return <code>(result, err)</code>, and you test <code>err != nil</code> immediately. <code>nil</code> means fine — use the result. Anything else means failure — handle it here or <code>return err</code> to whoever knows what to do. Handle where it happens, forward the rest, never trust data beside a non-nil error. With the toolchain, the first program, and this habit, you own everything unit 01 assumes: it teaches you types next, and every type in Go carries errors exactly this way.
</Recap>
