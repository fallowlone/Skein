<Hook>
Every tutorial in every language starts with printing a line — and every learner skips it as trivial. Do not skip this one. In Go the first program teaches the only three facts the rest of the track stands on: where the program starts, how you run it, and what a compiler error looks like when you are the one who caused it.

<Crux>A Go program starts at <code>func main</code> in package <code>main</code>; <code>go run</code> executes it, and compiler errors point at the exact line before anything runs.</Crux>

## Twelve lines that do something

Create a file called `hello.go` and type exactly this:

Run it with `go run hello.go`. You see `hi`. That output is the entire feedback loop of Go development: edit, run, read. Everything in units 01 through 04 is a longer version of these thirty seconds.

## Break it on purpose

Now delete one closing quote so the line reads `fmt.Println("hi)` and run again. You do not get `hi` and you do not get silence — you get an error naming the file, the line number, and the missing quote, and nothing executes. This is the compiler earning its keep: in Go, broken code never half-runs. Read the error top to bottom — file first, then line, then what it wanted — because that reading order is a skill this track will reuse on every single unit.

Fix the quote, run once more, see `hi`. You now know the complete loop: write, run, read the output — or read the error, which is also output, and usually the more useful kind.

<Inset kind="why" lang="en">
Why does Go make you declare `package main` for a five-line program? Because the same rule scales unchanged to five thousand files: the toolchain always knows what is executable and what is a library by reading one word. Ceremony that never grows is not bureaucracy — it is the reason a Go repository of any size is navigable on day one.
</Inset>

<KeyTakeaway>Execution starts at <code>func main</code> in package <code>main</code> and nowhere else. <code>go run</code> compiles the whole file before running any of it, so an error means nothing executed — read it as file, line, complaint, fix, repeat.</KeyTakeaway>

<Recap lang="en">
A Go program is a file in package <code>main</code> with a <code>func main</code> where execution starts. You develop in a loop of write, <code>go run</code>, read — and when the code is broken, what you read is a compiler error naming the file and line, because nothing runs until everything compiles. Next: the one Go habit that surprises every newcomer — errors returned as ordinary values, checked with a two-line <code>if</code> you will write a thousand times.
</Recap>
