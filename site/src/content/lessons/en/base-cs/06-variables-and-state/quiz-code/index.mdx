## Snippet 1 — the shared object

```ts
const original = { count: 0 };
const copy = original;       // assigns the reference, not the object
copy.count = 5;              // mutate through copy
console.log(original.count); // ?
```

  question="What does the final line print, and why?"
  choices={[
    { label: "5 — 'const copy = original' copies the reference, so both names point at one object on the heap. 'copy.count = 5' mutates that single object in place, and original reads back the same field.", correct: true },
    { label: "0 — copy is an independent duplicate of original, so mutating it leaves original untouched.", misconception: "Assignment copies the reference, not the object. There is only one object; both names alias it. To get an independent duplicate you must copy explicitly, e.g. { ...original }." },
    { label: "It throws — both are const, so 'copy.count = 5' is illegal.", misconception: "const seals the binding (you cannot do copy = something else), but it does not freeze the object. Mutating a property of the referenced object is allowed under const." },
    { label: "undefined — assigning original to copy clears original's fields.", misconception: "Assignment never clears the source. It copies the reference value into copy's cell; original keeps its reference and its field, which the mutation then changes to 5." },
  ]}

## Snippet 2 — primitive vs object side by side

```ts
let n = 10;
let m = n;          // copies the value 10
m = m + 1;          // changes m's own cell

let p = { v: 10 };
let q = p;          // copies the reference
q.v = q.v + 1;      // mutates the shared object

console.log(n, q === p, p.v); // ?
```

  id="06-variables-and-state-code-2"
  lessonSlug="06-variables-and-state"

  question="What is printed?"
  choices={[
    { label: "10 true 11 — n is a primitive, so m got an independent copy and changing m left n at 10. p and q share one object (q === p is true), so mutating through q makes p.v read 11.", correct: true },
    { label: "11 true 11 — incrementing m also incremented n because they started equal.", misconception: "Primitives copy by value; m and n are separate cells. Changing m never touches n. Only the object side is shared, which is why p.v changes — not n." },
    { label: "10 false 10 — p and q are different objects, so q === p is false and p.v stays 10.", misconception: "'let q = p' copies the reference, so q and p point at the same object: q === p is true and the mutation through q is visible as p.v === 11." },
    { label: "10 true 10 — q === p is true but mutating q cannot change p.", misconception: "If q === p, there is exactly one object behind both names. A mutation through either name is the same write, so p.v becomes 11." },
  ]}
/>

## Snippet 3 — scope shadowing

```ts
let x = 1;
{
  let x = 2;        // a new binding in the inner block
  x = x + 10;       // writes to the inner x's cell
  console.log(x);   // inner
}
console.log(x);     // outer
```

<Quiz
  id="06-variables-and-state-code-3"
  lessonSlug="06-variables-and-state"
  lang="en"
  question="What do the two console.log lines print, in order?"
  choices={[
    { label: "12 then 1 — the inner 'let x' declares a separate variable (its own cell) that shadows the outer x inside the block. All writes there hit the inner cell; the outer x is never touched and stays 1.", correct: true },
    { label: "12 then 12 — there is only one x, so the inner reassignment carries out to the outer one.", misconception: "'let x' inside the block creates a new binding to a new cell. Inside the block, the name x resolves to that inner cell; the outer x keeps its own value 1." },
    { label: "2 then 1 — the inner block cannot reassign x, so it stays 2 inside.", misconception: "The inner x is a normal let; 'x = x + 10' reads 2 and writes 12 to the inner cell. The block can freely mutate its own binding." },
    { label: "It throws — you cannot declare x twice.", misconception: "Re-declaring x in a nested block is legal: each scope has its own binding. The inner declaration shadows, rather than collides with, the outer one." },
  ]}
/>

## Snippet 4 — the swap

```ts
let a = 1;
let b = 2;
a = b;
b = a;
console.log(a, b);  // ?
```

<Quiz
  id="06-variables-and-state-code-4"
  lessonSlug="06-variables-and-state"
  lang="en"
  question="What is printed, and what is the fix if the intent was to swap a and b?"
  choices={[
    { label: "2 2 — 'a = b' overwrites a with 2, destroying the original 1, so 'b = a' just copies 2 back. Because assignment is a destructive overwrite, swapping needs a temp: let t = a; a = b; b = t.", correct: true },
    { label: "2 1 — the two assignments swap the values correctly.", misconception: "After 'a = b', a's old value 1 is gone. 'b = a' reads the new a (2), so both end at 2. A correct swap saves the original first into a temporary." },
    { label: "1 2 — the assignments cancel out and leave the originals.", misconception: "They do not cancel. 'a = b' overwrites a in place to 2; the original 1 is lost before 'b = a' runs, so b becomes 2, not 1." },
    { label: "1 1 — assignment copies the left value into the right.", misconception: "Assignment writes the right-hand value into the left-hand cell, not the reverse. 'a = b' makes a hold 2; both end up 2." },
  ]}
/>

<Recap lang="en">
Tracing by hand is the whole skill: a copied primitive (m, n) lives in its own cell and ignores changes to the other; a copied reference (p, q) makes both names alias one object so a mutation propagates and === is true; an inner 'let' creates a new binding that shadows the outer name without touching its cell; and a naive 'a = b; b = a' fails because each assignment is a destructive overwrite, which is why a real swap needs a temporary. Follow the cells and the answer is never a surprise.
</Recap>
