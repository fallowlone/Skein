## Snippet 1 — event-loop ordering

```js
console.log("start");

setTimeout(() => {
  console.log("timeout");   // a callback
}, 0);

console.log("end");
```

The synchronous 'end' runs before the queued callback, because a callback runs only when the call stack is empty. The 0 is a queueing delay, not an immediate run." },
    { label: "start, end (the timeout callback never runs because the delay is 0).", misconception: "A 0 delay still queues the callback; it runs after the synchronous code finishes. 'timeout' does print — it is simply last, once the stack is empty." },
    { label: "timeout, start, end — the timer fires before anything else.", misconception: "Synchronous code always runs first. The timer only makes the callback eligible to be queued; the event loop will not run it until 'start' and 'end' have printed and the stack is empty." },

## Snippet 2 — two threads, one shared variable

```text
shared: total = 0

Thread A:                  Thread B:
  r = read(total)            r = read(total)   // both read 0
  r = r + 1                  r = r + 1
  write(total, r)            write(total, r)   // both write 1
```

<Quiz
  id="12-time-and-concurrency-code-2"
  lessonSlug="12-time-and-concurrency"
  lang="en"
  question="Both threads run this once, in parallel, on two cores. After both finish, what can total be — and what is this called?"
  choices={[
    { label: "It can be 1 or 2. If the steps interleave so both read 0 before either writes, both write 1 and one increment is lost (final 1). Only a non-overlapping order gives 2. The bad outcome is a race condition — specifically a lost update.", correct: true },
    { label: "Always 2, because each thread adds 1 and there are two threads.", misconception: "That holds only if the threads do not overlap. Because read-add-write is three separate steps, the two threads can both read 0 first, then both write 1 — losing one increment. The result depends on interleaving, so it is not always 2." },
    { label: "Always 1, because the two writes collide and cancel out.", misconception: "Writes do not cancel; they overwrite. If the threads happen not to overlap, you correctly get 2. The value is 1 only in the interleaving where both read the same old value. The outcome is nondeterministic, not always 1." },
    { label: "It is undefined behaviour and the program crashes.", misconception: "A data race on a simple counter does not crash here; it silently produces a wrong number (often 1 instead of 2). The danger is exactly that it looks fine and just loses updates — a race condition, not a crash." },
  ]}
/>

## Snippet 3 — the same code under load

```text
total = 0
spawn 1000 threads, each does:  total = total + 1   // no synchronization
join all threads
print(total)
```

<Quiz
  id="12-time-and-concurrency-code-3"
  lessonSlug="12-time-and-concurrency"
  lang="en"
  question="On a multi-core machine, what is the likely printed value and why?"
  choices={[
    { label: "Often less than 1000, and it varies run to run. total = total + 1 is read-add-write; with no synchronization, threads interleave and overwrite each other's updates, so increments are lost. The lost count depends on timing.", correct: true },
    { label: "Exactly 1000 every run — 1000 threads, each adds 1.", misconception: "Only if the increments never overlap, which is not guaranteed without synchronization. In practice many threads read the same value before writing, so updates are lost and the total comes out below 1000, differently each run." },
    { label: "Exactly 0, because the threads overwrite total back to its start.", misconception: "Threads do not reset total to 0; each writes (old value it read) + 1. Some increments do land. The result is some number below 1000, not 0 — the lost updates reduce it, they do not erase it." },
    { label: "Exactly 1000 because spawning threads forces them to take turns.", misconception: "Spawning threads does not serialise them — on multiple cores they run in parallel and can interleave freely. Taking turns through the shared update is exactly what is missing here; that is what a lock would add." },
  ]}
/>

## Snippet 4 — adding a lock

```text
total = 0
lock = new Lock()

each of 1000 threads does:
  lock.acquire()
  total = total + 1     // protected: only one thread in here at a time
  lock.release()
```

<Quiz
  id="12-time-and-concurrency-code-4"
  lessonSlug="12-time-and-concurrency"
  lang="en"
  question="What does the lock change, and what is the cost?"
  choices={[
    { label: "It makes the read-add-write run as one indivisible step: a thread must hold the lock to enter, so no two threads overlap on total. The result is now exactly 1000 every run. The cost is that this section runs serially — threads queue for the lock instead of running it in parallel.", correct: true },
    { label: "It speeds the threads up by letting them all update total at once.", misconception: "A lock does the opposite of 'all at once' — it forces threads through the protected section one at a time. That is how it removes the race, but it also removes parallelism for that section, so it is a cost, not a speedup." },
    { label: "It has no effect; the race can still happen inside the lock.", misconception: "While one thread holds the lock, no other can enter the protected section, so the read-add-write cannot interleave. The race is gone — the result is exactly 1000. The lock is precisely what serialises the shared update." },
    { label: "It removes the need for the threads entirely.", misconception: "The threads still run and still do the work; the lock only controls when they may enter the shared section. It coordinates the threads, it does not replace them." },
  ]}
/>

<Recap lang="en">
Reading concurrency means reading *when things run*. The event loop puts synchronous code first and callbacks last (start, end, timeout). When work is split across **threads** that share state, a plain `total = total + 1` is really read-add-write, so parallel threads can interleave, read the same value, and overwrite each other — a **data race** that loses updates and gives a wrong, nondeterministic total. A **lock** fixes it by making the shared section indivisible: one thread at a time, exact result restored. The cost is that the locked section runs serially. The senior move is to keep the lock for correctness and make the locked region as small as possible.
</Recap>
