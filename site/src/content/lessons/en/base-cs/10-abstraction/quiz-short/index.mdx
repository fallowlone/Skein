    { q: "What is abstraction, and what are its two sides?", a: "Abstraction is hiding detail behind a name so you can use a thing without knowing how it works inside. It has two sides. The interface is the visible surface a user depends on — for a function, its name, its inputs, and its return value; it is a contract, a promise. The implementation is the hidden machinery that fulfils that promise — the function body and the instructions it runs. The point of the split is that the implementation can be rewritten freely as long as the interface keeps its promise, so callers never change. You have used abstractions since early units: a variable name hides a memory address, a function call hides a body." },
    { q: "What is a method, and what does encapsulation give you?", a: "A method is a function stored as a field of an object that operates on that object's own data, reaching it through this. An object then has data fields holding its state and method fields holding the operations on that state — together a bundle: one named unit holding data with its operations. The bundle's interface is the set of methods you can call; the field layout is the hidden implementation. Bundling data with its operations while hiding the internal data from outside code is encapsulation. The payoff: exactly one place — the methods — touches the data, so you can rename or restructure the fields and every caller stays unchanged because the interface held." },
    { q: "What is a module, and what does its boundary actually enforce?", a: "A module is a unit of code that groups related definitions behind a boundary. By default every name inside is private — visible only to other code in the same module, the same way a variable is scoped to its function. A module marks chosen names as exports; the set of exported names is its public interface, and everything else is hidden implementation. The boundary is language-enforced and does two concrete jobs: outside code cannot read or overwrite a module's private state, and a change to a private name cannot break any code outside. So the author can rewrite all internals freely — the boundary turns the convention 'do not touch my internals' into a guarantee." },
    { q: "What is namespacing, and why does a large program need it?", a: "Namespacing is grouping names under a module so that identical short names do not clash. Two modules can both define a function called format — one for dates, one for currency — and they do not collide because each is reached through its own module handle: dateModule.format and currencyModule.format. The module name in front gives each name a separate home. A large program needs this because in a single flat space every name would compete with every other; the second format would overwrite the first, and the program would run out of good names. Each module being a fresh space is what keeps large programs writable." },
    { q: "What is a leaky abstraction, and why do all non-trivial abstractions leak?", a: "An abstraction is leaky when it fails to fully hide the layer below — when detail from underneath shows through and you are forced to think about a level you were promised you could ignore. Leaks surface most often when the lower layer fails or runs slow: while everything works the hidden layer stays hidden, but the moment it breaks or drags it surfaces. Joel Spolsky's Law of Leaky Abstractions states all non-trivial abstractions are leaky to some degree. They leak because the layer below is still doing real work that can go wrong in ways the interface never described — time, memory limits, a finite stack, hardware faults. The interface describes the result; it cannot describe away the physics, and that gap is where every leak comes from." },
    { q: "If abstractions leak, why is the practical lesson NOT to stop using them or stop learning the lower layers?", a: "Both extremes are wrong. Abstraction is not optional — without it, no program past a few lines could be written, because a human can only hold a few things in mind and a real program is billions of gate switches per second. And no abstraction over a real machine is leak-proof. The mature view holds both facts at once: use the abstraction for the reasoning it buys you and still understand the layer below for the day it leaks. An abstraction saves you time working but not time learning. That is exactly why this track climbed the whole layer stack — gates, machine code, a language, then constructs — teaching every layer beneath the ones you will mostly work in." },
