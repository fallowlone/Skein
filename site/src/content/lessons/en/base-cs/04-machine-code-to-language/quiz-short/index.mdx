    { q: "Assembly already gives machine code readable names. Why invent high-level languages on top of it?", a: "Assembly fixes readability but leaves two problems. First, it is CPU-specific: x86-64 mnemonics name x86-64 opcodes, so a program must be rewritten for every new CPU family. Second, it is verbose — each CPU operation is its own line, so a single mathematical expression can take many instructions. High-level languages solve both: one statement can stand for many machine instructions (productivity — IBM reported roughly 20-to-1 over assembly with FORTRAN), and the same source can be translated by a different compiler or interpreter for each CPU (portability). The underlying principle is abstraction: hide the registers, opcodes, and addresses so you can express intent, not mechanism." },
    { q: "Contrast a compiler and an interpreter by what they produce and when they translate.", a: "A compiler translates the entire source program to machine code ahead of time, before the program runs, producing a standalone platform-specific binary. At run time the CPU executes that binary directly with no translation overhead, so compiled code is typically faster, but you must recompile for each target CPU. An interpreter reads the source at run time and carries out each statement as it encounters it — read, decide what it means, execute, move on — and never produces a machine-code binary for your program. Interpreted code is more portable (the same source runs anywhere an interpreter exists) and has no compile step, but it is slower because translation overhead is paid on every statement. The interpreter itself is a compiled binary running its own machine code in response to your statements." },
    { q: "What is JIT compilation, and what problem does the warm-up period reflect?", a: "Just-in-time compilation is a hybrid used by V8, the JVM, and PyPy. The program starts interpreted (or running bytecode through a fast VM); the runtime watches which functions execute most often — the hot spots — and compiles just those to native machine code while the program is already running. You get an interpreter's fast startup and portability plus near-compiled speed on the paths that matter, and the JIT can use run-time information (like the actual types seen) to optimise better than an ahead-of-time compiler. The warm-up period is the cost: the first calls to a function are interpreted (slow) until it has run enough times to be compiled, so peak performance arrives only after warm-up — which is why a Node service ramps up to full speed." },

It provides: (1) memory management — a heap for new objects and, in most modern languages, a garbage collector that automatically frees unreachable objects so you do not call malloc/free; (2) call-stack machinery — stack frames, return addresses, and calling conventions that make function calls and returns work, and whose exhaustion is a stack overflow; (3) the standard library — built-in functions and data structures (I/O, collections, math, strings) whose code lives in the runtime, not your file; and (4) the interpreter or virtual machine for interpreted or bytecode languages (CPython, the JVM, V8). Even compiled C has a thin runtime: libc, startup that sets up the stack and calls main, and exit cleanup.
