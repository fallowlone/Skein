  question="A function add(x, y) is called as add(3, 5). Where do the values 3 and 5 live while add runs, and what does that guarantee?"
  choices={[
    { label: "They are copied into add's own frame as the parameters x and y. The copy gives add a private workspace — it can reassign x or y without touching anything in the caller's frame (pass-by-value for numbers).", correct: true },
    { label: "They stay in the caller's frame and add reads them across the frame boundary by name.", misconception: "A callee cannot name the caller's locals — scope forbids it. Arguments are copied into the callee's frame at the call, so add works on its own cells, not the caller's." },
    { label: "They are written to a shared global region every function can read.", misconception: "Arguments are not globals. They are copied into the new frame, which is private to that call and discarded on return. Nothing global is involved." },
    { label: "Only their addresses are stored, so changing x inside add changes the caller's value.", misconception: "For primitive numbers the values themselves are copied (pass-by-value). Reassigning x inside add changes only add's cell, leaving the caller's argument untouched." },
  ]}

  lang="en"
  question="Function f declares a local variable result. After f returns, code in main tries to use result. What is true?"
  choices={[
    { label: "result was a cell in f's frame. When f returned, that frame was popped and the cell freed, so result no longer exists as a named value. main cannot reference it — its scope was f's body and its lifetime ended with f's frame.", correct: true },
    { label: "result is automatically moved into main's frame so main can keep using it.", misconception: "Locals do not migrate anywhere on return. The frame is popped and its cells are freed for reuse. There is no automatic hand-off of a callee's locals to its caller." },
    { label: "result persists in memory until the program ends; main just needs the right name.", misconception: "The cells are reused by the next call almost immediately. Even before they are overwritten, the name is out of scope — reaching those cells would be a use-after-free bug, not valid access." },
    { label: "main can read result because f's frame is still below main's on the stack.", misconception: "After f returns, f's frame is gone, not below main's. And even while a caller's frame is on the stack, scope rules forbid naming another function's locals." },
  ]}

    { label: "Four — n = 3, 2, 1, 0; the base case does not push a frame.", misconception: "The base-case call countdown(-1) is still a real call that pushes a frame; it just returns immediately without recursing. That frame counts, giving five at peak depth." },
    { label: "Three — recursion only counts the calls that recurse further.", misconception: "Every call, including the one that hits the base case, pushes a frame. Depth at peak is the number of nested live calls, which is n + 2 here, not the number of recursive steps." },

<Recap lang="en">
The unit's through-line is one mechanism seen from several angles: a CALL saves a return address and jumps to a fixed body; each call pushes a LIFO stack frame holding that return address plus the function's locals; parameters are copied in at CALL and the result handed back at RET; a local's scope and lifetime are bounded by its frame, so it vanishes on return; and recursion is just the same frame-push repeated, made safe only by a reachable base case — without one, the frames pile up until the stack overflows.
</Recap>
