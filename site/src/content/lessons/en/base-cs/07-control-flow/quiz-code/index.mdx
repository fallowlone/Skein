## Snippet 1 — count the iterations

```ts
let count = 0;
let i = 1;
while (i <= 5) {   // note: <= , not <
  count++;
  i++;
}
// what is count?
```

## Snippet 2 — the off-by-one boundary

```ts
const a = [10, 20, 30];   // length 3, valid indices 0,1,2
let i = 0;
while (i <= a.length) {   // <= length, not < length
  console.log(a[i]);
  i++;
}
```

<Quiz
  id="07-control-flow-code-2"
  lessonSlug="07-control-flow"
  lang="en"
  question="How many times does the loop body run, and what is the bug?"
  choices={[
    { label: "Four times (i = 0,1,2,3). The test i <= a.length lets i reach 3, but index 3 is past the last valid index 2, so a[3] is undefined — a classic off-by-one. The fix is i < a.length.", correct: true },
    { label: "Three times, one per element — no bug.", misconception: "i <= a.length is true for i = 0,1,2 and also for i = 3 (since 3 <= 3). The body runs four times and reads a[3], which does not exist." },
    { label: "It loops forever because i never reaches a.length.", misconception: "i++ runs each pass, so i reaches 3 and then 4; at i = 4 the test 4 <= 3 is false and the loop exits. It is not infinite — it just runs one time too many." },
    { label: "Zero times because a.length is not a valid index.", misconception: "The test compares i to a.length, it does not index with it. The first test is 0 <= 3 (true), so the body runs; the boundary error is at the end, not the start." },
  ]}
/>

## Snippet 3 — short-circuit as chained jumps

```ts
function check(user) {
  // && stops at the first falsy operand
  if (user && user.active && user.age >= 18) {
    return "allowed";
  }
  return "denied";
}
check(null);   // user is null
```

<Quiz
  id="07-control-flow-code-3"
  lessonSlug="07-control-flow"
  lang="en"
  question="check(null) returns 'denied'. Why does user.active never get evaluated, in machine-level terms?"
  choices={[
    { label: "&& compiles to chained conditional jumps: the first operand (user) is tested, and because it is falsy a conditional jump goes straight to the denied path, skipping the instructions that would read user.active. The later operands are never reached.", correct: true },
    { label: "All three operands are evaluated first, then combined; user.active just returns false.", misconception: "&& short-circuits: it stops at the first falsy operand. Reading user.active on a null user would actually throw — short-circuit is exactly what prevents that, by jumping past those reads." },
    { label: "The CPU evaluates right-to-left, so user.age is tested first and fails.", misconception: "Operands are evaluated left-to-right. user is tested first; being null (falsy), the conditional jump skips the rest before user.active or user.age is ever read." },
    { label: "user.active is evaluated but its result is discarded.", misconception: "It is never evaluated. The conditional jump after testing user transfers control past those reads entirely, which is why no error is thrown on the null user." },
  ]}
/>

## Snippet 4 — nested loop and conditional

```ts
let sum = 0;
for (let i = 0; i < 3; i++) {     // outer: i = 0,1,2
  for (let j = 0; j < 3; j++) {   // inner: j = 0,1,2
    if (i === j) {                // only the diagonal
      sum += 1;
    }
  }
}
// what is sum?
```

    { label: "1 — i === j is true only once across the whole run.", misconception: "i === j is true once per outer iteration, and there are 3 outer iterations, so it is true 3 times: (0,0), (1,1), (2,2)." },

<Recap lang="en">
Tracing by hand is the whole skill. A loop's count is exactly how many times its test stays true — and the boundary operator (`&lt;` vs `&lt;=`) is where off-by-one bugs live, here reading one element past the end of a 3-element array. Short-circuit && compiles to chained conditional jumps that bail to the false path the moment an operand is falsy, which is why later operands are never even read (and why a null check guards the reads after it). Nested loops multiply iteration counts, but a guarding if still only fires when its own condition holds. When in doubt, walk the program counter and the variables one step at a time.
</Recap>
