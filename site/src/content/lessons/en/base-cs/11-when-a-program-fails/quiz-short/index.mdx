    { q: "What is the difference between an error and an exception?", a: "An error is a condition — a fact about the program's state that it cannot continue past with normal logic, such as a missing file, a divide by zero, or a bad type conversion. An exception is the mechanism the runtime uses in response: the moment an error is raised (the throw keyword in JavaScript), normal control flow stops, the next line does not run, and the runtime begins unwinding the call stack to search for a handler. The two vary independently — the same condition can be raised as an exception in one program and handled with a plain check in another, and the same unwinding mechanism responds to thousands of different conditions identically. An exception is not proof something is broken: a program can raise one, catch it, and continue normally." },
    { q: "Walk through what the runtime does when an exception is raised and no handler is found.", a: "Normal control flow stops instantly — the rest of the throwing function does not run. The runtime then unwinds the call stack: starting at the frame that raised the exception, it checks each frame for a handler (a catch block). If a frame has none, it pops that frame — abandoning the function and discarding its locals — and moves to the frame below. It keeps walking down toward the program entry. If it reaches the bottom frame and still finds no handler, there is nowhere left to look: the program crashes, terminating and printing the unhandled exception together with the list of frames it unwound through, which is the stack trace." },
    { q: "What is a stack trace, where in it is the throw site, and how do you read it?", a: "A stack trace is a snapshot of the call stack taken at the instant the exception is raised — a list of frames, one line each, naming a function and the line it was executing. It is captured at the throw, not at the crash, because unwinding destroys the stack by popping every frame; if the runtime waited until the crash, nothing would be left to describe. It is printed top frame first: the top line is the throw site, the function and line where the exception surfaced, and each line below is the caller of the line above it, down to the program entry at the bottom. Read it top-down — start at the top line, which tells you exactly what threw and where; the lines below give the chain of calls that led there. The bottom line is the entry and is almost never the culprit." },
    { q: "What is undefined behaviour, and why is it more dangerous than a defined error?", a: "A defined error is a failure the language specifies a reported answer for: the machine detects the condition and raises an exception, so control flow stops and a trace points at the line — you find out immediately. Undefined behaviour is an operation the language guarantees no result for at all — reading past the end of an array in a low-level unchecked language, signed integer overflow, letting an undefined or NaN value spread through a calculation. The defining danger is that it is silent: no exception is raised, the program does not stop, no trace is printed. It carries a garbage value forward as if it were correct. A loud, defined failure is found and fixed quickly; a silent one can survive testing, ship to users, and corrupt real data far from the line that caused it, with no trace pointing back." },
    { q: "Why does the determinism of the machine make debugging a matter of reasoning rather than guessing?", a: "The fetch-decode-execute cycle is deterministic: the same instruction on the same machine state always produces exactly the same result, every time, with no luck involved. So a bug is not random — it is a fixed, repeatable consequence of the code and the input, producing the same wrong result every run with the same inputs. Because the bug sits still, it can be found by reasoning instead of luck. Guessing — changing lines and re-running until the symptom disappears — treats the bug as mysterious and can hide a defect while leaving it in place. Reasoning treats the bug as a determined consequence and locates the exact step where the program's actual behaviour first diverged from what it should do." },
    { q: "Name the three moves for testing a debugging hypothesis, and explain why the throw site is not always the cause.", a: "A hypothesis is a specific, testable claim about which step diverged from expected — sharp enough that one check confirms or refutes it. The three moves: narrow the range — split the program, check the state at a midpoint, and discard the half that is still correct, halving the suspect region each time; read the trace — when the failure is a raised exception, the top line hands you the throw site for free, a precise starting point instead of a blank page; and check state — go look at the actual variable values at the exact moment the hypothesis predicts a fact about them, killing or sharpening the hypothesis. The throw site is where the error surfaced, not always where the cause lives: a function may throw because a caller passed it bad data, so reasoning follows the chain past the throw site until it finds the step where state first went wrong. Only then do you change a line." },
