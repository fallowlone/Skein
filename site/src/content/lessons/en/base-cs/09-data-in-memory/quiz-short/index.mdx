Every element shares the same type, so every element needs the same number of bytes; that fixed number is the element size, and it makes every cell identical in size. The two properties are linked: equal-size cells packed contiguously form a perfectly regular grid, so the position of any cell is predictable. An array of N elements each of size S bytes is therefore one solid block of N x S bytes, and the array name refers to where that block begins." },
    { q: "Give the formula for the address of element i, and name each part.", a: "address of element i = base_address + (index x element_size). The base address is the byte address of the array's first cell — the fixed anchor the array name refers to. The index is the element's position counted from 0. The element size is the bytes one element occupies. The product index x element_size is the offset: how many bytes past the base that cell begins. So you take the base, multiply the index by the element size to get the offset, add it to the base, and read there. The length and the other elements never appear in the formula." },
    { q: "Why is the first element index 0, not index 1?", a: "The index is the offset measured in elements from the start, not an everyday count of which element. The first element sits exactly at the base address — it is zero elements past the start — so its offset is 0 x element_size = 0 and its address is base + 0 = base. The only index that produces a zero offset is 0, and the first element is the only element with a zero offset. The numbering is forced by the address arithmetic, not chosen by convention." },
    { q: "Why is reaching any element constant time, and what would break that?", a: "The address of any element is found by the same fixed work — one multiply, one add, one read — regardless of the index or the array's length. So reaching arr[0] costs exactly as much as reaching arr[9999]; this is constant time. It works only because the array is contiguous and equal-size: a single element size lets one multiplication find any offset. If elements had different sizes you would have to sum all earlier elements' sizes one by one (no longer constant time), and if there were gaps the multiplication would land on the wrong address." },
    { q: "How does an object differ from an array, and why does an object's field order not matter?", a: "Both group several values under one name, but they differ in how you reach a value inside. An array reaches a value by numeric position — arr[2] computes an address from the index. An object reaches a value by a named key — user.age finds the slot labelled age and reads it. Each field is a key-value pair: the key is the name, the value is the data. Because access is by name, the written order of fields carries no meaning: { a: 1, b: 2 } and { b: 2, a: 1 } are the same object. Use an array for an ordered sequence of same-kind values; use an object for a named set of differently-meaning pieces." },
    { q: "How can an array hold a hundred different-size objects and still keep its equal-size grid?", a: "A small fixed-size value (like a number) fits directly in a cell, but an object is variable-size and can grow, so it does not fit. Instead each cell holds a reference — the address of an object stored elsewhere. Because every reference is the same small fixed size, the array stays a contiguous grid of equal-size cells and base + i x element_size still works; only the cell contents changed from values to addresses. Reaching a field is then two hops: arithmetic into the array to read the reference, then following the reference out to the object. Carried all the way, nested data is a graph of cells — some holding values, some holding addresses — and to hold a nested structure is to hold one reference into that graph." },
