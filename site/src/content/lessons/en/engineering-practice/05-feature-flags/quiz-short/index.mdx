A feature flag splits them. You deploy the code dark, present in the binary but wrapped in a flag check that returns false for everyone, then release later by flipping the flag with no rebuild or redeploy. SDKs pick the change up fast — Unleash polls on a ~15-second default, LaunchDarkly streams over SSE in sub-second. This lets code merge continuously and small (trunk-based development instead of long-lived branches), lets incomplete features sit safely behind an off flag, and turns release into a deliberate config decision rather than an engineering event. Rollout becomes a percentage ramp and rollback becomes flipping the flag off in seconds." },
    { q: "Name the four flag types and explain why recording the type matters for lifecycle.", a: "Release flags gate an in-progress feature for gradual rollout and live days to weeks — deleted after 100%, owned by the dev team. Ops/kill-switch flags disable a subsystem under load or incident and are permanent by design, owned by SRE/on-call. Experiment flags serve A/B variants for one cycle then are deleted, owned by product/data. Permission flags gate by plan, role, or entitlement and are long-lived, tied to the product model and owned by product. The type matters because two flags can look identical — a single boolean serving one value for months — yet have opposite correct fates: a stale release flag must be deleted, while a kill-switch that someone 'cleans up' has removed the safety net. The type, not the staleness signal, decides, so it has to be recorded rather than guessed." },
    { q: "How does a sticky percentage rollout work mechanically, and what breaks if it is not sticky?", a: "Instead of jumping 0% to 100%, you ramp 1% to 5% to 25% to 100%, watching error rate and latency at each step, and flip off instantly if a step breaks. To keep the assignment consistent, the SDK hashes a stable key — userId plus a groupId — into a 0–99 bucket; a 25% rollout means buckets 0–24 are on. The hash is deterministic and computed locally, so a given user always lands in the same bucket and evaluation is sub-millisecond with no per-check network call. If the rollout is not sticky — for example rolling a fresh random number per evaluation — the same user flips between variants across requests: the UI flickers and experiment data is garbage because exposure is not stable per user." },
    { q: "Why do SDKs evaluate flags locally in memory with background sync rather than calling the flag service per check?", a: "On a hot path a flag is checked thousands of times per request. A network round-trip per check would add latency and, worse, make the flag service a hard dependency: if it is down, your app is down. So the SDK holds the whole ruleset in memory and refreshes it in the background; a flag check becomes a local hashmap lookup and bucketing hash, sub-millisecond and dependency-free at evaluation time. The crucial consequence is the failure mode: a flag-service outage degrades to 'last known config' rather than an outage of your own service. This is also why a kill-switch must be wired against the local cache with a safe default, never as a blocking remote call on the critical path." },
    { q: "What is flag debt, and what is the discipline that prevents it from becoming a Knight Capital?", a: "Flag debt is the accumulation of flags that have outlived their purpose but still live in the code. Each flag is an if/else whose both branches run in production, so N independent booleans create 2^N possible configurations — a combinatorial test surface you cannot fully cover. A flag left at 100% for months is dead config that still evaluates, clutters the code, and can be reused. Knight Capital is the canonical disaster: in 2012 a deploy reused an old flag named Power Peg — a dead 2003 test feature — and on one un-updated server flipping it woke the dead code, firing ~4 million bad trades and losing ~$440 million in 45 minutes. The discipline is lifecycle: record each flag's type, give release flags an expiry and a removal ticket, make deletion part of definition-of-done, label kill-switches permanent so nobody deletes the safety net, and archive stale flags — serving the same value for ~30+ days — on schedule. Tools like Uber's Piranha automate the cleanup PR." },

Ten independent flags is 2^10 = 1,024 runtime configurations; you cannot test them all, and the combination a real user hits may be one no test ever exercised, which is how bugs reach production that staging never reproduced. Flags also rot: left untouched they become stale config that still evaluates and can be reused to wake forgotten code. So while flags buy continuous merging, safe dark deploys, gradual rollout, and instant rollback, the senior weighs that against a growing, under-tested configuration surface and treats prompt flag deletion — keeping N small — as the lever that keeps the cost bounded." },
