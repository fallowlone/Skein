## Snippet 1 — the rollout check

```js
function inRollout(flag, user) {
  // 25% rollout: roll a fresh random number per call
  return Math.random() * 100 < flag.rolloutPercent;
}

if (inRollout(newCheckout, user)) {
  return renderNewCheckout(user);
}
return renderOldCheckout(user);
```

    { label: "Math.random is too slow for a hot path; cache the value.", misconception: "Random is cheap; speed is not the issue. The issue is correctness: a non-deterministic per-call roll means no per-user stickiness. The fix is a stable hash, not caching the roll." },
    { label: "It needs a network call to the flag service to assign the bucket consistently.", misconception: "A per-evaluation network call would add latency and a hard dependency. Stickiness comes from hashing a stable user key locally, deterministically — no network round-trip per check." },

## Snippet 2 — the kill-switch path

```js
async function chargeCard(order) {
  const enabled = await flags.evaluate("payments-enabled", order.user);
  if (!enabled) {
    throw new Error("payments disabled by kill-switch");
  }
  return gateway.charge(order);
}

// flags.evaluate throws if the flag service is unreachable
```

  choices={[

    { label: "The kill-switch is inverted; it should charge when `enabled` is false.", misconception: "The polarity is correct — disabled means do not charge. The hazard is that a network failure in evaluate throws and blocks the path, turning the flag service into a single point of failure." },
    { label: "Throwing an Error is the wrong type; it should return a boolean.", misconception: "The intentional disable path can legitimately reject the charge. The real defect is the per-call network dependency that fails the path when the flag service is down." },
    { label: "It should re-check the flag after charging to confirm it is still enabled.", misconception: "A second check adds another network dependency without fixing the first. The structural fix is local evaluation with a safe default so the flag service is never on the critical path." },
  ]}

## Snippet 3 — the targeting rule

```yaml
flag: new-dashboard
rules:
  - if: user.plan == "enterprise"
    serve: on
  - if: user.betaOptIn == true
    serve: on
  - rollout:
      percent: 10
      stickyBy: user.id
default: off
```

<Quiz

  lang="en"
  question="An enterprise user who has also opted into beta loads the dashboard. Which rule decides their variant, and what general property does this config rely on?"
  choices={[
    { label: "The first matching rule wins: the enterprise rule serves on, and evaluation stops before the beta or rollout rules are considered. Targeting is order-sensitive — rules are evaluated top-down and the first match short-circuits, so rule order encodes precedence.", correct: true },
    { label: "All matching rules combine, so they get on only if every rule agrees.", misconception: "Targeting does not AND every rule. Rules are evaluated in order and the first match serves; an enterprise user is on regardless of the later beta and rollout rules." },
    { label: "The 10% rollout decides, because percentage rules always take priority over attribute rules.", misconception: "There is no implicit priority for rollout rules. Precedence is purely positional — the enterprise rule comes first and short-circuits before the rollout is reached." },
    { label: "The default `off` applies because the user matches more than one rule, which is ambiguous.", misconception: "Multiple matches are not ambiguous; the first match wins and the default only applies when no rule matches. This user matches the enterprise rule first." },
  ]}
/>

## Snippet 4 — the stale flag in code

```js
// added 2023-02 for the checkout-v2 release, ramped to 100% in 2023-03
if (flags.isEnabled("checkout-v2")) {
  return renderCheckoutV2(cart);
} else {
  return renderCheckoutV1(cart);   // V1 no longer maintained
}
```

    { label: "Convert it to a permanent kill-switch so V1 can be re-enabled in an emergency.", misconception: "Re-enabling a year-old, unmaintained path resurrects dead code against stale assumptions.     { label: "Lower the rollout to 95% so a few users keep exercising V1 to keep it alive.", misconception: "Sending traffic to an unmaintained path to keep it warm institutionalises the debt. The right move is to delete V1 and the flag, not to preserve a path nobody maintains." },

<Recap lang="en">
Every flag review reads the same way: a rollout check must hash a stable key into a fixed bucket or it flickers; a kill-switch must evaluate locally with a safe default or the flag service becomes a hard dependency that fails your hot path; targeting rules are order-sensitive and the first match short-circuits, so rule order is precedence; and a release flag at 100% with an unmaintained other branch is flag debt to delete, not config to keep. Read the evaluation path, fix the structure, then re-review.
</Recap>
