Only if the consumer's code actually makes the declared request and reads the declared fields does the test pass — and on passing, Pact writes that exercised interaction, including any provider states it assumed, into a JSON pact file. The pact is therefore a recording of code that ran and passed, not a separately written promise. An OpenAPI doc is authored apart from the code and nothing executes it, so it rots silently — it can describe a phantom field or miss one three teams depend on. A pact can't describe an interaction the consumer doesn't perform, so it captures actual usage and stays honest." },

The comparison is asymmetric: the actual response must contain at least the minimal expected shape, so the provider can add fields no consumer reads and stay green, but renaming or removing a consumed field makes verification fail before deploy. Provider states make each interaction satisfiable: an interaction like GET /prices/42 returns 200 only holds if price 42 exists, so the pact records a given string and the provider registers a state handler that seeds that data before each interaction. Each interaction is verified in isolation with no carried-over state, and the handler sets up data, not the response — a missing handler fails verification for an unmet precondition, not a broken contract." },

The deploy-time question is whether your version is safe against the provider version physically running in the target environment. can-i-deploy answers it by crossing the version you want to deploy against the versions of every integrated app currently in that environment (which the broker only knows because deployments were recorded) and exiting non-zero if any required pair is unverified. Version by git SHA because the version must change exactly when the contract could and a bare semver can label two different contracts, letting the broker reuse a stale result for the wrong code. Expand: deploy a provider that returns both the old and new field with the same value — every existing pact still reads the old field, so can-i-deploy passes and the provider ships with zero consumer changes. Migrate: each consumer, on its own schedule with no lockstep, switches its test to the new field, regenerating its pact, which verifies immediately because the provider already returns it. So the call isn't contracts-or-e2e but both-in-proportion: contracts replace most cross-service e2e for known internal consumers, but keep a few real end-to-end smoke tests on the deployed services with real-ish data for value correctness across hops, fixture-divergent data, and end-to-end auth/config." },
