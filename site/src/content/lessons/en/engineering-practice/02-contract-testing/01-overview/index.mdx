## Why integration tests stop scaling

The naive answer to "will these services still talk?" is to spin them all up and test them together. It works for two services. It collapses for twenty. End-to-end suites are slow (you boot a half-dozen services, a database, a queue), flaky (one timeout in any hop fails the run), and combinatorially impossible: with N services that talk to each other, the number of integration pairs grows roughly with N², and a full e2e environment has to be healthy all at once for any test to pass. Teams that lean on e2e for integration confidence end up with suites that take 40+ minutes, fail 1-in-5 for reasons unrelated to the change, and get muted — which means they catch nothing.

Contract testing attacks the problem from the other side. Instead of running both services together, you test each side **against a recorded agreement** of how they interact. The consumer's test runs against a mock provider; the provider's test replays the consumer's recorded requests against the real provider code. Neither test needs the other service running. Fast, deterministic, and the count grows linearly with consumer-provider edges, not combinatorially.

## The contract as an executable spec

A contract is not a wiki page or an OpenAPI doc someone forgot to update. It is generated *from a passing consumer test* and executed *against the real provider*. In Pact — the de-facto standard — the flow is concrete:

1. The consumer writes a unit test against a **Pact mock server**, declaring: "when I `GET /orders/{id}`, I expect a `200` with a body containing `amount_cents` as a number." Running that test produces a **pact file** — a JSON document of every interaction the consumer actually exercises.
2. That pact file is published to a **Pact Broker** (the shared registry), tagged with the consumer's version and git branch.
3. The provider's CI fetches the pact and runs **provider verification**: it replays each recorded request against the real provider, sets up any required `provider states` (e.g. "an order with id 42 exists"), and checks the real response matches the consumer's expectation. Results are published back to the broker.

The agreement is "consumer-driven" because the consumer authors it. The provider does not guess what downstream needs — it is told, in executable form, and CI enforces it.

## The deploy gate: can-i-deploy

A contract that lives in CI but doesn't block a release is decoration. The gate that turns it into protection is **`can-i-deploy`**. The broker keeps a **matrix** — a grid of every consumer version × provider version and whether verification passed between them. Before deploying provider v5 to production, the deploy pipeline asks the broker: "given the consumer versions currently in production, has v5 been verified against all of them?" If any pact is unverified or failed, `can-i-deploy` exits non-zero and the deploy is blocked.

This is the piece that would have stopped the 02:14 outage. Renaming `total_cents` would fail provider verification against the three consumers still expecting it; `can-i-deploy` would return red; the deploy never ships. The breakage moves from production at 2 a.m. to a red CI check at the author's desk — which is the entire point of the pyramid: catch it where it's cheap.

<Inset kind="why" lang="en">
Pact's **pending pacts** keep a new consumer from breaking an established provider's build the instant it publishes. A freshly published, never-verified pact is marked pending: it shows up in verification output but does not fail the provider's build. Once the provider verifies it successfully, it transitions out of pending and from then on a regression *does* break the build. This lets a new consumer onboard without holding the provider's pipeline hostage on day one.
</Inset>

## Where it sits in the pyramid — and what it can't see

Contract tests slot between unit and integration tests: nearly the confidence of an integration test for cross-service compatibility, at close to unit-test speed. But the senior tradeoff is sharp and worth saying out loud: **a contract only covers interactions a consumer actually exercises.** If a consumer never calls `POST /orders/{id}/cancel`, no contract guards that endpoint, and the provider can break it freely. Contracts verify the *shape and semantics of the wire* — status codes, fields, types, presence — not business correctness. A provider can return a perfectly contract-valid `amount_cents` that is computed wrong; the contract passes, the money is incorrect. Contract testing replaces the *integration* layer for compatibility, not the provider's own functional tests, and not a thin slice of real end-to-end journeys.

The other failure mode is **contract rot.** If consumers stop running their pact tests, or pacts are published for versions no longer deployed, the broker matrix fills with stale agreements that gate deploys against integrations nobody runs. The discipline is to keep pacts tied to versions actually in environments (the broker's `deployedOrReleased` selector exists for exactly this) and to treat an unverified pact as a hard signal, not noise to mute.

<Recap lang="en">
Microservice integration confidence doesn't come cheaply from end-to-end tests: they are slow, flaky on any hop, and grow combinatorially with the number of services, so teams mute them and catch nothing. Consumer-driven contract testing flips this: the consumer writes a test against a mock and generates a pact file describing exactly the interactions it uses; the provider's CI verifies that pact by replaying it against real code; the broker records a matrix of which versions are compatible, and can-i-deploy gates the release so a breaking change fails at a CI check instead of a 2 a.m. pager. The tradeoff a senior weighs is real: contracts catch schema and semantic drift on exercised interactions fast and linearly, but they see nothing a consumer never calls, they verify wire shape rather than business correctness, and left unmaintained they rot into stale gates. Use them to replace the integration layer for compatibility — keep functional tests for correctness and a thin e2e smoke for true journeys.
</Recap>
