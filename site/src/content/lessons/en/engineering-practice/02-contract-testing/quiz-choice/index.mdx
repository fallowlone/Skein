  lang="en"
  question="A provider returns 40 fields; a consumer reads 4. Why is recording only those 4 (matched by type) the right scope for a consumer-driven contract?"
  choices={[
    { label: "The contract should capture actual dependence: recording the 4 consumed fields by type means the provider can freely evolve the other 36, and the gate trips only on a change that would truly break this consumer.", correct: true },
    { label: "Record all 40 with exact example values to be safe — more coverage means fewer surprises.", misconception: "Recording all 40 makes the contract a brittle snapshot that fails on benign value changes and on fields no one reads, generating the noise that gets it muted — the same trust-erosion that killed the team's OpenAPI doc." },
    { label: "Record the 4 fields but assert only that they exist, not their types — types change too often.", misconception: "Existence-only lets the provider switch a number to a string and slip past the gate, so real breakage leaks through.     { label: "Skip the consumer contract and rely on the provider's OpenAPI spec as the source of truth.", misconception: "The provider's spec flags every change equally, can drift from the code, and doesn't know which fields anyone depends on — the noisy, rot-prone model consumer-driven contracts exist to replace." },
  ]}

  choices={[
    { label: "Verification fails only because of the rename: the check is asymmetric — the actual response must contain at least the minimal expected shape, so extra unasserted fields are fine, but a missing consumed field breaks the minimal-response match.", correct: true },
    { label: "Verification fails because the response no longer exactly matches the recorded one, including the new fields.", misconception: "Provider verification is not an exact match. It asserts the actual response contains at least the minimal expected shape; extra fields are explicitly allowed, which is what lets the provider evolve fields no consumer reads." },
    { label: "Verification passes because additions and renames cancel out — the field count is unchanged.", misconception: "Field count is irrelevant.     { label: "Verification is skipped because the response shape changed and the pact is now stale.", misconception: "A shape change never skips verification — it triggers the comparison. <Recap lang="en">
The unit's through-line is one pipeline of decisions: e2e collapses because a shared environment's health is the product of every service's uptime, so push compatibility down to a per-edge test; the consumer records actual usage by type into a pact; the provider verifies by replaying each interaction against the real service, checking the minimal expected shape with provider states seeding the data; can-i-deploy turns the verification matrix into a deploy gate by crossing your git-SHA version against what's actually deployed; and the hard limit — contracts test shape, never semantics — is why a thin layer of real e2e smoke tests survives. Every wrong answer here is a real team's wrong turn.
</Recap>
