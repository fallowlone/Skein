## Integration frequency is the actual lever

Trunk-based development is one rule with large consequences: every developer merges small changes into a single shared branch — the trunk — at least once a day, and branches live hours, not weeks. It is the opposite of the long-lived feature branch, where you disappear for two weeks, build in isolation, and integrate at the end.

The reason this matters is not aesthetic. The cost of a merge is roughly proportional to how far trunk has drifted from your branch since you forked, and that drift compounds: every other engineer is also committing. A branch that is one day old conflicts with one day of other people's work; a branch three weeks old conflicts with three weeks of it, on top of having to re-understand code that changed under you. Microsoft's internal data found teams that went more than three days without merging spent **12× longer** resolving conflicts than teams that merged daily. Studies put merge-conflict resolution at **10–25% of developer time** in branch-heavy workflows. Frequent integration does not avoid conflicts; it keeps each one small enough to resolve in minutes, with full context, before it compounds.

## Short-lived branches vs gitflow

Gitflow gives you `develop`, `release`, `hotfix`, and long-lived `feature/*` branches with formal integration phases. It is built for shrink-wrapped software with scheduled releases and no continuous deployment. The price is exactly the drift above: the more branches you keep alive and the longer they live, the more pairwise merges someone eventually pays for, and the more your "done" features rot while waiting to integrate.

Trunk-based does not mean "no branches" — it means **short-lived** ones. DORA's research is specific: keep **three or fewer active branches**, branches should last **no more than a day** (often only a few hours), and you should have **no code freezes and no integration phases**. The CI build that gates a merge should run in a few minutes, because a slow gate quietly pushes people back toward batching.

## Flags decouple deploy from release

The obvious objection to merging daily: "my feature isn't finished — I can't put half a feature on trunk." You can, if you separate **deploying code** from **releasing a feature**. Wrap the unfinished path in a feature flag that is off in production. The code ships to prod on every merge, sits there *dark* — compiled, tested, integrated — but no user can reach it until you flip the flag. This is dark launching, and it is what makes daily integration possible for work that takes weeks.

The payoff is two-sided. Integration stays continuous even for big features, so you never accumulate weeks of drift. And release becomes a runtime decision, not a deploy: turn the feature on for 1% of users, watch the metrics, ramp to 100% — and if it misbehaves, flip the flag off in seconds instead of rolling back a deploy. The cost a senior weighs is real: every flag is a branch in your runtime, so flags must be short-lived too. A flag left on after a feature is fully released becomes dead conditional code and a combinatorial testing burden. Trunk-based trades branch debt for flag debt; you only win if you remove flags as aggressively as you remove branches.

<Inset kind="why" lang="en">
A feature flag that outlives its feature is just a long-lived branch hiding in an `if`. The same drift problem comes back as untested code paths: with N stale flags you have 2^N runtime configurations nobody verifies. The discipline that makes trunk-based work is *cleanup* — delete the branch on merge, delete the flag on full rollout.
</Inset>

## The CI gate is the whole bargain

Trunk-based development concentrates everyone on one branch, which means a broken trunk blocks the *entire team* — nobody can pull a clean base, nobody can merge on green. That is the central risk, and the mitigation is a CI gate that runs the full build and test suite on every change *before* it lands, fast enough (minutes) that people don't route around it. No green, no merge. This is why trunk-based is inseparable from continuous integration: the discipline is not "commit to main and pray," it is "commit to main behind an automated gate that keeps main always releasable."

This is also why the data is so strong. DORA's *Accelerate* research consistently finds trunk-based development among the **strongest technical predictors** of elite software-delivery performance — elite teams are roughly **2.3× more likely** to use it, and elite vs low performers show on the order of **182× more deployments** and dramatically faster recovery. But the causation runs through the prerequisites: trunk-based only delivers if you have the fast CI gate, the flags, and the team discipline. Adopt the branching model without the gate and you get the failure mode instead of the benefit — a perpetually red trunk that halts everyone.

<Recap lang="en">
Trunk-based development is the discipline of merging small changes into one shared branch at least daily, with branches living hours rather than weeks. The lever is integration frequency: merge cost grows superlinearly with branch age because trunk drifts under you while everyone keeps committing — Microsoft saw 12× longer conflict resolution past three days, and conflict work can consume a quarter of developer time. Short-lived branches keep each merge small and contextual instead of a big-bang at the end like gitflow. Feature flags make this possible for big features by decoupling deploy from release: unfinished work ships to prod dark behind an off flag, and release becomes a runtime ramp you can roll back in seconds — at the cost of flag debt you must clean up, or stale flags become long-lived branches in disguise. The CI gate is the bargain that makes a shared trunk safe: fast, full, and blocking, so a broken trunk can't halt the team. Get the trio right — daily integration, flags, green CI — and trunk-based is the strongest technical predictor of elite delivery DORA has found; skip the prerequisites and you inherit merge hell or a red trunk instead.
</Recap>
