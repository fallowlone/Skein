So a month-long feature merges to trunk every day as small green commits, each hidden behind an off flag: deployed, integrated, tested, but dark. Beyond hiding work, the flag gives three operational powers: dark launching (run the new path in prod against real traffic, compare and discard its output, validating with zero user risk), progressive exposure (internal then 1%, 5%, 25%, 100%, growing blast radius only as confidence grows), and a kill switch (flip off and everyone is back on the old path in seconds, no rollback deploy)." },

PR-A is green against trunk; PR-B is green against the same trunk; both merge — but they were never tested together, so they can conflict semantically and break trunk even though each passed. Rare at a few merges a day, constant at dozens. A merge queue fixes it: PRs enter a queue and CI tests each against the projected state of trunk — trunk plus all PRs ahead in line — so a change only lands if it's green against the exact state it will create. To keep throughput up, queues batch several PRs as one combined candidate and merge the batch if green, bisecting the batch on failure to eject the culprit. This is how GitHub kept one monorepo green from about 1,000 merges/month in 2016 to over 30,000 by 2023.
