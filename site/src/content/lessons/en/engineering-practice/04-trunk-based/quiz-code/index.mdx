<Goal lang="en">
Practise reading the artefacts that decide whether a team is actually trunk-based: how unfinished work is wrapped to ship dark, how a big change rides trunk via abstraction, and how the gate is configured to keep trunk green.
</Goal>

## Snippet 1 — shipping unfinished work to trunk

```ts
// New checkout flow isn't finished, but it must merge to trunk today.
export async function handleCheckout(cart: Cart, user: User) {
  if (flags.isEnabled("checkout-v2", { userId: user.id })) {
    return newCheckout(cart, user);   // half-built, still missing tax calc
  }
  return legacyCheckout(cart, user);  // current production path
}
```

## Snippet 2 — a six-week ORM swap on trunk

```ts
interface UserStore {                 // the abstraction
  find(id: string): Promise<User>;
  save(u: User): Promise<void>;
}

class LegacyOrmStore implements UserStore { /* current, in use */ }
class NewOrmStore    implements UserStore { /* built incrementally, dark */ }

// wired once, flipped at the boundary when NewOrmStore is ready
export const userStore: UserStore =
  flags.isEnabled("orm-v2") ? new NewOrmStore() : new LegacyOrmStore();
```

## Snippet 3 — the CI gate config

```yaml
# .ci/trunk-gate.yml — runs on every PR
on: pull_request
jobs:
  gate:
    steps:
      - run: make unit-tests          # ~2 min, blocks merge
      - run: make lint typecheck      # ~1 min, blocks merge
  e2e:
    steps:
      - run: make e2e-suite           # ~40 min
        if: github.event_name == 'schedule'   # nightly only, never blocks
```

  question="Reading this gate, which statement is the correct senior assessment?"
  choices={[
    { label: "Sound tiering: fast unit + lint/typecheck (~3 min) block the merge so the gate stays fast enough that integrating small and often is the path of least resistance, while the 40-min e2e suite runs nightly off the critical path.", correct: true },
    { label: "Broken — the e2e suite must block every merge or trunk can break.", misconception: "A 40-min blocking suite would push developers to batch changes, lengthening branches and reabsorbing drift. Tiering fast checks pre-merge and slow ones post-merge/nightly is the standard way to keep the gate fast." },
    { label: "Fine as long as developers remember to run e2e locally before merging.", misconception: "Relying on memory isn't a gate. The design choice is deliberate: block on fast checks, run slow ones nightly, and treat a rare nightly failure with stop-the-line plus bisect." },
    { label: "The gate is too strict because lint and typecheck block merges.", misconception: "Fast static checks blocking the merge is exactly what keeps trunk green cheaply. The risk to manage is slowness, not strictness — and these checks are seconds-to-minutes." },
  ]}

## Snippet 4 — a stale flag left behind

```ts
// shipped 14 months ago, "search-v2" has been at 100% the entire time
function rankResults(q: Query, results: Result[]) {
  if (flags.isEnabled("search-v2")) {
    return rankV2(q, results);        // the live path
  }
  return rankV1(q, results);          // never runs, never updated since launch
}
```

    { label: "Leave it as a permanent kill switch in case search-v2 regresses.", misconception: "That's type laundering — relabeling leftover release scaffolding as a permanent ops flag keeps the rotting old path alive. If a kill switch is genuinely needed, design one deliberately." },
    { label: "File a cleanup ticket for next quarter and move on.", misconception: "Deferred flag cleanup is exactly how teams reach 400 stale flags. Removal has to be the closing step of the rollout, part of 'done,' not a follow-up that gets deprioritized." },
    { label: "Nothing — a flag at a stable 100% is harmless dead code.", misconception: "It isn't harmless: rankV1 is still reachable (a config typo can route to it), unmaintained, and one more boolean in the combinatorial config space. A release flag at 100% should be deleted." },
  ]}

<Recap lang="en">
Trunk-based discipline is legible in the artefacts. A flag conditional on trunk lets unfinished work ship dark so it integrates daily with no drift; an abstraction interface lets a six-week migration ride trunk as small green commits with a single flip-and-delete; a tiered CI gate stays fast by blocking on unit/lint/typecheck and running slow e2e off the critical path; and a release flag still on at a stable 100% is a long-lived branch hiding in an if that you delete — flag and dead path together — as the closing step of the rollout.
</Recap>
