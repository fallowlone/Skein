## Code is read and changed far more than it is written

You write a line of code once. Then you and others read it, debug it, and change it for years. So the real cost of software is not typing it the first time — it is everything that comes after. Code that is hard to understand or risky to change is expensive forever, even if it runs fine today. Engineering practice exists to lower that long-term cost, not to make the first version faster to write.

The trouble is that a codebase decays by default. Each rushed fix, each "I'll clean it up later," each untested change adds a little mess. Left alone, the mess compounds until small changes take days and everyone is scared. Practice is the steady force that pushes the other way.

## Three habits that keep a codebase healthy

You do not need dozens of rules to start. Three habits carry most of the weight:

- **Tests.** Small programs that check your code still does what it should. When a test fails, you learn instantly — not from an angry user a week later. Tests let you change code without fear, because they catch what you broke.
- **Code review.** Before a change joins the shared codebase, another person reads it. They catch bugs, ask "why this way?", and spread knowledge so no single person is the only one who understands a part.
- **Small steps.** Make one focused change, check it works, integrate it, repeat. Small changes are easy to review, easy to test, and easy to undo. Big bang changes hide bugs and are terrifying to merge.

## The mental model to carry up

Hold one idea above all: **a codebase is something you keep changing, so optimize for change, not just for "it runs today."** Every practice in this pillar is a way to make the next change safer and faster — tests give you a safety net, reviews give you a second pair of eyes, small steps keep risk low. The rest of the climb is the specific techniques: test-driven and property tests, contract testing, code review, trunk-based development, feature flags, postmortems, and being on-call.
