<Hook>

Every unit test used round numbers like `19.99` and `100.00`, so every test passed. Nobody had written `0.005`, `2.675`, or a randomly generated decimal — because nobody thought to. <Explanation>

## Red-green-refactor is a design tool, not a coverage ritual

The loop is small on purpose: write the smallest failing test (**red**), write the least code that makes it pass (**green**), then improve the code without changing behavior (**refactor**). The value people miss is in the first step. Writing the test before the implementation forces you to call your own code from the outside before it exists — you decide the function's name, its arguments, its return shape, and its failure mode while you are still a *consumer*, not an author. Code that is hard to call is hard to test first, so TDD surfaces a bad interface in seconds instead of after it has fifteen call sites.

The trap is skipping the third step. Under deadline pressure teams stop at green: tests pass, ship it. The refactor step is where duplication and tangled names get cleaned up *while the tests still guard behavior*. Skip it for a quarter and you have a suite that passes over a codebase nobody wants to touch — green CI is not the same as healthy code.

The other quiet failure is what you couple the test to. A test that asserts behavior ("a refund for a fully-shipped order is rejected") survives refactoring. A test that asserts implementation ("the `RefundService` calls `inventoryClient.check()` exactly once, then `ledger.post()`") breaks the moment you reorganize internals — even when behavior is unchanged. Worse, the mirror case: such a test can stay green while the real behavior is broken, because it only checks that some internal dance happened, not that the customer got the right outcome. That is a brittle, untrustworthy suite, and a brittle suite is one developers learn to ignore.

## Example tests check what you thought of; property tests check what you didn't

An example-based test is a fixed input mapped to an expected output: `reverse([1,2,3]) === [3,2,1]`. It documents one case. You write the cases you can imagine, which means your test suite has exactly your blind spots. The money bug above is the canonical shape of this failure: every example was a "nice" number, so the half-even/half-up disagreement on `.005` values lived in the gap between the examples.

A property-based test instead asserts something true for *all* valid inputs, and the framework generates hundreds of them. Instead of one example you state an invariant: "reversing a list twice returns the original list," and Hypothesis (Python), fast-check (JS/TS), or QuickCheck (Haskell) throws hundreds of generated lists at it — empty, single-element, huge, with duplicates, with the values that sit on boundaries. fast-check runs 100 cases per property by default (`numRuns`), tunable to 1000+ in CI. You are no longer limited to the inputs you personally thought of.

The most reached-for style is the round-trip: any code that serializes then deserializes should give back what it started with. A `parse(serialize(x)) === x` property on a JSON or money formatter would have generated `0.005`-class values within a handful of runs and failed loudly — the bug that hid for eight months behind hand-picked examples.

## Shrinking: why the counterexample is small enough to debug

The reason property testing is usable and not just noise is **shrinking**. When the framework finds a failing input, it does not hand you the giant random array it happened to generate; it automatically searches for the *smallest* input that still fails. fast-check might generate a failing list of 40 random integers, then shrink it across 526 reduction rounds down to `[23, 22]` — the minimal pair that still violates the property. Hypothesis does the same, then runs the minimal example one extra time to confirm the failure is not flaky before reporting it.

This is the difference between a usable bug report and an unusable one. Without shrinking you get "it failed on `[483, -29, 0, 17, -6, 92, ...]`" and have to bisect by hand. With shrinking you get "it failed on `[0, -1]`" and the root cause is often obvious on sight. Both Hypothesis and fast-check also print a **seed**: re-run with that seed and you reproduce the exact failing case in CI on your laptop, which makes the otherwise-scary "random tests" deterministic to debug.

<Inset kind="why" lang="en">
Generated randomness is the source of the senior objection to property tests: a property that depends on a clock, an unseeded `Math.random`, or wall-time can pass 999 runs and fail the 1000th, turning CI red on an unrelated commit. The discipline is to make properties pure and inputs framework-generated, and to pin a seed when a flake appears so the failure is reproducible rather than a coin toss.
</Inset>

## The senior tradeoff: properties cost more and can bite back

Property tests are not free wins. They are harder to write: stating a true invariant is a real design act, and a weak property (`result is a number`) tests almost nothing while looking thorough. They are slower — hundreds of runs per property, sometimes thousands in CI, which is why frameworks ship per-run timeouts and deadlines. And they can be flaky if you let impurity leak in. The honest senior position is *both, not either*: example tests as living documentation of the cases that matter to the business and as fast regression guards, plus a handful of high-value properties (round-trip on every serializer, invariants on every sort/dedup/merge, an oracle when you rewrite a hot path) to mine the input space humans can't enumerate.

<Recap lang="en">
TDD's first step is design pressure: writing the test before the code forces you to use your own interface before it exists, surfacing a bad API in seconds. The loop only pays off if you keep the refactor step — green CI over a codebase nobody will touch is not health. Couple tests to behavior, never to implementation detail: implementation-coupled tests break on harmless refactors and can stay green while the real outcome is broken, which trains the team to ignore failures. Example tests document the cases you thought of; property tests assert invariants — round-trip, invariant, oracle, metamorphic — over hundreds of generated inputs and find the edge cases you never enumerated, like the money formatter that disagreed only on .005 values. When a property fails, shrinking reduces the input to a minimal counterexample (fast-check shrinking a 40-element array down to [23, 22] across 526 rounds) and a printed seed makes it reproducible. The cost is real — properties are harder to write, slower, and flaky if you let impurity in — so the senior answer is both: examples as fast, business-meaningful regression guards plus a handful of high-leverage properties on every serializer, sort, and rewrite.
</Recap>
