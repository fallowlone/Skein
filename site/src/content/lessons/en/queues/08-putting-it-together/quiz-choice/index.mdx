  lang="en"
  question="The order handler must both persist the order and emit order.placed. Why is the transactional outbox the right shape rather than INSERT-then-kafka.publish in the same handler?"
  choices={[
    { label: "The DB and the broker share no transaction, so any ordering of two separate calls loses an event or emits a phantom on a crash in the gap. The outbox writes the order row and an outbox row in one local ACID transaction, then a relay ships the event as a separate retryable step.", correct: true },
    { label: "kafka.publish is slower than a DB insert, so the outbox is a latency optimisation.", misconception: "The outbox is about atomicity, not speed — it actually adds a relay hop and some latency. Its job is to remove the dual-write gap where a crash loses or phantoms an event." },
    { label: "Wrapping both calls in try/catch and compensating on failure is equivalent and simpler.", misconception: "An OOM-kill mid-call throws nothing to catch, and hand-rolled compensation is a buggy distributed-transaction coordinator that can itself crash between steps. There is no safe dual-write order." },
    { label: "Publishing first, then inserting the order row, avoids losing events.", misconception: "Publish-first trades lost events for phantom events: crash after publish and before commit, and consumers act on an order that rolled back and never existed." },
  ]}

  question="The order topic is keyed by order_id with 6 partitions. Lag spikes on a hot Friday and someone bumps it to 12 partitions. What breaks, and why?"
  choices={[
    { label: "Per-order ordering breaks: the partitioner is hash(key) % N, so changing N reroutes most order_ids. A new event for an order can land on a different partition than its history, letting a cancel overtake its create. Migrate to a new topic instead of resizing in place.", correct: true },
    { label: "Nothing — Kafka re-shuffles existing records onto the new partitions and keeps them ordered.", misconception: "Existing records never move; they stay where they were written. The break is that future records for a key now hash elsewhere, splitting the key across two partitions with no ordering between them." },
    { label: "Throughput drops because more partitions add coordination overhead.", misconception: "More partitions generally raise throughput up to a point; the real damage here is the silent ordering corruption from rehashing keys, not a throughput regression." },
    { label: "The consumer group automatically rebalances ordering so the change is safe.", misconception: "There is no automatic re-ordering across old and new partitions. Per-key order is simply lost for in-flight keys — which is why partition count is treated as a one-way door." },
  ]}

  question="The payment consumer pulls order.placed, calls Stripe, succeeds, then the pod is killed before the Kafka offset commits. The group rebalances and replays the offset. How do you prevent a double charge?"
  choices={[
    { label: "Make the handler idempotent: record the event id under a unique constraint in the same transaction as the charge, and propagate an Idempotency-Key to Stripe so a retry returns the original charge for 24h instead of creating a second.", correct: true },
    { label: "Commit the Kafka offset before calling Stripe so a crash can't replay.", misconception: "Commit-before-process is at-most-once: crash after the commit and the charge silently never happens.     { label: "Route the replayed event straight to the DLQ and reconcile by hand.", misconception: "The DLQ is for poison messages that exhausted their retry budget, not for normal crash-induced replays that idempotency already neutralises.     { label: "Add more partitions so each consumer is lighter and crashes less often.", misconception: "A crash-before-commit replays regardless of load, and bumping partitions rehashes keys and breaks ordering. This treats a correctness bug as a capacity problem." },
  ]}

<Recap lang="en">
The whole track collapses into one design tree: the order write is atomic because the row and its outbox event commit in one local transaction; CDC (or a polling relay) publishes at-least-once by resuming from its log offset — and the slot is a loaded gun you must alert on and cap; the topic preserves per-key order by keying on order_id, which is why bumping partition count is a one-way door that rehashes keys; the consumer group delivers at-least-once by committing offsets only after processing; poison messages that exhaust a retry budget go to the DLQ instead of blocking the partition; and the UI tells the truth about the consistency window with optimistic-then-pending state. The thread through all of it is idempotency — a dedup key under a unique constraint plus an Idempotency-Key propagated to external calls — because every honest hop is at-least-once and duplicates are the contract, not the bug.
</Recap>
