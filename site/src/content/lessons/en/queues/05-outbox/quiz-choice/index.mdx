  choices={[
    { label: "Both writes target one database, so a single ACID transaction commits or rolls back both with no coordinator. 2PC spans two stores and needs a blocking coordinator — and Kafka isn't a practical XA participant anyway.", correct: true },

    { label: "2PC would work fine; the outbox is just simpler to code.", misconception: "2PC across a DB and Kafka isn't merely harder to code — a blocking 2PC coordinator becomes a worse availability problem than the dual write, and Kafka doesn't offer the XA participation you'd want in production." },

<Quiz
  id="05-outbox-choice-4"
  lessonSlug="05-outbox"
  lang="en"
  question="Why is the outbox at-least-once rather than exactly-once, and what does that force on every consumer?"
  choices={[
    { label: "The relay publishes then marks the row sent in two non-atomic steps; a crash after the broker accepts but before the UPDATE commits replays the event on restart. So consumers must be idempotent — dedupe on a stable event id.", correct: true },
    { label: "It's exactly-once as long as the broker has idempotent producers enabled.", misconception: "Idempotent producers dedupe retries within one producer session, not across a relay crash-and-restart that re-reads an unsent row. The outbox guarantee is at-least-once end-to-end; dedupe is the consumer's job." },
    { label: "Marking the row sent BEFORE publishing would make it exactly-once.", misconception: "That just moves the gap and converts a recoverable duplicate into an unrecoverable lost event — crash after the UPDATE and before the publish, and the row looks done but nothing was sent. Publish-then-mark is the strictly safer order." },
    { label: "It's at-least-once, but that means duplicates are acceptable and need no handling.", misconception: "At-least-once tolerates duplicates only because consumers dedupe them. Processing OrderPlaced twice must charge the card once; idempotency is the load-bearing half of the pattern, not optional." },
  ]}
/>

  lang="en"
  question="You scale the polling relay from one replica to three for throughput and immediately see every event published roughly three times. What is the fix?"
  choices={[
    { label: "Claim rows with SELECT ... FOR UPDATE SKIP LOCKED so each replica locks a disjoint batch and skips rows another worker already holds. The replicas then scale out without re-reading the same unsent rows.", correct: true },
    { label: "Reduce to one replica permanently — the outbox can't be scaled horizontally.", misconception: "The outbox scales fine across replicas; you just need row-claim coordination. SKIP LOCKED lets multiple workers share the table without overlap." },
    { label: "Give each replica a different polling interval so their ticks don't align.", misconception: "Offset intervals don't prevent two workers from selecting the same WHERE sent=false rows on overlapping ticks. Only a lock claim makes the batches disjoint." },
    { label: "Accept it — at-least-once means triple delivery is within spec.", misconception: "At-least-once tolerates the rare crash-induced duplicate, not deliberately tripling every event; that wastes throughput and hammers consumers. Coordinate the relays with SKIP LOCKED." },
  ]}
/>

<Recap lang="en">
Across the unit the through-line is one chain: a dual write across two stores has no crash-safe ordering, so you collapse it into a single local transaction that writes the business row and an outbox row together. A separate relay ships those rows — polling (simple, but interval-bounded latency and constant DB load) or CDC (single-digit-ms, near-zero table load, at operational cost). Because the relay publishes then marks sent in two steps, delivery is at-least-once, so consumers dedupe on a stable event id. The operational tax — table bloat, ordering under parallel relays, competing replicas — is paid with partitioning, batched reaps, aggregate keying, and FOR UPDATE SKIP LOCKED. Now when you review a service that must write a DB and notify a broker, you know which of these six failure modes to look for first.
</Recap>
