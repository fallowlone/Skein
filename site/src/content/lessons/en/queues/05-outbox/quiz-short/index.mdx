    { q: "Why does a handler that writes the database and publishes to a broker have no crash-safe ordering of those two calls?", a: "The database and the broker are two separate systems with no shared transaction, so the handler is doing a dual write. Write-the-row-then-publish loses the event if the process crashes after the commit and before the publish lands: the state changed but nobody downstream knows. Publish-then-write-the-row emits a phantom event if the crash falls after the publish and before the commit: consumers react to an order that rolled back and never existed. A try/catch can't compensate because an OOM kill mid-call throws nothing to catch, and the compensation logic is itself a tiny distributed-transaction coordinator that can also crash. There is simply no ordering of two non-atomic calls across two stores that survives a crash in the gap." },
    { q: "How does the transactional outbox convert the dual write into something atomic, and what exactly is durable after COMMIT?", a: "In the same local database transaction that changes the business state, you also INSERT a row into an outbox table describing the event. Because both writes are in one ACID transaction against one database, they commit together or roll back together — atomically, with no coordinator, and no 2PC. After COMMIT, what is durable is not just the order row but the intent that an OrderPlaced event must be delivered, recorded in the same database. Publishing to the broker is now a separate, retryable step the handler never performs; it returns the moment the transaction commits. You have traded an impossible atomic dual write for a trivially atomic single write plus an asynchronous, crash-safe pump." },
    { q: "Compare a polling relay and a CDC relay along latency, load on the primary, and operational cost.", a: "A polling relay runs SELECT ... WHERE sent = false on an interval, publishes each row, then marks it sent. It is dead simple and works on any database, but end-to-end latency is bounded by the interval (typically 100ms to 1s), and every poll loads the primary OLTP database whether or not there is work — a real burden at many relay replicas. A CDC relay (Debezium) instead tails the database write-ahead log and emits an event the moment the outbox INSERT commits: single-digit-ms latency, near-zero table load, and the log's natural commit ordering. The price is operational — you run and monitor a connector, manage replication slots, and reason about WAL retention. Polling fits modest volume with no new infra; CDC fits high throughput, low latency, and ordering requirements." },
    { q: "Why is outbox delivery at-least-once rather than exactly-once, and what does that force on consumers?", a: "The relay does two things that can't be made atomic across systems: publish to the broker, then UPDATE the row to sent. If it crashes after the broker accepted the message but before the UPDATE commits, the row still looks unsent, so on restart the relay publishes the same event again — a duplicate. Reversing the order (mark sent first, then publish) only converts the duplicate into a lost event if the crash lands between the UPDATE and the publish. So the only safe order is publish-then-mark, which is at-least-once. That forces every consumer to be idempotent: each outbox row carries a stable event id, and consumers dedupe on it — usually an inbox table of processed ids kept for hours to days, or a unique constraint on the side effect — so processing OrderPlaced twice still charges the card exactly once." },
    { q: "You scale the polling relay to multiple replicas. What two problems appear, and how do you solve each?", a: "First, competing relays: run several replicas naively and they all SELECT the same WHERE sent=false rows and double-publish them. The fix is SELECT ... FOR UPDATE SKIP LOCKED (Postgres / MySQL 8.0+), so each worker grabs and locks a disjoint batch, skipping rows another worker already holds, and replicas scale out without stepping on each other. Second, ordering: a single relay preserves created_at order, but two workers publishing concurrently can deliver events out of order. If a consumer needs per-aggregate order, key by aggregate id so all events for one order go to the same partition and one worker, preserving order where it matters while still parallelising across aggregates." },
    { q: "What causes outbox table bloat and how do you reap it without hurting the hot write path?", a: "The outbox grows with every event, and sent rows accumulate. Left unreaped, the table and its indexes balloon into hundreds of thousands of rows where polling queries degrade. The wrong fix is one giant DELETE of old sent rows: it fights inserts for locks and thrashes the indexes, hurting the hot path. The right fixes are to delete sent rows in small batches out of band, or to partition the outbox by day so cleanup becomes a metadata-only DROP PARTITION instead of index-thrashing row deletes. Either way, reaping is background maintenance kept off the business transaction, which should only do the two INSERTs." },

<Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: a dual write across two stores has no crash-safe ordering; the outbox collapses it into one local transaction whose COMMIT durably records the intent to publish; a relay ships rows by polling (simple, interval-bounded) or CDC (fast, operationally heavier); the publish-then-mark gap makes delivery at-least-once, so consumers dedupe on a stable event id; and the operational tax — bloat, ordering, competing relays — is paid with partitioning or batched reaps, aggregate keying, and FOR UPDATE SKIP LOCKED. Now when you see a handler that commits a row and fires a broker call, you know the exact question to ask: where does this crash, and where is the intent to publish made durable?
</Recap>
