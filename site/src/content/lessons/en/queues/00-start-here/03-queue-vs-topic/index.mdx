<Hook>
Your shop takes an order. Two things must happen: charge the card, and send the order to the warehouse. You could publish one message and let a single worker do both jobs in sequence — or publish one event and let two independent listeners each react to it. Both are correct designs. They are also different delivery models, and mixing them up is how you charge a card twice or ship nothing at all.
</Hook>

<Crux>A queue delivers each message to exactly one consumer that claims it; a topic delivers a copy of every message to all subscribers. Same broker — opposite promises about who gets the work.</Crux>

<Explanation>

## The same publish, two different fates

Publish one message — `order-placed #42` — into the broker. What happens next depends entirely on which model you chose.

Back to the shop. Charging the card is a queue job: exactly one worker must claim it, because two claims mean two charges. Notifying the warehouse AND updating the recommendations AND pinging analytics from the same `order-placed` event is a topic: three subscribers, three copies, nobody waiting on anyone.

## The mistake that teaches the difference

Put the card charge on a topic with two subscribers and both will charge the card — duplication by design, not by bug. Put the warehouse notification on a queue with one consumer and add a second feature that also needs the event — it will starve, because the first consumer acked and deleted the only copy. The symptom always looks like a bug. The cause is always the wrong model.

This fork is also the map of the track ahead: unit `02-kafka-partitions` is the queue idea scaled out (many queues side by side, order within each), and unit `03-rabbit-exchanges` is the topic idea made routable (rules deciding which subscribers get which messages).

<Inset kind="why" lang="en">
Why do brokers offer both instead of one flexible primitive? Because the guarantees point in opposite directions. A queue must ensure no two consumers process the same message — coordination. A topic must ensure every subscriber gets every message even if one is down for a week — retention per subscriber. One mechanism cannot optimize for "exactly one" and "every one" at the same time, so the broker asks you to choose up front.
</Inset>

<KeyTakeaway>Queue means one worker claims each message and the ack deletes it — use it for jobs that must happen once. Topic means every subscriber gets every message — use it for events many parts react to. Duplication or starvation that looks like a bug is usually this choice, made wrong.</KeyTakeaway>

<Recap lang="en">
A queue and a topic are opposite promises. A queue delivers each message to exactly one consumer; the ack deletes the only copy, so the work happens once — add consumers to split the load. A topic delivers every message to all subscribers; each acks its own copy, so every part of the system reacts — add subscribers to add reactions. Charges and emails are queue jobs; order-placed and price-changed are topic events. From here the track forks the same way: unit 02 scales the queue idea, unit 03 routes the topic idea.
</Recap>
