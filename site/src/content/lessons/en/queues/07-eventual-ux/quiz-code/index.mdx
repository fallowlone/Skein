## Snippet 1 — the half-finished optimistic update

```jsx
const mutation = useMutation({
  mutationFn: (todo) => api.addTodo(todo),
  onMutate: async (todo) => {
    await qc.cancelQueries({ queryKey: ['todos'] });
    qc.setQueryData(['todos'], (old) => [...old, todo]);
    // returns nothing
  },
  onSettled: () => qc.invalidateQueries({ queryKey: ['todos'] }),
});
```

Rollback on error must be explicit." },

## Snippet 2 — the retry button

```jsx
function PayButton({ orderId, amount }) {
  const [status, setStatus] = useState('idle');
  async function pay() {
    setStatus('pending');
    await fetch('/api/charge', {
      method: 'POST',
      body: JSON.stringify({ orderId, amount }),
    });
    setStatus('done');
  }
  // user sees no progress, clicks pay() again on a slow network
  return <button onClick={pay}>Pay</button>;
}
```

<Quiz

  lessonSlug="07-eventual-ux"
  lang="en"
  question="On a slow network the user clicks twice. What goes wrong, and what is the right fix?"
  choices={[
    { label: "Two POSTs hit /api/charge and can become two charges — there is no idempotency key. Fix: generate a stable key per intent (e.g. a UUID created once when the form opens) and send it as an Idempotency-Key header so the server dedupes; also disable the button while pending.", correct: true },
    { label: "Set status to done faster so the button hides sooner.", misconception: "Hiding the button is a race, not a guarantee — a refresh or a second tab still re-triggers it. At-most-once requires an idempotency key on the request, not faster UI." },
    { label: "Wrap the fetch in try/catch; the double charge is just an unhandled error.", misconception: "Both requests succeed independently; there is no error to catch. The problem is two real, accepted intents — only a shared key collapses them to one effect." },
    { label: "Switch from POST to PUT and the charge becomes idempotent.", misconception: "HTTP method semantics do not make a charge idempotent on their own — the server still creates a new charge per request unless it deduplicates on an explicit idempotency key." },
  ]}

## Snippet 3 — the fake-success toast

```jsx
async function publish(post) {
  const res = await fetch('/api/posts', {
    method: 'POST',
    body: JSON.stringify(post),
  });
  if (res.status === 202) {
    toast.success('Published!');
    await qc.invalidateQueries({ queryKey: ['posts'] });
  }
}
```

<Quiz
  id="07-eventual-ux-code-3"
  lessonSlug="07-eventual-ux"
  lang="en"
  question="The POST returns 202 and a consumer writes the post ~800ms later. What two things are wrong here?"
  choices={[
    { label: "It collapses 202 (queued) into a 'Published!' success — fake success before the consumer ran — and it then invalidates immediately, so the refetch races the consumer and returns the list without the new post. Show a pending state and reconcile on a push or a delayed refetch, not instantly.", correct: true },
    { label: "Nothing — 202 is a success code, so the toast and refetch are both correct.", misconception: "202 Accepted means 'queued', not 'done'. Announcing success and refetching inside the consistency window are exactly the two failure modes the unit warns about." },
    { label: "The only bug is the missing await on toast.success.", misconception: "toast.success is fire-and-forget UI; awaiting it changes nothing. The real bugs are treating 202 as done and refetching inside the window." },
    { label: "It should retry the POST until it returns 200.", misconception: "There is no 200 coming — the endpoint is async by design and returns 202. Retrying just enqueues duplicate work; you need a pending state and reconciliation." },
  ]}
/>

## Snippet 4 — the conflict that overwrites

```jsx
function onIncomingUpdate(remote) {
  // local has unsaved edits; remote arrived from another client
  setDoc(remote); // last write wins, silently
}
```

<Quiz

  lang="en"
  question="Two clients edit the same document body. This handler runs on the incoming remote update. What is the senior objection, and the better shape?"

For shared free-form text, reconcile through a CRDT (or at least surface a 409 as a real 'their version / your version / merge' choice) instead of overwriting local state outright.", correct: true },
    { label: "It is correct — the newest update should always win.", misconception: "Newest-wins on free-form text discards real work and trusts clocks that can skew. For a document body this is data loss; a CRDT merges both edits deterministically instead." },
    { label: "The bug is only that setDoc should be wrapped in useCallback.", misconception: "Memoisation is irrelevant to correctness here. The defect is silently overwriting the user's edits rather than reconciling or surfacing the conflict." },
    { label: "Add a setTimeout before setDoc so the local edit lands first.", misconception: "A timing hack does not resolve a conflict — it just changes which write is lost. You need a real merge strategy (CRDT) or an explicit conflict choice." },
  ]}

<Recap lang="en">
Every async-UX bug is read in the mutation and the retry path: an optimistic update without a snapshot-and-onError rollback strands a failed write on screen; a POST without an idempotency key turns a double-click into a double charge; collapsing 202 into a success toast plus an immediate refetch is fake success racing the consumer; and a silent last-write-wins handler destroys a user's unsaved edits. Complete the apply-send-reconcile contract, key the retries, show honest pending states, and reconcile conflicts deliberately instead of overwriting. Now when you open a mutation handler in a PR, your first three checks are: is there a snapshot, is there an onError rollback, and does every retry path carry an idempotency key?
</Recap>
