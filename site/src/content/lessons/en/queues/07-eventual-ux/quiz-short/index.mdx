    { q: "What is the consistency window, and why does an async backend make it the frontend's problem?", a: "The consistency window is the gap between 'the server accepted the write' and 'the server will return that write on a read.' The moment a write stops being synchronous — it goes onto a queue, an event bus, or a worker — that gap opens, because the POST only enqueues the work and a consumer applies it later. Under normal load it might be 50–300ms; under backpressure, a lagging consumer, or a partition rebalance it stretches to seconds. The backend team treats async as a throughput win, but the window does not disappear — it moves onto the client, which now has to render something honest during that gap. A naive UI either lies (shows 'done' before the consumer ran) or shows stale data (refetches inside the window). So the frontend owns the window whether it acknowledges it or not." },
    { q: "State the three-part contract of optimistic UI, and which part juniors skip.", a: "Apply, send, reconcile. (1) Apply the predicted change to local state and show it immediately, so perceived latency is ~0ms. (2) Send the request in the background, keeping enough context — a snapshot — to undo. (3) Reconcile: on success replace the prediction with server truth, which may differ; on failure roll back to the snapshot taken before applying. The part juniors skip is the reconcile/rollback step. An optimistic update that never reconciles is just a lie with better latency: if the request fails and you never restore the snapshot, the predicted value stays on screen forever, diverging silently from what the server actually holds. TanStack Query encodes the contract as onMutate (cancel refetches, snapshot, write prediction) → onError (restore snapshot) → onSettled (invalidate to reconcile)." },
    { q: "When is optimistic UI the wrong tool, and what do you show instead?", a: "Optimistic UI assumes the client can predict the server's result. That holds for actions whose outcome is determined client-side — toggle a checkbox, add a todo, like a post. It is wrong whenever the server decides the outcome: a payment that may be declined, an order number the server assigns, a discount it computes, a transcode that may fail, or a write that may lose a conflict to another user. Faking those produces a prediction that diverges from truth, and without reconciliation it is a confident lie. Instead show an explicit pending/processing state: signal the work is in flight, give it an affordance (a progress step, an ETA, 'we'll email you'), and converge the UI when the real event lands — replacing the pending state with the actual value, including surfacing a 409 conflict as a real choice rather than silently overwriting." },
    { q: "Why does every pending state need a timeout, and what are the two failure modes that lurk here?", a: "Because the event you are waiting for may never arrive. The first failure mode is the infinite spinner: the consumer crashed or the message was dead-lettered, the confirming event never fires, and the UI spins forever — no HTTP timeout governs it because the original POST already returned 202. So every pending state needs a timeout plus a reconciliation path: after N seconds, poll the authoritative endpoint or surface 'still processing, check back.' The second failure mode is double-submit on retry: with no feedback the user clicks again, and now two messages sit on the queue. Without an idempotency key that becomes two charges, two orders, two emails. The pending state and the idempotency key are complementary — the state stops the user from re-clicking out of confusion, the key makes it safe even when they do." },
    { q: "Explain the LWW vs merge vs CRDT tradeoff for reconciling two concurrent async writes, and the frontend's job in each case.", a: "Eventual consistency means two writes can be in flight at once — yours and a teammate's, or your phone's and your laptop's — and reconciliation must pick a winner. Last-write-wins (LWW) stamps each write with a timestamp and keeps the latest; it is trivial and stateless but silently drops the loser's data and depends on synchronized clocks, so clock skew can let an older edit win. Merge logic (field-level or three-way) preserves both sides when changes do not overlap but needs domain rules. CRDTs (conflict-free replicated data types) let replicas merge in any order to the same result with no coordination — the foundation of real-time collab editors — but accumulate metadata and can grow unbounded without garbage collection. For a rename, LWW is fine; for a shared document, LWW destroys text, so you reach for a CRDT. The frontend's job in every case is to make the chosen strategy legible: if LWW dropped a change, say so and offer to reapply; if a merge happened, show what merged; surface a 409 as a real choice, never a silent overwrite." },
    { q: "Why does 'POST then immediately refetch' break read-your-own-writes, and how do you keep the eventual refresh without the violation?", a: "The POST returns fast (often 202) because it only enqueues the work; the actual write happens when a consumer processes the message, anywhere from 50–300ms to seconds later. An immediate refetch races that consumer and almost always wins, so it reads the state from before the write landed and returns the user's own change as missing — then the UI trusts that stale read and erases what they just did. The fix is to stop depending on a racing read: apply the change optimistically as a local echo so the user sees it immediately, and reconcile with the server later — invalidate after a short delay, wait for a push (WebSocket/SSE) that signals the consumer finished, or sticky-read from a node guaranteed to have the write. You keep the eventual refresh; you just stop letting it overwrite the user's truth before the backend has caught up." },
