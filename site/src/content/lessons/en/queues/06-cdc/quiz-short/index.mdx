    { q: "Why does log-based CDC beat polling a table on a cursor, on every axis that matters?", a: "Polling asks the table 'any rows newer than my cursor?' on an interval, so it carries up to one interval of latency, misses any row that was inserted and deleted between two polls, and adds recurring query load to a table that may already be hot. Log-based CDC instead tails the database's own write-ahead log — the durable, ordered record the database writes for crash recovery and replication anyway. It emits one event per committed row change within milliseconds of commit, captures every intermediate state including hard deletes, and adds zero query load because it reads the log, not the rows. It also needs no application change: the app keeps doing plain INSERT/UPDATE/DELETE. The price is operational, not latency: you now own a replication slot." },
    { q: "Explain why a logical replication slot can take down the primary, and what you put in place before shipping CDC.", a: "A logical replication slot is a server-side bookmark: it records the LSN your consumer confirmed and promises Postgres will not recycle any WAL past that point, so the consumer can always resume. That promise is unconditional — it holds even when the consumer is dead. So if the Debezium connector or its Kafka Connect worker crashes, OOMs, or lags, WAL stops being recycled and piles up; on a busy OLTP box doing 20–50 GB of WAL per hour a healthy disk can fill in under two hours, and when Postgres runs out of disk it stops accepting writes — a full primary outage. A long-running transaction does the same silently by freezing restart_lsn. Before shipping I add two layers: alert on slot lag (the byte distance between confirmed_flush_lsn and current WAL in pg_replication_slots) so I act before disk pressure, and cap the blast radius with max_slot_wal_keep_size so Postgres invalidates a runaway slot instead of dying. The cap forces a re-snapshot, which beats an outage." },
    { q: "What is the snapshot-then-stream startup, and why is the snapshot the dangerous part?", a: "A connector starting on an existing database has a cold-start problem: the WAL only contains recent changes, but a downstream consumer needs the current state of every row. So Debezium snapshots first — read the whole table (or a filtered set) to seed initial state — then switches to tailing the log from the LSN captured at snapshot start, so nothing is missed at the seam. The snapshot is where load and locking bite: a classic blocking snapshot on MySQL takes a global read lock (FLUSH TABLES WITH READ LOCK) that can freeze writes on a large table for an uncomfortable window. The modern answer is the incremental snapshot — signal/watermark-based — which snapshots in chunks while streaming continues, can be paused and resumed, and never takes a long lock, at the cost of more moving parts. On a multi-terabyte table that is the difference between a multi-hour write freeze and a background trickle." },
    { q: "Why does capturing full DELETE events need REPLICA IDENTITY FULL, and what does it cost? What is a tombstone?", a: "A Postgres DELETE logs only the primary key by default, so the change event's before image is just the key — fine if you only need to know which row went away, useless if a downstream needs the full pre-delete row. Setting REPLICA IDENTITY FULL on the table makes the WAL log the entire old row for deletes, giving a complete before image — but it also makes every UPDATE log the whole old row, raising WAL volume (which feeds back into slot/disk pressure). Separately, a tombstone is a record with a null value that Debezium emits after a delete; it carries no row data, but it lets log-compacted Kafka topics actually drop the key rather than keep a ghost forever. Forget the tombstone semantics and your compacted topic keeps deleted keys around." },
    { q: "Why is CDC delivery effectively at-least-once, and how does that change how you write the consumer? How does ordering help?", a: "The slot/LSN mechanism gives precise resume, not exactly-once. On a crash the connector restarts from the last LSN it confirmed, so any events it emitted but had not confirmed get re-emitted — a downstream can see the same change twice. Debezium 2.x can do exactly-once into Kafka via Kafka transactions, but that guarantee ends at Kafka: the moment your consumer reads a record and performs a side effect, a replay means the side effect happens again. So end-to-end you design for at-least-once. The fix is idempotency: dedupe on a stable key plus the event's LSN/position, or make the operation naturally idempotent — an upsert keyed by primary key, set-to-this-value rather than increment, a no-op when the target already reflects the change. Ordering helps: Debezium keeps per-key order by routing a key to one partition, so an upsert-by-key consumer converges even with duplicates — but you cannot assume global cross-table commit order." },
    { q: "When would you reach for the outbox pattern instead of capturing domain tables directly, and how does it relate to CDC?", a: "CDC and the outbox pattern are not rivals — they compose. The outbox pattern solves atomicity: in the same transaction you write your business row and an event row, so they commit together and you never get the dual-write split-brain where the DB write succeeds but the message publish fails. But you still need something to ship outbox rows out: a polling relay is the simple option; pointing Debezium at the outbox table is the log-based one (Debezium even ships an outbox event router). So 'CDC vs outbox' is the wrong axis. The real choice is whether to capture your domain tables directly — zero app change, but you are coupled to your physical schema and emit raw row shapes — or capture a purpose-built outbox table whose event shape you control, at the cost of writing to it in every transaction. Pick the outbox when you want a stable public event contract decoupled from table layout." },
