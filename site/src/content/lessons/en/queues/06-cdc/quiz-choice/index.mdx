<Quiz

  lessonSlug="06-cdc"
  lang="en"
  question="A Debezium connector's Kafka Connect worker OOMs and stays down for six hours on a busy OLTP box. What is the dominant risk to the source Postgres, and why?"
  choices={[
    { label: "The slot pins WAL at its restart_lsn and the server keeps every segment since, so on a box doing tens of GB of WAL per hour the data volume fills and Postgres stops accepting writes — a full primary outage.", correct: true },
    { label: "Events between the crash and recovery are lost, but the database itself is unaffected.", misconception: "Events are not lost — the slot holds the WAL precisely so the connector can resume from its LSN. The danger is the opposite: retained WAL grows until the disk fills." },
    { label: "Postgres automatically drops the slot once the consumer disconnects, so nothing accumulates.", misconception: "A logical slot persists across disconnects by design — that persistence is the whole point and exactly why it is dangerous. Postgres only invalidates it if max_slot_wal_keep_size is set and exceeded." },
    { label: "Postgres pauses new writes until the consumer returns to keep the slot consistent.", misconception: "Postgres keeps accepting writes — that is what grows the WAL. It only stops when the disk is actually full." },
  ]}

  lessonSlug="06-cdc"
  lang="en"
  question="You must bootstrap CDC on a multi-terabyte MySQL table that takes constant writes, and you cannot freeze writes for hours. Which snapshot strategy fits, and what is the tradeoff?"
  choices={[
    { label: "An incremental (signal/watermark-based) snapshot: it reads the table in chunks while streaming continues, can pause and resume, and never takes a long lock — at the cost of more moving parts.", correct: true },
    { label: "A classic blocking snapshot with a global read lock for a guaranteed-consistent point in time.", misconception: "A blocking snapshot (FLUSH TABLES WITH READ LOCK) is exactly what freezes writes on a large table for an uncomfortable window — the thing the brief forbids on a multi-terabyte table." },
    { label: "Skip the snapshot and stream only from now; the WAL/binlog already holds the full table state.", misconception: "The log only contains recent changes, not the current state of every existing row. Skipping the snapshot leaves downstream consumers missing all rows that were not modified after start." },
    { label: "Dump the table with mysqldump, load it downstream, then start streaming from the dump's timestamp.", misconception: "A timestamp is not a replication position; you cannot reliably align a logical dump to an exact binlog offset, so you risk a gap or overlap at the seam. The incremental snapshot exists to align snapshot and stream cleanly." },
  ]}
/>

<Quiz
  id="06-cdc-choice-4"
  lessonSlug="06-cdc"
  lang="en"
  question="A Postgres DELETE event arrives with a before image that contains only the primary key, but your downstream needs the full pre-delete row. What is going on, and what is the cost of the fix?"
  choices={[
    { label: "The table is on the default REPLICA IDENTITY, which logs only the key for deletes. Setting REPLICA IDENTITY FULL logs the whole old row — but now every update also logs the entire old row, raising WAL volume.", correct: true },
    { label: "Debezium drops the before image to save space; raise the connector's payload size limit.", misconception: "Debezium emits exactly what the WAL contains for that table. The before image is key-only because of REPLICA IDENTITY, not a connector size limit." },
    { label: "The row was already vacuumed away, so only the key survives.", misconception: "Vacuum reclaims dead tuples but does not control what the WAL logs for a DELETE. The pre-delete image is governed by REPLICA IDENTITY, set per table." },
    { label: "You need a tombstone record to recover the full row.", misconception: "A tombstone is a null-value record after a delete that lets compacted Kafka topics drop the key — it carries no row data. The full before image comes from REPLICA IDENTITY FULL." },
  ]}
/>

  question="Your team says 'Debezium 2.x gives exactly-once, so our consumer can skip dedupe.' Where does that reasoning break?"
  choices={[
    { label: "Exactly-once applies only to delivery into Kafka via transactions. The moment your consumer reads a record and performs a side effect, a crash/resume can replay it — so end-to-end it is at-least-once and consumers must be idempotent.", correct: true },
    { label: "It is correct — exactly-once into Kafka means the consumer can never see a duplicate.", misconception: "The guarantee ends at Kafka.     { label: "It breaks because Debezium cannot track offsets precisely.", misconception: "Debezium tracks offsets precisely via the slot/LSN — that is how it resumes. Precise resume is exactly what can cause a replay of events after the confirmed point." },

  question="A consumer joins changes from an orders table and a payments table and assumes it sees them in commit order. Under Debezium-to-Kafka, why is that assumption unsafe?"

<Recap lang="en">
Across the unit the through-line is one chain of consequences: the slot's unconditional WAL promise is what makes CDC resumable and also what fills the disk when a consumer stalls or a long transaction freezes restart_lsn; bootstrapping means snapshot-then-stream, with incremental snapshots trading simplicity for a lock-free start; capturing full deletes costs WAL volume via REPLICA IDENTITY FULL; and because resume is at-least-once with only per-key ordering, consumers must be idempotent and must not assume global commit order.
</Recap>
