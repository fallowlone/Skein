Distribution: it spreads load across partitions, brokers, and disks. Ordering: because the same key always hashes to the same partition, all of that key's records sit in one ordered log — and Kafka guarantees order only within a partition, never across the topic. Co-location: a single consumer reading that partition sees the key's full history in sequence. The trap is that you cannot tune one without affecting the others. Choosing a key for even load distribution may scatter related events; choosing a key for ordering (say customerId) may pile a whale onto one partition. So the key choice is really a choice of what stays ordered and co-located, and changing N to rebalance load silently breaks the ordering the key was buying you." },
    { q: "Why is per-key ordering free in Kafka, and what is the exact scope of the ordering guarantee?", a: "Kafka guarantees ordering only within a single partition: records are appended to a partition's log at monotonically increasing offsets and read back in that exact order. There is no global, cross-partition, cross-topic, or wall-clock ordering. Per-key ordering comes for free only because the default partitioner sends every record with the same key to the same partition (hash(key) % N), so a key's events land in one log in send order. The moment a key's records can land on more than one partition — a null key that scatters, or a partition-count change that rehashes the key — that ordering is gone, because there is no defined order between two independent partitions." },
    { q: "Explain why consumer parallelism is hard-capped at the partition count.", a: "A consumer group divides the topic's partitions among its members so that each partition is owned by exactly one consumer in the group at a time — never two. That one-consumer-per-partition rule is what makes consumption safe and ordered, but it also means the number of partitions is the maximum number of consumers that can do useful work. With 6 partitions, a 7th consumer in the group gets no assignment and sits idle. So you cannot scale consumer throughput past the partition count by adding consumers; raising parallelism requires more partitions, which is the one-way door. This is why partition count is a capacity-planning decision made up front, not a runtime tuning knob." },
    { q: "Why is increasing a topic's partition count a one-way door, and what is the safe alternative?", a: "The partitioner is hash(key) % N, a function of N. Increase N from 6 to 12 and the modulo result changes for most keys, so a key that always went to partition 2 now routes to a different partition. Existing records are never moved — they stay where they were written — so a key's history is now split across the old and new partition with no defined order between them. Any consumer that built per-key state (a running balance, a state machine, a Kafka Streams changelog keyed by partition) reads a broken, out-of-order history. And you can never decrease the count to undo it, because two ordered logs cannot be correctly merged. The safe path is not to resize in place: create a new topic with the larger count, dual-write to old and new, drain the old, then cut consumers over — a migration, not a config edit. Better still, over-provision partitions up front for expected growth." },
    { q: "What is a stop-the-world rebalance, why does it hurt, and what two mechanisms reduce it?", a: "When a consumer joins, leaves, or is presumed dead (missed heartbeat, long GC pause, slow deploy), the group reassigns partitions among its members. Under the classic eager protocol every consumer revokes all of its partitions and consumption halts across the entire group until the new assignment is computed and accepted — a pause of seconds, worse during a rebalance storm where members keep flapping. It hurts because it converts one consumer's blip into downtime for every partition. Incremental cooperative rebalancing (Kafka 2.4+) revokes only the partitions that must actually move, so most consumers keep processing through the rebalance. Static membership (KIP-345) gives each consumer a stable group.instance.id, so a quick restart within the session timeout is recognized as the same member and triggers no rebalance at all. Together they turn rebalancing from a stop-the-world event into near-background bookkeeping." },
    { q: "What is hot-partition skew, why do more partitions and more consumers not fix it, and where is the real fix?", a: "Hot-partition skew is when one key dominates traffic — a whale customer, a viral product — so its records all hash to one partition. That partition's single owning consumer is pegged at 100% while the others idle. Adding partitions does not help because the hot key still hashes to exactly one of them; adding consumers does not help because consumer parallelism is capped at the partition count and a single partition still has a single owner. The bottleneck is structural: one key on one partition. The fix is at the key level, not the partition level — salt the key (append a bounded suffix so the hot entity spreads across several partitions, accepting that strict per-entity ordering is relaxed) or split the hot entity into sub-keys. You change what the partitioner sees, not how many partitions exist." },
