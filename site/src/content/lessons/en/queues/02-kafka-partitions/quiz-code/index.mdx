## Snippet 1 — the producer key

```java
// Order events: created, paid, shipped, cancelled all flow through here
ProducerRecord<String, OrderEvent> record =
    new ProducerRecord<>("order-events", event.getType(), event);
//                                       ^^^^^^^^^^^^^^^^^
//                                       key = event TYPE, not order id
producer.send(record);
```

## Snippet 2 — the partition math

```python
# Default murmur2-style partitioner: partition = hash(key) % N
def partition_for(key, N):
    return hash(key) % N

# orderId "A-4711" before and after a partition increase
partition_for("A-4711", 6)    # -> 2
partition_for("A-4711", 12)   # -> 8     # same key, different partition!
```

  id="02-kafka-partitions-code-2"

  lang="en"
  question={"A topic was raised from 6 to 12 partitions while live. Reading this math, what is the consequence for key A-4711, and why can't you undo it?"}
  choices={[
    { label: "A-4711's old records remain on partition 2 while all future records route to partition 8, so its history is split across two unordered partitions and per-key ordering breaks. You can't shrink back to 6 — Kafka can't correctly merge two independent ordered logs.", correct: true },
    { label: "Kafka re-runs the partitioner over old records and moves A-4711 to partition 8, keeping it together.", misconception: "Existing records are never relocated on a partition increase. Only future writes use the new modulo, which is exactly what splits the key across partition 2 and partition 8." },
    { label: "Nothing breaks because hash(key) is stable, so the partition stays the same.", misconception: "hash(key) is stable, but the partition is hash(key) % N, and N changed from 6 to 12. The modulo result changes for most keys — here from 2 to 8." },
    { label: "It's reversible: set N back to 6 and A-4711 returns to partition 2.", misconception: "Partition count can only increase, never decrease. Kafka refuses to merge partitions because there is no correct way to interleave two independent offset timelines." },
  ]}
/>

## Snippet 3 — the consumer config

```properties
# Consumer group: payments-processor, 4 instances behind a rolling deploy
group.id=payments-processor
session.timeout.ms=10000
heartbeat.interval.ms=3000
# group.instance.id is NOT set
partition.assignment.strategy=org.apache.kafka.clients.consumer.RangeAssignor
```

    { label: "session.timeout.ms is too high, so the group waits 10s before noticing the restart.", misconception: "Lowering the session timeout makes the group declare members dead faster — causing MORE rebalances, not fewer. Static membership lets a quick restart rejoin as the same member without any rebalance." },
    { label: "heartbeat.interval.ms is too low and floods the coordinator.", misconception: "A 3s heartbeat at a 10s session timeout is a normal ratio and is not the cause of the deploy stalls. The stall is the eager rebalance revoking all partitions on each restart." },
    { label: "RangeAssignor is the only assignor available, so this is unavoidable.", misconception: "CooperativeStickyAssignor exists precisely to avoid stop-the-world revocation by moving only the partitions that must change. Combined with static membership, deploy-time rebalances mostly disappear." },
  ]}

<Recap lang="en">
Every partition incident is read in code, config, and logs: the producer key decides what stays ordered (key by the entity, not the event type); hash(key) % N means a partition increase reroutes live keys and can never be undone; an eager assignor plus a missing group.instance.id makes every deploy a stop-the-world rebalance; and a join/revoke loop ending in poll-timeout is a rebalance storm from slow processing, not a broker or partition problem. Read the key and the config first, fix the structural cause, then confirm against lag and rebalance metrics.
</Recap>
