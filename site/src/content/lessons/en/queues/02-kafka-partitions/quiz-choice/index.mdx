    { label: "Raising to 12 is fine because Kafka migrates existing records to the new partitions and keeps each key together.", misconception: "Kafka never moves existing records on a partition increase — they stay where they were written.     { label: "Just decrease back to 6 if ordering breaks.", misconception: "You cannot decrease partition count at all — it only ratchets upward. There is no correct way to merge two ordered logs, so Kafka refuses; the change is effectively permanent." },

  question={"One consumer in a healthy group is pegged at 100% CPU and lagging while the other five idle. Partition and consumer counts are balanced. What is happening, and where is the fix?"}
  choices={[
    { label: "Hot-partition skew: one dominant key (a whale customer, a viral SKU) hashes to one partition, so all its traffic lands on one consumer. Adding partitions or consumers does nothing — fix at the key level by salting or splitting the hot entity.", correct: true },
    { label: "The assignment is unbalanced; trigger a rebalance to spread partitions more evenly.", misconception: "The partitions are evenly assigned — the imbalance is in the data, not the assignment. A rebalance reshuffles ownership but the hot key still funnels to one partition afterward." },
    { label: "Add more consumers so the load spreads off the hot one.", misconception: "Consumer parallelism is capped at the partition count, and a single key still maps to a single partition. New consumers either idle or own other partitions — none can relieve the one hot key." },
    { label: "The hot consumer needs a bigger fetch size to drain faster.", misconception: "Fetch tuning helps marginally but cannot fix a structural skew where one partition carries a disproportionate share of traffic. The bottleneck is one key on one partition." },
  ]}

    { label: "An eager (stop-the-world) rebalance: every consumer revokes all its partitions when one leaves, halting the whole group.     { label: "The new pod is slow to fetch its first batch; raise the fetch size.", misconception: "The pause spans the whole group, not just the new pod, and it happens before any fetching — it is the rebalance protocol revoking and reassigning partitions, not a fetch-sizing issue." },
    { label: "Partitions are being physically moved between brokers during the deploy.", misconception: "Consumer rebalances reassign partition ownership among consumers; they do not move partition data between brokers. Replica movement is a separate, broker-side operation." },
    { label: "The group coordinator is overloaded; add more brokers.", misconception: "The stall is the rebalance protocol itself stopping consumption, not coordinator capacity. The fix is the rebalance strategy — cooperative rebalancing and static membership — not more brokers." },
  ]}

    { label: "It works fine — Kafka orders all records in a topic by send time.", misconception: "Kafka orders only within a single partition, never across a topic, and never by wall-clock send time. Null-key records scatter, so same-entity events can interleave out of order." },
    { label: "Add more partitions so each entity gets its own.", misconception: "More partitions cannot pin a null-key record to a consistent one — without a key the partitioner has nothing to hash, so records keep scattering. The fix is to supply a key, not to add partitions." },

<Recap lang="en">
The through-line is one mechanism wearing three hats: hash(key) % N does distribution, per-key ordering, and co-location at once. From it everything follows — ordering holds only within a partition, consumer parallelism is hard-capped at the partition count, and changing N rehashes keys and breaks per-key order, so the count is a one-way door you provision for up front rather than tune. The two production failures, hot-partition skew (fix at the key level) and stop-the-world rebalances (tamed by cooperative rebalancing and static membership), both trace back to the same lesson: the key and the count are the real design decisions, and they are made before the topic exists.
</Recap>
