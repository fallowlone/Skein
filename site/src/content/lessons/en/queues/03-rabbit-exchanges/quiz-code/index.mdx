## Snippet 1 — topic bindings

```text
exchange: events  (type: topic)

bindings:
  Q_audit   <- "order.#"
  Q_eu      <- "order.*.eu"
  Q_created <- "order.created.*"

publish routing key: "order.created.eu"
```

  choices={[

    { label: "Only Q_audit, because # is the broadest pattern and wins.", misconception: "Topic bindings are not ranked or exclusive — there is no most-specific-wins. Every binding whose pattern matches independently delivers a copy, so all three queues receive the message." },
    { label: "Only Q_eu and Q_created, because order.# needs more than the matched words.", misconception: "# matches zero or more words, so order.# matches order.created.eu fully. Q_audit receives a copy too." },
    { label: "None — a routing key can only satisfy one binding pattern.", misconception: "A routing key can satisfy any number of bindings at once; that fan-out to multiple queues is exactly what topic exchanges are for." },
  ]}

## Snippet 2 — the prefetch config

```python
channel.basic_qos(prefetch_count=1000)   # one channel, many consumers
channel.basic_consume(queue="jobs", on_message_callback=handle)
# handle() does slow CPU-bound work, ~200ms per message
```

<Quiz
  id="03-rabbit-exchanges-code-2"
  lessonSlug="03-rabbit-exchanges"
  lang="en"
  question="Several workers consume jobs with this config and work is unevenly distributed while broker memory climbs. What is the defect and the fix?"
  choices={[
    { label: "prefetch_count=1000 lets one worker reserve a 1000-message batch of unacked messages, starving idle peers and pinning that memory in the broker. Set a low prefetch (start at 1) and raise it with metrics.", correct: true },
    { label: "basic_consume should be basic_get to pull on demand.", misconception: "Polling with basic_get is slower and still does not fix distribution; the push model is fine. The defect is the oversized prefetch reserving a large unacked batch on one consumer." },
    { label: "The queue needs to be declared durable.", misconception: "Durability controls whether messages survive a broker restart, not how in-flight messages are distributed across consumers. The skew and memory growth come from the high prefetch." },
    { label: "Nothing — a high prefetch always improves throughput.", misconception: "A high prefetch helps only when consumers are fast and uniform; with 200ms CPU-bound work it causes head-of-line starvation and unbounded unacked memory. Low prefetch is the senior default." },
  ]}
/>

## Snippet 3 — the dead-letter config

```text
declare queue "work" with arguments:
  x-dead-letter-exchange: "dlx"
  x-message-ttl: 30000          # 30s

exchange "dlx" (type: fanout)  ->  queue "work.dead"

consumer on "work": on failure -> channel.basic_nack(requeue=True)
```

<Quiz
  id="03-rabbit-exchanges-code-3"
  lessonSlug="03-rabbit-exchanges"
  lang="en"
  question="A poison message keeps looping on queue work and never reaches work.dead despite the dead-letter config. Why?"
  choices={[
    { label: "basic_nack(requeue=True) puts the message straight back on work, so it is never rejected or expired in a way that triggers dead-lettering. Nack with requeue=False (or rely on TTL/retry limit) so rejected messages route to the dlx.", correct: true },
    { label: "The dlx must be a topic exchange, not fanout, to receive dead letters.", misconception: "Any exchange type can be a dead-letter target; fanout to a single quarantine queue is fine. The reason nothing arrives is that requeue=True never lets the message become a dead letter." },
    { label: "x-message-ttl is too long, so the message never expires.", misconception: "TTL would eventually dead-letter an untouched message at 30s, but here the consumer immediately requeues it, resetting it onto the active queue before TTL fires. The requeue flag is the real defect." },
    { label: "Dead-lettering only works on quorum queues.", misconception: "Dead-lettering works on classic and quorum queues alike. The message loops because requeue=True keeps re-delivering it instead of rejecting it to the dlx." },
  ]}
/>

## Snippet 4 — the default exchange

```python
# no exchange declared; publish with empty exchange name
channel.basic_publish(exchange="", routing_key="reports", body=payload)
# a queue named "reports" exists but is ALSO bound to a topic exchange "events"
```

<Quiz

  lessonSlug="03-rabbit-exchanges"
  lang="en"
  question="Where does this message go, given the empty exchange name and routing key reports?"
  choices={[
    { label: "Straight to the queue named reports. The empty-string exchange is the default exchange — a direct exchange where every queue is implicitly bound by its own name — so routing_key=reports delivers to the queue reports.", correct: true },
    { label: "To the topic exchange events, because that is the only declared exchange.", misconception: "The empty exchange name selects the default (nameless) direct exchange, not events. The message never touches events on this publish." },
    { label: "Nowhere — an empty exchange name is invalid.", misconception: "The empty string is a valid, always-present exchange: the default direct exchange. It is the one case where a routing key behaves like a queue name." },
    { label: "To every queue, because an empty name means broadcast.", misconception: "Empty name is the default direct exchange, not a fanout. It delivers only to the queue whose name equals the routing key — here, reports." },
  ]}
/>

<Recap lang="en">
Routing is read in the binding table, not the stack trace: topic patterns match independently and every match yields a copy (* is exactly one word, # is zero or more); a too-high prefetch reserves a large unacked batch on one consumer and starves the rest; dead-lettering only fires on reject/expire, so nack-with-requeue loops a poison message forever; and the empty-string exchange is the default direct exchange where the routing key is the queue name. Read the type and bindings first, predict the copies, then fix.
</Recap>
