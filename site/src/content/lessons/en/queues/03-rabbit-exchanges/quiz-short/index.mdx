The exchange then uses its type, the message's routing key, and the bindings that connect it to queues to decide which queues — if any — get an independent copy. This indirection is the whole point: the producer knows nothing about consumers, queues, or how many exist. You can add a new consumer by declaring a queue and binding it, with zero changes to the producer. That decoupling is why RabbitMQ is called a smart broker — routing logic lives in the broker, not in the producer or consumer. Even the so-called default exchange is a direct exchange where the routing key equals the queue name, so publishing to a queue is really just publishing to that exchange." },
    { q: "Describe the four exchange types and the routing rule each one applies.", a: "The type is the routing algorithm. Direct routes when the routing key exactly equals the binding key — point-to-point work routing. Fanout ignores the routing key and copies every message to every bound queue — the cheapest, fastest broadcast path for cache invalidation or pub/sub. Topic treats the routing key as dot-delimited words and matches dotted patterns where * matches exactly one word and # matches zero or more, so order.*.eu catches order.created.eu but not order.created.us, and logs.# catches everything under logs — this is the workhorse for selective subscription. Headers ignores the routing key and matches on a map of header attributes with an x-match of all or any — powerful but slower and rarely worth it when a topic key expresses the same intent more cheaply." },
    { q: "Explain the smart-broker push model and how it differs from Kafka's pull log.", a: "RabbitMQ pushes messages to consumers and deletes each one once it is acknowledged. The broker is smart — it routes, tracks per-message acks, and redelivers on failure — while the consumer is relatively dumb, processing what it is handed and acking. A consumed-and-acked message is gone; there is no log to rewind. Kafka is the mirror image: a dumb broker with smart consumers, an append-only log where consumers track their own offset and pull at their own pace, and nothing is deleted on consume. That lets a Kafka consumer group replay from the beginning or reprocess after a bug fix. RabbitMQ's per-message ack-and-delete gives fine-grained workflow control and rich routing; Kafka's log gives replay and raw throughput." },
    { q: "Why does a too-high prefetch count cause both unfairness and an outage, and what is the safe default?", a: "Prefetch (basic.qos) caps how many unacknowledged messages the broker will push to one consumer before it must ack. RabbitMQ is push-based, so a high prefetch like 1000 hands a slow consumer a huge reserved batch up front; those messages are now in-flight, so faster idle consumers cannot take them — that is the unfairness. The outage angle is memory: every unacked message stays resident in broker memory, and if processing stalls the unacked count climbs without bound until the node hits its memory high-watermark, at which point RabbitMQ applies back-pressure and blocks all publishers — a full pipeline stall. The safe default is a low prefetch, often 1, raised only with metrics in hand: it spreads work fairly and keeps unacked memory bounded." },
    { q: "What is a dead-letter exchange, and which failure mode does it solve?", a: "A dead-letter exchange (DLX) is a separate exchange that a queue routes messages to when they are rejected (nacked without requeue), expire via TTL, or exceed a length limit. It solves the poison-message failure mode: a consumer that nacks-with-requeue on a payload it can never process gets the same message back forever, pinning a worker in an infinite redelivery loop and potentially stalling the whole pipeline. Configuring the queue to dead-letter on rejection routes that message out to a quarantine queue you can inspect, alert on, and reprocess, so one bad message leaves the hot path instead of looping. Without a DLX, a single poison message can stall an entire pipeline." },
    { q: "How would you guard against an exchange silently dropping unroutable messages?", a: "By default basic.publish does not tell the producer whether a message was actually routed; if no binding matches, the broker drops it and the publish still returns success — the classic silent-drop failure. Two guards: set the mandatory flag so an unroutable message is returned to the producer via a basic.return instead of vanishing, letting you handle or alert on it; or bind a catch-all queue (a topic # binding, or an alternate-exchange on the primary) so nothing is lost unobserved. Either way you should alert on unroutable-message counts in monitoring, because a missing or mistyped binding is invisible otherwise — the producer keeps reporting success while messages go nowhere." },

<Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: producers publish to an exchange, never a queue, and the type plus routing key plus bindings decide which queues get an independent copy. Direct is exact-match, fanout broadcasts, topic matches dotted * / # patterns, and headers matches attributes. The smart-broker push model acks-and-deletes, the opposite of Kafka's replayable pull log. And the production failures are predictable: an unbound exchange drops silently without the mandatory flag, a too-high prefetch starves consumers and grows unacked memory, and a poison message with no dead-letter exchange loops forever. Now when you design or review a RabbitMQ topology, you will catch a missing DLX or an oversized prefetch before they become a 3am incident — because you can reason from first principles, not pattern-match from symptoms.
</Recap>
