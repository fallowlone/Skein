Kafka expresses this with the partition key: choose accountId, Kafka hashes it to a partition, all of that account's events land there in order, and different keys spread across partitions and consumers at full per-partition throughput. SQS FIFO expresses it with MessageGroupId: ordering is strictly per group, never across groups, so aggregate throughput scales with the number of groups (tens of thousands of messages/second) only by spreading load across many groups and batching, not by speeding up any one group." },

A random key per message maximizes spread but scatters one entity's events across partitions, so they race and the ordering you needed is gone. A single fixed key collapses everything onto one partition — total order and a single-threaded pipeline, the throughput tax again. A timestamp key sorts by time, not by entity, which still scatters an entity's events. The key is about which messages must be serialized together, not about even load or chronological sorting." },

<Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: total order needs one serialization point and caps throughput, so you reach for partial order — per-key FIFO via Kafka's partition key or SQS FIFO's MessageGroupId. Choose the key as the consistency boundary, verify the producer is idempotent so it cannot reorder at the source, and remember that at-least-once redelivery, DLQ replay, and repartitioning all break order even when partitioning is correct. The durable consumer is idempotent, prefers commutative effects, and version-guards against stale updates. Now when you see ordering corruption in an incident, you know exactly where to look first: the partition key, then the producer config, then the consumer's version check.
</Recap>
