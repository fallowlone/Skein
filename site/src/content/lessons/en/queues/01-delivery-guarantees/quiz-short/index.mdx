    { q: "State the Two Generals' Problem and explain the asymmetry that makes exactly-once processing achievable even though exactly-once delivery is not.", a: "Two parties communicating over an unreliable channel can never reach mutual certainty that they share the same agreed fact. The proof is by contradiction: take the last message that, if delivered, guarantees agreement; remove it and the protocol must still work, since the sender already had certainty — inductively reducing to zero messages, which is absurd. Exactly-once delivery needs both producer and broker to know a message was delivered exactly once: two-sided certainty, impossible. Exactly-once processing only needs one side — the consumer — to keep a dedup log and skip messages it has already handled. One-sided certainty is achievable, so the production target is effectively-once: at-least-once delivery plus an idempotent consumer." },
    { q: "Name the three failure legs and say which produces most production duplicates and why.", a: "Leg 1, producer to broker: a lost ack makes the producer retry, so the broker sees the message twice (Kafka's idempotent producer fixes this at ~3%). Leg 2, broker durability: a crash before replication loses the message — a loss risk under misconfiguration, not a duplicate source. Leg 3, broker to consumer: the consumer processes the message (charges a card, writes the DB) then crashes before acking, so after the visibility timeout the broker redelivers and the side effect runs again. Leg 3 dominates production duplicates because the side effect is already visible and only the consumer can record that it happened — which is why the durable fix is consumer idempotency." },
    { q: "Why must the dedup INSERT and the side effect commit in one transaction, and why INSERT first?", a: "If the dedup INSERT commits separately and the side effect then fails, the message is recorded as processed but the work never happened — and redelivery skips it forever, causing silent loss. If the side effect runs and then the INSERT fails, the work happened but nothing recorded it, so redelivery repeats it. Wrapping both in one transaction makes them succeed or fail together. INSERT-first with a UNIQUE constraint also defeats the concurrent-delivery race: a second consumer that gets the same message hits the UNIQUE violation, the whole transaction rolls back, the side effect never runs, and it simply acks. SELECT-then-act is not atomic and re-opens the race on every rebalance." },
    { q: "What is the SQS visibility-timeout rule of thumb, and what resets on redelivery?", a: "Set the queue default visibility timeout to about 6x average processing time so the message does not reappear to other consumers while the first is still legitimately working — that gap is the concurrent-duplicate window. For widely variable processing times use the heartbeat pattern: call ChangeMessageVisibility every timeout/3 from a background thread, so a crash lets the timeout lapse naturally and a stuck consumer is recovered. Critically, on redelivery the timeout resets to the queue default — the extended value you set via ChangeMessageVisibility was scoped to the previous receipt handle, so you must raise the queue default itself or re-heartbeat each delivery." },
    { q: "What do Kafka's idempotent producer and transactions each cover, and what do they NOT cover?", a: "The idempotent producer (enable.idempotence=true, ~3%) assigns a producer-ID and per-partition sequence numbers so the broker silently discards producer-retry duplicates — Leg 1 only. Transactions (transactional.id + read_committed consumers, ~20–30%) wrap multi-partition writes plus the offset commit into one atomic unit via a coordinator, making the within-Kafka read-process-write cycle exactly-once. Neither covers cross-system writes: the moment you write to Postgres or call Stripe you exit the Kafka transaction boundary, so a crash between the Kafka commit and the external write replays it. Cross-system correctness needs consumer-side dedup (ON CONFLICT DO NOTHING keyed by offset/msg_id) plus an Idempotency-Key for external APIs." },

If the DB commits but the publish fails (broker down, process crash), downstream consumers never see the event — silent data loss; the reverse leaves an event with no committed state. The outbox pattern INSERTs the event payload into an outbox table in the SAME transaction as the business update, so the event row exists if and only if the update committed. A separate sender (polling, or CDC via Debezium reading the transaction log) publishes pending rows and marks them sent; a crash after publish but before marking leaves the row pending, so it republishes — a duplicate the idempotent producer or consumer dedup absorbs." },

<Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: Two Generals makes exactly-once delivery impossible, so production runs at-least-once and enforces effectively-once in the consumer. Duplicates concentrate at Leg 3; an INSERT-first transactional dedup plus an Idempotency-Key for external calls makes them harmless. Kafka's idempotent producer and transactions only harden the within-Kafka path, SQS visibility timeout must be sized to ~6x processing, and the outbox pattern closes the producer-side dual-write. The recurring lesson: broker guarantees are necessary but never sufficient — correctness lives in the consumer and the operational discipline.
</Recap>
