  question="A notification provider recovers from an outage and the backlog re-flushes; users get the same push 5–9 times. Retries with backoff are already in place. What single piece is missing?"
  choices={[
    { label: "An idempotency key (event+recipient+channel) checked in a fast store before each send, so any retried or re-flushed message collapses to one delivery.", correct: true },
    { label: "Exactly-once delivery negotiated with the provider.", misconception: "Exactly-once across a provider you do not control is unachievable — it can deliver then fail to ack.     { label: "Removing retries so each message sends once.", misconception: "That silently drops messages on any transient blip — the opposite failure. Keep retries (bounded, with backoff+jitter) and add an idempotency check so retries do not duplicate." },
    { label: "More channel workers to drain the backlog faster.", misconception: "Faster draining just delivers the duplicates faster. Duplicates come from re-sending without a dedup guard; throughput does not address it." },
  ]}

<Quiz
  id="02-social-feed-choice-3"
  lessonSlug="quiz-choice"
  lang="en"
  question="Two chat users on different gateways message rapidly; messages render out of order and one duplicates after a reconnect. How do you get consistent ordering and no duplicates?"
  choices={[
    { label: "Route each conversation to one shard that assigns a monotonic per-conversation sequence number at persist time; clients render by sequence and dedup on the client message id.", correct: true },
    { label: "Assign a single global sequence number across all conversations.", misconception: "A global sequence is needless coordination and a bottleneck, and meaningless since order only matters within a conversation. Per-conversation sequence on its shard gives a total order where it is needed without global serialization." },
    { label: "Sort by each client's local timestamp.", misconception: "Client clocks are skewed and unsynchronized, so timestamp sort reorders messages under drift. Order must come from a server-assigned per-conversation sequence at persist time; dedup still needs a message id." },
    { label: "Acknowledge faster so messages cannot arrive out of order.", misconception: "Speed does not impose order — network reordering and retries happen regardless. You need a sequence number for order and a message id for dedup." },
  ]}
/>

<Quiz
  id="02-social-feed-choice-4"
  lessonSlug="quiz-choice"
  lang="en"
  question="An autocomplete queries the search logs on each keystroke to rank matching queries; it is 600 ms slow and overloads the cluster. What is the architectural fix?"
  choices={[
    { label: "Split ranking from serving: an offline pipeline ranks queries periodically into a trie with precomputed top-k per node; the request path walks to the prefix and returns the cached top-k (O(1), no log access), behind an edge cache for popular prefixes.", correct: true },
    { label: "Add read replicas so per-keystroke aggregations spread out.", misconception: "More replicas still run a heavy aggregation per keystroke — scaling the wrong thing. The latency is ranking on the read path over a large dataset; precompute it offline and serve an O(1) lookup." },
    { label: "Cache each full query's results.", misconception: "Autocomplete is about prefixes, not full queries; caching full-query results does nothing for partial-prefix keystrokes. You need a trie of prefixes with precomputed top-k per node, built offline." },
    { label: "Debounce harder on the client.", misconception: "Debouncing trims load a little but even one request still triggers a live aggregation that blows the tens-of-ms budget. You must stop ranking on the read path entirely." },
  ]}
/>

<KeyTakeaway>Across the four cases, the senior move is the same: precompute or buffer on the write/build side — dedup keys, the feed hybrid, ordered-on-persist messages, offline-ranked tries — so the read path stays cheap and safe.</KeyTakeaway>

<Recap lang="en">
The four cases rhyme. A **notification system** retries at-least-once, so it needs an **idempotency key** to avoid the retry storm — retries without dedup duplicate. A **news feed** is read-heavy, so it pushes (fan-out-on-write) for normal authors but **pulls celebrities** in a hybrid, because the power-law tail breaks any single strategy. A **chat system** orders messages with a **per-conversation sequence number** assigned at persist time — a total order where it matters, with no global coordination — and dedups on a message id. **Autocomplete** never ranks live per keystroke; it serves a **precomputed top-k** from a trie built offline, an O(1) read behind an edge cache. The unifying principle across all four: do the expensive work once, on the write or build side, and keep the user-facing path a cheap, safe lookup.
</Recap>
