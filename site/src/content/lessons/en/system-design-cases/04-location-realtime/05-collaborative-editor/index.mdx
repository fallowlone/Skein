<Hook>
The first version of a team wiki saved the whole document on every keystroke pause. Two people edited the same page; the later save won and silently erased the other's paragraph. Version two sent *operations* instead: "insert 'X' at position 1", "delete position 2". Now nothing was erased, but documents slowly drifted apart: two people looking at the same page saw different text, and reloading picked whichever copy the server had. Both versions failed the same requirement, stated in one word: every replica of a document must **converge** to the same content, no matter in what order concurrent edits arrive.
</Hook>

<Crux>Concurrent edits must converge on every replica. OT transforms positions through a central order; CRDTs give each character an ID so merges commute.</Crux>

<Explanation>

## Requirements

Functional:

- Many users edit the same document at once and see each other's changes in near real time, plus cursors and selections (presence).
- Typing feels instant: a local keystroke appears with zero network round trip.
- Edits made offline or during a dropped connection merge when the client reconnects.
- Version history: view and restore earlier states.

Non-functional:

- **Convergence**: once all edits are delivered, all replicas show identical content.
- **Intention preservation**: a merged edit does what its author meant (delete the character they selected, not whatever now sits at that index).
- Remote edits visible within ~100–200 ms; durable once acknowledged.
- Scale to millions of documents; a single document typically has a few to ~100 concurrent editors.

## Estimation

Assume 5M documents open at peak with an average of 2 active editors each.

- An active typist produces roughly 3–5 operations per second; batching keystrokes into 50–100 ms frames brings that to about 10 messages/s per editor.
- 10M editors × 10 messages/s ≈ **100M small messages/s** globally, but each one only matters within its own document. The document is the natural shard key: no operation ever needs another document.
- Each operation is tens of bytes. Bandwidth is not the problem; ordering and merging within a document is.

Opening a document loads the latest snapshot plus the op-log tail after it, then subscribes to the session. The session is the owner of order for that document; the op log is the durable truth; snapshots are a cache over the log that bound load time and power version history.

## Deep dive

### Why index-based operations diverge

Start with the document `abc`. At the same moment, Alice inserts `X` at position 1 (wanting `aXbc`), and Bob deletes position 2 (the `c`, wanting `ab`). Each applies their own edit locally, then receives the other's.

- Alice has `aXbc`, receives "delete 2", deletes the `b`: **`aXc`**.
- Bob has `ab`, receives "insert X at 1": **`aXb`**.

Two replicas, two different documents, and Alice's copy lost the wrong character. Positions are only meaningful relative to the document state they were computed against. Both families of solutions fix exactly this.

### Operational transformation (OT)

OT keeps index-based operations but **transforms** each incoming operation against the concurrent operations it didn't know about. In the example, Bob's "delete 2" is transformed against Alice's "insert at 1": the insert landed before position 2, so the delete shifts to position 3 and removes the `c`. Both replicas end at `aXb`, and Bob's intent survived.

Production OT (Google Docs, and the Jupiter algorithm it descends from) relies on a **central server that defines a single order**. Each client operation carries the server revision it was based on. The server transforms it against every operation committed since that revision, assigns the next revision, and broadcasts it. The client keeps its unacknowledged operations in a pending buffer and transforms incoming server operations against them. This works well and the messages are compact, but writing correct transform functions for a rich document model (text, formatting, tables, lists) is notoriously hard, and OT without a central server needs extra transformation properties that many published algorithms got wrong.

### CRDTs

A **CRDT** (conflict-free replicated data type) avoids positions entirely. Every inserted character gets a globally unique ID, such as `(replicaId, counter)`, and an insert says "put `X` after the character with ID `a1`." Deletes mark a character as a **tombstone** instead of removing it, so later inserts that reference it still resolve. Because operations refer to stable IDs rather than shifting indices, they **commute**: any replica applying the same set of operations in any order reaches the same state. No central ordering is required, which is what makes CRDTs the basis of *local-first* software that works offline for days and syncs peer to peer. Yjs and Automerge are the widely used implementations.

The costs are metadata and cleanup: each character carries an ID, tombstones accumulate, and garbage-collecting them safely requires knowing every replica has seen the delete. Modern implementations compress runs of consecutive characters heavily, so the overhead is far lower than "an ID per character" suggests, but it is not zero.

### Persistence: op log plus snapshots

The durable model is event sourcing applied to a document. Every operation the session accepts is appended to a per-document **op log** before it is acknowledged. Every N operations or M seconds, the session writes a **snapshot**. Loading a document reads the last snapshot and replays the tail; version history is a list of snapshots, with the log for fine-grained replay. Old log segments behind a retained snapshot can be compacted. Because everything for one document lives under one key, the log partitions trivially by `doc_id`.

### Scaling and presence

- **One session owner per document.** Gateways route by `doc_id` through consistent hashing or a lease table, so all editors of a document meet on one server. If that server dies, another takes the lease, loads snapshot plus log, and clients reconnect and resend unacknowledged operations, which is safe because operations are idempotent by ID.
- **Hot documents.** A document with 10,000 viewers and 20 editors splits the paths: editors talk to the session, and viewers subscribe to a fan-out tier (pub/sub) that relays the committed stream.
- **Presence is separate.** Cursors and selections change constantly, are useless a second later, and don't need durability. Send them over an ephemeral channel, throttle to ~10–20 updates per second, and never write them to the op log.

<Inset kind="edgecase" lang="en">
Convergence alone isn't enough. A CRDT can converge to a state nobody intended. If Alice types "hello" and Bob types "world" at the same position while offline, some algorithms interleave the characters as "hweolrllod": every replica agrees, and the result is garbage. Kleppmann's "CRDTs: the hard parts" covers this interleaving anomaly and the algorithms (such as Fugue, or YATA in Yjs) designed to keep each user's run of characters together. The general lesson: test merge semantics against what users expect, not only that replicas match.
</Inset>

## Bottlenecks & tradeoffs

- **OT vs CRDT** is the central decision: OT with a central server for always-online browser editing and compact ops; CRDTs for offline-first, peer-to-peer, or multi-device sync, accepting metadata overhead.
- **The session owner** is a per-document single point of ordering; keep failover fast (lease plus snapshot plus log replay) and make client resends idempotent.
- **Load time** grows with log length; snapshot frequency trades write cost against open latency.
- **Rich content** (tables, comments, formatting) multiplies the merge cases. Model the document as a tree of CRDT types or define OT transforms per node type, and test with randomized concurrent edits (fuzzing) that assert convergence.

</Explanation>

<Recap lang="en">
A collaborative editor has one non-negotiable property: every replica must **converge** to the same content regardless of the order in which concurrent edits arrive, while **preserving each author's intention**. Saving whole documents fails by last-writer-wins, and naive index-based operations fail because a position means different things on replicas that applied edits in different orders. **Operational transformation** fixes this by transforming each incoming operation against the concurrent ones it missed, with a **central server** that defines the order; it is compact and proven in Google Docs but its transform functions are hard to get right. **CRDTs** fix it by giving every element a **unique ID** and turning deletes into **tombstones**, so operations commute and replicas converge in any order, which enables offline-first and peer-to-peer sync at the cost of metadata and tombstone cleanup, plus care about anomalies like interleaving. Around either choice the architecture is the same: clients **apply edits locally first**, a WebSocket gateway routes every editor of a document to **one session owner**, accepted operations go to a per-document **op log** with periodic **snapshots** for fast loads and history, hot documents get a separate viewer fan-out, and **presence** travels on a throttled ephemeral channel. The wiki in the hook needed exactly this: not a better save button, but a merge rule under which every copy ends up the same.
</Recap>
