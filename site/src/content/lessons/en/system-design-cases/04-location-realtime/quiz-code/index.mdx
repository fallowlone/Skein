## Snippet 1 — the proximity query

```python
def nearby(lat, lng, radius_m):
    cell = h3.geo_to_h3(lat, lng, res=9)         # the user's own cell
    candidates = store.get_by_cell(cell)         # only this one cell
    return [p for p in candidates
            if haversine(lat, lng, p.lat, p.lng) <= radius_m]
```

## Snippet 2 — the location publisher

```python
def on_ping(user_id, lat, lng):
    store.set(user_id, (lat, lng), ttl=30)
    for conn in all_connections:          # every connected client
        conn.send({"user": user_id, "lat": lat, "lng": lng})
```

    { label: "Batch the sends and flush every 100 ms.", misconception: "Batching reduces syscalls but still delivers each ping to every connection — the recipient set is the problem, not the flush cadence. Publish per region cell so only nearby subscribers receive it." },
    { label: "Increase the TTL so fewer writes happen.", misconception: "TTL governs expiry, not who receives a ping. The melt is the all-connections fan-out; fix it with region-keyed pub/sub plus an edge friendship/range filter." },

## Snippet 3 — the routing engine setup

```python
def update_traffic(edge_id, new_travel_time):
    graph.set_weight(edge_id, new_travel_time)
    graph.build_contraction_hierarchy()   # runs on every traffic update
    return graph
# called ~thousands of times per second from the probe stream
```

## Snippet 4 — the rank query

```sql
-- a player's rank on the leaderboard
SELECT COUNT(*) + 1 AS rank
FROM scores
WHERE score > (SELECT score FROM scores WHERE player_id = :id);
-- called per player, millions polling their own rank
```

<Quiz
  id="04-location-realtime-code-4"
  lessonSlug="quiz-code"
  lang="en"
  question="Why does this query scale badly, and what replaces it?"
  choices={[
    { label: "COUNT(*) WHERE score > mine is an O(n) count per call, so millions polling their rank scan the table repeatedly. Use a Redis sorted set: ZREVRANK player gives the rank in O(log n) because rank is held in the skip-list spans.", correct: true },
    { label: "Add an index on score and the query becomes O(1).", misconception: "An index helps locate rows but COUNT(*) over all higher scores is still O(n) work per query. A ZSET's ZREVRANK is genuinely O(log n) — it sums precomputed spans instead of counting rows." },
    { label: "Wrap it in a materialized view refreshed nightly.", misconception: "A nightly view makes rank stale (scores change live) and is O(n) to refresh for all players, most never viewed. ZREVRANK computes any rank fresh in O(log n) on read." },
    { label: "Denormalize a 'rank' column updated on each write.", misconception: "Updating a stored rank on a score change can shift the rank of everyone below — O(n) per write. A sorted set keeps rank implicit in its structure, so reads are O(log n) and writes are O(log n)." },
  ]}
/>

</Explanation>

<KeyTakeaway>The mistakes are structural: a single-cell read (query neighbors), a broadcast to all connections (publish by region), a per-tick re-contraction (split structure from weights), an O(n) rank count (use a sorted set).</KeyTakeaway>

<Recap lang="en">
Every failure in this unit is **visible in the code and structural**, not a tuning detail. A proximity query that reads **one cell** misses the place across the boundary — query the **neighbor ring** and filter by exact distance. A location handler that sends each ping to **all connections** is a quadratic broadcast — **publish by region cell** and filter at the subscriber edge. A routing engine that **rebuilds the contraction hierarchy** on every traffic tick is impossible at continental scale — **separate structure from weights** so traffic overlays live. And a SQL rank query (`COUNT(*) WHERE score > mine`) is an **O(n) scan** per poller — replace it with a **sorted set** whose `ZREVRANK` is `O(log n)`. The senior habit is the same each time: read the access pattern off the code, then choose the data structure or routing that fits it — never the version that hides an `O(n)` or a re-computation on the hot path.
</Recap>
