```python
REQUESTS = Counter("http_requests_total", labels=["route", "status", "user_id"])

def handle(req):
    REQUESTS.labels(route=req.route, status=resp.status, user_id=req.user_id).inc()
```

## Snippet 2 — the charge call

```python
def checkout(order):
    # client retries this call on timeout
    resp = psp.charge(amount=order.total, source=order.card)
    ledger.record(order.id, resp)
    return resp
```

## Snippet 3 — the wallet debit

```python
def debit(wallet_id, amount):
    bal = db.query("SELECT balance FROM wallets WHERE id = ?", wallet_id)
    if bal >= amount:
        db.execute("UPDATE wallets SET balance = ? WHERE id = ?", bal - amount, wallet_id)
        return "ok"
    return "insufficient"
```

  choices={[
    { label: "Lost update: both read `bal` before either writes, both pass the check, both write back, and the wallet overdraws. Fix with one atomic conditional UPDATE: `UPDATE wallets SET balance = balance - ? WHERE id = ?     { label: "It's fine because each statement is atomic on its own.", misconception: "Each statement is atomic, but the READ and the WRITE are separate, leaving a gap where another debit reads the same stale balance. Two concurrent debits both pass the check — the classic lost update. Collapse it into one conditional UPDATE." },
    { label: "Add an index on wallets.id.", misconception: "An index speeds lookups but does nothing about the read-modify-write race. The fix is concurrency control: an atomic conditional UPDATE (or SELECT … FOR UPDATE), so check-and-decrement is indivisible." },
    { label: "Cache the balance to make reads faster.", misconception: "Caching makes staleness WORSE and still leaves the gap between read and write. The fix is to make the decrement conditional and atomic at the DB, not to add a cache." },

## Snippet 4 — the multi-night reservation

```python
def reserve(room_type, nights):  # nights = [Dec31, Jan1, Jan2]
    for night in nights:
        db.execute(
          "UPDATE inventory SET booked = booked + 1 "
          "WHERE room_type = ? AND date = ? AND booked < total",
          room_type, night)
    return "reserved"   # each night updated independently, no transaction
```

    { label: "Nothing — each conditional UPDATE already prevents overbooking per night.", misconception: "Per-night atomicity prevents overbooking ONE night, but without a transaction across the range, a 3-night stay can book 2 nights then fail on the 3rd, leaving a broken partial reservation. The whole range must be all-or-nothing." },
    { label: "Add a retry around the loop.", misconception: "Retrying re-runs nights that already booked, double-decrementing inventory. The fix is a single transaction over all nights with a rollback if any night fails — not a retry over partial writes." },
    { label: "Book each night in a separate transaction for better concurrency.", misconception: "Separate transactions are exactly the bug — they allow a partial reservation (some nights booked, one failed). The range must commit atomically as one transaction, all-or-nothing." },

<KeyTakeaway>Money bugs are in the code: an unbounded metric label, a charge with no idempotency key, a read-then-write debit, a per-night loop with no transaction. Each fix: make the operation bounded or atomic.</KeyTakeaway>

<Recap lang="en">
Every data-and-money bug is readable straight off the code. An unbounded **metric label** (user_id) forks a series per value and OOMs the TSDB — series cardinality, not request rate, is the constraint, so drop it from labels. A **charge** the client retries with no **idempotency key** double-charges when the first response is lost — pass a client-minted key with an atomic check-and-store. A **wallet debit** that reads the balance then writes it back has a read-write gap that two concurrent debits exploit (the **lost update**) — collapse it into one atomic conditional UPDATE. And a **multi-night reservation** that decrements each night outside a transaction can leave a **partial reservation** — wrap the whole range in one all-or-nothing transaction. The senior habit is the same across all four: find the hazard, name it, and make the operation bounded (cardinality) or atomic (idempotency, lost update, partial write) — the fix the mechanism requires, not the one that hides it.
</Recap>
