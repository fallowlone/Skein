```bash

DATABASE_URL=postgres://app:Sup3rSecret@db.prod.internal:5432/main
STRIPE_SECRET_KEY=sk_live_51HxQ...redacted...9aZ
JWT_SIGNING_KEY=hs256-7f3e9c1b2a8d4e6f
```

## Snippet 2 — the Vault dynamic-secret fetch

```go
// Fetch a short-lived DB credential from Vault's database engine.
secret, err := client.Logical().Read("database/creds/reporting-ro")
if err != nil {
    return err
}
user := secret.Data["username"].(string)
pass := secret.Data["password"].(string)
// leaseDuration is seconds until Vault auto-revokes this credential
lease := time.Duration(secret.LeaseDuration) * time.Second

db := openDB(user, pass)
defer db.Close()
// ... long-running worker keeps using db for hours ...
```

    { label: "Reading from database/creds/reporting-ro is wrong — dynamic secrets should be read once at startup and cached forever.", misconception: "Caching a dynamic credential forever defeats its purpose: the whole point is the short TTL bounds the blast radius. The credential is meant to be renewed or re-fetched, not pinned for the process lifetime." },
    { label: "The bug is the read-only role; a long-running worker needs an admin credential.", misconception: "Scope is set by need, not duration — a reporting worker should stay read-only (least privilege). The actual defect is lifetime management: the lease is never renewed, so it expires under the worker." },
    { label: "Nothing is wrong; Vault keeps the credential alive as long as a connection is open.", misconception: "Vault revokes on the lease TTL regardless of open connections; an in-flight connection may survive but new auth fails. You must renew the lease or re-fetch — open sockets do not extend a lease." },
  ]}

## Snippet 3 — the KMS envelope-encryption helper

```python
def encrypt_blob(kms, key_id: str, plaintext: bytes) -> dict:
    # ask KMS for a data key: plaintext to use now + wrapped to store
    resp = kms.generate_data_key(KeyId=key_id, KeySpec="AES_256")
    data_key = resp["Plaintext"]
    wrapped_key = resp["CiphertextBlob"]

    ciphertext = aes_gcm_encrypt(data_key, plaintext)   # encrypt LOCALLY

    return {
        "ciphertext": ciphertext,
        "data_key": data_key,        # stored next to the ciphertext
        "wrapped_key": wrapped_key,
    }
```

<Quiz
  id="06-secrets-code-3"
  lessonSlug="06-secrets"
  lang="en"
  question="This helper does local AES-GCM encryption with a KMS-issued data key — envelope encryption. What undoes the whole scheme?"
  choices={[
    { label: "It stores the plaintext data_key next to the ciphertext. Anyone who reads the record decrypts the payload without ever calling KMS. Fix: zero the plaintext data key after use and persist only wrapped_key, unwrapping via KMS to decrypt.", correct: true },
    { label: "Using AES-GCM locally is the flaw; all encryption must happen inside KMS.", misconception: "Local bulk encryption with a KMS-issued data key is the entire point of envelope encryption — it scales and keeps plaintext off the wire. The defect is persisting the plaintext data key, not encrypting locally." },
    { label: "generate_data_key should be called once and the data key reused for every blob forever.", misconception: "Reusing one data key across everything widens the blast radius of a single key compromise; per-context data keys are preferred. Regardless, the fatal bug here is storing the plaintext data key, not how often you mint one." },
    { label: "Returning wrapped_key is the leak, since it is derived from the real key.", misconception: "wrapped_key is the data key encrypted under a KMS key that never leaves KMS — it is safe to store and is exactly what you keep. The leak is the plaintext data_key sitting beside the ciphertext." },
  ]}

## Snippet 4 — the leaky log line

```js
app.post("/charge", async (req, res) => {
  const cfg = { apiKey: process.env.STRIPE_SECRET_KEY, amount: req.body.amount };
  try {
    const charge = await stripe.charges.create(cfg);
    res.json({ id: charge.id });
  } catch (err) {
    // dump everything we have to help debugging
    console.error("charge failed", { cfg, err, body: req.body });
    res.status(500).json({ error: "charge failed" });
  }
});
```

    { label: "There is no leak — logs are internal and access-controlled.", misconception: "Logs flow to aggregators, get exported, and are read by many people and tools; a secret in logs is a well-known leak path. Treat any secret that reaches a log as compromised." },
    { label: "The fix is to log at debug level instead of error so it only appears in dev.", misconception: "Log level does not contain a secret — debug logs are still written, shipped, and read, and config often enables them in prod during incidents. Remove the secret from the log entirely." },

<Recap lang="en">
Every secrets incident is read in artifacts: a committed .env means all three values are leaked and must be rotated, not gitignored; a dynamic credential whose lease is never renewed expires mid-run, so renew or re-fetch; envelope encryption is undone the instant you persist the plaintext data key beside the ciphertext — store only the wrapped key and unwrap via KMS; and a secret-bearing object in a log line ships your live key to every aggregator, so redact it and rotate. Read the artifact, find where the value escapes its boundary or its lifetime is wrong, then fix the boundary before you touch a flag.
</Recap>
