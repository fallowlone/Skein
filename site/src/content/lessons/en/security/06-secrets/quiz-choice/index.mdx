<Quiz

  lang="en"
  question="A live AWS key was committed to a public repo last week. A teammate deleted the line and force-pushed. What is the first action that actually ends the exposure?"
  choices={[
    { label: "Rotate it: revoke the key at AWS so the value the attacker holds stops working — deletion never reaches the copies already cloned.", correct: true },
    { label: "Run git filter-repo to scrub the blob from every commit; once history is clean the secret is safe.", misconception: "History rewriting is hygiene, not remediation. It cannot touch clones, forks, or scanner caches already holding the blob — the key stays valid until you revoke it at the source." },
    { label: "Make the repo private so outsiders can no longer read the history.", misconception: "Flipping visibility cuts the audience but not the risk: the key was public long enough for scanners to grab it (often within a minute), and it is still valid. Only rotation ends the exposure." },
    { label: "Nothing further — the force-push rewrote history, so the line no longer exists anywhere.", misconception: "Force-push only moves your remote's tip. Every existing clone and fork keeps the old commit, and you can never confirm no copy escaped. Deletion is not revocation." },
  ]}

<Quiz
  id="06-secrets-choice-2"
  lessonSlug="06-secrets"
  lang="en"
  question="Your team stores production DB passwords in a .env file deployed to each server, kept out of git via .gitignore. Why is a secret manager the next rung, and what does it add that .env cannot?"
  choices={[
    { label: "Encryption at rest, per-service access control, and an audit trail of every read — the three things a plaintext .env on disk and in CI can never give you.", correct: true },
    { label: "Nothing material — both keep the value out of git, so they are equivalent for production.", misconception: "Out of git is the floor, not the goal. A .env is plaintext on every laptop and CI runner, readable by anyone with the box, with no access control and no audit of who read what — exactly what a manager fixes." },
    { label: "A manager makes the credential unreadable so the app itself cannot leak it.", misconception: "The app still fetches and uses the value in plaintext to authenticate. The manager controls who may read it and records that they did — it does not make a usable secret unreadable." },
    { label: "It removes the need to rotate the password ever again.", misconception: "A manager storing a static value still holds a long-lived secret that must be rotated; it just centralises and audits the storage. Rotation only becomes automatic once you move to dynamic secrets." },
  ]}
/>

<Quiz
  id="06-secrets-choice-3"
  lessonSlug="06-secrets"
  lang="en"
  question="A service fetches a dynamic database credential from Vault with a one-hour TTL instead of a static password. What does the TTL actually buy you?"
  choices={[
    { label: "It bounds the blast radius: a leaked credential auto-expires within the hour without anyone noticing, and each consumer gets a unique, scoped, auditable identity.", correct: true },
    { label: "It encrypts the credential in transit so it can never be intercepted on the wire.", misconception: "Transit encryption is TLS's job and is separate from the TTL. The TTL governs how long a leaked credential stays valid, not whether it can be observed in flight." },
    { label: "It guarantees the database is never overloaded by too many connections.", misconception: "Connection limits are a pooling and quota concern. A short TTL bounds the lifetime of a leaked credential; it says nothing about connection count." },
    { label: "It means the root credentials Vault uses never need rotation.", misconception: "Dynamic secrets automate the leaf credentials, but the engine's root and configuration credentials are still long-lived and must be rotated periodically — Vault even exposes a rotate-root operation for exactly this." },
  ]}
/>

<Quiz
  id="06-secrets-choice-4"
  lessonSlug="06-secrets"
  lang="en"
  question="A team encrypts a 2 MB config blob by sending the whole payload to KMS on every request and hits the KMS request-rate limit. What does envelope encryption change?"
  choices={[
    { label: "KMS generates a data key; you encrypt the payload locally with that data key and store only the KMS-encrypted data key beside the ciphertext. KMS sees tiny keys, not your data, so it scales and your plaintext never leaves the box.", correct: true },
    { label: "It sends the data to KMS in smaller chunks so each request fits under the size limit.", misconception: "Envelope encryption does not chunk the payload through KMS at all. KMS only wraps a small data key; the bulk data is encrypted locally with that key, so KMS never sees the payload." },
    { label: "It replaces KMS with a local key, so KMS is no longer involved.", misconception: "KMS stays in the loop — it protects the data key, and the key-encryption key never leaves KMS. You only move the bulk encryption local; the data key still must be unwrapped by KMS to decrypt." },
    { label: "It removes the need to ever rotate the encryption key.", misconception: "Envelope encryption is orthogonal to rotation. You still rotate the KMS key-encryption key; the win is that you re-wrap data keys rather than re-encrypting every payload." },
  ]}
/>

<Quiz
  id="06-secrets-choice-5"
  lessonSlug="06-secrets"
  lang="en"
  question="An auditor finds one shared API token used by twelve services, granting full admin scope. The reporting service was compromised and the attacker dropped a production table. Which principle would have contained this?"
  choices={[
    { label: "Least privilege with per-service identities: a read-only reporting credential, distinct from every other service, cannot delete a table and the audit log names exactly which service acted.", correct: true },
    { label: "Encryption at rest on the token store — if the token were encrypted the attacker could not have used it.", misconception: "Encryption at rest protects the stored value, not its use. The service decrypts and uses the token legitimately; the damage came from an over-broad scope and a shared identity, not from how the value was stored." },
    { label: "A longer, higher-entropy token so it cannot be guessed.", misconception: "Token strength stops guessing, not abuse of a stolen-but-valid credential. The breach used a real token whose scope was admin and which was shared — entropy is irrelevant to both failures." },
    { label: "Rotating the token more frequently on a fixed schedule.", misconception: "Scheduled rotation shortens exposure but does nothing about the over-broad scope or the inability to tell which of twelve services acted. Least privilege plus unique identities is what limits and attributes the damage." },
  ]}
/>

<Quiz
  id="06-secrets-choice-6"
  lessonSlug="06-secrets"
  lang="en"
  question="A six-year-old org has the same Stripe key pasted into four repos, three CI systems, two wikis, and a Slack thread, and nobody knows which copy any service reads. What is this called and what is the durable fix?"
  choices={[
    { label: "Secret sprawl: the same value copied to many untracked places. The fix is a single source of truth — one secret manager that every consumer reads from at runtime — so there is one place to rotate and one audit trail.", correct: true },
    { label: "Normal redundancy — multiple copies mean the secret is highly available, which is good.", misconception: "Copies are not redundancy; they are uncontrolled duplicates. Each is an independent leak surface, and rotation must hit every copy or stale values break a service. Sprawl is a liability, not availability." },
    { label: "A rotation problem — rotate the key and the duplicates resolve themselves.", misconception: "Rotation makes sprawl worse: you must find and update every scattered copy at once or something breaks. The root cause is the duplication itself; centralising to one source is the fix, then rotation is a single safe operation." },
    { label: "An encryption problem — encrypt each copy where it sits.", misconception: "Encrypting twelve scattered copies leaves twelve copies and twelve places to rotate and audit. The defect is duplication across untracked locations, not that each copy is plaintext." },
  ]}

<Recap lang="en">
Across the unit the through-line is one decision chain: a secret that touches a repo is leaked, so rotation — not deletion — ends the exposure; the maturity ladder climbs from hardcoded to .env to a manager (encryption at rest, access control, audit) to dynamic short-lived credentials whose TTL is the blast radius; envelope encryption lets KMS protect data at scale by wrapping a local data key instead of your payload; least privilege with unique per-service identities contains and attributes a breach; and secret sprawl is cured by a single source of truth, not more copies. Every answer resolves back to bounding and attributing the damage before it happens. Now when you see a colleague reach for gitignore or a force-push to "clean up" a leaked key, you know the first question to ask: has it been rotated?
</Recap>
