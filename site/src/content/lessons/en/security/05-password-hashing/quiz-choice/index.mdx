<Recap lang="en">
The through-line is one threat model and one defense stack. The attack is offline cracking — a leaked hash column run at full hardware speed (~22 billion SHA-256/sec per GPU), which makes any fast hash the wrong tool. The defense is slow + salted + memory-hard: a per-user salt (not secret, beside the hash) to kill rainbow tables, a vetted KDF with named parameters (Argon2id m=19 MiB/t=2/p=1 preferred, bcrypt cost 10+ or scrypt N=2^17 acceptable, PBKDF2 only under FIPS), an optional pepper kept outside the DB, a work factor you raise on a schedule via rehash-on-login, and the library's constant-time verify rather than a hand-rolled equality check. Watch bcrypt's 72-byte truncation trap. Now when you see any of these choices in a code review — SHA-256 in signup, memoryCost: 512, a naked ===, or a login with no needsRehash check — you know exactly which lever to pull and why.
</Recap>
