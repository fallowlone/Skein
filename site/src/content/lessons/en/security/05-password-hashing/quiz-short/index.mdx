Against standard wordlists plus mutation rules, every weak and medium password falls in hours. A salt fixes a different problem — it makes identical passwords hash differently and defeats rainbow tables — but does nothing about speed. The fix is to switch the algorithm to a deliberately slow, memory-hard KDF so that one login verification costs a few hundred milliseconds while a billion offline guesses become economically infeasible." },
    { q: "What is the difference between a salt and a pepper, and where does each one live?", a: "A salt is a random value (at least 16 bytes from a CSRNG) generated per user. Its only job is uniqueness: it makes two users with the same password produce different hashes, which kills rainbow tables and forces per-account cracking. A salt is NOT secret — it is stored right beside the hash, usually embedded in the encoded output string the KDF produces, and that is fine. A pepper is a single secret value mixed into every hash (commonly via HMAC) but stored OUTSIDE the database — in a KMS, HSM, or app secret. It is defense-in-depth for the common breach where only the DB leaks but the app secret does not: without the pepper the leaked salted hashes can't be cracked at all. So salt = per-user, public, in the row, defeats rainbow tables; pepper = global, secret, outside the DB, defeats DB-only leaks. You can use both." },
    { q: "Why does memory-hardness cripple an attacker more than simply raising a CPU-bound iteration count?", a: "The attacker's structural advantage is parallelism: a GPU has thousands of cores and runs thousands of guesses at once, so a purely CPU-slow hash (a high PBKDF2 iteration count, say) just gets divided across those cores and the attacker still wins on throughput. Memory-hardness changes the economics by making each single guess allocate a configured block of fast RAM — Argon2id's OWASP minimum is m=19456 (19 MiB). A GPU has limited memory bandwidth, so it can only run a handful of 19-MiB guesses in parallel instead of thousands. You attack the hardware advantage directly rather than just the clock speed, which is why Argon2id (and scrypt) resist GPUs and ASICs far better than PBKDF2." },

Use the id variant for both GPU and side-channel resistance, not i or d. scrypt: also memory-hard, predates Argon2; OWASP N=2^17, r=8, p=1 — solid where Argon2 isn't available. bcrypt (legacy, still acceptable): Blowfish-based, slow and salted but NOT memory-hard; minimum cost factor 10, each +1 doubles work — fine for existing systems, but watch its 72-byte truncation. The naive 'fix' of pre-hashing with a fast hash and base64-encoding can backfire: a SHA-256 digest is 32 bytes but its hex/base64 form is 44–64 bytes, and prepending other data can push you back past 72, re-truncating the entropy you tried to preserve.
