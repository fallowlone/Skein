## Snippet 1 — the naive store

```js
import { createHash } from "node:crypto";

function storePassword(user, password) {
  const hash = createHash("sha256").update(password).digest("hex");
  db.users.update(user.id, { passwordHash: hash });
}
```

## Snippet 2 — the Argon2id parameters

```js
import argon2 from "argon2";

async function hashPassword(password) {
  return argon2.hash(password, {
    type: argon2.argon2id,
    memoryCost: 512,   // KiB
    timeCost: 1,
    parallelism: 1,
  });
}
```

## Snippet 3 — the comparison

```js
function verifyResetToken(provided, stored) {
  // both are hex-encoded HMAC digests
  if (provided === stored) {
    return true;
  }
  return false;
}
```

<Quiz
  id="05-password-hashing-code-3"
  lessonSlug="05-password-hashing"
  lang="en"
  question="This compares two secret digests with ===. Why is that a problem and what's the fix?"
  choices={[
    { label: "=== short-circuits on the first differing byte, so it returns faster the fewer leading bytes match — a timing side-channel an attacker can exploit to recover the secret byte by byte. Use a constant-time compare (crypto.timingSafeEqual on equal-length Buffers). KDF verify functions like bcrypt.compare / argon2.verify already do this internally.", correct: true },
    { label: "=== is fine for strings; timing only matters for numbers.", misconception: "String === in V8 short-circuits on the first mismatching character, so its duration depends on how many leading characters matched — exactly the leak. Use a constant-time comparison." },
    { label: "The bug is that it returns a boolean; it should throw on mismatch.", misconception: "Returning a boolean is correct API design. The defect is the timing variability of ===, not the return type." },
    { label: "Just hash both values again before comparing to fix it.", misconception: "Re-hashing doesn't make the final comparison constant-time, and comparing the re-hashes with === has the same leak. Use a timing-safe equality primitive on the bytes." },
  ]}
/>

## Snippet 4 — login without migration

```js
async function login(email, password) {
  const user = await db.users.findByEmail(email);
  if (!user) return null;
  const ok = await argon2.verify(user.passwordHash, password);
  if (!ok) return null;
  return issueSession(user);
}
```

<Recap lang="en">
These are the defects you find in real auth reviews: a fast hash with no salt must become a slow, memory-hard KDF; Argon2id with under-sized memory cost throws away the property that defeats GPUs, so honor OWASP's m=19 MiB/t=2/p=1; secret comparisons must be constant-time (crypto.timingSafeEqual, or the KDF's own verify) rather than ===; and a correct verify still needs rehash-on-login via needsRehash to keep the work factor current without forced resets. Diagnose the algorithm, the parameters, the timing, and the migration — in that order. Now when you open an auth PR, those four questions run automatically — and you catch the breach-day problem before it ships.
</Recap>
