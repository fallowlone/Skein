But it deliberately leaves three gaps. (2) SameSite=None: cookies that must work cross-site (third-party SSO, embedded widgets, cross-origin APIs) are set SameSite=None; Secure, which turns all SameSite protection off.     { q: "Contrast the synchronizer token pattern with the double-submit cookie pattern: how each works, and when you'd pick which.", a: "Synchronizer token: the server generates a per-session (or per-request) cryptographically random token, stores it server-side, and embeds it in every form or expects it in a custom header. The attacker's cross-site page can't read it (same-origin policy) and can't guess it, so a forged request can't carry a valid one. Stateful, strongest, the OWASP default for server-rendered apps. Double-submit cookie: stateless — the server sets a random value in a cookie and expects the same value echoed in a header/field; the attacker can't read your cookie to copy it, so the two won't match. Cheaper (no server storage) but weaker: if an attacker can write a cookie for your domain (subdomain XSS, cookie injection) they can make both values match. Pick the synchronizer for stateful server-rendered apps; pick the HMAC-signed double-submit (token bound to the session) for stateless APIs where you can't keep server-side state." },
    { q: "What do Origin and Referer header checks add, and why are they a defense-in-depth layer rather than a sole defense?", a: "The server checks that the request's Origin header (falling back to Referer) matches its own origin and rejects foreign origins — a cheap broad filter that catches most cross-site forgeries before any token logic runs. It's defense-in-depth, not a sole defense, for two reasons. First, both headers can be absent or stripped: privacy settings, proxies, or a strict referrer-policy can remove Referer, and some requests carry no Origin, so a strict reject breaks legitimate traffic while a lenient fallback weakens the check. Second, it's a negative filter (reject foreign origins) with no positive proof that the user intended the action — that's what the token provides. Use Origin/Referer alongside a token, not instead of one." },

CORS preflight only fires for non-simple requests (custom headers, non-simple content types), and even then it gates response readability, not request execution. The one related-but-real mitigation: requiring a custom header plus a non-simple content type forces a preflight that a forged cross-site fetch can't satisfy — but that's a partial measure, not the token defense, because top-level form posts and simple requests skip preflight entirely." },
