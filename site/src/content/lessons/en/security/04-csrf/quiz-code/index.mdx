## Snippet 1 — the cookie config

```js
// Express session cookie
app.use(session({
  secret: process.env.SECRET,
  cookie: {
    httpOnly: true,
    secure: true,
    sameSite: 'none',   // <-- needed so the embedded widget on partner.com works
  },
}));
```

## Snippet 2 — the double-submit check

```js
function verifyCsrf(req, res, next) {
  const cookieToken = req.cookies['csrf'];
  const headerToken = req.get('X-CSRF-Token');
  if (cookieToken && cookieToken === headerToken) return next();
  return res.status(403).send('CSRF check failed');
}
```

<Quiz
  id="04-csrf-code-2"
  lessonSlug="04-csrf"
  lang="en"
  question={"This plain double-submit check passes when the cookie value equals the header value. What's the weakness a senior reviewer flags, and the fix?"}
  choices={[
    { label: "It trusts that only your origin can set the csrf cookie. If an attacker can write a cookie for your domain — a subdomain XSS, or cookie injection over an insecure sibling — they set csrf=X and send X in the header; the two match and the check passes. Fix: the HMAC-signed variant that binds the token to the session, so a planted value won't verify.", correct: true },
    { label: "It should use === on trimmed strings; whitespace is the bug.", misconception: "String comparison is not the defect. The structural weakness is that the pattern assumes the attacker can't write your cookie — break that assumption (subdomain XSS, injection) and matching values are trivial to forge." },
    { label: "The check is fine; double-submit is unconditionally secure because the header can't be forged cross-site.", misconception: "The header can't be READ or set cross-site by script, true — but the attacker doesn't need to read it; they need to control both halves, which a cookie-write primitive grants. Plain double-submit is weaker than it looks." },
    { label: "It must store the token server-side, so any stateless approach is unsafe.", misconception: "Stateless can be secure: the HMAC-signed double-submit binds the token to the session secret so a planted cookie value won't validate, with no server storage. The fix is binding, not abandoning statelessness." },
  ]}
/>

## Snippet 3 — the route handler

```js
// "Unsubscribe with one click from the email link"
app.get('/account/email-prefs/unsubscribe', requireSession, (req, res) => {
  db.users.update(req.session.userId, { subscribed: false });  // mutates!
  res.send('You are unsubscribed.');
});
```

<Quiz
  id="04-csrf-code-3"
  lessonSlug="04-csrf"
  lang="en"
  question={"Sessions here are SameSite=Lax and there's a CSRF token on all POST routes. Is this GET handler safe? Why or why not?"}
  choices={[
    { label: "No — it mutates state on a GET. SameSite=Lax sends the session cookie on top-level GET navigations, and GET routes are exactly what teams exempt from token checks. An attacker just needs the victim to load a link or an image tag pointing here. Fix: move the mutation to POST/PUT and require the CSRF token.", correct: true },
    { label: "Safe — requireSession means only logged-in users reach it.", misconception: "requireSession is satisfied by the victim's own auto-attached Lax cookie on a forged top-level GET. Authentication is present; intent is not. The mutating GET is the hole." },
    { label: "Safe — Lax blocks all cross-site requests, including this GET.", misconception: "Lax deliberately sends the cookie on top-level GET navigations. That's precisely the case this handler is exposed to; Lax does not block it." },
    { label: "Safe — it's idempotent, so re-running it changes nothing.", misconception: "Idempotency is irrelevant to CSRF: one forged request already flips subscribed to false against the user's will. The defect is mutating on GET, where the token check doesn't run." },
  ]}
/>

## Snippet 4 — the Origin check

```js
function checkOrigin(req, res, next) {
  const origin = req.get('Origin');
  if (origin === 'https://app.example.com') return next();
  return res.status(403).send('Bad origin');
}
```

  lessonSlug="04-csrf"
  lang="en"
  question={"Used as the ONLY CSRF defense on state-changing routes, what breaks, and how should this layer be used?"}
  choices={[
    { label: "Some legitimate requests carry no Origin header (certain same-origin navigations, older clients), so a strict equality reject blocks real users; and as a negative filter it adds no positive proof of user intent.     { label: "Nothing breaks — Origin is always present and unforgeable, so this is a complete defense.", misconception: "Origin is browser-set and not script-forgeable, true, but it isn't always present, and a sole negative filter proves no intent. It belongs alongside a token, with a Referer fallback, not on its own." },
    { label: "It's too weak because the attacker can set the Origin header to your domain.", misconception: "Origin is set by the browser and can't be spoofed by page script in a normal cross-site request — that's its strength. The real issues are absence/strictness and lack of positive proof, so it's a layer, not the whole defense." },
    { label: "It should check Referer first because Referer is more reliable than Origin.", misconception: "Origin is the more reliable signal (sent on cross-site state-changing requests and minimal); Referer is the fallback and is more often stripped by privacy settings or referrer-policy. The order is Origin first, Referer as fallback." },
  ]}

<Recap lang="en">
Every CSRF review is read in cookie attributes and handlers: SameSite=None opts you back into the full pre-2020 surface and mandates a token defense; plain double-submit trusts that only you can write your cookie, so the HMAC-signed variant is the fix; a mutation on a GET is forgeable through a top-level Lax navigation and must move to POST behind a token; and an Origin check is a cheap defense-in-depth filter — falling back to Referer — never the sole lock. Spot the structural defect, fix it at the highest-leverage layer, then confirm the forged request can no longer land.
</Recap>
