HS256 is symmetric: one secret both signs and verifies. The attack hits a server that decides its verification path from the token's own alg header. The attacker takes the published public key, forges a token with alg set to HS256, and signs it with HMAC-SHA256 using the public-key string as the HMAC secret. The server reads HS256, branches into its HMAC code, and verifies with the same public key as the secret — reproducing exactly what the attacker computed, so the signatures match and the forged admin token is accepted. RFC 8725 gives two defenses: pin the expected algorithm with an explicit allowlist passed to verify, so the header can never select HS256; and bind each key to exactly one algorithm, so an RS256 public key can never be handed to an HMAC verifier. Either alone breaks the attack; do both." },

You must still check exp (and nbf, the not-before time) to enforce the lifetime window with a little clock-skew leeway; iss to confirm the token came from the issuer you trust; and aud to confirm it was minted for THIS service and not a sibling that shares the same signing key. So verification is two steps — check the signature, then validate the registered claims against what your application expects." },

All of these are header fields the attacker controls. If the server resolves kid by trusting the header — fetching a key from a header-named URL, or treating kid as a path or SQL lookup — the attacker hosts their own key, points the header at it, signs the token with the matching private key, and the server verifies a fully self-signed token. The fix is to never source verification material from header-controlled locations: resolve kid only against a server-side pinned allowlist of trusted keys, ignore jku/x5u unless the host is allowlisted, and sanitize kid so it cannot be used for path traversal or injection. Treat the header as a hint to pick among keys you already trust, never as the source of the key itself." },

So there is nothing to delete on logout, and a token an attacker has already copied stays valid until it expires; clearing a client cookie does nothing to it. You contain this with time and rotation. Access tokens get a short TTL, typically 5 to 15 minutes, so a leaked one dies almost immediately. The long-lived refresh token is the real secret, so it rotates: each use issues a new refresh token and invalidates the old one. If an old, already-rotated refresh token is presented again, the server detects reuse and revokes the whole token family, locking out both attacker and user until re-authentication. This reintroduces a little server-side state for the rare refresh and revoke events, while the common case — verifying a signature on every request — stays stateless and cheap." },
