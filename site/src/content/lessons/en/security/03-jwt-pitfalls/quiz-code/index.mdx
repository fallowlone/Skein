## Snippet 1 — the forged alg:none token

```
header:  { "alg": "none", "typ": "JWT" }
payload: { "sub": "victim", "role": "admin" }
signature: (empty)

// server code
const claims = jwt.decode(token);   // decode only, no verify
if (claims.role === "admin") grantAdmin();
```

## Snippet 2 — verifying with the public key

```js
const publicKey = fs.readFileSync("rsa-public.pem");
function verifyToken(token) {
  // no algorithms option passed
  return jwt.verify(token, publicKey);
}
```

    { label: "Only if the public key is shorter than 256 bits.", misconception: "Key length is irrelevant to confusion; the public key is used verbatim as the HMAC secret. The bug is letting the header choose HS256 at all." },
    { label: "Because fs.readFileSync corrupts the PEM into a symmetric key.", misconception: "The file is read correctly. The attack reproduces the server's exact HMAC computation by using the same public-key string as the secret — no corruption involved." },
  ]}

## Snippet 3 — signature checked, claims not

```js
const claims = jwt.verify(token, key, { algorithms: ["RS256"] });
// signature OK — now trust everything
req.user = claims.sub;
req.roles = claims.roles;
// no exp / iss / aud checks beyond the library default
```

    { label: "Nothing — a verified RS256 signature is sufficient on its own.", misconception: "A valid signature only proves authentic issuance. Without aud, any service sharing the key accepts tokens minted for any other service in the mesh." },
    { label: "The bug is reading claims.sub before claims.roles.", misconception: "Field-read order is irrelevant. The defect is accepting a token whose audience is a different service entirely, because aud is never validated." },
    { label: "It needs HS256 instead of RS256 for microservices.", misconception: "Algorithm choice is unrelated to the missing audience check. Switching to HS256 would actually widen confusion risk, not fix the audience scoping." },

## Snippet 4 — resolving the key from the header

```js
function getKey(header) {
  // header.kid is attacker-controlled
  return fetch(header.jku)
    .then(r => r.json())
    .then(jwks => jwks.keys.find(k => k.kid === header.kid));
}
const claims = jwt.verify(token, await getKey(jwt.decodeHeader(token)));
```

    { label: "It is fine as long as kid matches a key in the fetched set.", misconception: "The attacker's own JWKS contains a matching kid by construction. Matching against an attacker-hosted set proves nothing; the key set must come from a trusted server-side source." },

<Recap lang="en">
Every JWT defect is read in the verify call and the checks around it: decode-only code trusts unsigned claims; a missing algorithms allowlist lets the header pick HS256 and turns a public key into an HMAC secret; a verified signature with no aud/iss check is a confused-deputy waiting to happen in a shared-key mesh; and resolving kid/jku from attacker-controlled headers hands key selection to the attacker. The fix is always the same shape — pin the algorithm, bind and allowlist the key, then validate the registered claims against what this service expects. Now when you open a code review on any auth path, you know exactly where to look first: the verify call, the algorithm option, the claim checks — in that order.
</Recap>
