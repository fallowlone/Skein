    { label: "The server's published RSA public key string, used as the HMAC secret. The server reads HS256, branches to HMAC, and verifies with that same public key — reproducing the attacker's computation, so the signatures match.", correct: true },
    { label: "The server's RSA private key, recovered by factoring the public key.", misconception: "No private-key recovery happens; RSA is not broken. The attack abuses the public key as a symmetric secret — the public key is already published in the JWKS endpoint." },

  lang="en"
  question="A service correctly pins alg:RS256 and verifies the signature, but a token minted for a different microservice in the same trust domain is accepted as its own. Which claim check is missing?"
  choices={[
    { label: "The aud (audience) check — and usually iss too. A valid signature only proves the token came from the trusted issuer; aud proves it was minted for THIS service, not a sibling that shares the signing key.", correct: true },
    { label: "The exp check — the token must have already expired.", misconception: "exp governs lifetime, not intended recipient. A perfectly fresh token for another audience is still wrong for this service; only aud/iss scope it to the right consumer." },
    { label: "Nothing is missing — a valid signature is sufficient.", misconception: "Signature validity only proves authenticity of issuance. Without aud, any service sharing the key accepts tokens minted for any other service — a confused-deputy across the trust domain." },
    { label: "The kid check — the wrong key id was used.", misconception: "kid selects which key verifies the signature; here the signature already verified. The defect is accepting a token whose audience is a different service entirely." },
  ]}

  question="A SPA must survive page refreshes. Which storage split does a security-minded senior ship, and why?"

    { label: "Both tokens in localStorage for easy access.", misconception: "localStorage is readable by any script on the page, so one XSS bug exfiltrates both tokens — including the long-lived refresh token, the worst thing to lose. There is no httpOnly equivalent for localStorage." },

    { label: "One long-lived (24h) access token in memory, no refresh token.", misconception: "In-memory is fine, but a 24h access token has no fast revocation and you have removed the refresh-rotation that detects reuse. Short TTL plus rotation is the entire point." },

<Recap lang="en">
The through-line across the unit is one rule: never trust the token to describe its own verification. alg:none and RS256-to-HS256 confusion both die when you pin an explicit algorithm allowlist and bind each key to one algorithm; attacker-controlled kid/jku die when you resolve keys only against a pinned allowlist. A valid signature is necessary but not sufficient — check aud and iss so a token is scoped to THIS service. And because a stateless token cannot be un-issued, short access TTLs, refresh-token rotation with reuse detection, and XSS-aware storage bound whatever leaks.
</Recap>
