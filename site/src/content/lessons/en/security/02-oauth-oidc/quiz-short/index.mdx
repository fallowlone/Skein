Before the redirect the client generates a random code_verifier (43–128 chars) and sends only its SHA-256 hash, the code_challenge, to /authorize. The authorization server stores the challenge alongside the one-time code. At /token the client sends the code plus the original code_verifier; the server hashes the verifier and compares it to the stored challenge — match issues tokens, mismatch rejects. With prefix or wildcard matching, an attacker triggers a flow whose redirect_uri points at an open-redirect or unexpected path under the legitimate domain; the authorization code lands on a server the attacker controls and they exchange it for tokens. Exact match means the authorization server only ever redirects to a URI the developer explicitly registered. Native apps that cannot register a fixed URL use loopback (http://127.0.0.1 on a random port) or an OS-registered private-use scheme instead." },

    { q: "Explain JWKS cache staleness during key rotation and the on-cache-miss refresh pattern.", a: "The client caches the IdP's JWKS (signing public keys) so it need not fetch on every request, with a 5–15 minute TTL. When the IdP rotates signing keys it publishes the new key, but the cached list still holds only the old one. New tokens are signed with the new key; the validator reads kid, looks in the cache, finds nothing, and fails signature validation — a 401 storm on completely valid tokens until the TTL expires. The fix: on a kid miss, immediately fetch fresh JWKS and retry the lookup, only failing if the kid is still absent. Short TTL plus on-miss refresh is the standard mitigation; mature IdPs also pre-publish keys 24–48 hours before activation." },
    { q: "How does refresh-token rotation turn a stolen refresh token from unlimited harm into a detection window?", a: "Under rotation every refresh issues a new refresh token and marks the old one used, with the server tracking which token superseded which. If an attacker steals RT1 and uses it, they get RT2 and RT1 is marked used; when the legitimate client later presents RT1, the server sees an already-used token — a replay — and revokes the entire chain (RT1, RT2, all descendants), forcing re-authentication. Both parties lose access. The harm window shrinks from the absolute expiry (days to months without rotation) to the rotation interval — minutes to hours until the next legitimate refresh trips the alarm. refresh_replay_detected_total greater than zero is a direct compromise signal." },

The token carries cnf.jkt, the thumbprint of the client's public key. On every API call the client sends a DPoP proof JWT signed by the private key, containing htm (method), htu (target URI), iat, jti (replay-cached), and ath (SHA-256 of the access token). The resource server verifies the proof signature, checks ath against the presented token, confirms htm/htu match, rejects stale iat or replayed jti, and verifies the proof's jwk hashes to cnf.jkt. A stolen token without the non-extractable private key cannot produce a valid proof. Choose DPoP for browser SPAs and mobile (WebCrypto / OS keychain hold the key, since browsers do not expose TLS client certs to JS); choose mTLS for backend service-to-service where X.509 client certificates are manageable.
