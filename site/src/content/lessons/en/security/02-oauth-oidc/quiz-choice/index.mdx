  lang="en"
  question="A team registers redirect_uri as a prefix match (https://app.example/callback*) to support dynamic return paths. Why is this a vulnerability?"
  choices={[
    { label: "OAuth 2.1 requires exact-match redirect URIs. A prefix or wildcard lets an attacker chain the flow into any open-redirect or unexpected path under the domain and exfiltrate the authorization code to a server they control.", correct: true },
    { label: "Prefix matching is fine as long as the host is correct — only the host is security-relevant.", misconception: "The host is not enough. An open redirect on a permitted path under that host forwards the code off-domain; only character-for-character exact match closes this." },
    { label: "Wildcards break PKCE because the challenge is bound to the path.", misconception: "PKCE binds the code to the verifier, not to the path. The redirect-URI rule is an independent mandatory check that prefix matching defeats." },
    { label: "It only matters for native apps using custom URI schemes.", misconception: "Exact match is required for all clients. Native apps additionally use loopback or registered private-use schemes, but web apps must exact-match too." },
  ]}

<Recap lang="en">
The through-line across the unit is one complete-set rule: PKCE binds the code to the client, exact redirect matching keeps the code on-domain, the eight id_token checks (with a server-pinned algorithm) authenticate the user, refresh rotation turns theft into a detection alarm, sender-constrained tokens (DPoP/mTLS) defeat bearer theft, and audience validation against a hard-coded identifier blocks cross-API confusion. Every real OAuth breach — Facebook, Slack, GitHub Enterprise, Azure AD — traces back to exactly one of these checks being skipped or inverted.
</Recap>
