<Crux>Security is assuming your system will be attacked and designing it so attacks fail, or stay contained when they get in.</Crux>

<Explanation>

## Why security is not a feature you add later

A normal feature answers "what should happen when someone uses this correctly?" Security answers a different question: "what happens when someone uses this *wrong* — on purpose?" That second question changes every choice. You stop trusting input. You assume any door can be pushed. You plan for the moment something gets through.

This is why you cannot bolt security on at the end. By then, every part of the system already trusts every other part, and one crack lets an attacker walk the whole house. Security is a way of thinking that runs through every line, from the first day.

## Assume breach, then limit the damage

Real security has two layers, and beginners usually only see the first one.

- **Keep attacks out.** Validate input, require strong passwords, check who is allowed to do what. This is the wall.
- **Assume the wall fails anyway.** Give each part of the system the least power it needs. Store passwords so a leaked database is still useless. Log what happened so you can see the break-in. This shrinks the **blast radius** — how much one mistake can wreck.

## What this track covers

The rest of the climb is the attacker's playbook turned into defenses. You will learn the most common ways real systems get broken (the OWASP Top Ten), how login and identity work (OAuth, tokens), why password storage is its own science, how attackers trick a logged-in browser (CSRF), and how to keep secrets out of code. Each topic is one move in the same game: make the attack fail, or make it cheap to survive.
