## Snippet 1 — the manifest

```jsonc
// package.json — and the CI step that installs it
{
  "dependencies": {
    "left-pad": "^1.3.0",
    "@acme/billing": "^2.0.0"
  }
}
// CI:  run: npm install
```

## Snippet 2 — manifest vs lockfile

```text
# package.json says:
"@acme/ui": "^3.1.0"

# package-lock.json (committed) pinned:
"@acme/ui": { "version": "3.1.0",
              "resolved": "https://registry.npmjs.org/@acme/ui/-/ui-3.1.0.tgz",
              "integrity": "sha512-Abc123..." }

# A new 3.4.0 was published yesterday. CI runs `npm ci`.
```

<Quiz
  id="07-supply-chain-code-2"
  lessonSlug="07-supply-chain"
  lang="en"
  question="With `npm ci` and this committed lockfile, which version installs, and what is the integrity field doing?"
  choices={[
    { label: "Exactly 3.1.0 — `npm ci` ignores the caret and installs the locked version, then verifies the fetched tarball against the recorded sha512; any byte mismatch fails the install loudly. The new 3.4.0 is never pulled until the lockfile is updated deliberately.", correct: true },
    { label: "3.4.0 — the caret in package.json always wins.", misconception: "`npm ci` does not consult the caret range; it installs the lockfile verbatim. The caret only matters when you deliberately run an update that regenerates the lock." },
    { label: "3.1.0, but the integrity field is cosmetic and not checked.", misconception: "The integrity field is enforced: npm hashes the downloaded tarball and compares to the recorded sha512, failing on any mismatch. That is the byte-tamper guarantee." },
    { label: "Whichever the registry serves — the lockfile is advisory.", misconception: "Under `npm ci` the lockfile is authoritative, not advisory: version and integrity hash are both enforced, and a mismatch errors out." },
  ]}
/>

## Snippet 3 — verifying provenance

```bash
# Release pipeline signs the image; deploy gate verifies before rollout:
cosign verify \
  --certificate-identity-regexp "https://github.com/acme/.*" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  ghcr.io/acme/api@sha256:9f2b...   # pinned by digest, not :latest
```

<Quiz
  id="07-supply-chain-code-3"
  lessonSlug="07-supply-chain"
  lang="en"
  question="What does this cosign verify gate actually guarantee, and why is the @sha256 digest (not :latest) important?"
  choices={[
    { label: "It proves the image was signed by a build from the acme GitHub org via the expected OIDC issuer (keyless Sigstore), so an unsigned or foreign-built image is rejected at deploy. The digest pins the exact bytes verified, so a mutated :latest tag cannot swap in a different image after verification.", correct: true },
    { label: "It scans the image for known CVEs before rollout.", misconception: "cosign verifies signatures and provenance identity, not vulnerabilities. CVE scanning is a separate step against the SBOM; verify answers authenticity, not patch state." },
    { label: "It guarantees the image has no malicious code.", misconception: "A signature proves who built it and that it is untampered since signing — not that the source was benign. A compromised but legitimately-signed build still verifies; signing reduces impostor risk, not insider risk." },
    { label: "The digest is optional; verifying :latest is equivalent.", misconception: "A tag is mutable: :latest can be repointed to a different image after you verify. Pinning by digest binds the verification to the exact immutable bytes you deploy." },
  ]}
/>

## Snippet 4 — the CI workflow

```yaml
on:
  pull_request_target:          # runs in the BASE repo context
jobs:
  build:
    permissions:
      contents: write
      packages: write
    steps:
      - uses: actions/checkout@v4
        with: { ref: ${{ github.event.pull_request.head.sha }} }  # checks out PR code
      - run: npm install && npm run build   # runs untrusted code with write tokens + secrets
```

<Quiz
  id="07-supply-chain-code-4"
  lessonSlug="07-supply-chain"
  lang="en"
  question="Why is this workflow dangerous, and what is the first fix?"
  choices={[
    { label: "`pull_request_target` runs with the base repo's secrets and a write-scoped token, but it checks out and executes untrusted PR code — so any PR (or a malicious dep it pulls) can exfiltrate the token and push poisoned packages. Fix: use `pull_request` (no secrets) for untrusted code, drop the token to read-only, and never run PR build steps with publish permissions.", correct: true },
    { label: "It is fine — pull_request_target is the recommended trigger for PRs.", misconception: "pull_request_target intentionally runs in the trusted base context with secrets; combining it with a checkout of PR head code and write permissions is the classic exploit pattern, not a recommendation." },
    { label: "The only issue is the unpinned actions/checkout tag.", misconception: "Pinning actions by SHA is good hygiene, but the dominant risk here is executing untrusted PR code with write-scoped secrets — a far larger blast radius than a tag." },
    { label: "Add an audit step and the workflow is safe.", misconception: "Audit catches known advisories; it does nothing about untrusted code running with a write token and secrets. The fix is least-privilege scoping and not granting secrets to untrusted-code runs." },
  ]}
/>

<Recap lang="en">
Every supply-chain review is read in manifests and pipeline YAML: caret ranges plus `npm install` let new or tampered bytes in, while a committed lockfile plus `npm ci` enforces exact versions and integrity hashes; cosign verify against an expected build identity, with the image pinned by digest, rejects impostor artifacts at the deploy gate; and a CI workflow that runs untrusted PR code with write-scoped secrets is the highest-blast-radius bug of all. Read the config, find where untrusted bytes or untrusted code meet your credentials, and fix that boundary before adding more scanning.
</Recap>
