## Snippet 1 — the ownership check

```js
// GET /api/invoices/:id
app.get("/api/invoices/:id", requireLogin, async (req, res) => {
  const invoice = await db.invoice.findUnique({
    where: { id: Number(req.params.id) },
  });
  if (!invoice) return res.status(404).end();
  res.json(invoice);   // returns whatever row matched the id
});
```

<Quiz
  id="01-owasp-modern-code-1"
  lessonSlug="01-owasp-modern"
  lang="en"
  question="requireLogin runs, so the caller is authenticated. What is the vulnerability, and what is the minimal correct fix?"
  choices={[
    { label: "Broken Access Control (IDOR). Authentication is not authorization — the handler never checks the invoice belongs to req.user. Scope the lookup: findFirst({ where: { id, ownerId: req.user.id } }) and 404 on miss, computed server-side.", correct: true },
    { label: "It's safe — requireLogin already gates the route.", misconception: "requireLogin proves who the caller is, not what they may access. Any logged-in user can read any invoice by changing the id; that is textbook IDOR." },
    { label: "Injection — Number(req.params.id) could be tampered with.", misconception: "The id is coerced to a number and passed through the ORM as a parameter, so there is no injection. The missing piece is an ownership check on the row." },
    { label: "Cryptographic Failures — the response should be encrypted.", misconception: "Transport is already encrypted by TLS; encrypting the body changes nothing about an authorized session reading a row it does not own. The fix is authorization." },
  ]}
/>

## Snippet 2 — the URL fetcher

```js
// POST /api/preview  { "url": "..." }
app.post("/api/preview", async (req, res) => {
  const r = await fetch(req.body.url);     // fetch whatever the client sent
  const html = await r.text();
  res.send(extractOpenGraph(html));        // server returns the fetched content
});
```

<Quiz
  id="01-owasp-modern-code-2"
  lessonSlug="01-owasp-modern"
  lang="en"
  question="What class of bug is this, what is the highest-impact exploit, and what is the right defense?"
  choices={[
    { label: "SSRF (A10). An attacker sends url=http://169.254.169.254/latest/meta-data/ to read cloud IMDS credentials, or hits internal services. Defense: allowlist scheme/host, resolve the IP and reject private/loopback/link-local ranges (re-checking after redirects), and lock down IMDS (IMDSv2).", correct: true },
    { label: "Injection — sanitize the URL string before fetching.", misconception: "String sanitization does not stop a perfectly valid URL pointing at an internal address. SSRF is about where the server is allowed to connect, defended by allowlisting and IP-range checks, not escaping." },
    { label: "It's fine — fetch only retrieves public web pages.", misconception: "fetch will happily request internal hosts, link-local metadata endpoints, and other schemes. That reachability is exactly what SSRF abuses." },
    { label: "Broken Access Control — require login on the endpoint.", misconception: "Requiring login limits who can trigger it but the authenticated server still makes the dangerous internal request. The root cause is unrestricted server-side fetch destination — SSRF." },
  ]}
/>

## Snippet 3 — the CORS config

```js
app.use(cors({
  origin: req.headers.origin,   // reflect whatever Origin the request sent
  credentials: true,            // allow cookies to be sent cross-origin
}));
```

<Quiz
  id="01-owasp-modern-code-3"
  lessonSlug="01-owasp-modern"
  lang="en"
  question="Reflecting the request Origin while allowing credentials — what does this actually permit, and how do you fix it?"
  choices={[
    { label: "Security Misconfiguration. Reflecting any Origin with credentials:true effectively allows every site to make authenticated cross-origin requests and read the responses with the victim's cookies. Fix: allowlist a fixed set of trusted origins and reflect only those (or none for public APIs).", correct: true },
    { label: "It's correct — reflecting the Origin is how CORS is supposed to work.", misconception: "Reflecting the caller's Origin with credentials is the canonical CORS misconfiguration; it is equivalent to a wildcard that also leaks cookies. CORS expects an explicit allowlist of trusted origins." },
    { label: "Cryptographic Failures — set Secure on the cookie instead.", misconception: "Secure controls HTTPS-only transmission, not which origins may read cross-origin responses. The defect is the reflected-origin-plus-credentials CORS policy." },
    { label: "Broken Access Control — add server-side auth checks.", misconception: "Server-side authz still runs, but the browser will hand the response to a malicious origin because CORS told it the origin is trusted. The fix is a correct CORS allowlist." },
  ]}
/>

## Snippet 4 — the log line

```
2026-05-29T11:42:08Z WARN auth login failed user=alice@corp.com
  pw=hunter2 ip=203.0.113.9 ua="Mozilla/5.0" attempt=5 within=30s
```

<Quiz
  id="01-owasp-modern-code-4"
  lessonSlug="01-owasp-modern"
  lang="en"
  question="Two findings are visible in this single log line. Which pair is correct?"
  choices={[
    { label: "Cryptographic/sensitive-data failure (the plaintext password pw=hunter2 must never be logged) plus a brute-force signal (attempt=5 within=30s) that A07 Identification & Authentication Failures and A09 logging would have you rate-limit and alert on, not just record.", correct: true },
    { label: "Only a formatting problem — the log is just verbose.", misconception: "Logging the cleartext password is a real sensitive-data leak into log stores and SIEM, and the rapid repeated failures are an unmitigated credential-stuffing signal. Both are security findings, not style." },
    { label: "SSRF — the ip field shows an external request.", misconception: "An ip field in an auth log is normal request metadata, not a server-side fetch. SSRF is not in play here." },
    { label: "Injection — the user-agent string could contain a payload.", misconception: "The UA is being logged, not executed against an interpreter. The actual issues are the logged plaintext password and the un-throttled repeated auth failures." },
  ]}
/>

<Recap lang="en">
Every finding reads back to a category and a root-cause fix: an authenticated handler with no ownership check is IDOR/Broken Access Control (scope to owner_id); a server fetching a client-supplied URL is SSRF (allowlist plus private-range rejection plus IMDS lockdown); reflecting the request Origin with credentials is a CORS Security Misconfiguration (allowlist trusted origins); and a log line carrying a plaintext password with rapid repeated failures is a sensitive-data leak plus an auth/logging gap. Read code and config like a reviewer — name the cause, then fix the cause.
</Recap>
