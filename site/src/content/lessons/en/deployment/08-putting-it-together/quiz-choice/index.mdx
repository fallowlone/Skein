<Quiz
  id="08-putting-it-together-choice-1"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="A team pushes every build as registry.example.com/api:latest and the Deployment pins image: api:latest. Rollouts mostly work, but twice now a node that recreated a pod served a months-old build. What single change fixes the class of bug, and why?"
  choices={[
    { label: "Pin the Deployment to the immutable digest (api@sha256:...) produced at build time. A mutable tag is a moving pointer, so a re-pulled or rescheduled pod can resolve :latest to whatever the registry holds now — pinning the digest makes the artifact identical to the one you tested.", correct: true },
    { label: "Set imagePullPolicy: Always so every pod re-pulls the image.", misconception: "Always makes the staleness worse, not better — it guarantees a rescheduled pod fetches whatever :latest points to right now, which may be a newer or older build than the rest of the ReplicaSet. The fix is an immutable reference, not a more aggressive pull." },
    { label: "Add a readinessProbe so stale pods are kept out of the Service.", misconception: "A probe checks whether a pod is serving, not whether it is running the right code — a months-old build can pass /healthz/ready perfectly. The seam here is the registry tag's mutability, not the readiness contract." },
    { label: "Increase the image layer cache on the nodes.", misconception: "Layer caching speeds up pulls; it has nothing to do with which build a tag resolves to. The bug is identity (which artifact), not performance (how fast it arrives)." },
  ]}
/>

<Quiz
  id="08-putting-it-together-choice-2"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="A rolling update is configured as below and a new release is rolled out. The manifest applies cleanly and the rollout reports success in 40s, but clients see a burst of 502s for ~2 minutes. Where is the seam?\n\n```yaml\nstrategy:\n  rollingUpdate:\n    maxUnavailable: 0\n    maxSurge: 1\ntemplate:\n  spec:\n    containers:\n    - name: api\n      image: api@sha256:abc\n      # no readinessProbe\n```"
  choices={[
    { label: "With no readinessProbe, k8s marks each pod ready the instant its process starts — before the DB pool opens — and the rolling update adds it to the Service, so traffic hits a running-but-not-serving pod. The surge math is correct; the readiness contract is missing.", correct: true },
    { label: "maxUnavailable: 0 caused the rollout to stall and time out.", misconception: "maxUnavailable: 0 keeps capacity at or above desired during the roll — it is the safe setting. It does not route traffic to unready pods; the absence of a probe does." },
    { label: "The digest pin api@sha256:abc forced a slow re-pull that produced the 502s.", misconception: "A slow pull delays a pod from starting at all; it does not produce a reported success followed by transient 502s from pods k8s already added to the Service. The missing readiness gate does that." },
    { label: "maxSurge: 1 is too low, so there were not enough pods to serve traffic.", misconception: "maxSurge: 1 adds a new pod before retiring an old one, so capacity never dips. Throughput was not the problem — traffic reached pods that were alive but not yet serving." },
  ]}
/>

<Quiz
  id="08-putting-it-together-choice-3"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="You ship a column rename as one migration bundled into the same blue-green release that flips the LB to green. Green serves fine, then throws an unrelated error and you flip back to blue — and blue now 500s on every request. Why did two reversible-looking stages produce a non-recoverable state?"
  choices={[
    { label: "The LB flip is reversible but the schema change is not. Bundling a destructive rename with the flip breaks N-1 compatibility, so the moment you roll back, blue queries a column that no longer exists. Expand-contract across separate deploys keeps every intermediate schema compatible with both versions.", correct: true },
    { label: "Blue-green requires green to use a separate database, which was misconfigured.", misconception: "Sharing one database across blue and green is normal and expected. The failure is the shared schema being incompatible with the version you rolled back to — not a connection-routing mistake." },
    { label: "The rollback failed because blue-green cannot roll back once traffic has shifted.", misconception: "Reversibility is exactly what blue-green promises — flip the LB back instantly. The promise held; what broke it was composing the reversible flip with an irreversible DROP COLUMN." },
    { label: "Canary would have caught this where blue-green did not.", misconception: "A canary watches metrics on the new version, but the destructive migration still breaks the old code on rollback regardless of rollout style. The real fix is expand-contract, not a different traffic-shift strategy." },
  ]}
/>

<Quiz
  id="08-putting-it-together-choice-4"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="During every deploy, a small fraction of in-flight requests are severed mid-response right as old pods terminate, even though readiness and rollout are correct. The service sits behind an L4 load balancer. What is the highest-leverage fix?"
  choices={[
    { label: "Move to L7 load balancing with connection draining and have the app handle SIGTERM: stop accepting new work, finish in-flight requests, then exit within terminationGracePeriodSeconds, with a preStop sleep to cover the endpoint-removal race. L4 routes by IP/port and cannot drain at the request layer.", correct: true },
    { label: "Raise maxSurge so more new pods absorb the traffic during termination.", misconception: "Surge controls how fast new capacity appears; it does nothing for requests already in flight on a pod that is shutting down. Draining and SIGTERM handling are what protect in-flight work." },
    { label: "Add a longer initialDelaySeconds to the readinessProbe.", misconception: "That delays when new pods receive traffic on startup; the problem here is the shutdown side — requests killed when old pods go away — which draining, not startup delay, addresses." },
    { label: "Switch from rolling update to Recreate so there is no overlap.", misconception: "Recreate kills all old pods before starting new ones, causing full downtime — it makes availability worse and still severs whatever was in flight when the old pods died." },
  ]}
/>

<Quiz
  id="08-putting-it-together-choice-5"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="A reviewer flags that the production database password is set in the Dockerfile so the image is self-contained. The team argues the registry is private, so it is fine. What is the correct objection?"
  choices={[
    { label: "A secret baked into an image layer is readable by anyone who can pull the image, persists in layer history even after a later RUN unsets it, and cannot be rotated without rebuilding and redeploying. Secrets must be injected at deploy/runtime — and a k8s Secret is only base64-encoded, so enable encryption-at-rest or an external secrets manager too.", correct: true },
    { label: "It is fine because a private registry restricts who can pull the image.", misconception: "Registry access control is one layer, but the secret is now permanently embedded in image history and in every node and cache that ever pulled it — un-rotatable and over-exposed. Build-time and runtime are different trust boundaries." },
    { label: "The real problem is that Dockerfiles cannot store environment variables.", misconception: "They can (ENV/ARG), and that is precisely the trap — a build-time ARG or ENV secret is baked into the image. The objection is about the trust boundary, not a capability gap." },
    { label: "Just base64-encode the password before putting it in the Dockerfile.", misconception: "base64 is encoding, not encryption — it is trivially reversible and adds zero protection. It is also still baked into the image, so it inherits every problem above." },
  ]}
/>

<Quiz

  lang="en"
  question="An incident postmortem finds the failing service had a hand-edited replica count and an env var that no IaC config declares — someone kubectl-edited it during a previous fire. The next terraform apply will revert both. What does this reveal, and what is the durable fix?"
  choices={[
    { label: "This is configuration drift: actual state diverged from the IaC-declared desired state, so the environment you tested in code is not the one running. The durable fix is to make IaC the single source of truth — detect drift in CI (plan on a schedule, alert on diffs) and forbid out-of-band kubectl edits so the state file and reality stay reconciled.", correct: true },
    { label: "The fix is to stop running terraform apply so manual edits survive.", misconception: "That abandons reproducibility entirely — the whole point of IaC is that the declared state is authoritative and recreatable. Letting manual edits win turns the cluster into an unrepeatable snowflake." },
    { label: "Drift is harmless as long as the service is currently up.", misconception: "Drift means your tested config and your live config differ silently — the next apply, node replacement, or scale event snaps reality back to the declared state and undoes the undocumented fix, often mid-incident." },
    { label: "Import the manual edits into the state file with terraform import and leave them as manual ops going forward.", misconception: "Importing the values into version-controlled IaC is right; continuing to make manual edits is the original sin. The fix is closing the out-of-band path, not legitimizing it." },
  ]}

<Recap lang="en">
The through-line across the track is one composed object: an immutable digest fixes which artifact runs, the readiness probe makes "ready" mean "serving," expand-contract keeps the rollout strategy and the migration N-1 compatible, an L7 drain plus SIGTERM handling protect in-flight requests across the cutover, runtime secret injection keeps credentials rotatable and out of image history, and IaC as the single source of truth kills drift. Every wrong answer here was a real outage shipped by a team whose individual stages were each fine — the failure lived in the seam. Now when you review a release plan, scan the column of seams first: which contract between stages is written down, tested, or enforced — and which is assumed.
</Recap>
