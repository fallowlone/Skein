  lang="en"
  question="A node reboots and takes 3 of a Deployment's 5 pods with it. No human runs any command. What restores the count, and what is the underlying mechanism?"
  choices={[
    { label: "The ReplicaSet controller observes actual=2 vs desired=5 and creates 3 new pods — a reconciliation loop continuously closing the gap between declared and observed state.", correct: true },
    { label: "The Deployment is recreated from scratch, including a fresh ReplicaSet.", misconception: "Reconciliation is incremental: the controller creates only the 3 missing pods to reach desired count. It does not tear down and rebuild the Deployment or its ReplicaSet." },
    { label: "Nothing happens until someone re-runs kubectl apply.", misconception: "That is imperative thinking. The desired state (replicas: 5) is already stored in the cluster; a controller enforces it forever without human action — that is the entire point of declarative orchestration." },
    { label: "The pods return only because a liveness probe is configured.", misconception: "Liveness restarts a wedged container in place on a surviving node. Replacing pods lost with a dead node is the ReplicaSet reconciling its count, which is independent of any probe." },
  ]}

<Quiz
  id="03-k8s-objects-choice-2"
  lessonSlug="03-k8s-objects"
  lang="en"
  question="A junior runs kubectl run debug --image=busybox to start a one-off pod, and it works fine for days. Why is this still wrong for anything that must stay up?"
  choices={[
    { label: "A bare Pod is unowned — no controller has it as a desired-state target — so when its node reboots or drains, nothing recreates it and it is gone permanently.", correct: true },
    { label: "Bare Pods cannot be assigned an IP or reach the network.", misconception: "Bare Pods get a normal Pod IP and full network access. The problem is purely lifecycle: nothing reconciles them, so they do not survive node loss or eviction." },
    { label: "kubectl run is disabled in production clusters by default.", misconception: "kubectl run is not disabled by default; admission policy might restrict it, but the fundamental issue is that the resulting Pod has no owning controller to recreate it." },
    { label: "Bare Pods are excluded from Service endpoints regardless of labels.", misconception: "A bare Pod with matching labels is added to a Service's endpoints like any other pod. The flaw is durability, not selectability." },
  ]}
/>

  question="A Deployment defines selector app=web and a Service also selects app=web. A second Deployment is later created whose pods also carry app=web. What happens to traffic?"
  choices={[
    { label: "The Service routes to pods from BOTH Deployments — it selects pods by label directly, with no notion of which Deployment owns them, so the overlapping label silently mixes both workloads behind one endpoint set.", correct: true },
    { label: "The Service rejects the ambiguity and routes to neither Deployment.", misconception: "Selectors never error on overlap; Kubernetes simply lists every matching pod IP in the Endpoints object. Overlapping labels are a common source of accidental traffic mixing, not a hard failure." },
    { label: "The Service routes only to the first Deployment, because it was created first.", misconception: "Creation order is irrelevant. The selector is evaluated against current pod labels each reconcile; any pod matching app=web is an endpoint regardless of which Deployment spawned it." },
    { label: "Only pods explicitly named in the Service spec receive traffic.", misconception: "A Service of this type does not name pods or IPs — it selects dynamically by label. Hardcoding pod IPs would break on every restart, which is exactly why selectors exist." },
  ]}

  lessonSlug="03-k8s-objects"
  lang="en"
  question={"An app needs ~25s to warm (config load + pool prime) before it can serve, and it occasionally wedges into a hung state hours later. The team adds only this:\n```yaml\nlivenessProbe:\n  httpGet: { path: /healthz, port: 8080 }\n  initialDelaySeconds: 30\n```\nRollouts still spike 500s. Why, and what is missing?"}
  choices={[
    { label: "Liveness controls only whether the pod is RESTARTED, not whether the Service routes to it. With no readiness probe the pod is added to endpoints the instant the process starts, so traffic lands on a cold app. Add a readiness probe (gates endpoint membership) and a startupProbe (covers the slow boot).", correct: true },
    { label: "initialDelaySeconds: 30 is too short for a 25s warmup, so liveness kills the pod mid-boot.", misconception: "30s does cover a 25s warmup, and the rollout 500s happen regardless. The real gap is that liveness never gates traffic — a readiness probe is required to hold the pod out of the Service until it can serve." },
    { label: "The httpGet path is wrong; it should hit the app root, not /healthz.", misconception: "The path is fine. Even a correct liveness path cannot fix rollout 500s, because liveness restarts pods — it does not decide endpoint membership. Readiness does." },
    { label: "Liveness and readiness are the same probe; one is enough.", misconception: "They are distinct: liveness restarts a wedged pod, readiness pulls a not-yet-serving pod out of Service rotation. Using liveness where you need readiness is the classic rollout outage." },
  ]}

<Quiz

  lang="en"
  question={"You update a ConfigMap consumed as env vars by a running Deployment:\n```yaml\nenvFrom:\n  - configMapRef: { name: app-config }\n```\nThe new value never reaches the pods even hours later. Root cause and the standard fix?"}
  choices={[
    { label: "Changing a ConfigMap does not trigger a rollout; env-var values are injected at pod start and frozen for the pod's life. The standard fix is to hash the ConfigMap content into a pod-template annotation so any change rolls a new ReplicaSet and restarts the pods.", correct: true },
    { label: "ConfigMaps are immutable, so the update silently failed to apply.", misconception: "The ConfigMap object did update. The issue is propagation: env vars are read once at container start and never refreshed, so running pods keep the old values until they restart." },
    { label: "The Deployment needs kubectl rollout restart because env vars hot-reload only on Secrets.", misconception: "Neither ConfigMap nor Secret env vars hot-reload; both are frozen at start. A rollout restart does work, but teams automate it by hashing config into an annotation so apply itself triggers the roll." },
    { label: "envFrom is deprecated; you must mount the ConfigMap as a volume to get updates.", misconception: "envFrom is fully supported. Volume-mounted ConfigMaps do eventually update the projected files, but env vars never refresh — and even mounted files do not restart the process, so apps must re-read them." },
  ]}

  lang="en"
  question={"A latency-sensitive service sets:\n```yaml\nresources:\n  requests: { cpu: 250m, memory: 256Mi }\n  limits:   { cpu: 500m, memory: 256Mi }\n```\nUnder load it shows periodic latency spikes and the occasional OOMKill. What are the two distinct mechanisms, and which knob is the bigger risk?"}
  choices={[
    { label: "CPU over the limit is THROTTLED (CFS quota stalls the process, causing the latency spikes); memory over the limit is OOMKilled (memory is incompressible, so the kernel kills the container). The memory limit is the sharper risk because it terminates the pod rather than slowing it.", correct: true },
    { label: "Both CPU and memory limits throttle the process; the OOMKill is unrelated to the limits.", misconception: "Memory is incompressible — you cannot throttle it. Exceeding the memory limit triggers an OOMKill, not a slowdown. Only CPU is throttled via CFS quota." },
    { label: "Requests cause the throttling and limits cause the OOMKill.", misconception: "Requests are for scheduling and the guaranteed share — they do not throttle. The CPU LIMIT enforces the throttle ceiling; the MEMORY limit enforces the OOM ceiling. Requests influence neither cap directly." },
    { label: "Setting requests equal to limits for memory is what causes the OOMKill.", misconception: "Equal request/limit for memory gives the Guaranteed QoS class — generally desirable. The OOMKill comes from actual usage exceeding the limit, not from the values matching; the fix is a higher limit or less memory use." },
  ]}

<Recap lang="en">
The unit's through-line is one model: you declare desired state and controllers reconcile actual toward it forever — which is why a Deployment self-heals and a bare Pod does not. The hierarchy stacks one job per layer (Pod runs containers, ReplicaSet keeps the count, Deployment rolls and rolls back), Services select pods by label into an Endpoints set with no notion of ownership, probes split into readiness (gates traffic) and liveness (restarts), ConfigMap/Secret changes never auto-roll, and resources split into CPU (throttled, compressible) and memory (OOMKilled, incompressible). Every production failure here traces back to one of those exact semantics.
</Recap>
