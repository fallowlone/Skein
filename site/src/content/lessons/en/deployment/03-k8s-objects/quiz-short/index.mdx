    { q: "Describe the Pod to ReplicaSet to Deployment hierarchy — what single job does each layer add?", a: "Each layer adds exactly one capability. A Pod is the smallest deployable unit: one or more containers sharing a network namespace (same IP, talk over localhost) and optionally volumes; it is ephemeral and gets a new IP on every restart. A ReplicaSet adds count-keeping: it watches its pods and reconciles toward replicas: N, recreating any that vanish — you almost never create one directly. A Deployment adds rollouts and rollback: on an image change it creates a new ReplicaSet and scales it up while scaling the old one down under maxSurge/maxUnavailable (both default 25%), keeping the old ReplicaSet at scale 0 so rollout undo can scale it back. So Pod runs containers, ReplicaSet keeps the count, Deployment manages versioned transitions." },
    { q: "How does a Service know which pods to route to, and what is the failure mode of overlapping labels?", a: "A Service declares a label selector, e.g. selector: app=web, and Kubernetes maintains an Endpoints (or EndpointSlice) object listing the IPs of every Pod whose labels match; kube-proxy then load-balances across those endpoints. It tracks pods dynamically by label, never by hardcoded IP — which is essential because pod IPs change on every restart. The Service has no notion of which Deployment owns a pod. So if two different Deployments produce pods that both carry app=web, the Service silently routes to pods from both, mixing workloads behind one endpoint set. Overlapping selectors never error; they just accumulate matching IPs, which is a common source of accidental traffic blending." },
    { q: "Contrast readiness, liveness, and startup probes — which one gates traffic, and what is the classic outage?", a: "A readiness probe gates Service endpoint membership: while it fails, the pod is pulled out of the Service's endpoints and receives no traffic — this is what makes rollouts zero-error, because new pods stay out of rotation until they can actually serve. A liveness probe restarts a pod whose container has wedged; it does not control routing. A startup probe holds the liveness and readiness loops off during a slow boot, so a slow-starting app is not killed before it finishes warming. The classic outage is using a liveness probe where you needed readiness: a slow-starting app gets killed and restarted in a loop instead of simply being held out of rotation, or — with no readiness probe at all — the Service routes to a pod the instant the process starts and traffic 500s on the cold app during every rollout." },
    { q: "Why does updating a ConfigMap or Secret not roll the pods that consume it, and how do teams force a refresh?", a: "Values consumed as environment variables are injected once when the container starts and are frozen for the pod's lifetime; changing the ConfigMap or Secret does not trigger any rollout, so running pods keep the old values until they restart. Volume-mounted ConfigMaps/Secrets do eventually update the projected files, but even then the process must re-read them and the pod is not restarted. The standard fix is to hash the ConfigMap/Secret content into a pod-template annotation: when the config changes the hash changes, the pod template changes, and the Deployment rolls a new ReplicaSet — so a plain kubectl apply propagates the new config. Note Secrets are only base64-encoded, not encrypted at rest unless encryption is enabled." },
    { q: "Explain the difference between resource requests and limits, and why CPU and memory behave differently at the limit.", a: "Requests are what the scheduler reserves to place the pod and what it is guaranteed under contention; limits are the hard ceiling on actual usage. The two resources behave differently because CPU is compressible and memory is not. When a container exceeds its CPU limit it is throttled — the CFS quota stalls the process, causing latency spikes but no kill. When it exceeds its memory limit it is OOMKilled, because you cannot reclaim memory by slowing the process; the kernel terminates the container. So the memory limit is the sharper risk. Setting request equal to limit yields the Guaranteed QoS class (last to be evicted under node pressure); requests well below limits yields Burstable. Right-sizing means setting requests to real steady-state usage and limits with enough headroom to avoid spurious throttling or OOMKills." },
