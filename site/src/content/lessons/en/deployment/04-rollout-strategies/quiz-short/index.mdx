    { q: "What do maxSurge and maxUnavailable control, what are their defaults, and what is the zero-downtime setting?", a: "Both are knobs on the Kubernetes rolling update. maxSurge is how many pods above the desired replica count may exist mid-rollout; maxUnavailable is how many of the desired pods may be missing at once. Both default to 25%. For strict zero-downtime you set maxSurge: 1, maxUnavailable: 0 — never drop below full capacity (no old pod leaves until its replacement is ready) and add at most one surge pod to make progress. The cost is a slower rollout, one pod at a time, plus capacity for the surge pod. The knobs alone are not enough: they guarantee capacity, but you still need a readiness probe so traffic is withheld until a new pod can actually serve." },
    { q: "Why is a readiness probe load-bearing during a rolling update, and how does it differ from a liveness probe?", a: "Kubernetes shifts traffic to a new pod the moment it is marked ready, and by default a pod is ready as soon as its container process starts — before the app has opened DB connections or warmed caches. Without a real readiness probe, traffic flows into a half-booted process and a fraction of requests fail with 502s while the Deployment still reports 'available'. A readiness probe returns success only when the app can serve a request, so Kubernetes withholds traffic (plus minReadySeconds for stabilisation) until then. Readiness only removes a pod from the load-balancer rotation; liveness restarts a pod it thinks is dead. Conflating them is dangerous — a liveness probe pointed at a slow dependency turns a backend hiccup into a restart storm." },
    { q: "What makes canary lower-risk than blue-green, and what single thing must be in place for that benefit to be real?", a: "Canary routes a small slice of traffic — typically 5%, then 25%, then 50% — to the new version and ramps only if metrics stay healthy, so a bad release hits 5% of users instead of 100%. Blue-green flips the whole router at once, exposing all traffic the instant you cut over. The benefit is real only with an automated metric gate: an analysis step (Argo Rollouts or Flagger reading SLO metrics like error rate and latency) that auto-pauses or rolls back without a human in the loop. This is progressive delivery. Canary without a gate is just a slow manual rollout — a tired engineer eyeballing a dashboard will promote a failing release to 100% anyway. The tiny blast radius is worthless if you cannot read the canary slice." },
    { q: "Why does blue-green's 'instant rollback' fail on a schema change, and how does expand-contract fix it?", a: "Blue-green flips the application atomically, but blue and green share one database — the schema does not flip with the router. If green's deploy drops or renames a column, the live schema is shaped for green only; blue, still your rollback target, no longer matches it, so flipping back crashes against a schema it cannot read. Expand-contract (parallel change) makes every schema change multi-step: first expand (add the new column or table, keep the old, dual-write so both shapes are populated) — additive and backward-compatible, so old and new code both work; then, only after the old version is fully retired and rollback is no longer possible, contract in a separate later deploy by dropping the old column. At no point is there a schema only one version can read, so rollback stays safe. This applies to rolling and canary too — any strategy with two versions live needs a schema both can read." },
    { q: "When is recreate the right choice despite its downtime, and why can't the other strategies substitute?", a: "Recreate is right when two versions genuinely cannot coexist — an in-place change to a stateful singleton, or a forward-incompatible change with no compatible intermediate schema — and you can tolerate a maintenance window. It kills every old instance, then starts the new ones, guaranteeing no version overlap, and it is the cheapest on resources. Rolling and canary both run two versions simultaneously to serve overlapping traffic, which is exactly what this workload cannot tolerate. Blue-green also has both environments live during cutover and doubles resource cost; expand-contract can't rescue it when there is no compatible intermediate schema. So when no-coexistence is a hard constraint, recreate's clean version swap is the fit, and you simply accept the downtime the maintenance window covers." },
