<Quiz
  id="07-secrets-at-deploy-choice-1"
  lessonSlug="07-secrets-at-deploy"
  lang="en"
  question="A Dockerfile sets ENV API_KEY=sk-live-abc in an early layer, then a later layer runs `unset API_KEY`. Is the key safe in the pushed image?"
  choices={[
    { label: "No — image layers are content-addressed and immutable; the earlier layer still holds the value and `docker history` / `docker save` replays it. Deleting in a later layer never removes it.", correct: true },
    { label: "Yes — the final layer wins, so the runtime environment no longer has the key.", misconception: "Runtime env state and on-disk layers are different things. The build-time ENV is baked into a layer that survives in the registry regardless of what a later layer does at runtime." },
    { label: "Yes — `unset` scrubs the variable from all layers during squash.", misconception: "There is no automatic squash, and even a squashed image leaks if the build cache or intermediate layers are pulled. The rule is never to put the secret in the build at all." },
    { label: "Only unsafe if the registry is public.", misconception: "Anyone with registry read access pulls and replays layers. Private registries still leak to every account, CI job, and cached node that can pull the image." },
  ]}
/>

<Quiz
  id="07-secrets-at-deploy-choice-2"
  lessonSlug="07-secrets-at-deploy"
  lang="en"
  question="A teammate insists the cluster is safe because every Kubernetes Secret value is base64-encoded. What is the precise correction?"
  choices={[
    { label: "base64 is reversible transport encoding with no key — `base64 -d` recovers plaintext in about a second. A leaked manifest, backup, or GitOps history is a leaked password; protection requires actual encryption.", correct: true },
    { label: "It is fine — base64 is a one-way transform, so the original cannot be recovered.", misconception: "base64 is fully reversible, not a hash. Anyone with the encoded string trivially gets the plaintext back." },
    { label: "It is fine — the API server encrypts the base64 value with the cluster key before storing it.", misconception: "Encoding and encryption are separate. The base64 value sits unencrypted in etcd by default; no cluster key is applied unless you configure encryption at rest." },
    { label: "It is partially safe — base64 stops casual reads but not determined attackers.", misconception: "base64 stops nothing. There is no key and no work factor; reversing it is a single command, so it offers zero confidentiality even against casual access." },
  ]}
/>

  lessonSlug="07-secrets-at-deploy"
  lang="en"
  question="You configure an EncryptionConfiguration so the API server encrypts Secrets at rest in etcd. An auditor still finds an old Secret in plaintext in an etcd backup. Why, and what was missed?"
  choices={[
    { label: "Enabling encryption at rest only encrypts writes from that point on — it does not re-encrypt existing Secrets. You must rewrite every Secret (e.g. `kubectl get secrets -A -o json | kubectl replace -f -`) after turning it on.", correct: true },
    { label: "The EncryptionConfiguration silently failed and nothing was ever encrypted.", misconception: "New Secrets written after the change are encrypted; the gap is specifically the pre-existing values, which are never touched until rewritten." },
    { label: "etcd backups are always stored in plaintext regardless of encryption at rest.", misconception: "Encryption at rest means the API server encrypts before writing to etcd, so a backup of encrypted Secrets is ciphertext. The plaintext here is leftover unconverted data." },
    { label: "base64 encoding overrode the encryption layer.", misconception: "base64 is just the encoding of the value field; it does not interact with or override the etcd encryption-at-rest layer." },
  ]}

<Quiz
  id="07-secrets-at-deploy-choice-4"
  lessonSlug="07-secrets-at-deploy"
  lang="en"
  question="An error tracker shows a live DB password indexed in plaintext inside a stack trace. The secret was injected as an environment variable. What is the root cause and the structural fix?"
  choices={[
    { label: "A crash dump serialises the whole process environment, so the SDK shipped the env to a third-party store. Inject the secret as a mounted file instead — not in the environment, not in /proc/.../environ, not inherited by child processes.", correct: true },
    { label: "The SDK has a bug logging env vars; upgrade it and the leak stops.", misconception: "Capturing process state on error is intended SDK behaviour, not a bug. As long as the secret lives in the environment, any crash-state capture can leak it." },
    { label: "The password was too long for safe env storage and got truncated into the log.", misconception: "Length is irrelevant. The leak comes from env being global, inherited, and dumped on crash — a file you read once and never re-export avoids all three." },
    { label: "The fix is to scrub the variable name in the SDK's deny-list.", misconception: "Deny-lists are brittle band-aids that miss renamed or nested keys. The structural fix is to keep the secret out of the environment entirely via a file mount." },
  ]}
/>

  question="A small GitOps team must commit secret config to a private repo so Argo CD can apply it, and they want minimal external dependencies. Which approach is correct, and why is it genuinely safe to commit?"
  choices={[
    { label: "Sealed Secrets — the public key encrypts the value and only the in-cluster controller's private key can decrypt, so the committed blob is real ciphertext. A leaked repo, fork, or full git history reveals nothing usable, with no external vault required.", correct: true },

    { label: "Put the values in a ConfigMap so they are not flagged as Secrets.", misconception: "A ConfigMap is plaintext by design and meant for non-sensitive config. Committing secrets there is strictly worse than a base64 Secret — no encoding, no encryption, no access separation." },
    { label: "External Secrets Operator pulling from Vault — commit the ExternalSecret reference.", misconception: "ESO is excellent at scale but adds an external manager the team did not ask for, and it does not put a self-contained committable artifact in the repo.   ]}

  question="Security wants secrets rotated every 30 days, and they want a stolen credential to be useless fast. You run on Kubernetes with Vault available. What pairing best meets both goals?"
  choices={[
    { label: "Vault dynamic secrets (short-lived per-app credentials that auto-revoke) injected as mounted files that update in place — there is no long-lived secret to rotate, and a leaked credential expires before it is useful.", correct: true },
    { label: "Inject a static 30-day credential as an environment variable and rely on a monthly redeploy to rotate it.", misconception: "Env vars are frozen at container start, so rotation needs a restart, and a static 30-day credential is fully valid for 30 days if stolen. Neither goal is met well." },
    { label: "Keep a static secret but shorten the rotation cron to daily.", misconception: "Faster rotation of a static long-lived secret shrinks the window, but a stolen credential is still valid until the next rotation. Dynamic short-lived creds remove the long-lived secret entirely." },
    { label: "Enable etcd encryption at rest and consider rotation solved.", misconception: "Encryption at rest protects stored Secrets from etcd theft; it does nothing about rotation cadence or limiting the lifetime of a leaked credential." },
  ]}

<Recap lang="en">
The through-line of the unit is one decision path: the secret enters at deploy or runtime (never in the image), it must be genuinely encrypted rather than base64-encoded, etcd needs encryption at rest configured and existing Secrets rewritten, file mounts beat env vars on leak surface and in-place rotation, Sealed Secrets make a committable GitOps artifact, and dynamic short-lived credentials make a stolen secret expire before it is useful. Every wrong answer here is a real incident someone has already lived through. Now when you see any of these patterns in the wild — a base64 blob in a git diff, an ENV in a Dockerfile, a crash dump in Sentry — you know exactly what the next move is.
</Recap>
