By default the value also sits unencrypted in etcd, so an etcd backup theft or node compromise dumps every secret as plaintext. The real protections are: configure encryption at rest with an EncryptionConfiguration, ideally KMS-backed so the key lives outside the cluster, and remember it does not re-encrypt existing Secrets, so you must rewrite them after enabling it. Production setups back it with a KMS provider (AWS KMS, GCP KMS) so the encryption key lives outside the cluster and can be rotated and audited independently. The trap is that enabling it only affects writes from that point forward — it does not re-encrypt the Secrets already stored. Pre-existing values stay in the clear in etcd until you rewrite every Secret, for example kubectl get secrets -A -o json piped to kubectl replace -f -. Skipping that step leaves a false sense of safety: the dashboard says encryption is on, but the old secrets are still readable in a backup." },
    { q: "Why do many teams inject secrets as mounted files rather than environment variables, and what does that buy them?", a: "Environment variables are convenient but leaky. They are global to the process and inherited by every child process you spawn, they are readable at /proc/<pid>/environ, and a crash dump captures the entire environment — so observability SDKs like Sentry or Datadog can serialize a live API key into a third-party log store, and many frameworks print the environment on a fatal error page. Mounted files avoid all of that: the secret lands as a file (often mode 0400 on a tmpfs that never hits disk), not in the environment, not inherited by children, not in /proc/.../environ. The decisive operational benefit is rotation — a mounted file can be updated in place when the secret rotates, while an env var is frozen at container start and needs a pod restart to pick up a new value. For credentials rotated every 30 to 90 days, that is the difference between a rolling restart and a silent in-place swap." },
