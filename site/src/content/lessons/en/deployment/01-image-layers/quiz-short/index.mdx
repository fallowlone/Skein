    { q: "What exactly is a Docker image layer, and what two inputs does the build cache key each layer on?", a: "An image is not one blob; it is a stack of read-only filesystem diffs presented through a union filesystem (overlay2 on Linux), so the container sees one merged tree while storage is a chain of diffs. Each RUN, COPY, and ADD produces exactly one layer — the filesystem changes that step made. The build cache keys a layer on two things: the instruction string itself, and the content it depends on. For COPY and ADD, Docker checksums the files being copied, so a single changed byte changes the key and misses. For RUN, the key is the literal command text — Docker does not inspect what the command actually does, which is its own trap." },
    { q: "State the cardinal ordering rule and explain why putting COPY . . before RUN npm ci wrecks build times.", a: "The cache is a strict prefix match: the first layer whose key changes is rebuilt, and so is every layer after it. The cardinal rule is therefore to order instructions least- to most-frequently-changing — rarely-changing steps deep in the prefix, every-commit source last. COPY . . checksums every file in the context, so editing any source file changes that checksum and invalidates the COPY layer. If RUN npm ci sits after it, the install is downstream of the miss and re-runs, pulling all dependencies over the network on every push. The fix is to split the copy by change frequency: COPY package.json package-lock.json ./ first, then RUN npm ci, then COPY . . for source — so the install stays a cache hit on the vast majority of commits. Teams commonly report CI build times falling by around 70% from this single reorder." },
    { q: "Why does 'RUN apt-get update' followed by a separate 'RUN apt-get install' serve stale packages, and how do you fix it?", a: "Because RUN is cached on its command text, not its effect. The 'apt-get update' string never changes, so Docker treats that layer as a cache hit and reuses a months-old package-index layer; the separate install then resolves against that stale index. The fix is to join them into one instruction — RUN apt-get update && apt-get install -y <pkg> — so they share a single cache key and invalidate together. The same logic explains why ARG placement matters: a build arg changes downstream cache keys, so declare it as late as the build allows." },
    { q: "How does a multi-stage build shrink an image, and roughly what size deltas should you expect?", a: "You write several FROM stages in one Dockerfile: a fat builder stage does the heavy work (compilers, dev dependencies, build caches), then a slim runtime stage does COPY --from=builder of only the finished artifacts. Only the last stage becomes the published image; the builder is discarded entirely, so its toolchain never ships. The deltas are large: a single-stage Node build around 380 MB+ drops to roughly 60 MB on a slim or distroless base; a Go binary near 180 MB collapses to a few MB on scratch or distroless/static because a compiled binary needs no runtime. One widely-cited example shrank 843 MB to 12.1 MB — a 98.6% reduction." },
    { q: "Compare distroless and alpine as final-stage bases — when do you reach for each?", a: "Alpine is tiny because it uses musl libc and BusyBox, and it ships apk, which is convenient when you need to add a tool. The catch is that musl differs from glibc enough to cause native-module breakage and the occasional DNS or performance surprise, and shipping a shell and package manager widens the attack surface. Distroless ships only your app and its direct runtime dependencies — no shell, no package manager — so attack surface and CVE-scan noise are minimal, but you cannot docker exec a shell to debug and must COPY in every runtime dependency. Reach for distroless for a hardened, self-contained compiled service; reach for alpine when you genuinely need a shell or to install runtime packages." },
    { q: "Why does deleting a secret in a later layer not remove it, and what should you do instead?", a: "An image is a stack of immutable, append-only diffs. COPYing a key into the image creates a layer containing the file; a later RUN rm is just another diff that marks it deleted in the merged view — it never edits or erases the earlier layer, which still physically holds the bytes. Anyone can run docker history or unpack the layers and recover the file, pushed or not. The correct approaches keep the secret out of any persisted layer: a BuildKit secret mount, RUN --mount=type=secret,id=token, which exposes the secret only for that one instruction and writes it to no layer; or a multi-stage build where the secret lives only in a discarded builder stage. The principle is that a secret must never become a layer in the first place — you cannot delete it back out." },
