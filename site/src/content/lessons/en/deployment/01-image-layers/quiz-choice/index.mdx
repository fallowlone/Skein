    { label: "It improves cache hits but increases the final image size.", misconception: "Reordering instructions does not change image size — the same layers exist. It changes only which layers stay cached. Here the reorder hurts cache, and size is unaffected either way." },

  lessonSlug="01-image-layers"
  lang="en"
  question={"A Dockerfile has these two lines as separate instructions. Builds keep installing months-old package versions even after the upstream repo updated. Why?\n\nRUN apt-get update\nRUN apt-get install -y curl"}
  choices={[
    { label: "RUN is cached on the command text, not its effect. The unchanged 'apt-get update' string is a cache hit, so a stale package-index layer is reused and install resolves against it. Join them into one RUN so they share a key and invalidate together.", correct: true },
    { label: "apt-get is non-deterministic and cannot be cached reliably.", misconception: "The caching is working exactly as designed — too well. Docker reuses the update layer because its instruction string never changed. The issue is splitting update and install into two cache keys, not non-determinism." },
    { label: "The base image pins an old apt mirror that must be changed.", misconception: "The mirror is not the cause; the cached 'apt-get update' layer is. Even with a fresh mirror, a cache-hit update layer still serves a stale index. Combine update and install in one RUN." },
    { label: "You must pass --no-cache on every build to keep packages fresh.", misconception: "--no-cache discards all caching and defeats the point of layer caching. The targeted fix is to merge update and install so the index refresh and the install invalidate as a unit." },
  ]}

<Quiz
  id="01-image-layers-choice-3"
  lessonSlug="01-image-layers"
  lang="en"
  question={"A single-stage Go build ships a ~180 MB image. A teammate proposes appending 'RUN apt-get remove -y build-essential && rm -rf /usr/local/go' at the end to slim it. Will the image shrink?"}
  choices={[
    { label: "No. Removing files in a later layer adds a deletion diff on top — the earlier layers still physically contain the bytes, so the image stays large and the toolchain remains recoverable. Use a multi-stage build and COPY only the binary into a scratch/distroless final stage.", correct: true },
    { label: "Yes — apt-get remove plus rm reclaims the space and the image shrinks accordingly.", misconception: "Layers are immutable, append-only diffs. A delete in a later layer hides files in the merged view but never edits earlier layers, so the bytes — and the image size — persist. Only a fresh final stage actually drops them." },
    { label: "Yes, as long as the removal runs in the same RUN as the install.", misconception: "Same-RUN cleanup helps only for files created and removed inside that one instruction. Here the toolchain came from the base image and earlier layers, so a removal RUN cannot shrink it. Multi-stage is the correct tool." },
    { label: "No, but switching to a larger ubuntu base would fix it.", misconception: "A larger base makes the image bigger, not smaller. The fix is the opposite direction: build in a fat stage, then COPY the artifact into a minimal final stage like scratch or distroless/static." },
  ]}
/>

    { label: "The full builder base reused as the runtime, to avoid a second FROM.", misconception: "That is the exact anti-pattern multi-stage builds exist to fix — you ship compilers, dev deps, and apt caches into production: hundreds of MB of bloat and attack surface that never serve a request." },
    { label: "ubuntu:22.04 with build tools removed afterward via apt-get remove.", misconception: "Removing tools in a later layer does not shrink the image (the bytes stay in earlier layers) and keeps a large glibc base with a shell and package manager.   lang="en"
  question={"During CI a build needs a private-registry token to fetch dependencies. An engineer writes COPY token.txt /tmp/token, uses it in a RUN, then RUN rm /tmp/token in the next instruction. The final image is published. What is the exposure?"}
  choices={[
    { label: "The token is permanently recoverable. COPY made it a layer; the later rm is just a diff hiding it in the merged view. Anyone can extract the earlier layer via docker history or by unpacking the image. Use RUN --mount=type=secret so the token is written to no layer, or keep it only in a discarded builder stage.", correct: true },
    { label: "Safe — the rm in the following instruction removes the token from the image.", misconception: "Layers are stacked immutable diffs. The rm adds a new diff marking the file deleted in the merged tree but cannot erase the earlier layer, which still physically holds the token. It is recoverable regardless." },
    { label: "Safe as long as the image is only stored in a private registry.", misconception: "A private registry controls who can pull, not whether the secret is in the layers. Anyone who can pull (or who has the local image) can extract it. The secret should never have become a layer." },
    { label: "Safe because the token was only in /tmp, which containers treat as ephemeral.", misconception: "The ephemeral-at-runtime semantics of /tmp are irrelevant to the build: COPY wrote the file into a persisted image layer at build time. The path does not exempt it from layer history." },
  ]}

  question={"docker build is slow to even start — several seconds elapse before the first instruction runs — and COPY . . occasionally pulls a developer's local .env into the image. The repo has no .dockerignore. What single change addresses both?"}
  choices={[
    { label: "Add a .dockerignore listing node_modules, .git, *.log, and .env. The whole build context is tarred and sent to the daemon first; excluding bulky and sensitive paths shrinks the upload (faster start) and stops COPY . . from raking secrets and junk into a layer.", correct: true },
    { label: "Switch COPY . . to ADD . . so Docker can stream files more efficiently.", misconception: "ADD adds URL/auto-extract behaviour, not a smaller context.     { label: "Pin a smaller base image to speed up the build.", misconception: "Base-image size affects pull and final-image size, not the pre-build context upload or what COPY . . includes. The slow start and the leaked .env both come from an unfiltered build context." },
    { label: "Run the build with --no-cache so the context is re-read cleanly each time.", misconception: "--no-cache forces full rebuilds and re-sends the same bloated context — it makes the slow start worse and does nothing about .env leaking. <Recap lang="en">
The through-line is one model: an image is immutable stacked layers, the cache is a strict prefix, and RUN is keyed on command text rather than effect. Order least- to most-changing so the expensive install stays a cache hit; merge update-and-install so they invalidate together; multi-stage so you compile fat and ship slim instead of deleting bytes that never leave history; pick distroless when you want minimal attack surface and accept losing the shell; and keep the build context lean with .dockerignore. The hardest trap — a secret added then rm'd — falls out of the same immutability rule: you cannot delete it back out, so it must never become a layer.
</Recap>
