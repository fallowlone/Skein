  lang="en"
  question="An NLB (L4) fronts your service. Product asks to route /api/v2/* to a new backend pool while keeping /api/v1/* on the old one. What is the honest answer, and why?"
  choices={[
    { label: "It is impossible at L4 — the path lives inside the HTTP request, which an L4 balancer never parses; you must move this routing to an L7 balancer (ALB / nginx / Envoy) that terminates the connection and reads the path.", correct: true },
    { label: "Add a path-prefix listener rule to the NLB target group.", misconception: "L4 listeners match on protocol and port only. The URL path only exists once HTTP is parsed, and an L4 balancer forwards raw TCP without parsing — there is no path rule to add at that layer." },
    { label: "Enable deep packet inspection on the NLB so it can read the path.", misconception: "Inspecting the HTTP payload to read a path is exactly what makes a balancer L7.     { label: "Use consistent hashing so /api/v2/* requests land on the new pool.", misconception: "Hashing pins a key (e.g. client IP) to a backend regardless of path; it cannot separate v2 from v1 because it never sees the path. Affinity is not routing." },
  ]}

  question="Backend request durations vary wildly: most return in 5 ms, a few take 2 s. Under round-robin, p99 latency is bad and one box is always hot. Which algorithm change helps most, and why?"
  choices={[
    { label: "Least-connections — it routes the next request to the backend with the fewest in-flight connections, so a box stuck on slow requests stops accumulating new ones instead of being handed its 1-in-N share regardless of load.", correct: true },
    { label: "Stay on round-robin but add more backends.", misconception: "Round-robin still hands each backend an equal share blind to how busy it is, so a box mid-slow-request keeps getting piled on. More capacity dilutes but does not fix the skew the algorithm creates." },
    { label: "Switch to IP hashing for even distribution.", misconception: "IP hashing pins clients to backends for affinity; it does not balance by current load and can actually worsen skew if a heavy client hashes to one box. It solves stickiness, not uneven request duration." },
    { label: "Lower the health-check interval so slow backends get pulled.", misconception: "A slow-but-healthy backend passes health checks; pulling it on latency alone would flap the pool. The fix is steering load by current connection count, not declaring a working box dead." },
  ]}

    { label: "Enable SNI-based routing so the balancer routes by path without decrypting.", misconception: "SNI exposes the hostname in the TLS handshake, so an L4 balancer can route by host without decrypting — but the path is in the encrypted body.   lessonSlug="06-lb-levels"
  lang="en"
  question="A service uses cookie-based sticky sessions to keep in-memory user state on one backend. Load is uneven (one box is hot) and that box cannot be drained cleanly during deploys. What is the senior fix?"
  choices={[
    { label: "Externalise session state — push it to Redis or a signed JWT so any backend can serve any request — then turn stickiness off. Stateless backends distribute evenly and drain cleanly; affinity is a workaround for state you should not have pinned to a box.", correct: true },
    { label: "Switch sticky sessions from cookie-based (L7) to IP-hash (L4).", misconception: "Changing the affinity mechanism does not remove affinity — load still concentrates and the box still owns sessions nobody else has. The root cause is per-backend state, not how the client is pinned." },
    { label: "Increase the drain window so the sticky box has more time to finish.", misconception: "A longer window lets active sessions wind down, but new requests for those sessions keep arriving and the box still cannot retire until they expire. You are managing the symptom, not the pinned state." },
    { label: "Use least-connections to even out the load despite stickiness.", misconception: "Stickiness overrides the algorithm by design — once a client is pinned, its requests bypass least-connections and return to the same box. You cannot balance away affinity you deliberately enabled." },
  ]}

<Recap lang="en">
The through-line of the unit is one rule: the layer you pick decides what the balancer can see, and what it can see decides what it can do. L4 forwards bytes by IP and port — fast, protocol-agnostic, capable of TLS passthrough, but blind to path, header, and cookie; L7 terminates the connection, reads HTTP, and routes on any of those, paid for in per-request CPU and crypto. On top of the layer sit the operational knobs that decide reliability: least-connections beats round-robin under uneven request durations, health checks pull dead backends but only as fast as their interval, sticky sessions trade even distribution and clean draining for pinned state (so externalise state first), and connection draining lets in-flight requests finish before a backend retires. And DNS round-robin is not a load balancer — no health awareness, failover bounded by uncontrolled TTLs and caches.
</Recap>
