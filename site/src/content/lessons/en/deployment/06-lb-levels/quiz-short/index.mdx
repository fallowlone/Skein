An L7 balancer terminates the client connection, parses the full HTTP request, makes a routing decision on method/host/path/header/cookie, then opens its own connection to the chosen backend. An L7 balancer ends the encrypted session at the edge: it holds the certificate, decrypts, reads plaintext HTTP, routes on path or header, then forwards as plaintext on the trusted network or re-encrypts to the backend. That same decryption is exactly what lets it route on request contents, and it centralises cert management and offloads crypto from app servers. An L4 balancer normally cannot terminate TLS because it would have to decode the request; instead it does TLS passthrough — the encrypted bytes flow straight to the backend, which holds the cert and terminates. Passthrough keeps the balancer blind by design: great for end-to-end encryption and non-HTTP protocols, useless if you wanted path routing." },
    { q: "Round-robin vs least-connections vs hashing — when does each win, and what does hashing give an L4 balancer?", a: "Round-robin spreads connections evenly and is fine when requests cost roughly the same — equal share, no per-request state. Least-connections routes to the backend with the fewest in-flight connections, which is far better when request durations vary widely, because a box stuck on slow requests stops accumulating new ones instead of getting its blind 1-in-N share. Hashing (by client IP, or consistent hashing) pins a given key to a given backend; that is how an L4 balancer fakes stickiness without cookies, and consistent hashing limits how many keys remap when the pool changes. The skew failure mode: under uneven durations round-robin keeps piling onto a busy box and wrecks p99, while hashing can concentrate a heavy client on one backend. Match the algorithm to the request profile." },
    { q: "What do active vs passive health checks do, and why does the check interval bound how fast a dead backend is removed?", a: "Health checks keep the pool honest. Active checks probe each backend on an interval (e.g. every few seconds) and pull it from rotation after N consecutive failures; passive checks mark a backend down after it returns errors to real traffic. Open-source nginx leans on passive checks, while ALB/NLB and nginx Plus do active probing. The interval bounds removal speed because a crashed backend is only pulled after the check notices — so a too-slow interval leaves a window where live traffic keeps hitting a dead box and 502s leak to users. You trade detection speed against probe load and flapping: too aggressive and a briefly-slow backend gets ejected and the pool oscillates; too lazy and failures leak. Draining and health checks pair up — drain, wait, terminate, with checks confirming the remaining pool is healthy." },

Without connection draining the balancer deregisters it immediately and those open connections are severed — users see resets or errors mid-request, e.g. mid-checkout, turning every deploy into a small self-inflicted outage. Connection draining (AWS calls it deregistration delay) fixes this: when a backend is marked for removal the balancer stops sending it new connections but lets existing ones run to completion for a grace window. On AWS the default deregistration delay is 300 seconds, configurable from 0 to 3600. The window must be at least as long as your longest legitimate request, or you still cut live traffic; set too long and deploys drag. The senior reflex is to make backends stateless — push session state into Redis or a signed JWT — so any backend can serve any request, which restores even distribution and clean draining.
