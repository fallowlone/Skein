Idempotency is the necessary consequence: because you declared an end state rather than a sequence of mutations, running apply twice must converge to the same result, not stack up duplicates.     { q: "Walk through what terraform plan actually does, and name its three inputs.", a: "plan is a diff engine. It reads three inputs: the config (your desired state in .tf or Pulumi code), the recorded state file (what the tool last built, including the map from config names to real resource IDs), and reality (it refreshes by querying the live provider). It reconciles state against the live provider first, then prints the diff — what it will create, change, or destroy — without touching anything. apply then executes that diff and writes the new reality back into the state file. The crucial detail is that both plan and apply refresh first, which is exactly where drift surfaces: if reality diverged from the recorded state, the refresh catches it and the plan shows the unexpected change." },
    { q: "Why is the state file both the source of truth and the biggest hazard?", a: "It is the identity map from the symbolic names in your config (aws_lb.web) to the real provider resource IDs the tool created. Without it the tool literally cannot tell which live resource a config block manages, so it would recreate or orphan things — that is the source-of-truth side. The hazard side is threefold. First, it serialises resource attributes including secrets in plaintext by default, so anyone with read access to the backend has your passwords and keys — the fix is to never route secrets through state as outputs, writing them straight to a secrets manager instead. Second, it is corruptible, so it must live in a versioned remote backend you can roll back. Third, writes are not safe under concurrency, so it must be locked. Treat it like a production database: locked, backed up, access-controlled, never a place you route secrets through." },
    { q: "Why do concurrent applies corrupt state, and what exactly does a lock prevent?", a: "A write to the state file is not atomic across a team. If two applies run at once, both read the old state, both compute plans against that same baseline, and both write back — the second clobbers the first, and the resulting file describes neither reality nor either plan. That is corruption, not a clean last-writer-wins. A lock prevents it by making the backend acquire an exclusive lock before any write operation; a second apply then waits (governed by -lock-timeout) or fails fast with 'Error acquiring the state lock' instead of racing. The CI discipline around it is a concurrency group so jobs never overlap, a sensible lock-timeout so legitimate in-flight runs are waited on rather than failed, and force-unlock reserved only for genuinely stale locks left by a crashed run — never while another apply is actively writing." },
    { q: "Define drift, the safe way to detect it, and the silent-revert trap.", a: "Drift is when the real infrastructure diverges from what the state file and config say — almost always because someone made an out-of-band change like a console click or an emergency CLI patch during an incident. You detect it with terraform plan, which refreshes against the provider and reports the differences; the safe, deliberate way is plan -refresh-only, which shows the divergence without overwriting state the way a bare refresh does, ideally on a schedule. The silent-revert trap is that IaC always reconciles reality back to the declared desired state, so a routine apply will quietly remove a manual fix that is not in the config — re-causing the very incident the fix solved. So when a plan shows drift you make a judgment call first: codify the manual change into the config if it should stay, or let apply restore the declaration if it was a mistake. You decide intent before applying, instead of letting apply decide for you." },

It also makes rollback trivial: instead of remembering and reversing every manual tweak, you redeploy the previous known-good image. So immutability is the deeper cure that drift detection only treats symptomatically: detect-and-reconcile handles drift after it happens, while immutability removes most of the opportunity for it to happen at all." },
