<Hook>
Imagine you have two ways to find a name in a phonebook:  
Option A: Start at page 1 and check every name until you find it.  
Option B: Open to the middle, decide if the name comes before or after, then repeat on the correct half.  
Both work, but if the phonebook has 1 000 000 names, Option A might need up to 1 000 000 checks, while Option B needs at most 20.  
The difference isn’t about which code you write — it’s about how the number of steps grows as the input gets bigger. That growth is what we call **complexity**.

<Idea>
When we talk about an algorithm’s "cost", we usually care about two things:  
- **Time** – how many steps it takes (or how long it runs)  
- **Space** – how much extra memory it needs  

For beginners, we focus on **time complexity** because it’s the most common bottleneck.  
Instead of counting exact steps (which depends on hardware, compiler, etc.), we look at how the step count changes when the input size *n* changes.  
We express this with **Big O notation**, which gives an upper bound on the growth rate.

Examples:
- **O(1)** – constant time: the algorithm takes the same number of steps no matter how big the input is.  
  Example: accessing an array element by index.
- **O(log n)** – logarithmic time: the steps grow slowly as n grows.  
  Example: binary search on a sorted array.
- **O(n)** – linear time: steps grow proportionally to n.  
  Example: scanning a list to find the maximum.
- **O(n log n)** – linearithmic time: common in efficient sorting algorithms like merge sort and quicksort (average case).
- **O(n²)** – quadratic time: steps grow with the square of n.  
  Example: nested loops where each loop runs n times (checking all pairs).
- **O(2ⁿ)** – exponential time: steps double with each addition to the input.  
  Example: trying every subset of a set (brute‑force).

We drop constants and lower‑order terms because, for large n, the highest‑order term dominates.  
So an algorithm that takes 5n² + 3n + 7 steps is still **O(n²)**.
</Idea>

<Code>
Let’s look at a few simple algorithms and write their complexity.

**1. Constant time – O(1)**
```
algorithm getFirst(list):
    return list[0]
```
No matter how long the list is, we do one step: return the first element.

**2. Linear time – O(n)**
```
algorithm sumList(list):
    total ← 0
    for value in list:
        total ← total + value
    return total
```
The loop runs once per element → n steps → O(n).

**3. Quadratic time – O(n²)**
```
algorithm hasDuplicate(list):
    for i from 0 to list.length - 1:
        for j from i + 1 to list.length - 1:
            if list[i] == list[j]:
                return true
    return false
```
Outer loop runs n times, inner loop runs up to n times for each outer iteration → roughly n²/2 comparisons → O(n²).

**4. Logarithmic time – O(log n)**
```
algorithm binarySearch(list, target):
    left ← 0
    right ← list.length - 1
    while left <= right:
        mid ← (left + right) // 2
        if list[mid] == target:
            return true
        else if list[mid] < target:
            left ← mid + 1
        else:
            right ← mid - 1
    return false
```
Each iteration cuts the search range in half → number of iterations is log₂(n) → O(log n).
</Code>

<Trace>
Let’s trace `sumList` on input `[2, 4, 6]` to see the linear work:

| Step | value | total (before) | total (after) |
|------|-------|----------------|---------------|
| Start| –     | 0              | 0             |
| Loop1| 2     | 0              | 2             |
| Loop2| 4     | 2              | 6             |
| Loop3| 6     | 6              | 12            |
| End  | –     | –              | 12            |

We visited each element exactly once → 3 steps for n=3 → O(n).

Now trace `hasDuplicate` on `[1, 2, 3]` (no duplicates) to see the quadratic work:

| Outer i | Inner j | Comparison | Action |
|---------|---------|------------|--------|
| 0       | 1       | 1==2?      | false  |
| 0       | 2       | 1==3?      | false  |
| 1       | 2       | 2==3?      | false  |
| (loops end) | | | return false |

We did 3 comparisons = n*(n-1)/2 for n=3 → O(n²).
</Trace>

<Complexity>
To compute the Big O of an algorithm:
1. Identify the basic operation that repeats (usually inside the innermost loop).
2. Count how many times that operation runs as a function of input size n.
3. Keep only the fastest‑growing term, drop constants and coefficients.

Examples from the code above:
- `getFirst`: basic operation = array access → runs 1 time → O(1).
- `sumList`: basic operation = addition inside loop → runs n times → O(n).
- `hasDuplicate`: basic operation = comparison inside inner loop → runs ~n²/2 times → O(n²).
- `binarySearch`: basic operation = comparison inside while loop → runs log₂(n) times → O(log n).

Why we drop constants:  
If an algorithm runs 5n steps, we still say O(n) because as n → ∞, the factor 5 doesn’t change the growth rate class.
</Complexity>

<Recap lang="en">
Complexity analysis lets us predict how an algorithm will scale without running it on every possible input.  
We use Big O notation to describe the upper bound on the growth rate of runtime (or space) as the input size increases.  
Common classes are O(1) (constant), O(log n) (logarithmic), O(n) (linear), O(n log n) (linearithmic), O(n²) (quadratic), and O(2ⁿ) (exponential).  
By looking at loops—especially nested loops—we can often determine the complexity directly from the code structure.
</Recap>
