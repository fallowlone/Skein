<Hook>
You’re given a task: “Write a program that tells you if a year is a leap year.”  
Do you open your editor and start typing `if (year % 4 == 0) { ... }`?  
Or do you first pause and ask:  
- What exactly counts as a leap year?  
- What are the inputs and outputs?  
- Are there any tricky cases (like year 1900 vs 2000)?  
- What steps will I need to follow?  
That pause — **problem analysis** — is what separates guessing from solving.
</Hook>

<Goal>
By the end of this lesson you will be able to:
- Read a problem statement and rewrite it in your own words
- Identify the inputs, outputs, and any constraints
- Break the problem into smaller, ordered steps (decomposition)
- Think about edge cases and how to handle them
</Goal>

<Idea>
Before writing a single line of code, good programmers spend time understanding the problem.
This process has four main parts:

1. **Understand the problem**
   Read the description carefully. If anything is unclear, ask questions (or, in practice, look for examples).
   Restate the goal in simple terms: “What do I need to produce, and from what?”

2. **Identify inputs and outputs**
   - **Input**: what data the algorithm receives (could be numbers, text, lists, etc.)
   - **Output**: what result it should produce
   Sometimes there are also **constraints**: limits on input size, time, or memory.

3. **Decompose into steps**
   Split the overall task into smaller, clearly ordered actions.
   Each step should be doable on its own and bring you closer to the solution.

4. **Consider edge cases**
   Think about unusual inputs that might break a naive solution:
   - Empty lists, zero, negative numbers
   - Duplicates, already‑sorted data
   - Boundary values (like the first or last element)
   Planning for these now saves debugging later.

Let’s apply these ideas to the leap‑year example.
</Idea>

<Code>
Here’s how we would analyze the leap‑year problem:

**Step 1: Understand the problem**  
A leap year in the Gregorian calendar occurs:
- Every year that is evenly divisible by 4
- EXCEPT years that are evenly divisible by 100
  UNLESS the year is also evenly divisible by 400

So 1996 is a leap year (divisible by 4, not by 100).  
1900 is NOT a leap year (divisible by 100 but not by 400).  
2000 IS a leap year (divisible by 400).

**Step 2: Identify inputs and outputs**  
- Input: a single integer representing a year (e.g., 2024)  
- Output: a boolean — true if it’s a leap year, false otherwise  
- Constraints: assume the year is a positive integer (we won’t handle BC years)

**Step 3: Decompose into steps**  
We can follow the rule directly:
1. If the year is divisible by 400 → leap year
2. Else if the year is divisible by 100 → NOT a leap year
3. Else if the year is divisible by 4 → leap year
4. Else → NOT a leap year

**Step 4: Consider edge cases**  
- Year 0? (if using astronomical year numbering) – but we assume AD years only.
- Negative years? Same as above.
- Non‑integer input? We’ll assume the input is already validated as an integer.
</Code>

<Trace>
Let’s trace the algorithm for three test cases: 1900, 1996, 2000.

| Year | div400? | div100? (after not div400) | div4? (after not div100) | Result |
|------|---------|----------------------------|--------------------------|--------|
| 1900 | 1900 % 400 = 300 → no | 1900 % 100 = 0 → yes → return false | – | false |
| 1996 | 1996 % 400 = 396 → no | 1996 % 100 = 96 → no → continue | 1996 % 4 = 0 → yes → return true | true |
| 2000 | 2000 % 400 = 0 → yes → return true | – | – | true |

The algorithm correctly handles the century edge case.
</Trace>

<Complexity>
The algorithm uses a constant number of modulo operations (at most three) and comparisons.
Regardless of the input size (the value of the year), the number of steps does not grow.
Therefore, the time complexity is **O(1)** — constant time.
Space usage is also **O(1)** — we only store the input year and a few temporary results.
</Complexity>

<Recap lang="en">
Problem analysis is the pause before you start coding. By first understanding the problem, identifying inputs and outputs, breaking the task into steps, and considering edge cases, you set yourself up to write correct, clear code.  
Skipping this step often leads to guesswork, missed requirements, and debugging headaches later.  
A good habit is to restate the problem in your own words, list what you need to produce from what, order the steps, and think about tricky inputs like empty lists, zeros, or boundary values.
</Recap>
