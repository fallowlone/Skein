That gives O(1) average lookup, insert, and delete. The cost is twofold: memory (you allocate an array of buckets with spare capacity to keep collisions rare) and unordered iteration (a hash map has no inherent key order — JavaScript's Map preserving insertion order is a separate convenience). You trade space and ordering for speed. The 'average' is conditional: it holds only while keys spread roughly uniformly and the load factor stays bounded." },
    { q: "What is a collision, and how does separate chaining resolve it?", a: "A collision is when two different keys hash to the same bucket index — unavoidable once you have more keys than buckets, by the pigeonhole principle. Separate chaining makes each bucket a small list. On insert you append (or update in place if the key already exists) to that bucket's list; on lookup you hash to the bucket, then scan the list comparing the full key, since the index alone cannot distinguish the colliding keys. Lookup cost is O(1 + chain length), and chain length averages the load factor." },
    { q: "Define the load factor and explain why it, not the total item count, governs lookup cost.", a: "The load factor alpha = items / buckets is the average number of items per bucket, which equals the average chain length under chaining. Lookup is O(1 + alpha): one hash to find the bucket, then a scan proportional to the chain. Total item count alone says nothing about speed — a million items in two million buckets (alpha = 0.5) is fast, while a hundred items in two buckets (alpha = 50) is slow. That is why tables resize to keep alpha bounded (often below 0.75) rather than just letting items accumulate." },
    { q: "Why is hash-table insert O(1) amortized even though a single insert can be O(n)?", a: "When alpha crosses a threshold, the table allocates a larger array (typically double) and rehashes every existing key into it — an O(n) operation, because the index hash(key) % length changes when length changes, so every key must be re-placed. But doubling means you resize only O(log n) times as the table grows. Summed over n inserts, the resize work is n + n/2 + n/4 + ... = O(n), which spread across the n inserts is O(1) amortized each. Most inserts are cheap; the rare expensive one is paid for by the many cheap ones." },
    { q: "Compare the seen pattern and the complement pattern, and give a problem each solves in one pass.", a: "The seen pattern keeps a hash set of values already encountered; for each new element you check membership in O(1) and then add it — used for contains-duplicate or detecting the first repeated element in O(n) time. The complement pattern keeps a hash map from value to index of what you have seen; for each x you look up the needed partner (e.g. target - x for two-sum) before recording x, so an element never pairs with itself. Both replace an O(n squared) nested loop with a single O(n) pass that trades memory for time." },
    { q: "When does a hash table fail to deliver O(1), and what do you do about it?", a: "It degrades to O(n) when keys do not spread uniformly: a poor hash function (e.g. using only the first character), pathological input, or an adversary crafting keys that all collide into one bucket — an algorithmic-complexity DoS. The fixes differ by cause. For a weak hash, use a well-mixing function (multiply by a prime, fold bits). For adversarial input, use a randomized, per-process seeded hash so collisions cannot be predicted. And always keep the load factor bounded by resizing — but note that resizing alone does not stop an attacker who controls the hash inputs, since they recollide after the resize." },

If you could reconstruct each answer from memory, you hold the unit's spine: a hash function buys O(1) average access at the price of memory and ordering; collisions are inevitable and chaining stores them in per-bucket lists; the load factor — not raw item count — sets the average chain length and thus the cost; resize keeps it bounded at O(1) amortized; and the seen, complement, frequency, and grouping patterns are all this machinery applied.
