The dogpile is what happens when many requests miss the same key in the same instant before any of them has written the new value. The dangerous window is the gap between the first miss and the value being rewritten; during it a naive cache-aside read has no coordination, so every concurrent request also misses and also starts recomputing. A hot key is the worst case because hotness means many requests are concurrently in flight at all times, so its single TTL expiry event hits the maximum number of in-flight requests at once. One expensive query times N concurrent requests is the meltdown — a 200ms query at 5000 req/s becomes 5000 simultaneous connections, exhausting a 20–100 connection pool." },
    { q: "What is the difference between a local single-flight and a distributed lock, and when do you need each?", a: "Local single-flight (e.g. Go's singleflight.Group) is an in-process map that deduplicates concurrent calls for the same key onto one in-flight call. It collapses the herd within one process but has no cross-instance visibility, so with N app instances behind a load balancer the origin still sees up to N concurrent recomputes — one per process. A distributed lock (e.g. Redis SET key token NX PX) lives in a shared store, so only the instance that wins the lock recomputes and the whole fleet collapses to one recompute. You use single-flight when one process or a single hot path needs coalescing and N-way fan-out is acceptable; you reach for a distributed lock when even N concurrent recomputes overwhelm the origin and you need exactly-one across the fleet — at the cost of a network round-trip and a dependency on the lock store's availability." },
    { q: "Why must a recompute lock have a TTL, and how do you choose it?", a: "Without a TTL, a holder that crashes, is OOM-killed, hangs, or has its pod evicted mid-recompute never releases the lock, so every other reader blocks or retries forever — a total outage with a healthy, idle database. The TTL is the deadlock escape hatch: it auto-releases a dead holder's lock. Choosing it is a bind: too short and a slow (p99/tail) recompute loses the lock mid-flight, a second worker acquires it, and the dogpile reopens with two writers racing; too long and a crashed holder leaves every reader waiting that full duration. A fixed TTL must exceed the worst-case recompute, which is why the better pattern is to renew the lease on a heartbeat rather than guess a single number." },
    { q: "Explain lease renewal: what problem it solves and what new failure it introduces.", a: "Lease renewal means the lock holder runs a heartbeat that re-extends the lock's TTL (e.g. PEXPIRE back to 10s every 3s) while it is still alive and working. This tracks the real recompute instead of a guessed fixed TTL: a live holder keeps extending so it never loses the lock mid-flight even on a slow tail recompute, while a crashed holder stops renewing and the short TTL releases it quickly. The new failure is the paused holder: a long stop-the-world GC pause or a network partition freezes the heartbeat too, the lease lapses, a second worker acquires the lock and recomputes, and when the first worker resumes it may still believe it holds the lock and write a stale value. So renewal alone does not give exactly-once — you must also fence the write." },
    { q: "What is a fencing token and why does it matter for a leased recompute lock?", a: "A fencing token is a monotonically increasing number handed out with the lock each time it is acquired; the holder attaches it to any write it makes, and the store (or cache) rejects a write carrying a token older than the last one it accepted. It matters because a leased lock can still be stolen out from under a holder that paused (STW GC, partition) long enough for its lease to lapse: the resumed holder still thinks it owns the lock and tries to write. CAS-on-token only stops it deleting someone else's lock; it does not stop the stale write itself. The fencing token (or a versioned check-and-set on the cached value) makes the store reject that stale write, so a paused-and-resumed worker cannot overwrite the newer value the second worker already produced." },

On each hit, a reader rolls a die and may voluntarily recompute early with a probability that rises as expiry approaches, using time() − delta * beta * log(rand()) ≥ expiry, where delta is the last recompute cost and beta ≈ 1 is near-optimal. Because each reader decides independently, the first lucky reader recomputes alone, well before the TTL hits zero, and rewrites the key — so when the herd arrives the value is fresh and nobody misses. Choose XFetch for a single very hot key where you can store the recompute-cost delta and can tolerate a little extra recompute work; choose a lock (with stale-on-wait) when you need a single coordinated write and want no extra recomputes. They are not interchangeable — they attack different points of the same collision." },
