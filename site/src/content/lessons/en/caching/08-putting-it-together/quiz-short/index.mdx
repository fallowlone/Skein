    { q: "Distinguish a stampede from a dogpile, and give the defence for each.", a: "Both are origin-overload patterns triggered when a cached value goes away. A stampede is the broad case: a single popular TTL expiry (or a flush) turns a hot key into a flash flood of misses that hammer the origin like a self-inflicted DDoS. A dogpile is the specific concurrent form: when one popular key expires, many in-flight requests miss at the same instant and all pile onto the database simultaneously. Defences overlap: a per-key mutex / single-flight collapses N concurrent misses into one recompute (the rest await the same result); probabilistic early expiry (XFetch) has one request refresh slightly before expiry so the key is rarely cold; and stale-while-revalidate serves the stale value while one background refresh runs, so nobody blocks. A senior often layers single-flight plus SWR." },
    { q: "When do you reach for a validator (ETag/Last-Modified) versus a freshness directive (max-age/s-maxage)?", a: "They solve different costs and compose together. A freshness directive (max-age, s-maxage) lets a cache serve a local copy with zero round-trip while it is fresh — it saves latency and origin load. A validator (ETag or Last-Modified) governs what happens at revalidation: when the cache must check, it sends a conditional request (If-None-Match / If-Modified-Since) and the origin answers 304 Not Modified with no body if nothing changed — saving bandwidth and the cost of regenerating the payload, but still paying one round-trip. So you use freshness to avoid the request entirely, and a validator to make the unavoidable revalidation cheap. The strong combination for a rarely-changing API read is s-maxage for the local hit, an ETag for cheap 304 revalidation, and stale-while-revalidate so the post-expiry refresh does not block a reader." },

A robust stack uses both — for example public, s-maxage=60, stale-while-revalidate=300, stale-if-error=86400 — so it is fast on the happy path and survives an outage. <Recap lang="en">
If you reconstructed each answer from memory, you hold the track's spine as one design: assign each layer its owned data, shrink freshness outward (or purge the outer layer on every inner change), defend a hot-key expiry with single-flight plus SWR, use freshness directives to skip the request and validators to make the unavoidable revalidation a cheap 304, layer stale-while-revalidate for the happy path with stale-if-error for outages, and wire invalidation into the write path so it propagates Redis → proxy → CDN in order. The capstone skill is composing these into a strategy that holds under real traffic — not memorising any one directive. Now when you sit down to design caching for a new service, you will start with the ownership map — not with TTL numbers.
</Recap>
