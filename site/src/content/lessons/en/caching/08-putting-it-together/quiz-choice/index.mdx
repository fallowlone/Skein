  question="A request passes through CDN, reverse proxy, Redis, and the DB. An editor changes a product, the write path updates the DB and deletes the Redis key, but users still see the old price for an hour. Where is the bug?"

  question="You set the CDN to s-maxage=3600 but the app revalidates its Redis fragment every 60s. Why is this a composition bug regardless of which numbers are correct individually?"
  choices={[
    { label: "The outer freshness window is longer than the inner one, so for up to an hour the edge serves a version the app already considers dead. Freshness must shrink outward, or every inner change must explicitly purge the outer layer.", correct: true },
    { label: "It is fine — Redis is the source of truth, so its 60s window governs what users see.", misconception: "Redis is not the source of truth, and even if it were, an inner refresh is invisible to an outer cache. The CDN serves its own copy for the full 3600s irrespective of Redis." },
    { label: "It is fine because s-maxage only affects browsers, which revalidate quickly anyway.", misconception: "s-maxage is precisely the directive shared caches like the CDN obey; max-age targets the private browser cache. The CDN honours the 3600s." },
    { label: "The bug is only that 3600 is too large; halving both numbers fixes the composition.", misconception: "Shrinking both equally keeps the outer window larger-or-equal than the inner, so the same stale-serving gap remains.   ]}

  lessonSlug="08-putting-it-together"
  lang="en"
  question="A hot key with thousands of concurrent readers expires. You can add (a) a per-key mutex so one request recomputes while the rest wait, or (b) stale-while-revalidate. A senior usually reaches for SWR first. Why?"
  choices={[
    { label: "SWR serves the stale value instantly to every reader and revalidates once in the background, so nobody waits — it removes the latency cliff entirely. A mutex still blocks the waiters until the single recompute finishes.", correct: true },
    { label: "A mutex risks deadlock, so it must always be avoided.", misconception: "A scoped per-key lock with a timeout does not deadlock; single-flight is a sound stampede defence. The reason to prefer SWR is latency, not safety — the mutex makes waiters block, SWR does not." },
    { label: "SWR guarantees readers never see stale data, so it is strictly more correct.", misconception: "The opposite: SWR's whole mechanism is serving a stale copy while it revalidates. You choose it when bounded staleness is acceptable; a mutex is right when readers must see the recomputed value." },
    { label: "A mutex does nothing to protect the origin under a stampede.", misconception: "A mutex (single-flight) is exactly an origin-protection mechanism — it collapses N misses into one recompute. Both protect origin; they differ in whether waiters block." },
  ]}

  question="A public API read costs 40ms to compute and changes rarely. You want low latency, low origin load, and bandwidth savings on the wire. Which combination composes these correctly?"
  choices={[
    { label: "s-maxage at the edge for shared caching + an ETag so revalidations return 304 with no body + stale-while-revalidate so an expired entry serves instantly while it refreshes. Each layer solves a different cost.", correct: true },
    { label: "A long max-age only — once cached, nothing else is needed.", misconception: "max-age alone gives no graceful expiry (no SWR, so the first reader after expiry eats the 40ms) and no cheap revalidation (no ETag, so every revalidation ships the full body).     { label: "no-store plus a server-side Redis cache, to keep HTTP caches out of the path.", misconception: "no-store forbids the edge and browser from caching, throwing away the cheapest wins (zero-RTT browser hits, edge offload, 304s).     { label: "ETag alone — conditional requests make the other directives redundant.", misconception: "An ETag still requires a round-trip per request to get the 304; without s-maxage there is no local hit, and without SWR the revalidation is synchronous.   ]}

<Recap lang="en">
The track's through-line is one composed strategy: assign each layer the data it owns, shrink freshness windows outward (or purge the outer layer on every inner change), protect the origin on a hot-key expiry with single-flight or SWR, save bandwidth with ETag-driven 304s, scope per-user responses with private/no-store, wire invalidation into the write path so it propagates Redis → proxy → CDN in order, and fail open with stale-if-error tuned per resource. No single directive is the answer; the answer is how the layers compose. Now when you face a real caching incident — stale content, a data leak, or an origin pileup — you have a checklist: which layer owns this data, which TTL is longest, and which write-path step was skipped.
</Recap>
