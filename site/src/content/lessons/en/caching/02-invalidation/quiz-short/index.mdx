    { q: "Walk through the set-after-delete race step by step, and name the three ways to close it in rising order of cost.", a: "A reader gets a cache miss and reads the old row from the DB (say name='Ann'). Before it writes that back, a writer updates the DB to 'Bob' and issues DEL on the key. The reader — still holding the stale 'Ann' it read milliseconds ago — then SETs the cache to 'Ann', silently undoing the delete. The cache now disagrees with the DB until the TTL expires, and it is hard to reproduce because it needs two requests racing within a few ms. Three fixes by cost: (1) delayed double-delete — DEL, then a second DEL a few hundred ms later to wipe any in-flight reader's stale SET; cheap and probabilistic. (2) Leases — on a miss the reader gets a token that a DEL invalidates, so a stale SET after the delete is rejected (Facebook's memcache; also cut their hot-key load from ~17K to ~1.3K qps). (3) Write-through — funnel writes through the cache so there is no reader-populated SET to race at all." },
    { q: "Why keep a TTL even when you actively invalidate on every write, and what is the dual-write problem?", a: "Active invalidation is a dual-write: the DB commit and the cache DEL are two operations with no transaction across them, so either can succeed while the other fails — a dropped packet, a Redis hiccup, or a crash between the two leaves the DB fresh and the cache stale. With no other mechanism, that missed purge serves the old value forever. The TTL is the backstop: it bounds how long any missed purge can stay wrong, turning a permanent inconsistency into a bounded one. So even a fully event-driven cache keeps a TTL as defence-in-depth for the purge that silently fails." },
    { q: "What is the thundering herd from synchronized TTL expiry, and how do jitter and probabilistic early refresh defuse it?", a: "If many servers cache the same hot key with an identical TTL and warm it in the same window (e.g. a deploy), they all expire it within the same narrow window. At expiry every one of them misses simultaneously and slams the origin in lockstep — the thundering herd / cache stampede, a sharp load spike. TTL jitter sets each entry to a random value around the target (e.g. ±10%, 270–330s), scattering expiries across a band so the origin sees a smooth ramp and a single rebuild serves the rest. Probabilistic early refresh goes further: as an entry nears expiry, each read has a small, rising chance of refreshing it early, turning the sharp spike into a gentle ramp and often rebuilding before anything actually expires." },
    { q: "Why delete the cache key on write rather than update it with the new value?", a: "DEL is idempotent and order-independent; a value-SET is not. With two concurrent writers, their cache writes can arrive in the opposite order from their DB commits — W1 to 'Bob', W2 to 'Carol' — leaving the cache on 'Bob' while the DB settles on 'Carol', a permanent disagreement. A DEL has no value to get out of order: whoever reads next repopulates from the now-settled DB. So delete-on-write sidesteps the writer-vs-writer ordering hazard that updates create. It does not, however, close the set-after-delete race against a concurrent reader — that still needs double-delete, leases, or write-through." },

Write-behind / write-back writes the cache now and queues the DB write asynchronously: fast writes and write coalescing under bursts, but a durability window — if the node dies before the flush, a committed-looking write is lost, so it is for tolerant data (counters, metrics) or paired with a durable queue. Write-around writes the DB only and lets reads populate later: good when written data is rarely read soon, but it breaks read-your-writes because the writer's own next read is a guaranteed miss-then-stale-until-populated." },
