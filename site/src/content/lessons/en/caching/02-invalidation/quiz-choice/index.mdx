  lang="en"
  question="Why is deleting the cache key on write the senior reflex, rather than updating it with the new value?"
  choices={[
    { label: "DEL is idempotent and order-independent, so two writers racing to invalidate cannot leave a half-merged value the way two concurrent SETs can — whoever reads next repopulates from the now-settled DB.", correct: true },
    { label: "DEL is faster than SET, so it reduces write latency on the hot path.", misconception: "The difference is correctness, not speed. DEL avoids an ordering hazard: two value-writes can land cache-first in the opposite order from their DB commits, leaving the cache permanently disagreeing with the DB." },
    { label: "Updating the key keeps it warm, which is always preferable for hit rate.", misconception: "Keeping it warm is a hit-rate argument, not a correctness one. Updating reintroduces the write-ordering race that delete-then-repopulate sidesteps." },
    { label: "DEL closes the set-after-delete race entirely, so no further mitigation is needed.", misconception: "DEL avoids writer-vs-writer ordering bugs, but it does NOT close the set-after-delete race against a concurrent reader — that still needs double-delete, leases, or write-through." },
  ]}
/>

  choices={[

    { label: "Nothing — if every write purges, the cache and DB can never diverge.", misconception: "They can diverge whenever the DEL fails but the DB commit succeeds. The DB and cache are two systems with no shared transaction, so the purge is not guaranteed." },

    { label: "Memory grows unbounded because keys are never evicted.", misconception: "Eviction policy (LRU/LFU) handles memory pressure independently. The reason to keep a TTL here is to bound the damage of a purge that silently failed." },

<Quiz
  id="02-invalidation-choice-5"
  lessonSlug="02-invalidation"
  lang="en"
  question="A user edits their own profile and must immediately see the new value (read-your-writes required). Which write strategy holds with the least racing risk?"
  choices={[
    { label: "Write-through — write cache and DB synchronously in the same call. The writer's own next read hits an entry that already reflects the write, with no reader-populated stale SET to race against.", correct: true },
    { label: "Write-around — write the DB only and let reads repopulate the cache later.", misconception: "Write-around is the worst choice here: the writer's own next read is a guaranteed miss, and any lingering stale entry serves the old value. It is for data rarely read soon after writing — the opposite case." },
    { label: "Write-behind — write the cache now and flush the DB asynchronously.", misconception: "It is read-your-writes-friendly on the cache, but it opens a durability window: if the node dies before the async flush, the committed-looking edit is lost.     { label: "Cache-aside with delete-on-write — update DB, DEL the key.", misconception: "Usually fine, but exposed to the set-after-delete race, so the writer can still see their old profile. It needs delayed double-delete or leases before it is safe for strict read-your-writes." },
  ]}
/>

<Recap lang="en">
The through-line is one sentence: invalidation is choosing which staleness you ship. TTL is the cheap floor — bounded but prone to synchronized stampedes you defuse with jitter. Event-driven purge cuts staleness to the write but is a dual-write, so you keep a TTL as the backstop for every missed DEL. Delete beats update because it is idempotent and order-independent, but it still races with a concurrent reader — the set-after-delete race — closed by delayed double-delete, by leases (which also slashed Facebook's hot-key load), or by funneling writes through the cache. And the write strategy you pick is a read-your-writes decision: write-through holds it, write-around breaks it, write-behind risks durability.
</Recap>
