Without a cache the DB sees, say, 5,000 RPS evenly and can be sized for it. With a 60 s TTL the DB sees near-zero for 59 seconds, then the full 5,000 RPS in the one-second window after the hot key expires and every concurrent request misses at once. Total work drops, but peak concurrency at the boundary equals the full unfiltered traffic rate — and the DB was provisioned for cached steady-state, not that one-second spike. So every stampede mitigation is about bounding how many callers rebuild simultaneously, not about reducing volume. Raising the TTL only moves the burst in time; it does not remove it." },
    { q: "Contrast in-process single-flight with a Redis distributed lock: what each bounds, what each costs, and the order to apply them.", a: "Single-flight lives in one process's memory: an O(1) map of key to in-flight promise. The first miss starts the rebuild and registers the promise; every concurrent miss on the same key subscribes to it instead of starting its own. It collapses the per-process herd to one at zero network cost — but a 50-node fleet still runs 50 rebuilds because each node has its own map. A Redis SETNX lock (SET lock:key uuid EX N NX) coordinates across the whole fleet: exactly one holder rebuilds, others wait and re-check or take a stale fallback. It costs a round-trip per acquire. Apply single-flight first (free, per-node), then the lock second (shared, cross-node): 100,000 misses become 50 (single-flight), then 1 (lock)." },
    { q: "How does XFetch achieve 'expected exactly one early refresh per TTL window' with no coordination, and when does it fail?", a: "Each read evaluates -beta * delta * ln(rand()) >= time_to_expire, where delta is the typical rebuild duration. The probability is near zero far from expiry and climbs steeply in the final seconds, so some reader fires an early rebuild while everyone else keeps hitting the still-valid value. The expected count is one because the minimum of N independent exponential draws is itself exponential with rate N times lambda: as the fleet grows, the winning reader fires sooner, but the total stays ~1 — no coordination, just one random number per read. It fails on cold or sporadic keys: if a key is read once every 30 s with a 60 s TTL, the narrow early-refresh window may pass with zero reads, so the key expires normally and stampedes. Use a lock or SWR for those." },
    { q: "What does stale-while-revalidate guarantee at a TTL boundary, what does it trade away, and how does CDN request coalescing extend it?", a: "SWR (RFC 5861) returns the expired cached value immediately to every request within the stale window while queuing exactly one background refresh. User wait at the boundary drops to zero and DB load drops to one rebuild query — no request blocks on the rebuild. The trade-off is explicit bounded staleness: readers see data up to the stale-while-revalidate duration old, which is fine for content, news, and listings but wrong for account balances, vote counts, or anything two users must see consistently. CDN request coalescing (Cloudflare) / collapsing (Fastly) extends the same idea at the edge: while one upstream fetch for a path is in flight, all other concurrent misses for that path attach to it, so a viral event with millions of viewers produces one origin fetch, not millions." },
    { q: "What is negative caching, and what attack does its absence enable?", a: "Negative caching stores a short-TTL sentinel for 'no such row' so that repeated lookups of a non-existent key are answered from the cache instead of hitting the DB every time. Without it, every request for a missing key is a fresh miss that reaches the DB — and positive-key protections (single-flight, locks) never engage because each lookup is for a different non-existent key, so there is nothing to coalesce. An attacker exploits this by minting endless random non-existent IDs (random UUIDs in a path), turning a normal request rate into a full-rate DB flood — a documented miss-storm amplification pattern. Fix: cache the missing sentinel with a short TTL (5–30 s) and invalidate it on real insert. Keep the negative TTL short to bound memory churn." },
    { q: "Describe the metastable failure that can follow an unmitigated stampede and why the system cannot self-recover.", a: "The stampede saturates the DB; queries queue past the client timeout and time out; clients retry (most SDKs retry on timeout with short backoff, mistaking overload for a transient network blip). Retries multiply the herd — 10,000 misses become 30,000 in-flight — so the DB now serves retries instead of fresh queries, and the cache cannot rebuild because the DB never answers fast enough. An empty cache means every new arrival also misses and retries. The system has two stable states, healthy and storm, and the perturbation moved it to storm; each component is following correct local behaviour, so none can break the loop alone. Recovery requires an external kill signal: 503-on-overload at the gateway (clients back off long), a circuit-breaker that serves stale and stops depending on the DB, or manually seeding known-good values into the cache." },
