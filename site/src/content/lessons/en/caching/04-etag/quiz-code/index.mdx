## Exchange 1 — the revalidation handshake

```http
# First fetch
GET /api/config HTTP/1.1
Host: api.example.com

HTTP/1.1 200 OK
ETag: "a3f5c901"
Content-Length: 8192
... 8 KB JSON body ...

# 30s later, content unchanged
GET /api/config HTTP/1.1
Host: api.example.com
If-None-Match: "a3f5c901"
```

  question="The content has not changed since the first fetch. What does the server return to the second request, and what crosses the wire?"
  choices={[
    { label: "304 Not Modified with an empty body and refreshed headers (~200 bytes). The 8 KB body is saved, but the request and its round-trip still happened.", correct: true },
    { label: "200 OK with the full 8 KB body, so the client can confirm the bytes match.", misconception: "A match means the client already holds the current version; re-sending the body is exactly what conditional requests exist to avoid." },
    { label: "204 No Content, since there is no new body to send.", misconception: "204 means the request succeeded with no content to return at all; revalidation has its own dedicated status, 304 Not Modified, which tells the client to reuse its cached copy." },
    { label: "Nothing — the server holds the connection open until the config changes.", misconception: "That is long-polling, a different mechanism. A conditional GET completes immediately with 200 or 304." },
  ]}
/>

## Exchange 2 — weak tag, strong precondition

```http
GET /report.html HTTP/1.1
Host: cdn.example.com
If-None-Match: "v42"

# server's current validator for this resource:
#   ETag: W/"v42"
```

<Quiz
  id="04-etag-code-2"
  lessonSlug="04-etag"
  lang="en"
  question="The client sent the strong tag in If-None-Match; the server currently holds the weak form of the same value. What status comes back?"
  choices={[
    { label: "304 Not Modified — If-None-Match uses the weak comparison algorithm, which ignores the W/ prefix, so the values match and revalidation succeeds.", correct: true },
    { label: "200 OK — the strong and weak forms are distinct tokens and cannot match.", misconception: "For If-None-Match the comparison is weak by definition; the W/ prefix is disregarded, so the tags match and the server sends 304." },
    { label: "412 Precondition Failed — a strong/weak mismatch is a precondition error.", misconception: "412 applies to If-Match preconditions on writes; for If-None-Match the weak comparison succeeds here, giving 304, not an error." },
    { label: "400 Bad Request — you cannot mix strong and weak forms in one exchange.", misconception: "Mixing forms is well-defined: If-None-Match always compares weakly, so this is a valid 304, not a protocol error." },
  ]}
/>

## Exchange 3 — resuming a download

```http
GET /video.mp4 HTTP/1.1
Host: media.example.com
Range: bytes=1000000-
If-Range: W/"clip-build-9"

# server's current validator:
#   ETag: W/"clip-build-9"
```

<Quiz
  id="04-etag-code-3"
  lessonSlug="04-etag"
  lang="en"
  question="The client is resuming a download with If-Range carrying a weak validator that matches the server's current weak ETag. What does the server return?"
  choices={[
    { label: "200 OK with the full resource — If-Range requires a strong validator, and a weak one is not allowed to authorise a partial response, so the server safely refuses the range and resends everything.", correct: true },
    { label: "206 Partial Content from byte 1,000,000 — the validators match, so the range is served.", misconception: "If-Range demands byte-for-byte identity; a weak validator only promises semantic equivalence and cannot guarantee the existing partial bytes line up, so the range is refused and a full 200 is sent." },
    { label: "304 Not Modified — the ETags match, so nothing needs to be sent.", misconception: "If-Range never produces 304; it chooses between a 206 partial response (strong validator matches) and a full 200. A weak validator forces the full 200." },
    { label: "416 Range Not Satisfiable — the weak ETag makes the range invalid.", misconception: "416 is for ranges outside the resource bounds. Here the range is valid; the weak validator simply downgrades the response to a full 200, not an error." },
  ]}
/>

## Exchange 4 — the per-node regression

```http
# Request lands on pod A, which minted the client's cached tag
GET /api/config HTTP/1.1
If-None-Match: "pod-a-counter-7"

HTTP/1.1 304 Not Modified

# Next poll round-robins to pod B
GET /api/config HTTP/1.1
If-None-Match: "pod-a-counter-7"

HTTP/1.1 200 OK
ETag: "pod-b-counter-3"
Content-Length: 8192
```

<Quiz
  id="04-etag-code-4"
  lessonSlug="04-etag"
  lang="en"
  question="Identical config content, yet pod A returns 304 and pod B returns 200 for the same If-None-Match. What is broken, and what is the highest-leverage fix?"
  choices={[
    { label: "Each pod derives the ETag from a per-process counter, so the same content yields a different token per node and no client matches across pods. Fix: derive the ETag purely from the content — a version/updated_at column or a content hash — so every pod computes the same token.", correct: true },
    { label: "Pod B is serving stale content; restart it to resync.", misconception: "The content is identical — pod B sends the same 8 KB body. The defect is the token derivation being node-local, not stale data, so restarting changes nothing." },
    { label: "The load balancer should pin each client to one pod with sticky sessions.", misconception: "Sticky sessions are a workaround that masks the real bug and breaks the moment a pod is replaced. The fix is a content-derived ETag, which makes revalidation correct regardless of which pod answers." },
    { label: "Raise Cache-Control max-age so the client stops revalidating.", misconception: "That hides the symptom by skipping revalidation, but stale config will now be served past its change. The root cause — inconsistent per-node tokens — still needs a content-derived ETag." },
  ]}
/>

<Recap lang="en">
Every ETag incident is read in the exchange: a matching If-None-Match returns 304 with an empty body but still costs the round-trip; If-None-Match compares weakly, so W/ and strong forms of the same value match; If-Range is the one place that demands a strong validator, so a weak tag forces a full 200 instead of a 206; and when identical content yields different tokens on different pods, the bug is a node-local ETag — fix it by deriving the tag from the content, not the box.
</Recap>
