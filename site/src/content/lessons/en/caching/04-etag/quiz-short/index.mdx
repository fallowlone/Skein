    { q: "A teammate says ETags make repeat requests free. Correct them precisely: what does a 304 save, and what does it still cost?", a: "A 304 saves the response body and nothing else. The client still sends the conditional request and waits for the answer, so the full round-trip latency is paid every time — at an 80 ms RTT, a 304 poll still costs 80 ms. What disappears is the download: an 8 KB JSON body becomes ~200 bytes of headers, and a 2 MB image transfers zero bytes on revalidation. So ETags are a bandwidth-and-download-time optimisation, not a latency one. They are not free on the server either: to answer a conditional request the origin must know the current ETag, which usually means reading or recomputing the resource just to compare and discard the body — the CPU-vs-bandwidth tradeoff. The way to skip the request entirely is freshness (Cache-Control max-age); the ETag is the fallback after freshness expires." },
    { q: "Walk through the conditional-request handshake end to end, naming the headers and statuses.", a: "On the first response the server attaches ETag — an opaque token identifying this exact version of the body, e.g. ETag: \"a3f5c901\". The client caches the body and stores the token next to it. On the next request it echoes the token in If-None-Match: \"a3f5c901\", which means 'give me this only if it changed'. The server recomputes or looks up the current ETag and compares: on a match it replies 304 Not Modified with no body and refreshed headers, and the client serves its cached copy; on a mismatch it replies 200 OK with the full new body and a new ETag. The token is opaque on purpose — only the origin that minted it interprets it, so you can change your ETag scheme without touching any client." },
    { q: "Explain strong vs weak validators and where the distinction actually matters.", a: "A strong validator (ETag: \"x\") promises byte-for-byte identity: two strong ETags match only if the representations are exactly equal. A weak validator (ETag: W/\"x\") promises only semantic equivalence — the resource is 'the same enough' to reuse despite trivial differences like a timestamp comment. The subtlety is that If-None-Match always uses the weak comparison algorithm, so for plain revalidation W/\"x\" and \"x\" are treated as a match and the W/ prefix is ignored. The distinction only bites where byte-exactness is mandatory — range requests via If-Range, where resuming a download needs the exact same bytes. There a weak validator is refused and the server resends the whole resource with 200." },
    { q: "Compare ETag and Last-Modified. When is Last-Modified not enough, and why?", a: "Last-Modified / If-Modified-Since is a timestamp-based validator, cheap to compute (a stat on a file), and it still works. Its hard limit is that HTTP dates have one-second resolution: if a resource changes twice within the same second — common for hot config, generated files, or high-write rows — Last-Modified cannot tell the two versions apart, and the client can be served a stale 304. ETags have no such blind spot: a content hash or version counter changes on every real change regardless of timing. The senior default is that when both are present, ETags take precedence and clients prefer If-None-Match; many servers emit both so timestamp-only caches still get some revalidation while ETag-aware clients get the precise one." },
    { q: "Why does adding a second and third server commonly kill 304s, and how do you make ETags load-balancer-safe?", a: "The whole contract is that identical content produces an identical ETag no matter which node answers. The moment the token depends on something local to one server, that breaks. Classic offenders: Apache's old inode-based FileETag (identical files have different inodes per machine), mtime that drifts because deploys copy files at slightly different times to each replica, and per-process state like a counter, salt, or startup timestamp baked into the token. Behind a round-robin LB the client's If-None-Match was minted by pod A but the next request lands on pod B, whose token differs, so it is always a mismatch — clean 200s forever while caching looks on. The fix is to derive the ETag purely from the content: a version or updated_at column, a content hash, or FileETag MTime Size with inode removed." },
    { q: "How does compression interact with a strong ETag, and what is the trap?", a: "The gzipped and identity representations of a resource are different byte streams, so a strong ETag — which promises byte identity — must differ between them. The trap appears when a proxy starts compressing on the fly: if it reuses one strong tag across both encodings, a client that fetched the gzipped 200 could later revalidate, land on a node serving identity, and the byte-exact If-Range semantics break. The correct behaviour is to vary the strong ETag per content-encoding (or weaken it when on-the-fly compression makes byte-exactness unenforceable), and to remember that a compression layer added between deploys can silently invalidate every cached validator at once." },
