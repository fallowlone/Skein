## Snippet 1 — the response header

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, no-store
```

## Snippet 2 — the trace headers

```http
HTTP/1.1 200 OK
Age: 240
Cache-Control: public, max-age=300
CF-Cache-Status: HIT
X-Cache: MISS from reverse-proxy
```

<Quiz
  id="01-layers-code-2"
  lessonSlug="01-layers"
  lang="en"
  question="A user reports stale data 4 minutes after a write. Reading these headers from the same response, what do you conclude?"
  choices={[
    { label: "The CDN is serving a cached copy (CF-Cache-Status: HIT) that is Age 240s old, within its 300s max-age, so the write never reached it — the CDN was not purged. The reverse proxy missed and went upstream, but the CDN short-circuited before that. Fix: purge the CDN on write (or shorten/standardize the TTL), since two layers are caching the same response.", correct: true },
    { label: "The reverse-proxy MISS proves the origin is serving stale data.", misconception: "A proxy MISS means the proxy went upstream — but the CDN HIT in front of it short-circuited the request first, so the origin response was never used. The stale copy is the CDN's, not the origin's." },
    { label: "Age: 240 means the data is fresh because it is under max-age=300.", misconception: "Being within max-age is exactly why the CDN still serves it — that is the problem. The entry is 'fresh' by TTL but stale by data because the write did not purge it. TTL freshness is not data freshness." },
    { label: "CF-Cache-Status and X-Cache contradict each other, so the headers are unreliable.", misconception: "They describe two different layers — the CDN HIT and the reverse-proxy MISS — and are consistent: the request hit the CDN and never reached the proxy's upstream. Reading them per-layer is exactly how you locate the lying copy." },
  ]}
/>

## Snippet 3 — the layered hit/miss path

```
client → CDN edge → reverse proxy → app (Redis) → Postgres
         miss        miss            HIT (Redis)   —
```

  lang="en"
  question="A request misses the CDN and the reverse proxy but hits Redis at the app layer. For an in-region setup, what is the rough latency story, and what does it tell you?"
  choices={[

If most traffic looks like this, the CDN/proxy layers are not earning their place for this endpoint and should be reconsidered.", correct: true },
    { label: "A Redis HIT means every layer above it also served from cache.", misconception: "The trace shows the opposite: CDN and proxy both missed and forwarded. A hit deep in the stack means every layer above it added a miss hop. Layers do not share state — each is checked and forwards on a miss." },
    { label: "The two misses mean the cache is broken and should be removed entirely.", misconception: "A miss is normal cache behaviour, not breakage — it just means those upper layers do not hold this key. The signal is whether the hit ratio at each layer justifies keeping it for this traffic, not that caching failed." },
    { label: "Postgres was queried, so Redis did not actually help.", misconception: "The trace ends at the Redis HIT — Postgres (—) was not queried. Redis saved the DB round trip on this request; the question is whether the CDN and proxy above it are pulling their weight." },
  ]}

## Snippet 4 — stale-while-revalidate

```http
Cache-Control: public, max-age=60, stale-while-revalidate=600
```

<Quiz
  id="01-layers-code-4"
  lessonSlug="01-layers"
  lang="en"
  question="A high-traffic, slightly-stale-tolerant feed switches to this directive and p99 drops sharply with no rise in origin load spikes. Why does it work?"
  choices={[
    { label: "For the first 60s the entry is fresh and served instantly. From 60s to 660s it is stale-but-usable: the cache serves the stale copy immediately AND revalidates in the background, so no user waits on the origin and the origin sees a smooth trickle of revalidations instead of a thundering herd at expiry. Ideal for read-heavy, staleness-tolerant data.", correct: true },
    { label: "It disables caching after 60s, forcing fresh fetches.", misconception: "The opposite — stale-while-revalidate extends usability for 600s past max-age by serving the stale copy while refreshing in the background. Nothing is forced to wait on a fresh fetch within that window." },
    { label: "It makes the data always fresh by revalidating on every request.", misconception: "It does not revalidate on every request — it serves the stale copy immediately and revalidates asynchronously. The data is intentionally slightly stale; that staleness tolerance is what buys the latency win." },
    { label: "It only helps because it lowers max-age to 60.", misconception: "max-age=60 alone would cause a synchronous origin fetch (and a possible herd) at every expiry. The win is the stale-while-revalidate window decoupling user latency from revalidation — not the max-age value." },
  ]}
/>

<Recap lang="en">
Cache behaviour is read in headers and traces. Cache-Control directives decide which layers may store a response — no-store forbids all, private forbids shared caches like the CDN — so a personalized endpoint correctly shows a 0% CDN hit ratio. Per-layer trace headers (CF-Cache-Status, X-Cache, Age) let you walk the stack and find which copy is stale: a CDN HIT within max-age that survived a write means the CDN was not purged. A hit deep in the stack means every layer above it added a miss hop, so confirm each layer earns its place. Now when you get a stale-cache report, you know the first thing to do is read the trace headers — not touch a TTL.
</Recap>
