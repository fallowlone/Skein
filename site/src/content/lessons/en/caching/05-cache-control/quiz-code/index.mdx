## Snippet 1 — the "secure" endpoint

```http
GET /api/account/balance HTTP/1.1

200 OK
Cache-Control: no-cache
Content-Type: application/json
```

    { label: "Add s-maxage=0 to keep the CDN from caching it.", misconception: "s-maxage=0 still permits storage and only forces shared-cache revalidation; it also says nothing about the browser. The correct exclusion for per-user data is private, no-store." },

## Snippet 2 — HTML behind a CDN

```http
200 OK
Cache-Control: public, max-age=31536000
Content-Type: text/html; charset=utf-8
```

<Quiz

  lessonSlug="05-cache-control"
  lang="en"
  question="This header is on the site's index.html, served through a CDN. What goes wrong, and what is the correct header for HTML that references content-hashed assets?"
  choices={[
    { label: "Both browser and CDN cache the HTML for a year, so deploys are invisible — visitors keep loading the old document and its old asset URLs for up to a year. HTML should be no-cache (or max-age=0, must-revalidate) so it always picks up new hashed asset URLs.", correct: true },
    { label: "It is fine — the CDN purge on deploy handles freshness.", misconception: "A CDN purge cannot reach a browser holding the HTML for a year; that client keeps the stale document. HTML must be revalidated by the browser, so it should not carry a year-long max-age." },
    { label: "Only the CDN caches it; the browser revalidates HTML automatically.", misconception: "Browsers honor max-age for HTML just like any resource; max-age=31536000 makes the browser hold it a year too. There is no automatic HTML revalidation when max-age is large." },
    { label: "Add immutable so the browser stops revalidating and the problem goes away.", misconception: "immutable makes it worse — it tells the browser to never revalidate even on reload, freezing the stale HTML harder. The rule is to hash assets, never the HTML." },
  ]}
/>

## Snippet 3 — no-cache vs no-store, side by side

```http
# Response A
Cache-Control: no-cache, private
ETag: "v9"

# Response B
Cache-Control: no-store
```

    { label: "Swap them: no-store on search wastes bandwidth, no-cache on reset is fine.", misconception: "no-cache on the reset page permits storage and only requires revalidation — the sensitive page would still be stored and in bfcache. no-store is required for the reset page; A's revalidation is exactly right for cheap, non-sensitive search results." },
    { label: "Response A is wrong because no-cache means it is never reused.", misconception: "no-cache means revalidate before reuse, not never reuse.     { label: "Both should be no-store for safety.", misconception: "no-store on the search page throws away all caching for non-sensitive content that revalidates cheaply, hurting performance for no security gain. Match the directive to the data: no-store only where storage itself is the risk." },
  ]}

## Snippet 4 — the CDN response line

```http
200 OK
Cache-Control: max-age=60, s-maxage=300, stale-while-revalidate=3600
Age: 420
CF-Cache-Status: HIT
```

<Quiz
  id="05-cache-control-code-4"
  lessonSlug="05-cache-control"
  lang="en"
  question="The CDN returns this for a JSON API. Age=420 exceeds s-maxage=300, yet it is a HIT. Is this correct, and what is the client getting?"
  choices={[
    { label: "Correct. At Age 420 the copy is past s-maxage=300 (stale) but within the 3600s stale-while-revalidate window, so the CDN serves the stale copy instantly as a HIT and refreshes in the background. The client gets a fast, slightly-stale response by design.", correct: true },
    { label: "It is a bug — a stale copy (Age greater than s-maxage) must never be a HIT.", misconception: "stale-while-revalidate explicitly authorizes serving stale within its window and counting it as a HIT while a background revalidate runs. That is the feature, not a bug." },
    { label: "Age=420 means the browser will reject it because it exceeds max-age=60.", misconception: "max-age=60 is the browser's freshness; the CDN copy is governed by s-maxage. Whether the browser revalidates depends on what the CDN returns now, but the CDN HIT here is valid under stale-while-revalidate." },
    { label: "CF-Cache-Status: HIT proves the response is fresh.", misconception: "HIT means served from cache, not that it is fresh. Under stale-while-revalidate a stale copy is served as a HIT; freshness is determined by Age vs s-maxage, which here says stale-but-serveable." },
  ]}
/>

<Recap lang="en">
Every caching bug is read from headers. no-cache without an ETag on per-user data is a stored, inefficiently-revalidated leak — ship private, no-store instead. A year-long max-age on HTML freezes deploys, because the rule is to hash assets and keep HTML revalidating. no-cache plus an ETag is the right choice for cheap, non-sensitive content that reuses via 304; no-store is for data that must never be stored at all. And a CDN HIT with Age past s-maxage is correct under stale-while-revalidate — stale-but-instant by design, with a background refresh. Read the directives per tier, match them to the data's sharing and sensitivity, then verify on the wire.
</Recap>
