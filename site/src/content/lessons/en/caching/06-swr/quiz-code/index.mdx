## Snippet 1 — the header timeline

```
Cache-Control: max-age=60, stale-while-revalidate=300, stale-if-error=86400
```

```
t=0s    cached fresh
t=45s   request  -> fresh hit, no origin call
t=150s  request  -> ???
t=600s  request, origin returns 503 -> ???
```

```
key=/catalog  HIT-STALE   revalidate=spawned   origin_inflight=1
key=/catalog  HIT-STALE   revalidate=spawned   origin_inflight=2
key=/catalog  HIT-STALE   revalidate=spawned   origin_inflight=874
...
origin  p99 1.9s -> 41s   5xx_rate 0% -> 12%
```

    { label: "Users are being served errors; add stale-if-error.", misconception: "stale-if-error helps when the origin errors, but it does not stop the edge from spawning hundreds of refreshes that CAUSE the errors. The root fix is coalescing." },

## Snippet 3 — the SWR client config

```js
const { data } = useSWR('/api/quote', fetcher, {
  dedupingInterval: 2000,
  revalidateOnFocus: true,
  revalidateOnReconnect: true,
})
```

    { label: "On focus it shows a spinner and blocks until fresh data arrives.", misconception: "revalidateOnFocus is stale-first: it shows cached data immediately and refreshes in the background. The whole model is no blocking on the refresh." },
    { label: "Two mounts fire two requests because each useSWR has its own cache.", misconception: "SWR's cache is keyed globally by the request key; concurrent calls for the same key inside dedupingInterval are coalesced onto one in-flight request." },
    { label: "It does nothing on focus unless you set revalidateIfStale.", misconception: "revalidateOnFocus: true triggers a revalidation on window focus regardless. That is precisely the trigger described." },

## Snippet 4 — caching an auth check

```
GET /api/permissions/user-42
Cache-Control: max-age=60, stale-while-revalidate=600
```

<Quiz

  lang="en"
  question="This header is applied to a per-user permissions endpoint. What is the defect?"
  choices={[

    { label: "The window is too short; raise stale-while-revalidate so refreshes are cheaper.", misconception: "Lengthening the window makes the security hole WORSE — stale 'allowed' is served even longer. The defect is caching an auth decision with SWR at all." },
    { label: "It is fine because the background refresh eventually corrects the answer.", misconception: "'Eventually' is the problem: between revocation and the next landed refresh, a revoked user is authorized. For access control, eventual is a vulnerability." },
    { label: "Just add stale-if-error so revocations propagate during outages.", misconception: "stale-if-error makes outages serve stale-allowed even longer. No stale-* directive is safe on an authorization decision." },
  ]}

<Recap lang="en">
Every freshness incident is read in a header, a log, or a config. A layered header is three nested windows — fresh, stale-while-revalidate, stale-if-error — and you trace a request by which window its timestamp lands in. An edge log with climbing origin_inflight on one key is the background-refresh herd, fixed by single-flight plus jitter, not a restart. Client config reproduces the model: focus/reconnect revalidation is stale-first, and dedupingInterval coalesces concurrent calls. And no header, anywhere, makes SWR safe on an authorization decision.
</Recap>
