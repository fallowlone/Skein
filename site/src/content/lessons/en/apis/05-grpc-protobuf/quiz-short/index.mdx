    { q: "What exactly does Protobuf put on the wire, and what does that buy and cost versus JSON?", a: "Protobuf serializes only field number, wire type, and value — the field names exist solely in the .proto at compile time and never travel. JSON does the opposite, repeating every key as UTF-8 text in every payload. That single choice makes Protobuf about 4-5x smaller for numeric-heavy data (varints cost one byte for small ints, not their decimal-string length) and 4-10x faster to (de)serialize, because there is no text tokenizing, key-string allocation, or reflection. The cost is the inverse of JSON's superpower: you cannot decode a Protobuf message without its schema — the bytes are meaningless on their own — so payloads are opaque in DevTools and curl, and the size win nearly vanishes for string-heavy data where strings are raw UTF-8 in both formats." },
    { q: "Why is renaming a field free but renumbering or reusing a field number a production disaster?", a: "Because identity on the wire is the field number, not the name. Renaming discount_pct to discountPercent changes only a local source-code label; the number is unchanged, the bytes are identical, and old and new binaries interoperate perfectly. Renumbering 3 to 4 makes every peer still on the old schema decode your new field 4 into whatever they call field 4, and your old field-3 data lands wherever they expect 3 — silent corruption that the compiler can't catch because each side compiled a self-consistent schema. Reusing a deleted number is the same disaster, delayed: a straggler still sending the original number writes the old meaning into the new field. The discipline is add-only evolution: never change or reuse a number, append with fresh numbers, and reserved the number and name of anything you remove." },
    { q: "Explain backward and forward compatibility in Protobuf and the two mechanisms that provide them.", a: "Backward compatibility means new code reads messages written by old code: missing new fields simply take their proto3 defaults (0, empty string, false, empty). Forward compatibility means old code reads messages from new code: unknown field numbers are skipped — the decoder uses the wire type to know how many bytes to step over — and preserved for re-serialization rather than erroring. Together these are what let producers and consumers in a large polyglot system deploy independently, in any order, without a coordinated lockstep release. The two mechanisms are proto3 zero-defaults (for the missing-field direction) and unknown-field skip-and-preserve (for the extra-field direction), and add-only evolution with reserved is what keeps both guarantees intact." },
    { q: "Name the four gRPC call shapes and the deciding question for picking one.", a: "Unary (one request, one response) is the REST-shaped ~95% case. Server streaming (one request, a stream of responses) suits a price feed, a log tail, or server-pushed progress. Client streaming (a stream of requests, one response) suits chunked uploads or telemetry batching. Bidirectional streaming (both sides stream independently over the same call) suits chat, live collaboration, or a long-lived control channel. The deciding question is simply who needs to send more than one message: if only the server does, it's server streaming; if only the client does, client streaming; if both do independently, bidi; if neither, unary. Reaching for bidi when the client only sends an initial subscribe is the common over-engineering smell. All four ride one multiplexed HTTP/2 connection." },
    { q: "How do gRPC deadlines work, and what is the classic confusing failure they cause?", a: "The client sets a deadline (a relative duration carried in metadata, not an absolute wall-clock time, so clock skew is irrelevant) and it propagates down the call chain. When it expires, the RPC is auto-cancelled on both ends, so a slow downstream can't pin server threads or resources forever — skipping deadlines is the most common reason a gRPC mesh cascades into resource exhaustion under partial failure. The classic confusing failure is a DEADLINE_EXCEEDED call that succeeded on the server (the handler ran and committed) but failed at the client (the response arrived too late). The work happened; the caller saw an error. The durable fix is idempotency (idempotency keys / safe retries) plus deadlines sized to real downstream latency, so a timeout never silently double-applies a side effect." },
    { q: "When does gRPC win over REST/JSON, and why can't the browser speak it directly?", a: "gRPC is the right default for internal, service-to-service traffic where you control both ends: a typed contract shared across polyglot services, 4-10x speed/size on hot paths, native streaming, and deadline/cancellation propagation across the call graph — savings that cut real tail latency and CPU in a busy mesh. The browser can't speak native gRPC because it can't control HTTP/2 framing or trailers from JavaScript, so a browser client needs grpc-web plus a translating proxy (Envoy or the framework's own), and grpc-web still can't do client or bidirectional streaming. (Connect-RPC sidesteps some of this by serving unary calls as plain HTTP.) So the senior pattern is gRPC between your own services and human-readable REST/JSON or Connect-RPC at the public, browser-facing edge, where debuggability and zero-proxy reach matter most." },
