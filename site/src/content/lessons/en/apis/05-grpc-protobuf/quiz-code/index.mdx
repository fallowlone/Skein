## Snippet 1 — the field-tag diff

```diff
 message Order {
   string id = 1;
   int64 amount_cents = 2;
-  int32 discount_pct = 3;
-  Priority priority = 4;
+  Priority priority = 3;
+  Coupon coupon = 4;
 }
```

    { label: "It reads the old priority bytes into coupon (now field 4) and finds priority empty (field 3, formerly discount_pct).     { label: "It reads everything correctly — protobuf matches the old priority to the new priority by field name.", misconception: "Names never travel on the wire; only numbers do. The old priority bytes are tagged 4, and field 4 is now coupon, so the value is decoded as a coupon." },
    { label: "It errors on decode because field 3 changed type from int32 to Priority.", misconception: "Decoding does not compare against the old type — it reads the wire bytes against the current schema. There is no type-mismatch error here, just a value steered into the wrong field." },
    { label: "It is safe because all four numbers (1-4) still exist in the message.", misconception: "Reusing the same numbers for different fields is the trap, not the safeguard. Wire compatibility is per-number identity, not per-number existence." },

## Snippet 2 — the removal

```proto
message Customer {
  reserved 2, 5 to 7;
  reserved "email", "legacy_tier";
  string id = 1;
  string display_name = 3;
  Address address = 8;
}
```

  lessonSlug="05-grpc-protobuf"
  lang="en"
  question="A new field is proposed: add `string email = 2;` back, because the team wants email again. Does this compile, and is it the right move?"
  choices={[
    { label: "It fails to compile — 2 and the name email are both reserved, which is exactly the point: it blocks the team from re-poisoning a number old peers may still send. Add email with a fresh, never-used number (e.g. 9) instead.", correct: true },
    { label: "It compiles fine; reserved is only documentation and does not prevent reuse.", misconception: "reserved is enforced by protoc — declaring a reserved number or name and then using it is a compile error. That enforcement is the whole reason to reserve on removal." },
    { label: "It compiles because the type matches the original email field, so reuse is safe.", misconception: "Type match is irrelevant; old peers that still send the original field 2 would write into the new email regardless. reserved exists to make this impossible." },
    { label: "It compiles but only if you also remove email from the reserved name list.", misconception: "Editing the reservation away to reuse the number defeats the safety mechanism — that edit is the mistake reserved is meant to stop a reviewer from approving." },
  ]}

## Snippet 3 — the streaming signatures

```proto
service ChatService {
  rpc History(HistoryRequest) returns (stream Message);
  rpc Send(stream Message) returns (SendSummaryResponse);
  rpc Live(stream Message) returns (stream Message);
}
```

<Quiz
  id="05-grpc-protobuf-code-3"
  lessonSlug="05-grpc-protobuf"
  lang="en"
  question="Map each RPC to its call shape and the position of the stream keyword."
  choices={[
    { label: "History is server streaming (stream on the response), Send is client streaming (stream on the request), Live is bidirectional (stream on both). The keyword's side tells you who produces the stream.", correct: true },
    { label: "All three are unary because each has one request type and one response type.", misconception: "The stream keyword changes the shape: stream Message means a sequence of Message, not one. Only an RPC with no stream on either side is unary." },
    { label: "History is client streaming because the stream keyword is on the second type.", misconception: "stream on the return type (the second one) means the server streams responses — server streaming. Client streaming puts stream on the request type." },
    { label: "Live cannot be expressed in a single RPC; bidi needs two separate RPCs.", misconception: "Bidirectional streaming is one RPC with stream on both the request and the response — exactly what Live declares. It rides one multiplexed HTTP/2 stream." },
  ]}
/>

## Snippet 4 — proto3 presence

```proto
message UpdateProfile {
  string user_id = 1;
  string bio = 2;            // plain scalar
  optional bool marketing_opt_in = 3;  // explicit presence
}
```

<Quiz
  id="05-grpc-protobuf-code-4"
  lessonSlug="05-grpc-protobuf"
  lang="en"
  question="A client sends UpdateProfile with bio set to the empty string and marketing_opt_in omitted. The server wants to PATCH only the fields the client actually meant to change. What does the schema let it distinguish?"
  choices={[
    { label: "It cannot tell whether bio was 'cleared to empty' or 'not sent' — a plain scalar defaults to empty with no presence bit. marketing_opt_in is optional, so the server can tell 'omitted' (do not touch) from 'explicitly false'. For PATCH semantics, mark fields optional (or use FieldMask).", correct: true },
    { label: "It can distinguish both — proto3 always tracks whether each field was set on the wire.", misconception: "Plain proto3 scalars have no presence: an empty string is indistinguishable from an unset one. Only optional (or message-typed) fields carry a presence bit." },
    { label: "Neither field can be distinguished, because proto3 dropped presence entirely.", misconception: "proto3 re-added explicit presence via the optional keyword; marketing_opt_in here does carry presence. It is the un-optional bio that cannot be distinguished." },
    { label: "bio being empty means the field was never sent, so the server knows to skip it.", misconception: "An empty-string scalar serializes the same as a defaulted/unsent one — the server cannot infer intent from it. That ambiguity is exactly why PATCH endpoints use optional or a FieldMask." },
  ]}
/>

<Recap lang="en">
Reviewing protobuf is reading numbers, not names: a renumber diff silently steers old values into the wrong field, so evolution must be append-only with reserved guarding removals (and protoc enforces the reservation). A streaming signature is read by which side carries stream — request for client, response for server, both for bidi. And proto3 presence is real but opt-in: plain scalars cannot tell unset from default, so PATCH-style APIs reach for optional or a FieldMask. Catch these at review time, before the corruption deploys.
</Recap>
