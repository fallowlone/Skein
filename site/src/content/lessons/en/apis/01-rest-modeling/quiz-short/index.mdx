The method already names the action, so the URL only needs to name the resource: POST /orders, GET /orders/42. The moment the URL also carries a verb (POST /createOrder, GET /getUserById) you are doing RPC over HTTP with extra steps. You forfeit the uniform interface — every tool, cache, and proxy that reasons about resources by method and path no longer can — and you lose cacheability, because the action is now encoded in a path the cache cannot interpret. Filtering, sorting, and paging are not new endpoints either; they are query parameters on the collection (GET /orders?status=open&sort=-created_at&page=2). Give the two clean patterns and the anti-pattern to avoid.", a: "Pattern one is the guarded action sub-resource: POST /orders/42/cancel. Yes, it is a verb in the URL, but it is scoped to a resource and uses POST honestly, and crucially the server owns the rules — it checks whether the transition is legal and performs the whole thing atomically or rejects it. Stripe and GitHub do exactly this. Pattern two is the transition resource, the 'nounify' trick: model the action itself as a resource with its own lifecycle. A refund is not a verb on a payment, it is a Refund you create: POST /payments/42/refunds. Now it has its own id, status, and audit trail, and you can GET /payments/42/refunds to list them — strictly better whenever the action needs a record. The anti-pattern is faking the transition through PATCH /orders/42 with a writable status field: it looks RESTful but exposes the state machine, letting a client set status to anything and skip the business rules that gate a real cancellation." },
    { q: "What is the senior rule of thumb for nesting depth, and what two problems does deep nesting cause?", a: "Nest at most one level deep, two as an absolute ceiling. /orders/42/items reads well; /customers/7/projects/3/orders/42/items/9/discounts is a slow-motion disaster. Two problems: first, the URLs are fragile — move an item between orders and every encoded path that contained the old ancestry breaks. Second, deep nesting forces a chatty client: to render one screen the app must walk the hierarchy — fetch the customer, then projects, then each project's orders, then each order's items — which is the N+1 problem promoted to network round-trips. A screen needing eight entities becomes eight-plus sequential calls, each paying its own latency tax; at 80 ms per round-trip that is 640 ms before any rendering. The fix is to address resources by their own stable ID at the root and use query params for the relationship (/orders?customer=7&project=3), plus field expansion (?expand=items,customer) so one call returns what the screen needs." },
    { q: "Distinguish a resource from a representation, and explain why 'don't serialize DB rows directly' is the highest-leverage decision in API design.", a: "A resource is the conceptual thing — the order. A representation is one serialization of it — the JSON you return, an XML variant, a summary view versus a full view. The same resource can have many representations; the resource is stable, the representation is a choice. When you serialize ORM rows straight to JSON, the representation IS the table, so the database schema becomes your public contract. The consequences land in production: rename a column and every deployed client renders blanks until it ships an update (weeks, for mobile); add a NOT NULL column and old writes fail; leak an internal flag like is_deleted and a client builds on it forever. An explicit mapping layer — a DTO, serializer, or view model — translates between the persistence shape and the wire shape. It costs a few minutes per endpoint and buys you a freely refactorable database: rename, split, merge, or denormalize tables and absorb the change in the mapping layer, so no migration ever forces a coordinated client release. The representation becomes a contract you own, not an accident of your ORM." },
    { q: "Define idempotency, say which HTTP methods are idempotent, and explain how to make a POST create safely retryable.", a: "A request is idempotent if making it once and making it many times have the same effect on server state. By the HTTP spec, GET, PUT, and DELETE are idempotent (DELETE /orders/42 leaves the order deleted whether called once or five times), and GET and HEAD are additionally safe (no side effects at all). POST is neither safe nor idempotent: two POST /orders create two orders, and a retried payment double-charges. That matters because networks drop responses — the client cannot tell whether a timed-out POST succeeded, so it retries. The fix is an idempotency key: the client generates a unique key per logical operation and sends it (e.g. an Idempotency-Key header); the server records the key with the first request's result and, on a replay with the same key, returns that original result instead of performing the operation again. This turns a non-idempotent create into one a client can retry safely." },

In theory it is the decoupling endgame: the server can evolve and reshape URLs freely because clients follow links rather than building paths, and the API becomes self-describing. In practice it is the most underused REST constraint. Most 'REST' APIs are level-2 Richardson — resources plus verbs, no hypermedia — because client frameworks rarely consume links, hardcoding a known URL is simpler, and the discipline rarely pays for itself outside large hypermedia-native ecosystems. The senior stance: know what it is, know why it is rare, and do not let a purist block a ship over its absence — but reach for it when clients genuinely benefit from runtime-discoverable actions." },

If you could reconstruct each answer from memory, you hold the unit's spine: model nouns and keep the verb in the method; non-CRUD transitions become guarded action or transition resources, never a writable status field; nest shallow and use expansion to defeat chatty screens; serialize through a mapping layer so the representation is a contract you own rather than your DB schema; POST is not idempotent, so use idempotency keys for safe retries; and HATEOAS is the elegant theory that level-2 REST, what almost everyone ships, usually does without.
