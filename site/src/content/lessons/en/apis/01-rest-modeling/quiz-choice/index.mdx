  question="You must expose 'cancel an order', a guarded transition with rules (not shipped, not already cancelled). Which model is both RESTful enough and safe?"
  choices={[
    { label: "POST /orders/42/cancel — a guarded action sub-resource. It is a verb in the URL, but it is scoped to the resource, uses POST honestly, and the server owns the rules and performs the whole transition atomically or rejects it.", correct: true },
    { label: "PATCH /orders/42 with {'status': 'cancelled'} — just update the field.", misconception: "Exposing status as client-writable hands the client the keys to the state machine: it can jump to any state, skip the cancellation rules, and corrupt order state. The transition must be guarded server-side." },
    { label: "DELETE /orders/42 — cancelling removes the order.", misconception: "A cancelled order is not a deleted one; it still happened and carries history. DELETE loses the audit trail and conflates two different lifecycle outcomes." },
    { label: "GET /orders/42/cancel — make it a simple link the client can click.", misconception: "GET must be safe and have no side effects, so a crawler or prefetch could cancel orders. A state-changing action must use POST, never GET." },

  lessonSlug="01-rest-modeling"
  lang="en"
  question="A dashboard renders /customers/7/projects/3/orders/42/items in nine sequential calls and the path breaks whenever an item moves between orders. What is the senior fix?"
  choices={[
    { label: "Flatten to root resources addressed by their own ID with query params for the relationship — /orders?customer=7&project=3 — and add ?expand=items,customer so one call returns what the screen needs.", correct: true },
    { label: "Cache every level aggressively so the nine calls are fast on warm hits.", misconception: "Caching hides cold-load latency only, invalidation across four nested levels is brutal, and the URLs are still fragile when relationships change. You are optimizing a shape you should flatten." },
    { label: "Add a bespoke /dashboard endpoint that returns exactly what this screen needs.", misconception: "That is an RPC view endpoint, not a resource. Every new screen then wants its own, and you drift back to a verb-per-view API. Field expansion on real resources scales; one endpoint per screen does not." },
    { label: "Keep the deep nesting; it correctly expresses ownership.", misconception: "Nesting does express ownership, but past one or two levels it forces chatty N+1 round-trips and fragile encoded paths. Deep ownership does not require deep URLs — reach the resource by its own ID." },
  ]}
/>

<Quiz
  id="01-rest-modeling-choice-4"
  lessonSlug="01-rest-modeling"
  lang="en"
  question="Your API serializes ORM rows straight to JSON. Why is adding an explicit mapping layer (DTO/serializer) the highest-leverage decision in the design?"
  choices={[
    { label: "Without it the representation IS the table, so the DB schema becomes the public contract — a column rename or new constraint becomes a breaking API change. A mapping layer decouples wire shape from storage so you can refactor the DB without a coordinated client release.", correct: true },
    { label: "A mapping layer makes JSON serialization faster than the ORM's path.", misconception: "Serialization speed is negligible and not the point. The leverage is decoupling: the representation becomes a contract you own instead of an accident of your schema." },
    { label: "It reduces bandwidth by trimming columns.", misconception: "You can trim columns either way; bandwidth is a side effect. The real win is that clients stop depending on column names, so the database stays refactorable." },
    { label: "ORMs cannot serialize relations, so you need a serializer to do it.", misconception: "ORMs serialize relations fine — that is precisely the risk, because they make it trivial to leak the whole schema to the wire. The mapping layer is a deliberate boundary, not a workaround." },
  ]}
/>

<Quiz
  id="01-rest-modeling-choice-5"
  lessonSlug="01-rest-modeling"
  lang="en"
  question="A client retries POST /payments because the response timed out, and the customer is charged twice. Which statement about idempotency is correct?"
  choices={[
    { label: "POST is not idempotent by spec, so a retried create can duplicate. The fix is an idempotency key the client sends and the server dedupes on, so a replay returns the original result instead of creating a second payment.", correct: true },
    { label: "POST is idempotent, so the double charge must be a database bug.", misconception: "Idempotency means repeating a request has the same effect as doing it once. PUT and DELETE qualify; POST does not — two POSTs create two resources unless you add an idempotency key." },
    { label: "Switch the create to GET so retries are safe.", misconception: "GET must be safe (no side effects) — it cannot create a payment at all. Safety is not the same as deduplicating a creating request; you need an idempotency key on the POST." },
    { label: "Make it PATCH instead; PATCH never duplicates.", misconception: "PATCH is not guaranteed idempotent either (e.g. an 'increment by 1' patch), and a create is not an update. The mechanism that prevents the duplicate is the idempotency key, not the method label." },
  ]}
/>

<Recap lang="en">
The through-line: a REST API models nouns the client needs, with the verb in the HTTP method, filtering and paging in query params, and non-CRUD transitions as guarded action or transition resources — never a client-writable status field. Keep nesting shallow and use expansion to kill chatty screens. Serialize through a mapping layer so the representation is a contract you own, not your DB schema. Know that POST is not idempotent (use idempotency keys for safe retries) and that HATEOAS is the elegant theory level-2 REST rarely needs.
</Recap>
