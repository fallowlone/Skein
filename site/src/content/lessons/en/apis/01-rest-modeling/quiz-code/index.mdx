## Snippet 1 — the state-change request

```http
PATCH /orders/42 HTTP/1.1
Content-Type: application/json

{ "status": "cancelled" }
```

<Quiz
  id="01-rest-modeling-code-1"
  lessonSlug="01-rest-modeling"
  lang="en"
  question="This is how the API cancels an order. What is the defect, and the fix?"
  choices={[
    { label: "It exposes the internal status field as client-writable, so a client can jump to any state and skip the cancellation rules (already shipped? refund issued?). Fix: a guarded action sub-resource, POST /orders/42/cancel, where the server runs the transition rules atomically.", correct: true },
    { label: "PATCH is the wrong verb; it should be PUT /orders/42 with the full body.", misconception: "PUT vs PATCH is not the problem — replacing the whole order has the same flaw. The defect is that the state transition is unguarded: the client writes status directly instead of the server enforcing the rules." },
    { label: "The Content-Type should be application/merge-patch+json.", misconception: "The media type is a detail; the structural defect is that any client can set status to any value. A guarded action resource, not a different patch format, is the fix." },
    { label: "Nothing — PATCH on a resource is textbook REST.", misconception: "It looks RESTful, but a writable status field hands the client the state machine. A real cancellation is a guarded transition the server must own, not a field the client flips." },
  ]}
/>

## Snippet 2 — the resource URL design

```
GET  /getUserOrders?userId=7
POST /createOrderForUser?userId=7
GET  /customers/7/projects/3/orders/42/items/9/discounts
```

<Quiz
  id="01-rest-modeling-code-2"
  lessonSlug="01-rest-modeling"
  lang="en"
  question="Two distinct modeling smells appear in these three lines. Name them and the redesign."
  choices={[
    { label: "Lines 1–2 are RPC: verbs (getUserOrders, createOrderForUser) in the path instead of GET/POST /orders?customer=7. Line 3 is over-nesting: six levels deep, fragile and chatty. Redesign: noun resources with the verb in the method, and reach deep resources by their own ID — /discounts?item=9 — nesting at most one or two levels.", correct: true },
    { label: "Only the nesting is wrong; the verb endpoints are acceptable RPC-style aliases.", misconception: "Both are defects. getUserOrders and createOrderForUser put the action in the URL, which is RPC and forfeits the uniform interface — not an acceptable alias alongside REST resources." },
    { label: "The query parameters are the problem; everything should be path segments.", misconception: "Query params for filtering and relationships are correct REST. The actual smells are the verbs in lines 1–2 and the six-level nesting in line 3, not the use of query strings." },
    { label: "All three are fine; they just need consistent casing.", misconception: "Casing is cosmetic. Two of these encode verbs in the path and one nests six levels deep — structural problems that consistent casing does not address." },
  ]}
/>

## Snippet 3 — the idempotent retry

```http
POST /payments HTTP/1.1
Idempotency-Key: 7f3c9a2e-...-d41
Content-Type: application/json

{ "amount": 4200, "currency": "usd", "source": "card_x" }
```

<Quiz
  id="01-rest-modeling-code-3"
  lessonSlug="01-rest-modeling"
  lang="en"
  question="The client sends this request, the TCP connection drops before the response arrives, and the client retries the identical request with the same Idempotency-Key. What must the server do?"
  choices={[
    { label: "Recognise the key as already processed and return the original payment's result (same id, same status) without creating a second charge. The key turns a non-idempotent POST into a safely retryable one by deduplicating on the server.", correct: true },
    { label: "Create a new payment, since each POST is an independent create.", misconception: "That is exactly the double-charge this header exists to prevent. The Idempotency-Key tells the server to detect the replay and return the first result, not create a second payment." },
    { label: "Reject the retry with 409 Conflict because the key was already used.", misconception: "A replay with the same key and body is not a conflict — the contract is to return the original successful response, making the retry transparent to the client. 409 would force the client to handle a non-error as an error." },
    { label: "Ignore the header — idempotency keys only apply to PUT and DELETE.", misconception: "PUT and DELETE are idempotent by their semantics; the idempotency key exists precisely because POST is not, letting a creating request be retried safely." },
  ]}
/>

## Snippet 4 — the leaky response

```json
{
  "id": 42,
  "full_name": "Ada Lovelace",
  "password_hash": "$2b$12$...",
  "is_deleted": false,
  "internal_risk_score": 0.13
}
```

<Quiz
  id="01-rest-modeling-code-4"
  lessonSlug="01-rest-modeling"
  lang="en"
  question="This is a user resource serialized straight from the ORM row. What is wrong, and the structural fix?"
  choices={[
    { label: "The representation IS the table: it leaks a credential (password_hash) and internal fields (is_deleted, internal_risk_score), and welds clients to column names like full_name. Fix: a mapping layer (DTO/serializer) that emits only the intended wire fields, decoupling the representation from the schema.", correct: true },
    { label: "Only password_hash is the problem; strip it and ship the rest.", misconception: "Removing the credential is necessary but not sufficient. is_deleted and internal_risk_score are internal, and serializing rows directly still welds the contract to column names — the structural fix is an explicit mapping layer." },
    { label: "The id should be a string, not a number.", misconception: "Number vs string id is a minor convention choice. The real damage is leaking a credential and internal fields and coupling the wire contract to the DB schema." },
    { label: "Nothing structural — just add field-level auth so only admins see the hash.", misconception: "A password hash should never be in any representation regardless of role, and the schema coupling remains. The fix is to map to a deliberate wire shape, not gate raw columns by role." },
  ]}
/>

<Recap lang="en">
Every API defect reads off the wire: a writable status field is an unguarded transition (use a guarded action resource); verbs in the path and six-level nesting are RPC and chattiness (noun resources, shallow paths, IDs at the root); a retried POST needs an idempotency key to dedupe safely; and a row serialized straight to JSON leaks credentials and internal fields while welding the contract to your schema (map through a DTO). Read the request, find the structural smell, fix the shape — not the symptom.
</Recap>
