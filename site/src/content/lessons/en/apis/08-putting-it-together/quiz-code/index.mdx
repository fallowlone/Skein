## Snippet 1 — the route table

```http
POST   /chargeCard
POST   /refundCharge?id=123
GET    /getUserOrders?user=42
POST   /orders/{id}/cancel?action=cancel
```

  lang="en"
  question="This route table mixes several modeling mistakes. What is the single highest-leverage correction, and why does it matter most?"
  choices={[
    { label: "Model nouns, not verbs: POST /payments, POST /payments/{id}/refunds, GET /users/{id}/orders, POST /orders/{id}/cancellations. Verb-shaped routes have nothing addressable, so they cannot return Location/201/409 and end up returning 200 for everything — which breaks the retry contract downstream.", correct: true },
    { label: "Just move the query params into the path; the verbs are fine.", misconception: "Fixing ?id=123 to a path segment is half the job, but POST /chargeCard and ?action=cancel are still verbs. The core defect is verb-shaped resources, which is what poisons the status codes." },
    { label: "Add an API version prefix (/v1) and the routes are correct.", misconception: "Versioning is orthogonal; /v1/chargeCard is still a verb with the same retry problem. Versioning organizes evolution, it does not fix bad modeling." },
    { label: "Switch them all to GET so they are cacheable.", misconception: "Creating a charge or cancellation mutates state — GET must be safe and idempotent. Making writes GET-able is a correctness and caching disaster." },
  ]}

## Snippet 2 — the create-payment response

```http
POST /payments
Idempotency-Key: 8f1c-...-a9
--> HTTP/1.1 200 OK
    { "status": "ok", "error": null }
```

<Quiz
  id="08-putting-it-together-code-2"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="The client sent an Idempotency-Key and the server returned 200 with no resource id. A timeout-driven retry follows. What is wrong and what should the server return?"
  choices={[
    { label: "200 with no Location/id is the wrong code for a creation: it tells the client 'done' but gives it nothing to address, and it does not distinguish first write from replay. Return 201 Created + Location on the first request, and 200 with the original resource on a replay of the same Idempotency-Key.", correct: true },
    { label: "The response is fine; 200 always means success for a POST.", misconception: "For a creation, 201 + Location is the honest code. A bare 200 with no id cannot tell a fresh create from an idempotent replay, which is exactly the ambiguity that drives double-charges." },
    { label: "The server should return 204 No Content to be efficient.", misconception: "204 means 'success, no body' — but a created payment must return its id/Location so the client can reference it and confirm the idempotent replay. 204 throws away the information the retry needs." },
    { label: "Return 409 on the first request to signal the resource now exists.", misconception: "409 is for a conflicting state (e.g. a replay that collided with a different in-flight result), not for a successful first creation. The first write is 201; the safe replay is 200 with the original result." },
  ]}
/>

## Snippet 3 — the deep-page query

```sql
-- page 5001 of a live, growing feed
SELECT id, created_at, title
FROM posts
ORDER BY created_at DESC
OFFSET 100000 LIMIT 20;
```

<Quiz
  id="08-putting-it-together-code-3"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="This query backs a live, growing feed and deep pages are slow and occasionally drop or duplicate posts. What is the cursor-based rewrite and what does it buy?"
  choices={[
    { label: "Keyset on a stable, unique sort key: WHERE (created_at, id) < (:last_created, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20, passing the last row's (created_at, id) as the cursor. Cost stays O(20) at any depth and rows do not shift when new posts are inserted mid-pagination.", correct: true },
    { label: "Keep OFFSET but add an index on created_at; that makes deep pages fast.", misconception: "The index speeds the ORDER BY but OFFSET 100000 still scans and discards 100k rows every deep page. Keyset is what removes the discard, not the index." },
    { label: "Use WHERE created_at < :last LIMIT 20 with created_at alone as the cursor.", misconception: "created_at is not unique — ties at the same timestamp get skipped or duplicated at page boundaries. A keyset cursor needs a unique tiebreaker (id), hence the composite (created_at, id)." },
    { label: "Order by id only and ignore created_at to simplify the cursor.", misconception: "The feed is sorted by created_at DESC; paginating by id alone returns the wrong order. The cursor must match the sort key, with id only as the tiebreaker." },
  ]}
/>

## Snippet 4 — the rate-limit headers

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 8
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1716998400
```

<Quiz
  id="08-putting-it-together-code-4"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="A client got this response. What is the correct client behavior, and what does each signal mean?"
  choices={[
    { label: "Stop sending, wait at least 8 seconds (Retry-After), then resume — the quota is 1000, none remain now, and Reset is the epoch when the window refills. A cooperative client honors Retry-After rather than retrying immediately or on its own fixed backoff.", correct: true },
    { label: "Retry immediately; 429 is transient and the next request will probably pass.", misconception: "Remaining is 0 and Retry-After is 8 — an immediate retry is guaranteed to be throttled again and amplifies load. The whole point of Retry-After is to make the client wait the stated window." },
    { label: "Treat 429 like 503 and fail the request to the user.", misconception: "429 is a backoff signal, not a hard failure — the request is valid, just over quota. The client should wait and retry, surfacing an error to the user only if it persists past the reset." },
    { label: "Ignore the headers and back off a random amount; the headers are advisory.", misconception: "Retry-After and the X-RateLimit-* fields are exactly the documented quota signal; ignoring them turns a cooperative throttle into guesswork and can keep the client locked out longer." },
  ]}
/>

<Recap lang="en">
Every API review reads the same artifacts: a route table tells you whether resources are nouns (and therefore whether status codes can be honest); a create response should be 201 + Location on first write and 200 on an idempotent replay, never a bare 200 with no id; a deep-page query should be a keyset cursor on a unique composite sort key, not OFFSET; and a 429 with Retry-After + X-RateLimit-* is a cooperative backoff contract the client must honor. Read the contract, predict the failure under retry or load, then apply the structural fix.
</Recap>
