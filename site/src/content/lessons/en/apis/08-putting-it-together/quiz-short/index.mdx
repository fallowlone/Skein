With nothing addressable, the endpoint has no Location to return and no 409 to give on a duplicate, so it returns 200 for everything.     { q: "Why is an HTTP status code a contract rather than decoration, and what does each class commit the client to?", a: "Generic clients, SDKs, proxies, caches, and monitoring all branch on the status code and headers automatically, without parsing your body — so the code is the machine-readable part of the contract and a wrong code corrupts client logic. 2xx means done, do not retry. 4xx means the request itself is wrong; retrying it unchanged is pointless (400, 404, 422). 429 and 503 mean retryable but back off — read Retry-After. 5xx means maybe retryable, but only if the operation is idempotent. The dangerous case is a non-idempotent POST that fails after the write but before the response; the honest answer there is an Idempotency-Key, because without it the only correct code for 'I do not know if it worked' is no code the client can safely act on." },
    { q: "When is cursor (keyset) pagination mandatory over OFFSET/LIMIT, and what is the tradeoff?", a: "Use cursor pagination for large or live datasets. OFFSET 100000 LIMIT 20 forces the database to scan and discard 100k rows on every deep page — a cost that grows with depth — and it silently skips or duplicates rows when items are inserted mid-pagination. Keyset pagination — WHERE (sort_key, id) < (:last_key, :last_id) ORDER BY sort_key, id LIMIT n, carrying the last row as an opaque cursor — stays O(page size) at any depth and is stable under concurrent inserts because it anchors on row values, not a numeric offset. The tradeoff is you lose random 'jump to page 500' access; OFFSET is fine only for small, stable, admin-grade lists where deep pages and live inserts are not a concern." },
    { q: "What is a breaking change versus an additive one, and what does the spec-first OpenAPI + CI break diff actually buy you?", a: "Backward compatibility has a precise meaning: an unmodified old client still works against the new API. Additive and safe: adding an optional field, a new endpoint, or a new enum value the client can ignore. Breaking: removing or renaming a field, tightening validation, changing a default, or changing a type — because some client depends on the exact old behavior. Spec-first OpenAPI makes the schema the source of truth, from which clients and server stubs are generated, and the CI break diff compares the new spec against the old and fails the build on a breaking change. That diff exists because humans consistently misjudge which bucket a change is in; without it, drift ships in a green deploy because the tests were written against the old shape and nobody regenerated them." },
    { q: "A teammate wants the public API to be gRPC because the benchmarks are far faster. How do you reason about it?", a: "First separate the axes: protocol (REST vs gRPC) is independent of modeling, versioning, and the contract — it is a transport choice, not part of the API-evolution story. The gRPC numbers are real — roughly 77% lower latency on small payloads, about 10x smaller protobuf messages, higher throughput, native streaming — but every one of them answers 'internal service-to-service at high volume,' not 'public contract.' A public API lives on discoverability, the ability for an external developer to curl it or hit it from a browser, generated SDKs, and low onboarding friction — exactly REST + OpenAPI's strengths. So the senior split is REST + OpenAPI at the public edge, and gRPC between your own services if and only if the volume justifies it. Choosing gRPC for the public edge because a benchmark is faster optimizes the one metric the public API is not constrained by while sacrificing the ones it is." },

The rate limit caps how many requests a client can make: over-quota requests get a 429 with a Retry-After header (and ideally X-RateLimit-Limit/Remaining/Reset) so a cooperative client backs off the stated window instead of hammering or guessing its own backoff. Idempotency makes the requests that do get through safe: an Idempotency-Key lets a retried unsafe write return the original result instead of re-executing, so even a flood of retries cannot produce duplicate side effects. Without Retry-After, clients fall back to aggressive or fixed backoff and amplify the storm; without idempotency, the throttled-but-still-arriving retries still double-write.
