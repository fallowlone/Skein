What actually protects you?", a: "A spec is just a file; it describes the contract but enforces nothing on its own. Protection comes from making the spec load-bearing in CI: a breaking-change diff tool (oasdiff) compares the new spec against the previous version and fails the pull request when it finds a removed response field, a newly-required request field, a narrowed type, a deleted enum value, or a removed endpoint. Without that gate, an engineer can add a required field, the spec faithfully records it, and every existing client still breaks in production. A spec nobody checks is documentation, and documentation drifts into fiction." },
    { q: "Define contract drift and name the two mechanisms that prevent it.", a: "Contract drift is when the written contract (a hand-authored spec or stale docs) and the running server silently diverge: the docs say a field is optional, the server now rejects requests without it, and clients integrate against the fiction and break. Two mechanisms prevent it. First, request validation at the edge — a middleware checks every incoming request against the spec before the handler runs, so a malformed body gets a precise 400 and the spec and runtime cannot disagree unnoticed. Second, a breaking-change diff in CI — the spec is compared against its previous version on every PR so an incompatible change fails the build. Together they make the spec impossible to violate without the pipeline noticing." },
    { q: "Contrast spec-first and code-first: what differs, and what enforcement do both still need?", a: "Spec-first (design-first) means you author the OpenAPI document by hand, review it as a contract, and generate server stubs, typed clients, and mock servers from it — the spec is the source of truth and code conforms to it, so the contract is reviewed before any code exists and frontend can build against a mock on day one. Code-first means you annotate the server (type hints, decorators) and generate the spec from the running code — the code is the source of truth, less ceremony, and the spec cannot drift from the handler it was extracted from. The senior call: spec-first for public APIs with many or external consumers that need a reviewed, stable contract; code-first when one team owns both ends and velocity wins. But neither escapes enforcement — both must diff the spec for breaking changes in CI and, ideally, validate requests at the edge. Code-first specs drift from consumer expectations just as easily." },
    { q: "What does codegen buy you, and what makes the difference between a strong generated client and an any-riddled one?", a: "Running a generator over the spec produces typed SDKs and server stubs — methods, models, error types — in TypeScript, Go, Swift, Kotlin, and more. That kills the whole class of hand-rolled-request bugs ('I sent userId, the server wanted user_id') because nobody writes the request by hand anymore, and server stubs guarantee handlers match the contract. The quality of the output is entirely a function of the schema you feed it: tight schemas (explicit types, explicit required arrays, closed additionalProperties, reused $ref components) generate strong, precisely-typed clients; loose schemas (untyped object blobs, missing required, open additionalProperties) generate any-riddled clients that defeat the point. The generator is only as honest as the contract." },
    { q: "List the canonical breaking changes a diff tool like oasdiff catches, and one compatible alternative to a breaking change.", a: "Breaking changes include: adding a new required request property; removing or renaming a response field a client may read; narrowing a type (string to enum, widening to tighter constraints); removing an enum value; deleting an endpoint or operation; making a previously-optional parameter required; tightening min/max or pattern constraints. Each rejects or breaks at least some existing clients. The compatible alternative for adding a required field: add it as optional first, give it a sensible default or backfill, let clients adopt it over time, and only flip it to required in a later, announced (often major) version. Additive-and-optional is the safe shape; removal and tightening are the dangerous ones." },

Concretely: nullable: true is gone — you express nullability with a type array, type: ['string', 'null']; exclusiveMinimum and exclusiveMaximum take a numeric value instead of a boolean; and 3.1 adds a top-level webhooks object to document events your API sends, not just receives. In practice it matters because many generators and validators still default to 3.0 and may not understand 3.1, so you check tool support before upgrading. It also subtly changes diffs — dropping 'null' from a type array later shows up as a type change rather than a nullable change, so you read the change category the tool reports, not just the count." },

<Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: an unenforced spec is fiction, and the cure for contract drift is making the spec load-bearing — edge validation and a CI breaking-change diff. Spec-first vs code-first decides where truth lives and whether the contract is reviewed, but both need the same gate. Codegen kills hand-rolled-request bugs only when the schema is tight, oasdiff catches the canonical breaking changes (added required field, removed response field, narrowed type), and OpenAPI 3.1 moves schemas to JSON Schema 2020-12 with type-array nullability. Always: make the contract impossible to break silently.
</Recap>
