## Snippet 1 — the loose schema

```yaml
components:
  schemas:
    Order:
      type: object
      properties:
        id: { type: string }
        items:
          type: object          # untyped blob
        total: {}               # no type at all
      additionalProperties: true # anything else is allowed
      # no `required:` array
```

## Snippet 2 — the oasdiff verdict

```
$ oasdiff breaking main.yaml pr.yaml
1 breaking changes: 1 error, 0 warning
error  api-required-request-property-added
       in API POST /orders
       added the required request property 'tenantId'
```

<Quiz
  id="04-openapi-code-2"
  lessonSlug="04-openapi"
  lang="en"
  question="The PR adds tenantId as a required field on POST /orders and oasdiff reports this in CI. What should the pipeline do, and what is the compatible alternative?"
  choices={[
    { label: "Fail the PR — adding a required request property rejects every existing client that does not send tenantId. The compatible path is to add tenantId as optional first, backfill clients, then flip it to required in a later, announced version.", correct: true },
    { label: "Pass with a warning — adding a field is backward compatible.", misconception: "Adding an optional field is compatible; adding a required one is the textbook breaking change, which is exactly why oasdiff classifies it as an error, not a warning." },
    { label: "Pass — oasdiff output is advisory and the docs portal will show the new field.", misconception: "Regenerated docs describe the change but do not prevent the breakage. The whole value of the gate is that the breaking change fails the build before any client breaks." },
    { label: "Fail, then fix it by removing tenantId from the response schema.", misconception: "The break is on the request, not the response. Touching the response does not make a newly-required request field compatible." },
  ]}
/>

## Snippet 3 — the 3.0 to 3.1 nullability rewrite

```yaml
# OpenAPI 3.0
status:
  type: string
  nullable: true

# OpenAPI 3.1 (JSON Schema 2020-12)
status:
  type: [string, "null"]
```

<Quiz
  id="04-openapi-code-3"
  lessonSlug="04-openapi"
  lang="en"
  question="You migrate the spec to 3.1 and rewrite nullability like this. What must you watch for in tooling and diffs?"
  choices={[
    { label: "nullable: true is not valid in 3.1 — nullability lives in the type array now. Check that your generator and validator support 3.1 (many still default to 3.0), and note that later dropping 'null' from the array registers in oasdiff as a type change, not a nullable change.", correct: true },
    { label: "Nothing — nullable: true still works in 3.1 as an alias for the type-array form.", misconception: "3.1 removed nullable entirely; it is ignored or invalid. You must use type: [string, 'null'], and tools built for 3.0 may not understand it." },
    { label: "The two forms are different contracts — the 3.1 version no longer allows null.", misconception: "Both express 'string or null' — the contract is identical. The migration is syntactic; the allowed values are the same." },
    { label: "3.1 makes status required because it is now an array type.", misconception: "type: [string, 'null'] is a union of allowed types, unrelated to whether the field is required. Required-ness is controlled only by the required array." },
  ]}
/>

## Snippet 4 — code-first annotations

```python
class CreateOrder(BaseModel):
    id: str
    items: list[Item]
    coupon: str | None = None   # optional, nullable

# FastAPI generates the OpenAPI spec from this model.
# A later edit makes coupon required:
    coupon: str                 # now required, no default
```

<Quiz
  id="04-openapi-code-4"
  lessonSlug="04-openapi"
  lang="en"
  question="In a code-first setup, an engineer makes coupon required by removing its default. The generated spec updates automatically. What is the risk, and what closes it?"
  choices={[
    { label: "Code-first keeps the spec in sync with the code but not with consumer expectations — the generated spec now requires coupon and breaks every client that omits it, silently. Closing it needs the same oasdiff gate: diff the generated spec against the previous one in CI and fail on the new required field.", correct: true },
    { label: "No risk — code-first specs cannot drift, so the change is safe.", misconception: "Code-first prevents drift between spec and handler, not between the contract and what clients depend on. A required-field change is breaking regardless of how the spec was produced." },
    { label: "The risk is that FastAPI will reject the model at startup.", misconception: "The model is valid Python; FastAPI starts fine and faithfully publishes coupon as required. The danger is downstream, on clients, not at startup." },
    { label: "Switch to spec-first and the problem disappears on its own.", misconception: "Spec-first surfaces the change for review but still does not block it without a diff gate. The fix is enforcement (oasdiff in CI), which both models need equally." },
  ]}
/>

<Recap lang="en">
Every contract change is read in three places: the schema (loose types and open additionalProperties produce any-riddled clients — tighten with explicit types, required arrays, and $ref), the diff (oasdiff classifies adding a required field, removing a response field, or narrowing a type as breaking — fail the PR and migrate compatibly), and the generation direction (code-first stays in sync with code but not with consumers, so it needs the same gate spec-first does). OpenAPI 3.1 moves nullability into the type array and aligns with JSON Schema 2020-12 — verify tool support before you migrate. Read the artifact, predict the consumer impact, then fix at the contract level.
</Recap>
