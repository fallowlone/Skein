    { q: "Why does LIMIT 20 OFFSET 200000 get slower the deeper you page, even though it always returns 20 rows?", a: "The database has no way to truly skip to row 200000. To honour the ORDER BY it produces rows in sorted order, reads and discards the first 200000, and only then returns the 20 you asked for. The work is proportional to the offset value, not the page size, so the response stays 20 rows while the cost climbs linearly with depth. On a multi-million-row table that pushes deep pages from milliseconds toward many seconds, and the cost repeats on every page. An index can supply the order cheaply but cannot remove the read-and-discard, because OFFSET is defined as counting off rows. That is why keyset, which seeks to a position by value instead of counting, stays flat." },
    { q: "Explain result drift: why does an offset feed show duplicate and missing items, and why even on a small table?", a: "Offset addresses pages by position in a live, shifting result set. Between two requests the set can change: insert a row near the top and every later row shifts down one position, so the item that was last on page 1 reappears as the first item on page 2 — the user sees it twice. Delete a row instead and everything shifts up, so one item that should have started page 2 is skipped entirely. This is not a load or cache problem; it happens the instant two requests straddle a single write, which on any active feed is constant. It shows up on tiny tables for the same reason — position is simply not a stable address when the underlying rows move. Keyset fixes it by anchoring on a specific row's key value, which inserts and deletes elsewhere cannot shift." },
    { q: "What two properties must a keyset sort key have, and what breaks if the key is not unique?", a: "The sort key must be unique and stable, and it must be backed by a composite index in the exact column order and direction of the ORDER BY. If the key is not unique — ordering by created_at alone, for example — two rows can share the same value, and at a page seam the boundary comparison cannot tell them apart: one row gets skipped or repeated across the seam. The fix is to append a unique tiebreaker such as the primary key and compare the whole tuple: ORDER BY (created_at, id) DESC with WHERE (created_at, id) < (lastCreatedAt, lastId). Without the matching composite index the tuple comparison still returns correct rows, but the planner falls back to a sort-and-scan and you lose the flat latency that was the whole point." },
    { q: "Why expose an opaque cursor instead of the raw (created_at, id) keys, and what does the client do with it?", a: "The cursor is a contract boundary. Encoding the keyset into an opaque string — commonly Base64-encoded JSON of the sort values, returned as nextCursor — lets the client treat it as a black box it sends back verbatim. That buys the server freedom to change the sort key, add a tiebreaker, or switch the underlying store later without breaking the wire contract, and it stops clients from hand-crafting cursors that seek into expensive territory. GraphQL's Relay Connection spec formalises this: edges carry per-row cursor values and pageInfo carries hasNextPage / endCursor. Raw keys, by contrast, couple the API surface to internal schema details and leak the sort columns to every client." },
    { q: "What does keyset give up compared to offset, and when is offset still the right choice?", a: "Keyset can only walk relative to a known row — next page or previous page from a cursor — so it cannot jump directly to an arbitrary page N. Offset's one genuine advantage is exactly that: 'go to page 4000 of 80000' is trivial with LIMIT/OFFSET and impossible with a pure cursor. So offset still fits bounded, low-cardinality surfaces where users legitimately jump around — an internal admin table, a report with a fixed small page count, search results capped at a few hundred. The senior move is to match the strategy to the access pattern: keyset for public, deep, write-heavy feeds where only next/prev is needed; offset where arbitrary page jumps are a real product requirement and the table or page range is small enough that the scan stays cheap." },
    { q: "Why is an exact total count expensive in Postgres, and what are the alternatives in order of preference?", a: "COUNT(*) cannot be read from a metadata field because of MVCC: each transaction sees its own set of visible row versions, so the engine must walk the rows to count the ones visible to your transaction. On a large table that is effectively a full scan whose cost grows with the table and often dwarfs the page query it accompanies. In order of preference: drop the exact total — infinite scroll and most lists need 'is there a next page', not 'of 4,812,339'; use a fast estimate from pg_class.reltuples, which ANALYZE keeps current and is normally within about ten percent of the truth when 'about 5 million' is acceptable; or fetch LIMIT n+1 and use only the presence of the extra row to set hasNextPage. Reserve a real COUNT(*) for small tables or admin views where the exact number is genuinely required and the scan is cheap." },

<Recap lang="en">
If you reconstructed each answer from memory, you hold the unit's spine: offset cost scales with depth because the engine reads and discards every prior row; offset drifts because position is not a stable address under writes; a valid keyset key is unique, stable, and index-backed, compared as a whole tuple; the cursor is opaque so the contract can evolve and clients can't craft expensive seeks; keyset trades arbitrary page jumps for flat latency, which is why offset still fits bounded admin surfaces; and an exact count is an MVCC full scan, so estimate or probe with n+1 instead. Now when you review a list endpoint, run through these six questions in your head — the answers tell you whether the design will hold at ten million rows and constant writes.
