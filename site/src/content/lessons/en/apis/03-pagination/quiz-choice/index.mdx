  question="An endpoint serves LIMIT 20 OFFSET 200000 against a 50M-row table. It returns 20 rows but takes ~8 seconds. Why does cost grow with the offset and not the page size?"

    { label: "The engine has no way to truly skip — it must produce rows in sort order, read and discard the first 200000, then return 20. Work is proportional to the offset, not the payload.", correct: true },
    { label: "The 20-row payload is larger for deeper pages, so serialization dominates.", misconception: "The payload is always 20 rows; response size is constant. The cost is the 200000 rows the engine reads and throws away to reach them — invisible in the response." },

    { label: "OFFSET takes a lock while counting, and lock contention adds the latency.", misconception: "OFFSET is a plain read and takes no such lock. The latency is the linear read-and-discard work proportional to the offset value." },

<Recap lang="en">
The unit's through-line is one decision: address pages by position (offset) and you pay twice — deep pages scan-and-discard linearly, and positional boundaries drift under writes into duplicates and skips. Address them by value (keyset) over a unique, stable, indexed key and latency stays flat with no drift, at the cost of losing arbitrary page jumps — which is why offset still earns its place on bounded admin tables. Hand clients an opaque cursor so the contract can evolve, and treat the exact total as its own scan: estimate or probe with LIMIT n+1 instead of paying for a count nobody needs. Now when you see a list endpoint with rising p99 and drift complaints, you have a checklist: check "actual rows" in the plan, check the sort key for uniqueness, check whether the cursor is opaque, and check whether the count footer is worth its scan.
</Recap>
