<Hook>
Your weather app shows today's forecast. But your app does not own the weather — a different company on a different computer does. So how does your app get it? It does not read their files or run their code. It sends a small message that asks one named question — "give me the forecast for this city" — and gets a small message back with the answer. That asking-and-answering channel, with its agreed list of questions, is an API.
</Hook>

<Crux>An API is a contract: one program offers named operations another can call over the network.</Crux>

<Explanation>

## A contract, not the code

When you order at a counter, you do not walk into the kitchen. You read a menu, say a dish name, hand over money, and get a plate. You never see how the food is cooked, and you do not need to. The menu is a **contract**: it lists what you can ask for and what you will get back.

An API is that menu for programs. The program offering the API (the **server**) publishes a list of named operations — "get the forecast", "create a user", "send a message". Another program (the **client**) calls one of those operations and gets a result. Neither side sees the other's code. As long as both honor the contract, either side can change inside however it likes.

## Request and response

A single call has two halves that travel over the network:

- A **request** — the client says which operation it wants and gives any needed details (which city, which user).
- A **response** — the server sends back the result, plus a small status saying whether it worked.

## Why a contract is the whole point

Because the contract hides the inside, two teams who never meet can still build together. The weather company can rewrite its entire system overnight; your app keeps working as long as "get the forecast" still takes a city and returns a temperature. That stability is what lets the modern web be assembled from thousands of programs calling each other. The rest of this track is about designing that contract well: naming operations, shaping responses, reporting errors, and not breaking callers when you change.

<Recap lang="en">
An API is a contract between programs: one side (the server) publishes named operations, the other side (the client) calls them over the network. Each call is a request out and a response back, with a status. The contract hides the code inside, so separate teams can build together and each can change internals without breaking the other. The rest of this track is how to design that contract well.
</Recap>
