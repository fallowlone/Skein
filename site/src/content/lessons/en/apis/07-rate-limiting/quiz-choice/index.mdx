    { label: "Leaky bucket — it drips requests out at a constant rate.", misconception: "Leaky bucket smooths output to a steady rate, which actively refuses the legitimate page-load burst and adds queuing latency. It fits a fragile downstream, not friendliness to bursty clients." },

  lessonSlug="07-rate-limiting"
  lang="en"
  question="You move the counter to Redis and implement it as INCR followed by EXPIRE. Why is a single Lua script the more robust pattern?"
  choices={[
    { label: "Lua runs the whole read-decide-update atomically. Separate INCR and EXPIRE can race, and if the process dies between them the key never gets a TTL and the counter leaks forever.", correct: true },
    { label: "Lua is faster than INCR on the Redis server.", misconception: "Speed is not the point — INCR is already sub-millisecond. The reason is atomicity: the script prevents interleaving and the TTL-less-key race." },
    { label: "Lua lets Redis persist the counter to disk for durability.", misconception: "Lua scripts run in memory like any Redis command; persistence is orthogonal. The benefit is the atomic read-decide-update cycle." },
    { label: "Lua removes the need for Redis to be single-threaded.", misconception: "Redis runs commands single-threaded already; that is why a script executes with no other command interleaved. Lua leverages that property, it does not change it." },
  ]}
/>

<Quiz
  id="07-rate-limiting-choice-5"
  lessonSlug="07-rate-limiting"
  lang="en"
  question="An auth service must enforce an exact per-account limit for compliance — no boundary slack, every attempt accounted for. Which algorithm, and what is the cost you accept?"
  choices={[
    { label: "Sliding window log — store a timestamp per request in a sorted set, trim entries older than the window, count what remains. It is exact over any rolling interval; the cost is memory and a ZADD plus trim per call.", correct: true },
    { label: "Sliding window counter — it is accurate enough at ~0.003% error.", misconception: "For a coarse edge limit ~0.003% error is great, but it is still an approximation. An audit-grade exact count for compliance is the one case where you pay for the log." },
    { label: "Fixed window — reset the counter every minute exactly.", misconception: "Fixed window is exact within a window but leaks up to 2x at the boundary, so the rolling count is not exact. That slack is unacceptable for an audited limit." },
    { label: "Token bucket — it tracks tokens precisely.", misconception: "Token bucket deliberately allows a bounded burst above the steady rate, so it does not enforce an exact rolling count. It optimises for friendliness, not audit-grade exactness." },
  ]}
/>

    { label: "Clients are ignoring Retry-After and retrying immediately.", misconception: "Here the clients are well-behaved — they obeyed Retry-After, which is exactly why they all woke at once. The herd is self-inflicted by an identical deadline, not by misbehaving clients." },

<Recap lang="en">
The through-line: how requests fall into windows is where fixed window leaks its 2x boundary burst; sliding window log buys exactness with per-request memory, the sliding counter approximates it for two integers, and token bucket models bursts as a tunable capacity. None of it is real if the counter lives in per-node memory — share it in Redis, make the read-decide-update atomic with Lua, and when you reject, honor the contract with 429 + Retry-After in delta-seconds plus jitter so the reset edge does not become a thundering herd.
</Recap>
