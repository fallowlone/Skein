A client can send the full limit at the very end of one window and the full limit again at the very start of the next, so up to twice the limit lands in a tiny span across the boundary. The sliding window log fixes it exactly by timestamping every request and counting any rolling 60s, at the cost of storing one timestamp per request. Token bucket sidesteps the boundary entirely: tokens refill continuously rather than resetting on an edge, so there is no seam to exploit, and the maximum burst is whatever you set capacity to — a deliberate, bounded knob rather than an accidental 2x leak." },
    { q: "Compare the sliding window log and the sliding window counter. When is each the right call?", a: "The log stores a timestamp per request in a sorted set, trims entries older than the window, and counts what remains — exact over any rolling interval, but it costs one entry per request plus a ZADD and a ZREMRANGEBYSCORE trim on every call, so a client at 10k req/min holds 10k timestamps. The counter keeps just two fixed-window integers — current and previous — and estimates the rolling count as current + previous * overlap fraction. It is an approximation, but Cloudflare measured roughly 0.003% error across about 400 million requests for two integers per key. Use the counter as the default edge limiter where that accuracy-for-near-nothing trade is ideal; reserve the log for auth or payments where an audit-grade exact count is worth the memory." },
    { q: "Explain how a token bucket enforces an average rate while still allowing bursts, and what the capacity parameter controls.", a: "A bucket holds up to capacity tokens and refills at a steady rate, say 100 tokens per minute. Each request spends one token; a request is rejected only when the bucket is empty. A client that has been idle accumulates tokens up to the cap, so it can fire a burst instantly, then is throttled to the refill rate — so over time the average is bounded by the refill rate while short spikes are allowed. Capacity is the burst knob: with a 100/min limit and capacity 100 a fresh client can fire 100 at once; set capacity to 10 and the same average tolerates only a 10-request spike. The burst is not a bug, it is the parameter that matches the limiter to how clients actually behave. It stores only two values — current tokens and last-refill timestamp — which is why Stripe and AWS use it as the general default." },
    { q: "An in-memory limiter passes every test on a laptop but lets traffic far exceed the limit in production. Explain the failure and the fix.", a: "The limiter keeps its counter in the process's own memory. On one machine that is correct, but production runs the app on several nodes behind a load balancer, and each node has its own independent counter. With N nodes the effective limit is N times what you configured, and a client whose requests the balancer spreads across nodes never sees a single counter fill. Tests pass because they hit one process. The fix is to move the counter to a store every node shares — almost always Redis — so all nodes read and write the same number, and to update it atomically." },
    { q: "Why run the Redis rate-limit check as a single Lua script instead of INCR then EXPIRE?", a: "Redis runs a Lua script atomically — the whole read-decide-update cycle executes with no other command interleaved, so concurrent requests cannot double-spend tokens or both pass a check that should have rejected one. A plain INCR followed by EXPIRE is two separate commands: they can race, and if the process dies between them the key never gets a TTL and the counter leaks forever, silently locking out a key. A token-bucket check in Lua is a handful of operations and runs in sub-millisecond time, cheap enough to sit on the synchronous request path even at millions of requests per second." },

Add the IETF RateLimit-* fields — RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset — so clients can self-pace before they hit the wall. The draft specifies RateLimit-Reset as delta-seconds, not a UNIX timestamp, for two reasons: a timestamp would require the client's clock to be in sync with the server's, and it would tell every throttled client to retry at the same absolute instant — a self-inflicted thundering herd at the reset boundary.
