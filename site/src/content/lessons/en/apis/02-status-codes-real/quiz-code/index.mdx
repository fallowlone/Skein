## Exchange 1 — the 200 that is really a failure

```http
POST /v1/payments HTTP/1.1
Content-Type: application/json

{ "amount": 4200, "currency": "usd" }

HTTP/1.1 200 OK
Content-Type: application/json

{ "ok": false, "error": "upstream_timeout", "code": "GATEWAY_DOWN" }
```

  lessonSlug="02-status-codes-real"

  question="The upstream timed out, yet the status line is 200. What is the consequence and the fix?"
  choices={[
    { label: "Every machine that branches on status — caches, APM/error-rate dashboards, client retry loops — sees success and does the wrong thing: the failure is cached, the outage stays invisible, and the retry that 5xx would have triggered never fires. Fix: return a real 5xx (here 504 Gateway Timeout) and keep the detail in the body.", correct: true },
    { label: "Nothing — the body's `ok: false` lets clients detect the failure.", misconception: "Only clients that parse and check your bespoke envelope detect it. Caches, dashboards, and retry middleware never read the body; they branch on the 200 and treat a total outage as perfect health. The status must carry the truth." },
    { label: "It is fine for payments because 200 avoids alarming clients with 5xx.", misconception: "Hiding a 5xx behind 200 does not avoid alarm; it removes the signal that would have driven the correct automatic recovery. The error must surface in the status so the system reacts." },
    { label: "Change the body to `code: 500` and keep the 200 status.", misconception: "Putting the number in the body changes nothing for the machines that branch on the HTTP status line. The status code itself must be a 5xx." },
  ]}

## Exchange 2 — 401 vs 403

```http
DELETE /tenants/acme/users/77 HTTP/1.1
Authorization: Bearer eyJhbGc...   # valid, non-expired token for user in tenant 'globex'

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer

{ "error": "you may not delete users in another tenant" }
```

<Quiz
  id="02-status-codes-real-code-2"
  lessonSlug="02-status-codes-real"
  lang="en"
  question="The token is valid; the caller simply lacks permission for another tenant. What is wrong with this response, and what should it be?"
  choices={[
    { label: "The code should be 403 Forbidden, not 401. The body even says 'may not' (authorization), but 401 means 'I don't know who you are' (authentication). 401 + WWW-Authenticate sends an authenticated client into a pointless re-login/token-refresh loop that can never grant access.", correct: true },
    { label: "401 is correct because the request was rejected for auth reasons.", misconception: "401 and 403 are both auth-related but mean different things. 401 = not authenticated (fix: log in / refresh). 403 = authenticated but not allowed (no credential change helps). The token is valid here, so it is 403." },
    { label: "It should be 400 Bad Request — the delete is not allowed.", misconception: "The request is well-formed; nothing about its syntax is wrong. The problem is permission, not structure. 400 would tell the client to fix the request shape, which is irrelevant." },
    { label: "It should be 409 Conflict because two tenants clash.", misconception: "There is no resource-state conflict — the user exists and the request parsed. The caller is simply not permitted. That is 403, not 409." },
  ]}
/>

## Exchange 3 — 503 without Retry-After, and a hot retry loop

```http
GET /catalog/items?page=3 HTTP/1.1

HTTP/1.1 503 Service Unavailable
Content-Type: application/json

{ "error": "overloaded, shedding load" }

# client behaviour: immediately re-issues the GET in a tight loop, no delay
```

<Quiz
  id="02-status-codes-real-code-3"
  lessonSlug="02-status-codes-real"
  lang="en"
  question="The server is shedding load with 503 but sent no Retry-After, and the client retries instantly. What are the two fixes — one per side?"
  choices={[
    { label: "Server side: 503 should carry a Retry-After header so clients know when to come back. Client side: when Retry-After is absent, retry with exponential backoff plus jitter — never a tight instant loop, which turns the overload into a self-inflicted thundering herd that keeps the server down.", correct: true },
    { label: "Only the client is at fault; the server's 503 is complete as-is.", misconception: "503 is the one 5xx that should carry Retry-After precisely so clients back off intelligently. Omitting it leaves clients guessing — the server shares the blame for the storm." },
    { label: "Only the server is at fault; an instant retry loop is acceptable client behaviour.", misconception: "Even without Retry-After, hammering a known-overloaded server with zero delay is the textbook way to keep it overloaded. The client must back off with jitter regardless." },
    { label: "The GET should not be retried at all because retries are unsafe.", misconception: "GET is idempotent, so retrying is safe and correct on a 503 — the issue is the timing (instant loop) and the missing Retry-After, not whether to retry." },
  ]}
/>

## Exchange 4 — conditional update and 412

```http
PUT /docs/42 HTTP/1.1
If-Match: "v7"
Content-Type: application/json

{ "title": "Q3 plan", "body": "..." }

HTTP/1.1 412 Precondition Failed

# the stored ETag is now "v9" — someone else saved twice since the client last read
```

<Quiz
  id="02-status-codes-real-code-4"
  lessonSlug="02-status-codes-real"
  lang="en"
  question="The conditional PUT returns 412 because the ETag moved from v7 to v9. What does this tell the client, and what should it do?"
  choices={[
    { label: "The optimistic-concurrency check failed: the resource changed since the client read it, so the server refused to overwrite a newer version (preventing a lost update). The client should refetch /docs/42, get the new ETag and content, reconcile its edit against v9, then retry the PUT with `If-Match: \"v9\"`.", correct: true },
    { label: "412 means the request body was malformed; resend with corrected JSON.", misconception: "412 is about the precondition header (If-Match) evaluating false, not the body. The body parsed fine. The fix is to refetch and update the precondition, not to repair JSON." },
    { label: "412 means the document was deleted; treat it as 404.", misconception: "412 says the precondition did not hold (the ETag moved), which means the resource still exists but changed. A deletion would surface differently. Refetch to see the current state." },
    { label: "Drop the If-Match header and PUT again so it always succeeds.", misconception: "Dropping If-Match defeats the optimistic-concurrency protection and silently overwrites someone else's v8/v9 changes — the exact lost-update bug the precondition prevents. Reconcile against the new version instead." },
  ]}
/>

<Recap lang="en">
On the wire, read the status line, headers, and body as one unit. A 200 with an error body lies to every machine that branches on status — return the real 5xx. 401 vs 403 turns on authentication vs authorization, and getting it wrong loops the client. A 503 should carry Retry-After, and a client without one must back off with jitter rather than hammer. A 412 is optimistic concurrency working — refetch, reconcile against the new ETag, and retry the conditional write rather than forcing the overwrite.
</Recap>
