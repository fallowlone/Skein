  lang="en"
  question="A plain view never goes stale, yet teams reach for a materialized view anyway. What is the single thing a materialized view buys, and what does it cost in exchange?"
  choices={[
    { label: "It serves reads from a stored result set (a cheap scan or index lookup) instead of re-running the defining query each read; in exchange you take on staleness and the duty to refresh.", correct: true },
    { label: "It makes the defining query itself run faster against the base tables.", misconception: "The base query is unchanged — it still runs in full at refresh time. What changes is that reads no longer trigger it; they hit stored rows. The cost moves from read-time to refresh-time, it does not vanish." },
    { label: "It guarantees the data is always current without re-running the query.", misconception: "That is a plain view, which re-executes every read and is therefore always fresh. A materialized view is stale the instant a base row changes after the last refresh." },
    { label: "It removes the need for indexes on the base tables.", misconception: "Base-table indexing is orthogonal; the MV is a stored copy of a result, not a substitute for it — and CONCURRENTLY refresh actually requires a unique index on the view itself." },

<Quiz
  id="04-materialized-views-choice-2"
  lessonSlug="04-materialized-views"
  lang="en"
  question="An analyst dashboard reads a materialized view constantly. Ops runs a nightly plain REFRESH MATERIALIZED VIEW (no CONCURRENTLY) on a 90-second aggregate. Users report the dashboard hangs every night. Why, and what is the fix?"
  choices={[
    { label: "Plain refresh holds an ACCESS EXCLUSIVE lock for its whole duration, so every read of the view blocks for ~90s. Add a UNIQUE index on the view and switch to REFRESH ... CONCURRENTLY so readers keep seeing the old version during the rebuild.", correct: true },
    { label: "The refresh empties the view first, so reads return no rows until it repopulates.", misconception: "Refresh does not expose an empty window; readers block on the lock rather than seeing partial or empty data. CONCURRENTLY is what lets the old rows stay readable during the swap." },
    { label: "Move the refresh to a read replica so the primary is not locked.", misconception: "A materialized view is refreshed where it lives; you cannot offload the refresh of a primary's MV to a replica. The lock is the issue, and CONCURRENTLY removes the read-blocking — not replica routing." },
    { label: "Raise work_mem so the aggregate finishes faster and the lock is shorter.", misconception: "Tuning may shave seconds but the read-blocking lock is structural to plain refresh. Even a fast refresh blocks reads; CONCURRENTLY changes the lock behaviour, not just the duration." },
  ]}
/>

<Quiz
  id="04-materialized-views-choice-3"
  lessonSlug="04-materialized-views"
  lang="en"
  question="Your team switched to REFRESH MATERIALIZED VIEW CONCURRENTLY to stop read-blocking. Refreshes now sometimes never complete and a backlog builds. What is the most likely cause?"
  choices={[
    { label: "CONCURRENTLY waits for in-flight transactions to drain before it starts, and only one refresh runs against a view at a time. A steady stream of long analytical queries keeps stalling the refresh, so refreshes queue behind each other and never catch up.", correct: true },
    { label: "CONCURRENTLY does not actually require a unique index, so it silently falls back to a slow path.", misconception: "It hard-requires a UNIQUE index (plain columns, no expressions, no WHERE) and errors without one — it does not silently fall back. The stall comes from waiting on old transactions and self-serialization, not a missing index." },
    { label: "CONCURRENTLY allows multiple refreshes in parallel, so they deadlock against each other.", misconception: "The opposite: only one refresh can run against a given view at a time. There is no parallel-refresh deadlock; a second refresh simply queues behind the first." },
    { label: "Concurrent refresh recomputes faster than plain refresh, so it over-schedules.", misconception: "CONCURRENTLY is generally slower than a plain refresh because it diffs the new result against the existing rows. Its slowness plus waiting on long transactions is exactly what builds the backlog." },
  ]}
/>

<Quiz
  id="04-materialized-views-choice-4"
  lessonSlug="04-materialized-views"
  lang="en"
  question="A fact table ingests ~5,000 inserts/sec; analysts read an aggregate MV all day and tolerate ~5 minutes of staleness. Someone proposes pg_ivm incremental maintenance so the view is always fresh. Why is that the wrong call?"
  choices={[
    { label: "pg_ivm installs AFTER triggers that compute and apply a delta inside each write transaction. At 5,000 inserts/sec every write pays that overhead and contends on view locks, throttling ingest — to buy zero staleness when the consumer already accepts 5 minutes.", correct: true },
    { label: "pg_ivm cannot maintain aggregate views at all, so it would error on the dashboard query.", misconception: "pg_ivm supports a meaningful subset including aggregates (with SQL restrictions). The problem is not capability; it is the per-write cost under a 5,000/sec write rate, which is the dominant cost path." },
    { label: "Incremental maintenance is the wrong shape for read-heavy tables.", misconception: "Read-heavy is exactly where IVM shines — reads stay cheap and fresh. The disqualifier here is the high write rate, not the read pattern." },
    { label: "pg_ivm only works on a single base table, and a join-aggregate uses several.", misconception: "pg_ivm installs triggers on every base table in the query and handles multi-table views. The high write rate, not the table count, is what makes it the wrong fit here." },
  ]}
/>

  lang="en"
  question="A materialized view showed yesterday's numbers all morning. The nightly refresh cron had failed on a lock timeout six days earlier and nothing alerted. What is the real lesson?"
  choices={[
    { label: "An unmonitored refresh fails open: reads keep succeeding against the last good snapshot, so the system looks green while the data is silently wrong. Own the refresh — alert on success/duration and expose a last-refreshed timestamp so staleness is detectable.", correct: true },
    { label: "Materialized views are inherently unreliable; use a plain view to avoid the failure mode.", misconception: "A plain view re-runs the expensive aggregate on every read, reintroducing the latency the MV existed to solve. The fix is owning and monitoring the refresh, not abandoning materialization." },
    { label: "The refresh should have thrown an error to the dashboard so users saw it.", misconception: "Refresh failures do not surface to readers — reads succeed against stale stored rows.     { label: "A lock timeout means the database was corrupted and needs recovery.", misconception: "A lock timeout just means the refresh could not acquire its lock in time; the stored data is intact, only frozen. The defect is the missing alert on the failed job." },
  ]}

<Recap lang="en">
The through-line of the unit is one decision sequence: confirm the read is genuinely expensive and repeated, bound the staleness the consumer tolerates, then pick refresh to match the write-rate — scheduled REFRESH CONCURRENTLY for minute-scale staleness, incremental (pg_ivm) only for read-heavy low-write tables, streaming MVs to remove the refresh job entirely. Every strategy carries a hidden cost: CONCURRENTLY needs a unique index and waits on old transactions, incremental taxes every write, ClickHouse MVs see only the inserted block. And the failure mode that recurs everywhere is the same — an unmonitored refresh serves stale data while the system looks green, so own it and alert on it.
</Recap>
