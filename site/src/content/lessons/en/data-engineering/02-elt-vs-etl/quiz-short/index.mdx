    { q: "Explain why the industry flipped from ETL to ELT, and what you gave up in the trade.", a: "The flip was enabled by cloud warehouses (Snowflake, BigQuery) decoupling storage from compute. Storage became cheap object storage, so landing all the raw data costs almost nothing; compute became elastic, so you only pay when a transform actually runs. That removed the old constraint that forced you to transform before load. What you give up: the transform cost now lands on the metered warehouse bill instead of a cluster you owned; raw PII physically lands before you can mask it; and schema enforcement moves from load-time (schema-on-write) to your own downstream tests (schema-on-read). For most data the trade is worth it; for hard compliance lines on PII, ETL's transform-before-load still wins." },
    { q: "What is replayability, and why is it the deepest reason ELT became the default — deeper than cost?", a: "Replayability is the ability to re-derive any downstream table from preserved raw input. In ETL the raw source data is discarded after transformation; the warehouse holds only the transformed output. So when you find a transform bug — a wrong join key, a timezone error — you cannot fix history; you must re-extract from a source that may have changed, rate-limited you, or dropped the old rows. In ELT the raw data lives permanently in the warehouse, so a transform bug is a one-line SQL fix plus a re-run against data you already have. Cost savings are real but secondary; replayability is what makes ELT pipelines durable and correctable, which is why it is the decisive advantage." },
    { q: "Describe the medallion architecture and the one contract that keeps it sound.", a: "Medallion is a three-layer ELT structure. Bronze is raw, append-only ingested data, never mutated. Silver is cleaned, conformed, deduplicated tables where schema is actually enforced. Gold is business-ready aggregates and marts that BI reads. Each layer is rebuildable from the one below it, and bronze is rebuildable from the source only as a last resort. The contract that keeps it sound: never mutate bronze, always transform forward. As long as bronze is immutable and every downstream layer is a pure function of the layer below, you can rebuild silver and gold at will after any transform fix — which is exactly the replayability ELT promises." },
    { q: "Where did the cost go when the industry moved to ELT, and what is the single most expensive mistake?", a: "ELT does not make transformation free — it moves the cost from a CapEx cluster you owned to a metered OpEx line on the warehouse bill (per warehouse-second on Snowflake, per byte scanned on BigQuery). That line is brutally sensitive to how you write SQL. The most expensive mistake is a model materialized as a full table rebuild, scheduled frequently, scanning everything every run — e.g. SELECT * over an unpartitioned 2 TB fact table run hourly, which is a four-figure monthly line item by itself. The fix is incremental materialization, plus per-team warehouses and auto-suspend on idle so heavy transforms do not starve BI or bleed credits doing nothing." },
    { q: "What does it mean for a load to be idempotent, why must warehouse loads be idempotent, and how do you achieve it in dbt?", a: "Idempotent means running the load twice produces the same result as running it once. Warehouse loads must be idempotent because EL tools (Fivetran, Airbyte) and your own loaders retry on transient failure by design — that is correct behaviour — so any non-idempotent load will eventually re-run a partially-succeeded batch and insert the same rows twice, inflating totals and destroying trust in the dashboard. In dbt you achieve it with an incremental model using incremental_strategy='merge' and a unique_key (e.g. event_id): merge updates the row if the key already exists and inserts only if it does not, so a re-run upserts in place instead of appending. The classic trap is an incremental model with no unique_key and no is_incremental() filter — dbt silently appends its whole output every run, duplicating rows and re-scanning everything." },
    { q: "How do you run a 90-day backfill safely after fixing a transform bug, and why are microbatch models the right tool?", a: "A backfill re-derives historical output from preserved raw data — which ELT makes possible because bronze still holds it. The naive approach, a single full-refresh over 90 days, runs as one long transaction: it can hit timeouts, and any failure discards all progress. Microbatch models split the range into independent time-window batches (e.g. one per day), each atomically replacing its own window. A failed day reruns in isolation without touching its neighbours, batches can run in parallel, and re-running the same window is idempotent. So the backfill becomes restartable and bounded per batch — you resume from the failed day instead of restarting the whole 90 days." },

<Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: decoupled storage/compute enabled the flip; replayability (not cost) is its deepest payoff; the medallion contract — immutable bronze, transform forward — is what makes replay sound; the cost moved onto the metered warehouse so you go incremental by default; every load must be idempotent (merge on a unique_key) because loaders retry; and microbatch turns a long backfill into restartable, independent, idempotent units. Now when you see a pipeline failure in production, you'll automatically ask: was the load idempotent, was the model incremental, and is the backfill structured as bounded per-batch units — because those three questions cover the root cause of most ELT incidents.
</Recap>
