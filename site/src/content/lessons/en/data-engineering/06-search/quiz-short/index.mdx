First, the leading wildcard means no B-tree index can help, so the database scans every row and runs a substring match — cost grows linearly with table size and times out at scale. Second, it matches substrings of bytes, not words of language: 'running' will not match 'run', 'Run', or 'runs', and it has no notion of relevance, so a footer mention ranks identically to a title repeated three times. Full-text search replaces both halves. The inverted index solves finding — turning a linear scan into a dictionary lookup. You need both: finding everything but ranking badly is as useless as ranking perfectly but being too slow to run." },
    { q: "Describe the inverted index and what makes a query fast on it regardless of corpus size.", a: "A forward index maps a document to its words; an inverted index maps the other way — each term points to a posting list of the document ids that contain it, usually with positions and term frequencies attached. A query like 'running shoes' becomes: look up the posting list for 'running', look up the posting list for 'shoes', and intersect the two sorted id lists. That is two dictionary lookups and a merge — milliseconds regardless of corpus size, because you never touch documents that do not contain the terms. This is the structure inside Postgres tsvector/GIN and inside Lucene (under Elasticsearch and OpenSearch). The hard part is not the lookup; it is deciding what counts as a term, which is the analysis pipeline's job." },
    { q: "What does an analyzer do, and why must the same analyzer run at index time and query time?", a: "An analyzer turns raw text into the normalized tokens that go into the index: tokenize, lowercase, drop stopwords, then stem or lemmatize. 'The Runners Were Running' becomes roughly [run, run] after splitting, lowercasing, dropping 'the'/'were', and stemming to the root. That is why full-text search matches singular and plural where LIKE cannot — matching happens on normalized tokens, not raw strings. The iron rule is that the same analyzer must run on both sides: if documents are stemmed to 'run' at index time but the query for 'running' is not stemmed, the lookup is for a token that was never written, and you get zero results silently, with no error. The diagnostic is the same tool that prevents it — Elasticsearch's _analyze API or Postgres to_tsvector — which shows the exact tokens each side produces so you can spot the mismatch." },
    { q: "Explain why search moved from TF-IDF to BM25, and what the k1 and b knobs control.", a: "TF-IDF's intuition is sound — a term matters more the more often it appears in a document (term frequency) but less if it is common across the whole corpus (inverse document frequency). Its flaw is that raw term frequency grows without bound, so a doc repeating 'shoes' 200 times would dominate. BM25 fixes this by saturating term frequency — the 10th occurrence adds far less than the 2nd — and by normalizing for document length so a long article is not boosted just for being long. It has two knobs: k1 (default 1.2 in Elasticsearch/Lucene) controls how fast term frequency saturates, lower saturating sooner; b (default 0.75) controls how strongly document length is normalized, with 0 ignoring length entirely and 1 normalizing fully. You tune them by measuring relevance against judged queries — never by vibes, because a change that helps one query class can silently regress another." },
    { q: "When is Postgres tsvector/GIN the right default, what pushes you to a dedicated engine, and how do you choose GIN vs GiST inside Postgres?", a: "Postgres FTS is the right default when the data already lives in Postgres, the corpus is moderate, writes are not extreme, and you need keyword matching with basic relevance — because there is no second system to deploy, secure, monitor, or keep consistent through dual writes. You move to Elasticsearch or OpenSearch when you need real BM25 tuning per field, faceting and aggregations, built-in fuzzy/typo tolerance, near-real-time indexing at high write volume, or horizontal scale-out — and you accept a cluster to run plus a sync pipeline as the cost. Inside Postgres, GIN looks up roughly 3x faster but is slower to build, larger on disk, and slower to update — and under high write with fastupdate=on its pending list bloats the index. GiST is smaller and faster to update but lossy, so it rechecks the table on matches. Rule of thumb: GIN for read-heavy, mostly-static text; GiST when writes are constant or index size hurts." },

Elasticsearch's refresh_interval defaults to 1s, so a freshly indexed document is not searchable for up to a second; under heavy bulk loads you raise it to 30s or set it to -1 and refresh once at the end, trading visibility latency for throughput. The trap is assuming write-then-read consistency you do not have. The bigger operational tax is the reindex-the-world migration: Lucene will not let you change the type or analyzer of an existing field because the tokens are already committed, so fixing a stemming bug or adding a synonym filter across hundreds of millions of docs means building a new index, reindexing everything into it (hours), and swapping a read alias from old to new.
