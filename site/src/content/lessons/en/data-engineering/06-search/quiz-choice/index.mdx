<Quiz
  id="06-search-choice-2"
  lessonSlug="06-search"
  lang="en"
  question="Why did modern engines move from raw TF-IDF to BM25 for term-frequency scoring?"
  choices={[
    { label: "BM25 saturates term frequency — the 10th occurrence adds far less than the 2nd — and normalizes for document length, so a doc spamming a term 200 times or a long article cannot dominate on raw counts.", correct: true },
    { label: "BM25 is much faster to compute at query time than TF-IDF.", misconception: "Speed is not the motivation; both are cheap once the posting lists are merged. BM25 is a relevance refinement, not a performance one." },
    { label: "BM25 removes the need for an inverted index.", misconception: "BM25 scores the candidates the inverted index already produced. It ranks the index's output; it does not replace the index." },
    { label: "BM25 makes the analysis pipeline unnecessary.", misconception: "Stemming and tokenization happen before scoring. BM25 scores whatever tokens analysis produced — the two stages are independent." },
  ]}
/>

  question="A SaaS app on Postgres needs search over ~2M support tickets: keyword match, basic relevance, modest writes, low ops budget. What is the right default?"
  choices={[
    { label: "Add a tsvector column with a GIN index and rank with ts_rank. The data already lives in Postgres, so there is no second system to deploy or keep in sync, and 2M rows with modest writes is well inside GIN's comfort zone.", correct: true },
    { label: "Stand up an Elasticsearch cluster and dual-write every ticket to it.", misconception: "Over-engineered for these constraints. ES earns its keep on faceting, fuzzy matching, tunable BM25, or scale-out — none required here — at the cost of a cluster to operate and a dual-write consistency problem." },
    { label: "Keep LIKE '%term%' but add a B-tree index on the column.", misconception: "A leading-wildcard LIKE cannot use a B-tree, so you still scan all 2M rows, with no stemming, no case-folding, and no relevance. This is the exact problem full-text search replaces." },
    { label: "Use GiST instead of GIN for the tsvector index.", misconception: "GiST shines under constant writes or hard disk limits; here reads dominate and writes are modest, which is GIN's sweet spot — GIN looks up roughly 3x faster, and GiST's lossiness forces table rechecks." },
  ]}
/>

  question="You picked GIN for a tsvector index. Months later, on a now write-heavy table, search latency degrades intermittently with no query change. What is the most likely mechanism?"
  choices={[
    { label: "GIN bloat under high write: with fastupdate=on, inserts batch into a pending list that periodically flushes, and the index grows and degrades until a REINDEX or autovacuum tuning rescues it. A query can stall when the pending list flushes.", correct: true },
    { label: "BM25 k1/b drifted because the corpus grew.", misconception: "k1 and b are static configuration; they do not drift with corpus size, and Postgres ts_rank does not use BM25 by default anyway. The symptom is write-driven index health, not scoring." },
    { label: "ts_rank got slower because there are more matching documents.", misconception: "More candidates add some ranking cost, but intermittent degradation tied to write volume points squarely at GIN's pending-list flush and bloat, not at ranking arithmetic." },
    { label: "The analyzer changed, so tokens no longer match.", misconception: "An analyzer change would cause wrong or empty results, not intermittent latency that tracks write volume. This is an index-maintenance failure mode, not a tokenization one." },
  ]}
/>

  id="06-search-choice-5"
  lessonSlug="06-search"
  lang="en"
  question="An Elasticsearch service writes a document and immediately reads it back by search, intermittently getting a miss. The team assumed write-then-read consistency. What is happening?"
  choices={[
    { label: "Elasticsearch is near-real-time, not instantly consistent: a freshly-indexed doc is not searchable until the next refresh (refresh_interval defaults to 1s). The miss is the refresh window, not a lost write.", correct: true },
    { label: "The document failed to index and was silently dropped.", misconception: "An intermittent miss that resolves within ~1s is the refresh window, not a drop. A dropped write would never become searchable; this one does, a beat later." },
    { label: "BM25 ranked the document below the result cutoff.", misconception: "Ranking position cannot make a document briefly invisible and then visible with no data change. The visible-then-not timing is the refresh interval signature." },
    { label: "The GIN index has not been built yet.", misconception: "GIN is a Postgres structure; Elasticsearch uses Lucene segments. The behaviour described is Lucene's refresh-to-searchable latency, by design." },
  ]}
/>

<Quiz

  question="You need to fix a stemming bug by changing an existing field's analyzer across 200M documents in Elasticsearch. What is the correct migration, and why?"
  choices={[
    { label: "Build a new index with the corrected mapping, reindex everything into it, then atomically swap a read alias from old to new.     { label: "Update the field mapping in place and let Elasticsearch re-tokenize lazily.", misconception: "Lucene cannot change the analyzer or type of an existing field — the committed tokens are immutable. There is no lazy re-tokenize; you must build a new index." },
    { label: "Drop and recreate the index, accepting a brief downtime window.", misconception: "Dropping the live index means clients see empty or failing search until reindex completes — hours at 200M docs. Designing behind a read alias avoids the outage entirely." },
    { label: "Raise refresh_interval so the analyzer change propagates faster.", misconception: "refresh_interval controls write-to-searchable latency, not analyzer changes. It has nothing to do with re-tokenizing already-committed documents." },
  ]}

<Recap lang="en">
The through-line: matching is tokens, not strings, so the same analyzer must run at index and query time or you get silent zero results; BM25 ranks the candidates the inverted index produces by saturating term frequency and normalizing length; Postgres GIN is the right default until you need facets, fuzziness, BM25 tuning, or scale, at which point GIN's write-bloat versus GiST's lossiness is the inside choice; and the operational traps — near-real-time refresh latency and the immutable-tokens reindex — are why you design behind a read alias from day one. Now when you see an analyzer-mismatch incident or a GIN-bloat alert, you know which lever to reach for before touching anything else.
</Recap>
