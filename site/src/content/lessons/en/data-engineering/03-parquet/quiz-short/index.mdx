First, column pruning: because Parquet is columnar, all values of one column sit together in a column chunk, so a query needing two of forty columns reads only those two chunks and never touches the rest — CSV is row-oriented, so reading any column means walking every byte of every row and parsing delimiters. Second, row-group skipping via predicate pushdown: the footer stores min/max/null-count statistics per column per row group, so for WHERE day = '2024-02-01' the engine checks each row group's day range and skips any group whose range can't contain the value without reading a data byte; optional page-level stats push this one level deeper.     { q: "Describe the physical nesting inside a Parquet file, from the file down to the encoded values.", a: "A Parquet file nests in four levels and ends with a footer. The file is split into row groups — horizontal slices of rows with a default target around 128 MB. Within each row group, every column is stored as a contiguous column chunk, so all values of one column are physically together. Each column chunk is split into pages, the unit of encoding and compression, around 1 MB by default. The page values are first encoded by type (dictionary, RLE, bit-packing, delta) and then compressed by a general-purpose codec (snappy, zstd, gzip). The footer at the end holds the schema plus per-row-group, per-column metadata including the min/max/null-count statistics that drive pushdown — which is why a reader opens the footer first." },
    { q: "How do encoding and compression differ in Parquet, and why keep them mentally separate?", a: "They are two stacked, distinct layers. Encoding is type-aware and structural: dictionary encoding replaces repeated values with small integer codes (great for low-cardinality strings), RLE collapses runs of identical values, bit-packing uses only as many bits as the value range needs, and delta encoding stores differences for sorted integers and timestamps. Compression is a general-purpose byte codec — snappy, zstd, or gzip — run over the already-encoded bytes. Keeping them separate matters because they have different knobs and different failure modes: dictionary blowup on a high-cardinality column is an encoding problem fixed by disabling the dictionary, while slow reads from gzip is a compression-codec problem fixed by switching to snappy or zstd. Encoding alone often delivers much of the size win before any codec runs." },
    { q: "What is the small-files problem, why does it cripple query planning, and how do table formats help?", a: "It happens when a job — usually a streaming writer flushing on a short interval — produces enormous numbers of tiny Parquet files instead of a few large ones. Each file carries its own footer and costs one I/O just to open. Before an engine plans a query it must list the files and read each footer for statistics; on cloud object stores, recursively listing millions of objects is slow and expensive, and reading millions of footers dominates planning, so the query is slow before scanning any data. The fix is compaction: a periodic background job rewrites the swarm into files of 128 MB to 1 GB. Table formats — Iceberg, Delta Lake, Hudi — address it directly: they keep data in Parquet but add a manifest layer tracking the current file set with per-file stats, so the engine prunes whole files before opening any footer, and they ship compaction plus ACID commits, snapshots, and metadata-only schema evolution." },

Too large and you lose skipping granularity (a filter can only skip whole groups, so a giant group is rarely skippable) and you need a lot of memory to buffer one group while writing. Too small and metadata and footer overhead balloon: the engine reads more footers than data, planning cost dominates, and you drift toward the small-files problem even within one file. The right size depends on column width and the typical filter selectivity — narrower, more selective filters benefit from smaller groups for finer skipping, while wide scans prefer larger groups for fewer footer reads." },

There's no single source of truth for the table's current schema or which files belong to it. Table formats fix this with a metadata layer that tracks schema by stable column IDs rather than names, so a rename is a metadata-only operation instead of a full data rewrite, and the manifest records exactly which files and which schema version are current. That gives safe, atomic schema evolution plus time travel to read the table as of an earlier schema." },

<Recap lang="en">
If you could reconstruct each answer from memory you hold the unit's spine: Parquet is columnar and self-describing, so pruning and pushdown read only what a query needs — but only when data is clustered by the filter columns. The file nests file to row group to column chunk to page, and each page is encoded (a structural, type-aware layer) then compressed (a byte codec) — two separate wins with separate failure modes. Row-group size is a real knob with bad extremes both ways, the small-files problem is fixed by compaction, and because raw Parquet has no transactions or stable schema identity, table formats wrap it with a manifest for ACID, safe schema evolution, time travel, and file-level pruning. Now when you open a slow lake table in production, you will reach for footer stats, clustering, and the access path first — not hardware.
</Recap>
