## Snippet 1 — pushdown lost in the engine

```python
import pyarrow.parquet as pq

# events/ is a year of daily Parquet files, sorted by `day`
table = pq.read_table("s3://lake/events/")      # reads everything
df = table.to_pandas()
df = df[df["day"] == "2024-02-01"]               # filter after the read
result = df[["user_id", "country"]]              # project after the read
```

## Snippet 2 — the writer config

```python
import pyarrow.parquet as pq

# one batch write of ~50 GB, queried almost always by `country`
pq.write_table(
    table,
    "s3://lake/events_2024.parquet",
    row_group_size=2048,        # rows per row group
    compression="snappy",
    write_statistics=True,
)
```

The defect is row-group granularity — 2048 rows per group means metadata overhead dominates. Codec choice is orthogonal to row-group sizing." },
    { label: "write_statistics=True bloats the file; turning stats off makes it faster.", misconception: "Statistics are exactly what enables row-group skipping — turning them off removes pushdown entirely and makes filtered queries scan everything. The problem is the tiny row-group size, not the presence of stats." },
    { label: "Writing a single 50 GB file is fine; row-group size has no effect on read performance.", misconception: "Row-group size is a primary read-performance knob: too small and metadata/footer reads dominate; too large and you lose skipping granularity and need huge write memory. 2048 rows is far too small." },

## Snippet 3 — column projection vs SELECT *

```sql
-- DuckDB over a wide 120-column Parquet table on S3
SELECT *
FROM read_parquet('s3://lake/wide_events/*.parquet')
WHERE country = 'DE';
```

<Quiz
  id="03-parquet-code-3"
  lessonSlug="03-parquet"
  lang="en"
  question="An analyst only needs user_id and amount but runs SELECT * on a 120-column table. What is the cost, and the fix?"
  choices={[
    { label: "SELECT * defeats column pruning: the engine reads all 120 column chunks from every surviving row group, even though only two are needed. List the columns (SELECT user_id, amount) so only those two chunks are read — projection is half of why Parquet is fast.", correct: true },
    { label: "SELECT * is fine on Parquet because columnar storage means unused columns cost nothing to read.", misconception: "Columns cost nothing only when you don't select them. SELECT * selects all of them, so every column chunk in every matching row group is read — exactly the case column pruning was meant to avoid." },
    { label: "The WHERE country = 'DE' already limits I/O, so the column list is irrelevant.", misconception: "The predicate limits which row groups are read (row dimension); the projection limits which columns are read (column dimension). They're independent — SELECT * still reads all 120 columns of every surviving row group." },
    { label: "Adding a LIMIT clause would prune the columns automatically.", misconception: "LIMIT caps row output after scanning; it doesn't reduce the set of columns read per row group. Only naming the columns enables column pruning." },
  ]}
/>

## Snippet 4 — dictionary fallback

```python
# a column of high-cardinality session UUIDs, ~10M near-unique values
pq.write_table(
    table,                       # contains a `session_id` UUID column
    "s3://lake/sessions.parquet",
    use_dictionary=True,         # on by default
    compression="zstd",
)
```

<Quiz
  id="03-parquet-code-4"
  lessonSlug="03-parquet"
  lang="en"
  question="The session_id column ends up barely smaller than plain bytes and write CPU is high. What happened?"
  choices={[
    { label: "Dictionary encoding only pays when values repeat. With ~10M near-unique UUIDs the per-column dictionary grows past its page-size budget, Parquet falls back to plain encoding for that column, and you paid to build a dictionary that bought nothing. Disable use_dictionary for that column (or store UUIDs as fixed-width binary).", correct: true },
    { label: "zstd can't compress UUIDs, so the file stays large no matter what.", misconception: "zstd still compresses the bytes somewhat; the wasted work is the dictionary build that overflowed and was discarded. The encoding-layer fallback, not the codec, is the story here." },
    { label: "use_dictionary=True corrupted the column by truncating long UUIDs.", misconception: "No truncation or corruption occurs — Parquet cleanly falls back to plain encoding when the dictionary overflows. The symptom is wasted CPU and no size win, not bad data." },
    { label: "The fix is a larger row_group_size so the dictionary has more room.", misconception: "A bigger row group gives the dictionary more values to absorb, making the cardinality problem worse, not better. The fix is to not dictionary-encode a near-unique column at all." },
  ]}
/>

<Recap lang="en">
Every slow Parquet query is read in the access path and the writer config: push the predicate and the column list into the reader or neither row-group skipping nor column pruning fires; size row groups by bytes toward ~128 MB-1 GB and cluster by the filter column so its ranges are skippable; SELECT * silently reads every column chunk, so always project; and dictionary encoding on a high-cardinality column overflows and falls back to plain, costing CPU for no size win. Diagnose from where the filter and projection land, fix the layout, then re-measure the bytes scanned. Now when you see a slow Parquet query in a code review, your first two questions are: where does the predicate land — in the reader or after materialisation — and did the writer cluster and size the row groups for this access pattern?
</Recap>
