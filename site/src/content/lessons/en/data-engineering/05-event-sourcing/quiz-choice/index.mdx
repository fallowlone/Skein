  choices={[
    { label: "Because they are pure derivations of the log — drop the table, replay the events, get it back. That means you can introduce a brand-new view months later by writing a projection and replaying history through it; the data was always in the log.", correct: true },
    { label: "Because read models are backed up nightly, so a drop is always recoverable from the backup.", misconception: "Disposability comes from being re-derivable by replay, not from backups. A backup restores an old shape; replay can build entirely new shapes the backup never had." },
    { label: "Because projections store the only copy of the events, so deleting them is reversible.", misconception: "Projections store derived state, never the authoritative events. The events live in the append-only store; the projection is a throwaway materialization of them." },
    { label: "Because CQRS forbids ever changing a read model once built.", misconception: "CQRS does the opposite — it lets you freely add, drop, and rebuild read models precisely because they are derived and disposable." },

<Quiz
  id="05-event-sourcing-choice-4"
  lessonSlug="05-event-sourcing"
  lang="en"
  question="Loading one aggregate folds 4 million events and is too slow. You add snapshots. What is the one failure mode a senior guards against?"
  choices={[
    { label: "Snapshot drift: if the snapshot diverges from the events (logic changed, a write was lost), it silently serves wrong state and masks the bug because replay never re-derives from scratch. Defend by checksumming snapshots and rebuilding on mismatch.", correct: true },
    { label: "Snapshots break the append-only invariant because they are written into the event stream.", misconception: "Snapshots are stored separately (a snapshot store or a side stream), not by mutating events. They are a pure read-path optimization and leave the log untouched." },
    { label: "Snapshots make replay impossible, so you lose temporal queries.", misconception: "Snapshots are an optimization layered on top of replay — you read the snapshot at version N then replay events after N. Full replay from genesis is still always available." },
    { label: "Snapshots must be taken after every single event or they are useless.", misconception: "Snapshots are taken periodically (every N events or on a schedule); their whole value is amortizing the fold cost, not capturing every event." },
  ]}
/>

  question="OrderPlaced gains a required currency field. Millions of historical OrderPlaced events lack it. What is the standard approach?"
  choices={[
    { label: "Upcasting: register a transformation that lifts the old event shape to the new one at deserialization time (e.g. default currency to USD for legacy events), so the rest of the code only ever sees the current version. History is never rewritten.", correct: true },
    { label: "Run a migration that updates every historical OrderPlaced event in place to add the field.", misconception: "Mutating past events violates the append-only invariant, breaks every downstream replay and audit guarantee, and invalidates version-based concurrency. <Recap lang="en">
The through-line of the unit is one inversion and its consequences: the append-only log is the source of truth, current state is a fold, and everything else is derived. Projections are disposable read models rebuilt by replay, so reads are eventually consistent. Snapshots bound replay cost but drift silently if unguarded. Versioning is permanent — old shapes live forever, so you upcast instead of rewriting. And GDPR against an immutable log is met with crypto-shredding, with a real legal caveat. Every answer here resolves back to the same rule: never mutate the log; derive, replay, and transform around it.
</Recap>
