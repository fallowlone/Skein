    { q: "What is the single inversion that defines event sourcing, and why is it the source of every benefit and every cost?", a: "Instead of storing current state and destroying history on every UPDATE, you store the immutable, append-only stream of state-changing events as the source of truth, and derive current state as a left-fold over that log (state = events.reduce(apply, initial)). Current state becomes a disposable cache you can recompute at will. Every benefit falls out of never throwing data away: a complete audit trail (the log IS the audit), temporal queries (fold only events before a timestamp to get state as-of any past instant), and deterministic debugging by replay (copy the production stream into staging and reproduce the exact bug). And every cost falls out of the same constraint: because you never rewrite the log, schema changes are permanent (upcasting), GDPR erasure collides with immutability (crypto-shredding), replay cost grows unbounded (snapshots), and reads lag the write side (eventual consistency)." },
    { q: "A colleague says 'we publish events to Kafka, so we are event-sourced.' Why may that be false, and what would actually make it event sourcing?", a: "Emitting events is not event sourcing. The defining property is that the log is the authoritative source of truth and state is rebuilt by folding it — not that events are emitted as a side-channel after a database already committed the real truth elsewhere. If the service writes a row to Postgres and then publishes a notification to Kafka, the row is the truth and Kafka is just a change feed; losing the topic loses nothing canonical. To be event-sourced, appending the event must BE the write (no separate authoritative row), and you must be able to drop all derived state and rebuild it purely by replaying the log. With Kafka specifically: log compaction keeps only the latest value per key and destroys the history the pattern depends on, so you need retention-based topics with infinite retention, not compacted ones; and per-aggregate optimistic concurrency (append only at expected version N) has no clean Kafka primitive, which is why purpose-built stores like EventStoreDB make expectedVersion a first-class append condition." },
    { q: "What is CQRS in this context, why are projections disposable, and what two properties make them safe in production?", a: "You cannot serve every query by folding the whole log on each request, so event sourcing pairs with CQRS: the write side appends events; the read side runs projections that consume the stream and materialize purpose-built read models (a SQL table, a search index, a denormalized cache). Projections are disposable because they are pure derivations — drop the table, replay the log, get it back — which means you can add a brand-new view months later just by writing a projection and replaying history. Two properties make this safe. First, idempotency: at-least-once delivery and retries can deliver the same event twice, so applying it twice must equal applying it once — the standard mechanism is a per-stream version checkpoint, ignoring any event whose version is less than or equal to the last seen. Second, eventual consistency: there is real lag between an append and the projection catching up, so reads are not guaranteed current at any instant — they converge over time." },
    { q: "How do you handle read-model lag in the UI without leaking the architecture to the user?", a: "The naive fix — poll the projection until the change appears — leaks the eventual-consistency lag to the user as a flicker or a missing row. The real fix is to not read the lagging projection for that one screen at all: return the new state optimistically from the command result (you already know what you appended), or read-your-own-writes from the write side for the immediate post-action view, and let the projection settle behind the scenes for everyone else. The mental model is that lag is a UX problem to be designed around per-screen, not an infra bug to be eliminated by forcing synchronous projection updates (which would throw away the decoupling CQRS exists for)." },
    { q: "Why does replay cost grow unbounded, how do snapshots fix it, and what is the snapshot footgun?", a: "Loading an aggregate by folding its entire stream gets slower as the stream grows — a system replaying millions of events (or terabytes of ticks) can take minutes per rebuild, because cost scales with stream length. Snapshots fix this by periodically persisting the folded state at version N in a separate store; on load you read the snapshot and replay only events strictly after N (an exclusive lower bound — re-folding version N double-applies it). Snapshots are a pure performance optimization that leaves the log untouched. The footgun: if a snapshot drifts from the events it claims to summarize — apply logic changed, or a write was lost mid-stream — it silently serves wrong state AND masks the bug, because replay never re-derives from genesis to expose the discrepancy. Defensive teams checksum snapshots and rebuild on mismatch, and treat snapshots as rebuildable, never authoritative." },

Upcasting solves this without touching history: a chain of small, pure transformation functions lifts an old event shape to the next version at deserialization time, until it reaches the current shape, so domain code only ever sees the latest version. Upcasters accrete — they are code you carry indefinitely and must test against real historical payloads. GDPR's right-to-be-forgotten collides head-on with immutability: you legally must erase a user's PII but cannot rewrite the log. The dominant technique is crypto-shredding — encrypt each user's PII with a per-user key stored outside the log, and 'forget' them by destroying the key, rendering the ciphertext permanently unrecoverable while the event structure stays intact. The honest caveat: regulators may still treat undeletable encrypted PII as personal data, so it is a strong pragmatic mitigation that needs legal sign-off, not an automatic guarantee." },

<Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: one inversion (the append-only log is the truth, state is a fold) buys audit, temporal queries, and replay, and bills you in versioning, GDPR, snapshots, and eventual consistency. Event sourcing is not a Kafka topic emitted after a DB write; CQRS projections are disposable, idempotent, and eventually consistent; lag is a per-screen UX problem; snapshots bound replay but drift silently; versioning is permanent so you upcast; and GDPR is met with crypto-shredding under a legal caveat. The one rule under all of it: never mutate the log. Now when you see a system design decision that would require editing a past event — a GDPR request, a schema fix, a "just delete this bad record" — you will reach for a compensating event, upcasting, or crypto-shredding instead, and you will know why.
</Recap>
