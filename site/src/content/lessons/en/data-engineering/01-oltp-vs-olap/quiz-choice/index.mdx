  question="A query runs SUM(total) over 40M orders rows that have 50 columns each. Why does a column store crush a row store on exactly this query?"
  choices={[
    { label: "Column pruning: the column store reads only the total column — roughly 6% of the bytes a row store touches — then scans it compressed and vectorized. Pruning, compression, and batch execution stack into a 10×–1000× gap.", correct: true },
    { label: "The column store keeps a better index on total that turns the scan into a seek.", misconception: "A full-table aggregate needs most or all rows, so there is nothing selective to seek — the planner does a sequential scan regardless. The win is reading fewer columns, not an index." },
    { label: "The column store caches the whole table in RAM while the row store reads from disk.", misconception: "Neither engine is defined by caching everything. The structural win is the on-disk layout — one column contiguous — which enables pruning, compression, and vectorized scans even from disk." },
    { label: "Column stores write single rows faster, so their reads are faster too.", misconception: "Column stores are slower at single-row writes, not faster — a write touches every column file. The advantage is on column scans, an entirely different axis." },
  ]}

<Recap lang="en">
The through-line of the unit is one decision: access pattern sets layout. Point lookups and small writes want a row store; full-table scans over a few columns want a column store, where pruning (read ~6% of the bytes), 5–10× compression, and vectorized batch execution stack into a 10×–1000× gap no index can close. The classic senior failure is analytics on the prod OLTP replica, where one scan evicts the hot buffer cache, contends for I/O, and drives replica lag. The fix is architectural — a separate columnar store fed by CDC or ETL — accepting a little data latency for isolated storage, caches, and failure domains. HTAP can manage the contention but never abolishes it.
</Recap>
