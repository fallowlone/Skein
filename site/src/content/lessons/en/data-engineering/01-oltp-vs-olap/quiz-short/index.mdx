    { q: "Name the three multipliers that make a column store beat a row store on analytical queries, and roughly how big the combined gap is.", a: "(1) Column pruning — a query touching 3 of 50 columns reads roughly 6% of the bytes a row store would, because each column is stored separately. (2) Compression — one column holds values of one type and often low cardinality, so dictionary + run-length + LZ4/ZSTD reach 5–10× (30×+ on low-cardinality columns) vs 1.5–3× for a row's mixed-type pages, and less data on disk is less I/O. (3) Vectorized execution — the engine processes a column in batches of thousands of contiguous same-type values in tight SIMD-friendly loops, instead of tuple-by-tuple with a function call and branch per row. The three stack, so columnar beats a row store by roughly 10×–1000× on analytical queries." },
    { q: "A teammate asks why you can't just add an index to make the 90-day revenue aggregate fast on Postgres. Explain.", a: "An index speeds up queries that select a small fraction of rows — it turns a scan into a seek. A 90-day, all-countries SUM needs most or all rows, so there is nothing selective to seek; the planner correctly chooses a sequential scan and the index just adds write cost on every insert. Indexes fix selectivity, not scan volume. The aggregate is slow because a row store reads every byte of every row — all 50 columns — to reach the one column it sums. The real fix is a different physical layout: a column store prunes to that one column, reads it compressed at 5–10×, and scans it vectorized — orders of magnitude less I/O, which no index on a row store could match." },
    { q: "Why is running the analytics dashboard on the prod read replica an outage waiting to happen, and what's the correct architecture?", a: "A read replica is still a row store with a buffer cache sized for the transactional working set. A long analytical scan does three damaging things at once: it pulls cold pages through shared_buffers and evicts the hot OLTP pages, so transactional reads that were memory-hits start hitting disk and slow 10–100×; it consumes CPU, hash-join memory, and I/O bandwidth that are zero-sum with the transactional threads on the same engine; and by holding resources it delays WAL apply, driving replica lag up so reads return stale data. 'It's just a read' is wrong — a full-table analytical read is the most destructive kind on a transactional engine. The fix is architectural: a separate columnar OLAP store (Redshift/BigQuery/Snowflake or ClickHouse) fed continuously from OLTP via CDC (e.g. Debezium streaming the WAL into Kafka) or batch ETL/ELT, giving independent storage, caches, and failure domains. The price is a pipeline to operate and a small data-latency window — almost always worth it." },
    { q: "Why does the OLTP schema stay normalized while the OLAP target is denormalized, and why is that not a contradiction?", a: "Normalization keeps OLTP writes small and consistent: each fact lives in one place, so an UPDATE touches one row and there are no update anomalies — ideal for a write-heavy transactional table. The OLAP target denormalizes into wide fact tables so analytical scans don't pay a join on every multi-million-row query, and folds dimensions in as low-cardinality columns that dictionary-encode and compress to near-free. It's not a contradiction because integrity is enforced upstream in OLTP, and the column store's repeated low-cardinality values cost almost nothing to store. Each layout matches its workload — you do not make OLTP look like OLAP or vice versa." },

It is genuinely useful when data latency must be near-zero and operating two systems is too costly. But no production HTAP eliminates the resource contention between a scan-heavy and a write-heavy workload — it manages it (separate row and column replicas, resource groups, isolation tiers) rather than abolishing it. So the underlying tension is the same; HTAP changes where you manage it, not whether it exists. That's why the two-store split fed by CDC/ETL — with independent caches and failure domains — remains the default." },
