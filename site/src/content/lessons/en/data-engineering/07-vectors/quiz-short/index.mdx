A query running at recall 0.3 returns the same ten ranked rows, in the same few milliseconds, with no error, no warning, and no anomalous metric — it just returns the wrong ten. Classic correctness failures throw exceptions or spike latency; this one looks identical to a healthy query, so it sails through staging and only shows up as vague 'the bot can't find things' reports weeks later. The trigger is usually a too-low hnsw.ef_search (pgvector's default is 40), often made worse by a selective WHERE filter that post-filtering shreds. You detect it by measuring recall@k directly: take a sample of queries, run them with an exact ORDER BY scan with no index to get ground truth, run the same queries through the ANN index, and compute the ID-set overlap. That recall number — not latency, not row count — is what you alert on." },
    { q: "Describe the recall–latency–memory triangle and which knob moves which axis in HNSW.", a: "The three are in tension and no ANN method optimizes all at once. Memory is set mostly at build time by M (links per node): higher M means a denser graph, more RAM (the HNSW graph runs 2-5x the size of the raw vectors), and higher achievable recall. Build quality is set by ef_construction: a larger candidate pool while building gives a better graph but build time scales roughly linearly. Recall vs latency at serving time is set by ef_search: raising it from 100 to 500 might lift recall from ~85% to ~98% while latency goes from ~1ms to ~5ms. So you spend memory and build time to make high recall cheaply reachable, then dial recall against latency per query with ef_search to hit your SLO." },
    { q: "When do you choose HNSW, IVFFlat, or IVF-PQ, and what does each cost?", a: "HNSW is the default for RAG: highest recall with the least tuning, and constant-cost inserts so it does not drift as data changes — at the cost of 2-5x the raw vectors in RAM and slow builds. IVFFlat k-means-clusters vectors into lists buckets and scans only the nearest probes buckets; it fits roughly 1x the raw vectors and builds fast, but its centroids are fixed at build time so recall drifts as you insert new data, and it needs representative data present before building. IVF-PQ adds product quantization — splitting each vector into sub-vectors replaced by codebook centroid ids — compressing dramatically (NVIDIA reported 360 GiB down to 54 GiB on a billion vectors), at the price of recall loss often landing near 70% of HNSW's, recovered with a rerank step. IVF-PQ is a memory-driven choice for 100M+ vectors that will not fit in RAM, not an everyday default." },
    { q: "How do cosine, dot product, and L2 relate, and how do you choose a metric?", a: "Cosine similarity measures the angle between vectors, ignoring magnitude; dot (inner) product folds magnitude in; L2 is Euclidean distance. For normalized embeddings cosine and dot product rank identically, which is why inner product is used as the cheaper equivalent — it skips the magnitude normalization. The rule is to match the metric to how the embedding model was trained: a model trained with cosine should be searched with cosine (or dot on normalized vectors), and the index opclass (vector_cosine_ops / vector_ip_ops / vector_l2_ops) plus the query operator (<=> / <#> / <->) must agree, or the planner cannot use the index. Picking a mismatched metric silently degrades relevance." },
    { q: "Why does metadata filtering interact badly with ANN, and how does pgvector address it?", a: "pgvector does post-filtering: it walks the HNSW graph to gather ef_search candidates first, then applies your WHERE clause. If the filter is selective — say tenant_id keeps 1% of rows — most of those ef_search candidates are discarded and you can end up with almost nothing, because the graph navigated a tiny, near-disconnected subgraph; recall collapses for small partitions. pgvector 0.8.0 added hnsw.iterative_scan (strict_order or relaxed_order) that keeps pulling more candidates from the graph until enough pass the filter, trading latency back for the recall you lost. The senior habit is to recognize that a selective filter plus a default ef_search is a recall trap, and to test recall on the filtered path specifically." },
    { q: "What is hybrid search, when do you need it, and how does Reciprocal Rank Fusion combine results?", a: "Hybrid search runs lexical retrieval (BM25 keyword) and vector retrieval in parallel and fuses the two result lists. You need it because pure vector search misses exact matches: a query for an error code, SKU, or function name is a lexical need, and embeddings smear it into 'semantically near', so 'panic: nil pointer' can rank below a vaguely related paragraph. Reciprocal Rank Fusion combines by rank position rather than score: RRF = sum over lists of 1/(k + rank) with k around 60, so the two incompatible score scales (BM25 term scores vs vector distances) never have to be compared directly. Teams report jumping from ~65-78% to ~91% recall@10 by adding the keyword leg." },
