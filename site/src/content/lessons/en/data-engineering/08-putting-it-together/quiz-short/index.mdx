    { q: "Why can't one storage layout serve both the OLTP checkout path and OLAP revenue scans, and what is the standard two-store answer?", a: "OLTP wants tiny, indexed reads and writes of whole rows — find one order, update its status — which a row-oriented layout serves cheaply because a row's columns sit together on a page. OLAP wants to scan one or two columns across billions of rows — sum amount over 90 days — which a row layout serves terribly because it drags every unused column off disk too. A columnar layout stores each column contiguously so a scan reads only the columns touched and compresses them well, but it answers a single-row lookup poorly. No single layout wins both, so the standard architecture is two stores: a row-oriented OLTP system of record for the transactional path, and a columnar warehouse (Parquet/Iceberg) fed from it by CDC for analytics. That split is the foundation the whole track builds on." },
    { q: "What does choosing ELT over ETL actually buy you, and what is the cost?", a: "ETL transforms in a separate engine before loading, so only cleaned, conformed data lands; ELT loads raw data first and transforms in-warehouse (typically with dbt's bronze/silver/gold layers). The win of ELT is replay and fidelity: because raw bronze is retained, when a business definition changes — what counts as an 'active user', how to attribute revenue — you re-run the transform against history instead of re-ingesting from a source that may no longer have the data. It also rides cheap, elastic warehouse compute, which is why the industry flipped to ELT. The cost is storage (you keep raw) and governance (raw data is messy and must be access-controlled). Where the T runs is fundamentally a cost-vs-replay-vs-fidelity decision, not a capability one." },
    { q: "How does Parquet skip data, and what code mistake silently defeats it?", a: "Parquet is columnar and self-describing: each file is split into row groups, and the file footer stores per-row-group statistics, including min/max for each column. When a query has a predicate like country = 'US' or event_date in a range, the engine reads the footer first and skips any row group whose min/max range can't contain a match — predicate pushdown / pruning — and reads only the columns the query projects. Partitioning the table by a column (e.g. event_date) prunes at the file/directory level on top of that. The classic mistake that defeats pruning is wrapping the column in a function in the predicate — upper(country) = 'US' — because the footer stats are on the raw column, not on upper(column), so the engine can no longer use them and falls back to scanning. Keep predicates sargable: compare the raw column, or normalise at write time." },
    { q: "What does a materialized view trade, and how do you keep that tradeoff honest in production?", a: "A materialized view stores the precomputed result of a query so reads are fast and cheap — you pay the heavy aggregation once at refresh time instead of on every read. The thing you trade, and must actively manage, is staleness: between refreshes the MV serves a number that is correct as of its last refresh and stale relative to the moving source. So 'is the dashboard correct?' has no answer without 'as of when?'. You keep it honest by declaring a freshness SLA on each source (dbt's warn_after / error_after), running the freshness check at least twice as often as the tightest SLA, and failing the pipeline when data is older than allowed — so a stalled feed is caught instead of silently serving stale numbers. The other managed cost is storage and refresh compute." },
    { q: "Why is the append-only event log the source of truth in event sourcing, and how does current state relate to it?", a: "Instead of storing current state and overwriting it on each change, event sourcing stores the immutable, append-only stream of events that produced the state — OrderPlaced, ItemShipped, OrderRefunded. Current state is then a left-fold (reduce) over that log: replay the events in order and you reconstruct any entity's state at any point. This gives you a complete audit trail for compliance, the ability to rebuild derived read models (search indexes, MVs, projections) by replaying, and time-travel debugging. The discipline it demands is ordering and idempotency: events must carry an id and a version/sequence so consumers dedupe and order by sequence rather than arrival time — otherwise out-of-order or replayed events double-count, which is exactly how revenue gets counted twice at a seam." },
    { q: "How do full-text search and vector search divide the relevance problem, and why do mature systems run both?", a: "Full-text search uses an inverted index: it tokenises and analyses text, maps each term to the documents containing it for fast candidate retrieval, then ranks with a scheme like BM25 — so it excels at exact and lexical matching, rare tokens, SKUs, and typo-tolerant term queries. Vector search embeds text into a high-dimensional space and does approximate nearest-neighbour (ANN) retrieval, so it captures semantic similarity — 'good for video editing' matching 'high-performance GPU' with no shared words — which powers semantic search and RAG. ANN silently trades recall for latency through parameters like ef_search, so wrong params still return ranked rows, just the wrong ones. They solve different halves of relevance: lexical precision vs semantic meaning. Mature systems hybrid-rank both, and crucially filter vector hits against live OLTP ids so a stale embedding can't surface a deleted entity." },

<Recap lang="en">
If you reconstructed each answer, you hold the track's spine: OLTP and OLAP split because no layout wins both access patterns; ELT buys replay by retaining raw; Parquet prunes via footer stats unless a function hides the column; an MV trades staleness for read speed and needs a declared freshness SLA; the event log is the source of truth and state is a fold over it; and search plus vectors divide lexical from semantic relevance. Above all, each store is correct for its job — the system stays correct only when you design the contract, delivery guarantee, freshness, and reconciliation at every seam between them.
