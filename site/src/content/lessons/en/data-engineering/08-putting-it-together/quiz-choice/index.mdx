<Goal lang="en">
Confirm you can route a workload to the right store and layout, and reason about the seams between them — the synthesis the OLTP/OLAP, ELT, Parquet, MV, event-sourcing, search, and vector units all built toward.
</Goal>

  question="A nightly dashboard query filters event_date = '2026-05-01' AND country = 'US' over a 2 TB Parquet/Iceberg table and still scans most of the data. What is the highest-leverage fix?"
  choices={[
    { label: "Partition/sort the data so event_date and country are prunable, and rely on Parquet footer min/max stats per row group so the engine skips files and row groups that can't match the predicate.", correct: true },
    { label: "Add a secondary B-tree index on country like you would in OLTP.", misconception: "Parquet has no per-row B-tree index; pruning is done by partition layout plus row-group footer statistics. The OLTP indexing instinct doesn't transfer — you make predicates prunable, not indexed." },
    { label: "Convert the table back to row format so filters are faster.", misconception: "Row format makes a column scan worse: you read every column of every row. Columnar plus footer stats is what lets the engine read only event_date/country and skip non-matching row groups." },
    { label: "Cache the whole table in memory so scans are RAM-speed.", misconception: "2 TB rarely fits in memory and you'd still scan it all; caching masks the real problem. Pruning means never reading the irrelevant 99% in the first place, which footer stats plus partitioning deliver." },
  ]}

  choices={[
    { label: "No declared freshness SLA. An MV trades read latency for staleness; the number is correct as of its last refresh and stale for now. Declare a freshness window and fail the pipeline when data is older than the SLA.", correct: true },
    { label: "The MV definition has a bug in its aggregation SQL.", misconception: "If both numbers are internally correct, the gap is time, not logic. The MV is right for its 6-hour-old snapshot and the live count is right for now — check and declare freshness before suspecting the transform." },
    { label: "Materialized views should never be used for finance numbers.", misconception: "MVs are fine for finance when the staleness fits the question. The failure is leaving staleness undeclared and unmonitored, not using an MV at all — the cost you manage is refresh and the staleness it leaks." },
    { label: "Switch to refreshing the MV on every write so it's always current.", misconception: "Per-write refresh defeats the point of an MV and can cost more than the original query. The senior move is to declare an SLA that matches the question's freshness need, not to chase zero staleness." },
  ]}

<Quiz
  id="08-putting-it-together-choice-5"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="A service writes an order to Postgres, then publishes 'OrderPlaced' to Kafka so search and analytics react. Occasionally the search index never learns about an order. What is the root cause and the fix?"
  choices={[
    { label: "The dual-write problem: two writes across a DB and a broker with no shared transaction, so a crash between commit and publish loses the event. Fix: transactional outbox (row + event in one transaction) shipped by CDC, with idempotent consumers and a periodic reconciliation job.", correct: true },
    { label: "Kafka is dropping messages; raise the broker's replication factor.", misconception: "The event is lost before it reaches Kafka — the process died after the Postgres commit but before publishing. Broker durability can't save an event that was never sent; you need to make the write and the event atomic via an outbox." },
    { label: "Publish to Kafka first, then write to Postgres, so the event is never lost.", misconception: "That just inverts the dual-write: now a crash after publish but before commit emits an event for an order that doesn't exist. Reordering two non-transactional writes never closes the gap — only a single atomic write (outbox) plus reconciliation does." },
    { label: "Have the search index poll Postgres every minute instead of consuming events.", misconception: "Polling rebuilds CDC by hand, bounds freshness to the poll interval, and misses deletes unless you also poll tombstones. The fix is to make the event path reliable (outbox plus idempotent consumer), with reconciliation as the safety net." },
  ]}
/>

<Recap lang="en">
The track's through-line is one habit: route each workload to the store and layout that fits it, then design the contract at every seam. Row-store OLTP for point writes, columnar Parquet for scans (with footer-stat pruning), ELT over retained raw for replayable definitions, MVs for read latency with a declared freshness SLA, an outbox to kill the dual-write, inverted indexes for lexical search, and vector ANN for semantic retrieval. Each store is correct for its job; the system stays correct only when you own the schema, delivery guarantee, freshness SLA, and reconciliation between them.
</Recap>
