## Snippet 1 — the analytics query on OLTP

```sql
-- runs hourly against the live Postgres orders table
SELECT country, date_trunc('day', created_at) AS d, sum(amount)
FROM orders
WHERE created_at >= now() - interval '90 days'
GROUP BY 1, 2;
```

## Snippet 2 — the incremental dbt model

```sql
{{ config(materialized='incremental', unique_key='order_id') }}
SELECT order_id, customer_id, amount, status, updated_at
FROM {{ source('raw', 'orders') }}
{% if is_incremental() %}
WHERE updated_at > (SELECT max(updated_at) FROM {{ this }})
{% endif %}
```

    { label: "The deleted order disappears automatically because the source no longer has it.", misconception: "Incremental models append/merge only changed rows from the source filter; they never re-scan the full source, so they cannot notice an absence.     { label: "The unique_key on order_id deletes the stale row for you.", misconception: "unique_key controls how a matched incoming row is merged (upsert) — it does nothing when no row arrives at all. A hard delete produces no incoming row, so there's nothing to match and remove." },
    { label: "Switch to a full table scan every run so deletes vanish — that's the only option.", misconception: "Full-refresh does reconcile deletes but throwing away incrementality on every run defeats the cost savings. The senior fix is to propagate deletes as CDC tombstones and merge them, keeping incremental for the common case." },

## Snippet 3 — the Parquet predicate

```python
# Iceberg table partitioned by event_date, with country as a regular column
df = spark.read.table("events")
result = (df
    .filter("upper(country) = 'US'")          # function wraps the column
    .filter("event_date = '2026-05-01'")
    .groupBy("country").count())
```

<Quiz

  lang="en"
  question="The event_date filter prunes well but the country filter scans far more than expected. Why, and what's the fix?"
  choices={[
    { label: "upper(country) wraps the column in a function, so the engine can't use row-group min/max footer stats to skip files — predicate pushdown/pruning is defeated. Compare the raw column (country = 'US') or store it pre-normalised so the predicate stays prunable.", correct: true },
    { label: "Parquet can't prune on any column other than the partition column.", misconception: "Parquet prunes non-partition columns too, using per-row-group min/max footer statistics. The problem here is that wrapping the column in upper() hides it from those stats, not that pruning is limited to partitions." },
    { label: "The filters run in the wrong order; swap them.", misconception: "Filter order doesn't change pruning — the optimiser pushes both predicates down. The defeat is the function wrapper on country, which makes its predicate non-sargable against the footer stats." },
    { label: "Add more partitions on country so it scans less.", misconception: "Over-partitioning by a high-cardinality column creates the small-files problem and won't help while upper() still wraps the predicate. First make the predicate prunable; only then consider partitioning country if cardinality is sane." },
  ]}

## Snippet 4 — the vector retrieval

```python
def recommend(query: str, k: int = 10):
    qvec = embed(query)
    hits = vector_index.search(qvec, ef_search=20, top_k=k)
    return [h.product for h in hits]   # embeddings rebuilt nightly
```

<Recap lang="en">
Every platform bug is read in a query, a transform, or an integration snippet: an OLAP aggregate stranded on an OLTP store, an incremental model that can't see deletes, a Parquet predicate wrapped in a function that defeats pruning, and a vector search that's both stale and recall-starved. The fix is almost never more hardware — it's the right store for the access pattern, deletes propagated as CDC tombstones, sargable predicates that let footer stats prune, and a live OLTP filter plus tuned ef_search for retrieval. Read the code, place the workload, then verify.
</Recap>
