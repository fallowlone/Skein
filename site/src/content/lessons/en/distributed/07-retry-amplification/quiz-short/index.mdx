    { q: "Why do retries compose by multiplication rather than addition, and what is the amplification formula?", a: "Because each layer with its own retry policy re-triggers the full retry behaviour of every layer beneath it. When the gateway retries, it does not send one extra call to the deepest dependency — it re-runs the entire downstream chain, each layer of which retries again. So the factors stack as a product, not a sum: the amplification factor is retries^depth. With 3 retries per layer and a 4-deep chain, one failing request becomes 3⁴ = 81 calls to the deepest dependency; a 5-deep chain is 3⁵ = 243. The number is geometric in depth, which is why it ambushes people who reason 'a retry is just one more call' — and it only kicks in during an incident, exactly when the backend has the least spare capacity to absorb it." },
    { q: "Define a metastable failure and explain why the system stays down after the trigger clears.", a: "A metastable failure is a system that has two stable states — a healthy one and a degraded one — where a temporary trigger (a failover, a spike, a brief dependency blip) shoves it into the degraded state, and a self-sustaining feedback loop keeps it there even though the trigger is long gone. For retries the loop is: backend slows, requests time out, timeouts fire retries, retries add load, backend slows more, more timeouts, more retries. Once that loop runs, the retry traffic itself is the dominant load, mostly re-attempts of requests whose original deadlines have already passed — pure wasted work that produces nothing but more load. The trigger becomes irrelevant; removing it does nothing. That is why waiting does not help and why operators must reduce load directly — shed traffic, open breakers, or restart tiers — to force the system back to the healthy stable state. The term comes from Bronson et al.'s 2021 HotOS paper unifying retry storms, congestion collapse, and death spirals." },
    { q: "Why is exponential backoff necessary but not sufficient, and what does jitter add on top?", a: "The first reason retries are deadly is synchronization: when a dependency blips, every client times out at roughly the same instant and retries at roughly the same instant — a thundering herd arriving as a spike. Fixed-interval retries are worst because they re-synchronize the herd every round. Exponential backoff (base, 2×base, 4×base) spreads attempts over time but does not de-correlate them — clients that started together still step together. Jitter adds randomness so clients spread across the window. Full jitter picks sleep = random(0, base × 2^attempt) for maximum spread and the fewest total calls; equal jitter keeps a guaranteed floor, sleep = base/2 + random(0, base/2), so no client sleeps less than half the backoff. AWS found full and equal jitter complete in roughly the same number of calls, both dramatically cutting total calls and time-to-recovery versus plain exponential backoff. Fixed backoff with no jitter is the one to never ship." },
    { q: "What is a retry budget, what value is canonical, and what does it bound that backoff cannot?", a: "Backoff smooths the timing of retries; it does not cap their volume — 81 calls spread over time are still 81 calls. A retry budget caps the volume. Instead of a per-request retry count, it bounds retries as a fraction of total traffic. Google SRE and Finagle both use roughly 10%: a client may spend retries up to 10% of its request volume, and once that budget is exhausted it fails fast instead of retrying. This converts unbounded geometric amplification into a hard ceiling — even in a full outage, retry traffic adds at most ~10% extra load instead of 80x. A common implementation is a token bucket: each request adds a small fraction of a token, each retry costs a full token, and a retry is only allowed when a whole token is available." },
    { q: "How does a circuit breaker break the sustaining loop, and what are its three states?", a: "A circuit breaker attacks amplification from the dependency end. It watches the failure rate to a dependency; once failures cross a threshold it opens — every call fails instantly without touching the network — for a cooldown. This hands the backend a window of zero retry traffic, the one thing that lets a metastable system fall back to its healthy state. After the cooldown it goes half-open, admitting a single probe (not full traffic): if the probe succeeds the breaker closes and normal traffic resumes; if it fails the breaker re-opens for another cooldown. The three states are closed (normal, tracking failures), open (failing fast, no calls), and half-open (one probe testing recovery). Admitting full concurrent traffic in half-open is a classic bug — it floods the still-fragile backend and re-trips immediately." },

Never retry a deterministic client error like a 400 — it will fail identically every time and just wastes a backend call. Never blindly retry a non-idempotent POST — a retry can duplicate a payment or an order; make the operation idempotent (idempotency keys) before retrying it. Retry only transient, retryable failures: timeouts, 503s, connection resets. Second, propagate the deadline — pass the remaining time budget down the call chain so a service never retries a request whose caller has already given up. Retrying a request whose original deadline has already passed is the purest form of wasted, amplifying work: it can never produce a useful result, it only adds load.
