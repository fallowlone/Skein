    { q: "Why is two-phase commit unusable across microservices, even though it is correct?", a: "2PC is correct but operationally fatal across services. During the prepare phase every participant holds its locks open, waiting for the coordinator's verdict across the network — so locks are held for the length of a round trip to the slowest service, not a local disk write. The coordinator is a blocking single point of failure: if it dies after prepare but before commit, participants are stuck in-doubt, unable to commit or abort until it recovers. And a typical request path includes services you cannot enroll at all, like a third-party payment gateway, which can never participate in your prepare/commit. Fine for two tables in one Postgres instance; fatal for six services owned by different teams. So you give up the global transaction: each service commits locally and you stitch steps together with messages instead of locks." },
    { q: "Explain why a compensating transaction is not a database rollback, and how that changes how you order steps.", a: "A rollback erases an uncommitted change — the database guarantees it is as if the change never happened. A compensation is a brand-new forward transaction that runs after the original already committed durably, and it can only approximate undoing the effect. A refund is not the inverse of a charge: the money moved twice, the customer sees two line items, and the gateway may take a fee both ways. Some steps have no compensation at all — a sent email cannot be unsent, a shipped package is gone. Because compensations are imperfect or impossible, the senior rule is to order steps so the irreversible or hard-to-undo ones run last: do the cancellable, reservable work first, and charge the card or send the confirmation only once every step that could fail has already succeeded. Then a mid-saga failure compensates cleanly instead of leaving an un-undoable side effect." },
    { q: "Contrast choreography and orchestration, and give the heuristic for choosing.", a: "In choreography there is no coordinator — each service listens for events and reacts, emitting its own events for the next service. It is decentralized with no single point of failure, but the saga's logic exists nowhere as a whole: to answer 'what happens after a card is charged?' you grep multiple codebases, adding a step touches several services, and tracing a stuck saga means reconstructing a sequence from logs. In orchestration a central orchestrator owns the workflow as explicit code, sending commands and driving compensations on failure; the whole saga is readable in one place and one trace, at the cost of a new stateful component you build, deploy, and keep available. Heuristic: choreography for a short, stable, linear flow (2–3 steps that rarely change); orchestration once the flow has branches, retries, timeouts, or more than about four steps — the point where 'where is the logic?' stops having a one-file answer. Durable-execution engines like Temporal fill the orchestration niche by persisting orchestrator state so a crash mid-saga resumes exactly where it stopped." },
    { q: "What does it mean that a saga is 'ACID minus I', and which three anomalies follow?", a: "A saga gives you Atomicity (the whole thing completes or is compensated back), Consistency, and Durability (each step commits for real), but it gives up Isolation. Because each local transaction commits immediately, its intermediate state is visible to other sagas before the overall saga has decided to succeed or fail. Three anomalies follow that a single ACID transaction would have prevented. Dirty read: saga B reads an order saga A committed but will later compensate away, then acts on data that is about to vanish. Lost update: two sagas read the same value, both write, one clobbers the other. Non-repeatable read: a saga reads a value at one step and a different value at a later step because another saga changed it in between. These can play out over seconds — or, for a workflow that waits on human approval, over days." },
    { q: "Name the application-level countermeasures for a saga's lost isolation and what each one does.", a: "Because the database no longer isolates you across steps, you rebuild a slice of isolation in the application. A semantic lock marks a record pending (for example status = PENDING_PAYMENT) so other sagas know it is mid-flight and skip or defer it — advisory, so it only works if every saga honours it. Commutative updates make concurrent writes order-independent: use balance += delta, never balance = newValue, so two interleaved updates do not clobber each other. A reread / version check (optimistic concurrency) confirms the value has not changed since you read it before overwriting, retrying if it has. Together these defend against dirty reads, lost updates, and non-repeatable reads — and the effort of reimplementing them by hand is the strongest argument for only reaching for a saga when one transaction genuinely cannot span the work." },
    { q: "Why must saga steps and compensations be idempotent, and how do you make a charge step idempotent?", a: "Saga messaging is at-least-once: brokers redeliver, orchestrators retry after timeouts, and a step may crash after committing but before acknowledging. So every step and every compensation can be invoked more than once for the same logical action, and it must produce the same result as running once — otherwise a redelivery double-charges a card or double-cancels a hotel. End-to-end exactly-once delivery is largely a myth across a network; the durable answer is idempotent consumers. You make a charge step idempotent by deriving a stable idempotency key from the saga and step id and passing it to the gateway (which dedupes on it), or by atomically checking for and inserting a payment record under a unique constraint before charging, so a second invocation is a no-op. The same applies to compensations: running C2 twice must leave exactly one refund." },

<Recap lang="en">
If you could reconstruct each answer from memory, you hold the unit's spine: 2PC is correct but holds cross-service locks behind a blocking coordinator, so sagas trade the global transaction for local commits plus hand-written compensations that are new forward actions (order the irreversible ones last). You wire steps with choreography or orchestration on a complexity heuristic, you pay for losing isolation with semantic locks, commutative updates, and version checks, and because delivery is at-least-once, every step and compensation must be idempotent.
