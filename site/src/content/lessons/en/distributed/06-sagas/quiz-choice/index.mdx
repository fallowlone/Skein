  choices={[
    { label: "C2 issues a refund — a new forward transaction that approximates undoing the charge. It is not a rollback: T2 already committed durably, the money moved twice, and the customer may see two line items.", correct: true },
    { label: "C2 rolls the payments database back to the state before T2 committed.", misconception: "There is nothing to roll back — T2 committed locally and durably the instant it ran. A compensation is a brand-new business action, not a database rollback." },
    { label: "C2 signals the 2PC coordinator to abort the in-flight transaction.", misconception: "A saga exists precisely because there is no coordinator holding a transaction open. Each step commits immediately; the only undo is an explicit compensation you write." },
    { label: "C2 does nothing — a committed charge is final and cannot be reversed.", misconception: "It cannot be rolled back, but it can be compensated. Skipping C2 leaves money taken with no order — the inconsistency a saga's compensations exist to prevent." },
  ]}

  lang="en"
  question="A trip saga does T1 book flight, T2 book hotel, T3 rent car, then charge the card, then email a confirmation. Why does a senior order it this way?"
  choices={[
    { label: "Irreversible or hard-to-undo steps (charge, email) go last, after every step that might fail has already succeeded — so a mid-saga failure compensates cleanly instead of leaving an un-undoable side effect.", correct: true },
    { label: "The charge goes first so you fail fast if the customer has no money.", misconception: "Charging first means every later failure forces a refund — the money moved twice and a fee may stick. Do the cancellable, reservable work first; charge only once the rest succeeded." },
    { label: "The order does not matter because every step has a compensation.", misconception: "Not every step does — a sent email cannot be unsent, and a refund is not a clean inverse of a charge. Step ordering is exactly how you minimise reliance on imperfect or missing compensations." },
    { label: "Steps must run in the order their services were deployed.", misconception: "Deployment order is irrelevant. Saga step order is a design choice driven by reversibility — put the steps with the worst compensations last." },
  ]}

<Quiz
  id="06-sagas-choice-5"
  lessonSlug="06-sagas"
  lang="en"
  question="Saga B reads an order that saga A has committed but will later compensate away, and acts on it. Which anomaly is this, and why is it even possible?"
  choices={[
    { label: "A dirty read — possible because a saga has no isolation: each local step commits immediately, so its intermediate state is visible to other sagas before the whole saga has decided to succeed or fail.", correct: true },
    { label: "A deadlock — saga A and saga B are each waiting on the other's locks.", misconception: "Sagas hold no locks across steps, so classic deadlock is not the issue. The opposite is true — nothing is locked, so not-yet-final state is freely visible. That is a dirty read." },
    { label: "A non-repeatable read — saga B got two different values for the same row.", misconception: "Non-repeatable read is one saga reading the same value twice and getting different results. Reading another saga's about-to-be-compensated state is a dirty read." },
    { label: "Impossible — a committed step is final, so reading it is always safe.", misconception: "Committed locally is not the same as the saga succeeding. A step can commit and still be compensated away, so reading it can mean acting on data that vanishes — a dirty read." },
  ]}
/>

<Recap lang="en">
The through-line: a single ACID transaction cannot span services, and 2PC's cure — cross-service locks plus a blocking coordinator — is worse than the disease. A saga gives up the global transaction for local commits plus hand-written compensations, which are new forward actions, not rollbacks, so you order irreversible steps last. You wire steps with choreography (decentralized but scattered) or orchestration (one durable place to read and resume), and you pay for losing isolation with application-level defences — semantic locks, commutative updates, and version checks — against dirty reads and lost updates.
</Recap>
