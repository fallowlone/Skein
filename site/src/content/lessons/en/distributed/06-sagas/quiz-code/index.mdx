## Snippet 1 — the compensating action

```go
// T2 already committed: the card was charged and a payment row written.
// C2 is supposed to undo it after a later step fails.
func compensateCharge(ctx context.Context, orderID string) error {
    // delete the payment row so it looks like the charge never happened
    return db.Exec(ctx, "DELETE FROM payments WHERE order_id = $1", orderID)
}
```

  lessonSlug="06-sagas"
  lang="en"
  question="Why is this compensation wrong, and what should it do instead?"
  choices={[
    { label: "Deleting the row pretends the charge never happened, but the money already moved through the gateway. The compensation must be a real reversing action — call the gateway to refund, then record a refund row — not erase the local record of a charge that physically occurred.", correct: true },
    { label: "It is fine — once the local payment row is gone, the saga is consistent again.", misconception: "Consistency is with the outside world, not just the local table. The gateway still holds the customer's money; deleting the row only hides the charge and breaks reconciliation." },
    { label: "The bug is that DELETE should be UPDATE ... SET status = 'voided'.", misconception: "Soft-deleting is better record-keeping, but it still does not move the money back. A compensation is a new forward action against the gateway, not a local-row edit." },
    { label: "It should roll back the original T2 transaction instead of deleting.", misconception: "There is no transaction to roll back — T2 committed durably long ago. The only undo for a real charge is a real refund." },
  ]}

## Snippet 2 — the orchestrator step

```python
# Orchestrator drives the saga forward, step by step, in memory.
def run_order_saga(order):
    book_flight(order)          # T1
    book_hotel(order)           # T2
    try:
        charge_card(order)      # T3
    except StepFailed:
        cancel_hotel(order)     # C2
        cancel_flight(order)    # C1
    # progress lives only in this call frame
```

<Quiz
  id="06-sagas-code-2"
  lessonSlug="06-sagas"
  lang="en"
  question="The orchestrator process crashes right after book_hotel returns but before charge_card. What is the failure, and what fixes it?"
  choices={[
    { label: "Saga progress lives only in the call stack, so the crash loses the in-flight workflow: the flight and hotel are booked with no record that the saga should continue or compensate. Persist each step transition durably (a saga log or a durable-execution engine) so the workflow resumes exactly where it stopped.", correct: true },
    { label: "Nothing breaks — when the process restarts, Python re-runs run_order_saga from the top.", misconception: "A restart does not re-enter a function that was mid-execution; the call frame is gone. Without persisted state the booked flight and hotel are orphaned." },
    { label: "The bug is that the except block should also retry charge_card before compensating.", misconception: "Retry policy is a separate concern. The crash here happens between steps, so even a perfect retry never runs — the lost in-memory state is the real defect." },
    { label: "Wrap the whole function in one database transaction so the crash rolls it back.", misconception: "The steps span separate services and their own databases; no single transaction spans them. That is the whole reason a saga exists. Durable step state, not a global transaction, is the fix." },
  ]}
/>

## Snippet 3 — the idempotent step

```go
// Message delivery is at-least-once, so this handler can be invoked
// more than once for the same saga step.
func handleChargeCard(msg ChargeMsg) error {
    amount := msg.Amount
    if err := gateway.Charge(msg.CustomerID, amount); err != nil {
        return err
    }
    return savePaymentRow(msg.OrderID, amount)
}
```

<Quiz
  id="06-sagas-code-3"
  lessonSlug="06-sagas"
  lang="en"
  question="With at-least-once delivery this handler has a real-money bug. What is it, and what is the minimal fix?"
  choices={[
    { label: "A redelivered message charges the card twice. The step is not idempotent — make it so by deriving an idempotency key from the saga/step id and passing it to gateway.Charge (gateways dedupe on it) or by checking for an existing payment row before charging.", correct: true },
    { label: "There is no bug — the gateway will reject the second charge as a duplicate automatically.", misconception: "Gateways only dedupe when you give them an idempotency key. With none supplied, two identical Charge calls are two distinct charges. The handler must supply the key." },
    { label: "The fix is to switch the broker to exactly-once delivery.", misconception: "End-to-end exactly-once is largely a myth across a network — brokers give at-least-once and you make consumers idempotent. The fix lives in the handler, not the broker setting." },
    { label: "Save the payment row first, then charge, so the row guards against re-charging.", misconception: "Reordering still races: two redeliveries can both pass the check before either writes. You need an atomic dedupe — a unique idempotency key the gateway or a unique DB constraint enforces." },
  ]}
/>

## Snippet 4 — the semantic lock

```sql
-- Saga A starts working an order. Saga B may touch the same order
-- concurrently because nothing is locked across saga steps.
UPDATE orders SET status = 'PENDING_PAYMENT' WHERE id = $1;
-- ... later steps of saga A run, then on success ...
UPDATE orders SET status = 'CONFIRMED' WHERE id = $1;
```

<Quiz
  id="06-sagas-code-4"
  lessonSlug="06-sagas"
  lang="en"
  question="What is the PENDING_PAYMENT status doing here, and what must other sagas do to make it work?"
  choices={[
    { label: "It is a semantic lock — an application-level marker that the order is mid-saga. Other sagas must check the status and refuse or defer work on a PENDING_PAYMENT order, because the database holds no real lock across saga steps to stop them.", correct: true },
    { label: "It is just an audit field; the database row lock during the UPDATE already protects the order.", misconception: "The row lock lasts only for that single UPDATE statement, not across the saga's steps. The status is the cross-step lock — but only if other sagas actually honour it." },
    { label: "It guarantees no other saga can read or write the order until it flips to CONFIRMED.", misconception: "It guarantees nothing on its own — it is advisory. Enforcement is in the application code that reads the status and chooses to skip or wait." },
    { label: "It makes the saga ACID-isolated again by serializing access at the database level.", misconception: "A semantic lock approximates isolation in application logic; it does not restore database-level isolation. Sagas remain ACID-minus-I — the marker just lets cooperating sagas avoid each other." },
  ]}
/>

<Recap lang="en">
Every saga defect in this set is a known shape: a compensation that deletes a local record instead of issuing a real reversing action; an orchestrator that keeps progress only in memory and loses the workflow on a crash; a step that double-charges because at-least-once delivery met a non-idempotent handler; and a status field that only works as a lock if every saga honours it. Now when you review a saga pull request, you scan for exactly these four shapes — the missing idempotency key, the rollback-in-disguise compensation, the unpersisted step, and the advisory lock nobody checks.
</Recap>
