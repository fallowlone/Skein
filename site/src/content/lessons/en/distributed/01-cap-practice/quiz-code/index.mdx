## Snippet 1 — Cassandra tunable consistency

```sql
-- N = 3 replicas per key (replication factor 3)
CONSISTENCY QUORUM;  -- W and R each require 2 of 3 acks
INSERT INTO orders (id, total) VALUES (?, ?);
SELECT total FROM orders WHERE id = ?;
```

<Quiz
  id="01-cap-practice-code-1"
  lessonSlug="01-cap-practice"
  lang="en"
  question="With RF=3 and QUORUM (W=2, R=2), what guarantee does W+R &gt; N give, and how does a partition change the system's stance?"
  choices={[
    { label: "W+R > N (2+2 > 3) guarantees the read and write quorums overlap on at least one replica, so a read sees the latest acknowledged write — strong consistency. But if a partition leaves fewer than 2 reachable replicas, the operation fails: at QUORUM, Cassandra behaves CP for that key.", correct: true },
    { label: "QUORUM makes Cassandra fully AP — it always answers regardless of partitions.", misconception: "Cassandra is AP only at low consistency (e.g. ONE). At QUORUM it requires 2 of 3 acks; a partition that strands the coordinator with one replica fails the operation, which is CP behaviour for that request." },
    { label: "W+R > N guarantees nothing about staleness; it only controls durability.", misconception: "The overlap from W+R > N is exactly the staleness guarantee: the read quorum must intersect the most recent write quorum, so a fresh value is observed. Durability is a separate concern." },
    { label: "It guarantees linearizability for all operations clusterwide.", misconception: "Quorum overlap gives strong consistency per key for these reads/writes, not full linearizability across keys or for concurrent updates. Two concurrent QUORUM writes can still race; LWW resolves them." },
  ]}

## Snippet 2 — MongoDB write/read concern

```js
db.accounts.updateOne(
  { _id: id },
  { $inc: { balance: -100 } },
  { writeConcern: { w: 1 } }          // ack from primary only
);
// elsewhere, a reporting service:
db.accounts.find({ _id: id }).readPreference("secondaryPreferred");
```

<Quiz
  id="01-cap-practice-code-2"
  lessonSlug="01-cap-practice"
  lang="en"
  question="What consistency hazard does this pairing create, and what is the highest-leverage fix?"
  choices={[
    { label: "w:1 acks before the write replicates; reading from a secondary can return a stale balance (no read-your-writes), and on a primary failover an un-replicated w:1 write can be rolled back entirely. Fix: w:majority writes plus majority/linearizable reads when correctness matters.", correct: true },
    { label: "No hazard — MongoDB is strongly consistent by default so both ops are safe.", misconception: "The default is consistent only for primary reads with majority concerns. Here w:1 plus a secondary read explicitly opts out: the secondary can lag, and a w:1 write is not majority-durable and can be lost on failover." },
    { label: "The only risk is slower writes; correctness is unaffected.", misconception: "w:1 is faster precisely because it skips waiting for replication — that is the source of the correctness risk (stale secondary reads and rollback on failover), not merely a latency knob." },
    { label: "Switch all reads to the primary and the problem disappears.", misconception: "Primary reads fix the stale-secondary read, but a w:1 write is still only on the primary and can be rolled back if that primary fails before replicating. You need w:majority for durability under failover." },
  ]}
/>

## Snippet 3 — partition scenario log

```
12:00:01  region=us-east  PUT cart/42  -> 200 OK   (local write accepted)
12:00:01  region=eu-west  PUT cart/42  -> 200 OK   (local write accepted)
12:00:02  link us-east<->eu-west: 100% packet loss (partition)
12:03:10  link restored; anti-entropy reconciliation begins
12:03:10  cart/42 has two divergent versions, equal vector-clock siblings
```

<Quiz
  id="01-cap-practice-code-3"
  lessonSlug="01-cap-practice"
  lang="en"
  question="Both PUTs returned 200 during the partition. What does that tell you about the store, and what must happen at reconciliation time?"
  choices={[
    { label: "Accepting both writes on both sides during a partition is textbook AP behaviour. The divergent siblings cannot be auto-ordered, so reconciliation must merge them — application-level merge, a CRDT, or surfacing both to the client — rather than blindly picking one.", correct: true },
    { label: "It is a CP store that briefly glitched; the duplicate will self-heal silently.", misconception: "A CP store would have rejected one side during the partition to avoid divergence. Returning 200 on both sides is the AP choice, and the resulting siblings need explicit conflict resolution, not silent self-healing." },
    { label: "Last-Write-Wins on timestamp is the safe resolution here.", misconception: "These are concurrent (equal vector-clock) siblings; LWW would discard one user's cart based on clock skew. Concurrent updates need a real merge (union the cart items) or client choice, not a timestamp coin-flip." },
    { label: "The 200s prove no conflict occurred since both succeeded.", misconception: "Both succeeding is the cause of the conflict, not evidence against it. Independent acceptance on both sides of a partition is exactly how divergence arises in an AP system." },
  ]}
/>

## Snippet 4 — Raft/etcd quorum config

```yaml
# 3-node etcd cluster, one node in a remote DC
cluster:
  - { name: n1, dc: primary }
  - { name: n2, dc: primary }
  - { name: n3, dc: remote }   # high-latency link to primary DC
election-timeout: 1000ms
heartbeat-interval: 100ms
```

<Quiz
  id="01-cap-practice-code-4"
  lessonSlug="01-cap-practice"
  lang="en"
  question="The remote link to n3 frequently spikes above 1000 ms RTT. What failure mode does this configuration invite, and what is the fix?"
  choices={[
    { label: "When n3's RTT exceeds the election timeout, n3 misses heartbeats and starts elections — a logical partition that churns the leader even though no link is truly down. Fix: raise the election timeout above worst-case RTT, enable pre-vote, or keep all voters in low-latency DCs (n3 as a learner/non-voter).", correct: true },
    { label: "No problem — Raft tolerates any latency because it only needs eventual delivery.", misconception: "Raft's liveness depends on heartbeats arriving within the election timeout. An RTT above that timeout makes a healthy-but-slow node trigger disruptive re-elections — high latency behaves like a partition." },
    { label: "Lower the election timeout to 200 ms so failover is faster.", misconception: "Lowering the timeout below the link's jitter makes false elections more frequent, not fewer. The timeout must sit comfortably above worst-case RTT to avoid flapping." },
    { label: "Add n3 as a 4th voter to break ties.", misconception: "Adding a slow voter worsens it: quorum size grows and the unstable remote node still triggers elections. Keep voters fast and co-located; make the remote node a non-voting learner." },
  ]}
/>

<Recap lang="en">
Every CAP/PACELC decision shows up as a knob: W+R &gt; N buys read-your-writes overlap but turns CP under partition; w:1 plus secondary reads quietly opts out of durability and freshness; two 200s during a partition are an AP signature whose siblings need a real merge, not LWW; and a Raft election timeout below worst-case RTT manufactures logical partitions. Read the config, name the guarantee it actually gives, then check how it degrades when the link breaks.
</Recap>
