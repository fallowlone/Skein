That is why Kafka partitions, a primary in a replica set, a cluster controller, and 'run on exactly one host' cron jobs are all leader-based. The cost is that you have deliberately created a single point of failure. So the hard part is not electing a leader — it is re-electing one safely when the current one dies, without ever letting two be active at once. Almost all the real difficulty, and almost every production incident, lives in that second requirement." },
    { q: "Walk through how Raft elects a leader, and why the election timeout is randomized.", a: "Raft divides time into terms — monotonically increasing integers that act as a logical clock, with at most one leader per term. A follower expects regular heartbeats from the leader; if none arrives within its election timeout, it increments the term, becomes a candidate, and requests votes. A candidate wins by collecting votes from a majority (quorum), and each node votes at most once per term, first-come-first-served. The timeout is drawn randomly from a range (typically 150–300 ms) so that followers do not all time out at the same instant. If they used a fixed timeout they would all become candidates together, split the vote, reach no majority, retry, and split again — a livelock. Randomization staggers the timers so one node almost always campaigns and wins in a single round." },
    { q: "Explain why a lease does not, by itself, prevent two nodes from both writing as leader.", a: "A lease bounds how long the coordinator waits before declaring a leader dead and electing a replacement. It does NOT bound how long a frozen leader keeps believing it still holds the lease — those are two different clocks. If the old leader is stuck in a long GC pause, swapped out, or its VM is paused for live migration, it executes no code during that window: it cannot notice its lease expired, cannot check the clock, cannot voluntarily step down. Meanwhile the coordinator has already elected a new leader. When the old one wakes it finishes the write it was mid-way through — now stale — and you have two writers and corrupted state. Shortening the TTL only makes false expirations more frequent; it never closes the window because you can never reliably bound the worst-case pause." },
    { q: "Define split-brain, and name its two distinct causes from the unit.", a: "Split-brain is two or more nodes simultaneously convinced they are the leader, both accepting writes, so shared state diverges and corrupts. The first cause is a network partition: a minority side that can no longer see the quorum may still believe it leads (a correct quorum protocol prevents this by barring the minority from electing or committing). The second, sneakier cause is a pause: the old leader was never partitioned — it was simply stopped (GC pause, paused VM, swapped process) — and wakes up holding a lease the world has already reassigned. The pause case is more dangerous precisely because it bypasses the partition-handling logic: the node looks healthy to itself and resumes its in-flight write." },
    { q: "Describe the fencing-token mechanism end to end, and state the one condition without which it is worthless.", a: "On every lock or lease grant the coordinator hands out a strictly increasing number — 33, then 34, then 35. The leader must include its token on every write to the protected resource, and the resource itself must reject any write whose token is lower than the highest it has already accepted. So when the paused leader wakes with token 33 and tries to write, the storage layer has already accepted the new leader's write at token 34 and rejects token 33 at the boundary. The stale writer is fenced off. The indispensable condition: the downstream resource must actively check the token. A lock service that hands out tokens but writes to a dumb store that ignores them buys you nothing — correctness must be enforced where the write actually lands, not where the lock is granted." },

In ZooKeeper the leader creates an ephemeral sequential znode tied to a session; the lowest-numbered znode is the leader. If session heartbeats stop for the session timeout (often seconds), ZooKeeper deletes the ephemeral znode automatically and the next-lowest candidate takes over. In etcd the leader attaches a lease with a TTL to a key and issues keep-alive renewals; if renewals stop, the lease expires, the key vanishes, and the role is freed — election typically uses a compare-and-swap on that key. In both, failover detection is bounded by the session/lease timeout, which trades responsiveness against the false-positive rate: a shorter timeout fails over faster but evicts healthy-but-slow leaders more often." },

<Recap lang="en">
If you could reconstruct each answer from memory you hold the unit's spine: a single leader serializes writes but creates a single point of failure that must be re-elected safely; Raft does it with terms and randomized 150–300 ms timeouts; leadership is a renewable lease or session (etcd lease TTL, ZooKeeper ephemeral znode) whose detection window bounds failover; a lease cannot stop a paused leader from waking and writing, which is one of the two faces of split-brain (the other being a partition, handled by quorum); and only a monotonic fencing token, enforced at the resource, makes the stale write impossible. Elect for liveness, fence for safety.
</Recap>
