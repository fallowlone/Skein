    { q: "Walk through exactly how clock skew turns into silent data loss under last-write-wins.", a: "LWW resolves conflicts by keeping the write with the highest timestamp. When one node's clock runs behind, a genuinely newer write routed through it gets stamped with a timestamp earlier than the row it should replace. Conflict resolution compares the two numbers, keeps the larger (older-clock) one, and discards the newer write. The killer detail: the client still receives a success response — there is no exception, no failed-quorum signal, no log line distinguishing the dropped write from one that never happened. You find out when a customer reports their change vanished, days later. It is worse with deletes: a tombstone stamped far in the future suppresses every real write until compaction garbage-collects it, which can be days." },
    { q: "Define the happens-before relation and what a Lamport timestamp guarantees about it.", a: "Happens-before (A → B) is the causal partial order: A happens-before B if they are on the same process with A first, or A is a send and B is the matching receive, or by transitivity. Events with no such path are concurrent. A Lamport clock is one counter per process: increment on every local event, and on receive set the counter to max(local, received) + 1. This guarantees that if A → B then L(A) < L(B). The converse does NOT hold: L(A) < L(B) does not mean A → B, because two concurrent events still get assigned some order. So Lamport gives a consistent total order that is consistent with causality, but cannot recover causality from the numbers — it imposes order, it cannot detect concurrency." },
    { q: "When do you need vector clocks instead of Lamport timestamps, and what do they cost?", a: "Reach for vector clocks when you must DETECT concurrency, not just impose an order — typically conflict resolution in a replicated store where two clients can write the same key without seeing each other. Each node carries a vector with one counter per node and ships the whole vector with each message; on receive you take the elementwise max and bump only your own component. Comparing two vectors tells you whether one happened-before the other (every component less-or-equal, at least one strictly less) or whether neither dominates — in which case the writes are concurrent and the store keeps both as siblings to merge. The cost is O(n) metadata per stamped value where n is the number of nodes, and it travels with every write and grows as the cluster grows, so real systems prune or scope the vectors (e.g. dotted version vectors)." },
    { q: "What does Spanner's TrueTime expose, and how does commit-wait use it to deliver external consistency?", a: "TrueTime equips each datacenter with GPS receivers and atomic clocks and exposes TT.now() not as an instant but as an interval [earliest, latest], whose width is the uncertainty ε — typically about 1ms, occasionally single-digit ms. Commit-wait assigns a transaction a commit timestamp s, then deliberately sleeps until TT.now().earliest > s — until it is certain s lies in the past everywhere. That wait is roughly ε and overlaps with Paxos replication, so it often adds little wall time. The payoff is external consistency: if T1 commits before T2 starts, T1's timestamp is guaranteed smaller than T2's, globally, with no skew caveat. Spanner converts clock uncertainty from a silent correctness bug into an explicit, bounded latency cost." },

A step can move the clock backward, and a failed daemon or paused VM leaves seconds of skew; during that window a newer write is stamped earlier than the row it should replace, loses the timestamp comparison, and is dropped while the client gets a 200 OK. Nothing in monitoring distinguishes the loss from a write that never happened. So NTP buys a smaller window of loss, not safety. If you need to order or merge distributed writes, use logical clocks (Lamport for total order, vector clocks to detect concurrency) or pay for real ordering with TrueTime commit-wait — never trust the wall." },
