When R + W is greater than N, the read set and the write set are guaranteed to overlap on at least one replica, so any read sees the most recently confirmed write — that is read-your-writes and the basis of 'order created' being durable and visible. With N=3, W=2, R=2 a write survives the loss of one replica and any later read overlaps it. So a self-check ('am I still leader?') can return a confidently wrong 'yes', because the process's view of the world is stale. The only reliable defense lives at the resource, not the leader: every write carries a monotonically increasing fencing token, and the resource records the highest token it has accepted and rejects any write with a lower token. When a new leader is elected it gets a higher token, so the old leader's stale, lower-token write is rejected outright. This is Kleppmann's point: leases bound wall-clock time but cannot bound a paused process, so correctness must be enforced by the resource via fencing, not by the leader trusting its own status." },

Causal order must be a fact, not a clock guess. Logical clocks (Lamport timestamps or vector clocks) capture happens-before relationships by incrementing on events and merging on message receipt, independent of physical time. Where you need physical-time semantics across services, Google's Spanner uses TrueTime, which exposes a bounded uncertainty interval and waits out that interval so commit timestamps are globally ordered. The principle: order steps by causality or bounded-uncertainty clocks, never by raw wall-clock comparison." },
    { q: "Why is there no distributed ACID transaction across the four services, and what replaces rollback?", a: "A classic ACID transaction needs all participants to hold locks and commit atomically under one coordinator; across independently-deployed services with their own databases this requires distributed two-phase commit, which couples availability (a single slow or down participant blocks everyone) and does not scale for long-running business workflows. Instead you use a saga: a sequence of local transactions, one per service, each committing independently. There is no rollback of an already-committed local transaction — instead each forward step has a compensation, a new transaction that semantically reverses the effect (refund a charge, restock inventory, cancel a shipment). Compensations are not undo logs; they are business-level reversals that must themselves be safe to retry. The trade is atomicity for availability and decoupling: the system is eventually consistent and you must reason explicitly about partial-completion states the saga can be left in." },

If a service blips and each of its callers retries a few times — and their callers retry too — the retry traffic stacks multiplicatively, and synchronized retries (fixed delay, no jitter) arrive in aligned waves that re-saturate the recovering service, turning a two-second blip into an outage. The defenses combine: exponential backoff spaces retries out, jitter randomizes them so callers don't fire in lockstep, a circuit breaker stops calling a service that is clearly down, and a retry budget caps how much extra load retries may add — typically about 10% on top of the normal request rate.
