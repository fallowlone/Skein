</Goal>

  lang="en"
  question="An order pipeline of four services double-refunds a customer occasionally. Every service passes its own unit tests; the payment service is idempotent for charges; the saga is textbook; retries have backoff and jitter. Where does the bug live?"
  choices={[
    { label: "In a seam: a retry layer re-invoked a refund compensation across a call that carried no shared idempotency key, so the receiver treated the retry as a fresh request. No single layer is wrong — the defect is in how two correct layers compose.", correct: true },
    { label: "Inside the payment service's refund path, which must have a hidden race the tests miss.", misconception: "The refund path passes its tests and the service is idempotent for charges.     { label: "In the message broker, which is delivering duplicates it promised not to deliver.", misconception: "Brokers deliver at-least-once by design; duplicates are expected, not a broker bug.     { label: "In the quorum config: R + W is set greater than N, which causes double writes.", misconception: "R + W > N is the property you want — it gives read-your-write overlap and durability. It governs replica visibility, not whether a retried compensation double-fires." },

<Quiz

  lessonSlug="08-putting-it-together"
  lang="en"
  question="The saga orchestrator runs as an elected leader. It suffers a long GC pause, its lease expires, a new leader is elected — then the old one wakes and tries to write a saga step. What actually prevents it from corrupting state the new leader already advanced?"
  choices={[
    { label: "A fencing token: every downstream write carries a monotonically increasing number, and the resource rejects any token lower than the highest it has already accepted.", correct: true },
    { label: "The old leader checks whether it is still the leader before writing.", misconception: "It cannot reliably know — that is the whole problem. A paused process believes no time passed and may think it still holds the lease. Only the resource enforcing a fencing token is safe against a stale, paused leader." },
    { label: "The lease expiry guarantees the old leader has stopped acting.", misconception: "A lease bounds wall-clock time, but a paused process has no idea time elapsed. Kleppmann's point: without a fencing token a stale leader can wake after its lease expired and still issue a write." },
    { label: "Exponential backoff delays the old leader's write until it is safe again.", misconception: "Backoff spaces out retries; it does nothing to reject a write from a node that should no longer be writing. Rejecting the stale write is the fencing token's job, not the retry policy's." },
  ]}
/>

  lang="en"
  question="A teammate proposes ordering saga steps across services by comparing wall-clock timestamps (Date.now()) so that 'Payment before Shipping' is enforced. Why does a senior reject this, and what is the correct mechanism?"
  choices={[
    { label: "Wall clocks on different hosts drift and can run backwards (NTP corrections), so a later event can carry an earlier timestamp — causal order is not a clock comparison. Use logical clocks (or TrueTime with bounded uncertainty) to order steps as a causal fact.", correct: true },
    { label: "Date.now() is too slow to call on the hot path; use a monotonic counter for speed.", misconception: "Performance is not the issue. The problem is correctness: physical clocks across hosts are not synchronized tightly enough to establish causal ordering, regardless of how fast the call is." },
    { label: "It is fine as long as all hosts run NTP, which keeps clocks identical.", misconception: "NTP bounds skew to tens of milliseconds at best and can step the clock backwards. Cross-service event ordering at sub-second granularity cannot rely on it; you need logical ordering." },
    { label: "Wall-clock ordering works, but only if every service is in the same datacenter.", misconception: "Same datacenter narrows skew but never eliminates it, and clock steps still happen. Co-location reduces — but does not remove — the need for a logical or bounded-uncertainty clock." },
  ]}

<Quiz
  id="08-putting-it-together-choice-4"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="Why is idempotency called the load-bearing primitive of the pipeline, rather than just one safeguard among many?"
  choices={[
    { label: "Distributed systems deliver at-least-once: a timed-out call may have succeeded, and the caller can never be sure. Since 'did it happen?' is unknowable, making 'do it again' harmless is what lets retries, at-least-once delivery, and compensations all be safe to lean on.", correct: true },
    { label: "Because it replaces the need for retries entirely — an idempotent operation never has to be retried.", misconception: "Idempotency does not remove retries; it makes them safe. A dropped request still needs a retry to complete. Idempotency guarantees the retry has no extra effect, not that no retry happens." },
    { label: "Because it lets you use exactly-once delivery, which the broker then guarantees.", misconception: "Exactly-once delivery over a network is impossible. What is called 'exactly-once' is at-least-once delivery plus idempotent processing keyed on a dedup id — the network gives duplicates, the key gives exactly-once effects." },
    { label: "Because it makes every operation naturally repeatable, like incrementing a counter.", misconception: "'decrement stock by 1' is naturally repeatable and still wrong when repeated. Idempotency is not natural repeatability — it is a stable business key the receiver records so a second arrival is a no-op returning the first result." },
  ]}

<Quiz
  id="08-putting-it-together-choice-5"
  lessonSlug="08-putting-it-together"
  lang="en"
  question="A retry storm is amplifying a small downstream fault into a full outage: every layer retries the layer below it. What is the structural fix, and what number anchors it?"
  choices={[
    { label: "A retry budget that caps retries at roughly 10% on top of the normal request rate (with backoff + jitter and a circuit breaker), so a fault cannot multiply load. When the budget is near 100% consumed, retries are shed instead of amplifying.", correct: true },
    { label: "Increase the timeout everywhere so calls have more time to succeed before retrying.", misconception: "Longer timeouts hold connections open longer and can worsen a storm by piling up in-flight work. They do not bound the multiplication of load; only a budget caps how much retries can add." },
    { label: "Retry more aggressively with no backoff so requests clear the queue faster.", misconception: "No backoff is exactly what turns a transient fault into a thundering herd — synchronized immediate retries amplify load. Backoff plus jitter spreads retries; the budget bounds their total." },
    { label: "Add more replicas so the downstream service can absorb the retries.", misconception: "Scaling capacity delays the collapse but the storm scales with traffic and re-saturates the new capacity. The durable fix bounds retry amplification at the source with a budget, not by absorbing it." },
  ]}
/>

<Recap lang="en">
The track's through-line is one decision tree: quorum makes a write durable, a leader with fencing tokens makes coordination single-writer-safe, logical clocks order steps causally, sagas reverse with compensations because there is no distributed ACID, and retries need a budget so a fault cannot amplify. Idempotency keyed on business intent is the load-bearing primitive that makes at-least-once safe everywhere. The real failures live in the seams — a retry re-firing a compensation with no shared key — and you catch them on seam signals, not on green per-service dashboards. Now when you sit across from a distributed-systems incident where every service is healthy, you know to ask: what two correct layers are touching at the seam — and is there a shared key between them?
</Recap>
