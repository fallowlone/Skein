## Snippet 1 — the quorum config

```yaml
# replicated order store
replication:
  N: 3          # replicas per key
  W: 1          # acks required to confirm a write
  R: 1          # replicas read on a get
```

## Snippet 2 — the fencing check

```python
# resource guarding a saga step; called by whichever node believes it is leader
highest_token_seen = 0

def apply_step(step, token):
    global highest_token_seen
    # accept the write, then remember the token
    write(step)
    highest_token_seen = max(highest_token_seen, token)
    return "ok"
```

  lang="en"
  question="A paused old leader wakes with token=7 while a new leader has already applied steps at token=12. What does this code do, and what is the fix?"
  choices={[
    { label: "It applies the stale write before checking the token, then sets highest back via max() — so the old leader's token=7 step corrupts state the token=12 leader advanced. Fix: reject first — if token is lower than highest_token_seen, return an error and do not write.", correct: true },
    { label: "It is safe because max() keeps highest_token_seen at 12, so the stale token is ignored.", misconception: "max() updates the bookkeeping but only after write(step) has already run. The corrupting write happens regardless; the token must be checked and rejected before the write, not recorded after it." },
    { label: "The bug is that token is an int; fencing tokens must be UUIDs to be monotonic.", misconception: "Monotonic integers are the canonical fencing token. The defect is the ordering — writing before validating — not the token type. A UUID would not even be comparable for monotonicity." },
    { label: "There is no bug; the new leader will simply overwrite the stale step on its next write.", misconception: "Relying on a later write to repair corruption is a race, not a guarantee — the stale step may be read or trigger effects before any overwrite. The fence must reject the stale write outright." },
  ]}

## Snippet 3 — the saga compensation

```python
# compensation for a cancelled order; invoked by the retry layer on timeout
def refund(order_id, amount):
    # no idempotency key threaded in
    charge_id = payment_api.create_refund(order_id=order_id, amount=amount)
    return charge_id
```

  lang="en"
  question="The first call's refund succeeds but its response is lost; the retry layer calls refund() again within budget. What happens, and what is the single highest-leverage fix?"
  choices={[
    { label: "create_refund runs a second time and the customer is refunded twice — the seam between the retry layer and payment carries no shared key. Fix: derive a stable key (refund:{order_id}) and pass it so the payment service dedups and returns the first refund's result on the repeat.", correct: true },
    { label: "Nothing bad happens because the saga only emits one compensation per order.", misconception: "The saga emits one compensation, but the retry layer re-invokes it on timeout — that is the whole point. One logical compensation becomes two physical calls, and with no key the second one refunds again." },
    { label: "It fails safely because create_refund will error on a duplicate order_id.", misconception: "Passing order_id is not an idempotency key — the API has no record tying this call to the first attempt, so it creates a fresh refund. A dedicated, recorded idempotency key is what makes the repeat a no-op." },
    { label: "Just remove the retry on compensations so refund() is only ever called once.", misconception: "Then a genuinely lost refund request never completes and a cancelled order silently keeps the customer's money — a wrong number in the other direction. Retries are needed; they need a key, not removal." },
  ]}

## Snippet 4 — the retry policy

```python
def call_with_retry(fn, attempts=6):
    for i in range(attempts):
        try:
            return fn()
        except Timeout:
            # fixed delay, no jitter, no budget
            sleep(1.0)
    raise
```

<Recap lang="en">
Every distributed incident is read at the seam: a quorum with R + W not greater than N silently serves stale reads; a fence that writes before checking the token lets a stale leader corrupt state; a compensation invoked by the retry layer with no shared key double-refunds; and a fixed-delay retry with no jitter or budget turns a blip into a herd. Read the config and the code, fix the seam — add the overlap, reject before writing, thread the key, add jitter and a budget — then verify under failure injection.
</Recap>
