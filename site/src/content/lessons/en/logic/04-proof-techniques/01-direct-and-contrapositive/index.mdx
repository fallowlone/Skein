During a code review, a junior engineer asked the team lead a question that sounds naive and is not: "How do you actually *know* this never returns null?" The lead did not run the code. She read it aloud, slowly. The route only fires after the auth middleware, so `req.user` exists. ## A proof is a chain you can defend link by link

A **proof** of a claim is a finite chain of statements in which every statement is either something already known — a definition, an established fact, an explicit assumption — or follows from earlier statements by a valid step. Nothing mystical: a proof is an argument so explicit that a hostile reader can poke every link and find a justification waiting.

Most claims worth proving have the shape of an implication: *if P, then Q*. A **direct proof** of P→Q makes the obvious move — walk forward:

1. **Assume** P holds, and unpack what P *means* using definitions.
2. **Manipulate** what you have — algebra, known facts — one justified step at a time, building a chain P→A→B→…
3. **Conclude** by recognizing the definition of Q in what you have produced.

Assume, manipulate, conclude. The fuel for steps 1 and 3 is always a **definition** — the precise meaning of the words in the claim. For our worked example we need two: an integer n is **even** if n = 2k for some integer k, and **odd** if n = 2k + 1 for some integer k. Definitions are the handles a proof grips; if you cannot state the definition, you cannot start the chain.

Here is a complete direct proof, written in full sentences the way mathematicians actually write them:

**Claim.** If n is even, then n² is even.

**Proof.** Assume n is even. By the definition of even, n = 2k for some integer k. Then n² = (2k)² = 4k² = 2·(2k²). Since integers are closed under multiplication, 2k² is an integer. So n² equals 2 times an integer — which is exactly the definition of even. Therefore n² is even. ∎

Read it again as anatomy. Sentence one is the *assume*. Sentence two unpacks the definition — it converts the word "even" into algebra the chain can grip. Sentence three is the *manipulate*: pure algebra, every equals sign checkable. Sentences four and five re-pack the algebra into the definition of the goal. The last sentence *concludes*. And notice the small word "some": k is whatever integer witnesses the evenness of n. We never said which one — so the chain works for every even n at once. That is how four sentences cover infinitely many numbers.

<Inset kind="why" lang="en">
Beginners often flinch at step one: "you *assumed* n is even — isn't that cheating?" No, and the reason is what an implication claims. P→Q does not claim Q; it claims that Q holds *whenever* P does. To check a promise of the form "whenever P, Q", you put yourself in the "whenever": suppose P just happened, and show Q must follow. You are not asserting that n is even out in the world — you are exploring the world where it is. The proof would only be circular if you assumed Q, the thing being concluded. Assuming P is not a bug in the method; it is the method.
</Inset>

## Reviewing code is chaining guarantees

The lead in the opening story was doing the same three moves on a function. The claim was an implication — *if the request got this far, the response is non-null* — and the proof was a chain whose links are not algebra but **guarantees**: things middleware, schemas, and contracts promise. Watch the links:

```js
// Claim: if the input passed validation, sendReceipt never sees a missing email.
app.post("/orders", validate(orderSchema), (req, res) => {
  const order = req.body;             // link 1: validate() ran → body matches orderSchema
  const email = order.customer.email; // link 2: schema requires customer.email, non-empty string
  sendReceipt(email);                 // link 3: email is a non-empty string → never null/undefined
  res.sendStatus(201);
});
```

Approving this PR responsibly *is* checking a direct proof: every line must be justified by a guarantee established earlier — the middleware ran, the schema requires the field, the type is what the contract says. The moment one link has no justification (say, the schema actually marks `email` optional), the chain breaks at that exact link — and that is the exact line the future bug report will point to. A review comment like "what guarantees that `order.customer` exists here?" is a request for a missing justification, word for word what a mathematician asks at a seminar.

Loops have their own version of this. When you argue "each iteration keeps `sum` equal to the total of the items processed so far", you are forging links of one long implication chain: the property holds before the first pass → each pass preserves it → so it holds after every pass → so at exit it covers all items. Each preserved-property step is one link; the loop welds them into a chain as long as the input. That pattern — the **invariant** — gets its full treatment in the induction lesson of this track; for now, recognize it as a direct proof wearing a hard hat.

## When the road is steep, flip it: the contrapositive

Some implications resist the head-on walk. Try to prove directly: *if n² is odd, then n is odd*. Assume n² is odd, so n² = 2k + 1 for some integer k… and now what? You hold a fact about n² and need a fact about n — extracting it means reasoning about square roots, and the algebra turns to mud.

Here is the escape. Recall from the propositional logic unit that an implication is logically equivalent to its **contrapositive**: P→Q says exactly the same thing as ¬Q→¬P. The truth table is the receipt — and it also shows the impostor we will meet in a moment, the **converse** Q→P:

| P | Q | P→Q | ¬Q→¬P | Q→P |
|---|---|------|--------|------|
| T | T | T | T | T |
| T | F | F | F | T |
| F | T | T | T | F |
| F | F | T | T | T |

The P→Q and ¬Q→¬P columns are identical in every row: one statement, two outfits. Proving either proves both. So flip the stubborn claim. The contrapositive of "if n² is odd, then n is odd" is "if n is *not* odd — that is, even — then n² is *not* odd — that is, even". And that is the claim we proved two sections ago, in four sentences. The proof of the flipped version *is* a proof of the original. One line, citing our earlier work: *by contraposition, since n even implies n² even, n² odd implies n odd.* ∎

The rule of thumb: look at which side of the implication hands you the easier object to work with. Direct gave us n² (hard to crack open); the contrapositive gave us n (trivial to square). When the premise is about the complicated thing and the negated conclusion is about the simple thing — flip.

## The converse proves nothing

Now the impostor in the table. The **converse** of P→Q is Q→P — the arrow reversed without negating. Its truth-table column differs from P→Q in two rows: it is a genuinely different statement, and neither one implies the other. Confusing them is not a beginner's exotic error; it is one of the most common reasoning bugs in working engineering teams.

The classic incident shape. The spec says: *if the input is invalid, the function returns null.* In the logs you find a null. The reviewer writes: "so the input must have been invalid." That is the converse — null→invalid — and the spec never promised it. Null might also come from a timeout, an empty result set, a code path nobody documented. The only flip the spec licenses is the contrapositive: *if the return was non-null, the input was valid.* Observing the output Q tells you nothing about P; observing ¬Q tells you ¬P. Memorize the asymmetry — it reads strangely until the truth table makes it inevitable.

<Recap lang="en">
A proof is a finite chain of statements, each one a definition, a known fact, an explicit assumption, or a valid step from earlier links — explicit enough that a hostile reader finds a justification at every poke. A direct proof of an implication runs assume, manipulate, conclude: unpack the premise with a definition (even means n = 2k), push justified algebra (n² = 2·(2k²)), and re-pack the result into the goal's definition. The phrase "for some integer k" names a witness without choosing it, which is how four sentences cover infinitely many cases. Code review is the same craft with guarantees for links: middleware ran, schema requires the field, contract forbids null — and an unjustified link is exactly where the future bug report will point. Loops join in through invariants: each iteration preserving a property is one link of a chain as long as the input. When the direct road is steep, flip to the contrapositive: P→Q and ¬Q→¬P are the same statement, so proving "n even → n² even" settles "n² odd → n odd" in one line — flip when the negated conclusion hands you the easier object. But never flip without negating: the converse Q→P is a different statement, and "it returned null, so the input must have been invalid" is its classic production disguise. Negate and swap, or do not swap at all.
</Recap>
