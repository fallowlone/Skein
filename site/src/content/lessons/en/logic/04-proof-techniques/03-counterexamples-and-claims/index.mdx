<Hook>
"I ran it on ten inputs — it works." The PR was merged on that sentence. The next morning a customer hit checkout with an empty cart and the total came out NaN. One user, one input, and the claim "it works" was dead. Notice the asymmetry of that fight: ten green examples could not establish the claim, and a single red one destroyed it. That is not bad luck — it is logic. "It works" secretly means *for all inputs, the code behaves* — a ∀-claim, and ∀-claims play on a brutal scoreboard: examples in favor count for almost nothing, while one example against ends the game. Claims that start with ∃ play on the mirror-image scoreboard, where one example wins outright. ## The quantifier decides the burden of proof

Recall the two quantifiers from earlier in this track: **∀x P(x)** says *every* x in the domain satisfies P; **∃x P(x)** says *at least one* does. The entire economics of arguing — what counts as proof, what counts as refutation — is set by which one the claim starts with:

| Claim shape | One example proves it? | One example kills it? |
|---|---|---|
| ∀x P(x) | never — examples only support | yes: a **counterexample**, an x with ¬P(x) |
| ∃x P(x) | yes: a **witness**, an x with P(x) | never — failed searches only fail |

To *prove* a ∀-claim you need an argument that covers every member of the domain — a proof chain like the previous two lessons built — or, when the domain is finite and small, an exhaustive check of all of it. To *refute* one, a single counterexample suffices, and no eloquence can save the claim afterwards. For ∃-claims everything mirrors: one witness proves it on the spot, while refuting it requires an argument that *every* candidate fails. The mirror is exact because of a law from the quantifier lesson: ¬∀x P(x) is equivalent to ∃x ¬P(x). Refuting a universal *is* proving an existential — which is precisely why one object can do it.

## A worked hunt: the claim that sounds like a theorem

**Claim.** Every function with n roots has degree at least n.

It sounds right. A root is an input where the function equals zero; a line (degree 1) crosses zero at most once, a parabola (degree 2) at most twice — surely many roots demand high degree. The claim has a ∀ in front, so before nodding along, hunt: what is the *weirdest* function you can feed it? Try the most degenerate one in stock: **f(x) = 0**, the zero function. Every single input is a root — infinitely many roots. And its degree? The zero polynomial is assigned no degree at all (by convention, sometimes −∞) — certainly not "at least n" for any n. One pathetic, degenerate object, and the universal claim is dead. (The word "function" was even looser: sin(x) has infinitely many roots and no degree to speak of — the claim was not even well-posed for most of its stated domain.)

But look at what the death bought. The counterexample did not destroy the idea — it located its boundary. The repaired statement, *every nonzero polynomial with n distinct roots has degree at least n*, is a genuine theorem. That is the usual life cycle: a counterexample rarely kills an insight; it amputates the false generality and leaves a claim that says exactly where it lives. Treat every counterexample you find as a free consultant marking where your claim's domain actually ends.

## The counterexample zoo, and the tests that hunt there

Where do counterexamples live? Overwhelmingly at the edges. The standard zoo, worth memorizing as a checklist: **0, 1, −1, the empty collection, the single-element collection, boundaries** (first/last index, min/max values), **duplicates, already-sorted and reverse-sorted inputs, unicode beyond ASCII, null/missing fields**. The reason is not superstition. A ∀-claim gets written while its author imagines a *typical* input — but the quantifier ranges over all of them, including every input nobody imagined. The zoo is simply a catalogue of inputs nobody imagines.

Now translate the whole lesson into your daily work: **a failing test is a counterexample** to the claim "this code is correct for all inputs", and a green suite is a collection of supporting examples — survivors, not proof. Watch both halves at once:

```js
// Claim: for every array xs of numbers, average(xs) returns a finite number.
function average(xs) {
  let sum = 0;
  for (const x of xs) sum += x;
  return sum / xs.length;
}

average([2, 4, 9]); // 5  — a supporting example: the claim survives
average([7]);       // 7  — survives the singleton cage of the zoo too
average([]);        // NaN — 0/0. A counterexample. The ∀-claim is dead.
```

One red line outvotes any number of green ones — the scoreboard from the hook, now in code. And the repaired claim writes itself the same way the polynomial one did: *for every non-empty array of finite numbers, average returns a finite number* — the counterexample told you exactly which words were missing.

<Inset kind="why" lang="en">
Property-based testing tools — Hypothesis in Python, fast-check in JavaScript, QuickCheck as the Haskell original — automate the hunt. You state the property as a genuine ∀-claim ("for every array xs, sorting twice equals sorting once"), and the tool generates hundreds or thousands of candidate inputs, deliberately biased toward the zoo, looking for a counterexample. When it finds one, it *shrinks* it: it whittles the failing input down to a minimal one, typically handing you exactly the empty array, the 0, or the "". One honest caveat keeps the tool in its place: a green property run is still just examples — more of them, better aimed, but examples. It raises confidence; it never proves the ∀. What it automates is the zoo, not the proof.
</Inset>

## Claims engineering: quantify before you argue

"The API is fast." A teammate writes this in a design review, and an argument starts — a pointless one, because as stated the sentence cannot be argued. Fast for *all* requests, or for most? Measured how — the median, the p95? On which endpoint, under what load? There is no observation that would *refute* the sentence as written: any slow request can be waved away as "not what I meant". A claim that no possible evidence could refute is **unfalsifiable**, and unfalsifiable claims are unreviewable — they can only be believed or disbelieved, never settled.

The fix is mechanical: rewrite the claim in quantified form before arguing about it. "The API is fast" becomes *for every GET /search request under nominal load, p95 latency over any 5-minute window stays at or below 200 ms.* Now the claim has a domain, a measurable predicate, and a quantifier — so both sides know the rules: a counterexample is a concrete 5-minute window with p95 above 200 ms, and the claim's defender knows what argument or evidence would support it. The same surgery applies to "the migration is safe", "this never happens in practice", "the cache makes things faster". A claim you cannot lose is a claim you also cannot win.

## "I tested ten cases, so it works"

The misconception of the unit, now in full view. Ten passing cases feel like accumulating proof, but a ∀-claim over a large domain — and "all inputs" for even a modest function is astronomically large — is never settled by sampling. What settles it: a **proof**, an argument over all inputs like the chains of the previous two lessons; or **exhaustive enumeration**, when the domain is genuinely finite and small — all 256 byte values, fine; all pairs of 64-bit floats, never. Dijkstra compressed this whole lesson into one sentence decades ago: testing can show the presence of bugs, never their absence — which is quantifier logic, nothing more.

The practical posture is not "abandon tests". Tests are cheap, automated counterexample hunters and regression tripwires — keep them and feed the zoo into them. Just be precise about what green means: *survived the hunt so far*. And when a claim truly must hold for all inputs — parser safety, money arithmetic, an invariant your system's correctness rests on — reach for proof-shaped tools: an invariant argument over the loop, an exhaustive check of a deliberately finite domain, types that make the bad states unrepresentable.

<Recap lang="en">
A claim's quantifier assigns the burden of proof before any argument starts. ∀x P(x) is proven only by an argument covering the whole domain — a proof chain, an invariant, or exhaustive enumeration when the domain is small and finite — and is killed by one counterexample; no pile of supporting examples ever proves it. ∃x P(x) mirrors exactly: one witness proves it, and only an argument that every candidate fails can refute it — 100,000 crash-free fuzzing runs refute nothing. The mirror is the equivalence of ¬∀ with ∃¬: refuting a universal is proving an existential. Counterexamples live at the edges — 0, 1, −1, empty, singleton, boundaries, duplicates, unicode, null — because authors imagine typical inputs while the quantifier ranges over all of them; the zero function with its infinitely many roots and no degree killed a plausible theorem the same way average([]) kills "it works". A counterexample rarely destroys the idea: it marks the boundary, and the repaired claim — nonzero polynomials, non-empty arrays — says exactly where the truth lives. A failing test is a counterexample; a green suite is a list of survivors; property-based tools automate the zoo and shrink failures to minimal counterexamples, but a green run still proves nothing. And before arguing any claim, quantify it — "the API is fast" cannot be refuted by any observation, and a claim you cannot lose is one you also cannot win.
</Recap>
