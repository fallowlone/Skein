<Hook>
The checkout validator had a line that looked lazy: `if (order.coupon) assertValid(order.coupon)`. A new hire read the business rule — "every order's coupon must be valid" — and decided the code was missing a case: orders *without* a coupon were never checked at all! The "fix" made validation fail whenever the coupon was missing. It deployed on a Friday. Roughly 80% of orders carry no coupon; checkout revenue flatlined for forty minutes. Here is the thing: the original code was *correct*, and the reason is one of the strangest-sounding rules in logic. The business rule is an implication — IF an order has a coupon, THEN it must be valid — and an implication whose if-part is false counts as true automatically. An order with no coupon satisfies the rule by doing nothing. That is called vacuous truth, it confuses every newcomer, and it quietly underlies your every() calls, your guard clauses, and half the early returns you have ever written.

<Crux>p → q is false only when p is true and q false; a false p makes it vacuously true. Only the contrapositive says the same thing.</Crux>

## The one row that breaks a promise

The **implication** `p → q` reads "if p, then q" — p is the *antecedent* (the condition), q the *consequent* (the promise). Its truth table has a shape worth memorizing: false in exactly **one** row.

| `p` | `q` | `p → q` |
|-----|-----|---------|
| T   | T   | T       |
| T   | F   | **F**   |
| F   | T   | T       |
| F   | F   | T       |

The best mental model is a promise: "If you pass the exam, I will buy you ice cream." When have I *broken* my word? Only in one world: you passed and got no ice cream — p true, q false. You passed and got ice cream: kept. You failed and got ice cream anyway: I promised nothing about that case; not broken. You failed, no ice cream: also not broken. A promise is innocent until proven broken, and the only proof is "condition met, promise unmet."

Note what implication does *not* claim: no causation, no relevance, no mechanism. `p → q` is purely a constraint on truth values — which is why it compiles directly to code. Since it is false only when p is true and q false, it is equivalent to `!p || q`:

```js
// Rule: if an order has a coupon, the coupon must be valid.
const satisfiesRule = (order) => !order.coupon || isValid(order.coupon);
// "p implies q" === "not p, or q" — one of the most useful encodings in programming
```

## Vacuous truth: rules about nothing are kept

The two bottom rows of the table say: when `p` is false, `p → q` is true *no matter what q is*. This is **vacuous truth** — the rule holds because it was never put to the test. "If an order has a coupon, it must be valid" is satisfied by a coupon-less order; "all unicorns in this room are green" is true of an empty room. Nothing made the claim false, so it stands.

This is not a philosophical quirk; your standard library is built on it:

```js
[].every(n => n > 0);          // true — vacuously: no element can fail the test
[].some(n => n > 0);           // false — no element can pass it either

const orders = [];
orders.every(o => isValid(o.coupon));   // true: "all zero orders comply"
```

An `every()` over an empty array returns `true` because "for all x, P(x)" is a chain of implications with no true antecedent in sight. Code that does `if (items.every(ok)) proceed()` will *proceed on an empty list* — usually right, occasionally a bug, always worth a deliberate decision. The Hook's new hire crashed into the other direction: they turned "if coupon, then valid" into "coupon must exist and be valid", strengthening `p → q` into `p && q`. Those are wildly different propositions — the second is false for every couponless order, which is exactly what took checkout down.

## Converse, inverse, contrapositive

From `p → q` you can manufacture three related statements, and confusing them is one of the oldest reasoning errors on record:

- **Converse**: `q → p` — the arrow reversed. **Not equivalent.**
- **Inverse**: `!p → !q` — both sides negated. **Not equivalent** (it is the converse in disguise).
- **Contrapositive**: `!q → !p` — reversed *and* negated. **Equivalent** — same truth table, same proposition, different clothes.

Take "if a user is premium, they see no ads" (`premium → noAds`). The converse — "if they see no ads, they are premium" — does not follow: a free trial tier might also hide ads. Code that infers premium status from the absence of ads commits the **converse error** (also called *affirming the consequent*), and it ships constantly in the form of "this symptom implies that cause" logic. The inverse — "if not premium, they see ads" — fails the same way and for the same reason. But the contrapositive — "if a user sees ads, they are not premium" — is *guaranteed* by the original rule. Check it against the table: `p → q` and `!q → !p` are false in exactly the same single row.

## Guard clauses are contrapositive reasoning

The contrapositive is not exam trivia — you write it every day. Take the rule "if we process a request, it must be authenticated" (`process → authed`). Its contrapositive: "if not authenticated, we do not process." That sentence *is* a guard clause:

```js
// Rule:           process → authed
// Contrapositive: !authed → !process  — the same rule, shaped like control flow
function handle(req) {
  if (!req.authed) return reject(req);   // guard: enforce the contrapositive
  if (!isValid(req.body)) return reject(req);
  process(req);                          // every rule now provably holds here
}
```

Each early return knocks out one `!q` case, and what survives to the bottom satisfies every rule — flat, readable, and logically identical to the nested-if pyramid it replaces. Finally, when an implication holds in *both* directions — `p → q` and `q → p` — the statements are **equivalent**, written `p ↔ q` ("if and only if"). Equivalence is the license to substitute: replacing a condition with an equivalent one (a De Morgan rewrite, a contrapositive guard) is safe in every context, while replacing it with its converse is a bug with a delay timer.

<Inset kind="why" lang="en">
Why define F → anything as true, rather than false or undefined? Because universal statements must survive irrelevant cases. Take "every multiple of 4 is even" — clearly true, and formally it is the implication: if x is a multiple of 4, then x is even, for all x. Now test x = 3: the antecedent is false. If a false antecedent made the implication false, x = 3 would disprove a true theorem about multiples of 4 — absurd; the claim never said anything about 3. If it made the implication undefined, every() over a list with one irrelevant element would be undefined too. Defining the untested case as true is the only choice that lets rules quantify over a messy world while being judged only where they actually apply.
</Inset>

<Recap lang="en">
The implication p → q is a promise that is false in exactly one truth-table row: antecedent true, consequent false — condition met, promise broken. It claims no causation, only a constraint on truth values, which is why it compiles directly to !p || q in code. When p is false the implication is vacuously true: the rule was never tested, so it stands — an empty array passes every(), a couponless order satisfies 'if there is a coupon it must be valid', and a room without unicorns makes all its unicorns green. Strengthening an implication into a conjunction (requiring p AND q) is a different and far stronger proposition — the difference is precisely every case where p fails, which is how a 'missing validation fix' becomes an outage. From p → q you can form the converse q → p, the inverse !p → !q, and the contrapositive !q → !p; only the contrapositive is equivalent, sharing the original's truth table, while converse and inverse — equivalent to each other — are the affirming-the-consequent trap: 'no ads, therefore premium' fails the moment another tier hides ads. Guard clauses cash in the equivalence: 'if we process, then authenticated' becomes the early return 'if not authenticated, reject', and a stack of guards leaves the bottom of the function in a state where every rule provably holds. Full equivalence p ↔ q — both directions at once — is the license to substitute conditions freely; anything less is a rewrite you must justify row by row.
</Recap>
