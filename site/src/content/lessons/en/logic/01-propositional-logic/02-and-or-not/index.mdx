## Four tables that define everything

A **connective** glues propositions into bigger propositions. The compound's truth value depends *only* on the truth values of its parts — and a **truth table** lists every combination. With two inputs there are just four rows, so the entire meaning of each connective fits in a glance:

| `p` | `q` | `p AND q` (`&&`) | `p OR q` (`\|\|`) | `p XOR q` |
|-----|-----|------------------|------------------|-----------|
| T   | T   | **T**            | T                | F         |
| T   | F   | F                | **T**            | **T**     |
| F   | T   | F                | **T**            | **T**     |
| F   | F   | F                | F                | F         |

And the one-input table for **NOT** (`!`): NOT T is F, NOT F is T.

Three things to internalize. **AND** is the strict one: true in exactly one row, when both parts are true. **OR** is *inclusive*: true when at least one part is true — including the row where both are. That clashes with everyday speech, where "soup or salad" usually means not both. The exclusive reading is its own connective, **XOR**: true when the parts *differ*. Mixing the two up produces real bugs: "premium OR trial users get access" should almost always be inclusive (someone who is both should obviously get in), while "entrance A or entrance B" on a ticket is XOR. There is no XOR keyword in most languages; `a !== b` on booleans does the job.

The tables are the *whole* definition. There is no hidden meaning in AND beyond its column — which means any question about a compound condition can be settled mechanically by enumerating rows. Four rows for two variables, eight for three. When a condition confuses you, stop reasoning in prose and write the table; prose is where the Hook's bug came from.

## De Morgan: how NOT moves through AND and OR

Negating a compound condition is where intuition fails most reliably, and **De Morgan's laws** are the mechanical fix. Both directions, in code form:

```js
!(a && b)  ===  (!a || !b)   // NOT (both)        = at least one fails
!(a || b)  ===  (!a && !b)   // NOT (at least one) = both fail
```

The pattern: when `!` distributes over the parts, the connective *flips* — AND becomes OR, OR becomes AND. The intuition for the first law: "not both" does not require both to fail; one failure is enough to break "both". The Hook's bug, fixed three equivalent ways:

```js
// Spec: block unless (verified AND active)
if (!(user.verified && user.active)) block(req);   // direct: negate the whole thing
if (!user.verified || !user.active) block(req);    // De Morgan: same table, flatter
if (!user.verified && !user.active) block(req);    // BUG: blocks only when BOTH fail
```

The buggy line and the correct ones differ in exactly two of the four rows — the rows where exactly one check fails. Those are precisely the half-revoked, half-configured, partially-migrated users that production is full of, which is why this bug class survives review: on the easy rows (fully good, fully bad) the wrong condition behaves correctly. The professional habit: every time you write or review a `!(...)`, mentally apply De Morgan and check the mixed rows — or name the condition positively (`const inGoodStanding = user.verified && user.active`) and negate the *name*, so the negation never touches the structure at all.

## Short-circuit: the truth table running left to right

Your runtime does not evaluate both sides of `&&` and then consult the table. It evaluates *left to right and stops as soon as the answer is decided*. Look at the AND column: if `p` is false, the result is F no matter what `q` is — so `q` is never evaluated. Symmetrically for OR: if `p` is true, the result is already T, and `q` is skipped. This is **short-circuit evaluation**: the truth table's shadow in the execution engine.

It is first a safety tool — the left side can *guard* the right:

```js
if (user && user.name.length > 0) { ... }
// user === null → left side falsy → right side never runs → no crash
```

And in JavaScript `&&` and `||` return the deciding *operand*, not a boolean — which powers idioms like `const port = config.port || 3000`. But the same skipping behavior has a sharp edge: anything on the right side *silently does not happen* when the left side decides. If the right side has a side effect, that side effect is conditional whether you meant it or not:

```js
let auditCount = 0;
function audit(u) { auditCount++; return true; }

function canAccess(u) {
  return u.isAdmin || audit(u);   // admins short-circuit past the audit
}

canAccess({ isAdmin: true });   // audit skipped!
canAccess({ isAdmin: false });  // audit runs
// auditCount === 1 — admin access was never logged
```

XOR, by contrast, can never short-circuit: both inputs are always needed, because the result depends on whether they differ.

<Inset kind="why" lang="en">
Why do languages short-circuit at all, given the trap? Two reasons. Performance: the right side may be expensive (a DB call, a network check), and skipping it when the left side already decides is free speed. Safety: the guard idiom — check for null on the left, dereference on the right — only works because the right side is guaranteed not to run. But the price is that order now matters: a &amp;&amp; b and b &amp;&amp; a have identical truth tables yet different behavior when one side can crash or has a side effect. The truth table is symmetric; execution is not. The rule of thumb: keep the right-hand side of &amp;&amp; and || pure (no side effects), and put cheap checks left, expensive ones right.
</Inset>

<Recap lang="en">
Connectives build compound propositions whose truth depends only on the parts, and truth tables are their complete definition: AND is true in exactly one of four rows (both parts true), inclusive OR is false in exactly one (both parts false), XOR is true when the parts differ, NOT swaps the single value. Everyday "or" is often exclusive, but code's || is inclusive — when "not both" matters, that is XOR, written a !== b on booleans. Negation is governed by De Morgan's laws: NOT (a AND b) equals (NOT a) OR (NOT b), and NOT (a OR b) equals (NOT a) AND (NOT b) — the connective flips as the negation moves inside. Distributing the NOT without flipping is the canonical compound-condition bug; it agrees with the correct condition on the uniform rows that reviews and happy-path tests exercise, and disagrees exactly on the mixed rows (one check passing, one failing) that production is full of. Fight it by enumerating the four rows or by naming the positive condition and negating the name. At runtime the table executes left to right with short-circuiting: a falsy left operand decides an AND and skips the right side, a truthy one decides an OR — which lets the left side guard the right against crashes and skip expensive work, but silently drops any right-hand side effect, so keep right operands pure. In JavaScript these operators return the deciding operand itself, powering default-value idioms and occasionally surprising you with a null where you expected false.
</Recap>
