## A sentence that must pick a side

A **proposition** (also called a *statement*) is a declarative sentence that is either true or false — exactly one of the two, never both, never neither. That single rule is the foundation of all of logic, and it filters out most of human language:

- "7 is an even number." — a proposition. It happens to be **false**, and that is fine: false statements are still perfectly good propositions. Having a truth value is the entry ticket; *which* value it is comes second.
- "The HTTP request returned status 200." — a proposition: out in the world it is either true or false.
- "Close the door!" — not a proposition. A command cannot be true or false; it can only be obeyed or ignored.
- "Is the server up?" — not a proposition. Questions ask for truth values; they do not carry one.
- "This pizza is delicious." — borderline. As a report of personal taste it has no objective truth value, so classical logic refuses it.

The two truth values are usually written **T** and **F**, or in programming, `true` and `false`. Logic does not care what a proposition is *about* — servers, numbers, pizza toppings — it only cares about that one bit attached to it. That ruthless reduction is exactly what makes logic transferable: the same laws govern a math proof and a firewall rule.

<Inset kind="why" lang="en">
Why does logic insist on *exactly one* truth value? Because everything downstream — proofs, equivalences, the truth tables you will meet in the next lesson — works by tracking how truth flows from small statements into big ones. If a sentence could be both true and false, or neither, that bookkeeping collapses: you could "prove" anything. Programming has the same allergy. A boolean column that can be `true`, `false`, or `NULL` is a famous source of bugs precisely because the third state breaks every assumption written for two. When engineers say a flag should be a "real boolean", they are demanding proposition-hood.
</Inset>

## Open sentences: why "x > 3" is not a proposition yet

Now look at the sentence "x > 3". True or false? You cannot say — it depends on what `x` is. A sentence like this, containing a **free variable** (a placeholder with no value attached), is called an **open sentence** or *predicate*. It is not a proposition; it is a *machine for making propositions*. Feed it a value and it closes:

- Bind `x = 7` → "7 > 3" — a proposition, and a true one.
- Bind `x = 1` → "1 > 3" — a proposition, and a false one.

The act of giving a variable a value is called **binding**. Until every variable in a sentence is bound, the sentence has no truth value, the same way a function has no return value until you call it:

```js
function isBig(x) {
  return x > 3;      // open sentence: x is free, no truth value yet
}

isBig(7);   // binds x = 7 → the proposition "7 > 3" → true
isBig(1);   // binds x = 1 → the proposition "1 > 3" → false
```

This is not a metaphor — it is the same structure. A function parameter *is* a free variable; a call *is* a binding. Every time you write `if (count > limit)`, you are writing an open sentence at coding time, and trusting the runtime to bind `count` and `limit` to actual values at execution time, turning it into a proposition it can evaluate. If one of them was never assigned, the binding silently goes wrong: in JavaScript, `50000 > undefined` evaluates via `NaN` and comes out `false` — your open sentence became a proposition, just not the one you meant.

## Your if-statement is a proposition factory

Every `if`, `while`, and ternary in your code is the runtime building and evaluating a proposition. The condition is an open sentence written by you; execution binds the variables; the result must collapse to one bit: take the branch or do not. That last step is where languages differ — and where the Hook's outage came from.

Strict languages force the condition to be an actual boolean. JavaScript instead **coerces**: any value is squeezed into true or false by truthiness rules. Non-empty strings, non-zero numbers, all objects → truthy. Only `false`, `0`, `""`, `null`, `undefined`, and `NaN` (plus `0n`) → falsy. So:

```js
const isAdmin = "false";   // a non-empty string

if (isAdmin) {
  // ALWAYS runs: Boolean("false") is true
  showRefundsDashboard();
}

// The proposition you meant:
if (isAdmin === true) {
  // runs only for the genuine boolean true
}
```

The condition `if (isAdmin)` does evaluate a proposition — but the proposition is "the value stored in isAdmin is truthy", which is a statement *about a value in memory*, not the statement "this user is an admin" that you had in mind. The bug is a swap of propositions. The defense is to keep the two glued together: convert untrusted input (config strings, env vars, query params — which are always strings) into real booleans at the boundary, and compare strictly so the proposition your code evaluates is the proposition your spec states.

<Recap lang="en">
A proposition is a declarative sentence with exactly one truth value — true or false, never both, never neither. Commands, questions, and matters of taste fail the test; false statements pass it, because carrying a truth value, not being true, is the entry condition. A sentence with a free variable, like x &gt; 3, is an open sentence: not a proposition itself but a template that becomes one when every variable is bound to a value — x = 7 yields the true proposition 7 &gt; 3, x = 1 the false one. Code mirrors this exactly: a function parameter is a free variable, a call is a binding, and every if-condition is an open sentence you write at coding time that the runtime closes at execution time into a proposition it evaluates to pick a branch. The danger zone is the gap between the proposition you meant and the one the machine builds: an unassigned variable still binds (to undefined, making 50000 &gt; undefined come out false through NaN), and coercing languages evaluate truthiness rather than meaning, so the non-empty string 'false' drives an if as confidently as true does. The discipline that follows: convert untrusted, stringly input into real booleans at the boundary, compare strictly, and always be able to say in one sentence which proposition your condition actually evaluates.
</Recap>
