## Ordered pairs: where position starts to matter

A set forgets order — `{a, b}` and `{b, a}` are one set. An **ordered pair** (a, b) is the opposite commitment: position is the whole point. (a, b) equals (c, d) only when a = c *and* b = d. So (1, 2) ≠ (2, 1), even though `{1, 2}` = `{2, 1}`.

You use ordered pairs constantly: a coordinate (x, y), a key-value entry, a row `(follower_id, followee_id)`. The Hook bug was precisely an ordered-pair bug: the row (ana, bob) means "ana follows bob", and reading it as (bob, ana) silently reverses every arrow in the graph. Nothing in the type system complains — both columns are ids — which is why position-meaning deserves a comment, a careful name, or both.

## The cartesian product: the grid of every possible pair

Given two sets, the **cartesian product** A × B is the set of *all* ordered pairs (a, b) with a from A and b from B. Picture a grid: members of A label the rows, members of B label the columns, every cell is one pair. The count is forced by the picture: each of the |A| rows holds |B| cells, so

|A × B| = |A| · |B|

With `A = {1, 2, 3}` and `B = {x, y, z, w}`: 3 rows × 4 columns = 12 pairs — count the cells, there is no thirteenth. Code builds the grid with two nested loops, and SQL has it as a verb:

```js
const a = [1, 2, 3];
const b = ["x", "y", "z", "w"];

const grid = a.flatMap((m) => b.map((n) => [m, n]));
grid.length;   // 12 = 3 * 4 — every combination, exactly once
```

```sql
-- CROSS JOIN is the cartesian product, rows × rows:
SELECT u.id, p.id FROM users u CROSS JOIN plans p;
-- 1,000 users × 5 plans = 5,000 rows. Forget the ON clause
-- in a regular join and this grid is what explodes at you.
```

## A relation is a subset of the grid

Here is the definition the whole lesson exists for. A **relation** from A to B is *any subset* of A × B. That is the entire definition — and it is exactly what "related" needs to mean to be precise. The grid lists every pair that *could* be related; the relation keeps the pairs that actually *are*. To say "a relates to b", check (a, b) ∈ R — a membership question, which you already know how to ask.

A foreign-key table is this definition stored on disk. The `follows` table over users `{ana, bob, cara}` is some subset of the 9-cell grid users × users:

```sql
-- follows ⊆ users × users — each row is one ordered pair in R
INSERT INTO follows VALUES
  ('ana',  'bob'),    -- (ana, bob)  ∈ R : ana follows bob
  ('bob',  'ana'),    -- (bob, ana)  ∈ R : and bob follows back
  ('ana',  'cara');   -- (ana, cara) ∈ R : ana follows cara
                      -- (cara, ana) ∉ R : cara does not follow back
```

The empty relation (nobody follows anybody) and the full grid (everybody follows everybody) are both legal relations — the two extremes of the same subset choice. And `===` on primitive values is a relation too: the set of pairs (x, y) where the check returns true.

## Three properties that sort relations

When a relation lives on one set (R ⊆ A × A), three questions reveal its character. Each is checkable pair by pair — no cleverness required:

- **Reflexive** — does *every* x relate to itself? (x, x) ∈ R for all x in A. "x ≤ x" — yes. "x is x's own ancestor" — no.
- **Symmetric** — does every arrow come with its reverse? Whenever (x, y) ∈ R, also (y, x) ∈ R. "Friendship" in apps that require mutual confirmation — yes. "Follows" — famously no: (ana, cara) without (cara, ana) is the normal case.
- **Transitive** — do arrows chain? Whenever (x, y) ∈ R and (y, z) ∈ R, also (x, z) ∈ R. "Ancestor of" — yes: your parent's ancestor is your ancestor. "Follows" — no: you do not automatically follow the accounts your friends follow.

Together these three questions partition all relations into species with very different engineering implications: a relation that is all three is an equivalence (the next lesson), while one that fails symmetry but keeps the other two becomes an order. Miss a property you assumed and code depending on it silently misbehaves — which is why the drill below is a real debugging technique, not just a homework exercise.

Try the **three-element drill** — small enough to check every property by hand. Take A = `{1, 2, 3}` and R = `{(1, 1), (2, 2), (1, 2), (2, 1)}`:

- Reflexive? Need (1, 1), (2, 2), (3, 3). Missing (3, 3) → **not reflexive**. One absent self-pair is enough.
- Symmetric? Check each arrow: (1, 2) has (2, 1) ✓, self-pairs are their own reverses ✓ → **symmetric**.
- Transitive? Chain every pair of touching arrows: (1, 2) then (2, 1) needs (1, 1) ✓; (2, 1) then (1, 2) needs (2, 2) ✓ → **transitive**.

```js
// The same drill, mechanically — pairs as "x,y" strings in a Set:
const A = [1, 2, 3];
const R = new Set(["1,1", "2,2", "1,2", "2,1"]);
const has = (x, y) => R.has(`${x},${y}`);

A.every((x) => has(x, x));                                  // false — no (3,3)
[...R].every((p) => { const [x, y] = p.split(","); return has(y, x); }); // true
A.every((x) => A.every((y) => A.every((z) =>
  !(has(x, y) && has(y, z)) || has(x, z))));                // true
```

The drill is not a toy: property checks on small finite relations are exactly how you sanity-test an access-control matrix or a "duplicate-of" link table before trusting code that assumes a property the data does not have.

<Inset kind="edgecase" lang="en">
Is `===` reflexive? It should be — every value equals itself — and for almost every primitive it is. The exception is `NaN`: the IEEE 754 standard defines `NaN === NaN` as false, making `===` on numbers *not reflexive*. This single missing self-pair breaks real code: `array.indexOf(NaN)` never finds it (indexOf uses ===), while `array.includes(NaN)` does (includes uses SameValueZero, which restores the self-pair). When a language offers several equality relations, they differ in exactly these property decisions.
</Inset>

## The misconception: "every relation is basically a function"

Functions feel like the default mental model: put x in, get y out. When you design a new table or shape data, ask yourself first: is this really a function (one output per input), or is it a relation that allows multiple pairs per first coordinate?

As sets of pairs, functions are the *special case*, not the rule. A relation R ⊆ A × B is a **function** from A to B only when every member of A appears as a first coordinate in *exactly one* pair — one output per input, no more, no less. "Follows" fails instantly: ana appears as first coordinate twice ((ana, bob) and (ana, cara)), and a brand-new user appears zero times. Most relations you store — follows, friendships, foreign keys, tags — are many-to-many and not functions at all. The function-shaped ones are the lookups: user_id → email (each id has exactly one). The next lesson takes the properties you just learned and builds the two most useful relation species from them: equivalences and orders.

<Recap lang="en">
A set cannot say "Ana follows Bob but not the other way around" — it forgets order. The ordered pair (a, b) is the fix: position is meaningful, and (a, b) equals (c, d) only when both coordinates match. The cartesian product A × B collects all possible pairs into a grid of exactly |A| · |B| cells — 3 × 4 makes 12, and a forgotten join condition in SQL hands you precisely this grid. A relation is any subset of the grid: the definition that turns "related" into a membership question, (a, b) ∈ R. Foreign-key tables store relations row by row; === defines one by its true pairs; the empty subset and the full grid are both legal. On a single set, three pair-by-pair checks classify a relation: reflexive (every self-pair present — ≤ yes, === no thanks to NaN), symmetric (every arrow reversed — mutual friendship yes, follows no), transitive (arrows chain — ancestor-of yes, follows no). The three-element drill makes the checks mechanical, and the same drill validates real link tables before code trusts a property the data lacks. Functions are not the general case but the special one: a relation where every input appears as a first coordinate exactly once — most stored relations are many-to-many. Now when you inherit a link table or design a new join, run the three-element drill before the code relies on a property the data does not have.
</Recap>
