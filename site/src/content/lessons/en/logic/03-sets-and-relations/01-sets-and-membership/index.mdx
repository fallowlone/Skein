## In or not in — the only question

A **set** is a collection about which only one fact exists per value: the value is a **member** (also called an *element*), or it is not. Membership has its own symbol: x ∈ A means "x is a member of A", and x ∉ A means it is not. The simplest way to describe a set is to list its members between braces: `{1, 2, 3}` is the set whose members are exactly 1, 2 and 3.

Because membership is the *only* fact a set carries, three familiar properties simply do not exist inside one:

- **No order.** `{1, 2, 3}` and `{3, 1, 2}` are the same set — both answer "yes" to exactly the same membership questions.
- **No duplicates.** `{1, 1, 2, 3}` is also the same set. Writing a member twice adds nothing, because "in" has no volume knob: a value is in once you list it, and listing it again changes no answer.
- **No counts.** A set cannot tell you that 1 "appeared three times". Appearances are an array concept; a set only knows the roster.

Two sets are **equal** exactly when they have the same members — that is the whole definition of set identity. And this is precisely the behavior your runtime ships:

```js
const clicks = [42, 7, 42, 42, 7];
const unique = new Set(clicks);

unique.size;     // 2 — the members are 42 and 7, nothing else
unique.has(42);  // true   — 42 ∈ unique
unique.has(99);  // false  — 99 ∉ unique
unique.add(7);   // adding an existing member changes nothing
unique.size;     // still 2

new Set([1, 2, 2, 3]).size;  // 3 — dedup IS set semantics
```

Deduplication is not a clever trick layered on top of `Set` — deduplication *is* set semantics. Feeding an array into a set asks each value one question, "are you already in?", and discards every "yes".

<Inset kind="why" lang="en">
Why would anyone want a structure that forgets so much? Because forgetting makes answers canonical. There is exactly *one* set with members 7 and 42 — so "have I seen this value?" has exactly one honest answer, no matter how the data arrived. An array is a log: it remembers what happened and in what order. A set is a roster: it remembers what exists. Most collection bugs in early code come from asking a log a roster question (counting clicks instead of users) or a roster a log question (expecting a set to remember who came first). Choosing the structure is choosing which question your code is able to ask.
</Inset>

## Sets by rule — and the first infinite set

Listing members works only when you can finish the list. The second notation, **set-builder notation**, describes members by a rule instead: `{x : x is even}` reads "the set of all x such that x is even". Everything after the colon is a condition — a predicate. If the condition is true for a value, the value is in; if false, it is out. A predicate is exactly the *open sentence* you met in the propositional logic unit: a sentence with a free variable that becomes true or false once you bind a value. A set-builder set is an open sentence wearing braces.

Code has both notations too. A literal `new Set([200, 301, 404])` is a list; a predicate function is a rule:

```js
// You cannot list the even numbers — but you can decide membership:
const isEven = (n) => n % 2 === 0;   // the set {x : x is even}, as a rule

isEven(10);  // true  → 10 is in
isEven(7);   // false → 7 is out

// Over a finite universe, filter materializes the rule into a roster:
[1, 2, 3, 4, 5, 6].filter(isEven);   // [2, 4, 6]
```

The rule notation unlocks **infinite sets**. The natural numbers ℕ — 0, 1, 2, 3 and so on forever — cannot be listed or fit in memory, yet ℕ is a perfectly well-defined set: for any candidate you name, the membership question has a definite yes-or-no answer. That is all a set needs. A set does not have to be *storable*; it has to be *decidable* in this gentle sense — every membership question has one answer.

## ∈ or ⊆ — one value, or a whole set

Here is the trap that catches almost everyone. There are two different claims you can make about sets, and they use two different symbols:

- **Membership** x ∈ A asks about *one value*: is x on the roster of A?
- **Subset** A ⊆ B asks about *two sets*: is every member of A also a member of B?

They feel similar — both say something is "inside" something — but they live at different levels. Take `A = {1, 2}`:

- 1 ∈ A — **true**. The value 1 is on the roster.
- `{1}` ⊆ A — **true**. Every member of the set `{1}` (there is just one: the value 1) is also in A.
- `{1}` ∈ A — **false**. The members of A are the *numbers* 1 and 2. The *set* `{1}` is a different kind of thing, and it is not on the roster.
- A ⊆ A — **true**. Every set is a subset of itself; ⊆ allows equality.

The **empty set** ∅ — the set with no members at all — makes both claims interesting. ∅ ⊆ B is true for *every* set B: to reject a subset claim you must point at a member of ∅ missing from B, and ∅ hands you nothing to point at. But ∅ ∈ B is almost always false — it holds only if someone explicitly listed the empty set as a member. Which also settles a classic puzzle: `{∅}` is *not* empty. It is a box containing one thing — an empty box. Its size is 1.

```js
const a = new Set([1, 2]);

a.has(1);              // true  — 1 ∈ a
a.has(new Set([1]));   // false — the SET {1} is not one of a's members

// Subset is a claim BETWEEN sets — you check every member yourself:
const isSubset = (x, y) => [...x].every((v) => y.has(v));
isSubset(new Set([1]), a);   // true — {1} ⊆ a
isSubset(new Set(), a);      // true — ∅ is a subset of everything

new Set().size;              // 0 — the empty set
new Set([new Set()]).size;   // 1 — a box holding an empty box
```

## A type is a set of values

One more place you already use sets daily without the word: types. The type `boolean` is the two-element set containing `true` and `false` — nothing more. A TypeScript union like `"GET" | "POST"` is a two-member set of strings, and asking "can I pass this value where that type is expected?" is exactly the subset question: a value of type A fits wherever B is expected when A, viewed as a set of values, is a subset of B. The next lesson builds on this: combining types with `|` will turn out to be a literal set union.

## The misconception: "a set remembers insertion order"

JavaScript muddies the water here, so let us clear it. A JS `Set` iterates in insertion order — that is a deliberate convenience of the language, deterministic and sometimes handy. But it is a property of the *container*, not of the *set*. Set identity ignores it completely:

```js
const s1 = new Set(["a", "b"]);
const s2 = new Set(["b", "a", "b"]);

[...s1];  // ["a", "b"]  — iteration shows insertion order…
[...s2];  // ["b", "a"]  — …which differs between the two containers

// As SETS they are equal: same members, same membership answers.
const sameSet = s1.size === s2.size && [...s1].every((v) => s2.has(v));
sameSet;  // true
```

If any logic in your program depends on which element comes out of a set first, that logic is using an array wearing a Set costume — and it will break the day the data arrives in a different order. Python makes the honest version visible: iteration order of a `set` is not guaranteed at all, yet `{"a", "b"} == {"b", "a"}` is `True`. Equality by membership is the set; iteration order is an accident of the container.

<Recap lang="en">
A set is the structure that knows one thing per value: in, or not in. Membership is written x ∈ A, its denial x ∉ A, and a set can be given by listing — `{1, 2, 3}` — or by a rule, like `{x : x is even}`, where the rule is a predicate, an open sentence whose true answers are the members. Because membership is the only stored fact, sets have no order, no duplicates and no counts: `{3, 1, 2}` and `{1, 1, 2, 3}` are the same set as `{1, 2, 3}`, and `new Set([1, 2, 2, 3])` having size 3 is that definition executing in your runtime. Equality of sets is equality of membership answers — which is also why infinite sets like ℕ are legitimate: nothing requires a set to fit in memory, only that every membership question has a definite answer. The two claims to keep apart live at different levels: x ∈ A asks about one value, A ⊆ B asks whether every member of A is in B. The singleton `{1}` is a subset of `{1, 2}` but not an element of it; ∅ is a subset of everything, an element of almost nothing, and `{∅}` is a box holding an empty box — size 1. Types preview the payoff: boolean is the set of `true` and `false`, and assignability is the subset question. When code seems to need "the first element of a set", it needs an array instead.
</Recap>
