## Equivalence: reflexive + symmetric + transitive

Before you ever write `groupBy`, `DISTINCT`, or a deduplication function, a question sits underneath: what does "same" mean for this data? Two email addresses that differ only by case? Two semver strings that parse to identical components? Getting that definition wrong means grouping data that should stay separate, or splitting data that should merge. The answer is always an equivalence relation — which is why the definition is worth nailing.

Last lesson gave you three pair-by-pair properties. A relation that has *all three* — reflexive, symmetric, transitive — is called an **equivalence relation**, and it is the precise version of "counts as the same for my purposes". The three properties are exactly what "same" demands: everything is the same as itself; if a is the same as b, then b is the same as a; if a is the same as b and b as c, then a is the same as c.

The canonical example: **same remainder when divided by 3**, on whole numbers. 7 and 4 both leave remainder 1, so they are equivalent. Check the properties: x always shares its own remainder (reflexive); if x shares a remainder with y, y shares it with x (symmetric); if x matches y and y matches z, all three carry one remainder (transitive). Other everyday equivalences: "same length" on strings, "is an anagram of" ("listen" ~ "silent"), "same person after normalization" on email addresses.

## The payoff: equivalence partitions the set

Here is why equivalences matter more than the sum of their three properties. An equivalence relation **partitions** its set: it cuts the set into non-overlapping pieces — **equivalence classes** — such that every element lands in *exactly one* class, and two elements are related exactly when they share a class. Remainder mod 3 cuts the whole numbers into precisely three classes:

- class of 0: `{0, 3, 6, 9, 12, …}`
- class of 1: `{1, 4, 7, 10, 13, …}`
- class of 2: `{2, 5, 8, 11, 14, …}`

No number is in two classes, none is left out — and that is guaranteed by the three properties, not by luck. Symmetry plus transitivity make classes swallow whole groups, reflexivity makes sure nobody escapes. The moment a "same as" relation fails a property, its classes stop being well-defined — and code that groups by it starts producing overlapping or missing groups.

You run partitions daily. A `groupBy` is a partition computed by key. A hash table is a partition into buckets by "same hash". Deduplication keeps one **representative** per class and discards the rest:

```js
// "Same person" on emails = same value after normalization.
const canon = (e) => e.trim().toLowerCase();   // class representative

const emails = ["Ana@Example.com ", "ana@example.com", "BOB@x.dev"];
const classes = new Map();                      // representative → class
for (const e of emails) {
  const rep = canon(e);
  (classes.get(rep) ?? classes.set(rep, []).get(rep)).push(e);
}
classes.size;   // 2 — two real people, three spellings
// Dedup = keep one member per class:
[...classes.keys()];   // ["ana@example.com", "bob@x.dev"]
```

The normalization function *is* the equivalence: x ~ y exactly when canon(x) === canon(y). A relation defined this way — same output under some function — is always a genuine equivalence, because === on the outputs (NaN aside) supplies the three properties for free.

<Inset kind="why" lang="en">
Why do hash buckets count as equivalence classes? A hash table files x and y into the same bucket when hash(x) === hash(y) — and "same hash" is reflexive, symmetric and transitive, so the buckets are the classes of a real equivalence relation. The subtlety is that this equivalence is *coarser* than "equal": equal values always share a bucket, but a bucket can also host unequal values that happen to collide. That is why a lookup has two stages — hash to find the class, then a true equality check inside it. The partition does the fast narrowing; equality does the final word. When someone says hashing "almost" identifies values, the precise statement is: the hash equivalence partitions the universe into classes cheap to compute, refining all the way to equality only inside one small class.
</Inset>

## Orders: when the relation ranks instead of grouping

Swap symmetry for its opposite and you get the other great species. A **partial order** is reflexive, transitive and **antisymmetric** — if a relates to b *and* b relates to a, then a and b are the same element. Arrows do not come back; they rank. Numbers under ≤ are the familiar case: x ≤ x, chains compose, and mutual ≤ forces equality.

The word *partial* is the surprise. ≤ on numbers is a **total order**: any two numbers can be compared — for every x, y, either x ≤ y or y ≤ x. But ⊆ on sets is a partial order where comparison can simply *fail*: `{1, 2}` and `{2, 3}` — neither is a subset of the other. They are not equal, neither is "smaller"; they are **incomparable**. Nothing is broken. The order is just partial, and "which of these two comes first?" honestly has no answer.

Software is full of partial orders wearing total-order costumes. The Hook's version bug is one: semantic versions have a perfectly good intended order (compare major, then minor, then patch — numerically), and JavaScript's default sort quietly substitutes a different total order, the lexicographic one:

```js
const tags = ["1.9.0", "1.10.0", "1.2.3"];

tags.sort();                 // default: string order, char by char
// → ["1.10.0", "1.2.3", "1.9.0"]   "1.10.0" < "1.2.3" because "1" < "2"

const byVersion = (a, b) => {
  const pa = a.split(".").map(Number);
  const pb = b.split(".").map(Number);
  return (pa[0] - pb[0]) || (pa[1] - pb[1]) || (pa[2] - pb[2]);
};
tags.sort(byVersion);        // → ["1.2.3", "1.9.0", "1.10.0"] — the intended order
```

Both orders are total; only one matches the meaning. The bug is not "the sort is broken" — it is *sorting by the wrong relation*. Sorting always begs the question: which order, and does it compare what you think it compares?

## Dependencies: a partial order you already manage

"Must run before" on tasks is the most engineering-relevant partial order. Migrations, build steps, package installs: `create-tables` must precede `seed-data`, and `compile` must precede `link` — but `lint` and `compile` may be genuinely incomparable: no constraint either way. Incomparability here is not a defect — it is *freedom*: incomparable tasks can run in parallel. When a tool needs one concrete execution sequence, it extends the partial order to a total one — that algorithm is **topological sorting**, and it is waiting for you in the algorithms track. One fact to carry there: a dependency relation with a cycle (a before b, b before a, a ≠ b) violates antisymmetry — it is not an order at all, and no valid sequence exists. "Circular dependency" is the name of that mathematical breakdown.

## The misconception: "any two things can always be compared"

Total orders train the intuition that comparison always succeeds — pick any two numbers, one is smaller. Partial orders say no: incomparable pairs are legal, common and meaningful. When you write a sort comparator, ask yourself whether the relation you are implementing is actually total on your data — or whether you are silently inventing a tie-break that the domain never asked for. Two sets where neither contains the other. Two tasks with no constraint between them. Two semver releases `1.4.0` and `2.0.0-beta` under a team policy that ranks stable and pre-release lines separately. Forcing a comparison where none exists is a real bug class: a JavaScript comparator that cannot decide returns something anyway, and `Array.prototype.sort` with an inconsistent comparator produces an arbitrary, engine-dependent arrangement — silently. The discipline mirrors the proposition discipline from the start of this track: before sorting or comparing, say out loud *which relation you are using*, and whether it is total on your data. If it is only partial, you owe the code an explicit tie-break — or an honest admission that some pairs have no order at all.

<Recap lang="en">
Two great species of relation are built from the three pair-by-pair properties. Keep all three — reflexive, symmetric, transitive — and you have an equivalence relation, the precise form of "counts as the same": same remainder mod 3, same string length, anagram-of, same email after lowercasing and trimming. Every equivalence partitions its set into disjoint classes — each element in exactly one, guaranteed by the properties — and that picture runs everywhere in code: groupBy partitions by key, hash buckets are the classes of "same hash" (coarser than equality, refined by a true equality check inside the bucket), and dedup keeps one canonical representative per class. Swap symmetry for antisymmetry — mutual relation forces equality — and you get orders, which rank instead of grouping. A total order compares every pair (numbers under ≤); a partial order legally leaves pairs incomparable: ⊆ on sets, where neither of `{1, 2}` and `{2, 3}` contains the other, and "must run before" on tasks, where incomparable means parallelizable and a cycle means no order exists at all — the mathematical name of "circular dependency". The version-sort incident distilled the discipline: string order and semver order are both total, but only one matches the meaning, and "1.10.0" losing to "1.9.0" is what sorting by the wrong relation looks like. Before comparing, name your order; before grouping, name your equivalence.
</Recap>
