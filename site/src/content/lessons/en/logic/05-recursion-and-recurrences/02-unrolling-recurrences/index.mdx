<Hook>
A batch importer sails through code review: process the first item, filter it out of the list, recurse on the rest. On staging it chews 200 test records instantly. On launch night it meets 100,000 real records — and the progress bar settles in for the weekend. Nobody wrote a slow line; every single call does honest, fast work. The killer hides in the shape: each call re-scans everything that remains, so the calls do n, then n−1, then n−2 steps… and those steps add up to about five billion. ## What a recurrence counts

Last lesson, recursion was about *what* gets computed. Now we count *how much it costs*. Write `T(n)` for the number of basic steps the function performs on an input of size n. Because a recursive function is "one layer of my own work, plus a smaller self", its cost obeys the same shape — a **recurrence**:

```
T(n) = T(smaller) + (work this layer)
```

Take the recursive sum of a list. Each call does one addition and one comparison — a constant, call it 1 step — then recurses on a list shorter by one:

```
T(n) = T(n-1) + 1,    T(0) = 1
```

To solve it, **unroll**: substitute the recurrence into itself a few times and watch the pattern emerge.

```
T(n) = T(n-1) + 1
     = (T(n-2) + 1) + 1  = T(n-2) + 2
     = (T(n-3) + 1) + 2  = T(n-3) + 3
       …pattern: T(n-k) + k
     = T(0) + n  =  n + 1        (set k = n to reach the base)
```

Linear: a list of a million takes about a million steps. Sensible. The method you just used is the whole craft, and it never changes: **unroll 3–4 steps, spot the pattern, sum it, sanity-check a small n by hand.** Check: `T(2)` should be 3 — and indeed `sum([a, b])` makes three calls: two elements and one empty list.

That sanity check deserves to be code. The formula predicts the call count, so count the calls:

```js
let calls = 0;
function sum(list) {
  calls++;
  if (list.length === 0) return 0;
  return list[0] + sum(list.slice(1));
}
sum([5, 2, 9]);
console.log(calls); // 4 — matches T(3) = 3 + 1
```

An empirical check this cheap should accompany every recurrence you solve: the formula says what *must* happen; the counter says what *did*.

## The painter who repaints everything: T(n) = T(n-1) + n

Now the importer from the prologue. Each call handles one record — but first it re-scans *all* remaining records to filter the list. The work this layer is not constant; it is proportional to the current size:

```
T(n) = T(n-1) + n
```

It is the painter who, each morning, repaints every fence plank painted so far before adding one new one. Unroll:

```
T(n) = T(n-1) + n
     = T(n-2) + (n-1) + n
     = T(n-3) + (n-2) + (n-1) + n
       …pattern: T(0) + 1 + 2 + … + n
```

So the price is the sum `1 + 2 + … + n`. A nine-year-old Carl Friedrich Gauss, ordered to add the numbers 1 to 100 to keep him busy, saw it instantly: pair the ends. 1 + 100 = 101, 2 + 99 = 101, 3 + 98 = 101 — fifty pairs, each worth 101, so the total is 50 · 101 = 5050. In general the n numbers form n/2 pairs each worth n + 1:

```
1 + 2 + … + n  =  n(n + 1) / 2
```

That is roughly n²/2 — **quadratic**. The number sense is brutal: n = 200 costs ~20,000 steps (staging shrugs); n = 100,000 costs ~5,000,000,000 steps (launch night dies). The recurrence predicted the postmortem from the armchair: a per-layer cost of n turns a linear-looking recursion into a quadratic bill.

```js
function process(items) {
  if (items.length === 0) return;
  handle(items[0]);
  const rest = items.filter((x) => x.id !== items[0].id); // n work per layer
  process(rest);                                          // T(n-1)
}
```

The fix is to make the per-layer work constant again — take `items[Math.min(i, …)]` by index or slice once — and the recurrence collapses back to `T(n-1) + 1`.

## Halving: T(n) = T(n/2) + 1

Binary search looks at the middle element and discards half the range. One comparison, then a problem of half the size:

```
T(n) = T(n/2) + 1
     = T(n/4) + 2
     = T(n/8) + 3
       …pattern: T(n/2ᵏ) + k
```

The base arrives when `n/2ᵏ` reaches 1 — that is, when k is the number of times n can be halved: `k = log₂ n`. Count it concretely, because logs deserve fingers:

```
1000 → 500 → 250 → 125 → 62 → 31 → 15 → 7 → 3 → 1     ≈ 10 halvings (2¹⁰ = 1024)
1,000,000 → … → 1                                      ≈ 20 halvings (2²⁰ ≈ 1,048,576)
```

A million sorted records, found in twenty probes. Doubling the data adds *one* step. This is why "sorted plus halving" is the most valuable shape in engineering — and the recurrence is the receipt.

## Two calls on half: the level sum of merge sort

The most famous sorting shape splits the list in half, recursively sorts *both* halves, then merges them with n steps of zipping:

```
T(n) = 2·T(n/2) + n
```

Unrolling still works, but a picture works better. Draw the calls level by level and total each level:

| Level | Subproblems | Size of each | Work at this level |
| ----- | ----------- | ------------ | ------------------ |
| 0     | 1           | n            | n                  |
| 1     | 2           | n/2          | 2 · n/2 = n        |
| 2     | 4           | n/4          | 4 · n/4 = n        |
| …     | …           | …            | n                  |
| log₂ n | n          | 1            | n                  |

Every level costs exactly n: the problems multiply, but they shrink at the same rate. So the total is *work per level × number of levels*:

```
T(n) ≈ n · log₂ n
```

For a million items: 1,000,000 · 20 = 20,000,000 steps — closer to linear than to the five-billion quadratic. This level-sum picture is the master key to divide-and-conquer costs. (There is a famous lookup table for these patterns called the Master Theorem — you will meet it in the algorithms track. It is exactly this table, generalized; never use it before you can draw the levels it summarizes.)

<Inset kind="practice" lang="en">
The craft, as a checklist you can run at code review speed: (1) write the recurrence straight off the code — what does one call cost, what does it recurse on; (2) unroll three or four steps mechanically; (3) spot the pattern and write the k-th step; (4) set k so the base case is reached, and sum what accumulated; (5) sanity-check a small n by hand or with a call counter. Five minutes of arithmetic, and the launch-night surprise becomes a review comment: this filter makes the importer quadratic — 5·10⁹ steps at prod size.
</Inset>

## The misconception: "two recursive calls = twice as slow"

A reasonable guess — and wrong in both directions. Compare two functions that each make **two** recursive calls:

```
A:  T(n) = 2·T(n/2) + 1      (two calls on HALVES)
B:  T(n) = T(n-1) + T(n-2) + 1   (two calls on n-1 and n-2 — fibonacci)
```

A's call tree is short and balanced: log₂ n levels, about 2n calls in total — barely worse than one call. B's tree shrinks by only 1 or 2 per level, so it stays deep *and* keeps branching: it explodes exponentially. Count B for n = 6 — every node below is one call:

```
fib(6)
├─ fib(5)
│  ├─ fib(4)
│  │  ├─ fib(3) …5 calls
│  │  └─ fib(2) …3 calls
│  └─ fib(3) …5 calls
└─ fib(4) …9 calls
                    total: 25 calls for n = 6
```

Twenty-five calls to compute fib(6) = 8 — and `fib(3)` alone is computed three separate times. The counter makes the explosion visceral:

```js
let calls = 0;
function fib(n) {
  calls++;
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
}
fib(6);  console.log(calls); // 25
calls = 0;
fib(30); console.log(calls); // 2,692,537 — for n = 30!
```

The number of calls is not set by how many recursive calls appear in the source — it is set by the **shape of the call tree**: how fast the input shrinks versus how much it branches. Two calls on halves: cheap. Two calls that overlap and barely shrink: exponential. The recurrence sees the difference instantly; the source code does not show it at all.

<Recap lang="en">
A recurrence counts the work of a recursion: T(n) equals the work of one layer plus the cost of the smaller self it calls. The solving craft never changes — unroll three or four steps by substitution, spot the k-th-step pattern, choose k to hit the base case, sum what accumulated, and sanity-check a small n by hand or with a call counter in the code. Four shapes cover most engineering. T(n) = T(n-1) + 1 unrolls to n + 1: linear, the honest scan. T(n) = T(n-1) + n is the painter repainting the fence: the sum 1 + 2 + … + n, which Gauss's end-pairing collapses to n(n+1)/2 — quadratic, the shape that breezes through a 200-row staging run and burns five billion steps on 100,000 prod records. T(n) = T(n/2) + 1 is binary search: the cost is the number of halvings, log₂ n — ten probes for a thousand, twenty for a million. And T(n) = 2T(n/2) + n is merge sort, solved by the level-sum picture: every level totals n, there are log₂ n levels, so n·log n; the Master Theorem you will meet later is this table generalized. The misconception to bury: two recursive calls do not mean twice the cost — A tree that halves stays shallow (about 2n calls), while fibonacci's tree barely shrinks and re-solves overlapping subproblems, exploding to 25 calls at n = 6 and 2.7 million at n = 30. The shape of the call tree, not the count of call expressions, decides the bill — and one line of arithmetic reads it before launch night does.
</Recap>
