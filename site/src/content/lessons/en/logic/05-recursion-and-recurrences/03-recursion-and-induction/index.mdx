<Hook>
In 2006, Joshua Bloch published a post with a headline worthy of a tabloid: nearly all binary searches and merge sorts are broken. The binary search in the Java standard library — reviewed, tested, shipped to millions of machines — had carried a bug for nine years: the line computing the middle, mid = (low + high) / 2, overflows when low + high exceeds the biggest int, which happens on arrays above about a billion elements. Nine years of passing tests. Nine years of users. The tests never used a billion-element array, of course — tests never use the inputs you did not think of. The fix was one line. The unsettling part was the question it left behind: if a decade of green checkmarks could not certify eleven lines of code, what does it mean to KNOW a function is correct? There is an answer, and you have already met both halves of it. Induction proves a claim for all n from two finite steps. Recursion computes a value for all n from two parts. They are the same ladder — and this lesson climbs it in both directions.
</Hook>

## One ladder, climbed two ways

Recall induction from the reasoning unit: to prove a claim `P(n)` for every n, you prove the **base** — `P(0)` holds — and the **step** — *if* `P(n-1)` holds, *then* `P(n)` holds. Two finite pieces of work, and the ladder reaches every rung: P(0), so P(1), so P(2), so P(3)…

Now put it next to a recursive function. The resemblance is not a resemblance; it is an identity:

| Induction (proving)            | Recursion (computing)                  |
| ------------------------------ | -------------------------------------- |
| Base: prove P(0) outright      | Base case: return the answer outright  |
| Hypothesis: assume P(n−1)      | Trust the call: f(n−1) is correct      |
| Step: derive P(n) from P(n−1)  | Layer: combine f(n−1) into f(n)        |
| Conclusion: P(n) for all n     | f works for every input                |

The "leap of faith" from the first lesson of this unit now has a formal name: it is the **inductive hypothesis**. When you trust `factorial(n - 1)` while writing `factorial(n)`, you are doing exactly what a mathematician does when she assumes `P(n-1)` while proving `P(n)`. Induction proves a tower of statements from a base and a step; recursion computes a tower of values from a base and a step. One structure, two sides — and the payoff is practical: any recursive function carries its own correctness proof inside it, waiting to be written out.

## Proving sum correct, fully

Let us write one out, end to end, in sentences a beginner can check. The function:

```js
function sum(list) {
  if (list.length === 0) return 0;       // base
  return list[0] + sum(list.slice(1));   // head + smaller self
}
```

**The claim** `P(n)`: for every list of length n, `sum(list)` returns the sum of its elements.

**Base — `P(0)`.** A list of length 0 is the empty list. The function hits the base case and returns 0. The sum of no numbers is 0. So the returned value is the correct sum. ✓

**Step — `P(n-1)` implies `P(n)`.** Assume the hypothesis: `sum` returns the correct sum for *every* list of length n−1. Take any list of length n, with n at least 1. It is not empty, so the function skips the base case and returns `list[0] + sum(list.slice(1))`. Now look at the pieces. `list.slice(1)` is the tail — a list of length n−1 — so the hypothesis applies to it: `sum(list.slice(1))` is exactly the sum of the tail's elements. The function therefore returns *first element + sum of all the rest*, which is precisely the sum of all n elements. ✓

**Conclusion.** By induction, `P(n)` holds for every n: `sum` is correct for *all* lists. Not all tested lists — all lists.

Read the step again and notice what you did *not* do: you never traced the inner call. You used its correctness as an assumption — legally, because the assumption is the inductive hypothesis and the tail is genuinely shorter. The proof has exactly the shape of the code. That is the deep reason recursive code is pleasant to verify: the proof obligations are the branches.

## The loop wears the same proof

Most production sums are loops, not recursion. Did the proof just evaporate? Write the loop:

```js
function sumLoop(list) {
  let acc = 0;
  // invariant: acc equals the sum of the first i elements
  for (let i = 0; i < list.length; i++) {
    acc += list[i];
  }
  return acc;
}
```

The comment is called a **loop invariant**: a statement that is true *every time the loop checks its condition*. Proving it correct has three beats — and they will feel familiar:

- **Establish.** Before the first iteration, i = 0 and acc = 0 — the sum of the first zero elements. True at the start. *(That is a base case.)*
- **Preserve.** Suppose the invariant holds entering an iteration: acc = sum of the first i elements. The body adds `list[i]`, and i becomes i+1; now acc = sum of the first i+1 elements. The invariant survives. *(That is an inductive step.)*
- **Conclude.** The loop exits when i = n. The invariant at that moment says acc = sum of the first n elements — the whole list. Return it. ✓

Establish, preserve, conclude — base, step, conclusion. **A loop invariant is induction in iterative clothing.** Recursion's induction and iteration's invariant are not two proof techniques; they are one truth wearing two syntaxes. This is also why converting a recursion to a loop (or back) feels mechanical once you see it: you are re-dressing the same proof.

## Termination: the proof correctness cannot give you

Everything above proves something subtle: *if* the function returns, the answer is right. When you write a loop invariant or an inductive proof, ask yourself whether you also have a termination argument — because without one, you have certified "right if it finishes" but not "finishes". Mathematicians call that **partial correctness**. A function that loops forever satisfies it vacuously — it never returns a wrong answer because it never returns. The missing half is **termination**, and it has its own proof tool: a **measure** — a quantity that is a non-negative integer and *strictly decreases* on every recursive call or loop iteration. A non-negative integer cannot decrease forever; it must bottom out, so the recursion must reach a base. For `sum`, the measure is the list length: n, n−1, n−2, … 0. Done.

Now the full treatment for the Hook's patient — binary search over a sorted array, with the candidate range held as a half-open interval `[lo, hi)`:

```js
function search(arr, target) {
  let lo = 0, hi = arr.length;
  // invariant: if target is in arr, its index is inside [lo, hi)
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);  // Bloch's fix: no lo+hi overflow
    if (arr[mid] === target) return mid;
    if (arr[mid] < target) lo = mid + 1;         // discard left half — too small
    else hi = mid;                               // discard right half — too big
  }
  return -1;
}
```

**Correctness (the invariant).** If the target exists, it lies in `[lo, hi)`. True initially — the range is the whole array. Preserved by each branch: the array is sorted, so if `arr[mid]` is smaller than the target, no index up to mid can hold it, and raising `lo` to mid+1 discards only impossible candidates; symmetrically for the other branch. At exit with an empty range, the invariant says the target is in an empty set — so it is absent, and −1 is the honest answer. ✓

**Termination (the measure).** Let the measure be the width `hi − lo`, a non-negative integer. Each iteration either returns, or sets `lo` to mid+1 (mid is at least lo, so lo grows by at least 1), or sets `hi` to mid (mid is strictly below hi, so hi shrinks by at least 1). Either way the width strictly decreases — so it must reach 0, and the loop must end. ✓

Correctness **and** termination together are called **total correctness**: the function returns, and what it returns is right. Eleven lines, two short proofs, and the function is certified for inputs no test will ever construct.

<Inset kind="edgecase" lang="en">
The measure argument is where off-by-one bugs go to be caught. Change lo = mid + 1 to lo = mid and re-run the proof: when the range narrows to width 1, mid equals lo, the branch sets lo to mid — and the width stays 1 forever. The invariant still holds (partial correctness is intact!), but the measure no longer decreases: infinite loop. Tests with lucky targets pass; the proof fails in one line. When a binary search hangs in production, it is almost always a measure that stopped decreasing on some branch.
</Inset>

## The misconception: "it passed for n up to 100, so it is correct"

A test suite checks finitely many inputs: n = 0, 1, 5, 100, maybe a fuzzer's thousand more. The claim "sum is correct" quantifies over *all* n — infinitely many. No finite pile of green checkmarks reaches it, the same way no list of even numbers proves all numbers are even. Recall the counterexamples lesson from the proof-techniques unit: one failing test *refutes* a universal claim forever, but a million passing tests only fail to refute it. **Testing supports; proof covers.** Induction is the only tool in this unit that touches all n at once — two finite steps, infinite coverage.

And yet the Hook cuts both ways, so let us be honest about it. Binary search *had* been proven correct — the proof was fine. It was a proof about ideal integers, and Java's `int` is not an ideal integer: at a billion elements, `low + high` wrapped around, and the proof's silent assumption snapped. The mature conclusion is not "proofs are useless"; it is that **a proof covers everything inside its assumptions, and you must know what those are.** Tests embed their assumptions silently (small n, friendly data); a proof at least writes its own fine print — and the overflow vanishes the moment the model includes bounded ints, which is why the fixed line computes the midpoint without ever forming `low + high`. Proof covers the infinite; tests probe the assumptions. Senior engineers run both.

<Recap lang="en">
Induction and recursion are the same structure read in two directions: induction proves P(n) from P(smaller), recursion computes f(n) from f(smaller), and the four-row mapping is exact — base to base case, inductive hypothesis to trusted call, step to layer of work, universal conclusion to a function correct on every input. The leap of faith from the start of this unit is the inductive hypothesis with its papers in order. The proof of sum shows the method: verify the empty list directly, then for length n assume the tail of length n−1 is summed correctly and check that head plus tail-sum is the whole sum — never tracing the inner call, because the strictly shorter tail is what makes the trust legal. The same proof survives translation to a loop as an invariant — establish it before the first iteration, show each iteration preserves it, harvest it at exit — so recursion's induction and iteration's invariant are one truth in two syntaxes. All of that buys only partial correctness: right if it returns. Termination is proven separately with a measure — a non-negative integer that strictly decreases every step: a list length, a counter's distance to n, binary search's range width hi − lo, where each branch provably shrinks the width and an off-by-one like lo = mid stalls it into an infinite loop. Correctness plus termination is total correctness, certified for all n — which no test suite reaches, since tests check finitely many inputs and a universal claim quantifies over infinitely many. Testing supports, proof covers; and a proof covers exactly what its assumptions allow, as nine years of a broken binary search taught everyone — so write the proof, and let the tests hunt its fine print.
</Recap>
