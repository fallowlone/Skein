<Hook>
Binary search over a million sorted records uses about 20 probes. To someone new to logarithms this looks like magic. It is not — it is mechanical: the call tree halves at every level, so its depth is log₂ n. Merge sort doubles the number of calls but halves the size at every level too, so each level still costs n total work — log₂ n levels, total n·log n. Fibonacci-style recursion doubles the calls without meaningfully shrinking the input, and explodes to 2.7 million calls at n = 30. This lesson is the map from recurrence shape to growth class: logarithmic, n·log n, and exponential.
</Hook>

<Goal>
After this lesson you can unroll T(n) = T(n/2) + 1 to log₂ n, read the merge-sort level-sum table for T(n) = 2T(n/2) + n to get n·log n, explain why fibonacci-style recursion is exponential, and predict the growth class from the recurrence without running the code.
</Goal>

<Step title="Halving: T(n) = T(n/2) + 1">

Binary search looks at the middle element and discards half the range. One comparison per call, then a problem of half the size:

```
T(n) = T(n/2) + 1
```

Unroll:

```
T(n) = T(n/2) + 1
     = T(n/4) + 2
     = T(n/8) + 3
       …pattern: T(n/2ᵏ) + k
```

The base arrives when `n/2ᵏ` reaches 1 — that is, when k equals the number of times n can be halved: `k = log₂ n`. Count it concretely, because logs deserve fingers:

```
1000 → 500 → 250 → 125 → 62 → 31 → 15 → 7 → 3 → 1     ≈ 10 halvings  (2¹⁰ = 1024)
1,000,000 → … → 1                                       ≈ 20 halvings  (2²⁰ ≈ 1,048,576)
```

A million sorted records, found in twenty probes. Doubling the data adds *one* step. This is why "sorted plus halving" is the most valuable shape in engineering — and the recurrence is the receipt.

<Step title="Level sum: T(n) = 2T(n/2) + n">

Merge sort splits the list in half, recursively sorts *both* halves, then merges them with n steps of zipping:

```
T(n) = 2·T(n/2) + n
```

Unrolling still works, but a picture works better. Draw the calls level by level and total each level:

| Level  | Subproblems | Size of each | Work at this level |
| ------ | ----------- | ------------ | ------------------ |
| 0      | 1           | n            | n                  |
| 1      | 2           | n/2          | 2 · n/2 = n        |
| 2      | 4           | n/4          | 4 · n/4 = n        |
| …      | …           | …            | n                  |
| log₂ n | n           | 1            | n                  |

Every level costs exactly n: the subproblems multiply at exactly the rate they shrink. Total work = work per level × number of levels:

```
T(n) ≈ n · log₂ n
```

For a million items: 1,000,000 × 20 = 20,000,000 steps — closer to linear than to the five-billion quadratic from the previous lesson.

<Inset kind="note" lang="en">
There is a famous lookup table for these level-sum patterns called the **Master Theorem**. You will meet it in the algorithms track. It is exactly this table, generalized. Learn the picture first, the table second — the table is only useful once you can draw the levels it summarizes.
</Inset>

</Step>

<Step title="Exponential: T(n) = T(n-1) + T(n-2) + 1">

The naive fibonacci function makes two recursive calls — but the inputs shrink by only 1 and 2:

```
T(n) = T(n-1) + T(n-2) + 1
```

The call tree stays deep *and* keeps branching. `fib(3)` is computed three separate times inside `fib(6)`:

```
fib(6)
├─ fib(5)
│  ├─ fib(4)
│  │  ├─ fib(3) …5 calls
│  │  └─ fib(2) …3 calls
│  └─ fib(3) …5 calls
└─ fib(4) …9 calls
                    total: 25 calls for n = 6
```

The counter makes the explosion visceral:

```js
let calls = 0;
function fib(n) {
  calls++;
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
}
fib(6);  console.log(calls); // 25
calls = 0;
fib(30); console.log(calls); // 2,692,537 — for n = 30!
```

Twenty-five calls to compute fib(6) = 8. At n = 30 that is 2.7 million calls. The tree barely shrinks while doubling at every level — exponential.

</Step>

<Step title="Call tree shape decides the bill">

Resist the urge to count call expressions in the source. Two functions can each make **two** recursive calls and produce wildly different costs:

```
A:  T(n) = 2·T(n/2) + 1      (two calls on HALVES)
B:  T(n) = T(n-1) + T(n-2) + 1   (two calls on n-1 and n-2)
```

A's call tree is short and balanced: log₂ n levels, about 2n calls in total. B's tree shrinks by only 1 or 2 per level while still branching — exponential.

The two questions that classify any recurrence:
1. **How fast does the input shrink?** Halving is fast (log₂ n levels). Subtracting 1 or 2 is slow (n levels).
2. **How many calls are made at each level?** One call = no branching. Two calls on halves = shallow branching. Two calls on barely-smaller inputs = explosive branching.

Those two quantities — shrink rate versus branching factor — fully determine the growth class. The count of call expressions in the source code does not.

</Step>

<WorkedExample title="Merge sort on n = 8 elements">

Trace the level-sum table for n = 8 (log₂ 8 = 3 split levels):

| Level | Subproblems | Size | Work |
| ----- | ----------- | ---- | ---- |
| 0     | 1           | 8    | 8    |
| 1     | 2           | 4    | 8    |
| 2     | 4           | 2    | 8    |
| 3     | 8           | 1    | 8    |

Total: 4 levels × 8 = 32 steps.

Using the formula: n · log₂ n = 8 · 3 = 24 (the formula counts the split levels, not the base level — the exact count is n · (log₂ n + 1) for this shape, which is 32 here). Either way, on n = 8 the cost is in the low thirties, not the hundreds you would get from a quadratic sort on the same input (8 · 9 / 2 = 36 for the quadratic, close here, but the gap explodes at n = 1000: n·log n ≈ 10,000 versus n² = 1,000,000).

The key insight: **every level costs the same n work**, so the total is just n times the number of levels.

</WorkedExample>

<Recap lang="en">
Three growth classes complete the recurrence map. T(n) = T(n/2) + 1 is logarithmic: the cost equals the number of halvings, log₂ n — ten probes for a thousand sorted records, twenty for a million. T(n) = 2T(n/2) + n is n·log n: the level-sum picture shows every level costs n and there are log₂ n levels, so the total is n·log n; the Master Theorem you will meet in the algorithms track is this table generalized. T(n) = T(n-1) + T(n-2) + 1 is exponential: the input barely shrinks while branching two ways, the same subproblems are re-solved repeatedly, and 25 calls at n = 6 becomes 2.7 million at n = 30. The unifying lesson: the shape of the call tree — how fast the input shrinks versus how much it branches — decides the bill. Two recursive calls in source code means nothing on its own; two calls on halves is nearly linear, two calls on barely-smaller inputs is explosive. The recurrence sees the difference instantly; the source code does not show it at all.
</Recap>
