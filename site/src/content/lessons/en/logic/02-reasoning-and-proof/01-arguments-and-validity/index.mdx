## Premises, conclusions, and what "valid" actually means

An **argument** is not a quarrel — in logic it is just a list of statements: some **premises** (the things you assume or observe) and one **conclusion** (the thing you claim follows). The release-night argument had two premises — "if the cache works, latency is low" and "latency is low" — and one conclusion, "the cache works."

An argument is **valid** when its *shape* makes it impossible for all premises to be true while the conclusion is false. Validity is a property of the form, not the topic: "if it rains, the street is wet; it rains; so the street is wet" and "if the cache works, latency is low; the cache works; so latency is low" are the same argument wearing different clothes. Swap in any statements for P and Q and a valid form still works.

Validity says nothing about whether the premises are actually true. For that there is a second word: an argument is **sound** when it is valid *and* all its premises are true. "All deploys on Friday fail; today is Friday; therefore today's deploy fails" is perfectly valid — and useless, because the first premise is false. Valid form plus false premises proves nothing about the world. In a debugging session you need both: a rule you actually trust, and an inference shape that cannot betray you.

<Inset kind="why" lang="en">
Why obsess over form instead of content? Because form is the only part you can check mechanically, without knowing anything about caches or weather. A valid form is a contract: feed it true premises and it is *guaranteed* to output a true conclusion, for any subject matter whatsoever. That guarantee is what lets a compiler's type checker, a database's query planner, and your own 3 a.m. debugging brain reuse the same handful of inference rules everywhere. Content can lie to you; a valid form never does — it can only be fed lies.
</Inset>

## The two safe moves: modus ponens and modus tollens

Both rules start from a conditional — a rule of the form "if P, then Q," written P → Q. From there, exactly two observations license a conclusion.

**Modus ponens** ("the affirming mode"): from P → Q and *P is true*, conclude Q. If the cache works, latency is low; the cache works (you verified the flag, watched the hit counter move); therefore latency is low. You confirmed the *if* part, so the *then* part follows.

**Modus tollens** ("the denying mode"): from P → Q and *Q is false*, conclude not-P (written ¬P). If the cache works, latency is low; latency is *high*; therefore the cache is **not** working. This is the skeleton of almost every real debugging step you will ever take: *if my hypothesis were true, I would see X; I do not see X; my hypothesis is dead.* Each failed expectation validly kills one suspect.

You can verify both shapes by brute force — try every combination of true and false and look for a case where the premises hold but the conclusion fails:

```js
// P → Q is false only in one world: P true, Q false.
const implies = (p, q) => !p || q;

// A form is valid if NO assignment makes all premises true and the conclusion false.
function isValid(premises, conclusion) {
  for (const p of [true, false]) {
    for (const q of [true, false]) {
      const premisesHold = premises.every((f) => f(p, q));
      if (premisesHold && !conclusion(p, q)) return false; // counterexample found
    }
  }
  return true;
}

// Modus ponens: from (p → q) and p, conclude q.
isValid([(p, q) => implies(p, q), (p, _q) => p], (_p, q) => q);   // true

// Modus tollens: from (p → q) and ¬q, conclude ¬p.
isValid([(p, q) => implies(p, q), (_p, q) => !q], (p, _q) => !p); // true

// Affirming the consequent: from (p → q) and q, conclude p.
isValid([(p, q) => implies(p, q), (_p, q) => q], (p, _q) => p);   // false!
// The counterexample: p = false, q = true. Cache broken, latency low anyway.
```

Four lines of loop do what Aristotle did by hand: the first two forms survive every world; the third has a counterexample, so it proves nothing.

## The two impostors: affirming the consequent, denying the antecedent

**Affirming the consequent**: from P → Q and *Q is true*, conclude P. That is release night: latency is low, therefore the cache works. Invalid — the rule only promises that a working cache *produces* low latency; it never promised that low latency has no other causes. Low traffic, a CDN, a lucky warm database — Q can be true while P is false, and the form collapses.

**Denying the antecedent**: from P → Q and *P is false*, conclude ¬Q. "If the cache works, latency is low; the cache is broken; therefore latency must be high." Also invalid, for the same reason viewed in a mirror: breaking one cause of low latency does not outlaw every other cause.

Both fallacies feel valid because they reuse the same three ingredients as the real rules — a conditional and two facts — just combined in the wrong order. A useful mental alarm: a conditional P → Q gives you traction in exactly two cases, *P confirmed* or *Q refuted*. The other two observations — Q confirmed, P refuted — license **nothing**. When the dashboard shows the good outcome, you have learned only that your hypothesis *survived*, not that it is true. Evidence consistent with your theory is not evidence for your theory unless it could have come out otherwise.

## Debugging is applied modus tollens

A debugging session is a chain of conditionals: *if the bug were in the parser, the failing input would be malformed; if the database were down, every endpoint would fail, not just one; if the cache were working, this key would be present.* Each test you run tries to refute a consequent. When the prediction fails — the input is well-formed, only one endpoint fails, the key is missing — modus tollens validly eliminates a suspect. Good debugging is the disciplined accumulation of ¬P after ¬P until one hypothesis remains standing.

The discipline cuts both ways. When a prediction *succeeds*, resist the warm feeling: you have affirmed a consequent, which eliminates nothing. The senior habit is to design tests whose *failure* would be informative — predictions specific enough that the world has a real chance to refute them. "If my fix works, the test goes green" followed by a green test is comfort, not proof; flaky tests go green too. "If my fix works, the test goes green *and reverting the fix makes it red again*" — now refutation has teeth, and surviving it means something.

<Recap lang="en">
An argument is premises plus a conclusion, and it earns the word valid when its form forbids the one fatal combination — all premises true, conclusion false — regardless of subject matter; it earns the word sound only when the form is valid and the premises are also actually true, which is the only verdict that guarantees anything about the real world. A conditional rule P → Q supports exactly two valid moves: modus ponens (P confirmed, conclude Q) and modus tollens (Q refuted, conclude ¬P), and the second is the skeleton of debugging — if my hypothesis were true I would see X, I do not see X, the hypothesis is eliminated. The two remaining observations are traps with classical names: affirming the consequent (Q is true, so P must be — the release-night cache fallacy, ignoring that low latency has other causes) and denying the antecedent (P is false, so Q must fail too). A green dashboard or a passing test only means your hypothesis survived, not that it is true; design checks whose failure would be informative, accumulate valid refutations, and keep validity and soundness separate in code review — a beautiful inference from a false premise proves exactly nothing. Now when you see a team conclude the cache works because latency is low, you have a name for the mistake and the valid alternative sitting right next to it.
</Recap>
