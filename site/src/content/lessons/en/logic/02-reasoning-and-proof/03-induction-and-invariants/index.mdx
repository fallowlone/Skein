Code review, Thursday afternoon. The diff is a tight little loop that batches user records for export, and the tests pass — for 3 records, for 10, for 100. The reviewer leaves one comment: "Why does this work for a million records? You tested three sizes." The author types and deletes several replies. ## Dominoes: a base case and an inductive step

How do you prove a statement about *every* natural number — infinitely many cases — in finite time? **Mathematical induction** says: do exactly two things. **Base case**: show the claim holds for the first value, usually n = 0 or n = 1. **Inductive step**: show that *if* the claim holds for an arbitrary n (this assumption is the *induction hypothesis*), *then* it holds for n + 1. Two finite proofs, and the conclusion covers infinity: the claim is true for every natural number from the base onward.

The standard picture is a row of dominoes. The base case tips the first domino. The inductive step guarantees each falling domino knocks over the next. Given both, every domino falls — including domino number one million, which nobody touched directly. Note what the step really is: not a claim that n works, but a *conditional* — n works → n+1 works. You prove the conditional once, for a generic n, and modus ponens does the rest, n times in a row, for any n you care about.

Both parts are load-bearing. Skip the base case and you can "prove" nonsense: the step "if n is even then n + 2 is even" is flawless, but starting from 1 it generates only odd numbers — a perfect chain of dominoes that nobody tipped. Skip the step's *generality* and you get the classic broken proof that all horses are the same color: the argument quietly assumes two groups overlap, which fails exactly at n = 2 — one rung of the ladder is cracked, and everything above it falls down.

## Strong induction: lean on everything below

Sometimes "it worked for n" is not enough fuel for the step. **Strong induction** upgrades the hypothesis: assume the claim holds for *all* values up to n, then prove it for n + 1. This matters whenever a problem decomposes not into "one smaller" but into "some smaller": every integer above 1 factors into primes (a number splits into two factors of *unpredictable* sizes — you need the hypothesis at both, not at n − 1); merge sort is correct (an array of length n splits into halves of length n/2, far below n − 1). Strong induction is not a different machine — it is provably equivalent to ordinary induction — but it is the natural shape for **recursion**: a recursive function that handles its base case and is correct whenever its recursive calls on *any smaller inputs* are correct, is correct, full stop. That is structural thinking you already use every time you trust `mergeSort` on the halves while writing the merge.

<Inset kind="why" lang="en">
Why does this argument pattern get to call itself proof while "it worked in staging" does not? Because induction is just dressed-up modus ponens, the valid form from lesson one. The step proves a universal conditional — for every n, P(n) → P(n+1) — and the base supplies P(0). Apply modus ponens once: P(1). Again: P(2). For any target n the chain is a finite, fully valid deduction; the induction principle merely asserts the whole family at once. Testing, by contrast, establishes P at scattered points with no conditional connecting them — which is why three passing sizes say nothing about the fourth, and why the reviewer's question has no answer made of more test runs.
</Inset>

## Loop invariants: induction wearing work clothes

A **loop invariant** is a statement about the program's variables that is true *every time the loop checks its condition*. Proving a loop correct with an invariant is induction with the labels changed: **initialization** (the invariant holds before the first iteration — base case), **maintenance** (if it holds at the top of an iteration, it holds at the top of the next — inductive step), **termination** (the loop exits, and at exit, invariant + loop-condition-false together imply the result you wanted). Here is the proof for the simplest loop that ever shipped a bug:

```js
function sumFirst(nums) {
  let total = 0;
  let i = 0;
  // INVARIANT: total === sum of nums[0..i-1]  (the first i elements)

  // Initialization: i = 0, total = 0, and the sum of zero elements is 0. Holds.
  while (i < nums.length) {
    // invariant holds here: total is the sum of the first i elements
    total += nums[i];
    i += 1;
    // total now includes nums[i-1]: it is the sum of the first (new) i elements.
    // The invariant survived the iteration — maintenance proved.
  }
  // Termination: i === nums.length, so the invariant reads:
  // total === sum of nums[0..nums.length-1] — the sum of ALL elements. QED.
  return total;
}
```

Three small checks and the function is correct for *every* array — length zero (the loop never runs; the invariant alone says total is the empty sum, 0), length three, length one million. No fixture file can say that.

The invariant is also a bug detector. Take the classic off-by-one: initialize `i = 1` "because we start with the first element already in `total`." Now run initialization: total = 0, i = 1, but the sum of the first 1 element is `nums[0]`, not 0 — the invariant is false *before the loop even runs*, and the proof fails at the base case, exactly where the bug is. The pagination loop from the Hook dies the same way: state the invariant "rows 0..k−1 have been emitted exactly once," and the maintenance step refuses to go through for the version that advances the cursor by `pageSize` from the *last seen id plus one*. A failing proof points at the line; a failing test points at a symptom.

## Writing invariants in real reviews

The skill that transfers to Thursday's code review is *stating* the invariant, because most loop bugs are invariant bugs in disguise. Practical heuristics: the invariant usually describes **what the variables mean** ("total is the sum of everything processed so far", "everything left of `write` is deduplicated", "the answer lies in `lo..hi`"); it must mention the loop variable, or it cannot connect iterations; and it should make the *return statement* a one-line consequence at exit. Binary search is the canonical payoff — the invariant "if the target exists, its index is in [lo, hi)" decides every agonizing detail (is the loop `lo < hi`? is it `hi = mid` or `hi = mid - 1`?) that engineers otherwise settle by superstition. Termination gets its own tiny proof: name a quantity that strictly decreases each pass and cannot decrease forever — `hi - lo` in binary search, `nums.length - i` in the sum. A loop with a proved invariant but no termination argument is a correct answer you may never receive. Write the invariant as a comment above the loop; the next reader inherits not just code that works, but the reason it must.

<Recap lang="en">
Mathematical induction proves a claim about every natural number with two finite pieces: a base case (the claim holds at n = 0) and an inductive step (a universal conditional — if it holds at an arbitrary n, it holds at n + 1), after which any specific n is reached by a finite chain of modus ponens; both pieces are mandatory, since a perfect step with no base is an untipped domino row, and a step proved only for examples is the all-horses fallacy with its crack hidden at one rung. Strong induction strengthens the hypothesis to all values up to n — equivalent in power, but the natural fit for problems that split into arbitrarily smaller parts: prime factorization, merge sort, and every recursive function that is correct whenever its recursive calls on smaller inputs are. A loop invariant transplants the proof into code: state what the variables mean at every condition check ("total is the sum of the first i elements"), then discharge three obligations — initialization (true before the loop; the base case), maintenance (each iteration preserves it; the step), and termination (a strictly decreasing quantity forces exit, where invariant plus failed loop condition imply the returned answer). The payoff over testing is categorical, not incremental: the proof covers the empty input, the million-element input, and the production data no fixture anticipates, and when a proof obligation fails it points at the guilty line — initialize i = 1 in the sum loop and initialization itself refuses, exposing the off-by-one before the loop runs. Write the invariant as a comment; ship the reason, not just the code.
</Recap>
