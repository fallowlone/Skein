Metrics are pre-aggregated numeric time series: cheap to query across years, but blind to any dimension not in the label set, and their cost axis is cardinality (series count). Logs are event records that preserve every field: any post-hoc question is answerable, but the cost is ingestion bytes and query scan time.     { q: "Explain why cardinality is the metrics cost cliff but high-cardinality fields are nearly free in logs.", a: "A Prometheus metric is identified by (name, label_set); every unique combination of label values is a separate time series stored at ~3 KB in the head block. Adding an unbounded label like user_id multiplies series count by the number of distinct values — 100k users can push a 400-series metric to tens of millions and OOM the TSDB in hours. Logs have no per-value series: each event is stored as raw bytes, so adding user_id to a log line costs only the marginal bytes of that field plus query scan time. The architectural difference is series-count memory (a hard cliff) versus ingestion volume (a linear bill that degrades gracefully)." },
    { q: "Contrast head-based and tail-based sampling: where is each cheap, and which traces does each risk losing?", a: "Head-based decides at trace start; if the decision is 'drop', the SDK emits no spans, so it is cheap end-to-end and collector load is proportional to the sampling rate. Its weakness is that a uniform random sample under-represents rare events — errors and slow tails get dropped as often as anything else. Tail-based buffers every span until the trace completes (30–60s), then decides on full context, so it keeps 100% of errors and slow traces — but every span flows through the collector regardless, so collector CPU and memory scale with raw traffic, not stored volume. Production pattern: head-based at 10–20% baseline plus tail policies for errors and slow tails." },
    { q: "What are join keys, why does OpenTelemetry Semantic Conventions matter even on 1.0 backends, and how do exemplars fit?", a: "Join keys are shared attribute NAMES that appear identically across metrics, logs, and traces — service.name, trace_id, http.route, db.system. They are what turn three separate backends into one navigable surface: with them, pivoting metric → log → trace is one click; without them every dashboard needs ad-hoc query translation and run-books are fragile. OpenTelemetry Semantic Conventions defines the canonical names, so it is load-bearing even on Prometheus + Loki + Jaeger — the field names ARE the semantics, independent of SDK or backend. Exemplars are the metric-to-trace bridge: a sampled trace_id attached to a histogram bucket observation lets you click from an aggregate spike to one concrete slow request without paying cardinality cost." },

Columnar storage and cheap object storage collapse all three into wide structured events — one record per unit of work carrying every field including high-cardinality ones, with metrics computed by GROUP BY, logs by filter, and traces by joining on trace_id at query time. Cardinality stops being a cost driver. But 1.0 still wins for very-long-retention (5+ year) low-cardinality SLO metrics, where pre-aggregation on cold storage is cheaper than scanning raw wide events.
