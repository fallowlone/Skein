<Crux>Observability is how you see what a running system is doing from the outside — through the signals it emits: logs, metrics, and traces.</Crux>

<Explanation>

## Why you cannot just look inside

On your laptop you can pause the code, print a value, step line by line. In production you cannot: the system is on another machine, it is serving many users at once, and the problem may have already passed by the time you look. The only way to understand it is from the outside — by what it reports about itself while it runs. Observability is exactly that: building a system that explains its own behavior, so you can ask "why is this happening?" without stopping it or guessing.

## The three signals

A running system emits three kinds of clue, and each answers a different question:

- A **log** is a timestamped message about one event — "user 42 logged in," "payment failed." It tells you *what happened*.
- A **metric** is a number measured over time — requests per second, error rate, memory used. It tells you *how much*, and shows trends.
- A **trace** follows one request as it travels across services. It tells you *where the time went* and which step broke.

## The mental model to carry up

Hold one idea for the whole climb: you cannot fix what you cannot see, and a running system only shows you what you taught it to report. Observability is the discipline of making a system describe itself well — so that when something breaks at 3 a.m. for a user you will never meet, the answer is already in the signals. The rest of this track is how: how to write logs worth reading, how to choose metrics that warn you early, and how to trace a request across many services.
