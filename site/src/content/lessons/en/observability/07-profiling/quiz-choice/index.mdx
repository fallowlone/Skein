<Quiz
  id="07-profiling-choice-1"
  lessonSlug="07-profiling"
  lang="en"
  question="A request takes 500 ms wall-clock but the CPU profile attributes only 20 ms to it. Where did the other 480 ms go, and which profile reveals it?"
  choices={[
    { label: "The thread was off-CPU — waiting on I/O, a lock, or the scheduler — and a CPU profile is blind to waiting. An off-CPU profile (or block/mutex profile, or the trace span) attributes that 480 ms to the blocking call site.", correct: true },
    { label: "The CPU profile is undersampled; raise the sample rate to 1000 Hz and the missing 480 ms appears.", misconception: "A higher rate gathers more samples of running code, but a descheduled thread consumes zero CPU and is never on the CPU to be sampled at any rate. The time is off-CPU by definition." },
    { label: "The 480 ms is GC pause time; take a heap profile.", misconception: "A heap profile shows allocated bytes per stack, not wait time. The general answer for a low-CPU/high-wall request is off-CPU waiting, surfaced by an off-CPU or block profile." },
    { label: "The profiler dropped samples; the 480 ms is unrecoverable.", misconception: "Nothing was dropped. The CPU profile correctly reports 20 ms of compute; the rest is off-CPU time a CPU profiler is designed not to see." },
  ]}
/>

<Quiz
  id="07-profiling-choice-2"
  lessonSlug="07-profiling"
  lang="en"
  question="A service makes 5 million function calls/second. You want always-on production profiling. Why is a sampling profiler the only viable choice over instrumentation?"
  choices={[
    { label: "Instrumentation cost scales with call frequency (5M timing measurements/s); sampling cost is fixed at N stack walks/s regardless of call rate. At 100 Hz that is ~1 ms overhead per second vs seconds of overhead per second for instrumentation.", correct: true },
    { label: "Instrumentation cannot capture call stacks, only sampling can.", misconception: "Instrumentation captures exact call counts and timings per function — more data, not less. The disqualifier is cost: it scales with call frequency, not the data it produces." },
    { label: "Sampling is more accurate than instrumentation.", misconception: "Instrumentation is exact; sampling is statistical with a confidence interval. Sampling wins on bounded overhead, not accuracy — its accuracy is merely sufficient to find hotspots." },
    { label: "Sampling profilers do not require representative load.", misconception: "Both need representative load — an idle system shows only the runtime idle loop. The reason sampling wins in production is its bounded, call-rate-independent overhead." },
  ]}
/>

<Quiz
  id="07-profiling-choice-3"
  lessonSlug="07-profiling"
  lang="en"
  question="An engineer points at two wide frames side by side at the same level of a flame graph and concludes the left one runs before the right one. What is wrong?"
  choices={[
    { label: "The x-axis is alphabetical grouping of full stack paths, not time. Left-of means lexicographically earlier, nothing about call order. For execution order you need a trace timeline (Gantt-style spans), not a flame graph.", correct: true },
    { label: "Nothing — flame graphs are time-ordered left to right, so the left frame did run first.", misconception: "This is the single most common flame-graph misread. The flame graph sorts stacks alphabetically by root to keep a parent's children adjacent; the x-axis is never time." },
    { label: "The two frames must share a parent, so order is undefined but they alternate.", misconception: "They may or may not share a parent. Adjacency comes from lexicographic sorting of the full stack string, and width is sample count — neither encodes when or how often they alternated." },
    { label: "The conclusion is right only if the profiler used wall-clock mode.", misconception: "No standard flame graph puts time on the x-axis. A wall-clock view of one request is a flame chart / trace timeline, a different visualisation." },
  ]}
/>

<Quiz
  id="07-profiling-choice-4"
  lessonSlug="07-profiling"
  lang="en"
  question="An eBPF profiler shows clean stacks for Go and Rust services but many '[unknown]' frames for a Python service on the same node. Why?"
  choices={[
    { label: "Go and Rust embed frame pointers / DWARF so the kernel can unwind and symbolize natively. CPython runs user code as bytecode inside its C interpreter loop, so captured addresses point into that loop, not Python source — symbolization needs CPython-aware support.", correct: true },
    { label: "Python is too slow for eBPF sampling, so frames time out and show as unknown.", misconception: "Speed is irrelevant to symbolization. The kernel captures the stack fine; it just cannot map interpreter-internal addresses to Python names without CPython-specific unwinding." },
    { label: "The eBPF agent is broken for Python and should be replaced.", misconception: "[unknown] frames for interpreted runtimes are expected without explicit support. The fix is a Python-aware profiler (py-spy) or a CPython-supporting eBPF mode, not replacing the agent." },
    { label: "Python uses JIT compilation that confuses the unwinder.", misconception: "CPython is a bytecode interpreter, not a JIT. JIT runtimes (JVM, V8) have a different symbolization problem solved via perf maps or AsyncGetCallTrace." },
  ]}
/>

<Quiz
  id="07-profiling-choice-5"
  lessonSlug="07-profiling"
  lang="en"
  question="A continuous profiler is advertised at 2-5% overhead, but you measure 12% in production. What is the most likely cause to check first?"
  choices={[
    { label: "Configuration or environment, not the tool: sample rate set far above default, expensive symbol resolution on the app thread, or very deep (120+ frame) middleware stacks that make each stack walk cost proportionally more.", correct: true },
    { label: "The tool is lying; switch profilers immediately.", misconception: "The 2-5% figure is real and verifiable on typical workloads. A spike above it almost always indicates misconfiguration or a deep-stack/JIT-symbolization cost — check config before swapping tools." },
    { label: "Continuous profiling is fundamentally too expensive for production.", misconception: "Continuous profiling at 2-5% is industry-standard always-on. The premise of the unit is that it is cheap enough to leave on; a 12% reading is an anomaly to diagnose." },
    { label: "Sampling overhead always grows with traffic, so 12% is expected under load.", misconception: "Sampling cost is bounded by sample rate, not call rate, so it does not grow with traffic. A rise to 12% points at rate misconfig, synchronous symbol work, or deep stacks." },
  ]}
/>

  question="During an incident review someone proposes attaching the production profile to the vendor support ticket. Why should a senior engineer object?"
  choices={[
    { label: "Profiles are security-sensitive: function names expose private APIs and internal structure, allocation profiles may capture argument values, and the names alone can telegraph proprietary logic. Treat them like debugger output — RBAC-gated, retention-limited, not shared externally without approval.", correct: true },
    { label: "No objection needed — profiles are operational data and safe to share widely.", misconception: "This is exactly the misconception the unit warns about. A profile is closer to debugger output than to a metric; function names and call patterns can reverse-engineer business logic." },
    { label: "Only allocation profiles are sensitive; a CPU profile is safe to attach.", misconception: "CPU profiles expose function names and call patterns already. Allocation profiles add possible argument values on top — but the CPU profile alone warrants access control." },
    { label: "The file is too large to email.", misconception: "Compressed profiles are tiny (~50-500 KB). The concern is information exposure, not file size." },
  ]}
/>

<Recap lang="en">
The unit's through-line is one diagnostic loop: pick the profile that answers your question (CPU for compute, off-CPU/block/mutex for waiting, heap/allocation for memory), read the flame graph correctly (width is sample share, x-axis is alphabetical not time), and trust the numbers only when you know their limits (sampling is bounded but blind to sub-interval hot paths, eBPF needs language-aware symbolization, 2-5% overhead is real but config-sensitive). And because a profile exposes code internals, you treat it as a security-sensitive artefact, not a freely shareable metric.
</Recap>
