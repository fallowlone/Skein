Sampling fires an external clock N times per second and walks the current stack, so cost is fixed at N stack walks/second regardless of how many calls happen between samples. At 100 Hz and ~5-20 microseconds per walk, overhead is ~0.5-2%, and a full continuous-profiler pipeline (batching, shipping) lands at 2-5%. The statistical property that makes it work: a function using X% of CPU appears in X% of samples, so you recover CPU-time share without touching every call. Sampling trades exactness for bounded, call-rate-independent overhead — exactly the trade production demands." },

Heap/allocation profile: which stacks allocate the most bytes (heap = live memory, allocation = total churn including GC-reclaimed) — answers 'what is causing GC pressure or OOM'. Off-CPU profile: where a thread spends time descheduled, captured at sched_switch — answers 'what is the request waiting on' (I/O, sleep, scheduling). Block profile: time on synchronisation primitives (channels, WaitGroups). Mutex profile: lock contention specifically, attributed at unlock time. The diagnostic shortcut is the CPU/wall-clock ratio: near 100% means a compute bottleneck (CPU profile); under ~30% means the bottleneck is off-CPU (off-CPU/block profile or trace spans); steady memory growth means heap/allocation profile." },
    { q: "What does the x-axis of a flame graph actually encode, and what is the most expensive misread?", a: "The x-axis is alphabetical grouping of full stack paths: identical stacks collapse into one column whose width is sample count, and unique stacks are sorted alphabetically by root so a parent's children sit adjacent. It is not time and not call order. The most expensive misread is treating left-of-another as 'runs before' — a frame's horizontal position tells you only that its stack path sorts earlier lexicographically, nothing about execution order. Two adjacent frames may share no parent, may be unrelated code paths, or may run in parallel. Width (sample share) is the only quantity that means anything about cost. When you genuinely need execution order, use a trace timeline (Gantt-style spans); flame graphs answer 'what' is hot, traces answer 'when' each step ran." },
    { q: "What does continuous profiling give you operationally that on-demand profiling cannot, and roughly what does it cost?", a: "On-demand profiling requires you to be present while the problem is happening: SSH in, reproduce under load, capture, analyse. Many production issues are intermittent and self-resolve before you can attach, so the evidence is gone. Continuous profiling runs an agent on every host sampling ~100 times/second, batching and shipping compressed profiles every 10-15 seconds to a backend indexed by service, host, and time. When an SLO burns at 2 AM, the flame graph for the burning minutes is already saved — no reproduction needed; the on-call filters to the burn window and reads it immediately. Cost is ~2-5% CPU and roughly 50-200 MB/service/day (about 1.5-6 GB/month), reduced further by symbol deduplication. This turns a multi-hour investigation into a sub-90-second root-cause." },

Go and Rust compile to native code with frame pointers or DWARF unwind info, so the kernel can follow the frame chain and map addresses to function names. CPython runs user code as bytecode inside its C interpreter loop (PyEval_EvalFrameDefault); the captured addresses point into that C loop, not Python source, so without CPython-aware unwinding (walking PyFrameObject linked lists) they show as [unknown].
