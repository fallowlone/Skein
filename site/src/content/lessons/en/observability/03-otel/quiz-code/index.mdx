## Snippet 1 — the processor order

```yaml
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [tail_sampling, memory_limiter, batch]
      exporters: [otlp/backend]
```

<Quiz

  lessonSlug="03-otel"

  question="Under a traffic spike this pipeline OOM-kills the gateway. What is wrong, and what is the fix?"
  choices={[
    { label: "The order is inverted: tail_sampling buffers every span for the decision window (30-60s) before memory_limiter can shed load, so the buffer grows past the RAM limit and OOMs. Put memory_limiter first, then batch, then tail_sampling — so the limiter can drop cheaply before the expensive buffering.", correct: true },
    { label: "tail_sampling should never be in the same pipeline as batch; remove batch.", misconception: "batch and tail_sampling coexist fine — tail_sampling buffers traces, batch groups the kept ones for export. The defect is that memory_limiter runs last, too late to protect against the buffering." },
    { label: "The OTLP receiver needs a rate limit; processors are fine.", misconception: "Rate-limiting masks the symptom. The structural bug is memory_limiter running after the processor that consumes the most memory — reorder it first." },
    { label: "Add a second exporter so load is shared.", misconception: "A second exporter does nothing for inbound buffering memory. The OOM is in the tail_sampling buffer, governed by processor order and num_traces, not export fan-out." },
  ]}

## Snippet 2 — the tail-sampling policy

```yaml
processors:
  tail_sampling:
    decision_wait: 30s
    num_traces: 50000
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow
        type: latency
        latency: { threshold_ms: 1000 }
      - name: baseline
        type: probabilistic
        probabilistic: { sampling_percentage: 1 }
```

<Quiz
  id="03-otel-code-2"
  lessonSlug="03-otel"
  lang="en"
  question="At a sustained 2,000 traces/sec the gateway starts dropping traces before decisions are made, and otelcol_processor_tail_sampling_count_traces_on_memory sits above num_traces. What is the sizing error?"
  choices={[
    { label: "num_traces is sized for baseline, not peak. The buffer must hold peak_rate × decision_wait × safety_factor: 2000 × 30 × 2 = 120,000, not 50,000. Resize num_traces to ~120k and raise gateway RAM proportionally.", correct: true },
    { label: "decision_wait is too short — raise it to 120s.", misconception: "Raising decision_wait makes it worse: a longer window means more concurrent in-flight traces, so the buffer needs to be even larger. The fix is sizing num_traces for the rate × window, not extending the window." },
    { label: "The probabilistic baseline of 1% is too high.", misconception: "The baseline percentage controls how many non-error, non-slow traces are kept after the decision — it does not control how many traces are buffered while waiting. Buffer pressure is set by peak_rate × decision_wait." },
    { label: "status_code and latency policies conflict and double-count.", misconception: "Policies are OR-ed: a trace kept by any policy is kept once. They do not double-count or cause the buffer overflow — undersized num_traces does." },
  ]}
/>

## Snippet 3 — the Collector self-metrics line

```
otelcol_processor_dropped_spans{processor="memory_limiter"} 18432
otelcol_receiver_refused_spans{receiver="otlp"} 9120
otelcol_exporter_send_failed_spans{exporter="otlp/backend"} 0
process_resident_memory_bytes 1.93e+09   # limit 2.0e+09
```

    { label: "The backend is down — that is why spans are being dropped.", misconception: "otelcol_exporter_send_failed_spans is 0, so the backend is accepting exports fine. The drops are from memory_limiter under RAM pressure, an upstream capacity problem, not a backend outage." },
    { label: "The OTLP receiver is misconfigured because it is refusing spans.", misconception: "refused_spans here is back-pressure: the receiver refuses because the processor chain (memory_limiter) is shedding load near the RAM ceiling. The receiver config is fine; the Collector is simply out of memory headroom." },
    { label: "Everything is healthy — dropped and refused spans are normal at steady state.", misconception: "Non-zero dropped_spans and refused_spans with RSS at 97% of limit is the signature of an under-provisioned gateway, not steady-state health. A healthy gateway shows these at zero." },
  ]}

## Snippet 4 — the manual span

```typescript
const span = tracer.startSpan("fraud.check");
try {
  const score = await fraud.evaluate(order);
  span.setAttribute("fraud.score", score);
  if (score > threshold) throw new FraudError(order.id);
  return score;
} catch (err) {
  throw err;
}
```

<Quiz
  id="03-otel-code-4"
  lessonSlug="03-otel"
  lang="en"
  question="This manual span has two defects a senior reviewer flags immediately. What are they?"
  choices={[
    { label: "The span is never ended — there is no span.end() (it should be in a finally block), so the span leaks and never flushes; and the catch re-throws without span.recordException(err) and setStatus(ERROR), so the error is invisible on the trace. Add a finally with span.end() and record the exception before re-throwing.", correct: true },
    { label: "setAttribute is called inside the try, which is incorrect placement.", misconception: "Setting attributes inside the try is fine and normal. The real defects are the missing span.end() (the span never flushes) and the unrecorded exception (the error never appears on the span)." },
    { label: "fraud.check is too generic a span name and will break sampling.", misconception: "The span name is acceptable and does not affect sampling correctness. The defects are lifecycle: the span is never ended and the error is never recorded on it." },
    { label: "Using await inside a span breaks trace context propagation.", misconception: "await is fine inside a span; OTel context propagates across awaits via the runtime's context manager. The actual bugs are the missing end() and the unrecorded exception." },
  ]}
/>

<Recap lang="en">
Every OTel artefact reads the same way: in a Collector pipeline, processor order is correctness — memory_limiter first or you OOM; tail-sampling num_traces must be sized for peak_rate × decision_wait × safety, not baseline; the Collector's own self-metrics distinguish a memory-bound gateway (dropped/refused high, send_failed zero) from a backend outage (send_failed high); and a manual span must always end() in a finally and record exceptions, or it leaks and hides the very errors it was meant to capture. Read the config, predict the failure mode, fix the structural cause.
</Recap>
