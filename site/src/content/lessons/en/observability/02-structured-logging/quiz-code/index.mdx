## Snippet 1 — the interpolated message

```js
// Express handler logging a user-submitted comment
logger.info(`comment received: ${req.body.comment}`);
```

Fix: pass the value as a typed field — logger.info({ comment: req.body.comment }, 'comment received') — so the serializer escapes it.", correct: true },
    { label: "The template literal throws because comment may be undefined.", misconception: "An undefined value stringifies to 'undefined'; it does not throw. The real defect is that raw user input becomes part of the log record structure, enabling a forged second line." },
    { label: "Nothing — pino escapes the string automatically even inside a template literal.", misconception: "The escaping happens when a value is passed as a field to the serializer. Here the string is already concatenated into the message before pino sees it, so the newline is preserved verbatim." },
    { label: "Only a performance issue — long comments bloat the log.", misconception: "Size is not the concern. The concern is integrity: the attacker can forge synthetic log lines that downstream tooling trusts." },
  ]}

## Snippet 2 — the redaction config

```js
const logger = pino({
  // intent: keep auth tokens and emails out of logs
  redact: ['req.headers.authorization', 'user.email'],
});

// elsewhere, on a validation error:
logger.error({ err, body: req.body }, 'signup validation failed');
```

<Quiz
  id="02-structured-logging-code-2"
  lessonSlug="02-structured-logging"
  lang="en"
  question="An auditor finds raw passwords and emails in the indexed logs despite this redact config. Why did redaction miss them, and what is the durable fix?"
  choices={[
    { label: "The deny-list only covers req.headers.authorization and user.email, but the error log dumps the whole req.body — so body.password and any body.email slip through under different paths. Add the body paths and, critically, add a collector-tier regex scrubber as defence-in-depth for paths the app misses.", correct: true },
    { label: "pino redact does not work on nested paths at all.", misconception: "pino redact does support dot-notation nested paths; that is exactly how user.email is matched. The miss is that body.* was never listed, and a whole-body dump leaks everything under it." },
    { label: "redact is too slow, so pino silently disabled it under load.", misconception: "pino does not silently disable redaction; overhead is roughly 2 ms per 1000 messages for a few fields. The leak is a coverage gap, not a performance fallback." },
    { label: "The fix is to redact at the backend (Datadog) instead.", misconception: "Backend masking is the last line, not the first — by then the data has left the host and may already be in cold storage. Defend at the source deny-list and the collector scrubber." },
  ]}
/>

## Snippet 3 — the async log line

```js
app.post('/checkout', async (req, res) => {
  res.json({ ok: true });
  setTimeout(() => {
    logger.warn({ orderId }, 'post-checkout reconciliation lag');
  }, 0);
});
```

<Quiz
  id="02-structured-logging-code-3"
  lessonSlug="02-structured-logging"
  lang="en"
  question="The WARN line lands with trace_id = '00000000000000000000000000000000'. Why, and what is the fix?"
  choices={[
    { label: "The setTimeout callback fires outside the request's AsyncLocalStorage scope, so the logger finds no active span and emits an all-zeros trace_id. Fix: bind the active context into the callback (context.bind / context.with) before scheduling it, or do the work inside the request scope.", correct: true },
    { label: "The trace_id is correct; all-zeros is just how pino renders a valid root trace.", misconception: "All-zeros is the sentinel for 'no active span at emit time', not a valid trace. A real root trace has a random non-zero ID." },
    { label: "The collector stripped the trace_id during sampling.", misconception: "Sampling drops whole records, not single fields. The field is all-zeros because it was never populated — the context was lost at the async boundary." },
    { label: "The fix is to pass trace_id manually to every log call.", misconception: "Manual passing is unreliable at scale — forgotten in refactors and third-party calls. The structural fix is to propagate the execution context across the async boundary so auto-injection keeps working." },
  ]}
/>

## Snippet 4 — the collector sampling rule

```yaml
# OTel Collector / pipeline sampling intent: cut log volume 90%
processors:
  probabilistic_sampler/logs:
    sampling_percentage: 10   # keep 10% of ALL log records
```

<Quiz
  id="02-structured-logging-code-4"
  lessonSlug="02-structured-logging"
  lang="en"
  question="This config cuts the bill, but the next incident is impossible to investigate. What is wrong, and what does a correct policy look like?"
  choices={[
    { label: "It samples uniformly across all severities, so 90% of WARN and ERROR lines are discarded and failure forensics are gone. Correct policy: success-path sampling — keep ~10% of INFO but 100% of WARN and ERROR — using a severity-aware rule so only the high-volume success path is thinned.", correct: true },
    { label: "10% is too aggressive; 50% would have kept enough errors.", misconception: "Any uniform percentage still drops the same fraction of ERROR lines. The ratio is not the bug — applying sampling to ERROR at all is." },
    { label: "Sampling must run in the application, not the collector.", misconception: "The collector is the right place for sampling (central policy, tail-sampling capability). The defect here is that the rule is severity-blind, not where it runs." },
    { label: "probabilistic_sampler cannot be made severity-aware, so this is the best possible.", misconception: "You route by severity first — keep WARN/ERROR at 100%, send only INFO through the 10% sampler — using a filter/routing processor ahead of the probabilistic sampler." },
  ]}
/>

<Recap lang="en">
Every structured-logging incident is read in the emit site, the config, and the raw line: interpolating user input into a message string is log injection — pass it as a typed field; a deny-list that misses body.* leaks PII, so list the paths and add a collector scrubber as defence-in-depth; an all-zeros trace_id means the execution context was dropped at an async boundary — bind it, do not pass trace_id by hand; and a severity-blind sampler throws away the failures you need — keep 100% of WARN/ERROR and thin only the success path. Read the snippet, find the structural defect, fix it at the source.
</Recap>
