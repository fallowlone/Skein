<Quiz
  id="02-structured-logging-choice-1"
  lessonSlug="02-structured-logging"
  lang="en"
  question="Two services on one team emit JSON logs, but one calls the field http.response.status_code and the other calls it status. Both are valid JSON. Why does this still break on-call?"
  choices={[
    { label: "JSON syntax is not the contract — the field names are. A cross-service dashboard or alert that queries http.response.status_code silently misses the service that uses status, so the join returns partial results and someone has to know the mapping under pressure.", correct: true },
    { label: "One service is not actually structured — only the OTel-named one counts as structured logging.", misconception: "Both are structured: stable serialized records with addressable fields. The defect is schema drift, not a missing structure. Both are queryable; they are just not queryable by the same name." },
    { label: "The fix is to make the dashboard regex-match both field names.", misconception: "Regex-bridging drift defeats the point of structured logs and rots as new variants appear. The fix is a shared schema (OTel Semantic Conventions) enforced before code ships, ideally via a per-org wrapper logger." },
    { label: "Nothing breaks — the backend normalises field names on ingest.", misconception: "Backends index the field names they receive; they do not invent canonical mappings. status and http.response.status_code are two different indexed fields." },
  ]}
/>

<Quiz
  id="02-structured-logging-choice-2"
  lessonSlug="02-structured-logging"
  lang="en"
  question="A retry helper logs ERROR on every one of its 5 attempts, including the 3 that ultimately succeed. The on-call channel is now noise and a real ERROR was missed last week. What is the correct fix and why?"
  choices={[
    { label: "Successful or recoverable retries are WARN; only a final failure that leaves work undone is ERROR. ERROR routes to a page, and paging on recoverable events causes alert fatigue — the most dangerous failure because real errors then get buried.", correct: true },
    { label: "Drop the retry logs to DEBUG so they stop paging.", misconception: "Retry outcomes are operationally relevant for capacity and reliability and must stay visible in production; DEBUG is off in prod by default, so this hides them entirely instead of routing them correctly." },
    { label: "Keep ERROR but raise the alert threshold so 5 ERRORs in a row do not page.", misconception: "Thresholds paper over a classification bug and will swallow genuine error bursts too. The level is the contract about what action is implied — fix the level, not the alert plumbing." },
    { label: "Sample the ERROR lines 1-in-10 to cut the noise.", misconception: "Sampling ERROR silently discards failure forensics; you must keep 100% of WARN and ERROR. The problem is misclassification, not volume." },
  ]}
/>

<Quiz
  id="02-structured-logging-choice-3"
  lessonSlug="02-structured-logging"
  lang="en"
  question="A single service at 1000 req/s with 1 KB JSON logs is costing ~$260/month in ingest. What is the first lever to cut it ~90% without losing the ability to investigate failures?"
  choices={[
    { label: "Success-path sampling: keep 1-in-10 INFO lines while keeping 100% of WARN and ERROR, applied at the collector tier. It drops INFO volume by 90% and never touches failure forensics.", correct: true },
    { label: "Sample all lines 1-in-10 uniformly — simpler to reason about.", misconception: "Uniform sampling loses 90% of ERROR lines and makes incident investigation impossible. Sampling must always preserve 100% of WARN and ERROR." },
    { label: "Shorten hot-tier retention to one day.", misconception: "Retention tiering controls how long you keep data, not how much you ingest per day. Ingest cost is volume times rate; sampling cuts the rate, retention only changes the storage horizon." },
    { label: "Bake the sampling logic into each service so it ships with the code.", misconception: "Per-service sampling fragments the policy across the fleet with no central visibility and makes tail sampling impractical. Sampling belongs at the collector tier for centralised control." },
  ]}
/>

  question="A handler interpolates user-submitted comment text directly into a log message string. A user submits a comment containing a newline followed by a forged ERROR JSON object. What class of failure is this, and what is the structural fix?"
  choices={[
    { label: "Log injection (CWE-117): the newline splits one line into two, and downstream parsers and SIEM rules treat the forged second line as a real record.     { label: "An encoding bug from non-ASCII input; normalise to UTF-8 before logging.", misconception: "The defect is structural — a newline acting as a record separator — not a character-encoding issue. UTF-8 normalisation does nothing to stop a forged log line." },

    { label: "Strip newlines from the message string before writing it.", misconception: "Blocklisting characters is fragile and misses JSON structural injection.   ]}

<Quiz
  id="02-structured-logging-choice-5"
  lessonSlug="02-structured-logging"
  lang="en"
  question="A Node service reports that ~5% of log lines carry trace_id = '00000000000000000000000000000000'. How do you read this?"
  choices={[
    { label: "Some code paths emit logs outside the active request context — setTimeout/setImmediate callbacks, unbound Promises, or worker threads that dropped AsyncLocalStorage. The all-zeros value is what gets emitted when there is no active span at the call site.", correct: true },
    { label: "The OTel SDK is globally misconfigured.", misconception: "A global misconfiguration would zero out close to 100% of lines, not 5%. A small, specific fraction points to particular async paths dropping the execution context." },
    { label: "The collector's sampling dropped the trace_id from those lines.", misconception: "Sampling drops whole records, not individual fields within a record. The trace_id is missing because it was never populated, not removed downstream." },
    { label: "The backend corrupts trace IDs on ingest under load.", misconception: "Backends do not rewrite trace IDs. All-zeros is the emitted value when the logger finds no active context — a code-side async-propagation gap, not an ingest bug." },
  ]}
/>

    { label: "Audit logs should use a non-JSON encoding, so storing them as JSON is the violation.", misconception: "JSON is fine for audit logs — they share the schema and trace_id. The violation is the retention, immutability, and access properties of the shared index, not the encoding." },
    { label: "The only problem is query performance from mixing high-volume and low-volume data.", misconception: "Performance is incidental. The compliance failure is that audit events are being deleted before their mandated retention and are readable by too broad an audience." },

<Recap lang="en">
The unit's through-line is one pipeline of decisions: a stable schema (OTel field names) makes logs queryable and joinable; the level ladder routes volume to storage and severity to humans; sampling keeps the bill proportional to incidents while always retaining WARN/ERROR; PII discipline and CWE-117 injection defence are first-class security concerns solved at the source and the collector; trace_id makes a log line a node in the observability graph instead of an island; and audit logs share the JSON schema but need their own pipeline, retention, immutability, and access. Every answer resolves back to treating the log line as an API contract your on-call and your auditor both depend on.
</Recap>
