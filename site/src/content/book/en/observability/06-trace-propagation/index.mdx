The previous pieces taught what to record (RED, USE) and what target to hit (SLO + error budget). When an SLO burns, you click an exemplar and land in a trace — but only if the trace actually got stitched together across every service the request touched. That stitching is the work of a single 55-byte HTTP header called `traceparent`, plus a sibling called `tracestate`. Get them wrong and every service has its own little trace; get them right and you can follow a single request from browser to database to cache and back, with every span correctly linked to a single shared trace-id.

<Crux>One 55-byte traceparent header turns N services into one trace. No header = N orphan traces. Observability hinges on this string.</Crux>

The mental model is a relay race. The first runner (a browser or an edge proxy) generates a trace-id — a random 128-bit hex string — and a span-id and writes them into a header that gets attached to the outgoing HTTP request. Every receiving service reads the trace-id from the header, uses it as the parent for its own work, generates a new span-id for itself, and writes a new traceparent before making any outbound call of its own. Through every protocol hop (HTTP, gRPC, queues, async fetch in browsers, batch jobs reading messages from Kafka), the trace-id stays constant and span-ids form a parent-child tree. Lose the header at any hop and the trace splits into two unrelated trees — a "broken trace" that is almost worse than no trace, because the dashboard claims you're observing something while quietly hiding half the work.

    <p><strong>What this is in one sentence.</strong> Trace propagation is the practice of passing a small identifier from one service to the next on every request, so that all the work done across many services for one user action gets stitched into a single picture.</p>
    <p><strong>Why care.</strong> Without propagation, a slow checkout looks like 50 separate stories. With it — one trace, top-to-bottom, in 30 seconds.</p>
    <p><strong>The metaphor.</strong> Think of an Amazon delivery with one tracking number. The package leaves a warehouse, hops between sorting facilities, rides on three different trucks, and finally arrives at your door. Each hop scans the same tracking number, recording where it was, when, and what the next hop is. If any one stop forgets to scan, the tracking page goes silent and you have no idea where the package is — even if it eventually arrives. Trace propagation is the scanning: every service must scan-in the incoming trace-id and scan-out a new span-id, or the chain breaks.</p>
    <p><strong>Bea and Sven.</strong> <PersonaTag id="bea" lang="en" /> the on-call engineer gets a customer support ticket: "checkout took 30 seconds." She sees: 50ms in the API gateway, 80ms in the auth service, 28 seconds in <PersonaTag id="sven" lang="en" /> the inventory service waiting on a database query, 200ms in payment, 100ms back to the user. Without propagation, she would have had to manually correlate 50 log entries across 7 services and guess which ones came from this user; with one trace she knows in 30 seconds.</p>

  <Fragment slot="middle">
    <p><strong>The traceparent header bit-by-bit.</strong> The W3C Trace Context spec (a W3C Recommendation since 2020, Level 2 since 2024) defines a single fixed-width HTTP header. The value is exactly 55 bytes: <code>00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01</code>. Four dash-separated fields. Version: 2 hex digits, currently <code>00</code>, with <code>ff</code> reserved and forbidden. Trace-id: 32 lowercase hex chars = 16 bytes = a 128-bit identifier, generated as a uniformly random number; all zeros is invalid. Parent-id (often called span-id of the caller): 16 lowercase hex chars = 8 bytes = 64-bit; all zeros invalid. Trace-flags: 2 hex digits = 8 bits, with only the lowest bit (<code>01</code>) currently defined as the "sampled" flag. The width is deliberately fixed so a router or sidecar can parse the header without a regex engine. The compact form means trace context costs about 0.04 KB per HTTP request — measurable but negligible relative to typical request payloads.</p>
    <p><strong>The tracestate companion.</strong> Where traceparent is the universal identifier, tracestate carries vendor-specific extra context: which sampler decided this trace, which canary version emitted it, what extra ids the backend wants. The format is comma-separated key=value list members, up to 32 members, each member up to 256 chars on each side. The spec mandates that vendors propagate at least 512 characters of cumulative tracestate even if they don't understand the keys — this preserves end-to-end tracing across heterogeneous vendor tooling. Mutations: a vendor may add a new key (prepend), update an existing one (move to front), but should not delete keys belonging to other vendors. The header is the escape hatch for things that can't be captured in the rigid traceparent.</p>
    <p><strong>The propagator interface.</strong> OpenTelemetry generalises the header logic with two operations on a <em>Context</em> object: <code>inject(context, carrier)</code> writes the relevant headers into an outgoing request, <code>extract(carrier) -&gt; context</code> reads them from an incoming request. Carriers are pluggable (HTTP headers, gRPC metadata, AMQP properties, plain dict) and propagators are pluggable (W3C TraceContext, W3C Baggage, B3 single, B3 multi, Jaeger). The default OTel composite propagator is TraceContext + Baggage; B3 is supported for interop with Zipkin-era systems. The library handles the bit-encoding, validation, and "if-no-incoming-then-generate" logic so application code never touches raw hex.</p>
    <p><strong>Baggage: arbitrary key-value across the journey.</strong> Baggage is a second header (<code>baggage</code>) defined by W3C, propagated identically to traceparent. It carries free-form key-value pairs: tenant-id, region, feature-flag selection, A/B test cohort. Baggage is read by downstream services and can be attached as span attributes or used by code (e.g., to enforce per-tenant quotas). The catch: baggage is unbounded by spec, sized only by the carrier protocol. HTTP header limits (typically 8-64 KB per header field, server-configurable) are the practical cap. Two real risks: bloated baggage adds latency (more header bytes per request) and PII leakage (user emails, personal data placed in baggage flows to every downstream service and any third-party integration that reads headers, often in less-audited contexts than the source database). Discipline: baggage holds operational tags, never identity data.</p>
    <p><strong>Trace-id generation: must be uniform random.</strong> The spec is firm: trace-id must be generated as a cryptographically-strong random 128-bit value. It must not encode timestamps, IPs, or user-ids because (a) downstream tools assume uniform distribution for sampling decisions, (b) embedded info leaks operational data. OpenTelemetry SDKs use the platform's secure random source (crypto.getRandomValues in browsers, /dev/urandom on Linux, java.security.SecureRandom on JVM). Speed: generating one 128-bit id is sub-microsecond; this is never a measurable cost. Collisions: at 128-bit randomness, the chance of collision in one trillion traces is on the order of 10⁻¹⁵, effectively zero. Trace-id uniqueness is the foundation: the tracing backend keys all spans by trace-id, joins them at query time, and if two unrelated requests share an id the backend will silently merge them into one nonsense trace.</p>
    <p><strong>Validation and the "missing header" fallback.</strong> When a service receives a request with no traceparent, or with one that fails validation (wrong version, all-zero trace-id, malformed hex), the receiver must generate a brand-new trace-id and start a fresh trace. The spec explicitly defines this fallback so a single misbehaving caller doesn't cascade into broken traces. Validation failures should also be logged as a span attribute (<code>invalid_traceparent_received=true</code>) so the trace appears in the backend with a marker, letting operators find broken upstream callers. Production teams treat a non-zero rate of <code>invalid_traceparent</code> spans as a propagation regression and chase the bad upstream.</p>
    <p><strong>Async boundaries: the killer.</strong> HTTP propagation is the easy case. The hard cases are queues, timers, callbacks. Pushing a message to Kafka, RabbitMQ, SQS, or Cloud Pub/Sub requires writing the traceparent into the message headers (Kafka headers, AMQP properties, SQS message-attribute) and reading it back at the consumer. The OTel SDKs handle this automatically via auto-instrumentation hooks, but only for supported clients in the recommended modes. Background timers in Node.js (<code>setTimeout</code>, <code>setImmediate</code>), worker threads, fire-and-forget promises, browser Web Workers — each breaks the in-process context unless the developer wraps the callback with the OTel <code>context.with()</code> helper. The most common production bug: a developer writes <code>setTimeout(() =&gt; doWork(), 100)</code>, the work runs, but it doesn't inherit the request's trace-id; the trace ends at the setTimeout boundary and a fresh trace starts for the work. The fix is mechanical (use <code>context.bind</code> or <code>context.with</code>) but easy to forget.</p>
    <p><strong>Head vs tail sampling.</strong> Tracing every request is expensive at high traffic. Sampling decisions can be made at the head (when the trace starts — encoded in the trace-flags <code>01</code> bit) or at the tail (after all spans complete and the collector can see the whole trace). Head-based: cheap, predictable, applied in the SDK at trace start. Common: probabilistic (1-5% of traces). Drawback: a slow or error-y request that happens to be in the unsampled 99% is invisible. Tail-based: the OTel Collector buffers all spans for a trace-id for 30s-5min, then decides whether to keep the trace based on policies (error present? duration &gt; threshold? specific attribute? probabilistic top-up). Tail sampling catches the interesting tail of slow / error traces that head sampling drops. Drawback: the collector must hold every trace's spans in memory until decision time, requiring load-balanced exporters to keep one trace's spans on one collector instance. Memory cost is the main constraint — a collector with 50,000 in-flight traces and 100 spans per trace at 1 KB per span is 5 GB.</p>
    <p><strong>Cross-protocol propagation table.</strong> HTTP: traceparent/tracestate/baggage as HTTP headers. gRPC: same names but in gRPC metadata. Kafka: traceparent and tracestate written as record headers (binary or string). RabbitMQ / AMQP: headers in the message properties. SQS / SNS: message-attribute named "traceparent". Cloud Pub/Sub: message attribute. GraphQL: inside the HTTP transport, identical to HTTP. WebSocket: inside the HTTP upgrade handshake; per-message context propagation is custom (because WS itself has no header semantics). gRPC-Web: HTTP headers. Service mesh: the sidecar (Envoy, Linkerd) handles propagation transparently for HTTP and gRPC, but you still need to instrument the application for queue / async boundaries.</p>
    <p><strong>Observability backends and trace storage.</strong> Once spans are emitted, they land in a tracing backend — Jaeger, Tempo, Honeycomb, Datadog APM, AWS X-Ray, Google Cloud Trace, Lightstep — that indexes by trace-id and supports queries by service, latency, tag, error. Storage shape: spans are append-only, keyed by trace-id, retained for 7-30 days typically. Indexes on service name, resource name, status, custom attributes. Query latency: sub-second for known trace-id lookups; seconds-to-minutes for free-text / aggregation queries. Cost: a sampled-1% deployment at 10k req/s with 10 spans/trace at 1 KB/span = 100k spans/s × 1% sampled = 1k retained spans/s = 86M spans/day × 1 KB = 86 GB/day raw, before compression. Compressed to ~10 GB/day, retained 14 days = 140 GB. At hosted pricing of ~$1/GB/month, ~$140/month per such service — trivial; at petabyte scale or with 100% sampling, the bill becomes operational. Backend choice is a trade between query power, retention cost, and operational maintenance.</p>
    <p><strong>Trace IDs as the join key.</strong> Beyond visualising one trace, trace IDs are the universal join across logs, metrics, and traces. A log line that contains the trace-id can be joined to the trace at query time, letting an operator pivot from "I see this log entry, what was the full request flow?" to a full trace view in one click. Metrics emit exemplars (trace-ids associated with histogram bucket observations); a slow p99 latency reading carries a trace-id you can click into. Profiles likewise: continuous profilers attach trace-id to CPU samples. The full stack of observability (logs + metrics + traces + profiles) joins on trace-id; lose propagation and the joins break. This is why "do tracing right" matters even if you barely look at traces directly — every other observability tool secretly depends on the trace-id ecosystem.</p>

  <Fragment slot="senior">
    <p><strong>The two-bit flag and the future.</strong> traceparent's trace-flags field is 8 bits but only the lowest bit (sampled, <code>01</code>) is specified in Level 1 (2020). Level 2 (W3C Recommendation 2024) adds the second bit (random-trace-id, <code>02</code>) which asserts that the trace-id is uniformly random — useful because some samplers use consistent hashing on the trace-id. The other six bits are reserved. The version field at the head exists precisely to allow future format evolution: a Version 01 traceparent could be longer, carry richer flags, or change layout entirely; receivers ignore unknown versions per the spec. The deliberate slowness of evolution is a feature — every router, sidecar, and SDK in the world parses byte-for-byte, and a breaking change costs years. Practitioners read the spec carefully because, unlike many protocols, traceparent has zero forward-compat tolerance for malformed input.</p>
    <p><strong>B3 vs W3C: the migration story.</strong> Before W3C, Zipkin/Brave (originally from Twitter) used B3, with two variants: B3 single-header (<code>X-B3-TraceId</code>, <code>X-B3-SpanId</code>, <code>X-B3-Sampled</code> combined or separate) and B3 multi-header. B3's trace-id was 64-bit (16 hex), later extended to 128-bit for compat with W3C. The OTel propagator API supports both B3 variants for interop, but production deployments are converging on W3C. The migration pattern: register a composite propagator (W3C + B3) at every service, write outbound traffic with W3C only, read inbound traffic with both. After a quarter, the B3 reads drop to zero and the composite can be replaced with W3C-only. The Zipkin server itself now accepts both formats. The story is identical to most spec migrations: read-loose, write-strict, deprecate slowly.</p>
    <p><strong>Async context propagation: language-by-language.</strong> Each runtime has its own pain points. Node.js: AsyncLocalStorage (built into Node 12+) is the substrate; OTel hooks it for in-process propagation. Pitfalls: setTimeout, setImmediate, queueMicrotask, and any third-party promise wrapping can lose context; OTel auto-instrumentation patches the common ones, but custom libraries break it. Python: contextvars from PEP 567 is the substrate; works automatically for asyncio but not threading without ContextVar.copy(). Java: traditional thread-local plus a Span.makeCurrent() try-with-resources block; Project Loom virtual threads are mostly transparent but require Scope nesting discipline. Go: explicit context.Context plumbing — Go made the right architectural choice early; every function takes ctx, every span lives in ctx. Browsers: zone.js (Angular's solution), or the new TC39 AsyncContext proposal; OTel-JS supports both via plugins. The mental model: in any runtime, "current context" is a fragile thing that survives only as long as the runtime's primitives carry it; whenever you cross a primitive that doesn't (raw setTimeout, native worker, raw fetch in some configs), you must bind explicitly.</p>
    <p><strong>Sampling consistency across services.</strong> "Consistent sampling" means all spans of one trace are either all-sampled or all-dropped. The trick is to make the decision at the trace's head (where the trace-id is generated) and propagate the result in the sampled flag. Probabilistic head-samplers use a deterministic hash of the trace-id mod 100; downstream services check the bit and obey. This guarantees coherent traces but loses control: if the head sets 1%, the tail can't increase. Tail-sampling restores control at the cost of memory: all spans buffered, decision after the fact. Hybrid pattern: head-sample at 100% (cheap path), tail-sample by policy (error → 100%, latency &gt; SLO → 100%, otherwise 1% probabilistic). The hybrid is the dominant production pattern; it gives the volume of head sampling and the selectivity of tail sampling, at the cost of one piece of additional infrastructure (the tail-sampling Collector).</p>
    <p><strong>The load-balancing exporter requirement.</strong> Tail sampling needs all spans of one trace to land on one collector instance, so it can see them together when the decision window closes. With multiple collector replicas (production typically runs 5-20 replicas), random distribution would scatter trace fragments. The OpenTelemetry Collector ships a <code>loadbalancing</code> exporter that hashes by trace-id and routes to a fixed replica. The exporter has a discovery mechanism (DNS, static list, Kubernetes service) for picking the replica set. Operational gotcha: re-balancing during collector scale events can briefly orphan spans whose old replica is gone; mitigations include short decision windows, graceful drain on scale-down, and explicit replica-set membership APIs. Without the load-balancing exporter, tail sampling silently produces fragmented decisions and is worse than not sampling at all.</p>
    <p><strong>Trace context across service mesh.</strong> Envoy, Linkerd, Istio, Cilium service-mesh data planes participate in tracing two ways: passing the traceparent through (always), and emitting their own spans for the network hop (optional but recommended). When the mesh emits its own span, you see exactly where time was spent in the mesh vs the application — sidecar latency, connection pooling, TLS handshake. Configuration: the mesh proxy needs the tracing-collector address and the sampling decision (usually inherit the incoming flag, sometimes always-sample for mesh spans for full network visibility at low cost). The mesh's sampling decision can override the application's, so production deployments make both agree (typically the mesh samples at the same rate as head sampling). The tracing infrastructure thus has three sources of spans for one HTTP request: client app, mesh sidecar, server app — three spans, one trace-id, one consistent picture.</p>
    <p><strong>Security: the trace-id as a tracking identifier.</strong> Trace-ids are unique per request, 128 bits of entropy, propagated in HTTP headers and visible to anyone who can inspect traffic between client and edge. This makes them powerful debugging tools and equally powerful potential trackers. The risk: if a third party (a CDN, a marketing pixel, a CSP-allowed analytics service) can read the traceparent header from the user's outbound requests, it can correlate user activity across sites that share the same tracing infrastructure. Mitigations: the W3C spec recommends that user-facing services do not propagate traceparent into responses (the response is to the user, not part of an upstream call), and that browser-side OTel SDKs limit propagation to same-origin and explicitly-allowed CORS origins. Production teams maintain an allowlist of downstream hostnames receiving traceparent and audit it quarterly. The same applies to baggage — anything in baggage is observable by every downstream, including third parties.</p>
    <p><strong>Observability for propagation itself.</strong> Just as the previous pieces argued for observing the observer, propagation needs its own metrics. The essential set: count of spans with no parent (orphans — should be only top-level entry-points, never internal services), count of invalid_traceparent_received (logged as span attribute), count of unique trace-ids per second (sanity-check trace generation rate), count of broken-trace markers (spans whose parent-id is not present in any other span for the same trace-id within a reasonable window). A healthy production estate sees orphan-span rates &lt;1% (only legit entry-points), invalid-traceparent &lt;0.01%, and broken-parent &lt;0.5%. Spikes in any of these are propagation regressions and warrant an alert. The pattern parallels the RED + USE pieces: you observe propagation health the same way you observe service health.</p>
    <p><strong>Real production failures.</strong> Uber 2019: a partial OTel rollout caused 30% of traces to break at the boundary between instrumented and uninstrumented services; postmortem mandated a "no service ships without W3C propagation" gate. GitHub 2022: a custom HTTP client wrapper bypassed OTel's hooks and silently dropped traceparent across half their internal services for a quarter before someone noticed orphan-span rate had risen from 1% to 50%; the fix was a single line to wrap the client in the OTel-aware version. Slack 2023: tail-sampling Collector OOMs took down their tracing pipeline during a major incident; postmortem forced them to add num_traces caps and a separate tier for high-priority always-keep traces. Datadog 2024 customer report: a large Java workload had a thread-pool that didn't carry context across submitted tasks, so 80% of background-task traces were orphans; fix was to switch to a CurrentTraceContext-aware executor. The pattern: propagation bugs are silent — the dashboards keep showing traces, just not the right ones — and need their own monitoring layer.</p>
    <p><strong>Span links: when the parent-child tree breaks down.</strong> Some workflows don't fit the parent-child model. A batch processor pulls 1000 messages from Kafka and processes them in one batch; the natural model is one batch-span with 1000 incoming trace contexts linked. OTel solves this with span-links: a span may declare additional span-contexts it is causally related to but does not descend from. Span-links are also used for fan-in (multiple inputs joined into one output), distributed locks (the lock-acquiring trace links to all later traces that used the lock), and asynchronous workflows where the parent finishes before the child starts. The W3C spec doesn't dictate links — they're a span-attribute pattern — but every major tracing backend supports them. The senior pattern: any trace longer than 30 seconds or wider than 100 spans probably has a span-link opportunity, where a workflow rebases its parent rather than dragging the original request span along forever.</p>
    <p><strong>Long-running traces and the 30-minute problem.</strong> Tail samplers' decision windows are typically 30s to 5min. A batch job that runs for 30 minutes has spans flush long after the decision window closes; from the sampler's view, the trace is dead by the time more spans arrive, and the late spans are orphaned. Production teams handle long traces two ways: (a) break long workflows into sub-traces linked via span-links, with each sub-trace fitting in the decision window; (b) use tracing backends that support late-arriving spans (Tempo, Honeycomb, Datadog all do) and skip tail sampling for long traces. The first is the cleaner architecture; the second is the practical retrofit for legacy workloads. Decision-window tuning is the lever to revisit when batch workloads break tail sampling.</p>
    <p><strong>The bigger picture: propagation as the foundation.</strong> Trace propagation is the boring plumbing that all the exciting observability features sit on top of. RED dashboards, SLO burn-rate alerts, exemplars-to-traces drilldown, distributed debugging, profiling correlation — every one of these depends on the trace-id stitching every service together. Skip propagation discipline and the rest of the observability stack is wallpaper over disconnected fragments. Get it right and you get end-to-end visibility for free in every new service, every new protocol, every new async boundary, because the W3C spec is small enough to memorise (55 bytes, four fields) and every OTel SDK does the heavy lifting. Senior engineers obsess about propagation in the way junior engineers obsess about visualisation — because they know the visualisation is downstream of the propagation, and the propagation is downstream of nothing else.</p>

traceparent is encapsulation at the protocol layer: a fixed-format string that any service can read without understanding what it means, exactly the way IP headers, TCP options, and HTTP request lines work. The same shape repeats every time a system needs to carry routing-decision metadata across boundaries; the discipline of fixed-width, parseable-without-context formats is what makes interop survive vendor turnover.
