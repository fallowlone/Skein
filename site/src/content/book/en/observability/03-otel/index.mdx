Pieces 01 and 02 set the vocabulary (the three signals) and the discipline of structured logging. This piece is about the substrate that makes all of it portable and composable: <em>OpenTelemetry</em>. OTel is not a single thing — it is four things layered: an <em>API</em> that your application code calls, an <em>SDK</em> that turns API calls into telemetry records, a <em>Collector</em> that processes and routes those records, and a <em>wire format (OTLP)</em> that carries them between every component. The layering is the point: each piece is replaceable, each speaks a stable contract, and together they let you instrument once and swap backends without touching application code. After this piece you should be able to draw the architecture from memory, configure a working Collector in 50 lines of YAML, and articulate exactly which decisions lock you to a vendor and which keep you neutral.

<Crux>OTel = API + SDK + Collector + OTLP. Instrument once, route anywhere — but only if your edge speaks OTLP.</Crux>

The strategic value of OTel is portability. Before OTel, every vendor shipped a proprietary agent — Datadog's `dd-trace`, New Relic's agent, AppDynamics's Java agent — and changing vendor meant rewriting instrumentation across every service. OTel is the CNCF's response: define an open API (so application code never imports a vendor library), an open SDK (so the runtime cost is identical across backends), an open wire format (so anyone can route to anyone), and a Collector (so policy and processing live outside the application). In 2026 every major observability vendor accepts OTLP — Datadog, New Relic, Honeycomb, Splunk, Grafana Cloud, Elastic, Dynatrace — which means OTel is no longer a bet, it is the default. The remaining questions are pragmatic: which deployment pattern, which sampling strategy, which auto-instrumentation level, and how to avoid the subtle vendor-lock-in escape hatches that creep back in through proprietary processors or non-OTLP edges.

  <Fragment slot="middle">
    <p><strong>The four pieces, in detail.</strong> The OTel architecture is layered so each layer is replaceable. <em>API</em>: language-specific public interfaces (Java's <code>io.opentelemetry.api</code>, Python's <code>opentelemetry.trace</code>, Go's <code>go.opentelemetry.io/otel</code>). The API is what application code and instrumentation libraries call. It is intentionally lightweight — it does <em>nothing</em> by default; a no-op SDK is the API's default implementation. <em>SDK</em>: the runtime piece that turns API calls into telemetry records. It owns sampling decisions (which traces to keep), aggregation (which metric updates to roll up), batching (when to flush to the exporter), and serialization (to OTLP wire format). The SDK is installed by the application owner, not the library author — this separation is why a library can instrument with OTel without forcing a dependency on any particular SDK on its users. <em>Collector</em>: a standalone process (binary or container) that receives OTLP, runs configurable processors, and exports to one or more backends. It is the policy layer. <em>OTLP</em>: the wire format — protobuf-encoded messages over gRPC or HTTP, defined in the OTel specification and stable across versions. Any pair of OTel-aware components communicate over OTLP.</p>
    <p><strong>Signals: traces, metrics, logs (and the path to profiles).</strong> OTel covers three signal types in stable form, each with its own API surface, SDK pipeline, and OTLP message shape, but sharing the same Resource concept (per-emitter attributes — service.name, host.name) and the same Trace context (trace_id, span_id) so cross-signal correlation works. <em>Traces</em> are GA since 2021; the workhorse, most mature, every backend speaks it. <em>Metrics</em> are GA since 2023; the API supports counter, gauge, histogram, and exponential histogram (the new default for high-resolution latency). <em>Logs</em> are GA for the API in late 2023 and SDKs in late 2024; less mature than traces and metrics but converging fast — bridging libraries (the "OTel log bridge" for slf4j, structlog, pino) let existing code emit OTel logs without rewrites. <em>Profiles</em> are in development (status: experimental in late 2024 / 2025) as a fourth signal; expect GA in 2026.</p>
    <p><strong>Semantic Conventions: the shared vocabulary.</strong> Independent of the four-piece architecture, OTel publishes <em>Semantic Conventions</em> — a normative set of attribute names for common operations. <code>service.name</code>, <code>service.version</code>, <code>deployment.environment</code> are the universal resource attributes. <code>http.request.method</code>, <code>http.route</code>, <code>http.response.status_code</code>, <code>url.full</code> are HTTP. <code>db.system</code>, <code>db.operation</code>, <code>db.namespace</code> are databases. <code>messaging.system</code>, <code>messaging.destination.name</code>, <code>messaging.operation</code> are queues. These are the join keys that make metrics, logs, and traces correlate. Adopting Semantic Conventions is the highest-leverage discipline in OTel; the SDK and Collector do not enforce them, but every backend's auto-derived dashboards and every cross-team query depend on them being populated consistently. Mature platform teams ship a per-language wrapper around the OTel SDK that pre-configures the Semantic Convention attribute extraction so it cannot be forgotten.</p>
    <p><strong>OTLP: the wire format that ties everything.</strong> OTLP is a protobuf-defined wire protocol with two transports: OTLP/gRPC (binary protobuf over HTTP/2) and OTLP/HTTP (protobuf or JSON over HTTP/1.1). OTLP/gRPC is preferred — it is smaller, faster, and supports streaming. OTLP/HTTP exists for environments that block gRPC (some firewalls) or for browser-side telemetry. The OTLP messages are <code>ExportTraceServiceRequest</code> (a batch of resource-spans), <code>ExportMetricsServiceRequest</code> (resource-metrics), and <code>ExportLogsServiceRequest</code> (resource-logs). Every OTel-compatible backend exposes an OTLP endpoint; the wire format has been stable for years and the spec evolves backward-compatibly. Strategically: if your edge (the application or its sidecar) emits OTLP, you are vendor-neutral; if your edge emits a proprietary format, you are not — independent of whether the gateway later converts.</p>
    <p><strong>Auto-instrumentation: the 70-80% you get for free.</strong> Most production traffic comes from a small set of frameworks (HTTP servers, HTTP clients, database drivers, message queue clients) that OTel's contrib libraries instrument out of the box. For Java, the OTel Java Agent (a -javaagent JAR) rewrites bytecode at JVM startup and instruments ~200 libraries automatically — no code changes required. For Python, <code>opentelemetry-instrument</code> wraps the process and monkey-patches common libraries. For Node.js, <code>@opentelemetry/sdk-node</code> plus a set of instrumentations registered before any other <code>require</code> hooks framework methods. For Go, auto-instrumentation is less mature (Go has no monkey-patching) — eBPF-based auto-instrumentation (the Go agent uses uprobes) is the emerging approach. The 70-80% is the easy part: HTTP routes, DB queries, cache calls, queue interactions. The remaining 20-30% — your business-specific spans, custom attributes, and cross-cutting concerns — is manual instrumentation, and that is where the actual value lives because it is where the business questions are answered.</p>
    <p><strong>Manual instrumentation: the value bridge.</strong> Auto-instrumentation tells you "this HTTP request took 800ms and made 5 DB queries." Manual instrumentation tells you "the slow part was the fraud-check loop, which fanned out to 12 calls on the rules engine, of which 3 timed out." The pattern: open a span around a business operation, attach attributes that describe the operation (customer_segment, feature_flag_state, batch_size), emit a span event for noteworthy moments (cache miss, retry, fallback). The catch: manual instrumentation is the same code in every service, so platform teams publish a thin helper library that wraps the OTel API with org-specific conventions (typed business attributes, redaction, span-event helpers). The other catch: do not over-instrument. Every span has overhead in collector processing and storage; aim for one span per service boundary plus one per significant subsystem call, not one span per function.</p>
    <p><strong>Collector: receivers, processors, exporters.</strong> The Collector is a YAML-configured pipeline. <em>Receivers</em> accept incoming telemetry — <code>otlp</code> (gRPC and HTTP), <code>filelog</code> (tail log files), <code>prometheus</code> (scrape /metrics endpoints), <code>kafka</code>, plus vendor-specific receivers. <em>Processors</em> transform records in-flight — <code>batch</code> (group records for efficient export), <code>memory_limiter</code> (drop when over RAM), <code>resource</code> (add service.name and other attributes), <code>attributes</code> (redact, rename, add fields), <code>tail_sampling</code> (decide which traces to keep based on full trace context), <code>transform</code> (general-purpose transformations via OTTL — OpenTelemetry Transformation Language). <em>Exporters</em> ship records to backends — <code>otlp</code> (to another OTel-aware backend), <code>datadog</code>, <code>prometheusremotewrite</code>, <code>loki</code>, vendor-specific. The Collector's power is composition: chain receivers through processors to multiple exporters in a single pipeline, or run multiple pipelines for different signal types. A 50-line YAML configures a production-grade collector.</p>
    <p><strong>Deployment patterns: agent, gateway, agent-to-gateway.</strong> Three patterns dominate. <em>Agent</em>: a Collector runs as a sidecar (one per pod) or DaemonSet (one per node), receives telemetry from the local application, does minimal processing (resource enrichment, batching), exports directly to the backend. Cheapest in network hops, hardest to scale tail sampling (each agent sees only one node's traffic). <em>Gateway</em>: applications export directly to a central pool of Collector replicas that does heavy processing (tail sampling, advanced redaction, multi-backend routing). Easier to scale processing, but every span crosses the network from the app to the gateway. <em>Agent-to-gateway</em> (the production-canonical pattern): a DaemonSet agent on every node does minimal local processing and forwards via OTLP to a centralised gateway pool that handles tail sampling, redaction, and routing. The gateway is stateful (it must buffer spans for tail sampling) and is typically deployed as a Deployment with horizontal scaling plus a load-balancing exporter on the agents that routes by trace_id to keep all spans of a trace on the same gateway instance.</p>
    <p><strong>Tail sampling at scale: the sticky-routing constraint.</strong> Tail sampling requires that every span of a trace arrive at the same Collector instance — otherwise the sampler cannot evaluate the full trace context. Two approaches. (1) <em>Single gateway instance</em> (well-resourced): all agents forward to one gateway pod with enough RAM to buffer the active trace working set (~1-2 GB per 50k in-flight traces with 100 spans each). Simple, but a SPOF. (2) <em>Load-balancing exporter on agents</em>: the agent's exporter hashes by trace_id and routes to a deterministic gateway pod. Stays sticky as long as the gateway pool composition is stable. Pod restarts and scale-up/down events shuffle the hash ring and lose in-flight traces; production setups use sticky-by-trace-id load balancing (the OTel Collector's `loadbalancing` exporter) with conservative scaling policies.</p>
    <p><strong>Sampling decisions: head, tail, parent-based.</strong> The SDK's Sampler decides which traces to record at the API call. <em>AlwaysOn</em> records every trace (cheap, large volume). <em>AlwaysOff</em> records none (useful for canary). <em>TraceIdRatioBased(p)</em> records a random p-fraction based on a hash of the trace_id (deterministic across services if all use the same algorithm). <em>ParentBased</em> defers to the parent span's decision via the W3C traceparent `sampled` flag — when an upstream service decides to sample, all downstream services follow; when upstream does not, downstream typically does not unless the local sampler overrides. Production pattern: <em>ParentBased(root=TraceIdRatioBased(0.2))</em> at the SDK (20% baseline, downstream inherits), tail sampling at the Collector to enforce "100% errors, 100% slow tail." This combines cheap predictable cost (head) with curated fidelity (tail) — the textbook senior choice.</p>

  <Fragment slot="senior">
    <p><strong>The vendor-neutrality trap: distro Collectors and proprietary processors.</strong> Many vendors ship "OTel-compatible" Collector distributions (Datadog Agent, Splunk OTel Collector, New Relic distro) that include their proprietary processors and exporters. Using one is fine — the distribution still receives OTLP and emits OTLP downstream — but with two caveats. (1) <em>Proprietary processors</em>: if you rely on a processor that exists only in vendor-X's distro (e.g., a vendor-specific routing-by-cost feature, a vendor-specific RUM correlator), your Collector config is no longer portable. Moving to vendor-Y means rewriting that piece. (2) <em>Edge OTLP</em>: the contract that defines vendor-neutrality is "does my edge emit OTLP?" If application code calls the vendor SDK (e.g., <code>dd-trace</code>) directly and the data is in vendor format at the application boundary, you are not vendor-neutral even if a Collector is in the middle — because the migration cost lives in the application code. The Honeycomb position paper "OTel Is Key to Avoiding Vendor Lock-In" makes this point precisely: vendor distros are fine for collection-tier conveniences, but if the application instrumentation is vendor-specific, you have an instrumentation-cost migration to face later.</p>
    <p><strong>OTel and the wide-event question.</strong> The piece-01 framing of observability 1.0 (three pillars) vs 2.0 (wide events) intersects OTel directly. OTel's data model in spec form is still three-pillar: traces, metrics, logs are separate APIs, separate SDK pipelines, separate OTLP messages. But the Honeycomb blog post "OpenTelemetry Is Not Three Pillars" explicitly reframes OTel signals as "ways to ship and store a single underlying telemetry model" — and indeed, a wide-event store can ingest OTel logs (with traces and metrics emitted alongside) and treat them as one stream. Future OTel work (the "Otel Profiles" experimental signal, the "wide-event correlation" discussions in the spec working group) is converging on a more unified data model. For senior teams in 2026 the implication: adopting OTel now is forward-compatible with both 1.0 backends and 2.0 wide-event backends — you do not have to commit to a pillar count upfront. Switching backends later is a Collector config change.</p>
    <p><strong>eBPF auto-instrumentation: the no-code path.</strong> A growing class of OTel-compatible instrumentation runs entirely in the kernel via eBPF — Grafana Beyla, Pixie (Plus Labs / New Relic), Datadog's USM. These tools attach kernel probes that observe syscalls, HTTP traffic on sockets, and gRPC RPCs without any application code or library changes. The output: OTel-shaped spans with reasonable Semantic Conventions attribution (service.name from the cgroup, http.route inferred from URL parsing). The tradeoff: eBPF instrumentation sees what the kernel sees, not what the application means — business attributes (customer_segment, feature_flag) are invisible, and slow-tail attribution to specific application logic is harder. Pattern in practice: eBPF for the breadth (free coverage of every service, including ones you cannot modify like vendor binaries), application-level SDK instrumentation for the depth (business spans + attributes). Both emit OTLP to the same Collector, both speak Semantic Conventions, both show up on the same dashboards.</p>
    <p><strong>Operator and Kubernetes-native deployment.</strong> The OTel Operator (a Kubernetes Operator under the CNCF umbrella) manages the Collector deployment declaratively. <code>OpenTelemetryCollector</code> CRDs define agent and gateway specs; <code>Instrumentation</code> CRDs configure auto-instrumentation injection via annotations on pods (<code>instrumentation.opentelemetry.io/inject-java: "true"</code>). The Operator installs the language-specific auto-instrumentation libraries at pod startup via an initContainer, configures the OTLP endpoint to point at the agent, and sets resource attributes from pod metadata. Strategic value: instrumentation becomes a platform-team responsibility, not a per-service responsibility. A new service deployed with the right annotations gets full auto-instrumentation without touching its Dockerfile or code. Mature platforms make this the default; opting out requires explicit annotation.</p>
    <p><strong>Browser and edge: OTel for RUM and serverless.</strong> The OTel JavaScript SDK supports the browser environment with <code>@opentelemetry/sdk-trace-web</code> — instrumenting <code>fetch</code>, <code>XMLHttpRequest</code>, document load, user interactions. Browsers emit OTLP/HTTP (not gRPC; gRPC is browser-incompatible) to a Collector endpoint configured with CORS. The resulting "browser-spans" join the server-side trace via the W3C traceparent header propagated on outgoing requests — true end-to-end traces from user click to database query. For serverless (AWS Lambda, Cloudflare Workers, Vercel Edge Functions), the cold-start cost of OTel SDK initialization is significant (50-200ms for full Lambda instrumentation), so the standard approach uses the Lambda layer or vendor-provided runtime extension to amortise startup across invocations. AWS publishes an OTel Lambda Layer; the layer initialises the SDK in the runtime extension and exposes OTLP for the function. Cloudflare Workers and Vercel Edge are still maturing OTel support, with limitations on async-context propagation in the V8 isolate model.</p>
    <p><strong>Version skew and stability strategy.</strong> OTel is many independently versioned components: the spec (v1.x), each language SDK (varies), each Collector binary (v0.x with rapid releases plus stable LTS), each Semantic Convention domain (HTTP 1.x, DB 1.x, etc.). Compatibility: SDKs are forward-compatible with newer Collectors and backward-compatible with older ones across multiple minor versions; OTLP is stable across versions. Strategic posture: pin SDK and Collector versions in deployment manifests; upgrade quarterly; run canaries before fleet-wide rollout; track Semantic Convention version per service so dashboards know what to expect. The OTel Collector has a notion of "stable" and "beta" components; production setups stick to stable receivers, processors, exporters and only adopt beta with a fallback plan. The Collector's release cadence is ~monthly; the spec is more stable.</p>
    <p><strong>Cost and reliability of the Collector tier itself.</strong> The Collector is a critical-path piece of the observability stack — if it fails, you lose visibility precisely when you need it most. Production reliability patterns: (a) <em>HA gateway</em> — minimum 3 replicas, behind a service (Kubernetes Service or cloud LB), survives one-pod failure with no data loss thanks to client retries. (b) <em>Persistent queue</em> — the Collector's file_storage extension provides disk-backed buffer that survives restarts; tune the queue size to absorb 5-15 minutes of backend slowdown. (c) <em>Health checks</em> — liveness and readiness probes against the Collector's health_check extension; do not let a slow collector be considered ready. (d) <em>Self-monitoring</em> — scrape the Collector's /metrics endpoint and alert on standard symptoms: dropped spans, refused spans, exporter failures, queue saturation. (e) <em>Resource sizing</em>: a commodity gateway pod (4 CPU, 8 GB RAM) handles ~100-200k spans/sec with tail sampling enabled; size for peak + headroom. The Collector's cost is a small fraction of the backend bill but its reliability is critical.</p>
    <p><strong>The Semantic Conventions governance question.</strong> Semantic Conventions are how every team's telemetry composes. Failures of governance produce expensive incidents: team-A names a field `route`, team-B names it `http_route`, team-C names it `http.route` — and now cross-team dashboards do not work, alerts misfire, and migrations to new backends multiply costs. Production pattern: platform-team publishes a per-language wrapper around the OTel SDK that pre-configures Semantic Conventions for the org's common attribute set. New services import the wrapper; CI lint rejects raw SDK usage in new code. The wrapper handles HTTP route extraction (matched template, not raw URL), DB system tagging (db.system=postgresql, not "psql"), redaction deny-lists, and trace-context mixins for logs. Override hooks let teams add business attributes without touching the wrapper. The wrapper is the highest-leverage platform investment in OTel adoption — it pays back on every cross-team incident, every backend migration, every new compliance audit.</p>
    <p><strong>Real production failure modes.</strong> (a) <em>Collector OOM under tail sampling</em>: gateway buffer grows past memory limit because decision_wait is set too long or trace volume spiked. Mitigation: memory_limiter processor before tail_sampling; alerts on otelcol_processor_dropped_spans. (b) <em>Tail-sample re-routing on scale events</em>: gateway pool scales up, loadbalancing exporter's hash ring re-shuffles, in-flight traces lose half their spans. Mitigation: pre-warm new pods, scale conservatively, use sticky hashing with longer convergence windows. (c) <em>OTLP version mismatch</em>: a Collector upgraded ahead of SDKs encounters an unknown field, drops the record. Mitigation: SDK and Collector compatibility matrix; staged upgrades. (d) <em>Auto-instrumentation footprint regression</em>: a new minor version of the OTel Java Agent adds an instrumentation that slows a critical library by 5%. Mitigation: canary the agent upgrade, monitor latency p99 on the affected service, opt-out specific instrumentations if needed. (e) <em>Cardinality leak via auto-instrumentation</em>: auto-instrumented HTTP client adds the full URL as an attribute, exploding cardinality downstream. Mitigation: configure the instrumentation to use http.route (templated) instead of url.full, or strip query strings via an attributes processor at the Collector.</p>
    <p><strong>Strategic posture: adopt OTel everywhere, treat vendor as configuration.</strong> For senior engineers in 2026, the OTel decision is no longer a debate. Every major vendor accepts OTLP. The instrumentation surface is portable. The cost of NOT adopting OTel is real every quarter: a vendor migration becomes an instrumentation rewrite, a wide-event experiment requires per-service code changes, a multi-region routing change demands a deploy cycle. The cost of adopting OTel is real but bounded and one-time: 1-2 weeks of per-language wrapper development, a per-service onboarding effort (often handled by the platform team via auto-instrumentation), and ongoing version management. The right strategic posture: adopt OTel by default for every new service, retrofit older services on the next significant refactor, push the platform team to own the wrapper and the Collector, and treat the choice of vendor as a configuration question — never an instrumentation question.</p>

<KeyTakeaway>OTel = API + SDK + Collector + OTLP. The split lets you instrument once and route anywhere — provided your edge emits OTLP. Vendor distros are fine in the middle; vendor SDKs in your code are not.</KeyTakeaway>

OTel's overhead is a latency line item like any other. The SDK adds 1-5μs per span; auto-instrumentation adds 2-5% p99 typically; the Collector adds 1-5ms in the agent-to-gateway path. These are measurable and bounded — and they buy the ability to swap backends without redeploying application code.
