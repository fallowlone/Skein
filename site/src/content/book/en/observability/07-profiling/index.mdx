The prior pieces stitched the request across services (traces) and named the symptom (RED) against a target (SLO). When a span says "1.2 seconds in inventory" but the inventory service is supposed to be fast, the next question is where exactly inside that span the time went. Profiling answers it: a flame graph of one span, one process, or an entire fleet, that points at the function eating the CPU or the allocation eating the heap.

<Crux>Profiling = sampled stacks. Wide frame = hot function. eBPF + continuous profiling = always-on flame graph at 2-5% overhead.</Crux>

The mental model is statistical sampling. A profiler interrupts the program 100 times a second, captures the current stack (the chain of functions calling each other from `main` down to whatever is running), and stores it. After a minute it has 6,000 stacks. The function that appears most often across those stacks is the one consuming the most CPU. Flame graphs visualise this: stacks sorted alphabetically along the x-axis with width proportional to sample count, depth on the y-axis. The widest frame at any level is the busiest path. Memory profilers do the same trick on allocations; lock profilers on contention; off-CPU profilers on time spent waiting. The unifying mechanism is sampling, and the unifying readout is a flame graph.

    <p><strong>What this is in one sentence.</strong> Profiling captures snapshots of what your program is doing — which function is on the CPU right now — many times per second, then shows you which functions ate the most time.</p>
    <p><strong>Why care.</strong> Logs say a span took 1.2s; profiling tells you 800ms of it was inside one function nobody suspected. Without it you guess; with it you point.</p>
    <p><strong>The metaphor.</strong> Imagine a stadium with 100,000 people doing different things. A polling helicopter flies overhead 100 times per second and takes a photo of who is doing what. After a minute you have 6,000 photos. Count which activity appears most often across the photos — that's where the crowd's "CPU time" goes. The flame graph is the bar chart of those counts, with parents and children stacked vertically. Wide bars = popular activities. The helicopter is the profiler; the photos are stack samples; the chart is the flame graph.</p>

  <Fragment slot="middle">
    <p><strong>Sampling vs instrumenting.</strong> Two ways to profile. Instrumentation: the runtime wraps every function entry / exit with timing code, producing exact call counts and exact durations. Cost: high — every function in every call costs CPU. Sampling: an external clock interrupts the program N times per second, captures the current stack, stores it. Cost: bounded — exactly N stacks per second, regardless of how many function calls happen between them. Instrumentation is great for small benchmarks; sampling is the only viable approach in production. Modern profilers (Go pprof, Linux perf, Java async-profiler, py-spy, eBPF profilers) are all sampling-based. The unifying property: at sample rate R Hz, a function that uses X% of CPU appears in X% of samples, regardless of how many times it was called — the statistic is "fraction of CPU time" not "function call count."</p>
    <p><strong>Sample rate and overhead.</strong> Linux perf samples by default at 99 Hz to avoid lockstep with periodic timers; Go pprof at 100 Hz; eBPF profilers typically at 19 or 49 Hz to minimise impact. At 100 Hz the profiler captures one stack every 10 ms; the cost is the stack walk itself (~5-20 microseconds depending on stack depth and platform), giving an overhead of ~0.5%-2% on a busy CPU. Production tools like Pyroscope, Parca, Datadog Continuous Profiler claim 2-5% steady-state — slightly higher than raw perf because they also include the cost of compressing, batching, and shipping the profiles to a backend. The tradeoff: lower rate = less overhead but worse statistical resolution on short hot paths; higher rate = better resolution but more noise. The 99-100 Hz default is empirically the sweet spot.</p>
    <p><strong>Memory and allocation profiles.</strong> Heap profilers sample allocations, not CPU. Go's heap profile samples one allocation per ~512 KB (Poisson distributed) and records the stack. The result: a flame graph where width is allocated bytes, not CPU time. This finds memory hotspots: one function allocating 100 MB/s shows up huge. Memory leak detection: take a profile, wait an hour, take another, diff them — functions whose allocation grew are leaking. Allocation profiles capture short-lived allocations that GC reclaims; heap profiles snapshot live memory. JVM equivalents: async-profiler with -e alloc, JFR allocation events. Python: tracemalloc, memray. Each has slightly different semantics but the flame-graph readout is the same.</p>
    <p><strong>Block, mutex, and off-CPU profiles.</strong> CPU profiling only sees functions that are running. Functions waiting on locks, I/O, or channels are invisible — the program is off-CPU. Three orthogonal profile types fill the gap. Block profile (Go's <code>runtime.SetBlockProfileRate</code>): time spent waiting on synchronisation primitives. Mutex profile (<code>runtime.SetMutexProfileFraction</code>): contention on locks. Off-CPU profile (Brendan Gregg's concept, eBPF implementations): time spent in any waiting state — disk I/O, network I/O, scheduling. A request that takes 500 ms but uses 20 ms of CPU is 96% off-CPU; CPU profiling won't reveal where. The off-CPU flame graph will: maybe 400 ms waiting on Postgres, 80 ms on Redis. Off-CPU is the dual of CPU profiling; both are required for full-spectrum debugging.</p>
    <p><strong>How a flame graph is built from samples.</strong> Each sample is a list of function names from leaf (currently executing) to root (program entry). Many samples are aggregated by exact stack equivalence; identical stacks collapse into one "thicker" column. The flame-graph rendering algorithm: sort all unique stacks alphabetically by root function (so the same parent groups its children together), then for each level, count occurrences and emit a rectangle whose width is proportional to the count. The result reads top-to-bottom: pick a leaf frame (top), look at its width, walk down to see who calls it. The x-axis order is alphabetical — not time, not call order. This is the most common misreading: people see horizontal flow and think "time" — it's frequency.</p>
    <p><strong>Continuous profiling.</strong> Traditional profiling is on-demand: SSH in, run perf, gather, leave. Continuous profiling runs always: an agent samples 100 times per second on every host, every container, and ships compressed profiles every 10-15 seconds to a backend. The backend (Pyroscope, Parca, Polar Signals, Datadog) stores them by service + time range, supports flame-graph queries, diffs between time windows, and joins with trace-id (so a slow trace links directly to the matching profile). Storage: 10 GB / week per medium service, $1-10/month. Overhead: 2-5% CPU. The win: when an SLO burns, the profile of the burning minutes is already saved — no need to reproduce the issue. Pyroscope 2.0 (released April 2026) cut storage 3x by deduplicating symbols and eliminating write-path replication, making continuous profiling cheap enough for every team.</p>
    <p><strong>eBPF and language-agnostic profiling.</strong> Traditional language profilers (pprof, JFR, async-profiler) need language-specific support: the runtime must expose stack walking. For C++/Rust/Go this is fine; for Python/Ruby/JS it requires hooks the runtime team must provide. eBPF profilers (Parca, Pyroscope eBPF mode) read stacks from the kernel side: the kernel's perf_event_open + bpf-attached probe captures user-space stacks at sample time. The advantage: works for any language, any binary, with no application change. The catch: symbol resolution — the kernel sees addresses, and the profiler needs to map them back to function names using debug info (DWARF, BTF, JIT-emitted symbol files for V8 / JVM). Most production eBPF profilers handle this; the cost is occasional missing symbols when DWARF is stripped or JIT is too volatile.</p>
    <p><strong>Joining profiles to traces.</strong> Each profile sample can carry the trace-id of the request being processed at the moment of sampling (via thread-local context). When a slow trace shows in the trace view, the matching profile samples — only those carrying that trace-id — can be filtered out and rendered as a flame graph for that specific request. This is the bridge between "where did time go in the request" (trace) and "what code ate the time" (profile). OpenTelemetry's profile signal (stabilising in 2025-2026) standardises this linkage. The pattern: when investigating a slow trace, click the span, jump to the trace-filtered flame graph, see the hot function, fix the code. End-to-end debug in 60 seconds.</p>
    <p><strong>Cross-language profiler matrix.</strong> Go: built-in pprof (runtime/pprof, net/http/pprof). Java: JFR (Java Flight Recorder, on by default in JDK 11+), async-profiler (industry standard for production). Python: py-spy (sampling, no app changes needed), cProfile (instrumentation, dev-only). Node: built-in --prof, clinic.js, 0x for flame graphs. Rust: pprof-rs, perf + addr2line. C/C++: perf, gprof (instrumentation), Intel VTune (commercial). Ruby: stackprof, rbspy. PHP: tideways, Excimer. The pattern: every modern language has a sampling profiler that emits stacks compatible with flame-graph rendering. Continuous-profiling backends (Pyroscope, Parca) ingest any of these.</p>
    <p><strong>Profile storage and retention.</strong> A single 30-second profile is ~50-500 KB compressed (raw pprof: 100 KB - 2 MB; gzip compression typically 4-8x). A service emitting one profile every 15 seconds produces 240 profiles/hour, ~50-200 MB/day, ~1.5-6 GB/month. For a fleet of 200 services that scales to 300 GB - 1.2 TB/month — manageable on object storage at $0.02/GB ≈ $25/mo. The cost driver is symbol storage: function names and source paths dominate the byte budget. Pyroscope 2.0's symbol deduplication (April 2026) trims this 3x by sharing the symbol table across profiles for the same binary. Retention strategy: 7 days full-fidelity for active debugging, 30 days downsampled (one profile per 5 minutes), 90 days for long-term trend analysis. Production retention is a knob; budget-conscious teams cap at 14 days fine + 60 days coarse.</p>
    <p><strong>Profile-as-data: queries beyond flame graphs.</strong> Profiles are time-series of stack samples; backends increasingly let engineers query them like a database. Examples: "show the top 10 functions by self-CPU across all services for the past hour" (capacity planning), "diff this service's profile between deploy A and deploy B" (regression detection, already covered), "find all profiles where function X appears in the top 5" (impact assessment for a known-slow function fixed in a library), "group flame graphs by Kubernetes node to spot hot nodes". Pyroscope's query language (PhlareQL-like), Datadog's continuous profiler, and Parca all support these queries. The shift in mindset: profiles are not just visualisations to look at, they are data to aggregate and alert on, the same way metrics and logs are.</p>
    <p><strong>Profiling and SLO burn.</strong> The previous SLO piece showed multi-window burn-rate alerts. The natural drilldown for any SLO burn: "what code is consuming the budget?" Continuous profiling answers it. The integrated workflow: SLO burn alert → click → time-range pre-filtered to burn window → CPU + off-CPU flame graphs side by side → identify which function changed → blame the deploy / change. Production-grade observability platforms (Datadog, Grafana with Pyroscope, Honeycomb) ship this drilldown out of the box; rolling it ourselves requires linking the SLO alert payload to the profile-backend URL with the right time range. The on-call's mental model becomes: pager rings → SLO dashboard names the burn → trace lists candidate slow spans → profile names the function → blame the git commit. Under 90 seconds from pager to git blame, for any incident where the bug ran on CPU.</p>

    <p><strong>The flame graph history.</strong> Brendan Gregg introduced flame graphs in 2011 at Joyent, generalising the trick of visualising sampled stacks. The original implementation was a Perl script generating SVG; the visualisation went viral because it solved a real problem nobody had solved well: making thousands of stack samples human-readable in one view. The ACM Queue paper (Gregg 2016) formalised the technique. Variants since: differential flame graphs (red/green diff between two profiles), inverted flame graphs (icicle graphs — leaf at bottom), flame charts (time-ordered, used in browser devtools, technically different from flame graphs despite the name), and aggregate flame graphs across many hosts. The original spec — alphabetical x-axis, depth y-axis, width = sample count — remains the canonical form because it scales: 10k samples, 1M samples, doesn't matter, the visual stays readable. Every major profiling backend renders flame graphs; the technique outlasted multiple tool generations.</p>
    <p><strong>Linux perf and the kernel mechanism.</strong> Linux's perf subsystem is the foundation under most profilers. The kernel exposes perf_event_open(2) which lets userspace request sampling on CPU cycles (or hardware events, cache misses, etc.). When the configured number of events fires, the kernel captures the current PID + user-space stack pointer and writes them to a ring buffer. Userspace reads the buffer and reconstructs stacks. Kernel-side cost: ~1-5 microseconds per sample including the stack walk. Modern Linux (5.x+) supports BPF programs attached to perf events, letting userspace customise what is captured: filter by PID, attach metadata, do statistical processing in-kernel. This is the engine under Pyroscope eBPF, Parca, BCC's profile.bt, and any "magic" continuous profiler — they all sit on perf_event_open + BPF. The security implication: perf requires capabilities (CAP_PERFMON in newer kernels, or root historically); production deployments use kernel-side cgroup permissions to restrict what each container can see.</p>
    <p><strong>eBPF and stack-walking nuances.</strong> The kernel can capture user-space stacks easily for compiled binaries (Go, Rust, C++ — frame pointers or DWARF unwind info on stack). For JIT runtimes (V8, JVM, .NET CLR, PyPy), the stack contains JIT-compiled code addresses that don't correspond to stable symbols. Profilers handle this with "perf maps": JITs emit /tmp/perf-PID.map files mapping address ranges to function names, which the profiler ingests. JVM async-profiler bypasses by hooking into the JVM's AsyncGetCallTrace API to capture Java stacks directly. V8 supports --perf-prof / --perf-basic-prof flags. The challenges: maps can lag, hot functions can be recompiled and re-mapped, stack unwinding can fail through certain JIT frames. Production profilers handle 90-95% of stacks accurately; the rest show as "[unknown]" frames. Worth knowing because mysterious "[unknown]" gaps in a flame graph usually mean a JIT-frame unwinding issue, not a bug in the application.</p>
    <p><strong>Off-CPU profiling in depth.</strong> Brendan Gregg's 2013 work on off-CPU analysis identified the gap: CPU profiles miss everything a process waits for. eBPF made off-CPU profiling cheap by hooking into the kernel scheduler's switch events. When the scheduler removes a thread from CPU (it blocks on I/O, sleeps, waits on a lock), the kernel captures the thread's stack — that's the "off-CPU stack" representing where the wait started. When the thread comes back, time elapsed is attributed. The off-CPU flame graph shows wait time the same way CPU flame graph shows running time. Production usage: off-CPU is essential for I/O-bound services (databases, network gateways) where CPU profile shows ~5% time and the real work happens off-CPU. Cost is comparable to CPU profile (~2-5%) when sampling, but unsampled (every switch) it can be expensive on highly-switching workloads; production deployments cap to ~99 Hz.</p>
    <p><strong>Differential profiling and regression detection.</strong> A single flame graph tells you what code is hot now. Two flame graphs over different time windows tell you what changed. Differential flame graphs (Brendan Gregg's red/blue version) color frames by their relative change between two profiles: red = grew, blue = shrank, white = unchanged. This is the deploy-regression detection workflow: capture a profile before deploy and after deploy, diff them, see exactly which functions got slower. Production-grade continuous-profile backends (Pyroscope, Datadog) bake this in: select "compare versions" and pick two commits or two time windows. The CI integration: a pre-merge perf job runs the standard load test under continuous profiling on both the PR branch and main, diffs the profiles, fails the PR if a new function appears with significant CPU share. This catches regressions before they hit production.</p>
    <p><strong>Profile-guided optimisation (PGO).</strong> Profilers don't just diagnose; they feed back into compilation. PGO: compile a binary, run it under representative load to collect a profile, recompile with the profile as input. The compiler now knows which branches are hot vs cold, which functions to inline aggressively, which to keep small, how to lay out basic blocks for cache locality. Real-world PGO improvements: Go 1.21+ PGO gives 2-7% speedup on typical workloads; Chrome saw 10%+ from PGO + LTO; PostgreSQL benchmarks 5-15%. The bottleneck is workflow: gathering representative profiles, automating the recompile, validating the result. Production-grade build pipelines (Google, Meta, larger startups) automate the loop; smaller teams use one-shot PGO once per release. Continuous profiling backends increasingly support exporting profiles in PGO-compatible formats (Go's pprof CPU profile is directly consumable by the Go compiler's PGO).</p>
    <p><strong>Security: profiles can leak code, secrets, and behaviour.</strong> A profile contains function names (often including private code, internal APIs, undocumented entry points). Some profilers also capture arguments or line numbers; some attach symbols including paths revealing the build environment. In hostile contexts, a profile from a competitor's binary can reveal proprietary algorithms — function names alone often telegraph what a service does. eBPF profilers running on shared kernels can in principle observe other tenants' execution; this is why eBPF requires explicit capabilities and is namespace-scoped on modern kernels. Memory profilers can capture allocation sites that include argument values (e.g., string contents); poorly-configured allocation profilers have leaked credentials. Production discipline: profiles are treated as security-sensitive artefacts, scoped to authorised on-call, retention-limited (30-90 days), and never shipped outside the org. The Linux kernel docs on perf-security spell out the threat model: profilers need to be treated like debuggers, not like logs.</p>
    <p><strong>Production failures and their profiles.</strong> Discord 2020: a chat service was at 80% CPU with mysterious tail latency. CPU profile pointed at JSON serialisation; switching to a faster JSON library dropped CPU to 30% and tail to baseline. GitHub 2021: Ruby workers were OOMing on certain endpoints; allocation profile showed a single template-rendering function allocating 200 MB per request because of an unbounded loop concatenating strings. Stripe 2022: continuous profiling caught a regression two days after deploy — a new feature flag was reading from disk on every request instead of from in-memory cache; off-CPU profile showed the disk wait. Cloudflare 2023: a Worker runtime regression showed in eBPF profiles as time spent in V8's GC; the team rolled back a V8 update that introduced more aggressive collection. Slack 2024: PHP service was spending 30% of CPU on autoloader; profiler-guided opcache tuning cut it to 5%. Pattern: every major engineering org has a war story about profiling catching what dashboards missed.</p>
    <p><strong>OpenTelemetry profile signal.</strong> OTel is standardising profiles as a fourth signal (after logs, metrics, traces). The spec defines a profile data model (samples with stacks, labels, time ranges), a transport (OTLP profile signal added in 2024), and integration with the existing context propagation (trace-id tagging). Adoption: Datadog, Grafana, Honeycomb, Splunk are implementing OTel profile ingestion; agents (OTel Collector + profiler-side) emit OTel-formatted profiles. The promise is the same as for logs/metrics/traces: cross-vendor portability and a unified collector pipeline. The catch is timing — the spec is in beta as of 2026 and many production deployments still use vendor-specific formats (pprof, JFR, Pyroscope-native). Senior engineers track this transition because choosing a tool today commits to a format for 2-3 years.</p>
    <p><strong>Sampling biases and pitfalls.</strong> Sampling has limits. Functions whose entire runtime is shorter than the sample interval (10 ms at 100 Hz) can be missed entirely — they finish before the timer fires. This is the rare hot path with many short calls: the function runs 1 million times for 5 microseconds each (5 seconds total CPU), but each call ends before any sample. Mitigation: longer profiling windows (more chances to catch it), higher sample rates (more chances per second), or instrumentation-based profiling for that specific path. Another pitfall: NUMA / multi-CPU asymmetry — profilers usually sample uniformly across CPUs, but if work is unevenly distributed, the hottest CPU's hotspot dominates. Use per-CPU profile views to see imbalance. Final pitfall: signal-handler safety — profilers using SIGPROF can interact with signal handlers; rare crashes in old profilers came from this. Modern eBPF-based profilers avoid signal handlers entirely, using kernel-side capture.</p>
    <p><strong>The bigger picture.</strong> Profiling is the closest tool to "where is the time and bytes" because it samples reality directly. Logs say "this happened"; metrics say "this much"; traces say "this took X long"; profiles say "this function in this thread used the CPU." The fourth pillar of observability. Continuous profiling at 2-5% overhead makes it cheap enough to keep on, which means SLO burns now come with a flame graph attached — no reproduction needed. The cultural shift: 2015-era teams reached for perf or pprof only when something was on fire; 2026-era teams have profile dashboards next to RED + USE + SLO, and a senior on-call's reflex is "open the profile" the same way "open the trace" was their reflex two years ago. Like trace propagation, profiling is plumbing; like trace propagation, the value compounds when every service has it on.</p>
