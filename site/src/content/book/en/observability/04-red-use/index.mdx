The first three pieces of this pillar argued *what to record* — logs, metrics, traces — and *how to ship them* through OpenTelemetry. This piece answers the next, sharper question: *which numbers do you stare at when the pager fires?* The wrong answer is "all of them." The right answer is two short checklists, written by two engineers two years apart, that between them cover both the service the user touches and the resources that service stands on.

<Crux>RED = Rate, Errors, Duration (services). USE = Utilization, Saturation, Errors (resources). Two checklists, no debate.</Crux>

The mental model is layered. A user fires a request at your service. RED tells you what *they* experienced: how many requests came in, how many failed, and how long the survivors took. If RED looks sick, the user is sick. USE tells you what the underlying resources — CPU, memory, disk, network, locks — looked like during that window. If USE looks sick on a box, that's a candidate cause. The senior engineer's reflex on an incident is not "open every dashboard"; it is "RED says the symptom, USE says the cause, and the four golden signals from Google's SRE book stitch them together." Everything else — log volume, trace samples, profiling data — is a deeper drill once those two checklists have narrowed the search space.

    <p><strong>What this is in one sentence.</strong> RED and USE are two short checklists that tell you which numbers matter when a system breaks — RED for the service the user calls, USE for the machines the service runs on.</p>
    <p><strong>Why care.</strong> When something is on fire, you have seconds to find the right dashboard. RED and USE compress thousands of possible metrics down to six headline numbers that almost always tell you which way to look first.</p>
    <p><strong>The metaphor.</strong> Think of a hospital. RED is the patient's vital signs — pulse, blood pressure, temperature — measured from the outside. USE is the ICU monitoring of each life-support machine — oxygen flow, pump pressure, error LEDs — measured at the equipment itself. You need both. If the patient's vitals crash you act fast, but to know <em>why</em> you walk over and check the machines. Doctors who only watch one or the other miss obvious problems; the discipline is to run both checklists in order, every time.</p>
    <p><strong>Bea and Sven.</strong> <PersonaTag id="bea" lang="en" /> the on-call engineer gets paged: p99 latency on the checkout service spiked from 80ms to 1.2s. <PersonaTag id="sven" lang="en" /> the service shows Rate steady at 400 req/s, Errors under 0.1%, Duration p99 15x worse. That is the RED triage — requests still arrive and mostly succeed, but they are slow. Bea switches to USE on the boxes: CPU at 92%, run queue jumped from 0 to 14. The boxes are CPU-saturated; threads queue for cycles. Fix: scale out. Diagnosis took under a minute.</p>
    <p><strong>One scenario.</strong> An e-commerce API slows during a flash sale. RED: Rate up 5x, Errors flat, Duration p99 up 10x. USE on the DB box: Disk I/O utilization 100%, queue depth 200. The read surge overwhelmed the DB disk. Without RED you would not know users felt it; without USE you would not know which resource was the bottleneck.</p>

  <Fragment slot="middle">
    <p><strong>Origin and definitions.</strong> The USE method was named by Brendan Gregg in 2012 as an emergency checklist for performance debugging: for every resource, check utilization, saturation, and errors. Utilization is the average percentage of time the resource was busy. Saturation is the degree of queued work the resource cannot service yet — measured as queue depth, run-queue length, wait time. Errors is the count of error events on that resource. Gregg's insight: 80% of real-world performance bugs are caught by walking a 30-item table (resource × U/S/E) before reaching for clever profilers. The method assumes that, given any computer, you can name a small fixed set of resources — CPUs, memory, network, storage I/O, controllers, interconnects, and on the software side mutex locks, thread pools, file descriptors — and that each of these can be in trouble in only three ways.</p>
    <p><strong>RED is the service-side dual.</strong> Tom Wilkie introduced RED at a London Prometheus meetup in 2015 while working at Weaveworks; the method is published in detail on the Grafana blog. RED's three metrics — Rate (requests per second), Errors (failed requests per second or as a ratio), Duration (the latency distribution of successful requests) — are emitted by every service in a microservices architecture in the same shape, so a single dashboard pattern covers the whole estate. Wilkie's stated motivation: the USE method "does not really apply to services" — a service is not a resource, and what its callers feel is not utilization. RED is request-centric, USE is resource-centric, and the two together let you reason about both halves of a system from one mental model.</p>
    <p><strong>The four golden signals from Google's SRE book.</strong> Predating both RED and USE in spirit but published in book form later, Google's SRE Workbook chapter on monitoring distributed systems names four signals: Latency, Traffic, Errors, Saturation. Latency is per-request response time; Traffic is request rate (or queue depth, or active sessions — system-specific); Errors is failed-request rate; Saturation is "how full" the system is relative to a known capacity limit. Notice the overlap: Latency = Duration, Traffic = Rate, Errors = Errors. The novel piece is Saturation, which the SRE book deliberately includes at the service level — not just on resources — because services have logical capacities (queue length, in-flight count) that matter even when no individual machine is at 100%. Many production teams treat RED + Saturation as the practical evolution of the SRE-book signals.</p>
    <p><strong>Instrumenting RED in Prometheus.</strong> The conventional shape: three metrics per HTTP service, named consistently. <code>http_requests_total</code> as a counter labelled by <code>method</code>, <code>route</code>, <code>status</code>. <code>http_request_errors_total</code> derived by selecting <code>status=~"5.."</code> (or a server-classified error label). <code>http_request_duration_seconds</code> as a histogram, bucketed at 5, 10, 25, 50, 100, 250, 500, 1000, 2500, 5000, 10000 milliseconds (typical web service buckets). Rate is <code>rate(http_requests_total[5m])</code>; error rate is <code>rate(http_request_errors_total[5m]) / rate(http_requests_total[5m])</code>; duration percentiles are <code>histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))</code>. Every service emits this trio; one dashboard template renders every service.</p>
    <p><strong>Instrumenting USE on Linux.</strong> CPU utilization: <code>vmstat 1</code> or node_exporter's <code>node_cpu_seconds_total</code>; saturation: run-queue length via <code>vmstat</code>'s <code>r</code> column or the kernel's Pressure Stall Information at <code>/proc/pressure/cpu</code> (kernel ≥ 4.20). Memory utilization: <code>node_memory_MemAvailable_bytes</code>; saturation: page-in / page-out via <code>vmstat</code>'s <code>si</code> / <code>so</code> columns, or <code>/proc/pressure/memory</code>. Disk I/O utilization: <code>iostat</code>'s <code>%util</code>; saturation: average queue depth (<code>avgqu-sz</code>). Network: utilization via <code>ifconfig</code> / <code>node_network_*</code> counters; saturation via NIC ring-buffer drops and TCP retransmits. Errors: ECC errors, link errors, dropped packets, ENOSPC, EIO. Modern Linux's PSI files give you a single number per resource that says "what percentage of wall-clock time were tasks stalled on this resource" — for incident response this is gold, because it is the saturation signal in a form you can alert on directly.</p>
    <p><strong>Histograms vs averages.</strong> RED's Duration must be a histogram, never an average. The average hides everything: a service with 99% of requests at 50ms and 1% at 5000ms has the same mean latency (~100ms) as one with all requests at 100ms; the first kills users on retries, the second doesn't. Prometheus's histogram_quantile reads bucket counts and estimates the percentile by linear interpolation between adjacent buckets. The estimate is only as good as the buckets: if 99% of your traffic falls in a single bucket spanning 100ms to 500ms, your p99 estimate could be anywhere in that range. Choose buckets to bracket your SLO target densely on each side. Typical mistake: leaving the Prometheus client library default of <code>[0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10]</code> seconds for a service whose SLO is 200ms — most of your traffic is between 50ms and 250ms, you have one bucket covering it (100ms to 250ms), and your p99 is unreadable. Production-grade: 10-15 buckets, densest around the SLO.</p>
    <p><strong>The four-golden-signals stitching pattern.</strong> A senior dashboard for any service holds three panels of RED at the top (Rate, Errors, Duration with p50/p95/p99 lines), then below each it puts the matching USE panel for the resources that service depends on. For a typical HTTP service that means: CPU utilization + saturation (PSI) for its boxes, memory utilization + saturation for the same boxes, network utilization + retransmits for the NIC, downstream-database response time and error rate (USE on the DB). The reading rhythm during an incident is top-to-bottom: which RED metric moved, then which USE row matches the timeline. The four golden signals are the panel headings; RED and USE are the cells.</p>
    <p><strong>What goes in the labels.</strong> RED metrics are labelled by what is actionable: <code>route</code> (the URL pattern, not the full URL), <code>method</code> (GET/POST/...), <code>status</code> (the HTTP status class — 2xx/4xx/5xx — not necessarily the exact code), and the service identifier (which usually comes from a meta-label injected by the deployment). Forbidden: user IDs, request IDs, customer email, country code unless small and bounded, individual query strings. The reason is cardinality, covered in the failure mode below. USE metrics are labelled by resource identity: which CPU, which device, which NIC, which thread pool. These are bounded by the number of CPUs / devices, so cardinality is not a concern.</p>
    <p><strong>How RED behaves under failure modes.</strong> A service degrading gradually shows Duration p99 climbing first while p50 stays flat (the slow tail is growing); a service hitting a hard limit shows Rate flattening at the cap while inbound traffic continues (you start dropping requests at the edge or queue them externally); a service with a logic bug shows Errors jumping at constant Rate and Duration. The pattern matters for diagnosis: a Duration-only spike with stable R and E usually points to a downstream slowness (database, cache miss, GC pause); an Error spike at stable R and D points to a logic regression or input shift; a Rate plateau with rising Duration points to capacity exhaustion — the service is queueing.</p>
    <p><strong>How USE behaves under failure modes.</strong> A CPU-bound workload shows utilization climbing toward 100% and saturation (run-queue) rising above the core count — that's the right signal that scaling out will help. A memory leak shows utilization climbing slowly with si/so eventually non-zero (swap-in / swap-out, the saturation signal). A disk-bound workload shows %util near 100% on one or more disks with growing queue depth; a network-bound one shows TCP retransmits, NIC drops, or saturation at the negotiated bandwidth. PSI's "full" line for memory or I/O is the most production-friendly: if memory pressure full &gt; 0 for &gt; 10 seconds, you almost certainly have a memory crunch even if free RAM looks plentiful (the kernel was thrashing reclaim).</p>
    <p><strong>Alerting on RED and USE.</strong> The mature pattern is to alert on user-facing symptoms (RED), and to alert on internal cause signals (USE) at lower severity for capacity planning. A RED page-grade alert: p99 Duration &gt; SLO for 5 minutes, or Error rate above 1% for 2 minutes. A USE warning-grade alert: PSI cpu some &gt; 20% for 10 minutes, or memory available &lt; 10% for 5 minutes, or disk &gt; 90% for 5 minutes. The split is deliberate. RED alerts wake humans because users are affected. USE alerts notify a slower channel (Slack, dashboards) so capacity teams plan ahead, not so on-call wakes up every time CPU touches 70%. Aligning page-grade alerts with user impact prevents the alert-fatigue spiral that ruins on-call rotations; this is one of the strongest cultural levers in incident-prone teams.</p>
    <p><strong>RED + USE in microservice meshes.</strong> Service meshes (Envoy, Linkerd, Istio) emit RED metrics at the sidecar without application code changes, which both lowers the cost of getting started and provides a consistent cross-service shape. The drawback is that the sidecar sees only what the network sees; an application bug that returns wrong-but-2xx data is invisible to the mesh. Mature deployments run both — sidecar RED for breadth and consistency, application-emitted RED for per-business-logic fidelity (e.g. a payment-success counter labelled by gateway is application-only). Keep the labels aligned across both layers so dashboards join them.</p>

  <Fragment slot="senior">
    <p><strong>Cardinality as a first-class cost driver.</strong> Every unique combination of label values on a Prometheus metric creates a separate time series, indexed in the TSDB head block at roughly 3 KB of RAM each. A naive RED instrumentation that labels by <code>user_id</code> in a service with 100k active users grows from a few hundred series to a few hundred thousand within hours; if the metric is replicated across 50 service instances, the headcount can exceed 5M series and crash the TSDB on a 16 GB Prometheus server. In hosted backends (Datadog, New Relic, Splunk, Chronosphere) the bill grows linearly: at $0.05/series/month per custom metric, an unbounded user_id label can add $5,000-50,000 of monthly cost overnight for one careless label. The discipline is iron: only labels with bounded, low cardinality go on metrics; everything else lives in logs (high cardinality is the natural home of logs) and traces (which sample). Route templates (not full URLs), HTTP status classes (not exact codes), customer segment buckets (not customer IDs) are the rule. If you need the exact value for a single query, use exemplars — Prometheus's mechanism for attaching a sampled trace ID to a histogram bucket — and follow the link into the tracing backend.</p>
    <p><strong>PSI: the production-grade saturation signal.</strong> Linux's Pressure Stall Information (kernel 4.20+, released December 2018, by Johannes Weiner at Facebook) exposes at <code>/proc/pressure/&#123;cpu,memory,io&#125;</code> a six-line report per resource: "some" and "full" pressure averaged over 10s, 60s, 300s. "some" means at least one task was stalled waiting; "full" means all non-idle tasks were stalled. PSI's design fixed a long-standing observability gap — pre-PSI you had to infer pressure from load averages, vmstat r column, iowait, none of which scale across many cores or capture transient saturation. PSI's resolution is microsecond, and its overhead is sub-1%. Production usage: scrape with node_exporter's <code>node_pressure_*</code> metrics; alert when <code>node_pressure_cpu_waiting_seconds_total rate</code> exceeds 0.1 (10% of time spent stalled on CPU). Kubernetes uses PSI for OOMKill decisions and Pod priority adjustments. Apple, Facebook, Google all run PSI-driven autoscalers internally. PSI replaces the legacy load-average metric in modern production stacks for the same reason: it actually answers "is something stalled," whereas load average is a 1-min smoothed mix of runnable and uninterruptible tasks that means different things on different kernels.</p>
    <p><strong>Cross-protocol RED.</strong> For HTTP RED is obvious. For gRPC, Rate is RPCs/sec, Errors is gRPC status &gt; 0 (any non-OK), Duration is the streaming-aware response latency (first-byte for server-streaming, end-to-end for unary). For queues: Rate is messages-in/sec + messages-out/sec (consumed and produced are different signals), Errors is the dead-letter rate, Duration is the queue wait time (publish to consume). For batch jobs: Rate is jobs/min, Errors is failed jobs, Duration is wall-clock per job — and crucially, the Saturation dimension matters as well, because batch systems queue work and the queue depth is a critical signal a pure-RED setup misses (this is exactly why the four golden signals add Saturation back at the service level). For event-driven serverless: Rate is invocations/sec, Errors is the function-error rate plus the throttled-invocations rate, Duration includes cold-start tail (which behaves as the slow tail and dominates p99). The shape transfers; the meanings of "request" and "error" do not.</p>
    <p><strong>Service mesh and auto-RED.</strong> Envoy, Linkerd, Istio, and the major service-mesh data planes emit RED metrics automatically at the sidecar, without application changes. Envoy's <code>http_downstream_rq_total</code>, <code>downstream_rq_xx</code>, <code>downstream_rq_time</code> give Rate, Errors-by-status, Duration histogram per cluster + listener + virtual host, labelled consistently across the fleet. The advantage: a polyglot estate (Node, Go, Python, JVM, Rust) gets one RED dashboard pattern even though languages disagree on Prometheus client conventions. The catch: the sidecar sees what the network sees, not what the application sees — a request that succeeds at the sidecar but is mis-served by buggy app code shows as a 2xx in mesh metrics. Production teams run sidecar-RED for breadth and per-service app-level RED for depth, joined by the same route label.</p>
    <p><strong>Histogram bucket strategy.</strong> The default Prometheus client buckets — 5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s, 2.5s, 5s, 10s — are wrong for most services. For a checkout API with a 200ms SLO, buckets should densify around 200ms: e.g., 25, 50, 100, 150, 200, 300, 500, 800, 1500, 3000 ms. Rule of thumb: have at least three buckets below the SLO target and three above; ensure adjacent buckets differ by ≤2x near the SLO; cap the highest bucket at the timeout (no need for a 10s bucket if your service times out at 3s). Native histograms (Prometheus 2.40+) reduce the bucket-tuning problem by emitting per-observation exponential buckets at fixed precision, trading some storage for far better p99 accuracy without manual configuration. OpenTelemetry's exponential histograms work the same way and are increasingly the default in new instrumentations.</p>
    <p><strong>Errors-budget tie-in.</strong> RED's Errors and Duration together feed the Service Level Objective (SLO) and its error budget. An SLO of 99.9% availability over 30 days allows 43.2 minutes of "errored" time; an SLO of 200ms-p99 over 30 days allows 0.1% of requests to exceed 200ms. The error budget is what is left over: minutes remaining, requests remaining. The SLO chapter in this pillar (piece 05) shows the formulas, the burn-rate alerting pattern (multi-window, multi-burn-rate), and the cultural-engineering side. The point here: RED is the substrate the SLO sits on. Without RED instrumentation, you do not have an SLO; you have a wish.</p>
    <p><strong>Self-referential observability.</strong> Prometheus itself emits RED and USE metrics — for a Prometheus server, scrape duration is RED-Duration, scrape failures are RED-Errors, ingestion rate is RED-Rate, and storage-write pressure is USE-Saturation on the underlying disk. Monitoring the monitor matters because cardinality-induced outages are usually invisible to the affected service (the service's own metrics keep accumulating, but the Prometheus pulling them gets slower). Alert on Prometheus's own scrape Duration p99 &gt; 1s, on TSDB head series count growth rate, on rule-evaluation duration. The same logic applies to OpenTelemetry collectors (emit collector_exporter_send_failed_total, otelcol_processor_dropped_metric_points) and to the logging tier (Fluent Bit, Vector emit their own RED). In a mature stack every layer of observability is itself observed; new senior hires get a checkpoint on "and how do we know the monitoring is working." The collapse mode for an unobserved monitoring tier is the worst kind of silent failure.</p>
    <p><strong>Security: labels can leak.</strong> A naive Errors counter labelled by <code>error_message</code> or <code>stack_trace</code> publishes the exception text into the metrics scrape, which is often less access-controlled than the application database. If the message contains user input — "could not find user alice@example.com" — that PII is now in a metrics backend that an entire engineering org reads. Discipline: label by error <em>class</em> (`auth_failed`, `db_timeout`, `parse_error`), never by error <em>content</em>. The same caution applies to labels like <code>query</code>, <code>body</code>, <code>user_agent</code>: each can carry PII or secrets, each multiplies cardinality, each lands in a less-audited datastore than the source. Audit your label set as a security-review item, not just a perf-review item. Real incident: a payments service in 2021 leaked customer phone numbers via a poorly-named "failed_phone" label; the postmortem mandated a global pre-commit hook that flags any new label named with a known-PII pattern.</p>
    <p><strong>Sampling vs aggregation.</strong> RED's Duration histogram and USE's PSI are pre-aggregated — they summarise across all requests / all wall-clock time without sampling. Traces are the opposite: sampled (typically 0.1-5%) because each trace carries the full request path. The senior pattern: pre-aggregate RED + USE at the source, sample traces (head-based for cost, tail-based for completeness on slow / error tails), and put profiles (continuous profiling via Parca, Pyroscope, Datadog) behind a much heavier sampling (~1%) but with always-on coverage so a slow tail can be drilled at any time. Aggregation gives volume; sampling gives detail. The four-pillar stack — RED metrics, USE metrics, sampled traces, sampled profiles — composes if and only if they share trace IDs and label keys (route, service, status_class). OpenTelemetry's semantic conventions formalise this: <code>http.route</code>, <code>http.response.status_code</code>, <code>service.name</code> are the join keys; using them consistently across logs / metrics / traces is what makes the stack usable.</p>
    <p><strong>Real production failures.</strong> Cloudflare 2022: a global outage was preceded by Prometheus servers OOMing under cardinality from a new label on the request_duration metric. The fix landed in 90 minutes, but the post-mortem mandated a per-team cardinality budget and a CI check that rejects new label dimensions over a threshold. GitHub 2023: an SLO alert for code-search latency repeatedly fired without action because the alert was on average latency, not p99 — a bug fix that pushed p99 from 200ms to 800ms barely moved the mean. The SLO was reworked to multi-window p99 burn rate alerts (1h short window, 6h long window) per the Google SRE workbook pattern. Stripe 2024: a webhook delivery worker stalled for 11 minutes because the Postgres replica it depended on had PSI memory pressure (full) at 90% — invisible on free-RAM dashboards which showed plenty of available memory, but the kernel was thrashing reclaim. Migration to PSI-based alerting caught the next incident in 30 seconds. Discord 2023: a refactor moved a hot label from one metric to two metrics; cardinality doubled without anyone noticing, and the Prometheus rule-evaluation latency grew from 100ms to 4s over two weeks, causing alert delays that masked a customer-facing incident. Rule-evaluation duration is now first-class on their meta-monitoring dashboard.</p>
    <p><strong>Push vs pull, OpenTelemetry collector, exemplars.</strong> Prometheus's pull model assumes targets are addressable on a network the Prometheus server can reach; for short-lived workloads (Lambdas, batch jobs) push via the Pushgateway or OpenTelemetry's OTLP push pattern works better. The collector pattern (OTel Collector, Vector, Telegraf) decouples emission from storage: the application emits to a local agent, the agent batches and routes to backends. Exemplars — sampled trace IDs attached to histogram observations — are the bridge between aggregated RED and detailed traces: a spike in p99 is a histogram bucket count growing, and each bucket can carry a trace ID that you can click into in Grafana to see the slow request's full span tree. This pattern, formalised in Prometheus 2.32+ and OTel 1.0+, eliminates the "metric says something is slow but I have no example to look at" gap that defined the pre-exemplar era.</p>
    <p><strong>The bigger picture: why the two checklists endure.</strong> RED and USE were both designed as <em>cognitive prosthetics</em> for engineers under pressure. The point is not that the six metrics are exhaustive — they aren't — but that they are short, memorable, and disjoint enough to drive the first 30 seconds of incident triage in a direction that is almost never wrong. Saturation as the fourth golden signal patches the one gap in pure RED. PSI in modern kernels gives USE a sharper saturation signal than was available when Brendan Gregg wrote it. Service meshes give RED for free at the infrastructure layer. OpenTelemetry gives the join keys to compose RED + USE + traces + profiles into one navigable surface. But the cognitive shape — symptom (RED) before cause (USE), both before logs / traces / profiles — is fifteen years old in 2025 and still load-bearing in every senior engineer's incident response. New tooling will keep changing; the checklist won't.</p>
