Piece 01 named the three signals and the cost shapes that distinguish them. This piece zooms into logs — the signal that absorbs high cardinality but pays in bytes — and answers the engineering question the cost shape pushes onto us: <em>what does a usable log line actually look like, and what discipline keeps the volume from doubling every six months</em>. The answer in 2026 is structured-or-nothing: JSON events with a stable schema, mandatory join keys (trace_id, service.name, level), redaction at the source, and a per-team sampling and retention policy. Free-text logs grep-able only by humans are a debt the size of your fleet times the cost of every incident. Later pieces in this pillar use the schema this piece defines — RED's exemplars (piece 04), trace context propagation (piece 06), and profiling join keys (piece 07) all assume the log line carries a trace_id.

<Crux>Structured logs = JSON events with a stable schema, level, and trace_id. Free-text logs are tech debt priced per byte and per incident.</Crux>

The cost of a log is paid in three places: at write time (CPU + RAM for serialization), in transit (network egress + collector capacity), and at the backend (ingest GB + indexed-event count + retention bytes). Structured logs are not free — JSON serialization costs CPU, and well-instrumented services emit dozens of fields per line — but they pay back at query time. A free-text line "user 42 failed checkout because gateway returned 503" requires regex and substring search to filter; the same JSON `{level:"error", user_id:42, route:"/checkout", upstream:"payment-gateway", upstream_status:503, trace_id:"abc..."}` is a single indexed-field query with millisecond response time over weeks of data. The discipline this piece teaches: pick a schema, populate it consistently, control volume with levels and sampling, redact PII at the source, and treat the log line as an API your future on-call self will read at 03:00 with no context.

    <p><strong>One sentence.</strong> A structured log is a JSON event with a stable schema — every line is a record with the same shape (timestamp, level, service, message, plus fields), not a free-form sentence.</p>
    <p><strong>Why care.</strong> When the pager fires at 02:00, you have minutes. Filtering 10 million log lines by `level=error AND service=checkout AND status_code=503` takes one query if logs are structured; it takes regex, luck, and tears if they are free-text.</p>
    <p><strong>The metaphor.</strong> Free-text logs are a diary. Structured logs are a spreadsheet. Both record what happened, but only one lets you ask "show me every payment failure last week grouped by upstream provider" without reading every entry by hand. The diary is fine when you have ten entries; at ten million it is unusable. The spreadsheet has rules: every row has the same columns, every column has a type, every value goes in the right cell.</p>

    <p><strong>The schema: what every line carries.</strong> A production-grade structured log line in 2026 has at minimum these fields. <code>timestamp</code> in ISO-8601 UTC with sub-second precision (`2026-04-12T14:02:11.482Z`). <code>level</code> as a string enum (TRACE / DEBUG / INFO / WARN / ERROR / FATAL). <code>service.name</code> (the OTel-canonical key) identifying the emitter. <code>trace_id</code> and <code>span_id</code> when the log is emitted in a traced context — these are the join keys to the tracing backend. <code>message</code> as a short human-readable summary (the only field humans skim). Then event-specific fields as a flat key-value tree: <code>http.route</code>, <code>http.response.status_code</code>, <code>db.system</code>, <code>error.type</code>, etc. — using OTel Semantic Conventions where they apply. Then <em>resource attributes</em>, typically set once at service start: <code>host.name</code>, <code>cloud.region</code>, <code>service.version</code>, <code>deployment.environment</code>. The OTel Logs Data Model formalises this split: log records contain Timestamp, Body (human-readable), Attributes (event fields), Resource (per-emitter), TraceId/SpanId/TraceFlags (W3C). Adopting this shape — even on a non-OTel backend — buys forward compatibility and lets every dashboard and on-call run-book speak the same field names.</p>
    <p><strong>Levels: the ladder that controls volume and alert routing.</strong> The ladder TRACE / DEBUG / INFO / WARN / ERROR / FATAL exists for two purposes: to control what gets stored, and to control who gets paged. The production default in 2026 is INFO and above — DEBUG is enabled only via a dynamic flag during active investigation, never on by default; TRACE rarely exists outside of frameworks. INFO represents the success path: state changes (request_received, request_completed, kafka_message_processed, transaction_committed) that let a human reconstruct what the service did. WARN is for recoverable issues (retry succeeded after 3 attempts, fallback path taken, deprecation hit). ERROR is for unrecoverable issues that left work undone (request returned 5xx, dead-letter queue emitted, write rolled back). FATAL is for "process is about to die" (assertion failure, out-of-memory imminent). Alert routing follows the ladder: ERROR + FATAL feed pages and incident channels; WARN feeds Slack and capacity dashboards; INFO is queried during investigation, not alerted on. The discipline: every log line's level is a contract about what action it implies. A misclassified level — INFO that should have been WARN, or ERROR that should have been WARN — pollutes either the alert or the bill.</p>
    <p><strong>Sampling: the cost lever you must pull.</strong> A modest service emitting one log line per request handles 1 MB/s at 1000 req/s — about 86 GB/day — and most teams have dozens of services. At hosted log pricing ($0.10/GB ingest plus indexed-event cost), the bill compounds fast. Sampling is the lever. <em>Success-path sampling</em> keeps 1-in-N INFO lines for high-volume successful events while keeping 100% of WARN and ERROR — typical N is 10 to 100. <em>Pattern-based sampling</em> keeps every distinct log_pattern at full rate and samples the duplicates (Vector and Fluent Bit ship sampling filters that hash the message template). <em>Tail sampling for logs</em> mirrors the trace pattern: buffer logs for a request, decide based on outcome — keep all logs for failed requests, sample the successful ones. The pipeline tier (collector / agent) is where sampling typically lives so the application code stays simple; some logging libraries (pino, structlog) also support in-process sampling for the hot path. Document the sampling policy: a 1% INFO sample is fine for traffic analytics but lethal for forensics if a single user reports a missing record.</p>
    <p><strong>The shipping pipeline.</strong> Logs travel through three stages: <em>emit</em> (the application writes a JSON line to stdout or to a logger SDK), <em>collect</em> (a sidecar agent or DaemonSet reads stdout, parses JSON, batches), <em>ship</em> (OTLP-HTTP, syslog, native vendor protocol to the backend). The collector layer (Fluent Bit, Vector, OTel Collector with the filelog receiver) does three things you do not want in the application: backpressure (buffer on disk if the backend is slow), enrichment (attach resource attributes — host, region — based on pod metadata), and redaction (strip PII patterns before they leave the host). Production rule: emit JSON to stdout, let the platform handle everything after that. The anti-pattern is application code that calls the vendor SDK directly — couples the code to the vendor and makes redaction and sampling harder to retrofit. Two-tier collector deployment (DaemonSet agent on every node + central gateway pool for tail sampling and routing) is the canonical pattern at scale.</p>
    <p><strong>Library performance matters at high throughput.</strong> In Node, pino emits at ~140k msg/sec on Node 24; Winston at ~20k; bunyan is deprecated. In Go, slog (stdlib, 1.21+) and zap are the production defaults — both serialize JSON with minimal allocations, with throughput in the hundreds of thousands of lines per second per core. In Python, structlog plus orjson is the high-performance combo; the stdlib logging module is slow under contention. In JVM, log4j2 with the JsonTemplateLayout is the standard — beware historical Log4Shell-class vulnerabilities (Dec 2021) and keep dependencies current. The performance cost of "wrong" logger choice shows up under load: a service whose checkout handler spends 5% of CPU in logging because of a slow library is invisible until traffic doubles and tail latency degrades. Benchmark before commitment.</p>
    <p><strong>Redaction at the source: PII discipline.</strong> Logs are the easiest signal to leak PII into and the hardest to clean up after the fact. Patterns that have leaked in real incidents: full request bodies (including auth headers and session tokens), email addresses, phone numbers, raw SQL queries (containing user input), stack traces with object dumps. The discipline: deny-list at the source. The logger SDK (pino's <code>redact</code> option, log4j2's pattern converter, structlog's processor chain) strips known-sensitive paths (`req.headers.authorization`, `body.password`, `user.email`) before serialization; a second-pass redaction at the collector tier catches anything the application missed. Static redaction (known field paths) is cheap — pino's redact adds ~2ms per 1k messages for 5 fields. Dynamic redaction (regex over the full message body) is far more expensive — ~8-22ms per 1k messages — and should be reserved for unstructured fields. PII review is a security gate, not a performance gate: the cost of a postmortem on a token leaked to logs dwarfs the redaction overhead.</p>
    <p><strong>Trace context propagation in logs.</strong> Every log line emitted inside a traced request must carry <code>trace_id</code> and <code>span_id</code>. The mechanism: the trace context (an immutable struct held in the language's request-scoped context — Node's AsyncLocalStorage, Go's context.Context, Python's contextvars) is consulted by the logger at emit time; pino's `mixin` callback, slog's `LogValuer`, structlog's `merge_contextvars` processor all pull from the active context. The result: a log line emitted deep inside a handler still carries the request's trace_id with no per-call-site boilerplate. Without this, the log → trace pivot — "find the trace for this failing request" — does not work, and observability degrades to the pre-OTel "correlate by timestamp and hope" mode. Auto-instrumentation libraries (OTel-JS, OTel-Python) wire this up automatically when the logger is registered with the SDK.</p>
    <p><strong>Retention tiering: hot, warm, cold.</strong> Indexed log storage at $0.10-$1.00/GB-month is too expensive for multi-month retention at scale. Mature stacks tier: <em>hot</em> (last 7-15 days, fully indexed, sub-second query — Datadog Standard, Splunk indexed, Loki recent), <em>warm</em> (30-90 days, partially indexed or scan-only — Datadog Flex, Splunk Frozen-Searchable), <em>cold</em> (compliance retention, in S3 or equivalent at $0.023/GB-month, restorable but not directly queryable). The split has cost-control implications and incident-response implications: an incident under 7 days old runs against hot tier with full query power; investigations into "what happened in our system 6 months ago" need warm-tier queries that may take minutes per scan and may not have every dimension indexed. Decide per service which questions you must be able to ask at what age.</p>

  <Fragment slot="senior">
    <p><strong>OpenTelemetry Logs Data Model: the spec everyone is converging on.</strong> The OTel Logs specification (status: stable for the API in late 2023, SDKs in late 2024) defines a log record as a typed structure with Timestamp, ObservedTimestamp, SeverityNumber, SeverityText, Body, Resource, Attributes, TraceId, SpanId, TraceFlags. Two timestamps matter: <em>Timestamp</em> is when the event actually occurred (often set by the application) and <em>ObservedTimestamp</em> is when the collector saw it — under clock skew or backpressure these diverge, and senior teams alert on the divergence as a pipeline-health metric. SeverityNumber is a numeric ladder (TRACE=1-4, DEBUG=5-8, INFO=9-12, WARN=13-16, ERROR=17-20, FATAL=21-24) so backends can compare severity across libraries that use different text labels. Body is the human-readable message; Attributes is the flat key-value map of event-specific data. Resource is set once per emitter (service.name, host.name, cloud.region). The Trace context fields are inherited from the active span at emit time. OTLP/Logs is the wire format — protobuf over gRPC or HTTP. The strategic value: adopting the OTel Logs Data Model in 2026 buys vendor portability the same way OTLP/Traces and OTLP/Metrics did — you can swap backends without rewriting instrumentation.</p>
    <p><strong>Log injection: the security failure-mode every team ignores.</strong> When user-supplied input is interpolated into a log message without sanitisation, a sufficiently crafted input can forge log lines that downstream consumers parse as real. Two attack shapes. (1) <em>Newline injection</em>: input contains a literal newline (or CRLF), splitting the apparent single log line into two — the second carries attacker-chosen severity, message, and even fake trace_id. Audit-trail manipulation is the textbook scenario: an attacker triggers a forgery that masquerades as an admin action by user X to misdirect investigation. (2) <em>Structure injection</em>: in JSON output, if user input is concatenated into a string field without escaping, special characters can close the string and open new fields. Real CWE-117 incidents have led to alert pollution, log search false positives, and SIEM rule bypass. The mitigation: never interpolate user input into log strings. Always pass it as a typed field that the JSON serializer escapes (passing `{user_input: ...}` as an attribute, not concatenating it into the message). The Log4Shell-class vulnerability (CVE-2021-44228, December 2021) was a related but distinct failure: log4j2's pattern lookup feature allowed user-controlled strings in log messages to trigger remote-code execution via JNDI lookup. The lesson stack is the same: <em>log messages are an input surface; treat them as user input</em>.</p>
    <p><strong>Cardinality of structured-log fields: still a real cost.</strong> Logs absorb high cardinality (one of their selling points over metrics), but cost still tracks unique-value count for indexed fields. A field like <code>user_id</code> is bounded by your user count; <code>request_id</code> is unbounded (one new value per request). For indexed-event pricing the per-line cost is roughly constant, so total cost scales with line count not field cardinality — but for facet-based queries and field-aware index size, high-cardinality string fields raise backend storage costs. Mature stacks tier the field set: <em>indexed</em> (always queryable by facet — service, level, route, error.type, region — typically 10-30 fields), <em>searchable</em> (string-match but not faceted — full body, headers, response samples), <em>archived</em> (stored but only available on restore from cold tier). Datadog Logs explicitly exposes this with index facets vs reserved attributes. Splunk has search-time vs index-time field extraction. Honeycomb's columnar model removes the discipline (every field is queryable) at the cost of a different pricing dimension. Pick the right model per workload; the failure is treating logs as "infinite-cardinality free space" until the bill arrives.</p>
    <p><strong>Async-context propagation pitfalls.</strong> The logger reads trace context from the active execution context. Anything that breaks the execution context breaks the trace_id on the log line. In Node.js, <code>setTimeout</code>, <code>setImmediate</code>, fire-and-forget Promises, and worker threads can each drop AsyncLocalStorage unless wrapped in <code>context.bind</code>. In Python, <code>asyncio.create_task</code> propagates contextvars correctly only since Python 3.7+; threads and ProcessPoolExecutor do not. In Go, the <code>context.Context</code> must be threaded explicitly — there is no automatic propagation through goroutines (you must pass the ctx into the goroutine launch). In JVM, the OTel Java agent's auto-instrumentation handles most cases, but custom thread pools without `traceContext.wrap` will lose the context. Symptom: log lines emitted "deep" in async paths carry a missing or stale trace_id. Detection: a log volume by `trace_id IS NULL` or `trace_id = "00000000..."` query — if non-trivial, something is dropping context. Production fix: a per-language hygiene checklist + a CI test that exercises async paths and asserts the log carries the inbound trace_id.</p>
    <p><strong>Log-based metrics: when you have to.</strong> The pure-pillar view says metrics come from a TSDB and logs come from a log backend. Reality: sometimes the only signal is in logs (legacy systems, third-party services, audit events), and you want a metric out of it. Tools: Loki's recording rules (LogQL → Prometheus metric), Datadog's "Logs to Metrics" pipelines, Splunk's "stats" search converted to a saved alert. The pattern: aggregate log volume (or a filtered subset) at a fixed interval into a counter or histogram. Costs to know: log-based metrics are slower to fire than native metrics (the log must be ingested first), they reflect ingestion success not application reality (a sampled log line is missing from the count), and they share the cardinality budget — emitting a metric labelled by `user_id` derived from logs has the same cardinality-explosion failure mode as emitting it directly. Use log-based metrics for legacy and bridging; emit native metrics for anything new.</p>
    <p><strong>The Honeycomb / wide-event critique applied to logs.</strong> In an observability 2.0 stack, "logs" and "events" merge: each unit of work emits one wide event per service boundary, and a log line is just one of those events with a level and a message field. The schema becomes much broader (every request attribute lives on the event) but the structural discipline is the same — stable field names, redaction, trace context. The difference is that the wide-event store (Honeycomb, ClickHouse-based stacks) makes every field queryable with no per-field cost discrimination, whereas a 1.0 log backend tiers fields between indexed and searchable. Teams that have moved to wide events report a related cultural shift: the log line is no longer "a thing to look at when something is wrong" but "the unit of telemetry" — every request emits one or two, no separate counters or histograms emitted from the application. The implication for piece-02 discipline: the schema you adopt now is the same in either world, so the work is portable; pick OTel Semantic Conventions, populate them consistently, and the migration cost to a wide-event stack later is low.</p>
    <p><strong>Audit logs as a first-class subsystem.</strong> Operational logs answer "why is the service slow." Audit logs answer "who did what when to which resource." They share the JSON schema and trace_id but differ on three axes: <em>retention</em> (audit: 1-7 years, ops: 30-90 days), <em>immutability</em> (audit: append-only, hash-chained or signed; ops: deletable), <em>access</em> (audit: narrow role + audit-of-audits, ops: developer-readable). Compliance frameworks (SOC 2, ISO 27001, HIPAA, PCI DSS) mandate audit logging for security-relevant events: authentication, authorisation changes, data access on regulated records, configuration changes. The architectural pattern: emit audit events through the same logger SDK but with a `category: "audit"` field that routes through a dedicated pipeline to a dedicated backend with the stricter properties. Common mistake: mixing audit and operational logs in the same index — failed compliance audit, expensive remediation, sometimes a real breach window.</p>
    <p><strong>Real production failure modes.</strong> (a) <em>Logger-side OOM</em>: a service generates log lines faster than the agent ships, in-memory buffer grows, process OOM-killed. Mitigation: bounded in-memory buffer + disk spill, plus a meta-metric (`log_buffer_bytes`) alerted at 80% capacity. (b) <em>Collector backpressure cascade</em>: the log backend slows, the collector buffers, the application's logger blocks on the buffer, request latency rises. Mitigation: drop policy on the collector (drop INFO+, keep WARN/ERROR) and a meta-metric for `dropped_lines_total`. (c) <em>Time-skew between Timestamp and ObservedTimestamp</em>: hosts with clock drift produce logs that arrive in the wrong window in the backend, breaking time-windowed queries. Mitigation: NTP everywhere, plus an alert on (ObservedTimestamp - Timestamp) p99 over 60s. (d) <em>Index-tier bill explosion</em>: a single PR adds a chatty INFO line on every request, log volume doubles in a week, bill follows. Mitigation: weekly volume-per-service review + a budget alert. (e) <em>Log-injection breach</em>: as described above, user input flows unsanitised into a log message; attacker forges audit events. Mitigation: never interpolate, always pass-as-field.</p>
    <p><strong>Operational hygiene: the per-service log-quality checklist.</strong> Every service in production should have, as a hard prerequisite: (1) JSON-only log output to stdout, (2) the canonical schema (timestamp, level, service, trace_id, span_id, message, plus event fields), (3) OTel Semantic Conventions for HTTP and DB fields, (4) the per-org wrapper logger that handles redaction and trace mixin, (5) levels mapped to alert severity, (6) a documented sampling policy if log volume per request exceeds 1, (7) audit event emission for security-relevant operations, (8) a "common log queries" section in the run-book, (9) a CI test that asserts at least one INFO and one ERROR can be parsed from a smoke-test deployment, (10) a dashboard panel showing log volume / error rate / dropped lines for the service. This is the difference between "we have logs" and "logs work in incident response."</p>
    <p><strong>The future: logs eaten by events, or hardened by OTel.</strong> Two paths are in play. <em>Path A (wide events)</em>: logs and events converge into one stream of wide structured records, the log line becomes a degenerate case (an event with a level and a message), and the log backend becomes an event analytics backend. Honeycomb, Hyperdx, ClickHouse-based stacks. <em>Path B (OTel Logs standardisation)</em>: the OTel Logs Data Model becomes the universal log schema, every vendor speaks OTLP/Logs, the three pillars stay structurally separate but join keys are unified. The two paths are not mutually exclusive — many shops adopt OTel Logs and let the wide-event question become a backend-choice question rather than an instrumentation question. The strategic implication for senior engineers in 2026: the cost of instrumenting wrong is at its lowest in years, because the choice of backend is no longer locked in at write time. Adopt OTel, adopt the schema, defer the wide-event vs three-pillar decision to a backend-selection conversation.</p>
