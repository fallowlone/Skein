Server-side batching covered fixed-cost amortisation. On the client, the fixed cost is the bytes your code asks the browser to download, parse, compile, and execute before the page is usable. That cost lands hardest on mid-range mobile devices on slow networks — the median user, in many markets. Bundle budgets are the discipline of measuring those bytes per route, capping them, and enforcing the cap at CI time.

<Crux>JS bundle bytes = parse + compile + execute on user's CPU. Mid-range mobile = 4-8x slower than dev laptop. Set a budget, enforce it.</Crux>

A 1 MB JavaScript bundle is not a 1 MB cost. It's a download (slow on mobile), a parse (V8 walks every byte), a compile (the JIT generates bytecode then optimised code), and an execute (the app's startup logic runs). On a fast laptop the chain is sub-second; on a median Android device on 4G it can be 5-15 seconds before the page is interactive. Core Web Vitals — LCP, INP, CLS — quantify what the user feels; bundle budgets are the lever that moves them. Senior front-end work treats bytes as a finite resource with per-route caps, not as a side-effect of feature development.

  <Fragment slot="middle">
    <p><strong>The cost of JavaScript: download, parse, compile, execute.</strong> Each phase has its own cost. Download: bandwidth-limited; 200 KB gzip'd on 4G ~150-500 ms. Parse: V8 parses ~1-2 MB/sec on a high-end laptop, ~200-400 KB/sec on a median Android — a 500 KB un-gzip'd bundle is ~1.5-2 seconds of parse on mid-range mobile. Compile: V8's pipeline (Ignition → Sparkplug → TurboFan) compiles each function as first called; total grows roughly linearly with code size. Execute: the bundle's top-level code (framework init, store creation, route registration) runs synchronously, blocking the main thread. For a typical React + Redux app, 100-500 ms of execution before interactive. Full chain on mid-range mobile for 500 KB un-gzip'd: download 800 ms + parse 1.5 s + compile 300 ms + execute 400 ms ≈ 3 seconds before the user can click anything. Each phase is a separate lever; bundle budgets cap the total.</p>
    <p><strong>Core Web Vitals and what they measure.</strong> Google's three primary metrics for user-perceived performance. LCP (Largest Contentful Paint): time to render the largest visible element above the fold. Target: &lt; 2.5 s. Heavy JS that blocks the main thread delays render — LCP suffers. INP (Interaction to Next Paint, replaced FID in 2024): worst-case latency from user input to next visual update. Target: &lt; 200 ms. JS execution that holds the main thread for long stretches hurts INP. CLS (Cumulative Layout Shift): how much the page jumps around during load. Target: &lt; 0.1. Late-arriving fonts, images without dimensions, JS that inserts above-the-fold content — all hurt CLS. Bundle budgets help all three: less JS = less parse+execute time = better LCP and INP. CLS is mostly a layout/image issue, fixed by reserving space rather than by bundle size directly.</p>
    <p><strong>Code splitting strategies.</strong> The most effective bundle reduction. Route-level: each route gets its own JS chunk; navigating to /settings doesn't download /editor's bundle. Component-level: components that are conditionally rendered (modals, drawers, dialogs) load only when used. Vendor-splitting: third-party libraries in their own chunk that's cached separately from app code. Webpack's `splitChunks`, Vite's automatic code splitting, Next.js's automatic per-route chunks, Remix's resource routes — every modern bundler ships these primitives. Senior pattern: every route has its own bundle, vendor libraries split out, any component &gt; 30 KB lazy-loaded unless on the critical path.</p>
    <p><strong>Tree shaking and dead code elimination.</strong> When a module exports many functions and you import only one, modern bundlers should remove the unused ones — "tree shaking". Requires ES modules, pure-marker annotations (`/* #__PURE__ */`), and the bundler's static analysis. Real-world traps: a module with side effects on import (setting `window.foo = ...` at module scope) can't be tree-shaken. lodash's main bundle imports all functions; `import _ from 'lodash'` includes everything (70 KB+); `import debounce from 'lodash/debounce'` includes only debounce (2 KB). Configuration: webpack `optimization.usedExports`, Rollup's built-in tree shaking, esbuild's `--tree-shaking=true`. Senior verification: open the bundle analyzer (`source-map-explorer`, `webpack-bundle-analyzer`, `vite-bundle-visualizer`) and confirm unused exports aren't present.</p>
    <p><strong>Compression: gzip vs brotli, static vs dynamic.</strong> Text-based assets (JS, CSS, JSON, SVG) compress 60-80% with gzip, 70-90% with brotli. Static compression (pre-compressed at build, served with Content-Encoding header) costs nothing at request time. Dynamic compression (server compresses on the fly) costs CPU per request — typically 5-30 ms per response for brotli, 1-5 ms for gzip. Senior choice: static brotli for assets where build is once and serve many; dynamic gzip for HTML responses that vary per user. Modern CDNs handle this automatically and cache the compressed version. Verify with `curl -I -H "Accept-Encoding: br" your-asset-url` and check the Content-Encoding response header.</p>
    <p><strong>Critical path vs deferred.</strong> Not all bytes are equal. Critical path: JS needed to render the first meaningful view (framework init, root component, above-the-fold data). Deferred: JS for interactions that don't happen on first paint (modals, settings panels, admin tools). Senior pattern: keep critical path under 80-100 KB gzip'd; defer everything else with dynamic `import()`. React's `React.lazy`, Vue's defineAsyncComponent, Svelte's lazy loading — all use the same dynamic-import primitive. Result: First Contentful Paint happens fast; the rest of the app downloads in the background while the user reads the first view.</p>
    <p><strong>Third-party scripts: the silent budget killer.</strong> Analytics, ads, customer-support widgets, A/B testing — third-party scripts often dominate the bundle. Not in your repo but they ship to every user. Common offenders: Segment (~150 KB), Hotjar (~200 KB), full-page Optimizely (~400 KB), Intercom widget (~200 KB), Google Tag Manager with several tags (~500 KB+). Mitigation: load with `async` or `defer` (don't block page render), gate by interaction (load chat widget only when the user clicks the chat icon), self-host critical analytics, audit quarterly to remove unused vendors. PartyTown runs third-party scripts in a Web Worker so they don't block main thread. Senior teams maintain a "third-party budget" separate from the app bundle budget.</p>
    <p><strong>Images, fonts, and static assets.</strong> JS often dominates parse cost but images and fonts can dominate total bytes. Images: modern formats (AVIF 30-50% smaller than JPEG, WebP 20-30% smaller), responsive `srcset`, lazy-load below-the-fold images with `loading="lazy"`. Fonts: subset to characters actually used (FontTools `pyftsubset` cuts ~70% off most fonts); `font-display: swap` to render fallback text immediately; preload critical fonts. CSS: critical CSS inline in the head; rest of the stylesheet loaded async. Each asset class deserves its own budget; combining everything into "total page weight" hides the per-class regression.</p>
    <p><strong>Mobile testing in practice.</strong> The most common cause of "great in dev, slow in prod" is testing only on the developer's machine. Production-grade mobile testing has four layers. (1) Chrome DevTools CPU throttling — set to 4x slowdown to approximate mid-range Android. Quick check during development. (2) Real device testing — keep a physical Moto G4 / Pixel 3a / similar mid-range Android on the team for representative testing. Lighthouse mobile emulation is close, but doesn't capture real-device quirks (GPU, memory pressure, thermal throttling). (3) BrowserStack or similar device cloud for QA — automated tests on dozens of real devices. (4) RUM with device-class breakdowns — segment dashboards by device tier (high/mid/low end). Engineering teams that ship to global markets routinely have 60-80% of users on mid-range or older hardware; testing only on flagship phones systematically underestimates real-user experience.</p>
    <p><strong>The 100 KB budget rule of thumb.</strong> Industry-standard recommendation: keep initial JS under 100-170 KB gzip'd for fast first interactive on mid-range mobile. Origin: Google's Web Fundamentals guidance plus empirical data from Lighthouse / WebPageTest studies. Math: 170 KB gzip'd ≈ 500 KB un-gzip'd. Parse on mid-range Android ≈ 1.5 s. Plus compile and execute ≈ 2-2.5 s total. Add network download (~500 ms on 4G) = ~3 s to interactive. That's the upper bound that keeps LCP under 2.5 s. Beyond 170 KB, every additional 100 KB roughly adds 300-500 ms to LCP on the median device. Different routes can have different budgets — marketing page tight (50-100 KB), dashboard medium (150-250 KB), admin tools relaxed (300-500 KB) — but the homepage is always the tightest constraint because it's where conversion happens.</p>
    <p><strong>Lighthouse vs PageSpeed Insights vs RUM.</strong> Three tools measuring CWV; each has its role. Lighthouse: synthetic test in DevTools or CLI; full audit on a dev machine with throttling. Good for PR-time check. PageSpeed Insights: Google-managed Lighthouse run + field data from CrUX (Chrome User Experience Report). Field data is real aggregated metrics from Chrome users. Useful for public-facing analysis. RUM: your own sampling of real users. Most accurate, but requires setup. Senior pattern: Lighthouse in CI for catching regressions before merge, RUM in production for catching regressions not caught in CI, PageSpeed Insights quarterly for cross-reference. Each catches a different class of issue; none replaces the others fully.</p>

    <p><strong>V8's tiered compilation pipeline.</strong> V8 (the JS engine in Chrome, Node, most Chromium browsers) compiles JS through multiple tiers. Ignition is the bytecode interpreter; most code runs there initially. Sparkplug (added 2021) is a non-optimising baseline JIT that compiles bytecode to machine code with no inlining or optimisation — fast to compile, ~5x faster to run than Ignition. Maglev (added 2023) is the mid-tier optimising JIT. TurboFan is the top-tier optimising compiler with full inlining and speculative optimisation. Each function moves up the tiers as it gets hotter. Implications for bundle budgets: code that runs only at startup (framework init, route setup) stays at Ignition/Sparkplug — fast to compile, slow to run. Critical hot loops (event handlers, render functions) eventually reach TurboFan and run near-native. Total cost picture: bundle size affects parse + Ignition compile (proportional to code), but execution speed depends on whether hot functions reach optimised tiers. Senior front-end perf engineers profile with --trace-deopt / Chrome's "Performance" tab to see which functions are stuck in low tiers; sometimes the fix is shape stabilisation rather than bundle reduction.</p>
    <p><strong>HTTP/2 + HTTP/3 priorities and the resource waterfall.</strong> Modern protocols let the server prioritise responses. HTTP/2 has stream priorities; HTTP/3 (over QUIC) has explicit Extensible Priorities (RFC 9218). Browsers send hints (CSS in head is "highest", lazy-loaded images "lowest"). A server that honours priorities sends critical resources first even if requested last. CDNs (Cloudflare, Fastly) implement this. Interaction with bundles: a small critical bundle competing with a large deferred bundle for bandwidth is starved without priorities; with priorities, critical bundle ships first. Verify with Chrome's network panel "Priority" column. Senior infra: ensure CDN sends `priority` hints and HTTP/3 prioritisation; misconfigured HTTP/3 priority can erase 20-30% of bundle-split benefits because the browser still downloads the big chunk before the small one.</p>
    <p><strong>Preload, prefetch, modulepreload, and 103 Early Hints.</strong> Four directives that tell the browser to fetch resources earlier than the parser would naturally discover them. `&lt;link rel="preload"&gt;`: download immediately, high priority. Use for critical CSS, fonts, hero images. `&lt;link rel="prefetch"&gt;`: download at idle priority for next navigation. Use for likely-next-route resources. `&lt;link rel="modulepreload"&gt;`: download AND parse-compile a module ahead. Use for ESM modules that will be imported. HTTP `103 Early Hints` (RFC 8297): server can send a 103 with `Link: ...; rel=preload` before the final HTML, telling browser to start fetching critical resources while server builds the rest. Cloudflare, Fastly, Vercel implement 103 Early Hints. Combined with bundle splitting: send preload hints for the route's critical chunks in 103, then ship HTML; user gets a 100-500 ms head start typically. Most production teams don't use Early Hints yet; senior teams should.</p>
    <p><strong>Bundle observability in production.</strong> Real User Monitoring (RUM) tracks Core Web Vitals from actual user devices. Implementations: Web Vitals JS library (Google), Sentry, Datadog RUM, New Relic Browser, Cloudflare Web Analytics. Each samples LCP, INP, CLS, FCP, TTFB on real page loads and reports back.     <p><strong>Tree-shaking pitfalls and how production-grade builds verify it works.</strong> Tree-shaking sounds automatic but has many failure modes. Pitfall 1: side effects. A module with code at module scope (e.g., `if (typeof window !== 'undefined') window.foo = bar`) can't be tree-shaken — bundler keeps the whole module to preserve the side effect. Solution: mark the package as `"sideEffects": false` in package.json, or use `/* #__PURE__ */` annotations. Pitfall 2: CJS interop. CommonJS exports are runtime values; require() prevents tree-shaking. Solution: use ESM-only or convert via `package.json: { "type": "module" }`. Pitfall 3: re-exports. `export * from './module'` re-exports everything; if even one consumer uses one export, the whole module survives. Solution: explicit named re-exports. Pitfall 4: dynamic imports that aren't really dynamic. `await import('./module')` where `./module` is a literal string is tree-shakeable; but `await import(name)` where `name` is dynamic prevents shaking. Production verification: after every build, run bundle analyzer and grep for the heaviest imports; confirm they're actually used. Some teams add CI checks that fail if specific large libraries (moment, lodash full) appear in the bundle.</p>
    <p><strong>Security implications of bundle delivery.</strong> Subresource Integrity (SRI): the `&lt;script src="..." integrity="sha384-..."&gt;` attribute lets the browser verify the script hasn't been tampered with. Without SRI, a compromised CDN could ship malicious JS to all users; with SRI, the browser rejects the script if its hash doesn't match. Production-grade: SRI on all third-party scripts; build-time SRI generation for first-party. CSP (Content Security Policy): restricts where scripts can come from. `script-src 'self' https://cdn.example.com;` blocks inline scripts and arbitrary domains, preventing XSS-injected scripts from running even if they get into the DOM. Common misconfiguration: `'unsafe-inline'` allows inline scripts, defeating CSP. Senior teams set strict CSP and use nonces or hashes for intentional inline scripts. Third-party scripts deserve extra scrutiny: every embedded analytics or widget script potentially has access to the page's DOM, cookies, localStorage. Quarterly audit: list every third-party domain in CSP, justify each, review the vendor's track record.</p>
    <p><strong>The cost of frameworks.</strong> The baseline cost of being a SPA. React + ReactDOM: ~140 KB gzip'd. React + Next.js: ~85 KB. Vue 3: ~35 KB.
