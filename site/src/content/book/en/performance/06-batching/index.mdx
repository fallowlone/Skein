N+1 was a specific shape — round-trips multiplied by N. Batching generalises the fix: any operation with a mostly-fixed per-call cost can be amortised by grouping. Kafka producers batch messages, syscalls batch via io_uring, Postgres batches inserts via COPY, Redis batches via pipelining. The same lever, the same tradeoff: bigger window = higher throughput + higher tail-latency for items at the front.

<Crux>Per-op fixed cost dominates? Batch. Window = batch size and max wait; bigger batches buy throughput, charge tail-latency.</Crux>

Every operation has a fixed cost (header, ACK, syscall transition, log flush, planner overhead) and a variable cost (payload size). When the fixed cost dominates and the operation rate is high, the per-op throughput floor is the fixed cost. Batching collapses N operations' fixed cost into one operation's fixed cost. Production systems use this everywhere: TCP Nagle's algorithm, Kafka linger.ms, Postgres COPY, Redis pipelining, io_uring submission queues, syslog buffering. The senior question is never "batch or not" but "what window size maximises throughput without breaking the SLO tail latency?".

    <p><strong>What this is in one sentence.</strong> Group many small operations into one bigger operation so the fixed cost (network header, syscall, ACK) gets paid once instead of N times.</p>
    <p><strong>Why care.</strong> A service writing 10,000 logs/sec one-at-a-time can crush a disk; the same service writing batches of 100 every 100 ms is fast and barely loaded. Same data, very different cost.</p>
    <p><strong>The metaphor.</strong> A delivery courier can take 1 package per trip or 50 packages per trip. Fuel + driver time is fixed per trip; payload barely changes cost. 50 trips of 1 vs 1 trip of 50 — same delivery, second is 50x cheaper. Batching = load the truck before driving.</p>
    <p><strong>Bea and Sven.</strong> <PersonaTag id="bea" lang="en" /> ships a Kafka producer flushing each message individually; throughput tops at 8k msg/sec, CPU high. <PersonaTag id="sven" lang="en" /> sets linger.ms=10 and batch.size=64KB; producer waits up to 10 ms or 64 KB, ships one request. Throughput jumps to 150k msg/sec; CPU drops. Items at the front of a window wait ≤10 ms — acceptable.</p>
    <p><strong>One scenario.</strong> A monitoring agent does one HTTP POST per metric = 50k POSTs/sec to the backend. Backend chokes. Agent switches to one POST every 10 seconds with all accumulated metrics. POSTs to backend drop to 0.1/sec/agent. If the agent crashes mid-batch, up to 10 s of data is lost — accepted for 100x reduction in load.</p>

  <Fragment slot="middle">
    <p><strong>The two-dimensional window.</strong> Every batching system has two knobs: max-size (bytes or records) and max-wait (time). Whichever fires first sends the batch. Without max-size, a slow producer holds the batch until time elapses, wasting throughput. Without max-wait, a producer with a slow trickle holds the first item indefinitely. Kafka calls these <code>batch.size</code> + <code>linger.ms</code>; the AWS SDK calls them <code>maxBatchItems</code> + <code>maxBatchWindowMillis</code>; io_uring uses queue depth + io_setup'd polling intervals. Senior tuning rule: set max-size to dominate at full load (batch fills before timer fires) and max-wait to bound latency for sparse periods. Common defaults: 10-100 ms wait, 64 KB - 1 MB size, tuned empirically by replaying production traffic against staging.</p>
    <p><strong>Amortising the fixed cost: the math.</strong> Suppose an operation has fixed cost F (per-call overhead, say 50 μs syscall + 100 μs network) and variable cost V*n (n is payload size, V is bytes/μs rate). Total time for N individual operations: N * (F + V*n). Total time for one batch of N: F + V*(N*n). Speedup ratio: (N*F + V*N*n) / (F + V*N*n). When F dominates (small payloads), speedup approaches N. When V dominates (large payloads), speedup approaches 1. For typical small-payload operations (~1KB messages, ~50 μs RTT), batching 100 items reduces wall time from ~5 ms to ~150 μs — a 33x speedup. Break-even is approximately F = V*n; above that, batching wins; below, it doesn't matter. Senior tuning measures F and V for the specific operation before tuning the window.</p>
    <p><strong>Kafka producer batching, in detail.</strong> Canonical batching pattern in distributed systems. Producer accumulates messages per (topic, partition); when batch.size reaches the limit OR linger.ms expires, the batch is sent as one ProduceRequest. linger.ms default 0 (no wait — every message goes immediately); for throughput-sensitive workloads, set 5-100 ms. batch.size default 16 KB; for high-volume topics, 64-512 KB. Network call cost: one TCP send per batch; broker writes one record per message but disk write is one fsync per batch (if acks=all). At 100k+ msg/sec/topic, batching dominates both producer CPU and broker disk performance. Compression (compression.type=lz4 or snappy) applied per-batch — bigger batches compress better, further reducing network and disk cost. Full chain: app produce → producer buffer → batch sent → broker receives → compression checked → written to segment + replicated → ACK returned. Each step has its own optimisations; producer-side batch is where most of the win comes from.</p>
    <p><strong>Database bulk inserts.</strong> Postgres COPY beats INSERT VALUES (...), (...), (...) which beats one INSERT per row. COPY: streams data in a custom protocol, bypasses parser per-row, single transaction commit. INSERT VALUES multi-row: one parse + one plan + one commit; can do ~5,000-50,000 rows depending on row size. Single-row INSERT: parse + plan + commit per row; ~1,000-5,000 rows/sec. Concrete: 1M rows takes ~10 seconds with single-row, ~2 seconds with multi-row INSERT VALUES, ~0.5 seconds with COPY. ORMs expose this: ActiveRecord's <code>insert_all</code>, Django's <code>bulk_create</code>, SQLAlchemy's <code>Session.execute(insert, list_of_dicts)</code>. Use them for any bulk path; not for single-row interactive inserts where simplicity matters more than micro-throughput.</p>
    <p><strong>Syscall batching: io_uring and its predecessors.</strong> Traditional POSIX I/O is one syscall per operation: read(), write(), recv(), send(). Each costs ~1-5 μs context switch. For a service doing 100k I/O ops/sec, that's 100-500 ms/sec spent in syscall transitions alone. Batched syscalls: <code>readv</code>/<code>writev</code> do multiple ranges in one call; <code>sendmmsg</code>/<code>recvmmsg</code> send/recv multiple UDP packets; <code>io_uring</code> (Linux 5.1+) submits N operations to a kernel-shared ring and reaps results from a completion ring, with potentially zero syscalls per op in polling mode. Production gains: Netflix saw 30%+ CPU reduction on TLS proxies via io_uring; Ceph and several databases report 20-50% throughput gains. The cost: io_uring's API is unfamiliar, has had security CVEs, and is sometimes disabled in container environments. Senior choice: use io_uring for new high-I/O workloads on modern kernels; writev/sendmmsg as portable fallbacks.</p>
    <p><strong>Failure modes: poison pill and head-of-line blocking.</strong> Two classic batch hazards. (1) Poison pill — one bad item in a batch causes the whole batch to fail. Example: a Kafka producer batch with one oversized message gets rejected; all messages in the batch get rejected. Mitigation: validate items before batching; size-bound each item; retry split-batches. (2) Head-of-line blocking — slow processing of one batch holds up all behind it. Example: metrics ingest batches 100 metrics per HTTP POST; if one POST is slow, the next waits. Mitigation: parallel batch dispatch (multiple in-flight), per-key sharding (different keys go to different batches), or async batching (no waiting for ACK before next batch). Production-grade batching has both: validation + parallel dispatch.</p>
    <p><strong>Adaptive batching.</strong> Static window sizes work for steady load; dynamic loads benefit from adapting. Algorithm: monitor batch fill rate and downstream latency; if downstream is slow, decrease batch size (smaller chunks faster); if downstream is fast, increase batch size (more amortisation). Implementations: Kafka producer's <code>delivery.timeout.ms</code> back-pressure; AWS Lambda concurrent execution scaling by queue depth; HTTP/2 stream prioritisation. Principle: window should be wide enough to amortise fixed cost, but no wider than downstream can absorb. Adaptive is more complex to implement and tune but pays off for workloads with daily/diurnal variation (e.g., metrics traffic 10x higher during business hours).</p>
    <p><strong>Observability for batching.</strong> Production-grade observability tracks four per-batch metrics. (1) Batch size histogram — are batches actually filling, or hitting the timer? p50 and p99 in records and bytes. (2) Batch wait time — how long items waited before shipping. (3) Buffer depth gauge — current items in the in-memory buffer; spikes indicate downstream backpressure. (4) Drop count — items dropped due to buffer overflow; should be 0; non-zero is a back-pressure signal. Dashboard layout: time series of all four with alerts on drop count &gt; 0 and buffer depth &gt; 80% cap. Without these, batched systems are opaque to operators; with them, they're debuggable in production.</p>
    <p><strong>Per-runtime batching primitives.</strong> Every major runtime ships a batching API. Node.js: setImmediate/process.nextTick for micro-batching at event-loop tick boundaries, plus stream.cork()/uncork() for batched writes. Go: bufio.Writer for buffered writes with explicit Flush(); channels with select + ticker for time-windowed batching; sync.Pool for buffer reuse. Java: BufferedOutputStream, async-profiler's writer queue, Spring's @Scheduled fixed-delay for time batching, Kafka producer config. Python: asyncio.Queue with batched consumers, asyncpg's executemany for batched DB inserts. Rust: tokio mpsc channels with batching adaptors, async-std stream extensions. Each provides the same primitives: bounded buffer, max-size + max-wait, explicit flush. Senior code review for new high-rate write paths includes "is the language's standard batching primitive applied here?" — usually the answer is "no, it's not", and adding it is a one-PR fix.</p>
    <p><strong>Pipelining vs batching: a related but distinct optimisation.</strong> Pipelining sends N requests without waiting for each ACK; the protocol handles ordering and matching responses. Redis pipelining, HTTP/1.1 pipelining, gRPC client streaming, MySQL pipeline mode all do this. Difference from batching: each request still has its own header + ACK, just sent back-to-back. Throughput gain comes from filling the in-flight window (sending while waiting for prior ACKs) rather than from amortising fixed cost across one merged operation. Combine them: batched requests sent in a pipeline. Redis MGET combines both — multiple keys in one command (batched), and Redis pipelining lets you fire several MGETs without waiting. Best total throughput: batch + pipeline. Senior tuning notes both axes: how many ops per request (batch size), how many requests in flight (pipeline depth).</p>
    <p><strong>Cross-level batching: nested batching across one system.</strong> Production systems often have batching at multiple layers, amortising fixed cost at each. Example: gRPC client with client-side message batching → HTTP/2 framing → TCP segmentation offload → NIC tx-batching. Each layer amortises its own fixed cost. Net effect: one logical operation call (you call client.SendBatch(items)) becomes dramatically fewer operations at every lower layer. Senior insight: when designing batching at one layer, look at the layer below — sometimes the lower layer already batches and your application-level batching duplicates; sometimes it doesn't and application-level batching is essential. Profiling with -e syscalls + iostat shows where batching actually works in the stack.</p>

  <Fragment slot="senior">
    <p><strong>Nagle's algorithm and the original batching tradeoff.</strong> John Nagle's 1984 RFC 896 ("Congestion Control in IP/TCP Internetworks") introduced what's now Nagle's algorithm: TCP buffers small outbound segments until either an ACK is received or the buffer fills to MSS bytes. Motivation was the same as modern Kafka batching: 1-byte telnet keystrokes were creating 40-byte TCP/IP headers per byte, swamping early networks. Nagle's algorithm batches small writes into one segment, amortising the header cost. The tradeoff is the same modern issue: interactive applications wait for the next write or ACK, hurting tail latency. The TCP_NODELAY socket option disables Nagle; modern protocols (HTTP/2, gRPC) typically set TCP_NODELAY and do application-level batching instead, which gives finer control. The lineage from Nagle 1984 through Kafka linger.ms (2011) to io_uring submission queues (2019) is one continuous design pattern.</p>
    <p><strong>io_uring deep dive.</strong> io_uring (Linux 5.1+) is the most recent and most powerful generic batching primitive in the kernel. Two ring buffers, mmap'd shared between user and kernel: submission queue (SQ) and completion queue (CQ). User pushes operation descriptors into SQ; kernel reads and executes them; results land in CQ. In default mode, user calls io_uring_enter() once to notify the kernel; the kernel processes all SQ entries and posts results. In polled mode (IORING_SETUP_SQPOLL), a kernel thread polls the SQ continuously — user can submit operations with zero syscalls. Result: at 1M ops/sec, traditional read/write would burn ~1 ms/sec on syscalls alone; io_uring polled mode brings this to near zero. Adoption: PostgreSQL 17 added io_uring backend, Ceph has experimental support, Netflix's async-profiler reports steady-state CPU reduction of 5-15% on TLS proxies. Security CVEs (CVE-2023-2598, CVE-2024-0582, several others) led to some container runtimes disabling io_uring by default; senior teams keep track and weigh tradeoffs per deployment.</p>
    <p><strong>The latency-throughput Pareto frontier.</strong> Batching is the most explicit tradeoff curve in performance engineering: every (throughput, latency) point is achievable by varying the window. No batching: lowest latency, throughput limited by fixed cost. Infinite batching: max theoretical throughput, latency = ∞ for the first item. Senior workflow: define SLO latency ceiling, find the largest batch window that stays under it — that's the throughput-maximising operating point under the constraint. Graph it: x-axis = batch wait time, y-axis-1 = throughput (rises with batch size, plateaus when downstream saturates), y-axis-2 = p99 latency (rises linearly with batch wait time). Intersection of (y-axis-2 = SLO ceiling) with (x-axis = batch wait) is your optimal window. Adaptive systems track this curve dynamically; static systems tune once and accept the drift over time.</p>
    <p><strong>Batch coalescing and request deduplication.</strong> A specialised batching pattern for cache/lookup workloads: when multiple concurrent requests ask for the same key, coalesce them into one batch. Classic example: cache miss handling. Worker A misses cache for key K, starts loading from DB; worker B also misses for K and would also load from DB, but instead joins A's pending request. Returns same result to both. Implementations: singleflight (Go's golang.org/x/sync/singleflight), Caffeine's AsyncLoadingCache for Java, request collapsing in Varnish/CDN edge. Production impact: a hot cache miss with 100 concurrent requests becomes 1 DB query instead of 100 — preventing thundering-herd. Combined with batch loading (DataLoader pattern from the N+1 piece), this becomes "all requests in this 10 ms window for any combination of keys → one batched DB query". Coordinated with cache stampede protection, it eliminates a class of cascading failures.</p>
    <p><strong>Batch failure isolation.</strong> A batch is an all-or-nothing transaction in many systems (Kafka producer batch is committed atomically; Postgres COPY commits as one). When one item poisons the batch, all items fail. Senior production design uses three patterns to limit blast radius: (1) Pre-validation — every item is shape/size checked before being added; oversized or malformed items rejected immediately. (2) Split-and-retry — on batch failure, the producer splits the batch in half, retries each half; recursively localises the bad item. Kafka's producer does this via custom retry logic; AWS SDKs build it in. (3) Per-item ACK — some protocols (Kafka exactly-once, AWS Kinesis) return per-item success/failure within the batch response, so callers can re-batch only the failures. Without these, a single bad item in a batch of 1000 either drops 1000 valid items or stalls the producer forever retrying. Real incidents: AWS Lambda batch event source has retried entire batches on single-item failures, causing cascading retries and SQS dead-letter queue spikes; teams configure smaller batch sizes + bisection retry.</p>
    <p><strong>Backpressure and bounded queues.</strong> Batching producers buffer in memory; an unbounded buffer is a memory leak waiting to happen. Backpressure: when downstream can't keep up, producer's buffer fills; without bounds, OOM is inevitable. Three production-grade patterns: (1) Bounded queue with block: producer blocks when buffer is full, applying back-pressure upstream. Reactive Streams, Akka Streams, RxJava use this. (2) Bounded queue with drop: producer drops items when buffer is full, increments a "dropped" counter. Metrics agents typically use this — losing some metrics preferable to crashing. (3) Bounded queue with spill-to-disk: producer flushes oldest items to disk-backed queue when memory queue is full. Fluentd, Vector, Filebeat use this for log shipping — durability over latency. Choice depends on workload: interactive paths want block; fire-and-forget metrics want drop; audit logs want spill-to-disk. All three are explicit policies; "infinite buffer, will be fine" is the production failure mode.</p>
    <p><strong>Security: batch-amplified DoS and replay risks.</strong> Batching can amplify attack vectors. (1) Compression bomb: an attacker sends a batch of highly-compressible payloads; the receiver decompresses to huge memory. Real CVE: CVE-2018-10872 (Kafka decompression bomb). Mitigation: cap decompressed batch size at receiver, not just compressed. (2) Replay risk: a sniffed batch can be replayed to insert N records once vs replaying N requests. Mitigation: per-batch nonce + idempotency token at receiver. (3) Reordering attacks: batched messages may arrive out-of-order between batches; ordering guarantees that hold within a batch may not hold across batches. Mitigation: explicit sequence numbers + reordering at receiver. Each is a known production-grade concern; batched systems include them in the design, not as afterthoughts.</p>
    <p><strong>Production failures.</strong> Lyft 2019: Kinesis batched event consumer fell behind during peak; batch size unbounded, leading to OOM. Fix: bounded batch size + backpressure. Stripe 2020: Postgres COPY ingest path failed when one row in a 50k-row COPY violated a constraint; entire batch rolled back. Fix: pre-validation + smaller batches with bisection retry. Pinterest 2018: Kafka producer with linger.ms=100 hit p99 SLO violation during low-traffic periods (items waited 100 ms for the timer, even when only 1 item per second arrived). Fix: adaptive linger — short window during low traffic. Discord 2021: gateway lost a few seconds of presence events during a deploy; users saw flapping presence. Fix: WAL-style buffer flush on shutdown signal. Pattern: every batched system has a story about the window being wrong for the situation; mature teams have observability and adjustability built in.</p>
    <p><strong>History and lineage.</strong> The batching pattern goes back further than performance engineering as a discipline. 1960s — IBM tape systems batched writes by tape-block size to amortise tape-spin cost. 1970s — early database systems batched commits via group commit. 1984 — Nagle's algorithm. 1990s — Sybase / Oracle bulk loaders, X11 protocol's request batching. 2000s — TCP segmentation offload (TSO) in NICs, generic receive offload (GRO). 2010s — Kafka linger, Redis pipelining, AWS Kinesis batch APIs. 2020s — io_uring, AWS Lambda event source batching, GraphQL DataLoader. Each generation discovered the same lesson in a new layer: fixed cost is the enemy, amortisation is the lever, the only design question is the window size. Senior engineers recognise the pattern instantly in any new system — it's the most reusable performance idea after profiling itself.</p>
    <p><strong>The bigger picture.</strong> Batching is the most generally-applicable performance technique in distributed systems. It's a layer below the specific protocols (N+1 fixes are a special case; GC compaction is another; bundle splitting yet another). The pattern names a fixed cost, amortises it across N operations, accepts a bounded latency penalty in return. Pieces in this chapter so far: profile-first, hot-paths, GC, N+1, this piece, next bundle budgets. The capstone weaves them. Reading the profile + applying the right family of fix is the consistent loop; batching is the family any time the cost is "fixed per call".</p>
