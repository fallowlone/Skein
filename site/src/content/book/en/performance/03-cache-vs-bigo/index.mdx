CS textbooks teach big-O as the universal performance lens: O(log N) beats O(N), O(N) beats O(N²), end of story. Modern CPUs disagree. Memory is 100x slower than L1 cache. Branch mispredictions cost 15-30 cycles. A "slow" O(N) linear scan on contiguous memory routinely beats a "fast" O(log N) binary search on a tree of pointers — because the linear scan stays in cache and the tree thrashes RAM. Big-O remains the right starting model; the cache hierarchy is the truth that ships in production.

<Crux>Big-O is asymptotic. Cache locality is real. Same O(N²): row-major loop 300ms, column-major 2800ms — same algorithm, 9x slower.</Crux>

The mental model: a modern CPU is not a uniform memory machine. The L1 cache sits 1 cycle away (sub-nanosecond), L2 around 5 cycles, L3 around 15 cycles, and main memory 100-300 cycles away. An access pattern that touches predictable, contiguous bytes feeds the hardware prefetcher and stays in L1; a pattern that jumps between distant pointers misses every level and pays full RAM latency on every step. Big-O counts logical operations as if each took the same time. In reality, each operation's wall-clock cost varies by 100x depending on where its data sits. The senior frontend or backend performance engineer's first reflex is not "make it O(log N)"; it is "make the working set fit in cache and the access pattern friendly to the prefetcher".

    <p><strong>What this is in one sentence.</strong> Big-O complexity counts operations, but modern CPUs care more about where data sits — fast cache or slow memory — and that gap can flip which algorithm wins.</p>
    <p><strong>Why care.</strong> Picking the "theoretically faster" algorithm can make your code 10x slower if it scatters data across memory. Picking the "slower" algorithm that touches contiguous data can win — even when big-O says it shouldn't.</p>
    <p><strong>The metaphor.</strong> A library has 10 books on your desk (L1 cache), 100 on a nearby shelf (L2), 10000 in the same room (L3), and 10 million in a warehouse two blocks away (RAM). A "fast" algorithm that needs to walk to the warehouse for every step loses to a "slow" algorithm that processes every book on your desk in order. Distance matters more than operation count. The desk is 100x faster to reach than the warehouse — same as L1 cache vs main memory.</p>
    <p><strong>Bea and Sven.</strong> <PersonaTag id="bea" lang="en" /> a developer benchmarks two list types in JS: an Array of 1 million numbers and a linked list of 1 million nodes. Iterating the Array takes 2ms; iterating the linked list takes 35ms. Both are O(N). <PersonaTag id="sven" lang="en" /> the CPU explains: the Array sits in contiguous memory, fits in cache, prefetcher loads the next chunk while you process the current. The linked list scatters nodes across the heap; each .next pointer jumps to random memory, every step pays a cache miss. Same big-O, 17x speed difference.</p>
    <p><strong>One scenario.</strong> A matrix multiply on 10000x10000 doubles. Both row-major and column-major loops are O(N²). The row-major loop touches array[i][0], array[i][1], array[i][2]... — contiguous in memory, cache-friendly. The column-major loop touches array[0][j], array[1][j], array[2][j]... — each step jumps 80000 bytes (10000 doubles), a fresh cache line every time. Row-major: 300ms. Column-major: 2800ms. Same algorithm, 9x slower, just from changing access order.</p>

  <Fragment slot="middle">
    <p><strong>The cache hierarchy in numbers.</strong> Modern x86 and ARM CPUs share the same broad shape. L1 cache: 32-64 KB per core, 3-5 cycles latency (about 1ns at 5GHz), private to each core. L2: 256KB to 1MB per core (Intel Raptor Lake P-cores hit 2MB, AMD Zen 5 stays at 1MB for lower latency), 10-15 cycles. L3: 4-64MB shared across all cores, 30-50 cycles. Main memory (DDR5-6000): 70-100ns, 200-300 cycles. The factor between L1 and RAM is roughly 100x in latency, which is the dominant lever in real-world perf tuning. A single cache miss costs more than 30 floating-point operations would take in registers.</p>
    <p><strong>Cache lines: the unit of transfer.</strong> Data does not move between RAM and cache one byte at a time. It moves in cache lines — 64 bytes on x86 and most ARM (some Apple Silicon and ARM server cores use 128 bytes). Reading byte at address X loads bytes X to X+63 into cache, all at once. This is why sequential access is so fast: read byte 0, the entire 0-63 line is now in L1; read bytes 1-63 next, each one is a free hit. It is also why "false sharing" hurts multi-threaded code: two threads writing to different variables in the same cache line still invalidate each other's L1 copies, ping-ponging the line between cores at ~30-50 cycles per ping. The fix is alignment: place per-thread state at least 64 bytes apart.</p>
    <p><strong>Big-O assumes uniform cost.</strong> The big-O analysis model treats every operation as taking constant time. On modern hardware, this is a wild approximation. A cache hit costs 1-15 cycles; a cache miss costs 100-300 cycles. Two operations with the same "instruction count" can differ by 100x in wall-clock time. This means big-O is still useful — for predicting how cost grows with N — but the constant factor it ignores is the difference between fitting in L1 (fast constant) and missing every line (slow constant). For small N, the constants dominate entirely; the O(log N) tree may not beat the O(N) array until N is in the millions.</p>
    <p><strong>Array vs linked list: the canonical case.</strong> Iterating a std::vector of 1 million int: about 2ms. Iterating a std::list of 1 million int: about 35ms. Same O(N) complexity, 17x runtime difference. The vector is one contiguous allocation; the prefetcher fills L1 ahead of the CPU. The list nodes are separately heap-allocated; each .next dereference is likely a cache miss. Even worse for trees: a red-black tree of 1M ints with random insertion order has nodes scattered all over the heap. A linear scan beats a binary search until N is so large that the array becomes too big to scan. Production rule of thumb: prefer arrays / vectors over linked structures unless you have a specific reason (mid-list inserts dominate, lock-free needs, etc.).</p>
    <p><strong>Row-major vs column-major.</strong> A 2D array <code>arr[i][j]</code> in C / Java / Rust / Python (numpy default) is laid out row by row: <code>arr[0][0]</code>, <code>arr[0][1]</code>, ..., <code>arr[0][N-1]</code>, <code>arr[1][0]</code>, etc. Looping <code>for i: for j: arr[i][j]</code> touches addresses in order — cache-friendly. Looping <code>for j: for i: arr[i][j]</code> jumps N*sizeof(elem) bytes per step — cache-hostile. On 10000x10000 doubles: 300ms vs 2800ms. Same instruction count, same logical algorithm, 9x slowdown. Fortran defaults to column-major; ALWAYS check your language's convention before assuming a layout. Cache-oblivious blocking (process the matrix in tiles of ~64 rows so each tile fits in L2) gets both row and column directions fast for the same code shape.</p>
    <p><strong>Branch prediction.</strong> Every if/else, loop boundary, and function call is a branch the CPU has to predict. Modern branch predictors are remarkable — 95-99% accuracy on most real code. But misprediction costs 10-30 cycles on modern x86, sometimes more on deeper pipelines (Zen 2 pipeline is 19 stages). For unpredictable branches (e.g. an if on random data), the misprediction rate climbs to ~50% and each miss flushes the pipeline. A canonical example: sorting an array before summing only elements above a threshold. The unsorted version mispredicts on every comparison (~50% miss rate); the sorted version predicts correctly almost always after the threshold crossing. Same loop, same O(N), often 2-3x speedup just from sorting first (despite the O(N log N) sort cost).</p>
    <p><strong>Branchless code.</strong> When branches are unpredictable, removing them is faster. Replace <code>if (x &gt; 0) y = a else y = b</code> with <code>y = (x &gt; 0) * a + (x &lt;= 0) * b</code>, or use conditional move (CMOV on x86). The branchless version always computes both sides; the branched version skips one but pays mispredict cost when wrong. Tipping point: if branch is predictable (95%+), branched is faster. If unpredictable (50/50), branchless wins by 2-5x. Compilers sometimes pick this automatically; sometimes they don't and need explicit <code>__builtin_expect</code> or PGO data. Common in sort partition, packet-classification loops, image-processing inner loops.</p>
    <p><strong>SIMD and data layout.</strong> Modern CPUs have wide vector registers (256-bit AVX2, 512-bit AVX-512, 128-bit NEON on ARM). One instruction can operate on 4-8 floats at once. To use them, data must be laid out in the right shape — typically "structure of arrays" (SoA) rather than "array of structures" (AoS). SoA: <code>xs[N], ys[N], zs[N]</code>. AoS: <code>Points[N] &#123; x, y, z &#125;</code>. The SoA layout lets the SIMD unit load 8 xs in one cycle and operate on them in parallel; the AoS layout requires gather/scatter, much slower. Game engines, ML inference, audio processing all prefer SoA. Browsers' V8 hot loops use SoA via TypedArrays for the same reason — see the V8-internals piece in this chapter.</p>
    <p><strong>Profile-guided thinking.</strong> The first step in any perf debug is not optimisation — it is measurement. Tools: <code>perf stat</code> (Linux) shows cache hit rate, IPC, branch miss rate. <code>perf record</code> samples the hot functions. Intel VTune adds per-line cache miss attribution. Apple Instruments equivalent on macOS. <code>cachegrind</code> simulates cache behaviour for fine-grained analysis. The goal: identify whether your bottleneck is cache misses, branch mispredictions, instruction issue rate, or memory bandwidth. Each has different fixes. "Optimising" without measuring is guessing; measurements turn guesses into engineering.</p>
    <p><strong>Memory bandwidth as a separate constraint.</strong> Cache hit rate is one axis; memory bandwidth is another. A workload that streams through 100GB of memory will be bound by RAM bandwidth (~50-100 GB/s on modern DDR5 systems) regardless of cache behaviour. Bandwidth-bound code is fixed by reducing data volume (more compact types, compression, on-the-fly computation instead of materialised tables), not by improving cache locality. The two metrics often appear together but require different fixes; <code>perf stat</code>'s <code>cache-misses</code> vs <code>mem-loads-retired.l3-miss</code> separates them.</p>
    <p><strong>NUMA: when multi-socket gets in the way.</strong> Servers with 2+ CPU sockets are Non-Uniform Memory Access: each socket has local RAM at ~70ns, remote (other socket) RAM at ~120-150ns. A thread that allocates on socket 0 but runs on socket 1 pays the remote-access tax on every load. Mitigations: pin threads to sockets (taskset, hwloc), allocate on the local NUMA node (numactl, allocator NUMA awareness), distribute work so each thread touches data from its local socket. Database engines (Postgres, MySQL, Mongo) and JVMs expose NUMA flags. Misconfigured: a 2-socket box can run slower than a 1-socket one for memory-bound workloads.</p>
    <p><strong>Vectorisation and auto-vec.</strong> Compilers auto-vectorise simple loops over arrays into SIMD instructions when the data layout permits (no aliasing, contiguous, predictable trip count). Auto-vec defeats: pointers that might alias (use <code>restrict</code> in C, mark types appropriately in Rust), data-dependent inner branches, variable trip counts. Check what the compiler emitted with <code>-fopt-info-vec</code> (GCC) or <code>-Rpass=loop-vectorize</code> (Clang). For loops that fail auto-vec, manual SIMD intrinsics (AVX2, NEON) or libraries (Highway, simd-everywhere) close the gap. Cold counter to auto-vec: don't force it via #pragma if the loop has correctness-relevant edge cases — auto-vec for those needs careful guards.</p>
    <p><strong>Inlining and instruction cache.</strong> Aggressive inlining helps branch prediction and removes call overhead, but bloats code size — which hurts the instruction cache (I-cache, typically 32-64 KB per core). A function called from 100 places that gets inlined adds 100 copies of its body to the binary; if it's hot, those copies pollute I-cache, evicting other hot functions. The fix is selective: inline tiny functions (1-3 lines) freely, inline larger functions only on the hottest call paths. Profile-guided optimisation (PGO) makes these decisions automatically — without PGO, the compiler defaults to "inline what fits the heuristic" which can be wrong.</p>

  <Fragment slot="senior">
    <p><strong>Hardware prefetcher behaviour.</strong> Modern CPUs have multiple hardware prefetchers: a sequential one that detects forward strides, a stride detector that catches "every Nth byte" patterns, and on some chips, a content-based prefetcher that follows pointer-like values. The sequential prefetcher kicks in after 2-3 consecutive cache misses in the same direction; once active, it prefetches up to 16 lines ahead. Defeating it: random access, or access patterns whose stride is too long for detection. Helping it: keep your hot loop's stride small (≤256 bytes) and consistent. Software prefetch via <code>__builtin_prefetch</code> is the manual escape hatch — useful when you know the access pattern but the hardware can't infer it (e.g. graph traversals where the next node is data-dependent).</p>
    <p><strong>TLB and page-level locality.</strong> Beyond L1/L2/L3, the Translation Lookaside Buffer (TLB) caches virtual-to-physical address translations. A TLB miss costs 5-50 cycles for the page walk. Workloads that touch random pages (each ~4KB) blow out the TLB even if data fits in L3. Mitigations: huge pages (2MB or 1GB pages reduce TLB pressure by 512x or 256000x), allocator awareness (jemalloc / mimalloc batch related allocations into the same page region). For high-perf code touching gigabytes — databases, ML inference, image processing — huge pages can be a 10-20% win independent of cache locality.</p>
    <p><strong>Cache associativity and conflict misses.</strong> Caches are not fully associative — each cache line can only be placed in a few specific "ways" (typically 8-16 way associative for L1). If many hot addresses happen to map to the same set, they evict each other even though plenty of cache is empty elsewhere. The classic example: stride pattern that matches the cache size modulo. Mitigation: pad data structures by an extra cache line to break alignment patterns, randomise large array alignments, use cache-oblivious data layouts. <code>cachegrind</code> reports D1mr/D1mw (L1 miss rate) and DLmr/DLmw (LL miss rate) per source line, exposing where the conflict misses happen.</p>
    <p><strong>Branch prediction algorithms.</strong> Modern predictors are sophisticated. Branch target buffer (BTB): caches the target address of recent indirect branches. Pattern History Table (PHT): tracks per-branch taken/not-taken history. TAGE (TAgged GEometric) predictor: combines multiple history lengths, used in modern Intel and AMD. Hit rates of 95-99% are typical on real code. Hard cases: data-dependent branches (sort, filter), virtual function calls with high polymorphism, very long pipelines (Apple M1/M2/M3 has 10+ stages). The cost of a miss is the pipeline depth — at 20 stages with multi-issue, a miss can waste 40+ slots, equivalent to executing 40 ops with no progress.</p>
    <p><strong>Memory-level parallelism (MLP).</strong> Modern CPUs can have 8-16 cache misses outstanding simultaneously. If your code's miss pattern allows the CPU to issue independent loads ahead, the latency stacks in parallel — 10 misses don't cost 1000 cycles, they cost ~150 cycles (one miss latency + dispatch slots). Dependent-load chains (pointer chasing: A.next.next.next) defeat MLP completely because each load needs the previous result. Independent-load patterns (array of indices, scatter/gather) get full parallelism. Optimising for MLP is the level above just optimising for cache hit rate; tools like <code>perf c2c</code> on Linux show MLP behaviour. ARM PMU counters expose similar metrics on Apple Silicon.</p>
    <p><strong>Non-temporal stores and streaming.</strong> Streaming through gigabytes of memory (memcpy-like workloads) does not benefit from caching the data — it's read once and discarded. Non-temporal store instructions (<code>movntps</code> on x86, similar on ARM) bypass the cache and write directly to memory, freeing cache for hot data. Compilers can emit them via <code>__builtin_nontemporal_store</code>. For bandwidth-bound workloads (DB scans, log processing), non-temporal stores improve sustained bandwidth by 20-30% by not polluting L3 with one-shot data.</p>
    <p><strong>Cache-oblivious algorithms.</strong> A cache-oblivious algorithm performs well at every cache level without knowing the specific sizes. The canonical example: recursive blocked matrix multiply. Instead of three nested loops, recursively divide the matrix into 4 sub-matrices; recurse until base case. At each recursion level, the active sub-matrix fits in some cache level naturally — even though the algorithm doesn't know which one. Result: cache-friendly behaviour from L1 through L3 simultaneously. Applies to sort (cache-oblivious mergesort), search trees (cache-oblivious B-trees), transposes, FFT. The 2-4x speedup over naive often dominates the cleverness cost.</p>
    <p><strong>Profile-guided optimisation (PGO).</strong> Compilers improve when given runtime data. Build the binary with instrumentation, run a representative workload, recompile using the collected profile. PGO improvements: better inlining decisions (inline hot callees, not cold ones), branch prediction hints baked into code layout (predicted-taken branches placed sequentially), reorder basic blocks to keep hot paths contiguous (better i-cache locality), function placement (group co-called functions in nearby pages). Real workloads see 10-30% speedups from PGO. Cost: build pipeline complexity, need a representative profiling workload. Used heavily in Chrome, Firefox, Postgres, Linux kernel.</p>
    <p><strong>Real production failures.</strong> Discord 2023: a Rust struct refactor moved a hot field to the end of a 96-byte struct, pushing it across a cache line boundary. p99 latency on the message-render path grew 40%. Fixed by reordering fields to keep the hot ones in the first 64 bytes. Mojang Minecraft Java edition 2018: an internal data structure was a HashMap of small entities; replacing with a contiguous array (entity component system, ECS) gave 3-5x throughput. Discord 2024 game-server: ECS layout combined with SIMD-aware structs delivered another 2x. Bun 2024 startup time regression: a new dependency added a HashMap on the cold path that, due to allocation order, blew the L1 cache during JIT warmup; fixed by lazy-init. The pattern: cache-related perf bugs hide as "small" code changes that move bytes around without changing the algorithm.</p>
    <p><strong>Observability for cache and branch perf.</strong> The essential set: <code>perf stat -e cache-misses,cache-references,branch-misses,branches,cycles,instructions</code>. Compute IPC (instructions / cycles): below 1.0 indicates a memory-bound workload; 2-4 is healthy compute-bound. Compute L1/LLC miss rate: 1% L1 misses is acceptable; 10%+ indicates a layout problem. Compute branch miss rate: 1-2% is normal; 5%+ means an unpredictable branch dominates. Linux <code>perf top</code> shows per-symbol miss attribution. Intel VTune and AMD uProf add per-line attribution. For production: BPF-based profilers (BCC's <code>cachestat</code>, <code>llcstat</code>) sample without instrumenting; ARM PMU and Apple Instruments expose the same metrics on those platforms.</p>
    <p><strong>The bigger lesson: design for the hardware.</strong> Modern CPUs reward locality and predictability. Big-O remains the right model for scalability with N; it is silent on constant factors that vary 100x with layout. The performance-engineering loop: measure (perf, VTune), identify dominant cost (cache miss, branch miss, bandwidth, instruction issue), choose the matching fix (layout, branch removal, prefetch, SIMD), measure again. Avoid the trap of "I'll just use the better-big-O algorithm" without measuring — production reality is that constants dominate well into the millions for many problem sizes. The senior performance engineer thinks in cache lines first, big-O second.</p>
    <p><strong>Co-location: data and code together.</strong> Cache locality applies not just to data structures but also to instruction layout. Functions called together should live near each other in the binary; PGO arranges this automatically based on call frequency. For very hot inner loops, "warm starts" — running an actual representative workload at startup to populate caches — turn cold-start regressions into invisible. The Linux kernel uses this for boot-critical paths; Postgres has connection-pool warming. The principle: caches reward the second-and-following accesses, so the engineering trick is ensuring the first access happens before users see latency.</p>
