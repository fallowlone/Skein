Indexes (<a href="/en/databases/02-indexes/">02-indexes</a>) told us how Postgres finds a row; execution plans (<a href="/en/databases/03-execution-plans/">03-execution-plans</a>) showed how the planner chose a path. The next question is concurrency: when two transactions touch the same row at the same time, what does each see, and why does neither have to wait for the other?

<Crux>How Postgres lets many writers and readers see consistent data at once — and what it costs to keep that promise.</Crux>

The trick is to never delete or overwrite a row in place. Every UPDATE creates a new version; every DELETE just marks the old version dead. Each transaction reads through a snapshot that pins which versions are visible, so readers never block writers and writers never block readers. The cost shows up later: dead versions accumulate, autovacuum has to reclaim them, and any transaction that lives too long stretches the pinning window — sometimes spectacularly.

    <p><strong>What MVCC does in one sentence.</strong> It keeps every row's history so each transaction sees a stable picture of the database without having to lock the rows other people are touching.</p>
    <p><strong>Why care.</strong> Without it, a five-minute analytics query would freeze every order coming in, and your dashboard would either lie about totals or block the checkout button.</p>
    <p><strong>The metaphor.</strong> Imagine a busy library where every book has many copies stamped with the date they were taken off the shelf. When <PersonaTag id="sven" lang="en" /> asks for "the catalog as of when I started reading", the librarian hands him a labeled copy frozen at that moment, even while <PersonaTag id="otto" lang="en" /> is back at the desk binding a new edition. Sven reads his copy in peace. Otto adds a new edition behind the counter. Neither has to wait for the other; they are looking at different stamped copies of the same shelf. Later, a janitor sweeps through and discards copies nobody is reading anymore. That sweep is what Postgres calls VACUUM, and the janitor only throws out a copy when no reader is still holding its date-stamp.</p>
    <p><strong>Sven and Otto.</strong> <PersonaTag id="sven" lang="en" /> the app server runs a monthly report. <PersonaTag id="otto" lang="en" /> the database has thousands of orders arriving per second. Without MVCC, the report either locks the orders table (freezing checkout) or sees half-finished updates. With MVCC, Sven gets a snapshot frozen at the report start; new orders go to fresh versions Sven cannot see. Report finishes, checkout never stalls.</p>
    <p><strong>One scenario.</strong> Two browser tabs edit the same profile. Tab A loads, you type. Tab B loads, edits one field, saves. You save Tab A: Tab B's edit silently disappeared. That is <em>lost update</em>. MVCC alone does not fix it — ask the database (<code>SELECT FOR UPDATE</code> or a stricter isolation level).</p>

  <Fragment slot="middle">
    <p><strong>Every row carries a header.</strong> When Postgres stores a tuple on a heap page, it prefixes the user columns with a 23-byte header containing two 32-bit transaction ids: <code>t_xmin</code> (the transaction that inserted this version) and <code>t_xmax</code> (the transaction that deleted or updated this version; zero if the version is still live). The header also carries <code>t_cid</code> (the command id within a transaction), <code>t_ctid</code> (a pointer to the next version of this row, used for chaining updates), and <code>t_infomask</code> + <code>t_infomask2</code> bitmaps that flag commit status, lock state, freeze state, and the HOT-related bits described below. These fields are how visibility decisions get made on every single tuple Postgres looks at.</p>
    <p><strong>How a snapshot decides what to read.</strong> When a transaction begins (more precisely: when it first executes a query under <code>READ COMMITTED</code>, or at <code>BEGIN</code> under <code>REPEATABLE READ</code>), Postgres builds a snapshot. The snapshot is a small structure that captures three numbers: <code>xmin</code> (the oldest still-running transaction id), <code>xmax</code> (one past the newest committed id at snapshot time), and <code>xip</code> (the list of in-progress transactions between <code>xmin</code> and <code>xmax</code>). When this transaction inspects a tuple, the visibility rule is roughly: a tuple is visible if its <code>t_xmin</code> is committed and not in the snapshot's in-progress list, and its <code>t_xmax</code> is either zero or rolled back or in the in-progress list. That tuple-level rule, applied row by row, is the entire mechanism. There are no read locks involved.</p>
    <p><strong>INSERT, UPDATE, DELETE — what actually happens on disk.</strong> An INSERT places a fresh tuple on a page with <code>t_xmin</code> set to the current transaction id and <code>t_xmax</code> at zero. An UPDATE is two operations: it marks the old tuple's <code>t_xmax</code> with the current transaction id and inserts a new tuple with the new values, setting that new tuple's <code>t_xmin</code> to the same current transaction id and chaining the old tuple's <code>t_ctid</code> to the new tuple's page-and-offset. A DELETE just marks the existing tuple's <code>t_xmax</code> with the current transaction id and writes nothing new. None of these operations physically remove anything. They are all logically reversible until commit, and after commit they are still physically present until VACUUM decides nobody needs them anymore.</p>
    <p><strong>HOT updates: an optimization with a famous cost model.</strong> If an UPDATE touches no indexed columns and the new tuple fits on the same page as the old tuple, Postgres can perform a <em>heap-only tuple</em> update: the old tuple gets a flag (<code>HEAP_HOT_UPDATED</code>) saying "follow the t_ctid chain to find me", the new tuple gets a flag (<code>HEAP_ONLY_TUPLE</code>) saying "no index entry points at me directly". The index continues to point at the original tuple, the heap chain takes the lookup the rest of the way. Two index writes become zero. On UPDATE-heavy workloads where most columns are not indexed this is the difference between WAL doubling and barely growing. HOT chains break when the new version cannot fit on the original page; once broken, every subsequent UPDATE pays the index-write cost again. The fillfactor storage parameter (<code>ALTER TABLE ... SET (fillfactor=85)</code>) reserves free space on each page precisely so HOT chains have room to grow.</p>
    <p><strong>The four isolation levels Postgres exposes.</strong> SQL standard defines four levels — Read Uncommitted, Read Committed, Repeatable Read, Serializable — by listing four anomalies that are or are not allowed: dirty reads, non-repeatable reads, phantom reads, and serialization anomalies. Postgres maps onto this menu but does not follow the standard literally. Read Uncommitted is silently treated as Read Committed; Postgres never allows dirty reads at any level. Read Committed (the default) gives each <em>statement</em> a fresh snapshot, so two SELECTs in the same transaction can see different data. Repeatable Read gives the <em>whole transaction</em> a single snapshot taken at the first statement; Postgres internally implements RR as snapshot isolation, which is stronger than the SQL standard's RR but weaker than true serializable — it forbids phantom reads, but allows write-skew anomalies. Serializable (since 9.1) layers Serializable Snapshot Isolation (SSI) on top of RR: Postgres tracks read–write dependencies during execution and aborts transactions whose commit order cannot correspond to any serial schedule, throwing SQLSTATE 40001.</p>
    <p><strong>What the application has to do about it.</strong> Under Read Committed, the application is responsible for avoiding lost updates: either reread + recompute inside <code>SELECT ... FOR UPDATE</code> (pessimistic locking on the row), or use atomic <code>UPDATE ... WHERE version = ?</code> with optimistic concurrency, or use the <code>RETURNING</code> clause to know whether the row you tried to update actually had the value you expected. Under Repeatable Read and Serializable, the database itself raises SQLSTATE <code>40001 serialization_failure</code> when a conflict is detected, and the application's only correct response is to retry the entire transaction. Frameworks like Django, ActiveRecord, and Hibernate ship retry middlewares; in raw psql you write a loop that catches 40001 and replays the same statements with a fresh snapshot.</p>
    <p><strong>Where the cost is paid.</strong> Each UPDATE creates one fresh tuple plus marks the old tuple dead — both on disk, both in the heap, both eligible for index entries. Until VACUUM clears the dead tuples, every sequential scan walks past them, every index lookup might hit them (and skip them based on visibility), and every page is bigger than the strict minimum. A common rule of thumb at production scale: target dead-tuple ratio below 20% for tables above 50 GB. Smaller tables tolerate higher bloat (30-50%) because the absolute waste is small. VACUUM never physically shrinks the file — it just marks space reusable inside the file. Reclaiming disk back to the operating system requires <code>VACUUM FULL</code> (rewrites the whole table while holding an <code>ACCESS EXCLUSIVE</code> lock, blocks every reader and writer) or the <code>pg_repack</code> extension (rewrites concurrently, swaps at the end). Hence the bumper-sticker version: MVCC is free for reads at a fixed marginal storage cost, and the production discipline is keeping that cost bounded.</p>
    <p><strong>How autovacuum actually decides to run.</strong> Autovacuum is a background process pool (3 workers by default) that wakes every minute and inspects every table in every database for two threshold conditions: the dead-tuple threshold (<code>autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × n_live_tup</code>, default 50 + 20% of live tuples) and the insert threshold (similar formula for fresh inserts that need ANALYZE). When a table crosses a threshold, autovacuum dispatches a worker. The worker takes a <code>SHARE UPDATE EXCLUSIVE</code> lock on the table — strong enough to block other VACUUMs and schema changes, weak enough to let regular reads and writes proceed in parallel. It computes the global oldest <code>xmin</code> across all sessions (the cap on reclaimable tuples), scans the heap, identifies dead tuples whose <code>t_xmax</code> is older than oldest <code>xmin</code>, marks their slots reusable, walks each index to remove pointers at the reclaimed slots, and finally rebuilds the table's free-space map. Throughout, autovacuum is rate-limited by a cost-based delay: every page read costs a few units, every page write costs more units, and once the worker exceeds <code>autovacuum_vacuum_cost_limit</code>, it sleeps for <code>autovacuum_vacuum_cost_delay</code> milliseconds. The cost-based mechanism is exactly what lets autovacuum run continuously on a 50 GB table without saturating IO; the wrong tuning (too slow on NVMe, too aggressive on rotational disks) is the most common autovacuum complaint.</p>
    <p><strong>The hot-standby feedback wrinkle.</strong> Streaming replicas in Postgres can be configured with <code>hot_standby_feedback = on</code>, which sends the replica's oldest active <code>xmin</code> back to the primary so the primary's autovacuum knows not to reclaim tuples a replica still needs. Without it, a long analytical query on a replica can fail with <code>canceling statement due to conflict with recovery</code> when the primary's autovacuum reclaims something the replica's snapshot still references. With it, the primary's bloat is held hostage by the replica's longest-running query. Most production setups choose <code>off</code> on the replica and accept the occasional query cancellation, because pinning primary bloat indefinitely is the worse failure mode. The alternative is to route long analytics to a logical replica that maintains its own snapshot policy independently.</p>

  <Fragment slot="senior">
    <p><strong>Snapshot visibility, bit by bit.</strong> The visibility decision Postgres makes on every tuple it scans is implemented in <code>src/backend/utils/time/snapmgr.c</code> and <code>src/backend/access/heap/heapam_visibility.c</code>. The key function is <code>HeapTupleSatisfiesMVCC(HeapTuple tuple, Snapshot snapshot, Buffer buffer)</code>. It walks a decision tree across <code>t_infomask</code> bits (<code>HEAP_XMIN_COMMITTED</code>, <code>HEAP_XMIN_INVALID</code>, <code>HEAP_XMAX_COMMITTED</code>, <code>HEAP_XMAX_INVALID</code>) to short-circuit the common cases without touching the commit log. When the bits are not set (the row was committed but the hint bit has not yet been written by a later scan), the function consults the <code>CLOG</code> (commit log) to determine commit status, then writes back the hint bit so the next visit is fast. This hint-bit propagation is the reason a SELECT immediately after a long INSERT can be slower than the same SELECT a second later: the first scan touches every tuple's CLOG entry and writes hint bits, the second scan reads the bits directly. Two different transactions cannot disagree on visibility because the rule is purely a function of the tuple's xmin/xmax and the reader's snapshot.</p>
    <p><strong>The CLOG (commit log) and how transaction status is tracked.</strong> Each committed-or-aborted transaction's outcome is recorded in <code>pg_xact/</code> (formerly <code>pg_clog/</code>): two bits per transaction id, packed into pages. At 8 KB per page and 2 bits per transaction, one page covers 16,384 transactions. The CLOG is heavily cached (the <code>clog_buffers</code> setting controls how many pages live in shared buffers). Hint bits on tuples avoid CLOG lookups, but on a freshly written tuple the first reader has to consult CLOG. After a transaction commits, its CLOG bits are durable on disk thanks to WAL — the <code>COMMIT</code> record on disk is what makes the transaction's effect visible to future readers. Crash recovery replays WAL up to the last COMMIT and rebuilds the CLOG state. This is why <code>fsync = on</code> and <code>synchronous_commit = on</code> are non-negotiable for durability: a commit acknowledged before the WAL hit disk could leave CLOG inconsistent on recovery.</p>
    <p><strong>Transaction id wraparound and freezing.</strong> Postgres transaction ids are 32-bit, and at 2 billion-ish active transactions the counter would wrap and old xmin/xmax values would suddenly appear newer than they are — a correctness disaster. Postgres prevents this by <em>freezing</em>: once a tuple is "old enough" (older than <code>autovacuum_freeze_max_age</code>, default 200 million transactions), VACUUM rewrites its <code>t_xmin</code> to the special <code>FrozenTransactionId</code> value, which is always visible to any snapshot. Wraparound prevention vacuum is the highest-priority autovacuum task — it runs even when <code>autovacuum = off</code>, and on a database that approaches 2 billion transactions without enough freezing, Postgres refuses new connections and shuts down with the message <code>database is not accepting commands to avoid wraparound data loss</code>. Operations: monitor <code>SELECT datname, age(datfrozenxid) FROM pg_database</code>, alert at 1 billion, page at 1.5 billion. Real outage in 2017 at Sentry was famously triggered by an autovacuum that fell behind on a 64-bit-xid-not-yet-released cluster — they ended up doing manual freezing to recover.</p>
    <p><strong>Heap fillfactor and HOT chain length.</strong> The fillfactor storage parameter (<code>ALTER TABLE foo SET (fillfactor = 85)</code>) reserves a percentage of each heap page for HOT updates. Default is 100 (fill the page completely); for UPDATE-heavy tables 70–90 is typical. A page filled to fillfactor at INSERT time leaves room for new versions of existing rows to stay on the same page, preserving the HOT chain. Once the chain fills the reserved space, the next UPDATE has to write the new tuple to a different page, breaking HOT for that row. <code>pg_stat_all_tables.n_tup_hot_upd</code> divided by <code>n_tup_upd</code> gives the HOT ratio; on UPDATE-heavy schemas you want this above 80%. Below 50% means fillfactor is too aggressive or the schema has the wrong index set for the workload. The pgstattuple extension exposes <code>tuple_count</code>, <code>dead_tuple_count</code>, and <code>free_space</code> per table for deeper introspection.</p>
    <p><strong>MultiXact and shared row locks.</strong> When more than one transaction wants to hold a non-exclusive lock on the same row (e.g., two transactions both running <code>SELECT ... FOR SHARE</code>), Postgres cannot fit multiple xids into a tuple's single <code>t_xmax</code> field. It instead allocates a <code>MultiXactId</code> — a 32-bit id pointing into <code>pg_multixact/</code> that lists the participating transactions and their lock modes. MultiXacts have their own wraparound (also 2 billion), tracked separately and frozen on a separate cadence. A workload that uses heavy <code>SELECT ... FOR KEY SHARE</code> (the implicit lock from foreign-key checks) can hit MultiXact wraparound long before XID wraparound. Symptom: <code>autovacuum: found xxx removable, xxx nonremovable row versions in xxx pages; xxx dead row versions cannot be removed yet</code> with a high "oldest MultiXact" age. <code>pg_stat_database.datminmxid</code> tracks the minimum MultiXact age; aging policy is identical to xmin freezing.</p>
    <p><strong>Serializable Snapshot Isolation (SSI) internals.</strong> Postgres 9.1 introduced SSI per Cahill, Röhm, and Fekete's 2008 paper. The mechanism: every read tracks "predicate locks" (lightweight, in-memory references to "I read this set"), every write tracks rw-antidependencies ("this transaction wrote something my predicate matched after I read"). At commit time, if a transaction is part of a "dangerous structure" — a cycle of rw-antidependencies — SSI aborts it with SQLSTATE 40001 <code>could not serialize access due to read/write dependencies</code>. The math is conservative: SSI sometimes aborts transactions that would have committed safely (false positives are correct but cost throughput), but it never allows a non-serializable schedule. Predicate-lock memory is bounded by <code>max_pred_locks_per_transaction</code> × <code>max_connections</code>; under memory pressure the locks coarsen from row → page → relation, raising false-positive rate further. Operations: track <code>could not serialize access</code> error rate in logs; if it exceeds a few percent, the workload's lock pressure exceeds the budget.</p>
    <p><strong>Production tuning of autovacuum.</strong> The default knobs are too lax for any high-write table. Per-table overrides via storage parameters: <code>ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.05, autovacuum_vacuum_cost_limit = 2000, autovacuum_vacuum_cost_delay = 2ms)</code> — this turns on autovacuum at 5% dead-tuple ratio (instead of 20%), with higher cost-budget per cycle (faster) and shorter delay between IO chunks (more aggressive). On NVMe-backed clusters the cost-delay can be zero. For tables with bursty write patterns, an explicit <code>VACUUM (PARALLEL 4) orders;</code> overnight via cron is common. <code>autovacuum_max_workers</code> bumps the worker pool from 3 to 6 or 8 on large hosts; the workers compete for <code>autovacuum_max_workers</code> slots in <code>max_worker_processes</code>. Watch <code>pg_stat_progress_vacuum.phase</code> to see live progress: <code>scanning heap</code>, <code>vacuuming indexes</code>, <code>vacuuming heap</code>, <code>cleaning up indexes</code>, <code>truncating heap</code>, <code>performing final cleanup</code>.</p>
    <p><strong>Observability: the metrics that actually move.</strong> Minimum-viable Postgres bloat dashboard exposes: <code>pg_stat_all_tables.n_dead_tup</code> + <code>n_live_tup</code> per table (ratio), <code>pg_stat_user_tables.last_autovacuum</code> and <code>last_autoanalyze</code> timestamps, <code>pg_stat_activity</code> filtered by <code>backend_xmin IS NOT NULL</code> sorted by xmin ascending (oldest snapshot first), <code>pg_stat_replication_slots.xmin</code> for slot-pinned bloat, <code>pg_stat_database.xact_commit + xact_rollback</code> for transaction throughput, <code>pg_stat_database.deadlocks</code> + <code>pg_stat_database_conflicts</code> for contention. For SSI: log scraping for <code>SQLSTATE 40001</code> and the relative rate vs successful commits. For wraparound: <code>SELECT datname, age(datfrozenxid), age(datminmxid) FROM pg_database</code> with alerts at 1 billion / 1.2 billion thresholds. The pgstattuple and pg_buffercache extensions expose physical-page state for deeper investigations. Prometheus exporters (pg_exporter, postgres_exporter) ship these out of the box.</p>
    <p><strong>Real-world failures: long-transaction bloat, orphan replication slots, write-skew in production.</strong> Sentry 2017 — autovacuum fell behind, wraparound triggered, manual freezing under fire. GitLab 2017 — a misclick during a routine maintenance window deleted the wrong directory, but the surrounding bloat made recovery harder because <code>pg_dump</code> against an unvacuumed cluster takes orders of magnitude longer. A common production pattern at companies running long ETL or analytical SELECTs against the OLTP cluster: a 6-hour aggregation pins backend_xmin, every <code>orders</code> table autovacuum logs "cannot remove tuples", overnight the orders table grows from 80 GB to 180 GB, the morning team discovers their disk-full alert at 7 AM. Mitigation: route analytics to a replica with <code>hot_standby_feedback = off</code> (so primary's autovacuum is not held back) or to a logical-replica with its own autovacuum policy, or use <code>SET TRANSACTION ISOLATION LEVEL REPEATABLE READ</code> with a 30-minute statement_timeout that forces such queries to fail loud instead of pinning silently. Replication slots that go orphan when a downstream consumer dies are a separate but identical-shaped failure: the slot's <code>xmin</code> column holds the global oldest-xmin until someone notices.</p>
    <p><strong>History: 8.3 HOT, 9.1 SSI, 12 partitioning, 13 incremental sort, 14 bottom-up index deletion, 16 freezing improvements, 17 vacuum reform.</strong> Postgres 8.3 (2008) shipped HOT updates. 9.1 (2011) shipped SSI for true SERIALIZABLE. 9.5 added <code>INSERT ... ON CONFLICT</code>, which interacts subtly with MVCC because the upsert internally retries on unique-violation. 12 (2019) shipped declarative partitioning that finally made multi-billion-row tables feasible. 13 incremental sort lowered VACUUM cost on heavy-update tables. 14 (2021) introduced bottom-up index deletion, dramatically reducing index bloat for UPDATE-heavy patterns where indexed columns rarely change. 16 (2023) improved cold-start freezing performance. 17 (2024) re-architected vacuum to use TID stores instead of arrays, removing the long-standing <code>maintenance_work_mem</code> ceiling on number of dead tuples per pass (the old "VACUUM has reached the maintenance_work_mem limit, restarting" log line). 18 (2025) continued the trend with better skip-scan during freezing.</p>
    <p><strong>Cross-protocol: logical replication, BDR, Citus.</strong> Logical replication uses MVCC under the hood — the WAL decoder reads tuple changes from WAL and produces a stream the subscriber applies. The subscriber's autovacuum runs independently and reclaims dead tuples there. Logical slots pin the publisher's xmin so the subscriber can catch up, which is why an idle subscriber is a slow-motion bloat bomb. BDR (BiDirectional Replication, by 2ndQuadrant/EDB) implements eventual consistency on top of logical replication with conflict resolution that explicitly understands MVCC: last-update-wins by tuple xmin timestamp. Citus shards a table across worker nodes; each shard is a real Postgres table with its own MVCC, and the coordinator's snapshot is propagated to workers as a "global snapshot" passed in the worker connection. Distributed serializable transactions on Citus require all worker nodes to agree on SSI dependencies — implemented via a coordinator-managed predicate-lock table.</p>
    <p><strong>Deployment patterns: pg_repack, pgbouncer, idle-in-transaction.</strong> <code>pg_repack</code> rewrites a bloated table online by creating a shadow copy, applying WAL changes incrementally, and atomically swapping at the end — no <code>ACCESS EXCLUSIVE</code> lock except for the brief swap. Production discipline: <code>pg_repack</code> nightly on the top-10 most-bloated tables. <code>pgbouncer</code> in <code>transaction</code> mode multiplexes thousands of client connections onto a small pool of Postgres backends; it interacts with MVCC because <em>session-mode</em> SET commands (<code>SET TRANSACTION ISOLATION LEVEL REPEATABLE READ</code>) leak across clients in transaction mode — use <code>SET LOCAL</code>. The <code>idle_in_transaction_session_timeout</code> setting (default off; set to 5–15 minutes in production) kills sessions that have an open transaction without activity, preventing them from pinning xmin indefinitely. Many production incidents trace to an application that opens a transaction at request start and forgets to close it on an error path; <code>idle_in_transaction_session_timeout</code> is the safety net.</p>
    <p><strong>Distributed snapshots and global serializability.</strong> Single-node Postgres has a global snapshot per backend, computed in shared memory. When sharding across multiple Postgres instances (Citus, Postgres-XC ancestors, YugabyteDB), no single shared-memory snapshot exists. The standard approach is hybrid logical clocks (HLC): each instance maintains a logical timestamp that monotonically advances, transactions are tagged with HLC values at start, and visibility decisions on remote shards use HLC ordering. The trick is that HLC needs to be consistent with wall-clock ordering enough that humans can reason about "the transaction at 12:00:01" — TrueTime in Spanner is one solution; HLC in YugabyteDB is another. SSI across shards requires either a centralized predicate-lock table (slow) or a deterministic concurrency-control protocol (Calvin-style; FaunaDB; CockroachDB's hybrid) that linearizes at start instead of commit. Citus chooses pragmatism: distributed transactions default to read-committed-with-prepared-commit, and applications that need stronger isolation co-locate dependent rows on the same shard to keep them on the same backend.</p>

A transfer reads and modifies exactly two rows; there is no write-skew surface. SERIALIZABLE pays a steep predicate-lock cost for safety the transfer workload does not need. The compliance officer can be satisfied by an audit trail showing that every transfer holds <code>FOR UPDATE</code> on both rows for the entire transaction, that the ordering is documented and tested, and that integration tests assert no double-spend under concurrent load. SERIALIZABLE belongs on the audit-log writer, not on the hot transfer path.</p>,
        },
      ]}
    />
  </Fragment>
</TierAccordion>

<KeyTakeaway>MVCC trades a fixed storage tax (every UPDATE writes a new tuple, every snapshot pins old ones) for unblocked reads + writes. Isolation level decides which anomalies you tolerate; bloat discipline keeps the tax bounded.</KeyTakeaway>
