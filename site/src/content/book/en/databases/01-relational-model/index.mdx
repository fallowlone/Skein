This pillar is about PostgreSQL — the production-default relational database for most fullstack engineering in 2026 — but it opens with the model itself, not the implementation. Edgar Codd's 1970 paper *A Relational Model of Data for Large Shared Databanks* defined relations, tuples, and the operations on them; that model is what every relational database since (Oracle, DB2, SQL Server, Postgres, MySQL) implements with vendor-specific extensions. Knowing the model is what lets a senior engineer reason about any one of them. This piece names the building blocks (relations, attributes, domains), the constraints (primary key, foreign key, unique, not null, check), the discipline (normalization 1NF→BCNF and when to deliberately bend it), and the Postgres-specific tools (JSONB, arrays, UUID, generated columns) that change the cost model. Later pieces in this pillar build on this vocabulary: indexes (02), execution plans (03), MVCC (04 — already ready), pooling (05), migrations (06), sharding (07), and a capstone (08).

<Crux>Tables, keys, constraints, normalization — fifty-five years old, still load-bearing. Bend deliberately, not accidentally.</Crux>

The relational model is small in concept and large in payoff. A *relation* is a set of tuples sharing a fixed shape; a *table* is the implementation. Each tuple has the same attributes (columns), each attribute draws from a *domain* (a type), and each row is uniquely identified by some subset of its attributes (a candidate key). The database engine enforces this shape via constraints — declarative rules the engine checks before any insert, update, or delete. That declarative checking is the model's enduring win: instead of every application that touches the data re-implementing "must have a customer", "must reference a real product", "amount cannot be negative", you write it once at the table boundary and the engine refuses bad data on behalf of every caller. Application bugs become impossible to commit. The cost is the constraint check at write time and the discipline of designing the schema before you can write code. Senior engineers pay that cost knowingly; new teams either pay it accidentally (denormalize first, regret later) or skip it (treat the database as a key-value store and accumulate years of integrity debt). This piece is about why the first path is almost always cheaper across the lifetime of a system.

    <p><strong>One sentence.</strong> The relational model says: store data in tables of rows and columns, name keys that identify each row, declare relationships between tables with foreign keys, and let the database engine refuse data that breaks the rules.</p>
    <p><strong>Why care.</strong> Every application is a thin layer around its data; if the data is shaped wrong, every feature pays the cost. A good schema makes a hundred future features easy; a bad one makes every feature a fight.</p>
    <p><strong>The metaphor.</strong> A relational schema is a library catalogue. Each table is a drawer (books, authors, loans). Each row is a card with the same fields. A loan card has member-id and book-id pointing at other drawers (foreign keys). The librarian (the engine) refuses to file a loan card if the book-id does not exist, refuses two cards with the same primary key. The system stays coherent without humans re-checking.</p>
    <p><strong>Sven and Otto.</strong> <PersonaTag id="sven" lang="en" /> wants a "favourites" feature for a marketplace. <PersonaTag id="otto" lang="en" /> asks the shape question. Sven says "user has many favourites." Otto reaches for the model: users, items, favourites table with (user_id, item_id) as PK plus two FKs. Three DDL lines and the feature is structurally correct — no duplicates, no orphans, queryable both ways. A JSON-array shortcut breaks the moment you ask "who favourited this item."</p>
    <p><strong>One scenario.</strong> A team stores addresses as comma-separated text on the user row. Six months later marketing asks "how many users in Oregon?" — every text field must be parsed. A year later finance asks "sales by state" — same problem on every order. A relational design (addresses table with structured columns) is two extra schema lines and three orders of magnitude cheaper to query.</p>

    <p><strong>Codd's relational model.</strong> Edgar Codd's 1970 paper formalised relations as sets of tuples drawn from typed domains, and defined a closed algebra of operations (selection, projection, join, union, intersection, difference) — closed because each operation takes relations as input and produces a relation as output. SQL is a non-strict implementation of that algebra; it adds null (which Codd disliked), order (rows are conceptually unordered), and duplicate rows (relations conceptually have no duplicates). Knowing the gap matters because it explains the rough edges: NULL semantics in SQL (3-valued logic with `NULL = NULL` being NULL, not true), the ORDER BY requirement at the top-level (the engine is free to return any order without it), and the existence of `DISTINCT` (the engine must keep duplicates unless you ask). Treat the gap as "SQL = relational algebra plus practical compromises", and the surprises stop being surprising.</p>
    <p><strong>Constraints: the engine's declarative guarantees.</strong> A relational engine enforces five core constraint kinds. <em>PRIMARY KEY</em>: a non-null unique identifier for each row; one per table. <em>UNIQUE</em>: a non-primary-key uniqueness rule on one or more columns; supports null in standard SQL (multiple nulls allowed) — Postgres lets you opt into the SQL:2023 `UNIQUE NULLS NOT DISTINCT` clause. <em>NOT NULL</em>: a per-column rule that says "this column always has a value." <em>FOREIGN KEY</em>: a multi-column reference from one table to a primary or unique key on another (or the same) table, with ON DELETE / ON UPDATE clauses (NO ACTION, RESTRICT, CASCADE, SET NULL, SET DEFAULT) that decide what happens when the referenced row changes. <em>CHECK</em>: an arbitrary boolean expression evaluated on each row at write time; e.g., `CHECK (amount &gt;= 0)` or `CHECK (status IN ('open', 'closed', 'archived'))`. Together, these are how the schema encodes the business rules the engine refuses to break.</p>
    <p><strong>Normalization 1NF → BCNF, in plain terms.</strong> Normalization is a series of progressively stricter rules for splitting tables to eliminate redundancy. <em>1NF</em>: each cell is atomic (no comma-separated lists, no JSON-as-bag, no repeating groups). <em>2NF</em>: every non-key column depends on the whole primary key, not part of it (only matters for composite PKs). <em>3NF</em>: every non-key column depends only on the primary key, not on other non-key columns (no transitive dependencies). <em>BCNF</em> (Boyce-Codd): every determinant must be a candidate key — stricter than 3NF, handles edge cases where multiple overlapping candidate keys exist. Most production schemas target 3NF; BCNF matters when you have multiple candidate keys with overlapping attributes (rare in modern applications). The point of normalization is not "follow the rules" but "eliminate the kind of duplication that lets two facts disagree." If you can update Anna's email in three places, two will be out of date within a year.</p>
    <p><strong>Denormalization: when and why.</strong> Normalization optimises for write correctness; it can be expensive on the read side because answering a question requires joining many tables. Denormalization deliberately duplicates data to avoid joins on hot read paths. Typical patterns. (1) <em>Stored aggregates</em>: an `order_total` column on orders that caches `SUM(line_items.amount)` for fast reporting, refreshed on each line-item write. (2) <em>Wide read models</em>: a `user_profile` table that combines name, email, current address, latest order — fed by triggers or application code from the normalised tables. (3) <em>Materialised paths</em>: storing the full hierarchy of a tree node in one column to avoid recursive joins. The discipline: denormalize on the read side, keep the source of truth normalized, and accept that the duplicates must be reconciled by something (triggers, jobs, application code). The failure mode is denormalize-everywhere with no reconciliation — every column eventually disagrees with every other.</p>
    <p><strong>Surrogate vs natural keys: the production default.</strong> A <em>natural key</em> is data that already exists in the business domain (user email, product SKU, order number). A <em>surrogate key</em> is database-generated, opaque, and meaningful only inside the database (BIGSERIAL, UUID). Production default in 2026: surrogate key as the primary key, plus a UNIQUE NOT NULL constraint on the business-natural key. Why: natural keys change (a customer changes email), and PK changes cascade across every foreign key; surrogate keys never change. The exception: pure join tables (favourites: user_id, item_id) often use the composite of foreign keys as the PK — the relationship itself is the identity, no surrogate needed. UUID vs BIGSERIAL is the next question — UUIDs are globally unique (good for distributed inserts, multi-region, offline-first clients) but bigger (16 bytes vs 8) and worse for index locality (random UUIDv4 makes B-trees fragment); UUIDv7 (time-ordered, RFC 9562) fixes the locality issue and is the modern default for new schemas where UUID is wanted. BIGSERIAL is smaller, sequential, and cache-friendly — pick it when you do not need globally-unique IDs.</p>
    <p><strong>Postgres data types: pick the narrowest that fits.</strong> Postgres has the richest type system of any mainstream database. <em>Integers</em>: SMALLINT (2B), INTEGER (4B), BIGINT (8B). Pick the narrowest range that exceeds your domain by 100x — a user_id that will never exceed 10 million can be INTEGER (saves half the bytes per index entry). <em>Strings</em>: TEXT, VARCHAR(n), CHAR(n) — TEXT is the production default; VARCHAR(n) adds a check constraint at write time but no storage benefit; CHAR(n) is almost always wrong (pads to length, surprises with trailing spaces). <em>Numeric</em>: NUMERIC(p,s) for exact arithmetic (money), REAL/DOUBLE PRECISION for IEEE 754 (scientific, ML features). Never store money in REAL — floating-point arithmetic loses cents. <em>Timestamps</em>: TIMESTAMPTZ (with time zone) is the production default; TIMESTAMP (no zone) is a footgun; DATE for date-only data. <em>UUID</em>: native 16-byte type, never store as TEXT. <em>Booleans</em>: native BOOLEAN, never store as smallint or text. <em>JSON</em>: JSONB (binary, indexable) over JSON (text, not). <em>Arrays</em>: typed arrays (INTEGER[], TEXT[]) for small bounded lists that always live with the row. The discipline: the type is the first line of constraint. A column typed correctly catches 80% of bad data before any check constraint runs.</p>
    <p><strong>JSONB and arrays: the relational-shortcut pattern.</strong> JSONB stores arbitrary nested JSON as a parsed binary structure, indexable via GIN, queryable with operators (`-&gt;`, `-&gt;&gt;`, `@&gt;`, `?`). The right use case: data with no fixed schema or schema that varies per row (event payloads, third-party API responses, user-defined custom fields). The wrong use case: replacing what should be a related table because the schema is "still being figured out". The cost: every JSONB query is more expensive than a typed column query — GIN indexes are slower than B-trees, JSONB cannot be sorted efficiently, FK constraints cannot reference inside JSONB. Pattern: top-level columns for fields you query or constrain frequently, JSONB for the long tail of metadata. Arrays follow the same logic — they are great for "tags on a row" where you only query "show rows with tag X" (GIN-indexable) and never query "list all rows that have tag X with count" (that wants a join table).</p>
    <p><strong>Foreign keys at scale: the PlanetScale controversy.</strong> Some hyperscale shops (PlanetScale on Vitess, several large Postgres deployments) recommend disabling foreign keys for one or more of: ease of online schema changes (FKs make some DDL slower or locked-out), cross-shard impossibility (FKs cannot cross shard boundaries), risk of large cascades (a poorly-thought delete cascades millions of rows in one transaction), simpler replication. The trade: application-level integrity enforcement, asynchronous cleanup (soft-delete + reaper jobs), and explicit cross-table consistency in the code. For most teams under ~100M rows per table, the trade is wrong — the FK constraint is the cheapest correctness guarantee available. Above that scale, with sharding and zero-downtime migration constraints, the calculus changes. Senior engineers should know the trade-off exists and not assume disabling FKs is always premature; equally, not assume the hyperscale pattern is automatically applicable to a 10M-row schema.</p>
    <p><strong>Generated columns and computed integrity.</strong> Postgres supports STORED generated columns (`amount NUMERIC GENERATED ALWAYS AS (price * quantity) STORED`) — the value is computed on each write and stored, queryable like any other column, indexable. Use case: derived values you query frequently (full_name from first_name + last_name, total from per-row math). Combined with CHECK constraints, generated columns make the schema express more invariants. Trade: writes are slightly slower (the expression is evaluated); migrations on generated columns can rewrite the table. The pattern is underused — many teams reach for triggers to maintain derived columns when GENERATED is cleaner.</p>

  <Fragment slot="senior">
    <p><strong>Relational vs document / wide-column / graph alternatives.</strong> The relational model is one data model among several; senior engineers should know the trade-off space precisely. <em>Document stores</em> (MongoDB, Firestore) win when documents are accessed as units and never joined. <em>Wide-column stores</em> (Cassandra, ScyllaDB) win for very high-write workloads with predetermined query patterns. <em>Graph databases</em> (Neo4j, Dgraph) win when graph traversal is the dominant query. <em>Key-value stores</em> (Redis, DynamoDB) win for pure point lookups. The relational model wins when data has recurring structure, queries are ad-hoc, and referential integrity matters across types — most production B2B SaaS, fintech, ecommerce, ops tooling. Choose Postgres unless you have a specific reason; specific reasons exist at scale.</p>
    <p><strong>Postgres's row storage: the <Term k="heap" lang="en">heap</Term>.</strong> Postgres rows are stored in 8KB pages on disk, with the row layout being: 23-byte tuple header (including transaction visibility info — covered in piece 04 on MVCC), then null bitmap if any column is nullable, then column data in declaration order with type-specific alignment padding. Column width matters for storage and cache density: a row with 20 columns of mixed types might occupy 200-400 bytes; a table with 100M rows takes 20-40 GB of raw heap, more with indexes. The order of columns matters because of alignment padding — a column layout of [int4, int8, int4] takes 24 bytes with 4 bytes of alignment padding; reordered as [int8, int4, int4] it takes 16 bytes. For wide tables, column-order tuning can save 10-20% of storage. This is a real production lever; ORM-generated schemas rarely optimise for it.</p>
    <p><strong>TOAST: how Postgres handles wide values.</strong> Postgres pages are 8KB; rows that exceed ~2KB trigger TOAST (The Oversized-Attribute Storage Technique) — values are compressed and / or sliced into a side table, with a pointer in the main heap. TOAST is transparent — queries return the full value — but has performance implications: reading a TOASTed column requires an extra disk fetch; updating a TOASTed column rewrites the side-table chunks; over-indexing on a TOASTed column hurts because the index must reference the full value. Implication for schema design: very wide TEXT/JSONB/BYTEA columns are essentially separate storage — keep them out of hot-read columns lists, do not index them unless GIN (which understands JSONB structure), and consider explicit separation into a side table if the wide column is rarely accessed but the row is read frequently.</p>
    <p><strong>JSONB index strategies.</strong> JSONB has two index families. <em>GIN</em> (Generalized Inverted Index) indexes individual keys or paths inside the JSONB; default operator class indexes every key, alternative `jsonb_path_ops` indexes whole paths (faster lookups, larger index). GIN supports `@&gt;`, `?`, `?&|`, `?&&` operators. <em>Expression B-tree</em> indexes a specific JSONB path as a typed value: `CREATE INDEX ON events ((data-&gt;&gt;'event_type'))` — supports equality and range queries on that path, much smaller than GIN. The discipline: GIN for "find rows where the JSONB contains key X" or "matches path Y"; expression B-tree for "find rows where data.field equals value." Picking the wrong index makes JSONB queries 10-100x slower than needed. The piece 02 (indexes) covers index types in depth; here it matters that JSONB is not query-cheap without thoughtful indexing.</p>
    <p><strong>Constraints and immutability: enforcing temporal invariants.</strong> Postgres CHECK constraints are evaluated at write time and must be deterministic. They can reference other columns of the same row but not other rows (that requires foreign keys). For temporal invariants — "completed orders cannot transition back to pending", "audit-log rows are immutable" — the right tool is row-level security policies, triggers (BEFORE UPDATE that raises an exception on disallowed transitions), or application-level state machines combined with database constraints. Pure-SQL state-transition enforcement is verbose; many teams encode the state machine in a typed column with a CHECK and a trigger that enforces transitions. Generated columns with CHECK constraints can encode some derived invariants declaratively — e.g., a `is_final BOOLEAN GENERATED ALWAYS AS (status IN ('completed','cancelled')) STORED` plus a trigger that refuses UPDATE WHERE OLD.is_final.</p>
    <p><strong>Schema versioning and breaking changes.</strong> A relational schema is a contract between the database and every consumer. Adding a nullable column is non-breaking; adding a NOT NULL column without default breaks every existing insert; dropping a column breaks every reader; renaming a column breaks both. Senior teams manage schema as code (migration files in version control, executed by a tool like Flyway, Liquibase, sqlx-migrate, golang-migrate, Prisma Migrate) and apply expand-then-contract: expand the schema to add the new shape, deploy code that writes to both, deploy code that reads from new, drop the old. The migrations piece (06) covers this pattern in depth. Here the relevant point: schema decisions are sticky. Choosing the wrong type or the wrong key shape at design time means paying a multi-week migration to undo it later; choosing right at design time costs nothing extra. Senior engineers spend 10x more time on schema reviews than on code reviews of equivalent feature complexity — and it pays back.</p>
    <p><strong>Constraint deferral and complex transactions.</strong> Foreign keys can be declared DEFERRABLE INITIALLY DEFERRED, which delays the constraint check until COMMIT. The use case: complex multi-table updates where intermediate states would violate the constraint (e.g., circular references during a graph-update). The trade: deferred constraints are evaluated at commit time, which means a failed constraint causes a transaction abort with no in-flight indication. Production hygiene: use DEFERRABLE sparingly, only on FKs that are genuinely needed, and only in transactions where the temporary violation is well-understood. Most teams should keep constraints IMMEDIATE (the default) and structure updates so that intermediate states are consistent.</p>
    <p><strong>Real production failure modes.</strong> (a) <em>Implicit type coercion</em>: a query `WHERE user_id = '42'` (string instead of int) silently works in some setups but kills the index — Postgres has to convert every row's user_id to text. Mitigation: typed query builders, ORM type-safety, EXPLAIN ANALYZE on every new query. (b) <em>NULL semantics in joins</em>: a LEFT JOIN with a NULL on the FK silently drops rows in inner queries; senior pattern is to use IS DISTINCT FROM and explicit COALESCE for null-tolerant logic. (c) <em>Cascade cascade cascade</em>: a delete on a heavily-cascaded root row creates a multi-million-row transaction that holds locks for minutes; senior pattern is to soft-delete the root, batch-clean the descendants with explicit DELETE FROM ... WHERE ... LIMIT 10000 loops. (d) <em>Schema drift via ad-hoc ALTER</em>: a junior engineer runs ALTER TABLE in production directly; the migration tool no longer matches reality, future migrations fail mysteriously. Mitigation: every schema change goes through migrations, period. (e) <em>JSONB columns that grew into relational shape</em>: a "metadata" JSONB column accumulated 30 typed fields over two years; each new feature checks "if metadata-&gt;'feature_x' = ..." — at this point the right move is to extract the structured fields into proper columns, but the migration is expensive and gets postponed.</p>
    <p><strong>The pgsql vs MySQL design difference.</strong> Postgres and MySQL implement the relational model with different defaults. MySQL is more forgiving (silent string-to-int coercion, NULL behaviour in unique constraints, default storage engine differences across versions); Postgres is stricter (explicit types, strict NULL handling, single storage engine). Senior teams in 2026 default to Postgres for new schemas — the stricter defaults catch bugs earlier, the type system is richer (JSONB, arrays, ranges, custom types), the extension ecosystem is broader (PostGIS, TimescaleDB, pg_vector, pgcrypto). MySQL is the right choice when (a) you are deep in the MySQL ecosystem (Vitess, PlanetScale, AWS Aurora MySQL), (b) you have specific operational expertise on it, or (c) you need MyRocks-style write throughput. For greenfield work without those reasons, pick Postgres.</p>
    <p><strong>Naming conventions and operational maturity.</strong> The schema is the lingua franca of the engineering team and operations. Conventions that pay back. (a) Singular vs plural table names — pick one, never mix; the production default is plural (users, orders, order_items). (b) snake_case for everything (PostgreSQL folds identifiers to lower case unless quoted). (c) Primary key always named `id` (or `<table>_id` in join tables for clarity). (d) Foreign-key columns named `<referenced_table_singular>_id`. (e) Timestamps named `created_at`, `updated_at`, `deleted_at` (for soft delete). (f) Boolean columns prefixed with `is_`, `has_`, `can_` or named as a clear property (e.g., `active` is acceptable; `flag` is not). These look pedantic; they pay back across every dashboard, every migration script, every cross-team query. Mature platforms publish the schema-style guide and CI-lint the conventions.</p>
