Pooling (<a href="/en/databases/05-pooling/">05-pooling</a>) showed how transactions hold connections; this piece is about a special transaction that holds something far more disruptive — an AccessExclusiveLock on a hot table — and how senior teams deploy schema changes without taking the database down. The crux is the Postgres lock queue: when a DDL statement like `ALTER TABLE` cannot acquire its lock immediately because another transaction is holding even a tiny read lock, the DDL waits — and every subsequent query that touches the table queues behind the waiting DDL, regardless of what lock they need. One slow `SELECT` + one impatient `ALTER TABLE` = entire table frozen for the duration of the slow SELECT. The fix is not "wait for low-traffic hours" (downtime is rarely acceptable in 2026 production); it is `SET lock_timeout` + retries + expand-contract decomposition of every breaking change into a series of always-safe, always-reversible steps. The senior tools — pgroll, Atlas, Squawk, gh-ost-style online schema change — encode these patterns so individual engineers do not have to memorize them.

<Crux>ALTER TABLE takes AccessExclusiveLock. Lock queue is FIFO. SET lock_timeout. Expand-contract for breaking changes.</Crux>

A Postgres migration is a transaction that runs DDL (`CREATE TABLE`, `ALTER TABLE`, `CREATE INDEX`, `DROP COLUMN`, etc.). DDL operations take table-level locks per the Postgres lock matrix: most acquire `ACCESS EXCLUSIVE` (the strictest mode — conflicts with every other lock including `ACCESS SHARE`, which `SELECT` needs). The lock matrix is the design surface: every migration's safety story comes down to "which lock does this take, what does it conflict with, how long does it hold". Modern Postgres makes many operations dramatically safer than the textbook suggests — `ADD COLUMN ... DEFAULT 'x'` is instant since PG 11 (default stored in metadata, no table rewrite), `CREATE INDEX CONCURRENTLY` takes a light `SHARE UPDATE EXCLUSIVE` that does not block reads or writes, `ALTER TABLE ... ADD CONSTRAINT ... NOT VALID` followed by `VALIDATE CONSTRAINT` splits the work into two short transactions instead of one long one. The discipline is to know which form is safe and to use it; the failure mode is to write the textbook form, deploy at 14:00, and page the team at 14:01 when the lock queue backs up.

    <p><strong>One sentence.</strong> A migration is a versioned, ordered SQL script that changes the database schema — adding a column, creating a table, building an index — applied in lock-step with the application code that depends on it.</p>
    <p><strong>Why care.</strong> Every product change that needs to persist new data requires a schema change. Migrations are the artefact that turns "we want a new field" into "the database has the field, the app uses it, and rollback is possible" — auditable, reviewable, deployable like code.</p>
    <p><strong>The metaphor.</strong> A migration is a recipe step in a versioned cookbook. The cookbook has rules: each step is numbered (V1, V2, V3...), each step happens exactly once on each kitchen (database), and the cookbook records which steps have been applied. A new chef joining the kitchen runs the cookbook from where they left off; the kitchen ends in a known state. Without the cookbook, "what does the database look like" is a question nobody can answer; with it, the schema is reproducible from blank.</p>

  <Fragment slot="middle">
    <p><strong>The Postgres lock matrix is the design surface.</strong> Eight lock modes, from `ACCESS SHARE` (used by `SELECT`) to `ACCESS EXCLUSIVE` (used by most DDL). The matrix tells you what blocks what: `ACCESS EXCLUSIVE` conflicts with <em>everything</em> including `ACCESS SHARE`, so any DDL taking it blocks every reader and writer on the table for its duration. `SHARE UPDATE EXCLUSIVE` (used by `CREATE INDEX CONCURRENTLY`, `VACUUM`, `ANALYZE`, `VALIDATE CONSTRAINT`) conflicts only with itself and stricter modes — does not block normal DML. The senior intuition: before writing any migration, ask "which lock does this take" and "what is the typical duration"; if both answers are "AccessExclusive" and "more than 50ms", split the operation.</p>
    <p><strong>The lock queue: the actual failure mode.</strong> Postgres acquires locks first-come-first-served. When an `ALTER TABLE` waits for `ACCESS EXCLUSIVE`, it joins a queue behind whatever is holding a conflicting lock — often a slow `SELECT` running for 30 seconds. While the `ALTER TABLE` waits, every <em>new</em> `SELECT` that comes in also waits, because the `ALTER TABLE` is ahead of them in the queue and they need a lock that conflicts with `ACCESS EXCLUSIVE`. The result: one slow `SELECT` + one well-meaning `ALTER TABLE` = entire table inaccessible until the slow `SELECT` finishes. This is the canonical "I ran a migration and the site went down" incident. Mitigation: `SET lock_timeout = '2s'` on every migration session. If the lock cannot be acquired within 2 seconds, the migration aborts cleanly, leaving the queue intact. Retry policy: backoff + retry; pgroll and Atlas do this automatically.</p>
    <p><strong>Safe operations (lightweight or instant).</strong> <em>ADD COLUMN with constant default</em> (PG 11+): instant, default stored in pg_attribute.atthasmissing/attmissingval; no rewrite. <em>ADD COLUMN without default</em>: instant, NULL for existing rows. <em>SET/DROP DEFAULT</em>: only affects new INSERT/UPDATE; metadata-only. <em>DROP NOT NULL</em>: metadata-only. <em>RENAME COLUMN/TABLE</em>: metadata-only, but breaks dependent code. <em>ADD CONSTRAINT ... NOT VALID</em>: enforces for new rows only, no table scan. <em>VALIDATE CONSTRAINT</em>: scans table under `SHARE UPDATE EXCLUSIVE` (does not block DML). <em>CREATE INDEX CONCURRENTLY</em>: builds in two phases, `SHARE UPDATE EXCLUSIVE` lock; does not block reads/writes. All of these are production-default. The wrong forms have safe equivalents; the senior pattern is to know the mapping.</p>
    <p><strong>Unsafe operations and their fixes.</strong> <em>ADD COLUMN with volatile default</em> (e.g., `DEFAULT clock_timestamp()`): full rewrite under `ACCESS EXCLUSIVE`. Fix: ADD COLUMN without default, backfill in batches, then SET DEFAULT for new rows. <em>ALTER COLUMN TYPE</em> when types are not binary-coercible: full rewrite. Fix: add new column + dual-write + backfill + swap + drop. <em>ADD NOT NULL on a column with existing rows</em>: full scan under `ACCESS EXCLUSIVE`. Fix: ADD CHECK CONSTRAINT NOT VALID (... IS NOT NULL), VALIDATE CONSTRAINT (light lock), then ALTER COLUMN SET NOT NULL (which checks the constraint and is fast). <em>ADD FOREIGN KEY</em> normally requires `ACCESS EXCLUSIVE` and a scan. Fix: ADD CONSTRAINT ... NOT VALID + VALIDATE CONSTRAINT. <em>DROP COLUMN</em>: usually fast (marks dropped, lazy cleanup), but breaks code expecting the column. <em>RENAME COLUMN</em>: fast, but breaks code. Each unsafe operation has a multi-step safe pattern; the linter Squawk catches the unsafe forms automatically in CI.</p>
    <p><strong>Expand-contract is the universal pattern.</strong> Any breaking change decomposes into: (1) <em>Expand</em>: add the new column/table/index alongside the old. App code dual-writes to old and new. (2) <em>Backfill</em>: copy historical data from old to new in batches. (3) <em>Cut over</em>: app code reads from new. (4) <em>Contract</em>: stop writing to old; drop the old column/table. Each step is independently deployable and reversible. The pattern is verbose — a column rename becomes 5+ deploys over days — but it is the only way to make schema changes truly safe at production traffic. pgroll and Atlas automate the boilerplate; even hand-written migrations should follow the pattern.</p>
    <p><strong>CREATE INDEX CONCURRENTLY in detail.</strong> Builds an index without blocking reads or writes. Trade: takes 2-3× longer than non-concurrent, cannot run inside a transaction (so most migration tools need a special "non-transactional" annotation), and can fail mid-build leaving the index in an INVALID state (visible in pg_indexes with `indisvalid = false`). Failure modes: long-running transactions on the table delay the second phase; out-of-memory aborts the build. Senior runbook: always CREATE INDEX CONCURRENTLY in production; always verify `indisvalid = true` after the migration; if failed, DROP INDEX CONCURRENTLY (also non-blocking) and retry. Tools that wrap migration tools (Atlas, pgroll) handle this by detecting INVALID indexes and retrying.</p>
    <p><strong>lock_timeout and statement_timeout.</strong> Two GUCs that turn a runaway migration into a clean failure. `lock_timeout = '2s'` (per migration session): if the migration cannot acquire its lock within 2 seconds, abort. Combined with retries (exponential backoff), the migration eventually grabs the lock during a quiet moment between long-running queries. `statement_timeout = '30s'` (per migration session, set higher than typical migration time but bounded): if a migration's actual work (e.g., a backfill UPDATE) takes longer than 30s, abort. The two together turn "migration freezes the database" into "migration logs an error, gets retried later" — graceful degradation. Note: do NOT set these in postgresql.conf globally; set per-session via the migration tool. Most migration tools (golang-migrate, Flyway, Prisma, Drizzle, Atlas) have hooks for this.</p>
    <p><strong>The migration tool landscape in 2026.</strong> <em>golang-migrate</em>: simple, language-agnostic, "up.sql" + "down.sql" files, run via CLI. <em>Flyway</em>: Java ecosystem, mature, similar file model. <em>Liquibase</em>: XML/YAML-based, more declarative. <em>Prisma Migrate</em>: TS/Node, integrated with Prisma schema (single source of truth — schema.prisma generates migrations). <em>Drizzle</em>: TS, similar integrated approach. <em>Atlas</em> (Ariga): modern, declarative + imperative; lints migrations; understands Postgres semantics; runs migrations safely with lock_timeout, retries, and dry-run; growing in popularity. <em>pgroll</em>: zero-downtime via virtual schemas (views) + automatic backfilling + triggers for dual-write — the most aggressive safety wrapper. <em>Squawk</em>: linter that catches unsafe DDL in PR review (e.g., flags `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT`). 2026 senior stack: Prisma/Drizzle/Atlas for everyday migrations + Squawk in CI + pgroll or pattern discipline for the few truly breaking changes.</p>
    <p><strong>Migration coupling with deploys.</strong> The order of migration vs code deploy determines safety. <em>Additive change</em> (add column the new code reads): migrate first, then deploy code. New code finds the column ready. <em>Removal</em> (drop column the old code reads): deploy code first (which stops reading the column), wait for old code to fully drain, then migrate. <em>Rename</em>: cannot be done in one step. Expand: add new column. Deploy code: dual-write. Backfill: copy old to new. Deploy code: read from new. Wait. Contract: drop old. Five deploys, days apart. <em>The fundamental rule</em>: at every moment, both the current app code and the new app code must be runnable against the current database schema. Violating this rule is how "the schema migration broke the app" happens.</p>
    <p><strong>Hint: rollback is not "down migration".</strong> Down migrations (the inverse SQL of an up migration) sound safe but rarely work in production. If the up migration added a column and the new code wrote data to it, running the down (DROP COLUMN) destroys data. If the up migration was an instant ADD COLUMN, the down is fast but you have lost everything that wrote to it. Production rollback is forward: write a new migration that fixes the problem, deploy it, do not "rollback" the previous one. Treat down migrations as documentation for development environments, not as a production safety net.</p>

  <Fragment slot="senior">
    <p><strong>The Postgres DDL transaction semantics.</strong> Most DDL in Postgres is transactional: `BEGIN; CREATE TABLE; ALTER TABLE; COMMIT;` either all succeeds or all rolls back, and concurrent sessions see the change atomically at commit time (via the snapshot/<Term k="mvcc" lang="en">MVCC</Term> system). Exceptions: `CREATE INDEX CONCURRENTLY`, `REINDEX CONCURRENTLY`, `ALTER TYPE ... ADD VALUE` (until PG 12, then transactional), and a few others — these cannot run inside `BEGIN..COMMIT`. Migration tools wrap each migration in a transaction by default, which is the right policy: a multi-statement migration that fails halfway should leave the schema in the pre-migration state. The implication: any migration that includes a CONCURRENT operation must run that operation outside the transaction wrapper — most tools have a `-- atlas:txmode none` or `-- prisma:nontx` directive for this.</p>
    <p><strong>The <Term k="advisory_lock" lang="en">advisory lock</Term> pattern for serialised migrations.</strong> Multiple app servers booting simultaneously can each try to run pending migrations — without coordination, two processes might apply the same migration twice or compete on the schema_migrations table. The standard fix is a Postgres advisory lock at migration start: `SELECT pg_advisory_lock(<unique_int>);` — the first server gets the lock, runs migrations, releases; later servers wait. golang-migrate uses lock_id=internal hash of database name; Prisma uses a similar pattern. Senior teams verify the lock is held throughout the migration (not just at start) by inspecting pg_locks during a test migration. Also useful: pg_try_advisory_lock with a short retry loop for non-blocking startup behaviour.</p>
    <p><strong>Online schema-change tools and their place.</strong> <em>pgroll</em> (xata): maintains virtual schemas via views. A migration creates a new view alongside the old; old code reads the old view (with the original column shape), new code reads the new view (with new shape); both views back onto the same underlying physical table, with triggers handling shape translation. When the migration completes, the old view is dropped. Zero downtime; complex breaking changes (rename, drop-with-data-preservation, type-change) are declarative. <em>Atlas</em>: declarative + linter. Define the desired schema; Atlas computes the migration plan, lints it for unsafe patterns, runs it with lock_timeout + retries. Works without virtual schemas; relies on the application following expand-contract discipline. <em>gh-ost</em> (MySQL but pattern-similar for Postgres via dbatools, pg_squeeze, pg_repack): for the rare case of a true rewrite (ALTER COLUMN TYPE with incompatible types, table-clustering changes), use a shadow-table approach — create a new table, copy in batches with triggers replicating writes, swap atomically. Reserve for the few cases that cannot expand-contract.</p>
    <p><strong>ADD COLUMN with stored default: PG 11 implementation.</strong> Before PG 11, `ALTER TABLE ... ADD COLUMN ... DEFAULT 'x'` rewrote every row to materialise the default. In PG 11+, when the default is non-volatile, Postgres stores the default in `pg_attribute.atthasmissing = true` and `pg_attribute.attmissingval = 'x'`. Existing rows keep their old physical tuple (without the column); SELECT returns the missing default at read time; new rows store the column normally. The result: ADD COLUMN with default is instant on tables of any size. There is a small read-time cost (the missing-default path) that disappears as rows get rewritten by normal UPDATE traffic; production teams either leave it (the cost is negligible) or run a one-time UPDATE to materialise. The mechanism is one of the largest practical wins of modern Postgres — single-handedly eliminated the most common cause of migration incidents pre-2018.</p>
    <p><strong>Validating constraints under load.</strong> `ADD CONSTRAINT ... NOT VALID` is instant but only enforces for new rows; existing rows may violate. `VALIDATE CONSTRAINT` scans the table to verify all rows pass. The lock taken: `SHARE UPDATE EXCLUSIVE` — does not block normal DML (INSERT/UPDATE/DELETE/SELECT), but does block other DDL on the same table. Implication: validate while the application is running normally; the only impact is that other DDL queues. Senior pattern: schedule validation for off-peak windows when other DDL is unlikely; monitor the scan progress via `pg_stat_progress_analyze` or by checking the holding transaction's xact_start age. Long-running validate (e.g., on a 1B-row table over an hour) is fine if no other migration is queued behind it. Same applies to `CREATE INDEX CONCURRENTLY` — long-running but DML-safe.</p>
    <p><strong>ALTER COLUMN TYPE: the binary-coercible exception.</strong> Most type changes rewrite the table. Exceptions: type changes that are <em>binary-coercible</em> — the same physical representation. Examples: `varchar(50)` to `varchar(100)` (wider but same bytes), `varchar` to `text` (same), `text` to `varchar` (same), `numeric(10,2)` to `numeric(12,2)` (wider, same). Postgres detects these and skips the rewrite — fast, AccessExclusive briefly, no row writes. Non-coercible changes (int → bigint, text → int, json → jsonb pre-PG 14) require either full rewrite or shadow-column expand-contract. The pg_type catalog has the type coercibility rules; the migration tool Atlas knows these and warns when a change would rewrite. Senior pattern: for any ALTER TYPE that is not provably coercible, expand-contract.</p>
    <p><strong>The Squawk linter and CI integration.</strong> Squawk (Linux Foundation, formerly Stripe-internal) parses migration SQL and warns on unsafe patterns: ADD COLUMN with non-constant default, ALTER COLUMN TYPE without coercibility check, CREATE INDEX without CONCURRENTLY, dropping NOT NULL on FK, renames, drops without prior code deploy. Run in CI on every PR touching `migrations/`. Configurable to error vs warn per rule; teams typically error on the dangerous ones (rewrite-causing) and warn on the operational ones (rename, drop). Combine with Atlas for plan visualisation (`atlas migrate diff` shows exactly what will run, including the SQL Postgres will execute) and the team has visibility before merge instead of discovery after incident. CI cost: under 30 seconds per migration PR; the saved incidents are worth orders of magnitude more.</p>
    <p><strong>Partitioning and migration scope.</strong> Partitioned tables (declarative partitioning, PG 10+) change migration calculus. ADD COLUMN on a partitioned table cascades to all partitions in one statement — instant for constant defaults, expensive for rewrites. CREATE INDEX must be done per-partition (or CREATE INDEX ON ONLY parent + attach to each partition) — most migration tools handle this. ATTACH PARTITION and DETACH PARTITION are the operational primitives for partition rotation (drop old time partitions, add new). Important: ATTACH PARTITION acquires AccessExclusive briefly; with `lock_timeout` it is safe; in PG 14+ ATTACH PARTITION CONCURRENTLY relaxes the lock further. Senior teams treat partition operations as first-class migrations and use the migration tool's partition support; rolling your own typically misses corner cases.</p>
    <p><strong>Coordinating migrations with continuous deploy.</strong> The deploy machinery — Kubernetes rolling updates, blue/green, canary — interacts with migrations in non-trivial ways. (1) <em>Migration runs before pod rollout</em> (most common): a deploy starts; an init container or pre-deploy job runs `migrate up`; once successful, the new pods roll out. Drawback: old pods are still running and could see the new schema before they are updated; the schema must be backwards-compatible (expand-only). (2) <em>Migration runs as part of pod startup</em> (each pod tries; advisory lock serialises): simpler but slower (every new pod waits for migration check). Drawback: race conditions if not locked properly. (3) <em>Migration runs separately from deploy</em> (manual or via dedicated migration jobs): full control, easier to schedule, but humans must coordinate with code deploys. Senior pattern: separate the migration runner from the application pod lifecycle; run migrations from a dedicated CI job after code merge but before code deploy; gate code deploy on migration success. Atlas and pgroll provide gates designed for this.</p>
    <p><strong>Failure-mode taxonomy.</strong> (a) <em>Lock-queue freeze</em>: ALTER waits, queue backs up, table frozen. Fix: lock_timeout + retries. (b) <em>CREATE INDEX CONCURRENTLY left INVALID</em>: build failed (long transaction blocking phase 2, or OOM); pg_indexes shows indisvalid = false. Fix: DROP INDEX CONCURRENTLY + retry. Detection: monitoring on indisvalid post-migration. (c) <em>Migration deadlock</em>: two migrations or migration + traffic conflict on lock acquisition order. Fix: serialise migrations via advisory lock; do not run parallel migrations on related tables. (d) <em>Rollback that destroys data</em>: down migration drops a column that has new data. Fix: forward-only; do not rely on down migrations in production. (e) <em>Schema drift across replicas</em>: migration applied on primary but replication lag delays it on standbys; app code reads from standby and sees old schema. Fix: gate code deploys on replica lag = 0 (or near-zero); use the migration tool's replica-aware mode. (f) <em>Backfill UPDATE eats WAL</em>: a single huge UPDATE generates GBs of WAL, fills disk, replicas fall behind. Fix: batch UPDATEs in 1k-10k rows with sleeps between; monitor WAL generation rate. (g) <em>Volatile default rewrite hidden</em>: `DEFAULT now()` on ADD COLUMN looks safe but is volatile → rewrite. Fix: detect via Squawk; use a constant default + post-migration update. (h) <em>NOT NULL added without backfill</em>: column has NULLs; SET NOT NULL fails. Fix: backfill first; use the NOT VALID + VALIDATE pattern. (i) <em>RENAME during deploy</em>: old code references old name, fails between migration and pod rollout. Fix: expand-contract instead of single-step rename.</p>
    <p><strong>Strategic posture: migrations are first-class production artefacts.</strong> Mature teams treat migration code with the same rigor as app code: PR review, CI lint (Squawk + Atlas dry-run), staging deploy on production-size data, runbook entries, observability on runtime + lock acquisition. Cost: moderate. Benefit: dozens of safe schema changes per week instead of monthly maintenance windows. Senior teams ship breaking changes routinely; juniors avoid them.</p>
