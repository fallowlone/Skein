MVCC (<a href="/en/databases/04-mvcc-isolation/">04-mvcc-isolation</a>) showed that every transaction holds its own snapshot and that long transactions hold back vacuum; this piece is about how transactions also hold something more visible — a Postgres backend, a heavyweight OS process — and what teams build to amortise that cost across many application clients. Postgres uses a process-per-connection model: every connection forks a backend that consumes 5-10 MB of RSS, occupies a slot in shared memory, and counts against `max_connections` (default 100). At ~10 application servers × 50 client connections each, you have 500 backends fighting for the same 100 slots. The standard fix is a connection pooler — PgBouncer is the canonical one, with Supavisor, Odyssey, and PgCat as the modern alternatives — sitting between the app and Postgres, multiplexing thousands of client connections onto a much smaller pool of backend connections. The trade is that some session-level semantics (SET, LISTEN, session-level advisory locks, classic SQL-level PREPARE) stop working in transaction mode, which is the only mode worth using in production for typical OLTP. Senior teams design around these constraints; the failure mode is invisible until pool exhaustion takes down the dashboard at 3am.

<Crux>Postgres backends are heavy. Pool to multiplex. Transaction mode breaks SET / session prepares / advisory locks unless you adapt.</Crux>

A connection pool has two layers in modern stacks. The <em>client-side pool</em> (HikariCP for Java, node-postgres `Pool` for Node, asyncpg for Python, ActiveRecord's CP for Rails) lives inside the application process and caches a small number (5-20) of TCP connections per worker. The <em>server-side pooler</em> (PgBouncer, Supavisor, Odyssey, PgCat) is a separate process — usually colocated with Postgres or in front of it — that accepts thousands of client connections and routes them onto a small Postgres backend pool. The combination is what makes 10,000 application clients sustainable on a Postgres with 100 max_connections: each app worker has ~10 client connections to PgBouncer (cheap, ~2KB per slot on PgBouncer), PgBouncer in turn opens 20-50 real backends to Postgres. The middle layer turns connection cost from "expensive setup per query" into "free pool checkout". This piece teaches the modes, the math, and the failure modes — and shows why "raise max_connections" is almost always the wrong answer.

    <p><strong>One sentence.</strong> A connection pool is a cache of open TCP connections to Postgres that your application reuses instead of opening a new connection for every query.</p>
    <p><strong>Why care.</strong> Opening a Postgres connection is expensive: TCP handshake + TLS handshake + Postgres protocol startup + auth + setting up a server-side backend process. That is 5-50ms per new connection and ~10MB of memory per backend that the database has to allocate. Doing this for every web request makes the database your bottleneck. A pool amortises the cost: open once at startup, reuse for thousands of queries.</p>
    <p><strong>The metaphor.</strong> A taxi rank versus calling a new Uber for every block. The taxi rank (pool) has a few cars idling, ready to go; you walk up, take a cab, ride, return it. Total time per trip: the ride. Calling a new Uber per block: wait for the app to find a driver, wait for the driver to arrive, then ride. Most of the time is the dispatch. A connection pool is the taxi rank — a few connections held open and idle, ready to be checked out for the next query.</p>

    <p><strong>The three PgBouncer pooling modes.</strong> <em>Session mode</em>: a backend is leased to a client for the entire duration of the client's connection. Everything works — SET, LISTEN, session-level advisory locks, temp tables, classic SQL PREPARE — because the backend is genuinely the client's for the whole session. The downside is that PgBouncer does almost no multiplexing in this mode: client connections and backend connections are 1:1, just with PgBouncer doing auth and queueing. <em>Transaction mode</em>: a backend is leased to a client only for the duration of one transaction (BEGIN..COMMIT, or one autocommit statement). Between transactions the backend goes back into the pool and may be handed to a different client on the next BEGIN. This is the mode that enables real multiplexing — a 10,000-client app can run on 20-50 backends. The cost is that any session state (SET LOCAL is OK; SET is not; LISTEN does not work; session-level advisory locks lose their owner between transactions; temp tables persist incorrectly) is broken. <em>Statement mode</em>: backend handed back after every statement. Multi-statement transactions are forbidden. Used almost exclusively for PL/Proxy-style sharding; not a general-purpose mode.</p>
    <p><strong>The transaction-mode contract.</strong> Switching from session to transaction mode is the single highest-leverage performance change for a Postgres-backed service — and it requires the application to follow rules. (1) No SET outside of a transaction (use SET LOCAL inside, or set role-level defaults via ALTER ROLE). (2) No SQL-level PREPARE/DEALLOCATE (use protocol-level prepared statements via libpq's PQprepare or driver equivalents — PgBouncer 1.21+ supports these). (3) No LISTEN / NOTIFY across transactions (use a dedicated session-mode connection, or a separate notification service). (4) Session-level advisory locks (pg_advisory_lock) do not survive transaction boundaries — use transaction-level (pg_advisory_xact_lock) instead. (5) Temp tables created in one transaction may not be visible in the next — promote to real tables or use ON COMMIT DROP. The most common production bug is "we switched to transaction mode and now SET search_path doesn't work" — fix by setting `search_path` per-role via ALTER ROLE.</p>
    <p><strong>Postgres's process-per-connection cost.</strong> Each connection forks a backend process (~10 MB resident, ~1-2 MB private; shared_buffers and other shared memory are mapped, not duplicated). 1000 backends ≈ 1-2 GB of private memory plus the proc-table overhead in the kernel — manageable on big iron, painful on small instances. But the bigger cost is scheduling: more backends = more context switches, more lock manager contention on shared structures (procarray, lock table). Postgres performance degrades non-linearly past a few hundred concurrent active backends; throughput often peaks around `(CPU cores × 2) + effective_spindles` and drops past that point. The HikariCP-popularised pool-sizing formula is `connections = (core_count × 2) + effective_spindle_count` — where "effective_spindle_count" is roughly 0 for fully-cached datasets and equal to the number of independent disks otherwise. On a 16-core machine with all data in RAM, the optimal active-backend count is ~32, not 200.</p>
    <p><strong>Client pool sizing.</strong> Per-worker pool size depends on workload shape: how many DB calls per request, how long each, how concurrent the worker is. Rule of thumb: `worker_pool_size ≈ concurrent_requests × db_calls_per_request × avg_query_ms / request_budget_ms`. For a Node.js worker serving 100 concurrent requests, each doing 2 DB calls of 5ms each, with 50ms total request budget — pool needs ≈ 100 × 2 × 5 / 50 = 20 connections. With 10 workers, total client pool = 200. Without a server-side pooler, those 200 connections hit Postgres directly — fine for Postgres if `max_connections >= 250` (200 + headroom). With PgBouncer in transaction mode, those 200 client connections multiplex onto 20-40 real backends because most are idle most of the time.</p>
    <p><strong>Pool exhaustion and queueing.</strong> When all pool connections are checked out and a new query arrives, the pool either waits (with a timeout) or rejects (`PoolExhaustedError` or equivalent). Common causes: (1) long-running queries holding connections — usually a missing index or huge analytical query; (2) idle-in-transaction transactions — application opened a transaction but did not COMMIT/ROLLBACK because of a bug or network drop; (3) traffic burst — concurrent demand exceeds steady-state pool sizing; (4) downstream slowness — a third-party API in the same request keeps the connection checked out for seconds. Symptoms: P99 latency spikes; errors of type "connection pool timeout" or "too many connections"; queues backing up; in PgBouncer logs, `cl_waiting` counter rises. Diagnostic tools: pg_stat_activity (every backend, what it is doing), pg_stat_statements (top queries by total_time), PgBouncer's SHOW POOLS (active / waiting / idle per database).</p>
    <p><strong>Idle-in-transaction is the silent killer.</strong> A backend in state `idle in transaction` is holding a connection without doing useful work — but it is also holding row locks, an MVCC snapshot, and blocking VACUUM. In a pool, it is also holding the connection from being returned. One bug that opens a transaction and forgets to commit on an error path can drain a 20-connection pool in seconds. Mitigations. (1) `idle_in_transaction_session_timeout` (Postgres GUC, e.g., 60 seconds) — Postgres aborts and disconnects backends idle in transaction past this threshold. (2) Application code: transactions in a try/finally; ROLLBACK on any unhandled error; do not call external APIs inside a transaction. (3) PgBouncer's `server_idle_timeout` and `query_wait_timeout`. (4) Monitoring: alert on `pg_stat_activity` rows where state = 'idle in transaction' and xact_start older than ~10 seconds.</p>
    <p><strong>PgBouncer's transaction-mode prepared-statement gotcha (and the 2024 fix).</strong> Before PgBouncer 1.21 (released March 2024), protocol-level prepared statements (driver-managed `PrepareStatement`, `prepare:true`) and transaction mode were incompatible: a client prepared a statement on backend A, but the next EXECUTE landed on backend B which did not know that statement. The driver got "prepared statement does not exist" errors. The workaround was to disable prepared statements at the driver — losing 10-30% performance — or to use session mode. PgBouncer 1.21+ adds protocol-level prepared-statement tracking: `max_prepared_statements > 0` lets PgBouncer rewrite statement names, re-prepare on whichever backend a client lands on, and serve cached plans transparently. Postgres 17 (September 2024) added the matching server-side feature to deallocate prepared statements via the protocol, closing the last gap. As of 2026, transaction mode + prepared statements is the production default; check your PgBouncer is 1.21+ and `max_prepared_statements` is set (e.g., 1000) and you get both performance wins simultaneously.</p>
    <p><strong>The server-side pooler landscape in 2026.</strong> <em>PgBouncer</em> is still the workhorse: tiny memory (2KB per pooled connection), single-threaded, battle-tested, the de facto standard. Recent 1.21+ versions added prepared-statement support; 1.22+ added improvements to TLS and observability. <em>Supavisor</em> (by Supabase) is cloud-native, multi-tenant, Elixir-based, designed for serverless edge workloads — handles millions of inbound connections, multiplexes them onto Postgres. <em>Odyssey</em> (by Yandex/Tarantool team) is multi-threaded C, supports prepared statements natively, and shows the lowest CPU and highest throughput in benchmarks at 50+ concurrent clients. <em>PgCat</em> is Rust, adds load balancing across read replicas and query routing on top of pooling. The default in most stacks is still PgBouncer because it is well-understood; Supavisor or Odyssey when you outgrow PgBouncer's single-threadedness; PgCat when you need query routing and want a single component.</p>
    <p><strong>Connection lifecycle GUCs in PgBouncer.</strong> Key knobs: `pool_size` (per-database backend pool target, default 20), `default_pool_size` (fallback when not set per-DB), `max_client_conn` (total inbound client cap, default 100), `reserve_pool_size` (extra backends spun up under sustained load), `reserve_pool_timeout` (how long to wait before tapping the reserve, default 5s), `server_lifetime` (rotate backends every N seconds to limit memory bloat, default 3600), `server_idle_timeout` (close idle backends after N seconds, default 600), `query_wait_timeout` (reject queries waiting longer than this, default 120s), `server_reset_query` (DISCARD ALL between leases, mandatory for transaction mode safety in some setups). Senior tuning: `pool_size` = roughly active-DB-concurrency target (not 1:1 with app workers — leverage multiplexing); `max_client_conn` = generous (thousands ok); `server_reset_query = DISCARD ALL` if any state could leak; alerts on `cl_waiting` and `pool_exhausted` counters.</p>
    <p><strong>Hint: pooling is layered, not replaced.</strong> The right architecture is application client pool → PgBouncer → Postgres, not "one or the other". The client pool handles connection caching inside one process (free on hot paths, no socket setup); PgBouncer handles multiplexing across processes (turns 10,000 client connections into 20 backends). Removing the client pool means every query opens a fresh TCP connection to PgBouncer — fast (PgBouncer is local) but still TCP setup per query. Removing PgBouncer means client pools talk directly to Postgres — fine for small apps, fatal at scale.</p>

  <Fragment slot="senior">
    <p><strong>Postgres process model in detail.</strong> A Postgres connection is an OS process — `postgres backend` — forked by the postmaster when a client connects. Each backend has private memory (~5-10 MB resident, mostly per-query memory + caches + libpq buffers) and a slot in shared memory (proc array entry, lock table entry, snapshot metadata). Process startup costs ~5ms on the Postgres side plus auth and TLS on the network side. Why processes, not threads? History: Postgres predates good threading on most Unixes; the process model isolates crashes (one backend OOM does not corrupt others), simplifies memory management (private heap per backend), and inherits well from forking. The cost is high per-connection overhead — irreducible in vanilla Postgres. The internal-pooling pattern: many connections × small private memory + heavy shared memory + one process per backend. PgBouncer changes the application contract: instead of opening many Postgres connections, open a few backends and multiplex.</p>
    <p><strong>Why "raise max_connections" does not scale.</strong> Naive teams hit pool exhaustion and raise max_connections from 100 to 1000. What goes wrong. (1) Each backend reserves shared memory pre-allocated at startup — proc array, lock hash, predicate-lock structures — scaling roughly linearly with max_connections. 1000 backends ≈ several hundred MB of fixed shared memory just for the structures. (2) Context-switch overhead grows: at 1000 backends with active load, kernel scheduling time becomes a measurable fraction of CPU. (3) Lock-manager contention: shared memory structures (proc array iteration during snapshot acquisition, lock-table scans, MultiXact buffers) become bottlenecks; throughput per backend drops. (4) Connection-establishment latency increases as the postmaster fork queue grows. The Postgres community guidance for 25+ years: cap max_connections at a few hundred; multiplex above that with a pooler. The math: at (cores × 2) optimal active backends, 100 backends easily serves a properly-architected system; 1000 is almost certainly a pooling failure, not a Postgres scaling failure.</p>
    <p><strong>Transaction-mode + prepared statements: the 2024 breakthrough.</strong> Until 2024, the production trade-off was: transaction mode for multiplexing OR prepared statements for query plan reuse — not both. Drivers like JDBC, asyncpg, pgx prepared statements over the wire protocol (`PrepareStatement`/`PQprepare`), giving 10-30% throughput on repeated queries. But PgBouncer's transaction mode would route the next `EXECUTE` to a different backend that did not have the statement prepared, producing "prepared statement does not exist" errors. The historical workaround: disable prepared statements at the driver (e.g., `prepareThreshold=0` in JDBC) — sacrificing the plan-reuse win. <em>PgBouncer 1.21</em> (March 2024) introduced protocol-level prepared statement tracking: PgBouncer parses the Parse/Bind/Execute protocol messages, maintains a global registry of prepared statements per logical client, and re-prepares on whatever backend it lands on next. <em>PostgreSQL 17</em> (September 2024) added the matching server-side support for protocol-level DEALLOCATE, allowing clean closure of prepared statements when clients disconnect — closing the last resource-leak hole. As of 2026, the production stack is PgBouncer ≥ 1.21 + Postgres ≥ 14 (≥ 17 ideal) + driver-managed prepared statements + transaction mode — all three wins simultaneously. Config: `max_prepared_statements = 1000` in pgbouncer.ini; verify with `SHOW STATS` for `query_count` and via driver telemetry.</p>
    <p><strong>The 2026 pooler landscape and when to choose each.</strong> <em>PgBouncer</em>: single-threaded C, ultra-low overhead (~2KB per pooled conn), the de facto standard. Use when you need a battle-tested, tiny, single-purpose pooler colocated with Postgres. Limitation: single-threaded means one CPU core ceiling on PgBouncer throughput; for >100k QPS through a single PgBouncer, you need multiple PgBouncers behind HAProxy or similar. <em>Odyssey</em>: multi-threaded C by Yandex/Tarantool team; supports native prepared statements (earlier than PgBouncer); higher throughput at high concurrency. Use when one node and >100k QPS through a single pooler; downside is younger codebase, smaller community. <em>PgCat</em>: Rust, multi-threaded, adds query routing (read replicas, sharding); useful when you want one component to handle pool + routing + load balance. <em>Supavisor</em>: Erlang/Elixir, cloud-native, designed for millions of inbound connections from serverless and edge environments; the Supabase-managed answer. Use in serverless / edge / multi-tenant SaaS where inbound connection storms are the design constraint. <em>pgpool-II</em>: traditional choice for HA + read load balancing on top of pooling; heavier, more features, more complex; viable but less popular than PgBouncer in greenfield. The default in 2026 is still PgBouncer + a separate load balancer; reach for the others when their specific feature wins justify their operational cost.</p>
    <p><strong>Client-side pool internals.</strong> HikariCP (Java) uses a lock-free FastList for connection acquisition, async housekeeping for idle/leak detection, and integrates with JDBC's connection-validation protocols. node-postgres `Pool` wraps a `Client` instance per connection and a queue for waiting checkouts. asyncpg (Python) uses asyncio primitives for waiting. The common contract: `acquire` blocks (or rejects) when at max; `release` returns to the idle list; periodic background tasks close idle-past-timeout connections and validate broken ones. Common bugs. (1) Forgetting to release on error paths — use language-level guarantees (try/finally, defer, RAII, `using`). (2) Holding a connection across an async wait — node.js `await` in middle of a checkout. (3) Validation queries adding latency on every checkout — disable if your network and Postgres are reliable, enable only if you have observed dropped idle connections (NAT-rebinding firewalls, ELBs with idle-timeout). (4) Pool exhaustion masking as a "slow API" — instrument checkout-wait-time as a separate metric from query-time.</p>
    <p><strong>Connection storms in serverless and edge.</strong> Serverless platforms (Lambda, Vercel Functions, Cloudflare Workers) instantiate hundreds-thousands of cold workers under load, each wanting a Postgres connection. Even with client-side pools, each cold start opens a new connection — connection-storm. The mitigation patterns. (1) Always front Postgres with a pooler — Lambda's `RDS Proxy`, Supavisor in front of Supabase Postgres, PgBouncer on a beefy node in front of self-hosted. (2) For Cloudflare Workers / edge: HTTP-based protocols like Neon's serverless driver / Postgres-over-HTTP — each query is a stateless HTTP request to a pooler, no persistent connections from edge to origin. (3) Cold-path optimisation: pre-warm pools at deployment time if possible; aggressive idle-timeout to free resources between bursts. (4) For very high cardinality multi-tenant: Supavisor or Cloudflare Hyperdrive (or commercial offerings) handle inbound concurrency in the millions via Erlang/Elixir-style lightweight processes. The architectural lesson: persistent-connection pools assume long-lived clients; serverless violates that — design for stateless query dispatch.</p>
    <p><strong>Postgres GUCs that interact with pooling.</strong> `max_connections` (hard cap); `superuser_reserved_connections` and `reserved_connections` (kept aside, reducing effective cap); `idle_in_transaction_session_timeout` (server-side kill switch for stuck transactions, set to 60s as a safety net); `statement_timeout` (per-query upper bound, kill runaway queries); `lock_timeout` (DDL safety); `tcp_keepalives_idle`/`tcp_keepalives_interval`/`tcp_keepalives_count` (detect dead connections — important with PgBouncer in front, where NAT or stateful firewalls can silently drop idle TCP); `client_connection_check_interval` (Postgres 14+; detect dead client without TCP layer); `default_transaction_isolation`. Senior tuning: set all of these explicitly in postgresql.conf, not just defaults; document each with rationale.</p>
    <p><strong>Failure-mode taxonomy.</strong> (a) <em>Pool exhaustion from long queries</em>: a missing index makes a query take 5s; under 1000 QPS that is 5000 in-flight queries, far over any pool. Fix: index the query, or shorten the work via pagination. (b) <em>Idle-in-transaction stuck backends</em>: an unhandled exception left BEGIN open; the backend sits 'idle in transaction' forever. Fix: idle_in_transaction_session_timeout = 60s; code review for missing try/finally COMMIT/ROLLBACK. (c) <em>External-API-inside-transaction</em>: BEGIN → external HTTP call → COMMIT — the transaction is open for the duration of the API call. Fix: move the call outside the transaction; commit before, then call; or use the outbox pattern for write-then-event. (d) <em>NAT/firewall idle-drop without TCP keepalive</em>: backend appears idle to PgBouncer but the actual TCP is dead; new queries get RST or timeout. Fix: tcp_keepalives in postgresql.conf + PgBouncer; reduce client_connection_check_interval (PG14+). (e) <em>Prepared-statement collisions before PgBouncer 1.21</em>: legacy code with prepared statements + transaction mode = "prepared statement does not exist" errors at random. Fix: upgrade to PgBouncer ≥ 1.21 + max_prepared_statements > 0. (f) <em>DISCARD ALL not firing in transaction mode for state leaks</em>: a SET that should have been SET LOCAL leaks to the next client on the same backend. Fix: server_reset_query = DISCARD ALL in pgbouncer.ini (forces a reset between client leases). (g) <em>Pool sizing wrong for spike vs steady-state</em>: pool sized for steady-state, spikes back up. Fix: reserve_pool_size in PgBouncer; autoscaling at the application layer; queue-and-degrade pattern (return 503 with Retry-After before exhaustion). (h) <em>PgBouncer single-threaded CPU bottleneck</em>: at very high QPS one PgBouncer pegs a core. Fix: horizontal-scale PgBouncer behind HAProxy/keepalived; or migrate to Odyssey/PgCat.</p>
    <p><strong>Strategic posture: pooling is part of the schema.</strong> Senior teams treat the pooler config as a first-class component of the data-tier architecture, versioned with the schema and deployed via infrastructure-as-code. The PgBouncer config, the Postgres GUCs (max_connections, idle_in_transaction_session_timeout, statement_timeout), the application client-pool config, and the observability (alerts on cl_waiting, idle-in-transaction backends, max_connections used) are all owned together. Every PR that changes query patterns is reviewed for hold-time impact ("does this open a transaction around a slow operation?"). Every load test exercises 2× target traffic for ≥30 minutes to confirm steady-state pool behaviour. Every deploy includes a post-deploy `SHOW POOLS` snapshot and `pg_stat_activity` summary. The cost is small (an SRE-style runbook + a few alerts); the benefit is no 3am pages from a service the team thought was fine.</p>
