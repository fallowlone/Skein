Indexes (<a href="/en/databases/02-indexes/">02-indexes</a>) gave you sorted copies of data; this piece is about the engine that decides whether to use them. Postgres's planner reads your SQL, asks pg_statistic how many rows each condition will produce, enumerates the possible scan + join combinations, and picks the cheapest one by an internal cost formula. The plan that comes out is a guess — a tree of operators with row estimates attached. When the estimates match reality, the chosen plan is usually optimal. When the estimates are wrong by 1000×, the planner picks a Nested Loop on what it thinks is 10 rows, hits 10 million rows, and turns a 50ms query into an 8-minute query. The single most valuable senior skill in production Postgres is reading EXPLAIN ANALYZE — comparing the planner's prediction to actual execution — and knowing whether to fix the statistics, fix the index, or fix the query.

<Crux>EXPLAIN shows the plan. The plan is a guess from statistics. Rows estimated vs actual is the most diagnostic number in the database.</Crux>

A Postgres query goes through four stages: <em>parse</em> (text → parse tree), <em>rewrite</em> (apply views, rules), <em>plan</em> (build the cheapest execution tree), <em>execute</em> (run it). The planner is the only stage you tune. It chooses among scan types (Seq Scan, Index Scan, Bitmap Heap Scan, Index Only Scan), join algorithms (Nested Loop, Hash Join, Merge Join), and aggregation strategies, costing each option using table statistics and the per-operation cost constants (`seq_page_cost`, `random_page_cost`, `cpu_tuple_cost`, etc.). The cost is in arbitrary units roughly proportional to time on default hardware — not milliseconds, not bytes. EXPLAIN prints the chosen plan; EXPLAIN ANALYZE actually runs the query and shows real timings alongside the estimates. The gap between the two is the diagnostic surface for every performance question in Postgres.

    <p><strong>One sentence.</strong> An execution plan is the tree of operations Postgres has decided to run for your query, and EXPLAIN prints it so you can see whether the database is doing what you expect.</p>
    <p><strong>Why care.</strong> Without reading plans, you optimise by guesswork — "let me add an index and hope". With plans, you can prove a query is doing a Seq Scan, prove an index is being ignored, and prove a fix worked. Every senior Postgres performance fix starts with EXPLAIN ANALYZE.</p>
    <p><strong>The metaphor.</strong> EXPLAIN is the GPS route preview before you drive. EXPLAIN ANALYZE is the dashcam from the actual trip. The preview says "this route is 12 minutes" — that is an estimate from the map data. The dashcam says "the trip took 47 minutes because we hit traffic the map did not know about". The gap between estimate and reality is exactly where you intervene: bad map data (stale statistics) gives bad route choices; bad sensors (no index for this turn) make the trip slower than the route promised.</p>

  <Fragment slot="middle">
    <p><strong>Reading the cost line.</strong> Every plan node prints `(cost=startup..total rows=N width=B)`. `startup` is the cost paid before the first row can be emitted (zero for a Seq Scan, non-zero for a Sort that must read everything before emitting). `total` is the cost to run the node to completion. `rows` is the planner's estimate of how many rows this node will emit. `width` is the average row width in bytes. Cost is in arbitrary units where 1.0 ≈ a sequential page fetch on the planner's default hardware model; only ratios matter. With ANALYZE, every node also prints `(actual time=startup..total rows=N loops=L)` — real wall time in milliseconds, real row count, real number of times the node was executed. The interpretation rule: if the node is inside a Nested Loop's inner side, divide actual time by loops to get per-execution cost.</p>
    <p><strong>Scan types.</strong> <em>Seq Scan</em> reads the whole heap; cost is `relpages × seq_page_cost + reltuples × cpu_tuple_cost`. Optimal when the predicate matches a large fraction of rows or when no index helps. <em>Index Scan</em> walks the index to find matching TIDs, then fetches each row from the heap; cost grows with `random_page_cost × matching_rows`. Optimal when few rows match and they are not clustered. <em>Bitmap Heap Scan</em> + <em>Bitmap Index Scan</em>: build a bitmap of TIDs from one or more indexes, sort by physical location, then scan heap in order — turns random I/O into sequential I/O. Optimal when many rows match (hundreds to millions) and they are scattered across the heap. <em>Index Only Scan</em>: read only the index, no heap fetch, when all needed columns are in the index AND the visibility map says the page is all-visible. Fastest scan type when applicable.</p>
    <p><strong>Join algorithms.</strong> <em>Nested Loop</em>: for each row of the outer relation, look up matching rows in the inner relation (typically via index). Cost is `outer_rows × inner_cost`. Wins when outer is small (10s of rows) and inner has a usable index. Dangerous when the outer is misestimated as small and is actually huge — the loop blows up. <em>Hash Join</em>: build a hash table from the smaller side (the "build" side), then probe with rows from the larger side. Cost is `build_cost + probe_cost + hash_table_size / work_mem` (spills if larger than work_mem). Wins for medium-to-large equi-joins where neither side has the right index. <em>Merge Join</em>: sort both sides on the join key (or use indexes that already provide sort order), then merge in parallel. Wins when both sides are already sorted (matching index) or when sorts can spill efficiently. Default planner picks based on cost; you can disable a join type with `SET enable_hashjoin = off` (etc.) for diagnostic comparison.</p>
    <p><strong>The pg_statistic catalog.</strong> When you run ANALYZE, Postgres samples the table (default: 300 × default_statistics_target rows = 30,000 with the default 100) and computes per-column statistics: `n_distinct` (number of distinct values, or a negative fraction if it scales with table size), `most_common_vals` + `most_common_freqs` (the MCV list, up to default_statistics_target entries), `histogram_bounds` (an equi-frequency histogram of non-MCV values), `correlation` (statistical correlation between physical and logical ordering, used to estimate index scan random-vs-sequential cost). The planner combines these to estimate selectivities: "how many rows match `WHERE x = 42`" is answered from the MCV list if 42 is an MCV, otherwise interpolated from the histogram. Read the catalog yourself: `SELECT * FROM pg_stats WHERE tablename = 'orders';`</p>
    <p><strong>ANALYZE: when to run, when autovacuum runs it.</strong> Autovacuum schedules ANALYZE per table based on `autovacuum_analyze_threshold` (default 50 rows) + `autovacuum_analyze_scale_factor × reltuples` (default 0.1 → 10% of the table). On a 100M-row table, autovacuum analyzes only after 10M changes — too infrequent for skewed or fast-changing data. Operational fix: lower the scale factor for hot tables: `ALTER TABLE orders SET (autovacuum_analyze_scale_factor = 0.02)`. Manual ANALYZE is fast (seconds on a 100M-row table) and acceptable to run after bulk inserts, large UPDATEs, or schema changes. The single most common "the query suddenly got slow" cause is stale statistics — and the single most underused fix is increasing default_statistics_target on a column with skewed distribution (`ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000; ANALYZE orders;`).</p>
    <p><strong>BUFFERS and the I/O picture.</strong> `EXPLAIN (ANALYZE, BUFFERS)` adds buffer accounting per node: `shared hit` (page found in Postgres's shared_buffers cache), `read` (page fetched from OS/disk), `dirtied` (page modified), `written` (page flushed). On a warm system most pages should be hits; many reads mean the working set is larger than shared_buffers or the query is touching cold data. BUFFERS is the diagnostic for "is this slow because of CPU or I/O" — high buffer reads = I/O-bound, low buffer counts but high actual time = CPU-bound (often a poor join or sort).</p>
    <p><strong>EXPLAIN options.</strong> `FORMAT JSON | XML | YAML | TEXT` — JSON is the format for tooling (depesz's explain.depesz.com, dalibo's explain.dalibo.com, pganalyze auto-EXPLAIN). `VERBOSE` adds output column lists per node. `SETTINGS` (PG 12+) prints non-default planner GUCs. `WAL` (PG 13+) shows WAL bytes generated. `GENERIC_PLAN` (PG 16+) plans a parameterised query without sample values — useful for prepared-statement diagnostics. `SERIALIZE` (PG 17+) includes the cost of serialising rows for the client — closes the gap between EXPLAIN ANALYZE total time and what the client actually sees.</p>
    <p><strong>auto_explain and pg_stat_statements.</strong> Two extensions every production Postgres should have. <em>pg_stat_statements</em> records every executed query (normalised by parameter), tracking calls, total_time, mean_time, rows, buffer counts. The top queries by `total_time` are the optimisation targets. <em>auto_explain</em> automatically logs EXPLAIN ANALYZE for any query exceeding a duration threshold: `SET auto_explain.log_min_duration = '500ms'; SET auto_explain.log_analyze = true;` — slow queries land in the log with full plans, no need to reproduce them manually. Together they answer "which queries are slow, and why" without instrumenting the application.</p>
    <p><strong>Row-estimate errors and the cascade.</strong> The planner's biggest failure mode is misestimating intermediate row counts. A WHERE clause that the planner thinks matches 10 rows but actually matches 10,000 is a 1000× error at that node — but the error cascades into the next decision. With 10 rows on the outer side, the planner picks Nested Loop (cheap when outer is small). With 10,000 rows actually flowing into the loop, the inner side runs 10,000 times instead of 10 — 1000× more work. A query that should be a Hash Join in 50ms becomes a Nested Loop in 8 minutes. The root cause is not the join choice; it is the row estimate. Fix the estimate (ANALYZE, multivariate stats, expression index, query rewrite) and the join choice fixes itself.</p>
    <p><strong>Non-sargable predicates.</strong> A predicate is "sargable" (Search ARGument-ABLE) if the planner can use an index for it. `WHERE created_at &gt;= '2026-01-01'` is sargable; `WHERE date(created_at) = '2026-01-01'` is not — the function on the indexed column forces a Seq Scan. Common offenders: `WHERE LOWER(email) = 'alice@x.com'` (cast on indexed column), `WHERE id::text = '42'` (type coercion), `WHERE EXTRACT(year FROM created_at) = 2026` (function call), leading-wildcard LIKE (`'%foo'`), `OR` across columns the planner cannot index together. Fixes: expression indexes (`CREATE INDEX ON users (LOWER(email))`), query rewrites (range predicates instead of function calls), trigram indexes (pg_trgm for fuzzy match). EXPLAIN reveals these immediately as Seq Scan + Filter where you expected Index Scan.</p>
    <p><strong>Hint: the planner's choice is reproducible.</strong> Same data + same statistics + same GUCs = same plan. If a query is slow in production but fast in staging, one of those three differs. Most often: different table size + different statistics. Less often: different GUC (work_mem, random_page_cost) set per-environment. Rarely: different Postgres version or extension. The diagnostic is to capture EXPLAIN (no ANALYZE) on both, and diff the plans; identical plans mean the issue is execution-time (data, locks); different plans mean the issue is planning-time (stats, GUCs).</p>

  <Fragment slot="senior">
    <p><strong>The planner's internal structure.</strong> Postgres's planner is a cost-based optimiser. For each query it builds <em>paths</em> — lightweight, partial plans for portions of the query (single-table scans, joins of small relation sets). Paths are compared by cost; only the cheapest path per "relation set + sort order" is kept (the rest are pruned). For multi-relation joins, it considers all combinations using dynamic programming — exhaustively up to <Term k="geqo_threshold" lang="en">`geqo_threshold`</Term> (default 12) relations, after which it switches to the <Term k="genetic_query_optimizer" lang="en">Genetic Query Optimizer</Term> (heuristic search). The final cheapest path is converted to a full plan tree (Plan nodes: SeqScan, IndexScan, HashJoin, etc.). The path representation is a senior debugging mental model: when you see a surprising plan, ask "what other paths did the planner consider, and why were they pruned" — often the answer is row-estimate-driven cost difference. `EXPLAIN (VERBOSE)` and pg_hint_plan (extension) reveal alternatives.</p>
    <p><strong>Cost constants and SSD tuning.</strong> Postgres ships with `random_page_cost = 4.0` and `seq_page_cost = 1.0` — values calibrated for spinning HDDs where random reads are 4× slower than sequential. On NVMe SSDs the ratio is much smaller (1.5-2×); on cached-in-RAM hot workloads it is effectively 1.0. Senior production tuning: set `random_page_cost = 1.1` on SSD-backed systems with normal cache behaviour; set `random_page_cost = 1.0` and reduce `seq_page_cost` proportionally (e.g., 0.1, 0.1 with `cpu_tuple_cost = 0.01`) if the working set fits entirely in <Term k="shared_buffers" lang="en">shared_buffers</Term>. The effect: the planner becomes more willing to use Index Scan and Index Only Scan vs Seq Scan, which is the right bias for modern hardware. Set `effective_cache_size` to ~75% of total RAM (or the OS file-cache size) so the planner accounts for cached pages in its cost estimates. Mis-tuning here is one of the most common silent production sins: a database running on M2 NVMe with default HDD-era costs underuses its indexes.</p>
    <p><strong>Generic vs custom plans.</strong> Prepared statements (every parameterised query from a driver, every PL/pgSQL function with parameters) go through plan caching. The first 5 executions are planned per-parameter (custom plans, best for skewed parameter distributions); from execution 6 onwards, Postgres computes the average custom-plan cost and compares it to a hypothetical <Term k="generic_plan" lang="en">generic plan</Term> (parameter-agnostic). If the generic plan cost is within ~10% of the average custom cost, Postgres switches permanently to the generic plan for the lifetime of the prepared statement. The switch is invisible to the application but can be catastrophic: a generic plan optimised for a "typical" parameter is the wrong plan for outlier parameters. Symptoms: prepared statement that was fast suddenly slow after a while; same query as ad-hoc SQL still fast. Diagnosis: `EXPLAIN (GENERIC_PLAN)` (PG 16+) on the prepared statement; if the generic plan is bad, set `plan_cache_mode = 'force_custom_plan'` per role or per session — every execution is replanned but always picks the right plan. Cost: planning time per execution (~0.5-2ms typical). Worth it when execution-time variance is high.</p>
    <p><strong>Parameter sniffing in Postgres vs SQL Server.</strong> SQL Server compiles the plan on first execution using that parameter's value, then caches and reuses it — "parameter sniffing" — which can produce a plan optimised for an outlier first parameter. Postgres's hybrid (5 custom + comparison + maybe-generic) avoids the worst of this by averaging across parameters, but introduces its own pitfall (the average can mask outliers). Production discipline in Postgres: monitor pg_stat_statements for prepared statements with high variance in `stddev_exec_time`; investigate with EXPLAIN (GENERIC_PLAN) and EXPLAIN (ANALYZE) on representative parameters; consider plan_cache_mode = force_custom_plan for problem cases. The general lesson: every plan-caching strategy has failure modes; the engineering question is which failure mode you can detect and fix.</p>
    <p><strong>Extended statistics: dependencies, ndistinct, mcv.</strong> CREATE STATISTICS supports three kinds. <Term k="dependencies" lang="en">dependencies</Term> tracks functional dependencies (A determines B with probability p); useful when one column's value implies another's (zip → city, country → region, product_id → category). <Term k="ndistinct" lang="en">ndistinct</Term> tracks the number of distinct combinations for multi-column GROUP BY estimation (without this, the planner multiplies per-column n_distinct values and overestimates). <Term k="mcv" lang="en">mcv</Term> stores multi-column most-common-value combinations directly — analogous to the per-column MCV list but for tuples. Default is "all three kinds"; specify subset if you only need one. CREATE STATISTICS requires ANALYZE to populate. Senior pattern: identify the top-10 multi-column predicates from pg_stat_statements + EXPLAIN, create one statistics object per correlated pair or triple. Storage cost is small (kilobytes per statistics object); planning improvement on the affected queries can be 100-1000×. Available since PG 10 (dependencies, ndistinct); PG 12+ added mcv; PG 14+ added expression statistics (statistics on `(col + col)` or `LOWER(col)` style expressions).</p>
    <p><strong>JIT compilation.</strong> Postgres 11+ supports <Term k="jit_compilation" lang="en">JIT compilation</Term> of expression evaluation (filter expressions, projections, aggregation paths). When a plan's total cost exceeds `jit_above_cost` (default 100,000), JIT activates; `jit_inline_above_cost` (default 500,000) inlines function calls; `jit_optimize_above_cost` (default 500,000) applies LLVM optimisations. JIT helps CPU-bound queries on big scans (millions of rows with complex predicates) by 10-30%; for short OLTP queries it adds overhead (compilation time exceeds saved execution time). Diagnose with `EXPLAIN (ANALYZE, JIT)` which shows JIT timings per phase. Tune: raise the thresholds (or set `jit = off`) for short-query OLTP workloads; lower them on analytic workloads. The default thresholds are conservative; tune empirically per workload.</p>
    <p><strong>GEQO and large joins.</strong> The <Term k="genetic_query_optimizer" lang="en">Genetic Query Optimizer</Term> activates when the number of relations in a join exceeds `geqo_threshold` (default 12). Below the threshold, the planner uses exhaustive dynamic programming to find the optimal join order. Above, GEQO uses heuristic search — fast but not guaranteed optimal. For queries with 15-30 joined tables (analytic queries, reporting), GEQO can produce sub-optimal plans inconsistently (the heuristic is randomised — same query, different plan run-to-run). Workarounds: set `geqo = off` (forces exhaustive search even on large joins — slower planning but stable plans); set <Term k="from_collapse_limit" lang="en">`from_collapse_limit`</Term> and <Term k="join_collapse_limit" lang="en">`join_collapse_limit`</Term> lower (default 8) to prevent the planner from reordering joins, locking in the explicit JOIN order. The latter is the senior trick for stabilising plans on analytic queries: `SET join_collapse_limit = 1; SET from_collapse_limit = 1;` makes Postgres respect your explicit join order — useful when you have hand-tuned a query and want it to stay tuned.</p>
    <p><strong>auto_explain in production.</strong> Configure: `shared_preload_libraries = 'auto_explain'`; `auto_explain.log_min_duration = '500ms'`; `auto_explain.log_analyze = true`; `auto_explain.log_buffers = true`; `auto_explain.log_format = 'json'`; <Term k="auto_explain_sample_rate" lang="en">`auto_explain.sample_rate = 0.01`</Term> (sample 1% of slow queries to limit log volume). The result: slow queries land in postgres logs with full ANALYZE + BUFFERS plans, no need to reproduce them in staging. Pipe logs to a tool that parses plans (pganalyze, pgwatch2, or self-hosted analysis); over weeks, the top slow-query plans aggregate naturally. Caveat: log_analyze = true adds overhead per query — the timing instrumentation is non-trivial on very fast OLTP. Tune sample_rate or use auto_explain.log_min_duration to only catch the actually-slow.</p>
    <p><strong>Plan stability across deploys.</strong> A common operational pain: a deploy with new tables, new data, or different volumes causes plan regressions on unchanged queries. Mitigations. (1) Maintain a "golden plan" snapshot for the top-20 queries in pg_stat_statements; compare after deploys; alert on plan structure changes (different node types). (2) Pin plans for ultra-critical queries via pg_hint_plan (extension) — explicit hints like `/*+ IndexScan(orders idx_x) HashJoin(orders customers) */` force a plan shape; trades planner adaptability for predictability. (3) Stabilise statistics: run ANALYZE on critical tables in the post-deploy hook so the planner sees fresh data before traffic resumes. (4) Use pg_stat_statements to detect regressions: stddev_exec_time spikes, mean_time degradation, total_time concentration on previously-cheap queries. Senior teams own a plan-regression playbook the same way they own incident response.</p>
    <p><strong>Real production failure modes.</strong> (a) <em>Stale statistics cascade</em>: bulk INSERT or large UPDATE shifts distributions; autovacuum has not triggered ANALYZE yet; the next query uses an old MCV list and picks a wrong plan. Mitigation: ANALYZE in the post-batch hook of any large data operation. (b) <em>Generic-plan trap</em>: prepared statement was fast for the first 5 executions (custom plans), regressed on the 6th (generic plan). Mitigation: plan_cache_mode = force_custom_plan for that role. (c) <em>Correlated-columns blowup</em>: `country='US' AND region='CA' AND status='shipped'` underestimated 1000×; Nested Loop runs 1M times instead of 1k. Mitigation: CREATE STATISTICS (dependencies, mcv) on the column group. (d) <em>random_page_cost mis-tuned</em>: on SSDs, default HDD-era cost makes Index Scan look 4× more expensive than it should; planner prefers Seq Scan. Mitigation: SET random_page_cost = 1.1 in postgresql.conf for SSD systems. (e) <em>JIT overhead on OLTP</em>: short queries trigger JIT (some pathological cost estimate exceeds jit_above_cost) and spend more time compiling than executing. Mitigation: raise jit_above_cost to 500000+ or disable JIT for the role. (f) <em>work_mem too low</em>: Sort Method: external merge, or Hash Join Batches &gt; 1, indicates spilling. Mitigation: SET work_mem per session for the query; do not raise globally without considering concurrent backend count × work_mem. (g) <em>Hash Aggregate spill bug</em>: pre-PG 13, large GROUP BYs could not spill — they used unbounded memory and got OOM-killed. Mitigation: upgrade past PG 13 (Hash Aggregate now spills correctly). (h) <em>Plan flips with workload phase</em>: same query gets different plans at different times of day because data distribution shifts (overnight imports inflate one table's row count); autovacuum eventually rebalances. Mitigation: pin plans via pg_hint_plan for critical paths; otherwise accept the variance.</p>
    <p><strong>Strategic posture: plans are a first-class operational artefact.</strong> Mature Postgres teams treat execution plans the way SRE teams treat dashboards — captured, versioned, alerted on, reviewed in PRs that change SQL. Every PR that touches a hot query carries an EXPLAIN ANALYZE diff in the description (before and after). Every deploy includes a post-deploy ANALYZE on critical tables and a pg_stat_statements snapshot. The top-20 queries by total_exec_time have explicit "golden plan" expectations documented. Slow-query regressions are caught by auto_explain + alerting, not by user complaints. The cost is moderate (a quarterly index/plan audit + automated alerting); the benefit is no 3am calls because a query that worked for two years suddenly does not. EXPLAIN ANALYZE is the senior engineer's microscope for Postgres — the more often you use it, the less often you debug blind.</p>
