Migrations (<a href="/en/databases/06-migrations/">06-migrations</a>) showed how to change one Postgres safely; this piece is about what to do when one Postgres is not enough — when the working set no longer fits in shared_buffers, when write throughput saturates a single primary, when one tenant's queries starve the rest. Sharding is the horizontal split: take a logically single dataset and partition it across many physical databases by a <em>shard key</em>, route each query to the shard owning its key. The win is linear-ish scale-out (10 shards ≈ 10× the storage, often 5-8× the throughput); the cost is operational complexity (every migration runs N times, cross-shard joins become expensive, transactions span machines, the shard map becomes critical infrastructure). The failure mode you must design around from day one is <em>hot shard</em>: one shard receives a disproportionate share of traffic because the shard key was poorly chosen or because one tenant grew 1000× larger than the median. Senior teams pick shard keys deliberately, monitor for skew, and have a resharding playbook before the first incident — not after.

<Crux>Sharding splits one DB by shard key. Co-location is the win; hot shards are the failure mode; resharding online is the test.</Crux>

There are two layers conflated in everyday speech: <em>partitioning</em> (one Postgres, table split into pieces by a key — declarative partitioning since PG 10) and <em>sharding</em> (many Postgres instances, each holding a subset of rows). Partitioning is single-node and is mostly a query-planning + manageability win (drop a partition instead of a DELETE; prune partitions in plans); it does not increase throughput beyond one machine. Sharding is multi-node and is the only way to scale Postgres past one machine's CPU/IO/storage ceiling. The two compose: real-world systems usually partition within each shard (e.g., shard by tenant_id; within each tenant's shard, partition events table by month for fast retention). Citus is the Postgres extension that turns a cluster into a transparent sharded database (coordinator + workers + automatic routing); the alternatives are application-level routing (your code picks the shard) and database-per-tenant (each tenant gets its own Postgres). All three are deployed in 2026; the right choice depends on tenant count, query shape, and operational budget.

  <Fragment slot="middle">
    <p><strong>Partitioning vs sharding — the same word means two things.</strong> <em>Partitioning</em> (Postgres-internal): a single table split into sub-tables on one Postgres instance, declared with `PARTITION BY RANGE/LIST/HASH` (PG 10+). Useful for query pruning (DROP partitioning of old time-ranges instead of DELETE) and for managing large tables. Does not increase throughput past one machine. <em>Sharding</em> (cross-instance): the dataset split across many Postgres instances, routed by a shard key. The increases throughput linearly with shard count up to the bottleneck (often cross-shard coordination). The two compose: a sharded cluster typically also partitions within each shard. The senior intuition: partition for manageability and pruning; shard for capacity.</p>
    <p><strong>Shard-key strategies.</strong> <em>Hash sharding</em>: shard = hash(key) mod N. Uniform distribution; simple to reason about; rebalancing is hard (changing N moves most rows). <em>Range sharding</em>: shard owns a key range (`tenant_id 1-1000` on shard A, `1001-2000` on B). Natural for time-series; rebalancing is easier (split a range); risk of hot tail (newest rows all on one shard). <em>List sharding</em>: explicit map of key → shard. Maximum control; doesn't scale to millions of keys. <em>Directory-based / lookup sharding</em>: external table (the "shard map") maps key → shard; can move individual tenants between shards by updating one row. Most flexible; adds a lookup cost; chosen by Citus tenant isolation and by manual app-level routing. <em>Consistent hashing</em>: a hash variant where adding/removing a shard moves only K/N keys, not most of them. Used in caches more than in SQL sharding; some Postgres setups use it for directory-based remapping.</p>
    <p><strong>The shard-key contract.</strong> A good shard key has four properties. (1) <em>Selectivity</em>: 95%+ of queries filter by it; queries without it are rare or fan-out. (2) <em>Uniform distribution</em>: each shard gets roughly equal data and load; no tenant or key range dominates. (3) <em>Stable</em>: the value does not change for a given row (you can't re-shard mid-flight). (4) <em>Available at routing time</em>: every API request can supply it (every request carries a tenant_id in the URL or token). For multi-tenant SaaS, `tenant_id` is almost always the right key. For B2C scale, `user_id`. For geo-partitioned, `region`. Designs that don't have one such key are red flags — split the data model until one emerges.</p>
    <p><strong>Co-location: the performance win.</strong> When tables that join frequently share the same shard key (e.g., `orders.tenant_id` and `payments.tenant_id`), Citus places matching shards on the same physical worker. A join filtering by tenant_id stays local — one machine, no network round-trips, identical performance to a single Postgres for that tenant's queries. Without co-location, the join becomes a cross-shard operation: coordinator gathers data from N shards, merges, returns — orders of magnitude slower. Co-location is the design rule that lets sharded Postgres feel like single Postgres for the common queries. Senior pattern: define a tenant-scoped tables list, every one of them sharded by tenant_id, all co-located.</p>
    <p><strong>Cross-shard queries.</strong> Queries that don't filter by the shard key fan out to all shards. The coordinator (Citus or your app) sends the query to every shard, collects the results, applies an aggregation if needed, returns. Costs: N× the work, P99 latency = max(shard latencies), every slow shard slows the query. Examples: "list all users in the system" without tenant_id; "global count of orders today"; cross-tenant analytics. Mitigations: (1) avoid them in OLTP — design APIs around per-tenant scopes. (2) For analytics, replicate data to a separate analytical store (Snowflake, BigQuery, ClickHouse) via CDC; let the OLTP cluster stay tenant-scoped. (3) For dashboards needing per-tenant metrics, precompute and store per-tenant.</p>
    <p><strong>Citus: Postgres's sharding extension in detail.</strong> Citus turns a cluster of Postgres instances into one logical database. Architecture: <em>coordinator</em> (one node, holds metadata, plans queries, routes); <em>workers</em> (N nodes, hold shards, execute their share of queries). Table types: <em>distributed</em> (rows split across workers by shard key); <em>reference</em> (full copy on every worker, for tables joined to many distributed ones — e.g., countries, plans, feature flags; updates use 2PC across workers); <em>local</em> (only on coordinator, for admin/control tables). Distribution: `SELECT create_distributed_table('orders', 'tenant_id');` — Citus hashes tenant_id into N shards (default 32, often raised to 64 or 128 for larger clusters). Co-located tables created with same distribution column land on aligned shards. Rebalancer is online (Citus 11.1+): moves shards between workers with logical replication, no downtime, no read-only window.</p>
    <p><strong>Schema-based sharding (Citus 12+, 2023).</strong> A newer model: each tenant gets a Postgres <em>schema</em>; Citus distributes schemas across workers transparently. `CREATE SCHEMA acme; CREATE TABLE acme.orders (...);` and Citus assigns the schema to a worker. The application sets `search_path = acme` per connection to scope queries. Benefits: no shared distribution key required (any query within the schema is local); easy to onboard one tenant (CREATE SCHEMA); easy to migrate one tenant (move the schema); 1:1 tenant isolation including for schemas with no shared columns. Limits: schemas-per-cluster ceiling (Citus recommends "low thousands"); not suitable for B2C with millions of users. Production sweet spot: B2B SaaS with hundreds to a few thousand tenants where each has its own schema with isolation requirements.</p>
    <p><strong>Application-level sharding.</strong> Skip Citus; your app code routes queries. Pattern: a "shard map" table or service (`tenant_id → connection_string`) plus a routing layer that wraps every query. Pros: explicit, simple, no extra database product; flexible per-tenant logic. Cons: every cross-shard concern (joins, transactions, fan-out) becomes app code; resharding is your job; the routing layer is critical infrastructure. Common when sharding count is low (10-100 shards) and queries are highly tenant-scoped. Tooling: ORMs like Prisma support multiple `datasources`; libraries like `tenant-extractor` (custom) read tenant_id from a request context; connection pools per shard (each behind its own PgBouncer). The senior pattern: build the routing layer minimal, test it under chaos (one shard down, slow shard, misrouted requests), and have a runbook for cross-shard operations.</p>
    <p><strong>Distributed transactions and 2PC.</strong> A transaction touching multiple shards needs two-phase commit (2PC): all shards prepare; if all OK, all commit; if any fail, all rollback. Postgres supports 2PC natively; Citus uses it for distributed transactions. Cost: latency (2 round-trips minimum, often more); risk (in-doubt transactions if coordinator crashes between prepare and commit — recoverable but painful); throughput hit. Best practice: design transactions to be single-shard whenever possible. For inevitable cross-shard, accept 2PC + monitor pg_prepared_xacts for stuck transactions; have a runbook for recovering them.</p>
    <p><strong>Hint: most apps don't need sharding.</strong> Modern Postgres on modern hardware handles 1-10 TB working sets and 10-50k QPS without breaking a sweat. Read replicas absorb most read scale; vertical scaling (more CPU, more RAM, faster disk) buys years. Sharding is the answer when you have measured the bottleneck and proven it cannot be solved by indexing, caching, replicas, or vertical growth. The cost of sharding is real: every migration N×, every cross-shard query slow, every operational task (backup, vacuum, upgrade) per-shard. Don't pre-shard.</p>
    <p><strong>Pre-sharding signals from a single Postgres.</strong> Before committing to sharding, check the leading indicators. (1) <em>Working set vs RAM ratio</em>: if `pg_stat_database.blks_hit / (blks_hit + blks_read)` drops below 95-99% sustained on a large instance, the working set has outgrown shared_buffers + OS cache; vertical scale buys time but the trajectory matters. (2) <em>Write throughput</em>: `pg_stat_database.xact_commit` per second approaching tens of thousands; primary CPU dominated by WAL generation. (3) <em>Connection count</em>: PgBouncer pool limit (see piece 05) often binds before raw CPU. (4) <em>Maintenance pain</em>: VACUUM takes hours; reindex windows shrink; backups exceed retention recovery time. (5) <em>One-tenant impact</em>: a single noisy tenant's query saturates IO and degrades all others — a "hot tenant on single Postgres" is the dress-rehearsal for hot-shard. When 2-3 of these signals are real, sharding moves from speculative to scheduled.</p>
    <p><strong>The deploy/operations multiplier.</strong> Once sharded, every operation scales by shard count. Backups: N pg_basebackups (or per-shard streaming); restore time is per-shard but often parallel. Postgres minor-version upgrades: N rolling updates, monitored per worker. Major-version upgrades: N pg_upgrades, careful coordination. Logical replication setup (for OLAP CDC): per-worker slot, per-worker publisher. Each runbook in single-Postgres operations becomes an N-runbook in sharded. Senior teams automate via per-shard orchestration (Ansible, Terraform with for_each over the worker list, custom operators in Kubernetes); without automation, ops staff scales linearly with shard count, which is the operational tax of sharding made concrete.</p>

  <Fragment slot="senior">
    <p><strong>The full shard-strategy taxonomy.</strong> (1) <em>Hash sharding</em>: shard = hash(key) mod N. Uniform if keys are uniform; rebalancing changes most placements when N changes; consistent hashing variants reduce that to K/N. (2) <em>Range sharding</em>: each shard owns a key range. Natural for time-series; risk of hot tail (newest data); rebalancing by splitting a range. (3) <em>List sharding</em>: explicit key → shard map. Maximum control; doesn't scale to millions of keys. (4) <em>Directory-based sharding</em>: external lookup table mapping each key to a shard; can move individual tenants by updating one row; basis of Citus tenant isolation. (5) <em>Schema-based sharding</em> (Citus 12, 2023): each tenant has its own Postgres schema; Citus distributes schemas across workers; clean tenant isolation; ceiling at low thousands of tenants. (6) <em>Database-per-tenant</em>: each tenant gets a dedicated Postgres database (or instance). Maximum isolation, simplest mental model; scales operationally to dozens-hundreds (PgBouncer pools per (db, user), backups per DB, upgrades per DB); painful past that. (7) <em>Row-level isolation (RLS) on single Postgres</em>: not sharding per se, but the same-cluster equivalent for multi-tenant data — RLS policies enforce tenant boundaries; works until single Postgres saturates. The senior choice depends on tenant count, isolation requirements, and operational maturity.</p>
    <p><strong>Citus internals: query planning across shards.</strong> When the coordinator receives a query, it parses, plans against the Citus metadata (which shards live where, which tables are reference/distributed/local), and produces a distributed plan. Three plan classes. (a) <em>Single-shard query</em>: WHERE has shard key equality (`tenant_id = $1`). Citus routes the query as-is to one worker; that worker executes it like normal Postgres. Performance: identical to single-Postgres. (b) <em>Distributed query, co-located</em>: query joins co-located tables, or runs SELECTs across all shards but can be pushed down (most aggregations, GROUP BY on shard key). The coordinator sends partial plans to all workers; each worker executes; coordinator merges. Performance: parallelism win, latency = max worker. (c) <em>Cross-shard query</em>: requires gather-and-merge on the coordinator. Slowest path; should be rare in OLTP. Citus exposes the plan class via `EXPLAIN (VERBOSE)` — production teams audit query patterns to keep cross-shard queries to a minimum.</p>
    <p><strong>Online resharding: the operational test.</strong> Adding a shard (scaling out) or removing one (consolidation) requires moving data. Old-school: take downtime, dump + restore. Modern: <em>online rebalancing</em> via logical replication. Citus 11.1+ rebalancer: (1) plans the move list (which shards go from worker A to worker B for balance); (2) starts logical replication on each shard from source to target; (3) once caught up, briefly pauses writes to the shard, switches the metadata pointer, resumes; (4) drops the source. Per shard: pause is sub-second; total rebalance time scales with data volume and network throughput (~10-100 MB/s per shard). Vitess provides similar online resharding for MySQL. The same pattern (logical replication + cut-over) applies to app-level sharding too, but you build it yourself. Senior teams have rebalanced in production before they need it, not after — capacity is a planned operation, not an emergency.</p>
    <p><strong>Distributed transactions and 2PC: when to use, when to avoid.</strong> Cross-shard transactions need two-phase commit: prepare on all shards; if all OK, commit on all; otherwise rollback all. Postgres has 2PC (`PREPARE TRANSACTION`, `COMMIT PREPARED`); Citus uses it for any DML touching multiple shards. Cost: latency (2 network round-trips minimum), throughput (each shard's connection is held during prepare), and the in-doubt-transaction risk (coordinator crashes between prepare and commit; the prepared transactions sit in pg_prepared_xacts holding locks until manually resolved). Best practices. (1) Design transactions to be single-shard whenever possible — co-located tables make this natural. (2) Avoid `BEGIN; UPDATE shard1; UPDATE shard2; COMMIT` patterns; prefer eventual consistency via outbox or saga where the business logic allows. (3) Monitor pg_prepared_xacts on every worker; alert on rows older than a few minutes; have a recovery runbook. (4) For genuinely-distributed-transactional needs (rare in B2B SaaS), use Citus's built-in 2PC, not roll-your-own — the recovery semantics are subtle.</p>
    <p><strong>Schema-based sharding deep-dive.</strong> Citus 12 (2023) added schema-based sharding: each tenant maps to a Postgres schema, schemas distribute across workers, queries scope via `search_path`. Implementation: `CREATE SCHEMA acme;` Citus assigns the schema to a worker (lookup table). Application: `SET search_path TO acme, public;` — every subsequent query resolves table names within the acme schema; Citus routes to acme's worker. Benefits over row-based: (1) no shared shard key column required (any query within the schema runs locally); (2) schema is the natural deployment unit (CREATE/DROP SCHEMA); (3) clean isolation (one tenant cannot accidentally read another's data because table names are different); (4) easy to migrate (move the schema); (5) per-schema migrations work just like single-Postgres. Limits: schema-count ceiling (Citus recommends &lt; few thousand); cross-tenant queries are still cross-shard; some features (Citus reference tables) don't apply within schemas. Sweet spot: B2B SaaS with 50-2000 tenants where strict tenant isolation is part of the product (compliance, contractual isolation). Outside that band, row-based sharding (Citus distributed tables) or DB-per-tenant fits better.</p>
    <p><strong>Postgres FDW for federated queries (non-Citus).</strong> postgres_fdw lets one Postgres query another over libpq. Without Citus, you can build a federated read pattern: a coordinator Postgres holds metadata + FDW foreign tables pointing at worker Postgres; reads through the foreign table fetch from the worker; the coordinator can join across FDW tables (with significant overhead). Useful for: read-only analytics across shards; consolidating data from per-tenant DBs into one query interface; bridge during migration to/from Citus. Limits: writes through FDW are slow and not transactional across foreign tables (Postgres 17+ improved this with COMMIT/ROLLBACK PREPARED on foreign tables, but it is niche); joins push down only when predicates allow. Not a Citus replacement; useful tool in app-level sharding setups.</p>
    <p><strong>Resharding the shard key (rare and painful).</strong> Sometimes the original shard key turns out wrong: you sharded by user_id but most queries are by org_id; the user-to-org ratio creates skew or fan-out. Re-sharding by a different key means rewriting every row to its new shard. Approaches. (1) <em>Dual-write + backfill</em>: app writes to old and new sharding scheme; backfill historical data; cut over reads when caught up; drop old. Months of work; senior team's careful project. (2) <em>Vitess-style live resharding</em>: tool-managed copy + replication + cut-over; minutes of write pause. Vitess does this for MySQL; Citus's analog is shard-splitting, which works within one shard key but not for changing keys. (3) <em>New cluster</em>: stand up a parallel cluster with the new sharding, replicate via CDC, cut over. Most flexible; most operational work. The senior takeaway: shard-key change is among the most expensive ops; choose carefully from the start, and prefer a key that scopes to the natural unit of work even if it adds short-term complexity.</p>
    <p><strong>Multi-region sharding and consistency.</strong> Geo-partitioning shards data by region (`region = 'us-west'`, `region = 'eu-central'`, etc.) and routes traffic to the nearest shard. Benefits: low-latency reads/writes per region; data residency compliance (GDPR). Costs: cross-region queries are slow (50-200ms across continents); cross-region writes need 2PC or eventual consistency; failover policies must be clear (does a region's data become read-only when its primary fails?). Postgres-native geo-sharding: declarative partitioning by region column on each cluster + app routing by region. Newer commercial options: CockroachDB, YugabyteDB are Postgres-compatible distributed SQL databases designed for multi-region from the start; trading off Postgres-the-extension-ecosystem for built-in multi-region semantics. Senior choice: stay on Postgres for as long as the workload tolerates single-region or per-region clusters; consider distributed-SQL only when multi-region writes with strict consistency are a hard requirement and the trade-offs are acceptable.</p>
    <p><strong>Failure-mode taxonomy.</strong> (a) <em>Hot shard from skewed tenant</em>: one tenant 100-1000× median. Mitigate: monitor skew, isolate large tenants (Citus isolate_tenant_to_new_shard or app-level directory remap). (b) <em>Hot tail with range sharding</em>: newest rows on one shard for time-keyed data. Mitigate: hash within the range, or distribute by combination of time + tenant_id, or use Citus hash distribution. (c) <em>Cross-shard query explosion</em>: a new feature adds queries without shard key filter, fan-out costs spike. Mitigate: query review in PR (Citus EXPLAIN class), CDC to OLAP store for analytics, rate limiting cross-shard endpoints. (d) <em>Stuck prepared transactions</em>: coordinator crash leaves pg_prepared_xacts entries; locks held forever. Mitigate: alerts on pg_prepared_xacts age, runbook for `COMMIT PREPARED` or `ROLLBACK PREPARED` recovery. (e) <em>Reference-table write storm</em>: a small reference table has high write rate; 2PC across all workers becomes the bottleneck. Mitigate: convert to distributed by something stable, or accept higher latency on those writes. (f) <em>Migration drift across shards</em>: one shard ran the migration, another didn't; schema diverges. Mitigate: migration tool aware of sharding (Citus is; app-level needs custom runner that hits every shard, retries on failure, verifies post-run schema_migrations table consistency). (g) <em>Resharding mid-failure</em>: rebalancer crashes mid-shard-move; the shard exists on two workers with logical replication interrupted. Mitigate: Citus rebalancer is idempotent and resumable; manual recovery uses pg_stat_subscription state + pg_logical_slot_get_changes; runbook drilled in staging. (h) <em>Schema-sharding ceiling hit</em>: tenant count outgrows the schema model. Mitigate: migrate the very-large tenants to row-based sharding while keeping smaller ones schema-based; hybrid model is real in production.</p>
    <p><strong>Strategic posture: sharding is a one-way door.</strong> Once a system is sharded, every operational task scales by shard count. Migrations run per-shard; backups per-shard; upgrades per-shard; alerts per-shard. Senior teams shard only after the bottleneck is measured and alternatives are exhausted. They start with the simplest sharding that works (often Citus + row-based + tenant_id), measure for six months, and adjust. They write the operational runbooks before they need them. They treat the shard map as critical-tier-1 infrastructure with on-call coverage. They reshard preemptively when skew approaches the threshold, not after pages.</p>

<KeyTakeaway>Sharding splits Postgres across many instances by a shard key (tenant_id for B2B SaaS). Co-location of tenant-scoped tables on the same key is the central invariant — keeps 99% of queries single-shard. Failure mode is hot shard from skewed tenant; isolate large tenants via Citus's primitive. Cross-shard queries: push analytics to OLAP via CDC. Reshard online with logical replication. Don't pre-shard.</KeyTakeaway>
