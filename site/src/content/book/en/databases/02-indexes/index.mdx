The relational model (<a href="/en/databases/01-relational-model/">01-relational-model</a>) showed how to shape data; this piece is about the only practical reason that shape is queryable at all. An index is a copy of the data sorted to answer one specific question fast — and every index costs storage and slows every write. Senior engineers pick indexes deliberately: which questions are hot, which can be merged into a single composite, which can be partial to save space, which path the planner will actually choose. The most violated rule in production is the leading-column rule: a multi-column index `(a, b, c)` accelerates queries that filter by `a` (or `a, b`, or `a, b, c`) but not queries that filter only by `b` or `c`. This piece teaches the rule, the index families Postgres ships, the rare cases where you need something other than B-tree, and the operational discipline of adding indexes without taking the table down.

<Crux>Indexes = sorted copies of data for one question. Leading-column rule. Every index taxes every write. Pick deliberately.</Crux>

Postgres ships six index types: <em>B-tree</em> (default, range queries and equality on ordered types), <em>Hash</em> (equality only, niche), <em>GIN</em> (inverted index for composite types — arrays, JSONB, full-text), <em>GiST</em> (generic search tree for geospatial and range types), <em>SP-GiST</em> (space-partitioned search tree, niche), <em>BRIN</em> (Block Range INdex for huge insert-only tables with natural ordering). B-tree handles 95% of production work. The other types matter when the data shape demands them — JSONB needs GIN, geospatial needs GiST, time-series needs BRIN, full-text search needs GIN or a specialized extension. Knowing which is which is the difference between a 5ms query and a 5-second one. The remaining 5% — partial, expression, covering, unique, multicolumn, and concurrent index builds — is where the productivity wins live.

    <p><strong>One sentence.</strong> An index is a separate data structure (usually a B-tree) that lets the database find rows matching a condition in logarithmic time instead of scanning every row.</p>
    <p><strong>Why care.</strong> Without indexes, every query that filters or sorts touches every row. At 1M rows that is slow; at 100M it is broken. Indexes are how a relational database scales from prototype to production.</p>
    <p><strong>The metaphor.</strong> A book has an index at the back: alphabetical list of terms with page numbers. To find "MVCC", flip to the index (one O(log n) lookup), get the page, jump to it. Without the index, scan every page. The book index is a copy of part of the content (the terms) organised for one specific kind of question. Database indexes work identically — copy of column values, organised for fast lookup.</p>
    <p><strong>Otto and Sven.</strong> <PersonaTag id="otto" lang="en" /> sees a slow query: SELECT * FROM orders WHERE user_id = 42 takes 2 seconds on 10M rows. <PersonaTag id="sven" lang="en" /> wonders why — "user_id is just an integer". Otto runs EXPLAIN: sequential scan. Otto creates an index: CREATE INDEX ON orders(user_id). Same query, 3 milliseconds. The index is a sorted copy of user_id values mapping to row locations; the planner uses it instead of scanning. One DDL line, 600x speedup.</p>
    <p><strong>One scenario.</strong> A team adds a "filter by status" feature to an orders dashboard. SELECT * FROM orders WHERE status = 'pending' returns in 50ms on staging (100k rows). In production (50M rows) it takes 8 seconds. Diagnosis: no index on status. Fix: CREATE INDEX CONCURRENTLY ON orders(status). Same query, 20ms. Lesson: every WHERE clause your application runs hot needs an index, or you find out at the worst possible time.</p>

    <p><strong>B-tree: the workhorse.</strong> Postgres's default index type. A balanced search tree where each node is a disk page (8KB) containing a sorted list of keys and pointers to child pages (or to heap rows at leaves). Range scans (`column = ?`, `column &gt; ?`, `column &lt; ?`, `column BETWEEN ? AND ?`, `column IN (?, ?, ?)`) are all O(log n) plus the cost of reading matching leaves. Equality, range, sort order (ORDER BY), LIKE with a fixed prefix (`'abc%'`) — all answered by B-tree. For a 100M-row table, a B-tree typically has ~4 levels and an index lookup is a few page reads. The index size is roughly bytes_per_key × number_of_rows × 1.3 (overhead). For BIGINT (8 bytes), 100M rows produces a ~1 GB index; for UUID (16 bytes), ~2 GB.</p>
    <p><strong>The leading-column rule.</strong> A multi-column B-tree on `(a, b, c)` is sorted primarily by `a`, then by `b` within equal `a` values, then by `c`. The index accelerates: queries that filter on `a` alone (great), `a` and `b` (great), `a, b, c` (best), `a` with a range on `b` (great), or `a` with `ORDER BY b`. The index does NOT accelerate queries that filter only on `b`, only on `c`, or only on `b, c`. This is the single most violated rule in production indexing. Fix: design the index to match the dominant query, or create multiple indexes if multiple queries need different leading columns. Composite indexes are cheaper than two separate indexes when most queries use the leading column anyway.</p>
    <p><strong>Index-only scans.</strong> When a query reads only columns that are present in the index (the indexed columns plus any INCLUDE columns), Postgres can answer it without touching the table heap at all — an "index-only scan". For analytic queries on hot data, this is a 10-100x speedup over a regular index scan (which has to fetch the row from the heap for each matching index entry). The catch: Postgres also needs to know the row is "visible" to the current transaction (MVCC, covered in piece 04). The visibility check uses the Visibility Map, which is updated by VACUUM. So index-only scans only work well on tables that have been recently vacuumed. Use the INCLUDE clause to add extra payload columns to the index without making them part of the sort key: `CREATE INDEX ON orders(user_id) INCLUDE (status, total_cents)`.</p>
    <p><strong>Partial indexes.</strong> A partial index is a B-tree (or other type) built only over rows matching a WHERE clause. `CREATE INDEX ON orders(user_id) WHERE status = 'pending'` indexes only pending orders — typically a small fraction of the table. Smaller index, faster lookup, cheaper writes (the index is only touched when status = 'pending'). Production use cases: soft-delete pattern (`WHERE deleted_at IS NULL`), feature flags (`WHERE feature_x_enabled = true`), status filters where only one or two statuses are queried hot. Caveat: queries must include the WHERE clause for the planner to use the partial index. Partial indexes are one of the most underused performance levers in Postgres.</p>
    <p><strong>Expression indexes.</strong> An index on a function of one or more columns, not the columns themselves. `CREATE INDEX ON users (LOWER(email))` lets `WHERE LOWER(email) = 'alice@x.com'` use the index — without the expression index, the function call on every row prevents index use. Common patterns: case-insensitive search (LOWER, UPPER), date truncation (`DATE_TRUNC('day', created_at)`), JSON path extraction (`(data-&gt;&gt;'event_type')`), computed values that match the query shape. Expression indexes are how you make functional-style queries fast without changing the schema.</p>
    <p><strong>Unique indexes.</strong> A UNIQUE constraint is implemented as a unique B-tree index. The constraint and the index are the same physical structure. Adding a UNIQUE constraint via ALTER TABLE locks the table; adding a UNIQUE index via CREATE UNIQUE INDEX CONCURRENTLY does not (but takes longer). Partial unique indexes are powerful: `CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL` enforces "email is unique among non-deleted users" — letting you soft-delete a user, then later re-register the same email. This pattern is impossible with a simple UNIQUE constraint on email alone.</p>
    <p><strong>GIN: inverted index for composite types.</strong> Generalized Inverted Index. Where B-tree indexes one value per row, GIN indexes many values per row — every key in a JSONB, every element in an array, every lexeme in a tsvector. Use cases: JSONB containment (`data @&gt; '{"type":"login"}'`), array overlap (`tags && ARRAY['premium']`), full-text search (`to_tsvector('english', body) @@ to_tsquery('term')`). GIN is bigger than B-tree (typically 2-5x the size of the indexed column data) and slower to update (each row update touches every indexed value). For high-write JSONB columns, the GIN index can dominate the write cost; in that case the `fastupdate` option defers index maintenance to a separate process at the cost of slower reads until consolidation.</p>
    <p><strong>GiST: generic search tree.</strong> For data that does not fit B-tree's ordered model: geospatial (PostGIS uses GiST), range types (`tsrange`, `int4range`), nearest-neighbour queries. GiST is extensible — implement a few operators and the engine uses your custom GiST index. In practice, most engineers encounter GiST via PostGIS (`CREATE INDEX ON locations USING GIST (geom)`) for "find all points within distance D of point P".</p>
    <p><strong>BRIN: for huge insert-only tables.</strong> Block Range INdex. Stores summary information per block-range (default 128 pages, ~1MB): min and max values of indexed columns in that range. To answer a query, Postgres reads the BRIN to find candidate ranges, then scans only those blocks. BRIN is tiny (kilobytes for billions of rows) and fast to maintain — but only useful when the data is physically clustered by the indexed column. Classic use case: time-series tables where rows are inserted in time order, indexed on `created_at`. BRIN turns a 10TB time-series table into something queryable on cheap hardware. Not useful for randomly-distributed data.</p>
    <p><strong>Hash indexes.</strong> Historically broken in Postgres (no WAL until Postgres 10), now stable. Useful for equality lookup on very large indexed columns where B-tree size would be a problem — but in practice B-tree is almost always preferred because it supports range queries and ORDER BY for free. Hash indexes have a narrow niche; default to B-tree.</p>
    <p><strong>Bloom indexes for multi-column equality lookups.</strong> The `bloom` extension provides a probabilistic index that supports equality on many columns simultaneously, without the leading-column rule. A bloom index on (a, b, c, d, e) accelerates any query that filters by any subset of those columns. Trade: it is approximate — every match is a candidate that must be re-checked against the heap, so false positives are possible. Use case: tables with many columns where queries combine different filter sets unpredictably; alternative to building 2^N composite indexes. Niche but powerful when the right fit.</p>
    <p><strong>HOT updates and fillfactor.</strong> When a row is UPDATEd, Postgres normally creates a new tuple version (MVCC) and updates every index that references the row — even indexes whose columns did not change. HOT (Heap-Only Tuple) updates skip the index update entirely when (a) no indexed column changed, AND (b) there is enough free space on the heap page for the new tuple version. HOT cuts write overhead dramatically on update-heavy workloads. Fillfactor (the percentage of each page filled at insert time, default 100 for tables and 90 for B-tree indexes) leaves room for HOT updates; setting fillfactor to 70-80 on update-heavy tables ensures HOT triggers. The trade is initial storage (smaller fillfactor = more space per row); production teams measure update frequency and tune fillfactor on hot tables — a frequently overlooked lever.</p>
    <p><strong>Hint: ANALYZE matters more than indexes.</strong> The planner's choice of index (or no index) depends on table statistics — row counts, value distributions, correlations. ANALYZE (run automatically by autovacuum, manually when needed) collects these statistics. Without fresh stats, the planner under- or over-estimates how many rows a filter will match, and picks the wrong plan. Production discipline: run ANALYZE after bulk inserts, after large UPDATEs, after schema changes that affect distributions; tune autovacuum_analyze_scale_factor lower on tables with skewed data; use CREATE STATISTICS for correlated columns (e.g., country + city) so the planner does not assume independence. A "wrong index choice" diagnosis is often actually "stale stats."</p>

  <Fragment slot="senior">
    <p><strong>Index-only scans and the <Term k="visibility_map" lang="en">visibility map</Term>.</strong> An index-only scan returns column data straight from the index without fetching the row from the heap. Postgres can do this when: (a) every column the query needs is in the index (either as a key column or as an INCLUDE column), and (b) the engine knows the row is "visible" to the current snapshot without having to check the heap's per-tuple visibility info. The second condition is the trick. The Visibility Map (VM) is a per-table bitmap with one bit per heap page; the bit is set when "every tuple on this page is visible to every active transaction." VACUUM sets bits; any write or transaction-aborted tuple unsets them. Implication: index-only scans only help when the indexed table has been recently VACUUMed. On insert-only tables, this works almost always; on heavily-updated tables, less often. Mature teams tune autovacuum to be aggressive on tables that depend on index-only scans, and monitor pg_stat_user_tables.n_dead_tup as the leading indicator.</p>
    <p><strong>INCLUDE columns and covering indexes.</strong> Postgres 11+ supports `CREATE INDEX ... INCLUDE (cols)` — the INCLUDE columns are stored in the index leaves but not in the sort key. The result: the index is "covering" for queries that need those columns in the SELECT projection, enabling index-only scans without forcing the included columns into the sort. Use case: a query that filters by workspace_id, sorts by created_at, and projects id, total — build the index as `(workspace_id, created_at DESC) INCLUDE (id, total)`. The sort is served by the key columns; the projection is served by the included columns; no heap fetch needed.</p>
    <p><strong>Postgres index types in detail.</strong> (a) B-tree internal: pages are linked in a sibling-list at each level for efficient range scans; the latest Postgres versions implement "bottom-up index deletion" that removes dead entries on hot pages without waiting for vacuum, significantly reducing bloat on UPDATE-heavy workloads. (b) GIN structure: an inverted index where each indexed key maps to a posting list (or posting tree) of TIDs that contain that key. fastupdate mode buffers pending entries and merges them periodically — faster writes, slower reads when the buffer is full. (c) GiST structure: a generalized search tree where each non-leaf node stores a "predicate" that summarises its subtree (e.g., a bounding box for geometries). The engine uses these predicates to prune subtrees during search. (d) BRIN structure: per-block-range summary tuples (min, max, null-bitmap by default); intentionally lossy — narrows the heap scan but does not eliminate it. (e) SP-GiST: like GiST but uses space-partitioning (quadtree, k-d tree shapes); narrow use cases like IP ranges and IP CIDR matching. (f) Hash: equality only; useful for very wide keys where B-tree size would be a concern.</p>
    <p><strong>Operator classes and custom operators.</strong> Each index type supports a set of operators, defined by operator classes. The B-tree default operator class for TEXT does lexicographic comparison; the `text_pattern_ops` class disables locale-aware sorting and makes LIKE-prefix queries (`column LIKE 'abc%'`) use the index. The `varchar_pattern_ops`, `bpchar_pattern_ops` are similar. Custom operator classes are how you make complex types indexable; PostGIS, pg_trgm (trigram fuzzy search), pgvector (embedding similarity), pg_bigm (bigram for CJK) — all ship operator classes that let GiST/GIN/B-tree/HNSW index their data types. Senior teams use operator-class selection to make uncommon queries fast without changing query shape.</p>
    <p><strong>Index maintenance: REINDEX, bloat, <Term k="fillfactor" lang="en">fillfactor</Term>.</strong> Indexes accumulate dead entries over time. Postgres 14+ does aggressive cleanup via bottom-up index deletion, but heavy-update tables still benefit from periodic REINDEX CONCURRENTLY. The fillfactor parameter (default 90 for B-tree) leaves space in each leaf page for in-place updates (HOT updates — see piece 04 on MVCC), reducing page splits and slowing bloat. Lower fillfactor (e.g., 70) reduces bloat on heavily-updated tables at the cost of larger initial index size. Production discipline: monitor pg_stat_user_indexes for idx_scan = 0 (unused, drop) and high pg_stat_user_indexes.idx_tup_read / idx_tup_fetch ratio (indicates index points to many heap fetches, possibly stale stats or poor selectivity). Schedule monthly REINDEX CONCURRENTLY on hot indexes.</p>
    <p><strong>Index strategy with replicas and standby.</strong> Indexes on a primary are replicated to standbys via WAL — every CREATE INDEX, every index write — so standbys have the same indexes. CREATE INDEX CONCURRENTLY on the primary does not block reads on standbys, but the standby cannot serve queries that conflict with the index build (rare). Replicas may have additional read-only-specific indexes added via the `EXTERNAL` index option in extensions like pglogical, but stock Postgres replicates the schema verbatim. For OLTP + OLAP workloads on the same Postgres, the canonical pattern is a primary with OLTP-tuned indexes plus a logical-replication-based analytics copy where OLAP-specific indexes (often BRIN, GIN, or wide composites) live.</p>
    <p><strong><Term k="hnsw" lang="en">HNSW</Term> for vector similarity (pgvector).</strong> Postgres 16+ with pgvector supports HNSW (Hierarchical Navigable Small World) indexes for approximate nearest-neighbour search on embedding vectors. HNSW is not a B-tree variant — it is a graph-based index optimised for high-dimensional similarity search. Trade: indexes are large (vector dimension times row count) and writes are slow (graph rebalancing per insert), but queries on 1M+ embeddings return in single-digit milliseconds. For 2026 production AI/ML systems with Postgres as the primary store, pgvector + HNSW is the canonical choice; alternatives include Pinecone, Weaviate, Milvus as dedicated vector databases when scale or feature requirements exceed pgvector's reach.</p>
    <p><strong>Real production failure modes.</strong> (a) <em>Missing index on FK column</em>: foreign-key columns are not automatically indexed; CASCADE deletes do a sequential scan on the child table to find rows to delete, which takes hours on large tables. Mitigation: index every FK column unless you can prove the parent is never deleted. (b) <em>Implicit type coercion bypasses index</em>: WHERE bigint_column = '42' forces type conversion on every row, defeating the index. Mitigation: typed query builders, EXPLAIN ANALYZE on every new query. (c) <em>Stale statistics</em>: planner picks Seq Scan because it underestimates how many rows the index would return; ANALYZE the table after large data changes. (d) <em>Bloated index</em>: index 5x larger than expected; REINDEX CONCURRENTLY. (e) <em>Index-only scan disabled by recent updates</em>: visibility map is partially clear after writes; VACUUM the table. (f) <em>Composite index with wrong column order</em>: queries that should use the index fall back to Seq Scan because the leading column is not in the filter; redesign the composite or add a second one. (g) <em>Cardinality bomb in JSONB GIN</em>: a JSONB column with millions of unique keys creates a huge GIN index that overwhelms shared_buffers; consider per-field expression indexes for known-hot fields instead.</p>
    <p><strong>The index audit playbook.</strong> Quarterly, every team running Postgres at scale should run an index audit. (1) Drop unused: SELECT indexrelname FROM pg_stat_user_indexes WHERE idx_scan = 0 AND indexrelname NOT LIKE '%_pkey' AND indexrelname NOT IN (known constraint-supporting indexes). (2) Find bloat: pgstattuple_approx() on hot indexes; REINDEX CONCURRENTLY on bloated ones. (3) Find missing indexes: pg_stat_statements joined with EXPLAIN on the top-N queries by total_time; any Seq Scan on a large table is a candidate. (4) Find redundant indexes: indexes whose key columns are a prefix of another index's key columns — drop the shorter one (the longer covers the shorter). (5) Verify visibility-map health for index-only scans: monitor pg_stat_user_tables.n_dead_tup and autovacuum schedule. The audit is 1-2 hours of work and routinely produces 10-30% storage savings plus 2-5x write-rate improvements on heavily-indexed tables.</p>
    <p><strong>Strategic posture: indexes are part of design, not afterthought.</strong> The single most common production performance issue traced in postmortems is "missing index on this hot query." The second most common is "we have too many indexes and writes are slow." Both have the same root cause: indexes were not treated as part of the design. Senior teams add indexes to the migration that ships the feature; review indexes in code review alongside the query; audit usage quarterly; and own the index strategy at the platform level, not per-team. The cost of getting this right is small (an extra checklist item on PRs touching SQL); the cost of getting it wrong is a 3am page when a customer dashboard times out. Treat indexes as deliberate engineering, not as a runtime knob.</p>

<KeyTakeaway>Indexes are sorted copies of data for one query. B-tree is default; GIN/GiST/BRIN for non-ordered types. Leading-column rule is iron. CREATE INDEX CONCURRENTLY, INCLUDE for covering, partial for hot subsets. Audit quarterly.</KeyTakeaway>
