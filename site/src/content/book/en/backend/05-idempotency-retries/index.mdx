The request lifecycle (<a href="/en/backend/01-request-lifecycle/">01-request-lifecycle</a>) ends when the server returns a response. But what if the client never sees it — a TCP RST, a load-balancer 504, a phone losing signal mid-POST? The client retries. If your endpoint creates state, the user just got charged twice.

<Crux>How to make every retry-safe POST cost the user exactly one outcome, even when the network swallows the response.</Crux>

The internet does not guarantee that a request was processed exactly once. It guarantees "at-least-once" if the client retries until it gets a definitive answer, and "at-most-once" if it never retries. The application has to bridge the gap. The bridge is idempotency: design POSTs so that processing them twice is observably identical to processing them once, then make the client comfortable retrying.

    <p><strong>What idempotency does in one sentence.</strong> It lets a client retry the same write operation without the server doing the work twice.</p>
    <p><strong>Why care.</strong> Without it, a flaky network turns "Pay Now" into "Charged Three Times" and your customer-support queue catches fire.</p>
    <p><strong>The metaphor.</strong> Imagine sending money via courier. You hand the courier an envelope marked "Order #A7-payment" and say "if this envelope was already delivered, do not deliver another." On every retry, you write the same Order # on the new envelope. The recipient sees the marking, checks a clipboard, and either delivers the new envelope or hands it back saying "already done — here's the receipt from last time." The clipboard is the idempotency cache. The marking on the envelope is the idempotency key.</p>
    <p><strong>Bea and Sven.</strong> <PersonaTag id="bea" lang="en" /> the browser is on a flaky train wifi. She POSTs a $50 charge and her wifi dies before the response arrives. She does not know whether <PersonaTag id="sven" lang="en" /> the server charged her or not. Without idempotency, retrying might charge her twice; not retrying might leave her unpaid. With an Idempotency-Key header, the retry is safe — Sven sees the same key, recognizes the original POST, and replays the same response. Bea gets one charge and one confirmation, no matter how many times she had to retry.</p>
    <p><strong>One scenario.</strong> You hit "Submit Order" on a checkout page. Connection times out. You hit it again. With idempotency, the server's clipboard says "this order already exists, here is order #A7-payment, charged once, status confirmed." Without idempotency, the second click creates a second order and a second charge — and there is no purely server-side way to know which was the duplicate. Idempotency moves the burden from "guess" to "remember."</p>

  <Fragment slot="middle">
    <p><strong>What the Idempotency-Key header actually carries.</strong> An idempotency key is an opaque client-generated string — typically a 16-byte UUID v4 rendered as 36 characters — sent in the <code>Idempotency-Key</code> HTTP header. The client picks one fresh key per logical operation, not per request: every retry of the same operation reuses the same key. Stripe popularized the convention; Square, PayPal, Adyen, and IETF draft "The Idempotency-Key HTTP Header Field" (draft-ietf-httpapi-idempotency-key-header) all align on roughly the same shape. The server treats the key as a primary lookup token for "have I already processed this?"</p>
    <p><strong>The server-side state machine.</strong> When a request arrives with an Idempotency-Key the server moves through four states. <strong>(1) New</strong>: no row with this key exists. The server writes <code>(key, request_fingerprint, status=in_progress, expires_at)</code> in a single transaction with the actual business work (or just before it), processes the work, then updates the row with the response body and status code. <strong>(2) In flight</strong>: a row exists with status=in_progress. The server has two choices — return <code>409 Conflict</code> immediately (Stripe's approach) so the client backs off, or block briefly waiting for the in-flight request to finish (some payment gateways do this with a short timeout). <strong>(3) Replay</strong>: a row exists with status=completed and a stored response body. The server returns the cached response with the original status code, never re-runs the business logic. <strong>(4) Mismatch</strong>: a row exists with the same key but a different request fingerprint (e.g., the client reused a key for a different amount). The server returns <code>422 Unprocessable Entity</code> with an explanation; the application must regenerate the key for the new operation.</p>
    <p><strong>The request fingerprint matters.</strong> The fingerprint is a hash of the request method, path, query, body, and any headers the server considers part of the operation identity. Stripe hashes the body but not the headers; payment APIs that depend on the <code>Stripe-Account</code> header add it explicitly. The fingerprint catches a class of client bugs: code that reuses an idempotency key but changes the amount or the recipient. Without the fingerprint check, the second request would silently replay the first response, and the second amount would be lost. The cost is one SHA-256 per request (microseconds) — cheap insurance against silently dropping a real change.</p>
    <p><strong>Where to store the cache.</strong> The simplest implementation is a Postgres table: <code>idempotency_keys (key TEXT PRIMARY KEY, fingerprint TEXT, response_body JSONB, response_status INT, status TEXT, expires_at TIMESTAMPTZ)</code>. Index on key. Run a daily cleanup job to delete rows past expires_at. Stripe holds keys for 24 hours; their API v2 extended this to 30 days. At higher throughput, the cache moves to Redis with TTL set on each key — but Redis can lose keys on failover, so payment APIs that hold the legal liability for double charges typically keep the canonical record in the transactional database and use Redis only as a read-through cache.</p>
    <p><strong>Retry strategy on the client.</strong> The client side is symmetric: do not retry without a backoff. The minimum viable retry loop is "exponential backoff with jitter": each attempt waits <code>random_between(0, min(cap, base × 2^attempt))</code> before the next retry. <code>base</code> is typically 100ms–500ms, <code>cap</code> is typically 30s–60s, and the attempt count caps at 3–6 depending on operation criticality. The jitter is essential: without it, a service outage that flaps 5,000 clients all back at the same 2-second mark hits the server harder than the original failure. With full jitter, those 5,000 retries spread uniformly across a 2-second window, smoothing the load. Implementations: AWS SDK <code>StandardRetryStrategy</code>, Tenacity (Python), Resilience4j (Java), <code>retry</code> npm package, gRPC built-in retry config.</p>
    <p><strong>Which HTTP methods are idempotent by spec.</strong> RFC 9110 §9.2.2 spells it out: GET, HEAD, PUT, DELETE, and OPTIONS are idempotent by definition. POST is not. PATCH is conditionally idempotent — depends on the patch document semantics. For payment APIs, "POST + idempotency key" is the idiom because POST is the natural verb for "create a charge" but the operation must be safe to retry. PUT (which is idempotent by REST semantics) is sometimes used instead for "update or create with this id" workflows.</p>
    <p><strong>At-least-once + idempotent processing = effectively-once.</strong> True exactly-once delivery is impossible across a network (Two Generals' Problem — both sides cannot simultaneously agree something happened with zero rounds of additional communication). Production systems settle for at-least-once delivery (retry until acknowledged) plus idempotent processing (server dedupes). Combined, the observable behavior is exactly-once: the operation happens once and any number of retries are no-ops. Kafka, AWS SQS, Stripe webhooks, RabbitMQ, GCP Pub/Sub — all of them deliver at-least-once and instruct consumers to dedupe. The application engineer's job is to make the consumer truly idempotent: not just "the second message returns the same response", but "the second message has no observable side effect beyond replaying the first response."</p>
    <p><strong>Client-side retry patterns in detail.</strong> A typical client wraps each POST in a retry loop with jitter, capped budget, and a global deadline. AWS SDK v3 ships <code>maxAttempts</code> + <code>retryMode=standard|adaptive</code>; gRPC has retry config in service-config JSON with <code>maxAttempts</code>, <code>initialBackoff</code>, <code>maxBackoff</code>, <code>backoffMultiplier</code> per RPC; Axios + <code>axios-retry</code> in JavaScript; Go <code>retryablehttp</code>; Rust <code>reqwest-retry</code>. Three knobs must be set correctly: retry condition (5xx and timeouts yes; 4xx no, because the client is broken and retrying produces the same 4xx); a global deadline (total time budget for the operation so retries do not hide an outage from the user); and a retry budget (token-bucket of allowed retries per second across the call site) that opens the circuit when the backend stops responding. Without a budget the retry loop turns from defense into outage amplifier.</p>
    <p><strong>Server-side defenses against retry storms.</strong> A good server not only dedupes but also asks the client to slow down. The standard HTTP mechanism is the <code>Retry-After</code> header on 429 (Too Many Requests) and 503 (Service Unavailable) responses: the value (seconds or absolute date) tells the client "stop retrying for at least N seconds." A well-behaved client honors <code>Retry-After</code> before applying its own backoff. gRPC uses the <code>grpc-retry-pushback-ms</code> trailer for the same purpose. Servers also implement per-client rate limiting (429 with the remaining budget header) so a retry storm degrades to graceful refusal: each client gets a 429 with a Retry-After, waits the indicated time, and returns staggered. The combination of server-issued backoff hints and client retry budgets is what keeps a recovering service from being re-killed by the very clients trying to use it.</p>
    <p><strong>Service-mesh + edge integration.</strong> At the infrastructure layer, Envoy and Istio expose retry policy per route: <code>retries.attempts</code>, <code>retries.perTryTimeout</code>, <code>retries.retryOn</code> (e.g., <code>5xx,reset,connect-failure,refused-stream</code>), and a retry budget shared across the cluster. AWS API Gateway has built-in idempotency support since 2023 with TTL up to 10 minutes per stage. Cloudflare Workers expose <code>Cache.put</code> with a TTL primitive that some teams repurpose as a cheap idempotency cache for non-financial workloads. The pattern is consistent: defer retries + idempotency to the platform layer where you can, fall back to application-level middleware where you cannot. Hand-rolling per-endpoint is the wrong default.</p>
    <p><strong>Testing idempotency.</strong> An idempotent endpoint without an idempotency test is a belief, not a property. Minimum acceptable test: integration test sends the same POST with the same Idempotency-Key twice (with a microsecond gap) and asserts that (1) both responses have identical status and body, and (2) the business side effect occurred exactly once (e.g., exactly one charge row in the payments database). Extended test injects random network failures between the first attempt and the retry, asserting that the server still routes the retry to the replay path even if the first attempt did not finish writing to the cache. Stripe runs an internal chaos-load harness that injects latency and failures at every layer to keep the race surface from growing silently. Without these tests, the first production race is the first discovery of the problem.</p>
    <p><strong>DLQ and poison messages.</strong> Not every failure is recoverable by retry. Some messages are poisoned — malformed data, broken schema, business invariant violations. Infinite retry of such a message blocks the queue partition (especially in FIFO Kafka), and with it every subsequent message. The solution is a dead-letter queue (DLQ): after N processing attempts the message moves to a separate queue for human review, while the main pipeline keeps flowing. Production settings: N = 3-5 attempts, DLQ retention 7-30 days, alert on DLQ depth growth, runbook for poison-message types (schema breakage, missing dependency, expired-business-id). Without a DLQ the retry loop becomes a guaranteed pipeline stall, and the operational discipline of regularly draining DLQ entries (whether by fixing the upstream bug, manually replaying, or formally rejecting) is what separates a healthy event-driven system from a quietly broken one — and any growing DLQ that no one looks at is also a slowly accumulating compliance liability.</p>

  <Fragment slot="senior">
    <p><strong>Concurrency edge cases inside the idempotency cache.</strong> Two requests with the same key can race inside the server. The naive "INSERT if not exists, else replay" sequence is not atomic: between the SELECT and the INSERT, a second request can slip through and both can think they are the first. The fix in Postgres is <code>INSERT ... ON CONFLICT (key) DO NOTHING RETURNING *</code> — atomic insert-or-noop. If the RETURNING set is empty, the second request lost the race. It then re-reads the row and either waits for the in-progress one to complete (with a short timeout and a fallback to 409) or returns 409 immediately. Stripe's documented behavior on a concurrent in-flight: return 409 with the body <code>{"{\"error\": \"idempotency key in use\"}"}</code> and let the client back off. This is correct: the client owns the retry budget; the server's job is to refuse to do duplicate work.</p>
    <p><strong>Postgres advisory locks vs row locks.</strong> Some implementations use <code>pg_advisory_xact_lock(hashtext(key))</code> to serialize concurrent attempts on the same key. Advantage: cleaner than ON CONFLICT semantics, single lock-and-go path. Disadvantage: the hashtext is 64-bit, so collisions are possible at scale (10⁻¹⁰ at 10M keys/day — usually acceptable, but security-critical paths use the full key in a unique index instead). Either approach must hold the lock for the entire request, including any external API calls, which can be tens to hundreds of milliseconds — be mindful of pool exhaustion and watch <code>pg_locks</code> during incidents.</p>
    <p><strong>Distributed cache: Redis Cluster vs database.</strong> At very high write throughput (>10k req/s per shard) the synchronous Postgres write per request becomes the bottleneck. Production systems move the idempotency cache to Redis Cluster with a <code>SETNX key value EX ttl</code> primitive: atomic set-if-not-exists with TTL. Redis Cluster shards by key hash, so each request hits one node. The catch is durability: Redis defaults to async fsync, so a crash within milliseconds of a write can lose the entry. Payment APIs that hold the legal liability for double charges keep the authoritative idempotency record in the transactional database and use Redis only as a hot-path optimization — a Redis miss falls through to the database. Pure Redis is acceptable for non-financial workloads (signups, analytics events) where the impact of a rare duplicate is logging noise rather than a customer-facing error.</p>
    <p><strong>The outbox pattern in detail.</strong> The canonical dual-write problem: an application wants to (1) update its own database and (2) publish an event to Kafka, atomically. Doing both in sequence breaks either way — write DB first then Kafka, and a crash between leaves Kafka silent; write Kafka first then DB, and a crash leaves stale events. Outbox solves it by writing the event TO the database as an "outbox" row, in the same transaction as the business write. A separate outbox-relay process polls the outbox table (or tails the WAL via logical replication) and publishes the events to Kafka, marking the row as published on broker ack. The relay's at-least-once delivery is fine because consumers dedupe via the event's own idempotency key. Patterns: Debezium reads the Postgres WAL and produces a Kafka topic, removing the polling overhead entirely. AWS SAM has a built-in DynamoDB-streams → Lambda → EventBridge variant. The CDC + outbox stack is the "right way" to get effectively-once message delivery in microservices.</p>
    <p><strong>The inbox pattern on consumers.</strong> The mirror image: a consumer reads a stream that may deliver the same event twice. Inbox pattern says: before applying the event's business effect, write the event's id into a <code>processed_events</code> table inside the same transaction as the business write. If the id already exists, skip the business write. This makes consumer processing effectively-once without coordinating with the broker. Pitfall: the inbox table grows forever unless you partition or archive. Production deployments partition the inbox by event timestamp and drop partitions older than the broker's retention window (typically 7–14 days).</p>
    <p><strong>Jitter math: full, equal, decorrelated.</strong> AWS Architecture Blog popularized three jitter variants. <strong>Full jitter</strong>: <code>delay = random(0, min(cap, base × 2^attempt))</code> — smoothest distribution, simplest to implement, the default recommendation. <strong>Equal jitter</strong>: <code>delay = (base × 2^attempt)/2 + random(0, (base × 2^attempt)/2)</code> — half deterministic, half random. Smoother lower bound, harder to reason about. <strong>Decorrelated jitter</strong>: <code>delay = min(cap, random(base, prev_delay × 3))</code> — each retry's window depends on the previous delay, growing organically; commonly used in AWS SDK v3. Empirical AWS data shows full jitter and decorrelated jitter produce nearly identical load profiles; pick whichever your runtime supports natively. Avoid "exponential backoff without jitter" — it is a thundering-herd trap.</p>
    <p><strong>Where to NOT retry.</strong> Retries make sense for transient failures: 5xx, network timeouts, 429 Too Many Requests. They do not make sense for 4xx errors (the client's request is wrong; retrying produces the same 4xx) or for 410 Gone (the resource is permanently absent). Some libraries naively retry every non-2xx, generating retry storms for client bugs. Idempotent retries also must include a budget: capped attempt count plus a global deadline. Tail-latency papers from Netflix and Google demonstrate that uncapped retries amplify tail latencies into outages. The right pattern is "retry budget" — token bucket of allowed retries per second across the whole call site; once the bucket empties, the client breaks the circuit and returns a deterministic error.</p>
    <p><strong>Observability for idempotency + retries.</strong> Minimum viable dashboard exposes: <code>idempotency_key_total</code> sliced by outcome (new / replay / 409 / 422), <code>retry_attempt_total</code> sliced by attempt number, <code>retry_delay_seconds_bucket</code> as a histogram of actual wait times, <code>outbox_lag_seconds</code> (how stale the outbox relay is), <code>dead_letter_queue_depth</code>, and <code>http_request_outcome</code> sliced by status class (2xx / 4xx / 5xx / timeout). A spike in attempt-3 retries precedes an outage by minutes — the canary clients are already paying the cost of an underlying problem before users notice. A growing outbox_lag means the relay or downstream is failing; alert at lag &gt; 30s. A growing DLQ is a permanent failure: poison messages that no amount of retry will fix; have a human review process.</p>
    <p><strong>Production failure stories.</strong> Stripe 2017: a switchover of the idempotency cache from one Redis cluster to another briefly lost in-flight keys, leading to a handful of double charges; Stripe added the cache backed by Postgres as a permanent invariant. Knight Capital 2012: an absent feature flag plus aggressive retries against an exchange feed turned a deployment glitch into $440M in unintended trades in 45 minutes. AWS S3 Sept 2017: an internal subsystem returned 500s during an outage; aggressive retry policies in clients amplified the failure across the region until AWS published guidance to add jitter. GitHub 2018: a database failover lost the lease on an outbox-relay process; events accumulated in the outbox for 2 minutes, then all flushed at once — a self-inflicted thundering herd on the consumer side. Every story has the same root: at-least-once delivery without idempotent consumers, OR retries without jitter.</p>
    <p><strong>History: from MQ Series to gRPC retry policy.</strong> IBM MQ Series in the 1980s shipped "guaranteed delivery" with at-most-once + transactions, but the latency and complexity made it unworkable for the web. Stripe's 2014 blog post on idempotency keys popularized the at-least-once + dedupe pattern for HTTP APIs. RFC drafts followed: <code>draft-idempotency-header</code> in 2020, refined through 2022, parking under <code>draft-ietf-httpapi-idempotency-key-header</code> in 2024. gRPC adopted machine-readable retry policy in its service-config JSON around 2019, exposing <code>maxAttempts</code>, <code>initialBackoff</code>, <code>maxBackoff</code>, and <code>backoffMultiplier</code> per RPC. Envoy and Istio expose retry budgets, retry-on conditions, and per-route retry policy. The pattern is universal now: client backs off + retries; server dedupes; observability covers both.</p>
    <p><strong>Cross-protocol: HTTP, gRPC, Kafka.</strong> HTTP's Idempotency-Key header is the convention. gRPC uses <code>grpc-retry-pushback-ms</code> trailers to suggest backoff and a service-config <code>retryPolicy</code> for client behavior. Kafka exposes idempotent producer (<code>enable.idempotence=true</code>) which guarantees at-most-once delivery per partition via producer-side sequence numbers, plus transactions for cross-partition atomicity. SQS has its own <code>MessageDeduplicationId</code> for FIFO queues. The common thread is "a token that identifies the operation independent of the transport attempt", and a server-side state machine that maps that token to outcomes.</p>
    <p><strong>Deployment patterns: middleware libraries vs hand-rolled.</strong> Hand-rolling idempotency in every endpoint is the wrong default — three weeks in you have inconsistent fingerprint formulas and incompatible TTLs across services. Middleware libraries do it once: Stripe's <code>idempotent-requests</code> middleware (open-sourced), <code>AspNetCore.Idempotency</code>, <code>express-idempotency</code>, <code>django-idempotency-key</code>, <code>fastapi-idempotency</code>. The middleware reads the header, computes the fingerprint, checks the cache, either replays or routes to the handler, then writes the response. The handler is none-the-wiser. At a service-mesh level, Envoy and Istio have request-id-based dedup primitives for sidecars; for serverless, AWS API Gateway has built-in idempotency since 2023.</p>
