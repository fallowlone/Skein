REST modelled rows; OpenAPI froze the wire shape. GraphQL throws both away in favour of a query language where the client picks fields. The client wins flexibility; the server inherits a query planner. When the planner is naive — one resolver per field, one trip per row — the server fires hundreds of database calls for a single request. This is the N+1 problem, and every GraphQL system either solves it deliberately or dies of it slowly.

<Crux>One GraphQL query of 1+N rows fires 1+N DB trips. DataLoader collapses them to 2. Every other GraphQL defence builds on that fix.</Crux>

GraphQL resolves a query by walking the document tree, calling a resolver function for every field the client asked for. Each resolver is independent: it does not know how its siblings will be resolved, it does not see the parent query plan, it just returns the value for its field. That isolation is what makes GraphQL composable — but it is also why nested queries blow up. A list of N posts each needing an author triggers 1 query for the posts plus N independent queries for the authors, with zero coordination. DataLoader and the complexity / depth / persisted-query controls layered on top are not optional extras; they are the operational scaffolding without which production GraphQL falls over.

    <p><strong>What N+1 is in one sentence.</strong> The server does one query to get a list, then N more queries — one per item in the list — to enrich each row.</p>
    <p><strong>Why care.</strong> One harmless-looking GraphQL request can turn into hundreds of database trips, and your API gets slow and expensive long before anyone notices on the client.</p>
    <p><strong>The metaphor.</strong> A restaurant where each table sends the waiter to the kitchen with one order at a time. A table of six orders six trips; ten tables, sixty trips. The kitchen is fast; the waiter spends the shift walking. DataLoader is the manager who says: "Hold tickets until I clap, then bring them all at once." The clap is one tick of the event loop. The tickets are <code>.load(id)</code> calls. The single sweep is one batched database query.</p>
    <p><strong>Bea and Sven.</strong> <PersonaTag id="bea" lang="en" /> the browser asks for <code>posts &#123; title, author &#123; name &#125; &#125;</code> — fifty posts, each with one author. <PersonaTag id="sven" lang="en" /> the server resolves posts, then calls <code>getAuthor(authorId)</code> fifty times — fifty round-trips. The page takes 600ms. Bea wires a DataLoader: <code>authorLoader.load(authorId)</code> instead of <code>getAuthor</code>. Sven now batches the fifty loads into one <code>WHERE id IN (...)</code> query. The page takes 80ms. The schema and client query are unchanged.</p>
    <p><strong>One scenario.</strong> A blog page asks for ten posts and comments on each. Without batching: 1 + 10 = 11 trips. With DataLoader: 1 + 1 = 2 trips. Scale to 50 posts with 20 nested fields and the difference is 1000+ vs ~20.</p>

    <p><strong>Why GraphQL naturally produces N+1.</strong> The GraphQL execution algorithm walks the query document depth-first and breadth-first at each level. For every field the client asks for, it calls the resolver function the server registered for that <code>type.field</code> pair. Resolvers are pure: they receive <code>(parent, args, context, info)</code> and return a value (or a promise). They do not see other resolvers, do not have access to a query plan, and cannot rewrite the SQL. So when the query says <code>posts &#123; author &#123; name &#125; &#125;</code>, the server resolves <code>posts</code> first (one fetch, returns 50 rows), then runs the <code>Post.author</code> resolver 50 separate times — once per post — with the parent argument set to each post object. Each of those 50 invocations independently goes to the database. The query planner that REST controllers have built-in is, in GraphQL, an external concern: you have to add it yourself.</p>
    <p><strong>DataLoader: the standard fix.</strong> DataLoader is a small library, originally extracted from Facebook's GraphQL implementation and maintained as part of the GraphQL Foundation. It provides <code>new DataLoader(batchLoadFn, options)</code> where <code>batchLoadFn(keys: Array&lt;K&gt;)</code> returns <code>Promise&lt;Array&lt;V | Error&gt;&gt;</code> in the same order as the input keys. Resolvers call <code>loader.load(key)</code> and get back a promise. Under the hood, every <code>.load()</code> call enqueues the key into an internal array. When the current synchronous JavaScript turn ends — specifically, when the microtask queue starts draining — DataLoader takes the accumulated keys, calls <code>batchLoadFn</code> once with all of them, and resolves the individual <code>.load()</code> promises from the returned array. It also memoises by key inside the same request, so <code>loader.load(7)</code> twice in the same request returns the same promise both times.</p>
    <p><strong>The per-request instance rule.</strong> A DataLoader instance is a cache. Its lifetime is the request, not the process. If you create a single global DataLoader at server start, every request shares its cache — which means Bea's "load user 7" and Cara's "load user 7" return the same object. That is a tenant-data leak with security and freshness implications: a user updated by one request will not appear updated to another, and a user authorised in one request will be served to another with the cached data even if permissions changed. The discipline is hard: create new DataLoader instances per request, attach them to <code>context</code>, and let GC reclaim them when the request ends. Apollo Server's documentation calls this out explicitly: "DataLoader instances are per-request — if you use a DataLoader in your data source, ensure you create a new instance with every request."</p>
    <p><strong>Batch ordering matters.</strong> The <code>batchLoadFn</code> contract is: given keys <code>[k1, k2, k3]</code>, return values <code>[v1, v2, v3]</code> with the same length and same positions. If the underlying database returns rows in a different order (which Postgres does freely when there is no ORDER BY), the loader maps them wrong — every resolver gets someone else's row. The fix is mechanical: after the SQL <code>WHERE id IN (...)</code>, build a lookup table keyed by id and walk the input keys in order. A common bug: forgetting that a key may have no row, and silently returning the previous row in its slot, which corrupts subsequent positions. DataLoader allows <code>null</code> or an <code>Error</code> in any slot, and you must populate both.</p>
    <p><strong>Beyond DataLoader: lookahead and joins.</strong> DataLoader fixes the "N requests for one column" shape, but it does not solve every variant. If the client asks for <code>posts &#123; author &#123; profile &#123; bio &#125; &#125; &#125;</code>, you still have three levels of resolution, and DataLoader buffers each level independently — three trips, not one. To collapse those further, advanced servers use <em>resolver lookahead</em>: read the <code>info</code> argument's GraphQL AST, see which child fields the client asked for, and join them in one SQL query at the top level. Libraries like Pothos, TypeGraphQL, and Hasura do this by mapping the AST to a SQL query planner. The tradeoff is complexity: lookahead resolvers know about the entire subtree, breaking the per-field isolation that made GraphQL composable in the first place.</p>
    <p><strong>Apollo Federation and the entity-resolver N+1.</strong> In federated GraphQL, multiple subgraphs back a single supergraph. When a query crosses subgraph boundaries — say the <code>users</code> subgraph owns <code>User</code> and the <code>posts</code> subgraph owns <code>Post</code> with a field <code>Post.author: User</code> — the supergraph router asks the users subgraph for each referenced user via <code>_entities(representations: [_Any!]!)</code>. The router automatically batches the representations into one call: if 50 posts reference users, the router sends one <code>_entities</code> request with 50 representations. The users subgraph's <code>__resolveReference</code> implementation must batch internally (DataLoader again) or it will hit the database 50 times within that one call. So federation hands you the cross-service batch for free; you still owe the intra-service batch yourself.</p>
    <p><strong>Persisted queries: trust at the edge.</strong> Persisted queries (also "trusted documents" in the proposed GraphQL-over-HTTP spec) replace the inline query string with a hash. The client registers known queries with the server at build time; at request time it sends only the hash and variables. The server looks up the document and executes it. This collapses an entire class of attacks: arbitrary client-supplied queries are no longer possible, so introspection-driven enumeration, query-complexity attacks, alias batching, and depth bombs are all blocked at the gate. The downside is operational: every client deploy requires a registration step, and ad-hoc tooling (Postman, browser console) no longer works against production. Public APIs that cannot constrain clients (Shopify Storefront, GitHub's Public GraphQL) keep queries open but add complexity scoring; first-party APIs increasingly require persisted queries.</p>
    <p><strong>Complexity scoring and depth limiting: the two-front defence.</strong> Without persisted queries, the server defends by analysing the incoming query before executing it. <em>Depth limiting</em> (typical max 7-10) walks the AST and rejects queries whose nesting exceeds the limit. This stops the trivial <code>user &#123; friend &#123; friend &#123; friend... &#125; &#125; &#125;</code> recursion bomb where a 12-deep query reads exponentially more rows. <em>Complexity scoring</em> assigns a cost to each field — usually <code>cost = 1</code> for scalars and a multiplier <code>cost = limit_arg × child_cost</code> for connection fields. The server sums the costs across the AST, rejects if it exceeds a budget (typical: 1000-10000 cost units per request), and bills clients by cost in pay-per-call APIs. GitHub publishes per-query cost in response extensions; Shopify Storefront caps queries at 1000 units per request and 1000 units/second per IP. Both are AST-only analyses, so they run before any resolver fires — even malicious queries cost no database.</p>
    <p><strong>Batching attacks and alias bombs.</strong> Many GraphQL servers accept an array of operations in one HTTP request (operation batching) or a single document with many top-level aliases (<code>q1: user(id:1) q2: user(id:2) ...</code> repeated 1000 times). Each variant is parsed as a single document but executes thousands of resolvers, each of which may hit the database independently. Operation batching bypasses per-HTTP-request rate limits; alias batching bypasses naive per-document depth checks. Production servers cap operation batch size at 5-10 and alias count per document at 20 by default. Some attacks combine: 10 batched operations, 20 aliases each, 5 levels deep — easily 10000 resolver calls per HTTP request, all under any naive rate limit.</p>
    <p><strong>Introspection: useful in dev, dangerous in prod.</strong> GraphQL ships with introspection (the <code>__schema</code> and <code>__type</code> meta-queries) so tooling can render schemas without external documentation. Attackers use the same endpoint to enumerate every type, field, and argument — and then craft worst-case queries against the schema's expensive corners. Production stance varies: some teams disable introspection in production entirely (Apollo Router default: off in prod), some restrict it to authenticated requests, some leave it on but rely on complexity scoring as the only defence. OWASP's GraphQL cheat sheet recommends disabling unless the API is genuinely public.</p>
    <p><strong>DataLoader memoisation and batch sizing.</strong> DataLoader caches by key inside one request, so the same <code>.load(7)</code> twice returns the same promise — useful when the same entity is referenced from multiple paths in one query (e.g. a Post's author and a Comment's author resolving to the same user). The cache is opt-out via <code>options.cache = false</code> for resolvers that need fresh reads inside one request (rare, but real for write-after-read patterns). <code>options.maxBatchSize</code> caps the keys-per-batch — when a single GraphQL document references 5000 unique authors, a 5000-element <code>WHERE id IN (...)</code> is slower than five 1000-element batches because of Postgres planner overhead. Typical cap: 500-1000 keys per batch, splitting larger sets into multiple <code>batchLoadFn</code> calls. <code>options.batchScheduleFn</code> overrides the tick-boundary dispatch; production rarely uses it, but federation routers sometimes do to align batch boundaries with subgraph request frames.</p>
    <p><strong>Loader patterns: one-to-one, one-to-many, count.</strong> Three shapes cover most cases. <em>One-to-one</em>: key is the parent id, batch returns an array of values, one per key. The classic authorLoader. <em>One-to-many</em>: key is the parent id, batch returns an array of arrays; an empty array for parents with no children is mandatory, otherwise positions shift and resolvers receive someone else's children. The tagsLoader. <em>Count</em>: key is the parent id, batch runs <code>GROUP BY parent_id COUNT(*)</code>, maps results back. The likeCountLoader. A less obvious shape is the <em>composite-key loader</em>, where the key is a tuple (e.g. <code>[userId, date]</code>); for the cache to deduplicate correctly, the key must be stably serialisable, otherwise identical tuples are seen as different keys. The <code>cacheKeyFn</code> option lets you pass a serialiser; standard recommendation is <code>JSON.stringify</code> for objects with fixed field order.</p>
    <p><strong>Error handling in the batch function.</strong> What if the database is down or some keys lack permission? <code>batchLoadFn</code> can return an <code>Error</code> object in a slot instead of a value; DataLoader propagates that error only to the <code>.load()</code> promise that requested it, not to all the others. This is the opposite of <code>throw</code>: throwing from the batch function fails ALL pending <code>.load()</code> promises, which is often too coarse. The right shape is try/catch inside the batch function, turning per-key failures into <code>new Error(...)</code> in their slot, and only catastrophic failures (database down) propagated via throw. Apollo Server by default translates a resolver error into a GraphQL error on the specific field — the client sees a partial response with one <code>null</code> and one error entry, the other fields resolved. The discipline: always return Error for known failures (not-found, no permission), throw only for unknown-fatal (database down, network timeout). Logs aggregate by error type — a per-loader error-rate metric catches degradations.</p>

  <Fragment slot="senior">
    <p><strong>DataLoader's exact scheduling contract.</strong> The library uses <code>enqueuePostPromiseJob</code>, a wrapper over <code>process.nextTick</code> in Node and <code>Promise.resolve().then</code> in browsers, to schedule the batch dispatch. The dispatch runs after the current synchronous frame and after any microtasks queued during it — so all <code>.load()</code> calls made inside resolver bodies, inside <code>.then()</code> chains following resolver synchronous work, and inside any nextTick-deferred logic land in the same batch. The crucial property: this window is bounded by the JavaScript runtime's event-loop semantics, not a timer. There is no setTimeout, no setImmediate, no fixed millisecond window. The batch fires as soon as the runtime is free to drain the microtask queue. For most GraphQL resolvers, that means within microseconds of the last <code>.load()</code> call. The custom <code>batchScheduleFn</code> option exists for the rare case where you want different semantics — for instance, debouncing at the cluster level by holding the batch until a cross-process broker dispatches it, but that is exceptional. Production servers leave the default in place.</p>
    <p><strong>The order-preservation contract and its operational consequences.</strong> <code>batchLoadFn(keys)</code> must return a Promise resolving to an Array with the same length and order as <code>keys</code>. If the underlying data source returns fewer items, the loader resolves missing slots with <code>undefined</code> — which then propagates as a value to resolvers expecting a non-null. If the data source returns more items, the loader silently drops the extras. If the data source returns them in a different order, every <code>.load()</code> promise is resolved with the wrong value. None of these surface as runtime errors. The discipline: always build an explicit <code>Map(keys.map(k =&gt; [k, null]))</code>, walk the rows from the data source filling it in, then <code>return keys.map(k =&gt; map.get(k))</code>. The same shape applies to grouped batches (one-to-many): <code>return keys.map(k =&gt; map.get(k) ?? [])</code>. Skipping the empty-array default for missing-key slots is a category-defining bug: a parent with no children gets some other parent's children, or undefined, or a TypeScript-incompatible <code>null</code>.</p>
    <p><strong>Per-request scope and tenant isolation in code.</strong> Apollo Server's context factory is the canonical place to instantiate per-request DataLoaders: <code>context: async (&#123; req &#125;) =&gt; (&#123; loaders: makeLoaders(req.auth.tenantId) &#125;)</code>. The <code>makeLoaders</code> function returns a new <code>&#123; users: new DataLoader(...), posts: new DataLoader(...) &#125;</code> object on every call. The tenant id flows into the loaders so cross-tenant cache hits cannot happen even on the same key value — the cache key is internally <code>$&#123;tenant&#125;::$&#123;id&#125;</code>, not just <code>id</code>. Forget the tenant scoping and one tenant's data leaks into another's response within the same Node process. This is the single most-CVEd shape in DataLoader misuse: SonarSource's 2024 audit of OSS GraphQL servers found tenant-leak bugs in 6 of the 12 audited codebases, all traceable to module-scope DataLoader or missing tenant in the cache key.</p>
    <p><strong>Apollo Federation: the _entities + __resolveReference contract.</strong> Federation's batching model is fixed by the subgraph spec. Every subgraph that owns an entity type exposes a <code>__resolveReference(representation: &#123;__typename, ...keyFields&#125;)</code> resolver, and the query plan sends batches of representations via the <code>_entities(representations: [_Any!]!): [_Entity]!</code> root field. The supergraph router gathers all references to a given entity type that arose during a query and dispatches them as a single <code>_entities</code> call to the owning subgraph. So the cross-subgraph batching is free — but the per-subgraph fan-out inside <code>_entities</code> is still your problem. A naive subgraph that loops over representations and runs one SQL query per item produces an in-subgraph N+1. The fix is the same DataLoader trick, with the subgraph context's loaders driven by the representations argument: <code>representations.map(r =&gt; loader.load(r.id))</code> turns the 50-rep call into one SQL batch. Apollo's docs recommend this pattern by default in any federated codebase.</p>
    <p><strong>Persisted-query mechanics: APQ vs trusted documents.</strong> Apollo's Automatic Persisted Queries (APQ) is opportunistic: client computes the SHA-256 of the query string, sends only the hash, server returns a 200 if it has the document cached or a special <code>PersistedQueryNotFound</code> error if not. On the latter the client resends with the full document and the hash, server caches it for next time. APQ saves bytes on the wire (a 5KB query collapses to a 64-character hash on warm cache) but does not constrain the query shape — any client can send any document. <em>Trusted documents</em> (in the proposed GraphQL-over-HTTP spec) flip the model: only pre-registered hashes execute, unknown hashes are rejected. Registration happens at client build time via a manifest the server admits before deploy. The first model is a performance optimisation; the second is a security boundary. Production teams that want both deploy trusted documents and use APQ-style hashing inside the registered set.</p>
    <p><strong>Complexity-scoring algorithms.</strong> The two dominant styles. <em>Static field weights</em>: each schema field has a <code>@cost(value: Int!)</code> directive; the analyser walks the AST and sums the costs, multiplied by list-field <code>limit</code> arguments where applicable. Simple to author, easy to game (the analyser is conservative on connection-style schemas). <em>Operation-cost calculator</em> (GitHub's model): every connection's <code>first/last</code> argument is required, costs include both objects and the work to fetch them, and the total is published in <code>extensions.cost</code>. GitHub's GraphQL API caps points at 5000 per hour and per-query at 1000; the cost is computed by analysing arguments and child counts, not just node counts. Shopify Storefront publishes a similar model, capped at 1000 cost/sec per IP and 1000 cost per query. The shared pattern: the analyser runs before any resolver, so an over-budget query never reaches the database — the cost is the wire bytes plus a few microseconds of AST walking.</p>
    <p><strong>Depth limiting: AST walking with list-depth nuance.</strong> A naive depth limiter counts the nesting of field selections — root → user → friends is depth 2. The subtlety: list-valued fields amplify cost exponentially with depth, so the same numeric limit means different things on scalar vs list nesting. The <code>graphile/depth-limit</code> library exposes both <code>maxDepth</code> (scalar depth) and <code>maxListDepth</code> (separate counter, much stricter — typically 3-4). The check runs during the validation phase, before execution; rejection returns a GraphQL error with a stable code, not a database load. Common pitfall: introspection queries are deep (<code>__schema</code> traverses every type's every field), so depth limits must whitelist introspection or also disable introspection in production. Apollo Router's default is to keep introspection on with depth limit 10, but production deployments typically lower this to 7-8 plus a list-depth of 3-4.</p>
    <p><strong>Batching attacks and the alias-bomb shape.</strong> A single GraphQL document can declare hundreds of top-level aliases pointing to the same resolver with different arguments: <code>q1: user(id:1) &#123; email &#125; q2: user(id:2) &#123; email &#125; ... q1000: user(id:1000) &#123; email &#125;</code>. This is a valid document with 1000 root-level fields, parsed once, executed as 1000 resolver invocations. DataLoader collapses the database trips, but the resolver-execution count is still the attack's leverage. Production servers cap alias count per document (typical: 20 root aliases), reject operation batches over 5-10 items, and apply complexity scoring even per-alias. Without these limits, a single curl with a 5MB document can do six-figure resolver counts on one HTTP request, defeating any naive per-request rate limit. Escape.tech's 2024 audit found 64% of production GraphQL endpoints had no alias caps; the Imperva 2023 GraphQL state-of-the-API report attributed 18% of GraphQL-related production incidents to alias-batch DoS.</p>
    <p><strong>Production observability for resolvers.</strong> The minimum-viable dashboard: <code>graphql_request_total</code> by operation_name and outcome, <code>graphql_request_duration_seconds_p99</code>, <code>graphql_resolver_duration_seconds</code> histogram by type.field, <code>graphql_resolver_call_count</code> per request (alerts above N — N+1 is the canonical pattern), <code>graphql_query_cost</code> histogram (alerts on long-tail above the budget), <code>graphql_persisted_query_hit_ratio</code> (warns if it falls below 90% — clients deploying unregistered documents), <code>graphql_introspection_request_total</code> (warns on non-zero in prod with introspection disabled). Per-resolver tracing via OpenTelemetry GraphQL instrumentation emits a span per type.field call; aggregating spans by operation gives you the resolver call counts above. Apollo Router's coprocessor protocol plus their built-in metric set covers the same ground for production deployments. Without this instrumentation, an N+1 regression is invisible until the database CPU pages someone.</p>
    <p><strong>Schema-design discipline as cost defence.</strong> The cheapest defence is the schema itself. Connection fields with optional <code>first/last</code> let clients ask for unbounded lists — require the argument and cap the value (typically 100). Fields that join across boundaries (cross-subgraph in federation, cross-table in a single subgraph) should expose only via connections, never bare arrays. Recursive types (User → friends → friends) should either be capped at the schema level (max 2 nestings via convention + lint rule) or only available via a flat alternative (User.allDescendants with a depth argument). Anti-pattern: a "convenience" field that returns a full subtree (e.g. <code>User.feed</code> resolving 50 posts each with 10 comments each with 5 likes) — every read becomes a 2500-call resolver storm whether the client wanted that or not. Production schemas evolve to push the work back to the client: ask for posts, ask for comments, separately.</p>
    <p><strong>Real production failures.</strong> GitHub 2021: a GraphQL query-cost calculation bug let some queries report a lower cost than their actual database load — under-counted queries bypassed rate limits and triggered API-tier outages; fixed by tightening the cost-calculator definitions. Shopify 2022: a Storefront API deployment shipped a complexity rule with the wrong default that allowed unbounded <code>first</code> on a connection, leading to ~30-minute degraded latency on the Storefront edge; fixed in the next deploy. Apollo Studio 2023: a customer's federated graph had a subgraph that exposed introspection without auth, and an attacker enumerated and built complexity-attack queries against the supergraph; the Apollo Router's complexity limits caught the executions but operations-metrics alerted on the unusual pattern. CVE-2021-41248 (GraphiQL): introspection-driven XSS via crafted schema responses. The pattern across all four: defences exist (cost limits, depth limits, persisted queries, introspection off) but each was missing or misconfigured in one dimension; the layered controls saved the system from worse.</p>
    <p><strong>Cross-protocol bridges.</strong> Many production stacks expose REST and GraphQL side-by-side. Hasura and PostgREST auto-generate GraphQL from a SQL schema; Apollo Connectors do the inverse, declaratively wiring REST endpoints into GraphQL fields. The N+1 pattern persists across translations: a REST endpoint that calls <code>GET /authors/:id</code> per parent does the same database damage whether wrapped in a GraphQL resolver or called directly from a client SDK. Connectors-style binding (declaring "this GraphQL field reads from this REST endpoint with these parameters") moves the batching to the binding layer — the supergraph router can group representations into a single batched HTTP call when the REST endpoint supports it (e.g. <code>GET /authors?ids=7,9,11</code>). Without such a batched REST endpoint, the connector falls back to per-item calls, and N+1 returns in REST clothes.</p>
    <p><strong>The GraphQL-over-HTTP spec and trusted documents.</strong> The IETF/GraphQL Foundation joint draft for GraphQL-over-HTTP (status: working group draft as of 2025) is consolidating the wire-protocol semantics that have been ad-hoc across servers. Trusted documents are part of that proposal: a server-side allow-list of operation hashes, optionally with required variable shape constraints, that bounds the query surface to the developer-vetted set. The draft also clarifies persisted-query negotiation, error response formats, and content-type rules. Combined with the OWASP cheat-sheet's defensive guidance, a 2026-grade GraphQL deployment looks like: trusted documents required, introspection off in prod, depth limit 7 and list-depth 3, complexity budget 1000-10000 per query, alias cap 20, op-batch cap 5, DataLoader instances per request scoped by tenant, and per-resolver tracing emitting OpenTelemetry spans tagged with the persisted-query hash for postmortem replay.</p>
