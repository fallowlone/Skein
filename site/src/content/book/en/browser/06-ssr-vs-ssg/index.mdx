A user requests a page. Somewhere a tree of components turns into an HTML string, travels the wire, paints, and then — the part everyone forgets — becomes interactive. That last step has a name and a price: hydration. Every render strategy is a different answer to two questions: *when* do we produce the HTML, and *what* does it cost to make that HTML come alive in the browser. Get the first question wrong and the page is slow to appear; get the second wrong and the page appears fast but cannot be clicked.

<Crux>SSR, SSG, ISR, streaming — *when* to render the HTML. Hydration — the price to make that HTML interactive.</Crux>

The strategies split on timing. **SSG** renders at build time — HTML is a file on a CDN. **SSR** renders per request — fresh, but the server works on every hit. **ISR** is SSG that refreshes itself on a schedule or on demand. **Streaming SSR** sends the HTML in chunks as it is ready instead of waiting for the whole page. And cutting across all of them: **hydration** is React (or any framework) re-running on the client to attach event handlers and state to the server's HTML — the work that turns a picture of an app into an app.

  <Fragment slot="middle">
    <p><strong>SSG: render at build time.</strong> Static Site Generation runs the components once, during the build, and writes the result to HTML files. Those files are deployed to a CDN and served as static assets. The request path is unbeatable — no server compute, an edge cache hit, time-to-first-byte in the tens of milliseconds. The cost is freshness and scale: the content is frozen at build time, and a site with a million pages takes a long time to build. SSG is the right default for anything whose content does not change per request and per user: marketing pages, docs, blog posts. The moment the page must reflect "now" or "this specific user", pure SSG breaks down.</p>

    <p><strong>SSR: render per request.</strong> Server-Side Rendering runs the components on the server for every request, producing fresh HTML each time. It can read the user's cookies, the current time, live data — the HTML is exactly right for this request. The cost is on the critical path: the user's time-to-first-byte now includes the server's render time plus any data fetching it does. A slow database query in the render is a slow TTFB for the user. SSR also means you run and pay for server capacity that scales with traffic. SSR is right when the page genuinely must be per-request fresh or per-user personalised — a logged-in dashboard, a feed, search results.</p>

    <p><strong>ISR: SSG that refreshes itself.</strong> Incremental Static Regeneration (the Next.js term; other frameworks have equivalents) is SSG with a revalidation rule. The page is served static from cache, but after a configured time — or on an explicit on-demand trigger — the next request gets the stale copy <em>while</em> the server regenerates a fresh one in the background; subsequent requests get the new version. It is `stale-while-revalidate` applied to whole pages. ISR is the answer to "mostly static, but the content does change — a product page whose price updates a few times a day." You get SSG's instant delivery for the overwhelming majority of requests and bounded staleness instead of a full rebuild.</p>

    <p><strong>Streaming SSR: send the HTML in chunks.</strong> Plain SSR has a blocking flaw: the server must finish rendering the <em>entire</em> page — including its slowest data fetch — before it can send a single byte. If one widget needs a 400 ms query, every user waits 400 ms for time-to-first-byte. Streaming SSR fixes this. With `renderToPipeableStream`, the server sends the shell immediately, and each `<Suspense>` boundary streams in as its data resolves. The user sees the header, nav, and layout in ~50 ms; the slow widget arrives 400 ms later as a streamed chunk that the browser slots into place. TTFB drops to the speed of the fastest part of the page, not the slowest. Streaming turns "the page waits for its worst query" into "the page appears immediately and fills in."</p>

    <p><strong>React Server Components: components that never ship to the client.</strong> RSC is a different axis entirely. A Server Component runs only on the server — its code is never sent to the browser. It can read the database directly, use server-only secrets, and import heavy libraries (a markdown parser, a syntax highlighter) that cost the client nothing because they never cross the wire. Its output is not HTML and not a JS bundle — it is a special serialized format, the RSC payload, describing the rendered tree. Client Components (marked `'use client'`) are the interactive islands within that tree; only their code ships. The win is bundle size: the parts of your app that are just "display server data" carry zero client JavaScript, so there is nothing to download and nothing to hydrate for them.</p>

    <p><strong>Hydration: the price of interactivity.</strong> Server rendering gives you HTML — pixels, fast. But that HTML has no event handlers, no state, no effects. Hydration is the client-side process that fixes this: the framework downloads its JavaScript, walks the same component tree the server walked, and — instead of creating DOM nodes — <em>adopts</em> the existing server DOM, attaching event listeners and wiring up state and effects. `hydrateRoot` is React's entry point for it. The mental model: the server render produced a body; hydration is the framework re-running to put a nervous system into that body. Until hydration completes for a given part of the tree, that part is visible but inert — and that gap is where INP regressions and "I clicked and nothing happened" bugs live.</p>

    <p><strong>Why hydration is expensive.</strong> Hydration roughly doubles render work — the tree is rendered once on the server and effectively rendered again on the client. But it is worse than a doubling, because the client render runs on the <em>user's</em> device, which may be a mid-range phone an order of magnitude slower than your server. And it is all main-thread JavaScript: downloading the bundle, parsing and compiling it (V8 work), then running the component tree and attaching handlers. On a large app this is hundreds of milliseconds to seconds of main-thread time during which the page looks done but is not. The whole modern evolution of render strategies — selective, progressive, islands, resumability — is a series of attacks on this one cost.</p>

    <p><strong>Full vs selective hydration.</strong> Classic React hydration is <em>full and eager</em>: the whole app hydrates in one pass before anything is interactive, and it is blocking. React 18 introduced <em>selective hydration</em>: with `Suspense` boundaries, parts of the tree hydrate independently, and React prioritises hydrating whatever the user just interacted with. If the user clicks a not-yet-hydrated section, React hydrates that section first, ahead of the rest. It also makes hydration interruptible — it can yield to input mid-hydration. Selective hydration does not remove the total cost; it reorders it so the cost lands where the user is not looking and the part they touched comes alive first.</p>

    <p><strong>Progressive hydration and the islands architecture.</strong> The deeper fix is to hydrate <em>less</em>. The islands architecture (Astro, Marko, Fresh) starts from the opposite default: the page is static HTML, and only the specific interactive components — the "islands" — ship JavaScript and hydrate. A blog post is 95% text: with islands, that 95% ships zero JavaScript and never hydrates, and only the comment box and the like button — the actual islands — carry JS. Each island hydrates independently, and can be told <em>when</em> to (`client:visible` hydrates on scroll into view, `client:idle` when the main thread is free). This is progressive hydration: the page is interactive where it needs to be, inert and free everywhere else.</p>

    <p><strong>Resumability: skipping hydration entirely.</strong> Qwik pushes the idea to its limit with <em>resumability</em>. Instead of re-running the component tree on the client to rebuild state and handlers, Qwik serializes the entire application state — including which handler is attached where — into the HTML itself. The client does not re-render to hydrate; it <em>resumes</em> from the serialized state, attaching a handler only when the user actually interacts with that specific element. Startup JavaScript approaches zero regardless of app size. The trade-off is a more complex serialization format and a framework built around it from the ground up — but conceptually it is the endpoint of the whole progression: from "hydrate everything" to "hydrate what the user touched" to "do not hydrate at all, just resume."</p>

    <p><strong>The hydration mismatch.</strong> Hydration assumes the client's first render produces exactly the DOM the server produced. When it does not, you get a <em>hydration mismatch</em>. Causes: rendering `new Date()` or `Math.random()` (server time ≠ client time), reading `window` or `localStorage` during render (undefined on the server), locale or timezone differences, or browser extensions mutating the DOM before hydration. React detects the divergence, and historically discarded the server HTML for the mismatched subtree and re-rendered it on the client — a visible content flash plus a CLS spike. The fix is to make the first client render deterministically equal to the server render: defer client-only values to a post-hydration `useEffect`, or gate them behind a mounted flag so both renders agree on the first pass. The same trap applies to data: if the server renders from one snapshot of an API response and the client refetches a newer one before hydrating, the trees diverge. Frameworks solve this by embedding the server's data in the HTML — the dehydrated query cache — so the client's first render uses the exact same data and only fetches fresh afterward — the data, like the time and the locale, must be identical on both sides of the hydration boundary.</p>

    <h4 class="mt-2 mb-3 text-[15px] font-semibold text-ink tracking-tight">Failure mode: the hydration mismatch</h4>
    <p><strong>The mechanism, precisely.</strong> Hydration is a contract: the DOM the client produces on its first render must be structurally identical to the DOM the server serialized. React walks the server DOM and the client's virtual tree in lockstep, adopting each node. When a node disagrees — different text, different attributes, a different element, an extra or missing child — the contract is broken. React's recovery has tightened over versions: it logs a mismatch error and, for the affected subtree, throws away the server HTML and client-renders it from scratch. That recovery render is the visible symptom: a flash of changed content and a layout shift that spikes CLS. The common causes are all forms of non-determinism between the two environments — `Date.now()`, `Math.random()`, `window`/`document`/`localStorage` read during render, `Intl` formatting that depends on locale or timezone, `typeof window` branches, and browser extensions that mutate the DOM before React hydrates. The cure is determinism: the first client render must be a pure function of the same inputs the server had. Client-only values move into `useEffect` (which runs after hydration), or behind a `useState(false)` "mounted" flag flipped in an effect, so both the server render and the first client render produce the placeholder and only the second client render shows the live value. A second, often-missed point: the same constraint applies to data. If the server renders from a snapshot of an API response and the client refetches and gets a newer one before hydrating, the trees diverge — so the server's serialized data must be embedded in the HTML and reused by the client for the first render, never refetched. This is exactly what frameworks do with the dehydrated query cache (React Query, Apollo): serialize the server's data, rehydrate it on the client, render the first pass from it, and only then allow fresh fetches.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Streaming SSR internals</h4>
    <p><strong>How the stream is assembled.</strong> `renderToPipeableStream` renders the tree depth-first and flushes the shell — everything outside any pending `Suspense` boundary — as soon as it is ready. For each `Suspense` boundary whose data has not resolved, the server emits the fallback inline and keeps the connection open. When a boundary's data resolves, the server renders that boundary's real content and writes it down the same connection as a chunk: a hidden `<div>` carrying the content plus a tiny inline `<script>` that relocates it into the right slot and removes the fallback. The browser, parsing HTML progressively, executes that script the moment the chunk arrives. This is why streaming works without client framework code being involved for the placement itself — the relocation is plain DOM scripting embedded in the stream. The ordering is interesting: boundaries stream in <em>completion order</em>, not document order, so a fast widget low on the page can arrive before a slow widget above it.</p>

    <p><strong>Streaming and hydration interleave.</strong> Streaming SSR and selective hydration are designed to compose. As each `Suspense` boundary's HTML streams in, React on the client can hydrate that boundary independently — it does not wait for the whole document. And if the user interacts with an already-streamed-but-not-yet-hydrated boundary, React records the event and prioritises hydrating that boundary first, then replays the event. The result is that "streamed in" and "hydrated" are both per-boundary and both prioritised by user attention. The senior implication: where you place `Suspense` boundaries is a performance design decision, not just an error/loading-state decision. A boundary around a slow, below-the-fold widget lets the rest of the page stream and hydrate without waiting for it; no boundary, and that widget blocks the whole document.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">RSC: the payload and the boundary</h4>
    <p><strong>What actually crosses the wire.</strong> An RSC render produces two things. The initial request gets HTML (Server Components rendered to HTML, streamed) <em>plus</em> the RSC payload — a serialized, line-delimited description of the component tree, where Client Components appear as references ("module X, props Y") rather than as code. On client navigation, only the RSC payload is fetched, not a fresh HTML document — React applies it to the existing tree. The `'use client'` directive marks the boundary: a module with that directive, and everything it imports, is in the client bundle; everything above it in the tree is server-only. A subtle and frequently-missed rule: props passed from a Server Component to a Client Component must be serializable — they cross the wire in the payload. You cannot pass a function, a class instance, or a Date-with-methods as a prop across that boundary. Getting the boundary placement right — pushing `'use client'` as far down the tree as possible — is what minimises the client bundle.</p>

    <p><strong>RSC is not a replacement for SSR — it composes with it.</strong> A common confusion: RSC and SSR are different axes. SSR is "where does the HTML get generated"; RSC is "which components ship code to the client at all." A production Next.js App Router page typically uses both: Server Components run on the server and produce HTML via SSR (often streamed), and the Client Components within are also server-rendered to HTML for first paint and <em>then hydrated</em>. RSC reduces how much there is to hydrate (Server Components never hydrate — they have no client code); SSR/streaming controls when the HTML appears. They are orthogonal tools that a modern framework uses together.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">The hydration cost model in depth</h4>
    <p><strong>Where the milliseconds go.</strong> Hydration's cost has four parts, all on the main thread, all after the HTML has already painted. One: <em>download</em> the JavaScript bundle — network-bound, mitigated by code-splitting and compression. Two: <em>parse and compile</em> the JavaScript — V8 work, scaling with bundle bytes, brutal on low-end mobile CPUs. Three: <em>execute</em> — run the module top level and the component tree to rebuild the virtual tree. Four: <em>attach</em> — walk the server DOM adopting nodes and wiring handlers. Parts two and three are why bundle size matters beyond download time: a 500 KB bundle is not just 500 KB of network, it is hundreds of milliseconds of parse-compile-execute on a phone. This whole window is the "uncanny valley" of SSR — the page is painted and looks interactive, the user tries to interact, and the input is either dropped or queued behind the hydration long task, spiking INP. Measuring it: the gap between First Contentful Paint and Time to Interactive, and field INP on interactions that happen early in the page's life.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Choosing a strategy: the decision frame</h4>
    <p><strong>Per-route, not per-app.</strong> The senior mistake is picking one strategy for a whole application. Modern frameworks let you choose per route, and you should. The decision frame: is the content the same for everyone? If yes and it rarely changes — SSG. If yes and it changes on a known cadence — ISR. Is it per-user or per-request fresh? Then SSR, and if any part of it has a slow data dependency, streaming SSR with a `Suspense` boundary around the slow part. Is a route mostly static content with a few interactive bits? That is the islands case — and even within React, that maps to mostly Server Components with small `'use client'` leaves. The marketing homepage, the docs, the blog: SSG. The pricing page with a daily-changing number: ISR. The logged-in dashboard: streaming SSR. The same app, three strategies, chosen by the nature of each route's data and interactivity.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Production observability</h4>
    <p><strong>What to measure and where it breaks.</strong> Four signals catch the failure modes of this whole space. <em>TTFB</em> in the field separates a slow server render or a missing cache from a fast one — a TTFB regression on an SSR route usually means a slow data fetch crept into the render path. <em>LCP</em> tells you whether the largest content is in the streamed shell or stuck behind a slow boundary. <em>INP</em> on early interactions is the hydration-uncanny-valley detector: a high INP only for interactions in the first few seconds is hydration blocking the main thread. <em>Hydration mismatch errors</em> should be wired to telemetry, not just the console — they cause CLS and re-render cost, and they are invisible unless you collect them. The CI gate: a synthetic test that loads each route type, asserts no hydration-mismatch errors, and budgets the FCP-to-TTI gap. Without that gate, a non-deterministic render or a bundle-size regression ships silently and only shows up as field INP weeks later.</p>

<Misconception id="mc-hydration-mismatch">
**Myth:** Server-rendered means fast — if the HTML painted, the page is ready.

**Reality:** Painted is not interactive. Hydration must download, parse, and run the JS to attach handlers — until it finishes, buttons are dead. "Looks ready" and "works" are different moments, and the gap is where INP regressions live.
</Misconception>

<p class="text-ink-2 my-6">Hydration is, at bottom, a question of state: the server produced a render whose state — the props, the data, the moment in time — must be reconstructed identically on the client, or the contract breaks. SSG freezes that state at build; SSR captures it per request; resumability serializes it whole so the client never recomputes it. Every strategy here is a different decision about which state is captured when, and what it costs to carry it across the wire — the same statefulness question that decides whether a connection is cheap to resume or expensive to rebuild. <SpiralCue thread="statefulness" lang="en" /></p>
