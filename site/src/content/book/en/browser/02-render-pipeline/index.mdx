You hit Enter on a URL. Bytes start arriving. Somewhere between the first packet and the moment a button is clickable on screen, the browser ran a six-stage pipeline — and most pages spend the wrong amount of time in the wrong stage. The frame budget is 16.67 ms at 60 fps. If layout takes 12 ms, nothing else gets to finish, the frame drops, and the user sees jank.

<Crux>From bytes off the wire to pixels on screen — where does the time go?</Crux>

Two threads do the work. The **main thread** owns Parse HTML, CSSOM construction, style recalc, layout, and paint setup. The **compositor thread** assembles GPU-friendly layers and ships them to the GPU. Animations that stay on the compositor cost almost nothing per frame. Animations that fall back to layout cost the entire budget. The whole craft of render performance is keeping the work on the right thread.

    <p><strong>What the browser does in one sentence.</strong> It takes HTML + CSS + JS off the wire and turns them into pixels in six stages: read the markup, read the styles, decide which styles win, measure the boxes, fill in the pixels, glue the layers onto the screen.</p>
    <p><strong>The kitchen metaphor.</strong> The browser is a restaurant kitchen. Parsing HTML is reading the order ticket. CSSOM is reading the recipe book. Style is matching ingredients to dishes. Layout is measuring the plate and arranging food on it. Paint is doing the actual cooking — heat and colour. Composite is the runner picking up six plates at once and walking them to the table. If any station is slow, the whole table waits.</p>
    <p><strong>Why care.</strong> You hit 60 frames per second only if the whole kitchen finishes in 16.67 ms. Drop a frame and the user sees a stutter — a scrolling list judders, a button feels sticky, a chart lags behind the mouse. The fix is almost never "make JS faster" — it's "stop the kitchen from re-doing layout when it could have just rearranged plates."</p>

    <p><strong>The six stages, with cost shape and DevTools label.</strong> Read top-to-bottom: each stage's input is the previous stage's output.</p>

    | Stage | Owner thread | Cost driver | DevTools label |
    | --- | --- | --- | --- |
    | Parse HTML | Main | Document size, blocking scripts | `Parse HTML` |
    | Build CSSOM | Main | Stylesheet count, rule count | `Parse Stylesheet` |
    | Style calc | Main | DOM size × selector complexity | `Recalculate Style` |
    | Layout | Main | DOM depth × box dependencies | `Layout` |
    | Paint | Main | Painted area × paint op count | `Paint` |

    <p><strong>The renderer process model.</strong> A modern Chromium-family browser runs each tab in its own renderer process. Inside that process: the <strong>main thread</strong> runs HTML parsing, CSSOM construction, style, layout, paint setup, and your JavaScript. The <strong>compositor thread</strong> assembles the layer tree and decides which layers need new bitmaps. <strong>Raster worker threads</strong> rasterise individual tiles in parallel. A separate <strong>GPU process</strong> takes the rasterised tiles, uploads them as textures, and runs the final composite-and-display. Firefox uses a similar split (Quantum CSS for parallel style, WebRender for GPU-driven compositing); Safari/WebKit splits the work across its WebContent process and the GPU process too. Names differ; the architecture rhyme is universal.</p>

    <p><strong>Why the main thread is the bottleneck.</strong> The main thread is single-threaded by design — DOM, CSSOM, and JS state can only be mutated by one execution context at a time, otherwise consistency would be impossible. That means any work you put on the main thread (parsing a JSON blob, deserialising a Redux state, running a layout, executing a click handler) competes for the same 16.67 ms window. The compositor and raster threads exist precisely so a chunk of rendering work can leave the main thread and run in parallel — which is the architectural justification for transform/opacity animations being "free": they reach the GPU without touching the bottleneck thread.</p>

    <p><strong>The invalidation rule.</strong> Changing a CSS property invalidates one or more stages. Width and height invalidate layout (everything downstream re-runs). Background-color invalidates paint only. Transform and opacity invalidate composite only — the GPU restages the same bitmap at a new position. <a href="https://csstriggers.com/">csstriggers.com</a> publishes a per-property map; learn the cheap ones (transform, opacity, filter) and the expensive ones (top, left, width, height, anything that affects flow).</p>

    <p><strong>How invalidation propagates.</strong> Each stage marks its output dirty when an input changes. Style flags propagate via the DOM tree (a class change on a parent dirties all descendants whose selectors match). Layout flags propagate via the box tree (a width change to a parent may dirty siblings if their position depends on it). Paint flags propagate via the paint tree (a paint-affecting change on a layer invalidates that layer's bitmap; sibling layers are unaffected if they have their own bitmap). Composite is the dirt-free stage — it works from already-rasterised tiles and only re-runs the GPU draw call. The clean propagation rule: <em>dirty bits flow down the dependency graph, not up</em>. If you can isolate your changes to an independent subtree (a contained layer, a `contain: layout` parent, a `content-visibility: auto` element), the invalidation stops at the isolation boundary.</p>

    <p><strong>Stage-by-stage cost amplifiers.</strong> Each stage has typical levers that blow up its cost. Parse HTML scales with document bytes; a 500 KB SSR-rendered page parses faster than a 2 MB one, simply because there is less to walk. Synchronous `<script>` tags block the parser until they finish downloading and executing — modern best practice puts `defer` or `async` on every external script not strictly needed for first paint. CSSOM cost grows with stylesheet bytes and rule count; an unused 800-rule CSS framework wastes parse time even if zero rules actually match anything on the page. Style calc cost is roughly <code>DOM size × selectors</code>: a 5 000-node DOM with a 2 000-rule stylesheet is 10 million selector-match checks. Most selectors are skipped via a bloom filter, but `:has()`, descendant combinators with no ancestor anchor, and universal selectors defeat the filter and cost more. Layout cost is roughly <code>DOM depth × box dependencies</code>: a deeply nested flexbox with auto sizing forces multiple measure passes; a flat grid with explicit cell sizes is one pass. Paint cost is painted area × paint op count; box-shadow with a large blur radius and filter properties (blur, drop-shadow) are paint-heavy because each pixel requires multi-pixel sampling. Composite cost is layer count × layer pixel area. The cheap stages are cheap by orders of magnitude, but only if the upstream stages don't invalidate downstream.</p>

    <p><strong>How the browser reaches the compositor.</strong> Some elements get their own layer: those with <code>transform: translate3d(...)</code>, <code>will-change: transform</code>, <code>position: fixed</code>, video, canvas, animated opacity, and a few other triggers. Each layer is rasterised once (paint), uploaded to the GPU, and then re-composited cheaply for the next thousand frames. Animating a layer's transform is "free" — the main thread can sleep. Animating its <code>top</code> is expensive — the main thread re-lays-out the world every frame.</p>

    <p><strong>Layer creation rules in detail.</strong> Promotion to a layer is not always under your control. Implicit promotions happen for: 3D transforms (anything with a `Z` component or `translate3d`), elements with `will-change` listing a compositable property, position-fixed elements, video, canvas, opacity that is currently being animated, `filter: blur(...)` and other graphical filters, isolated <Term k="stacking_context" lang="en">stacking contexts</Term> that overlap a layer. There are also <em>compositing reasons</em> the browser invents itself: an element must be promoted if it overlaps another layer and would otherwise be cut into pieces by it. This is why a single innocent `transform` can suddenly promote a dozen sibling elements — the compositor's invariant is that layers must not visibly cross each other without being layered. Use DevTools' Rendering panel ("Layer Borders") to see what is promoted; you will often find the page has more layers than you expected.</p>

    <p><strong>Reading a DevTools Performance flame strip.</strong> Open DevTools → Performance, click record, do whatever caused the jank, stop recording. The "Main" track shows main-thread work coloured by category: yellow for scripting, purple for rendering (layout + style), green for paint, dark blue for compositing. The "Frames" track shows green for on-time frames, yellow for late, red for dropped. The flame strip stacks calls top-down: the top bar is what JS triggered, each bar below is what that called. Find a long bar in red or yellow — that is your bottleneck. Hover to see exact ms. Common patterns: a yellow JS bar followed by a purple Layout bar of similar length means your JS triggered a forced sync layout (one of the most common bugs). A wide purple Recalculate Style after a class change on a high-up ancestor means you cascaded too much. A wide green Paint after a `filter: blur(...)` change means you exceeded paint complexity. A wide dark-blue Composite Layers when nothing else looks wrong means too many layers, often from will-change abuse.</p>

    <p><strong>Modern optimisation toggles: contain and content-visibility.</strong> CSS Containment gives you a knob to cap how far invalidation can propagate. <code>contain: layout</code> tells the browser "this element's layout cannot affect its ancestors" — if a child resizes, the parent's siblings do not need to re-layout. <code>contain: paint</code> guarantees painting is contained inside the box (anything overflowing is clipped) and allows the browser to skip painting it entirely when off-screen. <code>contain: strict</code> combines layout, paint, and size containment. The newer <code>content-visibility: auto</code> property goes further: it tells the browser "this element may be skipped entirely (no layout, no paint) when it is off-screen." Combined with <code>contain-intrinsic-size</code> (which gives the browser a placeholder size to reserve), it lets a page with thousands of below-the-fold elements render in milliseconds because only on-screen elements pay the cost. These are the modern "free wins" for any page rendering large lists, infinite scroll feeds, or long-form content.</p>

    <p><strong>Frame lifecycle and scheduler order.</strong> Inside one frame the browser runs work in a strict order: (1) collect input events (mousemove, keypress); (2) run scheduled `setTimeout` and `setInterval` callbacks if their time has elapsed; (3) run microtasks (promise resolutions) until the queue is empty; (4) run `requestAnimationFrame` callbacks; (5) run ResizeObserver and IntersectionObserver callbacks; (6) compute style and layout; (7) paint; (8) composite. After step 8 the browser yields to the OS and waits for the next <Term k="vsync" lang="en">vsync</Term>. The crucial property: rAF runs <em>before</em> style/layout, so a write inside rAF is followed by exactly one layout pass for the frame — that is the entire purpose of rAF. ResizeObserver fires <em>after</em> layout but <em>before</em> paint; you can use it to react to layout changes without triggering another forced layout. IntersectionObserver fires asynchronously across frames, never blocking the current one. Understanding this order is what separates "scheduling tricks that work" from "scheduling tricks that quietly thrash."</p>

    <p><strong>Microtasks vs tasks: how scheduling boundaries work.</strong> The microtask queue (promises, queueMicrotask) drains to empty between every step of the event loop, including between rAF callbacks. A misbehaving promise chain that schedules itself indefinitely starves rendering — the browser cannot reach step 6 until the queue empties. This is why long promise chains and tight `await` loops are visible in DevTools as a single uninterrupted yellow scripting bar, not a series of small ones. Modern code that wants to yield to the renderer mid-task uses `scheduler.yield()` (Scheduler API, Chrome 115+) or a deliberate `setTimeout(fn, 0)` to drop work onto the macrotask queue and unblock rendering.</p>

    <h4 class="mt-2 mb-3 text-[15px] font-semibold text-ink tracking-tight">Failure mode: layout thrash</h4>
    <p><strong>Forced synchronous layout (layout thrash).</strong> Layout is dirty-flag-driven: the browser batches style writes and only flushes them when it needs the latest geometry. The pathological case is a read-then-write loop in JS:</p>

```javascript
for (const row of rows) {
  const w = row.offsetWidth;     // read → forces flush of pending writes
  row.style.width = w + 10 + 'px'; // write → marks layout dirty again
}
```

    <p>Each iteration forces the browser to compute layout to answer <code>offsetWidth</code>, then immediately dirties layout for the next iteration. N rows = N full layouts. A 5000-row list at 1 ms per layout = 5 seconds of main-thread blocking. DevTools shows this as a violet "Layout" bar followed by a "Forced reflow while executing JavaScript took XX ms" console warning.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Compositor layers and GPU memory</h4>
    <p><strong>Compositor layer creation.</strong> Layers are not free. Each layer is a GPU bitmap that costs memory (width × height × 4 bytes) and a one-time paint. On a phone with 256 MB of GPU memory, fifty 1080p layers exhausts the budget; the browser evicts layers, re-rasterises on the fly, and the page stutters more than if you had not asked for layers at all. <code>will-change: transform</code> is a hint that says "this element will animate, please promote to a layer." Use it for the duration of the animation and remove it afterwards. Slapping <code>will-change: *</code> on a hundred elements is the will-change anti-pattern — you trade a known animation cost for an unknown memory bill.</p>

    <p><strong>Why composite-only animations are special.</strong> Once an element is a layer, the main thread paints it once. From that point the compositor thread is the only consumer of <code>transform</code> and <code>opacity</code> changes; the main thread can be busy parsing a 200 KB JSON blob and the animation still runs at 60 fps. This is the architectural reason transform-based animations beat top/left animations by orders of magnitude — not "GPU is faster," but "the slow thread is no longer in the loop."</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Two-thread architecture: BeginMainFrame</h4>
    <p><strong>BeginMainFrame: the handshake between threads.</strong> In Chromium's renderer process, the compositor thread is the driver and the main thread is the worker. Each vsync the compositor sends a <code>BeginMainFrame</code> message to the main thread. The main thread runs all the per-frame work (rAF callbacks, style, layout, paint setup) and then sends a <code>CommitMainFrame</code> message back, handing off a new layer tree. The compositor takes the new layer tree, asks raster workers to fill any dirty tiles with bitmaps, then performs the GPU draw. If the main thread is too slow, the compositor does not wait: it ships the previous frame's tree again (a frame is "drawn but stale"), which the user perceives as missed input or a stutter. This is the deep reason main-thread work cannot exceed the frame budget: the compositor is a relentless metronome that does not negotiate. <code>BeginMainFrame</code> arrives every ~16.67 ms whether you are ready or not.</p>

    <p><strong>Compositor-driven animations (CSS animations on transform/opacity).</strong> When you write a CSS animation that only changes <code>transform</code> or <code>opacity</code> on a compositor-promoted element, the browser detects this at animation-start and hands the animation's timeline directly to the compositor thread. From that point the main thread is no longer involved at all — the compositor interpolates the value frame-by-frame and renders the next bitmap directly. This is why a CSS animation can keep running smoothly even when the main thread is completely blocked (an alert dialog, a long synchronous parse, a debugger pause): the compositor still runs. The same animation written in JS via rAF cannot do this, because rAF runs <em>on the main thread</em>, so a blocked main thread freezes the animation. Compositor-driven CSS animations are the only way to guarantee animation continuity under main-thread pressure.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Compositor edge cases</h4>
    <p><strong>Layer squashing and overlap-induced promotion.</strong> A subtle source of "layer explosion" is the overlap rule. The compositor must maintain visual correctness: if element A is layered (say, because it has `transform`) and element B paints on top of A in the document order without itself being layered, the compositor cannot resolve their stacking — A's layer would appear on top of B even though B is supposed to be on top. The browser fixes this by promoting B to its own layer too, often dragging adjacent elements with it. The compositor then squashes adjacent non-animating layers into a shared "squashed" layer to limit explosion, but the heuristic is imperfect. A single innocent `will-change: transform` on a card in the middle of a feed can promote a dozen siblings. Use DevTools' Rendering panel → "Layer Borders" to visualise this; pay attention to layers labelled "compositor-induced" or "overlap" — those are the ones that crept in without your asking.</p>

    <p><strong>Off-main-thread scroll.</strong> Browsers have shipped compositor-thread scrolling for a decade: when the user scrolls a normal page, the compositor translates the viewport on the GPU without touching the main thread. This is why a page can scroll smoothly even while a long JS task runs. The catch: any element with a JS scroll handler attached <em>non-passively</em> (without <code>&#123;passive: true&#125;</code>) forces the browser to fall back to main-thread scrolling, because the handler might call <code>preventDefault()</code>. Always pass <code>passive: true</code> to scroll, wheel, and touchmove listeners unless you actually need to call preventDefault. Modern browsers warn in DevTools when a non-passive listener delays scrolling — the warning is one of the most reliable signals you have a main-thread scroll regression.</p>

    <p><strong>content-visibility: auto and display locking.</strong> The mechanism behind <code>content-visibility: auto</code> is "display locking": the browser pauses rendering for the locked subtree (no style calc, no layout, no paint) and replaces it with an intrinsic-size placeholder. When the subtree intersects the viewport (via the browser's internal IntersectionObserver), it is unlocked and rendered. This turns a 10 000-row table that previously cost 1 200 ms of style + layout into a ~10 ms first-paint with on-demand rendering as the user scrolls. The trade-off: scrolling into a previously locked region briefly pauses to render it; if your rows are expensive, you can see a single-frame stutter at the unlock boundary. Pair with <code>contain-intrinsic-size</code> to give the browser a realistic placeholder size so scroll position is not jumpy.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Production observability</h4>
    <p><strong>Long animation frames and INP.</strong> Two newer browser APIs surface the render pipeline's failure modes. <code>PerformanceLongAnimationFrameTiming</code> (LoAF, shipped 2023–2024 in Chromium) reports any frame that took longer than 50 ms, with a breakdown of what dominated: render time, blocking JS, forced layout. <strong>INP</strong> (Interaction to Next Paint) measures the time from a user input event (click, key, tap) to the next paint that visibly responds. INP became a Core Web Vital in March 2024, replacing FID. A poor INP score (> 200 ms p75) almost always traces to one of two pipeline problems: a long JS task on the input handler delaying rAF, or a forced sync layout caused by reading geometry inside the handler. LoAF gives you the data to attribute these in production; INP gives you the metric the user feels. Together they close the loop from production telemetry back to specific render-pipeline diagnostics.</p>

    <p><strong>Reduced-motion as a render-budget escape valve.</strong> The CSS Media Queries Level 5 spec defines <code>@media (prefers-reduced-motion: reduce)</code>, set by users who experience motion sickness or want lower power consumption. Beyond accessibility, it is a useful escape valve for the render budget: any compositor-driven animation can be replaced by an instant state change when reduced-motion is on, freeing the compositor of the per-frame work entirely. Battery-constrained users on a budget Android phone get a meaningful battery saving from a page that respects this signal.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Putting it together</h4>
    <p><strong>The full attack surface for a sluggish page, summarised.</strong> Any page that drops below 60 fps is paying main-thread cost it should not be paying. The attack surface is: parser-blocking scripts that delay first paint; oversized CSS that forces large CSSOM construction; complex selectors that defeat the bloom filter; deep flexbox/grid hierarchies that need multi-pass layout; paint-heavy properties (large box-shadow, filter); layer overflow from will-change abuse; forced sync layout from JS reading geometry between writes; non-passive scroll listeners that fall back to main-thread scrolling; tasks longer than 50 ms reported by LoAF; input handlers that delay rAF and blow up INP. Each is its own specific failure mode rooted in the same pipeline. The cure is always the same shape: identify the stage doing the work, then either reduce the input to that stage, isolate the damage with contain/content-visibility, or move the work to a different thread.</p>

<Misconception id="mc-layout-thrash">
**Myth:** Wrapping a read-then-write loop in `requestAnimationFrame` batches layout work.

**Reality:** rAF batches invocation only. Reading any layout-dependent value (`offsetWidth`, `getBoundingClientRect`) after a write forces a synchronous layout flush. The fix is separating reads from writes, not wrapping in rAF.
</Misconception>
