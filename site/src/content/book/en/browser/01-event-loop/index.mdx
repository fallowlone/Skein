A button click feels instant. A scroll judders. A modal blocks for 300 ms while JSON parses. The thing that decides which experience the user gets is one piece of machinery older than the modern web: the event loop. It is a single thread that pulls one task, runs it to completion, drains a queue of follow-up promises, optionally renders a frame, then repeats. Every interaction your code touches is queued behind some other task on this loop. Whoever runs longest, blocks everyone.

<Crux>One thread, two queues, one render step — and a 50 ms cap on whoever holds the floor.</Crux>

The loop has three players. The **task queue** (also called the macrotask queue) holds discrete jobs: `setTimeout` callbacks, parsed HTML chunks, fired DOM events, message-channel messages. The **microtask queue** holds promise-resolution callbacks and `queueMicrotask` jobs; it drains to empty after every task. The **rendering steps** — style, layout, paint, composite — run between iterations, but only when the browser thinks a frame is due. Three queues, one engine, one user.

    <p><strong>What the event loop does.</strong> The browser has one thread that runs your JavaScript. While it is busy, nothing else runs — no clicks, no animations, no rendering. The event loop decides what runs next when the thread frees.</p>
    <p><strong>The barista metaphor.</strong> Imagine a one-person coffee shop. Customers put orders on the counter (the task queue). When the barista finishes one drink, she checks for sticky notes on the espresso machine (microtasks — small follow-ups like "add cinnamon") and does every one before greeting the next customer. If she keeps writing herself sticky notes faster than she finishes them, she never reaches the next customer at all. That failure mode is microtask starvation.</p>
    <p><strong>Why care.</strong> Every animation, keystroke, click, and scroll is a queued task waiting for the thread. Hold the thread for 200 ms and the user sees 200 ms of frozen UI. The fix is not "faster code" — it is "shorter tasks."</p>

    <p><strong>The HTML spec model: tasks, task sources, and task queues.</strong> The HTML standard (§ event loops) defines an event loop as a thread of execution with a set of <em>task queues</em>. Each task is associated with a <em>task source</em> — the kind of work that produced it (DOM manipulation, user interaction, networking, history traversal, microtask, idle). Each task source has its own queue, and the user agent picks one queue per iteration, dequeues the oldest task, and runs it to completion. There is no preemption. When the task ends, the agent runs the microtask checkpoint, then optionally the render step, then loops back. The single guarantee: one task at a time, run to completion, microtasks drained between.</p>

    <p><strong>The processing model in detail.</strong> One iteration does this:</p>

    | Step | What runs | When skipped |
    | --- | --- | --- |
    | 1. Select task | Pull one task from a non-empty task queue | If all queues empty, idle |
    | 2. Run task | Execute the callback to completion | Never skipped if step 1 ran |
    | 3. Microtask checkpoint | Drain the microtask queue | Microtask queue empty |
    | 4. Update rendering | rAF → ResizeObserver → IntersectionObserver → style → layout → paint → composite | Only on frame boundary; usually every ~16.67 ms |
    | 5. Loop back | Return to step 1 | Never |

    <p><strong>Microtasks vs tasks.</strong> A microtask is queued by `Promise.then`, `Promise.catch`, `Promise.finally`, `queueMicrotask`, `MutationObserver`, and `await` (which is sugar over Promise.then). A task is queued by `setTimeout`, `setInterval`, `setImmediate` (Node only), `MessageChannel.postMessage`, network responses delivered to fetch promises, dispatched DOM events, parsed HTML chunks. The decisive operational rule: <em>microtasks drain to empty between every task and every frame</em>. If a microtask schedules another microtask, both run before the loop moves on. This is why `Promise.resolve().then(self)` in a tight chain hangs the page: the microtask queue is never empty, the loop never reaches step 4, and the browser never paints.</p>

    <p><strong>queueMicrotask vs Promise.resolve().then vs MessageChannel.</strong> Three ways to "schedule something soon," each with different semantics. `queueMicrotask(fn)` queues a microtask directly — runs after the current task, before the next. `Promise.resolve().then(fn)` does the same thing with extra allocation (a Promise, a closure, an entry in the resolution chain) — slightly slower, otherwise identical timing. `new MessageChannel().port1.postMessage(...)` queues a <em>task</em> — runs after the current task, after microtasks, possibly after a frame. The pattern matters when you want to yield to rendering: microtasks do not, MessageChannel does. Modern code uses `scheduler.yield()` (Chrome 115+) for explicit yield points.</p>

    <p><strong>Browser loop vs Node loop: same primitives, different phases.</strong> Browser loop = task queue + microtask queue + rendering. Node loop = several phases (timers, pending callbacks, idle, poll, check, close) + microtask queue + `process.nextTick` queue. Node has no rendering step (no DOM) and no input phase, so its loop is bigger and more rigidly phased. Two extra Node-only queues: `process.nextTick` (fires before microtasks!) and the `setImmediate` queue (fires in the check phase, after I/O). If you write code that runs in both, the trap is timing differences: a microtask in the browser fires immediately after the current task; in Node, `process.nextTick` fires <em>before</em> microtasks and `setImmediate` fires in a different phase entirely. Code that relies on exact ordering will desync between environments.</p>

    <p><strong>Where requestAnimationFrame fits.</strong> rAF callbacks run in step 4 of the loop, immediately before style/layout/paint. The browser only enters step 4 when it has decided a frame is due — typically every 16.67 ms at 60 Hz, every 8.33 ms at 120 Hz. If the previous task was so long that several frame deadlines passed during it, the browser does <em>not</em> queue up multiple rAF callbacks; it runs the rAF set once and counts that as the catchup. This is why a long task always shows as exactly one frame drop, not many — the browser is not running rAF on a timer; it is running it on a render budget.</p>

    <p><strong>Where input fits.</strong> Input events (mousemove, click, keydown, touchstart) are queued as tasks by the browser's input thread (a separate OS thread that owns the OS event handle). The main thread pulls them in step 1 like any other task. There is no preemption: if your JS task runs for 80 ms when a click arrives at the 20 ms mark, the click waits 60 ms before its handler can run. INP measures exactly this latency: when did the user click, when did the next paint reflect the result. INP &lt; 200 ms p75 is "good." Hitting that requires that no single task on the loop exceeds about 50 ms, because longer tasks queue up downstream work that pushes the next paint past the 200 ms threshold.</p>

    <p><strong>Yielding inside a long task: techniques and tradeoffs.</strong> If you must do 200 ms of work, break it into ≤50 ms chunks separated by yield points so input can interleave. Three techniques: (1) <code>setTimeout(fn, 0)</code> — queues a task in ~4 ms (browsers clamp to a minimum); coarse but universal. (2) <code>MessageChannel</code> with `postMessage` — queues a task immediately, no clamping; what React 18 uses internally for time-slicing. (3) <code>scheduler.yield()</code> (Scheduler API, Chrome 115+) — promises a yield point that allows input and rendering to run, then resumes the same logical task with priority. Modern recommendation: use `scheduler.yield()` when available, fall back to `setTimeout(0)`. Do <em>not</em> use `await Promise.resolve()` to yield — it queues a microtask, which does not let the renderer run.</p>

    <p><strong>Cross-realm gotchas.</strong> Each iframe and each Worker has its own event loop. Cross-loop communication (postMessage, BroadcastChannel) uses tasks, never microtasks — there is no shared microtask queue between realms. This means a `postMessage` from a worker to the main thread always arrives in the main thread's task queue, runs <em>after</em> any microtasks the main thread already queued. If you need a fast round-trip between threads, the latency lower bound is one task hop each way — typically 1–5 ms even on a free system.</p>

    <p><strong>Timer accuracy and throttling.</strong> A `setTimeout(fn, 100)` does not promise to run `fn` in exactly 100 ms — it promises to queue the task <em>no sooner</em> than 100 ms. The actual run time depends on when the main thread is next free. If a 300 ms task is in flight when the timer fires, your callback waits the full 300 ms plus its queue position. Three throttling layers compound this. First, the 4 ms minimum-delay clamp after 5 levels of nesting. Second, <em>background-tab throttling</em>: when a tab is hidden, browsers clamp timers to a 1-second minimum, and after a tab has been hidden for several minutes, to once per minute — this is why a background tab's polling loop quietly slows down. Third, <em>timer alignment / coalescing</em>: to save battery, browsers round timer fire times to a shared grid so the CPU can wake once for many timers instead of many times. The practical consequence: never use `setTimeout`/`setInterval` for anything that needs sub-frame precision. For animation use `requestAnimationFrame`; for precise scheduling use the `AudioContext` clock or `performance.now()` deltas inside a rAF loop.</p>

    <p><strong>How a DOM event becomes a task.</strong> When the user clicks, the browser's input thread (a separate OS thread) records the hit-test target and queues a single task on the main thread's user-interaction task source. When the main thread pulls that task, it runs the full event dispatch in one shot: capture phase from `document` down to the target, then the target itself, then bubble phase back up. <em>Every</em> matching listener along that path runs synchronously inside this one task — there is no yield point between them. This is why a slow listener on a high ancestor (a `mousemove` handler on `document`, an analytics wrapper on `body`) taxes every descendant interaction. Event delegation — one listener on a container instead of N listeners on N children — is cheaper for memory and setup, but the delegated handler still runs synchronously in the dispatch task, so a slow delegated handler is just as capable of blowing the 50 ms budget. The `passive: true` listener option matters here for scroll, wheel, and touch: it promises the listener will not call `preventDefault()`, letting the browser start compositor scrolling without waiting for the dispatch task to finish.</p>

    <p><strong>Idle work: requestIdleCallback.</strong> Not all work is urgent. Analytics beacons, prefetching, cache warming, and log flushing can wait until the loop has nothing better to do. `requestIdleCallback(fn)` queues a callback that the browser runs only when an iteration finishes with spare time before the next frame deadline — the callback receives a `deadline` object whose `timeRemaining()` tells you how many ms you may safely use (capped around 50 ms). The discipline: do a small slice, check `timeRemaining()`, and if it is near zero, re-schedule the rest with another `requestIdleCallback`. If the page is busy and no idle time ever appears, the optional `{ timeout }` parameter forces the callback to run anyway after the deadline so the work is not starved forever. `requestIdleCallback` is the cooperative opposite of `requestAnimationFrame`: rAF says "run me right before the next paint," ridle says "run me only if nobody else needs the thread." Used together they let you keep urgent work on rAF and defer everything else off the critical path.</p>

    <p><strong>Promise combinators and scheduling.</strong> `Promise.all`, `Promise.allSettled`, `Promise.race`, and `Promise.any` change <em>what</em> you wait for, not how the loop schedules. All four start every passed promise immediately — the parallelism comes from kicking the async operations off before awaiting. `Promise.all` rejects on the first failure (fail-fast) and is right when any failure makes the whole result useless. `Promise.allSettled` never rejects; it resolves with a status array and is right when you want partial results — five independent dashboard widgets where one failing should not blank the other four. `Promise.race` settles on the first to settle, success or failure — the classic use is a timeout: `Promise.race([fetchData(), rejectAfter(5000)])`. `Promise.any` resolves on the first <em>success</em>, ignoring rejections until all fail — right for redundancy, like racing three CDN mirrors and taking whichever answers first. Picking the wrong combinator is a correctness bug, not a perf bug: `Promise.all` for a dashboard means one slow widget's failure blanks the page.</p>

    <h4 class="mt-2 mb-3 text-[15px] font-semibold text-ink tracking-tight">Failure mode: microtask starvation</h4>
    <p><strong>The starvation pattern.</strong> Microtasks drain to empty between tasks. If a microtask schedules another microtask before returning, the loop never escapes the microtask checkpoint — no rendering, no input, no further tasks. The pathological example:</p>

```javascript
function loop() {
  Promise.resolve().then(loop);  // schedules itself as a microtask
}
loop();
```

    <p>This freezes the page indefinitely: the microtask queue is never empty, step 4 (rendering) never runs, the user sees a frozen tab. DevTools Performance shows it as a single uninterrupted yellow scripting bar. The same pattern appears in production as accidental recursion through async chains: a `.then` that resubscribes to the same observable, a router middleware that re-resolves on every change, a state library that re-fires reactions inside a reaction. Detection: long-task entries with no clear single function, scripting bar that grows without bound, INP &gt; 1 s. Cure: insert at least one task-level yield (`setTimeout`, `MessageChannel`, `scheduler.postTask`) into the chain.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Long Tasks API and Long Animation Frames</h4>
    <p><strong><Term k="performance_long_task_timing" lang="en">PerformanceLongTaskTiming</Term>.</strong> Shipped in 2017, fires a `PerformanceObserver` entry for any task that exceeds 50 ms on the main thread. Each entry includes start time, duration, and an `attribution` array with the originating browsing context. Limitation: the attribution rarely points to a specific function; it tells you "something inside iframe A took 230 ms" — useful for SLO dashboards, less useful for root-cause. Use the Long Tasks API to <em>count</em> long tasks per session, not to debug them.</p>

    <p><strong>PerformanceLongAnimationFrameTiming (<Term k="loaf" lang="en">LoAF</Term>).</strong> Shipped 2023–2024 in Chromium. Fires for any frame whose render time exceeds 50 ms — a different unit than long tasks. A LoAF entry includes per-script attribution: an array of which scripts ran in the frame, what they did (event-handler, classic-script, module-script, user-callback), how long each took. This is the production diagnostic that long tasks should have been from the start. Combine with INP: when INP regresses, query LoAF entries from the same session, find the offending frame, get the script attribution, deploy a fix. The full pipeline is visible: from user-perceived metric (INP) to specific script (LoAF) to specific function (<Term k="sourcemap" lang="en">sourcemap</Term> on the script URL).</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">scheduler.yield() and the Scheduler API</h4>
    <p><strong>What scheduler.yield() does.</strong> The Scheduler API (Chrome 115+, partial in Edge, Firefox/Safari behind flag as of late 2025) gives the platform a first-class yield primitive. Awaiting `scheduler.yield()` suspends the current task, drains the microtask queue, allows input and rendering to run, and resumes the suspended task as the <em>next</em> task — with priority that prevents low-priority work from cutting in front. This is the missing piece in the platform: previously, yielding via `setTimeout(0)` worked for rendering but lost queue position (any task scheduled in the meantime would run first). With `scheduler.yield()`, you can split a 200 ms task into four 50 ms chunks that are still effectively one logical operation from the user's perspective.</p>

    <p><strong>scheduler.postTask() with priorities.</strong> The same API exposes `scheduler.postTask(callback, { priority })` with three priorities: `user-blocking` (input-response work), `user-visible` (default), `background` (non-urgent). The browser's scheduler honours these in its task selection, preferring higher-priority tasks. Practical pattern: route input handlers through `user-blocking` so they jump the queue ahead of background work like analytics flushes; route background analytics through `background` so they yield to anything urgent. The scheduler has access to system signals (battery, thermal throttling, page visibility) that JS code does not, so deferring to it produces better outcomes than implementing your own priority logic.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Node.js event loop differences</h4>
    <p><strong>Phases, nextTick, setImmediate.</strong> Node's libuv-driven loop runs through six phases per iteration: timers (expired setTimeout/setInterval), pending callbacks (deferred I/O errors), idle/prepare (internal), poll (block on I/O), check (setImmediate callbacks), close (close events). Between every phase, two queues drain: the `process.nextTick` queue (Node-specific, fires before microtasks) and the standard microtask queue. The implication: in Node, `process.nextTick` is the highest-priority callback short of synchronous code. Misuse causes the same starvation pattern as runaway microtasks in the browser, but at one priority level higher.</p>

    <p><strong>setImmediate vs setTimeout(0) in Node.</strong> Despite the names, `setImmediate` does not run immediately and `setTimeout(0)` does not run at zero delay. setImmediate runs in the check phase (after I/O completes for that iteration); setTimeout(0) runs in the timers phase of the <em>next</em> iteration. Inside an I/O callback (file read, socket read), `setImmediate` always wins — it fires this iteration's check phase before the next iteration's timers phase. Outside I/O callbacks, the order is non-deterministic by spec. Code that relies on either ordering between the two is brittle; if you need a guaranteed ordering, use `queueMicrotask` (always before either) or stack them with explicit dependencies.</p>

    <p><strong>Why blocking the Node loop matters.</strong> Node has no concept of frames or input — but it is single-threaded just like the browser. A 500 ms `JSON.parse` on a request handler blocks every other request on the same process for 500 ms. There is no rendering safety net. Mitigation: offload CPU-bound work to a Worker thread (`node:worker_threads`), keep request handlers async-first, and use streaming parsers (`JSONStream`, `oboe.js`) for large payloads. The same "shorter tasks" discipline that fixes browser INP fixes Node tail latency.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">async/await and the await trap</h4>
    <p><strong>await is sugar over Promise.then.</strong> When you write <code>const x = await fetchUser()</code>, the JS engine compiles it as: pause the async function, register a microtask that resumes the function with the resolved value, return control to the caller. The resume is always a microtask — even if the awaited promise was already resolved synchronously. This means <code>await Promise.resolve()</code> always yields one microtask boundary, no matter what. The trap: this looks like a rendering yield but it is not. If you write a "yield" loop as <code>for (const item of items) &#123; await Promise.resolve(); doWork(item) &#125;</code>, you have created a microtask spam pattern that hangs the page.</p>

    <p><strong>Sequential await vs Promise.all.</strong> A common bug: writing <code>const a = await fetchA(); const b = await fetchB();</code> when both fetches are independent. The two requests run sequentially because the second await does not start until the first resolves. <code>const [a, b] = await Promise.all([fetchA(), fetchB()])</code> kicks off both immediately and waits for both. The cost difference is one full RTT. The clue in DevTools is two network requests with non-overlapping timing where both could have run in parallel.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">React, Vue, and the loop</h4>
    <p><strong>How React 18 schedules work.</strong> React's scheduler runs reconciliation in cooperative chunks of 5 ms. After each chunk, it yields to the browser using `MessageChannel.postMessage` (the only cross-browser mechanism that yields without the 4 ms clamp). The browser's loop gets to run input, render, and other tasks; React resumes on the next task to do the next 5 ms chunk. This is the implementation of "concurrent React": a single render is split across many tasks, none of which exceeds the 50 ms long-task threshold. `useTransition` marks a state update as low-priority, allowing input updates to interrupt. The whole architecture is a layer on top of the event loop; understand the loop and React's scheduler stops being mysterious.</p>

    <p><strong>Vue 3's scheduler.</strong> Vue 3 batches reactive updates within a microtask: a write to a ref schedules a microtask that flushes all pending updates at the end of the current task. This means many writes in one task collapse into one update — but it also means the flush is a microtask and can prolong starvation if it triggers more reactive writes. Vue exposes `nextTick(callback)` for code that wants to run after the flush; underneath, this is just another microtask scheduled after the flush microtask.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Production observability</h4>
    <p><strong>Recipe for INP root-cause in production.</strong> Subscribe to LoAF entries with `PerformanceObserver`. For each entry, record the `firstUIEventTimestamp`, the entry's `renderStart`, and the array of `scripts` with attribution. When INP fires for a slow interaction (also via PerformanceObserver), correlate by interaction id: find the LoAF that overlapped the input, attribute the time to the heaviest script, send to telemetry with the script URL and function name (resolved via sourcemap server-side). This pipeline turns "users are complaining about lag" into "deploy 3a4f1c regressed search input by adding a 320 ms reducer call." Without LoAF, INP is a number with no actionable attribution; with LoAF, it is a click-through diagnostic.</p>

<Misconception id="mc-microtask-starvation">
**Myth:** `await Promise.resolve()` yields to the browser.

**Reality:** Promises queue microtasks, which drain before the render step — a microtask yield never lets rendering or input run. To truly yield, schedule a task: `setTimeout(fn, 0)` or `scheduler.yield()`.
</Misconception>

<KeyTakeaway>One thread, two queues, one render step. Microtasks drain before rendering — so awaiting a Promise is not a yield. Tasks longer than 50 ms blow up INP. Yield with `scheduler.yield()` or `setTimeout(0)`, never with `await Promise.resolve()`.</KeyTakeaway>

<p class="text-ink-2 my-6">The event loop carries state across iterations: the call stack of the running task, the partially-drained microtask queue, the deferred render. A "yielded" task resumes by being re-queued — its closures, its in-flight promises, its observed DOM all persist into the next iteration. The loop's cooperative model only works because state survives the yield; the same statefulness rule that makes TCP a connection rather than a sequence of packets. <SpiralCue thread="statefulness" lang="en" /></p>
