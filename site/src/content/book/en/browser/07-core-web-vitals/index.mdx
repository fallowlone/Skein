Everything in this chapter — the event loop, the render pipeline, V8, hydration — eventually rolls up into three numbers a real user feels and Google scores you on. Did the main content show up fast? Did the page respond when tapped? Did things stay still, or did a button jump out from under a finger? Those are the Core Web Vitals: LCP, INP, CLS. They are not lab curiosities — they are measured from real Chrome users in the field, and they decide both how the page feels and where it ranks.

<Crux>Three field metrics: did it show up fast (LCP), does it respond (INP), does it stay still (CLS)?</Crux>

Each metric has a "good" threshold measured at the 75th percentile of real users. **LCP** — Largest Contentful Paint — is good at ≤2.5 s: how long until the biggest piece of content is on screen. **INP** — Interaction to Next Paint — is good at ≤200 ms: how long from a tap or keypress to the screen visibly responding. **CLS** — Cumulative Layout Shift — is good at ≤0.1: a unitless score of how much the layout jumped around unexpectedly. Three questions, three numbers, one verdict on the page.

    <p><strong>LCP: what counts and when it is recorded.</strong> Largest Contentful Paint is the render time of the largest content element visible in the viewport during load. "Content" is a specific list: `<img>`, the poster of a `<video>`, a background image loaded via `url()`, and block-level elements containing text. The browser watches as elements paint, keeps updating its candidate for "largest", and finalises the LCP value at the first user interaction (because once the user is interacting, further "loading" is not load anymore). On most pages the LCP element is the hero image or the main headline. The metric is what the user perceives as "the page has loaded" — not the first pixel (that is FCP, First Contentful Paint), but the main thing.</p>

    <p><strong>What makes LCP slow — the four phases.</strong> LCP time decomposes into four sub-parts, and a fix only works if it targets the dominant one. <em>TTFB</em>: time to the first byte from the server — slow server render, no CDN, slow database query in an SSR path. <em>Resource load delay</em>: the gap between TTFB and the browser starting to load the LCP image — caused by the image being discovered late (in CSS, in JS, not in the initial HTML). <em>Resource load time</em>: how long the LCP image itself takes to download — caused by an oversized, uncompressed, wrong-format image. <em>Element render delay</em>: the gap between the image finishing download and it actually painting — caused by render-blocking CSS or JS still occupying the main thread. A common mistake is compressing the image when the real problem was load delay; profile first, fix the dominant phase.</p>

    <p><strong>Optimising LCP.</strong> The highest-leverage fixes, by phase. For load delay: put the LCP image in the initial HTML as a plain `<img>`, and add `<link rel="preload">` or `fetchpriority="high"` so the browser's preload scanner finds and prioritises it immediately. Never lazy-load the LCP image — `loading="lazy"` on the hero is one of the most common self-inflicted LCP regressions, because it tells the browser to delay exactly the image the metric is measuring. For load time: serve a correctly sized image in a modern format (AVIF, WebP), responsive with `srcset`. For render delay: cut render-blocking resources — inline critical CSS, defer non-critical JS. For TTFB: cache, use a CDN, move slow data fetches off the render path (streaming SSR with a Suspense boundary). LCP is usually fixable; it is rarely a mystery once the four phases are separated.</p>

    <p><strong>INP: what it measures.</strong> Interaction to Next Paint replaced First Input Delay as a Core Web Vital in March 2024. It measures the latency of interactions across the <em>whole</em> page lifecycle — every click, tap, and key press — and reports a high percentile (effectively the worst, with a small allowance on pages with many interactions). One interaction's latency is the time from the user's input to the next frame that visibly reflects a change. FID only measured the <em>delay before</em> the first input's handler started; INP measures the full input-to-paint of every interaction, which is far closer to what the user actually feels.</p>

    <p><strong>The three parts of an interaction's latency.</strong> INP for one interaction decomposes into: <em>input delay</em> — the time the input event waits before its handler can even start, because the main thread is busy with another task (this is the event-loop lesson directly: a long task in flight delays the input); <em>processing time</em> — how long your event handlers take to run; and <em>presentation delay</em> — the time after the handlers finish for the browser to run style, layout, paint, and composite and put the result on screen. A bad INP is always one of these three: the thread was busy when the tap arrived, the handler itself was slow, or the resulting render was heavy. Naming which third dominates is the whole diagnosis.</p>

    <p><strong>Optimising INP.</strong> By part. Input delay: stop shipping long tasks — break work into chunks under 50 ms, defer non-urgent JavaScript, and remember that hydration is one giant long task early in the page's life. Processing time: keep handlers small; if a handler must do heavy work, do the minimum to update the UI, then yield (`scheduler.yield()`) and continue the rest — or move pure computation to a Worker. A powerful trick: update the visible state synchronously and wrap the expensive downstream work in `startTransition` so the paint the user is waiting for is not blocked by it. Presentation delay: avoid forced synchronous layout in the handler, and keep the DOM update small (a handler that re-renders 5 000 nodes has a heavy presentation delay no matter how fast the handler logic was).</p>

    <p><strong>CLS: the layout-shift score.</strong> Cumulative Layout Shift measures unexpected movement. Each time a visible element changes position between two frames without a user-initiated cause, the browser records a <em>layout shift</em>. The score of one shift is <em>impact fraction</em> (how much of the viewport the shifting content covered) multiplied by <em>distance fraction</em> (how far it moved, as a fraction of viewport). CLS is the sum of the worst cluster of shifts in a 5-second window (the "session window"). Crucially, shifts within 500 ms of a user interaction are <em>excluded</em> — opening an accordion is expected movement and does not count. CLS only punishes movement the user did not cause and did not expect.</p>

    <p><strong>What causes CLS — and the fixes.</strong> Four classic causes. <em>Images without dimensions</em>: an `<img>` with no `width`/`height` has a 0×0 box until it loads, then jumps to full size, shoving everything down. Fix: always set `width` and `height` attributes (or `aspect-ratio` in CSS) so the browser reserves the space. <em>Ads, embeds, iframes</em> injected late into unreserved space: reserve a min-height container. <em>Web fonts</em>: a fallback font with different metrics swaps to the web font, reflowing text — fix with `size-adjust` and the font-override descriptors, or `font-display: optional`. <em>Dynamically injected content</em> above existing content: a cookie banner, a notification — insert it in pre-reserved space or overlay it instead of pushing. The unifying principle: reserve space for anything that loads in late.</p>

    <p><strong>Lab vs field — why they disagree.</strong> There are two ways to get vitals, and they answer different questions. <em>Lab</em> data is a synthetic test — Lighthouse, DevTools, PageSpeed Insights' Lighthouse run — one load, one simulated device and network, fully reproducible, great for debugging. <em>Field</em> data is real-user monitoring: actual visits, real devices, real networks, aggregated. The Chrome User Experience Report (CrUX) is Google's public field dataset, and CrUX is what Search ranking uses. They disagree constantly: a lab INP barely exists (lab tools do not script realistic interaction sequences well), and a lab LCP on a simulated fast connection can look fine while field LCP at p75 on real 4G is poor. The rule: <em>debug in the lab, judge in the field</em>. A lab improvement that does not move the field number did not actually help your users.</p>

    <p><strong>Reading a DevTools performance trace.</strong> Open DevTools, the Performance panel, record a page load and an interaction. The trace shows several tracks. The <em>Timings</em> track marks FCP, LCP, and DCL with vertical lines — the LCP marker tells you exactly when it fired and hovering names the element. The <em>Frames</em> track shows each rendered frame; a layout-shift is flagged with a red marker you can click to see the shifting nodes. The <em>Main</em> track is the flame chart of main-thread work — long tasks are flagged with a red corner. The INP workflow: interact during the recording, find the interaction in the <em>Interactions</em> track, and it is broken into input delay, processing, and presentation — the exact three parts, color-coded, so you can see which dominates without guessing.</p>

    <p><strong>The metrics relate — and trade off.</strong> The three are not independent dials. A fix for one can hurt another, and the senior move is to see the interaction. Inlining a large critical-CSS block helps LCP render delay but bloats the HTML, hurting TTFB. Lazy-loading everything to shrink the bundle helps INP but, applied to the hero, wrecks LCP. Reserving generous space to kill CLS can push the LCP element below the fold so it is no longer the LCP candidate — sometimes good, sometimes not. Shipping a big interactive framework for a snappy feel adds a hydration long task that spikes INP. There is no single knob; there is a budget shared across LCP, INP, and CLS, and every change spends from it. The discipline is to measure all three before and after any change, never one in isolation.</p>

    <p><strong>FCP, TTFB, and the supporting metrics.</strong> The three Core Web Vitals sit on top of a layer of diagnostic metrics that are not scored for ranking but are essential for debugging. <em>TTFB</em> — Time to First Byte — is the server-and-network portion, and it is the floor under LCP: LCP can never be faster than TTFB. <em>FCP</em> — First Contentful Paint — is when the <em>first</em> pixel of content appears, as opposed to LCP's <em>largest</em>; a large FCP-to-LCP gap means the page shows something quickly but the main content lags. <em>TBT</em> — Total Blocking Time — is the lab's proxy for INP: the sum of the blocking portion of every long task during load. You cannot measure true INP in a lab (it needs real interactions), so CI gates use TBT instead. Knowing the supporting metrics is what lets you read a Lighthouse report — it never just says "LCP is bad", it shows the TTFB and FCP underneath so you can see where in the chain the time went.</p>

    <h4 class="mt-2 mb-3 text-[15px] font-semibold text-ink tracking-tight">Failure mode: layout shift from un-sized media</h4>
    <p><strong>The mechanism in full.</strong> When the HTML parser meets an `<img>` with no `width` and `height` attributes and no CSS `aspect-ratio`, it cannot know the image's dimensions until the image bytes arrive — so it lays the element out as a 0-height box. The surrounding content flows up into that empty space and paints. Then the image downloads, the browser learns it is, say, 1200×800, re-runs layout to give it real height, and every element below it is pushed down. That push is a layout shift, and if it happens after the user has started reading or reaching for a control, it is exactly the un-caused, unexpected movement CLS punishes — and it is the single most common CLS cause in the wild. The fix is to give the browser the aspect ratio before the bytes arrive: set the `width` and `height` HTML attributes (modern browsers derive `aspect-ratio` from them automatically and reserve a correctly-proportioned box), or set `aspect-ratio` in CSS. The same logic extends to every late-loading thing: ads get a reserved min-height container, embeds get a fixed-size wrapper, web-font reflow is neutralised with `size-adjust`. The unifying rule: anything whose final size is not known at parse time must have space reserved for it, or it will shift the page when it arrives.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">LCP attribution in depth</h4>
    <p><strong>The preload scanner and why discovery is everything.</strong> Browsers run a secondary parser — the preload scanner — that races ahead of the main HTML parser looking for resources to start fetching, even while the main parser is blocked on a script. The preload scanner is why an `<img>` in the initial HTML loads early: the scanner sees it and kicks off the fetch immediately. It is also why an image referenced only in CSS (`background-image`) or injected by JavaScript loads late: the scanner cannot see it — the image is not discovered until the CSS is parsed or the JS runs. This is the deep reason "put the LCP image in the HTML" works: it is the only place the preload scanner can find it without waiting. `fetchpriority="high"` then tells the browser to raise that fetch above other early resources; `<link rel="preload">` is the heavier hammer for resources the scanner still cannot reach. The senior framing: LCP optimisation is largely a discovery problem — make sure the browser learns about the LCP resource as early and as prioritised as physically possible.</p>

    <p><strong>The soft-navigation gap.</strong> Core Web Vitals were designed around full page loads. In a single-page app, the first load has a real LCP — but subsequent client-side route changes ("soft navigations") historically had no LCP at all, because no document load happened. To the user a soft navigation absolutely feels like a page load — they clicked a link and expect new content fast — but the metric did not see it. Chrome has been shipping soft-navigation support to attribute LCP and other vitals to client-side route changes, but coverage is still maturing. The senior consequence: for an SPA, do not assume your vitals story is complete just because the initial-load numbers are green. A snappy first load and sluggish route transitions is a real, common, and historically under-measured failure — instrument soft navigations explicitly with the `PerformanceObserver` soft-navigation entries or your own RUM marks.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">INP attribution in depth</h4>
    <p><strong>From the metric to the line of code.</strong> A field INP number alone is not actionable — it is a latency with no cause attached. The attribution chain: the `event` timing entries from `PerformanceObserver` give you, per interaction, the input delay, processing time, and presentation delay split. Long Animation Frames (LoAF) give you, for the frame that the slow interaction landed in, the array of scripts that ran, with source URLs and function names. Combine them: a high-INP interaction whose split is dominated by <em>input delay</em> points at whatever long task held the thread — find it in the LoAF script list. Dominated by <em>processing</em> — the handler itself; the LoAF attributes it to your handler's source. Dominated by <em>presentation delay</em> — a heavy render or a forced synchronous layout in the handler. The whole point of wiring LoAF into RUM is to turn "p75 INP is 340 ms" into "the search handler's synchronous filter, search.js:88, is the dominant script in the slow frames."</p>

    <p><strong>The hydration window is an INP trap.</strong> The single most common INP failure on a server-rendered site is interactions that happen during hydration. The page is painted, the user sees a button and taps it — but the main thread is running the hydration long task. The tap's handler may not even be attached yet, and even once it is, the input is queued behind the rest of hydration. INP records a huge latency for that early interaction. This is why INP and the SSR/hydration material are inseparable: every technique that shrinks hydration (Server Components, islands, selective and progressive hydration, code-splitting) is also an INP optimisation. When INP is poor only for interactions in the first few seconds and fine afterward, the diagnosis is almost always hydration — not the handlers themselves.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">CLS edge cases</h4>
    <p><strong>The session window and animation pitfalls.</strong> CLS is not the lifetime sum of all shifts — it is the largest <em>session window</em>: a cluster of shifts where each is within 1 second of the previous and the whole cluster spans at most 5 seconds. This was a deliberate change (CLS originally summed everything, which unfairly punished long-lived pages and infinite scroll). The practical consequence: a burst of shifts during load that all land in one window is scored as that window's sum; spreading shifts out does not reduce the total within a window but can split them across windows. Two animation pitfalls. One: animating layout properties (`top`, `left`, `height`, `width`, `margin`) <em>does</em> generate layout shifts and can hurt CLS — animate `transform` instead, which never shifts layout. Two: a shift caused by content the user did not request, even if it is technically "after" an interaction but past the 500 ms window, still counts — the 500 ms exclusion is narrow. Verify CLS by clicking the red layout-shift markers in the DevTools Frames track, which highlight the exact shifting nodes.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Production observability</h4>
    <p><strong>The RUM and CI loop.</strong> The complete setup has two halves. <em>RUM</em>: ship the `web-vitals` library (or equivalent), which uses `PerformanceObserver` to capture LCP, INP, and CLS exactly as Chrome scores them, plus attribution — the LCP element, the INP interaction target and script, the CLS shifting sources — and send them to telemetry tagged by route, device class, country, and release. This is the real verdict and it catches regressions a lab never will. <em>CI</em>: a synthetic gate — Lighthouse CI or a Playwright trace — that runs on every PR, throttled to a realistic mid-tier device, asserting budgets on LCP, total blocking time (the lab proxy for INP, since true INP needs real interaction), and CLS, and failing the build on a regression. The lab gate catches the obvious regressions before merge; RUM catches what the lab cannot model and confirms that a lab fix actually moved the field number. Neither alone is enough: lab without RUM ships regressions that only real devices reveal; RUM without a lab gate means every regression reaches production before anyone sees it.</p>
