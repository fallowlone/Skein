The main thread is the bottleneck — one thread for your JS, your layout, your paint, your input. The browser's answer is not "make the thread faster." It is "give you more threads." But the extra threads come with rules: no DOM access, no shared variables, communication only by message-passing, and — for the most powerful one — a pair of HTTP headers you must get exactly right or the API silently returns `undefined`. Four off-main-thread tools, four different jobs.

<Crux>Thread or proxy: web workers compute, service workers proxy the network, worklets hook rendering, SharedArrayBuffer shares memory.</Crux>

The four are not interchangeable. A **web worker** is a second JS thread for CPU-bound work — parsing, crypto, image processing — with its own event loop and no DOM. A **service worker** is a network proxy that sits between the page and the server, can serve cached responses offline, and outlives the page. A **worklet** is a tiny, tightly-scoped hook into the browser's own rendering or audio pipeline. **SharedArrayBuffer** is the one escape from message-passing: real shared memory between threads, gated behind cross-origin isolation. Pick by the job, not by familiarity.

    <p><strong>What workers are.</strong> A worker runs JavaScript on a thread that is not the main thread, so heavy work cannot freeze the page.</p>
    <p><strong>The office metaphor.</strong> The main thread is you at your desk — you answer the phone (input) and update the whiteboard (DOM) yourself. A <em>web worker</em> is a colleague in a back room: you send a big calculation by note, they do it without disturbing your desk, they send the answer back by note. They cannot touch your whiteboard — only you can. A <em>service worker</em> is the mailroom: every letter in or out passes through it first, and it can answer some from its own filing cabinet without going outside.</p>
    <p><strong>Why care.</strong> Parse a 5 MB JSON file on the main thread and the page freezes for ~150 ms — dropped frames, dead buttons. Hand it to a web worker and the page stays at 60 fps. For instant repeat loads or offline support, the service worker serves cached files without a network round-trip.</p>

    <p><strong>Web workers: the dedicated compute thread.</strong> `new Worker('worker.js')` spins up a fresh JS realm on its own OS thread, with its own event loop, its own global (`DedicatedWorkerGlobalScope`), and no access to `document`, `window`, or the DOM. It can use `fetch`, `IndexedDB`, `WebSocket`, `OffscreenCanvas`, timers, and `importScripts`/ES modules. Communication is exclusively `postMessage` in both directions. A worker is tied to the page that created it: close the tab and the worker dies. Use it for anything CPU-bound that would otherwise blow the 50 ms task budget — JSON parsing of large payloads, image filters, cryptographic hashing, diffing, compression, syntax highlighting, physics. The mental model: a worker turns a long synchronous main-thread task into an asynchronous request that resolves later, freeing the main thread for input and rendering in the meantime.</p>

    <p><strong>Dedicated, shared, and module workers.</strong> There are three forms. A <em>dedicated worker</em> — the common case — belongs to one page and serves only it. A <em>shared worker</em> (`new SharedWorker('s.js')`) is shared across all tabs of one origin: each tab connects through a `MessagePort`, and the worker lives as long as any tab does — useful for one shared WebSocket connection or a coherent cross-tab cache, but support is weaker (not in every browser) and debugging is harder. The worker type is also set by the `{ type: 'module' }` option: a classic worker uses `importScripts()` to load dependencies synchronously, a module worker uses ordinary static `import`. Module workers are the modern default — they give tree-shaking, top-level `await`, and the same module graph as the rest of the app. Classic `importScripts` remains only for legacy code and cases that build the script name dynamically at runtime. One subtlety: the worker script URL must be same-origin (or a blob URL) — you cannot load a worker straight from a third-party CDN without proxying it through your own origin first.</p>

    <p><strong>The structured clone cost.</strong> `postMessage(data)` does not share `data` — it deep-copies it using the structured clone algorithm. Structured clone handles objects, arrays, Maps, Sets, Dates, typed arrays, Blobs, and ArrayBuffers, but not functions, DOM nodes, or class prototypes (methods are lost; only data survives). The copy is synchronous on the sending thread and scales with payload size: roughly 1 ms per MB for plain objects, more for deeply nested structures. Send a 50 MB object and you have just blocked the sending thread for ~50 ms — you moved the work, but you paid a clone tax to do it. Two escapes: <em>transferables</em> and <em>shared memory</em>. `postMessage(data, [data.buffer])` <em>transfers</em> the ArrayBuffer instead of copying — ownership moves to the receiving thread in O(1), and the buffer becomes unusable on the sending side (`byteLength` goes to 0). Transfer is the right move for large binary payloads: image bitmaps, audio buffers, file contents.</p>

    <p><strong>Service workers: the network proxy.</strong> A service worker is registered once (`navigator.serviceWorker.register('sw.js')`), then installed and activated, and from then on it intercepts every network request originating from pages within its scope via the `fetch` event. Inside the `fetch` handler you call `event.respondWith(...)` with a `Response` — from the Cache API, freshly fetched, synthesised, or a mix. This is what enables offline apps, instant repeat loads, and request manipulation. A service worker has no DOM and no persistent global state (it is killed and restarted freely by the browser to save memory), so all durable state lives in the Cache API or IndexedDB. It runs on its own thread, independent of any page — it can receive push notifications and run background sync even when no tab is open.</p>

    <p><strong>The service worker lifecycle.</strong> Registration leads to <em>install</em> (the event where you typically pre-cache the app shell), then <em>activate</em> (where you clean up old caches), then the idle/running cycle where it handles `fetch`, `push`, and `message` events. The lifecycle has one famous trap: a newly installed service worker does <em>not</em> take control of already-open pages by default — it waits in a "waiting" state until every tab using the old worker is closed. This is a safety feature (it prevents a page from running with one worker version and a stale asset cache from another), but it surprises everyone the first time: you deploy a new service worker, reload, and still get the old one. `self.skipWaiting()` in the install handler plus `clients.claim()` in the activate handler overrides this — the new worker activates immediately and claims open pages. Use that combination deliberately; skipping the wait when your asset versioning is not airtight causes the version-mismatch failure mode.</p>

    <p><strong>Cache strategies.</strong> Inside the `fetch` handler you pick a strategy per request type. <em>Cache-first</em>: check the cache, fall back to network — right for immutable, content-hashed static assets (`app.4f3a1c.js`). <em>Network-first</em>: try the network, fall back to cache on failure — right for API responses that should be fresh but must degrade gracefully offline. <em>Stale-while-revalidate</em>: serve the cached copy immediately, fetch a fresh copy in the background to update the cache for next time — right for content that can be slightly stale (avatars, feeds). <em>Network-only</em> and <em>cache-only</em> are the degenerate ends. Libraries like Workbox give these strategies declaratively with route matching, but the strategies themselves are ten lines of `fetch`-handler code; understand them before reaching for the library.</p>

    <p><strong>Worklets: hooks into the browser's own pipeline.</strong> A worklet is a much smaller, more constrained execution context than a worker — it runs a tiny snippet of code <em>inside</em> a browser subsystem, on a thread the browser owns. The <em>paint worklet</em> (CSS Painting API / Houdini) lets you write a custom image-painting function callable from CSS as `background: paint(myPainter)` — the browser runs it during the paint stage. The <em>animation worklet</em> runs animation logic on the compositor thread, so an animation keeps running smoothly even when the main thread is blocked. The <em>audio worklet</em> runs audio-processing code on the real-time audio thread, where the latency and jitter requirements are far stricter than anything the main thread can promise. Worklets have almost no API surface — no DOM, no fetch, often no console — because they run in latency-critical browser threads where you are a guest, not a tenant.</p>

    <p><strong>SharedArrayBuffer: real shared memory.</strong> Every tool above copies or transfers data. `SharedArrayBuffer` (SAB) is the exception: it is a block of memory that two threads can both read and write at the same time, with no copy. You build typed-array views over it on each thread and they see the same bytes. Because two threads writing the same memory is a data race, SAB comes with `Atomics` — `Atomics.load`, `Atomics.store`, `Atomics.add`, `Atomics.wait`, `Atomics.notify` — for race-free reads, writes, and cross-thread blocking. This is the foundation that makes multithreaded WebAssembly (pthreads, Rust threads, C++ threads compiled to WASM) work in the browser. SAB is powerful and dangerous in equal measure, and it is gated: it only exists when the page is <em>cross-origin isolated</em>.</p>

    <p><strong>Cross-origin isolation: the COOP/COEP gate.</strong> After the Spectre CPU vulnerability (2018), high-resolution shared memory became a security risk — a SAB-backed timer is precise enough to mount a side-channel attack. So browsers locked SAB behind two response headers the document must send: `Cross-Origin-Opener-Policy: same-origin` (COOP) isolates your browsing-context group from other origins, and `Cross-Origin-Embedder-Policy: require-corp` (COEP) requires every cross-origin subresource to explicitly opt in to being embedded. When both are present, `self.crossOriginIsolated` is `true` and `SharedArrayBuffer` is available. When they are not, `SharedArrayBuffer` is `undefined` and any code that needs it — multithreaded WASM especially — silently fails. The catch is the cost: COEP breaks cross-origin images, fonts, and scripts that do not send the matching `Cross-Origin-Resource-Policy` header, so enabling isolation often means auditing and fixing every third-party asset on the page.</p>

    <p><strong>OffscreenCanvas: the one exception to "no DOM".</strong> A worker cannot touch the DOM, but canvas is a special case — a canvas bitmap is not part of the DOM tree, it is just a pixel buffer. `OffscreenCanvas` is the canvas decoupled from a `<canvas>` element. The pattern: the main thread calls `canvas.transferControlToOffscreen()`, gets an `OffscreenCanvas`, and transfers it to a worker through postMessage's transfer list. From then on the worker owns the drawing — it can get a 2D or WebGL context and render entirely on its own thread, while the browser reflects the result into the visible `<canvas>` with no main-thread involvement at all. This makes smooth 60 fps WebGL visualisations, map rendering, and games possible even while the main thread is saturated. A worker can also create a standalone `new OffscreenCanvas(w, h)` purely for off-screen rendering — texture generation, image processing — and return the result as a transferable `ImageBitmap`. The constraint that remains: an `OffscreenCanvas` whose control was transferred cannot also be drawn from the main thread — ownership is exclusive, exactly like a transferred `ArrayBuffer`. If both threads need to draw, you need two canvases or a different architecture; the platform deliberately forbids two threads racing on one bitmap.</p>

    <h4 class="mt-2 mb-3 text-[15px] font-semibold text-ink tracking-tight">Failure mode: expecting a worker to touch the DOM</h4>
    <p><strong>The DOM-in-a-worker mistake.</strong> The single most common worker mistake is architectural: teams reach for a worker to "speed up rendering" and discover the worker cannot touch the DOM at all. A worker can compute <em>what</em> should render but never <em>render</em> it — the result must be posted back and applied by the main thread. If the bottleneck is DOM mutation itself (10 000 nodes inserted, a giant React reconciliation), a worker does not help, because the expensive part has to happen on the main thread regardless. Workers help when the bottleneck is <em>pure computation</em> that produces a small result: parse 5 MB of JSON (worker) → post back a 200-row array (cheap) → main thread renders 200 rows (fast). They do not help when the computation's output is itself a large DOM tree. The exception is `OffscreenCanvas`: canvas rendering — and only canvas — <em>can</em> be done from a worker, because a canvas bitmap is not the DOM. Transfer an `OffscreenCanvas` to a worker and it can draw 2D or WebGL entirely off the main thread.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">SharedArrayBuffer and Atomics in depth</h4>
    <p><strong>Why Atomics exist.</strong> Two threads writing the same `SharedArrayBuffer` location without coordination is a data race — the result depends on timing and is undefined. `Atomics` provides operations the CPU guarantees are indivisible: `Atomics.add(view, i, 1)` reads, increments, and writes as one uninterruptible step, so two threads incrementing the same counter never lose an update. `Atomics.compareExchange` is the building block for lock-free data structures. `Atomics.wait(view, i, expected)` blocks the calling thread until another thread calls `Atomics.notify(view, i)` — a real blocking primitive, which is why it is forbidden on the main thread (blocking the main thread is exactly what the platform forbids) and allowed only inside workers. This wait/notify pair is how a WASM thread pool parks idle workers and wakes them when work arrives.</p>

    <p><strong>The memory model.</strong> SAB exposes a <Term k="relaxed_memory_model" lang="en">relaxed memory model</Term>: without atomics, one thread's writes are not guaranteed to be visible to another thread in any particular order — the CPU and compiler may reorder non-atomic memory operations. Atomic operations establish synchronisation edges (<Term k="happens_before" lang="en">happens-before relationships</Term>) that make a batch of preceding non-atomic writes visible. The practical rule for application code: use a single atomic flag as a "data is ready" signal — the worker writes the bulk data with plain typed-array writes, then does one `Atomics.store` on the flag; the reader does one `Atomics.load` on the flag, and once it sees the ready value, all the bulk writes are guaranteed visible. Hand-rolling lock-free structures without this discipline produces bugs that appear only under load, only on certain CPUs.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Service worker edge cases</h4>
    <p><strong>The update-and-version-skew problem.</strong> A service worker controls a page; its asset cache is versioned to <em>its</em> code. When you deploy version N+1, a page may be running version N's worker while N+1's HTML has shipped — or the reverse. If the worker serves a cache-first `app.js` from version N while the HTML expects version N+1's `app.js`, you get a runtime error from mismatched modules. The robust pattern: content-hash every asset filename (`app.4f3a1c.js`), so old and new assets coexist in the cache without collision; precache the full set for each version under a version-tagged cache name; in `activate`, delete caches whose version tag is not the current one — but only after `clients.claim()` so no controlled page loses its assets mid-session. Navigation requests use network-first or a dedicated app-shell strategy so a user always lands on HTML consistent with the active worker.</p>

    <p><strong>Service workers are not durable.</strong> The browser kills an idle service worker aggressively — often within seconds of finishing a `fetch` event — and restarts it on the next event. Any state held in a module-level variable is gone on restart. This is a frequent bug source: a counter, a cache of in-flight requests, a WebSocket held in a global all evaporate. Durable state must live in `IndexedDB` or the Cache API. Long-running work inside an event handler must be wrapped in `event.waitUntil(promise)` — that tells the browser "do not kill me until this promise settles." Forgetting `waitUntil` means the browser may terminate the worker mid-operation, and background sync, push handling, and cache population silently fail to complete.</p>

    <p><strong>Navigation interception and the app-shell danger.</strong> The most powerful — and most dangerous — service worker pattern is intercepting navigation requests: the `fetch` handler catches the request for the HTML document itself and returns a cached app shell. This gives instant loads, but it creates a class of bug otherwise impossible — a service worker can "trap" users on a broken version. If you ship a bug in the app shell and cache it cache-first, every repeat visit serves the broken shell from cache, bypassing the network where the fix lives. The user cannot escape with an ordinary reload. The defence is layered: navigation requests should be network-first with a short timeout (try the network ~3 s, fall back to cache) so a fix reaches users on the first successful load; keep a "kill switch" — a versioned endpoint the worker checks, which on a signal calls `self.registration.unregister()` and clears caches; and never cache navigation cache-only. A broken service worker shipped widely is a stop-the-deploy incident, because ordinary users have no recovery button.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Worker pools and the cost model</h4>
    <p><strong>When workers pay off — and when they do not.</strong> Spawning a worker is not free: a new realm, a new event loop, a fresh copy of any imported scripts, typically 5–20 ms of startup plus a few MB of memory. A worker is worth it when the task is long (tens of ms or more) and the result-transfer cost is small relative to the compute. It is a net loss when the task is short — the postMessage round-trip and clone overhead can exceed the work itself. For repeated small jobs, do not spawn a worker per job; maintain a <em>worker pool</em>: a fixed set of N workers (commonly `navigator.hardwareConcurrency` minus one, to leave a core for the main thread), a queue of pending jobs, and a dispatcher that hands the next job to the next free worker. The pool amortises startup cost and bounds memory. Libraries like Comlink remove the postMessage boilerplate by wrapping a worker in a proxy so calls look like normal async function calls — but the clone/transfer cost and the architectural constraints are unchanged underneath.</p>

    <p><strong>Comlink and the RPC illusion.</strong> Comlink makes `await worker.heavyCompute(data)` look like a local call. This is ergonomic, but the abstraction hides the two costs that still matter: every argument is structured-cloned (or must be explicitly wrapped with `Comlink.transfer`), and every call is a task hop each way. The illusion breaks for chatty interfaces — a worker API with many small methods called in a tight loop pays a task hop per call and serialises the program on the round-trips. Design worker interfaces coarse: one call that does a batch of work and returns a batch of results, not many fine-grained calls. The same principle as designing a network API: minimise round-trips, maximise work per round-trip.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Production observability</h4>
    <p><strong>Debugging across threads.</strong> Each worker and each service worker is a separate context in DevTools. Web workers appear in the Sources panel's thread list; service workers have a dedicated panel under Application → Service Workers showing the lifecycle state (installing, waiting, activated), with buttons to skipWaiting, unregister, and force-update. The Application → Cache Storage panel shows exactly what the service worker has cached. For production telemetry, instrument both sides of every postMessage with timestamps so you can measure real task-hop latency and clone cost in the field — local dev on a fast machine systematically understates both. Track service worker `fetch`-handler duration: a slow handler delays every navigation and resource load on the page, and because it runs before the main thread sees the response, a regression there is invisible to ordinary main-thread profiling.</p>

<Misconception id="mc-worker-dom">
**Myth:** Move slow rendering into a web worker to speed it up.

**Reality:** Workers have no DOM — they compute *what* to render, the main thread still renders it. They help when the bottleneck is pure computation with a small result, not a large DOM tree. Canvas is the exception, via `OffscreenCanvas`.
</Misconception>

The same encapsulation principle that makes a module's private state safe to reason about, enforced here at the thread boundary. <SpiralCue thread="encapsulation" lang="en" /></p>
