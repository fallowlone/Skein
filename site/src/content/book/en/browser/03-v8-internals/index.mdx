JavaScript is a dynamic language: variables hold any type, objects gain and lose properties at will, every call site is polymorphic by design. The CPU underneath cares about none of that — it wants registers, predictable layouts, branch targets known in advance. V8 bridges the gap with a four-tier JIT and a concurrent garbage collector. The performance gap between code V8 loves and code V8 cannot optimise is roughly 100x. Knowing which side of the line you are on is the difference between 60fps and a hung tab.

<Crux>V8 = 4 JIT tiers + hidden classes + ICs + Orinoco GC. Polymorphism above 4 shapes kills hot paths 10-50x.</Crux>

The mental model: JavaScript code is bytecode-interpreted in Ignition while V8 records what types each call site sees. Hot code climbs the tiers — Sparkplug for cheap-and-fast, Maglev for mid-tier optimised, TurboFan for the hottest paths. At each tier, V8 specialises on observed types (hidden classes); deviation from those assumptions triggers deoptimization back to a lower tier. Object property access goes through inline caches whose state tracks how many object shapes that one source line has seen. Orinoco GC walks the heap concurrently with JavaScript execution, evacuating young objects in parallel and marking old ones in the background, keeping pauses below 1ms in well-behaved apps. Every senior frontend perf question — why is this loop slow, why does this page jank, why did adding one field tank a render — answers from this stack.

    <p><strong>What V8 is in one sentence.</strong> V8 is the JavaScript engine inside Chrome, Edge, and Node.js — it takes the JS source code and turns it into machine code that the CPU runs.</p>
    <p><strong>Why care.</strong> The same JS function can run 100x faster or slower depending on whether V8 can optimise it. A few small habits (consistent object shapes, monomorphic call sites) make the difference between 60fps animation and a janky page.</p>
    <p><strong>The metaphor.</strong> V8 is a kitchen with four cooks. Trainee (Ignition) reads every recipe slowly but logs what was ordered. Line cook (Sparkplug) cranks out fast generic versions. Sous-chef (Maglev) makes specialised versions for popular dishes. Head chef (TurboFan) hand-crafts perfect for the most-ordered — but only if orders stay consistent. Change order mid-bite, TurboFan tosses the dish.</p>

  <Fragment slot="middle">
    <p><strong>The four-tier pipeline.</strong> V8 has four execution modes layered by compile-time-vs-run-time tradeoff. <em>Ignition</em>: the bytecode interpreter. The parser produces an AST; Ignition lowers it to a compact register-based bytecode and runs that on a virtual machine. While interpreting, Ignition records type feedback into a per-function FeedbackVector — slots for each "interesting" location (property load, function call, arithmetic, comparison). Cheap to enter (no compile cost), 10x slower per instruction than optimised native code. <em>Sparkplug</em>: the baseline JIT, added 2021. Sparkplug emits unspecialised machine code in a single linear pass over the bytecode — no SSA, no real optimisation, just a faithful translation of each bytecode to a small block of machine instructions plus a tail call. Compile cost is essentially free (sub-millisecond per function); speedup over Ignition is 1.5-2x. <em>Maglev</em>: the mid-tier optimising compiler, added 2023. Maglev uses observed types from the FeedbackVector and SSA-based optimisations to emit specialised machine code, but skips the heavyweight passes of TurboFan. ~10x slower compile than Sparkplug, ~10x faster compile than TurboFan, code roughly halfway between the two in runtime speed. <em>TurboFan</em>: the heavy optimising compiler. Aggressive inlining, escape analysis, range analysis, hidden-class-driven specialisation, speculative optimisations that may deopt. Compile cost is high (tens to hundreds of ms for complex functions); runtime code is the fastest V8 produces.</p>
    <p><strong>Profile-guided tiering.</strong> Functions enter Ignition. After execution-count thresholds are crossed (per-function, dynamic), V8 promotes to the next tier. Recent V8 uses profile-guided tiering: the FeedbackVector tracks not just types but also branch frequencies, so TurboFan can lay out the hot path with optimal branch prediction. The thresholds are tuned per-tier: Sparkplug at ~100 calls, Maglev at low thousands, TurboFan at tens of thousands. Promotion happens off-thread (concurrent compilation) — the JS main thread keeps running on the current tier while a worker thread compiles the next.</p>
    <p><strong>Hidden classes (also called Maps or Shapes).</strong> JavaScript objects are dynamic — properties can be added, deleted, reordered — but V8 internally represents each object as a pointer to a hidden class (Map in V8 source) plus a sequence of property slots. Two objects with the same property names added in the same order share one hidden class. When you add a property to an existing object, V8 transitions to a new hidden class along a "transition tree" — adding "x" then "y" goes to one class; adding "y" then "x" goes to a different one (even though both objects have the same logical contents). This matters because the inline cache keys off the hidden class pointer. <em>Stable hidden classes are the foundation of V8 performance.</em> Construct objects with all properties up front (in constructors or factory functions). Avoid <code>delete</code> on object properties — it forces a transition to a dictionary-mode object that is permanently slow.</p>
    <p><strong>Inline caches and their states.</strong> Every property access in JS is a polymorphic operation — the object could be any shape. V8 generates a tiny per-call-site cache: the first time the line runs, V8 records the hidden class it saw and the property offset for that class. Next time the same line runs and the object has the same hidden class, V8 reads the property at the recorded offset directly (5-10 cycles). The IC state machine: <em>uninitialized</em> (no observations), <em>monomorphic</em> (one hidden class seen — fast direct access), <em>polymorphic</em> (2-4 hidden classes — linear chain of class checks, still fast), <em>megamorphic</em> (5+ — V8 gives up on specialisation, falls back to the generic property lookup which is 10-50x slower). The IC state lives in the FeedbackVector slot for that source line. A function can have hundreds of IC slots; one megamorphic site does not kill the whole function, but a hot loop containing a megamorphic property access kills its loop body.</p>
    <p><strong>Deoptimization (deopt).</strong> When TurboFan optimises a function, it bakes in assumptions: "this argument is always a smi" (small integer), "this object's property z is always a number", "this loop never overflows 32-bit indices". A guard is inserted at each assumption. If at runtime any guard fails, V8 deoptimizes: throws away the compiled code, reconstructs the interpreter state from the optimised frame, and resumes execution in Ignition (or Sparkplug). The function may climb back up later, but the deopt itself is expensive (~microseconds). Common deopt triggers: passing a different type to a previously-typed argument, indexing past array bounds, hitting NaN in a numeric operation, accessing a deleted property. Chrome DevTools (<code>--trace-opt --trace-deopt</code> flags) exposes deopts; <code>%OptimizationStatus(fn)</code> at <code>--allow-natives-syntax</code> in d8 shows the current tier.</p>
    <p><strong>Orinoco: V8's concurrent garbage collector.</strong> The heap is divided into young generation (small, frequently collected) and old generation (large, infrequently collected). <em>Minor GC (Scavenger)</em>: copies live young objects from "from-space" to "to-space" semispace; dead objects are abandoned. Runs in parallel across multiple threads using dynamic work-stealing. Pauses on the main thread are short (~1ms typical) because young-gen heap is small. Survivors of two scavenges are promoted to old generation. <em>Major GC (Mark-Compact)</em>: traces all live objects from roots, marks reachable, sweeps dead, compacts surviving objects to reduce fragmentation. Pre-Orinoco this was a stop-the-world operation lasting hundreds of ms in big heaps. Orinoco moved marking to a concurrent thread that walks the heap while JS runs on the main thread; the actual pause for sweep/compact is reduced 50% on WebGL-heavy workloads. Pause-time budget on the main thread is the hardest performance constraint; Orinoco's design philosophy is "make GC pauses imperceptible at 60fps (16.6ms)".</p>
    <p><strong>The hot path: combining all of the above.</strong> A function in a tight loop hits the optimised flow: TurboFan-compiled, monomorphic IC at every access, hidden class stable, no GC interruption. Per-iteration cost is single-digit nanoseconds. Break any one of those and cost climbs: polymorphic IC → 2x, megamorphic IC → 10-50x, deopt mid-loop → 100-1000x for the loop body, GC pause → milliseconds visible to the user. Frontend perf engineering is almost entirely about keeping all four wheels on this car: stable object shapes, monomorphic call sites, no surprises that trigger deopt, low GC pressure.</p>
    <p><strong>Operational levers for JS perf.</strong> (1) Constructor pattern: declare all object properties in one place so hidden classes are stable. (2) Avoid <code>delete</code> on objects (use null or undefined assignment instead, or never declare properties you might want to remove). (3) Keep functions monomorphic: do not pass different shapes to the same call site. (4) Avoid <code>arguments</code> in old code; use rest parameters. (5) Pre-allocate arrays with known capacity to avoid resize. (6) Reuse object pools for short-lived workloads (canvas, animation) instead of allocating new objects per frame. (7) Avoid massive object literals in hot paths (they go megamorphic fast). (8) For very hot numeric loops, use TypedArrays — V8 has highly tuned paths for Uint32Array and friends that bypass the IC layer entirely.</p>
    <p><strong>Tooling and observation.</strong> Chrome DevTools Performance panel shows main-thread time broken down by Scripting / Rendering / Painting / GC. Memory panel snapshots and timeline diffs. Node.js: <code>--trace-opt --trace-deopt</code> flags log every promotion and demotion; <code>--print-bytecode</code> dumps Ignition bytecode; <code>--print-opt-code</code> dumps TurboFan-emitted machine code. d8 (V8 shell) with <code>--allow-natives-syntax</code> exposes intrinsic functions like <code>%HasFastProperties(obj)</code> (is the object in dictionary mode?), <code>%GetOptimizationStatus(fn)</code> (which tier?), <code>%DebugPrint(obj)</code> (full internal layout). Production perf debugging usually starts from DevTools, drills into a specific function, and ends in d8 to confirm the V8-level diagnosis.</p>
    <p><strong>Memory layout: in-object vs out-of-object properties.</strong> V8 stores the first ~8 properties of an object inline in the object's memory block; subsequent properties go to an out-of-object PropertyArray pointed to by the object. Access to in-object properties is a single memory load; out-of-object adds one pointer dereference. The "in-object slot count" is fixed at hidden class creation — adding more properties later spills to the PropertyArray. For perf-critical objects, declare the most-accessed properties first in the constructor so they land in-object. Beyond that, hidden classes also have a "dictionary mode" fallback: objects with too many properties (~32+) or many deletions transition to a HashMap-backed representation where every access goes through the slow generic path. This is the "dictionary mode" warning in V8 tooling — once in, the object is permanently slow.</p>
    <p><strong>Numeric specialisation: smi, heap-number, double.</strong> V8 represents small integers (Smi) inline in a 64-bit pointer slot with the low bit cleared — no allocation, no indirection, arithmetic in one CPU instruction. Numbers outside the smi range (±2^30 on 32-bit isolates, ±2^31 on 64-bit) become HeapNumbers — boxed in a heap-allocated cell with a double inside. The Smi-to-HeapNumber transition is V8's most common deopt trigger: a TurboFan-compiled loop assumes Smi, the value overflows once, deopt cascade. The fix: bound the integer range or use Math.fround / explicit Float64Array. Engineers writing perf-critical JS internalise the Smi range and design data flows to stay inside it.</p>

    <p><strong>The FeedbackVector: V8's profile-guided heart.</strong> Every function in V8 has an associated FeedbackVector — a fixed-size array indexed by source-position-derived slot numbers. Each slot corresponds to one "interesting" operation (property load, function call, binary operator, etc). The slot stores either a single observed hidden class pointer (monomorphic), a small array of hidden classes (polymorphic), or a "MegamorphicSentinel" object indicating the IC has given up. The FeedbackVector is allocated lazily on first execution and lives in the GC heap as a HeapObject. Sparkplug, Maglev, and TurboFan all read from it: Sparkplug uses minimal feedback (just the type), Maglev uses richer feedback (hidden class chains, call target frequencies), TurboFan uses everything plus inference about loop trip counts and branch probabilities. The FeedbackVector is the most concrete way to see V8's runtime profiling — d8's <code>%DebugPrintFeedback(fn)</code> dumps it. In production, a function's FeedbackVector pollution (e.g. a single megamorphic slot) explains why V8 cannot keep the function optimised even after deopt-and-reopt cycles.</p>
    <p><strong>Sparkplug: the JIT that does not actually optimise.</strong> Added in V8 9.1 (May 2021), Sparkplug is technically a baseline JIT but is more accurately described as "an interpreter that emits machine code directly". It does no <Term k="ssa" lang="en">SSA</Term>, no inlining, no instruction scheduling. For each Ignition bytecode, Sparkplug emits a fixed sequence of machine instructions that implements that bytecode. The result is approximately 1.5-2x faster than Ignition because the per-instruction overhead of the interpreter dispatch loop (dispatch table lookup, indirect jump) is replaced by direct execution of native code. Sparkplug's compile speed is near-free: ~1ms per kB of bytecode. The point of Sparkplug is to give hot-but-not-hot-enough-for-Maglev functions a measurable speedup without paying Maglev's compile cost. Google's V8 blog describes Sparkplug as "a non-optimizing compiler that produces code faster than you can run the interpreter". Documented average benefit: 5-15% on real workloads.</p>
    <p><strong>Maglev: SSA, but cheap.</strong> Added in 2023, Maglev fills the gap between Sparkplug and TurboFan. The compile pipeline: bytecode → Maglev IR (SSA) → register allocator → native code. The IR is simpler than TurboFan's (no concept of effect chains or graph rewriting passes), the register allocator is a simple linear scan rather than TurboFan's graph-colouring. Maglev does some speculative optimisation — uses observed types to specialise property loads, calls, and arithmetic — but skips the heavyweight passes (escape analysis, polymorphic inlining, type-narrowing iteration). Maglev compile time is ~10ms per function vs TurboFan's ~100ms; runtime code is ~50-70% of TurboFan's quality. The role of Maglev is to handle the "medium hot" tier — functions called thousands of times but not tens of thousands — without paying TurboFan's compile cost. V8's tiering policy now goes Ignition → Sparkplug → Maglev → TurboFan; functions can skip tiers if their hotness profile demands.</p>
    <p><strong>TurboFan's speculative optimisations.</strong> TurboFan is V8's heavy-weight optimising compiler. It builds a <Term k="sea_of_nodes" lang="en">sea-of-nodes</Term> graph IR, performs aggressive <Term k="escape_analysis" lang="en">escape analysis</Term> (object allocations can be stack-allocated or elided entirely if they never escape), inlines <Term k="polymorphic_inlining" lang="en">polymorphic</Term> call sites if there are 2-4 known targets, narrows types iteratively (a variable known to be 0..255 stays in a byte register), and emits highly-tuned machine code. Crucially, TurboFan installs guard instructions in front of every speculative assumption: a "this is a smi" guard before every numeric op, a "this object has hidden class HCx" guard before every property access. A guard failure means deopt. The cost-benefit is that TurboFan-optimised code is often 3-10x faster than Maglev when assumptions hold; when they break, the deopt overhead and falling back to a lower tier is worse than never having TurboFan-compiled in the first place. Production V8 carefully balances "should I optimise this function with TurboFan?" via profile-guided heuristics — functions whose feedback is unstable (frequent IC transitions) are deferred or skipped.</p>
    <p><strong>Hidden class transition trees in detail.</strong> When you write <code>const p = &#123;&#125;; p.x = 1; p.y = 2;</code>, V8 creates four hidden classes: empty → x → x+y, with each "transition edge" labelled by the property name added. A second object <code>const q = &#123;&#125;; q.x = 1; q.y = 2;</code> traverses the same path and ends up at the same hidden class as p. But <code>const r = &#123;&#125;; r.y = 2; r.x = 1;</code> takes the path empty → y → y+x, ending at a different hidden class than p and q. The transition tree is shared across all objects in the V8 isolate, so memory cost is bounded. Pathological cases: code that adds properties in dynamic order creates many leaf nodes in the tree, scattering objects across many hidden classes — the same shape never repeats, so ICs are perpetually polymorphic/megamorphic. <em>The 2008 V8 design assumption is that programmers naturally write code that constructs similar objects in similar orders.</em> Most code does; pathological code that breaks this (often generated code, JSON parsers writing properties in arbitrary input order) suffers severe perf degradation.</p>
    <p><strong>Inline cache memory layout.</strong> An IC slot in the FeedbackVector is 16 bytes: 8-byte hidden class pointer (or sentinel) + 8-byte handler object. The handler is a small piece of generated code (or a reference to it) that knows how to read/write the property given the cached hidden class. Polymorphic ICs use a different handler type that branches on hidden class. Megamorphic ICs use a generic handler that hits the V8 runtime's slow lookup path (the megamorphic_property_load_builtin in V8 source). A complete tour of one IC access in V8 source: ic_inl.h, ic.cc, ic-state.cc — the state transitions are explicit. Production-grade V8 work routinely involves looking at these for one specific call site that is mis-optimising. Mathias Bynens's "JavaScript engine fundamentals: Shapes and Inline Caches" remains the canonical external reference.</p>
    <p><strong>Orinoco: minor and major collector in detail.</strong> The V8 heap is divided into <em>young generation</em> (newly allocated, ~1-8 MB) and <em>old generation</em> (long-lived, can be 100s of MB). Minor GC (Scavenger) uses a copying collector with two semispaces: from-space holds live objects, to-space is empty. On collection, V8 walks roots (stack, globals, registers), copies reachable young objects to to-space, updates pointers. Survivors of two minor GCs are promoted to old generation. The Scavenger is parallel since 2017 (Orinoco's first major shipping feature): multiple worker threads share the work via dynamic work-stealing. Pauses on the JS main thread are short (~1ms for typical young heaps) because the live set is small and parallelism keeps wall-clock low. Major GC (Mark-Compact) marks all reachable objects in old gen, sweeps dead, compacts to reduce fragmentation. <em>Concurrent marking</em>: a background thread walks the heap while JS executes; write barriers ensure newly-written references are also marked. Concurrent marking reduces main-thread pauses by 50% in WebGL-heavy workloads (per Google blog). The remaining stop-the-world work is the final marking step (a brief pause to verify the concurrent thread's view) and the sweep/compact phase (parallel across worker threads but still blocking the main thread).</p>
    <p><strong>Incremental marking and write barriers.</strong> Before Orinoco, V8's major GC was a fully stop-the-world operation that could pause the main thread for hundreds of ms. To enable concurrent marking, V8 added a <em>write barrier</em>: every property write that may cross from a black (marked) object to a white (unmarked) object triggers a small piece of code to mark the destination object grey (to be visited). The write barrier is conceptually cheap (a few cycles) but happens on every reference write — V8 invests heavily in making it fast (specialised barriers per property type, <Term k="yuasa_snapshot" lang="en">snapshot-at-the-beginning</Term> vs incremental-update tradeoffs). The result is that marking is amortised across JS execution with no observable pause, only a small per-write overhead. Modern V8 uses <Term k="tri_color_marking" lang="en">Tri-color marking</Term> (white/grey/black) with snapshot-at-the-beginning semantics and a hybrid concurrent + incremental scheduling. <em>The choice of marking algorithm directly shapes write-barrier cost and pause distribution.</em></p>
    <p><strong>Pointer compression.</strong> V8 6.6 added pointer compression: instead of 64-bit pointers, V8 stores 32-bit offsets from a base address. This halves heap memory for typical workloads (most heaps are well under 4GB). The cost is a small extra cycle on every pointer dereference (add the base, then load), but cache effects from the smaller heap more than compensate. Pointer compression is the reason V8's per-process heap is capped at 4GB by default — beyond that, you need the larger pointer mode. Pointer compression interacts with hidden classes: the per-object hidden class pointer is now 32 bits, halving the per-object overhead. For an app that allocates millions of small objects (typical of any large JS framework), pointer compression alone saves hundreds of MB. Disabled at compile time on systems where 32-bit offsets are insufficient.</p>
    <p><strong>Real production failures.</strong> Discord 2022: a chat-feature change introduced a polymorphic IC in the message-render hot path; p99 frame time went from 8ms to 25ms; rolled back when reported by gaming-mode users with 120Hz monitors. Figma 2023: an editor refactor leaked closures in a long-lived animation callback, causing old gen to grow 200MB per session; fixed by hoisting the closure outside the per-frame call. Google Maps 2024: a 3D-tile renderer hit megamorphic ICs after a typing refactor where some tile objects had an extra optional field; throughput dropped 40%, fixed by always-allocating the field with null when absent. Slack 2021: a Node-side serialisation function deoptimized every minute due to occasionally hitting NaN in a numeric reduce; the deopt cycle ran every 60s costing 5ms each, visible as periodic latency spikes; fixed by guarding the NaN before the hot loop. The pattern: V8 perf bugs hide as "small refactor" PRs that shift one object's shape or one function's type signature; the perf regression appears in production rather than CI.</p>
    <p><strong>Isolates: V8's tenant isolation.</strong> An Isolate is one independent V8 instance with its own heap, GC, and compilation queues. Each browser tab is its own Isolate; Node.js has one Isolate per process. Isolates do not share state — communication goes through serialisation (postMessage, IPC). This is V8's tenant isolation primitive: a memory leak in one Isolate cannot affect another. Worker threads in Node use Isolates plus shared memory regions for explicit cross-thread communication. The Isolate boundary is also a security boundary — V8 sandboxes (the experimental V8-Sandbox project) attempt to confine memory-corruption bugs to the Isolate's heap so a compromised script cannot escape to host process memory. For server-side multi-tenant JS (Cloudflare Workers, Vercel Edge), each tenant gets its own Isolate, allowing thousands of tenants per machine with strong memory isolation.</p>
