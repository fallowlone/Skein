TCP agreed on sequence numbers, DNS resolved a name to an IP — now <PersonaTag id="bea" lang="en" /> (browser) and <PersonaTag id="sven" lang="en" /> (server) must agree on encryption before sending anything that matters. That encryption is negotiated in the TLS handshake. For decades, this negotiation took two round-trips over the network. TLS 1.3 cut it to one by moving cryptographic work forward: the client sends not just supported ciphers but its own ephemeral key in the opening message, letting the server derive a shared secret and send encrypted data in the same RTT.

<Crux>How key shares and ECDHE collapse TLS 1.2's two-RTT handshake into one, and what 0-RTT buys you.</Crux>

The goal of TLS is to build a sealed channel: one that anyone can intercept but only the sender and receiver can read. Before TLS 1.3, building that channel required at least two round-trips. TLS 1.3 redesigned the handshake to move key material into the first message, enabling the server to compute the shared secret and send encrypted application data without waiting. The trade-off: cold connections still cost one round-trip before the first encrypted byte, but warm connections (resumption via pre-shared keys) cost zero.

  <Fragment slot="junior">
    <p>TLS is a sealed envelope. <PersonaTag id="bea" lang="en" /> has a message. She wants to mail it to <PersonaTag id="sven" lang="en" />, but she fears the mailman will read it. So she puts it in a box, locks it with a seal, and mails it. On the way, anyone can see the box, but no one can read what's inside — only Sven, who has a matching key, can unlock it. Before mailing, though, Bea and Sven need to agree on the seal and the key. They meet online and negotiate: "Let's use AES as the lock, SHA-256 as the wax, and here's my half of the key." Sven replies: "I got it, here's my half." They combine the halves, derive a shared seal, and now every message Bea sends is locked with it. TLS 1.3 made this meeting shorter by letting Bea send her half of the key in her first message instead of waiting for Sven to ask for it.</p>
  </Fragment>
  <Fragment slot="middle">
    <p><strong>The 1-RTT handshake dance.</strong> <PersonaTag id="bea" lang="en" /> sends <code>ClientHello</code>, which includes the TLS version, supported cipher suites, <strong>and an ephemeral ECDHE public key (key share)</strong>. <PersonaTag id="sven" lang="en" /> receives it, picks a cipher suite and curve, generates his own ephemeral key pair, and replies with <code>ServerHello</code> containing his public key. Both sides now have each other's ephemeral public keys and can derive a shared secret using elliptic-curve Diffie-Hellman (ECDHE). Sven signs his server certificate (proof he's really google.com) with his long-term private key and sends <code>Certificate</code> and <code>CertificateVerify</code>. <PersonaTag id="cara" lang="en" /> (the certificate authority) issued that certificate, and Bea carries Cara's public key in her root store. Bea verifies the certificate chain, checks Sven's signature on the handshake transcript, and computes the shared secret. She sends <code>Finished</code> containing an HMAC of the entire handshake, proving she computed the same secret. From this point on, all data between them is encrypted with keys derived from the shared secret. Cost: one full RTT (ClientHello and ServerHello cross the wire once each).</p>
    <p><strong>Perfect Forward Secrecy (PFS).</strong> Both the client and server use ephemeral (temporary) key pairs, generated fresh for this connection. If an attacker later steals Sven's long-term private key from his server's disk, the attacker <strong>cannot decrypt past sessions</strong> because the past sessions used ephemeral keys that are already deleted. This is why PFS matters: compromise of the server today does not leak yesterday's secrets. RSA key transport (the old TLS 1.2 mode) avoided this: the client encrypted the shared secret with the server's long-term public key, so stealing the private key meant decrypting all past sessions. TLS 1.3 mandates ephemeral key exchange, making PFS the default.</p>
    <p><strong>Session resumption via PSK (pre-shared key).</strong> After the handshake, the server sends a <code>NewSessionTicket</code> — an encrypted ticket containing a pre-shared key and metadata. The browser caches it. On the next connection to the same server, Bea sends the same <code>ClientHello</code> but now includes a <code>pre_shared_key</code> extension with the ticket. Sven decrypts the ticket, recognizes it, and skips certificate validation. He derives the shared secret from the PSK instead of ECDHE, and both sides continue. Cost: still one full RTT, but no expensive cryptographic operations on the server.</p>
    <p><strong>0-RTT mode.</strong> If a browser has a cached PSK, it can encrypt the first request (e.g., a GET) using the PSK's key, and send the encrypted data inside the <code>ClientHello</code> itself. The server decrypts it immediately, processes the request, and responds — all within the same network round-trip as the handshake. Cost: zero RTT for the request. But this safety feature comes with a caveat: <strong>replay vulnerability.</strong> An attacker on the wire captures the 0-RTT ClientHello, and can resend it multiple times. If the request is "GET /news", replays are harmless. If it's "POST /transfer" with amount and recipient, replays are exploitable.</p>
  </Fragment>
  <Fragment slot="senior">
    <p><strong>HKDF key schedule (RFC 8446 §7.1).</strong> TLS 1.3 derives every key from a tree rooted at <code>HKDF-Extract(salt=0, IKM=PSK_or_zero)</code> — the <em>early secret</em>. From the early secret, <code>Derive-Secret(early_secret, "derived", "")</code> produces the salt for the next extract, which mixes in the ECDHE shared secret to yield the <em>handshake secret</em>. The same derive-then-extract pattern produces the <em>master secret</em>. Every traffic key is then <code>HKDF-Expand-Label(traffic_secret, "key", "", key_length)</code> with a matching IV expansion (RFC 8446 §7.3). The <code>Derive-Secret(Secret, Label, Messages)</code> primitive folds the running transcript hash into each step, so an attacker who tampers with any handshake byte invalidates every downstream key. The hash is fixed by the negotiated cipher suite (SHA-256 for <code>TLS_AES_128_GCM_SHA256</code>, SHA-384 for <code>TLS_AES_256_GCM_SHA384</code>) and changing it requires changing the suite — there is no separate hash negotiation.</p>
    <p><strong>0-RTT replay defenses in production.</strong> RFC 8446 §8 and RFC 8470 specify three orthogonal mitigations layered together by serious operators. First, <strong>ticket-age validation</strong>: the client sends <code>obfuscated_ticket_age</code> in the PSK identity; the server subtracts the ticket-issue time, accounts for an expected RTT, and rejects if the result lies outside a narrow window (typical 10 s). Second, <strong>single-use ticket consumption</strong>: an in-memory cache keys on <code>(ticket_nonce, age_bucket)</code> and rejects any second decryption attempt — Cloudflare, Fastly, and AWS run a per-PoP cache plus a best-effort cross-PoP gossip layer so attackers cannot replay across regions inside the window. Third, <strong>application-level idempotency</strong>: only safe methods (GET/HEAD/OPTIONS) ever cross into <code>early_data</code>; non-safe methods must wait for the <code>Finished</code> from the server. Frameworks (Spring, Express, Caddy) expose middleware that inspects the <code>Early-Data: 1</code> request header (RFC 8470 §5.1) and returns <code>425 Too Early</code> for any handler that mutates state. Cryptographically inclined deployments add <strong>puncturable PRFs</strong>: the server's ticket-decryption key advances after every use so the same ciphertext literally cannot decrypt twice, eliminating the cache requirement.</p>
    <p><strong>Session-ticket encryption key (STEK) rotation.</strong> Without forward-secrecy on resumption, a leaked STEK lets an attacker decrypt every 0-RTT payload protected by tickets that key issued. At Cloudflare scale, STEKs rotate hourly, never touch disk, and are pushed to every edge via a memcached-style fan-out; the previous 24 keys are retained for decryption so in-flight tickets continue to resume. Nginx's <code>ssl_session_ticket_key</code> directive accepts a list of files — the first is the encryption key, the rest decrypt-only — and operators reload Nginx with a fresh head to rotate. Two failure modes dominate: keys persisted to disk and recovered after a node compromise, and operators who configure a static <code>ssl_session_ticket_key</code> for a year, turning resumption into a single-key crypto monoculture. The fix is non-negotiable: keep STEKs in memory, rotate at least daily, and shred old material instead of keeping a forever-archive "for debugging."</p>
    <p><strong>Encrypted ClientHello (ECH, RFC 9849).</strong> A vanilla TLS 1.3 <code>ClientHello</code> still leaks Server Name Indication, ALPN, supported groups, signature algorithms, and certificate authorities — enough fingerprint surface to identify the destination domain and the client's stack. ECH (published as RFC 9849 in March 2026) defines an <em>outer</em> ClientHello sent to a public "client-facing" name and an <em>inner</em> ClientHello encrypted via HPKE using the origin's published ECH key. The client fetches that key from a DNS <code>HTTPS</code>/<code>SVCB</code> resource record (RFC 9460) before opening the connection — without it, the client can either GREASE (send fake ECH to mask traffic patterns) or fall back to plaintext SNI. As of May 2026 Chrome ships ECH on by default; Firefox enabled it for general users from version 119 in 2024. Cloudflare terminates ECH on every plan; enterprise networks that need on-path TLS inspection can break it via DoH blocking or HTTPS-RR suppression, and several CISA-aligned MDM profiles do exactly that. Operators integrating ECH must keep the public key rotated (the DNS TTL is the upper bound on key compromise) and remember that the <em>outer</em> SNI still names a generic frontend, which becomes a privacy and abuse signal of its own.</p>
    <p><strong>Hybrid post-quantum key exchange.</strong> The current draft is <code>draft-ietf-tls-ecdhe-mlkem-04</code> (February 2026), which standardizes <code>X25519MLKEM768</code> (named-group codepoint <code>0x11EC</code>) plus <code>SecP256r1MLKEM768</code> and <code>SecP384r1MLKEM1024</code> for FIPS environments. ML-KEM is the NIST FIPS 203 standardization of CRYSTALS-Kyber (August 2024). The hybrid shared secret is the byte-concatenation of the ECDHE result and the ML-KEM result, fed into <code>HKDF-Extract</code> exactly where the classical ECDHE secret used to sit — so the key schedule downstream is unchanged. Wire-format cost is significant: ML-KEM-768 ciphertexts are 1088 bytes, public keys 1184 bytes, which pushes ClientHello over the typical 1500-byte initial congestion window and forces TLS implementations to handle ClientHello fragmentation cleanly. Chrome started experimental rollout in 2024; as of May 2026 hybrid PQ is widely available behind a feature flag but not yet a browser default, while Java 24+ exposes ML-KEM as a first-class JCA primitive. The deployment risk to watch is "store now, decrypt later" — adversaries are recording today's classical-only handshakes for replay against a future cryptographically relevant quantum computer.</p>
    <p><strong>Kernel TLS (kTLS) offload on Linux.</strong> <code>setsockopt(fd, SOL_TLS, TLS_TX, &amp;crypto_info)</code> hands the symmetric record layer to the kernel after user-space completes the handshake. Linux 4.13 shipped TX, 4.17 added RX, and modern kernels (6.0+) plus OpenSSL 3.2+ can offload to NIC hardware so the encrypted record stream is built on the wire by the network card with zero per-record CPU cost. Supported algorithms are AES-128-GCM, AES-256-GCM, and ChaCha20-Poly1305 — TLS 1.3 only. Netflix and Cloudflare both attribute single-digit-to-double-digit-percent CPU savings (8–29% in published benchmarks) to <code>sendfile()</code> over kTLS for static file serving, because the file moves from page cache to NIC without ever entering user space. The catch is that kernel records max out at 2^14 bytes (TLS 1.3 record limit) and that anti-replay logic, alert handling, and renegotiation paths still live in user space — frameworks like Nginx call <code>SSL_sendfile()</code> only when the connection state is steady-state.</p>
    <p><strong>OCSP, CRLite, and the revocation reality.</strong> Online Certificate Status Protocol was supposed to give browsers a real-time "is this cert revoked" check, but soft-fail (the dominant browser default) means any on-path adversary who can block the OCSP responder also turns revocation into a no-op. The web PKI walked away from OCSP between 2024 and 2026: Let's Encrypt stopped serving OCSP responses on 2025-05-07 and ceased issuing certificates with <code>id-pe-tlsfeature must-staple</code> after 2025-01-30, citing the privacy leak that every OCSP query reveals to the responder which sites the user visits. Firefox 137 (January 2025) shipped CRLite by default — a compact, signed cascade of bloom filters covering all WebPKI revocations from Certificate Transparency logs, refreshed every 12 hours, no per-connection responder hit. Apple uses a smaller built-in CRL set; Chrome continues to rely on CRLSets pushed by component update. The operational implication: stapling is still worth keeping where you have it, but new infrastructure should plan around shorter cert lifetimes (90 days, soon 47 days) and CT-log-derived revocation rather than runtime OCSP.</p>
    <p><strong>Production observability for TLS.</strong> A minimum-viable Prometheus sketch for an HTTPS service exposes <code>tls_handshake_duration_seconds_bucket&#123;le=...&#125;</code> (histogram), <code>tls_resumption_total&#123;kind="psk|ticket|none"&#125;</code>, <code>tls_version_total&#123;version="1.2|1.3"&#125;</code>, <code>tls_cipher_suite_total&#123;suite=...&#125;</code>, <code>tls_alpn_protocol_total&#123;alpn="h2|h3|http/1.1"&#125;</code>, <code>tls_early_data_total&#123;outcome="accepted|rejected"&#125;</code>, and <code>tls_ocsp_staple_total&#123;outcome="ok|expired|missing"&#125;</code>. Envoy and Nginx-Ingress emit most of these natively. A handshake p95 above 200 ms on a CDN-fronted origin is a deploy regression smell — usually OCSP fetch latency, an unrotated session ticket key bringing every connection back to a full handshake, or hybrid PQ wire-size pressure on the first packet. Track <em>resumption ratio</em> (resumed / total) per node: a sudden drop usually means the STEK rotated without an overlap window. ALPN distribution is the cheapest health check for HTTP/3 rollout, and an early-data rejection spike often precedes a customer report of "my POST shows up twice."</p>
    <p><strong>CVEs and post-1.3 attack surface.</strong> TLS 1.3 closed the most prominent record-layer disasters (BEAST, CRIME, BREACH, POODLE, padding oracles), but the surrounding ecosystem keeps shipping bugs that operators must triage. CVE-2024-12797 (OpenSSL 3.2–3.4) skipped the "abort on mismatch" branch for Raw Public Key (RFC 7250) server authentication, letting a MITM substitute a different RPK without detection — fixed in 3.4.1. CVE-2025-9230 in OpenSSL's CMS PWRI decryption path introduced an out-of-bounds read/write that turns parsing attacker-supplied CMS into a remote DoS, and on some allocators a code-execution primitive. CVE-2025-9231 leaked SM2 private-key bits via timing measurements on 64-bit ARM, relevant to any deployment using SM2 (state-mandated crypto in mainland China) on Graviton or Ampere hardware. The pattern repeats: ASN.1 parsers, side channels on less-tested algorithms, and authentication-handler branches are where TLS bugs live in 2025–2026. Operations: keep an automated tracker against the OpenSSL security advisories feed, pin a known-good Go <code>crypto/tls</code> version per service, and don't treat "we use TLS 1.3" as a substitute for patch hygiene.</p>
    <p><strong>Middlebox interference and GREASE.</strong> RFC 8446 Appendix D.4 documents the depressing reason TLS 1.3 ships pretending to be TLS 1.2: too many middleboxes (firewalls, government inspection proxies, ancient corporate TLS terminators) abort connections whose record-layer or handshake bytes do not match TLS 1.2 patterns they recognize. So TLS 1.3 puts <code>0x0303</code> (TLS 1.2) in the <code>legacy_version</code> field, sends a dummy <code>ChangeCipherSpec</code> record during the handshake, and disguises the real version inside a <code>supported_versions</code> extension. RFC 8701 (GREASE) defines reserved codepoints — <code>0x0A0A</code>, <code>0x1A1A</code>, <code>0x2A2A</code>, … through <code>0xFAFA</code> — that endpoints sprinkle through extension lists, cipher suite lists, named groups, signature algorithms, and version negotiation. A correct peer ignores unknown values; a fragile middlebox blows up immediately, surfacing the bug to the vendor instead of letting it ossify the protocol. When you debug a TLS 1.3 connection that fails at a customer site behind a corporate proxy, the working theory is almost always middlebox: capture the ClientHello, replay it from outside the network, and 95% of the time the connection completes.</p>
    <p><strong>Cross-protocol interactions.</strong> TLS 1.3 is the cryptographic core that QUIC (RFC 9001) lifted into its own packet protector — there is no separate "QUIC TLS handshake"; the same key schedule produces QUIC initial, handshake, and 1-RTT packet protection keys, so every TLS 1.3 advance (PQ hybrid, ECH, 0-RTT replay defense) arrives in HTTP/3 with no protocol changes. DTLS 1.3 (RFC 9147) does the same for UDP without QUIC. Outside the web, TLS 1.3 underlies modern SMTPS, IMAPS, syslog-over-TLS, gRPC, and service mesh mTLS (Istio, Linkerd) — and the operational concerns above (kTLS, STEK rotation, observability) apply wholesale once you cross the per-instance handshake budget any service mesh demands. A reasonable mental model: TLS 1.3 stopped being a "web" protocol around 2022; treating it as the universal channel-protection primitive is now the right default.</p>
    <p><strong>QUIC packet-protector integration depth.</strong> When QUIC runs TLS 1.3 in-band, the handshake bytes are still standard TLS 1.3 records but they ride inside CRYPTO frames rather than a TCP stream — there is no record-layer fragmentation because QUIC handles segmentation. The key schedule is identical down to <code>HKDF-Expand-Label</code>; QUIC just consumes the early, handshake, and application traffic secrets and runs them through one more <code>HKDF-Expand-Label</code> with the labels <code>quic key</code>, <code>quic iv</code>, and <code>quic hp</code> (header protection) per RFC 9001 §5.1. Header protection is what stops on-path observers from reading packet numbers, which would otherwise leak ordering and reordering across paths — important for connection migration. Operationally this means a single TLS 1.3 implementation backs both your HTTP/2-over-TLS and HTTP/3 deployments; an HSM that does TLS 1.3 ECDHE for HTTP/2 does the same for HTTP/3 because the cryptographic primitives are bit-for-bit identical. The split surfaces only at the I/O boundary: kTLS does not yet cover QUIC because QUIC's packet boundaries do not map cleanly onto kernel TLS records, so high-throughput HTTP/3 servers still pay for crypto in user space — quicly, msquic, and Cloudflare's quiche all sit above kernel UDP.</p>
    <p><strong>Distributed anti-replay across regions.</strong> A single-PoP single-use ticket cache is easy: a bounded LRU keyed by <code>(ticket_nonce, age_bucket)</code> rejects a second decryption attempt in O(1). The hard problem is cross-region: an attacker captures a 0-RTT ClientHello in Frankfurt and replays it through Tokyo within the ticket's age window. Pure synchronous global consensus does not work at line-rate handshake volume, so production stacks settle for "best-effort gossip plus per-region authoritative cache." Cloudflare's approach (publicly described): rotate STEKs every hour; each PoP runs an in-memory cache for the last 10 s of 0-RTT nonces; gossip via a low-latency multicast bus so 90%+ of replays cross enough PoPs to be caught; the remaining tail is bounded by the 10 s window which keeps damage at most three nonce-sized replays per origin per attacker. AWS Cloudfront uses a similar regional design. The takeaway: 0-RTT is acceptable for read-only paths, never for stateful POST/PUT/DELETE, and the application MUST still treat 0-RTT-tagged requests as idempotent-or-rejected at the framework layer.</p>
    <p><strong>SNI/ALPN privacy beyond ECH.</strong> Encrypting ClientHello stops the obvious leaks but TLS sessions remain fingerprintable. JA3 (2017) hashes ClientHello extension list + cipher list + named groups + signature algorithms — the resulting hash identifies a TLS client by stack version (curl 8.5 vs Firefox 124 vs an automation toolkit) with high precision. JA4 (2024) refines this with additional features (ALPN, version count, extension count, sorted vs unsorted) and is the de-facto modern fingerprint. Bot defenders use these hashes to identify automated clients even when User-Agent is spoofed. The defensive perspective: ECH hides <em>which site</em> you visit, but JA3/JA4 still reveals <em>what stack</em> is visiting. The offensive perspective: any malware that ships with a non-mainstream TLS library gets an immediate fingerprint hit. This is why post-2024 evasion tooling reverse-engineers Chrome's exact TLS extension ordering and replays it byte-for-byte. There is no clean protocol-level fix; reducing entropy in ClientHello (GREASE positions, extension order) is what browsers do, and what middleboxes break.</p>
    <p><strong>HSM-backed long-term keys.</strong> The server certificate's private key never has to leave a hardware security module: PKCS#11 (or AWS CloudHSM, GCP Cloud KMS, Azure Key Vault HSM) presents a <code>C_Sign</code> primitive that returns a signature without exposing the key. TLS 1.3 calls this primitive once per handshake (the <code>CertificateVerify</code> over the transcript) — not per-record. Throughput math: a FIPS 140-3 Level 3 HSM at the high end does roughly 10,000–20,000 RSA-2048 sign operations per second; ECDSA P-256 is 30,000–50,000. A single HSM tops out at a small fraction of a Cloudflare-class edge's handshake rate, so production designs front the HSM with a TLS terminator that does keyless TLS (Cloudflare Keyless SSL, RFC 8492 also adapts it for password-authenticated TLS) — the terminator runs in untrusted infrastructure, signs requests are forwarded to the HSM in a trusted zone, and the long-term key never leaves origin custody. Operational caveat: sigops are now your scaling bottleneck for cold handshakes, which makes session resumption a hard requirement and STEK rotation discipline non-optional.</p>
    <p><strong>Real-world failure stories.</strong> Cloudflare February 2017: a buffer-bounds bug in their HTML parser (later named Cloudbleed) leaked TLS-encrypted session data into cached HTML, including some other customers' Auth headers and cookies — TLS protected the wire, not the proxy memory. Let's Encrypt September 2021 chain expiry: the cross-signed "DST Root CA X3" expired and any client without the newer ISRG Root X1 root suddenly failed verification — Android &lt; 7.1.1 was hit hardest, breaking a long tail of devices. Let's Encrypt January 2024: the legacy cross-sign was retired, breaking older OpenSSL versions whose chain-building preferred the expired path. GoDaddy 2023: a leaked STEK in a customer's misconfigured backup let an attacker decrypt several months of cached 0-RTT data after the fact — exactly the failure mode RFC 8446 §2.3 warns about and the reason rotation cadence below one hour matters. Heartbleed (CVE-2014-0160) is still the reference disaster: a missing length check in OpenSSL's TLS heartbeat extension let attackers read 64 KB of process memory per request, including private keys; the post-mortem reshaped the entire memory-safe-TLS ecosystem (BoringSSL, rustls, Tigerl) and is the primary reason kTLS limits the kernel surface to record-layer encryption only.</p>
    <p><strong>mTLS at service-mesh scale.</strong> Istio + SPIFFE/SPIRE issue a fresh leaf certificate per workload, often with TTL ≤24 hours, and rotate via short-lived SVIDs delivered over the SPIRE workload API. At 10,000 pods × 24-hour rotation × even handshake distribution that is 7,000 cert issuances per minute baseline, spiking during deploys. The control-plane CA becomes a hotspot; Istio's recommendation is a hierarchical CA (root → intermediate per cluster) so the leaf-signing path stays warm and on-cluster. The data plane (Envoy) terminates and re-originates TLS for every hop — your end-to-end latency budget pays for a TLS 1.3 handshake at every service boundary unless connection pools are large enough that handshakes amortize across thousands of requests. Observability stays the same metric set (handshake duration, resumption ratio, cipher distribution) but is now reported per-workload, and a single misbehaving service can be diagnosed by an outlier in the <code>tls_handshake_duration_seconds</code> p95 alone.</p>
    <p><strong>TLS 1.2 vs 1.3 handshake costs.</strong> TLS 1.2 required at least two round-trips: ClientHello + ServerHello (one RTT) to exchange parameters and learn the server's certificate, then key exchange and authentication (second RTT). Some implementations used session resumption to skip the second RTT, but the first was unavoidable. TLS 1.3 collapses the first RTT by sending key material in ClientHello, and PSK resumption skips even that for warm connections. QUIC also layers on top: it's a UDP protocol with TLS 1.3, so the cryptographic handshake integrates into the transport handshake — the first QUIC packet can carry 0-RTT data if the client has a cached ticket.</p>

The handshake is now fast, but why do certificate verifications take any time at all? <PersonaTag id="sven" lang="en" /> sends his certificate, and Bea must verify that <PersonaTag id="cara" lang="en" /> (the CA) actually issued it. This verification is cryptographic: Bea uses Cara's public key to check Sven's signature. RSA signatures (traditional) are slower; ECDSA signatures (modern, especially P-256) are faster — on modern x86 server CPUs, roughly a 5× difference, though verification times are hardware-dependent. In large-scale deployments (CDNs, cloud providers), even 1 ms per connection adds up. This is why cached resumption (PSK) matters: it skips the verification entirely.

<SpiralCue thread="encapsulation" lang="en" /> — TLS wraps every byte of application data in a symmetric-key envelope. The envelope is negotiated via asymmetric cryptography (ECDHE, RSA signatures) during the handshake. Once negotiated, the symmetric key handles all data encryption. <SpiralCue thread="statefulness" lang="en" /> — the handshake builds state: both sides remember the shared secret, the negotiated cipher, and derived keys. This state persists until the connection closes or the key renegotiates.

Once the handshake completes, the channel is sealed: every request and response travels encrypted. The next layer up is the protocol on top — HTTP — which negotiates its own version and flow control. TLS 1.3 works beneath it, transparent but essential.
