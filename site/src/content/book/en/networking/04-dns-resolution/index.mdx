You type `google.com` into your browser. The browser does not know where Google is. It sends a question to a recursive resolver — a computer that does the detective work. That resolver does not know either. It starts at the root of the DNS tree, asks which server can answer about `.com`, gets pointed to a TLD server, asks again, gets pointed to Google's authoritative server, asks there, and returns a final answer: `142.250.185.46`. This sequence is DNS resolution. Every time you visit a domain, this negotiation happens silently. But caching, nameserver trees, and DNSSEC signing are where the puzzle becomes interesting.

<Crux>How a recursive resolver climbs the root → TLD → authoritative tree to turn `google.com` into an IP, and where caches and DNSSEC live.</Crux>

DNS is a tree of questions and answers. The tree is anchored at 13 root servers (in reality, ~1950+ instances via anycast, as of 2025). Below them are TLD servers (one per top-level domain: `.com`, `.org`, `.uk`, etc.). Below those are authoritative nameservers for each domain. <SpiralCue thread="statefulness" lang="en" /> — DNS caching spreads state across the browser, operating system, ISP resolver, and authoritative server. Every part of the chain remembers answers for a time (governed by TTL), avoiding repeated questions and making DNS lookups fast.

<TierAccordion id="tier-mechanism" lang="en">
  <Fragment slot="junior">
    <p><PersonaTag id="bea" lang="en" /> (the browser) wants to visit a website. She has a domain name: `example.com`. But the network only understands IP addresses — like a phone number instead of a name. She calls <PersonaTag id="rex" lang="en" /> (the recursive resolver), who is a phone operator. Bea says "Do you know the IP for `example.com`?" Rex doesn't know, but he knows how to find out. He calls the root operator, who sends him to a different operator (the TLD operator). That operator sends him to a third operator (the authoritative server for example.com). That third operator says "IP is 203.0.113.10." Rex writes it down and tells Bea. Bea remembers the answer for a while so she doesn't call Rex again immediately.</p>
  </Fragment>
  <Fragment slot="middle">
    <p><strong>The resolver walk.</strong> A recursive resolver starts with a query like "What is the IP for `cdn.example.co.uk`?" It does not know the answer, so it asks a root server: "Who has the answer?" The root responds: "I don't have it, but ask a `.uk` TLD server." The resolver asks the `.uk` server: "Who has `cdn.example.co.uk`?" The `.uk` server replies: "I don't have it, but ask the authoritative server for `example.co.uk`" (returning the NS record pointing to that server). The resolver then asks the authoritative server directly, and finally gets back an A record: `cdn.example.co.uk A 203.0.113.10`. That IP is the answer.</p>
    <p><strong>Record types.</strong> DNS serves many record types: A (IPv4 address), AAAA (IPv6 address), CNAME (alias), MX (mail server), TXT (text data, used for SPF and DKIM), SRV (service), NS (nameserver). Each record also carries a TTL (Time To Live) — a number in seconds saying "I am valid for this many seconds before you must ask again."</p>
    <p><strong>Caching is the lever.</strong> When the resolver gets an answer, it caches it. If a browser asks the same question 10 seconds later, the resolver returns the cached answer without querying the internet. TTL governs how long the cache entry lives. A TTL of 300 seconds (5 minutes) means the resolver forgets and re-queries every 5 minutes. A TTL of 86400 seconds (1 day) means the browser can reuse the answer for a day. High TTL = fewer queries = faster (but stale data lingers). Low TTL = fresher data = more queries = load on authoritative servers.</p>
    <p><strong>Privacy and integrity.</strong> Traditional DNS runs over UDP port 53 in plaintext. An eavesdropper can see every query. DoH (DNS over HTTPS, RFC 8484) encrypts queries inside HTTPS, hiding the domain you're visiting from your ISP. DoT (DNS over TLS) uses TLS on port 853. Neither protect the data from the resolver itself — the resolver still sees the question — but they hide it from the network.</p>
  </Fragment>
  <Fragment slot="senior">
    <p><strong>DNSSEC chain of trust.</strong> A traditional DNS answer can be forged. DNSSEC adds cryptographic signatures to DNS records. The authoritative server signs its records with a private key; the resolver verifies with the public key. But how does the resolver trust the public key? The answer is a chain: the key is itself signed by the TLD server's key, which is signed by the root. The resolver carries the root's public key (the "trust anchor") and verifies the chain. This is DNSSEC validation. Adoption is patchwork (~30% of zones). Many middleboxes strip DNSSEC records, and large-scale signing requires operational discipline.</p>
    <p><strong>Cache poisoning and its defences.</strong> Before DNSSEC, an attacker could forge a DNS response and trick a resolver into caching false data. In 2008, Kaminsky showed that blind poisoning (guessing the transaction ID and source port) was easy. Modern defences: randomize transaction IDs and source ports—a 16-bit transaction ID combined with a 16-bit randomized UDP source port yields ~2^32 entropy, raising blind-attack cost—implement 0x20 case-mixing (mixing upper/lower case in domain names to add entropy), and deploy DNSSEC validation. These are layered; no single defence is sufficient.</p>
    <p><strong>Anycast architecture.</strong> The 13 root servers (A–M) are named, but each has 1000+ anycast instances globally. Clients query the "nearest" instance (by BGP routing). This distributes load and reduces latency. A root query that once meant long-haul latency now hits a local replica.</p>
    <p><strong>Negative caching and NXDOMAIN.</strong> If a resolver queries for `nonexistent.example.com` and gets "this does not exist" (NXDOMAIN), it caches that too. This prevents a resolver from hammering authoritative servers with questions for domains that don't exist. Negative cache TTL depends on response type: NXDOMAIN and NOERROR-no-data use SOA MINIMUM (typically 1–3 hours per RFC 2308); SERVFAIL responses are capped at 5 minutes. Default is dictated by the authoritative server's SOA MINIMUM field.</p>
  </Fragment>
</TierAccordion>

Now let's trace the walk. <PersonaTag id="bea" lang="en" /> sends a query to <PersonaTag id="rex" lang="en" /> for `cdn.example.co.uk`. Rex starts with a root server, receives a referral to `.uk`, queries `.uk`, receives a referral to `example.co.uk`'s nameserver, queries that, and returns the IP address to Bea.

DNS is the directory of the internet. Without caching, every page load would trigger 4+ network round-trips before the browser even started the HTTP handshake. <SpiralCue thread="statefulness" lang="en" /> — this statefulness (cached answers across the system) is invisible to the user but critical to latency.

<Misconception
  id="r-dns-poison"
  title="Heads-up: TTL isn't security"
>
Low TTL does not prevent cache poisoning. Defences are randomized transaction IDs, random source ports, 0x20 case-mixing, and DNSSEC validation. TTL only controls stale data duration, not poisoning risk.
</Misconception>

DNS is ancient. RFC 1035 is from 1987. Yet it still works because the design is hierarchical and decentralized: no single server holds all the data, and caching distributes load. Modern threats (cache poisoning, eavesdropping) are addressed with DNSSEC, DoH, and entropy-based protections. But the fundamental tree remains: query flows down from root to TLD to authoritative, answer flows back, and caches stay warm.
