HTTP was born request-response: client asks, server answers, connection closes. Chat, trading floors, live feeds — none of those fit that rhythm. WebSocket tears down the request-response wall. One TCP connection. Both sides send any time. After the handshake, you have a full-duplex message pipe that lives until someone unplugs it.

<Crux>How a single persistent TCP connection becomes a full-duplex message pipe — and why applications still crash when clients can't keep up.</Crux>

Every protocol is a contract. TCP says "order and deliver or fail." WebSocket built atop it says "exchange binary or text frames indefinitely until either side closes." That contract is negotiated in the handshake and then the frame format takes over. <SpiralCue thread="statefulness" lang="en" /> — a WebSocket connection IS state: both sides commit to keeping a socket alive, buffering messages, managing backpressure. Break that contract and you leak memory, lose messages, or crash.

    <p><strong>What WebSocket does in one sentence.</strong> It upgrades a normal HTTP connection into a bidirectional message pipe where either side can send at any time without waiting for a request-response cycle.</p>
    <p><strong>Why care.</strong> HTTP is pull-only: client asks, server answers. For live chat, stock tickers, multiplayer games, collaborative editing — anything where the server needs to push updates to the client without waiting for the next request — you need a different model. WebSocket gives you that.</p>
    <p><strong>The metaphor.</strong> Imagine a post office. With HTTP you write a letter, mail it, and wait at the counter for a reply. With WebSocket you and the post office keeper open a direct phone line and chat face-to-face — either one can speak at any moment without waiting.</p>
    <p><strong>How the handshake starts.</strong> <PersonaTag id="bea" lang="en" /> opens an HTTP connection and sends: <code>GET /chat HTTP/1.1</code> plus headers <code>Upgrade: websocket</code>, <code>Connection: Upgrade</code>, <code>Sec-WebSocket-Key: &lt;random base64&gt;</code>, and <code>Sec-WebSocket-Version: 13</code>. <PersonaTag id="sven" lang="en" /> receives this and says: "Yes, I agree to upgrade." He replies <code>101 Switching Protocols</code> with <code>Sec-WebSocket-Accept: &lt;computed value&gt;</code>. Both sides now own the same TCP socket and stop speaking HTTP.</p>
    <p><strong>One scenario end to end.</strong> You open Discord. The browser connects to Discord's server using <a href="/en/networking/03-tcp-handshake/">TCP handshake</a>, wraps it with <a href="/en/networking/05-tls-handshake/">TLS</a>, then upgrades with WebSocket. From that moment until you close the tab, the socket stays open. When a friend sends a message, the server pushes it to your client via the open WebSocket. You type and send, the client pushes to the server the same way. No new connections, no HTTP round-trip latency — just a live pipe.</p>

    <p><strong>The HTTP Upgrade handshake in detail.</strong> The client sends an HTTP/1.1 GET request with specific headers. <code>Upgrade: websocket</code> declares the protocol it wants. <code>Connection: Upgrade</code> tells intermediate proxies this is not a keepalive request — this is a protocol change. <code>Sec-WebSocket-Key</code> is 16 random bytes, base64-encoded; the server will use this to prove it actually processed the upgrade and didn't cache the response (cache-poisoning defense). <code>Sec-WebSocket-Version: 13</code> specifies RFC 6455 (the only version in practice). The server validates: does the Host match, is the method GET, does the HTTP version support Upgrade? If yes, it computes <code>Sec-WebSocket-Accept = base64(SHA-1(Sec-WebSocket-Key + GUID))</code> where GUID is the fixed string <code>258EAFA5-E914-47DA-95CA-C5AB0DC85B11</code>. This is not encryption — it proves the server intentionally processed the request. The server replies <code>HTTP/1.1 101 Switching Protocols</code> with the Accept header. From that moment the connection is no longer HTTP; both sides speak WebSocket frame format.</p>
    <p><strong>The WebSocket frame format.</strong> Every frame starts with 2 mandatory bytes plus length and mask fields. Byte 1: FIN (1 bit) says "this is the last fragment of a message." RSV1-3 (3 bits) are reserved for extensions (e.g., compression). Opcode (4 bits) tells the receiver what the payload means: 0x0 = continuation, 0x1 = text data, 0x2 = binary data, 0x8 = close, 0x9 = ping, 0xA = pong. Byte 2: MASK (1 bit) says whether the payload is masked. Payload length: if the next 7 bits are < 126, they are the length. If 126, the next 2 bytes (uint16) are the length. If 127, the next 8 bytes (uint64) are the length. If MASK=1, the next 4 bytes are the masking key; if MASK=0 they are omitted. Finally, the payload. Total overhead for a small frame sent client→server is 2 (header) + 4 (mask) = 6 bytes. For a small server→client frame it is just 2 bytes.</p>
    <p><strong>Why client frames must be masked.</strong> In the early web, a malicious JavaScript on site-a.com could open a WebSocket to a proxy or firewall. The JavaScript sends bytes that happen to match a cached HTTP response. If the proxy is stateless and naive, it treats those bytes as valid HTTP and echoes them back to the next client request, poisoning the cache. Masking — XORing the payload with a 4-byte random key — randomizes the bytes so the JavaScript cannot craft a specific response. The server XORs back with the same key to recover the data. The server's frames are not masked because JavaScript running on site-a.com cannot read raw bytes from site-b.com's response anyway (same-origin policy). Masking is not encryption; it is obfuscation to break cache-poisoning attacks.</p>
    <p><strong>Fragmentation and continuation frames.</strong> A message can be split across multiple frames. The first frame carries the real opcode (0x1 for text or 0x2 for binary) and has FIN=0. Subsequent frames use opcode 0x0 (continuation) with FIN=0. The last frame has FIN=1. The receiver buffers fragments until FIN=1, then assembles the complete message. Control frames (ping, pong, close) cannot be fragmented and must be ≤125 bytes; they can arrive between data fragments.</p>
    <p><strong>Control frames: ping, pong, close.</strong> A ping frame (opcode 0x9) is a keepalive probe. The receiver must echo it as a pong frame (opcode 0xA) with the same payload. Both are ≤125 bytes. Proxies often have an idle timeout (60 seconds typical); if no TCP packet crosses in that window the proxy closes the connection. Sending a ping every 25–30 seconds resets the idle timer without needing application data. The close frame (opcode 0x8) carries an optional 2-byte status code plus UTF-8 reason text. Standard codes: 1000 (normal closure), 1001 (going away — server shutdown or browser closed), 1006 (abnormal — no close frame received, generated by the implementation), 1008 (policy violation), 1011 (unexpected condition), 1013 (try again later). After receiving a close frame the endpoint replies with one and closes the TCP socket.</p>
    <p><strong>Subprotocol and extension negotiation.</strong> The client can list subprotocols (comma-separated) via <code>Sec-WebSocket-Protocol: chat, superchat</code>. The server picks one and sends it back; if the server sends none the connection has no chosen subprotocol (still valid). Subprotocols let you version or layer protocols on top of WebSocket without needing to change the WebSocket code. Extensions (like compression) are negotiated in <code>Sec-WebSocket-Extensions</code> headers; the server lists which extensions it supports and the client accepts or rejects.</p>
    <p id="ws-vs-sse-vs-longpoll"><strong>WebSocket vs alternatives: latency and overhead.</strong> WebSocket: one persistent TCP connection, 2–6 byte frame header, either side sends instantly. Latency is 0–5 ms per message after the initial handshake. SSE (Server-Sent Events): unidirectional server→client over HTTP/1.1 persistent connection. The server sends <code>Content-Type: text/event-stream</code> and streams messages as lines. Browser's EventSource API handles reconnection automatically via <code>Last-Event-ID</code>. Latency is 3–8 ms; frame overhead is ~5 bytes per message plus metadata. SSE is extremely proxy-friendly and has native auto-reconnect. Long-polling: the client opens an HTTP request and the server holds it open until it has data (or a timeout fires). The response comes back, the client immediately opens a new request. Latency = request latency + server hold time, typically 500–60000 ms. Overhead is a full HTTP header (~500+ bytes per poll). WebSocket wins on latency and overhead; SSE wins on simplicity and proxy compatibility; long-polling is the fallback.</p>
    <p id="backpressure-failure"><strong>Backpressure and flow control.</strong> TCP has a receive window — the receiver advertises how many bytes it can accept. The sender's congestion window limits how much it can send without waiting for ACKs. When the application on the receiving end is slow (stuck in a database query), the kernel's socket buffer fills. The receiver advertises a shrinking window. The sender pauses. If the sender is a WebSocket server broadcasting to 1000 clients and 10 of them are slow, those 10 clients' buffers fill. The server's <code>send()</code> call would block waiting for the window to open. In production the server usually does not block — it queues the message in an application-level buffer. If slow clients accumulate faster than they drain, the application buffer grows until the server runs out of RAM and crashes. This is THE failure mode of WebSocket services.</p>
    <p><strong>Example: 1 MB message, 10000 clients, 1% slow.</strong> The server wants to broadcast a 1 MB message. For the 99 fast clients, TCP buffers and sends in milliseconds. For the 100 slow clients, the message sits in the application queue. Each slow client might buffer 10–50 of these messages before the server hits its backpressure limit. 100 slow clients × 50 msgs × 1 MB = 5 GB of RAM bloat. The server detects the slow-client count and either (a) evicts slow clients, (b) stops sending to the slowest tier, or (c) crashes. Productions systems monitor per-connection send-buffer size and slow-client count continuously.</p>

    <p><strong>HTTP/2 extended CONNECT and multiplexing.</strong> The Upgrade approach works well for single connections, but opening 10 WebSocket connections means 10 TCP 3-way handshakes (30 ms at 10 ms RTT) plus 10 TLS sessions (another 20 ms if resuming). Over time, you also burn 10 file descriptors instead of 1, and buffer memory per connection multiplies. HTTP/2's framing layer multiplexes streams over a single TCP connection. RFC 8441 defines extended CONNECT for WebSocket: instead of GET + Upgrade, the client sends CONNECT with `:protocol websocket` pseudo-header. The server replies 200 OK (not 101 Switching Protocols). The HTTP/2 stream becomes the WebSocket tunnel, and now 100 WebSocket connections share the same TCP connection, reducing both handshake latency and file descriptor pressure by two orders of magnitude. Throughput across all streams benefits from TCP congestion control tuning on the shared connection. The trade-off is complexity: intermediate proxies and load balancers must understand HTTP/2 and CONNECT_PROTOCOL. As of 2026, major clouds (AWS ALB, Google Cloud Load Balancer) support it, but many corporate proxies and firewalls do not, making it a niche deployment pattern outside hyperscale operators.</p>

  <Fragment slot="senior">
    <p><strong>WebSocket over HTTP/2 (RFC 8441).</strong> HTTP/2 multiplexes multiple streams over one TCP connection using frame-based headers and data. WebSocket over HTTP/2 is defined via extended CONNECT: instead of GET with Upgrade, the client sends a CONNECT request with `:method CONNECT`, `:scheme` (usually https), `:path /chat`, and a new `:protocol websocket` pseudo-header. The server replies with 200 OK (not 101). The HTTP/2 stream becomes the WebSocket tunnel; both sides can send frames over it while other streams on the same TCP connection carry different traffic. Advantage: multiple WebSocket connections share one TCP connection, reducing overhead and improving latency by eliminating 3-way handshake per connection. Requires HTTP/2 support from client, server, and all proxies on the path; HTTP/2 with CONNECT_PROTOCOL enabled is still limited to hyperscale sites (Google, Facebook, Cloudflare) and not yet a default.</p>
    <p><strong>WebSocket over HTTP/3 (RFC 9220, June 2022).</strong> HTTP/3 uses QUIC instead of TCP. WebSocket over QUIC uses the same extended CONNECT with `:protocol websocket`. FIN on the WebSocket close becomes a QUIC FIN; RST becomes H3_REQUEST_CANCELLED. QUIC's streams are independent at the transport layer — a loss on stream 0 does not block stream 4 (no head-of-line blocking). This is theoretically superior to HTTP/2+WebSocket (which still suffers TCP-level HoL blocking). As of early 2026, no major browser or server ships production WebSocket-over-HTTP/3 support; WebTransport (a QUIC-native protocol) is the preferred choice for applications needing QUIC semantics.</p>
    <p><strong>WebSocket vs WebTransport.</strong> WebTransport is an emerging protocol (WHATWG spec, not yet IETF RFC) that runs over HTTP/3/QUIC. It offers bidirectional channels (like WebSocket) plus unreliable datagrams. Each WebTransport connection opens multiple independent streams; loss on one stream does not block others. Handshake is 1 RTT (0 RTT on return). Browser support is ~75% as of 2026 (Safari 17+, Chrome 120+, Firefox 127+). WebSocket remains more widely supported (~95% browsers) and is the default for production systems. WebTransport is gaining adoption in gaming (where unreliable datagrams suit multiplayer state sync) and media (where some packet loss is acceptable). Choose WebSocket for broad compatibility and guaranteed delivery; WebTransport for latency-critical applications where loss tolerance exists.</p>

    <p><strong>Permessage-deflate (RFC 7692).</strong> The <code>permessage-deflate</code> extension compresses each message using DEFLATE (RFC 1951). Negotiated in the Sec-WebSocket-Extensions header during the handshake. Parameters: <code>server_no_context_takeover</code> (reset compression state between messages on server side), <code>client_no_context_takeover</code> (same for client), <code>server_max_window_bits=N</code> (compressor history buffer, default 15 = 32 KB). Compression ratio: 50–90% on text (JSON, HTML, ASCII), poor on small messages (can expand), essentially zero on already-compressed data (images, video). The cost is memory and CPU: at window_bits=15 (default) each compressor consumes ~256 KB and each decompressor ~44 KB. At window_bits=12 the footprint drops to ~50 KB. On a server with 100k idle WebSocket connections at default settings, permessage-deflate adds ~25 GB of memory. Most production deployments disable it by default (no compression on the wire) or set small window_bits for idle connections and inflate it on active streams.</p>
    <p><strong>Backpressure internals and high-water marks.</strong> In a production WebSocket server (e.g., Node.js, Go, Rust), each connection has a send queue. When the application calls <code>connection.send(message)</code>, the message is enqueued. A background writer thread dequeues and writes to the socket. If the socket's kernel buffer is full (from slow client TCP window), the writer blocks. The application's enqueue rate > dequeue rate causes queue growth. To prevent OOM, the server sets a high-water mark (e.g., 100 messages or 10 MB per connection). When a connection's queue exceeds the high-water mark, the server either (a) stops enqueueing and applies backpressure to the application (signals the sender to slow down), or (b) evicts the connection. Production servers monitor total queued bytes and per-connection queue depth continuously. Metrics: p95 and p99 of per-connection queue depth (target < 5 messages for interactive apps), total queued bytes (target < 5% of heap), and slow-client count (target < 0.1%).</p>
    <p><strong>Connection pools and reconnection strategy.</strong> WebSocket has no built-in reconnection. If the network drops, the client sees close code 1006 (abnormal). The application must reconnect. Production systems use exponential backoff: <code>delay = min(base × 2^attempt + jitter, max_delay)</code> with <code>base</code> = 100–500 ms, <code>jitter</code> = ±50% randomization, <code>max_delay</code> = 30–60 s. Example: attempt 0 fails immediately, retry at 100 ms, retry at 200 ms, retry at 400 ms, ..., cap at 60 s. Jitter prevents the thundering herd (all clients reconnecting simultaneously after a server restart). Additionally, production systems add message resumption: each message gets a client-generated ID, the server ACKs it, and on reconnect the client resends unacknowledged messages. This requires server-side durable state (Redis, database) and client-side retry queues.</p>
    <p><strong>Head-of-line blocking on a single TCP connection.</strong> WebSocket multiplexes all application logic onto one TCP connection. If a packet is lost, TCP retransmits it, blocking the entire connection until it arrives (typical retransmit time ~10–30 ms). If your application sends independent data (e.g., multiple game-entity updates), a lost packet for one entity stalls updates for all entities. This is a problem for latency-critical applications. Mitigation: (a) use multiple WebSocket connections (each gets independent TCP stream and retransmit), (b) use WebTransport/QUIC (independent streams avoid HoL), or (c) send critical updates via an unreliable channel (UDP) in parallel. Most production applications use a single WebSocket for reliability and accept the HoL risk for interactive latency (< 100 ms).</p>
    <p><strong>Proxy and load-balancer mishandling of long-lived upgrades.</strong> Proxies like Nginx, HAProxy, and AWS ALB expect HTTP conversations to complete in milliseconds. A long-lived WebSocket is alien. Common misconfigurations: (a) the proxy's L7 buffering waits for the HTTP response to complete before forwarding it to the client, delaying the 101 response by several hundred milliseconds; (b) the proxy has an idle timeout (Nginx default 60s, AWS ALB default 60s) and closes quiet connections without a close frame; (c) the proxy does not understand the HTTP/2 extended CONNECT and falls back to HTTP/1.1 only. Fixes: raise idle timeouts to at least 3600 seconds on the proxy (Nginx <code>proxy_read_timeout 3600s; proxy_send_timeout 3600s;</code>; AWS ALB <code>idle_timeout.timeout_seconds = 3600</code>), explicitly enable buffering bypass (Nginx <code>proxy_buffering off;</code>), enable HTTP/2 end-to-end, and test with real long-lived connections under load. The server must send a ping every 25–30 seconds to reset the proxy's idle timer.</p>
    <p><strong>The thundering herd and jittered exponential backoff.</strong> A production service goes down for 30 seconds. All 10 million connected clients instantly receive close code 1006. If every client retries at the same interval (e.g., 1 second), the server gets 10 million connection attempts in 1 second — CPU and NIC saturation, cascading failures, inability to recover. The fix is jittered exponential backoff: each client picks a random base between 100–500 ms, then adds ±50% jitter, doubling each attempt up to a cap. Client A retries at 145 ms, client B at 287 ms, client C at 423 ms, etc. The 10 million retries spread over 10+ seconds, and the server recovers. Without jitter, even with exponential backoff, the second retry (at the same doubled interval for all clients) still has synchronization; jitter breaks the synchronization. This is a cheap fix with enormous impact. Standard libraries (grpc-go, @tensorflow/tfjs, Phoenix, etc.) ship jittered backoff by default.</p>
    <p><strong>Connection scaling limits (C10K, C10M, and memory).</strong> C10K (ten thousand concurrent connections per server) was a famous bottleneck in the 1990s and is solved by any modern OS. C10M (ten million) is the current frontier. Phoenix framework demonstrated 2 million concurrent WebSocket connections on a single 64 GB server with a single 2 Gbps NIC (one-second broadcast latency). MigratoryData reports 10 million concurrent on commodity hardware. Limits: (a) RAM per idle connection (2–10 KB framework-dependent, can swell to 100 KB with buffering), so 10M connections = 20–100 GB RAM; (b) file descriptors (Linux default 1024, production servers raise to 100k–1M via ulimit), so 10M connections need 10M FDs; (c) NIC bandwidth, which at 2 Gbps and 1KB-per-ping payloads = ~2.6 million pings/second, consuming the NIC at scale. The practical ceiling for a single server is 500k–2M idle connections before RAM or NIC hits the wall.</p>
    <p><strong>Observability and monitoring.</strong> Key metrics for production WebSocket services: (a) active connection count (alert if it grows without bound — connection leak), (b) per-connection send-queue depth (p95/p99; target < 5 messages), (c) total buffered bytes (target < 5% of heap), (d) slow-client count (connections with queue depth > high-water mark; target < 0.1%), (e) message latency p99 (time from server send() to client receive, target < 100 ms), (f) close-code distribution (count of 1000 = normal, 1006 = abnormal, 1013 = try-again-later), (g) reconnection rate (per minute; spike = server restart or network event), (h) CPU per connection (target < 1 ms). Tools: netstat/ss to see socket counts by state, tcpdump for packet-level traces, application-level metrics exported to Prometheus, and custom BPF programs to measure socket buffer sizes and retransmit rates. Without this observability, backpressure failures and cascading close-code 1006 spikes are invisible until the service is already on fire.</p>
    <p><strong>Security: masking, origin checks, and DoS.</strong> Masking defends against cache-poisoning. TLS/wss:// defends against eavesdropping and MITM. The server must check the Origin header and reject connections from unauthorized origins (the browser sends it automatically; a WebSocket client outside the browser must implement it). Rate-limiting at the handshake (connection attempts per IP per second) defends against botnets attempting to exhaust the connection backlog. Slow-reader attacks (a malicious client sends a SYN, completes the WebSocket handshake, then never reads — the server's send queue fills) are mitigated by enforcing per-connection queue limits and timeouts (no data sent in 30 seconds = close the connection). Broadcasting attacks (a client sends a huge message attempting to OOM all other clients' queues) are mitigated by enforcing per-message size limits and per-connection rate limits (X messages per second max). Most production systems have a WAF or DDoS service upstream that rate-limits and drops obvious attacks.</p>
    <p><strong>Production architecture patterns.</strong> Single server: works up to ~10k connections if queuing and backpressure are managed; beyond that, scale horizontally. Multiple servers: clients connect to a load balancer (sticky session so reconnects go to the same server, or full session replication). Pub/sub (Redis, RabbitMQ): a message published to a channel is broadcast to all servers' clients subscribed to it. This decouples the sender from the receiver and allows horizontal scale. State replication: user session, game state, or resume tokens stored in Redis/memcached so any server can handle a reconnect. Shard by room/channel: a chat room lives on one server; if that server goes down, all room clients reconnect and the room re-syncs from persistent storage. The hardest part is not the WebSocket plumbing — it is the application-level state management and consistency under failures.</p>
