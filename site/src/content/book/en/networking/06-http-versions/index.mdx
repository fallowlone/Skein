TLS encrypted the bytes. TCP numbered them. Now comes the protocol on top: HTTP — the language browsers and servers speak to request and receive web pages, APIs, images, fonts, scripts. For thirty years, HTTP/1.1 handled nearly all traffic. Then browsers demanded more: faster page loads despite high latency. HTTP/1.1 could not deliver. Every request had to wait for the previous response. Even with six parallel connections per origin, that wait was the problem. HTTP/2 and HTTP/3 attacked the bottleneck differently, but both converge on one mechanism: <SpiralCue thread="multiplexing" lang="en" /> — putting multiple requests on the same line without blocking each other.

<Crux>Why each HTTP version exists, what each version changed, and why head-of-line blocking is the core antagonist.</Crux>

    <p><strong>What HTTP does in one sentence.</strong> It is the request-response language browsers and servers use to exchange web pages, APIs, images, and every other thing you ever see in a browser.</p>
    <p><strong>Why care about versions.</strong> The protocol has three live versions (1.1, 2, 3). Each tries a different trick to load more files at once over the same connection without blocking. The right version depends on the network: fast wired connections care less; mobile and lossy connections care a lot.</p>
    <p><strong>The metaphor.</strong> Think of HTTP as a waiter taking orders at a restaurant. HTTP/1.1: one waiter per table, one order at a time per waiter — you wait for each plate before ordering the next. To go faster, the restaurant hires six waiters per customer (six parallel connections). HTTP/2: one waiter takes ten orders at once and brings dishes back in whatever order the kitchen finishes them. HTTP/3: same as /2, but a delayed dish in the kitchen no longer makes other dishes wait — they come out independently.</p>
    <p><strong>Read-aloud dialogue.</strong> <PersonaTag id="bea" lang="en" /> the browser to <PersonaTag id="sven" lang="en" /> the server: "GET /index.html." Sven replies with the HTML. Bea sees `<script src="app.js">` inside and says: "GET /app.js." Sven replies with the JS. In HTTP/1.1 Bea waits for each file to finish before asking for the next on the same line. In HTTP/2 and /3 Bea fires all the GETs at once and Sven streams them back interleaved.</p>
    <p><strong>One scenario end to end.</strong> You navigate to a site. Browser does <a href="/en/networking/04-dns-resolution/">DNS</a>, <a href="/en/networking/03-tcp-handshake/">TCP</a>, <a href="/en/networking/05-tls-handshake/">TLS</a>, then sends the first HTTP request. The page's HTML names dozens more files; the browser fires those requests using whatever HTTP version the server agreed to during ALPN. Modern sites get HTTP/2 or HTTP/3; old origins still see HTTP/1.1.</p>

  <Fragment slot="middle">
    <p><strong>HTTP/1.1: pipelining and six connections.</strong> HTTP/1.1 (RFC 9112) sends one request per TCP connection and waits for the complete response before sending the next. To parallelize, browsers open 6–8 connections to the same origin. A browser loading a page with 10 critical JavaScript files opens 6 connections, sends one request on each, then queues the remaining 4. Once a response completes, the connection is freed and can fetch the next file. Pipelining (RFC 7230) allowed clients to send multiple requests without waiting for responses, but it rarely worked in practice: proxies broke it, and if request #1 stalled waiting for the server, request #2 would block behind it anyway — a phenomenon called head-of-line (HOL) blocking on the response side.</p>
    <p><strong>HTTP/2: multiplexing within one TCP connection.</strong> HTTP/2 (RFC 9113) abandons the one-request-per-connection model. Instead, a single TCP connection carries many concurrent "streams" — each stream is an independent request-response pair. Frames are the unit: a HEADERS frame opens a stream and sends request metadata, DATA frames carry body content, and RST_STREAM aborts a stream. The server can interleave responses from different streams: send 100 bytes of stream #1's response, then 100 bytes of stream #3's, then more of stream #1 — all on the same underlying TCP connection. Header compression via HPACK (RFC 7541) reduces the size of HEADERS frames: a second request to the same domain reuses the first request's headers, sending only the delta. This cuts header overhead from ~400 bytes per request to ~20–50 bytes. HTTP/2 also introduced Server Push — the server could send resources the browser did not yet request, betting it would need them. Push was rarely used, it introduced complexity (duplicate requests, wasted bandwidth if the client cached the resource), and browsers removed support: Chrome dropped Server Push in 2022 and other browsers followed; RFC 9113 still defines PUSH_PROMISE but recommends against use in practice — effectively dead but not formally removed from the standard.</p>
    <p><strong>HTTP/3: QUIC and stream-level loss isolation.</strong> HTTP/3 (RFC 9114) switches the transport from TCP to QUIC (RFC 9000) — a protocol built on UDP that includes congestion control, reliability, and connection migration. The big win: QUIC "streams" are independent at the loss-recovery level. In HTTP/2, a single lost TCP packet causes TCP to halt the entire byte stream until retransmission, which blocks all HTTP/2 streams multiplexed on that connection. QUIC has each stream track its own loss and recovery; one stream's packet loss does not stall other streams. HTTP/3 also adopted QPACK (RFC 9204) instead of HPACK — QPACK has the same compression but decouples the dynamic state from stream ordering, so lost HEADERS frames do not block HEADERS frames on other streams.</p>
    <p><strong>Connection cost and warm-up.</strong> Every connection starts cold: TCP handshake (1 RTT), then TLS 1.3 (1 RTT, or 0 RTT if resuming). At 100 ms RTT, a new connection costs 100–200 ms before the first byte. HTTP/1.1's six parallel connections meant six cold handshakes for new origins. HTTP/2 and HTTP/3 reuse one connection, so the cost is paid once. But if the server closes the connection or the browser navigates to a new origin, the cost is paid again. Keep-Alive (HTTP/1.1) and connection pooling (modern browsers) extend connection lifetime. HTTP/3 added connection migration: if the client switches from WiFi to LTE (changing its local IP), the connection persists without re-handshaking — a win for mobile.</p>
    <p><strong>Methods, status codes, and idempotency.</strong> HTTP defines verbs (methods) for what the client wants: GET (read), POST (create or generic non-idempotent), PUT (idempotent replace), DELETE (idempotent remove), PATCH (partial update), HEAD (metadata-only GET), OPTIONS (capabilities), CONNECT (tunnel for proxies). Idempotent methods (GET, HEAD, PUT, DELETE, OPTIONS) MAY be safely retried after timeout because the result is the same regardless of how many times the request runs. Non-idempotent methods (POST, PATCH) MUST NOT be auto-retried without idempotency-key headers or app-level safeguards. Status codes follow RFC 9110: 1xx informational (100 Continue, 101 Switching Protocols, 103 Early Hints), 2xx success (200 OK, 201 Created, 204 No Content, 206 Partial Content), 3xx redirect (301 permanent, 302/307 temporary, 304 Not Modified for caching), 4xx client error (400 Bad Request, 401/403 auth, 404 Not Found, 409 Conflict, 422 Unprocessable, 429 Rate Limited), 5xx server error (500 Internal, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout).</p>
    <p><strong>Headers and conditional requests.</strong> HTTP headers are name/value pairs separated by colon. Common request headers: `User-Agent` (client identification), `Accept` / `Accept-Language` / `Accept-Encoding` (content negotiation), `Authorization` (credentials), `Cookie` (session token), `Range` (partial content), `If-None-Match` (cache validation via ETag), `If-Modified-Since` (cache validation via date). Common response headers: `Content-Type`, `Content-Length`, `Cache-Control`, `ETag`, `Set-Cookie`, `Strict-Transport-Security` (HSTS), `Content-Security-Policy` (CSP). Conditional requests via `If-None-Match`/`ETag` enable 304 Not Modified responses — server replies with empty body if the cached version is still fresh, saving bandwidth. `Cache-Control: max-age=3600` says cache for an hour; `no-cache` forces revalidation; `no-store` forbids storage entirely (common for sensitive data).</p>
    <p><strong>Cookies, sessions, and security flags.</strong> Cookies persist client state across requests. Server sets via `Set-Cookie: name=value; HttpOnly; Secure; SameSite=Strict; Max-Age=3600`. `HttpOnly` blocks JavaScript access (XSS mitigation). `Secure` restricts to HTTPS only. `SameSite=Strict|Lax|None` controls cross-origin behaviour — Strict blocks all cross-site sending, Lax allows safe (GET) cross-site, None requires Secure and allows everything (used for third-party embedded content). Modern browsers default to SameSite=Lax if the directive is missing, breaking many legacy third-party cookie flows. Session tokens stored in cookies need rotation, CSRF protection (matching SameSite + CSRF token), and secure transport (Secure + HSTS).</p>
    <p><strong>CORS — Cross-Origin Resource Sharing.</strong> Browsers enforce the same-origin policy: a script on `a.example.com` cannot read responses from `b.example.com` by default. CORS opts in: server replies with `Access-Control-Allow-Origin: https://a.example.com` to permit. Preflight requests (OPTIONS) check before the real request for non-simple methods/headers. `Access-Control-Allow-Credentials: true` plus a non-wildcard origin lets the cross-origin request carry cookies. Misconfigured CORS (Allow-Origin: *) with credentials is a security hole — the browser refuses to send credentials with a wildcard origin to prevent confused-deputy attacks.</p>
    <p><strong>Streaming, chunked transfer, and SSE.</strong> HTTP/1.1 supports `Transfer-Encoding: chunked` for streaming responses without knowing total length upfront — server sends size-prefixed chunks until a zero-length chunk closes the body. HTTP/2 and /3 use DATA frames natively; chunked encoding is not used at the framing layer (it would be redundant). Server-Sent Events (SSE, `Content-Type: text/event-stream`) is a long-lived response delivering JavaScript-readable events from server to browser one-way; pairs well with HTTP/2 multiplexing. WebSockets (RFC 6455) start as HTTP and Upgrade to a binary frame protocol for bidirectional traffic — incompatible with HTTP/2 multiplexing until RFC 8441 (websockets-over-HTTP/2) and now widely supported.</p>
    <p><strong>Compression.</strong> Servers compress response bodies via `Content-Encoding: gzip|br|zstd`. Brotli (br) compresses ~20% better than gzip on text. Compression on encrypted content has security implications: CRIME and BREACH attacks exploited HTTPS+compression to leak session tokens; the mitigation is to disable compression on responses that include both attacker-controlled and secret content. Static-asset compression is precomputed at deploy time; dynamic content is compressed per-request (CPU cost).</p>
    <p><strong>Content negotiation.</strong> Clients tell the server what they prefer via `Accept` headers. `Accept: application/json, text/html;q=0.9` means JSON preferred, HTML acceptable but lower-quality. `Accept-Encoding: br, gzip` lists supported compressions. `Accept-Language: en-US, en;q=0.8, ru;q=0.6` for locale. The server picks one that satisfies both client preferences and what it can serve. The chosen variant is reported back via `Content-Type`, `Content-Encoding`, `Content-Language`. The `Vary` response header tells caches which request headers affect the response so caches can store separate variants per unique combination. Without `Vary` a cache may serve an English page to a Russian user or a gzipped body to a client that doesn't accept gzip.</p>
    <p><strong>Range requests.</strong> A client can request a byte range of a resource via `Range: bytes=500-999`; the server replies with 206 Partial Content and the requested bytes. Range requests enable HTTP-based video streaming (browsers fetch the file in chunks as the user watches), parallel downloads of large files, and resume-after-disconnect. Browsers and curl use range requests automatically when re-fetching a partially-downloaded resource. Servers must support range requests on static assets to enable these flows; CDN edges typically handle range requests transparently.</p>
    <p><strong>Authentication schemes.</strong> Modern web apps use `Authorization: Bearer <token>` carrying a JWT or opaque session token. Older basic-auth (`Authorization: Basic base64(user:pass)`) survives mostly for internal API tooling. Digest auth is largely retired. OAuth 2.0 / OIDC define how tokens are obtained; the HTTP layer just transports them. WWW-Authenticate response challenges with realm and scheme; the browser shows a credential prompt for Basic, or the app handles Bearer flows entirely in JavaScript. Hidden danger: tokens in URLs leak via Referer headers and browser history — always use the Authorization header for sensitive credentials.</p>
    <p><strong>HTTP/2 flow control and stream limits.</strong> Each HTTP/2 connection has connection-level and stream-level flow control via WINDOW_UPDATE frames — the receiver tells the sender how many bytes it is willing to buffer. Defaults: 65535 bytes per stream, sometimes raised to 16 MiB by modern servers. SETTINGS_MAX_CONCURRENT_STREAMS bounds how many streams a client can open simultaneously (typical 100). Hitting the limit forces the client to queue requests, undoing some of the multiplexing benefit. Server tuning: raise the window size on long-lived streams; raise max-concurrent-streams for chatty APIs. Browser tuning: largely automatic, no knobs exposed.</p>
    <p><strong>HTTP-level rate limiting.</strong> Server returns `429 Too Many Requests` with `Retry-After: <seconds>` to throttle abusive clients. Algorithms: token bucket (refill rate + burst capacity), leaky bucket, fixed window, sliding window. CDNs like Cloudflare and Fastly do this at edge before reaching origin; origin servers do it as defence-in-depth. Client behaviour: respect Retry-After. Production patterns: rate-limit by IP for anonymous traffic, by API key for authenticated, exponential back-off on the client side. Avoid 429 for legitimate burst usage — distinguishing "abuse" from "legitimate burst" is the hard part.</p>
    <p><strong>Trailers and grpc.</strong> HTTP normally puts metadata in headers (before the body) but some metadata is only known after the body — checksums, gRPC status, processing time. HTTP/1.1 supports trailers via `Trailer:` header listing which headers come after the body; rarely used outside chunked transfer. HTTP/2 supports trailers cleanly as a trailing HEADERS frame after DATA frames. gRPC depends on trailers to convey status — every gRPC call ends with `grpc-status` and `grpc-message` trailers carrying the RPC result code separate from HTTP's own status. This is why gRPC-Web exists: browsers cannot read HTTP trailers reliably, so gRPC-Web rewrites trailers as a final framed message in the response body.</p>
    <p><strong>Misconception block.</strong> Three things commonly confused. One: "HTTP/2 fixes head-of-line blocking." False — HTTP/2 multiplexes but TCP still has HOL blocking at packet level; HTTP/3's QUIC streams are what actually fix it. Two: "Server Push speeds up page loads." Historical — Push is dead-on-arrival; Chrome dropped it in 2022, RFC 9113 deprecates it. Use `103 Early Hints` plus `<link rel="preload">` instead. Three: "HTTPS only adds latency." False — HTTP/2 and /3 require TLS, and HTTP/3's 0-RTT resumption is often faster than plaintext HTTP/1.1's cold start.</p>

  <Fragment slot="senior">
    <p><strong>Head-of-line blocking at the TCP layer.</strong> The antagonist of HTTP/2 is not HTTP/2's design but TCP's contract: TCP guarantees delivery in order. A packet containing bytes 1000–1099 of the stream gets lost. TCP retains incoming bytes 1100–1199 in a buffer, waiting for the lost packet. Only after the retransmission arrives are bytes 1100+ delivered to the application. At the HTTP layer, if stream #1 uses bytes 1000–1099 and stream #2 uses bytes 1100–1199, both streams block. This is why high-loss links (cellular, satellite) suffer under HTTP/2: a single lost packet stalls ALL streams. RTT × loss rate is the metric; at 1% loss and 100 ms RTT, you expect one loss event per 100 requests, freezing the entire connection for 100 ms. At 50 RTT/s throughput, that's a ~1% slowdown per loss event. On high-loss links, HTTP/2 is slower than HTTP/1.1 with parallel connections because parallel TCP connections have independent loss recovery.</p>
    <p><strong>QUIC stream independence.</strong> QUIC numbers packets, not bytes. Packet N contains frames from streams A, B, and C. If packet N is lost, QUIC retransmits only the frames from streams whose data was in that packet. If stream A's frame was in packet N, stream A retransmits; streams B and C were not in packet N and keep sending. The cost: QUIC frames add overhead (each frame has a stream ID and offset), and the application must buffer out-of-order frames across multiple QUIC packets. But the win is massive on lossy links: loss is no longer a global event; it's stream-scoped.</p>
    <p><strong>HPACK vs QPACK.</strong> HPACK (RFC 7541) uses a dynamic table indexed by (name, value) pairs. If the first request sends "user-agent: Mozilla", the second request can reference it with a 1-byte index. But the dynamic table is ordered; if index 60 is added to the table, and then a HEADERS frame carrying references to index 60 is lost, subsequent HEADERS frames cannot decode index 60 until the lost frame is retransmitted. QPACK (RFC 9204) separates the dynamic table from the stream encoding: a "blocked" stream waits only for its own HEADERS frame, not for all prior frames. Additionally, QPACK uses a "known static table" of common headers (":method", "content-type", etc.) with fixed indexes, reducing the need for dynamic state on short-lived requests.</p>
    <p><strong>Server Push mechanism and its failure.</strong> HTTP/2 Server Push (RFC 7540 § 8.2) allows the server to send PUSH_PROMISE frames, which declare a stream that the server will send without the client requesting it. For example: GET /index.html prompts the server to PUSH_PROMISE /style.css. The browser can reject the push (RST_STREAM) if it already has /style.css cached. In theory, push saves a request-response round-trip. In practice: (a) the server does not know what the browser cached — it blindly pushes, wasting bandwidth; (b) push only works on the first navigation to a domain — on warm loads, the browser is already caching aggressively; (c) Middleboxes and CDNs do not handle push well, leading to duplicate transfers. By 2022, usage was negligible, Chrome removed it, and the spec (RFC 9113) removed push entirely from HTTP/2. Link prefetch and preload headers are better: they let the browser fetch resources in parallel without the server guessing.</p>
    <p><strong>Congestion control in QUIC.</strong> TCP has congestion control in the kernel (Reno, BBR, CUBIC). QUIC implements it in userspace, per-application. This is both a strength and weakness: the application can tune the algorithm (change from Reno to BBR per-connection), but the cost is CPU. Some implementations use TCP's congestion window; others use custom logic. At large scale (CDNs, cloud providers), per-connection congestion control is more flexible, but it adds monitoring complexity: each connection must emit telemetry (loss, RTT, throughput) so operators can tune the algorithm and detect congestion.</p>
    <p><strong>HTTP version negotiation.</strong> ALPN (RFC 7301, Application Layer Protocol Negotiation) is a TLS extension: during the TLS handshake, the client advertises supported protocols (["h2", "http/1.1"]), and the server picks one. For HTTP/3, QUIC carries its own protocol negotiation (the Initial packet includes a "protocol version" field); the browser tries HTTP/3 first, and if the server does not support it (e.g., QUIC blocked by firewalls), the browser falls back to HTTP/2 or HTTP/1.1. This fallback is silent and implicit, so users do not see it — but operators must monitor: if 30% of requests fall back to HTTP/1.1, that's a signal of firewall rules blocking UDP/QUIC.</p>
    <p><strong>Deployment and adoption.</strong> HTTP/2 is now ubiquitous on the web (&gt;95% of traffic). HTTP/3 is growing: as of 2024, ~30–40% of web traffic uses HTTP/3 (Cloudflare reports), but adoption varies by region and use case. Mobile networks are slower to upgrade; enterprise firewalls often block UDP, forcing fallback to HTTP/2. For greenfield deployments (new APIs, edge compute), HTTP/3 is the default. For legacy users (older browsers, constrained networks), graceful fallback to HTTP/2 is required.</p>
    <p><strong>RFC 9218: extensible priorities.</strong> HTTP/2's original priority scheme (dependency trees with weights) was complex and rarely implemented correctly. Cloudflare reported that browsers and servers disagreed badly enough that priorities sometimes made performance worse than no priorities at all. RFC 9218 deprecates the tree-based scheme in HTTP/2 and defines a simpler signalling: clients send `Priority` header (or PRIORITY_UPDATE frame in /3) with `u=<urgency 0-7>` and `i` (incremental flag). Lower urgency = more important. Browser hints "u=0, i" for HTML, "u=3" for stylesheets, "u=5" for fonts and async scripts. Servers honour these to schedule transmission order across streams. Chrome and Firefox shipped Priority hints in 2023; CDN support (Cloudflare, Fastly) followed.</p>
    <p><strong>MASQUE and QUIC datagram (RFC 9221).</strong> MASQUE is a family of IETF drafts that lets a client tunnel arbitrary connections through an HTTP/3 server. The connection initiates a CONNECT-UDP or CONNECT-IP request which the proxy accepts; the body becomes a tunnel for the encapsulated traffic. Apple's iCloud Private Relay uses MASQUE: traffic goes Apple-server-1 (TLS-tunnelled) → Apple-server-2 (decrypted) → origin, splitting trust between two providers. QUIC datagram frames (RFC 9221) deliver unreliable but encrypted UDP-like payloads inside a QUIC connection — used for real-time media (WebTransport, RTC) where retransmission is worse than loss.</p>
    <p><strong>HTTP/3 fallback mechanics.</strong> A browser cannot just try HTTP/3 first because QUIC packets travel on UDP, which many corporate firewalls drop. Two discovery paths: `Alt-Svc: h3=":443"` header sent on an HTTP/1.1 or /2 response tells the browser "next time, try HTTP/3 here"; HTTPS / SVCB DNS records (RFC 9460) advertise protocol support before connection. On first navigation the browser uses TCP-based HTTP/1.1 or /2, learns about /3 via Alt-Svc, then attempts /3 on subsequent navigations. If /3 fails (UDP blocked, packet loss too high), the browser remembers the failure for some time and continues using /2.</p>
    <p><strong>0-RTT in HTTP/3.</strong> QUIC inherits TLS 1.3's 0-RTT resumption: if the client has a cached session ticket the first QUIC packet carries application data (the HTTP request) alongside the handshake. Saves one full RTT — meaningful on intercontinental links. Same caveat as TLS 1.3 0-RTT: replayable, so servers MUST only honour 0-RTT for idempotent methods. Modern stacks (h2o, nginx-quic) detect non-safe methods in 0-RTT and respond `425 Too Early`, prompting the client to retry after the handshake completes.</p>
    <p><strong>Operational observability for HTTP/3 deployments.</strong> Key signals: ALPN distribution (% h3 vs h2 vs http/1.1), HTTP/3 → HTTP/2 fallback rate (signal of UDP-blocking middleboxes), QUIC packet retransmission rate, connection migration count (cell-Wi-Fi handovers), 0-RTT acceptance rate. Cloudflare's qlog format (per-connection JSON dump of QUIC events) is the deep-debug tool; for production, Prometheus/OTel exporters aggregate. A sudden HTTP/3 → /2 fallback spike usually correlates with a corporate network or carrier route change blocking UDP/443.</p>
    <p><strong>WebSockets, WebTransport, gRPC.</strong> WebSockets (RFC 6455) start as HTTP/1.1 then Upgrade to a binary frame protocol; with HTTP/2 they ride RFC 8441 (extended CONNECT). WebTransport (W3C, RFC 9298-ish) is the modern replacement for WebSockets on HTTP/3, exposing both reliable streams and unreliable datagrams to JavaScript. gRPC layers on HTTP/2 (binary framing, multiplexed RPC calls) and is the dominant intra-datacentre RPC protocol; gRPC-Web translates for browsers that cannot speak raw HTTP/2 trailers.</p>
    <p><strong>HTTP semantic correctness pitfalls.</strong> Misusing 200 OK to carry an error in JSON body bypasses HTTP's machinery — proxies retry, caches store, browsers don't show error UI. Pick the right 4xx/5xx code. Returning 304 Not Modified without matching ETag breaks browsers. `Vary: Authorization` is required on cacheable responses that differ per logged-in user, else CDN caches leak responses across users. `Cache-Control: private` restricts to browser cache, blocks CDN cache. CDN edge configurations must match origin's intent; mismatched directives cause customer-visible bugs.</p>
    <p><strong>HTTP/3 datagram + WebTransport detail.</strong> The DATAGRAM frame in QUIC carries unreliable encrypted payloads — they may be dropped by the network and the protocol does not retransmit. WebTransport exposes both reliable streams and unreliable datagrams to browser JavaScript via the WebTransport API; suitable for game state where retransmission is worse than loss, or VoIP audio where late audio is worse than missing audio. The API mirrors WebSocket's send/receive but lets you pick reliability per channel. Implementations: Chromium ships WebTransport, Firefox 124+ as well, Safari behind flag as of 2026.</p>
    <p><strong>Connection coalescing in HTTP/2 and /3.</strong> Multiple origins with the same IP and certificate (e.g. cdn.example.com and api.example.com on the same edge cert) can share one HTTP/2 or /3 connection — saves handshake cost. Chrome and Firefox do this when the cert's SAN list covers both names. CDN operators rely on this for resource consolidation: a single edge connection serves dozens of customer hostnames. Pitfall: a misconfigured cert that doesn't include a SAN for the second hostname forces a new connection — silent latency regression.</p>

The tradeoff between versions is not just about speed. It's about what breaks under real-world conditions.

<Misconception
  id="r-h2-tcp-block"
  title="Heads-up: HTTP/2 ≠ HOL-free"
>
HTTP/2 multiplexes at the HTTP layer, but sits on TCP — an ordered byte stream. One lost TCP packet stalls all HTTP/2 streams. Only HTTP/3 (with QUIC) escapes HOL blocking at the transport layer.
</Misconception>

Why does this matter? Because real networks are lossy. On satellite links (400 ms RTT, 2–5% loss), HTTP/2 often underperforms HTTP/1.1 with parallel connections. On cellular networks (50–100 ms RTT, 0.5–2% loss), HTTP/2 is usually faster, but loss events can still cause visible pauses. On WiFi and fiber (low loss, &lt;0.1%), all three versions converge on similar speed — but the latency floor is set by RTT and connection setup, not loss. This is why <SpiralCue thread="multiplexing" lang="en" /> — understanding when and why to use each version — is an operator's skill. Greenfield deployments should default to HTTP/3 (QUIC); legacy deployments must support HTTP/1.1 fallback for ancient clients and broken proxies.

Each HTTP version solved a problem of its era. HTTP/1.1 added Keep-Alive to reuse connections. HTTP/2 added multiplexing to eliminate the six-connection workaround. HTTP/3 added transport-level loss isolation to win on lossy networks. As a full-stack engineer, you should know the trade-off: HTTP/1.1 is still alive (older clients, some proxies); HTTP/2 is the default on modern servers; HTTP/3 is the future but has not yet forced out HTTP/2. Knowing when each wins is part of operations expertise.

<KeyTakeaway>
HTTP/1.1 multiplexes by opening six TCP connections; HTTP/2 multiplexes streams over one TCP connection (but TCP head-of-line blocking still bites under loss); HTTP/3 moves to QUIC over UDP and isolates loss to individual streams while adding connection migration for mobile. Above the protocol layer, the headers — Cache-Control, Authorization, CORS, SameSite cookies, ETag, Priority — are where most operational bugs live and most security wins or losses happen. Modern production HTTP means serving all three versions, choosing per-connection via ALPN, and monitoring HTTP/3 fallback rate as a leading indicator of network-path health.
</KeyTakeaway>
