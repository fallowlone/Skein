<Crux>When you type a URL and the page loads, which twelve things happen in order, and where does the 200–400 ms go?</Crux>

Let's walk one HTTPS request from keystroke to first pixel.

## The walk: one request from London to California and back (through proxies and security gates)

**You type. Bea wakes.** <PersonaTag id="bea" lang="en" /> receives the keystroke and assembles a request for `example.com`. She has no IP address yet — only a hostname. She opens a UDP socket and sends a DNS query to her configured resolver.

**Rex looks it up.** <PersonaTag id="rex" lang="en" /> is the recursive resolver — maybe your ISP's DNS, maybe 8.8.8.8, maybe your company's private resolver. Rex checks his cache: "Do I have the IP for example.com?" If warm, he replies in &lt;1 ms. If cold, Rex walks the DNS tree: ask the root nameserver, then the .com nameserver, then example.com's authoritative nameserver. Each hop crosses the network. Typical time: 30–100 ms. The answer comes back with a TTL (time-to-live) — "cache this for 300 seconds."

**Rita routes the TCP SYN.** Now Bea knows the IP. She opens a TCP socket and sends a SYN packet. Rita and her peers are routers — they forward the packet hop-by-hop toward California, using their forwarding tables. Each router inspects the destination IP, consults its routing table, and sends the packet to the next hop. The latency is bound by the speed of light through fiber and radio: 1 round-trip from London to California is ~100 ms over a direct submarine cable. The SYN arrives at Sven's firewall.

**Patty's proxy intercepts (or forwards).** Before Bea's SYN reaches Sven's server, it may hit a reverse proxy or load balancer. Call this Patty (if it's a CDN edge) or her cousin, a regional load balancer. Patty (or the load balancer) decides: "Is this a cached response I can serve locally?" (If yes, it replies 200 OK and closes the TCP stream — Sven never sees the request.) If no, Patty's proxy forwards the request onward or performs connection draining and health checks. If Sven's server is unhealthy (health check failed, process down), Patty routes the connection to a backup server instead. Health checks happen out-of-band (every few seconds, a periodic ping to /health endpoint). If Sven's main server was just receiving the SYN, Patty's health check might reroute the request mid-flight to another server in the pool. For now, assume Sven is healthy; Patty forwards the connection.

**Rate limit and WAF gates.** <PersonaTag id="sven" lang="en" /> (the origin server) receives the SYN, but before he responds, security middleware intercepts. A rate limiter checks: "Has this IP (Bea's) sent more than N requests per second?" If yes, the SYN is silently dropped (or rate limit is enforced at Patty's edge, not at Sven). A Web Application Firewall (WAF) checks: "Does this connection signature match known attack patterns?" Signatures are rule-based (e.g., "SQL injection keywords in query string") or anomaly-based (e.g., "this IP usually sends 2 req/min, now 100 req/sec"). If suspicious, the WAF blocks or challenges. For normal requests, both checks pass instantly. If Bea were a botnet sending 10,000 req/s from the same IP, the rate limiter drops packets silently. The defense: token bucket or leaky bucket algorithm. For every second, tokens accumulate (up to a limit); each request consumes one token. When tokens run out, new requests are dropped. Jitter across clients prevents thundering herd when limits reset.

**Sven accepts the handshake.** Bea's ACK arrives (the third packet of the TCP handshake). Sven responds and the connection is established. Three packets, 1 round-trip (~100 ms), and now both sides trust the TCP connection state. <PersonaTag id="cara" lang="en" /> (the CA — certificate authority) is offline for now; she vouched for Sven's identity when Sven was registered, and her signature sits in his certificate.

**Cara's signature is validated during TLS.** Bea and Sven now perform a TLS 1.3 handshake. Bea sends a ClientHello with a list of cipher suites and a pre-shared key (if it's a warm connection, she can skip round-trips). Sven responds with a ServerHello, his certificate, and a server pre-shared key. Bea validates Sven's certificate by checking Cara's signature — cryptographic proof that Sven is who he claims. If the signature is invalid, the connection aborts. If valid, Bea and Sven derive shared encryption keys and can now send encrypted data. Time: 1 RTT (~100 ms) for a new connection, 0 RTT if Bea has resumption state.

**mTLS: Sven validates Bea (optional, for sensitive paths).** Ordinarily, only Bea validates Sven. But for sensitive operations (internal APIs, microservices between Sven's backend services, financial transactions), Sven also verifies Bea's certificate. This is mutual TLS (mTLS). Sven sends a CertificateRequest message during TLS handshake, requesting Bea's certificate. Bea sends hers. Sven checks the certificate signature against a list of trusted CAs (often an internal CA specific to Sven's company, SPIFFE cluster, or organization). If Bea's certificate is not recognized, Sven closes the connection. mTLS adds one extra round-trip for request/response (CertificateRequest), but is essential for service-to-service authentication in zero-trust networks. The cost: every Bea must have a valid certificate issued by Sven's trusted CA. Certificate expiry, rotation, and distribution are operational burdens.

**HTTP/3 streams multiplex independently.** Bea constructs an HTTP request: GET /index.html, with headers, accept-language, cookies, and a user-agent. On HTTP/3 (using QUIC), she opens a stream on the same UDP connection and sends the request. QUIC merges the transport layer (UDP packet demultiplexing) and encryption (TLS) into one handshake, saving 1 RTT for new connections compared to TCP+TLS. Sven's kernel handles QUIC framing and passes the request to the application layer. Sven constructs a response: status 200, content-type: text/html, cache-control headers, and the HTML body. He sends it in QUIC frames, each frame tagged with the stream ID so Bea's kernel can reassemble it. Other requests (images, scripts, styles) are opened as separate streams and sent in parallel. If one stream's packet is lost, others keep flowing (stream independence, a QUIC win over HTTP/2+TCP where a single packet loss stalls all streams). Time for request/response: ~1 RTT (~100 ms), assuming the response fits in the initial congestion window.

**QUIC connection migration (mobile networks).** If Bea's device switches from WiFi to cellular, her IP address changes. In TCP+HTTP/2, an IP change breaks the connection — Bea must re-establish and lose all in-flight streams. In QUIC, the connection persists via a Destination Connection ID (a stateless token Sven issued at handshake). Bea's kernel sends a PATH_CHALLENGE frame to Sven with the new IP. Sven responds with PATH_RESPONSE using the same token, proving the IP change is legitimate (not an attack). The connection continues with no loss of streams, no TLS re-negotiation. Cost: one extra round-trip (PATH_CHALLENGE/RESPONSE), but cheaper than re-establishing the entire connection. Migration happens silently; Bea's application (browser or HTTP client) does not need to know.

**Patty serves from the edge (or Sven services from the origin).** If the request hits a CDN, <PersonaTag id="patty" lang="en" /> (the edge proxy) intercepts the request. Her DNS is configured to return a regional IP, so Bea connected to the London POP instead of California. Patty checks her cache: "Do I have index.html with the correct Vary headers?" If yes (cache hit), she responds immediately (~10 ms round-trip). Patty's edges near clients have much lower latency than the origin. If no (cache miss), Patty may first check an origin shield (a regional cache shared by many edge nodes) to avoid thundering-herd requests to Sven. If the shield also misses, Patty forwards the request to Sven's origin. If Sven responds with a 503 Service Unavailable (overloaded, or under DDoS), Patty's circuit breaker stops forwarding new requests to him and instead serves stale content from her cache (if Cache-Control: stale-while-revalidate is set). Sven responds. Patty stores the response in her cache and sends it to Bea. The response trickles back through Rita's routers (same route, reverse direction) and arrives at Bea's kernel, which passes it to the browser.

**Rita's routers queue and prioritize.** As packets traverse Rita and her peers, they encounter congestion windows, retransmit timers, and DSCP prioritization. If the link is saturated, routers queue packets. If a packet is lost (due to bit-flip or congestion), the sender retransmits. Most links are not saturated; most packets arrive on the first try. But every additional hop, every retransmit, and every retry compounds latency.

**Bea parses and renders.** The browser receives the HTML bytes, parses the DOM, fetches critical resources (CSS, fonts, JavaScript), parses the stylesheets, constructs the render tree, performs layout, and paints pixels. The first contentful paint (FCP) happens when Bea has HTML + CSS ready. The largest contentful paint (LCP) happens when the largest visible element is painted. Modern browsers parallelize all of this: as HTML streams in, parsing begins; as CSS arrives, reflow happens incrementally. The entire dance — from keystroke to LCP — on a typical page takes 2–4 seconds. The networking portion is only ~200–300 ms (1 RTT DNS + 1 RTT TCP + 1 RTT TLS + 1 RTT HTTP + 1 RTT response arrival + rendering overhead). The rest is JavaScript, network roundtrips for subresources, and the browser's rendering pipeline.

  <Fragment slot="middle">
    <p><strong>Seven phases in sequence, with typical timings.</strong></p>
    <p><strong>Phase 1: DNS Resolution (~30 ms cold, &lt;1 ms warm).</strong> Bea asks Rex, "What is the IP for example.com?" If Rex has the answer cached (TTL &gt; 0), he replies in microseconds. If not, Rex walks the DNS hierarchy: root nameserver → TLD nameserver → authoritative nameserver. Each hop is a network round-trip. A cold DNS lookup in North America or Europe takes 30–100 ms. Most users' resolvers have warm caches, so DNS is amortized: first visitor pays ~30 ms, subsequent visitors pay &lt;1 ms.</p>
    <p><strong>Phase 2: TCP Handshake (1 RTT, ~10–25 ms regional, ~56–100 ms intercontinental).</strong> Bea sends SYN to Sven. Sven responds SYN-ACK. Bea sends ACK. Three packets, one round-trip. A connection within a region (London to Frankfurt) is ~10–25 ms. A connection intercontinentally (London to California) is ~56–100 ms each way (speed of light through fiber; per HPBN, London–New York is ~56 ms). After the handshake, TCP's initial congestion window is usually 10 packets (IW=10, RFC 6928). Bea can send up to 10 packets without waiting for an ACK.</p>
    <p><strong>Phase 3: TLS 1.3 Handshake (1 RTT new, 0 RTT resumption, ~25 ms).</strong> Bea sends ClientHello with a pre-shared key and supported cipher suites. Sven responds with ServerHello, certificate, and server key. Bea validates the certificate using Cara's signature. Both derive keys. Encrypted data can now be sent. If Bea has seen Sven before (session ticket from last time), she can send early data (0-RTT) — the request is encrypted with the old key and sent immediately, without waiting for Sven's response. Risk: 0-RTT data is not forward-secret (it can be decrypted if the old session key leaks), so it is safe only for idempotent operations (GET, not POST/PUT).</p>
    <p><strong>Phase 4: HTTP Request (~1 RTT, ~25 ms).</strong> Bea sends the HTTP request: method, path, headers, cookies. On HTTP/3, this is a QUIC HEADERS frame. On HTTP/2, this is an HTTP/2 HEADERS frame on a stream. Sven's application layer receives the request and processes it: check authentication, query the database, construct a response. Processing time is app-dependent; assume 10 ms for a cache hit.</p>
    <p><strong>Phase 5: HTTP Response (RTT + processing, ~50 ms).</strong> Sven sends the response: status, headers, body. On HTTP/3, QUIC streams are independent, so if multiple requests are in flight, Sven can interleave responses. Bea's kernel receives frames, reassembles them into the response, and passes it to the browser.</p>
    <p><strong>Phase 6: Subresource Fetches (parallelized, RTT × depth).</strong> The HTML includes references to CSS, JS, images. Bea's browser parses the HTML, discovers the subresource URLs, and fetches them. Critical resources (CSS, fonts) are fetched first. On HTTP/3, Bea can send requests for 10+ subresources in parallel; all are multiplexed on the same connection. Time to fetch N resources: ~1 RTT if N &lt; IW, ~2 RTT if IW &lt; N &lt; 2×IW, etc. (Assuming fast serialization and no processing delay.)</p>
    <p><strong>Phase 7: Rendering (parallelized, 0–100+ ms).</strong> As CSS arrives, Bea's browser parses it and constructs the CSSOM. As HTML arrives, she parses the DOM. Browser merges DOM + CSSOM → render tree → layout → paint. If JavaScript blocks the main thread, painting stalls. Modern sites defer JavaScript; rendering is concurrent with network fetches.</p>
    <p><strong>The full picture.</strong> Assuming warm DNS, regional geography (~25 ms RTT), HTTP/3 with 0-RTT resumption, and a CDN cache hit: DNS (&lt;1 ms) + TLS (0 ms, 0-RTT) + HTTP request (0 ms, piggybacked on 0-RTT data) + edge processing + response (~10 ms) + subresources (1 RTT, ~25 ms) + rendering (100 ms) = ~150 ms to LCP. The limiting factor is the browser's rendering pipeline, not the network.</p>
    <p><strong>Critical render path.</strong> The browser's render pipeline depends on HTML, CSS, and (for interactivity) JavaScript. HTML is parsed as bytes stream in — DOM construction starts before the full body has arrived. CSS blocks rendering: nothing paints until at least one stylesheet has loaded for the current viewport. JavaScript blocks parsing unless marked `async` or `defer`; placing scripts at the bottom of `<body>` or with `defer` lets HTML and CSS parse in parallel. The browser's preload scanner runs a tokenizer ahead of the main parser to discover sub-resource URLs and fire requests early. Critical-path resources should be inlined or marked `<link rel="preload">` for browsers to fetch in parallel with HTML parsing.</p>
    <p><strong>Core Web Vitals interpretation.</strong> Google's Web Vitals quantify user-perceived performance. LCP (Largest Contentful Paint) is when the biggest visible element finishes rendering — typically the hero image or main heading. Good: under 2.5 s; poor: over 4 s. INP (Interaction to Next Paint, replaced FID in March 2024) measures responsiveness across an entire session — the longest delay between user input and visual response. Good: under 200 ms. CLS (Cumulative Layout Shift) measures unexpected layout movement during page load — images without dimensions, ads inserting content, fonts shifting text. Good: under 0.1. Search ranking depends on these; Google uses field RUM data, not synthetic tests, so optimising for synthetic alone misses the point.</p>
    <p><strong>Connection reuse across requests.</strong> Each new origin requires a fresh DNS + TCP + TLS handshake. Cross-origin requests (a CDN-hosted page loading fonts from Google Fonts, scripts from a third-party tracker, images from a different CDN) pay that price per origin. `<link rel="preconnect">` and `<link rel="dns-prefetch">` warn the browser to open connections to anticipated origins before the main parser reaches them; saves the handshake from the critical path. Connection coalescing (browsers reuse one HTTP/2 or /3 connection for multiple origins served by the same edge and certificate) helps with major CDNs.</p>
    <p><strong>Resource hints.</strong> `<link rel="preload" as="font" crossorigin>` for fonts (load early to avoid FOIT/FOUT). `<link rel="preload" as="script">` for critical JS bundles. `<link rel="modulepreload">` for ES modules including their dependencies. `<link rel="prefetch">` for likely-next-navigation resources (low-priority). `<link rel="preconnect">` for origins you will need within milliseconds. Modern frameworks (Next.js, Astro, SvelteKit) emit these hints automatically based on usage.</p>
    <p><strong>HTTP/3 0-RTT specifics for this flow.</strong> If the browser has a cached session ticket and the server allows 0-RTT, the initial HTTP request travels inside the QUIC initial packet — handshake and request fly together. Saves 1 RTT but only for idempotent methods (GET, HEAD, OPTIONS). Modern stacks reject 0-RTT for state-changing methods, retrying after handshake. Effective gain: 10-30% faster first-byte on warm connections.</p>
    <p><strong>Compression cascade.</strong> Text responses (HTML, CSS, JS, JSON) compress 70-90% with gzip or 20% better with Brotli. Static assets are pre-compressed at deploy time; dynamic responses compressed at runtime. CDN edges typically handle compression transparently with edge-side caching of compressed variants. The browser advertises support via `Accept-Encoding: br, gzip`; servers select the best mutually-supported algorithm.</p>
    <p><strong>Caching effects across the full request.</strong> A warm request hits: (1) browser memory cache (sub-millisecond), (2) browser disk cache (~10 ms), (3) CDN edge cache (~20-50 ms over network), (4) CDN shield cache (~50-100 ms), (5) origin (~100-300 ms). Each layer reduces traffic to the next. A well-architected site with content-hash-versioned assets caches almost everything at level 1-3 for repeat visitors.</p>
    <p><strong>Misconception block.</strong> Three things commonly misunderstood at this synthesis tier. One: "Faster network always means faster page." False — for cache hits, rendering dominates; for cache misses, server compute often dominates. Two: "Reducing bundle size always helps." Helps loading, but if rendering is JavaScript-bound, parsing time is the bottleneck — splitting bundles can help main-thread responsiveness even if total bytes are similar. Three: "0-RTT saves time for every request." Saves time only for warm connections (resumption ticket available); cold connections pay full handshake.</p>
    <p><strong>Browser preconnection and warm-up tricks.</strong> Modern pages can warm the network stack before the user clicks. `<link rel="dns-prefetch" href="//cdn.example.com">` resolves the hostname in the background. `<link rel="preconnect" href="//cdn.example.com" crossorigin>` does DNS + TCP + TLS preemptively, so the first real request finds the connection already open. The cost: each preconnected origin holds an idle TCP socket; doing this for ten origins fragments your network resources. The right pattern: preconnect to your two or three most-critical origins (CDN, fonts, API), let everything else warm on demand. Service Workers extend this further — they can pre-fetch entire resource bundles on a previous navigation so the next page load is essentially offline.</p>
    <p><strong>Concurrent fetching budgets.</strong> Browsers enforce per-origin connection limits (6 for HTTP/1.1, hundreds of streams over a single HTTP/2 or /3 connection). They also enforce per-page bandwidth fair-share so one origin cannot starve others. The browser's resource scheduler ranks requests by `Priority` hint (RFC 9218) and a built-in cost model — render-blocking CSS first, fonts second, async scripts later, images deferred until visible. As a developer you can influence the order via `fetchpriority="high|low"` attribute on individual elements; e.g. mark the hero image `fetchpriority="high"` and async scripts `fetchpriority="low"` so the critical render path finishes first.</p>
    <p><strong>Service Workers and offline.</strong> A Service Worker is a JavaScript file the browser registers as an intercepting proxy for all requests from your origin. It can serve cached responses without hitting the network, queue requests when offline, transform responses, push notifications. It also runs background sync — uploading queued user actions when the network returns. The cost: complexity (your "page" now has two execution contexts that must stay in sync), debugging difficulty, and a registration footprint. Right pattern: Service Workers for offline-first PWAs (mail clients, document editors); avoid for simple content sites where the value-to-complexity ratio is poor.</p>
    <p><strong>Caching layers in modern stacks.</strong> Beyond browser cache and CDN edge, modern apps cache in many places: in-memory (LRU cache in the application process), Redis or Memcached (shared per-region cache for app-server pool), database query plan cache, CDN regional shield, browser disk cache, browser memory cache. Each layer has its own invalidation rules; designs that span all layers must propagate invalidation events explicitly. The opposite mistake — relying on TTL expiry across multiple layers — leads to stale data living in cracks for far longer than any single layer's TTL.</p>
    <p><strong>The path of an interactive API call.</strong> User clicks a button. Browser issues a fetch() — already-open HTTP/2 or /3 connection avoids handshake. Request rides to CDN edge (no cache, mutating endpoint). Edge forwards to origin region. Origin auth-checks, queries DB, computes response, returns. Edge does not cache (Cache-Control: no-store). Browser receives response. JavaScript handler updates state, triggers re-render. Total time: typical 100–200 ms on a good day. If any layer is slow (DB query, third-party API in the response computation, slow JS handler), the user perceives lag. Optimisation per layer is the operations engineer's daily work.</p>

  <Fragment slot="senior">
    <p><strong>Cross-layer state and optimizations.</strong> The network is not just a sequence of phases; it's a state machine. After TLS handshake, Sven's kernel maintains a connection state (established, closing, closed). Bea's kernel maintains per-stream state on HTTP/3 (sent, receive-waiting, local-close, etc.). Both sides maintain congestion windows (how much data can be in flight without acknowledgment). Bea maintains DNS cache entries with TTL; when TTL expires, the entry is evicted. Patty (the CDN) maintains per-URL cache entries with Vary headers and expiration times. TLS session tickets are state — Bea caches them, Sven can validate them without a full handshake. This state is the reason for the optimization: TLS resumption (reuse last session's keys, skip 1 RTT), DNS caching (skip resolver walk), HTTP/3 0-RTT (send before server's hello), and connection pooling (reuse TCP+TLS across requests).</p>
    <p><strong>Latency optimizations and their tradeoffs.</strong> Each phase can be optimized, but optimizations trade consistency, complexity, or security for speed. DNS: use Anycast resolvers or GeoDNS to move DNS closer, but risk misrouting. TCP: use BBR congestion control to avoid timeouts, but require kernel patches. TLS: use session tickets for 0-RTT, but accept replay attack risk (mitigated by idempotency). HTTP: use server push to preload subresources, but waste bandwidth if the client already cached them (push was removed from HTTP/2 spec). CDN: use stale-while-revalidate to serve expired cache, but risk stale data. The pattern: profile first, identify the slowest phase, optimize that phase, and accept the tradeoff.</p>
    <p><strong>Cascading retries and their cost.</strong> When the network is slow, clients retry. A TCP connection times out → client opens a new connection (TCP handshake, TLS, HTTP request × 3). A TLS handshake takes too long → browser retry with a shorter timeout. An HTTP request times out → client library retry (exponential backoff, e.g., 100ms, 200ms, 400ms). When many clients retry, the load on the origin amplifies. A 99.9% origin server (1 error per 1000 requests) suddenly handles 10× normal traffic (from 10 concurrent clients all retrying). The server slows, causing timeouts upstream, causing more retries, causing more load. This is a cascade: 1 error → many retries → many errors. Defence: implement exponential backoff with jitter at every retry layer (DNS, TCP, TLS, HTTP, app), so retries are staggered, not synchronized.</p>
    <p><strong>Encrypted Client Hello and privacy implications.</strong> Traditional TLS exposes the Server Name Indication (SNI) header in plaintext, allowing on-path observers to fingerprint the request: "This client is fetching google.com" without decrypting. Encrypted Client Hello (ECH, draft-ietf-tls-ech) encrypts the SNI, protecting against category-level fingerprinting. But ECH requires a DNS lookup (to fetch the server's ECH config), adding latency. Adoption is slow; most servers do not yet support it. The tradeoff: privacy vs. latency.</p>
    <p><strong>Connection migration and mobile networks.</strong> HTTP/3 (QUIC) supports connection migration: if a client's IP changes (switched from WiFi to LTE), the connection persists using a stateless reset token. TCP has no migration; an IP change breaks the connection. On mobile, IP changes are frequent. HTTP/3 reduces handshake cost per migration (no TLS, just a QUIC frame). But the statefulness itself is a burden: Sven must track client state (sent packets, acks, congestion window) and continue it after migration. If Sven restarts or the connection is routed to a different server (load-balanced), the state is lost. The tradeoff: stateless simplicity vs. stateful optimization.</p>
    <p><strong>Why you care about the layers.</strong> The entire seven-phase dance is sub-100 ms on a good day. The payoff is clarity: the next time a page is slow, you can profile and name the suspect — was it DNS (slow resolver), TCP (far geography or congestion), TLS (heavy handshake or untrusted cert), HTTP (slow application server), cache (miss rate too high), rendering (JavaScript blocking), or network loss (retransmits stalling streams)? Without understanding the layers, "the network is slow" is all you have. With the layers, you say "DNS + CDN edge miss cost 50ms, TLS resumption would save 25ms, and server-side caching would eliminate the origin round-trip entirely." And you ship the fix that gives the best ROI.</p>
    <p><strong>OpenTelemetry trace propagation.</strong> Modern observability instruments every layer with W3C Trace Context: a 16-byte trace ID and 8-byte span ID propagate via the `traceparent` HTTP header. Every component in the request path (browser → CDN edge → load balancer → application → database) reports spans that aggregate into a distributed trace. You can see the request's exact path, time spent per hop, and which dependency caused the long tail. CDN edges (Cloudflare Workers, Fastly Compute) emit trace headers; backends propagate them; observability backends (Tempo, Honeycomb, Datadog) display the full trace. Without trace propagation, debugging "where did 500 ms go" devolves into log archaeology across multiple systems.</p>
    <p><strong>USE method, RED method, error budget calculus.</strong> Three operational frameworks. USE (Brendan Gregg) for resources: Utilization, Saturation, Errors — applied to CPU, memory, disk, network interfaces. RED (Tom Wilkie) for services: Rate (requests/s), Errors (error rate), Duration (latency distribution). Both methods discipline you to instrument what matters and ignore what doesn't. Error budgets: an SLO of 99.9% allows 0.1% errors per 30-day window — about 43 minutes of downtime. When you've burned half the budget you slow risky changes; when you've burned all of it you freeze releases until reliability improves. This formalises the latency/feature-velocity trade-off.</p>
    <p><strong>Distributed tracing sampling strategies.</strong> Tracing every request is too expensive at scale (1 M req/s would produce terabytes of trace data per day). Sampling strategies: head-based (decide at request entry whether to trace, fixed percentage e.g. 1%), tail-based (buffer all spans, decide after seeing outcome — sample 100% of errors, 0.1% of successes), adaptive (sample more from high-cardinality endpoints). Tools like OpenTelemetry Collector implement tail sampling. The right strategy: 100% sampling for errors and slow requests, low rate for fast successes.</p>
    <p><strong>Retry policies and circuit breakers.</strong> Naive retry: client sees error, retries immediately, server still broken, sees same error, retries again — death spiral. Exponential backoff with jitter (initial 100 ms, doubled each retry, random ±25% jitter to avoid synchronisation) lets the server recover. Circuit breakers (Netflix Hystrix, Spring Cloud Resilience4j, Polly) close the circuit when failures exceed threshold — stop calling the failing dependency entirely for a cool-down window, return fast errors to callers, periodically test recovery. Combined: client-side retry + server-side health checks + circuit breakers + load shedding = resilient distributed system.</p>
    <p><strong>Production observability stack.</strong> Metrics: Prometheus or VictoriaMetrics, scraped from every service via `/metrics`. Logs: Loki or Elasticsearch, structured (JSON) for queryability. Traces: Tempo, Jaeger, or commercial (Datadog, New Relic). Dashboards: Grafana. Alerting: PagerDuty + Alertmanager. RUM: in-house beacons or Sentry/LogRocket for browser perf. All five layers correlate via trace IDs and timestamps. A well-instrumented service ships with default dashboards from day one; the org-level observability standard is part of the platform's developer experience.</p>
    <p><strong>Edge compute composition patterns.</strong> Cloudflare Workers + KV + R2 + Durable Objects let you build full applications without an origin server. Patterns: API gateway at edge (auth, rate limit, routing to multiple backends), static site with personalisation (edge worker injects user-specific fragments), event broker (Durable Objects coordinate state). The trade-off: lock-in plus per-CDN compute idioms. The benefit: latency under 50 ms globally without managing servers.</p>
    <p><strong>Failure isolation across regions.</strong> One US-East-1 outage should not take down your European users. Patterns: regional deployments with independent failure domains, traffic routing via Route 53 / Cloudflare Load Balancing health checks, cross-region replication for stateful services, blast-radius scoping so a bad deploy goes to one region first. Cell-based architecture (AWS internal pattern) divides users into "cells" each served by a dedicated infrastructure slice — one cell's failure affects only that cell's users.</p>
    <p><strong>Performance budgets.</strong> Set explicit budgets: total bytes (e.g. 200 KB compressed for HTML), JS execution time (e.g. 100 ms), LCP (under 2.5 s), CLS (under 0.1). Enforce in CI: a build that exceeds budget fails the check. Tools like bundlewatch, size-limit, Lighthouse CI integrate with GitHub Actions. The budget forces conscious trade-offs at PR time instead of discovering bloat in production.</p>
    <p><strong>The full mental model for synthesis.</strong> Every layer in this chapter is one box in the request lifecycle. The browser orchestrates. DNS is one network operation. TCP is another. TLS adds encryption and one more handshake. HTTP is the actual app-level conversation. CDN edges shorten the geography. Routers carry the bits. The CSS+JS+HTML mix decides what paints when. Observability lets you see all of it. Optimisation = profile the slowest box and shrink it; round-trip elimination beats round-trip shortening; cache hits beat cache misses; the right metric beats the precise metric. You now have the full vocabulary to debug, design, and ship performant network-bound systems.</p>
    <p><strong>Capacity planning at scale.</strong> Once your system handles meaningful traffic, capacity numbers start mattering: requests per second per worker, p99 latency under load, memory per concurrent connection, CPU per request. Load tests (k6, Locust, vegeta) measure these. Stress tests push past the cliff to find the breaking point. Chaos engineering (Gremlin, Litmus) injects failures to verify the system degrades gracefully. The discipline: never deploy a new high-traffic service without knowing its capacity envelope. Run-books document failover, recovery, and rollback procedures. On-call rotations distribute the work of responding to incidents — no individual carries the pager forever.</p>

## Heads-up: cascading retries amplify outages across all 12 layers

<Misconception
  id="r-cascade"
  title="Heads-up: cascading retries amplify outages across all 12 layers"
>
<strong>Retry storms amplify outages.</strong> Origin timeout causes retries at every layer. A 99.9% server sees 10× normal load in 30s from cascading retries. <strong>Defense:</strong> exponential backoff + jitter, circuit breakers, load shedding, bulkheads.
</Misconception>

<KeyTakeaway>
Every HTTPS request is a coordinated sequence of twelve layers: DNS to find the IP, TCP for reliable byte transport, load balancers and proxies for health checks and routing, TLS for confidentiality and integrity (plus optional mTLS for service-to-service), rate limiters and WAFs for security, HTTP for application-level conversation, QUIC for low-latency alternatives and connection migration, WebSocket upgrades for real-time bidirectional flows, CDN edges for geographic proximity and cache, routers for packet forwarding, and the browser's render pipeline. Optimisation work means knowing which layer dominates each specific slow request — round-trip elimination (cache hits, 0-RTT, connection migration) is the highest-leverage move; round-trip shortening (CDN, multi-region, edge compute) is next; everything within a round-trip (compression, parsing speed, smaller bundles) is third. Security hardening (mTLS for service mesh, WAF for edge, rate limiting for DDoS) must not be retrofitted; design it in from layer 1. The operational frontier is distributed tracing with W3C Trace Context, USE/RED method-based instrumentation, circuit breakers for cascade isolation, and error-budget-driven release cadence — all of which give you the vocabulary to debug, design, and ship performant, resilient network-bound systems.
</KeyTakeaway>

## Key takeaways: what recurs next

Chapter 01 is done. You have walked the full network from Bea's keystroke to pixels on screen. Four threads wove through every layer:

- **Encapsulation.** Each layer wraps the previous one — IP inside Ethernet, TCP inside IP, TLS inside TCP, HTTP inside TLS, content inside HTTP. This abstraction lets each layer specialize.
- **Multiplexing.** TCP/IP multiplex many streams onto one pipe. HTTP/2 and HTTP/3 multiplex many requests onto one connection. Routers multiplex many flows onto one link. The pattern recurs: compress independent work onto shared resources.
- **Statefulness.** Connections are stateful — they remember sequence numbers, congestion windows, TLS keys, and HTTP session cookies. This state is what allows optimizations like resumption and 0-RTT. But it also means lost state = broken connection.
- **Latency.** Every round-trip, every handshake, every cache miss is a cost. The entire architecture is an optimization against round-trip latency. Why? Because the speed of light is the speed limit, and the distance between user and server is fixed. The only lever is the number of round-trips.

You'll see these threads again in **Chapter 02: Browser & Frontend Runtime** (how Bea renders and executes JavaScript), **Chapter 03: APIs & Services** (how multiple backends encapsulate and multiplex), **Chapter 04: Databases** (how transactions are stateful and why consistency is costly), and **Chapter 05: Deployment & Observability** (how to profile and optimize latency in production).
