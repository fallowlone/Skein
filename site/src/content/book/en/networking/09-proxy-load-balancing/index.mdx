A user connects to what they think is a direct server, but it is not. In between, an intermediary — a proxy — intercepts the request, decides where to send it, balances the load across that choice, and shields the real server from seeing who asked. The proxy reads the TCP packet, inspects the payload, and makes routing decisions that a dumb packet-forwarder cannot. That is how the modern internet hides scale.

<Crux>How reverse proxies route requests, choose backends, detect failures, and recover from overload.</Crux>

A client connects to what feels like a single origin server. But behind that address lives a load balancer (LB) — a reverse proxy sitting between clients and a pool of real backends. The LB's job is threefold: route each request to a healthy backend, balance load so no single backend drowns, and preserve the connection state (session affinity) if the application requires it. This piece explores the mechanisms that make this invisible to the client and the failure modes that expose it when something breaks.

  <Fragment slot="junior">
    <p><strong>What a reverse proxy does.</strong> A reverse proxy sits between clients and origin servers. Clients connect to the proxy thinking it is the real server; the proxy receives the request, picks a backend to handle it, forwards the request, waits for the response, and sends it back to the client. The client never sees the real backends.</p>
    <p><strong>Why care.</strong> Without a reverse proxy every backend would handle client connections directly, limiting scale and making it impossible to upgrade backends without breaking active connections. A reverse proxy decouples clients from backends so backends can be added, removed, or restarted without downtime.</p>
    <p><strong>The metaphor.</strong> Imagine a restaurant with one host who seats customers (the load balancer) and multiple chefs in the kitchen (the backends). When a customer arrives the host decides which chef is least busy, hands the order to that chef, waits for the dish, and brings it back to the customer. If a chef calls in sick the host stops sending orders to that station and reroutes them. Customers never talk directly to the chefs; they always talk to the host.</p>
    <p><strong>Persona dialog.</strong> <PersonaTag id="bea" lang="en" /> connects to her bank's website and makes a request to transfer money. <PersonaTag id="sven" lang="en" /> (the load balancer) receives it. Sven looks at his list of backend servers and sees one is handling fewer requests than the others, so he forwards Bea's request to that backend. The backend processes it, sends the response back through Sven, and Bea sees the confirmation. Sven never tells Bea which backend handled her request.</p>
    <p><strong>One scenario linking prior pieces.</strong> You click a link and your browser initiates a <a href="/en/networking/03-tcp-handshake/">TCP handshake</a>. But instead of connecting directly to the server, you are actually connecting to a load balancer. The LB completes the handshake with you, then opens a separate connection to a backend server and tunnels your traffic through. If that backend gets overloaded the LB can mark it as unhealthy, stop sending it traffic, and route future requests to healthier backends instead — a level of resilience the TCP layer alone cannot provide. This is why CDNs (see <a href="/en/networking/07-cdn-edge/">CDN edges</a>) use load balancers: they need to balance millions of simultaneous client requests across dozens of servers while hiding the complexity.</p>

  <Fragment slot="middle">
    <p><strong>Forward proxy vs reverse proxy.</strong> A forward proxy (like a corporate proxy) sits between the client and the outside world. The client knows about it and connects to it intentionally. A reverse proxy sits between the client and the origin servers. The client is unaware of it — it appears as the direct server. Forward proxies are used for outbound client control (filtering, caching, privacy); reverse proxies are used for inbound server load balancing, caching, and protection.</p>

    <p><strong>Layer 4 (transport) vs Layer 7 (application) load balancing.</strong> L4 load balancers route on IP:port only, with no inspection of the payload. They see a TCP stream from client to LB and another from LB to backend; they forward packets between the two without parsing HTTP. This is fast (~1–5 µs per packet, &lt;1% CPU) and can handle any protocol (TCP, UDP, MQTT, PostgreSQL). However, L4 LBs cannot inspect the request to make intelligent routing decisions — they cannot route by HTTP path, hostname, or header, and they cannot retry failed requests because they do not understand HTTP. L7 (application) load balancers parse the HTTP request, route by path/host/header, terminate the TLS session (seeing plaintext), and can retry on 5xx errors. But L7 costs more CPU (~100–500 µs per request, 5–15% CPU) and throughput is lower (1–10 Gbps/server vs 10–40 Gbps for L4). Choose L4 for high-throughput, protocol-agnostic traffic; choose L7 for content routing and advanced policies.</p>

    <Misconception id="lb-tradeoff">
      "L7 is always better." Not true. L4 is 10–100× faster, handles UDP/databases/custom protocols. L7 adds latency but enables content routing. Speed vs smarts: L4 for raw throughput (CDN, game servers), L7 for microservices.
    </Misconception>

    <p><strong>Client-IP preservation.</strong> When the LB forwards a request to the backend, the backend sees the LB's IP as the source, not the client's real IP. Three standards exist to fix this. First, the X-Forwarded-For header (de-facto standard but HTTP-only) appends the client IP as a comma-separated list. This is easily spoofed if an untrusted proxy appends to it. Second, RFC 7239 Forwarded header (standardized, more robust): includes client address and protocol in a structured format. Third, the PROXY protocol (a HAProxy feature) prepends a binary header before the HTTP payload that includes source/dest IP and port. The PROXY protocol works below HTTP for any TCP/UDP protocol and is harder to spoof because it is a binary format.</p>

    <p><strong>Round-robin and weighted round-robin.</strong> The simplest balancing algorithm: rotate through backends in order (B1, B2, B3, ...). It is O(1) fast but ignores actual load. Weighted round-robin assigns each backend a weight: if B1 has weight 2 and B2 has weight 1, B1 receives twice as many requests. Both assume all requests cost the same, which is rarely true — a 1 ms query and a 100 ms file upload should not weight equally. Round-robin works fine for homogeneous backends with similar response times but fails when backends have different capacity or requests have wildly different cost.</p>

    <p><strong>Least-connections and the herding problem.</strong> Route the next request to the backend with the fewest active connections. This adapts to real backlog but requires an O(N) scan per request and produces synchronized herding: if a backend recovers from overload all pending clients perceive it at the same instant and surge to it, causing another spike. Least-connections works better than round-robin on real workloads but the herding remains a real failure mode at scale.</p>

    <p><strong>Power-of-two-choices: the modern default.</strong> Pick two random backends and send the request to the less-loaded one. This is O(1), adapts in real time like least-connections, but the randomness prevents synchronized herding. Load imbalance across N backends is ~12% with power-of-two-choices vs ~100% with pure random vs O(N) latency with pure least-connections. Nginx, Envoy, and most modern LBs default to this algorithm because it is the sweet spot: simple, fast, and fair. It also scales well across thousands of backends without contention.</p>

    <p><strong>Health checks: active and passive.</strong> Active health checks: the LB probes each backend (HTTP GET, TCP SYN, or gRPC check) every 10–30 seconds. After 2–3 consecutive failures the backend is marked unhealthy; after 2–3 successes it returns to healthy. This catches silent failures (crashed server that still accepts TCP) but adds extra traffic. Passive / outlier detection (Envoy): observe real client traffic. If a backend returns repeated 5xx or timeouts, eject it from the pool. Envoy starts with 30 seconds of ejection, doubles it on each re-ejection up to ~300 seconds. Use both: active catches total failures, passive catches application-level hangs and resource exhaustion that active probes miss.</p>

    <p><strong>Connection draining and graceful shutdown.</strong> When removing a backend, stop sending NEW requests to it but allow in-flight requests to finish within a drain timeout (AWS ALB: 300 s default; GCP: configurable 0–3600 s; 300+ s for WebSocket/streaming; 5–30 s for short HTTP). The application handles SIGTERM: stop accepting new connections, finish in-flight work, exit cleanly. Without draining, the LB tears down active connections mid-request, causing data loss and user errors. Slow start / warm-up: when a backend rejoins after a restart, ramp traffic gradually (10%→50%→100% over 1–5 minutes) so caches prime and connection pools stabilize.</p>

    <p><strong>Connection limits, queuing, and load shedding.</strong> The LB and each backend have finite capacity: max concurrent connections, max pending requests in queue, max threads. When a backend hits its limit, incoming requests queue. If the queue grows unbounded (no limit), memory bloats and latency spikes. Load shedding: drop new requests with 503 immediately when queue depth exceeds a threshold (e.g., max 1000 queued requests) instead of accepting them. This causes fast failure, allowing clients to retry elsewhere or degrade gracefully. Circuit breakers enforce connection limits per backend (e.g., max 100 concurrent to a backend; 101st request gets 503 immediately). Without limits, a single slow backend can cause a cascade: requests pile up, client connections timeout, retries accumulate, and the LB exhausts resources.</p>

    <p><strong>Session affinity (sticky sessions).</strong> Some applications store session state on a single backend (bad practice but common). Session affinity makes the LB route all requests from one client to the same backend. Cookie-based affinity (`LB_ROUTE=backend_2`) survives client-IP changes and graceful failover. IP-hash affinity works for any protocol but breaks if the client's IP changes (NAT, mobile handover) and clusters badly when many clients share one corporate NAT IP. Stickiness causes 1.5–2.5x worse load imbalance and session loss on backend failure. Best practice: store sessions in Redis or another distributed store instead of on a single backend.</p>

    <p><strong>The retry-storm failure mode.</strong> When a backend blips (GC pause, pool exhaustion), requests time out and clients retry. Each retry adds load to the already-overloaded backend, causing it to fall further behind. Within seconds the overload cascades to other backends as their connections pile up. This is the retry storm: N clients × M retries → 2^K× amplification across layers. Mitigations: retry budgets (cap retries at ~10% of traffic, excess fails fast); exponential backoff with jitter (randomize retry delays so they do not synchronize); circuit breakers (open after N failures, half-open after cooldown, refusing new requests); load shedding (drop new requests with 503 when queue depth exceeds threshold).</p>

    <Misconception id="r-retry-storm">
      "Automatic retries make systems resilient." Retries amplify failures. One timeout becomes 2× load on a drowning backend. Across N microservice layers, a single blip cascades into outage. Fix: retry budgets (~10%), circuit breakers, exponential backoff with jitter. Fail fast, not hard.
    </Misconception>

    <p><strong>Consistent hashing for cache locality and sharding.</strong> Round-robin spreads requests evenly but loses cache locality: if request A goes to B1 and request B goes to B2, their caches never overlap. Consistent hashing maps each cache key onto a hash ring; backends are spaced around the ring with virtual nodes (~150–300 per backend) to even out distribution. When a backend joins or leaves, only ~1/N of keys remap — the rest stay on their original backend. Lookup is O(log N). Use it for cache backends, database sharding, or sticky session hashing.</p>

    <p><strong>Rendezvous hashing (highest-random-weight).</strong> Hash(key, each_backend) for all backends, pick the one with the highest hash. No ring structure, simpler logic, O(N) per lookup but better hash distribution in practice than consistent hashing. Some CDNs prefer it for sharding.</p>

    <p><strong>Health-check types and intervals.</strong> Active health checks come in several flavors: HTTP GET (most common; LB sends GET /healthz, expects 200 OK), TCP SYN (lightweight; just try to connect, if connection succeeds backend is alive), gRPC health check (for gRPC services; standard proto), custom UDP probes. Each check fires every 10–30 seconds. Thresholds: after 2–3 consecutive failures mark unhealthy; after 2–3 consecutive successes mark healthy. Too-frequent checks (every 1 second) waste bandwidth; too-infrequent checks (every 300 seconds) delay failure detection. Combine active checks with passive outlier detection (observing real traffic failures) for fast, reliable detection. A backend can fail silently — still accepting connections but returning 5xx errors — so passive observation catches what active checks miss. Both together provide defense in depth.</p>

This decouples routing from state, allows the LB to move a client's traffic freely, and provides resilience: if one backend dies the client's session persists in Redis and the LB routes the next request to a healthy backend that can resume it.`,

    <p><strong>Power-of-two-choices in depth.</strong> Why does picking two random backends and choosing the less-loaded one beat both pure random and pure least-connections? Pure random produces ~100% imbalance: some backends get 2x the average load. Pure least-connections requires an O(N) scan and the synchronized herding when a backend recovers. Power-of-two-choices is O(1): compute two random indices, compare their load counters (updated on each request completion), pick the minimum. The mathematics (Adler 1996) prove that load imbalance converges to ~12% as N grows — a massive win. The randomness prevents synchronization while the comparison prevents the worst-case behavior of pure random.</p>

    <p><strong>Consistent hashing: hash rings and virtual nodes.</strong> When a request key (e.g., user ID for session routing, cache key for sharding) needs to route to the same backend repeatedly, consistent hashing maps the key onto a ring and backends partition the ring with virtual nodes. A key hashes to a point on the ring and routes to the nearest backend clockwise. If a backend joins or leaves, only ~1/N of keys remap — the rest keep their backend because their position on the ring is unchanged. Virtual nodes (~150–300 per backend) even out the distribution so one backend does not claim a huge arc. Lookup is O(log N) with a sorted tree; insertion/deletion is O(1) amortized. Downside: it adds state complexity and does not adapt to per-request load variations. Use it for sharding and cache locality; use power-of-two-choices for request balancing.</p>

    <p><strong>Rendezvous hashing (highest-random-weight).</strong> For every backend, compute Hash(key, backend_id). Pick the backend with the highest hash value. No ring structure, no virtual nodes, just O(N) comparisons per lookup. Simpler to implement and reason about than consistent hashing. Some systems prefer it because the hash distribution is often more uniform in practice — the ring can have uneven gaps but HRW spreads more evenly. Trade-off: O(N) vs O(log N) lookup, but for small N (&lt;100 backends) the difference is negligible.</p>

    <p><strong>Sticky sessions and session affinity: cookie-based vs IP-hash.</strong> Cookie-based affinity: the LB sets a cookie `LB_ROUTE=backend_2` on the response. Client sends it back on the next request, LB parses it, routes to backend_2. Survives client-IP changes and provides graceful failover: if backend_2 is down the LB can redirect to a fallback. IP-hash affinity: route by Hash(client_IP) % num_backends. Works for any protocol (no cookie support needed) but breaks on client-IP change (mobile handover, NAT failover) and clusters badly: if 50 clients behind a corporate NAT hash to the same backend that backend gets 50x load. Cookie-based is superior for HTTP services; IP-hash for non-HTTP (game servers, custom protocols). Both cause ~1.5–2.5x imbalance compared to stateless balancing. The right architecture: store session state in a distributed session store (Redis, Memcached) keyed by session ID, accessible from any backend, so the LB can route requests freely without affinity and sessions survive backend failures.</p>

    <p><strong>Active vs passive health checks and outlier detection.</strong> Active health checks: LB probes each backend independently every 10–30 seconds (HTTP GET, TCP SYN, gRPC health check, or custom). After 2–3 consecutive failures the backend is unhealthy; after 2–3 successes it returns to healthy. Catches total failures (crashed server) but adds traffic overhead. Passive / outlier detection (Envoy paradigm): observe real client traffic. If a backend returns repeated 5xx errors or timeouts, mark it as an outlier. Envoy default: eject after 5 consecutive 5xx (configurable); ejection duration starts at 30 seconds, doubles on each re-ejection up to ~300 seconds max. Catches application-level hangs (connection pool exhaustion, database slowness) that active checks might miss. Use both: active is the safety net, passive catches the common cases. Circuit breaking (Envoy again): enforce hard limits on concurrent or pending requests to a backend (e.g., max 100 concurrent). Return 503 immediately if the limit is hit instead of queueing, preventing resource exhaustion on the backend.</p>

    <p><strong>Connection draining, graceful shutdown, and slow start.</strong> Connection draining: when removing a backend, stop accepting NEW requests to it but wait for in-flight requests to finish within a drain timeout (AWS ALB default: 300 s; GCP: 0–3600 s configurable; long-lived WebSocket/SSE: 300+ s; short HTTP: 5–30 s). Typically triggered by the backend itself via a drain endpoint that causes the LB to mark it "draining" while it finishes existing requests. The application calls `close(listening_socket)` on SIGTERM to stop accepting new connections, finishes the in-flight requests, and exits. Without draining an LB that pulls a backend mid-request tears down the connection, causing data loss. Slow start / warm-up: when a backend rejoins after recovery or new deployment, ramp traffic gradually (10%→50%→100% over 1–5 minutes). This allows in-process caches to warm, database connection pools to prime, and TLS session caches to populate. If you send full load to a cold backend it slows down under the surge and risks cascading failure. Envoy supports this via `slow_start_window` and `slow_start_duration`.</p>

    <p><strong>Retry storms and thundering herds: retry amplification.</strong> A backend blips (GC pause, thread pool exhaustion). Requests time out and timeout. Each timeout triggers a client retry, adding load to the already-overloaded backend. With N clients, M request attempts per client, and K layers of retries, load amplifies to ~2^K× the original. Example: 100 clients, 1 retry each = 200 requests to an already-broken backend. 100 clients, 2 retries each = 300 requests. Across N=10 layers (client → LB → backend_lb → shard_lb → replica_lb → ...) with 1 retry per layer, amplification approaches 2^10 = 1024×. Mitigations: (1) retry budgets — cap retries at ~10% of request rate so excess fails fast; (2) exponential backoff with jitter — randomize retry delays with base × 2^attempt + random(0, base) so retries do not synchronize; (3) circuit breakers — open after N failures, refuse new requests with 503; (4) load shedding — drop new requests with 503 when queue depth exceeds a threshold; (5) observe and alert on retry rates > 0.1% so humans intervene before cascade.</p>

    <p><strong>Health-check flapping and detection jitter.</strong> A network blip causes active health checks to fail. After 2–3 failures the backend is ejected. A moment later the network recovers and checks pass; after 2–3 successes the backend rejoins. This flapping (ejected → healthy → ejected ...) causes rapid traffic churn. Fix: increase failure/success thresholds (require 5 consecutive failures before ejection, 5 consecutive successes before re-adding); add jitter to check timing so multiple health checks do not fire in lockstep. Envoy's ejection behavior includes an exponential backoff: 30 s → 60 s → 120 s → ... up to max, so a flapping backend naturally stabilizes as the ejection window widens.</p>

    <p><strong>Load balancer single point of failure: anycast, ECMP, and consistent hashing.</strong> A single LB is a single point of failure — if it crashes all traffic stops. Multiple active LBs sharing one anycast VIP (virtual IP) address solve this: BGP ECMP (Equal-Cost Multipath) advertises the same IP from multiple LBs and load-balances traffic among them at the network layer. If one LB dies its BGP route is withdrawn and traffic reroutes to the healthy LBs. Internal glitch: connections rerouted to a different LB mid-flight lose state unless all LBs share the connection state (stateless LBs) or use consistent hashing so a given flow always maps to the same physical LB (stateful). Maglev (Google's distributed LB) uses a consistent hash of the 5-tuple (src, dst, sport, dport, protocol) to ensure a flow always hits the same LB; if a backend pool changes, only ~1/backend fraction of flows remap. Cross-zone routing: an LB in zone A routing to backends in zone B incurs egress charges ($0.01–0.02/GB) and extra latency. Best practice: zone-aware routing — prefer same-zone healthy backends, fall back to other zones only if all local backends are down.</p>

    <p><strong>RFC 7239 Forwarded header for client-IP preservation.</strong> `X-Forwarded-For` is de-facto but HTTP-only and easily spoofed. RFC 7239 standardizes the `Forwarded` header: `Forwarded: for=203.0.113.195;proto=https;host=example.com`. It is more robust and parse-safe. The PROXY protocol (HAProxy) works below HTTP — the LB prepends a line before the TLS/HTTP payload: `PROXY TCP4 203.0.113.195 93.184.216.34 35646 80` (binary version exists too). Works for any protocol and is harder to spoof. Nginx, HAProxy, and most modern LBs support all three; choose based on your protocol and trust model.</p>

    <p><strong>TLS termination and 0-RTT resumption at the LB.</strong> The LB terminates the client's TLS handshake (decrypts the request, sees plaintext), re-encrypts to the backend on a separate connection (or sends plaintext if backend is internal). This costs ~20–50 ms per connection under normal load, 50–2000 ms under spikes. The LB saves CPU by doing it once instead of every backend doing it. TLS 1.3 0-RTT resumption: if the client has a valid pre-shared key (PSK) from a prior connection, the first request can be sent with the ServerHello in the same flight. The LB must route resumption requests to the same LB instance (session state affinity) unless the PSK is stored in a distributed session cache. Modern CDNs (Cloudflare, AWS CloudFront) offer this transparently.</p>

    <p><strong>Observability: metrics and dashboards.</strong> Essential metrics: (1) request rate per backend and per endpoint (RED method); (2) p50/p95/p99 latency per backend; (3) error rate per backend; (4) active connection count; (5) health-check success/failure rates; (6) circuit-breaker opens/closes; (7) retry rate (alert if >0.1%); (8) load imbalance (std dev of request counts across backends); (9) drain time on shutdowns. Tools: Prometheus exporters from Envoy/HAProxy emit these; Datadog, Grafana dashboards; log aggregation for tail latency analysis. SLO: p99 latency < 100 ms, error rate < 0.01%, circuit-breaker open time < 1 minute/week.</p>

    <p><strong>DNS load balancing vs LB load balancing.</strong> DNS can return multiple A records for a hostname (round-robin at resolution time). But DNS TTLs are typically 60–300 seconds, so backend changes are not reflected immediately and clients cache results, defeating rebalancing. A better pattern: DNS points to an LB IP (one per region), the LB handles per-request balancing. Hybrid: DNS geolocation routes to regional LBs (Anycast), each LB load-balances within the region. This isolates regional failures and reduces latency.</p>
