You know TCP. You know TLS. You know how they stack: the browser does a TCP <a href="/en/networking/03-tcp-handshake/">handshake</a> (1 RTT), then a TLS handshake on top (1 more RTT), then finally sends the HTTP request. On a 100 ms intercontinental link that's 200 ms of overhead before your page even starts loading. QUIC merges both into one, runs entirely in user space so it evolves faster than the kernel, and lets connections survive when you switch from WiFi to cellular. But it lives on UDP — the dumb, fire-and-forget protocol — so it has to reinvent everything TCP already solved: retransmission, flow control, congestion control, and connection state. The tradeoff is latency won against CPU cost.

<Crux>How QUIC merges UDP, transport logic, and TLS into a fast protocol that multiplexes streams and survives network migration.</Crux>

QUIC is RFC 9000, published in May 2021. It took thirteen years to standardize because the protocol is radical: move TCP's logic out of the kernel (where evolution grinds to a halt due to middlebox ossification — firewalls and NATs that only understand existing TCP options and drop anything new), put it in user space (where applications control every aspect), and send it all over UDP so middleboxes have no special cases for it. The payoff is a protocol that can evolve, migrate connections across networks, and deliver <a href="/en/networking/06-http-versions/">HTTP/3</a> 30–55% faster on lossy mobile networks. <SpiralCue thread="latency" lang="en" /> — every millisecond counts, and QUIC's design is built around latency obsessively.

    <p><strong>Why QUIC, not just TCP+TLS?</strong> Two problems with TCP: (1) kernel TCP evolves slowly — any new TCP option gets stripped by middleboxes that don't understand it, so improvement stops; (2) losing a single packet stalls all the streams on the connection, even the ones with unrelated data — a condition called head-of-line blocking. QUIC fixes both by living in user space (no kernel recompile cycle, every app can have the latest congestion control) and multiplexing independent streams so a lost packet only blocks the stream carrying it.</p>
    <p><strong>The one-sentence definition.</strong> QUIC is a transport protocol running on top of UDP that carries a TLS 1.3 handshake, multiplexes many independent data streams, and survives network migration (your laptop switching from WiFi to cellular without losing the connection).</p>
    <p><strong>The metaphor.</strong> Imagine postal mail: TCP is like sending envelopes one at a time in strict order. Lose one and all others wait. QUIC is like a postman with one bag holding many separate envelopes; lose one and the rest keep moving. Also, QUIC's bag is encrypted.</p>
    <p><strong>One scenario end to end.</strong> You open a mobile app that streams video over QUIC while sending periodic beacon requests (analytics) and real-time chat. In <a href="/en/networking/03-tcp-handshake/">TCP</a> each would use its own connection and pay three handshakes. In QUIC they share one connection, so you pay one 1-RTT handshake and then the app can use stream ID 0 for video, stream ID 2 for analytics, stream ID 1 for chat. A dropped packet in stream 1 doesn't block stream 0's video frames from arriving. When you move from WiFi to 4G the connection ID stays valid, all the streams stay alive, and the game never even notices.</p>

  <Fragment slot="middle">
    <p><strong>Why QUIC and the UDP foundation.</strong> TCP is old. Adding new TCP options requires kernel updates, OS patches shipped months later, and then you hope middleboxes (firewalls, NATs, load balancers) don't silently drop the option. This ossification meant TCP could barely evolve for decades. QUIC's radical solution: move the transport logic to user space where it can be updated with every application, run it over UDP (which middleboxes have no special knowledge of), and encrypt almost the entire packet so middleboxes can't even inspect it. The cost is CPU — user-space packet processing adds overhead — but the payoff is latency (1-RTT handshake, 0-RTT resumption, connection migration) and evolution (applications ship new congestion control algorithms weekly).</p>
    <p><strong>What QUIC reuses from TCP and what it changes.</strong> QUIC borrows TCP's packet numbers (not sequence numbers, but the same idea — each packet gets a number for ACK and loss detection), ACK ranges (like TCP's SACK), retransmission logic, congestion control (slow start, window growth, loss signals), and connection state machine. What QUIC changes: packet numbers are monotonically increasing and never retransmitted (eliminating TCP's Karn's-algorithm ambiguity), flow control is two-level (per-stream and per-connection), and handshake is merged with TLS so there is no separate TLS layer on top. Every QUIC packet is encrypted except the outermost header (version, connection ID); TCP's headers are cleartext. The result: QUIC feels like TCP's DNA rearranged in user space.</p>
    <p><strong>Independent streams and the head-of-line-blocking fix.</strong> QUIC multiplexes many bidirectional streams (IDs 0, 4, 8, 12, ... for client-initiated even IDs; 1, 5, 9, 13, ... for server-initiated odd IDs) and many unidirectional streams (separate ID spaces) on a single connection. Each stream has its own flow-control window (max-stream-data) and its own application-level framing. When a STREAM frame carrying stream 7's data is lost, only stream 7's receiver has to wait for the retransmit; streams 1, 3, 5 keep flowing with new data. Measurement: at 0.5% random loss and 100 ms RTT, a message blocked in TCP's ordered delivery waits ~230 ms, while the same message in QUIC per-stream delivery experiences ~0.4 ms blocking — a 575× difference. This is why QUIC dominates on lossy mobile networks.</p>
    <p><strong>The integrated transport+TLS handshake and 1-RTT.</strong> QUIC fuses the transport and TLS layers. The client sends an Initial packet containing a CRYPTO frame with the TLS ClientHello inside; the server replies with its own Initial packet containing a CRYPTO frame with ServerHello + EncryptedExtensions + Certificate + CertificateVerify; the client sends a Handshake packet with a CRYPTO frame containing Finished. One round-trip from client to server to client, and both sides have the TLS record keys. This is 1-RTT from client start to receiving the server's Finished — compare TCP+TLS where TCP's three-way handshake takes 1 RTT, then TLS takes another RTT on top. On 100 ms latency, QUIC saves 100 ms to first application data. QUIC supports four encryption levels: Initial (before handshake), 0-RTT (client data before receiving server's Finished), Handshake (server's Finished + client's later Handshake packets), and 1-RTT (post-handshake traffic). These map to three packet-number spaces: Initial/Handshake share one space, 0-RTT and 1-RTT share another, so loss detection is independent.</p>
    <p><strong>0-RTT resumption and replay risk.</strong> On subsequent connections to the same server, the client can reuse a cached session ticket and send application data in the ClientHello (0-RTT data) without waiting for the server's response. The server may accept it immediately (server-side 0-RTT) or force the client to wait for the Finished message before processing the data (safer but not 0-RTT). The trade-off: 0-RTT data has no forward secrecy and is not replay-protected by TLS. An on-path attacker who captures the 0-RTT packet can replay it to the server. The mitigation: the server MUST accept only idempotent requests in 0-RTT (GET, HEAD, safe operations); the server includes an Early-Data: 1 header when forwarding 0-RTT to an origin; the origin can answer 425 (Too Early) to force a retry after the full handshake; and the server uses replay protection keyed by the client's address so the same client replaying their own old ticket once is safe, but different clients spoofing the same address cannot replay.</p>
    <p><strong>Connection IDs and connection migration.</strong> A QUIC connection is identified by a variable-length Connection ID (up to 20 bytes, typically 8), not by the 4-tuple (client IP, client port, server IP, server port). When the client's IP address changes (Wi-Fi to cellular, NAT rebind, etc.) the connection ID stays the same and the connection is still valid. The server validates the new path by sending a PATH_CHALLENGE frame and expecting a PATH_RESPONSE; until that exchange completes the server may limit the rate of packets sent to the new address (anti-amplification, see below). This is a game-changer for mobile: a video stream continues seamlessly when you step outside the office and drop to cellular without any application visible reconnect. TCP cannot do this — a new IP kills the connection. Connection IDs also prevent idle-connection ambiguity: a middlebox forgetting a QUIC connection and later seeing a QUIC packet with the same Connection ID correctly identifies it as old, not new.</p>
    <p><strong>Packet-number-based loss detection.</strong> QUIC packet numbers are monotonically increasing integers (1, 2, 3, ...) never reused and never retransmitted. ACK frames carry multiple ACK ranges (e.g., ack_ranges: [1000-1005, 1007-1010] meaning packets 1000–1005 and 1007–1010 arrived, 1006 is missing). Loss is declared when (a) a later packet is acknowledged and the time-based reorder window expires (typically 1.5× max RTT), or (b) the PTO (Probe Timeout, like TCP's RTO) fires. Unlike TCP where retransmitted packets are ambiguous (does the ACK acknowledge the first or the retransmit?), QUIC never retransmits — a lost packet gets a new packet number. The old Karn's algorithm workaround is unnecessary. The downside: QUIC sends an extra 4+ bytes per packet for packet numbers, and packet loss is detected using PTO (a timer similar to RTO) so extreme clock skew matters more than in TCP. RFC 9002 specifies the algorithm in detail with Ack-Eliciting frames ensuring ACKs arrive regularly; implementations must track ACK-Eliciting frames separately from non-ack-eliciting frames (like ACK frames themselves) so bundling is optimal.</p>
    <p><strong>Congestion control in user space.</strong> Because QUIC lives in user space, congestion control is pluggable. The RFC 9002 baseline is NewReno (the classical algorithm: slow start, additive increase, halve window on loss). Major implementations ship CUBIC (aggressive probing after loss, standard on Linux), BBR (bandwidth-RTT model, used on Google YouTube/Cloud), and sometimes Hystart++ (faster slow-start exit on bursty traffic). A single QUIC library (e.g., quiche from Cloudflare) can support multiple algorithms selectable at connection open. This agility is impossible with kernel TCP where changing congestion control requires recompiling or sysctl changes across millions of servers. The trade-off is that user-space processing is slower — more CPU per byte — so QUIC's CPU cost (15–30% higher than kernel TCP per byte) is a real operational burden on high-throughput servers.</p>
    <p><strong>Tradeoff: latency vs CPU cost.</strong> QUIC saves 100+ ms on handshake latency and 30–55% on page load time over lossy mobile networks. But every QUIC packet is processed in user space with per-packet AES-GCM encryption, which burns more CPU than kernel TCP's hardware-offloaded crypto. On a fast link (1 Gbps, ~125 MB/s at line rate) QUIC's overhead translates to up to ~45% goodput loss compared to HTTP/2 over TCP. On a slow or lossy link (typical mobile, 2% loss, 10 Mbps) the HoL-blocking fix dominates and HTTP/3 delivers 30–55% faster page loads. Modern defenses: UDP GSO (Generic Segmentation Offload, sending many packets in one syscall), NIC offload of QUIC header parsing, and kernel-bypass networking on high-end servers reduce the CPU gap to ~15–20% in steady state.</p>
    <p><strong>UDP amplification and anti-amplification limits.</strong> Until the server validates the client's address the server may send at most 3× the bytes it received from that address (anti-amplification limit). This prevents UDP-based amplification attacks where a small packet to a reflector bounces a large response to a victim. Clients must send Initial packets of at least 1200 bytes (even if padding is needed) so servers have headroom. If a client sends a 1200-byte Initial, the server can respond with up to 3600 bytes before validating the address. Clients that exceed this are rejected. Servers use Retry packets (send-only packets that don't count against the limit) to request an address token (proving the client's IP is real) before processing the handshake. Cloudflare shipped a WAF rule in early 2025 that inadvertently violated the 3× limit on broadcast addresses by sending enormous responses, amplifying attacks — a reminder that every implementation that touches the handshake must enforce this.</p>
    <p><strong>Almost-fully-encrypted packets and header minimization.</strong> TCP headers are cleartext, so any observer (network engineer, ISP, attacker, DPI firewall) can read source/dest IP, ports, and sequence numbers. QUIC encrypts almost everything: the packet number, payload, even connection ID when using short-form headers (post-handshake packets). Only the outermost 4 bytes (version + connection ID length) and the connection ID itself are unencrypted in long-form headers; short-form headers (used after handshake) encrypt even more. This prevents passive snooping, hides stream structure from middleboxes, and makes it impossible for a firewall to inject RST packets (TCP's weakness). The cost is that network monitoring tools (tcpdump, traffic analysis) see QUIC as opaque blobs and cannot inspect flows. Network operations teams hate this; privacy advocates love it.</p>

  <Fragment slot="senior">
    <p><strong>Four encryption levels and three packet-number spaces.</strong> QUIC has four distinct encryption keys: Initial (deterministic from connection ID, allows both sides to encrypt before key exchange), 0-RTT (from the session ticket, allows early data before Finished), Handshake (derived from the shared secrets after ClientHello-ServerHello exchange), and 1-RTT (the final keys). These correspond to three packet-number spaces: (1) Initial/Handshake share one space where packets are numbered independently; (2) 0-RTT and 1-RTT share the Application Data space. The packet-number space separation is critical because loss detection must be independent per space — a loss in the Initial space does not trigger congestion control reduction for 1-RTT packets. RFC 9002 specifies PTO-based loss detection per space.</p>
    <p><strong>Almost-fully-encrypted packets and long vs. short headers.</strong> Long-form headers (used during handshake and Initial packets) carry version, destination connection ID, source connection ID, token (for Retry), packet number, and payload — all except the outermost 4 bytes are encrypted using the appropriate level's key. Short-form headers (used post-handshake) carry only the connection ID and packet number plus the payload, almost entirely encrypted. This is radically different from TCP's cleartext 20-byte header visible to every observer. An on-path attacker cannot inject RST packets (TCP's weakness) because they cannot construct a valid encrypted packet without the 1-RTT key. Network operators cannot perform per-packet traffic engineering without decrypting, leading to operational friction and encrypted traffic pushing anonymity arguments. The privacy gain is real; the operational cost is also real.</p>
    <p><strong>Loss detection internals: monotonic packet numbers and ACK ranges.</strong> Unlike TCP where retransmitted packets carry the same sequence number (creating Karn's algorithm ambiguity), QUIC packet numbers are strictly increasing — a lost packet gets a new packet number on retransmit. ACK frames list ACK ranges, e.g., ack_ranges: [1000..1005, 1008..1010] with a gap at 1006, using variable-length integers so ACK frames are compact. Loss is declared when a later packet is acknowledged and a reorder-window has expired (typically 1.5 × max RTT), or when PTO (Probe Timeout) fires. PTO is computed similarly to TCP's RTO with SRTT and RTTVAR but operates per packet-number space. Ack-Eliciting frames (any frame that should trigger an ACK) are tracked separately from non-ack-eliciting (e.g., ACK frames themselves), so the receiver can bundle ACK piggyback smartly. The monotonic packet-number model is simpler than TCP's but requires retransmitted frames to be reserialized with new packet numbers, adding CPU cost.</p>
    <p><strong>Pluggable congestion control: NewReno, CUBIC, BBR, HyStart++.</strong> RFC 9002 specifies NewReno as the baseline: slow start (cwnd doubles per RTT), congestion avoidance (cwnd += MSS per RTT), and halve cwnd on loss. Implementations ship CUBIC (quiche, Linux kernel standard): faster probing back after loss with a cubic function, more aggressive than Reno on high-BDP paths. BBR (Google, YouTube, Cloudflare edges): model bottleneck bandwidth and minimum RTT, pace sends to fill but not overflow, ignore random loss. Hystart++ (exit slow start early by detecting queueing, used in quiche with CUBIC). Applications can select the algorithm at connection open; user-space placement means algorithms evolve weekly on CDN edges whereas kernel TCP is stuck with the compile-time choice. The downside: this flexibility makes benchmarking hard — comparing two QUIC stacks with different CC algorithms is not a fair comparison of QUIC itself.</p>
    <p><strong>Connection migration mechanics and path validation.</strong> When the client's IP or port changes (verified by the Connection ID matching a known connection), the server sends PATH_CHALLENGE: a random 8-byte value. The client must echo it in PATH_RESPONSE. Until response is received the server limits send rate to 3× received bytes (anti-amplification). After validation the server updates its record of the client's address and unlocks send rate. Path validation prevents address spoofing: an attacker cannot redirect a QUIC connection to a victim's IP. The client also sends packets from multiple addresses during handshake (probing) to detect which addresses work, a feature TCP cannot do. Connection IDs are opaque and per-endpoint-chosen, so even if an observer links old and new IP addresses via the connection ID the server can rotate connection IDs periodically (NEW_CONNECTION_ID frames) to prevent linkage across addresses — privacy without IP hiding.</p>
    <p><strong>The 3× anti-amplification limit and Retry packets.</strong> Before validating the client's address the server may send at most 3× the bytes it received from that address. Clients send Initial packets padded to at least 1200 bytes (even if the handshake is tiny), so servers have room for ~3600 bytes of response (3600 / 1200 = 3×). Servers use Retry packets to request an address token: the server sends a token in a Retry packet and the client echoes it in the next Initial. Retry packets are send-only — they do not count against the limit because they are not addressed to the client (they carry no connection ID). This prevents naive reflection amplification. However, a vulnerable server that echoes extremely large certificate chains or server-hello extensions to an untrusted address can violate this. Cloudflare patched a 2025 DDoS-amplification bug where a broadcast address spoofed as source could receive massive responses; a reminder that enforcement is per-implementation.</p>
    <p><strong>0-RTT replay defence: idempotency and the 425 Too Early response.</strong> 0-RTT data lacks replay protection at the TLS layer — an on-path attacker can capture a 0-RTT handshake and replay it. Servers must accept only idempotent requests in 0-RTT: GET, HEAD, safe operations. Non-idempotent requests (POST, DELETE, state-changing) should either be blocked or deferred until 1-RTT. When the server forwards 0-RTT to an origin server it includes an Early-Data: 1 HTTP header, allowing the origin to reject with 425 (Too Early) forcing a retry after full handshake. Implementations that naively enable 0-RTT for all requests risk executing the same mutation twice (two POST requests from one replay), a serious bug. RFC 9001 and 9114 specify the requirements; RFC 8470 standardizes the 425 response code and Early-Data header.</p>
    <p><strong>UDP blocking (~3–5% of networks) and the mandatory fallback to HTTP/2.</strong> Some networks block UDP entirely (corporate proxies, some ISP gateways, certain 4G LTE contexts). When QUIC is blocked silently (no ICMP error, just dropped packets) the client's timeout is the only signal — QUIC_INITIAL_TIMEOUT is typically 1–3 seconds (exponential backoff on retries), so the user experiences a 1–3 second hang before falling back to TCP. Modern browsers race QUIC and TCP in parallel (both start immediately), reducing this pain: whichever protocol succeeds first wins. HTTP/3 support is advertised via the Alt-Svc header; clients discover this on first connection and attempt QUIC on the second. Observability is poor: you cannot distinguish UDP-blocked from a slow/flaky QUIC path without deep packet inspection. The QUIC spec mandates that implementations MUST support fallback to HTTP/2 over TCP; any deployment that doesn't will fail in blocked networks.</p>
    <p><strong>CPU cost: 15–30% higher per byte than kernel TCP, up to ~45% goodput loss on fast links.</strong> QUIC's user-space packet processing incurs: (1) per-packet AES-GCM encryption (~15–20 cycles per byte on modern CPUs, vs hardware-offloaded TCP), (2) variable-length integer decoding for packet numbers and stream IDs, (3) payload framing (STREAM, CRYPTO, ACK frames are serialized/deserialized in user space). On a 1 Gbps link (125 MB/s) at full rate, QUIC saturates CPU cores faster than kernel TCP. Under load, goodput drops up to ~45% vs HTTP/2 on TCP because the server runs out of CPU before the link fills. On slower or lossy paths (typical mobile) the goodput loss is unmeasurable because the network, not CPU, is the bottleneck. Mitigations: (1) UDP GSO — batch many packets in one sendmsg() syscall, ~3–4 syscalls per 64 KB instead of one per packet; (2) NIC QUIC offload (Intel 810, newer NICs) parse packet headers in silicon; (3) core affinity — keep the QUIC process on the same CPU, reducing cache misses; (4) async I/O to avoid syscall overhead per packet. Modern deployments see the per-byte CPU cost drop from 30% to 15–20% with GSO + careful tuning. Cloudflare reports ~20% CPU gain from GSO alone.</p>
    <p><strong>Deployment reality 2026: ~21% of web traffic runs HTTP/3, ~35–40% of sites advertise it.</strong> QUIC was standardized in 2021, HTTP/3 RFC 9114 in 2022. Adoption is steady but not explosive. Major CDNs (Cloudflare, Google, Akamai, Fastly) enable HTTP/3. Browsers (Chrome, Safari, Firefox) support it. But adoption is bimodal: mobile browsers default-enable HTTP/3 because the latency and HoL benefits are massive on cellular; desktop (where connections are often short-lived over fast local networks) sees less benefit and still races QUIC vs. TCP. Measurement: ~21% of Alexa 1M sites emit Alt-Svc headers for HTTP/3; actual traffic is lower because browsers still race TCP in parallel and TCP often wins on LAN. Adoption will stabilize as fallback becomes seamless (transparent racing in all clients), UDP blocking becomes even rarer, and QUIC CPU cost continues dropping with hardware offload. In 5 years QUIC will likely be the default; for now it is opt-in.</p>
    <p><strong>Observability: encrypted traffic, connection semantics, and tool gaps.</strong> QUIC encryption prevents packet inspection — a tcpdump of QUIC traffic shows only opaque blobs. This breaks traditional network monitoring: you cannot count HTTP requests per endpoint, cannot detect slow clients, cannot identify misbehavior at the flow level. The industry is adapting: QUIC-aware metrics are exposed by applications (via JSON-based QUIC trace export, RFC 9312), browsers report connection timing in user-facing APIs (PerformanceResourceTiming.nextHopProtocol), and cloud providers (AWS, GCP) are adding QUIC-aware observability tools. Tracing a QUIC connection's full lifecycle requires application integration or kernel-bypass introspection (eBPF probes on the userspace socket). This is a trade-off: encryption gains privacy at the cost of operational opacity.</p>
