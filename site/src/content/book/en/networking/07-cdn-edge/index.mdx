When <PersonaTag id="bea" lang="en" /> (the browser) loads a page from a server in California, every request travels 200 ms round-trip from her network in London. The page stalls. But what if her request never left London? What if a copy of the server's data lived in a data center next door, served the response in 20 ms, and stayed synchronized? That is a CDN — Content Delivery Network. It is the most direct way to defeat latency: put content near the user. Three mechanisms work in concert: <SpiralCue thread="latency" lang="en" /> Anycast IP routing (same address advertised from many cities), edge DNS (returning different server addresses by geography), and tiered caching (so the origin server answers only 1% of requests). Together, they move the performance bottleneck from the speed of light to the strategy of the cache.

    <p><strong>What a CDN does in one sentence.</strong> It keeps copies of your website on hundreds of servers around the world so the user's browser fetches bytes from a server 20 ms away instead of one 200 ms away.</p>
    <p><strong>Why care.</strong> Speed of light is finite. A request between London and California is fundamentally ~70 ms one-way at best. No code optimisation closes that gap. A CDN closes it by moving the content, not by speeding up the network.</p>
    <p><strong>The metaphor.</strong> Imagine you publish a magazine. Without a CDN you mail every reader a copy from one print shop. With a CDN you ship pallets to local distribution centres in every city; each reader picks up a copy from their nearest one. Same magazine, far shorter trip.</p>
    <p><strong>Read-aloud dialogue.</strong> <PersonaTag id="bea" lang="en" /> in London asks for example.com. The Internet's routing magic sends her to a CDN edge in London 20 ms away. The edge has the page cached: hands it to Bea immediately. <PersonaTag id="patty" lang="en" /> in Tokyo asks the same URL and lands on the Tokyo edge with its own cached copy. <PersonaTag id="sven" lang="en" />, the origin server in California, sees one request from each city's edge and almost no traffic from users directly.</p>
    <p><strong>One scenario end to end.</strong> You navigate to a CDN-fronted site. Browser does <a href="/en/networking/04-dns-resolution/">DNS</a>, which returns the IP of the nearest edge. <a href="/en/networking/03-tcp-handshake/">TCP</a>, <a href="/en/networking/05-tls-handshake/">TLS</a>, <a href="/en/networking/06-http-versions/">HTTP</a> request all happen against the edge, not the origin. If the edge has the response cached you get a fast reply; otherwise the edge forwards to origin (or to an intermediate shield) and caches the answer for the next user.</p>

  <Fragment slot="middle">
    <p><strong>Three pieces cooperate: Anycast IP, GeoDNS, and tiered cache.</strong></p>
    <p><strong>Anycast IP:</strong> The CDN advertises the same IP address (say, `93.184.216.1`) from multiple geographic locations. BGP routing selects the "nearest" edge location (by hop count or AS path length). When Bea makes a request, her local router sends it to the closest edge POP (Point of Presence) that advertises that IP. No special DNS — just routing.</p>
    <p><strong>GeoDNS:</strong> Most CDNs prefer explicit control via DNS. The CDN operator configures DNS to return different A records based on the resolver's geographic location (inferred from IP). A query from a London resolver returns the London edge IP; a Tokyo resolver gets Tokyo. The resolver is the client requesting DNS, not the end browser. A global resolver like 8.8.8.8 appears to come from Google's data center, so GeoDNS returns a regional IP based on that location, not the browser's. This is why users sometimes get misrouted — their DNS provider is far from home.</p>
    <p><strong>Tiered caching:</strong> The edge has limited storage. Frequent requests (top 20% of assets) live at the edge. Rare requests miss the edge and go to an origin shield — an intermediate cache tier between edge and origin. The shield absorbs ~99% of misses, protecting the origin from request storms. Cache key is URL + variant headers (Accept-Encoding, Accept-Language). The response header `Vary: Accept-Language` tells the cache: "Keep separate entries for each language." `Cache-Control` directives govern duration: `max-age=3600` (1 hour, for browser and CDN), `s-maxage=86400` (1 day, CDN only, browser ignores), `private` (browser only, skip CDN), `no-store` (never cache), `stale-while-revalidate=604800` (serve stale, refresh in background for 7 days after expiry).</p>
    <p><strong>What edges typically cache.</strong> Static assets (JS, CSS, images, fonts, video segments) are the bread and butter — they rarely change and are huge. HTML pages may be cached if they don't include user-specific content. JSON API responses can be cached when the request is read-only and idempotent. Dynamic, personalised responses are usually marked `private` or `no-store`. The rule of thumb: anything with a long max-age belongs at the edge; anything personalised belongs at origin. Modern frameworks (Next.js, Astro, Remix) automatically tag responses for cache eligibility so operators don't have to hand-craft directives per route.</p>
    <p><strong>Origin shield architecture.</strong> Edges in a single region funnel their misses through one regional shield rather than going directly to origin. Why: 200 edges all missing the same uncached URL at the same time would create 200 origin requests; the shield collapses that to one. Cloudflare calls this "Tiered Cache," Fastly calls it "Origin Shield," AWS CloudFront has the same feature. The shield also handles slow-origin scenarios gracefully — long-running origin response is served once to the shield and propagated out as edges re-request the same URL.</p>
    <p><strong>Cache invalidation patterns.</strong> Three ways to drop stale content from cache. (1) TTL expiry — wait for max-age to expire (cheap, slow). (2) Explicit purge — API call to the CDN to remove a specific URL or pattern (`POST /purge {"url": "/api/products"}`); slow when purging thousands of URLs. (3) Cache tags — tag responses at origin (`Cache-Tag: user:42, article:1001`), purge by tag at the CDN (`POST /purge {"tag": "user:42"}`); the most flexible but requires CDN-enterprise feature support. Fastly and Cloudflare Enterprise expose this; cheaper plans only support URL purge.</p>
    <p><strong>The Vary footgun.</strong> Caches key responses by URL plus the headers listed in the `Vary` response header. Missing Vary on a response that genuinely varies (e.g. user-language-aware page) means the first user's response gets served to everyone afterwards. `Vary: Accept-Encoding` is required if you serve gzipped or brotli'd versions. `Vary: Authorization` is required if logged-in vs anonymous users see different content. `Vary: Cookie` is dangerous — wildly fragments the cache because every cookie value is a new variant — typically you want `Cache-Control: private` instead.</p>
    <p><strong>Conditional requests and 304 Not Modified.</strong> Even cache hits can be optimised. The browser caches the response locally; when the cache TTL expires, the browser sends `If-None-Match` with the cached ETag. If the response hasn't changed the CDN (or origin) returns `304 Not Modified` with empty body — saves bandwidth even on revalidation. CDNs handle this transparently for cacheable responses, only forwarding to origin when the ETag actually changed.</p>
    <p><strong>Static-asset versioning.</strong> The clever trick: name your CSS/JS/image files with a content hash (e.g. `app.f3a2b8c.js`). Set very long max-age (`max-age=31536000` = 1 year). When you update the file the URL changes, so the cache never serves stale content — the browser fetches the new URL on the next deploy. Tools like Webpack, Vite, esbuild, Astro do this automatically with `assetsInclude` patterns.</p>
    <p><strong>SLA basics.</strong> CDNs publish SLAs typically around 100% uptime with credits for breaches. The interesting number is p95/p99 latency at the edge: Cloudflare and Fastly target sub-50ms p95 worldwide; Akamai is competitive on infrastructure-heavy traffic. Bandwidth pricing varies wildly: Cloudflare flat rate, AWS CloudFront tiered, Fastly per-GB. For high-volume video or large-asset use cases the bandwidth bill dwarfs the per-request cost.</p>
    <p><strong>Misconception block.</strong> Three things commonly confused at this tier. One: "A CDN automatically caches everything." False — the origin's response headers govern cacheability; without `Cache-Control: public` or equivalent, the edge passes through. Two: "Purging by URL clears the browser cache too." False — purges only affect the CDN; browsers use their own cache and you must use cache-busting URLs or rely on TTL expiry. Three: "More PoPs always means better performance." False — a PoP your ISP doesn't peer with locally adds latency, not removes it.</p>
    <p><strong>Cache hierarchy in a browser-to-edge request.</strong> When the browser issues a request, four caches may answer: (1) The browser's own memory cache (sub-millisecond hits, lasts the tab session). (2) The browser's disk cache (~10 ms, persists across tabs). (3) The CDN's edge POP cache (~20-50 ms over the network). (4) The CDN's origin-shield or regional cache (~50-100 ms). Only if all four miss does the origin server actually serve the request (~100-300 ms depending on geography). Each layer obeys the same `Cache-Control` directives but has its own TTL discipline; the `s-maxage` directive applies only to shared caches (CDN, proxy) and overrides `max-age` there. The browser respects `max-age` and `private`, ignores `s-maxage`. Understanding this layering is essential when debugging "why does the change not show up?" — you may be looking at any of the four caches, each with its own staleness.</p>
    <p><strong>HTTP/2 push, 103 Early Hints, and preconnect.</strong> An edge with no awareness of the origin response cannot ship resources early. Tooling to help: `103 Early Hints` (informational status, RFC 8297) sent before the final response carrying `Link: </style.css>; rel=preload` so the browser starts fetching critical assets while origin generates HTML. `<link rel="preconnect">` in HTML tells the browser to open TCP+TLS to other origins before they are needed (saves the handshake from being on the critical path). Both work even when CDNs are in the middle, because edges forward the hints intact. Modern best practice: use 103 + preconnect for critical render path, skip Server Push entirely.</p>
    <p><strong>Image and video delivery.</strong> Images are typically 50-80% of total page bytes; CDNs optimise hard. Format negotiation: send WebP/AVIF to capable browsers (Accept: image/avif), fallback to JPEG; CDN's image-optimisation feature handles transcoding on-the-fly with caching of variants. Responsive images: `srcset` lets the browser pick the right resolution; CDN resizes once per resolution and caches. Video: HLS (HTTP Live Streaming) and DASH chunk video into small segments delivered over HTTP — CDN caches segments aggressively (each is a static asset with content hash). Multi-bitrate manifests let the player switch quality based on bandwidth.</p>
    <p><strong>Geo-routing nuances.</strong> Anycast picks the BGP-shortest POP, not always the latency-shortest. GeoDNS picks based on the resolver's IP, not the user's IP — a user in Toronto using 8.8.8.8 may be routed to whichever PoP Google's resolver appears to come from (often Mountain View, suboptimal). EDNS Client Subnet (covered in 04-dns) sharpens this when the resolver opts in, at the cost of advertising the user's subnet upstream. Apple and Cloudflare's "1.1.1.1 for Families" disable ECS for privacy, accepting suboptimal routing. The right CDN choice depends on whether your users' ISPs peer with the CDN locally — for large operators (Cloudflare, Akamai) almost any ISP does; smaller CDNs may have geographic blind spots.</p>
    <p><strong>Origin selection and failover.</strong> Modern CDNs let you configure multiple origin servers with health checks and failover policies. Active-passive: edge sends traffic to primary, failover to standby on health-check failure. Active-active: edge round-robins or geo-routes between live origins. Health check parameters: HTTP path (typically `/_health`), expected response code (200), interval (30-60 s), failure threshold (3 consecutive failures = unhealthy). When all origins are unhealthy, fallback options: serve stale-if-error from cache, return a maintenance page, return 503 with `Retry-After`. The choice is configurable per route — your e-commerce checkout might fail loudly with 503 while the marketing homepage degrades gracefully to a static cached page.</p>
    <p><strong>Cache poisoning attacks.</strong> An attacker submits a request crafted to make the origin return a malicious response, which the CDN then caches and serves to other users. Common vectors: HTTP request smuggling (front-end and back-end disagree on request boundaries), header injection via unkeyed inputs (response varies on a header the CDN does not include in the cache key), parameter cloaking (request differs in a way the CDN does not see). Mitigation: keep CDN and origin tightly aligned on request parsing, use cache-key normalisation (strip non-significant query params), disable response variation on user-controlled headers unless explicitly in Vary. James Kettle's research at PortSwigger documents the live attacks.</p>
    <p><strong>Cost models.</strong> CDN pricing varies widely. Cloudflare: flat rate per plan, unlimited bandwidth (within fair-use). Fastly: per-GB egress + per-request. AWS CloudFront: tiered per-GB egress + per-request, regionally priced. Akamai: enterprise contract, usually per-GB + features. For a small site (10 TB/month), Cloudflare's free or Pro plan is fine. For 100+ TB/month or specialized features (DDoS protection at high scale, WAF rules, image optimisation), enterprise pricing kicks in and the bill is meaningful. Bandwidth tends to dominate; per-request costs matter for high-cardinality dynamic content.</p>
    <p><strong>CDN-native compute.</strong> Beyond static-asset delivery, every modern CDN offers code-at-edge. Cloudflare Workers (V8 isolate model, KV/D1/R2 storage tiers), Fastly Compute@Edge (WebAssembly), AWS Lambda@Edge (Node/Python runtimes), Vercel/Netlify edge functions (similar V8 model). These run per-request with millisecond cold start and let you customise routing, auth, A/B test selection, and dynamic-content composition. The selling point: zero infrastructure to manage, global deployment, low latency. The pitfall: vendor lock-in plus compute models differ enough that porting is non-trivial.</p>

  <Fragment slot="senior">
    <p><strong>Anycast and smart routing layering.</strong> Anycast is simple but suboptimal. BGP selects by hop count, not latency. Two cities 10 hops away via optimal backbone might measure worse by BGP metrics. Cloudflare Argo and AWS Global Accelerator add a smart layer: measure actual latency via probes, then use a private backbone (not the public internet) to route requests to the lowest-latency POP regardless of BGP. This can save 50+ ms on inter-continental hops.</p>
    <p><strong>Cache keys and Vary header semantics.</strong> The cache key is built from: URL (required), method (GET vs POST), Host header, and headers listed in `Vary`. If a response carries `Vary: Accept-Encoding, Accept-Language`, the cache creates separate entries for [URL + gzip], [URL + brotli], [URL + en], [URL + ru]. When a request arrives, the cache matches URL + method + Vary-listed headers. A missing Vary header means subsequent requests with different Accept-Language get the first response regardless. RFC 7234 § 4.1 formalizes this; it's a silent footgun.</p>
    <p><strong>Cookies and cache poisoning.</strong> Cookies are NOT included in the cache key by default. If an endpoint reads a session cookie and returns personalized content, a missing `Vary: Cookie` or `Cache-Control: private` means one user's response can serve to another. This is a real vulnerability: developer forgets to mark `/account` as private; first user logs in, hits the cache; second user (with no cookie) gets the first user's account page. Solution: either `private` (no CDN cache) or `Vary: Set-Cookie` plus a unique identifier in the cookie that becomes part of the key.</p>
    <p><strong>Stale-while-revalidate (SWR).</strong> After a cached response expires, the next request would cause a cache miss (round-trip to origin). SWR flips this: serve the stale response immediately, then refresh it in the background. Users get fast loads even after expiry; staleness window is `max-age + stale-while-revalidate`. For a news feed (max-age=60, SWR=604800), users can fetch a 10-day-old cache, which hits within milliseconds, while the CDN refreshes in the background. Great for availability; not for correctness-critical data.</p>
    <p><strong>Cache tags and surrogate invalidation.</strong> Fastly and Cloudflare Enterprise support cache tags: the origin assigns tags to responses (e.g., `Cache-Tag: user:42, article:1001`). Later, a single API call (`PURGE tag user:42`) invalidates all cached responses tagged with `user:42` without touching others. This beats URL purging (which requires knowing every URL) and beats time-based expiry (which forces stale data). Origin shield becomes critical here: without it, a large invalidation (e.g., popular user's post updated) causes a thundering herd of origin hits as all edges request fresh data simultaneously.</p>
    <p><strong>Edge workers and compute.</strong> Modern CDNs (Cloudflare Workers, Fastly Compute, AWS Lambda@Edge) run code at the edge — V8 isolates with ~5 ms cold start. Transform requests (add headers, merge microservices, A/B test variants), compose responses (ESI — Edge Side Includes, or dynamic fragments), or decide cache strategy on the fly. Worker cold starts are negligible; the latency win over a 200 ms round-trip to origin dwarfs the startup cost.</p>
    <p><strong>TLS resumption and session state at the edge.</strong> A new TLS connection costs 1 RTT. Session resumption (via session tickets or TLS 1.3 pre-shared keys) amortizes this. Modern CDNs generate tickets at one edge POP and replicate them across the network — if Bea's connection was interrupted and she reconnects via a different POP, that POP already has her ticket, skipping re-handshake. The payoff is massive on mobile (frequent reconnects).</p>
    <p><strong>P95/P99 SLO math for edge latency.</strong> Edge latency dominates user-perceived performance. Cloudflare's published p50 edge response time is ~10–30 ms worldwide; p95 is ~40–60 ms; p99 hits 100–200 ms on long-tail routes. For an SLO of "p99 page load &lt; 1 s" you have a budget you must split across DNS, TCP, TLS, edge, origin, render. Edge usually consumes 20–50 ms of that p99 budget. If your p99 spikes to 500 ms it usually means an unhealthy POP somewhere in your provider's network — open a ticket with reproduction trace. Operators alarm on edge p99 by region to catch regional regressions before users notice them.</p>
    <p><strong>Cache stampede / thundering herd.</strong> A cached resource expires. Many edges simultaneously request the new version from origin. Origin sees 100x normal traffic; some of those requests time out, cache stores error responses, more retries hit origin. Solutions: (1) Origin shield (already covered) consolidates the stampede to one origin request per region. (2) `stale-while-revalidate` lets edges serve stale while a single edge refreshes in background. (3) Probabilistic early expiration (e.g. PER algorithm) makes some edges refresh slightly before TTL expiry to spread the load. (4) Application-level singleflight pattern at origin coalesces concurrent requests for the same key into one upstream computation.</p>
    <p><strong>Edge worker isolates and cold-start economics.</strong> Cloudflare Workers run on V8 isolates: cold start ~5 ms; memory limited (typically 128 MiB); CPU bounded by 50ms wall-time. Compared to Lambda@Edge (200+ ms cold start) Workers' isolate model lets one process host thousands of customers' code. Cost: tens of microseconds of isolation per request. Use cases: A/B testing variant selection, URL rewriting, JWT validation, geo-redirect, custom auth at edge, dynamic asset transformation. Caveat: long-running compute (image resizing, ML inference) is not a fit for the 50ms wall-time budget — those run at regional compute tiers (CF Workers Unbound, Lambda@Edge).</p>
    <p><strong>ESI and edge-side composition.</strong> Edge Side Includes (W3C draft 2001, still in use at Akamai) let HTML responses contain placeholders that the edge fills with cached fragments. Each fragment has its own cache key and TTL. The shared chrome (header, footer, nav) caches for hours; per-user fragments cache for seconds. Modern reincarnations: Cloudflare Workers + HTMLRewriter API, Fastly Compute@Edge with ESI tags, Vercel's React Server Components on Edge Runtime. The unifying idea: assemble HTML at edge from independently-cached pieces.</p>
    <p><strong>WAF and bot management at edge.</strong> Beyond caching, CDNs sit in the request path and can inspect, block, or mutate. Web Application Firewall (WAF) matches request signatures against rule sets (OWASP Top 10, custom). Bot management uses JA3/JA4 TLS fingerprints, behavioural analytics, and machine learning to distinguish humans from automated traffic. Rate limiting per IP / per token at edge. DDoS scrubbing at edge stops volumetric attacks before reaching origin. Operators run all four in front of origin even when caching is light — the CDN is the cheapest defence layer.</p>
    <p><strong>Multi-CDN strategies.</strong> Large operators (Netflix, Apple, large news sites) front their traffic with two or more CDNs simultaneously, steering traffic via DNS or via real-user-monitoring measurements. The goals: vendor resilience (one CDN outage doesn't kill the site), regional optimisation (one CDN faster in Asia, another in EU), commercial leverage. Tooling like NS1 Pulsar or Cedexis aggregates RUM data and steers DNS in real time. Cost: operational complexity — purges, headers, edge-worker code must work on every CDN.</p>
    <p><strong>BGP-level optimisations: Argo and Global Accelerator.</strong> Anycast picks the BGP-closest POP, not the latency-closest. Cloudflare Argo Smart Routing and AWS Global Accelerator measure actual end-to-end latency from many POPs to many origins and route via a private backbone instead of the public Internet. Typical savings: 30-50% reduction in p95 latency on intercontinental paths. Cost: per-GB premium pricing for traffic that traverses the private backbone. Worth it for latency-sensitive APIs; overkill for static-asset delivery where BGP is already good enough.</p>
    <p><strong>Origin connection management.</strong> Edges keep long-lived HTTP/2 connections to the origin for connection reuse — opening a new TCP+TLS connection per request would amplify the origin's CPU and the perceived latency. Pool size matters: too few connections and edges queue waiting; too many and origin's open-file-descriptor limit hits. Operators tune via `Keep-Alive` directives and CDN-side origin-pool sizing. mTLS between edge and origin (client cert from CDN, validated by origin) protects against origin-IP exposure: even if attacker discovers origin IP, requests without the CDN's cert get refused.</p>
    <p><strong>Failure modes and graceful degradation.</strong> When origin is down or slow, what does the edge serve? Options: serve last-known-good cached version (stale-if-error directive, RFC 5861), serve a maintenance page, fall back to a different origin. CDN-side "origin pool" with health checks routes traffic to a healthy origin; if all origins are down, the cache-tier serves stale or the WAF returns a friendly 503. Designing the degradation explicitly beats letting the timeout cascade reach the user as a generic browser error.</p>
    <p><strong>Observability for CDN deployments.</strong> Key metrics: cache hit rate per URL prefix (target &gt; 90% for static, &gt; 70% for HTML, depends on per-route TTL), p95/p99 edge response time per region, origin-shield offload ratio (% of edge misses absorbed by shield without reaching origin), Vary-key cardinality (how fragmented the cache is — too high = poor hit rate), WAF block rate, bot score distribution. CDN dashboards expose these; for SLOs, export to your own Prometheus/OTel stack.</p>
    <p><strong>Real-User Monitoring (RUM) at edge.</strong> Beyond synthetic probes, CDNs collect per-request beacons from the browser (Performance API, Web Vitals) reporting Time-to-First-Byte, Largest Contentful Paint, Cumulative Layout Shift, First Input Delay. These ride on top of CDN telemetry and feed into multi-CDN steering decisions. Operators look at p75 LCP per geography to spot regional regressions even when synthetic probes from your own monitoring infrastructure look healthy. The cost: a few hundred bytes per page-view in beacon traffic, usually batched and sent on page-unload.</p>

As <SpiralCue thread="latency" lang="en" /> — reducing response time — becomes a competitive advantage, engineers tune cache strategies obsessively. High hit ratios (95%+) mean most requests never reach the origin. Low TTLs (60 seconds) keep data fresh but increase origin load. The balance is a dial you turn per endpoint.

CDNs are not free. Storage at 300 POPs is expensive. Synchronizing content across the world is operationally complex. But the latency win (10 ms instead of 250 ms) justifies the cost for any site that serves global users. Static assets (images, CSS, JS) are the easiest wins — cache them aggressively, distribute globally, let the CDN do the work. Dynamic content (APIs, personalized pages) requires more care: cache what you can, invalidate strategically, and understand the trade-off between stale data and origin load.

<KeyTakeaway>
A CDN turns "the server is 250 ms away" into "the server is 20 ms away" by replicating content to hundreds of edge POPs and routing each user to the nearest via Anycast or GeoDNS. The interesting layer is cache configuration — Cache-Control TTLs, Vary header keying, surgical purges via cache-tags, edge-side composition for partially-cacheable pages, and stale-while-revalidate for graceful misses. Most CDN-related production incidents trace back to one of three causes: missing Vary (cache poisoning across users), wrong Vary (cache fragmenting per User-Agent), or the deploy pipeline not purging on origin updates.
</KeyTakeaway>
