The OWASP top-ten (<a href="/en/security/01-owasp-modern/">01-owasp-modern</a>) tells you which attacks to block. OAuth and OpenID Connect tell you how to let users delegate access without handing over passwords. Done wrong, they leak tokens that work for months. Done right, they are the single most important auth standard on the modern web.

<Crux>How to let one app act on a user's behalf in another app without ever seeing the password — and without leaking the access.</Crux>

OAuth 2.1 is a 2025 consolidation of OAuth 2.0 plus a decade of security errata. It mandates PKCE for every flow, kills the implicit flow, requires exact-match redirect URIs, and forces refresh token rotation. OpenID Connect adds an identity layer on top: an ID token that says who the user is. Together they cover three jobs: authorize a third-party app, mint short-lived access tokens to a resource API, and prove the user's identity. Production systems get them wrong all the time; the senior engineer's job is to know exactly where the safety gates sit.

    <p><strong>What OAuth does in one sentence.</strong> Lets you grant an app limited access to your account on another service without handing over your password.</p>
    <p><strong>Why care.</strong> Without it, every app you connect to your account knows your full password — and one leak compromises everything.</p>
    <p><strong>The metaphor.</strong> You hire a dog walker. You do not give them your house key. Instead you go to a key kiosk (the identity provider), tell it "Frank needs to walk the dog Tuesdays 9-10am", and the kiosk prints Frank a single-use card that opens only the back gate, only on Tuesday, only for one hour. Frank loses the card — no problem, you just tell the kiosk to revoke it. The kiosk is the OAuth authorization server. The card is the access token. The back gate is the resource API.</p>
    <p><strong>Bea, Cara, Sven.</strong> <PersonaTag id="bea" lang="en" /> the browser wants to let "PrintPic" upload photos to her Google Drive. PrintPic asks the user to log in. Bea clicks "Sign in with Google", goes to <PersonaTag id="cara" lang="en" /> the identity provider, types her Google password (never seen by PrintPic), grants permission. Cara hands PrintPic a short-lived access token. PrintPic uses that token to talk to <PersonaTag id="sven" lang="en" /> the Google Drive API. Sven checks the token with Cara, sees it allows uploads but not reading other files, and lets PrintPic write. Bea's password never left Google.</p>
    <p><strong>One scenario.</strong> "Sign in with Google" on any website. You click. The site redirects you to Google. You log in (or are already logged in). Google asks "let this site know your name + email?". You consent. Google redirects you back with a code. The site swaps the code for an access token (which authorizes API calls) and an ID token (which proves you are you). You are now signed in without giving the site your Google password.</p>

  <Fragment slot="middle">
    <p><strong>OAuth 2.1 is a framework, not a single protocol.</strong> The OAuth 2.1 specification (consolidated draft, expected RFC by 2026) replaces OAuth 2.0 plus six security errata into one document. It defines an authorization framework with multiple "grant types" — interaction shapes that produce tokens. The four grants used in 2026: <em>authorization code with PKCE</em> (the only one for user-facing apps, mandatory PKCE for everyone), <em>client credentials</em> (service-to-service, no user), <em>device code</em> (smart TVs and CLI tools), and <em>refresh token</em> (renew an access token without re-prompting the user). The implicit grant and the resource-owner password grant are formally dead under 2.1 — implementations that still ship them are insecure by definition.</p>
    <p><strong>Authorization code with PKCE: the flow that matters.</strong> The user clicks "Sign in with Provider" in app A. A generates a random <em>code_verifier</em> (43-128 chars, cryptographically random), computes <em>code_challenge = SHA-256(code_verifier)</em>, and redirects the browser to the authorization server's <code>/authorize</code> endpoint with parameters: client_id, redirect_uri (must exactly match a pre-registered URI), response_type=code, scope, state (random per-request anti-CSRF token), nonce (random per-request anti-replay token for OIDC), and code_challenge plus code_challenge_method=S256. The user authenticates at the authorization server, consents to the requested scopes, and the server redirects back to the app's redirect_uri with a one-time code plus the state. App A's server then calls the <code>/token</code> endpoint with the code, client_id, client_secret (for confidential clients) or just client_id (for public clients), redirect_uri, and crucially the original code_verifier. The authorization server hashes the verifier, compares to the stored challenge, and only mints tokens on match. This is the PKCE check: an attacker who intercepts the code cannot redeem it because they do not have the verifier.</p>
    <p><strong>What you get back from the token endpoint.</strong> A successful token response contains: <em>access_token</em> (an opaque string or JWT; the credential to send to APIs in the <code>Authorization: Bearer</code> header), <em>token_type</em> (almost always "Bearer", or "DPoP" if using DPoP), <em>expires_in</em> (access token TTL in seconds, typically 300-3600), <em>refresh_token</em> (long-lived credential to renew the access token), <em>scope</em> (the granted permissions, which may be narrower than requested), and for OpenID Connect flows, <em>id_token</em> (always a JWT with claims like sub, iss, aud, exp, iat, auth_time, nonce, and user profile fields). The application validates the id_token signature against the issuer's <code>/.well-known/jwks.json</code> public keys, confirms iss matches the expected issuer, aud matches its client_id, exp is in the future, iat is in the past, and nonce matches what it sent — only then is the user signed in.</p>
    <p><strong>Refresh token rotation.</strong> OAuth 2.1 requires that every refresh-token use issues a fresh refresh token and invalidates the old one. The client must store and use the new refresh token; presenting the old one after rotation triggers a "replay detected" response, and the authorization server is required to revoke the entire refresh-token chain. This catches the case where an attacker has stolen a refresh token: as soon as either the attacker or the legitimate client uses it after rotation, the other one fails, and the server invalidates both. Without rotation, a stolen refresh token works until its absolute expiry — often weeks or months. With rotation, the window is the rotation interval, typically minutes.</p>
    <p><strong>OpenID Connect: identity on top of OAuth.</strong> OAuth answers "can this app do thing X on behalf of the user?". OIDC answers "who is the user?". The mechanism: alongside the access token, the authorization server returns an id_token — a JWT with claims about the user — signed by the IdP's private key. The application validates the signature using the IdP's JWKS (a public key set, fetched from <code>/.well-known/jwks.json</code> and cached). The minimum validation set: signature (using the kid header to pick the right key from JWKS), iss (must match expected issuer), aud (must contain client_id), exp (must be in the future), iat (must be in the past, with clock-skew tolerance of ~5 minutes), and nonce (must match what was sent in the authorize request). Skipping any of these is a CVE waiting to happen.</p>
    <p><strong>The redirect_uri exact-match rule.</strong> OAuth 2.1 requires the redirect_uri in the token request to match a pre-registered URI exactly — no wildcards, no path prefixes, no partial matches. Why so strict? Open redirect vulnerabilities. If the authorization server accepted any URI under your domain as a redirect, an attacker could trick it into redirecting the code to <code>https://yourapp.com/blog/comments/?next=https://attacker.com</code> — depending on your blog comment system, the code might end up in the attacker's server logs. The exact-match rule shuts this down: the URI must equal one of the strings you registered. For native apps, where you cannot reliably register a URL (deep links, custom schemes), OAuth 2.1 plus RFC 8252 require either a loopback URL (http://127.0.0.1:RANDOM_PORT) or a private-use URI scheme registered with the OS.</p>
    <p><strong>State and nonce: two separate anti-attack tokens.</strong> The state parameter is OAuth's anti-CSRF: the client generates random state at /authorize, the server echoes it back at the redirect, the client confirms it matches. Without state, an attacker can craft a malicious /authorize URL with their own redirect_uri-and-code, send it to a victim, and on click the victim's browser silently completes the flow in the attacker's account. The nonce parameter is OIDC's anti-replay: the client generates random nonce at /authorize, the IdP echoes it inside the id_token, the client confirms match. Without nonce, an attacker who captures an id_token over an unrelated channel can replay it at the application. Both are random per-request, both are validated server-side, neither is optional in modern flows.</p>
    <p><strong>Where access tokens go and how.</strong> The standard is the <code>Authorization: Bearer eyJhbGciOi...</code> HTTP header, present on every API request. The resource server validates the token: either via <em>introspection</em> (calling the IdP's <code>/oauth/introspect</code> endpoint, the trust-but-verify model) or via <em>local JWT validation</em> (the token is a signed JWT and the resource server validates the signature using JWKS, scalable but stales). The choice is operational: introspection is real-time (knows about revocations immediately) but adds latency per request; local JWT validation is fast (microseconds) but cannot see revocations until expiry. Most production systems compromise: local JWT validation for the hot path, periodic JWKS refresh, short-lived access tokens (15 min to 1 hour) so revocations propagate within that window.</p>
    <p><strong>Scopes and least privilege.</strong> Every access token carries a scope claim — the permissions granted at consent time. The application requests a scope set at /authorize; the user sees the consent screen and either approves all or denies. Production design forces granular scopes: read:photos, write:photos, read:profile, instead of one super-scope. Why? Two reasons. First, user trust: a photo-printing app asking for read:photos is reasonable; the same app asking for full account access is not, and users decline. Second, blast radius: if the app is compromised, attackers can only do what the granted scopes allow. Industry pattern: read scopes are freely granted, write scopes require explicit per-action consent, admin scopes never appear in third-party flows. OAuth 2.1 plus dynamic-scope extensions (RFC 9396 — Rich Authorization Requests) let the client request fine-grained permissions like "transfer up to $500 to account X" instead of just "write:transfers".</p>
    <p><strong>Client registration and dynamic client metadata.</strong> Before an app can do OAuth, it must register with the IdP and receive a client_id (and client_secret for confidential clients). Static registration is the legacy default: developer fills a form at the IdP's console, gets credentials, embeds them in the app. Dynamic Client Registration (RFC 7591) lets the IdP accept JSON requests with client metadata (redirect_uris, grant_types, contacts, software_id, software_version) and return fresh credentials. Modern IdPs combine: static config for known apps, dynamic for mobile/IoT where each device installation is a separate client. Federations (educational identity providers, government SSO) use Dynamic Client Registration via Federation API (OpenID Federation) so an app can join hundreds of IdPs without manual registration at each.</p>
    <p><strong>Multi-factor authentication inside OAuth.</strong> Modern IdPs transparently integrate MFA: when the user logs in at /authorize, the IdP separately decides whether a second factor is required (TOTP, SMS, push notification in an authenticator app, passkey/WebAuthn). From the OAuth flow's perspective, the application does not see this — it just receives an id_token with an acr (Authentication Context Class Reference) or amr (Authentication Methods References) claim describing the factors used. The application can require a specific acr via the acr_values parameter at /authorize. The IdP either satisfies it (prompting MFA if needed) or returns an error. This lets sensitive endpoints (transfer, delete-account) require step-up authentication — the user is already logged in with a password, but on attempting a transfer the IdP raises an MFA-challenge and only issues an elevated token on success.</p>
    <p><strong>Logout and session termination.</strong> OAuth alone does not define logout; OIDC adds two flows. <em>RP-Initiated Logout</em>: the application redirects the browser to the IdP's /endsession endpoint with the id_token_hint, and the IdP terminates its session and redirects back to a post_logout_redirect_uri. <em>Front-Channel Logout</em>: the IdP includes &lt;iframe&gt;s pointing to each app's logout URI in its logout page, so all apps clear local sessions in parallel. <em>Back-Channel Logout</em>: the IdP POSTs a signed logout_token to each app's back-channel-logout-URI; the app validates the signature and invalidates the session in its DB. Back-channel is the only logout that works when the browser is closed; production systems combine front-channel for active sessions and back-channel for durable cleanup.</p>

    <Misconception id="mc-bearer-token">
      <p><strong>"Access tokens are encrypted, so they're safe to log."</strong> No. Access tokens are typically signed (JWT), not encrypted — anyone with the token can use it as the bearer. Logging tokens in nginx, CloudWatch, or Sentry leaks them to anyone with log access. Never log Authorization headers.</p>

    <p><strong>Bearer tokens are the legacy default; sender-constrained tokens are the future.</strong> A bearer access token is exactly what the name says: anyone who holds it can present it and the server accepts it. Theft equals compromise. Two RFCs fix this. RFC 8705 (mTLS-bound tokens) binds the access token to a specific X.509 client certificate — the resource server verifies the TLS-presented client cert matches the cnf (confirmation) claim in the token, and rejects if they differ. RFC 9449 (DPoP — Demonstrating Proof of Possession) binds the token to a client-controlled key pair without needing TLS client certs — every API request includes a DPoP proof JWT signed by the client's private key, with the access token's hash inside. Stolen tokens are useless without the corresponding private key. FAPI 2.0 (the OpenID Foundation's open-banking profile) requires sender-constrained tokens via either mTLS or DPoP; for any high-value workload in 2026 (banking, healthcare, regulated AI agents), DPoP is the practical choice because it works for browser SPAs and mobile apps where mTLS does not.</p>
    <p><strong>DPoP wire shape.</strong> When the client makes a token-protected API call, it computes a DPoP proof JWT in the <code>DPoP</code> HTTP header. The proof's payload contains: jti (random unique id, server caches to detect replays), htm (HTTP method, e.g. POST), htu (HTTP target URI, e.g. https://api.example.com/v1/transfer), iat (issued-at timestamp), and ath (SHA-256 of the access_token, ensuring the proof is bound to this specific token). The proof's header includes the public key (jwk) used to sign it. The resource server validates: signature with the proof's embedded jwk, ath equals SHA-256 of the incoming bearer access token, htm and htu match the actual request, iat within an acceptable window (typically 60s), and jti not seen recently (anti-replay cache, typically 5-10 minute window). The access token itself contains a cnf claim with a jkt (JWK thumbprint) — the proof's jwk must hash to that jkt. A stolen token without the private key cannot generate a valid proof; the API call is rejected.</p>
    <p><strong>PAR and JAR: hardening the authorize request.</strong> Pushed Authorization Requests (RFC 9126) lets the client POST the authorize parameters to a /par endpoint over a TLS-authenticated back channel, receiving a short-lived request_uri. The client then redirects the browser to /authorize with just that request_uri — no parameters in the URL. This moves the entire request out of browser-visible URLs (no leakage in browser history, referrers, or screenshots) and lets the auth server enforce the request integrity before the user-agent even gets involved. JAR (RFC 9101) similarly lets the client sign and encrypt the request as a JWT; the auth server validates the signature before processing. Together PAR + JAR are required by FAPI 2.0 and by GAIN-Trust frameworks for regulated identity flows. Standard consumer OAuth typically skips them; banking, healthcare, and government implementations require them.</p>
    <p><strong>The OIDC discovery and metadata flow.</strong> Modern OIDC clients do not hard-code endpoints. They fetch <code>https://issuer.example.com/.well-known/openid-configuration</code> (RFC 8414) at startup, which returns a JSON document listing /authorize, /token, /userinfo, /jwks_uri, /revocation, /introspection, /registration, plus the supported response_types, scopes, claims, code_challenge_methods, dpop_signing_alg_values_supported, and so on. The client uses these to drive flows dynamically. JWKS at /jwks_uri returns the active public keys; clients cache and refresh on rotation events. The kid header in the id_token tells which key to use. For multi-tenant SaaS (Auth0, Okta, Azure AD), the issuer URL includes the tenant ID, so each tenant has its own metadata and JWKS. Production discipline: cache .well-known and JWKS for 5-15 minutes, refresh on signature-validation miss, and pre-warm caches before known IdP rotation events if the IdP publishes them.</p>
    <p><strong>Token introspection vs JWT validation: the real tradeoff.</strong> Opaque tokens require the resource server to call /introspect (or /tokeninfo) at the IdP on every API request — strong consistency on revocation, costs one extra round trip per request. JWT tokens require only local cryptographic validation on the resource server — fast, scales to millions of RPS, but a revoked JWT keeps working until expiry. Production systems pick by throughput need: high-RPS APIs use short-lived JWTs (5-15 min expiry) + JWKS rotation, accepting that revocation propagates within the expiry window. Sensitive APIs (transfer, delete-account) layer introspection on top of JWT validation for the writes, keeping read paths fast. A small server cache of "recently introspected tokens" amortises the introspection cost: introspect once per 30 seconds, cache the result, fall back to expiry when the cache says "active".</p>
    <p><strong>Audience attacks and the cnf-claim pattern.</strong> When the same auth server issues tokens for multiple resource servers (API A and API B), an attacker can sometimes trick API B into accepting a token issued for API A. The defense is the aud claim — the resource server MUST validate the token's aud contains its own identifier. Some auth servers omit aud or set it to a generic string, breaking this defense. RFC 8707 (Resource Indicators) lets the client request audience-specific tokens via the resource parameter at /token. cnf (confirmation) claim narrows the binding further: the token can only be used with the proof key in cnf.jkt. This is the formal name for what DPoP enforces — the token "confirms" it can only be used by the holder of the matching private key.</p>
    <p><strong>Real production failures.</strong> Facebook September 2018: an access-token-leak vulnerability in the "View As" feature exposed 50M access tokens; attackers could log in as any of those users at any Facebook OAuth client (Spotify, Tinder, Instagram). Fix: invalidate 90M tokens. Slack February 2017: a misconfigured OAuth Redirect URI in a third-party Slack app let an attacker phish a workspace owner's auth code, escalating to full admin. GitHub Enterprise 2021: a bug in PKCE verification allowed downgrade attacks against older clients; fixed in patch release. Microsoft Azure AD November 2024: token-validation cache poisoning let a crafted token bypass aud validation for ~30 minutes on cached negative responses; fixed within hours. The pattern across all four: implementations missed one of the standard mandatory checks, or had a tiny logic bug in a check, and the impact was full account takeover or token replay.</p>
    <p><strong>Production observability for OAuth flows.</strong> Minimum viable dashboard exposes: authorize_request_total by client_id and response_type, token_request_total by grant_type and outcome (success / invalid_grant / invalid_client / invalid_scope), token_introspection_latency_p99, jwks_cache_hit_ratio, id_token_validation_failure_total by failure_reason (sig / iss / aud / nonce / exp / iat), refresh_replay_detected_total (a non-zero rate is a probable compromise indicator), and dpop_proof_failure_total by reason. Alert on refresh_replay_detected_total above zero, on id_token_validation_failure_total spikes (often a JWKS cache miss storm during rotation), and on token_introspection latency above 200ms p99 (the IdP is overloaded). Audit log every consent grant + revoke event; sign and timestamp them for regulatory retention.</p>
    <p><strong>History: OAuth 1.0 to OAuth 2.1.</strong> OAuth 1.0 (RFC 5849, 2010) used per-request HMAC signatures, secure but operationally painful. OAuth 2.0 (RFC 6749, 2012) traded signatures for TLS plus bearer tokens, dramatically simpler but at the cost of every-misconfig-is-a-CVE. OAuth 2.0 errata accumulated (RFC 6750, 7521, 7636 PKCE, 8252 native apps, 8414 discovery, 8628 device code, 8705 mTLS, 9068 JWT access tokens, 9101 JAR, 9126 PAR, 9449 DPoP). OAuth 2.1 (draft 2023-2025, expected final 2026) consolidates the safety errata into one document: PKCE mandatory, implicit flow removed, password grant removed, exact redirect match required, refresh rotation required. OIDC 1.0 (2014, errata sets through 2024) adds the identity layer. FAPI 2.0 (final 2024) is the high-assurance profile for finance/health.</p>
    <p><strong>Cross-protocol interactions.</strong> SAML 2.0 still serves enterprise SSO where IT teams have invested in ADFS, Shibboleth, or Okta SAML. SAML and OIDC coexist via "IdP-initiated" and "SP-initiated" patterns; modern federation usually does OIDC for new apps and SAML for legacy. WebAuthn (FIDO2 passkeys) replaces the password at the front door of OAuth — the user authenticates to the IdP via a passkey, and the IdP still issues OAuth tokens to apps. SCIM (RFC 7644) provisions users into apps; OAuth authorizes the SCIM API itself. Combining OAuth + WebAuthn + SCIM is the modern enterprise stack: passkey-based primary auth, OAuth for app delegation, SCIM for lifecycle. mTLS for service-to-service; OAuth client_credentials grant for service-to-service when mTLS is unavailable.</p>
    <p><strong>Deployment patterns: SPAs vs native apps vs server-side.</strong> SPAs use authorization-code-with-PKCE, store access tokens in memory only (never localStorage), and refresh via short-lived rotating refresh tokens stored in httpOnly cookies. Native apps use authorization-code-with-PKCE with a private-use URI scheme or universal links for the redirect; store tokens in OS keychain. Server-side apps use authorization-code-with-PKCE (PKCE still required in 2.1) + client_secret, store tokens in the session, refresh via the backend. For machine-to-machine (CI/CD pipeline calling an API), use client_credentials grant; never embed user-tokens in CI. For CLI tools and IoT devices, use device-code flow — the device shows a code, the user enters it on a phone, the device polls for the token.</p>
    <p><strong>Token theft mitigations beyond rotation.</strong> Cookie security: httpOnly (no JS access), Secure (HTTPS only), SameSite=Lax or Strict (cross-site CSRF defense). Avoid storing access tokens in localStorage (XSS-readable) — keep them in memory. For mobile, OS keychain. For SPAs, the access token lives only in a closure or React state, never persisted; on page reload the SPA does a silent /authorize round (prompt=none) using the refresh token in the httpOnly cookie. Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy lock down popups used in OAuth flows to prevent <code>opener.postMessage</code> attacks. CSP (Content-Security-Policy) blocks accidental third-party script execution that could exfiltrate tokens. CORS (Cross-Origin Resource Sharing) restricts which origins can call your token endpoint with credentials.</p>
