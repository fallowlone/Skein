A page is data plus chrome. The chrome is fast — HTML, CSS, JS bundles cached at the CDN. The data is slow — a database query, an API call, a third-party integration. Where data fetching happens decides whether the user sees content in 200ms or 2000ms. Three answers: fetch on the server before rendering, fetch on the client after JS loads, or stream a hybrid. The wrong answer adds round-trips to LCP; the right answer hides them.

<Crux>Server fetch + stream = LCP under 1s. Client fetch after JS = LCP over 3s. Waterfalls kill; Promise.all cures.</Crux>

The mental model: every page has a critical path of network round-trips from "user clicks link" to "main content visible". On a pure client-rendered SPA, the path is HTML → JS bundle → React mount → fetch data → render — four sequential trips, easily 2-3 seconds on slow networks. On an SSR page, the path is server fetch (parallel) → HTML with data → browser paint — one effective round-trip if the server cleverly parallelises its own fetches. React Server Components push it further: the server streams content as it becomes available, so the user sees the page header in 200ms and the slow data-heavy section a moment later. The art is matching the rendering strategy to the data shape — known-at-request-time data on the server, user-interactive state on the client, with TanStack Query or SWR managing the client cache.

  <Fragment slot="middle">
    <p><strong>Where fetching can happen.</strong> Modern frameworks support four fetching locations, each with different LCP implications. <em>Build time</em> (static generation): data baked into HTML at build, zero per-request fetch cost, but stale until rebuild. Use for blog posts, marketing pages, anything that changes hourly or less. <em>Server-side at request time</em> (SSR or Server Components): fetch happens on the server while rendering the response. The HTML contains the data inline. One round-trip from browser to server. Used by Next.js getServerSideProps, RSC async components, Remix loaders. <em>Streaming server-side</em>: server starts sending HTML before all data is ready. Initial chunk has the layout shell; subsequent chunks contain data as it arrives. Implemented via React Suspense boundaries — each boundary is independently streamable. <em>Client-side after mount</em>: useEffect, useQuery, useSWR. The page mounts with no data; data arrives after JS runs and fetches kick off. Necessary for user-interactive flows (filters, real-time updates).</p>
    <p><strong>React Server Components (RSC).</strong> A React feature stable in React 19, default in Next.js 15's app router. RSC are components that render only on the server — they can be async functions, call databases directly, use any server-side library. The server renders them to a special "RSC Payload" (a serialized React tree) plus the initial HTML. The client receives the HTML for instant paint, then the RSC Payload for hydration. RSC do not ship their code to the client. Components are marked with 'use client' to opt into client-rendering (for interactivity, state, effects). The pattern: keep static and data-display components server-side; mark only interactive leaves as client components. Bundle size shrinks dramatically because the React component tree is no longer entirely shipped to the browser.</p>
    <p><strong>Suspense boundaries and streaming.</strong> React Suspense is the primitive for "show a fallback while this part of the tree is loading". On the server, a Suspense boundary lets the rest of the tree stream while the suspended part is still resolving. Client receives HTML chunks in order: first the layout shell with skeleton fallbacks, then each suspended chunk as its data resolves. Each chunk is a small piece of script that swaps the fallback for the real content. The benefit: TTFB drops to "however long the layout takes" (often under 100ms), and slow data sections do not block the rest of the page. Best practice: each independent data dependency gets its own Suspense boundary with a dimension-matched skeleton fallback so layout does not shift when content arrives.</p>
    <p><strong>Client-side caching: TanStack Query and SWR.</strong> Both libraries implement the same core pattern: a shared cache keyed by query key, with stale-while-revalidate semantics. <code>useQuery(['products', id], fetchProduct)</code> returns immediately with cached data if available, then re-fetches in the background; the UI re-renders when fresh data arrives. Cache lifetimes are tunable: <code>staleTime</code> controls how long data is considered fresh, <code>gcTime</code> (formerly cacheTime) controls how long unused data lingers before garbage collection. Both libraries deduplicate concurrent queries with the same key (single-flight pattern). Both support optimistic updates (apply mutation locally before server confirms; rollback on error). Sizes differ: SWR is ~5KB minified+gzipped, TanStack Query ~16KB but with DevTools, infinite queries, parallel mutations.</p>
    <p><strong>Optimistic updates.</strong> The pattern for write paths that should feel instant: when the user clicks "Like", update the local cache to show "Liked" immediately, fire the mutation to the server in parallel, rollback if the server rejects. TanStack Query's <code>onMutate</code> callback runs before the request; <code>onError</code> rolls back. The UI feels instant because the user never waits for the round-trip. Tradeoff: brief inconsistency if the server later rejects (e.g. rate-limited, validation error). For idempotent actions (like, bookmark, mark-read) this is virtually always worth it; for non-idempotent (transfer money, submit order), the optimistic UI is misleading and should be avoided.</p>
    <p><strong>Cache invalidation strategies.</strong> When a mutation succeeds, dependent queries must be refreshed. TanStack Query offers three approaches: <em>invalidate</em> (mark queries stale, refetch on next observer), <em>setQueryData</em> (write the new value directly into the cache), <em>refetch</em> (force an immediate fetch). The cheapest is setQueryData when the mutation response includes the new state. Invalidate is safer when multiple queries depend on the mutation. Refetch is reserved for cases where you need fresh data immediately and cannot trust the mutation response. Most production code uses a mix: setQueryData for the directly-mutated entity, invalidate for everything that lists it.</p>
    <p><strong>Request waterfalls in detail.</strong> The classic waterfall: component A fetches user data, then renders component B which fetches the user's posts, then renders component C which fetches comments on each post. Three sequential round-trips minimum. Total latency = A + B + C even though A's response was enough to know all three queries. Fix patterns: <em>parallel from above</em> — the parent fetches all three (via Promise.all or by orchestrating queries at a higher level). <em>data colocation</em> — restructure the API so one call returns all needed data. <em>prefetch</em> — start the next fetch before the user navigates, using the time the user spends reading the current page. <em>RSC parallel</em> — siblings in a server tree fetch concurrently by default. TanStack Query's <code>useQueries</code> hook runs multiple queries in parallel from one call.</p>
    <p><strong>SSR hydration and the dual-fetch trap.</strong> A common bug: server fetches the data, renders HTML, ships it; client hydrates by re-mounting the same components which then fetch the data again. Two fetches for one page load, wasted server time. The fix is dehydration/rehydration: the server fetches, serializes the cache state into a script tag in the HTML, the client TanStack Query/SWR reads that state on mount instead of re-fetching. <code>HydrationBoundary</code> in TanStack Query and the <code>fallback</code> prop in SWR are the API for this. RSC sidesteps this entirely — server components do not hydrate, so they cannot dual-fetch. Mixed RSC + client query setups need careful boundary placement.</p>
    <p><strong>LCP and the critical fetch.</strong> Largest Contentful Paint measures when the main content becomes visible. For a product page, the LCP element is usually the hero image or the product title. If the title is server-rendered, LCP is bound by HTML arrival time. If the title is client-fetched, LCP is bound by HTML + JS + fetch — typically 2-4x longer. Web Vitals targets: LCP under 2.5s for "good", under 1.5s for excellent. The single biggest LCP improvement most apps can make: move the LCP element's data fetching from client to server. <code>fetchpriority="high"</code> on the LCP image helps the browser prioritise its discovery; preload links for the LCP image's URL when known at build time push it earlier.</p>
    <p><strong>Race conditions in interactive fetching.</strong> The classic race: user types in a search box, each keystroke triggers a fetch, responses arrive out of order. The user types "rea" then "react". Server responds for "rea" after "react" due to slowness — UI shows "rea" results while the input shows "react". Fix patterns: AbortController to cancel in-flight on new query, response-tagging with the originating query to discard mismatched results, debounce so only the last keystroke fires a fetch. TanStack Query handles this via its queryKey mechanism: the response is associated with its key, the cache stores only the latest. Custom fetch code must implement one of these — silent failure mode otherwise.</p>
    <p><strong>Pagination and infinite scroll patterns.</strong> Three approaches. <em>Offset-based</em>: <code>?page=2&limit=20</code>. Simple but breaks under concurrent inserts (item shifts between pages). <em>Cursor-based</em>: <code>?cursor=abc123</code>. Stable across inserts because the cursor is a stable position marker (typically a sort-key value). <em>Keyset-based</em>: <code>?after_id=42&after_date=2026-05-13</code>. A specialised cursor encoding multiple sort keys. TanStack Query's <code>useInfiniteQuery</code> handles cursor-based natively, prefetching the next page when the user nears the bottom. The data shape impact: lists must use cursor pagination for correctness under churn; offset is acceptable only for static or rarely-mutated data.</p>
    <p><strong>Prefetch and prerender.</strong> Smart fetching can start work before the user explicitly navigates. <em>Hover prefetch</em>: when the cursor hovers over a link, start fetching the target page's data. By the time the user clicks (typically 100-300ms later), data is already in flight or done. <em>Viewport prefetch</em>: as a link scrolls into view, start prefetching. <em>Predictive prefetch</em>: ML-driven, observe past navigation patterns and prefetch likely next pages. Next.js Link prefetches by default; TanStack Query's prefetchQuery seeds the cache. Tradeoff: prefetching uses bandwidth speculatively; abuse it on mobile and you destroy data plans. Limit prefetch to next-likely targets and avoid prefetching large media.</p>

    <p><strong>RSC payload format: not HTML, not JSON.</strong> When React renders a Server Component, the output is a custom serialization called the RSC Payload — a compact representation of the React tree plus references to client components by their bundle URL. The browser receives the initial HTML (rendered from the RSC tree for fast paint) plus the RSC Payload (used to hydrate the React tree for subsequent navigations). The RSC Payload format is intentionally not JSON: it is a streaming-friendly format with row-prefix codes (M for module, J for JSON literal, etc) so React can begin processing before the full payload arrives. Each row references previous rows by ID, building up the tree incrementally. This allows the browser to render parts of the tree as the network delivers them. The format is documented in React's RFC repository; framework authors implement servers that emit it (Next.js, Waku, Remix), and clients (React DOM) that consume it.</p>
    <p><strong>Server Functions and the action protocol.</strong> Beyond Server Components, React 19 introduces Server Functions — async functions marked with <code>'use server'</code> that can be called from client components but execute on the server. They get a stable URL endpoint generated by the framework; the client-side call is a fetch that the framework routes to the function. Combined with form actions (<code>&lt;form action=&#123;serverFunc&#125;&gt;</code>), Server Functions replace most ad-hoc API routes. The benefit: type-safe across the boundary (TypeScript signature matches), no need to hand-define request/response shapes, framework handles serialization and progressive enhancement. Limitations: arguments must be serializable, secrets stay server-side (client never sees the function body, only invokes the endpoint), authentication/authorisation must be done explicitly inside the function.</p>
    <p><strong>Streaming hydration order.</strong> When the server streams HTML with Suspense boundaries, the browser builds the DOM progressively. React's selective hydration matches HTML chunks as they arrive: the layout shell hydrates first, then each Suspense child hydrates when its chunk is received. The selective part: if the user clicks a button before hydration of that section completes, React prioritises hydrating that section first (the click event is queued, then dispatched after hydration). This is "concurrent React" in practice — the framework juggles partial hydration, user input, and incoming server chunks. Production implication: a 200KB JS bundle that takes 800ms to parse on a phone can still feel snappy because the visible-and-clicked-on section hydrates before the rest. Implementations to read: React's <code>renderToReadableStream</code> on the server, <code>hydrateRoot</code> on the client.</p>
    <p><strong>Caching layers and their interactions.</strong> A modern app has many caches: CDN edge cache (URL-keyed, seconds-to-hours), server-side framework cache (Next.js fetch cache, RSC cache, route segment cache), database query cache (Redis, server memory), client HTTP cache (browser, controlled by Cache-Control), client library cache (TanStack Query, SWR, Apollo). A request can be served from any of them depending on the URL, mode, and freshness. The invalidation cascade: a mutation that changes data must invalidate the server caches (revalidate path), the CDN if applicable (cache-tag-based purge), and the client library (queryClient.invalidateQueries). Next.js 15's revalidate functions (revalidatePath, revalidateTag) handle server + CDN; the library cache is the developer's responsibility. Skipping any layer leaves the user staring at stale data.</p>
    <p><strong>Race conditions in client fetching.</strong> The classic race: user types in a search box, each keystroke triggers a fetch, responses arrive out of order. The user types "rea", server responds with results for "rea" (3 results). User types "react", server responds with results for "react" (50 results). User pauses typing on "react" — but the "react" response arrived before "rea" response due to server slowness. Now the UI shows "rea" results despite the input showing "react". Fix patterns: <em>abort in-flight on new query</em> (AbortController), <em>tag responses with the query that produced them</em> and discard mismatched, <em>debounce the input</em> so only the last keystroke fires a fetch. TanStack Query handles this via its queryKey mechanism: the response is associated with its key, the cache only stores the latest. SWR uses similar key-based versioning. React Query 5's <code>signal</code> support means cancellation is built-in. Custom fetch code must implement one of these.</p>
    <p><strong>Streaming protocols beyond HTTP/1.1.</strong> HTTP/1.1 chunked transfer encoding is the minimum requirement. HTTP/2 multiplexes streams over one connection so multiple Suspense chunks can interleave. HTTP/3 (QUIC) further improves head-of-line behaviour for slow networks. WebSockets push beyond request/response for subscription-style flows (chat, live dashboards). Server-Sent Events (SSE) is a one-way server-to-client stream useful for notifications, progress updates, AI chat completion. The choice between these depends on the data shape: HTTP for one-shot loads, SSE for one-way streams, WebSockets for bidirectional. Next.js 15 RSC streaming uses HTTP/1.1 chunked or HTTP/2 streams; the framework abstracts the choice.</p>
    <p><strong>Real production failures.</strong> Vercel 2024: a customer's RSC migration shipped a Server Component that fetched 50 items in a loop sequentially instead of with Promise.all — TTFB regressed from 100ms to 2.5s on the affected pages. Caught in production after observability dashboards flagged the regression; fixed by wrapping the fetches in Promise.all. Linear 2024: an SSE-based real-time sync used the wrong message ID scheme; on reconnect the client missed messages sent during the disconnect window, leading to "I dragged this card but it bounced back" complaints. Fixed with a server-assigned monotonic ID and client-side resume-from-last-id. The pattern: data-fetching bugs hide as UX papercuts that accumulate; serious analysis of "why does this feel slow / wrong" usually surfaces them.</p>
    <p><strong>Observability for data fetching.</strong> Minimum metrics: <code>fetch_duration_seconds</code> histogram by endpoint, <code>fetch_error_total</code> by endpoint + error_kind, <code>rsc_payload_size_bytes</code> by route, <code>cache_hit_ratio</code> by query key (client library), <code>web_vitals_lcp_seconds</code> p75 + p95 (RUM). Distributed tracing: every fetch carries a trace ID propagated through the framework; you can see a single user request's full waterfall from browser through framework through database. Alerts: LCP p75 regressing >20% in any 10-min window, fetch_error_rate above baseline, cache_hit_ratio dropping below historical norms (often signals an invalidation bug). The harder metric: time-to-first-meaningful-paint (TTFB → first Suspense chunk → LCP) — Next.js 15 exposes this in its built-in telemetry.</p>
    <p><strong>Edge runtime constraints.</strong> Many frameworks (Next.js, Cloudflare Workers, Vercel Edge) offer an "edge runtime" — a Node-compatible-ish environment running at CDN edges instead of in a central data center. Latency to the user is single-digit ms vs hundreds for traditional servers. Tradeoffs: limited APIs (no Node fs, no native bindings, smaller memory limits), Web-standard APIs only (fetch, crypto.subtle, URL). Edge is ideal for data-fetching that hits a globally-replicated source (Planetscale, FaunaDB, Cloudflare D1) and routes results back. Edge-rendered RSC is the bleeding-edge pattern in 2025-2026: server runs at the edge, data comes from a nearby replica, the user sees first paint in 50-100ms regardless of geography.</p>
    <p><strong>Service worker caching: the offline-first layer.</strong> A service worker can intercept fetches, serve from a local Cache API store, and update in the background. Stale-while-revalidate semantics at this layer give "second visit feels instant even on slow networks". Workbox is the standard library. Pitfall: stale service worker code can persist for hours after deploy if not configured for self-update; production deploys must include a service worker version bump. Service workers are essential for offline-capable apps (PWAs); for purely online apps, they are an optimization on top of HTTP caching. The cache lifecycle (install, activate, fetch) is a small state machine; getting the activation right (skipWaiting, clients.claim) is the most common service-worker bug source.</p>
    <p><strong>Hydration mismatches.</strong> When the server renders HTML and the client mounts the same React tree, the two must produce identical output. Any difference (date formatting using local timezone, random values, conditional content based on screen size) causes a hydration mismatch warning and silently breaks interactivity in production. Fix patterns: <em>useEffect for client-only logic</em> — render the safe initial state on both sides, mutate to client-specific state after mount. <em>suppressHydrationWarning</em> for known-divergent leaves (timestamps formatted with locale). <em>Client Components for genuinely interactive parts</em>. The hydration step is implicit in any SSR setup; mismatches happen quietly and accumulate. React 19's improved hydration error messages help; production teams add error-boundary monitoring (Sentry) to catch them before users notice.</p>
