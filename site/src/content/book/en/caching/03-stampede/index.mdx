A cache layer is supposed to absorb load. Invalidation (this chapter, 02) is supposed to keep it honest. But the moment a hot key expires under traffic, the cache stops absorbing — every concurrent request misses simultaneously and rushes the database. The database, which the cache was hiding, sees its full real load for the first time. This is the cache stampede: the failure mode where the cache itself is the weapon.

<Crux>One TTL expires. 10000 requests miss at once. The DB sees flash-DDoS from its own cache. Four fixes: lock, single-flight, XFetch, SWR.</Crux>

The shape is universal: any cache with a TTL plus enough concurrent traffic produces a stampede when that TTL fires. A blog homepage cached for 60s, 5000 RPS sustained — at second 60, all 5000 requests in that next second miss the cache and hit the renderer. The renderer was sized for 50 RPS (it relied on the cache). Database CPU goes vertical, p99 climbs, a few requests timeout, the timed-out requests retry, the retries multiply the herd, and the system enters a metastable failure where every TTL boundary is another outage. The cure is not "longer TTL" — that just shifts when. It is one of four mechanisms that ensures the rebuild work is done by a bounded number of callers, regardless of how many missed at the same moment.

    <p><strong>What stampede is in one sentence.</strong> A popular cached value expires; thousands of requests simultaneously miss and all try to rebuild it at the same instant, overloading whatever is behind the cache.</p>
    <p><strong>Why care.</strong> The whole point of the cache is to shield the slow thing behind it. If every expiry releases a herd, the cache makes the slow thing worse than no cache at all — because traffic is bursty instead of steady.</p>
    <p><strong>The metaphor.</strong> A bakery sells a fresh hot pie every five minutes. Without coordination, every customer in line places an independent order the instant the pie sells out — the lone baker is now juggling fifty orders for the next pie. The fix is not more pies; one customer takes the order and the rest wait, or the next pie starts baking before the current one sells out.</p>

  <Fragment slot="middle">
    <p><strong>The mechanics of the herd.</strong> Caches in front of databases (Redis, memcache), of computed results (image transforms, ML inferences), or of upstream APIs (third-party data) all share the same shape: a key, a TTL, a backend rebuild path. When a request arrives, the cache layer runs <code>GET key</code>; if the result is non-null and not expired, return it (cache hit). If null or expired, run the rebuild, store the result with TTL, return it. Under low concurrency this works: at TTL boundary, the first request to arrive triggers one rebuild and stores the new value; all subsequent requests in that TTL window are hits. Under high concurrency, the boundary is destroyed: requests 1 through N (where N is the number of concurrent in-flight requests) all run the rebuild in parallel because they all hit between the moment the old key expired and the moment any of them wrote the new value. The DB sees N times the load it expected.</p>
    <p><strong>Mitigation 1: distributed locking.</strong> Before running the rebuild, acquire a lock. In Redis the canonical primitive is <code>SET lock:key 1 EX 5 NX</code> — set if not exists, expire in 5 seconds. The first request to arrive acquires the lock and runs the rebuild; subsequent requests get <code>nil</code> from the SET (because NX failed), see the lock is held, and either wait-and-retry or serve a fallback (stale value, default page, empty 204). After the rebuild completes, the lock is deleted explicitly. The 5-second EX is the safety net: if the rebuilder crashes mid-work, the lock auto-releases. Tradeoff: locks serialise rebuilds across the whole fleet, so any node can rebuild but only one at a time. Waiters add latency. The lock TTL must be longer than the slowest expected rebuild but short enough that crashes do not stall traffic for too long.</p>
    <p><strong>Mitigation 2: single-flight / request coalescing.</strong> Distributed locks coordinate across the fleet; single-flight coordinates within a single process. The pattern: maintain an in-process map of <code>key → in-flight Promise</code>. When a request needs the value, check the map. If a Promise is already in flight, return it (the request now subscribes to the same computation). If not, create a new Promise that runs the rebuild, put it in the map, and return it. When the Promise resolves, remove it from the map. The Go standard library has this as <code>singleflight.Group.Do</code>; Node has <code>p-memoize</code> with the same shape. Single-flight is much cheaper than a distributed lock because there is no network round-trip — the coordination happens in-memory. It only deduplicates within one process, so a 10-node fleet still has 10 concurrent rebuilds at expiry, but each node coalesces its own thousand-request herd into one. Combine with the per-key lock for full coverage.</p>
    <p><strong>Mitigation 3: probabilistic early expiration (XFetch).</strong> Vattani et al. (VLDB 2015) proposed a coordination-free approach: every read decides probabilistically whether to refresh the cache early, based on how close it is to expiry. The formula: refresh if <code>-beta * delta * ln(random()) &gt; time_to_expire</code>, where <code>delta</code> is the typical rebuild duration in seconds, <code>random()</code> is a uniform random in (0, 1), and <code>beta</code> is a tuning constant (default 1.0). As the TTL approaches, the probability climbs, so some lucky reader refreshes the cache before expiry while everyone else is still served from the still-valid cache. On average, exactly one early refresh happens per TTL window, smeared randomly. No lock, no coordination, no fleet awareness needed — every reader independently decides. The catch: XFetch only works if reads are frequent enough that "some reader" hits the probabilistic threshold before TTL. For cold-ish keys with sporadic reads, XFetch can miss the window and stampede the way naive TTL does.</p>
    <p><strong>Mitigation 4: stale-while-revalidate.</strong> RFC 5861 defines a cache directive that says "serve the stale value for up to N seconds while refreshing in the background". The server side stores not just the value and its TTL, but a longer stale-grace window. On a read after TTL but before stale-grace expires, the cache returns the stale value immediately and enqueues a background refresh. The user sees one fast response with slightly stale data; the cache gets repopulated for the next reader. CDNs (Cloudflare, Fastly, Akamai) have shipped SWR for years; Next.js's ISR is SWR for full pages. Trade: readers tolerate some staleness. The pattern explicitly accepts that the cached representation is allowed to lag the source of truth by the stale-grace window — usually fine for product listings, content pages, anything not requiring strong consistency.</p>
    <p><strong>Facebook memcache leases: the production reference.</strong> Nishtala et al. (NSDI 2013) describe Facebook's approach as "memcache leases": when a client misses, the cache returns a 64-bit lease token along with the miss. Only the client holding the token may write the new value back. Concurrent miss-clients in the same key get the miss but no lease — they are told to wait. Additionally, leases throttle: a key gets at most one lease per 10 seconds. The reported impact: peak DB query rate fell from 17K QPS to 1.3K QPS — roughly 13× reduction. The lease is the lock plus the throttle in one mechanism. Memcache implements this server-side; Redis lacks a native equivalent but can be modelled with <code>SET lease:key uuid EX 10 NX</code> plus client logic to check the returned uuid before writing.</p>
    <p><strong>Composition: defence in depth.</strong> Production stampede protection rarely uses one mitigation alone. The canonical stack: SWR at the edge (Cloudflare or your CDN) absorbs the bulk of expiry traffic by serving stale; XFetch in the origin's cache layer prevents the next layer's stampede by refreshing before expiry; single-flight in each application instance coalesces any remaining herd; a per-key distributed lock serialises rebuilds across the fleet for ultra-hot keys. Each layer drops the herd size by an order of magnitude. The fully-stacked configuration takes 10000 concurrent misses and turns them into one rebuild somewhere in the stack — every other request returned a stale-but-acceptable value or waited on an in-flight rebuild.</p>
    <p><strong>Detecting stampede in production.</strong> The fingerprint is sharp: at-TTL-boundary spikes in DB CPU, query count, and request latency, with regular periodicity matching the TTL value. A 60-second TTL produces 60-second-spaced spikes; a 300s TTL produces them every five minutes. Metrics to watch: <code>cache_miss_total</code> rate (a normal-shape cache shows low and smooth, a stamped cache shows sharp periodic spikes), <code>db_query_rate</code> p99 (sharp spikes at TTL boundaries indicate downstream stampede), <code>rebuild_duration_seconds</code> (long tails during boundary indicate contention). The mitigations leave traces: SWR shows <code>cache_stale_serve_total</code> (non-zero during refreshes); single-flight shows <code>singleflight_subscriber_count_p99</code> (a number above 1 means coalescing was active); lock-based shows <code>lock_wait_total</code> and <code>lock_acquire_duration</code>. If none of these are instrumented, stampedes are invisible until they cause an outage.</p>
    <p><strong>Negative caching and miss-storms.</strong> The same stampede shape applies when the answer is "not found". If the application caches DB null-results as a cache entry with the same TTL as positive results, a flood of requests for non-existent keys produces the inverse stampede: every cache miss results in a DB miss-lookup, which (under high concurrency) overloads the DB just as completely as positive misses. Mitigation has two parts: cache the "no such row" sentinel with a much shorter TTL (5-30s vs the positive 60-300s) so memory churn is bounded; and use a Bloom filter in front of the cache to reject lookups for keys that definitely do not exist (false-positive rate ~1% is fine; the filter is reset whenever the table is rebuilt). Without negative caching, an attacker can mint random non-existent keys (e.g. random UUIDs in a URL) to amplify DB load by orders of magnitude — a documented attack pattern that hit multiple CDN-backed sites in 2024.</p>
    <p><strong>Pre-warming and cache-priming.</strong> When a cache layer restarts (deploy, eviction, machine restart), it starts empty. Every incoming request misses and hits the DB. The recovery period is its own mini-stampede: if you restart at peak traffic, you produce a full-traffic origin spike. Production caches avoid this by pre-warming on startup: replay yesterday's top-N URLs against the new cache before accepting public traffic. Cloudflare's edges pre-warm from neighbouring POPs; Redis-as-a-cache deployments use a startup script that reads "top 1000 keys" from an audit log and primes the cache. Pre-warming is also the only safe deploy strategy for cache-tier upgrades: blue-green the cache instances, warm the green, then cut traffic. Cold-start stampede is the most common cause of post-deploy outages for high-traffic sites.</p>

  <Fragment slot="senior">
    <p><strong>XFetch derivation: why exponential is optimal.</strong> Vattani et al. (VLDB 2015) frame the problem as: given a cache key with TTL <code>t</code> and rebuild cost <code>delta</code>, schedule refreshes so that (a) the cache rarely expires under load, (b) exactly one refresh happens per TTL window on average, and (c) no coordination between readers. The probability distribution that satisfies all three is the exponential. The decision rule is <code>refresh ← random_exp(beta * delta) ≥ time_to_expire</code>, which simplifies to <code>refresh ← -beta * delta * ln(random()) ≥ time_to_expire</code>. The expected fraction of reads that trigger an early refresh, integrated over the TTL window, is one. The variance is exactly the variance of an exponential distribution. The parameter <code>beta</code> controls aggression: lower beta means earlier refreshes (more staleness avoidance, more wasted work), higher beta means later refreshes (closer to TTL, smaller refresh window). The original paper proves no coordination-free algorithm with these guarantees can beat exponential's expected work; any tighter rule requires either coordination or accepting more variance.</p>
    <p><strong>Facebook memcache leases: the algorithm in detail.</strong> A memcache lease is a 64-bit token returned alongside a cache miss. The protocol: client reads key, gets a null value plus a lease token. Only a client holding a valid token for that key may run SET. The server tracks the most recent lease issued per key; SET requests with a non-matching token are silently dropped. The throttle: a memcache server issues at most one lease per key per 10 seconds. If a second miss arrives within 10s, the server returns a null value with no lease and the client backs off (waits 100ms-1s, retries the GET — by which time some other client probably wrote the value). Concurrent miss-handlers spread across the fleet self-coordinate via lease ownership; only one writes the value, the rest serve the previous (stale) value if available or back off. Nishtala et al. (NSDI 2013) report 17K → 1.3K QPS reduction at peak. The mechanism doubles as a thundering-herd defence and a stale-set-invalidation race fix (a SET from the old read is silently dropped because the lease became invalid the moment the value was invalidated by a write).</p>
    <p><strong>Cloudflare and Fastly request collapsing at the edge.</strong> Production CDNs implement single-flight at the cache layer: when the edge sees N simultaneous misses for the same path, it forwards exactly one origin request and pipes the response to all N waiting client connections. Cloudflare calls this "request coalescing"; Fastly calls it "request collapsing". The mechanism is part of the cache's lifecycle: a miss enters the "stitching" state, originating one upstream fetch; new misses for the same key while in stitching attach to the in-flight fetch. The response splays to all attached connections simultaneously. The edge effect is that a viral content event (10 million viewers hitting one URL) produces one origin fetch, not 10 million. Both CDNs publish that request collapsing turns sudden-traffic incidents into low-impact events at the origin; without it, every CDN miss = upstream load.</p>
    <p><strong>Stale-while-revalidate semantics: RFC 5861.</strong> The HTTP Cache-Control extensions in RFC 5861 add two values: <code>stale-while-revalidate=N</code> (serve the stale response for up to N seconds while revalidating in the background) and <code>stale-if-error=N</code> (serve the stale response for up to N seconds if revalidation fails). Together they shape the cache's behaviour at expiry: when the cached response is past its <code>max-age</code> but within the stale-while-revalidate window, the cache returns it immediately and asynchronously initiates a fetch to the origin. Cloudflare implements this at edge; Vercel's ISR is the same shape at framework level; Apollo's GraphQL caching uses it for normalised cache entries. The design tradeoff: the user always sees a fast response, the source-of-truth is asynchronously reconciled. Critical for content/feed APIs; unsuitable for endpoints requiring strong consistency (account balance, vote count, anything that affects business logic).</p>
    <p><strong>Cache-Aside, Read-Through, Write-Through and their stampede profiles.</strong> Cache-aside (application owns both reads and writes to the cache) is the most stampede-prone shape: every reader checks cache, on miss reads DB and writes cache, with no built-in coordination. Read-through (cache library transparently fetches from DB on miss) can build in single-flight if the library implements it (Caffeine, Redis with redisson_client_side_caching, Apollo's RestDataSource). Write-through (every write hits both DB and cache) eliminates a class of stampedes by keeping the cache always-fresh — at the cost of doubled write latency. Write-back (write to cache, async to DB) has its own stampede shape: bursts of cache writes can flood the DB asynchronously. Choose by access pattern: cache-aside for reads with read-heavy traffic and tolerable staleness, write-through for transactional state, write-back for high-write throughput.</p>
    <p><strong>Negative caching and miss-amplification attacks.</strong> A subtle production trap: if the DB returns "no such row" and the application caches that as null, two failure modes appear. First, a malicious client can request random non-existent keys to fill the cache with nulls (cache-poison-by-flood). Second, after a real INSERT the cache still has null and the new row is invisible until TTL fires. Mitigation: explicit "missing" sentinel with short TTL (5–30s, much shorter than the positive TTL) and per-key write-through invalidation that deletes the negative entry on INSERT. Some caches (Redis with bloom filters, DynamoDB with item-not-found cache) support this natively. The other shape — DDoS by requesting many cold keys to amplify DB misses — is the actual "cache miss attack" pattern that affected CDNs in 2024 and caused at least two large public incidents.</p>
    <p><strong>Real production failures.</strong> Reddit 2017: a feed-cache change shipped without single-flight produced 3× DB peaks at every TTL; rolled back within an hour after on-call paged on DB CPU. Shopify 2020: a Black Friday flash-sale page had 30s TTL and no SWR; the entire storefront edge had a multi-second outage at every TTL boundary in the first 10 minutes — fixed by deploying stale-grace 5min on the next push. Twitter 2022: timeline cache stampede caused by an unrelated invalidation bug; the invalidation triggered 30M concurrent rebuilds and the DB pool saturated for 4 hours. Cloudflare 2024 disclosed a coalescing bug in KV cache that briefly allowed N requests for the same key to bypass coalescing during a deploy window. The pattern across all four: stampede protection was either missing, mis-configured, or had a bug that defeated it under load — and the cost was an outage proportional to the protection's gap.</p>
    <p><strong>Observability instrumentation.</strong> Minimum-viable instrumentation for stampede protection: <code>cache_request_total</code> by outcome (hit/miss/stale) by key prefix, <code>cache_rebuild_duration_seconds</code> histogram with p50/p99/p99.9, <code>cache_lock_acquired_total</code> and <code>cache_lock_wait_seconds</code>, <code>cache_singleflight_subscriber_count</code> histogram (a long tail means coalescing is doing real work), <code>cache_swr_stale_serve_total</code> (non-zero during refresh windows), <code>cache_swr_background_refresh_total</code> and the per-key version, <code>cache_lease_throttled_total</code> if using memcache leases. Alert on three signals: (1) cache_miss rate above N × steady_state (stampede in progress or imminent), (2) DB QPS p99 above K × p50 (sawtooth from boundary spikes), (3) cache_lock_wait_seconds_p99 above the rebuild duration (locks queueing). Without these, the first sign of a stampede is the database paging on-call.</p>
    <p><strong>TTL design beyond static values.</strong> Per-key TTL jitter: instead of TTL=60 for every key, use TTL=uniform(45, 75) so different keys expire at different times. A fleet of 1000 keys with jittered TTLs produces a smooth load curve at the DB instead of synchronized spikes. Production caches (Caffeine, Memcached, Redis with manual jitter) support this either natively or via a wrapper. Dynamic TTL: shorten TTL when the cache item is reaccessed within its lifetime, lengthen when reads are sparse — adaptive caches like Caffeine's W-TinyLFU implement this. Per-tier TTL: short at the edge (CDN, ~seconds), longer at the application cache (Redis, ~minutes), longest at a warm-cache backing store (S3, ~days). Each tier absorbs traffic at its own boundary, so even if all expire near each other, the lower tier serves the upper tier's miss without round-tripping to the DB.</p>
    <p><strong>Cross-protocol composition: cache + CDN + DB.</strong> A modern stack has at least three caching layers. Browser cache (per-user, microseconds) absorbs reload bursts. CDN (per-edge, multiple ms) absorbs viral traffic with SWR + request coalescing. Application cache (Redis, ~ms) absorbs API-shape traffic with single-flight + lock. Database (~tens of ms, the slow truth) sees only what the upper layers fail to absorb. A stampede at any tier propagates to the next; SWR at the CDN absorbs CDN-tier expiry; single-flight at the application absorbs application-tier expiry; lock at the application absorbs cross-application-instance expiry. The full-stack rule: every tier's stampede must be locally bounded, so the tier below sees one rebuild per N misses, regardless of N. If any tier breaks this, the failure cascades to the bottom.</p>
    <p><strong>The metastable failure shape.</strong> A cache stampede can push a system into a metastable state where it cannot recover even after the original cause is gone. Sequence: TTL expires, herd hits DB, DB CPU 100%, queries queue, queue depth grows past timeout, queries time out, clients retry (often with exponential backoff that does not apply because they think the timeout was their fault), retries multiply the herd, queue grows further, latency goes up, more timeouts, more retries. The system is now in a self-sustaining storm where the cache cannot rebuild fast enough to escape because the DB is too busy serving retries. Recovery requires either (a) load shedding at the front door (return 503 immediately on overload to break the retry loop), (b) circuit-breaking the rebuild path (serve stale forever until DB recovers), or (c) restarting the application servers to drop in-flight retries. Bouman et al. (2024) formalised this as a metastability pattern; the mitigation is the same as any metastable failure: have an explicit "kill the herd" signal that overrides normal cache behaviour during the storm.</p>
