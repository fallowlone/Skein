Этот pillar — про PostgreSQL, продакшн-дефолтную реляционку фуллстека 2026, — но открывается самой моделью, не реализацией. Статья Эдгара Кодда 1970 года *A Relational Model of Data for Large Shared Databanks* определила relations, tuples и операции над ними; эту модель реализует каждая SQL-БД (Oracle, DB2, SQL Server, Postgres, MySQL) с vendor-specific-расширениями. Знание модели — то, что позволяет senior-инженеру рассуждать о любой из них. Этот фрагмент называет строительные блоки (relation, attribute, domain), constraints (primary key, foreign key, unique, not null, check), дисциплину (нормализация 1NF → BCNF и когда осознанно гнуть), и Postgres-specific инструменты (JSONB, массивы, UUID, generated columns), меняющие cost-модель. Последующие фрагменты pillar'а строятся на этом словаре: indexes (02), execution plans (03), MVCC (04, уже готов), pooling (05), migrations (06), sharding (07), capstone (08).

<Crux>Таблицы, ключи, constraints, нормализация — 55 лет, всё ещё несущая. Гни осознанно, не случайно.</Crux>

Реляционная модель мала концептуально и велика по отдаче. <em>Relation</em> — это множество tuple одной формы; <em>таблица</em> — реализация. У каждого tuple одинаковые attribute (столбцы), каждый attribute берётся из <em>domain</em> (типа), каждая строка идентифицируется подмножеством своих attribute (candidate key). Engine форсит эту форму через constraints — декларативные правила, проверяемые до любого insert/update/delete. Декларативная проверка — вечный выигрыш модели: вместо того чтобы каждое приложение, трогающее данные, переизобретало «должен быть customer», «должен ссылаться на реальный product», «amount не может быть отрицательным», ты пишешь это один раз на границе таблицы, и engine отказывает плохим данным от лица каждого вызывающего. Application-баги становится невозможно закоммитить. Цена — constraint-проверка на write-time и дисциплина проектировать схему до того, как сможешь писать код. Senior-инженеры платят эту цену осознанно; новые команды либо платят случайно (денормализуют первым, жалеют потом), либо пропускают (трактуют БД как key-value-store с SQL-синтаксисом и накапливают годы integrity-долга). Этот фрагмент — про то, почему первый путь почти всегда дешевле за жизненный цикл системы.

    <p><strong>Зачем это нужно.</strong> Каждое приложение — тонкий слой вокруг своих данных; если данные неправильной формы, каждая фича платит цену. Хорошая схема делает сотню будущих фич лёгкими; плохая — каждую фичу битвой.</p>

Система остаётся когерентной без человеческих пере-проверок.</p>

    <p><strong>Реляционная модель Кодда.</strong> Статья Кодда 1970 формализовала relations как множества tuple, взятых из типизированных domain, и определила закрытую алгебру операций (selection, projection, join, union, intersection, difference) — закрытую, потому что каждая операция берёт relations на вход и даёт relation на выходе. SQL — нестрогая реализация этой алгебры; добавляет null (которое Кодд не любил), порядок (строки концептуально неупорядочены) и duplicate-строки (relations концептуально не имеют дубликатов). Знание разрыва важно, потому что объясняет острые углы: NULL-семантика в SQL (3-значная логика, где `NULL = NULL` — это NULL, не true), требование ORDER BY на top-level (engine свободен возвращать любой порядок без него), и существование `DISTINCT` (engine обязан хранить дубликаты, пока не попросишь убрать). Трактуй разрыв как «SQL = реляционная алгебра плюс практические компромиссы», и сюрпризы перестают быть сюрпризами.</p>
    <p><strong>Constraints: декларативные гарантии engine'а.</strong> Реляционный engine форсит пять основных видов constraint. <em>PRIMARY KEY</em>: non-null уникальный идентификатор каждой строки; один на таблицу. <em>UNIQUE</em>: non-PK uniqueness-правило на одном или нескольких столбцах; поддерживает null в стандартном SQL (несколько null допустимо) — Postgres даёт opt-in `UNIQUE NULLS NOT DISTINCT` из SQL:2023. <em>NOT NULL</em>: per-column правило «у этого столбца всегда есть значение». <em>FOREIGN KEY</em>: multi-column-ссылка с одной таблицы на primary или unique key на другой (или той же) таблице, с ON DELETE / ON UPDATE-clause'ами (NO ACTION, RESTRICT, CASCADE, SET NULL, SET DEFAULT), решающими, что происходит при изменении referenced-строки. <em>CHECK</em>: произвольное boolean-выражение, оцениваемое на каждой строке на write-time; например `CHECK (amount &gt;= 0)` или `CHECK (status IN ('open', 'closed', 'archived'))`. Вместе они — то, как схема кодирует бизнес-правила, которые engine отказывается нарушать.</p>
    <p><strong>Нормализация 1NF → BCNF простыми словами.</strong> Нормализация — серия прогрессивно строже правил разделения таблиц для устранения redundancy. <em>1NF</em>: каждая ячейка атомарна (никаких comma-separated-списков, никакого JSON-as-bag, никаких повторяющихся групп). <em>2NF</em>: каждый non-key-столбец зависит от целого primary key, не от его части (имеет значение только для composite PK). <em>3NF</em>: каждый non-key-столбец зависит только от primary key, не от других non-key-столбцов (никаких transitive-зависимостей). <em>BCNF</em> (Boyce-Codd): каждый determinant обязан быть candidate key — строже 3NF, обрабатывает edge-cases с перекрывающимися candidate-keys. Большинство продакшн-схем целятся в 3NF; BCNF важен при множественных candidate-keys с перекрывающимися attribute (редко в современных приложениях). Смысл нормализации — не «следуй правилам», а «устрани вид дубликата, при котором два факта могут разойтись». Если ты можешь обновить Anna's email в трёх местах, два устареют в течение года.</p>
    <p><strong>Денормализация: когда и зачем.</strong> Нормализация оптимизирует write-корректность; может быть дорогой на read-стороне, потому что ответ на вопрос требует join'а многих таблиц. Денормализация осознанно дублирует данные, чтобы избежать join'ов на горячих read-путях. Типичные паттерны. (1) <em>Stored aggregates</em>: столбец `order_total` на orders, кеширующий `SUM(line_items.amount)` для быстрых отчётов, рефрешащийся на каждом line-item write. (2) <em>Wide read models</em>: таблица `user_profile`, комбинирующая name, email, текущий адрес, последний order — питается триггерами или application-кодом из нормализованных таблиц. (3) <em>Materialised paths</em>: хранение полной иерархии tree-node в одном столбце для избегания рекурсивных join'ов. Дисциплина: денормализуй на read-стороне, держи source of truth нормализованным, и прими, что дубликаты должны сверяться чем-то (триггеры, jobs, application-код). Failure mode — денормализовать-везде без сверки: каждый столбец в итоге не согласован с каждым другим.</p>
    <p><strong>Surrogate vs natural keys: продакшн-дефолт.</strong> <em>Natural key</em> — данные, уже существующие в бизнес-домене (user email, product SKU, order number). <em>Surrogate key</em> — сгенерированный БД, opaque, имеющий смысл только внутри БД (BIGSERIAL, UUID). Продакшн-дефолт 2026: surrogate key как primary key плюс UNIQUE NOT NULL constraint на бизнес-natural-ключе. Почему: natural-keys меняются (customer меняет email), и PK-изменение каскадирует через каждый foreign key; surrogate keys никогда не меняются. Исключение: чисто join-таблицы (favourites: user_id, item_id) часто используют composite из foreign keys как PK — само отношение и есть identity, surrogate не нужен. UUID vs BIGSERIAL — следующий вопрос: UUID глобально уникальны (хорошо для распределённых insert'ов, multi-region, offline-first-клиентов) но больше (16 байт против 8) и хуже для index-locality (случайный UUIDv4 фрагментирует B-tree); UUIDv7 (time-ordered, RFC 9562) чинит locality и — современный дефолт для новых схем, где UUID нужен. BIGSERIAL меньше, последователен, cache-friendly — выбирай, когда не нужны globally-unique ID.</p>
    <p><strong>Postgres data types: бери самый узкий, что подходит.</strong> У Postgres самая богатая type-system среди mainstream-БД. <em>Integer</em>: SMALLINT (2B), INTEGER (4B), BIGINT (8B). Бери самый узкий диапазон, превышающий domain в 100x — user_id, который никогда не превысит 10 миллионов, может быть INTEGER (экономит половину байт на index-entry). <em>Strings</em>: TEXT, VARCHAR(n), CHAR(n) — TEXT продакшн-дефолт; VARCHAR(n) добавляет check на write-time, но без storage-выгоды; CHAR(n) почти всегда неверен (паддит до длины, удивляет trailing-пробелами). <em>Numeric</em>: NUMERIC(p,s) для точной арифметики (деньги), REAL/DOUBLE PRECISION для IEEE 754 (наука, ML-фичи). Никогда не храни деньги в REAL — float-арифметика теряет центы. <em>Timestamp</em>: TIMESTAMPTZ (с timezone) — продакшн-дефолт; TIMESTAMP (без) — footgun; DATE — для дат. <em>UUID</em>: нативный 16-байтный тип, никогда не храни как TEXT. <em>Boolean</em>: нативный BOOLEAN, никогда smallint или text. <em>JSON</em>: JSONB (binary, indexable) против JSON (text, не). <em>Arrays</em>: типизированные массивы (INTEGER[], TEXT[]) для маленьких bounded-списков, всегда живущих со строкой. Дисциплина: тип — первая линия constraint. Правильно типизированный столбец ловит 80% плохих данных до любого check-constraint.</p>
    <p><strong>JSONB и массивы: pattern «реляционный escape-hatch».</strong> JSONB хранит произвольный nested JSON как parsed binary, indexable через GIN, queryable операторами (`-&gt;`, `-&gt;&gt;`, `@&gt;`, `?`). Правильный use case: данные без фиксированной схемы или схема, варьирующаяся per-row (event payload'ы, third-party API-ответы, user-defined custom fields). Неправильный: замена того, что должно быть related-table'ой, потому что «схему ещё придумываем». Цена: каждый JSONB-запрос дороже типизированного — GIN-индексы медленнее B-tree, JSONB нельзя эффективно сортировать, FK constraints не могут ссылаться внутрь JSONB. Pattern: top-level столбцы для полей, по которым запрашиваешь или constraint'ишь часто, JSONB для long-tail-метаданных. Массивы следуют той же логике — отлично для «tag'ов на строке», где запрашиваешь только «строки с tag'ом X» (GIN-indexable) и никогда «список tag'ов с count'ом» (это хочет join-table).</p>
    <p><strong>Foreign keys на масштабе: PlanetScale-полемика.</strong> Некоторые hyperscale-конторы (PlanetScale на Vitess, несколько крупных Postgres-деплоев) рекомендуют отключать foreign keys ради одного или нескольких из: лёгкость online schema-changes (FK делают часть DDL медленнее или locked-out), невозможность cross-shard (FK не пересекают shard-границ), риск больших каскадов (плохо продуманный delete каскадирует миллионы строк в одной транзакции), упрощённая репликация. Trade: application-level integrity, асинхронная очистка (soft-delete + reaper-jobs), и явная cross-table-консистентность в коде. Для большинства команд под ~100M строк на таблицу trade неверен — FK-constraint самая дешёвая correctness-гарантия из доступных. Выше этого масштаба, с шардингом и zero-downtime-migration-ограничениями, расклад меняется. Senior-инженеры должны знать, что trade-off существует, и не считать отключение FK всегда преждевременным; равно и не считать hyperscale-pattern автоматически применимым к 10M-схеме.</p>
    <p><strong>Generated columns и computed integrity.</strong> Postgres поддерживает STORED generated columns (`amount NUMERIC GENERATED ALWAYS AS (price * quantity) STORED`) — значение вычисляется на каждом write и хранится, queryable как любой другой столбец, indexable. Use case: derived values, которые часто запрашиваешь (full_name из first_name + last_name, total из per-row-математики). В сочетании с CHECK constraint'ами generated columns делают схему выражающей больше инвариантов. Trade: write чуть медленнее (выражение оценивается); миграции на generated columns могут переписывать таблицу. Pattern недоиспользуется — многие команды тянутся к триггерам для поддержания derived-столбцов, когда GENERATED чище.</p>
    <p><strong>Indexes как часть schema-design.</strong> Каждый индекс — это копия данных под конкретный query-pattern. Primary key неявно создаёт unique B-tree-индекс; UNIQUE constraint — то же. Дальше — explicit индексы под known-hot-query'ы: B-tree под equality + range, GIN под JSONB и full-text, GiST под geospatial и range-types, BRIN под огромные insert-only-таблицы с естественной clustering'ом. Цена индекса: ~10-30% storage per index плюс ~5-50 μs на write-операцию (engine обновляет индекс на каждый insert/update/delete на indexed-столбце). Дисциплина: индексируй то, что часто фильтруешь или сортируешь; не индексируй то, что только пишешь. Piece 02 (indexes) покрывает types и trade-offs глубоко. Здесь важно: индекс — это часть schema-design, не runtime-tuning. Решение, где индексы будут, — design-time-решение наравне с column-набором.</p>
    <p><strong>Per-runtime ORM-ловушки.</strong> ORM-инструменты (Prisma, Drizzle, Hibernate, ActiveRecord, SQLAlchemy) генерируют схему из ORM-моделей. Удобно — но скрывает важные decisions. (1) ORM часто дефолтят на nullable-столбцы для optional-полей — против NOT NULL discipline. (2) ORM редко оптимизируют column-order под alignment-padding. (3) ORM-FK часто без ON DELETE clause — что эквивалентно NO ACTION (refuse with error), что обычно не то, чего хочет команда. (4) ORM-migration-tools часто генерируют ALTER TABLE без `CONCURRENTLY` для index-builds — что блокирует таблицу. (5) ORM-сгенерированные индексы — часто реакция на explain-feedback, не proactive-design. Senior-pattern: использовать ORM для query-build, но review schema-DDL руками (или с lint-инструментом, проверяющим NOT NULL, ON DELETE, index-corectness). Не доверять ORM-default'ам на schema-decisions.</p>
    <p><strong>Соглашения schema-style.</strong> Команда обязана документировать convention: singular vs plural names (продакшн-дефолт plural — users, orders), snake_case везде, PK = `id`, FK = `<referenced_table_singular>_id`, timestamps = `created_at`, `updated_at`, `deleted_at`, booleans с префиксами `is_`, `has_`, `can_`. CHECK constraint на каждом enum-столбце. NOT NULL по дефолту. TIMESTAMPTZ для каждого момента-во-времени. NUMERIC для каждых денег. CI-lint форсит convention'ы; schema-review на каждом PR с DDL. Кажется педантичным; окупается на каждом cross-team-запросе, каждой migration, каждом аудите. Soft-delete pattern: `deleted_at TIMESTAMPTZ NULL` + partial-индексы `WHERE deleted_at IS NULL` — позволяет восстановление и отдельную retention-policy от hard-delete. Audit-pattern: триггеры на UPDATE/DELETE, пишущие в audit-таблицу — каждое изменение логируется с user_id, timestamp, before/after-значениями. Эти patterns — не optional; они baseline продакшн-schema-зрелости.</p>

    <p><strong>Реляционная модель vs document / wide-column / graph альтернативы.</strong> Реляционная модель — одна из нескольких; senior-инженеры должны знать trade-off-пространство точно. <em>Document stores</em> (MongoDB, Firestore) — когда документы читаются как unit и никогда не join'ятся. <em>Wide-column stores</em> (Cassandra, ScyllaDB) — для очень высокой write-throughput с известными query-patterns. <em>Graph databases</em> (Neo4j, Dgraph) — когда graph-traversal и есть запрос. <em>Key-value stores</em> (Redis, DynamoDB) — для чистых point-lookup. Реляционная выигрывает при recurring структуре, ad-hoc-запросах и referential integrity — большинство B2B SaaS, fintech, ecommerce, ops-tooling. Выбирай Postgres, если нет конкретной причины; конкретные причины существуют на масштабе.</p>
    <p><strong>Row-storage Postgres: <Term k="heap" lang="ru">heap</Term>.</strong> Postgres-строки хранятся в 8KB-страницах на диске; layout: 23-байтный tuple-header (с visibility-инфой — покрыто в piece 04 про MVCC), потом null-bitmap при nullable-столбцах, потом column-data в declaration-order с type-specific alignment-padding. Ширина столбца имеет значение для storage и cache-density: строка с 20 столбцами смешанных типов занимает 200-400 байт; таблица 100M строк — 20-40 GB raw-heap, больше с индексами. Порядок столбцов имеет значение из-за alignment-padding — layout [int4, int8, int4] занимает 24 байта с 4 байтами padding; переупорядоченный как [int8, int4, int4] — 16 байт. Для широких таблиц column-order tuning экономит 10-20% storage. Реальный продакшн-рычаг; ORM-сгенерированные схемы редко это оптимизируют.</p>
    <p><strong>TOAST: как Postgres обрабатывает широкие значения.</strong> Postgres-страницы 8KB; строки, превышающие ~2KB, триггерят TOAST (The Oversized-Attribute Storage Technique) — значения сжимаются и/или нарезаются в side-таблицу, с указателем в основной heap. TOAST прозрачен — запросы возвращают полное значение — но имеет performance-импликации: read TOASTed-столбца требует extra disk-fetch; UPDATE TOASTed-столбца переписывает side-table-chunks; over-indexing TOASTed-столбца ломает производительность, потому что индекс обязан ссылаться на полное значение. Импликация для schema-design: очень широкие TEXT/JSONB/BYTEA — по сути отдельное storage — держи их вне горячих column-list'ов, не индексируй без GIN (понимает JSONB-структуру), и рассмотри явное разделение в side-table, если широкий столбец редко читается, а строка читается часто.</p>
    <p><strong>JSONB-стратегии индексирования.</strong> У JSONB две index-семьи. <em>GIN</em> (Generalized Inverted Index) индексирует отдельные ключи или пути внутри JSONB; default operator-class индексирует каждый ключ, альтернативный `jsonb_path_ops` индексирует полные пути (быстрее lookup'ы, больше индекс). GIN поддерживает `@&gt;`, `?`, `?&|`, `?&&`. <em>Expression B-tree</em> индексирует конкретный JSONB-путь как типизированное значение: `CREATE INDEX ON events ((data-&gt;&gt;'event_type'))` — поддерживает equality и range на этом пути, гораздо меньше GIN. Дисциплина: GIN для «строки, где JSONB содержит ключ X» или «matches path Y»; expression B-tree для «строки, где data.field равно X». Неправильный индекс делает JSONB-запросы 10-100x медленнее. Piece 02 (indexes) покрывает типы индексов глубже; здесь важно: JSONB не query-cheap без вдумчивого индексирования.</p>
    <p><strong>Constraints и immutability: temporal-инварианты.</strong> Postgres CHECK constraint оцениваются на write-time и должны быть детерминированными. Могут ссылаться на другие столбцы той же строки, но не на другие строки (это требует FK). Под temporal-инварианты — «completed orders не возвращаются к pending», «audit-log immutable» — правильный инструмент: row-level-security policies, триггеры (BEFORE UPDATE, выбрасывающие exception на disallowed-переходах), или application-уровневые state machines в сочетании с DB-constraint. Pure-SQL state-transition-enforcement многословен; многие команды кодируют state-machine как типизированный столбец с CHECK и триггером, форсящим transitions. Generated columns с CHECK кодируют часть derived-инвариантов декларативно — например `is_final BOOLEAN GENERATED ALWAYS AS (status IN ('completed','cancelled')) STORED` плюс триггер, отказывающий UPDATE WHERE OLD.is_final.</p>
    <p><strong>Versioning схемы и breaking changes.</strong> Реляционная схема — контракт между БД и каждым consumer'ом. Добавить nullable-столбец — non-breaking; добавить NOT NULL без default — ломает каждый существующий insert; drop столбца — ломает каждого reader'а; rename — оба. Senior-команды управляют схемой как кодом (migration-files в version control, исполняемые Flyway, Liquibase, sqlx-migrate, golang-migrate, Prisma Migrate) и применяют expand-then-contract: expand схему под новую форму, deploy кода, пишущего в оба, deploy кода, читающего из нового, drop старого. Piece 06 (migrations) покрывает pattern глубоко. Здесь важное: schema-решения липкие. Выбор неверного типа или формы ключа на design-time означает многонедельную миграцию, чтобы откатить; правильный выбор на design-time не стоит ничего лишнего. Senior тратят 10x больше времени на schema-review, чем на code-review эквивалентной feature-сложности — и это окупается.</p>
    <p><strong>Constraint deferral и сложные транзакции.</strong> FK можно объявить DEFERRABLE INITIALLY DEFERRED — отложит constraint-check до COMMIT. Use case: сложные multi-table-обновления, где intermediate-состояния нарушали бы constraint (например circular-references на graph-update). Trade: deferred constraint оцениваются на commit-time — failed constraint вызывает abort транзакции без in-flight-сигнала. Продакшн-гигиена: используй DEFERRABLE редко, только на FK, реально нужных, и только в транзакциях, где временное нарушение хорошо понятно. Большинство команд должны держать constraint IMMEDIATE (дефолт) и структурировать обновления так, чтобы intermediate-состояния были consistent.</p>
    <p><strong>Реальные продакшн-failure-modes.</strong> (a) <em>Implicit type coercion</em>: запрос `WHERE user_id = '42'` (string вместо int) тихо работает в одних setup'ах, но убивает индекс — Postgres конвертирует каждый user_id в text. Mitigation: типизированные query-builder'ы, ORM type-safety, EXPLAIN ANALYZE на каждом новом запросе. (b) <em>NULL-семантика в join'ах</em>: LEFT JOIN с NULL на FK тихо дропает строки во inner-запросах; senior-pattern — IS DISTINCT FROM и явный COALESCE под null-tolerant-логику. (c) <em>Cascade cascade cascade</em>: delete на сильно cascaded root-строке создаёт multi-million-транзакцию, держащую lock'и минутами; senior-pattern — soft-delete root'а, batch-clean потомков явными DELETE FROM ... WHERE ... LIMIT 10000-циклами. (d) <em>Schema drift через ad-hoc ALTER</em>: junior-инженер запускает ALTER TABLE в продакшне напрямую; migration-tool больше не матчит реальность, будущие миграции фейлят загадочно. Mitigation: каждое schema-change через migration. (e) <em>JSONB-столбцы, выросшие в relational-shape</em>: «metadata» JSONB-столбец накопил 30 типизированных полей за два года; каждая новая фича проверяет «if metadata-&gt;'feature_x' = ...» — правильный ход — извлечь структурные поля в proper-столбцы, но миграция дорогая и откладывается.</p>
    <p><strong>Дизайн-разница pgsql vs MySQL.</strong> Postgres и MySQL реализуют реляционную модель с разными дефолтами. MySQL прощающее (silent string-to-int coercion, NULL-поведение в unique-constraints, storage-engine-различия между версиями); Postgres строже (явные типы, строгий NULL, single storage-engine). Senior-команды в 2026 дефолтят на Postgres для новых схем — стрóже defaults ловят баги раньше, type-system богаче (JSONB, arrays, ranges, custom types), extension-экосистема шире (PostGIS, TimescaleDB, pg_vector, pgcrypto). MySQL правилен, когда (a) ты глубоко в MySQL-экосистеме (Vitess, PlanetScale, AWS Aurora MySQL), (b) есть конкретный operational-expertise, или (c) нужна MyRocks-write-throughput. Для greenfield без этих причин — Postgres.</p>
    <p><strong>Naming-conventions и операционная зрелость.</strong> Схема — lingua franca команды и operations. Convention'ы, окупающиеся: (a) singular vs plural имена таблиц — выбери одно, никогда не смешивай; продакшн-дефолт — plural (users, orders, order_items). (b) snake_case везде (PostgreSQL fold'ит идентификаторы к lower case без кавычек). (c) PK всегда `id` (или `<table>_id` в join-таблицах). (d) FK-столбцы — `<referenced_table_singular>_id`. (e) Timestamps — `created_at`, `updated_at`, `deleted_at` (soft-delete). (f) Boolean'ы с префиксом `is_`, `has_`, `can_` или ясное имя свойства. Кажется педантичным; окупается на каждом дашборде, миграции, cross-team-запросе. Зрелые платформы публикуют schema-style-guide и CI-lint'ят convention'ы.</p>
