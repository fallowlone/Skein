Индексы (<a href="/ru/databases/02-indexes/">02-indexes</a>) дали отсортированные копии данных; этот фрагмент про движок, который решает, использовать ли их. Планировщик Postgres читает ваш SQL, спрашивает pg_statistic, сколько строк породит каждое условие, перебирает возможные комбинации сканов и соединений, и выбирает самую дешёвую по внутренней формуле стоимости. На выходе план — это догадка: дерево операторов с прикреплёнными оценками количества строк. Когда оценки совпадают с реальностью, выбранный план обычно оптимален. Когда оценки занижены в 1000 раз, планировщик берёт Nested Loop на якобы 10 строках, налетает на 10 миллионов, и превращает запрос за 50 мс в запрос на 8 минут. Самый ценный навык в production-Postgres — чтение EXPLAIN ANALYZE: сравнить предсказание планировщика с фактическим выполнением и понять, что чинить — статистику, индекс или запрос.

<Crux>EXPLAIN показывает план. План — догадка по статистике. Оценочные строки против фактических — самый диагностический показатель в базе.</Crux>

Запрос в Postgres проходит четыре стадии: <em>parse</em> (текст → дерево разбора), <em>rewrite</em> (применение представлений и правил), <em>plan</em> (построение самого дешёвого дерева выполнения), <em>execute</em> (запуск). Тюнить можно только планировщик. Он выбирает между типами сканов (Seq Scan, Index Scan, Bitmap Heap Scan, Index Only Scan), алгоритмами соединений (Nested Loop, Hash Join, Merge Join) и стратегиями агрегации, оценивая каждую опцию через статистику таблиц и константы стоимости операций (`seq_page_cost`, `random_page_cost`, `cpu_tuple_cost` и т.д.). Стоимость — в условных единицах, грубо пропорциональных времени на стандартном железе, не в миллисекундах и не в байтах. EXPLAIN печатает выбранный план; EXPLAIN ANALYZE действительно выполняет запрос и показывает реальные тайминги рядом с оценками. Разрыв между ними — диагностическая поверхность для любого вопроса о производительности в Postgres.

    <p><strong>Чтение строки стоимости.</strong> Каждый узел плана печатает `(cost=startup..total rows=N width=B)`. `startup` — стоимость, которую надо оплатить до первой выданной строки (ноль для Seq Scan, ненулевая для Sort, который должен прочитать всё до выдачи). `total` — стоимость полного выполнения узла. `rows` — оценка планировщика, сколько строк узел выдаст. `width` — средняя ширина строки в байтах. Стоимость в условных единицах, где 1.0 ≈ последовательное чтение страницы по дефолтной модели железа; важны только соотношения. С ANALYZE каждый узел также печатает `(actual time=startup..total rows=N loops=L)` — реальное стенное время в миллисекундах, реальный счёт строк, реальное число запусков узла. Правило интерпретации: если узел внутри Nested Loop на внутренней стороне, разделите actual time на loops, чтобы получить стоимость одного запуска.</p>
    <p><strong>Типы сканов.</strong> <em>Seq Scan</em> читает всю кучу; стоимость = `relpages × seq_page_cost + reltuples × cpu_tuple_cost`. Оптимален, когда предикат отбирает большую долю строк или индекс не помогает. <em>Index Scan</em> проходит по индексу, чтобы найти подходящие TID, затем извлекает каждую строку из кучи; стоимость растёт как `random_page_cost × подходящие_строки`. Оптимален, когда строк мало и они не сгруппированы. <em>Bitmap Heap Scan</em> + <em>Bitmap Index Scan</em>: строит битмап TID из одного или нескольких индексов, сортирует по физическому положению и сканирует кучу по порядку — превращает случайный I/O в последовательный. Оптимален, когда строк много (сотни — миллионы), и они разбросаны по куче. <em>Index Only Scan</em>: читает только индекс без обращения к куче, когда все нужные колонки в индексе И карта видимости подтверждает, что страница «вся видна». Самый быстрый тип скана, когда применим.</p>
    <p><strong>Алгоритмы соединений.</strong> <em>Nested Loop</em>: для каждой строки внешнего отношения ищем подходящие строки внутреннего (обычно через индекс). Стоимость = `внешние_строки × внутренняя_стоимость`. Выигрывает, когда внешнее отношение маленькое (десятки строк) и у внутреннего есть подходящий индекс. Опасен, когда внешнее ошибочно недооценено, а на деле огромное — цикл взрывается. <em>Hash Join</em>: строит хеш-таблицу из меньшей стороны (build-сторона), затем пробивает её строками из большей. Стоимость = `build_cost + probe_cost + размер_хеш_таблицы / work_mem` (выливается, если больше work_mem). Выигрывает на средних и больших equi-join, где ни у одной стороны нет нужного индекса. <em>Merge Join</em>: сортирует обе стороны по ключу соединения (или использует уже отсортированные индексы) и сливает параллельно. Выигрывает, когда обе стороны уже отсортированы (подходящий индекс) или сортировки выливаются эффективно. По умолчанию планировщик выбирает по стоимости; для диагностического сравнения тип соединения можно отключить через `SET enable_hashjoin = off` (и так далее).</p>
    <p><strong>Каталог pg_statistic.</strong> Когда вы запускаете ANALYZE, Postgres сэмплирует таблицу (по умолчанию 300 × default_statistics_target строк = 30 000 при дефолтном 100) и вычисляет статистики на колонку: `n_distinct` (число различных значений или отрицательная доля, если масштабируется с размером таблицы), `most_common_vals` + `most_common_freqs` (MCV-список, до default_statistics_target записей), `histogram_bounds` (гистограмма равных частот по не-MCV значениям), `correlation` (статистическая корреляция между физическим и логическим порядком, используется для оценки соотношения случайного к последовательному при индексном скане). Планировщик комбинирует это для оценки селективности: «сколько строк подойдёт под `WHERE x = 42`» отвечается из MCV-списка, если 42 — MCV, иначе интерполируется по гистограмме. Читайте каталог сами: `SELECT * FROM pg_stats WHERE tablename = 'orders';`</p>
    <p><strong>ANALYZE: когда запускать, когда запускает autovacuum.</strong> Autovacuum планирует ANALYZE по таблице на основе `autovacuum_analyze_threshold` (по умолчанию 50 строк) + `autovacuum_analyze_scale_factor × reltuples` (по умолчанию 0.1 → 10% таблицы). На таблице в 100M строк autovacuum проанализирует только после 10M изменений — слишком редко для перекошенных или быстро меняющихся данных. Операционный фикс: понизить scale factor для горячих таблиц: `ALTER TABLE orders SET (autovacuum_analyze_scale_factor = 0.02)`. Ручной ANALYZE быстрый (секунды на таблице в 100M строк) и приемлем после массовых INSERT, больших UPDATE или изменений схемы. Самая частая причина «запрос внезапно стал медленным» — устаревшая статистика, а самый недоиспользуемый фикс — увеличить default_statistics_target на колонке с перекошенным распределением (`ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000; ANALYZE orders;`).</p>
    <p><strong>BUFFERS и картина I/O.</strong> `EXPLAIN (ANALYZE, BUFFERS)` добавляет учёт буферов на каждом узле: `shared hit` (страница найдена в shared_buffers Postgres), `read` (страница прочитана с ОС/диска), `dirtied` (страница изменена), `written` (страница сброшена). На прогретой системе большинство страниц должны быть hit; много read означает, что рабочий набор больше shared_buffers или запрос трогает холодные данные. BUFFERS — диагностика «медленно из-за CPU или I/O»: много read = ограничено I/O, мало буферов но высокое actual time = ограничено CPU (часто плохой join или сортировка).</p>
    <p><strong>Опции EXPLAIN.</strong> `FORMAT JSON | XML | YAML | TEXT` — JSON для тулинга (explain.depesz.com, explain.dalibo.com, авто-EXPLAIN в pganalyze). `VERBOSE` добавляет списки выходных колонок на каждом узле. `SETTINGS` (PG 12+) печатает не-дефолтные планировщики GUC. `WAL` (PG 13+) показывает байты WAL. `GENERIC_PLAN` (PG 16+) планирует параметризованный запрос без подстановки значений — полезно для диагностики prepared-statement. `SERIALIZE` (PG 17+) включает стоимость сериализации строк клиенту — закрывает разрыв между total time в EXPLAIN ANALYZE и тем, что видит клиент.</p>
    <p><strong>auto_explain и pg_stat_statements.</strong> Два расширения, которые должны быть в любом production-Postgres. <em>pg_stat_statements</em> записывает каждый выполненный запрос (нормализованный по параметрам), отслеживая calls, total_time, mean_time, rows, счёт буферов. Топ-запросы по `total_time` — цели оптимизации. <em>auto_explain</em> автоматически логирует EXPLAIN ANALYZE для запросов, превысивших порог длительности: `SET auto_explain.log_min_duration = '500ms'; SET auto_explain.log_analyze = true;` — медленные запросы попадают в лог с полными планами, не нужно их воспроизводить вручную. Вместе они отвечают на «какие запросы медленные и почему» без инструментации приложения.</p>
    <p><strong>Ошибки оценки строк и каскад.</strong> Главный режим отказа планировщика — ошибочные оценки промежуточных количеств строк. WHERE-условие, которое планировщик оценивает в 10 строк, а в реальности это 10 000, — ошибка 1000× на этом узле, но ошибка каскадирует в следующее решение. При 10 строках на внешней стороне планировщик выбирает Nested Loop (дёшево при малом внешнем). С 10 000 строк, реально попадающими в цикл, внутренняя сторона запускается 10 000 раз вместо 10 — работы в 1000 раз больше. Запрос, который должен был быть Hash Join за 50 мс, становится Nested Loop на 8 минут. Корневая причина не выбор соединения; это оценка строк. Почините оценку (ANALYZE, мультистатистика, expression-индекс, переписать запрос) — и выбор соединения починится сам.</p>
    <p><strong>Не-sargable-предикаты.</strong> Предикат «sargable» (Search ARGument-ABLE), если планировщик может использовать индекс. `WHERE created_at &gt;= '2026-01-01'` sargable; `WHERE date(created_at) = '2026-01-01'` — нет, функция на индексированной колонке принуждает Seq Scan. Типичные нарушители: `WHERE LOWER(email) = 'alice@x.com'` (приведение типа на индексированной колонке), `WHERE id::text = '42'` (приведение типа), `WHERE EXTRACT(year FROM created_at) = 2026` (вызов функции), LIKE с ведущим подстановочным знаком (`'%foo'`), `OR` между колонками, которые планировщик не может индексировать вместе. Фиксы: expression-индексы (`CREATE INDEX ON users (LOWER(email))`), переписывания запроса (диапазонные предикаты вместо вызовов функций), trigram-индексы (pg_trgm для нечёткого поиска). EXPLAIN сразу выявляет такие случаи как Seq Scan + Filter там, где вы ожидали Index Scan.</p>
    <p><strong>Подсказка: выбор планировщика воспроизводим.</strong> Те же данные + та же статистика + те же GUC = тот же план. Если запрос медленный в проде и быстрый на стейдже, одно из трёх отличается. Чаще всего: разный размер таблицы + разная статистика. Реже: разные GUC (work_mem, random_page_cost) на окружение. Редко: разная версия Postgres или расширения. Диагностика: захватите EXPLAIN (без ANALYZE) на обоих и сравните планы; идентичные планы — проблема во времени выполнения (данные, блокировки); разные планы — проблема во времени планирования (статистика, GUC).</p>
    <p><strong>Практический рабочий цикл чтения EXPLAIN.</strong> Сначала ищите узел с самым большим actual time — там доминирующая стоимость; всё остальное вторично. Затем сравните rows-estimated и rows-actual на этом узле и его детях — если разрыв больше 10×, это якорь проблемы, а не алгоритм соединения сверху. Третий взгляд — на loops внутренних сторон Nested Loop: высокий loops при низкой ожидаемой выборке означает каскад от недооценки внешнего. Четвёртый — BUFFERS: много read указывает на холодные данные или маленький shared_buffers; много hit, но высокое actual time — CPU-bound операция (сортировка, агрегация, сложный фильтр). Пятый — Sort Method: external merge означает выливание на диск, фикс через work_mem или подходящий индекс. Шестой — Filter против Index Cond: Filter означает, что индекс не сузил предикат, а только пост-фильтровал результат — типичный симптом не-sargable условия или композита с неверным порядком колонок. Седьмой — Planning Time vs Execution Time: при правильно настроенном OLTP planning должен быть меньше 1 мс; больше — признак сложного запроса или избыточной мультистатистики на маленьких таблицах. Эти семь проверок занимают 30 секунд на план и закрывают 90% диагностики.</p>
    <p><strong>Чтение EXPLAIN в команде.</strong> Senior-практика: каждый PR, который добавляет или меняет горячий SQL-запрос, несёт в описании EXPLAIN ANALYZE до и после. Это не церемония — это способ зафиксировать ожидаемую форму плана. Когда через шесть месяцев другой инженер будет тюнить тот же запрос, у него будет точка отсчёта. Кроме того, в момент ревью второй пары глаз ловит ошибки раньше: «почему здесь Seq Scan на 50M строк?» — вопрос ревьюера, который мог бы стать инцидентом в проде. Инструменты: explain.depesz.com и explain.dalibo.com визуализируют JSON-выход EXPLAIN, показывая горячие узлы и большие row-estimate gaps. pganalyze и pgwatch2 автоматизируют этот цикл, накапливая планы за месяцы и алертя на структурные изменения. Команды, которые внедряют EXPLAIN-ревью как обязательную часть процесса, через квартал перестают видеть «база медленная» в трекере инцидентов.</p>

    <p><strong>Внутренняя структура планировщика.</strong> Планировщик Postgres — cost-based оптимизатор. Для каждого запроса он строит <em>paths</em> — лёгкие частичные планы для участков запроса (одно-табличные сканы, соединения малых наборов отношений). Paths сравниваются по стоимости; сохраняется только самый дешёвый per "набор отношений + порядок сортировки" (остальные отбрасываются). Для многотабличных соединений рассматриваются все комбинации динамическим программированием — исчерпывающе до `geqo_threshold` (по умолчанию 12) отношений, дальше включается Genetic Query Optimizer (эвристический поиск). Самый дешёвый path конвертируется в полное дерево плана (Plan-узлы: SeqScan, IndexScan, HashJoin и т.д.). Представление через paths — senior-модель для отладки: когда видите удивительный план, спросите «какие альтернативные paths рассмотрел планировщик и почему отбросил» — часто ответ в cost-разнице, вызванной плохой оценкой строк. `EXPLAIN (VERBOSE)` и pg_hint_plan (расширение) раскрывают альтернативы.</p>
    <p><strong>Константы стоимости и тюнинг под SSD.</strong> Postgres приходит с `random_page_cost = 4.0` и `seq_page_cost = 1.0` — значения для шпиндельных HDD, где случайные чтения в 4 раза медленнее последовательных. На NVMe SSD соотношение гораздо меньше (1.5-2×); на закешированных в RAM горячих рабочих наборах оно фактически 1.0. Senior-тюнинг продакшна: `random_page_cost = 1.1` на SSD-системах с нормальным поведением кеша; `random_page_cost = 1.0` и пропорционально снизить `seq_page_cost` (например, 0.1, 0.1 с `cpu_tuple_cost = 0.01`), если рабочий набор полностью помещается в shared_buffers. Эффект: планировщик охотнее использует Index Scan и Index Only Scan вместо Seq Scan — правильный наклон для современного железа. Установите `effective_cache_size` в ~75% от общего RAM (или размер file-cache ОС), чтобы планировщик учитывал кешированные страницы в оценках стоимости. Ошибка в этой настройке — один из самых частых тихих грехов: база на M2 NVMe с HDD-эпохи стоимостями недоиспользует индексы.</p>
    <p><strong>Generic против custom планов.</strong> Prepared-statement (любой параметризованный запрос от драйвера, любая PL/pgSQL-функция с параметрами) проходит через кеш планов. Первые 5 запусков планируются с подстановкой параметров (custom-планы, лучшие при перекошенных распределениях); с 6-го Postgres вычисляет среднюю стоимость custom-планов и сравнивает с гипотетическим generic-планом (без знания параметров). Если стоимость generic в пределах ~10% от средней custom, Postgres навсегда переключается на generic для жизни этого prepared-statement. Переключение невидимо приложению, но катастрофично: generic-план, заточенный под «типичный» параметр, не подходит для выбросов. Симптомы: prepared-statement был быстрым, потом внезапно медленнее; тот же SQL ad-hoc по-прежнему быстрый. Диагностика: `EXPLAIN (GENERIC_PLAN)` (PG 16+) на prepared-форме; если generic плох — поставьте `plan_cache_mode = 'force_custom_plan'` на роль или сессию — каждый запуск перепланируется, но всегда выбирается правильный план. Цена: время планирования на запуск (~0.5-2 мс). Стоит того, когда вариация времени выполнения высока.</p>
    <p><strong>Parameter sniffing: Postgres против SQL Server.</strong> SQL Server компилирует план на первом запуске с тем параметром, потом кеширует и переиспользует — «parameter sniffing» — что может дать план, заточенный под параметр-выброс первой записи. Гибрид Postgres (5 custom + сравнение + возможно generic) избегает худшего, усредняя по параметрам, но вводит свой подвох (среднее может скрыть выбросы). Production-дисциплина в Postgres: следить за prepared-statement с большим `stddev_exec_time` в pg_stat_statements; исследовать через EXPLAIN (GENERIC_PLAN) и EXPLAIN (ANALYZE) на репрезентативных параметрах; рассмотреть plan_cache_mode = force_custom_plan для проблемных случаев. Общий урок: у каждой стратегии кеширования планов есть режимы отказа; инженерный вопрос — какой из них вы можете обнаружить и починить.</p>
    <p><strong>Расширенная статистика: dependencies, ndistinct, mcv.</strong> CREATE STATISTICS поддерживает три типа. <em>dependencies</em> отслеживает функциональные зависимости (A определяет B с вероятностью p); полезно, когда одно значение колонки следует из другого (zip → city, country → region, product_id → category). <em>ndistinct</em> отслеживает число различных комбинаций для оценки multi-column GROUP BY (без этого планировщик перемножает per-column n_distinct и переоценивает). <em>mcv</em> хранит мульти-колоночные самые частые комбинации напрямую — аналог per-column MCV-списка, но для кортежей. По умолчанию — все три; можно ограничить подмножеством. CREATE STATISTICS требует ANALYZE для заполнения. Senior-паттерн: выявить топ-10 мульти-колоночных предикатов из pg_stat_statements + EXPLAIN, создать по одному объекту статистики на коррелированную пару или тройку. Стоимость хранения мала (килобайты на объект); улучшение планирования на затронутых запросах — 100-1000×. Доступно с PG 10 (dependencies, ndistinct); PG 12+ добавил mcv; PG 14+ добавил expression-статистики (статистики на выражениях типа `(col + col)` или `LOWER(col)`).</p>
    <p><strong>JIT-компиляция.</strong> Postgres 11+ поддерживает JIT-компиляцию вычисления выражений (фильтры, проекции, агрегации). Когда общая стоимость плана превышает `jit_above_cost` (по умолчанию 100 000), JIT включается; `jit_inline_above_cost` (по умолчанию 500 000) инлайнит вызовы функций; `jit_optimize_above_cost` (по умолчанию 500 000) применяет LLVM-оптимизации. JIT помогает CPU-bound запросам на больших сканах (миллионы строк со сложными предикатами) на 10-30%; на коротких OLTP-запросах добавляет накладные расходы (время компиляции превышает экономию). Диагностика: `EXPLAIN (ANALYZE, JIT)` показывает JIT-тайминги по фазам. Тюнинг: поднять пороги (или `jit = off`) для коротко-запросной OLTP-нагрузки; снизить для аналитики. Дефолтные пороги консервативные; настраивайте эмпирически под нагрузку.</p>
    <p><strong>GEQO и большие соединения.</strong> Генетический оптимизатор включается, когда число отношений в соединении превышает `geqo_threshold` (по умолчанию 12). Ниже планировщик использует исчерпывающее динамическое программирование для оптимального порядка. Выше GEQO использует эвристический поиск — быстро, но не гарантировано оптимально. Для запросов с 15-30 соединёнными таблицами (аналитика, отчёты) GEQO может давать субоптимальные планы непредсказуемо (эвристика рандомизирована — тот же запрос, разные планы run-to-run). Обходы: `geqo = off` (исчерпывающий поиск даже на больших соединениях — дольше планирование, но стабильные планы); снизить `from_collapse_limit` и `join_collapse_limit` (по умолчанию 8), чтобы планировщик не переупорядочивал соединения, фиксируя явный JOIN-порядок. Последнее — senior-трюк для стабилизации планов аналитики: `SET join_collapse_limit = 1; SET from_collapse_limit = 1;` заставляет Postgres соблюдать явный порядок соединений — полезно, когда вы вручную настроили запрос и хотите, чтобы он оставался настроенным.</p>
    <p><strong>auto_explain в продакшне.</strong> Настройка: `shared_preload_libraries = 'auto_explain'`; `auto_explain.log_min_duration = '500ms'`; `auto_explain.log_analyze = true`; `auto_explain.log_buffers = true`; `auto_explain.log_format = 'json'`; `auto_explain.sample_rate = 0.01` (выборка 1% медленных, чтобы ограничить объём логов). Результат: медленные запросы попадают в логи postgres с полными ANALYZE + BUFFERS планами, без воспроизведения на стейдже. Логи направить в инструмент разбора планов (pganalyze, pgwatch2 или самописное); за недели топ медленных планов накапливается естественно. Подвох: log_analyze = true добавляет накладные расходы на запрос — инструментация таймингов нетривиальна на очень быстром OLTP. Тюньте sample_rate или auto_explain.log_min_duration, чтобы ловить только реально медленное.</p>
    <p><strong>Стабильность планов между деплоями.</strong> Типичная операционная боль: деплой с новыми таблицами, данными или объёмами вызывает регрессии плана на неизменённых запросах. Митигации. (1) Хранить «золотой план» снимок для топ-20 запросов из pg_stat_statements; сравнивать после деплоев; алертить на изменение структуры плана (другие типы узлов). (2) Закреплять планы для критических запросов через pg_hint_plan (расширение) — явные подсказки вида `/*+ IndexScan(orders idx_x) HashJoin(orders customers) */` — фиксируют форму плана; меняют адаптивность планировщика на предсказуемость. (3) Стабилизировать статистику: запускать ANALYZE на критических таблицах в post-deploy хуке, чтобы планировщик увидел свежие данные до возобновления трафика. (4) Использовать pg_stat_statements для обнаружения регрессий: всплески stddev_exec_time, деградация mean_time, концентрация total_time на ранее дешёвых запросах. Senior-команды владеют playbook'ом по регрессиям планов так же, как owner'ят incident response.</p>
    <p><strong>Реальные режимы отказа в продакшне.</strong> (а) <em>Каскад от устаревшей статистики</em>: массовый INSERT или большой UPDATE сдвинул распределения; autovacuum ещё не запустил ANALYZE; следующий запрос использует старый MCV-список и берёт не тот план. Митигация: ANALYZE в post-batch хуке любой большой операции данных. (б) <em>Ловушка generic-плана</em>: prepared-statement был быстрым на первых 5 запусках (custom-планы), регрессировал на 6-м (generic-план). Митигация: plan_cache_mode = force_custom_plan для роли. (в) <em>Взрыв от коррелированных колонок</em>: `country='US' AND region='CA' AND status='shipped'` недооценено в 1000×; Nested Loop запускается миллион раз вместо тысячи. Митигация: CREATE STATISTICS (dependencies, mcv) на колонки. (г) <em>random_page_cost не настроен</em>: на SSD дефолтная HDD-эпохи стоимость делает Index Scan на 4× дороже, чем должно быть; планировщик предпочитает Seq Scan. Митигация: SET random_page_cost = 1.1 в postgresql.conf для SSD-систем. (д) <em>JIT-overhead на OLTP</em>: короткие запросы триггерят JIT (какая-то патологическая оценка стоимости превышает jit_above_cost) и тратят больше на компиляцию, чем на выполнение. Митигация: поднять jit_above_cost до 500 000+ или выключить JIT для роли. (е) <em>work_mem слишком мал</em>: Sort Method: external merge или Hash Join Batches > 1 — выливание. Митигация: SET work_mem пер-сессионно на запрос; глобально не поднимайте без учёта max_connections × work_mem. (ж) <em>Hash Aggregate spill bug</em>: до PG 13 большие GROUP BY не могли выливаться — использовали неограниченную память и попадали под OOM. Митигация: обновиться выше PG 13 (Hash Aggregate теперь корректно выливается). (з) <em>План меняется с фазой нагрузки</em>: тот же запрос получает разные планы в разное время суток, потому что распределение данных сдвигается (ночной импорт раздул счёт строк одной таблицы); autovacuum в итоге уравновешивает. Митигация: закрепить планы через pg_hint_plan для критических путей; иначе смириться с вариацией.</p>
    <p><strong>Стратегическая позиция: планы — первоклассный операционный артефакт.</strong> Зрелые Postgres-команды относятся к планам выполнения так же, как SRE — к дашбордам: захватываются, версионируются, алертятся, обсуждаются в PR, меняющих SQL. Каждый PR, трогающий горячий запрос, несёт EXPLAIN ANALYZE-диф в описании (до и после). Каждый деплой включает post-deploy ANALYZE на критических таблицах и снимок pg_stat_statements. Топ-20 запросов по total_exec_time имеют задокументированные ожидания «золотого плана». Регрессии медленных запросов ловятся auto_explain + алертингом, не жалобами пользователей. Цена умеренная (квартальный аудит индексов/планов + автоматический алертинг); выгода — никаких звонков в 3 ночи из-за запроса, который два года работал и вдруг сломался. EXPLAIN ANALYZE — микроскоп senior-инженера для Postgres: чем чаще используете, тем реже отлаживаете вслепую.</p>
