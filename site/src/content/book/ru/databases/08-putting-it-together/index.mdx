День 0 в SaaS-стартапе. PM просит «поиск пользователей по email». Один инженер, один Postgres, одна таблица. Через три года: 1 миллиард строк, шесть шардов Citus, и runbook размером с учебник. Между этими точками — семь моментов, когда база ломалась, а команда училась. <PersonaTag id="otto" lang="ru" /> держал строки. <PersonaTag id="sven" lang="ru" /> делал запросы. <SpiralCue thread="statefulness" lang="ru" /> <SpiralCue thread="latency" lang="ru" />

<Crux>Семь пьес главы — это семь раз, когда продукт обогнал свою базу, начиная с CREATE TABLE.</Crux>

Walk ниже называет триггер и рычаг на каждой стадии. Каждая стадия — один из семи прошлых разделов: пропустишь рычаг, следующая стадия обойдётся дороже.

## The walk: от нуля до миллиарда строк

**Act 1 — День 0, проектирование схемы (→ пьеса 01).** <PersonaTag id="sven" lang="ru" /> спрашивает <PersonaTag id="otto" lang="ru" />: «users(email, name, org_id).» Должен ли `email` быть `UNIQUE`? Должен ли `org_id` быть foreign key? Должен ли `prefs` быть отдельной таблицей или `JSONB`? Решения: `email` — это `UNIQUE NOT NULL CITEXT`. `org_id` — это `BIGINT REFERENCES orgs(id) ON DELETE CASCADE`. `prefs` — это `JSONB` с GIN-индексом когда поиск потребует. Цена: каждое позднее решение компонуется против этого baseline. Surrogate `id BIGSERIAL` изолирует от изменений email; нарушь правило (пропусти FK) только под давлением throughput, никогда по умолчанию.

**Act 2 — Неделя 1, 10K строк, первый медленный запрос (→ пьеса 02).** Email-search endpoint p95 растёт с 30 мс до 800 мс. <PersonaTag id="otto" lang="ru" /> видит что planner делает sequential scan. Sven запускает `CREATE INDEX users_email_idx ON users(email)`. Правило leading-column B-tree означает `WHERE email = ?` разрешается двумя page reads. p95 падает до 4 мс.

**Act 3 — Месяц 1, 100K строк, planner врёт (→ пьеса 03).** Половина запросов быстрые, половина 600 мс. `EXPLAIN ANALYZE` показывает что planner иногда выбирает seq-scan несмотря на индекс. Row estimate ошибается на 30×: stale statistics. `ANALYZE users;` перестраивает гистограммы; `pg_stat_statements` подтверждает worst-case plan исчез. Урок: planner выбирает планы из статистики, не из данных; maintenance статистики — это оперативная дисциплина.

**Act 4 — Месяц 6, тихий bloat (→ пьеса 04).** Nightly report runner держит одну транзакцию открытой четыре часа. `VACUUM` не может вернуть мёртвые tuples ниже `xmin`-горизонта. Таблица `users` вздулась с 200 MB до 80 GB. Vacuum логи показывают «removed 0 row versions» для long-running окна. Быстрое исправление: убей long transaction, установи `idle_in_transaction_session_timeout = 60s`, запусти `pg_repack` чтобы вернуть диск. Постоянное исправление: никогда не запускай reporting на OLTP базе — реплицируй на read replica.

**Act 5 — Year 1, 1M пользователей + 50 app pods, connection storm (→ пьеса 05).** Каждый pod имеет 20 workers, каждый открывает свой Postgres backend на cold-start. На момент pod-rollout кластер видит 1000 concurrent backends; kernel scheduler трасится; запросы которые были 4 мс становятся 4 с. PgBouncer развёрнут в transaction-mode перед Postgres: 100 server-side backends, 10000 client connections мультиплексированы. Trap: transaction-mode pooling ломает server-side prepared statements если PgBouncer < 1.21 без `server_prepared_statements`. Sizing math из пьесы 05: `pool_size = active_concurrent_transactions × safety_factor`, не `max_app_workers`.

**Act 6 — Year 2, миграция которая заморозила prod (→ пьеса 06).** День multi-tenancy. Миграция добавляет `tenant_id BIGINT NOT NULL`. Наивный `ALTER TABLE users ADD COLUMN tenant_id BIGINT NOT NULL DEFAULT 0` берёт `AccessExclusiveLock` и триггерит полную переписку таблицы. Prod замерзает на восемь минут. Рецепт expand-contract: (1) add nullable column без default, (2) backfill батчами, (3) add `CHECK (tenant_id IS NOT NULL) NOT VALID`, (4) `VALIDATE CONSTRAINT`, (5) `SET NOT NULL` (дёшево как только validated), (6) drop check. Builders как `pgroll` и `Atlas` кодифицируют рецепт.

**Act 7 — Year 3, 1B строк, hot shard (→ пьеса 07).** Citus rolled out. Shard key — `tenant_id`. Reads на большинстве tenants быстрые. Tenant `Acme` берёт 40% всех запросов. Acme's shard saturated пока остальные idle. Исправление — co-location: поместить `users`, `orgs`, `events`, `audit_log` на тот же shard key чтобы cross-tenant joins оставались local; затем либо (a) split Acme tenant через logical shards с tenant-aware router либо (b) move Acme на свой physical cluster. Online resharding (с `citus_rebalance_table_shards`) позволяет rebalance без downtime — но планируй окно потому что catch-up replication добавляет load.

  <Fragment slot="middle">
    <p><strong>Таблица семи стадий.</strong> Каждая строка — одна scale tier, один триггер, одна пьеса, один рычаг. День 0: проектирование схемы. Неделя 1: 10K строк, первый пропущенный индекс видим. Месяц 1: stale statistics, плanner ignores индекс. Месяц 6: bloat из long transactions блокирует vacuum. Год 1: pool saturation из connection. Год 2: migrations блокируют production. Год 3: один миллиард строк, single-node ceiling достигнут.</p>
    <p><strong>Act 1 деталь — схема irreversible на scale.</strong> Неправильный type (TEXT vs CITEXT для email) становится многодневной миграцией на 100M строк. Неправильный key (composite natural vs surrogate BIGSERIAL) делает каждый join дорогостоящим навсегда. Relational model награждает strictness с фронта: <em>NOT NULL по умолчанию</em>, FK constraints если ты не измерил throughput pressure, CHECK constraints на business invariants, и surrogate keys на external references. Нарушь правила только с доказательством — отключи FK на highest-write child таблицах если cost FK trigger превышает write budget, никогда как stylistic preference.</p>
    <p><strong>Act 2 деталь — индексы расплачиваются cost только на правильные columns.</strong> B-tree на `email` разрешает `WHERE email = ?` за O(log N) page reads. B-tree на `(org_id, created_at DESC)` разрешает "50 latest events для org" за two page reads. GIN индекс на `prefs jsonb` делает `WHERE prefs @> '{"theme":"dark"}'` lookup за 2 мс вместо 4 с seq-scan. Forgotten cost: каждый insert и update пишут в каждый индекс. Leading-column rule — most-violated principle в wild: `(b, a)` индекс не то же самое что `(a, b)` для queries которые фильтруют только по `a`. Cost ошибки здесь permanent: legacy apps через codebase наследуют bad column order, и любой attempt drop индекс для remediation рискует query regress в undocumented code paths.</p>
    <p><strong>Act 3 деталь — плanner выбирает plans из histograms.</strong> Postgres samples таблицу во время `ANALYZE` и builds histogram на column. Planner uses histograms для estimate row counts; cost model затем ranks plans. Когда statistics stale, estimates wrong. 1000× off estimate производит 1000× slower plan: planner выбирает nested loop expecting 10 rows; real cardinality 10000 rows; loop сканирует 10M индекс entries вместо одного hash join. Defence: `autovacuum_analyze_scale_factor = 0.05` на busy tables; `CREATE STATISTICS` для correlated columns; `pg_stat_statements` для find offending plans; `auto_explain.log_min_duration = 500ms` для tail-latency triage. Trap на scale: один bad estimate каскадирует; planner кеширует decisions, и human должен find и force replan вручную.</p>
    <p><strong>Act 4 деталь — MVCC и xmin horizon.</strong> Каждая row в Postgres имеет `xmin` (creation transaction id) и `xmax` (deletion transaction id). `DELETE` не освобождает row; это sets `xmax`. `VACUUM` reclaims rows чей `xmax` older чем global `xmin` horizon — oldest active transaction. Если один analyst session держит одну транзакцию открытой часами, horizon не advances, и no dead tuple created после того horizont не может быть reclaimed. Table swells; queries которые сканируют table становятся медленнее потому что читают dead rows. Fix operational: `idle_in_transaction_session_timeout = 60s`, `pg_stat_activity` alerts на `state = 'idle in transaction'` longer чем пять минут, и clear runbook killать offender. Long-running analytics должны быть на read replica. На 1B rows, одна idle session может bloat table на 10% в день.</p>
    <p><strong>Act 5 деталь — pool sizing math.</strong> Active concurrent transactions это load которая hits database одновременно; idle workers не active. Sizing rule: `pool_size = (cores × 2) + spindles`. Для 16-core SSD-only сервера, sweet spot обычно 30-60 backends; больше starves OS scheduler. App-side workers могут быть far higher; PgBouncer multiplexes их на small pool. Trap: transaction-mode pooling rebinds connections после каждой transaction, так что server-side prepared statements (`PREPARE foo AS SELECT ...`) теряются. PgBouncer 1.21+ ships `server_prepared_statements = on` который кеширует plan IDs server-side и replays их; без этого, app frameworks что auto-prepare statements платят re-prepare overhead на каждую transaction. Cold-start surge (app restart, deploy, failover) floods pool; connection handshake становится bottleneck прежде первый query executes.</p>
    <p><strong>Act 6 деталь — lock matrix.</strong> `ALTER TABLE` берёт `AccessExclusiveLock` по default — incompatible со всеми другими locks. Пока это waits для lock, каждый новый query waits позади него. Пока это holds lock, каждый query waits. Short ALTER под low load completes в milliseconds; ALTER позади long query (Act 4!) waits, builds queue, и queue freezes database. Expand-contract recipe sidesteps это splitting один big operation на many small lock-cheap ones. `ALTER TABLE ... SET NOT NULL` после successful `NOT VALID` constraint validation это metadata-only — milliseconds. Index creation это `CREATE INDEX CONCURRENTLY` — slower но no AccessExclusive. Discipline это treat каждую migration как production incident-in-waiting unless каждый step provably lock-cheap. Один 60-second lock на hot table может cascade в 10-minute incident из-за connection timeout и app-level retry storms.</p>
    <p><strong>Act 7 деталь — sharding choices.</strong> Три independent decisions. (1) Shard key: tenant_id (multi-tenant SaaS), user_id (consumer product), time bucket (time-series). High cardinality + uniform load + cheap to compute. (2) Distribution method: hash (even spread, range queries fan out), range (range queries local, hot range possible), list (manual), directory (most flexible, most operational cost). (3) Co-location: place tables что join together на same shard key так cross-shard joins дешёвые. Citus + Postgres declarative partitioning это pragmatic 2026 default. Schema-based sharding (one schema per tenant) shines для ≤ 1000 tenants но breaks down на 10000+ schemas из-за catalog overhead. Irreversible choice на Act 7: shard key, как только выбран, dictates resharding strategy forever. Wrong choice (e.g., shard by geography вместо tenant) означает multi-month reshard-heavy refactors.</p>
    <p><strong id="stage-tradeoffs">Семь-tier tradeoff cascade.</strong> Каждый act unlocks следующий, но только если ты nailed предыдущий. Skip Act 1 (schema) → Acts 2–7 fight losing battle против table-wide mutations и inefficient joins. Skip Act 2 (indexing) → Act 3 planning decisions made blind; stats useless если indexes не exist для planner выбирать. Skip Act 3 (stats) → Act 4 vacuum это only lever left; tables bloat пока ты guess cardinality. Skip Act 4 (MVCC/bloat) → Act 5 pool threads видят table scans slower; query latency climbs и triggers больше connection churn. Skip Act 5 (pool sizing) → Act 6 migrations starved по connection storms; release что needs миграция waits для capacity что never comes. Skip Act 6 (lock safety) → Act 7 sharding impossible; каждый shard rebalance это downtime event. Skip Act 7 (sharding) → один tenant dominates и остальные wait в queue. Order это не suggestion; это constraint imposed физикой и Postgres internals.</p>
    <p><strong id="scaling-stage-numbers">Cross-cutting числа и capacity limits.</strong> Index lookup cost: 5–50 microseconds в shared_buffers (L3 cache), 100 microseconds–2 milliseconds из OS page cache, 5–10 milliseconds из SSD, 50–500 milliseconds из network (warm standby или read-only replica). Heap fetch после index: same cost class. Sequential scan 1 GB: 1–3 seconds SSD-bound, пропорционально table size. P95 properly indexed point-lookup: under 5 milliseconds. P95 saturated connection pool (все backends active, no idle slots): seconds или timeout, exponential backoff в application code. Realistic OLTP write rate per backend: 5000 simple transactions в second на modern hardware. Realistic single-node ceiling для write-heavy workload перед sharding becomes only lever: 10–50 K writes/second sustained (depends на write complexity и concurrency). На 100 million rows, полный table scan takes 30–60 seconds на SSD. На 1 billion rows, полный scan takes 5–10 minutes; unplanned full scans cascade в long-running transactions и bloat. Table bloat growth: 1–10% per month на write-heavy workloads без autovacuum tuning. С proper tuning: 0.1–1% per month. С idle-in-transaction bugs: 50%+ per week.</p>
    <p><strong>Compound cost пропуска step.</strong> Team что omits Act 2 (indexing) discovers на Act 3 что queries slow; они blame planner и spend weeks tuning. Team что skips Act 4 (bloat ops) finds на Act 6 что их migrations take 30 minutes вместо 5 seconds потому что table bloated. Team что omits Act 5 (pool sizing) experiences mysterious timeouts на 2× expected QPS и spend месяц load testing. Cost late fix это exponential: Act 1 mistakes cost days; Act 7 mistakes cost months resharding. Это почему walk должен быть пройден по порядку.</p>
    <p><strong>Diagnostic tooling: твои eyes в каждый tier.</strong> Act 1 (schema) не имеет good tooling — ты must read table definition и trace migrations. Act 2 (indexes) visible в `pg_indexes`, но ты need `pg_stat_user_indexes` find unused ones. Act 3 (planning) это where `pg_stat_statements` и `EXPLAIN ANALYZE` dominate; slow_query_log tuning это prerequisite. Act 4 (bloat) requires `pg_stat_user_tables` (n_dead_tup vs n_live_tup) и `pg_table_size(...)` для actual disk usage; `pgstattuple` gives precise bloat percentage. Act 5 (pooling) monitored via `pg_stat_activity` (connection count, idle_in_transaction, state transitions) и PgBouncer's `SHOW STATS` (queue depth, avg. query time). Act 6 (migrations) requires `pg_locks` detect lock contention и `long_query_log` catch blockers. Act 7 (sharding) requires application-level metrics: tail latency по shard, write variance across shards, cross-shard join frequency. Missing или misinterpreted tooling это почему teams skip acts: "We can't see bloat" means autovacuum visibility off, не что bloat не exist.</p>
    <p><strong>Schema mistakes и их escape hatches.</strong> Surrogate key что не primary key causes join inefficiency — каждый foreign key reference это two-column tuple, и planner не может use efficiency SERIAL identity lookups. Fix: add PK после fact с `ALTER TABLE ... ADD CONSTRAINT ... PRIMARY KEY (...) NOT DEFERRABLE INITIALLY IMMEDIATE`, но это blocks все writes during scan; use `NOT DEFERRABLE` prevent transaction-mode evasion. Composite natural key (user_id, organization_id, email) что becomes PK means каждый join carries три columns; foreign keys replicate три columns. Fix: surrogate id дешевле на 1 BIGSERIAL vs 3 columns, но ты не можешь retrofit без миграции что rewrites table. Missing FK на child table means no referential integrity; data decays over time и queries что assume referential integrity produce wrong results. Fix: add FK retroactively, но ты must first fix orphaned child rows. Missing CHECK constraint на domain-specific column (e.g., status must быть один из ACTIVE, PENDING, ARCHIVED) means приложение это only guard; direct SQL update может create invalid state. Fix: add constraint, но ты must quarantine invalid existing rows и decide: delete, set default, или correct by hand.</p>
    <p><strong>Index selection и cost wrong choices.</strong> B-tree индекс на low-cardinality column (e.g., gender с 2 values или status с 5 values) это almost всегда waste; planner chooses seq-scan вместо, и index eats write throughput. Leading-column rule: index на (a, b, c) помогает queries что фильтруют по a, или по (a, b), или по (a, b, c), но NOT по b alone или c alone. Team что creates (user_id, created_at) satisfy "find events для user" затем later wants "find recent events by anyone" creates второй index (created_at) потому что первый не applies; они не realize третий index (created_at, user_id) would помочь обоим queries и planner would выбрать это based на query. JSONB indexes (GIN или GIST) это powerful но expensive на writes; JSONB column с 100K inserts/second может halve write throughput если ты index это. Partial indexes (e.g., `CREATE INDEX ... WHERE status != 'ARCHIVED'`) solve это для dimension tables но invisible teams unfamiliar с Postgres; они rediscover partial indexing years later и wonder почему они не использовали это earlier.</p>
    <p><strong>Planner statistics и forensics wrong plans.</strong> Planner's estimates это only как хороши как последний `ANALYZE`. На table с 1M rows и autovacuum_analyze_scale_factor = 0.1 (default), planner только re-analyzes после 100K new rows inserted. Если твоя table grows 1M rows в day, statistics stale в hours. Fix: set autovacuum_analyze_scale_factor = 0.01 или smaller на high-growth tables. Extended statistics (`CREATE STATISTICS`) помогают planner когда columns correlated; example: user_id и created_at correlated (new users created recently likely appear в recent data), и planner's histogram estimates assume independence. `CREATE STATISTICS col1, col2 ON user_id, created_at` teaches planner correlation. Planner также имеет work_mem limit (default 4MB) что affects sorts и hash joins; если estimates wrong и actual data requires больше work_mem чем available, query spills disk и becomes very slow. Fix: re-ANALYZE, или increase work_mem; ни один не является long-term solution.</p>
    <p><strong>Operational runbooks и escalation paths.</strong> Seven acts требуют разные operational disciplines. Act 1 (schema) requires schema review process перед table creation; cost post-launch review это months migrations. Act 2 (indexing) requires before-and-after query plan для каждый proposed index и monthly index utilization audit. Act 3 (planning) requires per-table autovacuum tuning и quarterly STATISTICS reviews; teams often leave default settings и wonder почему queries degrade. Act 4 (bloat) requires daily alerting rule: если n_dead_tup > 0.2 × n_live_tup или table_size > 1.5 × relation_size, page someone. Act 5 (pooling) requires connection metrics exported на observability platform и alerts на pool saturation (все backends active). Act 6 (migrations) requires runbook для every schema change: identify AccessExclusiveLock window, validate что expand-contract steps fit maintenance window, и co-ordinate с on-call be ready для rollback. Act 7 (sharding) requires quarterly resharding simulation на test data validate что chosen strategy scales к next 10× load. Teams что skip runbooks operate reactively: Act 1 mistakes surface как multi-day outages during peak season; Act 6 mistakes surface как 1-hour freezes что take down entire product.</p>
    <p><strong>Cross-shard queries и federation tax.</strong> Раз sharded (Act 7), queries что span multiple shards must быть federated: send query к каждый shard, collect results, и merge на application side. Naive outer join across два shards becomes два inner queries (one per shard) и client-side join. GROUP BY что involves shards becomes GROUP BY per shard, затем second GROUP BY на aggregates. Каждый cross-shard query имеет latency = max(latency per shard) + merge time; tail latency dominates. Citus handles это с distributed query planning, но только для `co-located` tables (те с same shard key). Reference table (replicating small dimension across все shards) это free; lookup table (replicated, immutable) costs replication time но amortizes over thousands queries. Teams что skip federation planning discover на Act 7+1 что их ORM generates single-shard queries efficiently но breaks на cross-shard ones; они spend weeks retrofitting query logic или restructuring data к co-locate tables.</p>
    <Misconception id="m-just-add-index" lang="ru">
      <strong>«Если медленно, добавь индекс.»</strong> Most common skip. Adding индекс когда stats stale wastes write throughput. Adding один когда bloated делает nothing — vacuum first. Когда hot shard queried, это не помогает. <em>Read plan first.</em> Индексы один lever из семи.
    </Misconception>

    <p><strong>Cross-cutting observability: USE + RED для Postgres.</strong> USE method (Utilization, Saturation, Errors) maps к: backend count vs `max_connections`, replication lag (`pg_stat_replication.replay_lag`), checkpoint pressure (`pg_stat_bgwriter.checkpoints_req` ratio), autovacuum lag (`pg_stat_user_tables.last_autovacuum`), buffer cache hit ratio (`pg_buffercache`). RED method (Rate, Errors, Duration) на top `pg_stat_statements`: queries/s per `queryid`, error rate из app logs (timeouts, deadlocks), p95/p99 duration. Together они tell тебе который lever pull. High backend count с low CPU это pooling problem (Act 5). High dead tuples с stable row count это vacuum problem (Act 4). Specific `queryid` с rising duration и stable plan_id это data-growth problem (Act 2 или 7).</p>

Skip Act 3 → ты имеешь index, но planner ignores это половину time; ты write runbook что says "если slow, restart Postgres" потому что flushes plan cache. Logs: structured (CSV или JSON) из Postgres itself, shipped via Vector/Fluent-bit к Loki или Elasticsearch. Slow-query introspection: `auto_explain` с `log_min_duration = '500ms'` для tail latency; `log_lock_waits = on` для lock cascades. Dashboards: Grafana с `postgres_exporter` и `pgwatch2` boards. Alerting: budget burn на 7-day rolling window для "% `pg_stat_statements` total time spent в queries slower чем 1 second."</p>

    <p><strong>XID wraparound и autovacuum freeze.</strong> Каждый row carries 32-bit transaction id; как только cluster reaches 2^31 transactions, ids wrap, и rows могут appear из future. Postgres protects против этого freezing old rows (rewriting `xmin` к special "frozen" value) перед wraparound. `autovacuum_freeze_max_age` это trigger. На write-heavy cluster (10 K TPS = 864 M transactions/day), freeze runs every ~2.5 days. Misconfiguration (very high `autovacuum_freeze_max_age`, e.g. 1B) может lead anti-wraparound emergency vacuums что lock database. Remedy в production: monitor `age(datfrozenxid)` per database, alert на 80% `autovacuum_freeze_max_age`.</p>

    <p><strong>Replication lag и read-replica gotchas.</strong> Async replication имеет unbounded lag under write load; sync replication trades latency для durability. Hot-standby read replicas serve reads на staleness bounded by `replay_lag`. Trap: long-running queries на replica delay WAL replay (recovery process must wait для snapshot release перед applying conflicting changes), creating cascading lag. Defence: `hot_standby_feedback = on` keep replica's `xmin` horizon pushed up к primary так vacuum не reclaim rows replica ещё needs — но это bloats primary вместо. Нет free lunch.</p>

    <p><strong>Sharded systems в 2026 — pragmatic choices.</strong> Citus это standard для Postgres-native sharding (CrunchyData, AWS RDS, Microsoft Azure CDB-for-PG). Vitess это standard для MySQL. Aurora DSQL (AWS, 2024) и Spanner (GCP) cover global ACID-on-distributed-storage если budget allows. CockroachDB и TiDB это NewSQL alternatives. Real-world: GitHub partitioned MySQL перед migrating critical paths к Vitess; Figma scaled с Vitess; Notion ran years на single very-large RDS Postgres и only recently considered Citus. 2026 default для новый Postgres-shop scaling past один node: declarative partitioning first (single node, fewer ops), Citus когда один node truly не может keep up, Aurora DSQL когда global writes это real product requirement.</p>

    <p><strong>Migration tooling landscape — 2026 snapshot.</strong> Atlas (Ariga), pgroll (Xata), Liquibase, Flyway, sqitch, golang-migrate, Prisma Migrate, Drizzle Kit, TypeORM migrations, Django migrations. Pragmatic 2026 stack для Postgres: `pgroll` для online schema changes (declarative expand-contract), Atlas для declarative schema diff + migration generation, Liquibase если твой shop это Java-heavy, и bespoke SQL files versioned с `golang-migrate` для всё что не fit. Avoid: `prisma migrate dev` в production (designed для dev loops, makes data-loss assumptions); blind `python manage.py migrate` на tables larger чем 1M rows.</p>

    <p><strong>Capacity planning для single Postgres перед sharding.</strong> Modern hardware (2026 Hetzner CAX21 или AWS r6g.4xlarge): 16 vCPU, 64 GB RAM, NVMe SSD, может sustain 30-50 K simple OLTP TPS, ~10 K complex transactions/s, 5-10 GB/s sequential read для analytics queries. Single-node ceiling для well-tuned Postgres: 50 K TPS, 1-5 TB data, 99.99% availability с one read replica. Past этого, sharding это only lever. Mental model: каждый order magnitude в scale adds новый operational concern. 1 TB это "мы should automate backups." 10 TB это "мы need recovery strategy." 100 TB это "мы need team."</p>

    <p><strong>Catalog overhead и schema-based sharding limits.</strong> Schema-based multi-tenancy ("one schema per tenant") works beautifully на low tenant count: clean isolation, easy backups, simple data export. Но Postgres catalog tables (`pg_class`, `pg_attribute`, `pg_constraint`) grow linearly с schema count × tables-per-schema. На 10000 schemas × 50 tables, `pg_class` имеет half million rows; planner walk-time на queries что touch multiple schemas climbs к seconds. Practical ceiling это 1000-3000 tenants per cluster с schema-based sharding. Past that, row-level multi-tenancy (`tenant_id` column на every table) с Citus shard distribution scales further.</p>

    <p><strong>Connection pooling в 2026 — landscape.</strong> PgBouncer remains standard (~50 K req/s per instance). Odyssey (Yandex) offers similar performance с hot-reload config. PgCat это Rust port с multi-tenant routing primitives. Supavisor (Supabase) это managed alternative для Postgres-as-a-service. 2026 default: PgBouncer 1.21+ для self-managed; managed pooling из твой cloud provider иначе. Antipattern: running pooler per app pod — defeats multiplexing.</p>

    <p><strong>Failure modes и их costs на scale.</strong> Act 1 failures (wrong schema) cost months migration work на scale; Act 2 failures (missing indexes) cost days emergency index tuning; Act 3 failures (stale stats) cost hours plan diagnosis; Act 4 failures (bloat) cost minutes query slowdown но hours remediation если unaddressed; Act 5 failures (pool saturation) cost seconds timeout storms но могут cascade в cascading application retries что amplify impact; Act 6 failures (lock contention) cost minutes database freeze; Act 7 failures (wrong shard key или no sharding когда needed) cost weeks или months data reshuffling. Cost ratio это exponential: early acts irreversible, later acts reversible но operationally expensive. Teams что skip early acts pay catastrophic costs later. Teams что over-engineer early acts (e.g., sharding 10 GB dataset) waste resources на problems что не exist yet. Art это knowing твой growth trajectory и cost tolerance, затем timing каждый act land just перед prior act's failure modes become production pain.</p>

    <p><strong>When NOT apply seven-act model.</strong> Model assumes traditional OLTP: rows in, rows out, queries что care о latency. Skip Act 2 entirely если твой queries analytical (full table scans by design); вместо, use columnstore indexes (Citus, Timescale) или materialized views. Skip Acts 1–6 если ты using managed cloud database что abstracts их (e.g., Aurora Serverless, Supabase). Skip Act 7 если твой traffic bursty и stateless (serverless functions querying managed database); database provider handles sharding и failover. Skip Act 3 если ты имеешь workloads где stale statistics не matter (write-only logs, append-only event streams). Seven-act walk это mental model для classical Postgres на scale, не dogma. Deeper skill это knowing когда apply это и когда step outside model entirely. Most teams operate на Acts 1–3; many никогда не reach Act 5 потому что их traffic stays ниже pool-saturation threshold; only hyperscale shops regularly face Acts 6–7. Твой job это know model well enough recognize который act ты in, затем decide whether next act это worth engineering cost right now.</p>

    <p><strong>Integration с rest curriculum.</strong> Этот piece sits на seam databases, performance (chapter 13), observability (chapter 11), и engineering practice (chapter 16). Каждый lever что ты pulled здесь имеет cousins elsewhere: caching (chapter 7) sits перед indexes и plans; queues (chapter 8) absorb write spikes что would иначе overwhelm Act 5's pool; distributed-systems (chapter 9) names consistency questions что drove Act 7's sharding decisions. Fullstack engineer's job это не just know Postgres но know который lever costs least на каждый layer система как whole.</p>
