Реляционная модель (<a href="/ru/databases/01-relational-model/">01-relational-model</a>) показала, как форматировать данные; этот фрагмент — про единственную практическую причину, почему эта форма вообще queryable. Индекс — это копия данных, отсортированная для ответа на один конкретный вопрос, и каждый индекс стоит storage и замедляет каждый write. Senior-инженеры выбирают индексы осознанно: какие вопросы горячие, какие сливаются в один composite, какие могут быть partial для экономии места, какой путь planner реально выберет. Самое нарушаемое правило в продакшне — leading-column rule: multi-column-индекс `(a, b, c)` ускоряет запросы фильтрующие по `a` (или `a, b`, или `a, b, c`), но не фильтрующие только по `b` или `c`. Этот фрагмент учит правилу, семействам индексов Postgres, редким случаям, где нужно что-то кроме B-tree, и операционной дисциплине добавления индексов без блокировки таблицы.

<Crux>Индексы = отсортированные копии данных под один вопрос. Leading-column rule. Каждый индекс облагает каждый write. Выбирай осознанно.</Crux>

Postgres поставляет шесть типов индексов: <em>B-tree</em> (дефолт, range и equality на упорядоченных типах), <em>Hash</em> (только equality, niche), <em>GIN</em> (inverted index под composite-типы — массивы, JSONB, full-text), <em>GiST</em> (generic search tree под geo и range), <em>SP-GiST</em> (space-partitioned, niche), <em>BRIN</em> (Block Range INdex под огромные insert-only таблицы с естественной упорядоченностью). B-tree обрабатывает 95% продакшн-работы. Другие типы важны, когда форма данных требует — JSONB нужен GIN, geo нужен GiST, time-series нужен BRIN, full-text нужен GIN. Знать, что под что — разница между 5мс запросом и 5-секундным. Оставшиеся 5% — partial, expression, covering, unique, multicolumn, concurrent index builds — где живут productivity-выигрыши.

    <p><strong>Зачем это нужно.</strong> Без индексов каждый запрос с фильтром или sort'ом трогает каждую строку. На 1M строк это медленно; на 100M — сломано. Индексы — то, как реляционная БД масштабируется от прототипа в продакшн.</p>

Урок: каждый WHERE, который приложение крутит горячо, нуждается в индексе, или ты узнаёшь об этом в худший момент.</p>

    <p><strong>B-tree: рабочая лошадка.</strong> Дефолтный тип Postgres. Сбалансированное дерево поиска, где каждый node — page (8KB) с отсортированным списком ключей и указателей на child-страницы (или на heap-строки на листьях). Range-scan'ы (`column = ?`, `column &gt; ?`, `column &lt; ?`, `column BETWEEN ? AND ?`, `column IN (?, ?, ?)`) — O(log n) плюс цена чтения матчевых листьев. Equality, range, sort (ORDER BY), LIKE с фиксированным префиксом (`'abc%'`) — всё отвечает B-tree. Для 100M-таблицы B-tree обычно ~4 уровня, и lookup — несколько page-read'ов. Размер индекса ~ bytes_per_key × rows × 1.3 (overhead). Под BIGINT (8 байт), 100M строк даёт ~1 GB индекс; под UUID (16 байт), ~2 GB.</p>
    <p><strong>Leading-column rule.</strong> Multi-column B-tree на `(a, b, c)` отсортирован первично по `a`, потом по `b` внутри равных `a`, потом по `c`. Индекс ускоряет: фильтр по `a` одному (отлично), `a, b` (отлично), `a, b, c` (лучше всего), `a` с range на `b` (отлично), или `a` с `ORDER BY b`. Индекс НЕ ускоряет фильтр только по `b`, только по `c`, или только по `b, c`. Это самое нарушаемое правило в продакшн-индексинге. Фикс: проектируй индекс под доминантный запрос, или создавай несколько индексов, если разные запросы требуют разных leading-столбцов. Composite-индексы дешевле двух отдельных, когда большинство запросов и так используют leading-столбец.</p>
    <p><strong>Index-only scan.</strong> Когда запрос читает только столбцы, присутствующие в индексе (key-столбцы плюс INCLUDE), Postgres может ответить без обращения к heap — «index-only scan». Для analytic-запросов на горячих данных — 10-100x ускорение против регулярного index scan (тот fetch'ит row из heap на каждый match). Подвох: Postgres также должен знать, что строка «visible» текущей транзакции (MVCC, piece 04). Visibility-check использует Visibility Map, обновляемую VACUUM'ом. Поэтому index-only scan работает только на recently-vacuumed таблицах. Используй INCLUDE для добавления payload-столбцов без включения в sort-key: `CREATE INDEX ON orders(user_id) INCLUDE (status, total_cents)`.</p>
    <p><strong>Partial-индексы.</strong> Partial-индекс — B-tree (или другой), построенный только над строками, матчащими WHERE. `CREATE INDEX ON orders(user_id) WHERE status = 'pending'` индексирует только pending-orders — обычно малую долю таблицы. Меньше индекс, быстрее lookup, дешевле writes (индекс трогается только когда status = 'pending'). Use cases: soft-delete (`WHERE deleted_at IS NULL`), feature-flags (`WHERE feature_x_enabled = true`), status-фильтры, где только один-два status'а запрашиваются горячо. Caveat: запросы обязаны включать WHERE-clause, чтобы planner использовал partial. Partial-индексы — один из самых недоиспользованных performance-рычагов Postgres.</p>
    <p><strong>Expression-индексы.</strong> Индекс на функции от столбцов, не на самих столбцах. `CREATE INDEX ON users (LOWER(email))` позволяет `WHERE LOWER(email) = 'alice@x.com'` использовать индекс — без expression-индекса вызов функции на каждой строке мешает использованию. Общие паттерны: case-insensitive поиск (LOWER, UPPER), date truncation (`DATE_TRUNC('day', created_at)`), JSON path extraction (`(data-&gt;&gt;'event_type')`), computed-values, матчащие форму запроса. Expression-индексы — как сделать functional-style запросы быстрыми без изменения схемы.</p>
    <p><strong>Unique-индексы.</strong> UNIQUE constraint реализуется как unique B-tree. Constraint и индекс — одна и та же физическая структура. Добавление UNIQUE через ALTER TABLE лочит таблицу; через CREATE UNIQUE INDEX CONCURRENTLY — не лочит (но дольше). Partial unique мощны: `CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL` форсит «email уникален среди не-удалённых» — позволяя soft-delete user'а, потом re-register того же email. Этот pattern невозможен с simple UNIQUE-constraint на email.</p>
    <p><strong>GIN: inverted index под composite-типы.</strong> Generalized Inverted Index. Где B-tree индексирует одно значение на строку, GIN индексирует много на строку — каждый ключ в JSONB, каждый element в массиве, каждый lexeme в tsvector. Use cases: JSONB containment (`data @&gt; '{"type":"login"}'`), array overlap (`tags && ARRAY['premium']`), full-text (`to_tsvector('english', body) @@ to_tsquery('term')`). GIN больше B-tree (типично 2-5x размера indexed-column данных) и медленнее на update (каждый row-update трогает каждое indexed-значение). Под high-write JSONB GIN-индекс может доминировать write-cost; в этом случае `fastupdate` опция откладывает index-maintenance в отдельный процесс ценой более медленных reads до consolidation.</p>
    <p><strong>GiST: generic search tree.</strong> Под данные, не подходящие B-tree-ordered-модели: geo (PostGIS использует GiST), range-типы (`tsrange`, `int4range`), nearest-neighbour. GiST расширяем — реализуешь несколько операторов, и engine использует custom GiST. На практике большинство инженеров встречают GiST через PostGIS (`CREATE INDEX ON locations USING GIST (geom)`) под «найти точки на дистанции D от точки P».</p>
    <p><strong>BRIN: под огромные insert-only таблицы.</strong> Block Range INdex. Хранит summary-инфу per-block-range (дефолт 128 страниц, ~1MB): min/max indexed-столбцов в этом range. Чтобы ответить на запрос, Postgres читает BRIN для поиска candidate-ranges, потом сканит только эти блоки. BRIN крошечный (килобайты на миллиарды строк) и быстрый в maintenance — но полезен только когда данные физически clustered по indexed-столбцу. Классический use case: time-series, строки вставляются в time-order, индекс на `created_at`. BRIN превращает 10TB time-series в queryable на дешёвом железе. Бесполезен на randomly-distributed-данных.</p>
    <p><strong>Hash-индексы.</strong> Исторически сломаны в Postgres (no WAL до Postgres 10), сейчас стабильны. Полезны под equality-lookup на очень больших indexed-столбцах, где B-tree-размер был бы проблемой — но на практике B-tree почти всегда предпочтительнее (поддерживает range и ORDER BY). Узкая ниша; дефолт B-tree.</p>
    <p><strong>Bloom-индексы под multi-column equality.</strong> Расширение `bloom` даёт probabilistic-индекс, поддерживающий equality на многих столбцах одновременно, без leading-column-rule. Bloom на (a, b, c, d, e) ускоряет любой запрос с фильтром по любому подмножеству. Trade: approximate — каждый match — кандидат, пере-проверяемый против heap, false positive возможны. Use case: таблицы с много столбцами, где запросы непредсказуемо комбинируют разные filter-set'ы; альтернатива построению 2^N composite. Niche, но мощно при правильном fit.</p>
    <p><strong>HOT-updates и fillfactor.</strong> При UPDATE Postgres обычно создаёт новую tuple-версию (MVCC) и обновляет каждый индекс, ссылающийся на строку — даже индексы с unchanged-столбцами. HOT (Heap-Only Tuple) скипает index-update полностью, когда (a) ни один indexed-столбец не изменился, И (b) на heap-page достаточно места для новой tuple-версии. HOT режет write-overhead резко на update-heavy workloads. Fillfactor (процент заполнения page на insert, дефолт 100 таблицы / 90 B-tree) оставляет место для HOT; ставить fillfactor 70-80 на update-heavy таблицах гарантирует HOT-trigger. Trade — initial-storage; продакшн-команды меряют update-frequency и тюнят fillfactor — часто упускаемый рычаг.</p>
    <p><strong>ANALYZE важнее индексов.</strong> Выбор planner'а индекса (или его отсутствия) зависит от table-statistics — row-count, value-distribution, correlation. ANALYZE (автоматически autovacuum'ом, вручную при необходимости) собирает их. Без свежей stats planner недо- или переоценивает, сколько строк match'нет filter, и выбирает не тот план. Продакшн-дисциплина: запускать ANALYZE после bulk-insert, после больших UPDATE, после schema-changes, влияющих на distribution; тюнить autovacuum_analyze_scale_factor ниже на skewed-таблицах; использовать CREATE STATISTICS для коррелированных столбцов (country + city), чтобы planner не предполагал independence. «Wrong index choice» часто на самом деле «stale stats».</p>
    <p><strong>Index-overhead на каждый write.</strong> Каждый insert/update/delete на indexed-столбец требует update индекса. Цена per-индекс — 5-50 микросекунд depending on index-type, fillfactor, и whether HOT-update triggers. Для таблицы с 10 индексами каждый INSERT стоит 50-500 μs в overhead'е помимо самой записи в heap. Под write-heavy workload (например audit-log на 10k inserts/sec) это difference между 5k и 50k inserts/sec capacity. Дисциплина: считай write-cost при добавлении индекса. Если новый индекс ускорит запросы 100x но добавит 20% write-overhead, и таблица read-heavy — победа. Если таблица write-heavy и индекс ускоряет редкий запрос — проиграл. Senior-команды моделируют budget: каждая таблица имеет write-throughput-target, и index-set обязан укладываться. Tools: pg_stat_statements + pgbench для baseline'а; benchmarks под новый индекс до production-deploy.</p>
    <p><strong>Размер индекса и shared_buffers.</strong> Postgres кеширует hot-pages в shared_buffers (типично 25% RAM сервера). Index-pages, обращающиеся часто, остаются hot; cold-pages вытесняются. Большие индексы (GIN на huge JSONB, composite на wide-columns) могут вытеснять более ценные heap-pages. Симптом: shared_buffers cache-hit-ratio дропает (pg_stat_database.blks_hit / blks_read); запросы, ранее быстрые из cache, становятся disk-bound. Mitigation: измерь индекс-размеры vs shared_buffers; при доминировании одного индекса cache'ом — рассмотри: partial вместо full, expression вместо нескольких composite, drop неиспользуемых. Index-size — не invisible cost; он конкурирует за RAM с heap.</p>
    <p><strong>EXPLAIN ANALYZE: единственный способ verify.</strong> EXPLAIN показывает plan, который planner намерен использовать; EXPLAIN ANALYZE реально запускает запрос и показывает actual numbers — rows, timing, buffers. Без ANALYZE ты смотришь на estimates, которые могут быть off из-за stale stats. Под подозрительный запрос: EXPLAIN (ANALYZE, BUFFERS) показывает page-reads из shared_buffers vs disk — large disk-read и hint, что данные cold или индекс не cache-friendly. EXPLAIN (ANALYZE, FORMAT JSON) даёт machine-parsable вывод под dashboards. Production-команды интегрируют EXPLAIN в slow-query workflow: pg_stat_statements находит топ-запросы, ручной EXPLAIN на realistic params, design-fix, deploy, повторный EXPLAIN. Без EXPLAIN ты гадаешь. С EXPLAIN ты знаешь.</p>
    <p><strong>Concurrency и index-build на больших таблицах.</strong> CREATE INDEX CONCURRENTLY на 100M-table занимает 10-30 минут. Во время build: (a) Postgres сканит таблицу дважды; (b) ждёт окончания всех текущих транзакций между фазами; (c) standby реплицирует индекс через WAL. Импликации: long-running транзакции на той же таблице блокируют завершение build; убедись, что reporting-queries или migration-jobs не блокируют. Если build падает, индекс остаётся INVALID — pg_indexes.indisvalid = false; запросы не используют его. Recovery: DROP INDEX CONCURRENTLY + retry. Production-pattern: monitor pg_stat_progress_create_index для in-flight builds; alert на duration over expected; в runbook'е — «check indisvalid после deploy»; integration-test после migration verifying новый индекс работает в реальном EXPLAIN. Дополнительно: на shared production-database координируй timing build'ов между командами — несколько concurrent builds одновременно конкурируют за I/O и могут drastically замедлить друг друга, особенно на устройствах с ограниченной IOPS-budget. Schedule больших index-build'ов в low-traffic windows.</p>

  <Fragment slot="senior">
    <p><strong>Index-only scan и visibility-map.</strong> Index-entry хранит column-values + TID (Tuple Identifier — физический адрес строки в heap). Postgres-строки имеют visibility-info per-tuple (transaction-id, создавший и удаливший); чтобы знать, visible ли строка текущему snapshot'у, engine обычно fetch'ит строку из heap. Index-only scan избегает heap-fetch — но только если engine может verify visibility из индекса. Не может: индекс не несёт visibility-info. Вместо этого Postgres consults Visibility-Map (VM), per-table-bitmap с одним bit per heap-page, indicating «все tuples на этой page visible всем транзакциям». VACUUM ставит VM-bits. Любой write на page clears. Импликации. (1) Insert-only / append-mostly таблицы остаются near-fully-visible — index-only всегда работает. (2) Heavily-updated таблицы clear VM-bits часто — index-only деградирует до регулярного index-scan (heap-fetch на строку). (3) Long-running транзакции holdback vacuum и мешают VM-updates — chronically плохой index-only обычно tracе'ится в одну long transaction. Mature-команды тюнят autovacuum aggressive на таблицах, зависящих от index-only, и мониторят pg_stat_user_tables.n_dead_tup как leading-indicator.</p>
    <p><strong>INCLUDE и covering-индексы.</strong> Postgres 11+ поддерживает `CREATE INDEX ... INCLUDE (cols)` — INCLUDE-столбцы хранятся в leaves, но не в sort-key. Результат: индекс «covering» под запросы с extra-projection, enabling index-only scan без force'инга included-столбцов в sort. Use case: запрос фильтрует по workspace_id, sort'ит по created_at, projects id, total — build `(workspace_id, created_at DESC) INCLUDE (id, total)`. Sort обслуживается key-столбцами; projection — included; no heap-fetch.</p>
    <p><strong>Postgres index-types в деталях.</strong> (a) B-tree internal: pages linked в sibling-list на каждом уровне под efficient range-scan; последние Postgres-версии реализуют «bottom-up index deletion», удаляющую dead-entries на hot pages без ожидания vacuum, резко уменьшая bloat на UPDATE-heavy. (b) GIN structure: inverted-index, где каждый indexed-key мапится в posting-list (или posting-tree) TID, содержащих этот key. Fastupdate-mode буферит pending-entries и merges периодически — быстрее writes, медленнее reads когда buffer full. (c) GiST structure: generalized search-tree, где каждый non-leaf-node хранит «predicate», summarising subtree (bounding-box для geo). Engine использует predicates для prune subtrees. (d) BRIN structure: per-block-range summary-tuples (min, max, null-bitmap дефолтно); intentionally lossy — narrow'ит heap-scan, не eliminate. (e) SP-GiST: как GiST, но space-partitioning (quadtree, k-d-tree); narrow-use IP-ranges и CIDR-matching. (f) Hash: equality only; полезно при очень широких ключах.</p>
    <p><strong>Operator-classes и custom-operators.</strong> Каждый index-type поддерживает набор операторов, определённых operator-class'ами. B-tree default op-class под TEXT делает lexicographic-compare; `text_pattern_ops` отключает locale-aware sorting и делает LIKE-prefix (`column LIKE 'abc%'`) использующим индекс. Custom op-classes — как делаешь complex-типы indexable; PostGIS, pg_trgm (trigram fuzzy), pgvector (embedding similarity), pg_bigm (bigram под CJK) — все поставляют op-classes, позволяющие GiST/GIN/B-tree/HNSW индексировать data-types. Senior-команды используют operator-class selection, чтобы делать необычные запросы быстрыми без изменения query-shape.</p>
    <p><strong>Index-maintenance: REINDEX, bloat, fillfactor.</strong> Индексы накапливают dead-entries. Postgres 14+ агрессивно cleanup'ит через bottom-up deletion, но heavy-update таблицы всё равно выигрывают от periodic REINDEX CONCURRENTLY. Fillfactor (дефолт 90 под B-tree) оставляет место в leaf-page под in-place-updates (HOT — piece 04), уменьшая page-splits и замедляя bloat. Ниже fillfactor (70) уменьшает bloat ценой большего initial-size. Дисциплина: мониторить pg_stat_user_indexes на idx_scan = 0 (drop) и высокий idx_tup_read / idx_tup_fetch (stale stats или плохая selectivity). Schedule monthly REINDEX CONCURRENTLY на hot-индексах.</p>
    <p><strong>Index-стратегия с replicas и standby.</strong> Индексы на primary реплицируются на standby через WAL — каждый CREATE INDEX, каждый index-write — поэтому standby имеют те же индексы. CREATE INDEX CONCURRENTLY на primary не блокирует reads на standby, но standby не может обслуживать запросы, конфликтующие с index-build (редко). Replicas могут иметь read-only-specific индексы через `EXTERNAL` index option в pglogical, но stock Postgres реплицирует схему verbatim. Под OLTP + OLAP в одном Postgres канонический pattern — primary с OLTP-tuned индексами + logical-replication analytics-copy, где OLAP-specific индексы (часто BRIN, GIN или wide composite) живут.</p>
    <p><strong>HNSW под vector-similarity (pgvector).</strong> Postgres 16+ с pgvector поддерживает HNSW (Hierarchical Navigable Small World) под approximate nearest-neighbour search на embedding-векторах. HNSW не B-tree-variant — graph-based index под high-dimensional similarity. Trade: индексы большие (vector-dimension × row-count), writes медленные (graph-rebalancing на insert), но запросы на 1M+ embedding возвращаются за единицы миллисекунд. Под продакшн-AI/ML 2026 с Postgres как primary store, pgvector + HNSW — канонический выбор; альтернативы — Pinecone, Weaviate, Milvus как dedicated vector-БД при scale или feature-requirements за пределами pgvector.</p>
    <p><strong>Реальные продакшн-failure-modes.</strong> (a) <em>Missing index on FK column</em>: FK-столбцы не индексируются автоматически; CASCADE delete делает Seq Scan на child, что занимает часы. Mitigation: индексировать каждый FK. (b) <em>Implicit type coercion bypasses index</em>: WHERE bigint_column = '42' форсит type-convert на каждую строку. (c) <em>Stale statistics</em>: planner выбирает Seq Scan, недооценивая индекс; ANALYZE. (d) <em>Bloated index</em>: индекс в 5x больше ожидаемого; REINDEX CONCURRENTLY. (e) <em>Index-only disabled by recent updates</em>: VM partially clear; VACUUM. (f) <em>Composite с wrong column order</em>: redesign composite или add second. (g) <em>Cardinality bomb in JSONB GIN</em>: JSONB с миллионами unique-keys создаёт огромный GIN; рассмотри expression-индексы под known-hot fields.</p>
    <p><strong>Index-audit playbook.</strong> Квартально каждая команда на Postgres-масштабе обязана делать index-audit. (1) Drop unused: SELECT indexrelname FROM pg_stat_user_indexes WHERE idx_scan = 0 AND indexrelname NOT LIKE '%_pkey'. (2) Find bloat: pgstattuple_approx() на hot-индексах; REINDEX CONCURRENTLY на bloated. (3) Find missing: pg_stat_statements join'нутый с EXPLAIN на top-N по total_time; любой Seq Scan на большой таблице — кандидат. (4) Find redundant: индексы, чьи key-столбцы — prefix другого — drop shorter. (5) Verify VM-health под index-only: monitor pg_stat_user_tables.n_dead_tup. Аудит — 1-2 часа работы и routinely даёт 10-30% storage savings + 2-5x write-rate improvements на heavily-indexed.</p>
    <p><strong>Стратегическая поза: индексы — часть дизайна.</strong> Самая частая продакшн-perf-проблема в постмортемах — «отсутствует индекс на горячем запросе». Вторая — «у нас слишком много индексов, и writes медленные». Обе — одна root-cause: индексы не трактовались как часть design. Senior-команды добавляют индексы в migration, ship'ящую feature; ревьюют индексы в code-review рядом с query; аудитят квартально; владеют index-стратегией на platform-уровне. Цена сделать правильно мала (extra checklist-item на PR с SQL); цена ошибки — 3am-page при timeout customer-дашборда.</p>
    <p><strong>Per-environment index-strategy: dev vs staging vs prod.</strong> Индексы, оптимальные на dev (1k строк) — не те же, что на prod (100M строк). На dev seq-scan быстрый и индекс может быть лишним overhead'ом; на prod тот же запрос без индекса — incident. Mature-команды: (1) держат realistic data-size на staging (хотя бы 10% prod) для верификации EXPLAIN-планов; (2) тестируют CREATE INDEX CONCURRENTLY на staging до prod-migration, чтобы измерить duration; (3) перед каждым PR с новым SQL — EXPLAIN ANALYZE на staging с production-like volume; (4) post-deploy мониторинг — pg_stat_statements show new query patterns, индекс-coverage tracking. Без realistic-staging index-decisions делаются вслепую и проявляются в production как outages.</p>
