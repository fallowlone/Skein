MVCC (<a href="/ru/databases/04-mvcc-isolation/">04-mvcc-isolation</a>) показал, что каждая транзакция держит свой снимок и долгая транзакция тормозит VACUUM; этот фрагмент про то, что транзакции держат и кое-что более видимое — backend Postgres, тяжеловесный процесс ОС — и про то, что команды строят, чтобы амортизировать его стоимость на множество клиентов. Postgres использует модель «процесс на соединение»: каждое соединение порождает backend, потребляющий 5-10 МБ RSS, занимающий слот в shared memory и счётчик max_connections (по умолчанию 100). При ~10 серверах × 50 клиентских соединений каждый — 500 backend дерутся за те же 100 слотов. Стандартный фикс — connection pooler — PgBouncer канонический, плюс Supavisor, Odyssey и PgCat как современные альтернативы — между приложением и Postgres, мультиплексирующий тысячи клиентских соединений на гораздо меньший пул backend. Цена: часть session-семантики (SET, LISTEN, session-level advisory locks, классический SQL PREPARE) перестаёт работать в transaction mode — единственном режиме, который имеет смысл в продакшне для типичного OLTP. Senior-команды проектируют вокруг этих ограничений; режим отказа невидим, пока исчерпание пула не уронит дашборд в 3 ночи.

<Crux>Backend Postgres тяжёлый. Пулинг мультиплексирует. Transaction mode ломает SET / session prepare / advisory locks без адаптации.</Crux>

В современных стеках пул соединений двухслойный. <em>Client-side pool</em> (HikariCP для Java, `Pool` node-postgres для Node, asyncpg для Python, ActiveRecord CP для Rails) живёт внутри процесса приложения и кэширует небольшое количество (5-20) TCP-соединений на worker. <em>Server-side pooler</em> (PgBouncer, Supavisor, Odyssey, PgCat) — отдельный процесс — обычно соседствует с Postgres — принимающий тысячи клиентских соединений и маршрутизирующий их на маленький пул backend. Сочетание делает 10 000 клиентских приложений жизнеспособными на Postgres с 100 max_connections: каждый worker имеет ~10 соединений к PgBouncer (дёшево, ~2KB на слот), PgBouncer в свою очередь открывает 20-50 реальных backend к Postgres. Средний слой превращает стоимость соединения из «дорогой setup на каждый запрос» в «бесплатный pool checkout». Этот фрагмент учит режимам, математике и режимам отказа — и показывает, почему «поднять max_connections» почти всегда неправильный ответ.

    <p><strong>Одно предложение.</strong> Connection pool — это кэш открытых TCP-соединений к Postgres, которые ваше приложение переиспользует вместо открытия нового соединения для каждого запроса.</p>
    <p><strong>Почему важно.</strong> Открытие соединения к Postgres дорого: TCP handshake + TLS handshake + Postgres protocol startup + аутентификация + создание серверного backend процесса. Это 5-50 мс на новое соединение и ~10 МБ памяти на backend, которые база должна выделить. Делать это на каждый веб-запрос превращает БД в узкое место. Пул амортизирует стоимость: открыли при старте, переиспользуем на тысячи запросов.</p>
    <p><strong>Метафора.</strong> Стоянка такси против вызова Uber на каждый квартал. Стоянка (пул) — несколько машин ждут, готовы ехать; подошёл, сел, доехал, вернул. Время поездки = собственно поездка. Uber на каждый квартал: ждёшь, пока приложение найдёт водителя, ждёшь приезда, едешь. Большая часть времени — диспетчер. Connection pool — стоянка такси: несколько соединений держатся открытыми и готовы быть взятыми под следующий запрос.</p>
    <p><strong>Отто и Свен.</strong> <PersonaTag id="otto" lang="ru" /> пишет Node.js endpoint `new Client(); client.connect(); await client.query(...); client.end();` на каждый запрос. P99 = 80 мс — большая часть это connect. <PersonaTag id="sven" lang="ru" /> говорит «используй пул». Отто переходит на `const pool = new Pool({ max: 10 }); pool.query(...)`. P99 падает до 4 мс. Пул держит 10 соединений с момента старта; каждый запрос их checkout-runs-returns. Никакого per-request handshake.</p>
    <p><strong>Один сценарий.</strong> Команда масштабирует приложение с 4 worker до 40. У каждого worker client pool `max: 20`. Итого соединений к Postgres: 40 × 20 = 800. У Postgres `max_connections = 100`. Результат: 700 попыток получают `FATAL: sorry, too many clients already`. Приложение падает. Фикс: PgBouncer между приложением и Postgres. Worker подключаются к PgBouncer (дёшево, тысячи ок), PgBouncer открывает максимум 50 реальных backend. Итого backend Postgres: 50. Приложение работает; база здорова.</p>

    <p><strong>Три режима пулинга PgBouncer.</strong> <em>Session mode</em>: backend арендуется клиентом на всё время соединения клиента. Работает всё — SET, LISTEN, session-level advisory locks, temp tables, классический SQL PREPARE — потому что backend действительно принадлежит клиенту на всю сессию. Минус: PgBouncer почти не мультиплексирует в этом режиме: соединения клиент:backend 1:1, только PgBouncer делает auth и queue. <em>Transaction mode</em>: backend арендуется клиентом только на одну транзакцию (BEGIN..COMMIT или один autocommit statement). Между транзакциями backend возвращается в пул и может попасть к другому клиенту на следующий BEGIN. Это режим с настоящим мультиплексированием — приложение на 10 000 клиентов работает на 20-50 backend. Цена: любое session state (SET LOCAL OK; SET — нет; LISTEN не работает; session-level advisory locks теряют владельца между транзакциями; temp tables persist некорректно) ломается. <em>Statement mode</em>: backend возвращается после каждого statement. Multi-statement транзакции запрещены. Используется почти исключительно для PL/Proxy-стиля шардирования; не общего назначения.</p>
    <p><strong>Контракт transaction mode.</strong> Переход с session на transaction mode — самое высоко-leverage изменение производительности для Postgres-backed сервиса — и требует от приложения соблюдения правил. (1) Никаких SET вне транзакции (используйте SET LOCAL внутри или дефолты на уровне роли через ALTER ROLE). (2) Никаких SQL-level PREPARE/DEALLOCATE (используйте protocol-level prepared statements через PQprepare libpq или эквиваленты драйвера — PgBouncer 1.21+ поддерживает). (3) Никаких LISTEN/NOTIFY между транзакциями (используйте отдельное соединение в session mode или отдельный notification service). (4) Session-level advisory locks (pg_advisory_lock) не переживают границы транзакции — используйте transaction-level (pg_advisory_xact_lock). (5) Temp tables, созданные в одной транзакции, могут быть невидимы в следующей — продвигайте до настоящих таблиц или используйте ON COMMIT DROP. Самый частый production-баг: «мы переключились на transaction mode и SET search_path перестал работать» — фикс через `ALTER ROLE app SET search_path = ...`.</p>
    <p><strong>Стоимость модели «процесс на соединение» Postgres.</strong> Каждое соединение порождает backend (~10 МБ резидентной, ~1-2 МБ приватной памяти; shared_buffers и другая shared memory mapped, не дублируются). 1000 backend ≈ 1-2 ГБ приватной памяти + overhead в proc-table ядра — терпимо на большом железе, болезненно на маленьких инстансах. Но большая стоимость — планирование: больше backend = больше context switch, больше lock manager contention на shared структурах (procarray, lock table). Postgres деградирует нелинейно после пары сотен активных backend; throughput часто пикует около `(CPU cores × 2) + effective_spindles` и падает после. Популяризованная HikariCP формула: `connections = (core_count × 2) + effective_spindle_count` — где effective_spindle_count примерно 0 для полностью закешированных датасетов и равен числу независимых дисков иначе. На 16-ядерной машине с данными в RAM оптимальное число активных backend ~32, не 200.</p>
    <p><strong>Размер client pool.</strong> Размер per-worker зависит от формы нагрузки: сколько вызовов БД на запрос, как долго каждый, насколько параллелен worker. Правило: `worker_pool_size ≈ concurrent_requests × db_calls_per_request × avg_query_ms / request_budget_ms`. Для Node.js worker на 100 параллельных запросов с 2 вызовами БД по 5 мс при бюджете 50 мс — пул нужен ≈ 100 × 2 × 5 / 50 = 20 соединений. С 10 worker всего клиентских = 200. Без server pooler эти 200 идут прямо в Postgres — нормально для Postgres, если `max_connections >= 250` (200 + запас). С PgBouncer в transaction mode эти 200 клиентских мультиплексируются на 20-40 реальных backend, потому что большинство idle большую часть времени.</p>
    <p><strong>Исчерпание пула и очереди.</strong> Когда все соединения пула вылетели и приходит новый запрос, пул либо ждёт (с timeout), либо отвергает (`PoolExhaustedError` или эквивалент). Типичные причины: (1) долгие запросы, держащие соединение — обычно отсутствующий индекс или огромный аналитический запрос; (2) idle-in-transaction — приложение открыло транзакцию и не сделало COMMIT/ROLLBACK из-за бага или обрыва сети; (3) всплеск трафика — параллельный спрос превышает steady-state размер пула; (4) downstream замедление — сторонний API в том же запросе держит соединение секундами. Симптомы: всплески P99; ошибки типа «connection pool timeout» или «too many connections»; очереди растут; в логах PgBouncer растёт `cl_waiting`. Инструменты: pg_stat_activity (каждый backend, что делает), pg_stat_statements (топ запросы по total_time), SHOW POOLS PgBouncer (active / waiting / idle на БД).</p>
    <p><strong>Idle-in-transaction — тихий убийца.</strong> Backend в состоянии `idle in transaction` держит соединение без полезной работы — но также держит row locks, MVCC snapshot и блокирует VACUUM. В пуле также не отдаёт соединение. Один баг, открывающий транзакцию и забывающий COMMIT на error path, сливает 20-соединительный пул за секунды. Митигации. (1) `idle_in_transaction_session_timeout` (Postgres GUC, например 60 с) — Postgres прерывает backend, idle in transaction дольше порога. (2) Код приложения: транзакции в try/finally; ROLLBACK на любое необработанное исключение; не вызывайте внешние API внутри транзакции. (3) PgBouncer `server_idle_timeout` и `query_wait_timeout`. (4) Мониторинг: алерт на `pg_stat_activity` где state = 'idle in transaction' и xact_start старее ~10 секунд.</p>
    <p><strong>Ловушка prepared statements в transaction mode PgBouncer (и фикс 2024).</strong> До PgBouncer 1.21 (выпуск март 2024) protocol-level prepared statements (driver-managed `PrepareStatement`, `prepare:true`) и transaction mode были несовместимы: клиент подготовил statement на backend A, а следующий EXECUTE попал на backend B, который этот statement не знал. Драйвер получал «prepared statement does not exist». Обход: отключить prepared statements в драйвере — теряя 10-30% производительности — или использовать session mode. PgBouncer 1.21+ добавил protocol-level prepared statement tracking: `max_prepared_statements > 0` позволяет PgBouncer переписывать имена statement, re-prepare на любом backend, на который попал клиент, и обслуживать кешированные планы прозрачно. Postgres 17 (сентябрь 2024) добавил серверную поддержку для DEALLOCATE через протокол, закрывая последний пробел. Как 2026 — transaction mode + prepared statements — production-дефолт; проверьте, что PgBouncer ≥ 1.21 и `max_prepared_statements` установлен (например, 1000), и получаете оба выигрыша одновременно.</p>
    <p><strong>Ландшафт server-side pooler в 2026.</strong> <em>PgBouncer</em> по-прежнему рабочая лошадка: маленькая память (2KB на пул-соединение), однопоточный, проверенный, де-факто стандарт. Версии 1.21+ добавили поддержку prepared statements; 1.22+ улучшения TLS и observability. <em>Supavisor</em> (Supabase): cloud-native, multi-tenant, Elixir, для serverless edge — миллионы входящих соединений, мультиплексируемых на Postgres. <em>Odyssey</em> (Yandex/Tarantool): multi-threaded C, нативная поддержка prepared statements, в бенчмарках самый низкий CPU и самый высокий throughput при 50+ параллельных клиентах. <em>PgCat</em>: Rust, добавляет load balancing на read replicas и query routing поверх пулинга. Дефолт в большинстве стеков — PgBouncer (хорошо понимается); Supavisor или Odyssey, когда вы перерастаете однопоточность PgBouncer; PgCat, когда нужен routing и хочется один компонент.</p>
    <p><strong>GUC жизненного цикла соединений PgBouncer.</strong> Ключевые ручки: `pool_size` (целевой пул backend на БД, дефолт 20), `default_pool_size` (fallback, если не на БД), `max_client_conn` (лимит входящих клиентов всего, дефолт 100), `reserve_pool_size` (дополнительные backend при устойчивой нагрузке), `reserve_pool_timeout` (сколько ждать до использования резерва, дефолт 5 с), `server_lifetime` (ротация backend каждые N секунд для ограничения роста памяти, дефолт 3600), `server_idle_timeout` (закрытие idle backend через N секунд, дефолт 600), `query_wait_timeout` (отвергать запросы, ждущие дольше, дефолт 120 с), `server_reset_query` (DISCARD ALL между арендами, обязательно для безопасности transaction mode при некоторых setup). Senior-тюнинг: `pool_size` ≈ target активного DB concurrency (не 1:1 с worker — leverage мультиплексирования); `max_client_conn` = щедро (тысячи ок); `server_reset_query = DISCARD ALL` если может протекать state; алерты на `cl_waiting` и `pool_exhausted`.</p>
    <p><strong>Подсказка: пулинг — слой, не замена.</strong> Правильная архитектура: client pool приложения → PgBouncer → Postgres, а не «или одно, или другое». Client pool кеширует соединения внутри процесса (бесплатно на hot path, нет socket setup); PgBouncer мультиплексирует между процессами (превращает 10 000 клиентских в 20 backend). Убрать client pool: каждый запрос открывает свежее TCP к PgBouncer — быстро (PgBouncer локально), но всё равно TCP setup. Убрать PgBouncer: client pool говорит напрямую с Postgres — норм для маленького приложения, фатально на масштабе.</p>
    <p><strong>Практический рабочий цикл диагностики пула.</strong> Первый взгляд на инцидент исчерпания — всегда `SHOW POOLS` в PgBouncer админ-консоли: соотношение `cl_active / cl_waiting / sv_active / sv_idle` сразу говорит, переполнен ли пул запросами или клиенты ждут свободного backend. Если `cl_waiting > 0` и `sv_active == pool_size` — все backend в работе и клиенты в очереди; смотрим в `pg_stat_activity` GROUP BY state, чтобы понять, что эти backend делают (active = слишком много долгих запросов, idle in transaction = код приложения держит транзакции). Второй взгляд — топ-N pg_stat_statements по mean_exec_time × calls: запросы, дающие самую большую совокупную работу, и есть кандидаты на оптимизацию. Третий — application traces: для каждой долгой транзакции мы хотим знать, что между BEGIN и COMMIT — обычно это внешний HTTP-вызов, синхронный SQS-publish или ожидание мьютекса. Без трейсов диагностика останавливается на «pg_stat_activity показывает idle in transaction» без понимания, какой endpoint виноват.</p>
    <p><strong>Code-review для пулинга.</strong> Senior-команда добавляет в чек-лист PR несколько вопросов про пулинг. (1) Открывает ли PR транзакцию вокруг операции с неизвестной длительностью (внешний HTTP, очередь, удалённый RPC, IO в файл, ожидание лока)? Если да — выносить наружу. (2) Использует ли PR `SET` без LOCAL, классический `PREPARE`, `LISTEN`, session-level `pg_advisory_lock`? Если да — миграция к transaction-mode-совместимому варианту. (3) Изменяет ли PR размер client pool или ожидаемый QPS? Если да — пересчитать формулу и проверить, что Postgres `max_connections` × PgBouncer headroom всё ещё держит. (4) Добавляет ли PR новый горячий запрос? Если да — EXPLAIN ANALYZE в описании, ожидаемое hold-time проговорено. Эти 4 вопроса — 30 секунд ревью, и они ловят 90% классов багов, ведущих к исчерпанию пула в продакшне.</p>

    <p><strong>Модель процессов Postgres детально.</strong> Соединение Postgres — OS-процесс `postgres backend`, форкнутый <Term k="postmaster" lang="ru">postmaster</Term> при подключении клиента. У каждого backend приватная память (~5-10 МБ резидентной, в основном per-query память + кеши + буферы <Term k="libpq" lang="ru">libpq</Term>) и слот в shared memory (<Term k="proc_array" lang="ru">proc array</Term> entry, lock table entry, snapshot метаданные). Стоимость старта процесса ~5 мс плюс auth и TLS на сети. Почему процессы, а не потоки? История: Postgres появился до хорошей поддержки потоков на большинстве Unix; модель процессов изолирует crash (OOM одного backend не портит остальные), упрощает управление памятью (приватная heap на backend) и хорошо наследуется от форка. Цена — высокий overhead per connection — несокращаемая в ванильном Postgres. Внутренний паттерн пулинга: много соединений × маленькая приватная память + тяжёлая shared memory + один процесс на backend. PgBouncer меняет контракт приложения: вместо открытия многих соединений Postgres — открыть мало backend и мультиплексировать.</p>
    <p><strong>Почему «поднять max_connections» не масштабируется.</strong> Наивная команда упирается в исчерпание и поднимает max_connections с 100 до 1000. Что идёт не так. (1) Каждый backend резервирует shared memory pre-allocated при старте — proc array, lock hash, predicate-lock структуры — линейно по max_connections. 1000 backend ≈ сотни МБ фиксированной shared memory только на структуры. (2) Overhead context switch: при 1000 backend под нагрузкой kernel scheduling — измеримая доля CPU. (3) Lock manager contention: shared memory структуры (procarray iteration при получении snapshot, lock-table scan, <Term k="multixact" lang="ru">MultiXact</Term> buffers) — узкие места; throughput на backend падает. (4) Latency установления соединения растёт по мере роста очереди форков postmaster. Рекомендация сообщества Postgres 25+ лет: кэп max_connections в пару сотен; мультиплексирование выше через pooler. Математика: при (cores × 2) оптимальных активных backend, 100 backend легко обслуживают правильно-архитектурированную систему; 1000 — почти наверняка отказ пулинга, не масштабирования Postgres.</p>
    <p><strong>Transaction mode + prepared statements: прорыв 2024.</strong> До 2024 production-trade-off был: transaction mode для мультиплексирования ИЛИ prepared statements для переиспользования плана — не оба. Драйверы JDBC, asyncpg, pgx готовили statement через wire protocol (`PrepareStatement`/`PQprepare`), давая 10-30% throughput на повторных запросах. Но transaction mode PgBouncer направлял следующий `EXECUTE` на другой backend, не знающий statement, выдавая ошибку «prepared statement does not exist». Исторический обход: отключить prepared в драйвере (например, `prepareThreshold=0` в JDBC) — теряя plan-reuse выгоду. <em>PgBouncer 1.21</em> (март 2024) ввёл protocol-level prepared statement tracking: PgBouncer парсит protocol-сообщения Parse/Bind/Execute, поддерживает глобальный реестр prepared statement на логического клиента, и re-prepare на любом backend, на который попал. <em>PostgreSQL 17</em> (сентябрь 2024) добавил серверную поддержку protocol-level DEALLOCATE, позволяющую чистое закрытие prepared statement при отключении клиента — закрывая последнюю дыру resource-leak. На 2026 production-стек — PgBouncer ≥ 1.21 + Postgres ≥ 14 (≥ 17 идеально) + driver-managed prepared + transaction mode — все три выигрыша одновременно. Конфиг: `max_prepared_statements = 1000` в pgbouncer.ini; проверка через `SHOW STATS` для `query_count` и через driver telemetry.</p>
    <p><strong>Ландшафт pooler 2026 и когда что выбрать.</strong> <em>PgBouncer</em>: однопоточный C, ультра-низкий overhead (~2KB на пул-conn), де-факто стандарт. Когда нужен battle-tested, маленький, single-purpose pooler рядом с Postgres. Лимит: однопоточный = ceiling в одно CPU-ядро; для &gt;100k QPS через один PgBouncer нужно несколько за HAProxy. <em>Odyssey</em>: multi-threaded C от Yandex/Tarantool; нативная поддержка prepared (раньше PgBouncer); выше throughput при высокой конкуренции. Когда один узел + &gt;100k QPS через один pooler; минус — моложе codebase, меньше сообщество. <em>PgCat</em>: Rust, multi-threaded, добавляет query routing (read replicas, шардинг); полезно, когда хочешь один компонент для pool + routing + balance. <em>Supavisor</em>: Erlang/Elixir, cloud-native, для миллионов входящих соединений из serverless и edge; managed-ответ Supabase. В serverless / edge / multi-tenant SaaS, где connection storms — design constraint. <em>pgpool-II</em>: традиционный выбор для HA + read load balancing поверх пулинга; тяжелее, больше фич, сложнее; жизнеспособный, но менее популярный в greenfield. Дефолт 2026 — PgBouncer + отдельный load balancer; тянемся к другим, когда специфичные фичи оправдывают операционную стоимость.</p>
    <p><strong>Внутренности client-side pool.</strong> HikariCP (Java) использует lock-free FastList для acquisition, async housekeeping для idle/leak detection, интегрируется с JDBC валидационными протоколами. node-postgres `Pool` оборачивает `Client` на соединение и очередь для ожидающих checkout. asyncpg (Python) использует asyncio для ожиданий. Общий контракт: `acquire` блокирует (или отвергает) на max; `release` возвращает в idle; фоновые задачи закрывают idle-past-timeout и валидируют сломанные. Типичные баги. (1) Забыли release на error — используйте language-level гарантии (try/finally, defer, RAII, `using`). (2) Удержание соединения через async-wait — `await` посередине checkout в node.js. (3) Валидационные запросы добавляют latency на каждый checkout — выключайте, если сеть и Postgres надёжны, включайте только при наблюдаемых сбросах idle (NAT-rebinding firewalls, ELB с idle-timeout). (4) Исчерпание пула маскируется под «медленный API» — инструментируйте checkout-wait-time отдельной метрикой.</p>
    <p><strong>Connection storms в serverless и edge.</strong> Serverless-платформы (Lambda, Vercel Functions, Cloudflare Workers) инстанцируют сотни-тысячи холодных worker под нагрузку, каждый хочет соединение Postgres. Даже с client-side pool каждый cold start открывает новое соединение — connection-storm. Митигации. (1) Всегда фронтите Postgres pooler — `RDS Proxy` Lambda, Supavisor перед Supabase Postgres, PgBouncer на мощном узле перед self-hosted. (2) Для Cloudflare Workers / edge: HTTP-based протоколы вроде serverless driver Neon / Postgres-over-HTTP — каждый запрос stateless HTTP к pooler, без persistent соединений edge-to-origin. (3) Cold-path оптимизация: pre-warm пулов при deploy если возможно; агрессивный idle-timeout для освобождения между всплесками. (4) Для очень больших multi-tenant: Supavisor или Cloudflare Hyperdrive (или коммерческие) обрабатывают входящие в миллионах через Erlang/Elixir lightweight processes. Архитектурный урок: persistent-connection pool предполагают long-lived клиентов; serverless нарушает это — проектируйте под stateless query dispatch.</p>
    <p><strong>Postgres GUC, влияющие на пулинг.</strong> `max_connections` (жёсткий лимит); `superuser_reserved_connections` и `reserved_connections` (резерв, уменьшают эффективный лимит); `idle_in_transaction_session_timeout` (kill-switch для зависших транзакций, 60s как safety net); `statement_timeout` (per-query верхний лимит, kill runaway); `lock_timeout` (безопасность DDL); `tcp_keepalives_idle`/`tcp_keepalives_interval`/`tcp_keepalives_count` (детект мёртвых соединений — важно с PgBouncer впереди, где NAT или stateful firewalls могут тихо дропать idle TCP); `client_connection_check_interval` (PG 14+; детект мёртвого клиента без TCP-слоя); `default_transaction_isolation`. Senior-тюнинг: задайте всё это явно в postgresql.conf, не дефолт; документируйте каждое с обоснованием.</p>
    <p><strong>Таксономия режимов отказа.</strong> (а) <em>Исчерпание пула из-за долгих запросов</em>: отсутствующий индекс делает запрос 5с; при 1000 QPS — 5000 in-flight, далеко за пулом. Фикс: индекс или пагинация. (б) <em>Idle-in-transaction зависшие backend</em>: необработанное исключение оставило BEGIN открытым; backend сидит «idle in transaction» вечно. Фикс: idle_in_transaction_session_timeout = 60s; code review на отсутствие try/finally COMMIT/ROLLBACK. (в) <em>Внешний API внутри транзакции</em>: BEGIN → внешний HTTP → COMMIT — транзакция открыта на время API. Фикс: вынести вызов; commit раньше; outbox-паттерн для write-then-event. (г) <em>NAT/firewall idle-drop без TCP keepalive</em>: backend выглядит idle для PgBouncer, но реальный TCP мёртв; новые запросы получают RST/timeout. Фикс: tcp_keepalives в postgresql.conf + PgBouncer; уменьшить client_connection_check_interval (PG14+). (д) <em>Коллизии prepared statement до PgBouncer 1.21</em>: legacy-код с prepared + transaction mode = «prepared statement does not exist» случайно. Фикс: апгрейд PgBouncer ≥ 1.21 + max_prepared_statements &gt; 0. (е) <em>DISCARD ALL не срабатывает в transaction mode при утечках state</em>: SET, который должен был быть SET LOCAL, утекает к следующему клиенту на том же backend. Фикс: server_reset_query = DISCARD ALL в pgbouncer.ini (форс reset между арендами). (ж) <em>Pool размер не учитывает spike vs steady</em>: размерен под steady, всплески опрокидывают. Фикс: reserve_pool_size; autoscaling приложения; queue-and-degrade (503 с Retry-After до исчерпания). (з) <em>Однопоточный CPU bottleneck PgBouncer</em>: при очень высоком QPS один PgBouncer пегает ядро. Фикс: горизонтально-scale PgBouncer за HAProxy/keepalived; миграция на Odyssey/PgCat.</p>
