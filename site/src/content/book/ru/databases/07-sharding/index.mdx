Миграции (<a href="/ru/databases/06-migrations/">06-migrations</a>) показали, как безопасно менять один Postgres; этот фрагмент про то, что делать, когда одного Postgres мало — когда рабочий набор не помещается в shared_buffers, когда write-throughput насыщает primary, когда запросы одного тенанта starve остальных. Шардирование — горизонтальный split: логически единый датасет партиционируется через много физических баз по <em>ключу шардирования</em>, каждый запрос маршрутизируется на шард, владеющий его ключом. Выигрыш — почти линейный scale-out (10 шардов ≈ 10× storage, часто 5-8× throughput); цена — операционная сложность (каждая миграция N×, кросс-шардовые join'ы дорогие, транзакции через машины, shard map — critical infrastructure). Режим отказа, под который проектируете с первого дня — <em>hot shard</em>: один шард получает непропорциональную долю трафика, потому что ключ выбран плохо или один тенант вырос в 1000× больше медианы. Senior-команда выбирает ключи осознанно, мониторит skew, и держит resharding-плейбук до первого инцидента, а не после.

<Crux>Шардирование делит БД по ключу. Ко-локация — выигрыш; hot shards — отказ; online resharding — экзамен.</Crux>

В обиходе путают два слоя: <em>partitioning</em> (один Postgres, таблица разбита по ключу — declarative с PG 10) и <em>sharding</em> (много инстансов Postgres, каждый держит подмножество строк). Partitioning одноузловой и в основном выигрывает на planning + manageability (DROP partition вместо DELETE; partition pruning в плане); не повышает throughput выше одной машины. Sharding многоузловой и единственный способ масштабироваться за пределы CPU/IO/storage одной машины. Они композируются: реальные системы обычно партиционируют внутри каждого шарда (шардирование по tenant_id; внутри шарда таблица events партиционируется по месяцу для retention). Citus — расширение Postgres, превращающее кластер в прозрачную шардированную БД (coordinator + workers + автоматический routing); альтернативы — application-level routing (ваш код выбирает шард) и database-per-tenant (каждый тенант — свой Postgres). Все три используются в 2026; правильный выбор зависит от количества тенантов, формы запросов и операционного бюджета.

    <p><strong>Одно предложение.</strong> Шардирование разбивает логический датасет на много физических Postgres-инстансов, каждая строка живёт ровно на одном шарде, определяемом ключом шардирования (`tenant_id`, `user_id`).</p>
    <p><strong>Почему важно.</strong> У одного Postgres жёсткие потолки: ~1-10 ТБ рабочего набора в RAM, ~10-100k QPS write throughput, CPU и IO одной машины. За пределами либо перепишите приложение под другую БД (дорого), либо разделите данные на много инстансов (sharding). Почти любой B2B SaaS, масштабирующийся за пару тысяч тенантов, в итоге шардируется.</p>
    <p><strong>Метафора.</strong> Sharding — разница между одной библиотекой с миллионом книг (всё в одном здании, один вход, один стол справок) и десятью библиотеками по 100к книг каждая (каждая в своём здании, нужен индекс «в какой библиотеке моя книга»). Одна библиотека проще — всё в одном месте, любой найдёт что угодно прогулкой. Десять — требуют справочника (shard map); если книга оказалась не там, где вы думали, едете в другое здание. Книги, забираемые миллион раз в год, разбросаны по всем десяти; одна библиотека с бестселлерами — это hot shard.</p>

Фикс: <em>tenant isolation</em> — переместить этого клиента на dedicated шард. У Citus встроено.</p>

    <p><strong>Partitioning vs sharding — одно слово, два понятия.</strong> <em>Partitioning</em> (внутри Postgres): одна таблица разбита на под-таблицы на одном инстансе, объявлено `PARTITION BY RANGE/LIST/HASH` (PG 10+). Полезно для pruning (DROP partition вместо DELETE для retention) и manageability больших таблиц. Не повышает throughput за одну машину. <em>Sharding</em> (cross-instance): датасет на много инстансов, routing по ключу. Throughput линейно растёт с количеством шардов до bottleneck (часто кросс-шардовая координация). Композируются: шардированный кластер обычно партиционирует внутри каждого шарда. Senior-интуиция: partition для manageability и pruning; shard для capacity.</p>
    <p><strong>Стратегии ключа шардирования.</strong> <em>Hash sharding</em>: shard = hash(key) mod N. Uniform распределение; легко рассуждать; rebalancing сложен (смена N двигает большинство строк). <em>Range sharding</em>: шард владеет диапазоном ключа (`tenant_id 1-1000` на шарде A, `1001-2000` на B). Натуральный для time-series; rebalancing проще (split диапазона); риск hot tail (новейшие строки на одном шарде). <em>List sharding</em>: явный map ключ → шард. Максимальный контроль; не масштабируется на миллионы ключей. <em>Directory-based / lookup sharding</em>: внешняя таблица («shard map») маппит ключ → шард; можно перемещать отдельных тенантов между шардами обновлением одной строки. Самый гибкий; добавляет lookup-стоимость; основа Citus tenant isolation и ручного app-level routing. <em>Consistent hashing</em>: hash-вариант, где добавление/удаление шарда двигает только K/N ключей, не большинство. Чаще в кешах; некоторые Postgres-setup используют для directory-based remapping.</p>
    <p><strong>Контракт хорошего ключа.</strong> Четыре свойства. (1) <em>Selectivity</em>: 95%+ запросов фильтрует по нему; без него — редкие или fan-out. (2) <em>Uniform распределение</em>: каждый шард получает примерно равные данные и нагрузку. (3) <em>Стабильный</em>: значение не меняется для данной строки (нельзя re-shard на лету). (4) <em>Доступен в момент routing</em>: каждый API-запрос может подать его (URL или token несут tenant_id). Для multi-tenant SaaS почти всегда `tenant_id`. Для B2C scale — `user_id`. Для гео-партиционирования — `region`. Дизайны, в которых такого ключа нет — red flag — делите модель данных, пока он не появится.</p>
    <p><strong>Ко-локация: выигрыш производительности.</strong> Когда часто join'ящиеся таблицы делят один ключ шардирования (`orders.tenant_id` и `payments.tenant_id`), Citus размещает соответствующие шарды на одном физическом worker. Join с фильтром по tenant_id остаётся локальным — одна машина, без сетевых round-trip, та же производительность, что у single Postgres для этого тенанта. Без ко-локации join становится cross-shard: coordinator собирает данные с N шардов, мерджит — на порядки медленнее. Ко-локация — правило дизайна, делающее шардированный Postgres похожим на single для типичных запросов. Senior-паттерн: определите список tenant-scoped таблиц, все они шардированы по tenant_id, все ко-локированы.</p>
    <p><strong>Кросс-шардовые запросы.</strong> Запросы без фильтра по ключу fan-out на все шарды. Coordinator (Citus или ваше приложение) отправляет запрос каждому шарду, собирает результаты, агрегирует, возвращает. Цена: N× работы, P99 latency = max(latencies шардов), каждый медленный шард замедляет запрос. Примеры: «список всех users без tenant_id»; «глобальный count заказов сегодня»; кросс-tenant аналитика. Митигации: (1) избегать в OLTP — проектируйте API вокруг per-tenant scope. (2) Аналитика — реплицировать в OLAP (Snowflake, BigQuery, ClickHouse) через CDC; OLTP-кластер остаётся tenant-scoped. (3) Per-tenant метрики дашбордов — предвычислять и хранить per-tenant.</p>
    <p><strong>Citus: расширение шардирования Postgres детально.</strong> Citus превращает кластер Postgres в одну логическую БД. Архитектура: <em>coordinator</em> (один узел, держит метаданные, планирует запросы, маршрутизирует); <em>workers</em> (N узлов, держат шарды, выполняют свою долю). Типы таблиц: <em>distributed</em> (строки разбиты по workers по ключу); <em>reference</em> (полная копия на каждом worker, для таблиц, join'ящихся со многими distributed — countries, plans, feature_flags; обновления через 2PC); <em>local</em> (только на coordinator, для admin/control plane). Distribution: `SELECT create_distributed_table('orders', 'tenant_id');` — Citus хеширует tenant_id в N шардов (по умолчанию 32, часто 64 или 128 для больших кластеров). Co-located таблицы с тем же distribution column попадают на aligned шарды. Rebalancer online (Citus 11.1+): перемещает шарды через логическую репликацию, без downtime.</p>
    <p><strong>Schema-based sharding (Citus 12+, 2023).</strong> Новая модель: каждый тенант получает Postgres-<em>схему</em>; Citus распределяет схемы по workers прозрачно. `CREATE SCHEMA acme; CREATE TABLE acme.orders (...);` — Citus назначает схему worker'у. Приложение ставит `search_path = acme` на соединение. Преимущества: не нужен общий ключ (любой запрос внутри схемы — локален); легко онбордить тенанта (CREATE SCHEMA); легко мигрировать (move схемы); 1:1 tenant isolation, включая схемы без общих колонок. Ограничения: ceiling schemas-per-cluster (Citus рекомендует «low thousands»); не подходит B2C с миллионами. Sweet spot: B2B SaaS с сотнями-парой тысяч тенантов, где у каждого своя схема с требованиями isolation.</p>
    <p><strong>Application-level sharding.</strong> Пропустить Citus; код приложения маршрутизирует. Паттерн: «shard map» таблица или сервис (`tenant_id → connection_string`) + routing layer, оборачивающий каждый запрос. Плюсы: явный, простой, без extra database; гибкий per-tenant. Минусы: каждая cross-shard забота (join'ы, транзакции, fan-out) — код приложения; resharding ваше дело; routing layer — критическая инфраструктура. Распространено при малом числе шардов (10-100) и сильно tenant-scoped запросах. Инструменты: ORM вроде Prisma поддерживают много `datasources`; библиотеки читают tenant_id из request context; connection pool на шард (за своим PgBouncer). Senior-паттерн: routing layer минимален, тестируйте под chaos, имейте runbook для cross-shard.</p>
    <p><strong>Распределённые транзакции и 2PC.</strong> Транзакция, трогающая много шардов, нуждается в two-phase commit: все шарды prepare; если ок — все commit; иначе все rollback. Postgres поддерживает 2PC нативно; Citus использует для распределённых транзакций. Цена: latency (минимум 2 round-trip), риск (in-doubt транзакции, если coordinator упал между prepare и commit — recoverable, но болезненно), удар по throughput. Best practice: проектируйте транзакции single-shard, где возможно. Для неизбежных cross-shard — принимайте 2PC + мониторьте pg_prepared_xacts на застрявшие транзакции; имейте runbook recovery.</p>
    <p><strong>Подсказка: большинству приложений шардирование не нужно.</strong> Современный Postgres на современном железе тянет 1-10 ТБ рабочего набора и 10-50k QPS без проблем. Read-реплики поглощают большую часть read scale; vertical scaling (больше CPU, RAM, быстрее диск) покупает годы. Sharding — ответ, когда вы измерили bottleneck и доказали, что его не решить индексами, кешем, репликами или vertical growth. Цена шардирования реальна: каждая миграция N×, каждый cross-shard запрос медленный, каждая операционная задача (backup, vacuum, upgrade) на шард. Не pre-shard.</p>
    <p><strong>Сигналы pre-sharding с одного Postgres.</strong> До commitment к шардированию проверьте leading indicators. (1) <em>Отношение working set к RAM</em>: если `pg_stat_database.blks_hit / (blks_hit + blks_read)` падает ниже 95-99% sustained на большом instance — рабочий набор перерос shared_buffers + OS cache; vertical scale покупает время, но траектория важна. (2) <em>Write throughput</em>: `pg_stat_database.xact_commit` per second приближается к десяткам тысяч; CPU primary доминирован WAL-генерацией. (3) <em>Connection count</em>: лимит пула PgBouncer (см. фрагмент 05) часто связывает раньше, чем чистый CPU. (4) <em>Maintenance боль</em>: VACUUM часами; окна reindex сжимаются; бэкапы превышают retention recovery time. (5) <em>One-tenant impact</em>: запрос одного шумного тенанта насыщает IO и деградирует всех остальных — «hot tenant на single Postgres» — это репетиция hot-shard. Когда 2-3 из этих сигналов реальны, шардирование переходит из спекулятивного в запланированное.</p>
    <p><strong>Multiplier деплоев/операций.</strong> Когда шардирован, каждая операция масштабируется по числу шардов. Бэкапы: N pg_basebackup (или per-shard streaming); время восстановления per-shard, но часто параллельно. Minor-version апгрейды Postgres: N rolling updates, мониторинг per worker. Major-version: N pg_upgrade, тщательная координация. Установка логической репликации (для OLAP CDC): per-worker slot, per-worker publisher. Каждый runbook операций single-Postgres становится N-runbook в шардированной. Senior-команды автоматизируют через per-shard orchestration (Ansible, Terraform с for_each по списку workers, custom operators в Kubernetes); без автоматизации ops staff растёт линейно с числом шардов — это операционный налог шардирования, ставший конкретным.</p>
    <p><strong>Read-реплики на каждом шарде.</strong> Шардирование решает write scale; read scale внутри шарда решается репликами. Стандартный паттерн: каждый Citus worker имеет 1-2 streaming replica (физические или synchronous); приложение маршрутизирует read-only запросы на реплику текущего шарда, write — на primary этого же шарда. Citus умеет это нативно через `citus.use_secondary_nodes`; app-level — через явный per-shard read endpoint. Цена: replica lag (типично &lt; 1 секунда, но может расти под нагрузкой); консистентность read-your-writes требует stick-to-primary логики для свежих записей. Senior-паттерн: critical paths (e.g., load dashboard immediately after save) идут на primary; eventual-consistency-ок (analytics, history views) — на реплику. Реплики также служат HA: failover на реплику при падении primary шарда; Patroni или managed-сервис автоматизирует.</p>
    <p><strong>Backup-стратегия для шардированного кластера.</strong> Single-Postgres бэкап — один pg_basebackup или managed-снимок. Шардированный: N бэкапов, скоординированных так, чтобы все шарды были на одном logical point-in-time (или близко) — иначе восстановление одного шарда без другого даёт неконсистентные данные. Подходы: (1) <em>Скоординированные бэкапы</em>: pause writes на короткое время (минуты), снять snapshot на каждом шарде, resume. Подходит для редких maintenance windows. (2) <em>Point-in-time recovery per-shard</em>: каждый шард имеет свой WAL archive; PITR на одном шарде восстанавливает до момента T; если T одинаков для всех — кластер консистентен. Управляемые сервисы (Azure Cosmos DB for PostgreSQL, AWS RDS) делают это автоматически. (3) <em>Logical backup всего кластера</em>: pg_dumpall с координацией — медленно, но даёт portable artifact. Восстановление сценарий: «потеряли один шард полностью» — restore с последнего бэкапа этого шарда + apply WAL до желаемого T; «потеряли координатор» — restore координатор + восстановить shard map. Senior-команда регулярно drill'ит сценарии в staging.</p>
    <p><strong>Observability специфика шардирования.</strong> Поверх стандартных Postgres-метрик (CPU, IO, connections), шардированный кластер требует уровень <em>cluster-wide</em>. Per-shard метрики дают локальную картину; нужны агрегаты: cross-shard query rate (Citus distributed plan classification), shard skew ratio (max/median size + max/median CPU), per-tenant top-N (heavy hitters), 2PC pending count (pg_prepared_xacts на каждом worker), replication lag для logical-replication операций (rebalancing, CDC). Дашборды: cluster health (top-level), per-shard heatmap (визуализация skew), per-tenant top-10 (выявление growing tenants до hot-shard alert'а), rebalancer status. Алерты сгруппированы по тяжести: warn на skew &gt; 1.5×, page на skew &gt; 2× или any-shard CPU &gt; 80%. Без этой обсервабилити команда reactive — узнаёт о hot-shard от пейджей, не от трендов.</p>
    <p><strong>Code-review checklist для шардированной системы.</strong> Каждый PR в шардированном проекте проходит специфический ревью. (1) Новая таблица tenant-scoped? Должна иметь tenant_id NOT NULL FK + быть distributed с colocate_with. (2) Новый запрос содержит tenant_id в WHERE? Иначе fan-out — отвергнуть или объяснить. (3) Транзакция трогает много таблиц одного тенанта — ок (ко-локированы). Много таблиц разных тенантов — 2PC, обсудить. (4) Новый join — между ко-локированными таблицами? EXPLAIN VERBOSE в описании PR. (5) Миграция учитывает шардирование? Squawk + Citus auto-propagate, post-migration schema consistency check. Эти 5 проверок — 3 минуты на ревью, защищают co-location инвариант от размытия.</p>

  <Fragment slot="senior">
    <p><strong>Полная таксономия стратегий.</strong> (1) <em>Hash sharding</em>: shard = hash(key) mod N. Uniform при uniform ключах; rebalancing меняет большинство placements при смене N; consistent hashing варианты редуцируют до K/N. (2) <em>Range sharding</em>: каждый шард владеет диапазоном. Натуральный для time-series; риск hot tail; rebalancing через split. (3) <em>List sharding</em>: явный ключ → шард map. Максимальный контроль; не масштабируется на миллионы ключей. (4) <em>Directory-based</em>: внешняя lookup таблица; можно перемещать отдельных тенантов; основа Citus tenant isolation. (5) <em>Schema-based</em> (Citus 12, 2023): каждый тенант — своя Postgres-схема; Citus распределяет схемы по workers; clean isolation; ceiling в low thousands тенантов. (6) <em>Database-per-tenant</em>: каждый тенант — dedicated Postgres database (или инстанс). Максимальная isolation, простейшая ментальная модель; масштабируется операционно до десятков-сотен (PgBouncer pools per (db, user), backups, upgrades per DB); болезненно за пределами. (7) <em><Term k="rls" lang="ru">Row-level isolation (RLS)</Term> на одном Postgres</em>: не sharding strictly, но same-cluster эквивалент для multi-tenant — RLS policies enforce границы тенантов; работает, пока single Postgres не насыщен. Senior-выбор зависит от tenant count, требований isolation и операционной зрелости.</p>
    <p><strong>Внутренности Citus: query planning через шарды.</strong> Когда coordinator получает запрос, он парсит, планирует на основе метаданных Citus (какие шарды где, какие таблицы reference/distributed/local), производит distributed plan. Три класса. (а) <em>Single-shard query</em>: WHERE имеет равенство по ключу (`tenant_id = $1`). Citus маршрутизирует как есть на один worker; тот выполняет как обычный Postgres. Производительность: идентична single-Postgres. (б) <em>Distributed query, ко-локированный</em>: запрос join'ит ко-локированные таблицы или SELECT'ы через все шарды, push-downабельные (агрегации, GROUP BY по ключу). Coordinator отправляет частичные планы всем workers; каждый выполняет; coordinator мерджит. Производительность: parallelism, latency = max worker. (в) <em>Cross-shard query</em>: требует gather-and-merge на coordinator. Самый медленный путь; должен быть редким в OLTP. Citus отображает класс через `EXPLAIN (VERBOSE)` — production-команды аудитят паттерны, чтобы держать cross-shard минимальным.</p>
    <p><strong>Online resharding: операционный экзамен.</strong> Добавление шарда (scale-out) или удаление (consolidation) требует перемещения данных. Старая школа: downtime, dump + restore. Современно: <em>online rebalancing</em> через <Term k="logical_replication" lang="ru">логическую репликацию</Term>. Citus 11.1+ rebalancer: (1) планирует список move (какие шарды с worker A на worker B); (2) старт логической репликации на каждом шарде source → target; (3) после catch-up кратко паузит записи в шард, переключает указатель метаданных, возобновляет; (4) дропает source. На шард: пауза суб-секунда; общее время rebalance — по объёму данных и сетевому throughput (~10-100 МБ/с). Vitess делает похожее для MySQL. Тот же паттерн (<Term k="logical_replication" lang="ru">логическая репликация</Term> + cut-over) применим к app-level sharding, но строите сами. Senior-команды rebalance'ятся в production до того, как нужно — capacity это запланированная операция, не экстренная.</p>
    <p><strong>Распределённые транзакции и 2PC: когда использовать, когда избегать.</strong> Cross-shard транзакции нуждаются в 2PC: prepare на всех шардах; если все ок — commit на всех; иначе rollback всё. Postgres имеет 2PC (`PREPARE TRANSACTION`, `COMMIT PREPARED`); Citus использует для любого DML, трогающего много шардов. Цена: latency (минимум 2 сетевых round-trip), throughput (соединение каждого шарда удерживается во время prepare), риск in-doubt (coordinator падает между prepare и commit; prepared транзакции сидят в pg_prepared_xacts, держа блокировки, до ручного разрешения). Best practice. (1) Проектируйте транзакции single-shard, где возможно — ко-локированные таблицы делают это естественным. (2) Избегайте `BEGIN; UPDATE shard1; UPDATE shard2; COMMIT`; предпочтите eventual consistency через outbox или saga, где бизнес-логика позволяет. (3) Мониторьте pg_prepared_xacts на каждом worker; алерт на строки старше пары минут; runbook recovery. (4) Для действительно distributed-transactional нужд (редко в B2B SaaS) — встроенное 2PC Citus, не roll-your-own — recovery-семантика тонкая.</p>
    <p><strong>Schema-based sharding deep-dive.</strong> Citus 12 (2023) добавил schema-based: каждый тенант маппит на Postgres-схему, схемы распределяются по workers, запросы scope'ятся через `search_path`. Реализация: `CREATE SCHEMA acme;` — Citus назначает worker'у (lookup таблица). Приложение: `SET search_path TO acme, public;` — каждый последующий запрос разрешает имена внутри acme; Citus маршрутизирует к worker'у acme. Преимущества над row-based: (1) не нужен общий shard key column (любой запрос внутри схемы — локален); (2) схема — natural deployment unit (CREATE/DROP SCHEMA); (3) clean isolation (тенант не может случайно читать чужие данные, потому что имена таблиц разные); (4) легко мигрировать (move схемы); (5) per-schema миграции работают как single-Postgres. Ограничения: schema-count ceiling (Citus рекомендует &lt; few thousand); cross-tenant запросы всё ещё cross-shard; некоторые фичи (Citus reference tables) не применимы внутри схем. Sweet spot: B2B SaaS с 50-2000 тенантов, где строгая isolation — часть продукта (compliance, контрактная). Вне этого диапазона row-based (Citus distributed tables) или DB-per-tenant подходит лучше.</p>
    <p><strong>Postgres FDW для федеративных запросов (non-Citus).</strong> <Term k="fdw" lang="ru">postgres_fdw</Term> позволяет одному Postgres запрашивать другой через libpq. Без Citus можно построить federated read pattern: coordinator Postgres держит метаданные + FDW foreign tables, указывающие на worker Postgres; чтения через foreign table тянут с worker'а; coordinator может join'ить через FDW таблицы (со значительным overhead). Полезно для: read-only аналитики через шарды; консолидация данных из per-tenant DB в один query interface; мост во время миграции в/из Citus. Ограничения: записи через FDW медленные и не транзакционные через foreign tables (Postgres 17+ улучшил с COMMIT/ROLLBACK PREPARED на foreign tables, но niche); join'ы push down только когда предикаты позволяют. Не замена Citus; полезный инструмент в app-level setup.</p>
    <p><strong>Re-sharding по другому ключу (редко и больно).</strong> Иногда оригинальный ключ оказывается неверным: шардировали по user_id, но большинство запросов по org_id; user-to-org ratio создаёт skew или fan-out. Re-shard по другому ключу = переписать каждую строку. Подходы. (1) <em>Dual-write + backfill</em>: приложение пишет в старое и новое; backfill историю; cut-over reads после catch-up; drop old. Месяцы работы. (2) <em>Vitess-style live resharding</em>: tool-managed copy + replication + cut-over; минуты write-паузы. Vitess делает для MySQL; аналог Citus — shard-splitting, работает внутри одного ключа, не для смены. (3) <em>Новый кластер</em>: поднять параллельный кластер с новым шардированием, реплицировать через CDC, cut-over. Самый гибкий; больше операционной работы. Senior-вывод: смена ключа — среди самых дорогих операций; выбирайте тщательно с начала, и предпочитайте ключ, scopeащийся к natural unit, даже если добавляет краткосрочную сложность.</p>
    <p><strong>Multi-region шардирование и консистентность.</strong> Geo-partitioning шардирует по региону и маршрутизирует трафик на ближайший шард. Плюсы: low-latency reads/writes per region; data residency compliance (GDPR). Минусы: cross-region запросы медленные (50-200мс через континенты); cross-region writes нужны 2PC или eventual consistency; failover policies ясны (становится ли данные региона read-only при падении его primary?). Postgres-native geo: declarative partitioning по region column на каждом кластере + app routing. Новые commercial опции: CockroachDB, YugabyteDB — Postgres-совместимые distributed SQL для multi-region с самого начала; trade-off Postgres-экосистемы расширений vs встроенная multi-region семантика. Senior-выбор: оставайтесь на Postgres, пока workload терпит single-region или per-region кластеры; distributed-SQL только когда multi-region writes со строгой consistency — жёсткое требование.</p>
    <p><strong>Таксономия режимов отказа.</strong> (а) <em>Hot shard от перекошенного тенанта</em>: один тенант 100-1000× медианы. Митигация: мониторинг skew, изоляция больших (Citus isolate_tenant_to_new_shard или directory remap). (б) <em>Hot tail с range</em>: новейшие строки на одном шарде для time-keyed данных. Митигация: hash внутри range, или комбинация time + tenant_id, или Citus hash distribution. (в) <em>Взрыв cross-shard query</em>: новая фича добавляет запросы без фильтра по ключу, fan-out спайкает. Митигация: review запросов в PR (Citus EXPLAIN), CDC в OLAP, rate-limit cross-shard. (г) <em>Застрявшие prepared транзакции</em>: crash coordinator оставляет pg_prepared_xacts; lock'и держатся вечно. Митигация: алерт на age, runbook recovery. (д) <em>Шторм записей в reference</em>: малая reference таблица с высоким write rate; 2PC по всем workers — bottleneck. Митигация: конвертировать в distributed, или принять более высокую latency. (е) <em>Дрейф миграции между шардами</em>: один шард прогнал миграцию, другой нет; схема расходится. Митигация: tool-aware sharding (Citus есть; app-level — custom runner с retry на шард, проверка post-run consistency). (ж) <em>Resharding mid-failure</em>: rebalancer падает посреди move; шард есть на двух workers с прерванной репликацией. Митигация: Citus rebalancer идемпотентен и resumable; manual recovery через pg_stat_subscription. (з) <em>Ceiling schema-sharding</em>: tenant count перерастает модель. Митигация: мигрировать очень больших на row-based, оставив малых на schema-based; hybrid реален в production.</p>
    <p><strong>Стратегическая позиция: шардирование — однонаправленная дверь.</strong> После того как система шардирована, каждая операционная задача масштабируется по числу шардов. Миграции per-shard; бэкапы per-shard; апгрейды per-shard; алерты per-shard. Senior-команды шардируют только после измерения bottleneck и исчерпания альтернатив. Начинают с простейшего работающего шардирования (часто Citus + row-based + tenant_id), измеряют 6 месяцев, корректируют. Пишут runbook до того, как нужно. Относятся к shard map как к critical-tier-1 инфраструктуре. Re-shard'ятся превентивно при приближении skew к порогу, не после пейджей.</p>

Режим отказа — hot shard от перекошенного тенанта; изолируйте через Citus primitive. Cross-shard: analytics в OLAP через CDC. Resharding online через логическую репликацию. Не pre-shard.</KeyTakeaway>
