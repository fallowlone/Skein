Пулинг (<a href="/ru/databases/05-pooling/">05-pooling</a>) показал, как транзакции держат соединения; этот фрагмент про особую транзакцию, держащую кое-что более разрушительное — AccessExclusiveLock на горячей таблице — и как senior-команды деплоят изменения схемы без выключения базы. Суть в FIFO очереди блокировок Postgres: когда DDL вроде `ALTER TABLE` не может сразу получить блокировку, потому что другая транзакция держит даже маленький read lock, DDL ждёт — и каждый последующий запрос к таблице встаёт в очередь за этим ждущим DDL, независимо от того, какой lock ему нужен. Один медленный `SELECT` + один нетерпеливый `ALTER TABLE` = вся таблица заморожена на время медленного SELECT. Фикс не «дождаться часов низкой нагрузки» (downtime в 2026 редко приемлем), а `SET lock_timeout` + retries + декомпозиция любого breaking change на серию всегда-безопасных, всегда-обратимых шагов через expand-contract. Senior-инструменты — pgroll, Atlas, Squawk, gh-ost-style online schema change — кодируют эти паттерны, чтобы инженеры не вспоминали наизусть.

<Crux>ALTER TABLE берёт AccessExclusiveLock. Очередь FIFO. SET lock_timeout. Breaking changes — через expand-contract.</Crux>

Миграция Postgres — это транзакция с DDL (`CREATE TABLE`, `ALTER TABLE`, `CREATE INDEX`, `DROP COLUMN` и т.д.). DDL берут табличные блокировки по матрице Postgres: большинство — `ACCESS EXCLUSIVE` (самый строгий — конфликтует с любым другим, включая `ACCESS SHARE`, который нужен `SELECT`). Матрица — поверхность дизайна: история безопасности любой миграции сводится к «какой lock берёт, с чем конфликтует, сколько держит». Современный Postgres делает много операций драматически безопаснее, чем учебники: `ADD COLUMN ... DEFAULT 'x'` мгновенный с PG 11 (default в метаданных, без переписывания), `CREATE INDEX CONCURRENTLY` берёт лёгкий `SHARE UPDATE EXCLUSIVE` (не блокирует чтение/запись), `ALTER TABLE ... ADD CONSTRAINT ... NOT VALID` + `VALIDATE CONSTRAINT` разделяют работу на две короткие транзакции вместо одной длинной. Дисциплина — знать, какая форма безопасна, и использовать её; режим отказа — написать форму из учебника, задеплоить в 14:00 и получить пейдж в 14:01.

    <p><strong>Матрица блокировок Postgres — поверхность дизайна.</strong> Восемь режимов от `ACCESS SHARE` (нужен `SELECT`) до `ACCESS EXCLUSIVE` (большинство DDL). Матрица говорит, что блокирует что: `ACCESS EXCLUSIVE` конфликтует со <em>всем</em>, включая `ACCESS SHARE`, так что любой DDL с ним блокирует всех читателей и писателей на время удержания. `SHARE UPDATE EXCLUSIVE` (используется `CREATE INDEX CONCURRENTLY`, `VACUUM`, `ANALYZE`, `VALIDATE CONSTRAINT`) конфликтует только с собой и более строгими — не блокирует DML. Senior-интуиция: до написания миграции спросите «какой lock берёт» и «какая типичная длительность»; если оба ответа — «AccessExclusive» и «больше 50 мс», разделяйте.</p>
    <p><strong>Очередь блокировок — реальный режим отказа.</strong> Postgres получает блокировки в порядке прихода (FIFO). Когда `ALTER TABLE` ждёт `ACCESS EXCLUSIVE`, он встаёт в очередь за держателем конфликтующего lock — часто медленный `SELECT` на 30 секунд. Пока `ALTER TABLE` ждёт, каждый <em>новый</em> `SELECT` тоже ждёт, потому что `ALTER TABLE` впереди в очереди, и им нужен lock, конфликтующий с `ACCESS EXCLUSIVE`. Итог: один медленный `SELECT` + один благонамеренный `ALTER TABLE` = вся таблица недоступна, пока медленный SELECT не закончится. Это канонический инцидент «запустил миграцию, и сайт упал». Митигация: `SET lock_timeout = '2s'` на каждую сессию миграции. Если lock не получен за 2 секунды, миграция чисто прерывается, очередь не страдает. Retry: backoff + повтор; pgroll и Atlas делают это автоматически.</p>
    <p><strong>Безопасные операции (лёгкие или мгновенные).</strong> <em>ADD COLUMN с константным default</em> (PG 11+): мгновенно, default в pg_attribute.atthasmissing/attmissingval; без переписывания. <em>ADD COLUMN без default</em>: мгновенно, NULL для существующих. <em>SET/DROP DEFAULT</em>: только для новых INSERT/UPDATE; метаданные. <em>DROP NOT NULL</em>: метаданные. <em>RENAME COLUMN/TABLE</em>: метаданные, но ломает зависимый код. <em>ADD CONSTRAINT ... NOT VALID</em>: enforce только для новых строк, без скана. <em>VALIDATE CONSTRAINT</em>: скан под `SHARE UPDATE EXCLUSIVE` (не блокирует DML). <em>CREATE INDEX CONCURRENTLY</em>: двухфазная постройка, `SHARE UPDATE EXCLUSIVE`; не блокирует чтение/запись. Все эти — production-дефолт. У неверных форм есть безопасные эквиваленты; senior-паттерн — знать маппинг.</p>
    <p><strong>Небезопасные операции и их фиксы.</strong> <em>ADD COLUMN с volatile default</em> (`DEFAULT clock_timestamp()`): полное переписывание под `ACCESS EXCLUSIVE`. Фикс: ADD COLUMN без default, backfill батчами, потом SET DEFAULT для новых. <em>ALTER COLUMN TYPE</em> когда типы не binary-coercible: полное переписывание. Фикс: новая колонка + dual-write + backfill + swap + drop. <em>ADD NOT NULL на колонке с существующими строками</em>: полный скан под `ACCESS EXCLUSIVE`. Фикс: ADD CHECK CONSTRAINT NOT VALID (... IS NOT NULL), VALIDATE CONSTRAINT (лёгкий lock), потом ALTER COLUMN SET NOT NULL (проверяет уже доказанный constraint, быстро). <em>ADD FOREIGN KEY</em> обычно требует `ACCESS EXCLUSIVE` + скан. Фикс: ADD CONSTRAINT ... NOT VALID + VALIDATE CONSTRAINT. <em>DROP COLUMN</em>: обычно быстро (метит как dropped, ленивая очистка), но ломает код. <em>RENAME COLUMN</em>: быстро, но ломает код. У каждой небезопасной операции есть многошаговый безопасный паттерн; линтер Squawk ловит небезопасные формы автоматически в CI.</p>
    <p><strong>Expand-contract — универсальный паттерн.</strong> Любое breaking change декомпозируется на: (1) <em>Expand</em>: добавить новый элемент схемы (колонку/таблицу/индекс) рядом со старым. Код dual-write в старое и новое. (2) <em>Backfill</em>: скопировать историю старое → новое батчами. (3) <em>Cut over</em>: код читает из нового. (4) <em>Contract</em>: перестать писать в старое; удалить старое. Каждый шаг независимо деплоится и обратим. Паттерн многословный — переименование колонки = 5+ деплоев за дни — но единственный способ сделать изменения схемы реально безопасными под продакшн-трафиком. pgroll и Atlas автоматизируют boilerplate; даже руками написанные миграции должны следовать паттерну.</p>
    <p><strong>CREATE INDEX CONCURRENTLY в деталях.</strong> Строит индекс, не блокируя чтения/записи. Цена: в 2-3× дольше непараллельного, не может в транзакции (большинство migration-tool нуждаются в специальной non-transactional аннотации), может упасть посередине, оставив индекс в состоянии INVALID (видно в pg_indexes как `indisvalid = false`). Режимы отказа: долгие транзакции на таблице задерживают вторую фазу; OOM прерывает постройку. Senior-runbook: всегда CREATE INDEX CONCURRENTLY в проде; всегда проверяйте `indisvalid = true` после; если упал — DROP INDEX CONCURRENTLY (тоже не блокирующий) и retry. Atlas, pgroll умеют детектировать INVALID индексы и retry.</p>
    <p><strong>lock_timeout и statement_timeout.</strong> Два GUC, превращающие runaway-миграцию в чистый отказ. `lock_timeout = '2s'` (на сессию миграции): если lock не получен за 2 секунды — abort. С retry (exponential backoff) миграция в конце концов получит lock в тихий момент между долгими запросами. `statement_timeout = '30s'` (на сессию миграции, выше типичной длительности но ограниченный): если реальная работа миграции (backfill UPDATE) идёт дольше 30с — abort. Вместе превращают «миграция заморозила базу» в «миграция залогировала ошибку, retry попозже» — graceful degradation. Заметка: НЕ ставьте глобально в postgresql.conf; ставьте per-session через migration tool. Большинство (golang-migrate, Flyway, Prisma, Drizzle, Atlas) имеют хуки для этого.</p>
    <p><strong>Ландшафт migration-tool в 2026.</strong> <em>golang-migrate</em>: простой, language-agnostic, «up.sql» + «down.sql», CLI. <em>Flyway</em>: Java, зрелый, та же файловая модель. <em>Liquibase</em>: XML/YAML, более декларативный. <em>Prisma Migrate</em>: TS/Node, интеграция с Prisma schema (single source — schema.prisma → миграции). <em>Drizzle</em>: TS, аналогично. <em>Atlas</em> (Ariga): современный, декларативный + императивный; линтит миграции; понимает семантику Postgres; запускает миграции безопасно с lock_timeout, retry, dry-run; растёт в популярности. <em>pgroll</em>: zero-downtime через виртуальные схемы (views) + автоматический backfill + триггеры для dual-write — самая агрессивная safety-обёртка. <em>Squawk</em>: линтер, ловящий unsafe DDL в ревью PR (например, флагает `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT`). Стек 2026: Prisma/Drizzle/Atlas для повседневных миграций + Squawk в CI + pgroll или дисциплина паттерна для редких breaking changes.</p>
    <p><strong>Сопряжение миграций с деплоями.</strong> Порядок миграции vs деплоя кода определяет безопасность. <em>Additive</em> (добавить колонку, читаемую новым кодом): сначала миграция, потом код. Новый код находит колонку готовой. <em>Removal</em> (удалить колонку, которую читает старый код): сначала деплой кода (он перестаёт читать), дождаться полного дренажа старого кода, потом миграция. <em>Rename</em>: за один шаг нельзя. Expand: добавить новую колонку. Деплой: dual-write. Backfill: старое → новое. Деплой: чтение из нового. Подождать. Contract: удалить старое. Пять деплоев на дни. <em>Фундаментальное правило</em>: в каждый момент и текущий, и новый код приложения должны корректно работать против текущей схемы. Нарушение этого правила — это как «миграция сломала приложение» случается.</p>
    <p><strong>Подсказка: rollback — это не «down-миграция».</strong> Down-миграции (обратный SQL up-миграции) звучат безопасно, но редко работают в проде. Если up-миграция добавила колонку, и новый код в неё писал — запуск down (DROP COLUMN) уничтожает данные. Если up-миграция была мгновенным ADD COLUMN, down быстрая, но вы потеряли всё, что в неё записали. Production-откат — вперёд: написать новую миграцию, фиксящую проблему, задеплоить, не «откатывать» предыдущую. Воспринимайте down как документацию для dev-окружений, не как production safety net.</p>
    <p><strong>Практический воркфлоу написания миграции.</strong> Перед открытием PR senior-инженер проходит ментальный чек-лист. (1) Какая операция: additive (ADD COLUMN, CREATE TABLE, CREATE INDEX) или breaking (DROP, RENAME, ALTER TYPE)? Additive → одна миграция. Breaking → expand-contract последовательность из 4-6 шагов на дни. (2) Какой lock берёт DDL и какая ожидаемая длительность? AccessExclusive + миллисекунды — поставить lock_timeout = '2s' и идти. AccessExclusive + минуты — переделывать в безопасный паттерн (NOT VALID + VALIDATE, CONCURRENTLY, expand-contract). (3) Где writes? Любой ADD COLUMN с NOT NULL без default или volatile default требует backfill — отдельная миграция батчами с pg_sleep. (4) Где код приложения? Если код пишет новое поле — миграция первой; если код читает старое — миграция последней. (5) Что в release notes Postgres? Версия PG может изменить семантику: PG 11 сделал ADD COLUMN с default мгновенным, PG 14 улучшил CONCURRENTLY, PG 17 добавил DEALLOCATE-over-protocol. Senior-команда сверяется с release notes своей версии до написания SQL.</p>
    <p><strong>Code-review checklist для миграций.</strong> Когда PR с миграцией попадает на ревью, ревьюер задаёт 5 вопросов до approve. (1) <em>Squawk-clean?</em> CI должен показать green; если warn — обсудить и либо переписать, либо принять с justification в описании PR. (2) <em>lock_timeout + statement_timeout?</em> Сессия миграции должна явно ставить оба; без них — request changes. (3) <em>Backfill для NOT NULL/volatile default?</em> Если миграция добавляет NOT NULL колонку или volatile default, должен быть отдельный backfill PR с батчевой логикой и pg_sleep. (4) <em>Координация с code deploy?</em> В описании PR явно указан порядок: «миграция перед деплоем кода», «деплой кода перед миграцией» или «expand-contract последовательность с шагами X, Y, Z». (5) <em>Rollback plan?</em> Forward-fix (не down-миграция) — что мы напишем, если эта миграция сломается? Эти 5 вопросов — 2 минуты ревью; они ловят 95% классов багов, попадающих в production.</p>
    <p><strong>Тестирование миграций до прода.</strong> Senior-практика: каждая миграция гоняется на production-size снимке БД в staging до того, как попасть в прод. Это не просто синтаксическая проверка — это измерение реального времени выполнения, реального удержания lock, реального impact на конкурентный трафик. Инструменты: pg_dump-restore прод-снимка в staging еженедельно (или CDC через pglogical для near-realtime); скрипт нагрузочного теста, гоняющий реалистичный трафик параллельно с миграцией; metric collection через pg_stat_activity + pg_locks для измерения lock-wait time. Результат — измеренная длительность миграции с CI-числом, прикреплённым к PR. Если ожидаемое 10 мс, а измеренное 8 с — это сигнал, что миграция требует переписывания в безопасный паттерн. Без этой практики первое production-измерение происходит во время инцидента; с ней инцидент предотвращён в staging.</p>

Схема — supersеt; старый код не знает о новом, новый знает. (2) <em>Dual-write</em>: задеплоить код, пишущий и в старое, и в новое. Чтения по-прежнему идут в старое. (3) <em>Backfill</em>: копирование исторических данных old → new. (4) <em>Cut over reads</em>: задеплоить код, читающий из new, но всё ещё пишущий оба. То же касается drop (drop колонки, читаемой запущенным кодом), изменения типа (код ждёт int, колонка теперь text), добавления constraint (код генерирует строки, проваливающие constraint).   <Fragment slot="senior">
    <p><strong>Транзакционная семантика DDL в Postgres.</strong> Большинство DDL транзакционны: `BEGIN; CREATE TABLE; ALTER TABLE; COMMIT;` — либо всё успешно, либо всё откатывается, и конкурентные сессии видят изменение атомарно на момент commit (через snapshot/MVCC). Исключения: `CREATE INDEX CONCURRENTLY`, `REINDEX CONCURRENTLY`, `ALTER TYPE ... ADD VALUE` (до PG 12, потом транзакционный) и пара других — не могут в `BEGIN..COMMIT`. Migration tool по умолчанию оборачивают каждую миграцию в транзакцию — правильная политика: многоstatement-миграция, упавшая посередине, должна оставить схему в pre-migration состоянии. Следствие: любая миграция с CONCURRENT операцией должна запустить её вне транзакционной обёртки — большинство инструментов имеют директиву `-- atlas:txmode none` или `-- prisma:nontx`.</p>
    <p><strong>Паттерн advisory-lock для сериализации миграций.</strong> Несколько app-серверов, стартующих одновременно, могут пытаться запустить pending миграции — без координации два процесса могут применить одну дважды или конкурировать на schema_migrations. Стандартный фикс — Postgres advisory lock в начале: `SELECT pg_advisory_lock(<unique_int>);` — первый сервер получает lock, гоняет миграции, освобождает; остальные ждут. golang-migrate использует lock_id=хеш имени БД; Prisma похоже. Senior-команды проверяют, что lock удерживается всю миграцию (не только на старте), инспектируя pg_locks во время теста. Также полезен pg_try_advisory_lock с коротким retry-циклом для неблокирующего поведения старта.</p>
    <p><strong>Инструменты online-schema-change и их место.</strong> <em>pgroll</em> (xata): поддерживает виртуальные схемы через views. Миграция создаёт новый view рядом со старым; старый код читает старый view (оригинальная форма колонки), новый код читает новый view (новая форма); оба views на одной физической таблице, с триггерами трансляции записей. По завершении старый view удаляется. Zero downtime; сложные breaking changes (rename, drop-with-data-preservation, type-change) декларативны. <em>Atlas</em>: декларативный + линтер. Определите желаемую схему; Atlas вычисляет план миграции, линтит на unsafe, запускает с lock_timeout + retry. Работает без виртуальных схем; полагается на дисциплину expand-contract от приложения. <em>gh-ost</em> (MySQL, но паттерн похож в Postgres через pg_squeeze, pg_repack): для редкого случая настоящего переписывания (ALTER COLUMN TYPE с несовместимыми типами, table-clustering changes) — shadow-table подход: создать новую таблицу, копировать батчами с триггерами на репликацию записей, swap атомарно. Резервируйте для случаев, не подходящих под expand-contract.</p>
    <p><strong>ADD COLUMN со stored default: реализация PG 11.</strong> До PG 11 `ALTER TABLE ... ADD COLUMN ... DEFAULT 'x'` переписывал каждую строку для материализации default. В PG 11+ при non-volatile default Postgres хранит его в `pg_attribute.atthasmissing = true` и `pg_attribute.attmissingval = 'x'`. Существующие строки сохраняют старую физическую форму tuple (без колонки); SELECT возвращает missing default на чтение; новые строки хранят колонку нормально. Итог: ADD COLUMN с default мгновенный на таблицах любого размера. Есть маленькая read-time стоимость (missing-default path), исчезающая по мере переписывания нормальным UPDATE-трафиком; production-команды либо оставляют (стоимость пренебрежима), либо запускают one-time UPDATE для материализации. Механизм — один из крупнейших практических wins современного Postgres — однопальцево устранил самую частую причину инцидентов миграций до 2018.</p>
    <p><strong>Validate constraints под нагрузкой.</strong> `ADD CONSTRAINT ... NOT VALID` мгновенный, но enforce только для новых строк; существующие могут нарушать. `VALIDATE CONSTRAINT` сканирует таблицу для проверки. Берёт `SHARE UPDATE EXCLUSIVE` — не блокирует нормальный DML (INSERT/UPDATE/DELETE/SELECT), но блокирует другой DDL на той же таблице. Следствие: валидируйте при нормально работающем приложении; единственное влияние — другие DDL встают в очередь. Senior-паттерн: планируйте валидацию на off-peak; мониторьте прогресс скана через `pg_stat_progress_analyze` или возраст xact_start удерживающей транзакции. Долгий validate (например, на 1B-строчной таблице за час) ок, если другая миграция не очерёдывается за ним. То же касается `CREATE INDEX CONCURRENTLY` — долго, но DML-safe.</p>
    <p><strong>ALTER COLUMN TYPE: исключение binary-coercible.</strong> Большинство type changes переписывают таблицу. Исключения: type changes, которые <em>binary-coercible</em> — то же физическое представление. Примеры: `varchar(50)` → `varchar(100)` (шире, но те же байты), `varchar` → `text` (то же), `text` → `varchar` (то же), `numeric(10,2)` → `numeric(12,2)` (шире, то же). Postgres детектирует и пропускает rewrite — быстро, кратко AccessExclusive, без записей строк. Non-coercible (int → bigint, text → int, json → jsonb до PG 14) требуют либо полного переписывания, либо shadow-column expand-contract. Каталог pg_type содержит правила coercibility; Atlas знает их и предупреждает, когда изменение перепишет. Senior-паттерн: для любого ALTER TYPE, не доказуемо coercible, — expand-contract.</p>
    <p><strong>Линтер Squawk и интеграция CI.</strong> Squawk (Linux Foundation, изначально Stripe) парсит SQL миграции и предупреждает на unsafe паттернах: ADD COLUMN с не-константным default, ALTER COLUMN TYPE без проверки coercibility, CREATE INDEX без CONCURRENTLY, drop NOT NULL на FK, rename, drop без предыдущего деплоя кода. Запуск в CI на каждом PR, трогающем `migrations/`. Настраивается error vs warn per rule; команды обычно error на опасные (rewrite-causing) и warn на операционные (rename, drop). Сочетайте с Atlas для визуализации плана (`atlas migrate diff` показывает ровно то, что запустится, включая SQL, который выполнит Postgres), и команда имеет видимость до merge вместо обнаружения после инцидента. CI-стоимость: меньше 30 секунд на PR миграции; сэкономленные инциденты стоят порядков больше.</p>
    <p><strong>Партиционирование и scope миграций.</strong> Партиционированные таблицы (декларативное партиционирование, PG 10+) меняют расчёт миграций. ADD COLUMN на партиционированной таблице каскадирует на все партиции одним statement — мгновенно для константных default, дорого для переписывания. CREATE INDEX надо делать per-partition (или CREATE INDEX ON ONLY parent + attach к каждой) — большинство migration tool это умеют. ATTACH PARTITION и DETACH PARTITION — операционные примитивы для ротации (drop старых time-партиций, add новых). Важно: ATTACH PARTITION кратко берёт AccessExclusive; с `lock_timeout` безопасно; в PG 14+ ATTACH PARTITION CONCURRENTLY ослабляет lock ещё. Senior-команды относятся к partition-операциям как к first-class миграциям и используют partition-поддержку migration tool; собственная реализация обычно упускает corner cases.</p>
    <p><strong>Координация миграций с continuous deploy.</strong> Deploy-machinery — Kubernetes rolling updates, blue/green, canary — взаимодействует с миграциями нетривиально. (1) <em>Миграция до rollout pod</em> (самое частое): деплой стартует; init-контейнер или pre-deploy job запускает `migrate up`; после успеха новые pod выкатываются. Минус: старые pod ещё работают и могут увидеть новую схему до своего обновления; схема должна быть backwards-compatible (только expand). (2) <em>Миграция как часть startup pod</em> (каждый pod пытается; advisory lock сериализует): проще, но медленнее (каждый новый pod ждёт проверку). Минус: race conditions без правильного lock. (3) <em>Миграция отдельно от деплоя</em> (вручную или через выделенные migration jobs): полный контроль, проще планировать, но люди координируют с кодом. Senior-паттерн: отделить migration runner от lifecycle app pod; запускать миграции из выделенного CI job после merge кода, но до деплоя кода; gate деплой на успех миграции. Atlas и pgroll предоставляют gates для этого.</p>
    <p><strong>Таксономия режимов отказа.</strong> (а) <em>Lock-queue freeze</em>: ALTER ждёт, очередь забивается, таблица заморожена. Фикс: lock_timeout + retry. (б) <em>CREATE INDEX CONCURRENTLY оставлен INVALID</em>: постройка упала (долгая транзакция блокировала вторую фазу или OOM); pg_indexes показывает indisvalid = false. Фикс: DROP INDEX CONCURRENTLY + retry. Детект: мониторинг indisvalid после миграции. (в) <em>Deadlock миграций</em>: две миграции или миграция + трафик конкурируют на порядок acquisition. Фикс: сериализация миграций через advisory lock; не запускать параллельные миграции на связанных таблицах. (г) <em>Откат, уничтожающий данные</em>: down-миграция дропает колонку с новыми данными. Фикс: forward-only; не полагайтесь на down в продакшне. (д) <em>Дрейф схемы между репликами</em>: миграция применена на primary, но replication lag задерживает на standby; код читает со standby и видит старую схему. Фикс: gate деплоев кода на replica lag = 0 (или близко); использовать replica-aware mode migration tool. (е) <em>Backfill UPDATE ест WAL</em>: один огромный UPDATE генерирует ГБ WAL, заполняет диск, реплики отстают. Фикс: батчевать UPDATE по 1k-10k со sleep между; мониторить WAL generation rate. (ж) <em>Volatile default rewrite скрытый</em>: `DEFAULT now()` на ADD COLUMN выглядит безопасно, но volatile → rewrite. Фикс: детект через Squawk; константный default + post-migration update. (з) <em>NOT NULL добавлен без backfill</em>: в колонке есть NULL; SET NOT NULL падает. Фикс: backfill сначала; использовать паттерн NOT VALID + VALIDATE. (и) <em>RENAME во время деплоя</em>: старый код ссылается на старое имя, падает между миграцией и pod rollout. Фикс: expand-contract вместо single-step rename.</p>
    <p><strong>Стратегическая позиция: миграции — first-class production-артефакты.</strong> Зрелые команды относятся к коду миграций с той же строгостью, что к коду приложения: PR review с явными reviewer, CI lint (Squawk + dry-run через Atlas), staging deploy на production-size датасете до прода, runbook на каждую миграцию с ожидаемым impact, observability на runtime миграции + время acquisition lock. Цена умеренная (квартальный обзор паттернов + автоматический lint); выгода — каденс деплоев десятков безопасных изменений в неделю вместо «гоняем миграции в maintenance window раз в месяц». Senior-команды ship breaking changes рутинно; junior — избегают. Разница — процесс и тулинг, не храбрость.</p>
