REST моделировал строки; OpenAPI зафиксировал форму на проводе. GraphQL выбрасывает оба ради языка запросов, где клиент сам выбирает поля. Клиент получает гибкость; сервер получает планировщик. Когда планировщик наивен — один резолвер на поле, одна поездка на строку — сервер делает сотни SQL-вызовов на один HTTP-запрос. Это и есть N+1, и каждая GraphQL-система либо решает его осознанно, либо медленно от него умирает.

<Crux>Один GraphQL-запрос на 1+N строк — 1+N походов в БД. DataLoader сводит их к 2. На этом фиксе держится остальная защита.</Crux>

GraphQL разрешает запрос, обходя дерево документа и вызывая функцию-резолвер на каждое поле, которое попросил клиент. Резолверы независимы: каждый не знает, как разрешаются соседи, не видит общего плана запроса, возвращает значение своего поля. Эта изоляция и делает GraphQL композируемым — и именно поэтому вложенные запросы взрываются. Список из N постов, каждому нужен автор, генерирует 1 запрос за постами плюс N независимых запросов за авторами, без какой-либо координации. DataLoader и слои complexity / depth / persisted-query поверх него — не опциональные расширения; это операционные подпорки, без которых production GraphQL рушится.

    <p><strong>Почему GraphQL естественно порождает N+1.</strong> Алгоритм выполнения GraphQL обходит документ запроса в глубину и в ширину на каждом уровне. На каждое поле, которое попросил клиент, вызывается функция-резолвер, зарегистрированная сервером для пары <code>type.field</code>. Резолверы чисты: получают <code>(parent, args, context, info)</code> и возвращают значение (или промис). Они не видят соседних резолверов, у них нет доступа к плану запроса и они не могут переписать SQL. Поэтому, когда запрос говорит <code>posts &#123; author &#123; name &#125; &#125;</code>, сервер сначала разрешает <code>posts</code> (один fetch, 50 строк), затем запускает <code>Post.author</code> 50 раз — по разу на пост — с parent-аргументом, равным каждому посту. Каждый из этих 50 вызовов независимо идёт в БД. Планировщик, который встроен в REST-контроллеры, в GraphQL становится внешним делом — его надо добавлять самому.</p>
    <p><strong>DataLoader: стандартное решение.</strong> DataLoader — небольшая библиотека, изначально извлечённая из реализации GraphQL в Facebook и поддерживаемая GraphQL Foundation. Конструктор: <code>new DataLoader(batchLoadFn, options)</code>, где <code>batchLoadFn(keys: Array&lt;K&gt;)</code> возвращает <code>Promise&lt;Array&lt;V | Error&gt;&gt;</code> в том же порядке, что и входные ключи. Резолверы вызывают <code>loader.load(key)</code> и получают промис. Под капотом каждый <code>.load()</code> кладёт ключ во внутренний массив. Когда текущий синхронный шаг JavaScript заканчивается — точнее, когда очередь микротасок начинает сливаться — DataLoader берёт все накопленные ключи, вызывает <code>batchLoadFn</code> один раз с ними и разрешает индивидуальные <code>.load()</code>-промисы из возвращённого массива. Он также мемоизирует по ключу внутри одного запроса: <code>loader.load(7)</code> дважды в одном request возвращает один и тот же промис.</p>
    <p><strong>Правило per-request инстанса.</strong> DataLoader-инстанс — это кеш. Его время жизни — request, не процесс. Если создать один глобальный DataLoader при старте сервера, его кеш делят все запросы — то есть «load user 7» от Bea и «load user 7» от Cara возвращают тот же объект. Это утечка арендаторов с последствиями для безопасности и свежести данных: пользователь, изменённый одним запросом, не виден изменённым в другом; пользователь, которому в одном запросе урезали права, всё равно вернётся другому с кешированными данными. Дисциплина жёсткая: создавать новый DataLoader на каждый запрос, прикреплять к <code>context</code> и давать GC чистить его в конце запроса. Документация Apollo Server явно это подсвечивает: «Инстансы DataLoader — per-request; если используешь DataLoader в источнике данных, создавай новый инстанс на каждый запрос».</p>
    <p><strong>Порядок батча имеет значение.</strong> Контракт <code>batchLoadFn</code>: получая ключи <code>[k1, k2, k3]</code>, вернуть значения <code>[v1, v2, v3]</code> той же длины и в тех же позициях. Если БД возвращает строки в другом порядке (Postgres легко так делает без ORDER BY), loader неправильно сопоставит — каждый резолвер получит чужую строку. Решение механическое: после SQL <code>WHERE id IN (...)</code> построй таблицу поиска по id и пройди входные ключи в исходном порядке. Типичная ошибка — забыть, что строки по ключу может не быть, и тихо вернуть в его слот предыдущее значение, что портит все последующие позиции. DataLoader позволяет <code>null</code> или <code>Error</code> в любом слоте, и тот, и другой нужно заполнять явно.</p>
    <p><strong>За пределами DataLoader: lookahead и джойны.</strong> DataLoader чинит форму «N запросов за одной колонкой», но не решает каждый вариант. Если клиент просит <code>posts &#123; author &#123; profile &#123; bio &#125; &#125; &#125;</code>, у тебя по-прежнему три уровня разрешения, и DataLoader накапливает каждый уровень отдельно — три поездки, не одна. Чтобы свернуть их сильнее, продвинутые серверы используют <em>resolver lookahead</em>: читают AST из аргумента <code>info</code>, видят, какие дочерние поля попросил клиент, и джойнят их одним SQL на верхнем уровне. Библиотеки Pothos, TypeGraphQL и Hasura так и делают: маппят AST в SQL-планировщик. Цена — сложность: lookahead-резолвер знает про целое поддерево, ломая per-field изоляцию, которая и сделала GraphQL композируемым.</p>
    <p><strong>Apollo Federation и N+1 на entity-резолверах.</strong> В федеративном GraphQL несколько subgraph'ов стоят за единым supergraph'ом. Когда запрос пересекает границы — скажем, subgraph <code>users</code> владеет <code>User</code>, а subgraph <code>posts</code> владеет <code>Post</code> с полем <code>Post.author: User</code> — supergraph-роутер запрашивает каждого упомянутого user через <code>_entities(representations: [_Any!]!)</code>. Роутер автоматически батчит representations в один вызов: если 50 постов ссылаются на пользователей, роутер шлёт один <code>_entities</code>-запрос с 50 representations. Реализация <code>__resolveReference</code> в users-subgraph должна батчить внутри (опять DataLoader), иначе сходит в БД 50 раз в этом единственном вызове. Federation отдаёт тебе межсервисный батч бесплатно; внутрисервисный батч остаётся на тебе.</p>
    <p><strong>Persisted queries: доверие на границе.</strong> Persisted queries (или «trusted documents» в проекте спецификации GraphQL-over-HTTP) заменяют inline-текст запроса хешем. Клиент регистрирует известные запросы на сервере на этапе сборки; во время запроса шлёт только хеш и переменные. Сервер находит документ и выполняет. Это закрывает целый класс атак: произвольные клиентские запросы больше невозможны, поэтому интроспекционная разведка, complexity-атаки, алиас-батчинг и depth-бомбы блокируются на входе. Минус — операционный: каждый деплой клиента требует регистрации хешей, а ad-hoc инструменты (Postman, консоль браузера) перестают работать против production. Публичные API, которые не могут ограничить клиентов (Shopify Storefront, GitHub Public GraphQL), оставляют запросы открытыми, но добавляют complexity scoring; first-party API всё чаще требуют persisted queries.</p>
    <p><strong>Complexity scoring и depth limiting: две линии обороны.</strong> Без persisted queries сервер защищается AST-анализом до выполнения. <em>Depth limiting</em> (типичный максимум 7-10) обходит AST и отклоняет запросы, чья вложенность превышает лимит. Это рубит тривиальную рекурсию-бомбу <code>user &#123; friend &#123; friend &#123; friend... &#125; &#125; &#125;</code>, где 12-уровневый запрос экспоненциально читает строки. <em>Complexity scoring</em> присваивает стоимость каждому полю — обычно <code>cost = 1</code> для скаляров и множитель <code>cost = limit_arg × child_cost</code> для connection-полей. Сервер суммирует стоимости по AST, отклоняет при превышении бюджета (типично: 1000-10000 единиц на запрос) и тарифицирует клиентов по стоимости в pay-per-call API. GitHub публикует стоимость каждого запроса в response extensions; Shopify Storefront кепит запросы на 1000 единиц и 1000 единиц/сек на IP. Оба — анализ только AST, до запуска резолверов — даже злонамеренный запрос не стоит ни одного похода в БД.</p>
    <p><strong>Batching-атаки и alias-бомбы.</strong> Многие GraphQL-серверы принимают массив операций в одном HTTP-запросе (operation batching) или один документ с множеством корневых алиасов (<code>q1: user(id:1) q2: user(id:2) ...</code> повторённый 1000 раз). Каждый вариант парсится как один документ, но выполняет тысячи резолверов, и каждый может независимо сходить в БД. Operation batching обходит per-HTTP rate limit; alias batching обходит наивные per-document depth-проверки. Production-серверы кепят размер op-батча на 5-10 и количество алиасов на документ на 20 по умолчанию. Часть атак комбинирует: 10 batched operations × 20 aliases × 5 уровней — легко 10000 вызовов резолверов на один HTTP-запрос, под любым наивным rate limit.</p>
    <p><strong>Интроспекция: полезна в dev, опасна в prod.</strong> GraphQL поставляется с интроспекцией (мета-запросы <code>__schema</code> и <code>__type</code>), чтобы инструменты рисовали схему без внешней документации. Атакующие используют тот же эндпоинт, чтобы перечислить каждый тип, поле и аргумент — а потом сконструировать worst-case-запросы по дорогим уголкам схемы. Production-позиции разные: одни команды полностью выключают интроспекцию в проде (Apollo Router по умолчанию: off в проде), другие ограничивают авторизованными запросами, третьи оставляют, полагаясь только на complexity scoring. GraphQL-cheat sheet OWASP рекомендует отключать, если API не публичен по-настоящему.</p>
    <p><strong>Мемоизация DataLoader и размер батча.</strong> DataLoader кеширует по ключу внутри одного запроса, поэтому одинаковый <code>.load(7)</code> дважды возвращает тот же промис — полезно, когда одна сущность доступна по нескольким путям в запросе (например, автор поста и автор комментария — один и тот же user). Кеш отключаем через <code>options.cache = false</code> для резолверов, которым нужны свежие чтения внутри одного запроса (редко, но реально для шаблона write-after-read). <code>options.maxBatchSize</code> кепит ключи-на-батч — когда документ ссылается на 5000 уникальных авторов, 5000-элементный <code>WHERE id IN (...)</code> медленнее, чем пять батчей по 1000 из-за накладных расходов планировщика Postgres. Типичный кеп: 500-1000 ключей на батч, большие наборы разбиваются на несколько <code>batchLoadFn</code>-вызовов. <code>options.batchScheduleFn</code> переопределяет dispatch на границе тика; production использует редко, но федеративные роутеры иногда — чтобы синхронизировать границы батчей с фреймами запросов subgraph.</p>
    <p><strong>Паттерны loader: one-to-one, one-to-many, count.</strong> Три формы покрывают большую часть случаев. <em>One-to-one</em>: ключ — id родителя, batch возвращает массив значений, по одному на ключ. Это классический authorLoader. <em>One-to-many</em>: ключ — id родителя, batch возвращает массив массивов; пустой массив для родителей без детей обязателен, иначе позиции сдвинутся и резолверы получат чужих детей. Это tagsLoader. <em>Count</em>: ключ — id родителя, batch выполняет <code>GROUP BY parent_id COUNT(*)</code>, мапит результаты обратно. Это likeCountLoader. Менее очевидная форма — <em>composite-key loader</em>, когда ключ — кортеж (например, <code>[userId, date]</code>); чтобы кеш дедуплицировал корректно, ключ должен быть стабильно сериализуемым, иначе одинаковые кортежи воспринимаются как разные ключи. Опция <code>cacheKeyFn</code> позволяет передать сериализатор; стандартная рекомендация — <code>JSON.stringify</code> для объектов с фиксированным порядком полей.</p>
    <p><strong>Обработка ошибок в batch-функции.</strong> Что если БД недоступна или часть ключей не имеет прав? <code>batchLoadFn</code> может вернуть <code>Error</code>-объект в позиции вместо значения; DataLoader пробросит эту ошибку только тому <code>.load()</code>-промису, который её затребовал, не всем остальным. Это противоположность <code>throw</code>: бросок ошибки из batch-функции отказывает ВСЕ ожидающие <code>.load()</code>-промисы, что часто слишком грубо. Правильная форма: try/catch внутри batch-функции, превращающий per-key сбой в <code>new Error(...)</code> в его позиции, и только глобальные катастрофы (БД отказала) пробрасываются throw. Apollo Server по умолчанию транслирует резолверную ошибку в GraphQL error на конкретное поле — клиент видит partial-response с одним <code>null</code> и одной error-записью, остальные поля разрешены. Дисциплина: всегда возвращай Error для known-failures (отсутствие прав, не найдено), бросай throw только для unknown-fatal (БД упала, network timeout). Логи аггрегированы по типу ошибки — per-loader метрика error-rate помогает ловить деградации.</p>

    <p><strong>Точный контракт планирования DataLoader.</strong> Библиотека использует <code>enqueuePostPromiseJob</code> — обёртку над <code>process.nextTick</code> в Node и <code>Promise.resolve().then</code> в браузерах — для планирования dispatch'а батча. Dispatch запускается после текущего синхронного фрейма и после всех микротасок, поставленных в очередь во время него — поэтому все <code>.load()</code>, сделанные внутри тел резолверов, внутри <code>.then()</code>-цепочек после синхронной работы резолвера и внутри nextTick-отложенной логики, попадают в один батч. Ключевое свойство: окно ограничено семантикой event loop JS-рантайма, а не таймером. Никаких setTimeout, setImmediate, фиксированных миллисекунд. Батч уходит, как только рантайм свободен слить очередь микротасок. Для большинства GraphQL-резолверов это значит «через микросекунды после последнего <code>.load()</code>». Опция <code>batchScheduleFn</code> существует для редкого случая, когда нужна другая семантика — например, дебаунс на уровне кластера через cross-process брокер. Production-серверы оставляют дефолт.</p>
    <p><strong>Контракт сохранения порядка и его операционные последствия.</strong> <code>batchLoadFn(keys)</code> должен вернуть Promise, разрешающийся в Array той же длины и в том же порядке, что <code>keys</code>. Если источник возвращает меньше элементов, loader разрешает недостающие слоты в <code>undefined</code> — что распространяется как значение в резолверы, ожидающие non-null. Если источник возвращает больше — loader молча отбрасывает лишние. Если в другом порядке — каждый <code>.load()</code>-промис разрешается чужим значением. Ни один из случаев не всплывает как runtime-ошибка. Дисциплина: всегда строй явный <code>Map(keys.map(k =&gt; [k, null]))</code>, обходи строки из источника, заполняй её, потом <code>return keys.map(k =&gt; map.get(k))</code>. Та же форма для grouped-батчей (один-ко-многим): <code>return keys.map(k =&gt; map.get(k) ?? [])</code>. Пропуск empty-array дефолта для отсутствующих слотов — баг категории-разрушитель: родитель без детей получает чужих детей, или undefined, или TypeScript-несовместимый <code>null</code>.</p>
    <p><strong>Per-request скоуп и изоляция арендаторов в коде.</strong> Context-фабрика Apollo Server — каноническое место инстанциировать per-request DataLoader: <code>context: async (&#123; req &#125;) =&gt; (&#123; loaders: makeLoaders(req.auth.tenantId) &#125;)</code>. Функция <code>makeLoaders</code> возвращает новый <code>&#123; users: new DataLoader(...), posts: new DataLoader(...) &#125;</code> на каждый вызов. tenant id протекает в loader'ы, поэтому cross-tenant попадания в кеш невозможны даже на одном значении ключа — внутренний ключ кеша <code>$&#123;tenant&#125;::$&#123;id&#125;</code>, не просто <code>id</code>. Забудь про tenant-scoping — и данные одного арендатора утекут в ответ другого внутри одного Node-процесса. Это самая CVE-частая форма ошибки с DataLoader: аудит SonarSource 2024 года OSS GraphQL-серверов нашёл tenant-leak баги в 6 из 12 кодовых баз, все из-за module-scope DataLoader или отсутствия tenant в cache-key.</p>
    <p><strong>Apollo Federation: контракт _entities + __resolveReference.</strong> Модель батчинга Federation зафиксирована спецификацией subgraph. Каждый subgraph, владеющий entity-типом, экспонирует резолвер <code>__resolveReference(representation: &#123;__typename, ...keyFields&#125;)</code>, и query plan шлёт батчи representations через корневое поле <code>_entities(representations: [_Any!]!): [_Entity]!</code>. Supergraph-роутер собирает все ссылки на данный entity-тип, возникшие во время запроса, и шлёт их одним <code>_entities</code>-вызовом в subgraph-владелец. Межсервисный батч бесплатный — но fan-out внутри <code>_entities</code> на твоей стороне. Наивный subgraph, который проходит цикл по representations и выполняет один SQL на элемент, порождает intra-subgraph N+1. Решение то же: DataLoader, где loader'ы в контексте subgraph направляются аргументом representations: <code>representations.map(r =&gt; loader.load(r.id))</code> превращает 50-rep вызов в один SQL-батч. Документация Apollo рекомендует этот паттерн по умолчанию в любой федеративной кодовой базе.</p>
    <p><strong>Механика persisted-query: APQ vs trusted documents.</strong> Automatic Persisted Queries (APQ) от Apollo — оппортунистичны: клиент считает SHA-256 от текста запроса, шлёт только хеш, сервер возвращает 200, если документ закеширован, либо специальную ошибку <code>PersistedQueryNotFound</code>, если нет. Во втором случае клиент пересылает полный документ с хешем, сервер кеширует на следующий раз. APQ экономит байты на проводе (5 KB-запрос сворачивается до 64-символьного хеша на тёплом кеше), но не ограничивает форму — любой клиент может прислать любой документ. <em>Trusted documents</em> (в проекте спецификации GraphQL-over-HTTP) переворачивают модель: выполняются только pre-registered хеши, неизвестные отклоняются. Регистрация — на этапе сборки клиента через manifest, который сервер принимает до деплоя. Первая модель — оптимизация производительности; вторая — граница безопасности. Production-команды, которым нужно и то и другое, деплоят trusted documents и используют APQ-style хеширование внутри зарегистрированного набора.</p>
    <p><strong>Алгоритмы complexity scoring.</strong> Два доминирующих стиля. <em>Static field weights</em>: на каждое поле схемы навешивается директива <code>@cost(value: Int!)</code>; анализатор обходит AST и суммирует, умножая на аргументы <code>limit</code> list-полей где применимо. Просто авторить, легко обмануть (анализатор консервативен по connection-схемам). <em>Operation-cost calculator</em> (модель GitHub): аргумент <code>first/last</code> на connection обязателен, стоимость включает и объекты, и работу по их получению, итог публикуется в <code>extensions.cost</code>. GitHub GraphQL API лимитирует 5000 единиц/час и 1000 на запрос; стоимость считается анализом аргументов и числа детей, не просто числа узлов. Shopify Storefront публикует похожую модель: 1000 cost/sec на IP и 1000 cost на запрос. Общий паттерн: анализатор запускается до резолверов, поэтому over-budget запрос никогда не доходит до БД — цена в байтах провода и микросекундах AST-обхода.</p>
    <p><strong>Depth limiting: AST-обход с нюансом list-глубины.</strong> Наивный depth-limiter считает вложенность выборок — root → user → friends это depth 2. Тонкость: list-поля амплифицируют стоимость экспоненциально по глубине, поэтому одна цифра лимита значит разное на скалярной и list-вложенности. Библиотека <code>graphile/depth-limit</code> экспонирует и <code>maxDepth</code> (скалярная глубина), и <code>maxListDepth</code> (отдельный счётчик, гораздо строже — обычно 3-4). Проверка работает на фазе validation, до выполнения; отказ возвращает GraphQL-ошибку со стабильным кодом, без поездки в БД. Типичная ловушка: интроспекционные запросы глубокие (<code>__schema</code> обходит каждое поле каждого типа), поэтому depth-лимиты должны либо выпустить интроспекцию из whitelist, либо отключить её в проде. Apollo Router по умолчанию держит интроспекцию on с depth limit 10; production-деплои обычно опускают до 7-8 плюс list-depth 3-4.</p>
    <p><strong>Batching-атаки и форма alias-бомбы.</strong> Один GraphQL-документ может объявить сотни корневых алиасов, указывающих на тот же резолвер с разными аргументами: <code>q1: user(id:1) &#123; email &#125; q2: user(id:2) &#123; email &#125; ... q1000: user(id:1000) &#123; email &#125;</code>. Это валидный документ с 1000 корневых полей, парсится один раз, выполняется как 1000 вызовов резолверов. DataLoader свернёт поездки в БД, но число вызовов резолверов — рычаг атаки. Production-серверы кепят алиасы на документ (типично: 20 root-алиасов), отклоняют op-батчи больше 5-10 и применяют complexity scoring даже per-alias. Без этих лимитов один curl с 5 MB-документом даёт шестизначное число вызовов резолверов на одном HTTP-запросе, обходя любой наивный per-request rate limit. Аудит Escape.tech 2024 нашёл, что 64% production GraphQL-эндпоинтов не имеют alias-кепов; отчёт Imperva 2023 GraphQL state-of-the-API приписал 18% GraphQL-инцидентов в проде alias-batch DoS.</p>
    <p><strong>Production-наблюдаемость резолверов.</strong> Минимальный дашборд: <code>graphql_request_total</code> по operation_name и outcome, <code>graphql_request_duration_seconds_p99</code>, гистограмма <code>graphql_resolver_duration_seconds</code> по type.field, <code>graphql_resolver_call_count</code> на запрос (алерт выше N — каноническая форма N+1), гистограмма <code>graphql_query_cost</code> (алерт на long-tail выше бюджета), <code>graphql_persisted_query_hit_ratio</code> (warn, если ниже 90% — клиенты деплоят незарегистрированные документы), <code>graphql_introspection_request_total</code> (warn на non-zero в проде с выключенной интроспекцией). Per-resolver трассировка через OpenTelemetry GraphQL instrumentation шлёт span на каждый type.field-вызов; агрегация span'ов по операции даёт счётчики вызовов выше. Coprocessor-протокол Apollo Router и их встроенный набор метрик покрывают то же. Без этой инструментации регрессия N+1 невидима, пока CPU БД не запейджит дежурного.</p>
    <p><strong>Дисциплина дизайна схемы как защита от стоимости.</strong> Самая дешёвая защита — сама схема. Connection-поля с опциональным <code>first/last</code> позволяют клиенту просить безлимитные списки — делай аргумент обязательным и кепь значение (обычно 100). Поля, джойнящие границы (cross-subgraph в federation, cross-table в одном subgraph), должны экспонироваться только через connection, никогда через bare-массивы. Рекурсивные типы (User → friends → friends) либо кепятся на уровне схемы (max 2 вложенности через конвенцию + lint-правило), либо доступны только через плоскую альтернативу (User.allDescendants с аргументом depth). Анти-паттерн: «удобное» поле, возвращающее целое поддерево (например <code>User.feed</code>, разрешающее 50 постов с 10 комментариями с 5 лайками) — каждое чтение становится storm'ом из 2500 вызовов, нужно это клиенту или нет. Production-схемы эволюционируют, толкая работу обратно на клиента: попроси posts, попроси comments — отдельно.</p>
    <p><strong>Реальные production-сбои.</strong> GitHub 2021: баг в расчёте стоимости некоторых запросов GraphQL давал заниженную цифру против реальной нагрузки на БД — недосчитанные запросы обходили rate-limit и вызвали отключения API-уровня; исправлено ужесточением определений калькулятора. Shopify 2022: деплой Storefront API выкатил complexity-правило с неверным дефолтом, разрешавшим безлимитный <code>first</code> на connection, что привело к ~30 минутам деградации latency на Storefront-edge; пофикшено в следующем деплое. Apollo Studio 2023: у клиента в федеративном графе один subgraph экспонировал интроспекцию без auth, и атакующий перечислил и построил complexity-атаку против supergraph; complexity-лимиты Apollo Router поймали выполнения, но operations-метрики уведомили об необычном паттерне. CVE-2021-41248 (GraphiQL): introspection-driven XSS через crafted schema-ответы. Паттерн всех четырёх: защита существует (cost-лимиты, depth-лимиты, persisted queries, introspection off), но в одном измерении была пропущена или неверно сконфигурирована; слоистая защита спасла систему от худшего.</p>
    <p><strong>Cross-protocol мосты.</strong> Многие production-стеки экспонируют REST и GraphQL рядом. Hasura и PostgREST автогенерируют GraphQL из SQL-схемы; Apollo Connectors наоборот декларативно подключают REST-эндпоинты в GraphQL-поля. Форма N+1 переживает трансляцию: REST-эндпоинт, который вызывает <code>GET /authors/:id</code> на родителя, делает ту же боль в БД, обёрнут он в GraphQL-резолвер или вызван напрямую из клиента. Connectors-биндинг (объявить «это GraphQL-поле читается из этого REST-эндпоинта с этими параметрами») переносит батчинг в binding-слой — supergraph-роутер может сгруппировать representations в один батчевый HTTP-вызов, когда REST-эндпоинт поддерживает (например <code>GET /authors?ids=7,9,11</code>). Без такого батчевого REST-эндпоинта коннектор откатывается на per-item вызовы, и N+1 возвращается в REST-одежде.</p>
    <p><strong>Спецификация GraphQL-over-HTTP и trusted documents.</strong> Совместный проект IETF/GraphQL Foundation для GraphQL-over-HTTP (статус: working group draft на 2025) консолидирует wire-protocol-семантику, которая ad-hoc разбросана по серверам. Trusted documents — часть проекта: серверный allow-list хешей операций, опционально с ограничениями формы переменных, ограничивающий поверхность запросов разработчиком-проверенным набором. Проект также проясняет согласование persisted-query, форматы ответов на ошибки и правила content-type. В сочетании с defensive-руководством OWASP cheat-sheet, GraphQL-деплой на 2026 выглядит так: trusted documents обязательны, интроспекция off в проде, depth limit 7 и list-depth 3, complexity-бюджет 1000-10000 на запрос, кеп алиасов 20, кеп op-batch 5, инстансы DataLoader per-request, скоупленные по tenant, и per-resolver трассировка, отдающая OpenTelemetry-span'ы с тегом persisted-query-хеш для postmortem-реплея.</p>
