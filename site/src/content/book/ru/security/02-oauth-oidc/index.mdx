OWASP top-10 (<a href="/ru/security/01-owasp-modern/">01-owasp-modern</a>) рассказал, какие атаки блокировать. OAuth и OpenID Connect рассказывают, как дать пользователям делегировать доступ без передачи паролей. Неправильно — утекают токены, работающие месяцами. Правильно — единственный важнейший auth-стандарт современного веба.

<Crux>Как дать одному приложению действовать от имени пользователя в другом без знания пароля и без утечки доступа.</Crux>

OAuth 2.1 — это консолидация 2025 года OAuth 2.0 плюс десятилетие security-errata. Обязательный PKCE для каждого flow, удалён implicit, требуется exact-match redirect URI, форсирована ротация refresh-токенов. OpenID Connect добавляет identity-слой: ID-токен, говорящий кто пользователь. Вместе они покрывают три задачи: авторизовать third-party приложение, выдать short-lived access-токены для resource API, доказать identity пользователя. Production-системы постоянно ошибаются; работа senior-инженера — знать, где сидят safety-gate.

    <p><strong>OAuth 2.1 — это framework, не один протокол.</strong> Спецификация OAuth 2.1 (consolidated draft, ожидается RFC к 2026) заменяет OAuth 2.0 плюс шесть security-errata в один документ. Определяет authorization framework с несколькими "grant types" — формами взаимодействия, продуцирующими токены. Четыре grant, используемые в 2026: <em>authorization code with PKCE</em> (единственный для user-facing приложений, обязательный PKCE для всех), <em>client credentials</em> (service-to-service, без пользователя), <em>device code</em> (smart TV и CLI), <em>refresh token</em> (обновление access-токена без повторного запроса у пользователя). Implicit grant и resource-owner password grant формально мертвы в 2.1 — реализации, которые их шипают, по определению небезопасны.</p>
    <p><strong>Authorization code with PKCE: важнейший flow.</strong> Пользователь кликает "Sign in with Provider" в приложении A. A генерирует случайный <em>code_verifier</em> (43-128 chars, криптографически случайный), вычисляет <em>code_challenge = SHA-256(code_verifier)</em> и редиректит браузер на /authorize endpoint authorization server-а с параметрами: client_id, redirect_uri (должен точно совпадать с pre-registered URI), response_type=code, scope, state (случайный per-request anti-CSRF токен), nonce (случайный per-request anti-replay токен для OIDC), code_challenge плюс code_challenge_method=S256. Пользователь аутентифицируется на authorization server, даёт согласие на scope, сервер редиректит обратно на redirect_uri приложения с one-time кодом плюс state. Сервер A вызывает /token с кодом, client_id, client_secret (для confidential clients) или просто client_id (для public clients), redirect_uri и crucially исходным code_verifier. Authorization server хеширует verifier, сравнивает с сохранённым challenge, и выдаёт токены только при совпадении. Это PKCE-проверка: атакующий, перехвативший код, не может его обменять без verifier.</p>
    <p><strong>Что приходит обратно с token endpoint.</strong> Успешный ответ содержит: <em>access_token</em> (opaque строка или JWT; credential для отправки API в Authorization: Bearer header), <em>token_type</em> (почти всегда "Bearer", или "DPoP" при DPoP), <em>expires_in</em> (access TTL в секундах, обычно 300-3600), <em>refresh_token</em> (long-lived credential для обновления), <em>scope</em> (выданные разрешения, могут быть уже запрошенных), и для OpenID Connect flow — <em>id_token</em> (всегда JWT с claims вроде sub, iss, aud, exp, iat, auth_time, nonce и поля профиля пользователя). Приложение валидирует подпись id_token против публичных ключей issuer-а из /.well-known/jwks.json, подтверждает iss совпадает с ожидаемым, aud совпадает с client_id, exp в будущем, iat в прошлом, nonce совпадает с отправленным — только тогда пользователь залогинен.</p>
    <p><strong>Ротация refresh-токенов.</strong> OAuth 2.1 требует, чтобы каждое использование refresh-токена выдавало свежий refresh-токен и инвалидировало старый. Клиент должен сохранить и использовать новый refresh-токен; представление старого после ротации триггерит "replay detected" ответ, и authorization server обязан отозвать всю refresh-token цепочку. Это ловит случай украденного refresh-токена: как только либо атакующий, либо легитимный клиент использует его после ротации, другая попытка fail-ит, и сервер инвалидирует обоих. Без ротации украденный refresh-токен работает до absolute expiry — часто недели или месяцы. С ротацией окно — это интервал ротации, обычно минуты.</p>
    <p><strong>OpenID Connect: identity поверх OAuth.</strong> OAuth отвечает на "может ли это приложение сделать X от имени пользователя?". OIDC отвечает на "кто пользователь?". Механизм: вместе с access-токеном authorization server возвращает id_token — JWT с claims о пользователе — подписанный приватным ключом IdP. Приложение валидирует подпись через JWKS IdP (set публичных ключей, забираемых с /.well-known/jwks.json и кешируемых). Минимальный набор валидации: подпись (используя kid header, чтобы выбрать правильный ключ из JWKS), iss (должен совпадать с ожидаемым issuer), aud (должен содержать client_id), exp (должен быть в будущем), iat (должен быть в прошлом с tolerance ~5 минут), nonce (должен совпадать с отправленным в /authorize). Пропуск любой проверки — CVE waiting to happen.</p>
    <p><strong>Правило exact-match redirect_uri.</strong> OAuth 2.1 требует, чтобы redirect_uri в token-запросе точно совпадал с pre-registered URI — никаких wildcard, никаких path-prefix, никаких partial match. Зачем так строго? Open redirect уязвимости. Если authorization server принимает любой URI под твоим доменом как redirect, атакующий может обмануть его в редирект кода на <code>https://yourapp.com/blog/comments/?next=https://attacker.com</code> — в зависимости от системы комментариев blog, код может оказаться в логах атакующего. Exact-match отрубает это: URI должен равняться одной из registered строк. Для native apps, где нельзя надёжно зарегистрировать URL (deep links, custom schemes), OAuth 2.1 + RFC 8252 требуют либо loopback URL (http://127.0.0.1:RANDOM_PORT), либо private-use URI scheme, зарегистрированный с OS.</p>
    <p><strong>State и nonce: два отдельных anti-attack токена.</strong> Параметр state — это anti-CSRF OAuth: клиент генерирует случайный state на /authorize, сервер эхо-нит обратно на редиректе, клиент подтверждает совпадение. Без state атакующий может скрафтить malicious /authorize URL со своим redirect_uri-и-code, отправить жертве, и на клике браузер жертвы тихо завершает flow в аккаунте атакующего. Параметр nonce — anti-replay OIDC: клиент генерирует случайный nonce на /authorize, IdP эхо-нит внутри id_token, клиент подтверждает совпадение. Без nonce атакующий, перехвативший id_token через несвязанный канал, может replay-нуть его на приложении. Оба per-request случайные, оба валидируются на сервере, ни один не optional в современных flow.</p>
    <p><strong>Куда идут access-токены и как.</strong> Стандарт — HTTP-заголовок <code>Authorization: Bearer eyJhbGciOi...</code>, присутствующий на каждом API-запросе. Resource server валидирует токен: либо через <em>introspection</em> (вызывая /oauth/introspect IdP — модель trust-but-verify), либо через <em>local JWT validation</em> (токен — это signed JWT, и resource server валидирует подпись через JWKS, scalable, но stale). Выбор операционный: introspection real-time (знает о revocation сразу), но добавляет latency на запрос; local JWT validation быстрая (микросекунды), но не видит revocation до истечения. Большинство production систем компромиссят: local JWT validation для hot path, периодический JWKS refresh, short-lived access-токены (15 мин — 1 час), чтобы revocation распространялась в этом окне.</p>
    <p><strong>Scope и least privilege.</strong> Каждый access-токен несёт claim scope — разрешения, выданные на consent-этапе. Приложение запрашивает scope-set на /authorize; пользователь видит consent-экран и либо одобряет всё, либо отказывает. Production-дизайн форсирует гранулярные scope: read:photos, write:photos, read:profile вместо одного super-scope. Зачем? Две причины. Первая — user trust: photo-printing app, просящее read:photos, разумно; то же приложение, просящее полный account access, нет, и пользователи отказывают. Вторая — blast radius: если приложение скомпрометировано, атакующие могут делать только то, что выданные scope разрешают. Промышленный паттерн: read-scope выдаются свободно, write-scope требуют явного per-action consent, admin-scope никогда не появляются в third-party flow. OAuth 2.1 плюс dynamic-scope расширения (RFC 9396 — Rich Authorization Requests) позволяют клиенту запрашивать fine-grained разрешения вроде "перевести до $500 на счёт X" вместо просто "write:transfers".</p>
    <p><strong>Client registration и dynamic client metadata.</strong> Перед тем как приложение сможет делать OAuth, оно должно зарегистрироваться у IdP и получить client_id (и client_secret для confidential клиентов). Static registration — legacy дефолт: разработчик заполняет форму в консоли IdP, получает credentials, embed-ит в приложение. Dynamic Client Registration (RFC 7591) позволяет IdP принимать JSON-запросы с client metadata (redirect_uris, grant_types, contacts, software_id, software_version) и возвращать свежие credentials. Современные IdP комбинируют: static config для известных приложений, dynamic для mobile/IoT, где каждая установка — отдельный клиент. Federations (образовательные identity providers, government SSO) используют Dynamic Client Registration через Federation API (OpenID Federation), так что приложение может присоединиться к сотням IdP без ручной регистрации в каждом.</p>
    <p><strong>Logout и session termination.</strong> OAuth сам по себе не определяет logout; OIDC добавляет два flow. <em>RP-Initiated Logout</em>: приложение редиректит браузер на /endsession IdP с id_token_hint, IdP завершает свою сессию и редиректит обратно на post_logout_redirect_uri. <em>Front-Channel Logout</em>: IdP включает iframe-ы, указывающие на logout-URI каждого приложения в своей logout-странице, поэтому все приложения чистят local sessions параллельно. <em>Back-Channel Logout</em>: IdP POST-ит signed logout_token на back-channel-logout-URI каждого приложения; приложение валидирует подпись и инвалидирует сессию в своей БД. Back-channel — единственный logout, работающий, когда браузер закрыт; production-системы комбинируют front-channel для активных сессий и back-channel для durable cleanup.</p>
    <p><strong>Federation и IdP цепочки.</strong> Иногда identity провайдер сам не аутентифицирует пользователя, а делегирует другому IdP. Пример: корпоративная app использует Okta как IdP, но Okta сама делегирует Azure AD клиента через SAML. Когда пользователь нажимает "Sign in with Okta", Okta редиректит к Azure AD, получает SAML assertion, превращает в OIDC id_token и возвращает приложению. Эта цепочка может расти: app → Okta → Azure AD → on-prem ADFS. Каждый hop добавляет latency и поверхность атаки; production-системы стараются ограничивать глубину федерации до 2-3 уровней. Дополнительная сложность — token claim mapping: claim "groups" в Azure AD становится "okta:groups", потом "app:roles" — каждая трансформация может потерять данные или ввести bug.</p>
    <p><strong>Multi-factor authentication (MFA) внутри OAuth.</strong> Современные IdP обычно прозрачно интегрируют MFA: когда пользователь логинится на /authorize endpoint, IdP отдельно решает, нужен ли второй фактор (TOTP, SMS, push-нотификация в authenticator app, passkey или WebAuthn). С точки зрения OAuth-flow приложение этого не видит — оно просто получает id_token с claim acr (Authentication Context Class Reference) или amr (Authentication Methods References), описывающим использованные факторы. Приложение может потребовать определённый acr через параметр acr_values на /authorize: например acr_values=urn:mace:incommon:iap:gold означает "только сессии с MFA". IdP либо удовлетворяет это (поднимая MFA-prompt если нужно), либо отвечает ошибкой. Это позволяет sensitive endpoints (transfer, delete-account) требовать step-up authentication — пользователь уже залогинен с паролем, но при попытке transfer IdP подбросит MFA-challenge, и только после успеха выдаст токен с acr=gold.</p>
    <p><strong>Throttling и rate-limiting на /authorize и /token.</strong> OAuth endpoint-ы — обычные цели для брут-форса. /authorize атакуют для генерации фишинг-flow с целью украсть consent; /token атакуют для brute-force client_secret или подбора code при слабом entropy. Production-IdP применяют слоистый rate-limiting: per-IP (защита от mass-scan), per-client_id (защита от ошибочного клиента в loop), per-user (защита от прицельной атаки), глобальный (защита от DDoS). Превышение порога даёт 429 Too Many Requests с Retry-After. Дополнительно — adaptive rate-limiting на основе ML-сигналов (необычная гео-локация, новый device-fingerprint, превышение скорости попыток) — клиент может получить captcha-challenge или forced step-up MFA. Этот слой обычно живёт в API gateway перед auth-сервером, а не в самой auth-логике.</p>
    <p><strong>Тестирование OAuth-реализаций.</strong> OAuth — это протокол, где почти каждый bug = CVE. Test suite должен покрывать: positive flow (happy path для каждого grant type), negative flow (отсутствие state, mismatched state, отсутствие nonce, mismatched nonce, expired code, replayed code), edge cases (empty scope, unknown scope, multiple redirect_uri match attempts), security regressions (alg=none JWT, RS256→HS256 confusion, missing aud, wrong iss, future iat, past exp). Conformance test suites: OpenID Foundation Certified Test Suite (mandatory for FAPI compliance), Auth0 Authentication API Debugger, oauth.tools. Production-ready OAuth implementation проходит OIDC Certification — формальная аккредитация OpenID Foundation, которая запускает сотни test cases против deployment. Без сертификации — это experimental, не production.</p>
    <p><strong>Дополнительные параметры безопасности на /authorize.</strong> Помимо state, nonce, code_challenge, современный /authorize-запрос несёт max_age (максимальный возраст user authentication session — выше = re-prompt), prompt (none / login / consent / select_account — управление UX), login_hint (предполагаемое имя пользователя для UX), ui_locales (язык интерфейса), id_token_hint (для silent re-authentication при page reload SPA). Параметр prompt=none — критичный для SPA: на page reload приложение делает invisible iframe /authorize запрос с prompt=none, и если у пользователя есть валидная IdP-сессия, новый id_token приходит без user-interaction; иначе IdP отвечает login_required и SPA знает: показать "Sign in" кнопку. Это позволяет SPA восстанавливать authentication state после reload без полного logout flow.</p>

  <Fragment slot="senior">
    <p><strong>Bearer-токены — legacy дефолт; sender-constrained токены — будущее.</strong> Bearer access-токен — это ровно то, что в названии: любой держатель представляет его, и сервер принимает. Кража = компромисс. Два RFC чинят это. RFC 8705 (mTLS-bound токены) привязывает access-токен к конкретному X.509 client cert — resource server верифицирует, что TLS-presented client cert совпадает с cnf (confirmation) claim в токене, и отказывает при расхождении. RFC 9449 (DPoP — Demonstrating Proof of Possession) привязывает токен к client-controlled key pair без TLS client cert — каждый API запрос включает DPoP-proof JWT, подписанный приватным ключом клиента, с хешем access-токена внутри. Украденные токены бесполезны без соответствующего приватного ключа. FAPI 2.0 (open-banking профиль OpenID Foundation) требует sender-constrained токены через mTLS или DPoP; для любой high-value нагрузки в 2026 (банкинг, healthcare, регулируемые AI агенты) DPoP — практичный выбор, потому что работает для браузерных SPA и mobile app, где mTLS не работает.</p>
    <p><strong>Wire-форма DPoP.</strong> Когда клиент делает token-protected API вызов, он вычисляет DPoP-proof JWT в HTTP заголовке DPoP. Payload proof содержит: jti (случайный uid, сервер кеширует для детекции replay), htm (HTTP method, например POST), htu (HTTP target URI), iat (issued-at timestamp), ath (SHA-256 access_token, привязывая proof к этому конкретному токену). Header proof включает публичный ключ (jwk), использованный для подписи. Resource server валидирует: подпись через embedded jwk, ath равно SHA-256 incoming bearer access-токена, htm и htu совпадают с реальным запросом, iat в допустимом окне (типично 60с), jti не виден недавно (anti-replay cache, типично 5-10 мин окно). Access-токен сам содержит cnf claim с jkt (JWK thumbprint) — jwk proof-а должен хешироваться в этот jkt. Украденный токен без приватного ключа не может сгенерировать valid proof; API вызов отвергается.</p>
    <p><strong>PAR и JAR: укрепление authorize-запроса.</strong> Pushed Authorization Requests (RFC 9126) позволяет клиенту POST authorize-параметры на /par endpoint через TLS-authenticated back channel, получая short-lived request_uri. Клиент затем редиректит браузер на /authorize только с этим request_uri — никаких параметров в URL. Это убирает весь запрос из browser-visible URL (никакой утечки в browser history, referrers, screenshots) и позволяет auth server force-нуть integrity запроса до того, как user-agent в это вообще вовлечён. JAR (RFC 9101) аналогично позволяет клиенту подписывать и шифровать запрос как JWT; auth server валидирует подпись до обработки. Вместе PAR + JAR требуются FAPI 2.0 и GAIN-Trust frameworks для регулируемых identity flow. Обычный consumer OAuth обычно скипает их; банкинг, healthcare, government реализации требуют.</p>
    <p><strong>OIDC discovery и metadata flow.</strong> Современные OIDC клиенты не хардкодят endpoint. Они забирают <code>https://issuer.example.com/.well-known/openid-configuration</code> (RFC 8414) на старте, который возвращает JSON-документ с /authorize, /token, /userinfo, /jwks_uri, /revocation, /introspection, /registration плюс supported response_types, scopes, claims, code_challenge_methods, dpop_signing_alg_values_supported и т.д. Клиент использует это, чтобы драйвить flow динамически. JWKS на /jwks_uri возвращает активные публичные ключи; клиенты кешируют и refresh на rotation events. Header kid в id_token говорит какой ключ использовать. Для multi-tenant SaaS (Auth0, Okta, Azure AD) URL issuer-а включает tenant ID, поэтому каждый tenant имеет свой metadata и JWKS. Production-дисциплина: кешировать .well-known и JWKS 5-15 мин, refresh on signature-validation miss, pre-warm кеши перед известными IdP-ротациями, если IdP их публикует.</p>
    <p><strong>Token introspection vs JWT validation: реальный tradeoff.</strong> Opaque токены требуют от resource server вызов /introspect (или /tokeninfo) у IdP на каждом API запросе — strong consistency на revocation, цена одного extra round-trip на запрос. JWT токены требуют только local cryptographic validation на resource server — fast, scale до миллионов RPS, но отозванный JWT работает до expiry. Production-системы выбирают по throughput-нужде: high-RPS API используют short-lived JWT (5-15 мин expiry) + JWKS rotation, принимая, что revocation распространяется в этом окне. Sensitive API (transfer, delete-account) накладывают introspection поверх JWT validation для write-ов, держа read-paths fast. Маленький server-side кеш "recently introspected tokens" амортизирует cost: introspect раз в 30 сек, кеширует результат, fallback на expiry, когда кеш говорит "active".</p>
    <p><strong>Audience-атаки и cnf-claim паттерн.</strong> Когда один auth server выдаёт токены для нескольких resource server (API A и API B), атакующий иногда может обмануть API B принять токен, выпущенный для API A. Защита — claim aud — resource server ОБЯЗАН валидировать токен aud содержит свой собственный identifier. Некоторые auth серверы опускают aud или ставят его generic строкой, ломая защиту. RFC 8707 (Resource Indicators) позволяет клиенту запрашивать audience-specific токены через resource параметр на /token. Claim cnf (confirmation) сужает связку дальше: токен может использоваться только с proof-ключом в cnf.jkt. Это formal name того, что DPoP enforce-ит — токен "confirms", что используется только держателем matching приватного ключа.</p>
    <p><strong>Реальные production-провалы.</strong> Facebook сентябрь 2018: уязвимость access-token-leak в "View As" feature утекла 50M access-токенов; атакующие могли логиниться как любой пользователь в любом Facebook OAuth client (Spotify, Tinder, Instagram). Фикс: инвалидация 90M токенов. Slack февраль 2017: misconfigured OAuth Redirect URI в third-party Slack app позволил атакующему фишингом украсть auth code workspace owner, escalating до full admin. GitHub Enterprise 2021: баг в PKCE verification разрешил downgrade-атаки против старых клиентов; фикс в patch release. Microsoft Azure AD ноябрь 2024: token-validation cache poisoning позволил crafted токену обойти aud validation ~30 минут на cached negative response; фикс за часы. Паттерн всех четырёх: реализации пропустили одну из mandatory проверок или имели tiny logic bug в проверке, и impact — full account takeover или token replay.</p>
    <p><strong>Production-наблюдаемость для OAuth flow.</strong> Минимально-жизнеспособный дашборд: authorize_request_total по client_id и response_type, token_request_total по grant_type и outcome (success / invalid_grant / invalid_client / invalid_scope), token_introspection_latency_p99, jwks_cache_hit_ratio, id_token_validation_failure_total по failure_reason (sig / iss / aud / nonce / exp / iat), refresh_replay_detected_total (non-zero rate = вероятный compromise indicator), dpop_proof_failure_total по reason. Алерт на refresh_replay_detected_total выше нуля, на id_token_validation_failure_total spikes (часто JWKS cache miss storm во время ротации), на token_introspection latency выше 200ms p99 (IdP перегружен). Аудит-лог каждый consent grant + revoke event; sign и timestamp для regulatory retention.</p>
    <p><strong>История: OAuth 1.0 — OAuth 2.1.</strong> OAuth 1.0 (RFC 5849, 2010) использовал per-request HMAC подписи — безопасно, но операционно болезненно. OAuth 2.0 (RFC 6749, 2012) поменял подписи на TLS + bearer токены, dramatically simpler, но ценой "каждый misconfig — CVE". OAuth 2.0 errata копились (RFC 6750, 7521, 7636 PKCE, 8252 native apps, 8414 discovery, 8628 device code, 8705 mTLS, 9068 JWT access tokens, 9101 JAR, 9126 PAR, 9449 DPoP). OAuth 2.1 (draft 2023-2025, expected final 2026) консолидирует safety errata в один документ: PKCE мандатно, implicit удалён, password grant удалён, exact redirect match required, refresh rotation required. OIDC 1.0 (2014, errata sets through 2024) добавляет identity слой. FAPI 2.0 (final 2024) — high-assurance профиль для finance/health.</p>
    <p><strong>Cross-protocol взаимодействия.</strong> SAML 2.0 всё ещё обслуживает enterprise SSO, где IT-команды инвестировали в ADFS, Shibboleth или Okta SAML. SAML и OIDC сосуществуют через "IdP-initiated" и "SP-initiated" паттерны; современная federation обычно делает OIDC для новых приложений и SAML для legacy. WebAuthn (FIDO2 passkeys) заменяет пароль на front door OAuth — пользователь аутентифицируется в IdP через passkey, а IdP всё ещё выдаёт OAuth токены приложениям. SCIM (RFC 7644) provisions пользователей в приложения; OAuth авторизует сам SCIM API. Комбинация OAuth + WebAuthn + SCIM — современный enterprise stack: passkey-primary auth, OAuth для app-delegation, SCIM для lifecycle. mTLS для service-to-service; OAuth client_credentials grant для service-to-service, когда mTLS недоступен.</p>
    <p><strong>Deployment паттерны: SPA vs native app vs server-side.</strong> SPA используют authorization-code-with-PKCE, хранят access-токены только в памяти (никогда в localStorage), refresh-ят через short-lived rotating refresh-токены в httpOnly куках. Native apps используют authorization-code-with-PKCE с private-use URI scheme или universal links для редиректа; хранят токены в OS keychain. Server-side приложения используют authorization-code-with-PKCE (PKCE всё ещё требуется в 2.1) + client_secret, хранят токены в сессии, refresh через backend. Для machine-to-machine (CI/CD pipeline вызывает API) — client_credentials grant; никогда не embed user-tokens в CI. Для CLI и IoT — device-code flow: устройство показывает код, пользователь вводит его на телефоне, устройство polls для токена.</p>
    <p><strong>Audit-логирование и SIEM-интеграция OAuth.</strong> Production OAuth-стек обязан логировать каждое security-событие: consent grant, consent revoke, token issue, token refresh, token revoke, failed validation, replay-detected. Каждая запись signed (HMAC по shared secret или crypto-keyed по KMS) с timestamp, client_id, user_sub, scope, IP, User-Agent, событие. Эти логи поступают в SIEM (Splunk, Sentinel, Datadog Cloud SIEM) и triggers оповестители. Корреляция: "пользователь X отозвал consent для приложения Y, но access-токен ещё работает 14 минут" — SIEM немедленно поднимает security alert. Это требование compliance в финансовых регуляциях (PCI DSS 10, SOC 2 CC7.2) и health (HIPAA 164.312(b)). Retention: типично 90 дней hot-доступа, 2 года warm-archive хранения, и банкинг/здравоохранение — до 10 лет внутри специально выделенного WORM-хранилища без какой-либо возможности удаления или последующей модификации записей.</p>
    <p><strong>Митигации кражи токенов сверх ротации.</strong> Cookie security: httpOnly (нет JS access), Secure (только HTTPS), SameSite=Lax или Strict (cross-site CSRF защита). Избегать хранения access-токенов в localStorage (XSS-readable) — держать в памяти. Для mobile — OS keychain. Для SPA — access-токен живёт только в closure или React state, никогда не персистится; на page reload SPA делает silent /authorize round (prompt=none), используя refresh-токен в httpOnly cookie. Cross-Origin-Opener-Policy и Cross-Origin-Embedder-Policy лочат popup, используемые в OAuth flow, против opener.postMessage атак. CSP (Content-Security-Policy) блокирует случайное third-party script execution, которое может exfiltrate токены. CORS ограничивает, какие origin могут вызывать token endpoint с credentials.</p>
