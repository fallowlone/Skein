Страница — это данные плюс chrome. Chrome быстрый — HTML, CSS, JS-бандлы кешированы на CDN. Данные медленные — DB-запрос, API-вызов, third-party интеграция. Где происходит fetching, решает, увидит ли пользователь контент за 200мс или 2000мс. Три ответа: fetch на сервере до рендеринга, fetch на клиенте после загрузки JS, или stream-гибрид. Неверный ответ добавляет round-trips к LCP; верный их прячет.

<Crux>Server fetch + stream = LCP под 1с. Client fetch после JS = LCP свыше 3с. Waterfalls убивают; Promise.all лечит.</Crux>

Ментальная модель: каждая страница имеет critical path сетевых round-trips от «пользователь клик» до «main content visible». На чистой client-rendered SPA путь — HTML → JS-бандл → React mount → fetch data → render — четыре последовательных trip-а, легко 2-3 секунды на медленной сети. На SSR странице путь — server fetch (параллельно) → HTML с данными → browser paint — один эффективный round-trip, если сервер умно параллелизирует свои fetch-и. React Server Components идёт дальше: сервер стримит контент по мере доступности, поэтому пользователь видит header страницы за 200мс и slow data-heavy секцию моментом позже. Искусство — соответствовать стратегии рендеринга форме данных — known-at-request-time данные на сервере, user-interactive state на клиенте, с TanStack Query или SWR, управляющими клиентским кешем.

    <p><strong>Где fetching может происходить.</strong> Современные фреймворки поддерживают четыре места fetching, каждое с разными LCP-имликациями. <em>Build time</em> (static generation): данные запечены в HTML на build, нулевая per-request fetch-цена, но stale до rebuild. Используй для блог-постов, маркетинговых страниц, всего меняющегося раз в час и реже. <em>Server-side at request time</em> (SSR или Server Components): fetch на сервере во время рендеринга response. HTML содержит данные inline. Один round-trip от браузера к серверу. Используется Next.js getServerSideProps, RSC async components, Remix loaders. <em>Streaming server-side</em>: сервер начинает слать HTML до того, как все данные готовы. Initial chunk имеет layout shell; subsequent chunks содержат данные, как они приходят. Реализовано через React Suspense boundaries — каждый boundary независимо streamable. <em>Client-side after mount</em>: useEffect, useQuery, useSWR. Страница монтируется без данных; данные приходят после того, как JS работает и fetches стартуют. Необходимо для user-interactive flows (фильтры, real-time updates).</p>
    <p><strong>React Server Components (RSC).</strong> Feature React, стабильная в React 19, дефолт в Next.js 15 app router. RSC — компоненты, рендерящиеся только на сервере — они могут быть async-функциями, вызывать БД напрямую, использовать любую серверную библиотеку. Сервер рендерит их в специальный «RSC Payload» (сериализованное React-дерево) плюс initial HTML. Клиент получает HTML для мгновенного paint, потом RSC Payload для гидратации. RSC не шипят свой код клиенту. Компоненты помечаются 'use client' для opt-in client-rendering (для интерактивности, state, effects). Паттерн: держи static и data-display компоненты server-side; помечай только interactive leaves как client. Bundle size dramatically уменьшается, потому что React component tree больше не shipped полностью браузеру.</p>
    <p><strong>Suspense boundaries и streaming.</strong> React Suspense — примитив «показать fallback, пока эта часть tree грузится». На сервере Suspense boundary позволяет остальной части tree stream-иться, пока suspended часть всё ещё резолвится. Клиент получает HTML chunks по порядку: сначала layout shell со skeleton fallbacks, потом каждый suspended chunk, как его данные резолвятся. Каждый chunk — маленький кусок скрипта, swap-ающий fallback на реальный контент. Профит: TTFB падает до «сколько занимает layout» (часто под 100мс), и slow data секции не блокируют остальную страницу. Best practice: каждая независимая data dependency получает свой Suspense boundary с dimension-matched skeleton fallback, чтобы layout не сдвигался при приходе контента.</p>
    <p><strong>Client-side кеширование: TanStack Query и SWR.</strong> Обе библиотеки реализуют тот же core-паттерн: shared cache, keyed query key, со stale-while-revalidate семантикой. <code>useQuery(['products', id], fetchProduct)</code> возвращает немедленно с кешированными данными, если доступны, потом re-fetches в фоне; UI re-renders, когда свежие данные приходят. Cache lifetimes тюнятся: <code>staleTime</code> контролирует, как долго данные считаются свежими, <code>gcTime</code> (formerly cacheTime) контролирует, как долго unused data сидит до garbage collection. Обе библиотеки дедуплицируют concurrent queries с тем же ключом (single-flight pattern). Обе поддерживают optimistic updates (применить mutation локально до подтверждения сервера; rollback на error). Размеры разные: SWR ~5KB minified+gzipped, TanStack Query ~16KB, но с DevTools, infinite queries, parallel mutations.</p>
    <p><strong>Optimistic updates.</strong> Паттерн для write paths, которые должны чувствоваться мгновенными: когда пользователь кликает «Like», обнови локальный кеш, показав «Liked» немедленно, fire mutation на сервер параллельно, rollback, если сервер отверг. TanStack Query <code>onMutate</code> callback запускается до request; <code>onError</code> делает rollback. UI чувствуется мгновенным, потому что пользователь никогда не ждёт round-trip. Tradeoff: brief inconsistency, если сервер позже отверг (rate-limited, validation error). Для идемпотентных действий (like, bookmark, mark-read) почти всегда стоит того; для не-идемпотентных (перевод денег, submit order) оптимистичный UI вводит в заблуждение и должен избегаться.</p>
    <p><strong>Cache invalidation стратегии.</strong> Когда mutation успешна, dependent queries должны быть обновлены. TanStack Query предлагает три подхода: <em>invalidate</em> (пометить queries как stale, refetch при следующем observer), <em>setQueryData</em> (записать новое значение прямо в кеш), <em>refetch</em> (форсировать немедленный fetch). Самый дешёвый — setQueryData, когда mutation response содержит новое state. Invalidate безопаснее, когда множественные queries зависят от mutation. Refetch резервируется для случаев, когда нужны свежие данные немедленно и нельзя доверять mutation response. Большинство production кода использует микс: setQueryData для directly-mutated entity, invalidate для всего, что её листит.</p>
    <p><strong>Request waterfalls в деталях.</strong> Классический waterfall: компонент A фетчит user data, потом рендерит компонент B, который фетчит user posts, потом рендерит компонент C, который фетчит comments на каждый пост. Три последовательных round-trip минимум. Total latency = A + B + C, хотя ответа A было достаточно знать все три queries. Фикс-паттерны: <em>parallel from above</em> — parent фетчит все три (через Promise.all или оркестрируя queries на higher level). <em>data colocation</em> — реструктурируй API так, чтобы один вызов возвращал все нужные данные. <em>prefetch</em> — начни следующий fetch до навигации пользователя, используя время, что пользователь тратит читая текущую страницу. <em>RSC parallel</em> — siblings в серверном дереве фетчат concurrent by default. TanStack Query <code>useQueries</code> hook запускает множественные queries параллельно из одного вызова.</p>
    <p><strong>SSR hydration и dual-fetch ловушка.</strong> Частый баг: сервер фетчит данные, рендерит HTML, шипит; клиент гидрирует, re-mount-ируя те же компоненты, которые потом фетчат данные снова. Два fetch на одну загрузку страницы, server-время потрачено впустую. Фикс — dehydration/rehydration: сервер фетчит, сериализует cache state в script-тег в HTML, клиент TanStack Query/SWR читает это state на mount вместо re-fetching. <code>HydrationBoundary</code> в TanStack Query и <code>fallback</code> prop в SWR — API для этого. RSC обходит это полностью — server components не гидрируются, поэтому не могут dual-fetch. Mixed RSC + client query setups требуют careful boundary placement.</p>
    <p><strong>LCP и critical fetch.</strong> Largest Contentful Paint измеряет, когда main content становится visible. Для product-страницы LCP-элемент обычно — hero image или product title. Если title server-rendered, LCP bound HTML arrival time. Если title client-fetched, LCP bound HTML + JS + fetch — обычно в 2-4 раза дольше. Web Vitals targets: LCP под 2.5с для «good», под 1.5с для excellent. Самое большое LCP-улучшение для большинства apps: переместить data fetching LCP-элемента с клиента на сервер. <code>fetchpriority="high"</code> на LCP image помогает браузеру приоритизировать discovery; preload links для URL LCP image, когда known at build, толкают его раньше.</p>
    <p><strong>Race conditions в interactive fetching.</strong> Классическая гонка: пользователь печатает в search box, каждое нажатие триггерит fetch, ответы приходят out of order. Пользователь печатает «rea» потом «react». Сервер отвечает на «rea» после «react» из-за медленности — UI показывает результаты «rea», пока input показывает «react». Фикс-паттерны: AbortController для cancel in-flight на новый query, response-tagging исходным query для discard mismatched, debounce так чтобы только последнее нажатие триггерило fetch. TanStack Query обрабатывает это через queryKey механизм: response ассоциирован с key, cache хранит только последнее. Custom fetch-код должен реализовать одно из этих — silent failure mode otherwise.</p>
    <p><strong>Pagination и infinite scroll паттерны.</strong> Три подхода. <em>Offset-based</em>: <code>?page=2&limit=20</code>. Просто, но ломается под concurrent inserts (item shifts between pages). <em>Cursor-based</em>: <code>?cursor=abc123</code>. Стабильно через inserts, потому что cursor — стабильный position marker (обычно sort-key value). <em>Keyset-based</em>: <code>?after_id=42&after_date=2026-05-13</code>. Специализированный cursor, encoding multiple sort keys. TanStack Query <code>useInfiniteQuery</code> обрабатывает cursor-based нативно, prefetching next page при приближении пользователя ко дну. Data shape impact: списки должны использовать cursor pagination для корректности под churn; offset приемлем только для static или редко-меняющихся данных.</p>
    <p><strong>Prefetch и prerender.</strong> Smart fetching может стартовать работу до того, как пользователь явно навигирует. <em>Hover prefetch</em>: когда курсор hover-ит над ссылкой, начни fetching данных target page. К моменту, когда пользователь кликает (обычно 100-300мс позже), данные уже in flight или сделаны. <em>Viewport prefetch</em>: как ссылка scroll-ит в view, начни prefetching. <em>Predictive prefetch</em>: ML-driven, наблюдает прошлые navigation patterns и prefetches likely next pages. Next.js Link prefetches by default; TanStack Query prefetchQuery seeds cache. Tradeoff: prefetching использует bandwidth спекулятивно; злоупотреби на mobile — разрушишь data plans. Limit prefetch к next-likely targets и избегай prefetching больших media.</p>
    <p><strong>Server Functions и form actions.</strong> Помимо чтения, RSC-стек также обрабатывает запись через Server Functions — async-функции, помеченные <code>'use server'</code>, которые могут быть вызваны из client components, но выполняются на сервере. Они получают стабильный URL endpoint, generated фреймворком; client-side вызов — fetch, которое framework routes к функции. В сочетании с form actions (<code>&lt;form action=&#123;serverFunc&#125;&gt;</code>) они заменяют большинство ad-hoc API routes. Type-safe через границу, secrets остаются server-side, прогрессивное улучшение работает (форма submits даже без JS). Не убирает нужду в Idempotency-Key для критичных write операций — Server Function может быть retried фреймворком, и если она триггерит платёж, нужны те же защиты, что в queues piece.</p>
    <p><strong>Error boundaries и graceful degradation.</strong> Когда server-side fetch падает (db down, timeout, rate-limited), что видит пользователь? Без обработки — error page или вечный spinner. С React Error Boundaries — fallback UI с retry-кнопкой. RSC + Next.js имеет error.tsx файл-конвенцию: в каждой route segment можно положить error.tsx, который рендерится, если что-либо в этой ветке упадёт. Лучшая практика: размещай error boundary на уровне фичи, не на уровне приложения. «Одна сломанная widget» не должна сваливать весь дашборд. Логи ошибок (Sentry, LogRocket) ловят production-падения; в dev runs error message указывает на точную причину. Pattern: optimistic UI on success path + error boundary on failure path + retry button = пользователь никогда не stuck.</p>
    <p><strong>Authentication и data fetching.</strong> Где живёт session? Cookie на server-side гарантирует, что server-fetched данные имеют правильную авторизацию. Client-side fetches должны передавать cookie automatically (same-origin) или Authorization header (cross-origin).     <p><strong>RSC payload format: не HTML, не JSON.</strong> Когда React рендерит Server Component, output — custom serialization, называемая RSC Payload — компактное представление React tree плюс ссылки на client components по их bundle URL. Браузер получает initial HTML (рендеренный из RSC tree для быстрого paint) плюс RSC Payload (используется для hydration React tree для последующих навигаций). RSC Payload format намеренно не JSON: это streaming-friendly format с row-prefix кодами (M для module, J для JSON literal и т.д.), чтобы React мог начать обработку до прихода full payload. Каждая row ссылается на предыдущие rows по ID, инкрементально строя tree. Это позволяет браузеру рендерить части tree, как сеть доставляет их. Format задокументирован в React RFC repository; авторы фреймворков реализуют servers, эмитящие его (Next.js, Waku, Remix), и clients (React DOM), потребляющие его.</p>
    <p><strong>Server Functions и action protocol.</strong> Помимо Server Components, React 19 вводит Server Functions — async-функции, помеченные <code>'use server'</code>, которые могут быть вызваны из client components, но выполняются на сервере. Они получают stable URL endpoint, generated фреймворком; client-side вызов — fetch, который framework routes к функции. В сочетании с form actions (<code>&lt;form action=&#123;serverFunc&#125;&gt;</code>), Server Functions заменяют большинство ad-hoc API routes. Профит: type-safe через границу (TypeScript signature совпадает), не нужно вручную определять request/response shapes, framework обрабатывает serialization и progressive enhancement. Ограничения: аргументы должны быть serializable, secrets остаются server-side (клиент никогда не видит function body, только invokes endpoint), authentication/authorisation должны быть явно внутри функции.</p>
    <p><strong>Streaming hydration order.</strong> Когда сервер стримит HTML с Suspense boundaries, браузер строит DOM прогрессивно. React selective hydration совпадает с HTML chunks, как они приходят: layout shell гидрируется первым, потом каждый Suspense child гидрируется, когда его chunk получен. Selective часть: если пользователь кликает кнопку до завершения hydration этой секции, React приоритизирует hydration этой секции первым (click event queued, потом dispatched после hydration). Это «concurrent React» на практике — framework жонглирует partial hydration, user input и incoming server chunks. Production implication: 200KB JS бандл, занимающий 800мс на parse на телефоне, может всё ещё чувствоваться snappy, потому что visible-and-clicked-on секция гидрируется до остальной.</p>
    <p><strong>Caching слои и их взаимодействия.</strong> Современное app имеет много кешей: CDN edge cache (URL-keyed, seconds-to-hours), server-side framework cache (Next.js fetch cache, RSC cache, route segment cache), database query cache (Redis, server memory), client HTTP cache (browser, controlled Cache-Control), client library cache (TanStack Query, SWR, Apollo). Request может быть обслужен любым из них в зависимости от URL, mode и freshness. Invalidation cascade: mutation, меняющая данные, должна invalidate server caches (revalidate path), CDN если применимо (cache-tag-based purge) и client library (queryClient.invalidateQueries). Next.js 15 revalidate functions (revalidatePath, revalidateTag) обрабатывают server + CDN; library cache — ответственность разработчика. Пропуск любого слоя оставляет пользователя пялящимся на stale data.</p>
    <p><strong>Streaming protocols вне HTTP/1.1.</strong> HTTP/1.1 chunked transfer encoding — минимальное требование. HTTP/2 multiplexes streams через одно соединение, чтобы множественные Suspense chunks могли interleave. HTTP/3 (QUIC) дополнительно улучшает head-of-line behaviour на медленных сетях. WebSockets идут дальше request/response для subscription-style flows (chat, live dashboards). Server-Sent Events (SSE) — one-way server-to-client stream, useful для notifications, progress updates, AI chat completion. Выбор зависит от data shape: HTTP для one-shot loads, SSE для one-way streams, WebSockets для bidirectional. Next.js 15 RSC streaming использует HTTP/1.1 chunked или HTTP/2 streams; framework абстрагирует выбор.</p>
    <p><strong>Реальные production сбои.</strong> Vercel 2024: customer RSC migration зашипила Server Component, фетчащий 50 items в loop последовательно вместо Promise.all — TTFB регрессировал с 100мс до 2.5с на affected pages. Поймано в production после observability dashboards отметили regression; пофиксили оборачиванием fetches в Promise.all. Spotify Web Player 2023: TanStack Query optimistic update для «add to playlist» использовал setQueryData, но не snapshot-нул previous state в onMutate, и когда сервер отверг request, rollback установил undefined вместо реального previous state — playlists появились исчезнувшими на несколько секунд. Пофиксили использованием канонического паттерна с queryClient.getQueryData snapshot. Linear 2024: SSE-based real-time sync использовал неверную message ID схему; на reconnect клиент пропускал сообщения, отправленные во время disconnect окна, ведя к «я перетащил эту карточку, но она отскочила». Пофиксили server-assigned монотонным ID и client-side resume-from-last-id. Паттерн: data-fetching баги прячутся как UX papercuts, аккумулирующиеся; serious analysis «почему это чувствуется медленно / неверно» обычно surfaces их.</p>
    <p><strong>Observability для data fetching.</strong> Минимальные метрики: <code>fetch_duration_seconds</code> histogram by endpoint, <code>fetch_error_total</code> by endpoint + error_kind, <code>rsc_payload_size_bytes</code> by route, <code>cache_hit_ratio</code> by query key (client library), <code>web_vitals_lcp_seconds</code> p75 + p95 (RUM). Distributed tracing: каждый fetch несёт trace ID, пропагируемый через framework; можно видеть full waterfall single user request от браузера через framework через БД. Алерты: LCP p75 регрессирует >20% в любое 10-min окно, fetch_error_rate выше baseline, cache_hit_ratio падает ниже исторической нормы (часто сигнал invalidation бага). Более сложная метрика: time-to-first-meaningful-paint (TTFB → first Suspense chunk → LCP) — Next.js 15 экспонирует в built-in telemetry.</p>
    <p><strong>Edge runtime ограничения.</strong> Многие фреймворки (Next.js, Cloudflare Workers, Vercel Edge) предлагают «edge runtime» — Node-compatible-ish окружение, работающее на CDN edges вместо в централизованном data center. Latency до пользователя — single-digit мс vs сотни для traditional servers. Tradeoffs: ограниченные API (нет Node fs, нет native bindings, меньше memory limits), Web-standard API только (fetch, crypto.subtle, URL). Edge идеален для data-fetching, хитающего globally-replicated source (Planetscale, FaunaDB, Cloudflare D1) и routing результатов обратно. Edge-rendered RSC — bleeding-edge паттерн в 2025-2026: сервер работает на edge, данные приходят из nearby replica, пользователь видит first paint за 50-100мс независимо от географии.</p>
    <p><strong>Service worker caching: offline-first слой.</strong> Service worker может intercept fetches, serve из локального Cache API store и обновлять в фоне. Stale-while-revalidate семантика на этом слое даёт «второй визит чувствуется мгновенно даже на медленной сети». Workbox — стандартная библиотека. Pitfall: stale service worker code может persist часами после deploy, если не сконфигурирован для self-update; production deploys должны включать version bump service worker. Service workers essential для offline-capable apps (PWAs); для чисто online apps — оптимизация поверх HTTP caching. Cache lifecycle (install, activate, fetch) — small state machine; правильное получение activation (skipWaiting, clients.claim) — самый частый source багов service-worker.</p>
    <p><strong>Hydration mismatches.</strong> Когда сервер рендерит HTML, и клиент монтирует тот же React tree, оба должны производить идентичный output. Любое различие (date formatting using local timezone, random values, conditional content based on screen size) вызывает hydration mismatch warning и silently ломает интерактивность в production. Фикс-паттерны: <em>useEffect для client-only логики</em> — рендерь safe initial state на обеих сторонах, мутируй в client-specific state после mount. <em>suppressHydrationWarning</em> для known-divergent leaves (timestamps, formatted with locale). <em>Client Components для genuinely interactive частей</em>. Hydration step неявный в любом SSR setup; mismatches случаются тихо и аккумулируются. React 19 улучшенные hydration error messages помогают; production teams добавляют error-boundary monitoring (Sentry), чтобы поймать их до того, как пользователи заметят.</p>
    <p><strong>Bundle splitting и code splitting.</strong> RSC уменьшает размер бандла per-page потому, что не client-rendered компоненты не shipped. Но даже client-rendered код можно разбить: dynamic import (<code>const M = await import('./M')</code>), React.lazy + Suspense для defer-загрузки тяжёлых компонентов. Bundle analyzer (webpack-bundle-analyzer, Next.js встроенный) показывает, какие пакеты доминируют по размеру. Типичные подозреваемые: lodash (импорти conkretly: <code>import &#123; debounce &#125; from 'lodash/debounce'</code>, не <code>lodash</code> целиком), moment.js (замени на date-fns или Intl.DateTimeFormat), огромные icon-packs (lucide-react импортируется selectively). Цель: critical-path бандл под 50KB для LCP-критичных страниц. Остальное defer-ится.</p>
    <p><strong>Real-time updates без polling.</strong> WebSockets, Server-Sent Events, polling — три выбора для server-push UI. Polling простейший: <code>useQuery</code> с refetchInterval=5000 шлёт fetch каждые 5с. Cheap для серверной нагрузки, но добавляет 0-5с latency и тратит bandwidth. SSE — long-lived HTTP response, сервер push-ит events through stream; one-way (server → client), идеально для notifications, presence updates, AI chat completion. WebSockets — bidirectional, нужны когда клиент тоже push-ит (multiplayer collaboration, chat). Каждое соединение стоит ресурсов на сервере; для миллионов пользователей нужен dedicated infrastructure (Redis pub/sub, Pusher, Ably). Pitfall: reconnect logic должен resume-ить с правильного места — server-assigned монотонные message IDs + client-side last-seen-id критичны для гарантии, что reconnect не пропустит ни одного событий и не доставит дубликат — та же форма, что at-least-once delivery semantics в queues piece — реальные real-time системы фактически работают на тех же принципах message-bus, что и backend очереди, и страдают от тех же race conditions без правильной reconnect-стратегии, поэтому опыт работы с очередями напрямую переносится на frontend real-time системы.</p>
