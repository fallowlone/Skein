Вы вводите `google.com`. Браузер не знает где Google. Он отправляет вопрос рекурсивному резолверу — компьютеру делающему детективную работу. Резолвер тоже не знает. Он начинает с корня DNS, спрашивает кто отвечает за `.com`, получает указатель на TLD-сервер, спрашивает снова, получает указатель на авторитативный сервер Google, спрашивает там и получает финальный ответ: `142.250.185.46`. Это разрешение DNS. Каждый раз когда вы заходите на домен, эти переговоры происходят молча.

<Crux>Как резолвер ходит root → TLD → авторитативный чтобы превратить google.com в IP, и где живут кеши.</Crux>

DNS — дерево вопросов и ответов. Дерево укоренено в 13 корневых серверах (реально ~1950+ инстансов через anycast, 2025). Ниже — TLD-серверы (по одному на top-level domain: `.com`, `.org`, `.uk`). Ниже — авторитативные nameserver-ы для каждого домена. <SpiralCue thread="statefulness" lang="ru" /> — кеширование DNS распределяет состояние через браузер, ОС, ISP-резолвер и авторитативный сервер.

    <p><strong>Что делает DNS одним предложением.</strong> Превращает человекочитаемое имя (`google.com`) в числовой адрес (`142.250.185.46`) который реально нужен сети для маршрутизации пакетов.</p>

  <Fragment slot="middle">
    <p><strong>Walk резолвера.</strong> Рекурсивный резолвер начинает с запроса «Какой IP у `cdn.example.co.uk`?». Не знает ответа, спрашивает root: «У кого ответ?». Root: «Не знаю, спроси `.uk` TLD-сервер». Резолвер спрашивает `.uk`: «У кого `cdn.example.co.uk`?» Отвечает: «Спроси авторитативный для `example.co.uk`» (возвращает NS-запись). Резолвер спрашивает авторитативного напрямую и наконец получает A-запись.</p>
    <p><strong>Типы записей.</strong> A (IPv4-адрес), AAAA (IPv6), CNAME (псевдоним), MX (mail-сервер), TXT (свободный текст, SPF/DKIM), SRV (служба), NS (nameserver), SOA (авторитет зоны + serial), PTR (обратный), CAA (какие CA могут выпускать сертификаты), HTTPS/SVCB (RFC 9460, ALPN+ECH ключи). Каждая несёт TTL — секунды актуальности до повторного запроса.</p>
    <p><strong>Кеширование — главный рычаг.</strong> Получив ответ, резолвер его кеширует. Если браузер спрашивает то же самое через 10 с, резолвер возвращает кеш без обращения в интернет. TTL управляет жизнью кеш-записи. TTL=300 (5 мин) — резолвер забывает и переспрашивает каждые 5 минут. TTL=86400 (1 день) — браузер использует ответ день. Высокий TTL = меньше запросов = быстрее (но устаревшие данные задерживаются). Низкий TTL = свежие данные = больше запросов = нагрузка на авторитативные.</p>
    <p><strong>Приватность и целостность.</strong> Традиционный DNS работает по UDP/53 в открытую. Любой прослушивающий видит запросы. DoH (DNS over HTTPS, RFC 8484) шифрует запросы внутри HTTPS, скрывая от ISP. DoT (DNS over TLS) использует TLS на порту 853. Ни тот ни другой не защищают от самого резолвера — он всё ещё видит вопрос — но скрывают от сети.</p>
    <p><strong>Авторитативный vs рекурсивный.</strong> Авторитативный сервер владеет одной или несколькими зонами; отвечает на запросы для имён в этих зонах из локальных файлов зоны и возвращает направления для всего вне его авторитета. Рекурсивный резолвер ничем не владеет; ходит по дереву от имени клиентов, кеширует и возвращает финальный ответ. Эти роли не смешиваются в продакшене — смешанный сервер называется «открытый резолвер» и является источником DNS reflection-атак.</p>
    <p><strong>Итеративный vs рекурсивный запрос.</strong> Когда клиент запрашивает рекурсивный резолвер, в DNS-заголовке установлен бит RD (Recursion Desired) — резолвер соглашается сделать полный walk. Когда сам резолвер запрашивает root или TLD, бит RD очищен — те серверы не рекурсируют, только возвращают что знают плюс направления.</p>
    <p><strong>UDP vs TCP для DNS.</strong> Запросы по умолчанию UDP порт 53; ответ не помещающийся в 512 байт (или 4096 с EDNS0) ставит флаг TC (truncation) и резолвер повторяет по TCP. TCP-fallback частый для DNSSEC-ответов и AXFR/IXFR трансфера зон между авторитативными.</p>
    <p><strong>EDNS0 (RFC 6891).</strong> Оригинальный DNS-протокол ограничивал UDP-ответы 512 байтами. EDNS0 добавил OPT псевдо-запись для согласования большего UDP-буфера (1232 или 4096 байт) и кодов опций для DNSSEC OK (DO), Client Subnet (ECS), Cookies, Padding. Каждый современный резолвер рекламирует EDNS0.</p>
    <p><strong>Glue-записи и in-bailiwick NS.</strong> Когда зона делегирует на nameserver внутри себя (NS для example.com — ns1.example.com), родительская зона должна включить A-запись для ns1.example.com как glue в направлении, иначе резолвер не сможет найти nameserver не разрешив сначала example.com. Без glue — периодические SERVFAIL.</p>
    <p><strong>Негативное кеширование.</strong> RFC 2308 определяет кеширование NXDOMAIN, NODATA, SERVFAIL. NXDOMAIN / NODATA кешируются на min(SOA.MINIMUM, SOA.TTL) — типично 1-3 часа. SERVFAIL кратко (RFC 9520, 30 с-5 мин) чтобы не усиливать сбой но избежать tight retry loops.</p>
    <p><strong>Refresh и распространение.</strong> Когда меняете DNS-запись, мир видит новое значение после истечения кешей. Старый TTL 300 с → каждый кеш забывает за 5 минут. Старый TTL 86400 с → некоторые отдают старый ответ до суток. Best practice для плановой миграции: за неделю до изменения снизить TTL до 60 с, сделать изменение, подождать TTL, поднять обратно.</p>
    <p><strong>Stub vs полный резолвер на клиенте.</strong> ОС запускает stub-резолвер — тонкий клиент посылающий запросы настроенному upstream. Linux: systemd-resolved; macOS: mDNSResponder; Windows: DNS Client. Stub почти ничего не делает: пересылает запросы, кратко кеширует, применяет /etc/hosts. Полный рекурсивный резолвер сидит upstream (роутер, ISP, 1.1.1.1). Браузеры часто обходят OS-stub (Chrome Async DNS, Firefox TRR).</p>
    <p><strong>Зонные трансферы.</strong> Авторитативные реплицируют через AXFR (полный, RFC 5936) или IXFR (инкрементальный, RFC 1995). Primary хранит авторитативный zone-файл; secondary опрашивают SOA serial и при инкременте запрашивают новые записи. NOTIFY (RFC 1996) push-сторона: primary при обновлении отправляет UDP NOTIFY известным secondary.</p>
    <p><strong>SOA-запись.</strong> Каждая зона имеет одну SOA на apex. Поля: MNAME (primary master), RNAME (email админа, @ заменён на .), SERIAL (инкремент при изменении), REFRESH (как часто secondary опрашивает), RETRY (интервал при сбое), EXPIRE (как долго secondary отдаёт устаревшее), MINIMUM (TTL негативного кеша).</p>
    <p><strong>Обратный DNS и PTR.</strong> Прямая зона маппит имя → IP (A). Обратная — IP → имя (PTR) внутри специальных зон in-addr.arpa (IPv4) и ip6.arpa (IPv6). Для 203.0.113.42 PTR-запрос на 42.113.0.203.in-addr.arpa — октеты перевёрнуты для иерархии.</p>
    <p><strong>DNS-based service discovery.</strong> SRV-записи (RFC 2782) позволяют клиентам обнаруживать сервер и порт без хардкода. Kubernetes CoreDNS экспонирует сервисы как SRV+A внутри кластера; Consul делает то же. Apple Bonjour использует DNS-SD over multicast DNS (mDNS, порт 5353) для локального обнаружения устройств.</p>
    <p><strong>Квирки браузерного DNS.</strong> Браузеры не доверяют OS-резолверу слепо. Chrome Async DNS перехватывает OS-путь; Firefox TRR делает то же через DoH. Браузеры также кешируют DNS внутренне ~1 минуту независимо от TTL. Сброс OS-кеша не сбрасывает браузерный.</p>
    <p><strong>Распространённые ловушки записей.</strong> AAAA независимы от A. Домен только с A недостижим из IPv6-only сетей. MX требует hostname (не IP). CAA проверяется только при выпуске сертификата. TXT имеет лимит 255 байт на строку но может нести несколько строк.</p>
    <p><strong>Блок ошибочных представлений.</strong> Один: «TTL это сколько запись валидна». Ложь — TTL это сколько downstream-кеш МОЖЕТ держать. Запись валидна пока авторитативный её не изменит. Два: «CNAME может быть на apex зоны». Ложь по RFC 1034 — CNAME на apex ломает SOA/NS. Современный фикс: ALIAS/ANAME или HTTPS/SVCB. Три: «1.1.1.1 всегда быстрее ISP-резолвера». Часто да, иногда нет — зависит от того пирится ли 1.1.1.1 anycast локально с вашим ISP.</p>
    <p><strong>Формат DNS-сообщения.</strong> Каждое DNS-сообщение имеет 12-байтный заголовок плюс четыре секции переменной длины: Question, Answer, Authority, Additional. Заголовок содержит ID запроса (16 бит, защищает от мисматчинга), флаги (16 бит — QR, OPCODE, AA, TC, RD, RA, Z, RCODE) и счётчики количества записей в каждой секции. Question section имеет один запрос (QNAME + QTYPE + QCLASS). Authoritative ответы имеют AA=1 в заголовке. RCODE 0 = NOERROR, 3 = NXDOMAIN, 2 = SERVFAIL, 5 = REFUSED.</p>
    <p><strong>Pretty-printing DNS-имён.</strong> На проводе DNS-имена кодируются как последовательность label-length-prefixed строк: `\x07example\x03com\x00`. Каждый label максимум 63 байта; полное имя максимум 255 байт. Точка в конце (`example.com.`) сигнализирует absolute name; без — relative. DNS клиенты обычно прикладывают search domains из настроек ОС если name не absolute. Это полезно для коротких имён в локальной сети но иногда вызывает странности когда search-domain резолвится первым.</p>
    <p><strong>Round-robin DNS и DNS load balancing.</strong> Несколько A-записей для одного имени — простая форма load balancing. Резолвер возвращает их в порядке (часто случайно перетасованном на каждый запрос — round-robin). Клиент пробует первый IP; при сбое пробует следующий (Happy Eyeballs или явная логика приложения). Слабые стороны: нет health-check (плохой IP всё ещё возвращается пока админ не уберёт), нет веса (равная нагрузка на каждый IP), TTL-зависимая пропагация. Современная замена — GeoDNS + health checks (Route 53, NS1, Cloudflare Load Balancer).</p>
    <p><strong>Internal vs external DNS (split-horizon).</strong> Компании часто хотят разные ответы для внутренних и внешних клиентов. example.com может разрешаться в 10.0.0.5 для сотрудников в офисе и в 203.0.113.42 для интернета. Реализуется через split-horizon resolver: внутренний резолвер имеет свою зону; внешний публичный авторитативный имеет свою. Запросы делятся по source IP или по сети. Useful for: внутренние сервисы доступные только из VPN, dev/staging endpoints, internal naming.</p>
    <p><strong>ECS на практике.</strong> Когда резолвер использует ECS, он включает префикс клиента в запрос к авторитативному. Например, клиент 203.0.113.42/24 → авторитативный видит «запрос с подсети 203.0.113.0/24» и возвращает географически близкий ответ. Без ECS авторитативный видит только IP резолвера (например 1.1.1.1 anycast PoP). Геомаппинг по resolver IP менее точен — пользователь в Сан-Франциско через 1.1.1.1-Frankfurt-PoP получит европейский ответ.</p>
    <p><strong>Работа с zone-файлами.</strong> Классический формат BIND zone-файла: каждая строка — RR с полями name, TTL, class (обычно IN), type, rdata. Пример: `www.example.com. 3600 IN A 203.0.113.10`. Директивы $TTL и $ORIGIN устанавливают значения по умолчанию. $INCLUDE включает другой файл. Серверы как Route 53 или Cloudflare DNS используют JSON/API вместо текстовых файлов, но семантика та же — те же RR-типы и TTL.</p>
    <p><strong>Wildcards.</strong> Запись `*.example.com A 203.0.113.10` отвечает на любое sub-имя не имеющее явной записи. Полезно для wildcard SSL-сертификатов и catch-all конфигураций. Ограничения: wildcard работает только на одном уровне (не маппит `a.b.example.com`), не работает на apex, не работает если у имени есть любая другая запись. Современная альтернатива — синтез ответов через провайдер (Cloudflare Workers, Lambda@Edge).</p>
    <p><strong>Лимиты и тайминги.</strong> Максимум 13 root-серверов с именами A-M, в реальности тысячи anycast instances. Максимум 255 байт на DNS-имя, 63 байта на label. UDP-payload 512 байт без EDNS0, до 4096 с. Реальные операционные тайминги: запрос к ISP-резолверу 5-30 мс, к 1.1.1.1 anycast 10-50 мс, к авторитативному рядом 10-100 мс, к авторитативному далеко 100-300 мс. Типичный TTL у CDN-фронтенда — 30-300 с; у статических хостинг — 3600 с; у MX-записи — 3600-86400 с.</p>
    <p><strong>Тестирование DNS.</strong> dig — основной инструмент. `dig A example.com` для A-записи; `dig MX example.com` для mail; `dig +trace example.com` для walk delegation; `dig @1.1.1.1 example.com` запросить конкретный резолвер; `dig +short` для скрипта. nslookup — interactive (`server 1.1.1.1`, `set type=MX`, etc). drill (более старый, ldns-based) — альтернатива с лучшей DNSSEC-отладкой. kdig (knot-utils) — современная альтернатива с DoT/DoQ-поддержкой.</p>
    <p><strong>Что такое NS-запись на практике.</strong> NS-запись делегирует ответственность за зону. Например `example.com. NS ns1.example.com.` говорит «авторитативный для example.com — это ns1». Несколько NS-записей даёт резервирование. Резолвер выбирает один (часто по производительности или случайно) и опрашивает его; при сбое переходит к следующему. Best practice — минимум два NS, в идеале географически разнесённых, в идеале у двух разных провайдеров.</p>
    <p><strong>DNS hosting providers.</strong> Cloudflare (бесплатный + платный enterprise), Route 53 ($0.50/zone/month + per-query), Google Cloud DNS, Azure DNS, NS1, DNSimple, BunnyDNS. Различия: API, скорость пропагации, anycast-география, цена per million queries, дополнительные features (GeoDNS, weighted records, health checks, traffic steering). Для серьёзных нагрузок выбор не банальный — характеристики на уровне p99 latency и DDoS protection заметны.</p>
    <p><strong>DNS как часть SDLC.</strong> Управление зонами как кодом: Terraform DNS-провайдеры, OctoDNS (Github tool синхронизирующий зоны через несколько провайдеров), CDK constructs. Это даёт audit log, PR-based changes, CI-проверки. Без code-as-config зональные изменения через GUI-консоль не оставляют следов и трудно ревьюются. Современные devops-команды требуют DNS-as-code.</p>
    <p><strong>Lookup vs reverse-lookup в логировании.</strong> Логи серверов обычно показывают IP клиента. Reverse DNS lookup (PTR-запрос) превращает IP в hostname для удобочитаемости. Но PTR может лгать или быть устаревшим; mail-сервера часто требуют что forward(reverse(IP)) == IP для разрешения отправки. Для безопасности и security-investigation logging IP + ASN + GeoIP даёт лучшую сигнал-цену чем PTR.</p>
    <p><strong>Anycast и stuck-state.</strong> Anycast DNS работает потому что DNS stateless — каждый запрос самостоятелен. Если BGP convergence перебрасывает трафик с одного POP на другой посередине query, нет shared state кроме закешированных записей (любой POP отдаст тот же ответ из кеша). Это даёт устойчивость к сбоям без сложной репликации состояния. Сравните с TCP — там переключение POP во время сессии ломает соединение, поэтому anycast TCP-сервисы обычно требуют stable-state per-flow через BGP atomicity или connection-level routing.</p>
    <p><strong>Внутренний vs внешний DNS в крупных компаниях.</strong> Большие компании часто запускают свой внутренний рекурсивный резолвер для внутреннего DNS-пространства (corp.example.com) с разнесением по регионам. Конфигурация: внутренний резолвер пересылает запросы для corp.example.com в свой авторитативный, а всё остальное — рекурсирует или пересылает в публичный upstream (1.1.1.1 или ISP). Hybrid Active Directory deployments в Microsoft-стеке часто требуют split-horizon DNS чтобы внутренние сервисы видели внутренние имена не утекая в публичный DNS.</p>
    <p><strong>Resolver bypass на мобильных платформах.</strong> На Android и iOS приложения могут запросить системный резолвер (по умолчанию) или подключиться напрямую к выбранному резолверу через DoH/DoT. Многие защитные/VPN-приложения переопределяют системный DNS для контроля трафика. Это даёт пользователю выбор резолвера независимо от настроек сети — полезно для приватности но осложняет enterprise-управление (MDM-профили могут принудительно использовать корпоративный резолвер).</p>
    <p><strong>Истинный размер DNS-вселенной.</strong> Корневая зона ~1500+ TLD (com, org, страновые, generic). Общее количество зарегистрированных доменов на 2025 — ~350 миллионов. .com один — ~165 миллионов. Распределение записей в зонах сильно перекошено: топ-1000 доменов получают большинство трафика, длинный хвост из миллионов с минимальным трафиком. Это влияет на cache design — Zipf-distribution позволяет небольшому кешу резолвера давать высокий hit-rate.</p>

    <p><strong>DNSSEC chain of trust в деталях.</strong> Каждая подписанная зона публикует DNSKEY (публичные ключи), RRSIG (подписи над каждым RRset), NSEC/NSEC3 (аутентифицированное отрицание существования). Две роли ключей: Zone Signing Key (ZSK) подписывает данные RRsets, Key Signing Key (KSK) подписывает только DNSKEY RRset. Родительская зона несёт DS-запись — криптографический хэш KSK ребёнка — подписанная родительским ZSK, до root. Резолвер несёт один trust anchor: отпечаток root KSK. Любое сломанное звено → BOGUS → SERVFAIL. Ротация KSK самый рискованный момент.</p>
    <p><strong>DoH vs DoT vs DoQ — усвоение в 2026.</strong> DoH (RFC 8484) туннелирует DNS внутри HTTPS порт 443; резолвер выглядит как обычный HTTPS-сервер. DoT (RFC 7858) использует TLS на отдельном порту 853; цензоры блокируют 853 целиком. DoQ (RFC 9250) использует QUIC на UDP/853 — TLS 1.3 конфиденциальность + миграция соединений QUIC (DNS переживает Wi-Fi → мобильный handover) + 0-RTT (возобновлённые соединения пропускают handshake). Усвоение 2026: Firefox сообщает DoH-усвоение выше 85% среди пользователей США; над 931 активных DoH-резолверов глобально. Задержка DoH в среднем 12–18 мс, DoT 20–25 мс, DoQ на 40% ниже DoT (12–15 мс по измерениям APNIC 2026). AdGuard и NextDNS поставляют DoQ в продакшене. Chrome дефолтит DoH, Firefox включил с v102, Safari использует DoH в macOS 13+ режиме приватности. Android поддерживает Private DNS (DoT) с версии 9; iOS/macOS экспонируют DoH/DoT через конфигурацию. Enterprise-сети часто отключают браузерный DoH через policy чтобы сохранить инспекцию периметра.</p>
    <p><strong>EDNS Client Subnet (ECS, RFC 7871) утечка приватности.</strong> ECS позволяет рекурсивному резолверу прикрепить IP-префикс клиента (/24 IPv4, /56 IPv6) к upstream-запросам чтобы гео-aware авторитативные возвращали оптимальный edge. Цена: авторитативный (и каждый сервер на пути) узнаёт примерно какой район просматривает домен. Cloudflare 1.1.1.1 отключает ECS по умолчанию ради приватности; Quad9 opt-in; Google 8.8.8.8 включает.</p>
    <p><strong>DNS over QUIC специфика.</strong> Каждый DNS-запрос — отдельный QUIC stream — без head-of-line blocking как в DoH-over-HTTP/2. Connection migration использует QUIC connection ID а не четвёрку, та же DoQ-сессия переживает Wi-Fi → LTE. 0-RTT resumption отправляет запрос в ClientHello при наличии session ticket — экономит 1 RTT. RFC 9250 предупреждает что 0-RTT данные replayable; mitigation — одноразовые resumption tokens.</p>
    <p><strong>Kaminsky / SAD DNS / история cache poisoning.</strong> До 2008 DNS использовал 16-битный transaction ID и фиксированный source UDP port. Kaminsky показал в 2008 что атакующий триггерящий много запросов на случайные sub-имена мог выиграть гонку против авторитативного ответа, отравив кеш. Патч: случайный source UDP port (RFC 5452) — 65k догадок → ~4 миллиарда. 0x20-кодирование добавляет энтропии. 2020 SAD DNS возродил угрозу через ICMP rate-limit side channels на Linux. Современная защита — DNSSEC + DoH/DoT.</p>
    <p><strong>Anycast маршрутизация резолверов.</strong> Публичные резолверы анонсируют один IPv4-префикс (1.1.1.1/32, 8.8.8.8/32) и IPv6 из десятков-сотен POPs по миру. BGP выбирает кратчайший AS-path к каждому пирящему ISP. Cloudflare ~100+ POPs, Google ~40, Quad9 ~150. Ловушка: если ISP пиритится с оператором только в дальнем городе, ваш трафик идёт туда — типичный штраф 30 мс.</p>
    <p><strong>Внутренности резолвера и структура кеша.</strong> Современный рекурсивный резолвер (BIND, Unbound, Knot, PowerDNS) держит кеш по ключу (QNAME, QCLASS, QTYPE) → RRset + TTL + DNSSEC-state. Параллельные lookup-ы на одно имя коалесируют — только один upstream-запрос в полёте даже при 1000 одновременных клиентах. Prefetch (Unbound `prefetch yes`) переспрашивает перед истечением TTL. Память: занятый резолвер кеширующий 10M уникальных имён потребляет ~10 ГБ RAM.</p>
    <p><strong>Производственная наблюдаемость.</strong> `dig +trace example.com` ходит по пути разрешения вживую, печатая каждое направление — канонический инструмент для отладки делегации. `dig +short` для скриптов. `dnstop` читает tcpdump-выход. Для SLO Prometheus blackbox-exporter тестирует задержку резолвера и SERVFAIL-rate. Алерт-пороги: кешированный запрос &gt; 5 мс, некешированный &gt; 100 мс, p99 &gt; 200 мс, SERVFAIL rate &gt; 0.1% устойчиво.</p>
    <p><strong>Кросс-протокольное наслоение.</strong> DNS — первый шаг почти каждого интернет-взаимодействия; сбой каскадно падает. Браузеры кешируют DNS активно (~1 минуту, отдельно от системного резолвера) поэтому один сбой резолвера часто не ломает веб сразу. Сервис-меши используют DNS-based service discovery (Consul, Kubernetes CoreDNS) — misconfigured CoreDNS ломает каждый pod-to-pod вызов. Lambda cold start платит задержку резолвера раз на контейнер.</p>
    <p><strong>NSEC vs NSEC3 — отрицание существования.</strong> NSEC цепится алфавитно: «между alphabet.example.com и zebra.example.com ничего нет». Легко проверять но позволяет «walking» зоны — запросы на несуществующие имена раскрывают все имена. NSEC3 (RFC 5155) заменяет имена хэшами с солью, повышая стоимость перечисления до brute-force хэш-пространства.</p>
    <p><strong>Trust anchor management и DNSSEC в 2026.</strong> Каждый валидирующий резолвер несёт один криптографический секрет как корень доверия: отпечаток публичного ключа KSK root-зоны. Trust anchor предустановлен и обновляется через RFC 5011 автоматическую ротацию ключей — root-зона публикует новый KSK параллельно со старым минимум 30 дней до ротации, чтобы валидирующие резолверы увидели и доверили новому ключу до того как старый уйдёт. Первая в истории ротация — октябрь 2018 (KSK-2010 → KSK-2017). Подготовка заняла годы потому что операторы по всему миру должны были вручную обновить non-RFC-5011-compliant резолверы. Около 1–2% пользователей испытали сбои DNS в 48-часовом окне — мало, но достаточно чтобы ICANN остановила ротацию на 11 месяцев в 2017 давая операторам больше времени. Следующая запланированная ротация где-то в 2027-2028; операционные уроки (долгие окна параллельной публикации, автоматический мониторинг резолверов в диких условиях) формируют playbook сегодня. Регуляторный сдвиг 2026: CA/Browser Forum (Ballot SC-085v2) требует всех публично-доверенных CA валидировать DNSSEC если присутствует во время Domain Control Validation и CAA проверок, эффективно с 15 марта 2026. Impact: домены с неправильно конфигурированным DNSSEC (истёкшие подписи, сломанные цепи делегации) блокируются от выпуска или обновления сертификата до фиксирования. Это требование не мандатирует активацию DNSSEC, но домены которые его используют должны держать его валидным.</p>
    <p><strong>EDNS Cookies (RFC 7873).</strong> Лёгкий механизм аутентификации: клиент и сервер каждый держат 64-битный секрет для вычисления cookie. Клиент включает cookie-опцию в запросы; сервер валидирует. Cookies не шифруют ничего но усложняют spoofing произвольных off-path source IP — снижают DNS-amplification reflection-атаки на порядки. BIND и Knot Resolver включают по умолчанию.</p>
    <p><strong>Encrypted ClientHello (ECH) и HTTPS resource records в 2026.</strong> ECH (RFC 9849, опубликован март 2026) прячет Server Name Indication (SNI) из сетевого слоя — обычно TLS handshake утекает какой домен клиент открывает. ECH заворачивает ClientHello данные в публичный ключ сервера, зашифрованный, так что только правильный сервер может расшифровать. Развёртывание требует двух частей: (1) сервер публикует ECHConfig в DNS HTTPS resource record (RFC 9460), и (2) клиент получает HTTPS запись перед TLS handshake. Статус 2026: 59% mainstream браузеров (Chrome, Edge, Firefox, Safari) поддерживают ECH когда обнаруживают валидные HTTPS records; 4.2% top-100K веб-сайтов и 9.2% top-1M веб-сайтов публикуют HTTPS records с ECH ключами. Cloudflare, первый major CDN, включил ECH на всех планах. OpenSSL 4.0 и NGINX 1.29.4 добавили native ECH поддержку. Усвоение ускоряется по мере того как enterprise прокси и файрволы адаптируются к ECH opacity.</p>
    <p><strong>Серверный rate limiting.</strong> Авторитативные серверы запускают Response Rate Limiting (RRL) для отказа в избыточных идентичных запросах от одной client-subnet — побеждает DNS reflection/amplification. Публичные рекурсивы как 1.1.1.1 rate-limit-ят по source IP. Операторы мониторят REFUSED rate как сигнал DDoS-попыток.</p>
    <p><strong>Зонные трансферы детали.</strong> AXFR посылает всю зону (дорого для больших — Cloudflare несёт миллионы записей на зону). IXFR посылает только diff с последнего serial. Оба работают по TCP — UDP не подходит. NOTIFY заменяет периодический polling event-driven обновлениями. Операционная ловушка: файрвол блокирующий TCP/53 между primary и secondary тихо ломает AXFR и зоны дрейфуют пока кто-то не заметит.</p>
    <p><strong>DNSSEC validation как операционный риск.</strong> Хотя DNSSEC защищает от cache poisoning, ошибки конфигурации создают новые сбойные режимы. Истёкшие RRSIG, забытое обновление DS у родителя после ротации KSK, опечатки в zone-файле — все вызывают BOGUS и SERVFAIL для валидирующих резолверов. Мониторинг expiry DNSSEC-подписей обязателен — типичная подпись валидна ~1 неделю. Автоматизированные пайплайны (например через OctoDNS, OpenDNSSEC) обрабатывают ротацию и валидацию.</p>
    <p><strong>Современные осложнения.</strong> DoH-в-браузере означает что сетевой администратор больше не видит DNS-трафик своих пользователей — корпоративная боль, выигрыш приватности. DNS невидим пока не сломается, а тогда ломает всё; самый частый инцидент «интернет лежит» на самом деле «DNS лежит». Service-mesh используют DNS-discovery; misconfigured CoreDNS убивает кластер. Lambda cold-start платит задержку резолвера на контейнер.</p>
    <p><strong>Lame delegation и orphan glue.</strong> Lame delegation: родитель указывает на NS, но этот NS не считает себя авторитативным для зоны. Происходит когда зона переезжает но один nameserver не обновили. Клиенты иногда получают ответ от lame NS, иногда нет — периодические загадочные сбои. Orphan glue: NS-запись указывает на хост IP которого нет в зоне. Современные TLD-операторы регулярно сканируют и flag-ят такие конфигурации владельцам.</p>
    <p><strong>DDoS на DNS-инфраструктуре.</strong> Авторитативные DNS остаются ценной целью DDoS. Атака на Dyn (октябрь 2016) положила Twitter, Netflix, GitHub. Защита: anycast (большой attack surface разнесён по PoP), большая overprovisioned пропускная способность, RRL (Response Rate Limiting), и второй DNS-провайдер для резервирования. Современная best practice — иметь две независимые authoritative-сети (например один свой + один managed Route53/Cloudflare). Делегация делается через NS-записи у обоих провайдеров.</p>
    <p><strong>Hijacking через registrar.</strong> Захват доменного имени происходит чаще не через cache poisoning а через социальную инженерию регистратора. Атакующий звонит регистратору представляясь владельцем, меняет NS-записи на свои. С этого момента весь трафик домена идёт на атакующего. Защита: registrar lock (изменения требуют дополнительной аутентификации), 2FA на аккаунт регистратора, DNSSEC (хоть и не защищает от смены NS, осложняет дальнейшую атаку).</p>
    <p><strong>Современный DNS-стек.</strong> Authoritative: BIND (классика, GPL, многофункционален), NSD (минималистичный, быстрый, для крупных авторитативных без рекурсии), PowerDNS Authoritative (модульный, с backend-плагинами). Recursive: Unbound (минимальный, быстрый), Knot Resolver (CZNIC, модульный), PowerDNS Recursor. Облачные сервисы: Route 53, Cloudflare DNS, NS1, Google Cloud DNS. Open-source резолверы для частного использования: dnsmasq, systemd-resolved.</p>
    <p><strong>RFC ландшафт DNS.</strong> Основополагающие: RFC 1034 (концепция, 1987), RFC 1035 (детали, 1987). Современные обновления: RFC 8499 (терминология, 2019), RFC 9499 (обновлённая терминология, 2023). DNSSEC: RFC 4033-4035. EDNS0: RFC 6891. DoH: RFC 8484. DoT: RFC 7858. DoQ: RFC 9250. Цепочка RFC длинная и взаимосвязанная — рекомендую начинать с draft-ietf-dnsop-rfc8499bis и оттуда копать.</p>
    <p><strong>Авторитативная архитектура крупных операторов.</strong> Cloudflare DNS, Route 53, NS1 — это не один сервер, а распределённая система. Зональные данные хранятся в центральной БД с ACL и audit log. Изменения публикуются в anycast-edges по push (CDN-like). Каждый edge запускает легковесный DNS-сервер (RRDNS у Cloudflare, NSD-форки у других) обслуживающий запросы за единицы миллисекунд. Метрики: query rate per zone, RCODE-распределение, response-size distribution, ECS coverage. Доступ через API + Terraform-провайдеры для управления зонами как кодом.</p>
    <p><strong>DNS в Kubernetes.</strong> CoreDNS — стандартный DNS-сервер кластера. Создаёт зону `<namespace>.svc.cluster.local` где каждый Service автоматически имеет A/AAAA-запись и SRV для портов. Pod-ы имеют имена в формате `pod-ip.<namespace>.pod.cluster.local`. ServiceDiscovery работает через DNS-имена. Конфиг через ConfigMap. Misconfigured CoreDNS = весь кластер не может общаться. Hardening: rate limiting per pod, кеширование cluster-external запросов, prometheus метрики, alerts на error-rate.</p>
    <p><strong>DDoS-mitigation провайдеры и DNS.</strong> Cloudflare, Akamai, AWS Shield смягчают DNS-атаки на свои anycast-сети. Самые крупные DNS-атаки достигают сотен миллионов QPS. Метрики чтобы знать всё хорошо: дефолтный QPS должен быть стабильно низкий, response-rate близок к 100% в обычное время, p95 latency стабильна. Когда атака — REFUSED rate растёт (RRL срабатывает), p99 latency может скакнуть. Большие операторы пишут про инциденты публично — стоит читать post-mortem-ы.</p>
    <p><strong>Будущее DNS.</strong> Encrypted Client Hello (ECH) делает SNI приватным; DoQ становится стандартом мобильных DNS. Hot debates: должен ли браузер делать DoH напрямую обходя OS-настройки (Mozilla yes, Apple/Google пошли по разным путям). Authoritative DNS-провайдеры всё больше становятся CDN-провайдерами с edge compute и кеширующими прокси встроенными. RPZ (Response Policy Zone) позволяет резолверу применять policy ответы (блокировка известно-вредоносных доменов) на лету. DNS — старый протокол но эволюция продолжается.</p>
    <p><strong>Тонкости TTL и пропагации.</strong> «Пропагация занимает 24-48 часов» — стандартное заблуждение продавцов хостинга. Реальная пропагация — это просто истечение кешей. Если ваш TTL был 300 с до изменения, мир видит новое значение за 5 минут. Если TTL был 86400 с, до суток. Существует кеш браузера (своя политика), кеш OS-stub, кеш ISP-резолвера, кеш публичного резолвера если он используется. Самый медленный кеш в цепи и есть «пропагация». Снижение TTL заранее перед миграцией — это инструмент сократить эту worst-case пропагацию.</p>
    <p><strong>Negative trust anchors (NTA).</strong> Когда DNSSEC цепь сломана на чужой зоне (вы знаете что владелец накосячил), резолверы могут временно отключить валидацию для этой зоны через NTA — клиенты получают неподписанный ответ вместо SERVFAIL. Cloudflare и крупные операторы добавляют NTA через тикет когда сообщения о сломанной DNSSEC массово приходят. NTA — инструмент кризисного управления, не permanent fix.</p>
    <p><strong>Stale-while-revalidate для DNS (RFC 8767).</strong> Когда упсtream недоступен и кеш-запись истекла, резолвер может отдавать устаревший ответ до 1-3 дней (настраиваемо) параллельно пробуя обновить. Радикально улучшает доступность во время сбоев upstream — при наличии любого предыдущего ответа клиенты не видят разрыва. Цена — slightly stale данные. Современные резолверы (Unbound, Knot) включают по умолчанию.</p>
    <p><strong>DNS observability stack 2026.</strong> Метрики: query rate per zone, RCODE distribution, response-size distribution, DNSSEC validation success rate, DoH/DoT/DoQ adoption ratio. Logs: structured (JSON), per-query (если разрешено приватностью). Traces: распределённые трейсы для multi-tier-resolver путей (resolver → forwarder → upstream). Sampling: 1% sampling для basic метрик, 100% для errors/anomalies. Стандартный стек — Prometheus + Loki + Grafana + OpenTelemetry.</p>
    <p><strong>DNS и certificate management.</strong> Каждый TLS-сертификат привязан к hostname через DNS. Let's Encrypt и другие ACME-провайдеры проверяют контроль над доменом через DNS-01 challenge — записывают определённую TXT-запись и проверяют её доступность. Wildcard-сертификаты (`*.example.com`) требуют DNS-01 (HTTP-01 не может покрыть wildcards). CAA-записи указывают какие CA имеют право выпускать сертификаты для домена — браузеры проверяют CAA перед доверием сертификату. Misconfigured CAA блокирует Let's Encrypt и проявляется как непонятная ошибка выпуска.</p>

<Misconception
  id="r-dns-poison"
  title="Внимание: DNS cache poisoning не мёртв"
>
До DNSSEC атакующий мог подделать DNS-ответ и обмануть резолвер кешировать ложные данные. Современные защиты: рандомизация transaction ID и source port, 0x20 case-mixing, DNSSEC валидация — каждый слой обязателен.
</Misconception>

DNS — древний. RFC 1035 из 1987. И всё ещё работает потому что дизайн иерархический и децентрализованный: никакой одиночный сервер не держит все данные, и кеширование распределяет нагрузку. Современные угрозы (cache poisoning, eavesdropping) обрабатываются DNSSEC, DoH и entropy-based защитами. Но фундаментальное дерево остаётся: запрос течёт вниз от root к TLD к авторитативному, ответ течёт обратно и кеши остаются warm.

<KeyTakeaway title="Главное">
DNS — глобально распределённый иерархический key-value-store маппящий имена в IP-адреса (плюс другие типы записей). Рекурсивный резолвер обходит дерево от root → TLD → авторитативный от имени клиентов, кеширует результаты по TTL и возвращает финальный ответ. Операционный фронтир 2026 — шифрованные транспорты (DoH на 443, DoT на 853, DoQ через QUIC), аутентифицированные ответы через DNSSEC и privacy-сознательные выборы вокруг EDNS Client Subnet.
</KeyTakeaway>
