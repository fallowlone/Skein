    <p><strong>Метафора.</strong> Думайте о доставке: вы заказываете посылку (HTTP-запрос). Адрес ищется (DNS). Фургон диспатчируется (TCP). Содержимое запечатывается (TLS). Фургон едет по дорожной сети (IP routing). Локальный депот имеет товар (CDN-кеш). Посылка прибывает (response). Получатель распаковывает (browser render).</p>
    <p><strong>Диалог вслух.</strong> Браузер сам себе: «Мне нужно example.com.» Спрашивает DNS: «где?» Получает IP. Открывает TCP к этому IP. Делает TLS. Отправляет GET / HTTP/3. Получает 200 OK с HTML. Парсит HTML. Спрашивает DNS на cdn.example.com. Открывает новое соединение. Фетчит CSS, JS, изображения. Рендерит. Готово.</p>
    <p><strong>Конкретный сценарий.</strong> Ваш ноутбук в Лондоне открывает https://shop.example.com. DNS разрешает на CDN edge в Лондоне в 20 мс. TCP + TLS handshake к edge: 1 RTT каждый. HTTP/3 GET: ещё один RTT (или 0 если 0-RTT-resumed). Edge кеширует HTML: возвращает. Браузер парсит, находит 30 sub-ресурсов. Ещё 30 запросов на том же соединении, мультиплексированных. Вся страница рендерится в ~300 мс. Тот же сайт без CDN, из Калифорнии: ~1.5-2 с. Вся суть главы в этом ratio.</p>

  <Fragment slot="middle">
    <p><strong>Семь фаз в последовательности с типичными таймингами.</strong></p>
    <p><strong>Фаза 1: DNS Resolution (~30 мс cold, &lt;1 мс warm).</strong> Антон спрашивает Rex «Какой IP у example.com?». Если у Rex закешировано (TTL &gt; 0), он отвечает в микросекунды. Если нет — Rex обходит DNS-иерархию: root → TLD → авторитативный. Каждый хоп — round-trip. Cold DNS в Северной Америке или Европе — 30-100 мс.</p>
    <p><strong>Фаза 2: TCP-рукопожатие (1 RTT, ~10-25 мс регионально, ~56-100 мс межконтинентально).</strong> Антон отправляет SYN Диме. Дима отвечает SYN-ACK. Антон отправляет ACK. Три пакета, один round-trip. После handshake initial congestion window 10 пакетов (IW=10, RFC 6928).</p>
    <p><strong>Фаза 3: TLS 1.3 Handshake (1 RTT new, 0 RTT resumption, ~25 мс).</strong> Антон отправляет ClientHello с pre-shared key и поддерживаемыми наборами шифров. Дима отвечает ServerHello, сертификатом, серверным ключом. Антон валидирует сертификат через подпись Cara. Оба производят ключи. Если у Антона session ticket — early data (0-RTT) сразу.</p>
    <p><strong>Фаза 4: HTTP-запрос (~1 RTT, ~25 мс).</strong> Антон отправляет HTTP-запрос: method, path, headers, cookies. На HTTP/3 это QUIC HEADERS-кадр. На HTTP/2 — HTTP/2 HEADERS-кадр на stream. Дима получает запрос, обрабатывает: auth, DB, response.</p>
    <p><strong>Фаза 5: HTTP-ответ (RTT + processing, ~50 мс).</strong> Дима отправляет ответ: status, headers, body. На HTTP/3 QUIC streams независимы, поэтому если несколько запросов в полёте Дима может interleave ответы.</p>
    <p><strong>Фаза 6: Sub-resource Fetches (parallelized, RTT × depth).</strong> HTML включает ссылки на CSS, JS, изображения. Антон парсит, обнаруживает URL, фетчит. Критические (CSS, шрифты) первыми. На HTTP/3 параллельно 10+ ресурсов мультиплексированных на одном соединении.</p>
    <p><strong>Фаза 7: Rendering (parallelized, 0-100+ мс).</strong> Когда CSS приходит, Антон парсит и строит CSSOM. Когда HTML — парсит DOM. Браузер мерджит DOM + CSSOM → render tree → layout → paint. Если JS блокирует main thread, painting тормозит.</p>
    <p><strong>Полная картина.</strong> Предполагая warm DNS, региональная география (~25 мс RTT), HTTP/3 с 0-RTT resumption, CDN cache hit: DNS (&lt;1 мс) + TLS (0 мс, 0-RTT) + HTTP request (0 мс) + edge processing + response (~10 мс) + subresources (1 RTT, ~25 мс) + rendering (100 мс) = ~150 мс до LCP. Bottleneck — browser rendering pipeline, не сеть.</p>
    <p><strong>Критический render path.</strong> Browser render pipeline зависит от HTML, CSS, и (для интерактивности) JavaScript. HTML парсится по мере прихода — DOM-construction начинается до полного прихода body. CSS блокирует rendering: ничего не paint-ится пока хотя бы один stylesheet не загружен. JavaScript блокирует парсинг кроме как с `async` или `defer`. Browser preload scanner работает ahead основного парсера обнаруживая sub-resource URL и стартуя запросы рано.</p>
    <p><strong>Core Web Vitals.</strong> LCP (Largest Contentful Paint) — когда самый большой видимый элемент завершает рендеринг — типично hero-изображение или главный заголовок. Хорошо: &lt; 2.5 с; плохо: &gt; 4 с. INP (Interaction to Next Paint, заменил FID в марте 2024) измеряет responsiveness через всю сессию — самая длинная задержка между user input и visual response. Хорошо: &lt; 200 мс. CLS (Cumulative Layout Shift) измеряет неожиданное движение layout-а. Хорошо: &lt; 0.1.</p>
    <p><strong>Connection reuse между запросами.</strong> Каждый новый origin требует свежего DNS + TCP + TLS. Cross-origin requests (CDN-hosted page загружающая шрифты с Google Fonts, скрипты от тракера, изображения с другого CDN) платят эту цену per origin. `<link rel="preconnect">` и `<link rel="dns-prefetch">` предупреждают браузер открыть соединения к ожидаемым origins до того как main parser до них дойдёт.</p>
    <p><strong>Resource hints.</strong> `<link rel="preload" as="font" crossorigin>` для шрифтов. `<link rel="preload" as="script">` для критических JS-бандлов. `<link rel="modulepreload">` для ES-модулей. `<link rel="prefetch">` для likely-next-navigation ресурсов. `<link rel="preconnect">` для origins нужных в ближайшие миллисекунды. Современные фреймворки (Next.js, Astro, SvelteKit) эмитят эти hints автоматически.</p>
    <p><strong>HTTP/3 0-RTT specifics для этого flow.</strong> Если браузер имеет session ticket и сервер разрешает 0-RTT, начальный HTTP-запрос путешествует внутри QUIC initial packet — handshake и request летят вместе. Экономит 1 RTT но только для идемпотентных методов. Эффективный выигрыш: 10-30% быстрее first-byte на тёплых соединениях.</p>
    <p><strong>Compression cascade.</strong> Текстовые ответы (HTML, CSS, JS, JSON) сжимаются 70-90% gzip-ом или на 20% лучше Brotli. Статические ассеты pre-compressed на deploy; динамические — runtime-сжатие. CDN edges обрабатывают сжатие прозрачно с edge-side кешированием compressed-вариантов.</p>
    <p><strong>Caching effects через весь запрос.</strong> Warm-запрос попадает: (1) browser memory cache (sub-ms), (2) browser disk cache (~10 мс), (3) CDN edge cache (~20-50 мс), (4) CDN shield cache (~50-100 мс), (5) origin (~100-300 мс). Каждый layer снижает трафик к следующему. Хорошо архитектурированный сайт с content-hash versioning кеширует почти всё на уровнях 1-3 для повторных посетителей.</p>
    <p><strong>Блок ошибочных представлений на синтез-уровне.</strong> Один: «Быстрее сеть всегда значит быстрее страница». Ложь — для cache hits rendering доминирует; для cache misses server compute часто доминирует. Два: «Уменьшение размера bundle всегда помогает». Помогает загрузке, но если rendering JS-bound, parsing-время — bottleneck. Три: «0-RTT экономит время каждому запросу». Экономит только для warm-соединений; cold платят полный handshake.</p>
    <p><strong>Предварительное соединение и warm-up трюки.</strong> Современные страницы могут разогревать сетевой стек до того как пользователь кликнет. `<link rel="dns-prefetch" href="//cdn.example.com">` разрешает hostname в фоне. `<link rel="preconnect" href="//cdn.example.com" crossorigin>` делает DNS + TCP + TLS превентивно. Service Workers расширяют это — могут pre-fetch целые resource bundles на предыдущей навигации.</p>
    <p><strong>Concurrent fetching budgets.</strong> Браузеры enforce per-origin connection limits (6 для HTTP/1.1, сотни streams через одно HTTP/2 или /3 соединение). Browser resource scheduler ранжирует запросы по `Priority` hint (RFC 9218) и встроенной cost-модели. Можете влиять через `fetchpriority="high|low"` атрибут на отдельных элементах.</p>
    <p><strong>Service Workers и offline.</strong> Service Worker — JavaScript-файл который браузер регистрирует как intercepting proxy для всех запросов с вашего origin. Может подавать кеш без сети, queue запросы offline, трансформировать ответы. Стоимость: complexity (двa контекста выполнения должны быть синхронны), debugging difficulty.</p>
    <p><strong>Кеширующие слои в современных стеках.</strong> Помимо browser cache и CDN edge, современные приложения кешируют во множестве мест: в-памяти (LRU cache в application процессе), Redis или Memcached (shared per-region cache для app-server pool), database query plan cache, CDN регионарный shield, browser disk cache, browser memory cache. Каждый слой имеет свои invalidation rules; дизайны охватывающие все слои должны propagation invalidation events явно.</p>
    <p><strong>Путь интерактивного API-вызова.</strong> Пользователь кликает кнопку. Браузер делает fetch() — уже-открытое HTTP/2 или /3 соединение избегает handshake. Запрос едет к CDN edge (нет cache, mutating endpoint). Edge форвардит к origin региона. Origin auth-проверяет, запрашивает DB, вычисляет ответ, возвращает. Edge не кеширует (Cache-Control: no-store). Браузер получает ответ. JS-handler обновляет state, триггерит re-render. Total time: типично 100-200 мс на хороший день.</p>
    <p><strong>Network waterfall — что показывает Chrome DevTools.</strong> Network panel показывает каждый запрос как horizontal bar. Цвета: queueing, blocking (browser ждёт), DNS, connect, SSL, waiting (TTFB), content download. Длина — duration. Высоко-вертикальные waterfalls (много запросов параллельно) — хорошо для HTTP/2. Длинные waiting-bars — server-side проблема. Stairsteps вертикальные — request dependencies (один запрос блокирует следующий). Идеальный waterfall: всё параллельно, короткие bars, raning из левого верхнего угла.</p>
    <p><strong>Browser preload scanner — глубже.</strong> Когда HTML парсится, preload scanner смотрит ahead находя &lt;link&gt;, &lt;script&gt;, &lt;img&gt;, &lt;video&gt; теги и стартует параллельные fetches. Работает на raw HTML bytes до полного парсинга. Защищён от document.write который теперь требует blocking атрибут. Видит modern ES-модули через script type=module и их dependencies через modulepreload. Это причина почему правильно структурированный HTML загружается так быстро: вся последовательность fetches происходит до того как parser окончит main document.</p>
    <p><strong>Когнитивный фреймворк: что искать в первую очередь.</strong> При оптимизации страницы спросите: 1) Где LCP — какой ресурс, какой layer? 2) Сколько round-trips до первого визуального контента? 3) Какие ресурсы render-blocking? 4) Какие ресурсы можно preload или defer? 5) Что в critical render path что не должно быть там? Ответы дают concrete fix-list. Без этого framework — guess-work.</p>
    <p><strong>Связь со следующей главой.</strong> Глава 02 — Browser & Frontend Runtime — углубится в как браузер фактически парсит HTML, executes JavaScript, делает layout. Та страница которая «грузится за 200 мс» в этом разделе — какие 200 мс? Разделить на JS-parsing, layout, paint — отдельная глубокая тема. Видите как networking прокладывает дорогу но другие слои (rendering, application logic) делают остальную работу. Следующие пять глав строят на этой networking-основе: каждый раз когда мы говорим «backend сервис» подразумевается полный stack от Антон-laptop до сервера и обратно с цепочкой DNS, TCP, TLS, HTTP, CDN.</p>
    <p><strong>HTTP/3 миграция соединений на практике.</strong> Пользователь идёт по улице с телефоном. Wi-Fi падает. Связь переключается на cellular. IP-адрес меняется. На TCP — соединения умирают, app must reconnect (новый TLS, новый stream restart). На HTTP/3 — connection ID сохраняется, packet flow продолжается из нового IP. Streaming-видео не прерывается. Real-time game не teleport-ит. Это самая user-visible win HTTP/3 после loss isolation.</p>
    <p><strong>Что делает приложение «быстрым».</strong> Не одна вещь. Combination: быстрый origin (хорошая БД, scaled compute), aggressive caching (CDN + browser), small bundle sizes (tree-shaking, code-splitting), Critical CSS inlined, JS deferred, preload hints для критических ресурсов, content-hash для bust-proof caching, image optimization (WebP/AVIF, responsive sizes, lazy loading), font optimization (preload, font-display: swap), HTTP/3 + 0-RTT, edge compute для dynamic personalization. Все эти оптимизации работают cumulatively.</p>
    <p><strong>Common антипаттерны.</strong> 1) Render-blocking JS в head без async/defer. 2) Большие unoptimized изображения без lazy-loading. 3) Третьеparty-скрипты (analytics, ads) синхронно в head. 4) Web fonts без preload или с FOIT instead of FOUT. 5) Heavy client-side rendering без SSR — пустая страница пока JS не загрузится. 6) Cookies без SameSite или Secure. 7) Кеширование без Vary заголовка для language/encoding-aware ответов. 8) Missing Cache-Control — CDN guess-ит TTL что обычно неправильно.</p>
    <p><strong>Production debugging checklist.</strong> При user-report «сайт медленный»: 1) Воспроизвести с разных географий через RUM или synthetic tests. 2) Посмотреть на trace conкретного медленного запроса. 3) Проверить cache-hit-rate на CDN. 4) Проверить ALPN distribution — есть ли fallback на h2 откуда-то? 5) Проверить TLS resumption rate. 6) Проверить origin metrics (CPU, DB connections, response time). 7) Сравнить с baseline доhandshake/deploy метриками. 8) Если найдена регрессия — bisect commits до сломавшего изменения. 9) Документировать findings как post-mortem чтобы learning сохранилось команде.</p>
    <p><strong>Что измерять в production.</strong> Browser-side: LCP, INP, CLS, TTFB (через Web Vitals). Network: ALPN distribution, h3-fallback rate, TLS resumption rate, retransmission rate, p95/p99 latency per region. Server-side: requests/sec, error rate per endpoint, p95/p99 response time, CPU/memory/IO. Database: query rate, slow query log, connection pool saturation, lock contention. Каждая метрика — ранний сигнал чего-то одного. Set alerting thresholds — например p99 latency &gt; 500мс для 10 мин triggers PagerDuty.</p>
    <p><strong>Cost vs performance.</strong> Каждая performance-оптимизация имеет cost. CDN — дополнительный bandwidth-bill. Edge compute — usage fees. Multi-region — multiplied infrastructure. Aggressive caching — потенциальная stale data. Bigger origin — higher operational expense. Поиск sweet spot — задача architecting: pay for performance которая reflects business value (homepage заслуживает aggressive optimization; obscure admin page — нет).</p>
    <p><strong>HTTP-specific gotchas в production.</strong> Browser caching сильно зависит от точных заголовков — даже маленькие изменения дают разное поведение. Service Worker может interfere с native browser caching. Cookies, особенно с partitioned-state, теперь обрабатываются по-разному в Chrome/Firefox/Safari. Cross-origin requests требуют точной CORS-конфигурации. ETag-based revalidation иногда disabled by proxies в средине. Знать эти границы — половина борьбы за консистентное поведение across browsers. Корректировать всегда замеряя реальное поведение через RUM.</p>
    <p><strong>End-of-life и migration patterns.</strong> Старые browsers, старые TLS-версии, старые HTTP-протоколы постепенно уходят. Поддержка: SHA-1 certs — мертвы. TLS 1.0/1.1 — disabled в Chrome 84+, Firefox 78+. HTTP/0.9 — практически невидим. Регулярно audit usage логов чтобы планировать deprecations. Сообщать пользователям заранее. Postpone deprecation если значимая популяция legacy-клиентов всё ещё активна — но не вечно.</p>

    <p><strong>Cross-layer state и оптимизации.</strong> Сеть не просто последовательность фаз; это state machine. После TLS handshake ядро Димы держит state соединения (established, closing, closed). Ядро Антона держит per-stream state на HTTP/3. Обе стороны держат congestion windows. Антон держит DNS-кеш с TTL. Patty (CDN) держит per-URL cache entries с Vary и expiration. TLS session tickets — state. Этот state — причина оптимизаций: TLS resumption, DNS caching, HTTP/3 0-RTT, connection pooling.</p>
    <p><strong>Latency optimizations и их trade-offs.</strong> Каждая фаза оптимизируема, но оптимизации trade-ят consistency, complexity, security на скорость. DNS: anycast или GeoDNS приближают, но риск misrouting. TCP: BBR избегает timeouts но требует kernel patches. TLS: session tickets для 0-RTT, но replay-риск. HTTP: server push для preload, но wasted bandwidth. CDN: stale-while-revalidate подаёт expired cache, но stale данные. Pattern: профилируйте, идентифицируйте slowest, оптимизируйте, принимайте trade-off.</p>
    <p><strong>Cascading retries и их стоимость.</strong> Когда сеть медленная, клиенты повторяют. TCP timeout → клиент открывает новое соединение (TCP, TLS, HTTP × 3). TLS handshake долго → браузер retry. HTTP request timeout → client library retry (exponential backoff, 100мс, 200мс, 400мс). Когда много клиентов retry, нагрузка на origin amplify-ет. 99.9% origin сервер вдруг обрабатывает 10× нормального трафика. Cascade: 1 error → много retries → много errors. Защита: exponential backoff с jitter на каждом retry-уровне.</p>
    <p><strong>Encrypted Client Hello и приватность.</strong> Традиционный TLS exposes SNI в открытом виде, позволяя on-path observer fingerprint запрос: «Этот клиент идёт на google.com» без расшифровки. Encrypted Client Hello (ECH, RFC 9849) шифрует SNI, защищая от category-level fingerprinting. Но ECH требует DNS-lookup для server's ECH config — добавляет latency. Adoption медленный.</p>
    <p><strong>Connection migration и mobile networks.</strong> HTTP/3 (QUIC) поддерживает миграцию соединений: если IP клиента меняется (Wi-Fi → LTE), соединение persist через stateless reset token. TCP не имеет миграции. На mobile IP-changes частые. HTTP/3 снижает handshake-стоимость на миграцию (просто QUIC-кадр). Но statefulness сама по себе — burden: Дима должен трекать client state.</p>
    <p><strong>Почему вы заботитесь о слоях.</strong> Вся семи-фазная dance — sub-100 мс на хороший день. Payoff — clarity: в следующий раз когда страница медленная, можете профилировать и назвать suspect — DNS (медленный резолвер), TCP (далёкая география), TLS (тяжёлый handshake), HTTP (медленный app-сервер), cache (miss rate высокий), rendering (JS блокирует), потеря (retransmits тормозят). Без понимания «сеть медленная» — всё что у вас есть. С пониманием: «DNS + CDN edge miss стоят 50 мс, TLS resumption сэкономит 25, server-side кеширование уберёт origin round-trip».</p>
    <p><strong>OpenTelemetry trace propagation.</strong> Современная observability инструментирует каждый слой с W3C Trace Context: 16-байтный trace ID и 8-байтный span ID распространяются через `traceparent` HTTP-header. Каждый компонент в пути запроса (browser → CDN edge → load balancer → application → database) сообщает spans которые агрегируются в распределённый trace. Можете видеть exact path запроса, время на хоп, какая зависимость вызвала длинный tail.</p>
    <p><strong>USE method, RED method, error budget calculus.</strong> Три операционных framework. USE (Brendan Gregg) для ресурсов: Utilization, Saturation, Errors — на CPU, память, диск, сетевые интерфейсы. RED (Tom Wilkie) для сервисов: Rate (requests/s), Errors (error rate), Duration (latency distribution). Error budgets: SLO 99.9% разрешает 0.1% errors за 30-day window — ~43 минуты downtime. Когда сожгли половину budget — замедляете risky changes; всё — release freeze.</p>
    <p><strong>Distributed tracing sampling strategies.</strong> Трассировать каждый запрос дорого на масштабе (1М req/s даст терабайты trace data в день). Strategies: head-based (решение на entry, fixed 1%), tail-based (буферизация spans, решение после исхода — sample 100% errors, 0.1% successes), adaptive (sample больше с high-cardinality endpoints). OTel Collector реализует tail sampling. Правильная стратегия: 100% sampling для errors и slow, low rate для fast successes.</p>
    <p><strong>Retry policies и circuit breakers.</strong> Наивный retry: клиент видит error, retry немедленно, сервер всё ещё сломан, тот же error, retry — death spiral. Exponential backoff с jitter (initial 100 мс, удваивается, random ±25% jitter чтобы избежать синхронизации) даёт серверу восстановиться. Circuit breakers (Netflix Hystrix, Spring Cloud Resilience4j) closure circuit когда failures превышают threshold — прекращают вызывать failing dependency, возвращают fast errors caller-ам, периодически проверяют recovery.</p>
    <p><strong>Production observability stack.</strong> Metrics: Prometheus или VictoriaMetrics, scrape от каждого сервиса через /metrics. Logs: Loki или Elasticsearch, structured (JSON). Traces: Tempo, Jaeger, или commercial (Datadog, New Relic). Dashboards: Grafana. Alerting: PagerDuty + Alertmanager. RUM: in-house beacons или Sentry/LogRocket. Все пять слоёв коррелируют через trace IDs и timestamps.</p>
    <p><strong>Edge compute composition patterns.</strong> Cloudflare Workers + KV + R2 + Durable Objects позволяют строить full applications без origin сервера. Patterns: API gateway на edge (auth, rate limit, routing к нескольким backends), static site с personalization (edge worker инжектирует user-specific фрагменты), event broker (Durable Objects координируют state). Trade-off: lock-in plus per-CDN compute idioms. Польза: latency под 50 мс глобально без management серверов.</p>
    <p><strong>Failure isolation через регионы.</strong> Один US-East-1 outage не должен убивать ваших European пользователей. Patterns: regional deployments с независимыми failure domains, traffic routing через Route 53 / Cloudflare Load Balancing health checks, cross-region replication для stateful сервисов, blast-radius scoping. Cell-based architecture (AWS internal pattern) делит пользователей на «cells» каждая обслуживается dedicated infrastructure slice.</p>
    <p><strong>Performance budgets.</strong> Установите явные бюджеты: total bytes (200 KB compressed HTML), JS execution time (100 мс), LCP (под 2.5 с), CLS (под 0.1). Enforce в CI: build превышающий budget fail check. Tools: bundlewatch, size-limit, Lighthouse CI интегрируются с GitHub Actions. Budget заставляет сознательные trade-offs на PR-time вместо обнаружения bloat в продакшене.</p>
    <p><strong>Полная mental model для синтеза.</strong> Каждый слой в этой главе — одна box в request lifecycle. Browser orchestrate-ит. DNS — одна network operation. TCP — другая. TLS — encryption + handshake. HTTP — app-level разговор. CDN edges — сокращение географии. Routers — носят биты. CSS+JS+HTML mix решает что красится когда. Observability даёт видеть всё это. Оптимизация = профилировать slowest box и сократить; round-trip elimination бьёт round-trip shortening; cache hits бьют cache misses; правильная метрика бьёт precise метрику.</p>
    <p><strong>Capacity planning на масштабе.</strong> Когда система обрабатывает значимый трафик, capacity-числа начинают значить: requests per second per worker, p99 latency под нагрузкой, memory per concurrent connection, CPU per request. Load tests (k6, Locust, vegeta) измеряют. Stress tests пушат за cliff чтобы найти breaking point. Chaos engineering (Gremlin, Litmus) инжектирует failures чтобы проверить graceful degradation. Дисциплина: никогда не деплоить новый high-traffic сервис без знания его capacity envelope. Run-books документируют failover, recovery, rollback.</p>
    <p><strong>Распределённые системы и сетевые проблемы.</strong> В микросервис-архитектуре каждый запрос пользователя может разлететься на 10-100 внутренних сервисных вызовов. Каждый внутренний вызов — миниатюрный HTTP-запрос со своей latency, error rate, retry-policy. Cascading failures, partial outages, byzantine state — каждый узел сети должен обрабатывать корректно. Mature production stack включает: service mesh для observability, circuit breakers, bulkheads, timeout пирамиды от backend к frontend, graceful degradation.</p>
    <p><strong>Production-grade incident response.</strong> Реальные инциденты на масштабе: первые 5 минут — assess scope (один регион, all regions, отдельный сервис, ALL сервисы). Следующие 15 — identify root cause (метрики, traces, recent deploys, recent infrastructure changes). Затем — mitigate (rollback, kill-switch, traffic shift). После — post-mortem (timeline, contributing factors, action items). Хорошо tracked инциденты дают institutional knowledge — следующий похожий инцидент решается за минуты не часы.</p>
    <p><strong>SRE-практики для веба.</strong> SLI (Service Level Indicator): метрика — например p99 latency. SLO (Service Level Objective): цель — например p99 &lt; 500 мс. SLA (Service Level Agreement): контракт с пользователем — например 99.9% uptime. Error budget: разница между current и SLO. Когда burning error budget слишком быстро — фокус на reliability. Когда medvedя — фокус на features. Этот фреймворк (Google SRE book) — стандарт для serious production систем.</p>
    <p><strong>Microservices и transactional integrity.</strong> Распределение бизнес-операций через несколько микросервисов создаёт трудность: одна логическая операция (например «оформить заказ») может включать вызовы к product-сервису, inventory, payments, notifications. Если payment проходит а inventory падает — система в inconsistent state. Решения: distributed transactions (2PC, медленно), saga pattern (compensating transactions), outbox pattern + event sourcing, idempotent operations + retry. Каждое имеет trade-offs между consistency, availability, complexity. Архитектурный выбор зависит от business requirements — финансовые операции требуют strong consistency, social-feed updates терпят eventual.</p>
    <p><strong>Caching через все слои — стратегия.</strong> Multi-tier кеш требует careful invalidation. Когда product price меняется: invalidate database cache, redis cache, CDN cache, browser cache. Каждый слой имеет свой TTL и invalidation mechanism. Если один пропустить — stale data висит часами. Подходы: cache-tagging (один tag-purge invalidate-ит везде), event-driven invalidation (Kafka topic для cache events), short TTL on lower tiers (CDN 60с, browser 5min) + content-hash на статике.</p>
    <p><strong>Реальные размеры — что мы строим.</strong> Современное среднее веб-приложение: 50-200 endpoints API, 10-50 микросервисов, 1-5 PostgreSQL баз данных, 1-3 Redis-кластера, 50-200 разных pages во фронтенде, 1-3 терабайта статики на CDN, 1-10 млн запросов в сутки на старте, 100М-1Б на масштабе. Все слои о которых мы говорили — DNS, TCP, TLS, HTTP, CDN — масштабируются и работают согласованно во всём этом ландшафте.</p>
    <p><strong>Сетевая безопасность через слои.</strong> Каждый слой имеет свои security concerns. Physical: cable tap, RF eavesdropping. Link: ARP spoofing, MAC flooding. Network: IP spoofing, BGP hijack. Transport: SYN flood, RST injection. TLS: cipher downgrade, certificate fraud. HTTP: SQLi, XSS, CSRF, replay attacks. Application: business logic flaws. Defence in depth — каждый слой добавляет защиту: encryption на TLS не убирает нужду в auth на app-уровне. Каждый production система должна иметь threat model для своего стека.</p>
    <p><strong>Continuous improvement цикл.</strong> Production performance не статичен. Мониторинг → identify worst metric → hypothesise improvement → measure baseline → deploy fix → measure delta → repeat. Tools: A/B testing для customer-facing изменений, canary deploys, feature flags. Документировать каждый improvement и его measured impact — builds organizational performance knowledge. Регулярные performance reviews — раз в квартал команда смотрит trend-данные и приоритизирует.</p>
    <p><strong>Запоминающиеся числа из главы.</strong> Light в glass ~200000 км/с. Transatlantic London-NY ~56 мс one-way. Transcontinental ~70-150 мс RTT. TCP handshake 1 RTT. TLS 1.3 cold 1 RTT, warm 0-1 RTT. CDN edge cache hit 10-30 мс. Origin RTT 100-300 мс. LCP good &lt; 2.5 с. INP good &lt; 200 мс. Эти числа — рамки внутри которых мы строим современный веб.</p>
    <p><strong>На этом этап Networking закончен.</strong> Вы понимаете как байты идут от вашего ноутбука до сервера и обратно через все слои. Знаете где платится цена за каждый RTT и каждый failed handshake. Можете диагностировать прод-инциденты на каждом уровне. Это foundation на котором стоит весь остальной веб-стек. Следующие главы (browser runtime, APIs, databases) добавляют на эту base, но networking понимание остаётся фундаментальным. <Misconception
  id="r-cascade"
  title="Внимание: каскадные retries усиливают сбои"
>
Когда клиенты массово retry, нагрузка amplify. 99.9% сервер видит 10× трафик от retries и тормозит. Все слои (DNS, TCP, TLS, HTTP, app) retry независимо. Защита: exponential backoff с jitter на каждом слое.
</Misconception>

<KeyTakeaway title="Главное">
Каждый HTTPS-запрос — координированная последовательность семи слоёв: DNS чтобы найти IP, TCP для надёжного byte-транспорта, TLS для конфиденциальности и целостности, HTTP для application-level разговора, CDN edges для geographic proximity, routers для packet forwarding, и browser render pipeline. Optimization работа означает знать какой слой доминирует каждый конкретный медленный запрос — round-trip elimination (cache hits, 0-RTT, edge compute) — highest-leverage move; round-trip shortening (CDN, multi-region) — следующее; всё внутри round-trip (compression, parsing speed, smaller bundles) — третье. Operational frontier — distributed tracing с W3C Trace Context, USE/RED method-based instrumentation, error-budget-driven release cadence.
</KeyTakeaway>

## Главные выводы: что повторяется дальше

Глава 01 закрыта. Вы прошли всю сеть от keystroke Антона до пикселей. Четыре нити проходят через каждый слой:

- **Encapsulation.** Каждый слой оборачивает предыдущий.
- **Multiplexing.** TCP/IP мультиплексируют много streams на одну трубу. HTTP/2 и /3 — много запросов на одно соединение.
- **Statefulness.** Соединения stateful — помнят sequence numbers, congestion windows, TLS keys, HTTP cookies. Это позволяет оптимизации вроде resumption и 0-RTT.
- **Latency.** Каждый round-trip, каждый handshake, каждый cache miss — стоимость. Архитектура — оптимизация против round-trip latency.

Вы увидите эти нити в **Главе 02: Browser & Frontend Runtime**, **Главе 03: APIs & Services**, **Главе 04: Databases**, **Главе 05: Deployment & Observability**.
