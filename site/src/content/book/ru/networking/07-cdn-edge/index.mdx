Когда <PersonaTag id="bea" lang="ru" /> в Лондоне загружает страницу с сервера в Калифорнии, каждый запрос идёт 200 мс туда-обратно. Страница тормозит. А что если её запрос никогда не покидал Лондон? Что если копия данных сервера жила в датацентре по соседству, отвечала за 20 мс и оставалась синхронизированной? Это CDN — Content Delivery Network. Самый прямой способ победить latency: положить контент близко к пользователю. Три механизма работают вместе: <SpiralCue thread="latency" lang="ru" /> Anycast IP-маршрутизация (один адрес из многих городов), edge DNS (разные адреса по географии), и многоуровневое кеширование.

<Crux>Как CDN-кеширование побеждает задержку: edge-location, ключи кеша, и почему забыть Vary всё ломает.</Crux>

Если edge закешировал — быстрый ответ; иначе edge форвардит к origin (или shield).</p>

    <p><strong>Три механизма работают вместе: Anycast IP, GeoDNS, многоуровневый кеш.</strong></p>
    <p><strong>Anycast IP:</strong> CDN рекламирует один и тот же IP-адрес (например `93.184.216.1`) из нескольких географических локаций. BGP-маршрутизация выбирает «ближайший» edge (по количеству хопов или длине AS-пути). Когда Bea делает запрос, её локальный роутер отправляет его в ближайший edge POP рекламирующий этот IP. Никакого специального DNS — просто маршрутизация.</p>
    <p><strong>GeoDNS:</strong> Большинство CDN предпочитают явный контроль через DNS. CDN-оператор конфигурирует DNS возвращать разные A-записи в зависимости от географии резолвера (по IP). Запрос от Лондонского резолвера возвращает Лондонский edge IP; Токийский — Токио. Резолвер — клиент запрашивающий DNS, не конечный браузер. Глобальный резолвер вроде 8.8.8.8 кажется приходящим из дата-центра Google, поэтому GeoDNS возвращает региональный IP на основе той локации, не браузера.</p>
    <p><strong>Многоуровневое кеширование:</strong> Edge имеет ограниченное хранилище. Частые запросы (топ 20% ассетов) живут на edge. Редкие запросы промахиваются мимо edge и идут на origin shield — промежуточный уровень кеша между edge и origin. Shield поглощает ~99% промахов, защищая origin от request-штормов. Ключ кеша — URL + variant headers (Accept-Encoding, Accept-Language). Заголовок ответа `Vary: Accept-Language` говорит кешу: «Держи отдельные записи для каждого языка». Cache-Control: `max-age=3600` (1 час, browser и CDN), `s-maxage=86400` (1 день, только CDN), `private` (только browser, skip CDN), `no-store` (никогда не кешировать), `stale-while-revalidate=604800` (отдавай stale, обновляй в фоне 7 дней после истечения).</p>
    <p><strong>Что edges типично кешируют.</strong> Статические ассеты (JS, CSS, изображения, шрифты, видео-сегменты) — хлеб с маслом, редко меняются и большие. HTML страницы могут быть закешированы если не содержат user-specific контент. JSON API-ответы могут быть закешированы для read-only идемпотентных запросов. Динамические персонализированные — обычно помечены `private` или `no-store`. Правило: всё с длинным max-age — на edge; всё персонализированное — на origin.</p>
    <p><strong>Origin shield архитектура.</strong> Edges в одном регионе пропускают свои misses через один регионарный shield вместо прямого обращения к origin. Почему: 200 edges все промахивающиеся одновременно одним и тем же uncached URL создадут 200 origin-запросов; shield коллапсирует это в один. Cloudflare называет это «Tiered Cache», Fastly — «Origin Shield», AWS CloudFront — то же.</p>
    <p><strong>Паттерны invalidation кеша.</strong> Три способа выкинуть устаревший контент. (1) TTL expiry — ждать пока max-age истечёт (дёшево, медленно). (2) Явный purge — API-вызов CDN убрать конкретный URL или паттерн. (3) Cache tags — тегировать ответы на origin, purge по тегу на CDN.</p>
    <p><strong>Vary footgun.</strong> Кеши ключуют ответы по URL плюс заголовкам перечисленным в `Vary`. Отсутствие Vary на ответе который реально варьируется (например language-aware страница) означает что первый ответ кеша подаётся всем последующим. `Vary: Accept-Encoding` обязателен если подаёте gzipped или brotli-варианты. `Vary: Authorization` обязателен если logged-in vs anonymous видят разный контент. `Vary: Cookie` опасен — wildly фрагментирует кеш потому что каждое значение cookie новый variant — лучше `Cache-Control: private`.</p>
    <p><strong>Conditional requests и 304 Not Modified.</strong> Даже cache hits можно оптимизировать. Браузер кеширует ответ локально; когда TTL истекает, отправляет `If-None-Match` с закешированным ETag. Если ответ не изменился, CDN (или origin) возвращает `304 Not Modified` с пустым телом — экономит bandwidth даже на revalidation. CDN обрабатывают это прозрачно.</p>
    <p><strong>Versioning статических ассетов.</strong> Умный трюк: называйте CSS/JS/image файлы с content hash (например `app.f3a2b8c.js`). Ставьте очень long max-age (`max-age=31536000` = 1 год). Когда обновляете файл, URL меняется — кеш никогда не отдаёт устаревший контент. Webpack, Vite, esbuild, Astro делают это автоматически.</p>
    <p><strong>SLA basics.</strong> CDN публикуют SLA типично ~100% uptime с кредитами на breaches. Интересное число — p95/p99 latency на edge: Cloudflare и Fastly целятся в sub-50ms p95 по миру; Akamai конкурентен на infrastructure-heavy traffic. Цены на bandwidth сильно варьируются: Cloudflare flat rate, AWS CloudFront tiered, Fastly per-GB.</p>
    <p><strong>Блок ошибочных представлений.</strong> Один: «CDN автоматически кеширует всё». Ложь — заголовки ответа origin управляют cacheability. Два: «Purge по URL чистит и browser-кеш». Ложь — purge затрагивает только CDN; браузеры используют свой кеш. Три: «Больше PoPs всегда значит лучше». Ложь — PoP с которым ваш ISP не пиритится локально добавляет задержку, не убирает.</p>
    <p><strong>Иерархия кеша при browser-to-edge запросе.</strong> Когда браузер делает запрос, четыре кеша могут ответить: (1) Browser memory cache (sub-ms hits, длится сессию tab). (2) Browser disk cache (~10 мс, persist между tabs). (3) CDN edge POP cache (~20-50 мс по сети). (4) CDN shield (~50-100 мс). Только если все четыре miss — origin server отвечает (~100-300 мс).</p>
    <p><strong>HTTP/2 push, 103 Early Hints, preconnect.</strong> Edge без awareness origin response не может отгрузить ресурсы рано. Tooling: `103 Early Hints` (informational status, RFC 8297) посылается до final response с `Link: </style.css>; rel=preload` чтобы браузер начал fetch критических ассетов параллельно с генерацией HTML на origin. По состоянию на 2026, 103 Early Hints имеет поддержку 93% браузеров но только ~5% adoption на реальных сайтах; Vercel лидирует с ~2.8% adoption пока Cloudflare и Fastly остаются ниже 1%. Трение оперативное: ты должен знать какие ресурсы хинтировать на каждой странице, что большинство CMS не автоматизируют. `<link rel="preconnect">` в HTML говорит браузеру открыть TCP+TLS к другим origin-ам заранее, сохраняя handshake с critical path. Оба подхода работают даже когда CDN в middle, потому что edges форвардят хинты intact. Современная best practice: используй 103 + preconnect для critical render path, skipping Server Push полностью.</p>
    <p><strong>Доставка изображений и видео.</strong> Изображения — типично 50-80% общих байтов страницы; CDN сильно оптимизируют. Format negotiation: WebP/AVIF для способных браузеров (Accept: image/avif), fallback JPEG; CDN image-optimization транспилирует на лету. Responsive images: `srcset` даёт браузеру выбрать правильное разрешение. Видео: HLS и DASH режут видео на маленькие сегменты доставляемые через HTTP — CDN кеширует сегменты агрессивно.</p>
    <p><strong>Geo-routing тонкости.</strong> Anycast выбирает BGP-кратчайший POP, не всегда latency-кратчайший. GeoDNS выбирает по IP резолвера, не пользователя. EDNS Client Subnet (covered in 04-dns) заостряет когда резолвер opts in. Apple и Cloudflare «1.1.1.1 for Families» отключают ECS ради приватности, принимая suboptimal routing.</p>
    <p><strong>Origin selection и failover.</strong> Современные CDN позволяют сконфигурировать несколько origin-серверов с health checks и failover policies. Active-passive: edge отправляет трафик primary, переключается на standby при health-check failure. Active-active: edge round-robin или geo-routing между live origins.</p>
    <p><strong>Cache poisoning attacks.</strong> Атакующий отправляет запрос специально подделанный так чтобы origin вернул вредоносный ответ, который CDN затем кеширует и подаёт другим пользователям. Векторы: HTTP request smuggling, header injection через unkeyed inputs, parameter cloaking. Защита: align CDN и origin на парсинг запросов, нормализация cache key, отключение варьирования ответа на user-controlled заголовки.</p>
    <p><strong>Cost models.</strong> CDN-ценообразование сильно варьируется. Cloudflare: flat rate per plan, unlimited bandwidth (fair-use). Fastly: per-GB egress + per-request. AWS CloudFront: tiered per-GB egress + per-request, regionally priced. Akamai: enterprise контракт. Для маленького сайта (10 ТБ/мес) Cloudflare free или Pro plan подходит.</p>
    <p><strong>CDN-native compute.</strong> Помимо static-asset delivery, каждый современный CDN предлагает code-at-edge. Cloudflare Workers (V8 isolate, KV/D1/R2 storage), Fastly Compute@Edge (WASM), AWS Lambda@Edge (Node/Python), Vercel Edge/Fluid Compute. 2026 performance: Cloudflare Workers p99 cold-start 2–5ms (V8 isolate, no initialization overhead). Lambda@Edge 400–600ms at некоторых PoPs (нужна инстанция setup). Vercel Fluid Compute 99.37% zero-cold-start ratio с 1.2x–5x улучшением на SSR vs Workers. Компромисс: Workers быстрые но ограничены (50ms CPU wall-time, 128 MiB). Lambda@Edge медленнее но полнопривилегированный Node.js. Vercel Fluid занимает middle ground — мощнее Workers но с нулевой инициализацией. Правило thumb: edge для быстрой логики (auth, A/B, transforms), region-specific Functions или Lambda для heavy compute (database, ML).</p>
    <p><strong>Покрытие и стратегии edge-placement.</strong> Cloudflare имеет ~330 PoP в 120+ странах. Akamai - крупнейшая инфраструктура с ~365k серверов в 4000+ сетях. Fastly меньше но более сфокусирован (~80 высокопроизводительных PoP). AWS CloudFront ~600+ edge-локаций. У каждой стратегии trade-off: больше PoP даёт меньшую latency но усложняет cache fragmentation; меньше PoP с более мощными узлами выигрывает на throughput. Для производственного выбора смотрите на peering с вашим целевым ISP списком — это часто важнее общего числа PoPs.</p>
    <p><strong>Безопасность edge.</strong> Современный edge — не просто кеш, а часть defense-in-depth. WAF фильтрует SQL injection, XSS, командные injection patterns. Bot management отличает людей от автоматики через JA3/JA4 TLS fingerprinting, поведенческий анализ, IP-репутацию. Rate limiting per-route, per-IP, per-token. DDoS scrubbing на уровне L3/L4 (volumetric) и L7 (application). Геоблокировка (страны, ASNs). Все эти политики применяются на edge до того как трафик достигает origin — снижает нагрузку и attack surface.</p>
    <p><strong>Bandwidth и cost.</strong> Главная статья затрат CDN — egress bandwidth (исходящий трафик к пользователям). Тарификация: per GB (CloudFront $0.085/GB первые 10TB), либо flat-rate (Cloudflare unlimited на платных планах в рамках fair-use). Для high-volume video streaming bandwidth-bill может быть значительной частью операционных costs. Multi-CDN strategies включают commercial leverage — переговоры с двумя провайдерами дают лучшие цены чем привязка к одному.</p>
    <p><strong>Cache hierarchy реальные числа.</strong> На крупном веб-сайте типичные значения: cache hit ratio на edge — 85-95% для static assets, 60-80% для HTML, 30-50% для API responses. p50 latency edge → user — 10-30 мс, p95 — 50-100 мс, p99 — 200-400 мс. Origin RTT (edge → origin) — 20-100 мс в зависимости от geography. Bandwidth saving от кеша часто 80-95% — origin видит лишь малую долю трафика что критично для cost и reliability.</p>
    <p><strong>Operational tactics CDN.</strong> Production CDN-ops включает: мониторинг hit ratio per route и alerting при падении; periodic purge при major content updates; warming cache после deploy через crawl-script; A/B testing routing changes на small fraction трафика; chaos testing — намеренно отключать одну CDN из multi-CDN setup чтобы убедиться что fallback работает. Документировать SOP для каждого failure mode (origin down, edge degraded, certificate expiry, BGP issue).</p>
    <p><strong>CDN-провайдеры сегодня.</strong> Cloudflare — крупнейший по PoP-count, известный за бесплатный tier и Workers. Akamai — старейший, доминирует на enterprise. Fastly — фокус на developer experience и edge compute. AWS CloudFront — интеграция с AWS-стеком. Google Cloud CDN — интеграция с Cloud Run и BigQuery. Microsoft Azure Front Door. Каждый имеет сильные и слабые стороны; выбор часто диктуется существующим стеком cloud-провайдера.</p>
    <p><strong>CDN как часть веб-стандарта.</strong> Современные веб-стандарты (HTTPS-only, HTTP/3, ECH, Resource Hints) часто проще развёртывать через CDN чем через origin-сервер. Cloudflare auto-включает HTTP/3, TLS 1.3, post-quantum hybrid keys для всех клиентов. Это превращает CDN не просто в кеш а в первый слой реализации новых стандартов до того как они достигают origin-серверов.</p>
    <p><strong>API-кеширование на CDN.</strong> Не только статика; современные API часто кешируются на CDN. Read-only GET-запросы с правильными Cache-Control могут хитить cache 90%+ времени. Cache key включает full path + query + auth-headers (если нужно). Invalidation через cache-tags при mutations. Это сильно снижает нагрузку на API-сервера и улучшает latency для пользователей.</p>
    <p><strong>Push vs pull invalidation.</strong> Pull: CDN не знает о изменении пока TTL не истечёт. Push: origin активно сигнализирует CDN invalidate-ить (через purge API или webhooks). Modern CDN поддерживают push purge с propagation в секунды по всем PoPs. Это позволяет deploy → automatic purge → пользователи видят свежий контент почти мгновенно.</p>
    <p><strong>Static-site generation и CDN.</strong> Jamstack-архитектура (Next.js static export, Gatsby, Astro static, Hugo, Jekyll) генерирует весь сайт как набор статических файлов при deploy. Эти файлы заливаются на CDN (Vercel, Netlify, Cloudflare Pages) и обслуживаются прямо с edge — никакого backend-сервера на критическом пути. Latency минимальна, scaling automatic. Подходит для контент-сайтов, документации, маркетинговых страниц. Не подходит для high-frequency dynamic content без edge compute.</p>
    <p><strong>Migration на CDN: типичный процесс.</strong> 1) DNS прокси через CDN (Cloudflare proxied DNS, AWS Route 53 + CloudFront). 2) Cache rules для статических путей. 3) WAF в monitor-mode для базовой защиты. 4) Health checks на origin. 5) Постепенное перенаправление трафика. 6) Мониторинг hit-rate, error-rate, latency. 7) Полный cutover. Большинство компаний делают это за неделю-месяц без downtime благодаря CDN-proxy между origin и пользователями.</p>
    <p><strong>Cost optimization CDN.</strong> Bandwidth dominates billing. Strategies: aggressive Brotli compression на статике (Brotli даёт 20% лучше gzip); content-hashed versioning для долгого TTL; image optimization (WebP/AVIF vs JPEG); video adaptive bitrate; lazy-loading offscreen images; HTTP/3 connection reuse. Регулярный audit cache hit ratio выявляет misconfigured Vary, неоптимальные TTL, и другие footguns. Каждые 10% улучшения hit ratio могут сократить billing на десятки процентов на трафик-heavy сайтах.</p>
    <p><strong>Edge functions vs serverless functions.</strong> Edge functions (Cloudflare Workers, Vercel Edge) бегут на 100+ PoPs близко к пользователю. Serverless functions (AWS Lambda, Google Cloud Functions) бегут в region-specific data centers (10-30 регионов). Edge — быстрее (10-50 мс vs 100-300 мс) но ограничены (no Node APIs, 50ms wall-time, малая память). Serverless — медленнее но мощнее. Современный паттерн: edge для лёгкой логики (auth, A/B, redirects), serverless для тяжёлой (DB queries, ML).</p>
    <p><strong>CDN и SEO.</strong> Поисковые движки (Google, Bing) часто отдают CDN-fronted сайтам преимущество в ранжировании благодаря быстрому LCP и низкому TTFB. Vercel и Cloudflare публикуют case-studies показывающие 10-30% улучшение Core Web Vitals после миграции на edge. Pre-rendering на edge (Vercel ISR — Incremental Static Regeneration) даёт SEO-friendly HTML + dynamic content в одной странице.</p>
    <p><strong>Заключение.</strong> CDN превратился из «просто кеш статики» в полноценный edge compute platform. Современные веб-приложения часто строятся edge-first: static site от build → edge functions для auth и personalization → backend только для transactional logic. Latency сокращается с сотен миллисекунд до десятков. Это самый большой архитектурный сдвиг в web-инфраструктуре за последнее десятилетие.</p>

  <Fragment slot="senior">
    <p><strong>Anycast и умное routing.</strong> Anycast прост но subotimal. BGP выбирает по hop count, не latency. Два города 10 хопов через оптимальный backbone могут measure хуже по BGP-метрикам. Cloudflare Argo и AWS Global Accelerator добавляют умный слой: измеряют реальную задержку через probes, потом используют приватный backbone (не публичный интернет) чтобы маршрутизировать запросы к самому low-latency POP независимо от BGP. Может экономить 50+ мс на межконтинентальных хопах.</p>
    <p><strong>Cache keys и Vary семантика.</strong> Cache key построен из: URL (обязательно), method (GET vs POST), Host header, и заголовки перечисленные в `Vary`. Если ответ несёт `Vary: Accept-Encoding, Accept-Language`, кеш создаёт отдельные записи для [URL + gzip], [URL + brotli], [URL + en], [URL + ru]. Когда запрос приходит, кеш матчит URL + method + Vary-listed headers. Отсутствующий Vary заголовок означает что последующие запросы с разным Accept-Language получают первый ответ независимо. RFC 7234 § 4.1 формализует это.</p>
    <p><strong>Cookies и cache poisoning.</strong> Cookies НЕ включены в cache key по умолчанию. Если endpoint читает session cookie и возвращает персонализированный контент, отсутствие `Vary: Cookie` или `Cache-Control: private` означает что ответ одного пользователя может подаваться другому. Это реальная уязвимость: developer забывает пометить `/account` как private; первый пользователь логинится, попадает в кеш; второй (без cookie) получает страницу аккаунта первого. Решение: либо `private` (нет CDN-кеша), либо `Vary: Set-Cookie` плюс уникальный идентификатор в cookie становящийся частью ключа.</p>
    <p><strong>Stale-while-revalidate (SWR).</strong> После истечения кешированного ответа следующий запрос вызвал бы cache miss (round-trip к origin). SWR переворачивает: отдаёт stale ответ немедленно, потом обновляет в фоне. Пользователи получают быстрые загрузки даже после истечения; staleness window — `max-age + stale-while-revalidate`. Для news feed (max-age=60, SWR=604800) пользователи могут получить 10-дневный кеш мгновенно пока CDN обновляет в фоне.</p>
    <p><strong>Cache tags и surrogate invalidation.</strong> Fastly и Cloudflare Enterprise поддерживают cache tags: origin присваивает теги ответам (например `Cache-Tag: user:42, article:1001`). Позже один API-вызов (`PURGE tag user:42`) invalidate-ит все закешированные ответы тегированные `user:42` не трогая другие. Это побеждает URL purging (требует знания каждого URL) и time-based expiry (форсирует устаревшие данные).</p>
    <p><strong>Edge workers и compute.</strong> Современные CDN (Cloudflare Workers, Fastly Compute, AWS Lambda@Edge) запускают код на edge — V8 isolates с ~5 мс cold start. Трансформируют запросы (добавляют заголовки, мерджат микросервисы, A/B тесты), составляют ответы (ESI — Edge Side Includes, или динамические фрагменты), или решают cache strategy на лету. Worker cold starts незначительны.</p>
    <p><strong>TLS resumption и state на edge.</strong> Новое TLS-соединение стоит 1 RTT. Session resumption (через session tickets или TLS 1.3 pre-shared keys) амортизирует. Современные CDN генерируют tickets на одном edge POP и реплицируют по сети — если соединение Bea прервалось и она переподключилась через другой POP, тот POP уже имеет её ticket, пропуская re-handshake.</p>
    <p><strong>P95/P99 SLO math для edge latency.</strong> Edge latency доминирует user-perceived performance. Cloudflare's published p50 edge response time ~10-30 мс по миру; p95 ~40-60 мс; p99 hits 100-200 мс на long-tail routes. Для SLO «p99 page load &lt; 1с» у вас бюджет который надо разделить через DNS, TCP, TLS, edge, origin, render. Edge обычно потребляет 20-50 мс этого p99 budget.</p>
    <p><strong>Cache stampede / thundering herd.</strong> Закешированный ресурс истекает. Много edges одновременно запрашивают новую версию у origin. Origin видит 100x нормального трафика; некоторые из тех запросов timeout, кеш хранит error-ответы, больше retries попадают на origin. Решения: (1) Origin shield (уже covered) консолидирует stampede в один origin-запрос на регион. (2) `stale-while-revalidate` даёт edges подавать stale пока один edge обновляет в фоне. (3) Probabilistic early expiration. (4) Application-level singleflight pattern на origin.</p>
    <p><strong>Edge worker isolates и cold-start economics.</strong> Cloudflare Workers работают на V8 isolates: cold start ~5 мс; memory ограничена (типично 128 MiB); CPU bounded by 50ms wall-time. По сравнению с Lambda@Edge (200+ мс cold start) isolate-модель Workers позволяет одному процессу хостить код тысяч клиентов. Цена: десятки микросекунд изоляции на запрос. Use cases: A/B test selection, URL rewriting, JWT validation, geo-redirect, custom auth на edge.</p>
    <p><strong>ESI и edge-side composition.</strong> Edge Side Includes (W3C draft 2001, до сих пор используется в Akamai) позволяет HTML-ответам содержать placeholders которые edge заполняет закешированными фрагментами. Каждый фрагмент имеет свой cache key и TTL. Современные реинкарнации: Cloudflare Workers + HTMLRewriter API, Fastly Compute@Edge с ESI tags, Vercel React Server Components на Edge Runtime.</p>
    <p><strong>WAF и bot management на edge.</strong> Помимо кеширования, CDN сидят на пути запросов и могут inspect, block, или mutate. Web Application Firewall (WAF) матчит request-сигнатуры против rule sets (OWASP Top 10, custom). Bot management использует JA3/JA4 TLS-fingerprints, поведенческий анализ и ML чтобы отличать людей от автоматизированного трафика. Rate limiting per IP / per token на edge. DDoS scrubbing на edge останавливает volumetric атаки до достижения origin.</p>
    <p><strong>Multi-CDN strategies.</strong> Крупные операторы (Netflix, Apple, большие новостные сайты) фронтят трафик с двух или более CDN одновременно, steering трафик через DNS или RUM-measurements. Цели: vendor resilience (один CDN-outage не убивает сайт), regional optimization (один CDN быстрее в Asia, другой в EU), commercial leverage.</p>
    <p><strong>BGP-level оптимизации: Argo и Global Accelerator.</strong> Anycast выбирает BGP-closest POP, не latency-closest. Cloudflare Argo Smart Routing и AWS Global Accelerator измеряют actual end-to-end latency от многих POPs к многим origins и маршрутизируют через приватный backbone вместо публичного интернета. Типичная экономия: 30-50% снижение p95 latency на межконтинентальных путях.</p>
    <p><strong>Origin connection management.</strong> Edges держат долгоживущие HTTP/2 соединения к origin для переиспользования соединений — открытие нового TCP+TLS на запрос amplify-ло бы CPU origin и perceived latency. Размер pool важен: слишком мало и edges queue-ют ждать; слишком много и hit лимит open-file-descriptors на origin. mTLS между edge и origin защищает от exposure origin-IP.</p>
    <p><strong>Failure modes и graceful degradation.</strong> Когда origin лежит или медленный, что edge подаёт? Опции: подавать last-known-good кешированную версию (stale-if-error, RFC 5861), maintenance page, fallback на другой origin. CDN-side «origin pool» с health checks маршрутизирует трафик на healthy origin; если все origins лежат, cache-tier подаёт stale или WAF возвращает дружелюбный 503.</p>
    <p><strong>Observability для CDN-развёртываний.</strong> Ключевые метрики: cache hit rate per URL prefix (target &gt; 90% для static, &gt; 70% для HTML), p95/p99 edge response time per region, origin-shield offload ratio (% edge misses поглощённых shield), Vary-key cardinality (как фрагментирован кеш), WAF block rate, bot score distribution.</p>
    <p><strong>Real-User Monitoring (RUM) на edge.</strong> Помимо synthetic probes, CDN собирают per-request beacons от браузера (Performance API, Web Vitals) сообщающие Time-to-First-Byte, Largest Contentful Paint, Cumulative Layout Shift, First Input Delay. Эти едут поверх CDN-телеметрии и feed-ят multi-CDN steering решения.</p>
    <p><strong>Edge storage tiers.</strong> Помимо в-памяти кеша на edge, современные CDN предлагают persistent storage: Cloudflare KV (eventually consistent key-value), D1 (SQL), R2 (S3-compatible object storage без egress fees), Durable Objects (strongly-consistent stateful primitives). Fastly KV Store. AWS S3 + CloudFront. Это позволяет строить full-stack приложения на edge без backend-сервера — auth tokens, sessions, asset metadata, всё близко к пользователю.</p>
    <p><strong>Современные edge compute frameworks.</strong> Next.js Edge Runtime, Astro Server Islands, Remix on Cloudflare Workers, SvelteKit с Vercel Edge — все позволяют запускать SSR (server-side rendering) на edge. Преимущество: HTML генерируется в 20 мс от пользователя вместо 200 мс. Ограничения: edge-environments урезаны (нет Node.js APIs, ограниченные library, runtime ~50 ms wall-time). Подходит для большинства веб-страниц, не подходит для тяжёлой обработки изображений или ML inference.</p>
    <p><strong>Image и video optimization на edge.</strong> Cloudflare Images, Fastly Image Optimizer, AWS CloudFront + Lambda — на лету конвертируют изображения в WebP/AVIF, ресайзят под устройство, сжимают per-image. Webhook-based optimization (Cloudinary): origin отдаёт оригинальный JPEG, CDN кеширует оптимизированные варианты. Видео: Cloudflare Stream, AWS Elemental MediaConvert + CloudFront — конвертируют в HLS/DASH, кеш сегментов на edge.</p>
    <p><strong>Конец заголовков на edge.</strong> Большинство CDN позволяют переопределить response headers перед доставкой пользователю. Сценарии: добавить security-заголовки (Strict-Transport-Security, X-Content-Type-Options, X-Frame-Options) к каждому ответу без изменения origin; удалить чувствительные заголовки (X-Powered-By, Server) для security; добавить custom-заголовки для трассировки. Cloudflare Page Rules, Fastly VCL, CloudFront response policies — каждый CDN имеет свой механизм.</p>
    <p><strong>Региональные различия CDN-производительности.</strong> CDN-производительность сильно варьируется по регионам. В Северной Америке и Европе все top-tier провайдеры дают &lt; 50 мс p95 благодаря густой сети PoPs. В Латинской Америке, Африке, Юго-Восточной Азии — характеристики хуже из-за меньшей плотности peering. Для глобальных аудиторий outside-US сервисов проверьте latency в целевых рынках до выбора провайдера. RUM-данные (Web Vitals) — лучший способ оценки реальной производительности; синтетические тесты часто оптимистичны.</p>
    <p><strong>Production checklist для CDN-deployment.</strong> 1) HTTP/3 и /2 enabled. 2) TLS 1.3, post-quantum-hybrid в опционе. 3) Brotli compression. 4) Static assets с content-hash + max-age=1y. 5) Cache-Control для всех routes. 6) Vary только Accept-Encoding (плюс Accept-Language если применимо). 7) ETag на динамическом контенте. 8) WAF rules для OWASP Top 10. 9) Rate limiting per-IP и per-token. 10) Health checks на origin. 11) Stale-while-revalidate для UX. 12) Logging + RUM подключены. 13) Documentation и runbooks для инцидентов.</p>
    <p><strong>HTTPS на CDN: подходы.</strong> Полное TLS-терминирование на edge (CDN держит сертификат, origin может быть HTTP) — самое простое. Sideline (CDN терминирует TLS, к origin идёт через encrypted tunnel) — добавляет slight overhead но безопаснее. SSL passthrough (CDN форвардит TLS-handshake к origin) — origin держит ключи, CDN видит только зашифрованный трафик; ломает caching и WAF потому что CDN не может прочитать контент. Для большинства производств — full TLS-termination на edge стандарт.</p>
    <p><strong>Edge-side observability стек.</strong> Cloudflare Logs, Fastly Real-Time Log Streaming, AWS CloudFront real-time logs — поставляют per-request метаданные в Kafka/Kinesis/Cloudflare Workers Analytics. Метрики: cache hit rate per path, bandwidth per origin, error rate per region, attack metrics (WAF blocks, bot traffic). Интеграция с Datadog, Grafana, Splunk через стандартные log-shippers.</p>
    <p><strong>Cache hierarchy real-world numbers.</strong> На крупном веб-сайте типичные значения: cache hit ratio на edge — 85-95% для static assets, 60-80% для HTML, 30-50% для API responses. p50 latency edge → user — 10-30 мс, p95 — 50-100 мс, p99 — 200-400 мс. Origin RTT (edge → origin) — 20-100 мс в зависимости от geography. Bandwidth saving от кеша часто 80-95% — origin видит лишь малую долю трафика что критично для cost и reliability.</p>
    <p><strong>Operational tactics.</strong> Production CDN-ops включает: мониторинг hit ratio per route и alerting при падении; periodic purge при major content updates; warming cache после deploy через crawl-script; A/B testing routing changes на small fraction трафика; chaos testing — намеренно отключать одну CDN из multi-CDN setup чтобы убедиться что fallback работает. Документировать SOP для каждого failure mode (origin down, edge degraded, certificate expiry).</p>
    <p><strong>CDN-mesh и multi-cloud.</strong> Большие компании часто используют hybrid: trafic на статику через CDN, dynamic API через service mesh, video через специализированные video-CDN. Inter-region replication trafic через cloud-provider's backbone (AWS PrivateLink, GCP Interconnect) минуя публичный интернет — даёт лучшую latency и предсказуемость. Это формирует cross-region mesh где каждая часть architectured для своего use-case.</p>
    <p><strong>Mental model для архитектора.</strong> Думайте о CDN не как о «кеш» а как о «программируемый proxy с глобальной географией и compute». Каждый запрос проходит через edge worker который может: применить policy, переписать URL, fetch из cache или origin, инжектить заголовки, рендерить HTML, проверить auth — всё близко к пользователю. Origin тогда становится упрощённой backend-частью с фокусом только на bus logic и persistence.</p>

<Misconception
  id="r-cache-key-bypass"
  title="Внимание: cache key bypass через Vary footgun"
>
Vary: User-Agent или Vary: Cookie фрагментирует кеш per-user. Cache hit rate падает к нулю. Vary: Accept-Encoding обязателен; всё остальное обдумайте дважды. Для персонализированного контента используйте Cache-Control: private или no-store.
</Misconception>

Почему это важно? <SpiralCue thread="latency" lang="ru" /> Неправильный Vary — один из трёх главных источников production-инцидентов на edge. Другие два: отсутствующий Vary (cache poisoning между пользователями) и забытый purge при develop (stale контент разиходит по POPs).

<KeyTakeaway title="Главное">
CDN превращает «сервер в 250 мс» в «сервер в 20 мс» реплицируя контент в сотни edge POPs и маршрутизируя каждого пользователя в ближайший через Anycast или GeoDNS. Интересный слой — конфигурация кеша: Cache-Control TTLs, Vary-ключирование, surgical purges через cache-tags, edge-side composition для partially-cacheable страниц, и stale-while-revalidate для graceful misses. Большинство CDN-related production-инцидентов трассируются к одной из трёх причин: отсутствующий Vary (cache poisoning между пользователями), неправильный Vary (cache фрагментирует per User-Agent), или deploy pipeline не purge-ит на origin updates.
</KeyTakeaway>
