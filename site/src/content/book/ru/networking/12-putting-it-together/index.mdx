Вы вводите URL. Страница появляется. Между ними: семь действующих лиц договариваются через слои, которые вы уже встретили. <PersonaTag id="bea" lang="ru" /> (браузер) просыпается. <PersonaTag id="rex" lang="ru" /> (DNS resolver) консультирует кеш. <PersonaTag id="rita" lang="ru" /> (маршрутизатор) пересылает пакет. <PersonaTag id="sven" lang="ru" /> (origin server) держит истину. <PersonaTag id="cara" lang="ru" /> (CA) подтверждает доверие. <PersonaTag id="patty" lang="ru" /> (CDN edge) раздаёт из памяти. Каждый слой инкапсулирует тот, что ниже. <SpiralCue thread="encapsulation" lang="ru" /> Каждый запрос мультиплексируется с другими. <SpiralCue thread="multiplexing" lang="ru" /> Состояние соединения persists через round-trips. <SpiralCue thread="statefulness" lang="ru" /> И вся церемония должна завершиться до того, как latency её убьёт. <SpiralCue thread="latency" lang="ru" />

<Crux>Когда вы вводите URL и страница загружается, какие двенадцать слоёв срабатывают в порядке, и где уходит 200–400 мс?</Crux>

Давайте проходим один HTTPS-запрос от keystroke до первого пикселя.

## Проход: один запрос от Лондона до Калифорнии и обратно (через proxies и security gates)

**Вы печатаете. Bea просыпается.** <PersonaTag id="bea" lang="ru" /> получает keystroke и assembles запрос для `example.com`. У неё ещё нет IP-адреса — только имя хоста. Она открывает UDP socket и отправляет DNS query к configured resolver.

**Rex ищет ответ.** <PersonaTag id="rex" lang="ru" /> — recursive resolver — может быть ISP DNS, может быть 8.8.8.8, может быть private resolver вашей компании. Rex проверяет кеш: "Есть ли у меня IP для example.com?" Если warm, он отвечает за меньше чем 1 мс. Если cold, Rex ходит по DNS-дереву: спрашивает root nameserver, потом .com nameserver, потом authoritative nameserver example.com. Каждый hop пересекает сеть. Типичное время: 30–100 мс. Ответ приходит с TTL (time-to-live) — "кешируй это 300 секунд."

**Rita маршрутизирует TCP SYN.** Теперь Bea знает IP. Она открывает TCP socket и отправляет SYN пакет. Rita и её коллеги — маршрутизаторы — они пересылают пакет hop-by-hop к Калифорнии, используя forwarding tables. Каждый маршрутизатор проверяет destination IP, konsultirует routing table и отправляет пакет на следующий hop. Latency bound speed of light через fiber и radio: 1 round-trip от Лондона до Калифорнии это ~100 мс по direct submarine cable. SYN приходит на Sven's firewall.

**Patty's proxy перехватывает (или пересылает).** Прежде чем Bea's SYN доберётся до Sven's сервера, он может hit reverse proxy или load balancer. Зовите это Patty (если это CDN edge) или её cousin, regional load balancer. Patty (или load balancer) решает: "Есть ли cached response который я могу serve локально?" (Если да, он replies 200 OK и closes TCP stream — Sven никогда не видит запрос.) Если нет, Patty's proxy forwards запрос дальше или performs connection draining и health checks. Если Sven's сервер unhealthy (health check failed, process down), Patty routes соединение на backup server вместо. Health checks происходят out-of-band (каждые несколько секунд, periodic ping к /health endpoint). Если Sven's main server только что получал SYN, Patty's health check может reroute запрос в полёте на другой сервер в пуле. Пока assume Sven healthy; Patty forwards соединение.

**Rate limit и WAF gates.** <PersonaTag id="sven" lang="ru" /> (origin server) получает SYN, но прежде чем он respond, security middleware перехватывает. Rate limiter проверяет: "Послала ли эта IP (Bea's) больше чем N requests в секунду?" Если да, SYN silently dropped (или rate limit enforced на Patty's edge, не на Sven). Web Application Firewall (WAF) проверяет: "Matches ли signature этого соединения known attack patterns?" Signatures rule-based (например, "SQL injection keywords в query string") или anomaly-based (например, "эта IP обычно sends 2 req/min, сейчас 100 req/sec"). Если suspicious, WAF blocks или challenges. Для нормальных запросов обе проверки pass instantly. Если бы Bea была botnet отправляющая 10,000 req/s с одного IP, rate limiter drops пакеты silently. Защита: token bucket или leaky bucket algorithm. Для каждой секунды tokens accumulate (до лимита); каждый запрос consumes один token. Когда tokens run out, новые запросы dropped. Jitter через clients prevents thundering herd когда limits reset.

**Sven принимает handshake.** Bea's ACK arrives (third packet TCP handshake). Sven responds и соединение established. Три пакета, 1 round-trip (~100 мс), и теперь обе стороны trust TCP соединение state. <PersonaTag id="cara" lang="ru" /> (CA — certificate authority) offline пока; она vouched за Sven's identity когда Sven был registered, и её signature sits в его certificate.

**Cara's signature validated во время TLS.** Bea и Sven теперь perform TLS 1.3 handshake. Bea sends ClientHello с list cipher suites и pre-shared key (если это warm соединение, она может skip round-trips). Sven responds ServerHello, его certificate и server pre-shared key. Bea validates Sven's certificate checking Cara's signature — cryptographic proof что Sven это кто он pretends быть. Если signature invalid, соединение aborts. Если valid, Bea и Sven derive shared encryption keys и теперь могут send encrypted data. Время: 1 RTT (~100 мс) для new соединения, 0 RTT если Bea has resumption state.

**mTLS: Sven validates Bea (optional, для sensitive paths).** Обычно, только Bea validates Sven. Но для sensitive операций (internal APIs, microservices между Sven's backend services, financial transactions), Sven also verifies Bea's certificate. Это mutual TLS (mTLS). Sven sends CertificateRequest message во время TLS handshake, requesting Bea's certificate. Bea sends свой. Sven checks certificate signature against list trusted CAs (часто internal CA specific к Sven's компании, SPIFFE cluster или организации). Если Bea's certificate не recognized, Sven closes соединение. mTLS adds один extra round-trip для request/response (CertificateRequest), но essential для service-to-service authentication в zero-trust networks. Стоимость: каждый Bea должен have valid certificate issued Sven's trusted CA. Certificate expiry, rotation и distribution — operational burdens.

**HTTP/3 streams multiplex независимо.** Bea constructs HTTP request: GET /index.html, с headers, accept-language, cookies и user-agent. На HTTP/3 (using QUIC), она opens stream на том же UDP соединении и sends запрос. QUIC merges transport layer (UDP packet demultiplexing) и encryption (TLS) в one handshake, saving 1 RTT для new соединений compared к TCP+TLS. Sven's kernel handles QUIC framing и passes запрос к application layer. Sven constructs response: status 200, content-type: text/html, cache-control headers и HTML body. Он sends это в QUIC frames, каждый frame tagged с stream ID так чтобы Bea's kernel могла reassemble его. Другие запросы (images, scripts, styles) открываются как separate streams и sent в parallel. Если один stream's пакет lost, другие keep flowing (stream independence, QUIC win над HTTP/2+TCP где single пакет loss stalls все streams). Время для request/response: ~1 RTT (~100 мс), assuming response fits в initial congestion window.

**QUIC connection migration (mobile networks).** Если Bea's device switches с WiFi на cellular, её IP address changes. В TCP+HTTP/2, IP change breaks соединение — Bea должна re-establish и lose все in-flight streams. В QUIC, соединение persists через Destination Connection ID (stateless token Sven issued на handshake). Bea's kernel sends PATH_CHALLENGE frame к Sven с new IP. Sven responds PATH_RESPONSE используя same token, proving IP change это legitimate (не attack). Соединение continues без loss streams, без TLS re-negotiation. Стоимость: один extra round-trip (PATH_CHALLENGE/RESPONSE), но cheaper чем re-establishing entire соединение. Migration happens silently; Bea's application (browser или HTTP client) не должна know.

**Patty serves с edge (или Sven services с origin).** Если запрос hits CDN, <PersonaTag id="patty" lang="ru" /> (edge proxy) intercepts запрос. Её DNS configured вернуть regional IP, так что Bea connected к London POP вместо Калифорнии. Patty checks её кеш: "Есть ли у меня index.html с correct Vary headers?" Если да (cache hit), она responds immediately (~10 мс round-trip). Patty's edges близко к clients имеют much lower latency чем origin. Если нет (cache miss), Patty может first check origin shield (regional cache shared много edge nodes) чтобы avoid thundering-herd запросы к Sven. Если shield также misses, Patty forwards запрос к Sven's origin. Если Sven responds 503 Service Unavailable (overloaded или under DDoS), Patty's circuit breaker stops forwarding новые запросы к нему и instead serves stale content из её кеша (если Cache-Control: stale-while-revalidate set). Sven responds. Patty stores response в кеш и sends к Bea. Response trickles назад через Rita's роuters (same маршрут, reverse направление) и arrives к Bea's kernel, который passes его browser.

**Rita's routers queue и prioritize.** Пока пакеты traverse Rita и её коллегами, они encounter congestion windows, retransmit timers и DSCP prioritization. Если link saturated, роuters queue пакеты. Если пакет lost (due к bit-flip или congestion), sender retransmits. Большинство links не saturated; большинство пакетов arrive с first try. Но каждый additional hop, каждый retransmit и каждый retry compounds latency.

**Bea parses и renders.** Browser receives HTML bytes, parses DOM, fetches critical resources (CSS, fonts, JavaScript), parses stylesheets, constructs render tree, performs layout и paints пиксели. Первый contentful paint (FCP) happens когда Bea имеет HTML + CSS ready. Largest contentful paint (LCP) happens когда largest visible element painted. Современные browsers parallelize всё это: как HTML streams, parsing begins; как CSS arrives, reflow happens incrementally. Вся танец — от keystroke к LCP — на typical странице takes 2–4 секунды. Networking часть это только ~200–300 мс (1 RTT DNS + 1 RTT TCP + 1 RTT TLS + 1 RTT HTTP + 1 RTT response arrival + rendering overhead). Остаток это JavaScript, network roundtrips для subresources и browser's rendering pipeline.

  <Fragment slot="middle">
    <p><strong>Механизм в деталях.</strong> HTTPS-запрос это choreography семи layers working в sequence. DNS resolves имя (30–100 мс cold). TCP handshake connects (25–100 мс regional). TLS handshake authenticates и encrypts (25–100 мс, или 0 если 0-RTT). HTTP request/response travels (1 RTT). CDN edge (если hit) replies в ~10 мс; если miss, request travels к origin (200+ мс intercontinental). Browser parses HTML, fetches subresources, renders. На каждом step, latency это round-trip count × one-way delay.</p>

    <p><strong>Где именно время уходит.</strong> На LCP-critical path для типичного сайта:</p>
    <ul>
      <li>DNS warm: &lt;1 мс (кеш)</li>
      <li>TCP handshake: 25–100 мс (географический RTT)</li>
      <li>TLS handshake: 25–100 мс (ещё один RTT)</li>
      <li>HTTP request send + TTFB: 1 RTT (network delay + server processing)</li>
      <li>Resource download: зависит от size и bandwidth</li>
      <li>Browser render: layout, paint, composite</li>
    </ul>

    <p><strong>Seven phases in sequence с typical timings.</strong> Phase 1: DNS Resolution (~30 мс cold, &lt;1 мс warm). Bea asks Rex, "Что IP для example.com?" Если Rex has answer cached (TTL &gt; 0), он replies в microseconds. Если нет, Rex walks DNS hierarchy: root nameserver → TLD nameserver → authoritative nameserver. Каждый hop это network round-trip. A cold DNS lookup в North America или Europe takes 30–100 мс. Most users' resolvers have warm caches, so DNS это amortized: first visitor pays ~30 мс, subsequent visitors pay &lt;1 мс. Phase 2: TCP Handshake (1 RTT, ~10–25 мс regional, ~56–100 мс intercontinental). Bea sends SYN к Sven. Sven responds SYN-ACK. Bea sends ACK. Three packets, one round-trip. A connection within region (London к Frankfurt) это ~10–25 мс. A connection intercontinentally (London к California) это ~56–100 мс each way (speed of light through fiber). After handshake, TCP initial congestion window это usually 10 packets (IW=10). Bea может send up к 10 packets без waiting для ACK.</p>

    <p><strong>TLS handshake, HTTP request/response, и rendering.</strong> Phase 3: TLS 1.3 Handshake (1 RTT new, 0 RTT resumption, ~25 мс). Bea sends ClientHello с pre-shared key и supported cipher suites. Sven responds с ServerHello, certificate, и server key. Bea validates certificate using Cara signature. Both derive keys. Encrypted data now может быть sent. Если Bea has seen Sven before (session ticket from last time), она может send early data (0-RTT) — request это encrypted с old key и sent immediately, без waiting для Sven response. Risk: 0-RTT data это не forward-secret, so это safe только для idempotent operations (GET, не POST/PUT). Phase 4: HTTP Request (~1 RTT, ~25 мс). Bea sends HTTP request: method, path, headers, cookies. На HTTP/3, это QUIC HEADERS frame. На HTTP/2, это HTTP/2 HEADERS frame. Sven application layer receives request и processes это: check authentication, query database, construct response. Processing time это app-dependent; assume 10 мс для cache hit. Phase 5: HTTP Response (RTT + processing, ~50 мс). Sven sends response: status, headers, body. На HTTP/3, QUIC streams это independent, so если multiple requests in flight, Sven может interleave responses. Phase 6: Subresource Fetches (parallelized, RTT × depth). HTML includes references к CSS, JS, images. Bea browser parses HTML, discovers subresource URLs, и fetches их. Critical resources (CSS, fonts) это fetched first. На HTTP/3, Bea может send requests для 10+ subresources в parallel; all multiplexed на same connection. Phase 7: Rendering (parallelized, 0–100+ мс). As CSS arrives, Bea browser parses это и constructs CSSOM. As HTML arrives, she parses DOM. Browser merges DOM + CSSOM → render tree → layout → paint. Если JavaScript blocks main thread, painting stalls. Modern sites defer JavaScript; rendering это concurrent с network fetches. The full picture: assuming warm DNS, regional geography (~25 мс RTT), HTTP/3 с 0-RTT resumption, и CDN cache hit: DNS (&lt;1 мс) + TLS (0 мс, 0-RTT) + HTTP request (0 мс, piggybacked на 0-RTT data) + response (~10 мс) + subresources (1 RTT, ~25 мс) + rendering (100 мс) = ~150 мс к LCP.</p>

    <p><strong>Connection reuse, resource hints, и caching layers.</strong> Каждый new origin requires fresh DNS + TCP + TLS handshake. Cross-origin requests (fonts from Google Fonts, scripts from third-party tracker, images from different CDN) pay этот price per origin. `&lt;link rel="preconnect"&gt;` и `&lt;link rel="dns-prefetch"&gt;` warn browser к open connections к anticipated origins до main parser reaches их; saves handshake from critical path. `&lt;link rel="preload"&gt;` для fonts, scripts, и ES modules helps load critical assets earlier. `&lt;link rel="prefetch"&gt;` для likely-next-navigation resources. A warm request hits: (1) browser memory cache (sub-millisecond), (2) browser disk cache (~10 мс), (3) CDN edge cache (~20-50 мс over network), (4) CDN shield cache (~50-100 мс), (5) origin (~100-300 мс). Каждый layer reduces traffic к next. Three common misconceptions: One: "Faster network always means faster page." False — для cache hits, rendering dominates; для cache misses, server compute often dominates. Two: "Reducing bundle size always helps." Helps loading, но если rendering это JavaScript-bound, parsing time это bottleneck. Three: "0-RTT saves time для every request." Saves time только для warm connections; cold connections pay full handshake.</p>

    <p><strong>Четыре нити которые recur через все layers.</strong> Encapsulation: каждый layer wraps данные в свой header/footer (Ethernet frame wraps IP packet wraps TCP segment wraps HTTP message). Multiplexing: много logical streams share один physical pipe (TCP multiplexes flows, HTTP/2 и /3 multiplex requests). Statefulness: connections помнят state (TCP window size, TLS keys, HTTP cookies) across round-trips, enabling optimization (resumption, connection pooling). Latency: каждый round-trip, каждый handshake, каждый cache miss это cost. Архитектура это optimization against latency.</p>

    <p><strong>Мониторинг и debugging per-layer latency.</strong> Вся магия находится в измерении. Используйте browser DevTools (Network tab) для synchronous timings: DNS lookup, TCP connection, TLS negotiation, request/response, content download. Используйте synthetic monitoring (WebPageTest, Lighthouse) для reproducible baseline. Используйте real-user monitoring (RUM) для capturing production variability: не все users в same geography, не все on same network speed. RUM tools (Datadog, New Relic, Sentry) aggregate latencies по layer и percentile (p50, p95, p99).典型的な pattern: p50 LCP 1 s из-за оптимизированного CDN cache hit, но p99 LCP 4 s потому что cold traffic и холодный resolver у 1% пользователей на slow network. Middle-tier engineer задача — найти и eliminate outliers. Instrumentation точка: в production, собирайте DNS timing (ResourceTiming API), TCP+TLS timing (same PerformanceNavigationTiming), HTTP status и header timings (PerformanceResourceTiming), render timings (PerformancePaintTiming для FCP, PerformanceObserver для LCP). Это возможно в JavaScript без server-side coordination, и этого достаточно чтобы debug 90% latency issues.</p>

    <p><strong>Cache-Control headers и layer interaction.</strong> HTTP responses могут быть cached на три места: browser memory/disk cache (управляется Cache-Control), CDN edge cache (управляется Cache-Control плюс Surrogate-Control), и optional origin shield (regional aggregation cache). Каждый layer имеет TTL. Проблема: если browser cache TTL 1 hour, но CDN cache TTL 5 minutes, и origin shield TTL 5 minutes, то browser может serve 1-hour-old content даже если edge или shield уже invalidated. Решение: исходить из fact что вы не можете синхронизировать все layer TTLs. Вместо, использовать smart cache busting: content-hash in filename (asset-v1a2b3c.js всегда can be cached агрессивно; если контент меняется, filename меняется и browser requests new copy). Для HTML (always changes), используй Cache-Control: max-age=0, must-revalidate чтобы проверить на edge свежесть с If-None-Match header (304 Not Modified если не-changed, 200 с новым телом если changed). Стоимость:额外的 round-trip для каждого checked asset, но избегает serving stale.</p>

    <p><strong>Origin shield, regional caches, и thundering herd problem.</strong> На popular site (news, social media), cache miss at CDN edge можно trigger simultaneous requests от edge к origin. 100 Londoners visit link одновременно, each misses edge cache, edge forwards 100 requests к origin, origin overloaded, returns 503, clients retry, scenario amplifies. Решение: origin shield — дополнительный cache layer между CDN edge и origin. Instead of 100 requests going straight к origin, все 100 edge misses коллапс к single origin shield request. Origin shield processes once, response cached, next 99 edges hit shield cache (не origin). Cost: additional network hop (~10–20 мс) но protect origin. Trade-off: worth it for bursty traffic (news drop, product launch). Not worth для mostly-cold traffic (low miss rate). Another pattern: stale-while-revalidate. Edge responds из stale cache (fast), simultaneously revalidates в background. Client gets instant response (old content), fresh content arrives by next page visit. Practical: set Cache-Control: max-age=300, stale-while-revalidate=86400. Within 5 minutes, edge serves fresh. After 5 minutes, edge serves stale but revalidates. After 1 day, edge discards. Result: most users see &lt;10 мс latency (cache hit), occasional user triggers background fetch (not on critical path).</p>

    <p><strong>Rendering bottlenecks и browser-side optimization.</strong> Когда HTML response arrives, browser парсит document в streaming fashion — parsing начинает immediately, не waiting for complete body. CSS arrives, CSSOM constructed, render tree merged (DOM + CSSOM). JavaScript может block parsing (unless async) или block rendering (script execution может modify DOM, so browser must finish running before continuing render). Стратегия: place non-critical JavaScript at end `&lt;/body&gt;`, mark it `async`, или use module system (`&lt;script type="module"&gt;`) which naturally async. Fonts cause rendering delay — if custom font не loaded and text заложено в `font-display: block`, browser won't paint text до font arrives (may take 100+ мс intercontinental). Better: use `font-display: swap` (paint fallback immediately, swap to custom font when ready) or `font-display: optional` (paint fallback, only use custom if instant). Large JavaScript bundle causing parse+compile bottleneck — на slow device (older mobile), parsing и compilation of large bundle может take 500+ мс. Mitigation: code-split (split bundle на chunks, only load necesary chunk per page), tree-shake (remove dead code), compress (minify, gzip). Images without explicit width/height cause layout shift — browser doesn't know space to reserve, image arrives, layout reflows. Mitigation: use `&lt;img width=... height=...&gt;` или CSS aspect-ratio. These strategies compound: шаг reduce per-layer latency by 10–50 мс быстро accumulate к several 100s мс improvement.</p>

    <p><strong>Third-party script performance impact.</strong> Third-party scripts (analytics, ads, tracking pixels) могут significantly slow page. Они often не optimized, может load synchronously (blocking render), может execute expensive code (DOM manipulation, network request). Typical script lifecycle: browser requests script URL, script downloads, script parses, script executes (synchronous, blocks main thread). If script takes 200 мс to download and 100 мс to execute, page blocked 300 мс. Multiple third-parties compound: analytics script blocks, ad script blocks, tracking pixel blocks. Result: p99 load time может быть 3+ секунд на slow network due third-party cascade. Solutions: (1) Load third-party асинхронно: &lt;script async src=...&gt; means script loads in parallel, but doesn't block render. (2) Defer third-party execution: use Web Workers (separate thread) for compute-heavy scripts. (3) Lazy-load non-critical third-parties: дождитесь critical content render, только then load analytics. (4) Sandbox third-party: use &lt;iframe&gt; для load script separately, sandbox attribute prevents access to parent document. (5) Monitor third-party latency: use PerformanceResourceTiming to track каждый third-party URL, alert если latency &gt; budget. Компромисс: full isolation (iframe) means third-party can't communicate dengan host (loses functionality), but improves latency и security. No isolation means performance risk.</p>

    <p><strong>Orchestrating optimization across teams.</strong> В large organization, network performance это not single engineer's job. Browser team owns rendering optimization (code-split, critical CSS). Backend team owns TTFB (caching, database optimization, API response time). DevOps team owns CDN configuration и edge caching policies. Platform team owns infrastructure (TCP tuning, TLS cert management, DDoS mitigation). Observability team owns RUM и synthetic monitoring, alerting на regressions. Success requires shared OKR (Objective Key Result): e.g., "Median LCP &lt;1.5 s, P99 LCP &lt;3 s across all geos and networks." Each team identifies bottleneck для their layer (browser: find largest JS file, backend: find slowest database query, CDN: check cache hit ratio), proposes change, measures impact. Orchestration happens via shared dashboard (single pane of glass) showing per-layer latency breakdown, per-team metrics, и performance budget tracking. Typical process: deploy experiment (e.g., new caching header), measure impact via RUM (p50/p95/p99 LCP), calculate cost/benefit (engineering effort vs latency improvement), decide rollout. Full deployment takes weeks (careful monitoring), not days (risk regression в production). This organizational structure isto avoid sub-optimization: one team improving их layer but breaking another's assumptions. Example: frontend team minifies JavaScript агрессивно, cuts bundle 30%, но now JavaScript parse+compile takes longer, net result no improvement. Proper way: measure end-to-end latency (LCP), not single metric.</p>

    <p><strong>Системный обзор.</strong> HTTPS-запрос это coordinated state machine где каждый layer contributes. DNS resolution = probabilistic (кеш hit vs miss). TCP handshake = deterministic (SYN, SYN-ACK, ACK). TLS = state negotiation (supported cipher suites, certificates, keys). HTTP = request/response semantics. CDN edge = cache coherency problem (stale vs fresh, Vary headers). Routers = congestion control game (cwnd, backoff, retransmit). Browser render = dependency DAG (parsing, layout, paint). Optimization требует measuring каждого layer и knowing bottleneck.</p>

    <p><strong>Причины why стандартный scenario медленнее чем best case.</strong> DNS может быть cold (30–100 мс вместо &lt;1). Соединение может быть к CDN edge в 200 мс away (не 20). TCP slow-start может fill initial congestion window не полностью (packet loss). TLS может использовать full 1-RTT handshake вместо 0-RTT (холодное новое соединение). HTTP может ждать для server processing (app latency не network). Browser может render-block на большой JS (не network-limited). Каждый из этих факторов это 10–200 мс.</p>

    <p><strong>W3C Trace Context и distributed tracing.</strong> End-to-end latency attribution requires propagating trace ID через все layers (HTTP header Traceparent: version-traceId-parentId-flags). Каждый сервис добавляет span с timings. Collector aggregates и correlates. Результат: видно что TCP takes 150 мс, TLS takes 80 мс, application takes 50 мс. Без tracing, вы видите только total TTFB и guessing. W3C Trace Context standard ensures каждый layer (DNS resolver, proxy, origin, CDN) propagates same trace ID и parent span ID, building complete causal chain. OpenTelemetry и Jaeger являются standard exporters. Cost: overhead of adding headers и instrumentation; benefit: visibility into every layer's contribution к latency.</p>

    <p><strong>Critical render path optimization и cascading optimizations.</strong> Browser render pipeline зависит от HTML, CSS, и (для interactivity) JavaScript. HTML parsed как byte stream in — DOM construction starts до полного arrival body. CSS blocks rendering: nothing paints пока at least one stylesheet не loaded для current viewport. JavaScript blocks parsing unless marked `async` или `defer`; placing scripts в bottom `&lt;body&gt;` или с `defer` lets HTML и CSS parse в parallel. Browser preload scanner runs tokenizer ahead main parser чтобы discover sub-resource URLs и fire requests early. Critical-path resources should быть inlined или marked `&lt;link rel="preload"&gt;` для browsers чтобы fetch в parallel с HTML parsing. HTTP/3 早期处理 (Early Hints status 103) lets server send preload headers до body arrives, further parallelizing resource discovery. Edge compute (Cloudflare Workers, Lambda@Edge) can generate personalized early hints based на geographic location или user profile, tailoring preload strategy per-region.</p>

    <p><strong>Service Workers, offline-first patterns, и cache invalidation strategies.</strong> Service Worker это JavaScript file browser registers как intercepting proxy для all requests from origin. Может serve cached responses без hitting network, queue requests when offline, transform responses, push notifications. Also runs background sync — uploading queued user actions when network returns. Cost: complexity (page now has two execution contexts что must stay в sync), debugging difficulty, registration footprint. Right pattern: Service Workers для offline-first PWAs (mail clients, document editors); avoid для simple content sites где value-to-complexity ratio это poor. Cache invalidation across multiple layers (browser cache, disk cache, CDN edge, regional shield, origin) это hard problem. Designs что span all layers must propagate invalidation events explicitly. Opposite mistake — relying на TTL expiry across multiple layers — leads к stale data living в cracks для far longer чем any single layer TTL. Solution: use content-hash versioning (asset-v1a2b3c.js never needs invalidation, only index.html updates), Surrogate-Key headers (CDN purges multiple variants from one key), и secondary TTLs (stale-while-revalidate: serve stale для N seconds while revalidating background).</p>

    <p><strong>Congestion control, TCP vs QUIC, и packet loss recovery.</strong> TCP congestion control живёт в kernel; not tunable per-flow. Сначала slow-start doubles cwnd every RTT до threshold, потом additive increase. Packet loss triggers multiplicative decrease (cwnd ÷ 2). QUIC congestion control живёт в user-space (libquic). Operators могут test new algorithms (BBR2, PCC) без kernel patches. Also QUIC sends ACKs in-band (как frames), не as separate TCP ACK packets, so routers process fewer packets. Throughput это similar но latency variance это lower. QUIC stream independence means packet loss на stream A does NOT stall streams B, C, D — каждый stream has свой sequence number и retransmit logic. Effectiveness gap widens на high-loss links (satellite, bad cellular): TCP entire window stalls on one loss; QUIC only affected stream retransmits. Cost: middle-box unfriendliness. Some firewalls, NATs, load balancers assume TCP и drop UDP packets. Debugging harder: tcpdump не shows QUIC streams (encrypted). Initial deployment cost real; payoff это latency и mobile UX. Operators must explicitly enable QUIC и test для packet loss, bit-flips, и rate-limiting на UDP.</p>

    <p><strong>API call path, database query optimization, и the operations engineer's role.</strong> User clicks button. Browser issues fetch() — already-open HTTP/2 или /3 connection avoids handshake. Request rides к CDN edge (no cache, mutating endpoint). Edge forwards к origin region. Origin auth-checks, queries DB, computes response, returns. Edge не caches (Cache-Control: no-store). Browser receives response. JavaScript handler updates state, triggers re-render. Total time: typical 100–200 мс на good day. Если any layer это slow (DB query, third-party API в response computation, slow JS handler), user perceives lag. Optimization per layer это operations engineer daily work. Database side: query plan cache, index hot tables, partition large tables по geographic region для localize lookups. Origin side: connection pooling к downstream DBs/caches, circuit breakers к flaky dependencies, graceful degradation (serve cached или partial response under failure). Browser side: defer non-critical work, batch updates, throttle event handlers. Path optimization это systems thinking — no single layer matters; total matter.</p>

    <p><strong>Core Web Vitals interpretation.</strong> Google Web Vitals quantify user-perceived performance. LCP (Largest Contentful Paint) это когда biggest visible element finishes rendering — typically hero image или main heading. Good: under 2.5 s; poor: over 4 s. INP (Interaction to Next Paint) measures responsiveness across entire page lifecycle — longest delay between user input и resulting visual response. Good: under 200 мс. CLS (Cumulative Layout Shift) measures unexpected layout movement во время page load — images без dimensions, ads inserting content, fonts shifting text. Good: under 0.1. Search ranking depends на these; Google uses field RUM data, не synthetic tests, so optimizing для synthetic alone misses point.</p>

    <p><strong>Connection reuse и multiplexing.</strong> HTTP/1.1 без multiplexing: каждый новый request требует fresh TCP + TLS. HTTP/2: один connection multiplexes много streams но packet loss к one stream stalls all others (head-of-line blocking). HTTP/3: один QUIC connection с independent streams — packet loss на stream 25 does NOT stall streams 26–50. Practical win HTTP/3: 100+ мс vs HTTP/2 на high-loss links (cellular, satellite).</p>

    <p><strong>Advanced caching coherency и cache key strategies.</strong> Наиболее subtle проблема в large-scale production это cache coherency across multiple CDN regions, origins, и customers' locales. Cached response может vary по Accept-Language (ES vs RU), Accept-Encoding (gzip vs brotli), device type (mobile vs desktop), или user tier (anonymous vs premium). HTTP Vary header tells cache "this response is specific to these headers" — но unless you set Vary correctly, cache завозит неправильный variant. Пример ошибка: response без Vary: Accept-Language cached с RU, потом Spanish user gets RU content. Решение: set Vary: Accept-Language явно. Но scale-up: 100 possible combinations, каждая кешируется отдельно, cache hit ratio падает. Продвинутый pattern: move variance-causing logic к edge compute — personalize at CDN region instead of origin, so origin sends one "canonical" response and edge personalize it. Другой advanced pattern: use Content-Negotiation in application layer, serve the "best" variant, и rely на Accept-* headers для browser-side re-request при смене condition. Trade-off: flexibility vs complexity, cache hit ratio vs freshness. Senior engineer must know когда each tool appropriate.</p>

    <p><strong>The END-TO-END ARGUMENT и where logic belongs.</strong> Seminal systems paper (RFC 1958) по Internet architecture: don't rely на intermediate nodes для correctness; only endpoints (client и server) understand application semantics. Applied к latency: don't expect network to be "smart" about optimization — design explicit layers (preload, prefetch, early hints). Applied к security: end-to-end encryption (TLS) means intermediary proxies cannot snoop, но also can't offload decryption or re-route based on deeper inspection. Applied к caching: edge caches are guess based on headers; origin knows ground truth. Applied к error handling: intermediate nodes (proxies, routers) can drop packets; only endpoints (TCP, QUIC) must handle retransmit and congestion. Takeaway: latency optimization must account for где logic lives — browser vs CDN edge vs origin vs third-party service. Offload expensive compute к edge only if logic stateless; maintain truth at origin. Этот trade-off between placing optimization close-to-user (fast) vs placing-at-source (correct) появляется каждый день в production.</p>

    <p><strong>Latency attribution under degradation.</strong> Во время outage или under heavy load, latency breaks down differently. Normal day: DNS &lt;1, TCP 25, TLS 25, TTFB 50 (20 server processing + 30 network), rendering 200 = ~300 total. Under origin overload: server processing 2–5 s (queueing), TTFB 2–5 s. CDN circuit breaker should catch this and serve stale content из кеша с stale-while-revalidate header (HTTP 200, но Content-Age: 600 indicating it's 10 min old). If circuit breaker absent или too slow, users see 500 errors. If circuit breaker serves stale too long, users see inconsistency (purchase confirmations на старом state). Senior engineer must tune circuit breaker parameters (failure threshold, timeout, fallback TTL) based на app semantics. How to know correct timeout? Use трассировку: median server p50 processing time + 2–3 × standard deviation. If median 50 мс, std 20 мс, set timeout 50+3×20 = 110 мс. Requests slower than timeout classified as degraded, fallback triggered.</p>

    <p><strong>Buffering policies и backpressure mechanisms.</strong> На transport layer (TCP/QUIC), sender has congestion window; if window full, sender blocks. На HTTP layer, proxy (CDN edge) может buffer response from origin; if origin slow, edge buffer fills, at some point edge closes connection upstream к client (или slows) to signal backpressure. On app layer (REST API), API can accept in-flight requests up to limit, then return 429 Too Many Requests. Multiple layers means multiple buffering decisions. Mistake: let all layers buffer independently leads к head-of-line blocking — client sends 100 requests, origin processes slowly, edge buffer fills, edges buffer fills at regional proxy, client keeps sending, TCP retransmit timer fires, jitter added, p99 latency spikes. Better: explicit rate-limit closer to client (e.g., token bucket at CDN edge with smaller allowance for unknown clients, larger for authenticated), so clients get fast feedback (429) and don't waste resources retransmitting. Trade-off: fairness (fast users don't starve slow users) vs latency (fast users wait for rate limiter check instead of instant response). Senior engineer must monitor queue depth at each layer and adjust buffer/rate-limit params accordingly.</p>

    <p><strong>Synthetic vs real-user measurement и representativeness.</strong> Synthetic tests (WebPageTest, Lighthouse) дают reproducible latency baseline и isolate specific factors (network speed, device type, third-party script load). But synthetic это fiction: no real user browsing, no background processes, no JavaScript slowing parse, cold cache only. RUM (real-user monitoring) captures actual distribution: p50 latency vs p99, cold cache vs warm, mobile vs desktop, geographic spread. Problem: RUM noisy; single slow third-party script can spike p99. Solution: combine both. Use synthetic for detecting regressions (runs on every deploy, alerts if LCP increases 50+ мс). Use RUM for strategic decisions (if p99 LCP 5 s across all users, big geographic latency spike, invest in multi-CDN). Also use synthetic to understand why: WebPageTest waterfall shows if CSS blocking, if third-party fonts slow, if unoptimized images. Then find cohorts in RUM data (filter by browser type, device, network) и verify synthetic result matches. Mismatch means synthetic didn't capture real condition. Example: synthetic test on fast device + desktop network shows LCP 1 s, but RUM shows median 800 мс for desktop but median 3 s for mobile. Then WebPageTest need re-run on mobile emulation to match RUM cohort.</p>

    <p><strong>Latency attribution in edge-case scenarios и failure modes.</strong> Nominally clear breakdown (DNS 30 мс, TCP 25 мс, TLS 25 мс, TTFB 50 мс, rendering 200 мс) breaks in corner cases. Example 1: client on residential ISP where DNS resolver is ISP-hosted но poorly maintained, DNS lookup takes 200 мс cold (instead 30). Solution: use third-party resolver (Cloudflare 1.1.1.1, Google 8.8.8.8, Quad9 9.9.9.9). Requires network configuration change (not browser-level). Example 2: client on mobile networks experiencing active mobility (cell tower handoff). TCP connection may see retransmits; QUIC handles透明ly with connection migration. Example 3: client behind corporate proxy/firewall that requires explicit TLS handshake negotiation. TLS latency increases 50+ мс due proxy inspection. Mitigation: CONNECT tunneling (TLS happens inside proxy tunnel, proxy doesn't inspect encrypted content). Example 4: DNS resolution working но authoritative nameserver for domain unreachable/slow (NXDOMAIN, SERVFAIL, timeout). Recursive resolver keeps retrying, timeout happens at 5–30 sec. Solution: graceful fallback (use hardcoded IP or secondary resolver). Example 5: client resolution to wrong regional CDN POP due to outdated Anycast prefix. Client thinks connecting to nearby POP но actually routing to far POP. Debugging: use traceroute или mtr to visualize packet path. Mitigation: BGP anycast tuning на CDN operator side, or explicit multi-CDN failover based on latency measurement.</p>

<KeyTakeaway title="Главное">
Каждый HTTPS-запрос — coordinated последовательность семи layers: DNS чтобы найти IP, TCP для надёжного byte-транспорта, TLS для конфиденциальности и целостности, HTTP для application-level диалога, CDN edges для geographic proximity, routers для packet forwarding, и browser render pipeline. Optimization работа означает знать какой слой доминирует каждый конкретный медленный запрос — round-trip elimination (cache hits, 0-RTT, edge compute) это highest-leverage move; round-trip shortening (CDN, multi-region) это следующее; всё inside round-trip (compression, parsing speed, smaller bundles) это третье. Operational frontier — distributed tracing с W3C Trace Context, USE/RED method-based instrumentation, error-budget-driven release cadence.
</KeyTakeaway>

## Главные выводы: что повторяется дальше

Глава 01 закрыта. Вы прошли всю сеть от keystroke к пикселям. Четыре нити проходят через каждый слой:

- **Encapsulation.** Каждый слой оборачивает предыдущий.
- **Multiplexing.** TCP/IP мультиплексируют много streams на одну трубу. HTTP/2 и /3 — много запросов на одно соединение.
- **Statefulness.** Соединения stateful — помнят sequence numbers, congestion windows, TLS keys, HTTP cookies. Это позволяет оптимизации вроде resumption и 0-RTT.
- **Latency.** Каждый round-trip, каждый handshake, каждый cache miss — стоимость. Архитектура — оптимизация против round-trip latency.
