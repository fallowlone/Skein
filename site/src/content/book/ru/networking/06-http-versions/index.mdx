TLS зашифровал байты. TCP пронумеровал. Теперь протокол сверху: HTTP — язык на котором браузеры и серверы говорят чтобы запрашивать и отдавать веб-страницы, API, картинки, шрифты, скрипты. Тридцать лет HTTP/1.1 обрабатывал почти весь трафик. Потом браузеры захотели больше: быстрее загружать страницы несмотря на высокую задержку. HTTP/1.1 не справлялся. Каждый запрос ждал предыдущий ответ. Даже с шестью параллельными соединениями ожидание оставалось проблемой. HTTP/2 и HTTP/3 атаковали bottleneck по-разному, но оба сходятся в одном механизме: <SpiralCue thread="multiplexing" lang="ru" /> — много запросов на одной линии без блокировки друг друга.

<Crux>Зачем каждая HTTP-версия существует, что меняла, и почему HOL-блокировка — главный враг.</Crux>

    <p><strong>Что делает HTTP одним предложением.</strong> Это request-response язык которым браузеры и серверы обмениваются веб-страницами, API, картинками — всем что вы видите в браузере.</p>
    <p><strong>Зачем разные версии.</strong> Протокол имеет три живые версии (1.1, 2, 3). Каждая пробует свой трюк чтобы загружать больше файлов за раз через одно соединение не блокируя друг друга. Какая лучше — зависит от сети: быстрые проводные линии не замечают разницы; мобильные и лоссовые — очень.</p>
    <p><strong>Метафора.</strong> Думайте о HTTP как об официанте принимающем заказы в ресторане. HTTP/1.1: один официант на стол, один заказ за раз — ждёте каждое блюдо до следующего заказа. Ресторан нанимает шесть официантов на клиента (шесть параллельных соединений). HTTP/2: один официант берёт десять заказов сразу и приносит блюда в порядке как кухня успеет. HTTP/3: то же что /2 но задержавшееся блюдо больше не задерживает остальные — они выходят независимо.</p>
    <p><strong>Диалог вслух.</strong> <PersonaTag id="bea" lang="ru" /> браузер серверу <PersonaTag id="sven" lang="ru" />: «GET /index.html». Дима отвечает HTML. Браузер делает <a href="/ru/networking/04-dns-resolution/">DNS</a>, <a href="/ru/networking/03-tcp-handshake/">TCP</a>, <a href="/ru/networking/05-tls-handshake/">TLS</a>, потом первый HTTP-запрос.     <p><strong>HTTP/1.1: pipelining и шесть соединений.</strong> HTTP/1.1 (RFC 9112) отправляет один запрос на TCP-соединение и ждёт полного ответа до следующего. Чтобы распараллелить, браузеры открывают 6-8 соединений к одному origin. Браузер загружающий страницу с 10 критическими JS открывает 6 соединений, отправляет один запрос на каждом, очередит оставшиеся 4. Pipelining (RFC 7230) позволял клиентам отправлять много запросов без ожидания ответов, но редко работал на практике: прокси ломали его.</p>
    <p><strong>HTTP/2: мультиплексирование на одном TCP.</strong> HTTP/2 (RFC 9113) отказывается от модели один-запрос-на-соединение. Вместо этого одно TCP-соединение несёт много параллельных «streams» — каждый stream независимая пара запрос-ответ. Кадры (frames) — единица: HEADERS-кадр открывает stream, DATA-кадры несут тело, RST_STREAM прерывает. Сервер чередует ответы. HPACK (RFC 7541) сжимает заголовки — повторные запросы используют дельты. Server Push (теперь удалён) пытался pre-emptively отправлять ресурсы.</p>
    <p><strong>HTTP/3: QUIC и stream-level потери.</strong> HTTP/3 (RFC 9114) переключает транспорт с TCP на QUIC (RFC 9000) — протокол на UDP с congestion control, reliability, миграцией соединений. Большая победа: QUIC streams независимы на уровне восстановления потерь. В HTTP/2 одна потерянная TCP-пакет тормозит весь поток байтов; в HTTP/3 каждый QUIC stream имеет свой loss recovery, потеря одного потока не блокирует другие. HTTP/3 также использует QPACK (RFC 9204) вместо HPACK — то же сжатие но разделяет dynamic state от stream ordering.</p>
    <p><strong>Стоимость соединения.</strong> Каждое соединение начинает холодно: TCP-рукопожатие (1 RTT), потом TLS 1.3 (1 RTT, или 0 при resumption). При RTT 100 мс новое соединение стоит 100-200 мс до первого байта. Шесть параллельных в HTTP/1.1 = шесть холодных рукопожатий. HTTP/2 и /3 переиспользуют одно соединение. HTTP/3 добавил миграцию соединений: при смене Wi-Fi → LTE соединение persist без re-handshake.</p>
    <p><strong>Методы, статус-коды, идемпотентность.</strong> HTTP определяет глаголы: GET (читать), POST (создать/неидемпотентно), PUT (идемпотентная замена), DELETE (идемпотентное удаление), PATCH (частичное), HEAD (только метаданные), OPTIONS (capabilities), CONNECT (туннель). Идемпотентные методы (GET, HEAD, PUT, DELETE, OPTIONS) могут безопасно повторяться. Неидемпотентные (POST, PATCH) НЕ должны автоповторяться без idempotency-key. Коды: 1xx info (100, 101, 103), 2xx success (200, 201, 204, 206), 3xx redirect (301, 302/307, 304), 4xx client (400, 401/403, 404, 409, 422, 429), 5xx server (500, 502, 503, 504).</p>
    <p><strong>Заголовки и условные запросы.</strong> Заголовки — пары имя/значение. Request: `User-Agent`, `Accept`/`Accept-Language`/`Accept-Encoding`, `Authorization`, `Cookie`, `Range`, `If-None-Match`, `If-Modified-Since`. Response: `Content-Type`, `Content-Length`, `Cache-Control`, `ETag`, `Set-Cookie`, `Strict-Transport-Security`, `Content-Security-Policy`. Условные запросы через `If-None-Match`/`ETag` позволяют 304 Not Modified — сервер отвечает пустым телом если кеш свежий.</p>
    <p><strong>Cookies, сессии и security-флаги.</strong> Cookies хранят клиентское состояние. Сервер устанавливает через `Set-Cookie: name=value; HttpOnly; Secure; SameSite=Strict; Max-Age=3600`. `HttpOnly` блокирует доступ JavaScript (защита от XSS). `Secure` только HTTPS. `SameSite=Strict|Lax|None` контролирует cross-origin. Современные браузеры дефолтят SameSite=Lax если директива отсутствует.</p>
    <p><strong>CORS.</strong> Браузеры enforce same-origin policy: скрипт на a.example.com не может читать ответы с b.example.com по умолчанию. CORS opt-in: сервер отвечает `Access-Control-Allow-Origin: https://a.example.com`. Preflight (OPTIONS) проверяет перед реальным запросом для non-simple методов/заголовков. `Allow-Origin: *` плюс credentials — security дыра.</p>
    <p><strong>Streaming, chunked, SSE.</strong> HTTP/1.1 поддерживает `Transfer-Encoding: chunked` для streaming без указания общей длины. HTTP/2 и /3 используют DATA-кадры нативно. Server-Sent Events (SSE, `Content-Type: text/event-stream`) — долгоживущий ответ доставляющий события server → browser. WebSockets (RFC 6455) начинают как HTTP и Upgrade до бинарного frame-протокола; HTTP/2-WebSockets через RFC 8441.</p>
    <p><strong>Сжатие.</strong> Серверы сжимают тела через `Content-Encoding: gzip|br|zstd`. Brotli сжимает на ~20% лучше gzip. Сжатие на encrypted content имеет security-импликации: CRIME и BREACH эксплуатировали HTTPS+compression. Статические ассеты сжимаются заранее на deploy; динамический контент per-request.</p>
    <p><strong>Content negotiation.</strong> Клиенты говорят `Accept: application/json, text/html;q=0.9` — JSON предпочтительно, HTML приемлемо. `Accept-Encoding: br, gzip`. Сервер выбирает что обоюдно поддерживается. Выбранный variant — через `Content-Type`. `Vary` заголовок ответа говорит кешам какие request-заголовки влияют на ответ.</p>
    <p><strong>Range-запросы.</strong> Клиент может запросить байт-range: `Range: bytes=500-999`; сервер отвечает 206 Partial Content. Включает HTTP-видео-стриминг, параллельные загрузки больших файлов, возобновление после disconnect. Браузеры и curl используют автоматически при дофетче. CDN-эджи обрабатывают range прозрачно.</p>
    <p><strong>Auth-схемы.</strong> Современные веб-приложения: `Authorization: Bearer <token>` с JWT или opaque token. Basic-auth выжил для внутренних API. OAuth 2.0 / OIDC определяют как токены получаются; HTTP их просто транспортирует. Скрытая опасность: токены в URL утекают через Referer.</p>
    <p><strong>HTTP/2 flow control и stream-limits.</strong> Каждое HTTP/2-соединение имеет connection-level и stream-level flow control через WINDOW_UPDATE кадры. Default 65535 байт на stream, расширяется до 16 MiB. SETTINGS_MAX_CONCURRENT_STREAMS ограничивает одновременные streams (типично 100).</p>
    <p><strong>HTTP rate limiting.</strong> Сервер возвращает `429 Too Many Requests` с `Retry-After: <seconds>`. Алгоритмы: token bucket, leaky bucket, fixed window, sliding window. CDN делают на edge; origin — defence in depth. Production: rate-limit по IP для анонимного трафика, по API key для аутентифицированного, exponential back-off на клиенте.</p>
    <p><strong>Trailers и gRPC.</strong> HTTP обычно кладёт метаданные в заголовки (до тела) но некоторые известны только после тела — checksums, gRPC статус. HTTP/1.1 поддерживает trailers через `Trailer:` заголовок, редко используется. HTTP/2 поддерживает trailers чисто как trailing HEADERS-кадр. gRPC зависит от trailers — каждый gRPC-вызов заканчивается `grpc-status` и `grpc-message` trailers.</p>
    <p><strong>Блок ошибочных представлений.</strong> Один: «HTTP/2 чинит HOL blocking». Ложь — мультиплексирует но TCP HOL остаётся на уровне пакетов; QUIC streams в /3 реально чинят. Два: «Server Push ускоряет загрузку». История — Push мёртв, Chrome убрал в 2022. Используйте `103 Early Hints` + `<link rel="preload">`. Три: «HTTPS только добавляет задержку». Ложь — HTTP/2 и /3 требуют TLS, 0-RTT часто быстрее plaintext HTTP/1.1 cold-start.</p>
    <p><strong>Pipelining в HTTP/1.1 — почему провалился.</strong> Pipelining (RFC 7230) разрешает отправить несколько запросов без ожидания ответов. В теории экономит RTT. На практике: (1) ответы должны возвращаться в порядке запросов — если запрос #1 медленный, все остальные тормозят (HOL blocking на application-уровне); (2) проксирующие серверы 90-х/00-х часто реализовывали pipelining неправильно — IE отключил по умолчанию; (3) идемпотентные ограничения (GET/HEAD only) сильно сужают полезность. Реальные браузеры открывали 6 параллельных соединений вместо.</p>
    <p><strong>HPACK дeтально.</strong> HPACK (RFC 7541) — алгоритм сжатия заголовков для HTTP/2. Использует две таблицы: статическую (предопределённые часто встречающиеся заголовки вроде `:method GET`, `content-type: text/html`) и динамическую (заголовки текущего соединения). Каждый заголовок кодируется либо индексом в таблице (1-2 байта), либо именем+значением с Huffman-сжатием. Типичный последующий запрос на тот же сервер: ~20-50 байт заголовков вместо 400+.</p>
    <p><strong>Frames структура HTTP/2.</strong> Каждый кадр имеет 9-байтный фиксированный заголовок: Length (24 бита, до 16 МБ), Type (8 бит), Flags (8 бит), R (1 бит зарезервирован), Stream ID (31 бит). Types: DATA, HEADERS, PRIORITY, RST_STREAM, SETTINGS, PUSH_PROMISE, PING, GOAWAY, WINDOW_UPDATE, CONTINUATION. Каждый stream имеет состояние state-machine (idle → reserved/open → half-closed → closed). RST_STREAM прерывает stream без закрытия всего соединения.</p>
    <p><strong>QUIC packet structure.</strong> QUIC пакеты идут поверх UDP. Каждый имеет header (long header при handshake, short header после — экономит байты), Packet Number, Frames. Frame types: STREAM (несёт application data), ACK (подтверждения), CONNECTION_CLOSE, RESET_STREAM, MAX_DATA (connection-level flow control), STREAM_BLOCKED. В отличие от TCP с одним sequence number per byte stream, QUIC нумерует пакеты independently от stream offsets — это и даёт независимое loss recovery per stream.</p>
    <p><strong>HTTP/3 over UDP — почему UDP.</strong> Эволюция TCP в ядре требует обновлений ОС — медленно, годы. QUIC реализуется в user space так что новые congestion control, миграция соединений, encryption-обновления внедряются с приложением (Chrome, mobile-app), не ожидая обновлений ОС. UDP — простой транспорт без semantics: QUIC реализует надёжность, ordering, congestion на нём. Цена: некоторые firewalls блокируют UDP/443 — Alt-Svc fallback на TCP-based HTTP/2.</p>
    <p><strong>HTTP/3 vs HTTP/2 deployment realities.</strong> Cloudflare включил HTTP/3 для всех клиентов в 2020. Google services (YouTube, Gmail) поддерживают с раньше. Большинство современных CDN (Fastly, AWS CloudFront, Akamai) теперь default HTTP/3. Enterprise networks часто блокируют UDP/443 как security policy — HTTP/3 откатывается на HTTP/2, пользователь не замечает. Major Operating Systems поддерживают QUIC в native networking-стеке (Linux msquic library, Windows native).</p>
    <p><strong>HTTP-семантика — что общего между версиями.</strong> RFC 9110 (HTTP Semantics) — отдельный документ описывающий концепции независимые от версии: методы, статус-коды, заголовки, content negotiation, кэширование, аутентификация. RFC 9111 — HTTP Caching. Версия-specific RFC только описывает framing-протокол. Это означает что 99% веб-разработки относится к концепциям RFC 9110/9111 — версия определяет производительность не функциональность.</p>
    <p><strong>Conditional GET и валидация кеша.</strong> Когда кеш содержит запись но запись истекла (max-age прошёл), отправляется conditional GET. Если ETag совпадает или Last-Modified не изменилось, сервер отвечает 304 Not Modified пустым телом, кеш обновляет timestamp и переиспользует тело. Экономит bandwidth, не RTT — соединение всё равно нужно. Strong vs weak ETag: `"abc123"` strong (бит-в-бит идентичны), `W/"abc123"` weak (semantically equivalent — например ответ с разным timestamp но тем же контентом).</p>
    <p><strong>HTTP authentication schemes.</strong> Basic Auth: `Authorization: Basic <base64(user:pass)>` — небезопасно без HTTPS. Digest Auth (RFC 7616): хэш-based, более безопасный но complex; редко используется сейчас. Bearer (OAuth 2.0): `Authorization: Bearer <token>` — JWT или opaque token. mTLS: client certificate в TLS handshake, без HTTP-уровня auth. API keys: custom header вроде `X-API-Key`. Современные системы используют OAuth 2.0 + OIDC для пользовательских flows, mTLS для service-to-service.</p>
    <p><strong>Connection vs request lifecycle.</strong> В HTTP/1.1 connection lifecycle: TCP-handshake → TLS handshake → keep-alive держит соединение → серия запросов → close. Каждый запрос завершается до следующего. В HTTP/2: одно соединение, много параллельных streams в любой момент. В HTTP/3: то же что /2 но с миграцией соединений. Implication для приложения: connection pooling в библиотеках клиентов (axios, fetch, requests-python) должен балансировать между переиспользованием и тайм-аут idle-соединений.</p>
    <p><strong>WebSocket vs SSE vs gRPC vs WebTransport.</strong> WebSocket: bidirectional, бинарный, любой trafic. SSE (Server-Sent Events): one-way server-to-client, текстовый, простое API. gRPC: RPC с строгой типизацией через ProtoBuf, бинарный, требует HTTP/2. WebTransport: WebSocket-replacement для HTTP/3, и reliable streams и unreliable datagrams. Выбор: SSE для простого server-push notifications, WebSocket для interactive bidi, gRPC для service-to-service RPC, WebTransport для real-time games.</p>
    <p><strong>Production routing patterns.</strong> Современная архитектура: пользователь → CDN edge → API Gateway (rate limit, auth) → BFF (Backend-for-Frontend, агрегирует) → микросервисы. Каждый hop может быть HTTP/1.1 или /2 или /3 — но обычно user-facing edge на /3 или /2, внутренние сервисы на /2 (gRPC). Tracing проходит через все hops через `traceparent` заголовок (W3C Trace Context). Logging на каждом уровне записывает метаданные запроса.</p>
    <p><strong>HTTP/2 + TLS вместе.</strong> RFC 9113 не требует TLS но все браузеры запускают HTTP/2 только over TLS. Это историческое решение: невидимое обновление протокола стало возможным потому что middlebox не вмешиваются в encrypted traffic. Plain HTTP/2 (h2c, HTTP/2 cleartext) технически возможен — используется в internal service-mesh trafic где TLS избыточен.</p>
    <p><strong>Долговечность HTTP/1.1.</strong> Несмотря на HTTP/2 и /3, HTTP/1.1 не умирает. Используется: для совместимости со старым browsers/clients, в internal service-mesh trafic где simplicity важна, в legacy API/proxy serv, в IoT-устройствах с минимальным CPU/память. HTTP/1.1 — universal lingua franca; любой stack может говорить им. HTTP/2/3 требуют более сложных libraries.</p>
    <p><strong>Content-Type matters.</strong> Сервер ответ должен правильно указывать Content-Type: application/json для API, text/html для страниц, application/octet-stream для downloads, image/webp для изображений. Неправильный type ломает рендеринг (HTML отображается как текст, JSON парсится неудачно). Charset (charset=utf-8) обязателен для текстовых форматов. MIME type sniffing — browser fallback когда type incorrect или missing — security риск; современные browsers блокируют через `X-Content-Type-Options: nosniff`.</p>
    <p><strong>Versioning APIs.</strong> Три подхода: URL path (`/v1/users`, `/v2/users`), query parameter (`?version=2`), Accept header (`Accept: application/vnd.api+json;version=2`). URL path самый явный, легко кешируется. Query parameter простой но мешает кешированию (Vary). Header более RESTful, требует более сложной маршрутизации. Production API обычно URL path для major versions + headers для minor changes.</p>
    <p><strong>HTTP-redirects и SEO.</strong> 301 Permanent Redirect — поисковые движки переносят rank на новый URL; 302 Temporary — rank остаётся на старом. 307/308 (RFC 7538) — то же что 301/302 но сохраняют method (POST остаётся POST). Цепочки redirects тратят RTT — каждый redirect требует отдельного запроса. Best practice — direct redirect без промежуточных hops. Сервер должен установить полный URL в Location header, не relative path.</p>

    <p><strong>Head-of-line blocking на TCP-уровне.</strong> Враг HTTP/2 не его дизайн, а контракт TCP: TCP гарантирует доставку в порядке. Пакет с байтами 1000-1099 потерян. TCP держит байты 1100-1199 в буфере ожидая потерянный. Только после пересылки 1100+ доставляются приложению. На HTTP-уровне если stream #1 использует байты 1000-1099 а stream #2 байты 1100-1199, оба stream-а встают. Поэтому high-loss линии (cellular, satellite) страдают под HTTP/2: одна потеря тормозит ВСЕ streams. RTT × loss rate — метрика; при 1% loss и 100 мс RTT ожидайте одно событие потери на 100 запросов, замораживающее всё соединение на 100 мс.</p>
    <p><strong>Независимость QUIC streams.</strong> QUIC нумерует пакеты, не байты. Пакет N содержит кадры из streams A, B, C. Если пакет N потерян, QUIC пересылает только кадры из streams чьи данные были в пакете. Если кадр stream A был в N, stream A пересылается; streams B и C продолжают отправлять. Цена: QUIC-кадры добавляют overhead (каждый имеет stream ID и offset), и приложение должно буферизовать out-of-order кадры. Но выигрыш огромен на лоссовых линиях: потеря больше не глобальное событие; она scoped к stream.</p>
    <p><strong>HPACK vs QPACK.</strong> HPACK (RFC 7541) использует dynamic table индексированный (name, value) парами. Если первый запрос отправляет «user-agent: Mozilla», второй может ссылаться 1-байтным индексом. Но dynamic table упорядочен; если индекс 60 добавлен и HEADERS-кадр ссылающийся 60 потерян, последующие HEADERS не могут декодировать 60 до пересылки. QPACK (RFC 9204) разделяет dynamic table от stream-encoding: «заблокированный» stream ждёт только свой HEADERS, не предыдущие.</p>
    <p><strong>Механизм Server Push и его провал.</strong> HTTP/2 Server Push (RFC 7540 §8.2) позволяет серверу отправлять PUSH_PROMISE-кадры объявляющие stream который сервер пришлёт без запроса клиента. Например GET /index.html подстрекает сервер PUSH_PROMISE /style.css. Браузер может отклонить (RST_STREAM) если уже закеширован. В теории Push экономит RTT. На практике: (а) сервер не знает что закешировано — слепо шлёт, теряя полосу; (б) Push работает только на первой навигации; (в) Middlebox и CDN плохо обрабатывают Push. К 2022 использование незначительно, Chrome убрал, RFC 9113 deprecated.</p>
    <p><strong>Congestion control в QUIC.</strong> TCP имеет congestion control в ядре (Reno, BBR, CUBIC). QUIC реализует в userspace, per-application. Это и сила и слабость: приложение может тюнить алгоритм per-connection, но цена — CPU. Некоторые реализации используют TCP cwnd; другие custom logic. На большом масштабе (CDN, cloud providers) per-connection congestion control более гибок но добавляет monitoring complexity.</p>
    <p><strong>HTTP version negotiation.</strong> ALPN (RFC 7301) — TLS-расширение: во время TLS handshake клиент рекламирует поддерживаемые протоколы (["h2", "http/1.1"]), сервер выбирает. Для HTTP/3 QUIC несёт свой protocol negotiation. Браузер сначала пробует HTTP/3, если сервер не поддерживает (QUIC заблокирован firewall) — откат на /2 или /1.1. Откат невидим для пользователя но операторы должны мониторить: если 30% запросов откатываются на /1.1 — firewall блокирует UDP/QUIC.</p>
    <p><strong>Развёртывание.</strong> HTTP/2 повсеместно (&gt;95% трафика). HTTP/3 растёт: ~30-40% веб-трафика по Cloudflare-отчётам в 2024, но варьируется по регионам и use-case. Мобильные сети медленнее обновляются; enterprise firewalls часто блокируют UDP, форсируя откат на HTTP/2. Для greenfield (новые API, edge compute) HTTP/3 default.</p>
    <p><strong>RFC 9218: extensible priorities.</strong> Оригинальная HTTP/2 priority scheme (dependency trees с весами) была сложна и редко реализовывалась правильно. Cloudflare сообщил что браузеры и серверы расходились настолько что приоритеты иногда ухудшали производительность. RFC 9218 deprecated tree-based scheme в HTTP/2 и определяет более простую сигнализацию: клиенты отправляют `Priority` header с `u=<urgency 0-7>` и `i` (incremental). Меньший urgency = важнее. Браузер подсказывает «u=0, i» для HTML, «u=3» для стилей, «u=5» для шрифтов и async-скриптов.</p>
    <p><strong>MASQUE и QUIC datagram (RFC 9221).</strong> MASQUE — семейство IETF-черновиков позволяющих клиенту туннелировать произвольные соединения через HTTP/3-сервер. Соединение инициирует CONNECT-UDP или CONNECT-IP запрос. Apple iCloud Private Relay использует MASQUE: трафик идёт Apple-сервер-1 (TLS-туннель) → Apple-сервер-2 (расшифрован) → origin, разделяя доверие между двумя провайдерами. QUIC datagram-кадры (RFC 9221) доставляют ненадёжные encrypted UDP-like payload внутри QUIC-соединения — для real-time медиа (WebTransport, RTC).</p>
    <p><strong>HTTP/3 fallback mechanics.</strong> Браузер не может просто попробовать HTTP/3 первым потому что QUIC-пакеты идут по UDP который многие corporate firewalls дропают. Два пути обнаружения: `Alt-Svc: h3=":443"` заголовок на HTTP/1.1 или /2 ответе говорит «в следующий раз попробуй HTTP/3 здесь»; HTTPS / SVCB DNS-записи (RFC 9460) рекламируют поддержку до соединения. При первой навигации браузер использует TCP-based /1.1 или /2, учится про /3 через Alt-Svc, потом пробует /3 на последующих.</p>
    <p><strong>0-RTT в HTTP/3.</strong> QUIC наследует TLS 1.3 0-RTT resumption: если у клиента закеширован session ticket, первый QUIC-пакет несёт данные приложения (HTTP-запрос) рядом с handshake. Экономия 1 RTT — значимо на межконтинентальных линиях. Та же оговорка: replayable, серверы ДОЛЖНЫ honour 0-RTT только для идемпотентных методов. Современные стеки (h2o, nginx-quic) детектят non-safe методы в 0-RTT и отвечают `425 Too Early`.</p>
    <p><strong>Операционная наблюдаемость для HTTP/3.</strong> Ключевые сигналы: ALPN distribution (% h3 vs h2 vs http/1.1), HTTP/3 → HTTP/2 fallback rate (UDP-blocking middleboxes), QUIC packet retransmission rate, count миграций (cell-Wi-Fi handovers), 0-RTT acceptance rate. Cloudflare qlog (per-connection JSON-дамп QUIC-событий) — инструмент deep-debug; production — Prometheus/OTel экспортёры.</p>
    <p><strong>WebSockets, WebTransport, gRPC.</strong> WebSockets (RFC 6455) начинают как HTTP/1.1 и Upgrade-ятся в бинарный frame-протокол; с HTTP/2 едут на RFC 8441 (extended CONNECT). WebTransport (W3C, RFC 9298-ish) — современная замена WebSockets на HTTP/3, выставляющая JavaScript и надёжные streams и ненадёжные datagrams. gRPC слоится на HTTP/2 (бинарный framing, мультиплексированные RPC); gRPC-Web транслирует для браузеров которые не могут говорить raw HTTP/2 trailers.</p>
    <p><strong>HTTP semantic correctness pitfalls.</strong> Использование 200 OK для возврата ошибки в JSON-теле обходит HTTP-машинерию — прокси повторяют, кеши хранят, браузеры не показывают error UI. Выбирайте правильный 4xx/5xx. Возврат 304 Not Modified без matching ETag ломает браузеры. `Vary: Authorization` обязателен на cacheable ответах различающихся для logged-in пользователей, иначе CDN-кеши утекают между пользователями. `Cache-Control: private` ограничивает браузерным кешем, блокирует CDN.</p>
    <p><strong>Connection coalescing в HTTP/2 и /3.</strong> Несколько origins с одним IP и сертификатом (cdn.example.com и api.example.com на одном edge cert) могут делить одно HTTP/2 или /3 соединение — экономит handshake. Chrome и Firefox делают это когда SAN-лист cert покрывает оба имени.</p>
    <p><strong>HTTP/3 DATAGRAM + WebTransport детали.</strong> DATAGRAM-кадр в QUIC несёт unreliable encrypted payload — могут быть дропнуты, протокол не пересылает. WebTransport выставляет браузерному JavaScript и reliable streams и unreliable datagrams через WebTransport API; подходит для game state где пересылка хуже потери, или VoIP-аудио где запоздалое аудио хуже отсутствующего. API зеркалит WebSocket send/receive но позволяет выбрать надёжность per-канал.</p>
    <p><strong>Историческая эволюция.</strong> HTTP/0.9 (1991) — только GET, без заголовков, без статус-кодов, тело — HTML. HTTP/1.0 (1996) — заголовки, статус-коды, методы. HTTP/1.1 (1997, обновлён 2014) — keep-alive, host header, chunked encoding, pipelining. HTTP/2 (2015) — мультиплексирование, бинарный фрейминг, HPACK, Server Push. HTTP/3 (2022 как RFC 9114) — QUIC-транспорт, stream loss isolation, connection migration. Каждая большая версия решала проблему предыдущей; следующая (HTTP/4?) пока без ясных мотиваций.</p>
    <p><strong>Browser implementation тонкости.</strong> Chrome использует свой движок Cronet для HTTP/3, портабельный на Android и Linux. Firefox использует Necko + neqo (QUIC implementation на Rust). Safari использует libquic-platform-specific. Все они реализуют ALPN selection, HTTP/3 fallback, Alt-Svc handling по-разному в деталях — но интерфейс протокола одинаков. Бенчмарки разных браузеров на одном сервере иногда различаются на 5-20% из-за этих деталей implementation.</p>
    <p><strong>gRPC и его специфика.</strong> gRPC — RPC-framework Google использующий HTTP/2 как транспорт. Бинарный protocol-encoding (Protocol Buffers), мультиплексирование multiple RPC через streams, server-streaming/client-streaming/bidi-streaming. Используется extensively в Google internal services и многими open-source проектами (Kubernetes, etcd, Envoy). gRPC-Web даёт ограниченную поддержку браузерам через прокси (Envoy gRPC-Web filter) — браузеры не могут читать HTTP/2 trailers напрямую.</p>
    <p><strong>QPACK encoder/decoder streams.</strong> В QPACK динамическая таблица обновляется через выделенный unidirectional encoder stream. Decoder stream используется для acknowledgement обновлений и сообщений о cancellation. Если HEADERS-кадр ссылается на entry динамической таблицы которая ещё не получена, stream «blocked» — ожидает encoder updates. Чтобы избежать stalls, encoder может либо использовать только static-table references, либо ждать ack перед dynamic-references.</p>
    <p><strong>Performance comparison real-world.</strong> Web.dev и WPO-stats регулярно публикуют benchmarks. Общий паттерн: HTTP/3 даёт 5-15% улучшение Largest Contentful Paint на мобильных сетях с потерями; марginal или negative effect на wired сетях с низкой задержкой и без потерь. Effect на initial connect-time меньше — оба HTTP/2 и HTTP/3 экономят на handshake-ах через resumption и connection-reuse.</p>
    <p><strong>QUIC implementations landscape.</strong> Cloudflare quiche (Rust). Google quiche (C++, основа Chromium). msquic (Microsoft C). nginx-quic (C, ставший mainline nginx). neqo (Mozilla Rust). lsquic (LiteSpeed). picoquic (academic). aioquic (Python). Каждая имеет небольшие различия в реализации деталей RFC 9000/9001/9114; interop-тесты проводятся регулярно на IETF-events чтобы обеспечить совместимость.</p>
    <p><strong>Будущее HTTP.</strong> RFC 9110/9111 — semantic layer, изменения редки. Framing-уровень (RFC 9112/9113/9114) — где идёт большая часть инноваций. HTTP/3 ещё разворачивается; HTTP/4 не на горизонте. Конкретные improvements: extensible priorities (RFC 9218, расширяет приоритизацию), Encrypted Client Hello (ECH, скрывает SNI), MASQUE/CONNECT-IP (туннелирование произвольного трафика). Веб-стандарты вокруг HTTP (CORS, Content-Security-Policy, Service Workers, WebTransport) эволюционируют быстрее самого протокола.</p>
    <p><strong>Тестирование и отладка HTTP.</strong> curl — стандартный инструмент, опции `-v` (verbose), `-i` (headers), `--http2-prior-knowledge`, `--http3-only`. wireshark/tshark — packet-level debug, расшифровывает TLS-traffic при наличии ключей. Chrome DevTools → Network — per-request timing, headers, body, response codes. nghttp/nghttp2 — HTTP/2 specific тестирование. h2load — load-testing для HTTP/2 и /3. Postman/Insomnia — interactive REST/GraphQL clients.</p>
    <p><strong>Service mesh и HTTP.</strong> Istio, Linkerd, Consul Connect — service-mesh решения внедряющие sidecar proxy (Envoy, linkerd2-proxy) рядом с каждым подом. Sidecar терминирует HTTP-трафик исходящий и входящий, добавляет mTLS, retries, circuit breakers, observability. Внутри service-mesh обычно HTTP/2 трафик с gRPC; user-facing edge может быть HTTP/3. Sidecar добавляет ~1 мс latency per hop но даёт сильные uniform контроль и observability.</p>
    <p><strong>API Gateways.</strong> Kong, Tyk, AWS API Gateway, Apigee, Azure API Management — sit между клиентами и backend сервисами. Функции: rate limiting, authentication (OAuth/JWT/API key), request transformation, response caching, request logging, version routing. Single point of policy enforcement vs distributed (sidecar) — обе модели валидны. API Gateway упрощает small teams; service mesh лучше для distributed teams ownership-ом каждого сервиса.</p>
    <p><strong>HTTP-level отладка прод-инцидентов.</strong> При user-facing проблемах первые шаги: проверить status codes в logs (5xx = server bug, 4xx = client/auth, 2xx с медленностью = latency issue). p95/p99 latency per endpoint. Error rate по region/POP. ALPN distribution для проверки протокола. Если возможно — reproduce с curl или из RUM-данных. Подключение error-tracking (Sentry, Datadog APM) к request-level метрикам даёт трассировку от пользователя до root cause.</p>
    <p><strong>Стандартизация процесса IETF.</strong> RFC создаются Internet Engineering Task Force через open process: Internet-Drafts → working group review → IESG approval → publication как RFC. HTTP Working Group отвечает за все HTTP-related RFCs. QUIC Working Group отвечает за QUIC. Процесс медленный (годы), но даёт высокое качество и interoperability. Дискуссии в mailing lists публичны; кто угодно может submit drafts. Совместимость между реализациями обеспечивается через interop-testing на регулярных IETF events.</p>

<Misconception
  id="r-h2-tcp-block"
  title="Внимание: HTTP/2 не чинит TCP HOL"
>
HTTP/2 мультиплексирует на application-уровне, но один потерянный TCP-пакет тормозит ВСЕ HTTP/2 streams на этом соединении. Только HTTP/3 над QUIC даёт настоящую stream-level loss isolation.
</Misconception>

Каждая HTTP-версия решала проблему своей эпохи. HTTP/1.1 добавил Keep-Alive для переиспользования соединений. HTTP/2 добавил мультиплексирование чтобы убрать six-connection-workaround. HTTP/3 добавил transport-level loss isolation для побед на лоссовых сетях. Как fullstack-инженер должен знать trade-off: HTTP/1.1 жив (старые клиенты, некоторые прокси); HTTP/2 default на современных серверах; HTTP/3 — будущее но ещё не вытеснил /2.

<KeyTakeaway title="Главное">
HTTP/1.1 мультиплексирует открытием шести TCP-соединений; HTTP/2 мультиплексирует streams над одним TCP (но TCP head-of-line blocking всё ещё бьёт под потерей); HTTP/3 переходит на QUIC над UDP и изолирует потерю до отдельных streams плюс добавляет миграцию соединений для mobile. Над протокольным слоем заголовки — Cache-Control, Authorization, CORS, SameSite cookies, ETag, Priority — где живут большинство операционных багов и большинство security-побед или потерь. Production HTTP 2026 означает serve все три версии, выбор per-connection через ALPN, и мониторинг HTTP/3 fallback rate как leading indicator здоровья сетевого пути.
</KeyTakeaway>
