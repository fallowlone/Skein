Первые три фрагмента этого pillar обсуждали *что записывать* — логи, метрики, трейсы — и *как их доставлять* через OpenTelemetry. Этот фрагмент отвечает на следующий, более острый вопрос: *в какие числа смотреть, когда сработал пейджер?* Неверный ответ — «во все». Правильный ответ — два коротких чек-листа, написанных двумя инженерами с разрывом в два года, которые вместе покрывают и сервис, к которому обращается пользователь, и ресурсы, на которых этот сервис стоит.

<Crux>RED = Rate, Errors, Duration (сервисы). USE = Utilization, Saturation, Errors (ресурсы). Два чек-листа, без споров.</Crux>

Ментальная модель послойная. Пользователь отправляет запрос в сервис. RED говорит, что *он* испытал: сколько запросов пришло, сколько упало и сколько по времени заняли выжившие. Если RED болеет — болеет пользователь. USE говорит, что в это окно происходило с нижележащими ресурсами — CPU, памятью, диском, сетью, локами. Если USE болеет на одной из машин — это кандидат на причину. Рефлекс senior-инженера в инциденте — не «открыть все дашборды», а «RED показывает симптом, USE показывает причину, а четыре golden signals из Google SRE Book склеивают их вместе». Всё остальное — объём логов, выборки трейсов, профили — это глубокая диагностика после того, как два чек-листа сузили область поиска.

    <p><strong>Что это в одном предложении.</strong> RED и USE — два коротких чек-листа, которые говорят, какие числа важны, когда система ломается: RED — для сервиса, к которому обращается пользователь, USE — для машин, на которых сервис работает.</p>
    <p><strong>Зачем это нужно.</strong> Когда что-то горит, у тебя есть секунды, чтобы найти нужный дашборд. RED и USE сжимают тысячи возможных метрик до шести заголовков, которые почти всегда подсказывают, куда смотреть первым.</p>
    <p><strong>Метафора.</strong> Представь больницу. RED — это жизненные показатели пациента: пульс, давление, температура — измеряемые снаружи. USE — это мониторинг каждой машины интенсивной терапии: расход кислорода, давление насоса, лампочки ошибок — измеряемые на самом оборудовании. Нужны оба. Врачи, которые смотрят только на одно, пропускают очевидные проблемы; дисциплина — пробегать оба чек-листа по порядку, каждый раз.</p>

  <Fragment slot="middle">
    <p><strong>Происхождение и определения.</strong> Метод USE назвал Brendan Gregg в 2012 как чек-лист для экстренной диагностики производительности: для каждого ресурса проверь utilization, saturation, errors. Utilization — средний процент времени, когда ресурс был занят. Saturation — степень очередной работы, которую ресурс ещё не успел обслужить, — измеряется как глубина очереди, длина run queue, время ожидания. Errors — счётчик ошибочных событий на ресурсе. Идея Gregg: 80% реальных performance-багов ловятся обходом таблицы из 30 ячеек (ресурс × U/S/E), ещё до того, как берёшь умные профайлеры. Метод исходит из того, что у любого компьютера можно перечислить небольшой фиксированный набор ресурсов — CPU, память, сеть, storage I/O, контроллеры, interconnect, а на стороне софта mutex-локи, thread pool'ы, file descriptor'ы — и каждый из них может болеть только тремя способами.</p>
    <p><strong>RED — двойник со стороны сервиса.</strong> Tom Wilkie представил RED на London Prometheus meetup в 2015 году, когда работал в Weaveworks; подробности опубликованы в блоге Grafana. Три метрики RED — Rate (запросов в секунду), Errors (упавших запросов в секунду или как ratio), Duration (распределение задержки успешных запросов) — эмитируются каждым сервисом в микросервисной архитектуре одинаковым образом, поэтому единый шаблон дашборда покрывает всю инфраструктуру. Мотивация Wilkie: метод USE «не очень применим к сервисам» — сервис не ресурс, и то, что чувствуют его клиенты, — это не utilization. RED request-центричен, USE — resource-центричен; вместе они позволяют рассуждать о обеих половинах системы из одной ментальной модели.</p>
    <p><strong>Четыре golden signals из Google SRE Book.</strong> Идейно они старше, чем RED и USE, но в книжной форме опубликованы позже. Глава по мониторингу распределённых систем называет четыре сигнала: Latency, Traffic, Errors, Saturation. Latency — время ответа на запрос; Traffic — частота запросов (или глубина очереди, или активные сессии — system-specific); Errors — частота упавших запросов; Saturation — «насколько полна» система относительно известного предела. Заметь пересечение: Latency = Duration, Traffic = Rate, Errors = Errors. Новинка — Saturation, который книга SRE специально добавляет на уровне сервиса, не только ресурса: у сервисов есть логические лимиты (длина очереди, in-flight count), которые важны даже когда ни одна машина не на 100%. Многие production-команды трактуют RED + Saturation как практическую эволюцию сигналов из книги SRE.</p>
    <p><strong>Инструментирование RED в Prometheus.</strong> Каноническая форма: три метрики на HTTP-сервис, именованные единообразно. <code>http_requests_total</code> как counter с label <code>method</code>, <code>route</code>, <code>status</code>. <code>http_request_errors_total</code> — выборка <code>status=~"5.."</code> (или отдельный server-classified error label). <code>http_request_duration_seconds</code> как histogram с bucket'ами 5, 10, 25, 50, 100, 250, 500, 1000, 2500, 5000, 10000 миллисекунд (типичные web-buckets). Rate — <code>rate(http_requests_total[5m])</code>; error rate — <code>rate(http_request_errors_total[5m]) / rate(http_requests_total[5m])</code>; перцентили — <code>histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))</code>. Каждый сервис эмитирует это трио; один шаблон дашборда рендерит каждый сервис.</p>
    <p><strong>Инструментирование USE на Linux.</strong> CPU utilization: <code>vmstat 1</code> или <code>node_cpu_seconds_total</code> из node_exporter; saturation: длина run queue через колонку <code>r</code> в <code>vmstat</code> или Pressure Stall Information ядра по <code>/proc/pressure/cpu</code> (ядро ≥ 4.20). Память utilization: <code>node_memory_MemAvailable_bytes</code>; saturation: page-in / page-out через колонки <code>si</code> / <code>so</code> в <code>vmstat</code> или <code>/proc/pressure/memory</code>. Disk I/O utilization: <code>%util</code> в <code>iostat</code>; saturation: средняя глубина очереди (<code>avgqu-sz</code>). Сеть: utilization через <code>ifconfig</code> или счётчики <code>node_network_*</code>; saturation — NIC ring-buffer drops и TCP retransmits. Errors: ECC, ошибки линка, dropped packets, ENOSPC, EIO. PSI-файлы в современном Linux дают одно число на ресурс — «какой процент wall-clock-времени задачи были застопорены на этом ресурсе» — для инцидент-ответа это золото, потому что это saturation-сигнал в форме, по которой можно алертить напрямую.</p>
    <p><strong>Histogram vs среднее.</strong> Duration в RED обязан быть histogram, никогда не среднее. Среднее прячет всё: сервис с 99% запросов по 50мс и 1% по 5000мс имеет ту же среднюю задержку (~100мс), что и сервис со всеми запросами по 100мс; первый убивает пользователей на ретраях, второй нет. <code>histogram_quantile</code> в Prometheus читает счётчики bucket'ов и оценивает перцентиль линейной интерполяцией между соседними bucket'ами. Оценка хороша настолько, насколько хороши bucket'ы: если 99% трафика попадает в один bucket от 100мс до 500мс, твоя оценка p99 может быть где угодно в этом диапазоне. Выбирай bucket'ы так, чтобы плотно обхватить целевую SLO с обеих сторон. Типичная ошибка: оставить дефолт клиентской библиотеки Prometheus <code>[0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10]</code> секунд для сервиса с SLO 200мс — почти весь трафик между 50мс и 250мс, у тебя один bucket покрывает (100мс - 250мс), и p99 нечитаем. Production-уровень: 10-15 bucket'ов, плотнее всего около SLO.</p>
    <p><strong>Сшивка через четыре golden signals.</strong> Senior-дашборд для любого сервиса держит три панели RED сверху (Rate, Errors, Duration с p50/p95/p99-линиями), а ниже под каждой — соответствующую USE-панель для ресурсов, на которые этот сервис опирается. Для типичного HTTP-сервиса это значит: CPU utilization + saturation (PSI) по его боксам, память utilization + saturation по тем же боксам, сеть utilization + retransmits по NIC, время ответа и error rate downstream-БД (USE на БД). Ритм чтения в инциденте — сверху вниз: какая RED-метрика дёрнулась, потом какая USE-строка совпадает по таймлайну. Четыре golden signals — это заголовки панелей; RED и USE — ячейки.</p>
    <p><strong>Что класть в label.</strong> RED-метрики маркируются тем, что actionable: <code>route</code> (шаблон URL, не полный URL), <code>method</code> (GET/POST/...), <code>status</code> (класс HTTP-статуса — 2xx/4xx/5xx, не обязательно точный код), идентификатор сервиса (обычно подкидывается мета-label при деплое). Запрещены: user ID, request ID, customer email, country code если он не маленький и не ограниченный, индивидуальные query string. Причина — cardinality, разобрана в failure mode ниже. USE-метрики маркируются идентичностью ресурса: какой CPU, какое устройство, какая NIC, какой thread pool. Они ограничены числом CPU / устройств, поэтому cardinality не проблема.</p>
    <p><strong>Как RED ведёт себя при отказах.</strong> Сервис, деградирующий постепенно, показывает Duration p99 ползущим вверх, пока p50 стоит на месте (медленный хвост растёт); сервис, упирающийся в жёсткий лимит, показывает Rate, плющащийся в потолок при продолжающемся входящем трафике (запросы либо дропаются на границе, либо очередь снаружи); сервис с логической ошибкой показывает Errors, скакнувший при стабильных Rate и Duration. Узор важен для диагностики: только Duration спайк со стабильными R и E обычно указывает на медленный downstream (БД, cache miss, пауза GC); Errors-спайк при стабильных R и D — на логический регресс или сдвиг входных данных; плато Rate при растущей Duration — на исчерпание capacity, сервис очередит.</p>
    <p><strong>Как USE ведёт себя при отказах.</strong> CPU-bound нагрузка показывает utilization, ползущий к 100%, и saturation (run-queue), растущую выше числа ядер — правильный сигнал, что scale out поможет. Утечка памяти показывает медленно растущий utilization с si/so в конце концов не-нулевым (swap-in / swap-out — saturation-сигнал). Disk-bound нагрузка показывает %util около 100% на одном или нескольких дисках и растущую очередь; network-bound — TCP retransmits, NIC drops или saturation на согласованной полосе. PSI «full» по памяти или I/O — самый production-friendly: если memory pressure full &gt; 0 более 10 секунд, у тебя почти наверняка memory crunch, даже если свободной RAM много (ядро трэшит reclaim).</p>
    <p><strong>Алертинг на RED и USE.</strong> Зрелый паттерн — алертить на user-facing симптомы (RED), а на внутренние сигналы причины (USE) — с меньшей severity для capacity planning. Page-grade алерт RED: p99 Duration &gt; SLO 5 минут, или Error rate &gt; 1% 2 минуты. Warning-grade алерт USE: PSI cpu some &gt; 20% 10 минут, или memory available &lt; 10% 5 минут, или диск &gt; 90% 5 минут. Разделение сделано намеренно. RED-алерты будят людей, потому что страдают пользователи. USE-алерты идут в более медленный канал (Slack, дашборды), чтобы capacity-команды планировали заранее, а не on-call просыпался каждый раз, когда CPU доходит до 70%. Привязка page-grade алертов к user impact ломает спираль alert fatigue, разрушающую on-call-смены; это один из сильнейших культурных рычагов в инцидент-prone командах.</p>
    <p><strong>RED + USE в service mesh.</strong> Service mesh (Envoy, Linkerd, Istio) эмитируют RED-метрики на sidecar без правки прикладного кода — это и удешевляет старт, и даёт единый шаблон между сервисами. Минус — sidecar видит только то, что видит сеть; ошибка приложения, отдающего неверный, но 2xx-ответ, для mesh невидима. Зрелые деплои гоняют оба слоя — sidecar RED для широты и единообразия, application-emitted RED для бизнес-логики (например, payment-success counter, маркированный gateway, — только app). Держи label'ы согласованными в обоих слоях, чтобы дашборды собирались по join'у.</p>
    <p><strong>Где RED ломается без помощи.</strong> RED предполагает понятную границу «запрос» с конечным временем. На async и batch-нагрузках понятие запроса размыто: у event-driven воркера Rate — это потребление сообщений, Duration — wall-clock на сообщение, Errors — dead-letter rate, но всё ещё нет понятия user-impact из чистого RED. Здесь возвращается четвёртый golden signal — Saturation на уровне сервиса: глубина очереди, in-flight количество, отставание consumer'а от producer'а. Зрелые async-сервисы эмитируют отдельную метрику queue_depth_seconds (сколько wall-clock ждёт сообщение перед обработкой) — это саrтурация RED для очередей, без которой Duration p99 говорит только о работе обработчика, но не о том, сколько user реально ждёт от publish до consume. Тот же принцип — для batch-job'ов: RED описывает обработку одного job'а, а Saturation описывает backlog, и оба нужны. Без этого пейджер по «нормальной» Duration придёт, когда backlog уже превратил минуту обработки в час ожидания пользователя.</p>

    <p><strong>Cardinality как первоклассный драйвер стоимости.</strong> Каждое уникальное сочетание значений label на Prometheus-метрике создаёт отдельную time series, индексированную в TSDB head block по примерно 3 KB RAM каждая. Наивная RED-инструментация с label <code>user_id</code> в сервисе на 100k активных пользователей вырастает от пары сотен серий до нескольких сотен тысяч за часы; если метрика реплицирована между 50 инстансами, headcount превысит 5M серий и упадёт TSDB на 16-гигабайтовом сервере Prometheus. В hosted-бэкендах (Datadog, New Relic, Splunk, Chronosphere) счёт растёт линейно: при $0.05 за серию в месяц неограниченный user_id-label может добавить $5,000-50,000 ежемесячных затрат за ночь из-за одного небрежного label. Дисциплина железная: на метриках живут только label со связанной, низкой cardinality; всё остальное — в логах (high cardinality их естественная среда) и трейсах (которые сэмплируются). Route-шаблоны (не полные URL), классы HTTP-статуса (не точные коды), бакеты customer-сегментов (не customer ID) — правило. Если для одного запроса нужно точное значение — используй exemplars: механизм Prometheus, прикрепляющий выборочный trace ID к bucket'у histogram, и ходи по ссылке в tracing-бэкенд.</p>
    <p><strong>PSI — production-уровневый сигнал saturation.</strong> Linux Pressure Stall Information (ядро 4.20+, релиз декабрь 2018, Johannes Weiner из Facebook) выкладывает в <code>/proc/pressure/&#123;cpu,memory,io&#125;</code> по шесть строк на ресурс: «some» и «full» pressure, усреднённые за 10с, 60с, 300с. «some» — хотя бы одна задача стояла в ожидании; «full» — все не-idle задачи застопорены. Дизайн PSI закрыл давний разрыв в observability — до PSI давление приходилось выводить из load average, колонки r в vmstat, iowait, ни один из которых не масштабируется на много ядер и не ловит транзиентную saturation. Разрешение PSI — микросекунды, overhead меньше 1%. Production-использование: скрейпь <code>node_pressure_*</code> через node_exporter; алерть при <code>rate(node_pressure_cpu_waiting_seconds_total) &gt; 0.1</code> (10% времени стояли на CPU). Kubernetes использует PSI для решений OOMKill и приоритета Pod'ов. Apple, Facebook, Google гоняют PSI-driven autoscaler'ы внутри. PSI заменяет legacy-метрику load average в современных production-стеках по той же причине: PSI реально отвечает на вопрос «что-то застопорено», а load average — 1-минутное сглаженное смешение runnable и uninterruptible-задач, которое значит разное на разных ядрах.</p>
    <p><strong>Cross-protocol RED.</strong> Для HTTP RED очевиден. Для gRPC: Rate — RPC/сек, Errors — gRPC status &gt; 0 (любой не-OK), Duration — потоково-осведомлённая задержка ответа (first-byte для server-streaming, end-to-end для unary). Для очередей: Rate — сообщений-вход/сек + сообщений-выход/сек (consumed и produced — разные сигналы), Errors — dead-letter rate, Duration — время ожидания в очереди (publish до consume). Для batch-job'ов: Rate — job/мин, Errors — упавшие job'ы, Duration — wall-clock на job — и существенно, что Saturation тоже важна, потому что batch-системы очередят работу, а глубина очереди — критический сигнал, который чистый RED пропускает (именно поэтому golden signals добавляют Saturation обратно на уровне сервиса). Для event-driven serverless: Rate — invocations/сек, Errors — function-error rate плюс throttled-invocations, Duration включает cold-start tail (ведёт себя как медленный хвост и доминирует p99). Форма переносится; смыслы «запрос» и «ошибка» — нет.</p>
    <p><strong>Service mesh и auto-RED.</strong> Envoy, Linkerd, Istio и крупные data plane service mesh эмитируют RED-метрики автоматически на sidecar без изменений приложения. Метрики Envoy <code>http_downstream_rq_total</code>, <code>downstream_rq_xx</code>, <code>downstream_rq_time</code> дают Rate, Errors-по-статусу, Duration histogram на cluster + listener + virtual host, маркированные единообразно по всему flot'у. Преимущество: полиглот-инфраструктура (Node, Go, Python, JVM, Rust) получает один шаблон RED-дашборда, даже если языки расходятся в конвенциях Prometheus-клиента. Подвох: sidecar видит то, что видит сеть, а не то, что видит приложение — запрос, успешный на sidecar, но неверно обслуженный буговым кодом приложения, выглядит как 2xx в метриках mesh. Production-команды гоняют sidecar-RED для широты и per-service app-level RED для глубины, соединённые по тому же label route.</p>
    <p><strong>Стратегия bucket'ов histogram.</strong> Дефолт клиента Prometheus — 5мс, 10мс, 25мс, 50мс, 100мс, 250мс, 500мс, 1с, 2.5с, 5с, 10с — не подходит большинству сервисов. Для checkout-API с SLO 200мс bucket'ы должны быть плотнее около 200мс: например 25, 50, 100, 150, 200, 300, 500, 800, 1500, 3000 мс. Правило: минимум три bucket'а ниже SLO и три выше; отношение соседних bucket'ов ≤ 2x около SLO; верхний bucket — на уровне таймаута (не нужен 10с-bucket, если сервис таймаутит на 3с). Native histogram (Prometheus 2.40+) уменьшают проблему ручной настройки bucket'ов, эмитируя per-observation экспоненциальные bucket'ы фиксированной точности, отдавая немного места ради куда лучшей точности p99 без ручной конфигурации. Экспоненциальные histogram в OpenTelemetry работают так же и всё чаще становятся дефолтом в новых инструментациях.</p>
    <p><strong>Связка с error budget.</strong> Errors и Duration в RED вместе питают SLO и его error budget. SLO 99.9% availability за 30 дней допускает 43.2 минуты «упавших»; SLO 200мс-p99 за 30 дней допускает 0.1% запросов выше 200мс. Error budget — то, что осталось: минуты, запросы. Глава по SLO в этом pillar (фрагмент 05) показывает формулы, шаблон burn-rate-алертинга (multi-window, multi-burn-rate) и культурно-инженерную сторону. Здесь — главное: RED — субстрат, на котором стоит SLO. Без инструментации RED у тебя нет SLO; у тебя есть пожелание.</p>
    <p><strong>Самосоотносимая observability.</strong> Prometheus сам эмитирует RED и USE — для Prometheus-сервера длительность скрейпа — это RED-Duration, неудачные скрейпы — RED-Errors, частота ингеста — RED-Rate, давление на запись хранилища — USE-Saturation на нижележащий диск. Мониторить монитор важно, потому что cardinality-инциденты обычно невидимы для затронутого сервиса (его метрики продолжают копиться, но Prometheus, который их тянет, тормозит). Алерть на собственный scrape Duration p99 &gt; 1с, на скорость роста TSDB head series, на длительность rule-evaluation. Та же логика — для OTel-коллекторов (эмитируют collector_exporter_send_failed_total, otelcol_processor_dropped_metric_points) и для логирующего слоя (Fluent Bit, Vector со своим RED). В зрелом стеке каждый слой observability сам observed; на onboarding'е новых senior'ов есть пункт «и как мы понимаем, что мониторинг работает». Режим коллапса неотслеживаемого мониторингового слоя — худший вид silent failure.</p>
    <p><strong>Безопасность: label'ы могут утекать.</strong> Наивный Errors-counter с label <code>error_message</code> или <code>stack_trace</code> публикует текст исключения в metrics scrape, который часто access-контролирован слабее, чем БД приложения. Если в сообщении пользовательский ввод — «could not find user alice@example.com» — эта PII теперь в мониторинг-бэкенде, который читает вся инженерия. Дисциплина: label по <em>классу</em> ошибки (`auth_failed`, `db_timeout`, `parse_error`), никогда по <em>содержимому</em>. То же касается label `query`, `body`, `user_agent`: каждый может нести PII или секреты, каждый множит cardinality, каждый попадает в datastore с меньшим аудитом, чем источник. Аудитуй набор label как security-review item, а не только perf-review. Реальный инцидент: платёжный сервис в 2021 утекал номера телефонов клиентов через плохо названный label «failed_phone»; в postmortem ввели глобальный pre-commit hook, помечающий любой новый label с известным PII-паттерном в имени.</p>
    <p><strong>Сэмплинг vs агрегация.</strong> Histogram Duration в RED и PSI в USE предагрегированы — суммируют по всем запросам / всему wall-clock без сэмплинга. Трейсы — противоположность: сэмплируются (обычно 0.1-5%), потому что каждый трейс несёт полный путь запроса. Senior-паттерн: преагрегируй RED + USE на источнике, сэмплируй трейсы (head-based по стоимости, tail-based по полноте на медленных / ошибочных хвостах), а профили (continuous profiling через Parca, Pyroscope, Datadog) держи с гораздо более жёстким сэмплингом (~1%), но всегда включёнными, чтобы медленный хвост можно было дотянуться. Агрегация даёт объём; сэмплинг — детали. Стек из четырёх pillar'ов — RED-метрики, USE-метрики, сэмплированные трейсы, сэмплированные профили — собирается только если они шарят trace ID и ключи label (route, service, status_class). Семантические конвенции OpenTelemetry формализуют это: <code>http.route</code>, <code>http.response.status_code</code>, <code>service.name</code> — ключи join'а; использование их единообразно через логи / метрики / трейсы — то, что делает стек юзабельным.</p>
    <p><strong>Реальные production-падения.</strong> Cloudflare 2022: глобальный outage предварил OOM серверов Prometheus от cardinality из-за нового label на метрике request_duration. Фикс прилетел за 90 минут, но postmortem обязал per-team cardinality-бюджет и CI-check, отбивающий новые label-dimension выше порога. GitHub 2023: SLO-алерт на latency code-search неоднократно срабатывал без действий, потому что алерт был на среднюю задержку, а не p99 — фикс бага, толкнувший p99 с 200мс до 800мс, едва сдвинул среднее. SLO переделали на multi-window p99 burn rate alert (короткое окно 1ч, длинное 6ч) по шаблону Google SRE workbook. Stripe 2024: воркер доставки webhook'ов стоял 11 минут, потому что у Postgres-реплики, на которой он висел, PSI memory pressure (full) был 90% — невидимо на дашбордах free RAM, показывавших много свободной памяти, но ядро трэшило reclaim. Переход на PSI-алертинг поймал следующий инцидент за 30 секунд. Discord 2023: рефакторинг перенёс горячий label с одной метрики на две; cardinality удвоилась незаметно, и rule-evaluation latency Prometheus за две недели выросла с 100мс до 4с, маскируя задержки алертов на user-facing инцидент. Длительность rule-evaluation теперь first-class на их meta-monitoring дашборде.</p>
    <p><strong>Push vs pull, OTel-коллектор, exemplars.</strong> Pull-модель Prometheus предполагает, что цели адресуемы по сети, до которой Prometheus достанет; для коротко-живущих нагрузок (Lambda, batch-job'ы) push через Pushgateway или OTLP-push OpenTelemetry работает лучше. Паттерн коллектора (OTel Collector, Vector, Telegraf) разводит эмиссию и хранение: приложение эмитирует в локальный агент, агент батчит и роутит в бэкенды. Exemplars — выборочные trace ID, прикреплённые к bucket'ам histogram — мост между агрегированным RED и детальными трейсами: спайк p99 — это рост счётчика в bucket'е, и каждый bucket может нести trace ID, на который можно кликнуть в Grafana и увидеть полное дерево spans медленного запроса. Этот паттерн, формализованный в Prometheus 2.32+ и OTel 1.0+, устраняет «метрика говорит, что медленно, но примера у меня нет», определявший pre-exemplar эру.</p>
    <p><strong>Крупнее: почему два чек-листа выживают.</strong> RED и USE оба придуманы как <em>когнитивные протезы</em> для инженеров под давлением. Смысл не в том, что шесть метрик исчерпывающи — нет, — а в том, что они короткие, запоминающиеся и достаточно непересекающиеся, чтобы повести первые 30 секунд триажа в почти всегда правильную сторону. Saturation как четвёртый golden signal латает единственный пробел чистого RED. PSI в современных ядрах даёт USE более резкий сигнал saturation, чем был доступен, когда Brendan Gregg это писал. Service mesh раздаёт RED бесплатно на инфраслое. OpenTelemetry даёт ключи join, чтобы собрать RED + USE + трейсы + профили в одну навигируемую поверхность. Но когнитивная форма — симптом (RED) до причины (USE), оба до логов / трейсов / профилей — пятнадцать лет от роду на 2025-й и всё ещё несущая в инцидент-ответе каждого senior. Инструменты меняются; чек-лист — нет.</p>
