Фрагменты 01 и 02 задали словарь (три сигнала) и дисциплину структурного логирования. Этот фрагмент — про подложку, делающую всё это переносимым и композиционным: <em>OpenTelemetry</em>. OTel — не одна вещь, а четыре, наслоенные друг на друга: <em>API</em>, к которому обращается код приложения, <em>SDK</em>, превращающий вызовы API в записи телеметрии, <em>Collector</em>, обрабатывающий и маршрутизирующий эти записи, и <em>wire-формат (OTLP)</em>, переносящий их между всеми компонентами. Слойность — это суть: каждый кусок заменим, каждый говорит стабильный контракт, и вместе они дают инструментировать однажды и менять backend без правки кода приложения. После этого фрагмента ты должен уметь рисовать архитектуру по памяти, конфигурить рабочий Collector в 50 строках YAML и точно формулировать, какие решения залочивают тебя на вендора, а какие держат нейтральным.

<Crux>OTel = API + SDK + Collector + OTLP. Инструментируй один раз, маршрутизируй куда угодно — но только если edge говорит OTLP.</Crux>

Стратегическая ценность OTel — портабельность. До OTel каждый вендор поставлял проприетарный агент — `dd-trace` Datadog, агент New Relic, Java-agent AppDynamics — и смена вендора означала переписывание инструментации во всех сервисах. OTel — ответ CNCF: определить открытый API (так что код приложения никогда не импортит vendor-библиотеку), открытый SDK (так что runtime-цена одинакова на backend'ах), открытый wire-формат (так что любой может маршрутизироваться к любому), и Collector (так что policy и обработка живут вне приложения). В 2026 каждый крупный observability-вендор принимает OTLP — Datadog, New Relic, Honeycomb, Splunk, Grafana Cloud, Elastic, Dynatrace — это значит, что OTel — не ставка, а дефолт. Оставшиеся вопросы прагматичны: какой deployment-pattern, какая стратегия sampling, какой уровень auto-instrumentation и как избежать тонких vendor-lock-in escape-hatch, проскакивающих обратно через проприетарные processor'ы или non-OTLP-edge.

    <p><strong>Четыре части подробно.</strong> Архитектура OTel наслоена так, что каждый слой заменим. <em>API</em>: per-language публичные интерфейсы (Java <code>io.opentelemetry.api</code>, Python <code>opentelemetry.trace</code>, Go <code>go.opentelemetry.io/otel</code>). API — то, что вызывают код приложения и instrumentation-библиотеки. Он намеренно лёгкий — по умолчанию <em>ничего не делает</em>; no-op SDK — дефолтная реализация API. <em>SDK</em>: runtime-кусок, превращающий вызовы API в записи телеметрии. Владеет sampling-решениями (какие трейсы оставлять), агрегацией (как сворачивать metric-update'ы), батчингом (когда флашить в exporter) и сериализацией (в OTLP wire-формат). SDK устанавливает application owner, не library author — это разделение позволяет библиотеке инструментироваться OTel без насильного навязывания пользователю конкретного SDK. <em>Collector</em>: standalone-процесс (бинарь или контейнер), принимающий OTLP, прогоняющий конфигурируемые processor'ы и экспортящий в один или несколько backend'ов. Это policy-слой. <em>OTLP</em>: wire-формат — protobuf-кодированные сообщения по gRPC или HTTP, определены в OTel-спеке и стабильны через версии. Любая пара OTel-aware компонентов общается по OTLP.</p>
    <p><strong>Сигналы: traces, metrics, logs (и путь к profiles).</strong> OTel покрывает три типа сигналов в стабильной форме, у каждого свой API-поверхность, SDK-pipeline и OTLP-сообщение, но они делят общую концепцию Resource (per-emitter-атрибуты — service.name, host.name) и общий Trace-контекст (trace_id, span_id), чтобы cross-signal-корреляция работала. <em>Traces</em> — GA с 2021; рабочая лошадка, самая зрелая, понятна всем backend'ам. <em>Metrics</em> — GA с 2023; API поддерживает counter, gauge, histogram и exponential histogram (новый дефолт под high-resolution latency). <em>Logs</em> — GA для API в конце 2023, SDK в конце 2024; менее зрелые, но сходятся быстро — bridge-библиотеки («OTel log bridge» для slf4j, structlog, pino) позволяют существующему коду эмитить OTel-логи без переписывания. <em>Profiles</em> — в разработке (status: experimental в конце 2024 / 2025) как четвёртый сигнал; ожидаемый GA в 2026.</p>
    <p><strong>Semantic Conventions: общий словарь.</strong> Независимо от четырёх-частной архитектуры, OTel публикует <em>Semantic Conventions</em> — нормативный набор имён атрибутов под общие операции. <code>service.name</code>, <code>service.version</code>, <code>deployment.environment</code> — универсальные resource-атрибуты. <code>http.request.method</code>, <code>http.route</code>, <code>http.response.status_code</code>, <code>url.full</code> — HTTP. <code>db.system</code>, <code>db.operation</code>, <code>db.namespace</code> — базы данных. <code>messaging.system</code>, <code>messaging.destination.name</code>, <code>messaging.operation</code> — очереди. Это join-ключи, делающие metric-, log- и trace-корреляцию возможной. Принятие Semantic Conventions — самая высокоэффективная дисциплина в OTel; SDK и Collector их не форсят, но автоматические дашборды каждого backend'а и каждый cross-team запрос зависят от их консистентного заполнения. Зрелые platform-команды поставляют per-language wrapper вокруг OTel-SDK, преднастраивающий извлечение Semantic Convention-атрибутов, чтобы это нельзя было забыть.</p>
    <p><strong>OTLP: wire-формат, связывающий всё.</strong> OTLP — protobuf-определённый wire-протокол с двумя транспортами: OTLP/gRPC (binary protobuf поверх HTTP/2) и OTLP/HTTP (protobuf или JSON поверх HTTP/1.1). OTLP/gRPC предпочтителен — меньше, быстрее, поддерживает streaming. OTLP/HTTP существует под среды, блокирующие gRPC (некоторые firewall'ы) или под браузерную телеметрию. OTLP-сообщения: <code>ExportTraceServiceRequest</code> (батч resource-spans), <code>ExportMetricsServiceRequest</code> (resource-metrics), <code>ExportLogsServiceRequest</code> (resource-logs). Каждый OTel-совместимый backend выставляет OTLP-endpoint; wire-формат стабилен годами и спека эволюционирует backward-compatible. Стратегически: если твой edge (приложение или его sidecar) эмитит OTLP, ты vendor-нейтрален; если edge эмитит проприетарный формат — нет, независимо от того, переводит ли потом gateway.</p>
    <p><strong>Auto-instrumentation: 70-80%, которые ты получаешь бесплатно.</strong> Большая часть продакшн-трафика приходит от маленького набора фреймворков (HTTP-серверы, HTTP-клиенты, DB-драйверы, message-queue-клиенты), которые contrib-библиотеки OTel инструментируют из коробки. Для Java — OTel Java Agent (-javaagent JAR) переписывает байткод на старте JVM и инструментирует ~200 библиотек автоматически — никаких code-changes. Для Python — <code>opentelemetry-instrument</code> wrap'ит процесс и monkey-patches общие библиотеки. Для Node.js — <code>@opentelemetry/sdk-node</code> плюс набор instrumentations, регистрируемых до любого другого <code>require</code>, hook'ает методы фреймворков. Для Go auto-instrumentation менее зрел (в Go нет monkey-patching) — eBPF-based auto-instrumentation (Go-agent использует uprobes) — emerging подход. 70-80% — простая часть: HTTP-routes, DB-queries, cache-calls, queue-interactions. Оставшиеся 20-30% — business-specific spans, custom-атрибуты, cross-cutting concerns — это manual instrumentation, и именно там фактическая ценность, потому что там отвечаются бизнес-вопросы.</p>
    <p><strong>Manual instrumentation: мост ценности.</strong> Auto-instrumentation говорит «этот HTTP-запрос занял 800мс и сделал 5 DB-запросов». Manual instrumentation говорит «медленная часть — fraud-check-loop, fan-out на 12 вызовов rules-engine, из которых 3 отвалились по timeout». Pattern: открываешь span вокруг бизнес-операции, прикрепляешь атрибуты, описывающие её (customer_segment, feature_flag_state, batch_size), эмитишь span-event на важные моменты (cache miss, retry, fallback). Подвох: manual instrumentation — один и тот же код в каждом сервисе, поэтому platform-команды публикуют тонкую helper-библиотеку, оборачивающую OTel API org-specific-conventions (typed бизнес-атрибуты, redaction, span-event helpers). Другой подвох: не переинструментируй. У каждого span есть overhead в обработке collector'а и хранилище; цель — один span на пересечение границы сервиса плюс один на значимый subsystem-вызов, не один span на функцию.</p>
    <p><strong>Collector: receivers, processors, exporters.</strong> Collector — YAML-конфигурируемый pipeline. <em>Receivers</em> принимают входящую телеметрию — <code>otlp</code> (gRPC и HTTP), <code>filelog</code> (tail-log-файлов), <code>prometheus</code> (scrape /metrics-endpoints), <code>kafka</code>, плюс vendor-specific receivers. <em>Processors</em> трансформируют записи на лету — <code>batch</code> (группировка под эффективный экспорт), <code>memory_limiter</code> (drop при превышении RAM), <code>resource</code> (добавить service.name и другие атрибуты), <code>attributes</code> (redaction, rename, добавление полей), <code>tail_sampling</code> (решать, какие трейсы оставлять по full-trace-context'у), <code>transform</code> (general-purpose трансформации через OTTL — OpenTelemetry Transformation Language). <em>Exporters</em> отправляют записи в backend'ы — <code>otlp</code> (в другой OTel-aware backend), <code>datadog</code>, <code>prometheusremotewrite</code>, <code>loki</code>, vendor-specific. Сила Collector'а — композиция: цепляешь receivers через processors к нескольким exporters в одном pipeline, или запускаешь несколько pipelines под разные сигналы. 50 строк YAML конфигурят production-grade collector.</p>
    <p><strong>Deployment patterns: agent, gateway, agent-to-gateway.</strong> Три pattern'а доминируют. <em>Agent</em>: Collector работает как sidecar (один на pod) или DaemonSet (один на node), принимает телеметрию от локального приложения, делает минимум processing'а (resource-enrichment, батчинг), экспортит напрямую в backend. Дешевле всего по network hop'ам, сложнее всего scale'ить tail sampling (каждый агент видит трафик только своего node'а). <em>Gateway</em>: приложения экспортят напрямую в центральный пул Collector-реплик, делающий тяжёлый processing (tail sampling, advanced redaction, multi-backend routing). Легче scale'ить processing, но каждый span пересекает сеть от приложения к gateway'ю. <em>Agent-to-gateway</em> (production-канонический pattern): DaemonSet-агент на каждом node'е делает минимальный локальный processing и форвардит через OTLP в централизованный gateway-пул, обрабатывающий tail sampling, redaction и routing. Gateway statful (буферит span'ы под tail sampling), обычно деплоится как Deployment с горизонтальным scaling'ом плюс loadbalancing-exporter на агентах, маршрутизирующий по trace_id, чтобы все span'ы трейса попадали в один gateway-инстанс.</p>
    <p><strong>Tail sampling на масштабе: sticky-routing-ограничение.</strong> Tail sampling требует, чтобы каждый span трейса попал в один Collector-инстанс — иначе sampler не может оценить full-trace-context. Два подхода. (1) <em>Один gateway-инстанс</em> (well-resourced): все агенты форвардят в один gateway-pod с достаточным RAM, чтобы буферить active-trace working set (~1-2 GB на 50k in-flight трейсов со 100 span'ами каждый). Просто, но SPOF. (2) <em>Loadbalancing-exporter на агентах</em>: exporter агента хеширует по trace_id и маршрутизирует в детерминированный gateway-pod. Остаётся sticky, пока gateway-pool stable. Pod-restart и scale-up/down события перемешивают hash-ring и теряют in-flight-трейсы; production-сетапы используют sticky-by-trace-id load balancing (loadbalancing-exporter OTel Collector'а) с консервативной scaling-политикой.</p>
    <p><strong>Sampling decisions: head, tail, parent-based.</strong> Sampler SDK решает, какие трейсы записывать на API-call. <em>AlwaysOn</em> записывает каждый трейс (дёшево, большой объём). <em>AlwaysOff</em> не записывает ничего (полезно под canary). <em>TraceIdRatioBased(p)</em> записывает случайную p-долю на основе хеша trace_id (детерминированно между сервисами, если все используют тот же алгоритм). <em>ParentBased</em> наследует решение parent span'а через W3C-traceparent `sampled`-флаг — когда upstream-сервис решает сэмплить, все downstream-сервисы следуют; когда upstream — нет, downstream — обычно нет, если только локальный sampler не override'ит. Production-pattern: <em>ParentBased(root=TraceIdRatioBased(0.2))</em> на SDK (20% baseline, downstream наследует), tail sampling на Collector'е, форсящий «100% ошибок, 100% slow tail». Это комбинирует дешёвую предсказуемую цену (head) с curated-fidelity (tail) — учебниковый senior-choice.</p>
    <p><strong>Operator и Kubernetes-нативное развёртывание (превью).</strong> CNCF-проект OTel Operator управляет Collector'ом декларативно через CRD: <code>OpenTelemetryCollector</code> описывает agent- и gateway-deployment в YAML, а <code>Instrumentation</code> CRD конфигурит auto-instrumentation-injection через аннотации на pod'ах (<code>instrumentation.opentelemetry.io/inject-java: "true"</code>). Operator при старте pod'а ставит initContainer, копирующий language-specific OTel-агент в общий volume; runtime-environment-переменные настраивают OTLP-endpoint, sampling и resource-атрибуты. Стратегический выигрыш: инструментация становится platform-обязанностью, не per-service. Новый сервис получает auto-instrumentation бесплатно, не правя Dockerfile. Это снижает adoption-friction до уровня «добавь одну аннотацию» и делает observability дефолтом, а не opt-in. Глубже про Operator — в senior-tier.</p>
    <p><strong>Browser / serverless / RUM поверхность.</strong> OTel-JS-SDK работает в браузере через <code>@opentelemetry/sdk-trace-web</code>, инструментируя <code>fetch</code>, <code>XMLHttpRequest</code>, document-load, user-interactions. Браузер эмитит OTLP/HTTP (не gRPC — gRPC браузеро-несовместим) на Collector-endpoint с CORS. Browser-spans join'ятся с серверной частью трейса через traceparent-заголовок, идущий на исходящих запросах — настоящие end-to-end-трейсы от user-click до database-query. Для serverless (AWS Lambda, Cloudflare Workers, Vercel Edge) cold-start-цена OTel-SDK-инициализации значительна (50-200мс под Lambda), поэтому стандарт — Lambda-layer или runtime-extension от вендора, амортизирующая startup через invocations. AWS публикует OTel-Lambda-Layer. Cloudflare Workers и Vercel Edge ещё созревают по OTel-поддержке, особенно по async-context-propagation в V8-isolate-модели.</p>
    <p><strong>Observability-tax под OTel.</strong> Каждый компонент стека имеет цену: в приложении (SDK 1-5μs/span, auto-instrumentation 2-5% p99, batch span-processor 50-200 MB RAM); на agent-tier'е (DaemonSet ~50 MB RSS + 0.1 CPU baseline + scaling с трафиком); на gateway-tier'е (1-2 GB RAM на реплику под tail sampling, 1-2 CPU); на backend'е (описано в NumbersCard). Что покупает: vendor-портативность (config-change вместо migration-quarter), unified-инструментация через polyglot-парк, дешёвый эксперимент с альтернативными backend'ами (dual-export через config), forward-compatibility с wide-event-backend'ами. Это окупается на первой смене вендора, первом cost-renegotiation или первом cross-pillar pivot, который перестаёт быть hand-coded coordination между тремя backend'ами.</p>
    <p><strong>Governance OTel-adoption'а: что нужно гейтить.</strong> Без процесса OTel-стек медленно дрейфит обратно в lock-in. Production-gate'ы. (1) CI-lint: ни одного импорта vendor-SDK (dd-trace, newrelic, applicationinsights) в новом коде; только @opentelemetry/* и platform-wrapper. (2) PR-template-поле «OTel-impact»: автор указывает, добавлены ли новые span'ы / атрибуты / Collector-processor'ы. (3) Quarterly portability audit: grep по vendor-импортам + инвентаризация Collector-processor'ов на proprietary-имена + ревью Semantic Conventions adherence (топ-10 наиболее используемых атрибутов per service, identification drift'ов). (4) Pre-merge runbook-check: новый user-facing endpoint обязан иметь SLO + RED-dashboard + типовые log/trace-query в runbook'е. (5) Postmortem-policy: на каждом observability-инциденте (Collector-OOM, sampling-regression, vendor-lock-in-erosion) — postmortem с prevention-гипотезой. Эти gate'ы культурные не менее, чем технические — их единственная цена есть небольшое замедление PR-flow против неконтролируемой техдолги в долгую.</p>

Помещение их в Collector означает, что platform-инженеры обновляют YAML без координации application-redeploy через 50 команд. (3) <em>Гетерогенный парк</em>: разные сервисы — разные языки с разными SDK-версиями. Collector нормализует всё в OTLP и применяет единую policy независимо от того, как выглядит upstream — auto-инструментированный Java, manually-инструментированный Go, browser RUM, эмитящий OTLP/HTTP, — все текут через тот же Collector. Результат: Collector — policy-плоскость, SDK — instrumentation-плоскость, приложение остаётся простым. Пропусти Collector — и ты толкаешь всю policy в application-код, что и есть ситуация, для решения которой OTel существует.</p>,

    <p><strong>Ловушка vendor-нейтральности: distro-Collector'ы и проприетарные processor'ы.</strong> Многие вендоры поставляют «OTel-совместимые» Collector-distribution (Datadog Agent, Splunk OTel Collector, New Relic distro), включающие проприетарные processor'ы и exporter'ы. Использовать одну — нормально (она всё ещё принимает OTLP и эмитит OTLP downstream), но с двумя оговорками. (1) <em>Проприетарные processor'ы</em>: если ты полагаешься на processor, существующий только в vendor-X-distro (например vendor-specific routing-by-cost-фича, vendor-specific RUM-correlator), твой Collector-конфиг больше не портативен. Перейти на vendor-Y — переписать эту часть. (2) <em>Edge OTLP</em>: контракт, определяющий vendor-нейтральность, — «эмитит ли мой edge OTLP?» Если код приложения вызывает vendor-SDK (например <code>dd-trace</code>) напрямую и данные в vendor-формате на границе приложения, ты не vendor-нейтрален, даже если Collector посередине — потому что migration-cost живёт в коде приложения. Honeycomb-position-paper «OTel Is Key to Avoiding Vendor Lock-In» формулирует это точно: vendor-distro нормальны под convenience collection-tier, но если application-instrumentation vendor-specific, у тебя впереди instrumentation-cost миграции.</p>
    <p><strong>OTel и вопрос wide-event.</strong> Формулировка piece-01 observability 1.0 (три pillar'а) vs 2.0 (wide events) напрямую пересекается с OTel. Data-model OTel в spec-форме всё ещё three-pillar: traces, metrics, logs — отдельные API, отдельные SDK-pipeline, отдельные OTLP-messages. Но Honeycomb-blog-post «OpenTelemetry Is Not Three Pillars» явно переформулирует OTel-сигналы как «способы доставлять и хранить одну подложечную telemetry-модель» — и действительно, wide-event-store может ингестировать OTel-логи (с traces и metrics эмитируемыми рядом) и трактовать как один поток. Будущие работы OTel («OTel Profiles» experimental signal, «wide-event correlation»-обсуждения в spec working-group) сходятся на более унифицированной data-модели. Для senior-команд в 2026 импликация: принятие OTel сейчас forward-compatible и с 1.0-backend'ами и с 2.0-wide-event-backend'ами — не нужно коммититься на pillar-count заранее. Смена backend'а позже — Collector-config-изменение.</p>
    <p><strong>eBPF auto-instrumentation: no-code-путь.</strong> Растущий класс OTel-совместимой инструментации работает целиком в ядре через eBPF — Grafana Beyla, Pixie (Plus Labs / New Relic), USM Datadog. Эти инструменты прикрепляют kernel-probe, наблюдающие syscall'ы, HTTP-трафик на socket'ах и gRPC-RPC без application-code или library-changes. Output: OTel-shaped span'ы с разумной Semantic Conventions-атрибуцией (service.name из cgroup, http.route выведено из URL-парсинга). Trade-off: eBPF-инструментация видит то, что видит ядро, а не то, что приложение имеет в виду — бизнес-атрибуты (customer_segment, feature_flag) невидимы, и slow-tail-атрибуция к конкретной application-логике сложнее. Pattern на практике: eBPF под breadth (бесплатное покрытие каждого сервиса, включая те, которые нельзя модифицировать — vendor-binary), application-level SDK-инструментация под depth (бизнес-span'ы + атрибуты). Оба эмитят OTLP в тот же Collector, оба говорят Semantic Conventions, оба показываются на тех же дашбордах.</p>
    <p><strong>Operator и Kubernetes-native deployment.</strong> OTel Operator (Kubernetes Operator под CNCF-зонтиком) управляет Collector-deployment'ом декларативно. <code>OpenTelemetryCollector</code> CRD'ы определяют agent- и gateway-spec'и; <code>Instrumentation</code> CRD'ы конфигурят auto-instrumentation-injection через аннотации на pod'ах (<code>instrumentation.opentelemetry.io/inject-java: "true"</code>). Operator устанавливает language-specific auto-instrumentation-библиотеки на старте pod'а через initContainer, конфигурит OTLP-endpoint, указывающий на агент, и ставит resource-атрибуты из pod-метаданных. Стратегическая ценность: инструментация становится ответственностью platform-team, а не per-service. Новый сервис, развёрнутый с правильными аннотациями, получает полный auto-instrumentation без правки Dockerfile или кода. Зрелые платформы делают это дефолтом; opt-out требует явной аннотации.</p>
    <p><strong>Browser и edge: OTel под RUM и serverless.</strong> OTel JavaScript SDK поддерживает browser через <code>@opentelemetry/sdk-trace-web</code> — инструментирует <code>fetch</code>, <code>XMLHttpRequest</code>, document-load, user-interactions. Браузеры эмитят OTLP/HTTP (не gRPC; gRPC браузеро-несовместим) на Collector-endpoint, конфигурированный с CORS. Получаемые «browser-span'ы» join'ятся с серверной частью трейса через W3C-traceparent-заголовок, пропагированный на исходящие запросы — настоящие end-to-end-трейсы от user-click до database-query. Для serverless (AWS Lambda, Cloudflare Workers, Vercel Edge Functions) cold-start-цена OTel-SDK-инициализации значительна (50-200мс для полной Lambda-инструментации), поэтому стандартный подход — Lambda-layer или vendor-provided runtime-extension, амортизирующая startup через invocations. AWS публикует OTel-Lambda-Layer; layer инициализирует SDK в runtime-extension и выставляет OTLP функции. Cloudflare Workers и Vercel Edge всё ещё созревают по OTel-поддержке, с ограничениями на async-context-propagation в V8-isolate-модели.</p>
    <p><strong>Version skew и stability-стратегия.</strong> OTel — это много независимо версионируемых компонент: spec (v1.x), каждый language SDK (varies), каждый Collector-binary (v0.x с быстрыми релизами + stable LTS), каждый Semantic Convention domain (HTTP 1.x, DB 1.x и т. д.). Совместимость: SDK forward-compatible с новыми Collector'ами и backward-compatible со старыми на несколько minor-версий; OTLP стабильна между версиями. Стратегическая поза: pin'ить версии SDK и Collector'а в deployment-манифестах; обновлять квартально; запускать canary до fleet-wide rollout; отслеживать Semantic Convention version per service, чтобы дашборды знали, чего ожидать. У OTel Collector'а есть понятие «stable» и «beta»-компонент; production-сетапы держатся stable receivers/processors/exporters и принимают beta только с fallback-планом. Cadence Collector'а — ~ежемесячный; spec стабильнее.</p>
    <p><strong>Цена и надёжность самого Collector-tier'а.</strong> Collector — critical-path-кусок observability-стека: если он падает, ты теряешь видимость ровно тогда, когда она нужнее всего. Production-reliability-pattern'ы: (a) <em>HA gateway</em> — минимум 3 реплики за service (Kubernetes Service или cloud LB), переживает падение одного pod'а без потери данных за счёт client-retry. (b) <em>Persistent queue</em> — file_storage-extension Collector'а даёт disk-backed-буфер, переживающий рестарт; тюнь размер queue, чтобы поглощать 5-15 минут backend-замедления. (c) <em>Health-checks</em> — liveness- и readiness-probe против health_check-extension'а Collector'а; не позволяй медленному collector'у считаться ready. (d) <em>Self-monitoring</em> — scrape /metrics-endpoint Collector'а и alert на стандартные симптомы: dropped span'ы, refused span'ы, exporter-failures, queue-saturation. (e) <em>Resource-sizing</em>: commodity gateway-pod (4 CPU, 8 GB RAM) обрабатывает ~100-200k span/сек с tail sampling; размеряй под peak + запас. Цена Collector'а — малая доля backend-bill'а, но его надёжность критична.</p>
    <p><strong>Вопрос governance Semantic Conventions.</strong> Semantic Conventions — то, как телеметрия каждой команды композируется. Failures governance дают дорогие инциденты: команда-A называет поле `route`, команда-B — `http_route`, команда-C — `http.route` — и cross-team-дашборды не работают, alerts misfire, миграции на новые backend'ы умножают цену. Production-pattern: platform-team публикует per-language wrapper вокруг OTel-SDK, преднастраивающий Semantic Conventions под общий набор атрибутов org'а. Новые сервисы импортят wrapper; CI-lint режектит raw-SDK-usage в новом коде. Wrapper обрабатывает извлечение HTTP-route (matched template, не raw URL), DB-system-tagging (db.system=postgresql, не «psql»), redaction-deny-list и trace-context-mixin'ы под логи. Hook'и override позволяют командам добавлять бизнес-атрибуты, не трогая wrapper. Wrapper — самая высокоэффективная platform-инвестиция в OTel-adoption — она окупается на каждом cross-team-инциденте, каждой backend-миграции, каждом новом compliance-аудите.</p>
    <p><strong>Реальные продакшн-failure-modes.</strong> (a) <em>Collector OOM под tail sampling</em>: gateway-буфер растёт за memory-лимит, потому что decision_wait слишком длинный или trace-volume скакнул. Mitigation: memory_limiter-processor до tail_sampling; alerts на otelcol_processor_dropped_spans. (b) <em>Re-routing tail-sample на scale-events</em>: gateway-pool scale'ится up, hash-ring loadbalancing-exporter'а перемешивается, in-flight-трейсы теряют половину span'ов. Mitigation: pre-warming новых pod'ов, консервативное scaling, sticky-hashing с длинными convergence-окнами. (c) <em>OTLP-version-mismatch</em>: Collector обновлён впереди SDK встречает неизвестное поле, дропает запись. Mitigation: SDK/Collector compatibility-matrix; staged upgrades. (d) <em>Footprint-регрессия auto-instrumentation</em>: новая minor-версия OTel Java Agent добавляет инструментацию, замедляющую критичную библиотеку на 5%. Mitigation: canary upgrade агента, мониторить p99 на затронутом сервисе, opt-out конкретных instrumentations при необходимости. (e) <em>Cardinality-leak через auto-instrumentation</em>: auto-инструментированный HTTP-клиент добавляет полный URL как атрибут, взрывая cardinality downstream. Mitigation: сконфигурить инструментацию использовать http.route (шаблон) вместо url.full, либо стрипать query-strings через attributes-processor в Collector'е.</p>
    <p><strong>Стратегическая поза: принимай OTel везде, трактуй вендора как конфиг.</strong> Для senior-инженеров в 2026 OTel-решение больше не дискуссия. Каждый крупный вендор принимает OTLP. Instrumentation-поверхность портативна. Цена НЕ-принятия OTel реальна каждый квартал: vendor-миграция становится instrumentation-rewrite'ом, wide-event-эксперимент требует per-service code-changes, multi-region routing-смена требует deploy-цикла. Цена принятия OTel реальна, но ограничена и one-time: 1-2 недели разработки per-language wrapper, per-service onboarding (часто обрабатывается platform-team через auto-instrumentation) и постоянный version-management. Правильная стратегическая поза: принимать OTel по дефолту под каждый новый сервис, retrofit'ить старые на следующем значимом рефакторинге, поручать platform-team владение wrapper'ом и Collector'ом, и трактовать выбор вендора как configuration-вопрос — никогда как instrumentation-вопрос.</p>
