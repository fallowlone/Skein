CAP на практике (<a href="/ru/distributed/01-cap-practice/">01-cap-practice</a>) рассказал, что мы не можем иметь consistency, availability и partition tolerance одновременно. CP-системы — те, что выбирают консистентность под partition — всё равно должны согласиться на одну историю изменений по многим машинам. Raft — это то, как такое согласие достигается в etcd, Consul, CockroachDB, TiKV, MongoDB config-серверах, Kafka KRaft и практически любом production CP-хранилище, к которому ты прикасался.

<Crux>Как 3-7 машин, любая из которых может рухнуть, договариваются об одном упорядоченном логе изменений.</Crux>

Работа консенсуса — заставить кластер из N машин вести себя как одна машина. Это значит: каждое изменение должно быть упорядочено одинаково на каждом выжившем, каждый читатель должен видеть закоммиченные изменения, и ни одно подтверждённое изменение не должно потеряться. Raft делает это, выбирая одного лидера в каждый момент времени, позволяя только лидеру дописывать в лог, и реплицируя этот лог на кворум follower-ов до того, как считать запись закоммиченной. Трюк в edge case-ах — что происходит, когда лидер умирает, сеть разрывается, диск переполнен, или нода была offline несколько часов. Следующие разделы разбирают каждое из этого.

    <p><strong>Три роли, один term.</strong> Каждая нода в Raft-кластере находится в одном из трёх состояний в каждый момент: <em>follower</em>, <em>candidate</em> или <em>leader</em>. Нода стартует как follower. Если она перестаёт слышать лидера дольше election timeout (обычно рандомизированный 150-300 мс), она становится candidate, увеличивает текущий <em>term</em> (монотонные логические часы кластера), голосует за себя и просит остальные ноды отдать голос через RPC <code>RequestVote</code>. Если собирает голоса большинства, становится лидером этого term и начинает слать heartbeat-ы. Если два кандидата делят голоса, term заканчивается без лидера, и оба возвращаются в follower с новым рандомным таймаутом. Рандомизация — это то, что ломает ничью: при достаточно широком диапазоне вероятность повторного split-vote быстро падает.</p>
    <p><strong>Election timeout и heartbeat.</strong> Лидер шлёт RPC <code>AppendEntries</code> каждому follower с регулярным интервалом меньше election timeout — обычно heartbeat 50 мс при election timeout 150-300 мс. Heartbeat несёт текущий term лидера, его commit index, и любые новые log entry (или ни одной — тогда это чистый сигнал liveness). Follower, получивший heartbeat с term не меньше своего, сбрасывает election-таймер и подтверждает. Лидер, чей heartbeat отвергнут (потому что получатель видел больший term), немедленно понижается до follower; больший term выигрывает. Это сравнение term — весь слой дедупликации "кто реальный лидер прямо сейчас".</p>
    <p><strong>Лог и AppendEntries.</strong> Лидер хранит in-memory + on-disk лог из entry, каждое — тройка (term, index, command). Когда клиент шлёт запись, лидер сначала дописывает новое entry в свой лог, потом шлёт <code>AppendEntries</code> каждому follower с новым entry плюс term и index предыдущего entry. Follower проверяет: есть ли у меня entry на этом prevIndex с этим prevTerm? Если да — дописывает новое entry и отвечает success. Если нет — отвечает mismatch, и лидер откатывается на один index назад и повторяет, в итоге находя последнюю точку согласия и переписывая расходящийся хвост follower-а своим. Этот туда-сюда редок в steady state (follower-ы обычно отстают на одно entry, не на много) и амортизируется почти до нуля в production.</p>
    <p><strong>Commit, apply и state machine.</strong> Log entry <em>закоммичено</em>, когда лидер услышал от большинства нод (включая себя), что они положили entry на диск. Commit index лидера — самый высокий index, известный как закоммиченный. Лидер пристёгивает свой commit index к следующему AppendEntries, так что follower-ы за один round-trip узнают, какие entry теперь можно применить к state machine. State machine специфична приложению — может быть key-value мапа, реляционная таблица, дерево конфига — но Raft её не смотрит. Он просто говорит: каждая нода, в log-порядке, применяет каждое закоммиченное entry ровно один раз, и state machine поэтому детерминирована между репликами. Это весь механизм: упорядоченный реплицированный лог + детерминированная state machine = replicated state machine.</p>
    <p><strong>Зачем большинство для коммитов И выборов.</strong> Доказательство безопасности Raft опирается на пересечение кворумов. Любые два большинства множества из N делят хотя бы один элемент (pigeonhole: удвоенный потолок (N+1)/2 превосходит N). Когда новый лидер выбран для term T+1, его election-кворум пересекается с commit-кворумом каждого закоммиченного entry каждого предыдущего term. Через эту общую ноду новый лидер гарантированно видит каждое ранее закоммиченное entry (правило выборов Raft отвергает кандидатов, чей лог отстаёт от лога любого voter). Поэтому ни одно закоммиченное entry не может быть потеряно при смене лидера. Это свойство называется <em>Leader Completeness</em>, и это единственная причина, по которой Raft безопасен, даже когда лидеры умирают посреди term.</p>
    <p><strong>Четыре свойства безопасности.</strong> Доказательство корректности Raft сводится к четырём инвариантам. <strong>Election Safety</strong>: максимум один лидер на term (следует из "один голос на ноду на term + требуется большинство"). <strong>Leader Append-Only</strong>: лидер никогда не перезаписывает и не удаляет свои собственные log entry — только дописывает. <strong>Log Matching</strong>: если два лога разделяют entry на index i с term t, они идентичны для всех index до i включительно (следует из проверки целостности AppendEntries). <strong>Leader Completeness</strong>: любое entry, закоммиченное в каком-то term, есть в логе каждого лидера более высоких term. <strong>State Machine Safety</strong> (выводится из вышесказанного): две ноды не применяют разные команды на одном index. Запомни эти и у тебя есть весь mental model.</p>
    <p><strong>Где Raft не применим.</strong> Raft — алгоритм crash-fault-tolerant (CFT) — он предполагает, что ноды либо следуют протоколу, либо останавливаются. Он не толерантен к Byzantine faults (ноды врут, шлют corrupted сообщения или ведут себя враждебно). Byzantine-нагрузки требуют PBFT, HotStuff, Tendermint или другого BFT-консенсуса. Практически для каждого backend database, config store и cluster manager CFT достаточно, потому что ноды внутри твоего датацентра и threat model — это сбои железа/софта, а не злонамеренные операторы. Выбирай BFT только когда у тебя реально adversarial-участники — типично для блокчейнов и некоторых federated систем.</p>
    <p><strong>Практическая wire-форма и эксплуатация.</strong> Кластер etcd или Consul проводит 90% жизни в steady state: лидер шлёт heartbeat каждые 50 мс, follower-ы подтверждают, изредка клиентские записи коммитятся за 2-3 мс intra-region. Выборы лидера случаются на каждом рестарте, сетевом блипе или pause-процесса дольше election timeout. На здоровом кластере выборы завершаются за 100-500 мс; кластер ненадолго недоступен для записей в этом окне. Операционные метрики стоит трекать: частоту смены лидера, commit latency p50/p99, RTT heartbeat, и disk-fsync latency на лидере (каждое закоммиченное entry должно лечь на диск до подтверждения, поэтому медленный диск на лидере — самая частая причина высокого tail latency).</p>
    <p><strong>Маршрутизация клиента и redirect запросов.</strong> Клиенты Raft-кластера должны слать записи текущему лидеру — только лидер может дописывать в лог. Простейший паттерн "любая нода сделает redirect": follower, получив запись, отвечает адресом текущего лидера (которого он знает из недавних heartbeat-ов). Клиент ретраит к этому адресу. Некоторые клиенты держат маленький кеш "last known leader", чтобы скипнуть redirect на следующих записях. Etcd, Consul, TiKV все так делают; на практике redirect добавляет 1-5 мс на редком промахе, а steady-state записи идут напрямую к лидеру. Чтения отличаются: линеаризуемые чтения должны идти через ReadIndex или lease лидера; eventually-consistent чтения может обслужить любой follower. Application-слой выбирает консистентность чтения per query.</p>
    <p><strong>Что ломается на практике — три failure mode.</strong> Первое, медленный диск: если fsync лидера занимает дольше heartbeat-интервала, follower-ы таймаутят до того, как лидер успевает подтвердить их AppendEntries, и кластер начинает выборы. Новый лидер ловит ту же disk-проблему и цикл повторяется. Фикс — dedicated NVMe для WAL, никогда shared cloud volume. Второе, network jitter: краткий partition или congestion обрывает heartbeat и триггерит выборы, хотя кластер по большей части здоров. Pre-vote (см. senior-tier) митигирует это. Третье, дрейф часов на lease read: если часы лидера убежали вперёд follower-ов, он может растянуть lease past фактический heartbeat round, обслуживая чтения, которые уже потеряли lease — stale read. NTP-синхронизация всех нод — практика корректности, не гигиены.</p>
    <p><strong>Что Raft НЕ решает.</strong> Raft реплицирует лог. Он не даёт queryable базу, схему партиционирования, multi-key транзакции, secondary indexes, geo-репликацию или schema-миграции. Всё это живёт поверх Raft как application-логика. Частая ошибка новичка — предполагать "мы используем Raft, значит у нас распределённая база"; правда в "мы используем Raft, чтобы реплицировать один лог; база — это state machine, которую мы строим сверху". Строй для state machine, которая нужна; пусть Raft занимается консенсусом изменений этой машины, и не более.</p>
    <p><strong>Минимальный пример приложения над Raft.</strong> Представь key-value-хранилище. State machine — это hash-map в памяти. Log entry — команды вида (SET key value) или (DELETE key). Когда клиент шлёт SET через лидера, лидер дописывает entry в лог, реплицирует на большинство, и когда entry закоммичено, каждая нода в log-порядке применяет команду к своему hash-map. Результат: все ноды имеют идентичный map после применения одного и того же лога. Чтения сегодня могут идти через лидера для линеаризуемости или через любую follower-ноду для eventually-consistent. Это весь скелет: построй state machine, запиши команды, пусть Raft передаёт согласованный лог. Большинство сложности production-систем — это именно state machine, не Raft.</p>
    <p><strong>Расширения state machine.</strong> Простой hash-map скелет масштабируется до более сложных state machine за счёт усложнения команд: SQL-таблицы становятся state machine с командами (INSERT/UPDATE/DELETE row); файловая система — с командами (CREATE/WRITE/DELETE inode); очередь сообщений — с командами (PUSH/POP). Каждое расширение требует от инженера обеспечить детерминизм: одна и та же последовательность команд должна давать одно и то же состояние на каждой ноде. Это означает никаких now(), random(), внешних HTTP-вызовов внутри обработчиков команд — все недетерминированные значения должны вычисляться лидером и записываться в лог как часть команды. Несоблюдение этого — самая частая причина "загадочного" расхождения реплик после нескольких часов работы; debug — повтор лога двух реплик из одного снимка и сравнение state hash.</p>
    <p><strong>Backpressure и rate-limiting на лидере.</strong> Лидер — узкое место writes-нагрузки. Если клиенты шлют записи быстрее, чем кворум может закоммитить, очередь in-flight entry в памяти лидера растёт. На high-throughput системах эта очередь должна быть ограничена явным rate-limit: лидер начинает возвращать 429 или gRPC RESOURCE_EXHAUSTED, когда in-flight превышает порог. Без этого лидер исчерпает память и упадёт, форсируя выборы — система деградирует в каскад смен лидера, каждый перегружен. Etcd использует параметр <code>max-request-bytes</code> и <code>quota-backend-bytes</code>; TiKV ограничивает Raft propose queue per region. Это та же дисциплина, что retry budget для клиентов: production-зрелость = ограничение на каждой стороне.</p>
    <p><strong>Тестирование Raft-реализаций.</strong> Raft печально известен количеством тонких багов в DIY-реализациях. Стандартное тестирование: unit-тесты на каждую RPC, property-based тесты (генерация случайных последовательностей сетевых событий + проверка инвариантов после), model checker (TLA+ модель оригинальной статьи Raft публично доступна и применяется к новым реализациям как differential test), и chaos test (Jepsen — фреймворк Kyle Kingsbury — формально верифицирует консистентность под сетевыми partition). Jepsen-отчёты по etcd, Consul, TiKV публично доступны и каждый раз находят как минимум один реальный баг — даже в реализациях, которые до этого верифицировались model checker. Production-готовая Raft-реализация прошла Jepsen test suite, а не только "наш юнит-тест зелёный".</p>

  <Fragment slot="senior">
    <p><strong>Membership change через joint consensus.</strong> Добавление или удаление нод из работающего Raft-кластера — самая error-prone операция в production. Наивное "просто поменяй конфиг и рестартни" может выбрать двух лидеров одновременно во время transition — ровно то safety violation, которое Raft в остальном предотвращает. Статья Raft, раздел 6, определяет <em>joint consensus</em>: переключение через промежуточную конфигурацию C_old_new, где коммиты требуют большинство И от старой, И от новой конфигурации. Как только C_old_new закоммичено, кластер переходит в C_new (только большинство нового). Промежуточная фаза устраняет окно, в котором могли существовать два разных большинства. Hashicorp Raft и etcd оба реализуют это плюс single-server изменения сверху (добавлять или удалять только одну ноду за раз с joint consensus внутри, чтобы операционная история была проще). Alibaba Cloud writeup о Raft engineering practices документирует реальные баги, возникшие из-за пропуска joint consensus в ранних реализациях.</p>
    <p><strong>Pre-vote: избегание инфляции term.</strong> Нода, которая возвращается после долгого partition со stale term, может ненадолго выглядеть кандидатом на очень высоком term (потому что она продолжала увеличивать его во время partition). Когда её RequestVote приходит к здоровым follower-ам, они обновляют свои term, чтобы соответствовать, потом понимают, что её лог отстаёт, отказывают в голосе и заставляют текущего лидера понизиться зря. У кластера прошли выборы лидера, которые ему не были нужны. PhD-диссертация Diego Ongaro добавила фазу <em>pre-vote</em>: перед увеличением term и стартом настоящих выборов кандидат шлёт необязательный pre-vote, который другие ноды оценивают; только если большинство ответило бы "да", кандидат увеличивает term и запускает реальные выборы. Pre-vote теперь стандарт в etcd, TiKV и Hashicorp Raft. Цена — один extra RPC round в выборах, которые и так бы успешно прошли; выгода — никаких лишних смен лидера после восстановления partition.</p>
    <p><strong>Learners (не-голосующие члены).</strong> Production-системы регулярно хотят добавить новую ноду в кластер, дать ей догнать лог за многие минуты и только потом промоутнуть в voter. Добавление напрямую как voter либо потребовало бы немедленного кворума, включающего ноду с пустым логом (тормозит коммиты), либо отказывало бы в записях во время catch-up. Расширение <em>learner</em> делает новую ноду non-voting получателем AppendEntries: она следует за логом, но не учитывается в кворумах и не голосует в выборах. Как только её лог догоняет до небольшого lag, оператор промоутит её через single-server membership change. Etcd, Consul и Yugabyte все поддерживают learner-ов. Это безопасный способ масштабировать размер кластера или заменить мёртвую ноду без падения availability.</p>
    <p><strong>Линеаризуемые чтения: ReadIndex и lease reads.</strong> Строгая линеаризуемость требует, чтобы чтение видело каждую ранее закоммиченную запись. Наивная реализация: маршрутизировать каждое чтение через лидера, коммитить no-op log entry просто ради чтения, потом возвращать. Цена — один полный round консенсуса на чтение, слишком дорого для production. Оптимизация Raft, называемая <em>ReadIndex</em>: когда чтение приходит, лидер запоминает текущий commit index, шлёт heartbeat большинству follower-ов, чтобы подтвердить, что он всё ещё лидер, и потом возвращает чтение, как только его state machine применила entry до этого index. Никакое новое log entry не пишется. Цена — один heartbeat round-trip. Более быстрая альтернатива — <em>leader lease</em>: лидер держит lease (например 9 мс, выданный предыдущим heartbeat round), в течение которого он может обслуживать чтения без RPC. Lease reads sub-миллисекундные и используются CockroachDB и TiKV для hot-path чтений. Trade-off: lease reads требуют bounded clock skew между лидером и follower-ами (обычно под 500 мс), так что синхронизация wall-clock (NTP, PTP) становится требованием корректности, а не просто гигиенической практикой.</p>
    <p><strong>Snapshots и log compaction.</strong> Лог Raft в принципе растёт вечно; на практике лог должен truncate-иться, иначе диск переполняется и recovery из disk-replay занимает часы. Snapshots решают это: каждая нода периодически пишет полное состояние state machine плюс кортеж (lastIncludedIndex, lastIncludedTerm) на диск, потом удаляет log entry до этого index. Follower, отставший больше чем на retention window, получает RPC <code>InstallSnapshot</code> вместо catch-up через AppendEntries — лидер шлёт свой snapshot, follower грузит его как своё состояние, потом догоняет недавний хвост лога. Частота snapshot — настройка: слишком часто бьёт по throughput (амплификация fsync); слишком редко бьёт по recovery и растит лог. Etcd по умолчанию делает snapshot каждые 10 000 entry. CockroachDB — каждые несколько секунд. Snapshot также должен включать последнюю конфигурацию membership — отсутствие этого знаменитый источник багов, который бьёт операторов, пишущих Raft вручную.</p>
    <p><strong>Persistence и fsync диска.</strong> Raft требует, чтобы каждый сервер персистил три куска состояния на durable storage до ответа: currentTerm, votedFor (для текущего term) и log entry (включая новые, подтверждаемые в текущем RPC). Пропуск любого ломает safety. Цена fsync — доминирующая операционная цена — каждое закоммиченное entry стоит как минимум одного fsync на лидере и одного на каждом follower, который подтверждает. На NVMe с battery-backed cache fsync 50-100 микросекунд; на cloud-volume (EBS gp3, GCP balanced PD) это может быть 1-3 мс. Поэтому high-throughput Raft-системы (Kafka KRaft, TiKV) батчат много клиентских записей в одно log entry и амортизируют fsync. Классический антипаттерн — fsync-per-request: никогда не делай это для Raft на любой нетривиальной нагрузке.</p>
    <p><strong>Multi-Raft и шардирование.</strong> Один Raft-group имеет ограниченный throughput — пропорциональный fsync самой медленной реплики плюс RTT сети. Чтобы масштабироваться за пределы нескольких тысяч записей/с, production-системы запускают много независимых Raft-group параллельно, каждый отвечающий за shard ключевого пространства. CockroachDB партиционирует ключевой диапазон в "ranges" (~512 МБ каждый) и запускает один Raft-group на range. TiKV делает то же с "regions". Kafka KRaft запускает один Raft-group на партицию метаданных topic. Челлендж — ребалансировка: когда трафик сдвигается, ranges должны split-иться, merge-иться и мигрировать, каждая операция — координированный membership change Raft-group. Систему, оркестрирующую это, иногда называют "shard manager" или "placement driver" — она сама использует Raft, чтобы держать placement-решения консистентными в operator pool.</p>
    <p><strong>Leadership transfer и graceful shutdown.</strong> Оператор, желающий дренировать Raft-ноду перед обслуживанием, может попросить кластер <em>передать лидерство</em>: текущий лидер шлёт сообщение <code>TimeoutNow</code> назначенному follower, который немедленно стартует выборы и почти гарантированно выигрывает, потому что никакой другой follower ещё не таймаутил. Текущий лидер понижается. Это избегает окна недоступности 150-300 мс, которое вызвал бы нормальный crash лидера; user-видимое влияние под 10 мс. Без leadership transfer drain лидера для deploy вызывает один election-шторм на мигрированного лидера, что приемлемо для 3-нодового кластера, но болезненно для multi-Raft-системы с тысячами групп. CockroachDB и TiKV оба expose-ят leadership-transfer endpoint-ы для rolling deploy.</p>
    <p><strong>Production-наблюдаемость для Raft.</strong> Минимально жизнеспособный Raft dashboard выдаёт: uptime лидера per group, частоту выборов в минуту (всплеск означает flapping leadership), commit latency p50/p99 per group, размер лога (uncompacted) per replica, гэдж raft_term (когда быстро растёт — повторные неудачные выборы), RTT heartbeat, follower-lag-entries (насколько каждый follower отстаёт) и rate установки snapshot (высокий означает, что follower-ы отстают быстрее, чем догоняют). Etcd шипает <code>etcd_server_leader_changes_seen_total</code>, <code>etcd_disk_wal_fsync_duration_seconds</code> и <code>etcd_network_peer_round_trip_time_seconds</code> по умолчанию. Метрики liveness и range_lease_holder CockroachDB играют ту же роль для тысяч Raft-group.</p>
    <p><strong>Реальные production-провалы.</strong> GitHub октябрь 2018: сетевой блип между датацентрами заставил etcd failover-нуться на partition, который ненадолго решил, что он authoritative. Реальная проблема была misconfigured external sync, писавший в оба региона в краткое окно — Raft был корректен, оркестратор над ним — нет. Datadog 2023: TiKV-кластер испытывал повторные выборы под высокой нагрузкой записи, потому что pre-vote был выключен в старой версии; апгрейд и включение pre-vote починили. Etcd Kubernetes incident 2020: админ удалил ноду из 3-нодового кластера без правильного membership change API; оставшиеся две ноды флипали между leader и candidate, потому что их сохранённые конфигурации не сходились. Фикс: остановить кластер, поправить конфиги вручную, рестартнуть. Урок: никогда не обходи joint-consensus membership change в production.</p>
    <p><strong>История: от Multi-Paxos к Raft и Multi-Raft.</strong> Paxos Leslie Lamport (1989) — первый proven-correct алгоритм консенсуса, но известно obscure. Multi-Paxos оптимизировал его для replicated-log случая, но всё ещё требовал тщательной инженерии. Diego Ongaro и John Ousterhout опубликовали Raft в 2014 ("In Search of an Understandable Consensus Algorithm") с явной целью дизайна — быть преподаваемым. К 2026 у Raft около 100 open-source реализаций и он дефолт в каждой новой системе, нуждающейся в CP-консенсусе. Индустрия сходится: greenfield-проекты выбирают Raft, legacy-системы иногда сохраняют Multi-Paxos (Spanner, Paxos-based LWT Cassandra, safekeeper-ы Neon). Multi-Raft — параллельно работающие Raft-group — паттерн дизайна, масштабирующий технику от единого config store к горизонтально-шардированной базе.</p>
    <p><strong>Cross-protocol: Raft как building block.</strong> Raft редко user-видимый примитив. Kubernetes использует Raft etcd, чтобы хранить конфиг. Service mesh (Consul) использует Raft для service discovery и KV. Базы используют Raft на shard для range-репликации. Stream-процессоры (Kafka KRaft, Pulsar BookKeeper) используют Raft для метаданных. Даже некоторые очереди (NATS JetStream) используют Raft для storage. Паттерн един: Raft реплицирует маленький, упорядоченный, чётко определённый лог; application-слой сверху определяет, что log entry означают. Обращаться с Raft как с примитивом — replicated state machine, которым ты управляешь через log entry — это mental model senior-инженера.</p>
    <p><strong>Deployment-паттерны: managed vs self-hosted.</strong> Self-hosting etcd или Consul-кластера по 3 AZ — каноничный "ты сам разбираешься с fsync-latency" деплой. Cloud-managed альтернативы (Raft-based storage AWS Aurora, GCP Spanner, Azure Cosmos DB) поглощают операционное бремя, но стоят 2-5x дороже. Для типичного 3-AZ деплоя: разместить Raft-ноды в трёх разных AZ, целить intra-region latency 1-5 мс, использовать NVMe-инстансы (i3, m5d), включать disk write-cache только с battery backup, никогда не co-locate-ить две Raft-реплики на одном хосте. Cross-region Raft (5 нод split 2-2-1) возможен, но платит 50-200 мс commit latency за привилегию пережить полную потерю региона — пользователи Spanner и CockroachDB регулярно платят эту цену.</p>
