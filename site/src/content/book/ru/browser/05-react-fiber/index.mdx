Вы вызываете `setState`. Где-то между этим вызовом и сменой пикселя на экране React решил, какие компоненты перезапустить, сравнил два дерева, вычислил минимальный набор мутаций DOM и применил их — возможно, остановившись на полпути, чтобы пропустить нажатие клавиши. Машина, которая это делает, — fiber-реконсилер. Это причина, почему React-приложение может перерендерить дерево на 5 000 узлов, не заморозив поле ввода, и причина, почему один неправильно поставленный `key` молча портит состояние компонента.

<Crux>Дерево компонентов становится мутациями DOM: render вычисляет дифф (прерываемо), commit применяет его (атомарно).</Crux>

React делит каждое обновление на две фазы. **Фаза render** обходит дерево компонентов, запускает ваши функциональные компоненты и строит новое дерево узлов *fiber* — эта фаза чистая, не производит видимых изменений, и с React 18 может быть приостановлена, возобновлена или выброшена. **Фаза commit** берёт готовое новое дерево и применяет мутации DOM одним синхронным, непрерываемым взрывом. Всё хорошее и всё опасное в производительности React живёт в зазоре между «прерываемым render» и «атомарным commit».

    <p><strong>Что такое fiber на самом деле.</strong> Fiber — это обычный JavaScript-объект, по одному на экземпляр компонента, по одному на DOM-элемент в дереве. Каждый fiber держит: `type` компонента, его `props`, его `key`, его текущий `state` и хуки, указатели на `child`, на следующий `sibling` и на `return` (родителя), плюс указатель `alternate` на двойника в другом дереве. Fiber-ы образуют связное дерево, не массив — и эта связная структура и есть весь смысл. Рекурсивный обход дерева живёт в стеке вызовов и не может быть приостановлен; обход связного списка держит свою позицию в обычной переменной, поэтому React может остановиться после любого fiber, сохранить указатель и возобновить ровно оттуда позже. Fiber — это структура данных, сделавшая прерываемый рендеринг возможным. Имя старше React 18 — архитектура приземлилась в React 16 (2017) — но только React 18 включил конкурентные фичи, эксплуатирующие её.</p>

    <p><strong>Два дерева: current и workInProgress.</strong> React всегда держит два fiber-дерева. Дерево <em>current</em> — это то, чьё состояние совпадает с тем, что нарисовано на экране прямо сейчас. Когда обновление стартует, React строит дерево <em>workInProgress</em> — клонируя fiber-ы из current по ходу, применяя новые props и state. Указатель `alternate` каждого fiber связывает его с двойником в другом дереве, поэтому клонирование дёшево: неизменённые поддеревья переиспользуются по ссылке. Когда дерево workInProgress завершено и закоммичено, два дерева меняются: workInProgress становится current, а старое current-дерево держится, чтобы стать следующим workInProgress. Это двойная буферизация. Она гарантирует, что дерево на экране никогда не наблюдается в полуобновлённом состоянии — и поэтому render, прерванный и выброшенный, не стоит ничего постоянного: выброшенное дерево workInProgress просто никогда не коммитится.</p>

    <p><strong>Фаза render: прерываема, должна быть чистой.</strong> Фаза render обходит дерево workInProgress, вызывает каждый функциональный компонент и гоняет реконсиляцию. Поскольку React 18 может приостановить эту фазу, возобновить или выбросить и начать заново, ваша функция компонента может быть вызвана больше одного раза для одного видимого обновления — и приостановленный render может сидеть полузаконченным, пока пользователь взаимодействует. Поэтому render должен быть <em>чистым</em>: никаких сайд-эффектов, никакой мутации внешних переменных, никаких чтений или записей DOM, никаких сетевых вызовов в теле функции. Сайд-эффект в render выполняется непредсказуемое число раз. StrictMode React намеренно дважды вызывает компоненты в разработке именно чтобы выявить нечистые render-ы рано. Дисциплинированное место для сайд-эффектов — `useEffect` (после commit) или обработчик события (вне render совсем).</p>

    <p><strong>Фаза commit: атомарна, синхронна, три под-шага.</strong> Как только дерево workInProgress полностью построено, commit гоняется одним непрерываемым блоком. У него три под-шага. <em>Before-mutation</em>: React читает любое состояние до мутации (здесь происходят `getSnapshotBeforeUpdate` и cleanup-снимок для `useLayoutEffect`). <em>Mutation</em>: React применяет каждое изменение DOM — вставки, удаления, обновления атрибутов, изменения текста — управляемые effect-флагами, которые он навесил на fiber-ы во время render. <em>Layout</em>: React гоняет колбэки `useLayoutEffect` и обновляет ref-ы, синхронно, до того как браузер рисует. Поскольку commit синхронен и непрерываем, огромное дерево с тысячами мутаций производит одну длинную задачу — commit это часть React, которую нельзя time-slice-ить, поэтому способ держать его коротким — держать число мутаций малым (виртуализация, мемоизация).</p>

    <p><strong>Реконсиляция: правила диффинга.</strong> Реконсиляция сравнивает новое дерево элементов против текущего fiber-дерева, чтобы решить, что сохранить, обновить или заменить. Полный дифф дерева — O(n³) в общем случае; React делает его O(n) двумя эвристиками. Первая: <em>разный тип элемента означает полную замену</em> — если `<div>` становится `<span>`, или `<ComponentA>` становится `<ComponentB>`, React сносит всё поддерево (размонтируя его, уничтожая его состояние) и строит новое с нуля. Он не пытается диффить через типы. Вторая: <em>ключи идентифицируют детей списка между рендерами</em> — внутри списка React матчит старых и новых детей по их `key`, не по позиции. Стабильный ключ говорит React «это тот же логический элемент, даже если он сдвинулся». Это вся причина существования ключей, и неправильно их сделать — самый частый баг состояния в React.</p>

    <p><strong>Почему `key` важен и почему `key={index}` — ловушка.</strong> Когда вы рендерите список, React нужно спарить каждого нового ребёнка со старым fiber, чтобы сохранить состояние того fiber (и его DOM-узел). Со стабильным ключом — id из базы, slug — React корректно отслеживает каждый элемент через вставки, удаления и переупорядочивания. С `key={index}` ключ — это позиция, поэтому когда список переупорядочивается или элемент вставляется в начало, ключ каждого элемента сдвигается. React тогда думает, что элемент-на-индексе-0 — «тот же элемент», хотя данные сдвинулись — он держит состояние и DOM старого fiber, но скармливает ему props нового элемента. Видимый баг: чекбокс, отмеченный на строке 3, остаётся отмеченным после удаления строки 1, теперь прицеплен к тому, что было строкой 4. `key={index}` безопасен только для списка, который статичен и никогда не переупорядочивается; для всего динамического он молча портит состояние.</p>

    <p><strong>Приоритетные lanes.</strong> React 18 назначает каждому обновлению <em>lane</em> — корзину приоритета. Модель lane (битовая маска из 31 lane) позволяет React работать сначала над высокоприоритетными обновлениями и откладывать низкоприоритетные. Важные уровни: <em>discrete</em> ввод (клик, нажатие) — синхронный приоритет — React рендерит его немедленно и блокирующе, потому что пользователь ждёт ровно это взаимодействие. <em>Default</em> приоритет покрывает обычные обновления. <em>Transition</em> приоритет (задаётся через `useTransition`) — для обновлений, которых пользователь напрямую не ждёт — фильтрация большого списка, навигация в новый вид — и они могут быть прерваны чем-то более срочным. <em>Idle</em> — самый низкий. Когда нажатие приходит посреди transition-render, React бросает render transition в процессе, обрабатывает нажатие на высоком приоритете и перезапускает transition после. Lanes — это то, как React решает, что рендерить сейчас, а что позже.</p>

    <p><strong>Time-slicing: как фаза render уступает.</strong> Длинный синхронный render блокирует ввод — ровно тот режим отказа, что описал фрагмент про event loop. Планировщик React разбивает фазу render на срезы. После примерно 5 мс работы реконсиляции планировщик проверяет `shouldYield()`; если true, он останавливается, постит задачу-продолжение через `MessageChannel` (кроссбраузерный способ запланировать задачу без зажима) и даёт браузеру гонять обработчики ввода и рендеринг. Задача-продолжение возобновляет render с сохранённого указателя fiber. Render на 50 мс становится десятью срезами по 5 мс, чередующимися с собственной работой браузера, и ввод остаётся отзывчивым всё это время. Это применяется только к <em>конкурентным</em> render-ам — transition-ам и другим несрочным обновлениям. Обновление синхронного приоритета (discrete ввод) всё ещё рендерится одним блокирующим проходом, потому что заставить пользователя ждать уступки свело бы на нет смысл.</p>

    <p><strong>useTransition и useDeferredValue.</strong> Это два хука, кладущие работу в transition-lane. `useTransition` даёт вам функцию `startTransition` — обновления состояния внутри неё помечены низкоприоритетными и прерываемыми, плюс флаг `isPending` для показа спиннера. Канонический случай: поле поиска, где само значение инпута обновляется синхронно (поэтому набор ощущается мгновенным), но дорогое обновление отфильтрованного списка обёрнуто в `startTransition` (поэтому оно уступает дальнейшим нажатиям). `useDeferredValue` — та же идея со стороны потребителя: он даёт вам копию значения, которая «отстаёт» — React обновляет её на transition-приоритете, поэтому компонент, читающий отложенное значение, перерендеривается, только когда у React есть свободное время. Используйте `useTransition`, когда вы владеете обновлением состояния; `useDeferredValue`, когда значение приходит из props или контекста, которыми вы не управляете.</p>

    <p><strong>Виртуальный DOM, честно.</strong> «Виртуальный DOM» — маркетинговое имя для дерева элементов, которое React диффит. Стоит быть точным: виртуальный DOM не быстрее прямой манипуляции DOM — написанная вручную, оптимальная последовательность DOM-вызовов всегда обгоняет React. Что виртуальный DOM покупает — это <em>модель программирования</em>: вы описываете UI как чистую функцию от состояния и никогда не пишете императивный DOM-код, а React делает результат достаточно быстрым диффингом. Цена реальна — построение и дифф дерева элементов это CPU-работа, которой компиляторный фреймворк (Svelte) или мелкозернистый реактивный (SolidJS) избегает. Ставка React в том, что выигрыш developer experience от «UI = f(state)» стоит оверхеда реконсиляции, и что time-slicing держит этот оверхед от блокировки пользователя. Знание этого даёт рассуждать о том, когда модель React — правильный инструмент, а когда нет.</p>

    <p><strong>Что значит «компонент перерендерился».</strong> Стоит развести три вещи, которые новички путают. <em>Re-render</em> — React заново вызвал функцию компонента и построил новое дерево элементов. <em>Реконсиляция</em> — React сравнил это новое дерево со старым. <em>DOM-мутация</em> — реконсиляция нашла различие и применила его к настоящему DOM. Re-render — самая дешёвая из трёх и сам по себе не «медленный»: вызвать функцию и создать несколько объектов это микросекунды. Дорого становится, когда re-render-ов тысячи (большое дерево без bailout-ов), или когда сам компонент делает тяжёлую работу при каждом вызове (несмемоизированное вычисление), или когда реконсиляция находит много DOM-мутаций. Поэтому «уменьшить re-render-ы» — не всегда правильная цель: лишний re-render компонента, который реально ничего не меняет в DOM, обычно безвреден. Цель — убрать <em>дорогие</em> re-render-ы: тяжёлые вычисления в теле и каскады, перерендеривающие тысячи узлов.</p>

    <p><strong>Контекст и каскад перерендеривания.</strong> `useContext` — самый частый источник неожиданного каскада. Когда value провайдера меняется по ссылке, <em>каждый</em> компонент, потребляющий этот контекст, перерендеривается — независимо от того, какую часть value он реально читает. Контекст не делает мелкозернистой подписки на поля: подписка идёт на весь объект value. Два следствия. Первое: `value` провайдера обязан быть референсно стабильным — обернут в `useMemo`, иначе свежий литерал каждый рендер триггерит весь каскад. Второе: не кладите быстро меняющееся и редко меняющееся в один контекст. Тема приложения и позиция курсора мыши в одном провайдере означают, что каждое движение мыши перерендеривает всех потребителей темы. Лечение — расщепить на несколько контекстов по частоте изменения, или использовать паттерн «контекст селектора» (библиотека вроде use-context-selector), где потребитель подписывается на производную часть value и перерендеривается, только когда меняется именно она. Это та же дисциплина гранулярности подписки, что у любого pub-sub: широкая подписка дёшево пишется и дорого стоит в рантайме.</p>

    <p><strong>Поднятие состояния и его обратная цена.</strong> Стандартный совет — «поднимай состояние вверх, к общему предку». Это правильно для корректности, но у него есть цена производительности, о которой совет молчит: компонент, держащий состояние, перерендеривается на каждое его изменение, и вместе с ним перерендеривается всё его поддерево (с поправкой на bailout-ы). Поднять состояние формы в корень `<App>` означает, что каждое нажатие в форме потенциально перерендеривает весь экран. Поэтому есть встречное правило — <em>опускать состояние вниз</em>, ближе к листьям, которые его реально используют. Если только поле поиска и список результатов читают `searchTerm`, держите его в общем родителе именно этих двух, не выше. Та же логика про производное состояние: значение, которое можно вычислить из props или другого состояния, не должно быть отдельным `useState` — лишний источник истины это лишний триггер re-render и риск рассинхронизации. Дисциплина не «поднимай» и не «опускай», а «держи состояние ровно на том уровне, где живёт наименьшее поддерево, которому оно нужно».</p>

    <h4 class="mt-2 mb-3 text-[15px] font-semibold text-ink tracking-tight">Режим отказа: index-ключи и порча состояния</h4>
    <p><strong>Механизм полностью.</strong> Реконсиляция списка строит map от `key` к старому fiber, потом обходит новых детей, матча каждого к его старому fiber по ключу. Спаренный fiber переносит вперёд всё stateful: значения `useState`, содержимое `useRef`, неуправляемое состояние DOM (напечатанный текст инпута, отмеченность чекбокса, позиция скролла, фокус) и сам DOM-узел. Когда ключи — индексы массива, ключ привязан к позиции, не к идентичности. Вставьте в начало, удалите из середины, отсортируйте или разверните, и маппинг индекс-к-элементу сдвигается, пока маппинг индекс-к-fiber не сдвигается. React добросовестно делает, что вы сказали: он держит состояние fiber-на-ключе-2 и пары его с тем элементом, что теперь на индексе 2. Управляемые props обновляются корректно (они передаются свежими каждый рендер); неуправляемое состояние нет (оно живёт на fiber). Результат — класс багов, проходящий каждый тест на статичных фикстурах и появляющийся только когда реальный пользователь переупорядочивает, удаляет или вставляет. Лечение всегда — ключ, выведенный из стабильной идентичности элемента — никогда индекс, никогда `Math.random()` (который форсирует перемонтаж каждый рендер и уничтожает состояние плюс производительность).</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Двойной буфер и bailout в глубину</h4>
    <p><strong>Bailout: как React пропускает работу.</strong> Не каждый компонент в перерендеривающемся поддереве реально перезапускается. Когда React достигает fiber во время render, он проверяет: изменились ли props (через `Object.is` на каждом props)? изменился ли state? есть ли ожидающее обновление контекста, которое этот fiber потребляет? Если ни одно не верно, React делает <em>bailout</em> — он клонирует fiber из alternate, переиспользует всё существующее дочернее поддерево по ссылке и вообще не вызывает функцию компонента. Поэтому референсная стабильность так важна: ребёнок, обёрнутый в `React.memo`, делает bailout, только если его props референсно равны. Передайте ему инлайновый `{}` или стрелочную функцию как props, и bailout проваливается каждый рендер, потому что свежий литерал никогда не `Object.is`-равен прошлому. `useMemo` и `useCallback` существуют, чтобы сохранить эти ссылки, чтобы bailout мог сработать. Ментальная модель: перерендеривание родителя не автоматически перерендеривает детей — оно предлагает им шанс сделать bailout, и стабильные ссылки — то, что даёт им этот шанс взять.</p>

    <p><strong>Состояние хранится на fiber, не на компоненте.</strong> У функционального компонента нет экземпляра — это просто функция, которую React вызывает. Так где `useState` держит своё значение между рендерами? На fiber. Каждый fiber держит связный список записей хуков, по одной на каждый вызов `useState`/`useReducer`/`useEffect`, в порядке вызова. React продвигает курсор по этому списку, пока ваш компонент вызывает хуки. Это глубокая причина Правил Хуков: хуки должны вызываться безусловно и в том же порядке каждый рендер, потому что React идентифицирует каждый хук чисто по его <em>позиции</em> в последовательности вызовов, не по имени. Поставьте `useState` за `if`, и на рендере, где условие переключается, каждый последующий хук читает неправильную запись. Это также объясняет сохранение состояния: состояние переживает re-render, потому что переживает fiber; состояние уничтожается, когда уничтожается fiber — что происходит на размонтаже, на изменении типа или на изменении ключа.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Lanes, батчинг и прерывание</h4>
    <p><strong>Битовая маска lane.</strong> Lane — это один бит в 31-битном целом. Представление приоритета как битовой маски позволяет React делать операции над множествами одной CPU-инструкцией: «есть ли ожидающие высокоприоритетные lanes?» — это mask-and-test; «отрендерить все lanes на приоритете или выше» — сравнение битовых масок. Когда обновления приходят, каждое назначается lane по своему триггеру — `setState` в обработчике клика получает sync-lane, обновление `startTransition` получает transition-lane, пересчёт `useDeferredValue` тоже получает transition-lane. React выбирает набор непустых lanes высшего приоритета, рендерит его и коммитит. Обновления в совместимых lanes <em>батчатся</em> — несколько вызовов `setState` в одном обработчике события (или, с React 18, через промисы и таймауты через автоматический батчинг) схлопываются в один render. Поэтому вы не можете прочитать новое состояние синхронно сразу после `setState`: render, применяющий его, ещё не случился.</p>

    <p><strong>Прерывание и tearing.</strong> Когда высокоприоритетное обновление приходит посреди transition-render, React выбрасывает полупостроенное дерево workInProgress и начинает заново на более высоком приоритете. Выбрасывание дёшево именно из-за двойной буферизации — дерево workInProgress никогда не коммитилось, поэтому ничего видимого не откатывается. Но прерываемый рендеринг вводит опасность под названием <em>tearing</em>: если внешнее хранилище меняется между двумя срезами времени, компоненты первого среза видели старое значение, а компоненты позднего среза видят новое, поэтому закоммиченный UI внутренне несогласован — «разорван». Именно поэтому существует `useSyncExternalStore`: он даёт React способ обнаружить, что внешнее хранилище изменилось во время конкурентного render-а, и перезапустить render, гарантируя, что каждый компонент в одном commit наблюдал то же значение хранилища. Любая библиотека состояния, интегрирующаяся с React 18 (Redux, Zustand, Jotai), маршрутизируется через `useSyncExternalStore` по этой причине.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Эффекты и их тайминг</h4>
    <p><strong>useLayoutEffect vs useEffect.</strong> Два отличаются тем, <em>когда</em> они гоняются относительно отрисовки. `useLayoutEffect` срабатывает синхронно на шаге layout фазы commit — после мутации DOM, до того как браузер рисует. `useEffect` («пассивный эффект») срабатывает асинхронно <em>после</em> отрисовки, на более поздней задаче. Правило: всё, что должно выполниться до того, как пользователь увидит кадр — измерить только что мутированный DOM-узел и подкрутить компоновку, чтобы предотвратить видимую вспышку — принадлежит `useLayoutEffect`. Всё остальное — загрузка данных, подписки, логирование — принадлежит `useEffect`, потому что делать это в `useLayoutEffect` задерживает отрисовку. Злоупотребление `useLayoutEffect` — реальная INP-регрессия: каждый layout-эффект — синхронная работа фазы commit, отодвигающая отрисовку. Другая ловушка фазы commit — форсированный reflow из пайплайна рендера: `useLayoutEffect`, читающий `getBoundingClientRect`, потом пишущий стиль, триггерит синхронную компоновку внутри commit.</p>

    <p><strong>Suspense и приостановка дерева.</strong> Suspense — это механизм React для дерева, которое «ещё не готово»: компонент, чьи данные или код-чанк не загружены, «приостанавливается» (бросает промис), и ближайший родитель `<Suspense fallback={...}>` показывает fallback вместо него. Под капотом приостановка — это часть модели приоритетов: приостановленное поддерево не блокирует остальное дерево, оно просто откладывается. Senior-тонкость в комбинации с transition: обновление, обёрнутое в `startTransition`, которое приводит к приостановке, <em>не</em> показывает fallback — React держит старый UI на экране, пока новый готовится, и переключает атомарно. Обновление вне transition, наоборот, мгновенно роняет поддерево в fallback. Поэтому навигация между страницами почти всегда оборачивается в transition: иначе каждый переход моргает спиннером, даже если данные приедут через 80 мс. Это та же двойная буферизация на уровне данных: показывай готовое, готовь новое в стороне, переключай разом.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">React Compiler и будущее мемоизации</h4>
    <p><strong>Почему ручная мемоизация, возможно, заканчивается.</strong> Десятилетие держать bailout работающим означало раскидывать `useMemo`, `useCallback` и `React.memo` руками — нудно, ошибкоопасно, и само по себе не бесплатно (каждая memo-ячейка стоит памяти и сравнения). React Compiler (раньше «React Forget», на stable-треке с React 19) — build-time инструмент, анализирующий код компонента и вставляющий мемоизацию автоматически и корректно, на более тонкой грануляции, чем человек. Он понимает, какие значения зависят от каких входов, и мемоизирует ровно их, поэтому bailout срабатывает без всяких рукописных хуков. Senior-вывод: <em>механизм</em> — референсная стабильность, гейтящая bailout — никуда не уходит; это фундамент, на котором строит компилятор. Понимание, почему стабильная ссылка даёт fiber пропустить работу — то, что даёт читать вывод компилятора, дебажить, когда он делает bailout консервативно, и рассуждать о производительности независимо от того, мемоизация рукописная или сгенерированная компилятором.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Stack-реконсилер: чем fiber лучше предшественника</h4>
    <p><strong>Почему fiber вообще появился.</strong> До React 16 реконсилер был «stack reconciler»: реконсиляция была обычной рекурсивной функцией, обходящей дерево компонентов. Рекурсия живёт в стеке вызовов JS-движка, а стек вызовов нельзя приостановить и возобновить — функция либо выполняется до конца, либо нет. Это значило, что весь render для большого дерева был одной неделимой синхронной задачей: начал реконсилить 5 000 компонентов — держи главный поток, пока не закончишь, пропусти все кадры по дороге. Fiber переписал реконсиляцию так, чтобы она не использовала стек вызовов: вместо рекурсии — обход связного списка fiber-узлов с явным курсором. «Стек вызовов» стал структурой данных в куче, которой React владеет и которую может остановить, сохранить и возобновить. Это и есть техническая суть архитектуры fiber: имя — отсылка к «легковесному потоку» (как fiber/coroutine в системном программировании), потому что fiber-дерево — это, по сути, ручная реализация приостанавливаемого стека вызовов поверх обычного JS. Всё конкурентное поведение React 18 — time-slicing, прерывание, приоритеты — было невозможно на stack-реконсилере и стало возможным ровно потому, что fiber вынес стек из движка в управляемую структуру.</p>

<Misconception id="mc-key-index">
**Миф:** `key={index}` нормально — ключи лишь должны быть уникальными.

**Реальность:** ключи идентифицируют элементы *между рендерами*. Индекс — позиция, не идентичность. При переупорядочивании или вставке индексы сдвигаются — React держит состояние fiber, но пары его с неправильным элементом. Нужен стабильный id.
</Misconception>

<KeyTakeaway>Две фазы: render строит дерево workInProgress и прерываем; commit применяет мутации DOM и атомарен. Fiber-ы хранят состояние, поэтому изменение ключа его уничтожает — используйте стабильные id, никогда индекс. Lanes приоритизируют; `startTransition` держит тяжёлый render от блокировки ввода. Референсная стабильность — то, что даёт fiber сделать bailout.</KeyTakeaway>

<p class="text-ink-2 my-6">Fiber — это место, где состояние компонента живёт между рендерами: значения `useState`, ref-ы, список хуков — всё висит на fiber, не на функции компонента. Рендер за рендером fiber переживает и несёт это состояние вперёд; уничтожьте fiber (размонтаж, изменение типа, изменение ключа) — и состояние пропало. Реконсилер — это, по сути, машина для решения, какие fiber-ы выживают, а какие пересобираются — тот же вопрос состояния, о том что переживает переход и что перевыводится, что проходит через каждый слой стека. <SpiralCue thread="statefulness" lang="ru" /></p>
