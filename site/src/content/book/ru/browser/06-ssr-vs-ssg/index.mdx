Пользователь запрашивает страницу. Где-то дерево компонентов превращается в строку HTML, пересекает провод, рисуется и затем — часть, которую все забывают — становится интерактивным. У этого последнего шага есть имя и цена: гидратация. Каждая стратегия рендеринга — это разный ответ на два вопроса: *когда* мы производим HTML, и *что* стоит оживить этот HTML в браузере. Ошибитесь в первом — страница медленно появляется; ошибитесь во втором — страница появляется быстро, но по ней нельзя кликнуть.

<Crux>SSR, SSG, ISR, streaming — *когда* рендерить HTML. Гидратация — цена сделать этот HTML интерактивным.</Crux>

Стратегии расходятся по таймингу. **SSG** рендерит на билде — HTML это файл на CDN. **SSR** рендерит на запрос — свежо, но сервер работает на каждый хит. **ISR** — это SSG, обновляющий себя по расписанию или по требованию. **Streaming SSR** шлёт HTML кусками по мере готовности, не дожидаясь всей страницы. И пересекая все из них: **гидратация** — это React (или любой фреймворк), переисполняющийся на клиенте, чтобы прицепить обработчики событий и состояние к серверному HTML — работа, превращающая картинку приложения в приложение.

    <p><strong>SSG: рендер на билде.</strong> Static Site Generation гоняет компоненты один раз, во время билда, и пишет результат в HTML-файлы. Эти файлы деплоятся на CDN и отдаются как статические ассеты. Путь запроса непобедим — никакого серверного вычисления, попадание в edge-кеш, time-to-first-byte в десятках миллисекунд. Цена — свежесть и масштаб: контент заморожен на момент билда, и сайт на миллион страниц билдится долго. SSG — правильный дефолт для всего, чей контент не меняется на запрос и на пользователя: маркетинговые страницы, документация, посты блога. В момент, когда страница должна отражать «сейчас» или «именно этого пользователя», чистый SSG ломается.</p>

    <p><strong>SSR: рендер на запрос.</strong> Server-Side Rendering гоняет компоненты на сервере на каждый запрос, производя свежий HTML каждый раз. Он может прочесть куки пользователя, текущее время, живые данные — HTML точно правильный для этого запроса. Цена — на критическом пути: time-to-first-byte пользователя теперь включает время серверного рендера плюс любую загрузку данных, которую он делает. Медленный запрос к базе в рендере — это медленный TTFB для пользователя. SSR также означает, что вы гоняете и платите за серверную ёмкость, масштабирующуюся с трафиком. SSR правилен, когда страница реально должна быть свежей на запрос или персонализированной на пользователя — залогиненный дашборд, лента, результаты поиска.</p>

    <p><strong>ISR: SSG, обновляющий себя.</strong> Incremental Static Regeneration (термин Next.js; у других фреймворков есть эквиваленты) — это SSG с правилом ревалидации. Страница отдаётся статически из кеша, но после настроенного времени — или по явному триггеру по требованию — следующий запрос получает протухшую копию, <em>пока</em> сервер регенерирует свежую в фоне; последующие запросы получают новую версию. Это `stale-while-revalidate`, применённый к целым страницам. ISR — ответ на «большей частью статично, но контент всё же меняется — страница товара, чья цена обновляется несколько раз в день». Вы получаете мгновенную доставку SSG для подавляющего большинства запросов и ограниченную протухлость вместо полного ребилда.</p>

    <p><strong>Streaming SSR: отправка HTML кусками.</strong> У обычного SSR есть блокирующий изъян: сервер должен закончить рендер <em>всей</em> страницы — включая её самую медленную загрузку данных — до того, как сможет отправить хоть один байт. Если одному виджету нужен запрос на 400 мс, каждый пользователь ждёт 400 мс на time-to-first-byte. Streaming SSR это чинит. С `renderToPipeableStream` сервер шлёт оболочку немедленно, и каждая граница `<Suspense>` стримится по мере резолва её данных. Пользователь видит шапку, навигацию и лейаут за ~50 мс; медленный виджет приходит на 400 мс позже как стримленный кусок, который браузер вставляет на место. TTFB падает до скорости самой быстрой части страницы, не самой медленной. Streaming превращает «страница ждёт свой худший запрос» в «страница появляется немедленно и заполняется».</p>

    <p><strong>React Server Components: компоненты, никогда не уходящие на клиент.</strong> RSC — совсем другая ось. Server Component гоняется только на сервере — его код никогда не шлётся в браузер. Он может читать базу напрямую, использовать серверные секреты и импортировать тяжёлые библиотеки (markdown-парсер, подсветку синтаксиса), которые ничего не стоят клиенту, потому что никогда не пересекают провод. Его выход — не HTML и не JS-бандл — это специальный сериализованный формат, RSC payload, описывающий отрендеренное дерево. Client Components (помеченные `'use client'`) — интерактивные острова внутри этого дерева; только их код шлётся. Выигрыш — размер бандла: части вашего приложения, которые просто «показывают серверные данные», несут ноль клиентского JavaScript, поэтому нечего скачивать и нечего гидрировать для них.</p>

    <p><strong>Гидратация: цена интерактивности.</strong> Серверный рендеринг даёт вам HTML — пиксели, быстро. Но у этого HTML нет обработчиков событий, нет состояния, нет эффектов. Гидратация — клиентский процесс, чинящий это: фреймворк скачивает свой JavaScript, обходит то же дерево компонентов, что обошёл сервер, и — вместо создания DOM-узлов — <em>усыновляет</em> существующий серверный DOM, цепляя слушатели событий и подключая состояние и эффекты. `hydrateRoot` — точка входа React для этого. Ментальная модель: серверный рендер произвёл тело; гидратация — фреймворк, переисполняющийся, чтобы вложить нервную систему в это тело. Пока гидратация не завершилась для данной части дерева, эта часть видима, но инертна — и в этом зазоре живут INP-регрессии и баги «кликнул, ничего не произошло».</p>

    <p><strong>Почему гидратация дорогая.</strong> Гидратация примерно удваивает работу рендера — дерево рендерится один раз на сервере и фактически рендерится снова на клиенте. Но это хуже, чем удвоение, потому что клиентский рендер гоняется на устройстве <em>пользователя</em>, которое может быть средним телефоном на порядок медленнее вашего сервера. И это всё JavaScript на главном потоке: скачать бандл, распарсить и скомпилировать его (работа <Term k="v8" lang="ru">V8</Term>), потом гонять дерево компонентов и цеплять обработчики. На большом приложении это сотни миллисекунд — секунды времени главного потока, во время которых страница выглядит готовой, но не готова. Вся современная эволюция стратегий рендеринга — selective, progressive, islands, resumability — это серия атак на эту одну цену.</p>

    <p><strong>Full vs selective гидратация.</strong> Классическая гидратация React — <em>полная и нетерпеливая</em>: всё приложение гидрируется одним проходом до того, как что-либо станет интерактивным, и это блокирующе. React 18 ввёл <em>selective hydration</em>: с границами `Suspense` части дерева гидрируются независимо, и React приоритизирует гидратацию того, с чем пользователь только что взаимодействовал. Если пользователь кликает по ещё-не-гидрированной секции, React гидрирует эту секцию первой, впереди остальных. Это также делает гидратацию прерываемой — она может уступить вводу посреди гидратации. Selective hydration не убирает суммарную цену; она переупорядочивает её так, чтобы цена приземлилась туда, куда пользователь не смотрит, а часть, которую он тронул, ожила первой.</p>

    <p><strong>Progressive hydration и архитектура островов.</strong> Более глубокий фикс — гидрировать <em>меньше</em>. Архитектура островов (Astro, Marko, Fresh) стартует от противоположного дефолта: страница — это статический HTML, и только конкретные интерактивные компоненты — «острова» — шлют JavaScript и гидрируются. Пост блога на 95% текст: с островами эти 95% шлют ноль JavaScript и никогда не гидрируются, и только бокс комментариев и кнопка лайка — собственно острова — несут JS. Каждый остров гидрируется независимо, и ему можно сказать, <em>когда</em> (`client:visible` гидрирует при скролле в зону видимости, `client:idle` когда главный поток свободен). Это progressive hydration: страница интерактивна там, где надо, инертна и бесплатна везде ещё.</p>

    <p><strong>Resumability: пропуск гидратации совсем.</strong> Qwik доводит идею до предела через <em>resumability</em>. Вместо переисполнения дерева компонентов на клиенте, чтобы пересобрать состояние и обработчики, Qwik сериализует всё состояние приложения — включая то, какой обработчик к чему прицеплен — в сам HTML. Клиент не перерендеривает, чтобы гидрироваться; он <em>возобновляется</em> с сериализованного состояния, цепляя обработчик только когда пользователь реально взаимодействует с этим конкретным элементом. Стартовый JavaScript приближается к нулю независимо от размера приложения. Компромисс — более сложный формат сериализации и фреймворк, построенный вокруг него с нуля — но концептуально это конечная точка всей прогрессии: от «гидрировать всё» к «гидрировать то, что пользователь тронул» к «не гидрировать вовсе, просто возобновить».</p>

    <p><strong>Hydration mismatch.</strong> Гидратация предполагает, что первый рендер клиента производит ровно тот DOM, что произвёл сервер. Когда нет — вы получаете <em>hydration mismatch</em>. Причины: рендер `new Date()` или `Math.random()` (серверное время ≠ клиентское), чтение `window` или `localStorage` во время рендера (undefined на сервере), различия локали или таймзоны, или браузерные расширения, мутирующие DOM до гидратации. React обнаруживает расхождение и исторически выбрасывал серверный HTML для несовпавшего поддерева и перерендеривал его на клиенте — видимая вспышка контента плюс скачок CLS. Фикс — сделать первый клиентский рендер детерминированно равным серверному: отложить клиентские значения до пост-гидратационного `useEffect` или загейтить их за флагом mounted, чтобы оба рендера сошлись на первом проходе.</p>

    <p><strong>SSR и SEO: почему это до сих пор важно.</strong> Один из исторических мотивов SSR — поисковая индексация. Поисковый бот, получивший пустую оболочку SPA и JS-бандл, должен сам исполнить JavaScript, чтобы увидеть контент — современный Googlebot это делает, но с задержкой и не идеально, а многие другие краулеры (соцсети для preview-карточек, мелкие поисковики) не исполняют JS вовсе. Серверно-отрендеренный HTML отдаёт боту готовый контент сразу, без исполнения. Это касается не только SSR в узком смысле: SSG и ISR дают тот же выигрыш — бот получает полный HTML. Тонкость senior-уровня: для SEO важен не сам факт серверного рендера, а то, что критичный для индексации контент попадает в <em>первый</em> HTML-ответ, а не дорисовывается клиентом после. Поэтому при streaming SSR контент, важный для SEO, должен быть в оболочке или в рано-резолвящейся Suspense-границе, а не за медленной границей, которая стримится последней — иначе бот, не дождавшийся стрима, увидит страницу без него.</p>

    <p><strong>Гидратация и порядок: партиал и островная независимость.</strong> Тонкость, которую упускают: классическая полная гидратация не просто дорогая — она ещё и «всё или ничего» по доступности интерактивности. Пока единый проход гидратации не дошёл до конца, ни одна кнопка на странице не работает, даже та, чей JS уже скачан и распарсен. Selective hydration и острова ломают эту связку: единица гидратации становится границей (Suspense-boundary или остров), и каждая единица оживает независимо от других. Практическое следствие для проектирования: размещение границ — это карта приоритетов интерактивности. Кнопка «В корзину» на странице товара должна быть в своей маленькой, рано-гидрируемой единице; галерея отзывов внизу страницы — в отдельной, поздней. Без явных границ фреймворк гидрирует в порядке обхода дерева, и кнопка в подвале может ожить раньше кнопки в шапке просто из-за позиции в JSX. Граница — это инструмент сказать «вот это оживи в первую очередь».</p>

    <h4 class="mt-2 mb-3 text-[15px] font-semibold text-ink tracking-tight">Режим отказа: hydration mismatch</h4>
    <p><strong>Механизм, точно.</strong> Гидратация — это контракт: DOM, который клиент производит на своём первом рендере, должен быть структурно идентичен DOM, который сервер сериализовал. React обходит серверный DOM и виртуальное дерево клиента в ногу, усыновляя каждый узел. Когда узел расходится — другой текст, другие атрибуты, другой элемент, лишний или отсутствующий ребёнок — контракт нарушен. Восстановление React ужесточалось от версии к версии: он логирует ошибку несовпадения и для затронутого поддерева выбрасывает серверный HTML и рендерит его на клиенте с нуля. Этот восстановительный рендер — видимый симптом: вспышка изменённого контента и layout shift, взрывающий CLS. Частые причины — все формы недетерминизма между двумя средами: `Date.now()`, `Math.random()`, `window`/`document`/`localStorage`, прочитанные во время рендера, `Intl`-форматирование, зависящее от локали или таймзоны, ветки `typeof window`, и браузерные расширения, мутирующие DOM до того, как React гидрируется. Лечение — детерминизм: первый клиентский рендер должен быть чистой функцией от тех же входов, что были у сервера. Клиентские значения переезжают в `useEffect` (который гоняется после гидратации) или за флаг `useState(false)` «mounted», переключаемый в эффекте, чтобы и серверный рендер, и первый клиентский рендер произвели плейсхолдер, и только второй клиентский рендер показал живое значение.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Внутренности streaming SSR</h4>
    <p><strong>Как собирается стрим.</strong> `renderToPipeableStream` рендерит дерево в глубину и сбрасывает оболочку — всё вне любой ожидающей границы `Suspense` — как только она готова. Для каждой границы `Suspense`, чьи данные не резолвнулись, сервер эмитит fallback инлайн и держит соединение открытым. Когда данные границы резолвятся, сервер рендерит реальный контент этой границы и пишет его в то же соединение куском: скрытый `<div>`, несущий контент, плюс крошечный инлайновый `<script>`, релоцирующий его в правильный слот и убирающий fallback. Браузер, парся HTML прогрессивно, исполняет этот скрипт в момент прихода куска. Поэтому streaming работает без участия клиентского кода фреймворка для самого размещения — релокация это обычный DOM-скриптинг, встроенный в стрим. Порядок интересен: границы стримятся в <em>порядке завершения</em>, не в порядке документа, поэтому быстрый виджет внизу страницы может прийти раньше медленного виджета выше него.</p>

    <p><strong>Streaming и гидратация переплетаются.</strong> Streaming SSR и selective hydration спроектированы композироваться. Как только HTML каждой границы `Suspense` стримится, React на клиенте может гидрировать эту границу независимо — он не ждёт весь документ. И если пользователь взаимодействует с уже-стримленной-но-ещё-не-гидрированной границей, React записывает событие и приоритизирует гидратацию этой границы первой, потом переигрывает событие. Результат — «застримлено» и «гидрировано» оба погранично и оба приоритизируются вниманием пользователя. Senior-следствие: где вы размещаете границы `Suspense` — это перформанс-дизайн-решение, не просто решение про состояние ошибки/загрузки. Граница вокруг медленного виджета ниже сгиба позволяет остальной странице стримиться и гидрироваться, не дожидаясь его; нет границы — и этот виджет блокирует весь документ.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">RSC: payload и граница</h4>
    <p><strong>Что реально пересекает провод.</strong> RSC-рендер производит две вещи. Начальный запрос получает HTML (Server Components, отрендеренные в HTML, стримленные) <em>плюс</em> RSC payload — сериализованное, построчно-разделённое описание дерева компонентов, где Client Components появляются как ссылки («модуль X, props Y»), а не как код. На клиентской навигации фетчится только RSC payload, не свежий HTML-документ — React применяет его к существующему дереву. Директива `'use client'` помечает границу: модуль с этой директивой, и всё, что он импортирует, — в клиентском бандле; всё выше него в дереве серверное. Тонкое и часто упускаемое правило: props, передаваемые из Server Component в Client Component, должны быть сериализуемыми — они пересекают провод в payload. Нельзя передать функцию, экземпляр класса или Date-с-методами как props через эту границу. Правильное размещение границы — толкая `'use client'` как можно ниже по дереву — это то, что минимизирует клиентский бандл.</p>

    <p><strong>RSC — не замена SSR, он композируется с ним.</strong> Частая путаница: RSC и SSR — разные оси. SSR — «где генерируется HTML»; RSC — «какие компоненты вообще шлют код на клиент». Продакшен-страница Next.js App Router обычно использует оба: Server Components гоняются на сервере и производят HTML через SSR (часто стримленный), и Client Components внутри тоже серверно-рендерятся в HTML для первой отрисовки и <em>потом гидрируются</em>. RSC уменьшает, сколько надо гидрировать (Server Components никогда не гидрируются — у них нет клиентского кода); SSR/streaming контролирует, когда HTML появляется. Это ортогональные инструменты, которые современный фреймворк использует вместе.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Модель стоимости гидратации в глубину</h4>
    <p><strong>Куда уходят миллисекунды.</strong> У стоимости гидратации четыре части, все на главном потоке, все после того, как HTML уже нарисован. Один: <em>скачать</em> JavaScript-бандл — сетевая работа, митигируется код-сплиттингом и сжатием. Два: <em>распарсить и скомпилировать</em> JavaScript — работа V8, масштабируется с байтами бандла, жестока на слабых мобильных CPU. Три: <em>исполнить</em> — гонять верхний уровень модуля и дерево компонентов, чтобы пересобрать виртуальное дерево. Четыре: <em>прицепить</em> — обойти серверный DOM, усыновляя узлы и подключая обработчики. Части два и три — почему размер бандла важен сверх времени скачивания: бандл на 500 КБ — это не просто 500 КБ сети, это сотни миллисекунд parse-compile-execute на телефоне. Всё это окно — «зловещая долина» SSR — страница нарисована и выглядит интерактивной, пользователь пытается взаимодействовать, и ввод либо отбрасывается, либо встаёт в очередь за длинной задачей гидратации, взрывая INP. Измерение: зазор между First Contentful Paint и Time to Interactive, и полевой INP на взаимодействиях, случающихся рано в жизни страницы.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Выбор стратегии: рамка решения</h4>
    <p><strong>На маршрут, не на приложение.</strong> Senior-ошибка — выбрать одну стратегию для всего приложения. Современные фреймворки дают выбирать на маршрут, и так и надо. Рамка решения: контент одинаков для всех? Если да и он редко меняется — SSG. Если да и он меняется на известной частоте — ISR. Он на пользователя или свежий на запрос? Тогда SSR, и если у любой его части есть медленная зависимость данных — streaming SSR с границей `Suspense` вокруг медленной части. Маршрут — большей частью статический контент с несколькими интерактивными битами? Это случай островов — и даже внутри React это маппится в большей частью Server Components с маленькими `'use client'`-листьями. Маркетинговая главная, документация, блог: SSG. Страница цен с ежедневно меняющимся числом: ISR. Залогиненный дашборд: streaming SSR. То же приложение, три стратегии, выбранные по природе данных и интерактивности каждого маршрута.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">ISR на грани: кеш, инвалидация, сборка</h4>
    <p><strong>Что делает ISR действительно сложным.</strong> На картинке ISR прост — «статика, которая иногда обновляется». В продакшене он несёт все классические проблемы кеша. Первое: где живёт регенерированная страница. На одном сервере это файл; на распределённой платформе (Vercel, Cloudflare) есть множество edge-узлов, и регенерация на одном не обновляет остальные мгновенно — пользователь может получить свежую версию в одном регионе и протухшую в другом, пока инвалидация распространяется. Второе: stampede. Если популярная страница протухает, и тысяча запросов приходит в окно регенерации, наивная реализация запускает тысячу регенераций; нужен single-flight — первый запрос регенерирует, остальные получают stale, пока он не закончит. Третье: on-demand инвалидация. Ревалидация по таймеру проста, но «обнови страницу товара ровно когда менеджер изменил цену» требует, чтобы бэкенд звал webhook инвалидации, и этот вызов сам может потеряться или прийти дважды. Четвёртое: согласованность с другими страницами. Цена изменилась — обновить надо не только страницу товара, но и страницу категории, и главную, где этот товар в подборке; забытая зависимость — это протухший фрагмент, который никто не заметит неделями. ISR — это `stale-while-revalidate` уровня страниц, и он наследует ровно те же ловушки, что кеширование на любом другом слое стека: инвалидация кеша остаётся одной из двух труднейших задач в computer science независимо от того, на каком слое её решать.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Production-наблюдаемость</h4>
    <p><strong>Что измерять и где ломается.</strong> Четыре сигнала ловят режимы отказа всего этого пространства. <em>TTFB</em> в поле отделяет медленный серверный рендер или отсутствующий кеш от быстрого — регрессия TTFB на SSR-маршруте обычно означает, что медленная загрузка данных прокралась в путь рендера. <em>LCP</em> говорит, в стримленной ли оболочке самый крупный контент или застрял за медленной границей. <em>INP</em> на ранних взаимодействиях — детектор зловещей долины гидратации: высокий INP только для взаимодействий в первые секунды — это гидратация, блокирующая главный поток. <em>Ошибки hydration mismatch</em> должны быть подключены к телеметрии, не только к консоли — они вызывают CLS и стоимость перерендера, и они невидимы, пока вы их не собираете. CI-гейт: синтетический тест, грузящий каждый тип маршрута, утверждающий ноль ошибок hydration-mismatch и бюджетирующий зазор FCP-to-TTI. Без этого гейта недетерминированный рендер или регрессия размера бандла отгружается молча и всплывает только как полевой INP неделями позже.</p>

          ),
        },
      }}
    />
  </Fragment>
</TierAccordion>

<Misconception id="mc-hydration-mismatch">
**Миф:** серверно-отрендерено значит быстро — если HTML нарисовался, страница готова.

**Реальность:** нарисовано — не интерактивно. Гидратация должна скачать, распарсить и запустить JS, чтобы прицепить обработчики — пока она не закончит, кнопки мертвы. «Выглядит готовым» и «работает» — разные моменты.
</Misconception>

<KeyTakeaway>SSG рендерит на билде, SSR на запрос, ISR обновляет статику по расписанию, streaming сбрасывает оболочку первой. Гидратация — отдельная, ~2× цена сделать этот HTML интерактивным. Срезайте её: Server Components не шлют клиентский код, острова гидрируют только интерактивные части. Держите рендеры детерминированными, иначе hydration mismatch мигает и сдвигает страницу. Выбирайте на маршрут.</KeyTakeaway>

<p class="text-ink-2 my-6">Гидратация — это, по сути, вопрос состояния: сервер произвёл рендер, чьё состояние — props, данные, момент времени — должно быть реконструировано идентично на клиенте, иначе контракт ломается. SSG замораживает это состояние на билде; SSR захватывает его на запрос; resumability сериализует его целиком, чтобы клиент никогда его не перевычислял. Каждая стратегия здесь — разное решение о том, какое состояние захвачено когда и что стоит перенести его через провод — тот же вопрос состояния, что решает, дёшево соединение возобновить или дорого пересобрать. <SpiralCue thread="statefulness" lang="ru" /></p>
