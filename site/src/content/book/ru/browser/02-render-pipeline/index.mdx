Вы нажали Enter на URL. Байты пошли. Где-то между первым пакетом и моментом, когда кнопка становится кликабельной на экране, браузер прогнал шестистадийный пайплайн — и большинство страниц тратят неправильное количество времени на неправильной стадии. Бюджет кадра — 16.67 мс при 60 fps. Если компоновка заняла 12 мс, всё остальное не успевает, кадр пропускается, пользователь видит дёрганья.

<Crux>От байтов в кабеле до пикселей на экране — куда уходит время?</Crux>

Работу делают два потока. **Главный поток** владеет парсингом HTML, построением CSSOM, пересчётом стилей, компоновкой и подготовкой отрисовки. **Поток композитора** собирает GPU-дружественные слои и отправляет их на GPU. Анимации, которые остаются на композиторе, стоят почти ничего за кадр. Анимации, скатывающиеся обратно в компоновку, съедают весь бюджет. Всё мастерство производительности рендера — держать работу на правильном потоке.

    <p><strong>Модель процесса рендерера.</strong> Современный браузер семейства Chromium запускает каждую вкладку в отдельном процессе рендерера. Внутри этого процесса: <strong>главный поток</strong> исполняет парсинг HTML, построение CSSOM, стили, компоновку, подготовку отрисовки и ваш JavaScript. <strong>Поток композитора</strong> собирает дерево слоёв и решает, каким слоям нужны новые bitmap-ы. <strong>Растровые рабочие потоки</strong> параллельно растеризуют отдельные тайлы. Отдельный <strong>GPU-процесс</strong> берёт растеризованные тайлы, грузит их как текстуры и выполняет финальный композит-и-показ. Firefox использует похожее разделение (Quantum CSS для параллельных стилей, WebRender для GPU-driven композитинга); Safari/WebKit разделяет работу между WebContent-процессом и GPU-процессом. Имена разные, архитектурная рифма универсальна.</p>

    <p><strong>Почему главный поток — бутылочное горлышко.</strong> Главный поток однопоточный по дизайну — DOM, CSSOM и состояние JS могут изменяться только одним контекстом исполнения за раз, иначе согласованность невозможна. Это значит, любая работа на главном потоке (парсинг JSON-блоба, десериализация Redux-стейта, исполнение компоновки, обработчик клика) конкурирует за то же окно в 16.67 мс. Композитор и растровые потоки существуют именно для того, чтобы кусок работы рендеринга мог уйти с главного потока и работать параллельно — это архитектурное обоснование того, что transform/opacity-анимации «бесплатные»: они достигают GPU, не трогая узкое горло главного потока.</p>

    <p><strong>Правило инвалидации.</strong> Изменение CSS-свойства инвалидирует одну или несколько стадий. Width и height инвалидируют компоновку (всё ниже по потоку перезапускается). Background-color инвалидирует только отрисовку. Transform и opacity инвалидируют только композитинг — GPU переставляет тот же bitmap в новое положение. <a href="https://csstriggers.com/">csstriggers.com</a> публикует карту по свойствам; выучите дешёвые (transform, opacity, filter) и дорогие (top, left, width, height, всё, что влияет на flow).</p>

    <p><strong>Как распространяется инвалидация.</strong> Каждая стадия помечает свой выход dirty, когда меняется вход. Style-флаги распространяются по DOM-дереву (смена класса на родителе делает dirty всех потомков, чьи селекторы матчатся). Layout-флаги — по box-дереву (изменение width у родителя может сделать dirty сиблингов, если их позиция от него зависит). Paint-флаги — по paint-дереву (paint-меняющее изменение на слое инвалидирует bitmap этого слоя; сиблинг-слои не затронуты, если у них свой bitmap). Композитинг — стадия без грязи: работает с уже растеризованными тайлами и лишь перезапускает GPU draw call. Чистое правило распространения: <em>dirty-биты текут вниз по графу зависимостей, не вверх</em>. Если удаётся изолировать изменения в независимом поддереве (contained-слой, родитель с `contain: layout`, элемент с `content-visibility: auto`), инвалидация останавливается на границе изоляции.</p>

    <p><strong>Усилители цены по стадиям.</strong> У каждой стадии есть типовые рычаги, раздувающие её цену. Парсинг HTML масштабируется с байтами документа; SSR-страница 500 КБ парсится быстрее, чем 2 МБ, просто потому что меньше байт ходить. Синхронные тэги `<script>` блокируют парсер до окончания загрузки и исполнения — современная практика ставит `defer` или `async` на всякий внешний скрипт, не строго нужный для первой отрисовки. Цена CSSOM растёт с байтами стилей и кол-вом правил; неиспользуемый CSS-фреймворк на 800 правил тратит время парсинга, даже если ноль правил матчатся. Цена пересчёта стилей примерно <code>размер DOM × селекторы</code>: DOM на 5 000 нод плюс 2 000 правил — 10 миллионов проверок мэтчинга. Большинство селекторов отсеивается bloom-фильтром, но `:has()`, descendant combinators без anchor-предка и универсальные селекторы пробивают фильтр и стоят дороже. Цена компоновки примерно <code>глубина DOM × зависимости между коробками</code>: глубоко вложенный flexbox с auto-размерами требует нескольких проходов измерения; плоский grid с явными размерами ячеек — одного. Цена отрисовки — площадь × кол-во paint-операций; box-shadow с большим blur radius и filter-свойства (blur, drop-shadow) тяжелы для отрисовки, потому что каждый пиксель требует мульти-пиксельной выборки. Цена композитинга — кол-во слоёв × площадь пикселей слоя. Дешёвые стадии дешевле на порядки — но только если верхние стадии не инвалидируют нижние.</p>

    <p><strong>Как браузер доходит до композитора.</strong> Некоторые элементы получают свой слой: с <code>transform: translate3d(...)</code>, <code>will-change: transform</code>, <code>position: fixed</code>, video, canvas, анимированный opacity, плюс несколько других триггеров. Каждый слой растеризуется один раз (отрисовка), грузится на GPU, потом дёшево пересобирается следующие тысячу кадров. Анимация transform слоя — «бесплатно», главный поток может спать. Анимация его <code>top</code> — дорого, главный поток перекомпоновывает мир каждый кадр.</p>

    <p><strong>Правила создания слоёв в деталях.</strong> Продвижение в слой не всегда под вашим контролем. Неявные продвижения происходят для: 3D-трансформаций (всё с компонентой `Z` или `translate3d`), элементов с `will-change`, перечисляющим компонуемое свойство, position-fixed элементов, video, canvas, opacity в процессе анимации, `filter: blur(...)` и других графических фильтров, изолированных <Term k="stacking_context" lang="ru">stacking-контекстов</Term>, перекрывающих слой. Есть также <em>compositing reasons</em>, которые браузер придумывает сам: элемент обязательно продвигается, если перекрывает другой слой и иначе был бы порезан на куски. Поэтому один невинный `transform` может внезапно продвинуть дюжину соседних элементов — инвариант композитора в том, что слои не могут видимо пересекать друг друга, не будучи слоями. Используйте панель Rendering в DevTools («Layer Borders»), чтобы увидеть, что продвинуто; страница часто содержит больше слоёв, чем вы ожидали.</p>

    <p><strong>Чтение flame strip в DevTools Performance.</strong> Откройте DevTools → Performance, нажмите запись, сделайте всё, что вызвало jank, остановите запись. Дорожка «Main» показывает работу главного потока цветом по категории: жёлтый для скриптинга, фиолетовый для рендеринга (компоновка + стили), зелёный для отрисовки, тёмно-синий для композитинга. Дорожка «Frames» показывает зелёный для кадров вовремя, жёлтый для опоздавших, красный для пропущенных. Flame strip складывает вызовы сверху вниз: верхняя полоса — что запустил JS, каждая ниже — что та вызвала. Найдите длинную полосу в красном или жёлтом — это ваше бутылочное горлышко. Hover показывает точные мс. Типичные паттерны: жёлтая JS-полоса, за которой идёт фиолетовая Layout-полоса похожей длины, значит JS форсировал синхронную компоновку (один из самых частых багов). Широкая фиолетовая Recalculate Style после смены класса на высоком предке — слишком сильный каскад. Широкая зелёная Paint после смены `filter: blur(...)` — превышена сложность отрисовки. Широкая тёмно-синяя Composite Layers, когда больше ничего не выглядит плохо, — слишком много слоёв, часто из-за злоупотребления will-change.</p>

    <p><strong>Современные ключи оптимизации: contain и content-visibility.</strong> CSS Containment даёт ручку, ограничивающую распространение инвалидации. <code>contain: layout</code> говорит браузеру «компоновка этого элемента не может затронуть предков» — если ребёнок ресайзится, сиблинги родителя не нужно перекомпоновывать. <code>contain: paint</code> гарантирует, что отрисовка ограничена коробкой (всё переполнение клипуется) и разрешает браузеру вообще пропустить отрисовку, когда элемент за пределами экрана. <code>contain: strict</code> комбинирует layout, paint и size containment. Более новое свойство <code>content-visibility: auto</code> идёт дальше: говорит браузеру «этот элемент можно полностью пропустить (без компоновки, без отрисовки), когда он за пределами экрана». В паре с <code>contain-intrinsic-size</code> (даёт браузеру placeholder-размер для резервирования) это позволяет странице с тысячами элементов ниже первого экрана рендериться за миллисекунды, потому что только видимые элементы платят цену. Это современные «бесплатные победы» для страниц с длинными списками, infinite scroll-лентами и длинным контентом.</p>

    <p><strong>Жизненный цикл кадра и порядок планировщика.</strong> Внутри одного кадра браузер запускает работу в строгом порядке: (1) собирает события ввода (mousemove, keypress); (2) исполняет запланированные `setTimeout` и `setInterval`, если их время пришло; (3) дренирует микротаски (резолвы промисов) до пустой очереди; (4) исполняет колбэки `requestAnimationFrame`; (5) исполняет ResizeObserver и IntersectionObserver-колбэки; (6) считает стили и компоновку; (7) отрисовка; (8) композитинг. После шага 8 браузер уступает ОС и ждёт следующего <Term k="vsync" lang="ru">vsync</Term>. Ключевое свойство: rAF идёт <em>до</em> стилей/компоновки, поэтому запись внутри rAF влечёт ровно один проход компоновки за кадр — в этом весь смысл rAF. ResizeObserver срабатывает <em>после</em> компоновки, но <em>до</em> отрисовки; можно реагировать на изменения компоновки, не вызывая ещё одной форсированной. IntersectionObserver срабатывает асинхронно между кадрами и никогда не блокирует текущий. Понимание этого порядка отделяет «трюки планирования, которые работают» от «трюков, которые тихо thrashят».</p>

    <p><strong>Микротаски vs таски: как работают границы планирования.</strong> Очередь микротасок (промисы, queueMicrotask) дренируется до пустой между каждым шагом event loop, включая между rAF-колбэками. Плохо ведущая себя цепочка промисов, бесконечно планирующая саму себя, голодит рендеринг — браузер не может дойти до шага 6, пока очередь не опустеет. Поэтому длинные цепочки промисов и плотные `await`-циклы в DevTools видны как одна непрерывная жёлтая полоса скриптинга, а не серия мелких. Современный код, желающий уступить рендереру в середине задачи, использует `scheduler.yield()` (Scheduler API, Chrome 115+) или намеренный `setTimeout(fn, 0)`, чтобы скинуть работу в очередь макротасок и разблокировать рендеринг.</p>

    <p><strong>Реактивные UI-фреймворки и пайплайн.</strong> Когда React делает re-render, DOM обновляется на главном потоке, потом запускается пайплайн стилей и компоновки на тех узлах, что изменились. Reconciliation сам по себе чистый JS на главном потоке — он попадает в желтую полосу скриптинга в DevTools. Если ваш re-render задевает узел около вершины дерева, инвалидация стилей каскадирует вниз по дереву; если задевает изолированный лист, инвалидация локальна. Поэтому ключевая практика — держать состояние локально, ближе к листам, чем можно: `useState` в листовом компоненте инвалидирует один узел; `useContext` на верхнем provider-е может инвалидировать сотни. То же про Svelte stores, MobX наблюдаемые, Vue refs: каждая модель реактивности в конечном счёте записывает в DOM, и DOM-запись запускает тот же пайплайн.</p>

    <p><strong>Тип шрифта и FOIT/FOUT.</strong> Шрифт — это входной байт для пайплайна, который часто упускают. Веб-шрифт начинает грузиться, когда CSS-парсер видит `font-family`, использующий font-face, у которого есть свойство `src`. Пока шрифт не пришёл, браузер либо показывает текст шрифтом-фоллбэком (FOUT, flash of unstyled text), либо прячет текст совсем (FOIT, flash of invisible text). Свойство `font-display` управляет этим: `swap` — фоллбэк сразу, потом сменить; `optional` — фоллбэк, если шрифт не успел за ~100 мс; `block` — спрятать до 3 секунд (старый FOIT). При смене шрифта на загруженный браузер запускает пересчёт стилей и компоновку, потому что метрики шрифта меняют ширину текста, что меняет размеры коробок. На странице с большим текстовым блоком эта смена видна как кадровый jank через 200–500 мс после первой отрисовки.</p>

    <p><strong>Изображения и пайплайн.</strong> Изображение, загружающееся без указанной ширины и высоты, форсирует перекомпоновку, как только грузится: коробка картинки была 0×0, стала фактическим размером, всё вокруг сдвигается. Это главная причина CLS-регрессий. Лечение — задавать explicit width/height в HTML или ставить `aspect-ratio` в CSS; браузер тогда резервирует место заранее, и загрузка изображения становится только paint-инвалидацией, без layout. Современное `loading="lazy"` грузит off-screen изображения лениво, экономя bandwidth и время до первой отрисовки страницы, но всё равно нужны заранее заданные размеры, иначе вылезет layout shift в момент попадания изображения во viewport.</p>

    <h4 class="mt-2 mb-3 text-[15px] font-semibold text-ink tracking-tight">Режим отказа: layout thrash</h4>
    <p><strong>Форсированная синхронная компоновка (layout thrash).</strong> Компоновка работает по dirty-флагам: браузер батчит записи стилей и сбрасывает их только когда нужна актуальная геометрия. Патологический случай — цикл read-then-write в JS:</p>

```javascript
for (const row of rows) {
  const w = row.offsetWidth;     // чтение → форсирует сброс отложенных записей
  row.style.width = w + 10 + 'px'; // запись → снова помечает компоновку dirty
}
```

    <p>Каждая итерация заставляет браузер посчитать компоновку, чтобы ответить на <code>offsetWidth</code>, и тут же делает компоновку dirty для следующей итерации. N строк = N полных компоновок. Список на 5000 строк по 1 мс на компоновку = 5 секунд блокировки главного потока. DevTools показывает это как фиолетовую полосу «Layout» и предупреждение «Forced reflow while executing JavaScript took XX ms» в консоли.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Слои композитора и GPU-память</h4>
    <p><strong>Создание слоёв композитора.</strong> Слои не бесплатны. Каждый слой — это GPU-bitmap, стоящий памяти (ширина × высота × 4 байта) и одной разовой отрисовки. На телефоне с 256 МБ GPU-памяти пятьдесят слоёв 1080p выжигают бюджет; браузер вытесняет слои, на лету перерастеризует, и страница дёргается сильнее, чем без слоёв вообще. <code>will-change: transform</code> — это подсказка «этот элемент будет анимирован, продвинь его в слой». Используйте на время анимации, потом убирайте. Раскидать <code>will-change: *</code> по сотне элементов — анти-паттерн will-change: вы меняете известную стоимость анимации на неизвестный счёт за память.</p>

    <p><strong>Почему composite-only анимации особенные.</strong> Как только элемент стал слоем, главный поток отрисовывает его один раз. С этого момента поток композитора — единственный потребитель изменений <code>transform</code> и <code>opacity</code>; главный поток может быть занят парсингом 200 КБ JSON, а анимация всё равно идёт на 60 fps. Это архитектурная причина, почему transform-анимации обгоняют top/left на порядки — не «GPU быстрее», а «медленный поток больше не в цикле».</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Двухпоточная архитектура: BeginMainFrame</h4>
    <p><strong>BeginMainFrame: рукопожатие между потоками.</strong> В процессе рендерера Chromium поток композитора — водитель, главный поток — рабочий. Каждый vsync композитор шлёт сообщение <code>BeginMainFrame</code> главному потоку. Главный поток исполняет всю покадровую работу (rAF-колбэки, стили, компоновку, подготовку отрисовки) и шлёт обратно <code>CommitMainFrame</code>, передавая новое дерево слоёв. Композитор берёт новое дерево, просит растровые воркеры заполнить грязные тайлы bitmap-ами, потом делает GPU draw. Если главный поток слишком медленный, композитор не ждёт: отправляет дерево предыдущего кадра ещё раз (кадр «нарисован, но устарел»), что пользователь воспринимает как пропущенный ввод или заикание. Это глубокая причина того, почему работа главного потока не может превысить бюджет кадра: композитор — неумолимый метроном, который не договаривается. <code>BeginMainFrame</code> приходит каждые ~16.67 мс независимо от того, готов ли ты.</p>

    <p><strong>Composite-driven анимации (CSS-анимации на transform/opacity).</strong> Когда вы пишете CSS-анимацию, меняющую только <code>transform</code> или <code>opacity</code> у композитор-продвинутого элемента, браузер обнаруживает это на старте анимации и передаёт её timeline напрямую потоку композитора. С этого момента главный поток вообще не задействован — композитор интерполирует значение кадр за кадром и рендерит следующий bitmap напрямую. Поэтому CSS-анимация может плавно идти, даже когда главный поток полностью заблокирован (alert-диалог, длинный синхронный парсинг, пауза дебаггера): композитор продолжает работать. Та же анимация на JS через rAF так не может, потому что rAF идёт <em>на главном потоке</em>, заблокированный главный поток замораживает анимацию. Composite-driven CSS-анимации — единственный способ гарантировать непрерывность анимации под давлением на главный поток.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Граничные случаи композитора</h4>
    <p><strong>Layer squashing и overlap-induced продвижение.</strong> Тонкий источник «взрыва слоёв» — правило перекрытия. Композитор должен сохранять визуальную корректность: если элемент A стал слоем (например, из-за `transform`) и элемент B рисуется поверх A в порядке документа, не будучи слоем, композитор не может разрешить их stacking — слой A окажется поверх B, хотя B должен быть сверху. Браузер чинит это, продвигая B тоже в свой слой, часто притягивая соседние элементы. Затем композитор squashит соседние неанимирующиеся слои в общий «squashed» слой, чтобы ограничить взрыв, но эвристика несовершенна. Один невинный `will-change: transform` на карточке посередине ленты может продвинуть дюжину сиблингов. Используйте панель Rendering в DevTools → «Layer Borders» для визуализации; обращайте внимание на слои с пометкой «compositor-induced» или «overlap» — это те, что прокрались без вашего запроса.</p>

    <p><strong>Off-main-thread scroll.</strong> Браузеры уже десять лет имеют скролл на потоке композитора: когда пользователь скроллит обычную страницу, композитор перемещает viewport на GPU, не трогая главный поток. Поэтому страница может плавно скроллиться, даже пока идёт длинная JS-задача. Подвох: любой элемент с JS-обработчиком scroll, прицепленным <em>non-passively</em> (без <code>&#123;passive: true&#125;</code>), форсирует браузер откатиться к main-thread scrolling, потому что обработчик может вызвать <code>preventDefault()</code>. Всегда передавайте <code>passive: true</code> в scroll-, wheel- и touchmove-listener-ы, если только реально не нужен preventDefault. Современные браузеры предупреждают в DevTools, когда non-passive listener задерживает скролл — это один из самых надёжных сигналов регрессии скролла на главном потоке.</p>

    <p><strong>content-visibility: auto и display locking.</strong> Механизм за <code>content-visibility: auto</code> — «display locking»: браузер ставит на паузу рендеринг для запертого поддерева (без пересчёта стилей, без компоновки, без отрисовки) и заменяет его placeholder-ом intrinsic-размера. Когда поддерево пересекается с viewport (через внутренний IntersectionObserver браузера), оно отпирается и рендерится. Это превращает таблицу 10 000 строк, ранее стоившую 1 200 мс стилей + компоновки, в ~10 мс первой отрисовки с on-demand рендерингом по мере скролла. Компромисс: скролл в ранее запертую область кратко паузится, чтобы её отрендерить; если строки дорогие, видно одно-кадровое заикание на границе разлочки. Пара с <code>contain-intrinsic-size</code> даёт браузеру реалистичный placeholder-размер, чтобы scroll-позиция не прыгала.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Production-наблюдаемость</h4>
    <p><strong>Long animation frames и INP.</strong> Два новых API браузера выводят на поверхность режимы отказа пайплайна рендера. <code>PerformanceLongAnimationFrameTiming</code> (LoAF, отгружено в 2023–2024 в Chromium) репортит любой кадр дольше 50 мс с разбивкой по тому, что доминировало: render time, блокирующий JS, форсированная компоновка. <strong>INP</strong> (Interaction to Next Paint) измеряет время от события ввода (клик, нажатие, тап) до следующей отрисовки, видимо отвечающей. INP стал Core Web Vital в марте 2024, заменив FID. Плохой INP (> 200 мс p75) почти всегда трассируется к одной из двух проблем пайплайна: длинная JS-задача в обработчике ввода задерживает rAF, или форсированная синхронная компоновка из чтения геометрии внутри обработчика. LoAF даёт данные для атрибуции в продакшене; INP даёт метрику, которую чувствует пользователь. Вместе они замыкают цикл от телеметрии в продакшене к конкретным диагностикам пайплайна рендера.</p>

    <p><strong>Reduced-motion как клапан сброса render-бюджета.</strong> Спецификация CSS Media Queries Level 5 определяет <code>@media (prefers-reduced-motion: reduce)</code>, выставленное пользователями, страдающими укачиванием от движения или желающими меньшего потребления питания. Помимо доступности, это полезный клапан сброса render-бюджета: любая composite-driven анимация может быть заменена мгновенной сменой состояния при включённом reduced-motion, полностью освобождая композитор от покадровой работы. Пользователи с ограничениями по батарее на бюджетном Android-телефоне получают заметную экономию батареи от страницы, уважающей этот сигнал.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Собираем всё вместе</h4>
    <p><strong>Полная поверхность атаки для медленной страницы — итог.</strong> Любая страница, проседающая ниже 60 fps, платит цену главного потока, которую платить не должна. Поверхность атаки: parser-blocking скрипты, задерживающие первую отрисовку; раздутый CSS, форсирующий большое построение CSSOM; сложные селекторы, пробивающие bloom-фильтр; глубокие flexbox/grid-иерархии, требующие мульти-проходной компоновки; paint-heavy свойства (большой box-shadow, filter); переполнение слоёв от злоупотребления will-change; форсированная синхронная компоновка из чтения геометрии между записями; non-passive scroll-listener-ы, откатывающие на main-thread scrolling; задачи дольше 50 мс, репортуемые LoAF; обработчики ввода, задерживающие rAF и раздувающие INP. Каждый — свой специфический режим отказа, корнящийся в одном и том же пайплайне. Лечение всегда одной формы: определить стадию, делающую работу, потом или сократить вход в неё, или изолировать ущерб через contain/content-visibility, или переместить работу на другой поток.</p>

    <p><strong>Тестирование производительности рендера в CI.</strong> Бюджеты держатся, только когда регрессии ловятся до мержа. Реалистичный CI-пайплайн комбинирует три уровня. Первый — Lighthouse CI в headless Chrome на каждом PR; гейтит на абсолютных метриках (LCP < 2.5 s, INP < 200 ms, CLS < 0.1) и блокирует мерж при регрессии. Второй — синтетические бенчмарки на критических сценариях (открыть страницу, скроллить список 1000 раз, кликнуть пять кнопок); измеряет p95 длительности кадра и p95 LoAF; сравнивает с baseline-веткой. Третий — RUM (real user monitoring) на проде, шлёт перцентили INP, LCP и CLS в Datadog или похожую систему; алертит, когда p75 INP пересекает 200 мс на каком-либо сегменте пользователей (страна, девайс, версия приложения). Без всех трёх уровней регрессия рендера сначала прорывается в прод, затем тихо живёт там месяцами до того, как кто-то её замечает.</p>

    <p><strong>Профилирование на реальном железе vs DevTools на ноутбуке.</strong> Самая частая ошибка: профилирование на M2 MacBook и удивление, почему страница тормозит на бюджетном Android. Throttling в DevTools («4× slowdown» в Performance-панели) — приближение, не замена. M2 на 4× slowdown всё ещё имеет другую модель памяти, другой GPU, другой профиль теплового троттлинга, чем Pixel 6a. Минимум: один раз в неделю запускайте Performance recording на физическом среднем Android-телефоне через WebDebug → Chrome on phone, и сравните длительность кадров с macbook + 4× throttling. Если различие > 30%, у вас регрессия на mobile, которая не видна на десктопе. Полная стратегия включает device-lab — пять-десять физических телефонов разного класса, к которым CI прогоняет автоматизированные сценарии и шлёт метрики.</p>

    <p><strong>Web Workers и render-thread offload.</strong> Когда главный поток упирается в потолок, единственный способ ускорить страницу — переместить работу. Web Workers исполняют JS на отдельном потоке без доступа к DOM; сериализация данных туда-обратно через postMessage стоит ~1 ms/MB, что окупается для CPU-тяжёлых задач (парсинг крупного JSON, сжатие, криптография, маркап-обработка). Modern OffscreenCanvas даёт прямой доступ к canvas API из воркера, обходя главный поток. SharedArrayBuffer + Atomics дают примитивы синхронизации между потоками для high-frequency данных (audio, real-time). Цена входа высокая (структура памяти, message-passing API), но потолок производительности кратно выше: 4-ядерный телефон, где главный поток забит, всё ещё имеет 3 свободных ядра, которые большинство приложений никогда не использует.</p>

    <p><strong>Service Worker и кеш как клапан сброса первой отрисовки.</strong> Service Worker не часть рендер-пайплайна, но критически влияет на его вход: он отвечает на запросы из кеша, минуя сеть. Стратегия «cache-first для статики, network-first для API» даёт первую отрисовку за 50 мс на повторных визитах вместо 500 мс — четыре кадра при холодном кеше vs три при тёплом. Combined с App Shell pattern (закешированный HTML-каркас + JS-инициализация), это даёт мгновенный TTI и поверхность для динамического контента, рендерящегося по мере прихода данных. Главное правило: Service Worker должен быть тонкий и быстрый, потому что его исполнение блокирует первую запись в DOM.</p>

            <p>Два прохода: первый собирает все <code>offsetWidth</code> в массив, второй пишет новые ширины из массива. Поскольку ни одно чтение не следует за записью в том же цикле, браузер батчит все записи и запускает один проход компоновки. Сложность падает с O(N × компоновка) до O(компоновка). Общее правило: в любой функции, трогающей геометрию, сначала все чтения, потом все записи.</p>
          ),
        },
      }}
    />
  </Fragment>
</TierAccordion>

<Misconception id="mc-layout-thrash">
**Миф:** обёртка read-then-write в `requestAnimationFrame` батчит компоновку.

**Реальность:** rAF батчит только вызов. Чтение любого layout-зависимого значения (`offsetWidth`, `getBoundingClientRect`) после записи форсирует синхронный сброс компоновки. Лечение — разделить чтения и записи, а не оборачивать в rAF.
</Misconception>
