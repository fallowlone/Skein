Семь фрагментов, семь механизмов — event loop, пайплайн рендера, V8, воркеры, реконсилер React, стратегии рендеринга, Core Web Vitals. Каждый изучался отдельно. Но реальная страница не переживает их по отдельности: она переживает их как одну непрерывную цепь, от момента, когда пользователь нажал Enter, до момента, когда кнопка ответила на тап. Этот фрагмент следует за ровно одной страницей — страницей товара e-commerce — через всю эту цепь, называя каждую границу, которую она пересекает, и пять мест, где продакшен ломается надёжнее всего.

<Crux>От URL до клика: одна страница через семь слоёв, и семь границ, где умирает продакшен.</Crux>

У жизни страницы есть форма. Байты приходят по сети. HTML-парсер превращает их в DOM. CSS становится CSSOM; JavaScript парсится и компилируется V8. Пайплайн рендера компонует и рисует первый кадр. Затем гоняется гидратация — реконсилер усыновляет серверный DOM — и только потом страница интерактивна. Service worker может перехватить следующую навигацию; воркер может вынести вычисления с главного потока. И всё это время Core Web Vitals измеряют это. Восемь слоёв, один таймлайн.

    <p><strong>Страница, которую мы трассируем.</strong> Одна конкретная страница: страница товара e-commerce, серверно-отрендеренная, на React, с hero-картинкой, ценой, кнопкой «В корзину», секцией отзывов ниже сгиба и service worker, зарегистрированным с прошлого визита. Пользователь на среднем Android-телефоне на 4G. Мы следуем за этой ровно страницей от момента, когда он тапает ссылку, до момента, когда он успешно добавляет товар в корзину — и на каждой границе называем механизм из фрагмента, который ей владеет.</p>

    <p><strong>Слой 1 — Сеть.</strong> Тап триггерит навигацию. DNS резолвит хост, TLS-рукопожатие защищает соединение, HTTP-запрос уходит. Но есть нюанс: service worker с прошлого визита зарегистрирован. Браузер даёт `fetch`-обработчику service worker первый взгляд — он может отдать навигацию из кеша или пропустить в сеть. В любом случае первый байт HTML приходит. Это TTFB, и это пол под всем: ничего ниже по потоку не может стартовать до прихода байтов. Фрагменты в игре: воркеры (перехват service worker) и Core Web Vitals (TTFB).</p>

    <p><strong>Слой 2 — Парсинг HTML и preload-сканер.</strong> HTML-парсер начинает превращать байты в DOM-дерево, сверху вниз. Впереди него мчится preload-сканер, замечая ссылки `<img>`, `<script>` и `<link>` и запуская их загрузки рано. Поэтому hero-картинка, сидящая в начальном HTML как обычный `<img>`, начинает скачиваться немедленно — часы LCP уже тикают, и обнаружение происходит так рано, как возможно. Render-blocking `<script>` в `<head>` поставил бы главный парсер на паузу здесь; `defer`-нутый — нет. Фрагменты в игре: пайплайн рендера (парсинг), Core Web Vitals (обнаружение LCP).</p>

    <p><strong>Слой 3 — CSS и CSSOM.</strong> Когда ресурсы `<link rel="stylesheet">` приходят, браузер парсит их в CSSOM. CSS render-blocking по дизайну: браузер не нарисует, пока у него нет CSSOM, потому что отрисовка с неполными стилями означала бы вспышку нестилизованного контента. DOM и CSSOM вместе образуют render tree. Если CSS большой или отдаётся медленно, каждая отрисовка ниже по потоку ждёт. Фрагменты в игре: пайплайн рендера (CSSOM, render tree).</p>

    <p><strong>Слой 4 — JavaScript: парсинг и компиляция V8.</strong> JavaScript-бандл приходит, и V8 берётся за дело — но не запуская его немедленно. V8 сначала парсит исходник и компилирует его в байткод (вход интерпретатора Ignition). Для большого бандла один этот шаг parse-and-compile — это десятки-сотни миллисекунд времени главного потока на среднем телефоне, до того как выполнилась хоть одна строка. Это скрытая цена внутри «JavaScript слишком большой»: байты — не просто загрузка, это CPU-работа. Фрагменты в игре: внутренности V8 (парсинг, компиляция, Ignition), event loop (это задача на главном потоке).</p>

    <p><strong>Слой 5 — Первая отрисовка.</strong> С готовым render tree пайплайн рендера гоняется: стили, компоновка, отрисовка, композитинг. Фото товара, цена и лейаут появляются. Hero-картинка, если она закончила скачиваться, рисуется — и это очень вероятно момент LCP, прибытие самого крупного contentful-элемента. Страница теперь <em>выглядит готовой</em>. Но это картинка: ни один обработчик не прицеплен, никакое состояние не живо. Фрагменты в игре: пайплайн рендера (пять стадий), Core Web Vitals (LCP срабатывает).</p>

    <p><strong>Слой 6 — Гидратация.</strong> Теперь React гоняет `hydrateRoot`. Он обходит то же дерево компонентов, что обошёл сервер, и вместо создания DOM-узлов усыновляет существующий серверный DOM, цепляя обработчики событий и подключая состояние и эффекты — реконсилер в режиме гидратации. Это одна длинная задача: V8 исполняет дерево компонентов, реконсилер делает свой render и commit. Пока она гоняется, главный поток заблокирован. Страница выглядела готовой на слое 5; она становится <em>реально</em> интерактивной, только когда гидратация доходит до каждого компонента. Фрагменты в игре: React fiber (реконсилер, render/commit), стратегии рендеринга (гидратация), event loop (длинная задача гидратации).</p>

    <p><strong>Слой 7 — Взаимодействие.</strong> Пользователь тапает «В корзину». Если он тапает до того, как гидратация дошла до этой кнопки, ввод задержан — поставлен в очередь за длинной задачей гидратации — и INP записывает большую задержку. Если он тапает после, обработчик гоняется: он обновляет состояние корзины, реконсилер перерендеривает бейдж корзины, пайплайн рендера рисует изменение. Время от тапа до этой отрисовки — один сэмпл INP. Хорошо построенная страница делает это быстро; страница, всё ещё гидрирующаяся, делает это медленно. Фрагменты в игре: event loop (input delay), React fiber (re-render), Core Web Vitals (INP).</p>

    <p><strong>Слой 8 — Вторая навигация и воркер.</strong> Пользователь навигирует на checkout. Теперь service worker отрабатывает своё содержание: он отдаёт app shell из кеша, поэтому TTFB второй навигации — десятки миллисекунд вместо сетевого round trip. Если у страницы товара было тяжёлое клиентское вычисление — скажем, 3D-вьюер товара — эту работу можно было вынести в web worker, держа главный поток свободным для взаимодействия. Фрагменты в игре: воркеры (кеш service worker, вынос в web worker).</p>

    <p><strong>Таймлайн, наложенный.</strong> Ключевой senior-инсайт в том, что эти слои — не аккуратная последовательность — они перекрываются на таймлайне через три ресурса. Дорожка <em>сети</em> занята фетчем HTML, потом CSS, потом JS-бандла, потом картинки, параллельно где протокол позволяет. Дорожка <em>главного потока</em> занята парсингом HTML, потом компиляцией JS, потом отрисовкой, потом длинной задачей гидратации. Дорожка <em>GPU</em> делает финальный композитинг. Performance-трасса DevTools показывает ровно эти три дорожки, и читать медленную страницу значит находить, какая дорожка — бутылочное горлышко в момент, который важен — network-bound до первой отрисовки, main-thread-bound во время гидратации. Навык не в знании слоёв; он в чтении того, где, на наложенном таймлайне, реально ушло время.</p>

    <p><strong>Куда уходит бюджет.</strong> Привяжем слои к числам. На нашей трассе со средним телефоном на 4G: TTFB ~300 мс (сеть плюс сервер, или ~30 мс если service worker отдал его). Парсинг HTML — несколько мс. Парсинг CSS — несколько мс. Парсинг и компиляция JS — ~150 мс для типового бандла. Первая отрисовка и LCP, приземляющиеся около 1.5–2.5 с если всё идёт хорошо. Гидратация — ~300 мс до больше секунды времени главного потока в зависимости от размера бандла. Само взаимодействие хочет быть под 200 мс. Каждый слой тратит из одного бюджета, и вердикт пользователя — LCP и INP — это сумма. Поэтому оптимизация — это всегда вопрос «где в этом бюджете самая большая статья расходов», а не «какой слой я умею ускорять»: слой, который вы хорошо знаете, и слой, который реально доминирует в бюджете, — это, как правило, разные слои. Бюджет — это и есть та рамка, что превращает абстрактное «сделай быстрее» в конкретное «найди самую дорогую статью и срежь именно её»; без этой рамки оптимизация сводится к ускорению того, что инженер умеет ускорять, а не того, что реально стоит дорого на этой конкретной странице.</p>

    <p><strong>Параллельность: почему слои не последовательны.</strong> Стоит развернуть, что значит «слои перекрываются». Браузер не делает один шаг, ждёт, делает следующий — он держит все три ресурса (сеть, главный поток, GPU) занятыми всегда, когда есть работа. Пока сеть скачивает JS-бандл, главный поток уже парсит HTML, который пришёл раньше. Пока главный поток компилирует JS, сеть уже фетчит картинку. Preload-сканер существует ровно ради этой параллельности — он находит ресурсы и кидает их в сеть, пока главный парсер занят чем-то ещё. Следствие для диагностики важное: «медленная страница» почти никогда не один медленный шаг — это момент, где параллельность сорвалась, где одна дорожка стала ограничением, и две другие простаивали, ожидая её. Render-blocking скрипт — классический пример: он останавливает главный парсер, и пока он качается, главный поток простаивает, хотя мог бы парсить остальной HTML. Senior читает трассу именно так: не «что медленное», а «где параллельность сломалась и одна дорожка заставила другие ждать».</p>

    <p><strong>Откуда взялась эта форма.</strong> Восемь слоёв — не произвольный список; это форма, которую веб приобрёл за тридцать лет эволюции. Ранние страницы были слой 1–3 и всё: сеть, парсинг, отрисовка — статический документ. JavaScript добавил исполнение, и слой 4 (V8) стал важным. AJAX и SPA сдвинули рендеринг в браузер, и страница стала приходить пустой оболочкой, рендерящейся на клиенте — что убило слой 5 как «первая отрисовка чего-то полезного». SSR вернул серверный рендер ради быстрой первой отрисовки и SEO — но он же ввёл слой 6, гидратацию, и вместе с ней зловещую долину. Service worker (слой 8) добавился, чтобы вернуть мгновенность повторных загрузок, потерянную при уходе от статики. Понимание этой эволюции — не историческая справка: оно объясняет, почему каждый слой существует и какую проблему он решал, а значит — какой компромисс он принёс. Гидратация существует не потому что кто-то захотел её — она цена, которую SSR платит за то, что вернул быструю первую отрисовку. Каждый слой — это решение прошлого компромисса, ставшее новым компромиссом.</p>

    <p><strong>Связь слоёв: причина в одном, симптом в другом.</strong> Стоит заранее назвать то, что станет главным уроком senior-уровня этого фрагмента: симптом и причина почти никогда не в одном слое. Пользователь видит «страница медленная» или «кнопка не нажимается» — это симптом на слое 5 или 7, на поверхности. Но причина регулярно живёт глубже и раньше. Кнопка не нажимается (симптом, слой 7), потому что бандл слишком большой (причина, слой 4), потому что в него втянули тяжёлую библиотеку (причина, решение на этапе сборки). LCP поздний (симптом, слой 5), потому что hero-картинка референсится в CSS (причина, слой 2 — обнаружение). Это не случайность — это структурное свойство цепи: каждый слой потребляет выход предыдущего, поэтому ошибка на раннем слое проявляется как симптом на позднем. Практическое следствие: чинить слой, который называет симптом, — почти всегда чинить не то. Кто-то «оптимизирует кнопку», когда проблема в бандле; кто-то «сжимает hero-картинку», когда проблема в том, что её поздно обнаружили. Вся остальная часть этого фрагмента — про дисциплину, которая разрывает эту ошибку: трассировать всю цепь и находить, на каком слое реально живёт причина, а не на каком кричит симптом. Именно это отличает инженера, который чинит медленную страницу за раз, от того, кто гоняет её по кругу, перекладывая медленность с одного слоя на другой и не понимая, почему число не двигается.</p>

    <h4 class="mt-2 mb-3 text-[15px] font-semibold text-ink tracking-tight">Режим отказа: зловещая долина и пять канонических поломок</h4>
    <p><strong>Зловещая долина как объединяющий отказ.</strong> Единственный отказ, связывающий эту главу — зазор между «нарисовано» и «интерактивно» — зловещая долина гидратации. Это не один баг; это структурное свойство серверно-отрендеренных, клиентско-гидрируемых приложений, и каждый другой отказ в этом списке либо расширяет эту долину, либо случается внутри неё. Senior-формулировка: у страницы два момента завершения, LCP-подобный («выглядит готово») и TTI-подобный («работает»), и всё мастерство современной фронтенд-производительности — схлопывание расстояния между ними. С этой рамкой — вот пять канонических поломок, по одной на домен — места, где продакшен надёжнее всего умирает по трассе.</p>

    <p><strong>Поломка 1 — Поздно-грузящаяся hero-картинка (LCP).</strong> Hero-картинка — LCP-элемент, но она референсится в CSS как `background-image`, или несёт `loading="lazy"`, или инжектируется JavaScript. Preload-сканер не может её увидеть, поэтому её загрузка стартует поздно — и LCP, который измеряет ровно этот элемент, приземляется на 4+ секундах. Трасса показывает длинную фазу resource-load-delay. Фикс: LCP-картинка должна быть обычным `<img>` в начальном HTML, нетерпеливо загружаемым, с `fetchpriority="high"`. Это слой 2 (обнаружение) ломается, и слой 5 (отрисовка) платит за это.</p>

    <p><strong>Поломка 2 — Hydration mismatch (CLS плюс корректность).</strong> Компонент рендерит значение, различающееся между сервером и клиентом — таймстемп, флаг из `localStorage`, цена с локальным форматированием. Серверный HTML и первый рендер клиента расходятся; React выбрасывает серверное поддерево и перерендеривает его, мигая изменённым контентом и взрывая CLS. Трасса показывает маркер layout-shift прямо после длинной задачи гидратации. Фикс: детерминизм рендера — отложить клиентские значения в пост-гидратационный `useEffect`. Это слой 6 (гидратация) ломается, потому что сериализованное состояние слоя 1 не было верно воспроизведено.</p>

    <p><strong>Поломка 3 — Megamorphic render path (INP).</strong> Обработчик «В корзину» триггерит re-render, и горячая функция на этом пути — аксессор свойства, компаратор — megamorphic: она видела слишком много форм объектов, поэтому V8 не может использовать inline cache и откатывается на медленные поиски. Re-render, который должен занять 5 мс, занимает 80 мс, и INP взаимодействия плох. Трасса показывает длинную полосу скриптинга внутри взаимодействия. Фикс: стабилизировать формы объектов, чтобы inline cache V8 оставались мономорфными. Это слой 4 (V8) и слой 7 (взаимодействие) сплетены.</p>

    <p><strong>Поломка 4 — Протухший кеш service worker (корректность).</strong> Деплой отгружает новый HTML и новый JS-бандл, но service worker отдаёт прошлонедельный закешированный `app.js` cache-first против HTML этой недели — несовпадение версий модулей, рантайм-ошибка. Или хуже, сломанный app shell закеширован, и каждый повторный посетитель заперт на нём, минуя сеть, где живёт фикс. Фикс: content-hashed имена файлов ассетов, version-tagged кеши, чистимые в `activate`, network-first навигация, kill switch. Это слой 1 / слой 8 (воркер) ломается через состояние — кеш пережил свою корректность.</p>

    <p><strong>Поломка 5 — Синхронная работа в обработчике события (INP).</strong> Обработчик «В корзину» делает что-то синхронное и тяжёлое на главном потоке до уступки — шлёт синхронный аналитический маяк, гоняет большой `JSON.parse`, перевычисляет производный список. Одно processing time обработчика пробивает бюджет INP 200 мс. Трасса показывает длинную жёлтую полосу скриптинга между вводом и следующей отрисовкой. Фикс: сделать минимум для обновления UI, потом уступить (`scheduler.yield()`) и вынести чистое тяжёлое вычисление в воркер. Это слой 7 (взаимодействие) ломается на правилах event loop напрямую.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Чтение наложенной трассы</h4>
    <p><strong>Метод трёх дорожек.</strong> Performance-трасса DevTools этой страницы показывает дорожку сети, дорожку главного потока и дорожку GPU/композитора на одном таймлайне. Senior-метод диагностики любой медленной страницы: первое, найти пользовательский симптом — поздний маркер LCP, длинное взаимодействие в дорожке Interactions, красный маркер layout-shift. Второе, опуститься к моменту, когда симптом случился, и спросить, какая дорожка была ограничением. Если LCP поздний и дорожка сети показывает hero-картинку всё ещё скачивающейся в момент LCP — это проблема сети или обнаружения (поломка 1). Если LCP поздний, но картинка закончилась рано и главный поток плотно занят работой — это render-blocking JS, проблема element-render-delay. Если взаимодействие медленное и дорожка главного потока показывает длинную задачу, перекрывающую его — это гидратация или тяжёлый обработчик (поломки 3 и 5). Трасса превращает «страница медленная» в «эта дорожка, в этот момент, была ограничением» — и это починяемое утверждение.</p>

    <p><strong>Почему слои надо понимать вместе.</strong> Каждый отказ выше неправильно диагностируется, если знаешь только один слой. Поломка 1 выглядит как «медленная картинка» для того, кто знает только сеть — но картинка была нормального размера; реальная причина — обнаружение, забота слоя парсинга. Поломка 3 выглядит как «React медленный» для того, кто знает только реконсилер — но реконсилер был в порядке; реальная причина — megamorphic-форма, забота V8. Весь смысл трассировки от начала до конца в том, что симптом и причина рутинно в разных слоях, и только тот, кто видит всю цепь, перестаёт чинить симптомы.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Слои deep-dive</h4>
    <p><strong>Гидратация, полностью.</strong> Гидратация — петля всей трассы, поэтому стоит ещё одного прохода. Это реконсилер React (фрагмент 05), гоняющийся в особом режиме: вместо `createRoot`, строящего свежий DOM, `hydrateRoot` обходит дерево компонентов и <em>усыновляет</em> существующий серверный DOM. Фаза render гоняется — ваши компоненты исполняются, fiber-дерево строится — но фаза commit, вместо вставки узлов, цепляет слушатели событий и гоняет эффекты. Она загейчена JavaScript-бандлом: ничего не гидрируется, пока V8 (фрагмент 03) не распарсил, не скомпилировал и не начал исполнять этот бандл. Это одна или больше задач на event loop (фрагмент 01), и большая нетерпеливая гидратация — одна длинная задача, блокирующая ввод — что Core Web Vitals (фрагмент 07) записывают как плохой INP для любого взаимодействия в том окне. И вся эта цена существует только потому, что страница была серверно-отрендерена (фрагмент 06) в первую очередь. Гидратация — место, где сходятся пять из семи фрагментов.</p>

    <p><strong>V8 и пайплайн отрисовки, полностью.</strong> Другое плотное пересечение — последовательность первой отрисовки. Пайплайну рендера (фрагмент 02) нужны DOM и CSSOM; DOM приходит от HTML-парсера, CSSOM — от парсинга CSS — обе задачи главного потока (фрагмент 01). JavaScript, который может изменить DOM до первой отрисовки, должен сначала быть распарсен и скомпилирован V8 (фрагмент 03), и если этот JS render-blocking, отрисовка ждёт его. Стадия композитинга отдаёт слои GPU. LCP (фрагмент 07) срабатывает, когда приземляется самый крупный элемент той отрисовки. То есть «первая отрисовка» — не один механизм — это пайплайн рендера, парсер, V8 и композитор, скоординированные, с Core Web Vital, наблюдающим результат. Урок капстоуна: ни один слой не остров; каждая реальная страница — это весь стек сразу.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Production-наблюдаемость</h4>
    <p><strong>От понимания всей цепи к мониторимой системе.</strong> Сквозная ментальная модель становится production-практикой через слоёную телеметрию, каждый слой наблюдает границу, которой владеет. Real-user monitoring с библиотекой `web-vitals` захватывает LCP, INP и CLS с атрибуцией — LCP-элемент, INP-скрипт, источник CLS — поэтому регрессия называет свой слой. Long Animation Frames атрибутируют медленные кадры конкретным скриптам, ловя длинную задачу гидратации и тяжёлые обработчики (поломки 3 и 5). Серверная трассировка наблюдает TTFB и путь загрузки данных (слой сети). Телеметрия service worker наблюдает cache hit rate и длительность `fetch`-обработчика (поломка 4). Синтетический CI-гейт — зажатая Lighthouse или Playwright-трасса на каждом PR — ловит очевидные регрессии до мержа. Принцип зеркалит главу: поскольку медленная страница — проблема цепи, мониторинг должен покрывать каждое звено, и каждая метрика должна нести достаточно атрибуции, чтобы указать назад на слой, который сломался. Так понимание всей цепи перестаёт быть навыком отладки и становится системой, которая ловит поломку за вас.</p>

    <p><strong>Дисциплина капстоуна.</strong> Отступите от страницы и посмотрите на сам метод. Senior-навык, к которому эта глава ведёт — не запоминание восьми слоёв — это дисциплина диагностики. У неё три хода. <em>Измеряй до того, как трогаешь</em>: реальная трасса и полевой RUM, никогда догадка, потому что симптом рутинно называет неправильный слой. <em>Найди ограничение, не одно из ограничений</em>: на наложенном таймлайне всегда есть одна дорожка, в один момент, которая — реальное горлышко; оптимизация чего-либо ещё двигает число, которое не было проблемой. <em>Чини доминирующую причину, потом перемеряй</em>: поскольку слои взаимодействуют, фикс в одном слое меняет бюджет в других, поэтому трасса после фикса — это новая диагностика, не подтверждение. Junior-инженер оптимизирует то, что умеет оптимизировать; senior-инженер оптимизирует то, что трасса называет ограничением. Восемь слоёв — это карта; дисциплина — знание, что карта не говорит, где проблема — это говорит измерение.</p>

<Misconception id="mc-uncanny-valley">
**Миф:** если страница нарисовалась быстро, она быстрая — работа сделана на первой отрисовке.

**Реальность:** первая отрисовка — картинка. Страница не интерактивна, пока гидратация не закончится — этот зазор, зловещая долина, и есть место мёртвых тапов. «Выглядит готово» (LCP) и «работает» (INP) — разные моменты.
</Misconception>

<KeyTakeaway>Одна страница пересекает восемь слоёв: сеть, парсинг HTML, CSS, V8, отрисовка, гидратация, взаимодействие, вторая навигация. <p class="text-ink-2 my-6">Вся эта цепь — одна длинная передача состояния: сервер захватывает его, байты несут его, парсер пересобирает его в DOM, гидратация реконструирует живую версию его, и каждый слой либо верно сохраняет это состояние, либо рвёт цепь. Задержка — цена каждой передачи; инкапсуляция — то, что даёт рассуждать о каждом слое отдельно; состояние — то, что должно пережить каждую границу нетронутым. Три нити этой программы — не отдельные уроки — это три силы, действующие на каждую страницу, каждый раз. <SpiralCue thread="statefulness" lang="ru" /></p>
