JavaScript — динамический язык: переменные хранят любой тип, объекты получают и теряют свойства по желанию, каждый call site полиморфен по дизайну. CPU под ним заботится о другом — регистры, предсказуемые layouts, branch targets, известные заранее. V8 мостит разрыв через четырёхъярусный JIT и concurrent garbage collector. Перформанс-gap между кодом, который V8 любит, и кодом, который V8 не может оптимизировать — примерно 100x. Знание, на какой стороне линии ты находишься — разница между 60fps и зависшей вкладкой.

<Crux>V8 = 4 JIT-яруса + hidden classes + ICs + Orinoco GC. Полиморфизм выше 4 shapes убивает hot path в 10-50x.</Crux>

Ментальная модель: JS-код байт-код-интерпретируется в Ignition, пока V8 записывает типы каждого call site. Горячий код поднимается по ярусам — Sparkplug для cheap-and-fast, Maglev для mid-tier оптимизированного, TurboFan для самых горячих путей. На каждом ярусе V8 специализируется на наблюдаемых типах (hidden classes); отклонение от ассумпций триггерит деоптимизацию обратно на нижний ярус. Доступ к свойству объекта идёт через inline cache, чей state трекает, сколько object shapes одна строка исходника видела. Orinoco GC обходит heap concurrent с выполнением JS, эвакуируя young-объекты параллельно и помечая старые в фоне, держа паузы ниже 1мс в well-behaved приложениях. Каждый senior frontend perf-вопрос — почему этот цикл медленный, почему страница дёргается, почему добавление одного поля обрушило render — отвечает из этого стека.

    <p><strong>Четырёхъярусный пайплайн.</strong> V8 имеет четыре режима выполнения, упорядоченных tradeoff-ом compile-time vs run-time. <em>Ignition</em>: bytecode-интерпретатор. Парсер строит AST; Ignition опускает его в компактный register-based bytecode и выполняет на виртуальной машине. Во время интерпретации Ignition записывает type feedback в per-function FeedbackVector — слоты для каждой «интересной» локации (property load, function call, арифметика, сравнение). Дёшевый вход (нет compile-cost), per-instruction в 10 раз медленнее оптимизированного native кода. <em>Sparkplug</em>: baseline JIT, добавлен в 2021. Sparkplug эмитит неспециализированный machine code за один линейный проход по bytecode — никакого SSA, реальной оптимизации нет, просто faithful translation каждого bytecode в маленький блок machine инструкций плюс tail call. Compile-cost практически нулевой (~1мс на kB bytecode); ускорение над Ignition в 1.5-2 раза. <em>Maglev</em>: mid-tier оптимизирующий компилятор, добавлен в 2023. Maglev использует observed types из FeedbackVector и SSA-based оптимизации, эмитя специализированный machine code, но пропуская heavy passes TurboFan. ~10x медленнее compile, чем Sparkplug, ~10x быстрее compile, чем TurboFan, runtime-код примерно посередине между ними. <em>TurboFan</em>: тяжёлый оптимизирующий компилятор. Агрессивный inlining, escape analysis, range analysis, hidden-class специализация, speculative optimisations, которые могут deopt. Compile-cost высокий (десятки до сотен мс на сложную функцию); runtime-код — самый быстрый, который V8 производит.</p>
    <p><strong>Profile-guided tiering.</strong> Функции входят в Ignition. После пересечения порогов execution-count (per-function, динамические) V8 промотит на следующий ярус. Недавний V8 использует profile-guided tiering: FeedbackVector трекает не только типы, но и branch frequencies, поэтому TurboFan может разложить hot path с оптимальным branch prediction. Пороги настроены per-tier: Sparkplug на ~100 calls, Maglev на низких тысячах, TurboFan на десятках тысяч. Promotion происходит off-thread (concurrent compilation) — главный поток JS продолжает работать на текущем ярусе, пока worker thread компилит следующий.</p>
    <p><strong>Hidden classes (Maps или Shapes).</strong> JS-объекты динамичны — свойства можно добавлять, удалять, реордерить — но V8 внутри представляет каждый объект как pointer на hidden class (Map в исходниках V8) плюс sequence of property slots. Два объекта с одинаковыми именами свойств, добавленными в том же порядке, делят один hidden class. Когда добавляешь свойство к существующему объекту, V8 transitions на новый hidden class по «transition tree» — adding "x" then "y" идёт на один class; adding "y" then "x" идёт на другой (даже хотя оба объекта имеют одинаковое логическое содержимое). Это важно, потому что inline cache key-ится по hidden class pointer. <em>Стабильные hidden classes — фундамент производительности V8.</em> Конструируй объекты со всеми свойствами upfront (в конструкторах или factory). Избегай <code>delete</code> на свойствах объекта — это форсирует transition на dictionary-mode объект, который перманентно медленный.</p>
    <p><strong>Inline caches и их состояния.</strong> Каждый доступ к свойству в JS — полиморфная операция, объект может быть любой shape. V8 генерирует крошечный per-call-site кеш: первый раз, когда строка выполняется, V8 записывает hidden class, который видел, и property offset для этого class. Следующий раз, когда та же строка выполняется и объект имеет тот же hidden class, V8 читает свойство по записанному offset напрямую (5-10 циклов). State machine IC: <em>uninitialized</em> (нет наблюдений), <em>monomorphic</em> (один hidden class — быстрый direct access), <em>polymorphic</em> (2-4 hidden classes — linear chain of class checks, всё ещё быстро), <em>megamorphic</em> (5+ — V8 сдаётся на специализации, падает на generic property lookup, который в 10-50 раз медленнее). IC-state живёт в FeedbackVector слоте для этой строки. Функция может иметь сотни IC слотов; один megamorphic site не убивает всю функцию, но hot loop, содержащий megamorphic property access, убивает свой loop body.</p>
    <p><strong>Деоптимизация (deopt).</strong> Когда TurboFan оптимизирует функцию, она запекает ассумпции: «этот arg всегда smi» (small integer), «property z этого объекта всегда число», «этот loop никогда не оверфлоу 32-bit индексов». Guard вставляется на каждой ассумпции. Если в runtime любой guard падает, V8 деоптимизирует: выбрасывает компилированный код, реконструирует интерпретатор state из оптимизированного frame и продолжает выполнение в Ignition (или Sparkplug). Функция может подняться обратно позже, но сам deopt дорогой (~микросекунды). Типичные deopt-триггеры: passing different type to ранее-typed аргументу, indexing за array bounds, попадание в NaN в numeric операции, accessing удалённого свойства. Chrome DevTools (<code>--trace-opt --trace-deopt</code> флаги) экспонирует deopts; <code>%OptimizationStatus(fn)</code> на <code>--allow-natives-syntax</code> в d8 показывает текущий ярус.</p>
    <p><strong>Orinoco: concurrent garbage collector V8.</strong> Heap разделён на young generation (маленький, часто собирается) и old generation (большой, редко собирается). <em>Minor GC (Scavenger)</em>: копирует живые young объекты из «from-space» в «to-space» semispace; мёртвые объекты выбрасываются. Работает параллельно через несколько threads, используя динамический work-stealing. Паузы на главном потоке короткие (~1мс типично), потому что young-gen heap маленький. Survivors двух scavenges promoted в old generation. <em>Major GC (Mark-Compact)</em>: трассирует все живые объекты с roots, помечает reachable, sweeps мёртвые, компактит surviving объекты для уменьшения фрагментации. До Orinoco это была stop-the-world операция длительностью сотни мс на больших heaps. Orinoco перенёс marking в concurrent thread, который обходит heap, пока JS работает на главном потоке; реальная пауза на sweep/compact сокращена на 50% на WebGL-heavy workloads. Pause-time budget на главном потоке — самое жёсткое perf-ограничение; философия дизайна Orinoco — «сделать GC паузы незаметными на 60fps (16.6мс)».</p>
    <p><strong>Hot path: комбинация всего вышесказанного.</strong> Функция в tight loop попадает на оптимизированный поток: TurboFan-компилирована, monomorphic IC на каждом access, hidden class стабилен, нет GC прерывания. Per-iteration cost — single-digit nanoseconds. Сломай любой из них и cost растёт: polymorphic IC → 2x, megamorphic IC → 10-50x, deopt в середине loop → 100-1000x для loop body, GC пауза → миллисекунды, видимые пользователю. Frontend perf engineering — почти исключительно о том, чтобы держать все четыре колеса этого автомобиля: стабильные object shapes, monomorphic call sites, никаких сюрпризов, триггерящих deopt, низкое GC давление.</p>
    <p><strong>Операционные рычаги для JS perf.</strong> (1) Constructor паттерн: декларируй все свойства объекта в одном месте, чтобы hidden classes были стабильны. (2) Избегай <code>delete</code> на объектах (используй null или undefined assignment, или просто никогда не объявляй свойства, которые можешь хотеть удалить). (3) Держи функции monomorphic: не передавай разные shapes в один call site. (4) Избегай <code>arguments</code> в старом коде; используй rest parameters. (5) Pre-allocate массивы с известной capacity для избежания resize. (6) Переиспользуй object pools для short-lived workloads (canvas, animation) вместо аллокации новых объектов per frame. (7) Избегай массивных object literals в hot paths (они megamorphic быстро). (8) Для очень hot numeric loops используй TypedArrays — V8 имеет высоко-tuned paths для Uint32Array и подобных, которые bypass IC layer полностью.</p>
    <p><strong>Tooling и наблюдение.</strong> Chrome DevTools Performance panel показывает main-thread время разбитое по Scripting / Rendering / Painting / GC. Memory panel snapshots и timeline diffs. Node.js: <code>--trace-opt --trace-deopt</code> флаги логируют каждое promotion и demotion; <code>--print-bytecode</code> дампит Ignition bytecode; <code>--print-opt-code</code> дампит TurboFan-эмитированный machine code. d8 (V8 shell) с <code>--allow-natives-syntax</code> экспонирует intrinsic функции типа <code>%HasFastProperties(obj)</code> (объект в dictionary mode?), <code>%GetOptimizationStatus(fn)</code> (какой ярус?), <code>%DebugPrint(obj)</code> (полный internal layout). Production perf debugging обычно стартует в DevTools, копает в специфическую функцию и заканчивается в d8 для подтверждения V8-уровня диагноза.</p>
    <p><strong>Memory layout: in-object vs out-of-object свойства.</strong> V8 хранит первые ~8 свойств объекта inline в memory block объекта; последующие свойства идут в out-of-object PropertyArray, на который указывает объект. Access к in-object свойствам — single memory load; out-of-object добавляет одну pointer dereference. «In-object slot count» зафиксирован при создании hidden class — добавление большего числа свойств позже spills в PropertyArray. Для perf-критичных объектов декларируй самые-часто-доступаемые свойства первыми в конструкторе. Кроме того, hidden classes также имеют «dictionary mode» fallback: объекты со слишком многими свойствами (~32+) или многими удалениями transitions на HashMap-backed представление, где каждый access идёт через slow generic путь. Это «dictionary mode» предупреждение в V8 tooling — раз попал, объект навсегда медленный.</p>
    <p><strong>Numeric специализация: smi, heap-number, double.</strong> V8 представляет small integers (Smi) inline в 64-bit pointer slot с low bit cleared — никаких аллокаций, никаких indirection, арифметика за одну CPU инструкцию. Числа вне smi range (±2^30 на 32-bit isolates, ±2^31 на 64-bit) становятся HeapNumbers — boxed в heap-allocated cell с double внутри. Smi-to-HeapNumber transition — самый частый deopt-триггер V8: TurboFan-компилирован loop ассумит Smi, value оверфлоу один раз, deopt cascade. Фикс — bound integer range или использовать Math.fround / explicit Float64Array. Инженеры, пишущие perf-критичный JS, интернализируют Smi range и проектируют data flows, чтобы оставаться внутри него.</p>
    <p><strong>Array элементов kinds: PACKED vs HOLEY.</strong> V8 трекает «kind» каждого массива на основе того, что в нём хранится. PACKED_SMI_ELEMENTS — массив только smi-чисел без пробелов, самая быстрая форма. PACKED_DOUBLE_ELEMENTS — только double-чисел. PACKED_ELEMENTS — mixed types или объекты. HOLEY_* варианты — массив с пробелами (sparse), что заставляет V8 проверять каждый access на «hole». Transitions всегда односторонние: PACKED → HOLEY, SMI → DOUBLE → ELEMENTS. Раз перешёл — не вернёшься, даже если массив снова заполнен. Production pitfall: <code>new Array(1000)</code> создаёт HOLEY массив с самого начала; <code>Array.from(&#123;length:1000&#125;, () =&gt; 0)</code> создаёт PACKED. Та же логическая операция, в 2-3 раза разная скорость access. Чтобы держать массив PACKED_SMI: pre-allocate с <code>[]</code>, добавляй через push, не присваивай по индексам выше длины. Diagnostic: <code>%DebugPrint(arr)</code> в d8 показывает kind.</p>
    <p><strong>String internalization и сравнение.</strong> V8 поддерживает internal pool для маленьких string-литералов и property names — две interned строки сравниваются как pointer равенство (1 цикл), не char-by-char. Property access всегда interns ключ. Конкатенация (<code>'a' + 'b'</code>) создаёт ConsString — flat tree concatenation без копирования. Substring создаёт SlicedString, держащий reference на parent. Это даёт O(1) substring/concat, но retain memory: длинная строка живёт в heap, пока хоть один slice есть. <code>str.flatten()</code> или explicit copy через <code>str.slice() + ''</code> разрывает reference, освобождая parent. Для perf-критичных string-heavy workloads (парсеры, шаблонизаторы) знание этого паттерна — разница между O(n) и O(n²) на ровном месте, особенно когда длинная строка случайно retain-ится через короткий substring и leak heap memory.</p>

  <Fragment slot="senior">
    <p><strong>FeedbackVector: profile-guided сердце V8.</strong> Каждая функция в V8 имеет ассоциированный FeedbackVector — fixed-size массив, индексированный source-position-derived slot numbers. Каждый slot соответствует одной «интересной» операции (property load, function call, binary operator и т.д.). Slot хранит либо один observed hidden class pointer (monomorphic), либо малый массив hidden classes (polymorphic), либо «MegamorphicSentinel» объект, указывающий, что IC сдался. FeedbackVector аллокируется лениво при первом выполнении и живёт в GC heap как HeapObject. Sparkplug, Maglev и TurboFan все читают из него: Sparkplug использует минимальный feedback (только тип), Maglev использует богаче (hidden class chains, call target frequencies), TurboFan использует всё плюс inference про loop trip counts и branch probabilities. FeedbackVector — самый конкретный способ увидеть runtime profiling V8 — <code>%DebugPrintFeedback(fn)</code> в d8 дампит его. В production загрязнение FeedbackVector функции (например, один megamorphic slot) объясняет, почему V8 не может держать функцию оптимизированной даже после deopt-and-reopt циклов.</p>
    <p><strong>Sparkplug: JIT, который на самом деле не оптимизирует.</strong> Добавлен в V8 9.1 (май 2021), Sparkplug технически baseline JIT, но точнее описывается как «интерпретатор, эмитящий machine code напрямую». Не делает <Term k="ssa" lang="ru">SSA</Term>, никакого inlining, instruction scheduling. На каждый Ignition bytecode Sparkplug эмитит fixed sequence machine инструкций, реализующих этот bytecode. Результат — примерно в 1.5-2 раза быстрее Ignition, потому что per-instruction overhead dispatch-loop интерпретатора (dispatch table lookup, indirect jump) заменён прямым выполнением native кода. Compile speed Sparkplug практически free: ~1мс per kB bytecode. Смысл Sparkplug — дать горячим-но-не-достаточно-горячим-для-Maglev функциям измеримое ускорение без оплаты Maglev compile cost. V8 блог Google описывает Sparkplug как «non-optimizing compiler, производящий код быстрее, чем ты можешь запустить интерпретатор». Задокументированная средняя выгода: 5-15% на реальных workloads.</p>
    <p><strong>Maglev: SSA, но дёшево.</strong> Добавлен в 2023, Maglev заполняет gap между Sparkplug и TurboFan. Compile pipeline: bytecode → Maglev IR (SSA) → register allocator → native code. IR проще чем TurboFan (нет концепции effect chains или graph rewriting passes), register allocator — простой linear scan, а не graph-colouring TurboFan. Maglev делает некоторую speculative optimisation — использует observed types для специализации property loads, calls и арифметики — но пропускает heavy passes (escape analysis, polymorphic inlining, type-narrowing iteration). Compile time Maglev ~10мс per function vs ~100мс TurboFan; runtime код ~50-70% качества TurboFan. Роль Maglev — обрабатывать «medium hot» tier — функции, вызываемые тысячи раз, но не десятки тысяч — без оплаты TurboFan compile cost. Tiering policy V8 теперь идёт Ignition → Sparkplug → Maglev → TurboFan; функции могут пропускать tiers, если их hotness profile требует.</p>
    <p><strong>Speculative оптимизации TurboFan.</strong> TurboFan — V8 heavy-weight оптимизирующий компилятор. Строит <Term k="sea_of_nodes" lang="ru">sea-of-nodes</Term> граф IR, делает агрессивный <Term k="escape_analysis" lang="ru">escape analysis</Term> (object allocations могут быть stack-allocated или elided полностью, если они никогда не escape), inlines <Term k="polymorphic_inlining" lang="ru">polymorphic</Term> call sites, если есть 2-4 known targets, narrows types итеративно (variable, известная как 0..255, остаётся в byte register), эмитит highly-tuned machine code. Crucially, TurboFan устанавливает guard инструкции перед каждой speculative ассумпцией: «это smi» guard перед каждой numeric op, «этот объект имеет hidden class HCx» guard перед каждым property access. Guard failure значит deopt. Cost-benefit: TurboFan-оптимизированный код часто в 3-10 раз быстрее Maglev, когда ассумпции держатся; когда они ломаются, deopt overhead и fall back на нижний ярус хуже, чем не TurboFan-компилить вообще. Production V8 аккуратно балансирует «должен ли я оптимизировать эту функцию TurboFan?» через profile-guided heuristics — функции, чей feedback нестабилен (частые IC transitions), deferred или skipped.</p>
    <p><strong>Hidden class transition trees в деталях.</strong> Когда пишешь <code>const p = &#123;&#125;; p.x = 1; p.y = 2;</code>, V8 создаёт четыре hidden classes: empty → x → x+y, с каждым «transition edge», помеченным именем добавленного свойства. Второй объект <code>const q = &#123;&#125;; q.x = 1; q.y = 2;</code> идёт по тому же пути и заканчивается на том же hidden class, что p. Но <code>const r = &#123;&#125;; r.y = 2; r.x = 1;</code> идёт по пути empty → y → y+x, заканчиваясь на другом hidden class. Transition tree разделяется через все объекты в V8 isolate, поэтому memory cost ограничен. Патологические случаи: код, добавляющий свойства в динамическом порядке, создаёт много leaf nodes в tree, разбрасывая объекты через много hidden classes — та же shape никогда не повторяется, ICs perpetually polymorphic/megamorphic. <em>2008 V8 design ассумпция: программисты естественно пишут код, конструирующий похожие объекты в похожих порядках.</em> Большинство кода так и делает; патологический код, ломающий это (часто generated код, JSON-парсеры, пишущие свойства в произвольном input-порядке), страдает severe perf degradation.</p>
    <p><strong>Memory layout inline cache.</strong> IC slot в FeedbackVector — 16 байт: 8-byte hidden class pointer (или sentinel) + 8-byte handler object. Handler — небольшой кусок generated кода (или reference на него), который знает, как read/write свойство, учитывая cached hidden class. Polymorphic ICs используют другой handler type, который branches на hidden class. Megamorphic ICs используют generic handler, попадающий в V8 runtime slow lookup path (megamorphic_property_load_builtin в V8 source). Полный тур одного IC access в V8 source: ic_inl.h, ic.cc, ic-state.cc — state transitions явны. Production-grade V8 работа routinely включает смотрение в эти для одного специфического call site, который mis-optimising. «JavaScript engine fundamentals: Shapes and Inline Caches» Маттиаса Биненса остаётся canonical внешним reference.</p>
    <p><strong>Orinoco: minor и major collector в деталях.</strong> V8 heap разделён на <em>young generation</em> (newly allocated, ~1-8 MB) и <em>old generation</em> (long-lived, может быть 100s MB). Minor GC (Scavenger) использует copying collector с двумя semispaces: from-space держит живые объекты, to-space пуст. На collection V8 обходит roots (stack, globals, registers), копирует reachable young объекты в to-space, обновляет pointers. Survivors двух minor GCs promoted на old generation. Scavenger параллелен с 2017 (первая major shipping фича Orinoco): множественные worker threads делят работу через динамический work-stealing. Паузы на JS-главном потоке короткие (~1мс для типичного young heap), потому что live set мал и параллелизм держит wall-clock низким. Major GC (Mark-Compact) помечает все reachable объекты в old gen, sweeps dead, компактит для уменьшения фрагментации. <em>Concurrent marking</em>: background thread обходит heap, пока JS выполняется; write barriers обеспечивают, что newly-written references тоже помечаются. Concurrent marking снижает main-thread паузы на 50% на WebGL-heavy workloads (per Google blog). Остающаяся stop-the-world работа — финальный marking step (короткая пауза для верификации view concurrent thread) и sweep/compact фаза (параллельно через worker threads, но всё ещё блокирующая main thread).</p>
    <p><strong>Incremental marking и write barriers.</strong> До Orinoco major GC V8 был полностью stop-the-world операцией, которая могла паузить main thread на сотни мс. Чтобы включить concurrent marking, V8 добавил <em>write barrier</em>: каждый property write, который может пересечь от black (marked) объекта к white (unmarked), триггерит маленький кусок кода, помечающий destination объект grey (для посещения). Write barrier концептуально дёшев (несколько циклов), но происходит на каждой reference write — V8 инвестирует heavily в его быстрое исполнение (специализированные barriers per property type, <Term k="yuasa_snapshot" lang="ru">snapshot-at-the-beginning</Term> vs incremental-update tradeoffs). Результат: marking амортизирован через JS выполнение без observable паузы, только маленький per-write overhead. Современный V8 использует <Term k="tri_color_marking" lang="ru">Tri-color marking</Term> (white/grey/black) с snapshot-at-the-beginning семантикой и гибридным concurrent + incremental scheduling. <em>Выбор marking алгоритма прямо формирует write-barrier cost и pause distribution.</em></p>
    <p><strong>Pointer compression.</strong> V8 6.6 добавил pointer compression: вместо 64-bit pointers V8 хранит 32-bit offsets от base address. Это вдвое уменьшает heap memory для типичных workloads (большинство heaps ниже 4GB). Цена — маленький лишний цикл на каждой pointer dereference (add base, потом load), но cache effects от меньшего heap более чем компенсируют. Pointer compression — причина, по которой V8 per-process heap cap-нут на 4GB по умолчанию — выше нужен larger pointer mode. Pointer compression взаимодействует с hidden classes: per-object hidden class pointer теперь 32 бита, вдвое уменьшая per-object overhead. Для app, аллоцирующего миллионы маленьких объектов (типично для любого крупного JS-фреймворка), pointer compression один экономит сотни MB. Disabled at compile time на системах, где 32-bit offsets недостаточны.</p>
    <p><strong>Реальные production failures.</strong> Discord 2022: chat-feature изменение ввело polymorphic IC в hot path message-render; p99 frame time с 8мс до 25мс; откатили, когда gaming-mode пользователи с 120Hz мониторами заметили. Figma 2023: editor рефакторинг утекал closures в long-lived animation callback, заставляя old gen расти 200MB per session; пофиксили хойстом closure снаружи per-frame call. Google Maps 2024: 3D-tile рендерер попал в megamorphic ICs после typing рефакторинга, где некоторые tile объекты имели extra optional поле; throughput упал 40%, пофиксили always-allocating поле с null when absent. Slack 2021: Node-side serialisation функция деоптимизировалась каждую минуту из-за occasional NaN в numeric reduce; deopt cycle бегал каждые 60с стоимостью 5мс, видимый как periodic latency spikes; пофиксили guard NaN перед hot loop. Паттерн: V8 perf баги прячутся как «небольшой рефакторинг» PRs, сдвигающие shape одного объекта или type signature одной функции; perf регрессия появляется в production, не в CI.</p>
    <p><strong>Isolates: tenant изоляция V8.</strong> Isolate — один независимый V8-инстанс со своим heap, GC и compilation queues. Каждая browser tab — свой Isolate; Node.js имеет один Isolate per process. Isolates не делят state — коммуникация идёт через сериализацию (postMessage, IPC). Это primitive tenant изоляции V8: memory leak в одном Isolate не может повлиять на другой. Worker threads в Node используют Isolates плюс shared memory regions для explicit cross-thread коммуникации. Isolate boundary — также security boundary — V8 sandboxes (экспериментальный V8-Sandbox project) пытается confine memory-corruption баги в heap Isolate, чтобы скомпрометированный скрипт не мог escape в host process memory. Для server-side multi-tenant JS (Cloudflare Workers, Vercel Edge) каждый tenant получает свой Isolate, allowing тысячи tenants per machine со strong memory изоляцией.</p>
