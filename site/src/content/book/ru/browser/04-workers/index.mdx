Главный поток — бутылочное горлышко: один поток на ваш JS, вашу компоновку, вашу отрисовку, ваш ввод. Ответ браузера — не «ускорить поток». Ответ — «дать вам больше потоков». Но дополнительные потоки идут с правилами: нет доступа к DOM, нет общих переменных, коммуникация только через message-passing, и — для самого мощного — пара HTTP-заголовков, которые надо выставить ровно правильно, иначе API молча возвращает `undefined`. Четыре инструмента вне главного потока, четыре разные работы.

<Crux>Поток или прокси: web workers — вычисления, service workers — сеть, worklets — рендеринг, SharedArrayBuffer — общая память.</Crux>

Эти четыре не взаимозаменяемы. **Web worker** — второй JS-поток для CPU-bound работы (парсинг, крипто, обработка изображений) со своим event loop и без DOM. **Service worker** — сетевой прокси, сидящий между страницей и сервером, может отдавать закешированные ответы офлайн и переживает страницу. **Worklet** — крошечный, жёстко ограниченный хук в собственный пайплайн рендеринга или аудио браузера. **SharedArrayBuffer** — единственный побег от message-passing: настоящая общая память между потоками, за гейтом cross-origin isolation. Выбирайте по работе, не по привычке.

    <p><strong>Метафора офиса.</strong> Главный поток — это вы за своим столом: вы отвечаете на телефон (ввод), обновляете доску (DOM) и делаете свою работу — всё сами. <em>Web worker</em> — коллега в задней комнате: вы можете отправить ему большой расчёт запиской (сообщение), он делает его, не трогая ваш стол, и присылает ответ запиской.     <p><strong>Web workers: посвящённый поток вычислений.</strong> `new Worker('worker.js')` поднимает свежий JS-realm на своём OS-потоке, со своим event loop, своим глобалом (`DedicatedWorkerGlobalScope`) и без доступа к `document`, `window` или DOM. Он может использовать `fetch`, `IndexedDB`, `WebSocket`, `OffscreenCanvas`, таймеры, `importScripts`/ES-модули. Коммуникация — исключительно `postMessage` в обе стороны. Воркер привязан к странице, его создавшей: закройте вкладку — и воркер умирает. Используйте его для всего CPU-bound, что иначе пробило бы бюджет задачи 50 мс — парсинг больших JSON-payload-ов, фильтры изображений, криптографическое хеширование, диффинг, сжатие, подсветка синтаксиса, физика. Ментальная модель: воркер превращает длинную синхронную задачу главного потока в асинхронный запрос, резолвящийся позже, освобождая главный поток для ввода и рендеринга тем временем.</p>

    <p><strong>Dedicated, shared и module-воркеры.</strong> Есть три формы. <em>Dedicated worker</em> — самый частый — принадлежит одной странице и обслуживает только её. <em>Shared worker</em> (`new SharedWorker('s.js')`) делится между всеми вкладками одного origin: каждая вкладка коннектится через `MessagePort`, и воркер живёт, пока жива хоть одна вкладка — полезно для одной общей WebSocket-связи или согласованного кеша между вкладками, но поддержка слабее (не во всех браузерах) и отладка тяжелее. Тип воркера также задаётся опцией `{ type: 'module' }`: classic-воркер использует `importScripts()` для синхронной загрузки зависимостей, module-воркер использует обычный статический `import`. Module-воркеры — современный дефолт: они дают tree-shaking, top-level `await` и тот же граф модулей, что и остальное приложение. Classic `importScripts` остаётся только для легаси-кода и случаев динамической сборки имени скрипта в рантайме. Есть тонкость: URL скрипта воркера должен быть same-origin (или blob-URL) — нельзя загрузить воркер прямо со стороннего CDN, не проксировав его сначала через свой origin; это та же origin-граница, что защищает остальную модель безопасности браузера.</p>

    <p><strong>Стоимость structured clone.</strong> `postMessage(data)` не делит `data` — он делает глубокую копию через алгоритм structured clone. Structured clone обрабатывает объекты, массивы, Map, Set, Date, типизированные массивы, Blob и ArrayBuffer, но не функции, DOM-узлы или прототипы классов (методы теряются; переживают только данные). Копия синхронна на отправляющем потоке и масштабируется с размером payload-а: примерно 1 мс на МБ для плоских объектов, больше для глубоко вложенных структур. Отправьте объект на 50 МБ — и вы только что заблокировали отправляющий поток на ~50 мс — вы переместили работу, но заплатили за это налог на клонирование. Два побега: <em>transferables</em> и <em>общая память</em>. `postMessage(data, [data.buffer])` <em>передаёт</em> ArrayBuffer вместо копирования — владение переходит к принимающему потоку за O(1), а буфер становится непригодным на стороне отправителя (`byteLength` уходит в 0). Transfer — правильный ход для больших бинарных payload-ов: bitmap-ы изображений, аудиобуферы, содержимое файлов.</p>

    <p><strong>Service workers: сетевой прокси.</strong> Service worker регистрируется один раз (`navigator.serviceWorker.register('sw.js')`), затем устанавливается и активируется, и с этого момента перехватывает каждый сетевой запрос, исходящий от страниц в его scope, через событие `fetch`. Внутри `fetch`-обработчика вы вызываете `event.respondWith(...)` с `Response` — из Cache API, свежезагруженный, синтезированный или микс. Это то, что включает офлайн-приложения, мгновенные повторные загрузки и манипуляцию запросами. У service worker нет DOM и нет персистентного глобального состояния (браузер свободно убивает и перезапускает его ради экономии памяти), поэтому всё устойчивое состояние живёт в Cache API или IndexedDB. Он работает на своём потоке, независимо от любой страницы — может получать push-уведомления и гонять background sync, даже когда ни одна вкладка не открыта.</p>

    <p><strong>Жизненный цикл service worker.</strong> Регистрация ведёт к <em>install</em> (событие, где вы обычно прекешируете app shell), затем <em>activate</em> (где вы чистите старые кеши), затем цикл idle/running, где он обрабатывает события `fetch`, `push` и `message`. У жизненного цикла одна знаменитая ловушка: только что установленный service worker по умолчанию <em>не</em> берёт под контроль уже открытые страницы — он ждёт в состоянии «waiting», пока не закроется каждая вкладка, использующая старый воркер. Это фича безопасности (она не даёт странице работать с одной версией воркера и протухшим кешем ассетов от другой), но она удивляет всех в первый раз: вы деплоите новый service worker, перезагружаетесь — и всё ещё получаете старый. `self.skipWaiting()` в install-обработчике плюс `clients.claim()` в activate-обработчике переопределяют это — новый воркер активируется немедленно и захватывает открытые страницы. Используйте эту комбинацию осознанно; пропуск ожидания, когда версионирование ассетов не идеально, вызывает режим отказа version-mismatch.</p>

    <p><strong>Стратегии кеширования.</strong> Внутри `fetch`-обработчика вы выбираете стратегию на тип запроса. <em>Cache-first</em>: проверить кеш, фоллбэк на сеть — правильно для неизменяемых, content-hashed статических ассетов (`app.4f3a1c.js`). <em>Network-first</em>: попробовать сеть, фоллбэк на кеш при провале — правильно для API-ответов, которые должны быть свежими, но должны деградировать gracefully офлайн. <em>Stale-while-revalidate</em>: отдать закешированную копию немедленно, фоном загрузить свежую, чтобы обновить кеш на следующий раз — правильно для контента, который может быть слегка протухшим (аватарки, ленты). <em>Network-only</em> и <em>cache-only</em> — вырожденные концы. Библиотеки вроде Workbox дают эти стратегии декларативно с матчингом маршрутов, но сами стратегии — это десять строк кода `fetch`-обработчика; поймите их до того, как тянуться к библиотеке.</p>

    <p><strong>Worklets: хуки в собственный пайплайн браузера.</strong> Worklet — куда меньший, более ограниченный контекст исполнения, чем воркер — он гоняет крошечный сниппет кода <em>внутри</em> подсистемы браузера, на потоке, которым браузер владеет. <em>Paint worklet</em> (CSS Painting API / Houdini) позволяет написать кастомную функцию рисования изображения, вызываемую из CSS как `background: paint(myPainter)` — браузер гоняет её на стадии paint. <em>Animation worklet</em> гоняет логику анимации на потоке композитора, поэтому анимация продолжает плавно идти, даже когда главный поток заблокирован. <em>Audio worklet</em> гоняет код обработки аудио на real-time аудиопотоке, где требования к задержке и джиттеру куда строже всего, что главный поток может пообещать. У worklet-ов почти нет поверхности API — нет DOM, нет fetch, часто нет console — потому что они работают в latency-критичных потоках браузера, где вы гость, а не арендатор.</p>

    <p><strong>SharedArrayBuffer: настоящая общая память.</strong> Каждый инструмент выше копирует или передаёт данные. `SharedArrayBuffer` (SAB) — исключение: это блок памяти, который два потока могут оба читать и писать одновременно, без копии. Вы строите views типизированных массивов над ним на каждом потоке, и они видят те же байты. Поскольку два потока, пишущие в одну память, — это гонка данных, SAB идёт с `Atomics` — `Atomics.load`, `Atomics.store`, `Atomics.add`, `Atomics.wait`, `Atomics.notify` — для безгоночных чтений, записей и межпотоковой блокировки. Это фундамент, делающий многопоточный WebAssembly (pthreads, потоки Rust, потоки C++, скомпилированные в WASM) работающим в браузере. SAB мощен и опасен в равной мере, и он за гейтом: он существует, только когда страница <em>cross-origin isolated</em>.</p>

    <p><strong>Cross-origin isolation: гейт COOP/COEP.</strong> После уязвимости CPU Spectre (2018) высокоточная общая память стала риском безопасности — SAB-таймер достаточно точен, чтобы провести side-channel атаку. Поэтому браузеры заперли SAB за двумя заголовками ответа, которые документ должен слать: `Cross-Origin-Opener-Policy: same-origin` (COOP) изолирует вашу browsing-context-группу от других origin-ов, а `Cross-Origin-Embedder-Policy: require-corp` (COEP) требует, чтобы каждый кроссоригинный сабресурс явно согласился на встраивание. Когда оба присутствуют, `self.crossOriginIsolated` равен `true`, и `SharedArrayBuffer` доступен. Когда их нет, `SharedArrayBuffer` равен `undefined`, и любой код, которому он нужен — особенно многопоточный WASM — молча падает. Подвох — цена: COEP ломает кроссоригинные изображения, шрифты и скрипты, не шлющие подходящий заголовок `Cross-Origin-Resource-Policy`, поэтому включение изоляции часто означает аудит и починку каждого стороннего ассета на странице.</p>

    <p><strong>OffscreenCanvas: единственное исключение из правила «нет DOM».</strong> Воркер не может тронуть DOM, но canvas — особый случай, потому что bitmap canvas — не часть DOM-дерева, это просто буфер пикселей. `OffscreenCanvas` — версия canvas, отвязанная от элемента `<canvas>`. Паттерн: главный поток вызывает `canvas.transferControlToOffscreen()`, получает `OffscreenCanvas`, передаёт его воркеру через transfer-список postMessage. С этого момента воркер владеет рисованием — он может получить 2D-контекст или WebGL-контекст и рисовать целиком на своём потоке, а браузер отражает результат в видимый `<canvas>` главного потока без участия главного потока вообще. Это делает возможными плавные 60 fps WebGL-визуализации, рендеринг карт и игры даже когда главный поток забит. Воркер также может создать standalone `new OffscreenCanvas(w, h)` чисто для off-screen рендеринга — генерации текстур, обработки изображений — и вернуть результат как transferable `ImageBitmap`.</p>

    <p><strong>MessageChannel: прямой канал между двумя контекстами.</strong> `worker.postMessage` связывает страницу с воркером, но иногда нужны два конца канала, которые можно передать куда угодно. `new MessageChannel()` создаёт пару связанных портов — `port1` и `port2`; что запостили в один, приходит на другой. Порты — transferable, поэтому один можно отдать воркеру, а другой — второму воркеру или iframe, и они получают прямой канал, не проходящий через главный поток вообще. Это убирает главный поток как посредника для воркер-воркер коммуникации: без MessageChannel сообщение от воркера A к воркеру B должно пройти A → главный поток → B, два task hop-а и две задачи на загруженном главном потоке. С прямым каналом — один hop, и главный поток свободен. MessagePort также используется внутри `SharedWorker` (каждая вкладка получает свой порт) и в Service Worker (`Client.postMessage`).</p>

    <p><strong>BroadcastChannel: широковещание между вкладками.</strong> Когда нужно не точка-точка, а «сказать всем», есть `BroadcastChannel`. Любой контекст того же origin — вкладка, воркер, service worker — открывает `new BroadcastChannel('updates')`, и `postMessage` на нём доставляется всем остальным подписчикам того же имени. Это правильный инструмент для синхронизации состояния между вкладками: пользователь разлогинился в одной вкладке — broadcast «logout», и остальные вкладки чистят своё состояние; одна вкладка обновила кеш — broadcast «cache-invalidated». Сообщения проходят structured clone, как и в postMessage, и доставляются как задачи. BroadcastChannel не переживает закрытие всех контекстов — для устойчивого межвкладочного состояния нужен IndexedDB; BroadcastChannel — это сигнальный канал поверх него, не хранилище.</p>

    <p><strong>Воркеры и потребление памяти.</strong> Каждый воркер несёт фиксированную цену памяти, которую легко недооценить: свой JS-heap, своя копия любых импортированных модулей, свой стек. На практике пустой воркер — это единицы МБ, воркер с загруженной библиотекой обработки изображений или WASM-модулем — десятки МБ. Породить тридцать воркеров «на всякий случай» — это сотни МБ, которые на бюджетном телефоне выталкивают вкладку под давление памяти и провоцируют её выгрузку браузером. Отсюда правило размера пула `hardwareConcurrency − 1`: оно ограничивает не только конкуренцию за CPU, но и суммарную память. Воркер также надо явно терминировать через `worker.terminate()`, когда он больше не нужен — забытый воркер продолжает держать свою память и свой event loop живыми до закрытия страницы. Утечка воркеров — частый баг в SPA, где компонент создаёт воркер в `useEffect`, но не терминирует его в функции очистки. На каждой перемонтировке компонента появляется новый воркер, старый остаётся висеть, и через десяток навигаций по приложению накапливается пул мёртвых воркеров, который никто не создавал намеренно — память растёт, а профайлер показывает странные простаивающие потоки без явного владельца.</p>

    <h4 class="mt-2 mb-3 text-[15px] font-semibold text-ink tracking-tight">Режим отказа: ожидать, что воркер тронет DOM</h4>
    <p><strong>Ошибка DOM-в-воркере.</strong> Самая частая ошибка с воркерами — архитектурная: команды тянутся к воркеру, чтобы «ускорить рендеринг», и обнаруживают, что воркер вообще не может тронуть DOM. Воркер может вычислить, <em>что</em> должно отрендериться, но никогда не <em>отрендерить</em> это — результат надо запостить обратно и применить главным потоком. Если бутылочное горлышко — сама мутация DOM (10 000 узлов вставлено, гигантская реконсиляция React), воркер не помогает, потому что дорогая часть всё равно происходит на главном потоке. Воркеры помогают, когда бутылочное горлышко — <em>чистое вычисление</em>, производящее маленький результат: распарсить 5 МБ JSON (воркер) → запостить обратно массив на 200 строк (дёшево) → главный поток рендерит 200 строк (быстро). Они не помогают, когда выход вычисления — сам по себе большое DOM-дерево. Исключение — `OffscreenCanvas`: рендеринг canvas — и только canvas — <em>можно</em> делать из воркера, потому что bitmap canvas — не DOM. Передайте `OffscreenCanvas` воркеру, и он может рисовать 2D или WebGL целиком вне главного потока.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">SharedArrayBuffer и Atomics в глубину</h4>
    <p><strong>Зачем существуют Atomics.</strong> Два потока, пишущие в одну ячейку `SharedArrayBuffer` без координации, — это гонка данных, результат зависит от тайминга и не определён. `Atomics` даёт операции, которые CPU гарантирует неделимыми: `Atomics.add(view, i, 1)` читает, инкрементирует и пишет как один непрерываемый шаг, поэтому два потока, инкрементирующие один счётчик, никогда не теряют обновление. `Atomics.compareExchange` — строительный блок для lock-free структур данных. `Atomics.wait(view, i, expected)` блокирует вызывающий поток, пока другой поток не вызовет `Atomics.notify(view, i)` — настоящий блокирующий примитив, поэтому он запрещён на главном потоке (блокировка главного потока — ровно то, что платформа запрещает) и разрешён только внутри воркеров. Эта пара wait/notify — то, как пул потоков WASM паркует простаивающие воркеры и будит их, когда приходит работа.</p>

    <p><strong>Модель памяти.</strong> SAB выставляет <Term k="relaxed_memory_model" lang="ru">relaxed-модель памяти</Term>: без atomics записи одного потока не гарантированно видны другому потоку в каком-либо конкретном порядке — CPU и компилятор могут переупорядочить неатомарные операции с памятью. Атомарные операции устанавливают рёбра синхронизации (<Term k="happens_before" lang="ru">отношения happens-before</Term>), делающие пачку предшествующих неатомарных записей видимой. Практическое правило для прикладного кода: используйте один атомарный флаг как сигнал «данные готовы» — воркер пишет основные данные обычными записями типизированного массива, потом делает один `Atomics.store` на флаге; читатель делает один `Atomics.load` на флаге, и как только видит готовое значение, все основные записи гарантированно видны. Самописные lock-free структуры без этой дисциплины производят баги, появляющиеся только под нагрузкой, только на определённых CPU.</p>

    <p><strong>Growable SAB и WASM-память.</strong> Изначально `SharedArrayBuffer` был фиксированного размера; современная спецификация добавила `new SharedArrayBuffer(size, { maxByteLength })` и `grow()`, чтобы буфер мог расширяться без переаллокации — критично для WASM, где линейная память растёт по мере того, как приложение аллоцирует. Память модуля WebAssembly при компиляции с `-pthread` (Emscripten) или `--shared-memory` (LLVM) <em>является</em> SharedArrayBuffer-ом: все потоки WASM видят одну линейную память, и `memory.grow` в одном потоке должен быть виден остальным. Это место, где модель памяти кусается сильнее всего: указатель, валидный в одном потоке, валиден в другом только потому, что оба смотрят на ту же SAB; но порядок видимости записей всё ещё управляется atomics. WASM-тулчейны генерируют корректные atomic-барьеры сами, поэтому прикладной Rust/C++ код просто работает — но если вы вручную делите SAB между JS и WASM, вы отвечаете за барьеры лично.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Граничные случаи service worker</h4>
    <p><strong>Проблема update-and-version-skew.</strong> Service worker контролирует страницу; его кеш ассетов версионирован под <em>его</em> код. Когда вы деплоите версию N+1, страница может работать с воркером версии N, пока HTML версии N+1 уже отгружен — или наоборот. Если воркер отдаёт cache-first `app.js` из версии N, пока HTML ожидает `app.js` версии N+1, вы получаете рантайм-ошибку от несовпавших модулей. Устойчивый паттерн: content-hash каждое имя файла ассета (`app.4f3a1c.js`), чтобы старые и новые ассеты сосуществовали в кеше без коллизии; прекешировать полный набор для каждой версии под version-tagged именем кеша; в `activate` удалять кеши, чей version-тег не текущий — но только после `clients.claim()`, чтобы ни одна контролируемая страница не потеряла ассеты посреди сессии. Навигационные запросы используют network-first или выделенную app-shell-стратегию, чтобы пользователь всегда приземлялся на HTML, согласованный с активным воркером. Тот же класс багов возникает с самим `sw.js`: браузер по умолчанию кеширует файл воркера до 24 часов, поэтому новый деплой может не подхватиться сутки — современная практика отдаёт `sw.js` с `Cache-Control: no-cache`, чтобы браузер всегда перепроверял его на каждой навигации.</p>

    <p><strong>Service worker-ы недолговечны.</strong> Браузер агрессивно убивает простаивающий service worker — часто в пределах секунд после окончания события `fetch` — и перезапускает на следующем событии. Любое состояние, хранимое в module-level переменной, исчезает на перезапуске. Это частый источник багов: счётчик, кеш запросов в полёте, WebSocket в глобале — всё испаряется. Устойчивое состояние должно жить в `IndexedDB` или Cache API. Долго работающая работа внутри обработчика события должна быть обёрнута в `event.waitUntil(promise)` — это говорит браузеру «не убивай меня, пока этот промис не осядет». Забыть `waitUntil` означает, что браузер может терминировать воркер посреди операции, и background sync, обработка push и наполнение кеша молча не завершаются.</p>

    <p><strong>Навигационный перехват и опасность app-shell.</strong> Самый мощный и самый опасный паттерн service worker — перехват навигационных запросов: `fetch`-обработчик ловит запрос самого HTML-документа и отдаёт закешированный app shell. Это даёт мгновенную загрузку, но создаёт класс багов, который иначе невозможен — service worker может «запереть» пользователей на сломанной версии. Если вы отгрузили баг в app shell и закешировали его cache-first, каждый повторный визит отдаёт сломанный shell из кеша, минуя сеть, где живёт фикс. Пользователь не может выйти из этого обычной перезагрузкой. Защита многослойная: навигационные запросы должны быть network-first с коротким таймаутом (попробовать сеть ~3 с, фоллбэк на кеш) — так фикс доезжает при первой же удачной загрузке; держите «kill switch» — версионный эндпойнт, который воркер проверяет и при сигнале вызывает `self.registration.unregister()` и чистит кеши; и никогда не кешируйте навигацию cache-only. Сломанный service worker, отгруженный широко, — это инцидент уровня «остановить деплой», потому что у обычных пользователей нет кнопки восстановления.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Пулы воркеров и модель стоимости</h4>
    <p><strong>Когда воркеры окупаются — и когда нет.</strong> Породить воркер не бесплатно: новый realm, новый event loop, свежая копия любых импортированных скриптов, обычно 5–20 мс старта плюс несколько МБ памяти. Воркер стоит того, когда задача длинная (десятки мс или больше) и стоимость передачи результата мала относительно вычисления. Это чистый убыток, когда задача короткая — round-trip postMessage и оверхед клона могут превысить саму работу. Для повторяющихся мелких работ не порождайте воркер на работу; держите <em>пул воркеров</em>: фиксированный набор из N воркеров (обычно `navigator.hardwareConcurrency` минус один, чтобы оставить ядро главному потоку), очередь ожидающих работ и диспетчер, отдающий следующую работу следующему свободному воркеру. Пул амортизирует стоимость старта и ограничивает память. Библиотеки вроде Comlink убирают boilerplate postMessage, оборачивая воркер в прокси, чтобы вызовы выглядели как обычные async-вызовы функций — но стоимость клона/transfer и архитектурные ограничения неизменны под капотом.</p>

    <p><strong>Comlink и иллюзия RPC.</strong> Comlink делает `await worker.heavyCompute(data)` похожим на локальный вызов. Это эргономично, но абстракция прячет две стоимости, которые всё ещё важны: каждый аргумент проходит structured clone (или должен быть явно обёрнут `Comlink.transfer`), и каждый вызов — task hop в каждую сторону. Иллюзия ломается для болтливых интерфейсов — API воркера с многими мелкими методами, вызываемыми в плотном цикле, платит task hop на вызов и сериализует программу на round-trip-ах. Проектируйте интерфейсы воркеров грубыми: один вызов, делающий пачку работы и возвращающий пачку результатов, не множество мелкозернистых вызовов. Тот же принцип, что в проектировании сетевого API: минимизировать round-trip-ы, максимизировать работу на round-trip.</p>

    <p><strong>Воркер-пул как структура: backpressure и приоритеты.</strong> Наивный пул — N воркеров плюс FIFO-очередь — ломается под нагрузкой по двум причинам. Первая: без ограничения очередь растёт неограниченно, и если задачи приходят быстрее, чем пул их переваривает, латентность хвоста уходит в секунды, а память — вверх. Решение — backpressure: ограничить длину очереди и либо отбрасывать самые старые задачи, либо отказывать новым (вернуть отклонённый промис), чтобы вызывающий код знал и притормозил. Вторая: не все задачи равны — превью фильтра, которое пользователь ждёт прямо сейчас, важнее фоновой генерации миниатюр. Очередь должна быть приоритетной: задачи с тегом `interactive` обходят задачи с тегом `background`. Зрелый пул также поддерживает отмену — если пользователь увёл скролл от элемента, чья миниатюра ещё в очереди, задачу надо снять; для уже запущенной во воркере задачи отмена означает `worker.terminate()` и пересоздание воркера, что возвращает нас к стоимости старта. Поэтому отменяемость закладывают в протокол: воркер периодически проверяет atomic-флаг отмены в SharedArrayBuffer и сам выходит чисто, без терминирования — это сохраняет воркер живым для следующей задачи и убирает повторную стоимость старта, которую `terminate()` навязывает на каждую отмену.</p>

    <h4 class="mt-8 mb-3 text-[15px] font-semibold text-ink tracking-tight">Production-наблюдаемость</h4>
    <p><strong>Отладка через потоки.</strong> Каждый воркер и каждый service worker — отдельный контекст в DevTools. Web worker-ы появляются в списке потоков панели Sources; у service worker-ов выделенная панель под Application → Service Workers, показывающая состояние жизненного цикла (installing, waiting, activated), с кнопками skipWaiting, unregister и force-update. Панель Application → Cache Storage показывает ровно то, что service worker закешировал. Для production-телеметрии инструментируйте обе стороны каждого postMessage таймстемпами, чтобы измерять реальную задержку task hop и стоимость клона в поле — локальная разработка на быстрой машине систематически занижает обе. Отслеживайте длительность `fetch`-обработчика service worker: медленный обработчик задерживает каждую навигацию и загрузку ресурса на странице, и поскольку он работает до того, как главный поток увидит ответ, регрессия там невидима для обычного профилирования главного потока.</p>

<Misconception id="mc-worker-dom">
**Миф:** перенести медленный рендеринг в web worker, чтобы ускорить его.

**Реальность:** у воркеров нет DOM — они вычисляют, *что* рендерить, рендеринг делает главный поток. Помогают, когда горлышко — чистое вычисление с малым результатом, не большое DOM-дерево. Canvas — исключение, через `OffscreenCanvas`.
</Misconception>

<KeyTakeaway>Четыре инструмента вне главного потока, четыре работы: web workers выносят вычисления, service workers проксируют сеть, worklets хукают пайплайн рендеринга, SharedArrayBuffer делит память. Ни один не трогает DOM. `postMessage` по умолчанию делает глубокую копию — передавайте большие буферы. SharedArrayBuffer нужны COOP + COEP, иначе он `undefined`.</KeyTakeaway>

<p class="text-ink-2 my-6">Каждый воркер — инкапсулированный контекст исполнения: свой realm, свои глобалы, свой цикл, жёсткая граница, которую данные пересекают только через определённый интерфейс сообщений. Эта изоляция и есть смысл — она делает второй поток безопасным, поскольку DOM остаётся single-owner, а гонки становятся невозможны. Тот же принцип инкапсуляции, что делает приватное состояние модуля безопасным для рассуждений, здесь энфорсится на границе потоков. <SpiralCue thread="encapsulation" lang="ru" /></p>
