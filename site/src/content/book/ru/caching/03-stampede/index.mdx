Кеш-слой должен поглощать нагрузку. Инвалидация (эта глава, 02) должна держать его честным. Но в момент, когда горячий ключ истекает под трафиком, кеш перестаёт поглощать — каждый параллельный запрос промахивается одновременно и врывается в БД. БД, которую кеш прятал, впервые видит свою настоящую нагрузку. Это и есть cache stampede: режим отказа, когда сам кеш становится оружием.

<Crux>Один TTL истёк. 10000 запросов разом. БД видит flash-DDoS из своего кеша. Четыре фикса: lock, single-flight, XFetch, SWR.</Crux>

Форма универсальная: любой кеш с TTL плюс достаточно параллельного трафика порождает stampede, когда TTL срабатывает. Главная страница блога кешируется на 60 с, 5000 RPS устойчиво — на 60-й секунде все 5000 запросов следующей секунды промахиваются и бьют в рендерер. Рендерер был рассчитан на 50 RPS (полагался на кеш). CPU БД вертикально вверх, p99 ползёт, часть запросов таймаутится, таймаутнутые ретраят, ретраи умножают стадо, и система входит в метастабильный отказ, где каждая граница TTL — новая авария. Лекарство не «длинный TTL» — это только сдвигает «когда». Это один из четырёх механизмов, гарантирующих, что rebuild делается ограниченным числом вызывающих, независимо от того, сколько промахнулось одновременно.

    <p><strong>Механика стада.</strong> Кеши перед БД (Redis, memcache), перед вычисленными результатами (трансформации изображений, ML-инференсы) или перед upstream API (third-party data) — все имеют одну форму: ключ, TTL, бэкенд rebuild-путь. Когда приходит запрос, слой кеша делает <code>GET key</code>; если результат не null и не истёк — возвращает (cache hit). Если null или истёк — запускает rebuild, сохраняет с TTL, возвращает. При низкой параллельности это работает: на границе TTL первый запрос триггерит один rebuild и сохраняет новое значение; все последующие в TTL-окне — hit. При высокой параллельности граница уничтожается: запросы 1..N (N — число параллельных в-полёте) все запускают rebuild параллельно, потому что попали между моментом истечения и моментом, когда любой из них записал новое значение. БД видит N-кратную нагрузку.</p>
    <p><strong>Митигация 1: распределённый лок.</strong> Перед rebuild — захват лока. В Redis канонический примитив: <code>SET lock:key 1 EX 5 NX</code> — установить, если не существует, истечь через 5 с. Первый запрос захватывает лок и делает rebuild; последующие получают <code>nil</code> от SET (NX не сработал), видят, что лок занят, и либо ждут-и-ретраят, либо возвращают fallback (stale-значение, дефолтную страницу, пустой 204). После rebuild лок удаляется явно. 5-секундный EX — страховка: если rebuilder упал, лок авто-освободится. Компромисс: локи сериализуют rebuild на всю флоту, любой нод может ребилдить, но только один за раз. Ожидающие добавляют латентность. EX лока должен быть длиннее самого медленного ожидаемого rebuild, но достаточно коротким, чтобы падение не глушило трафик надолго.</p>
    <p><strong>Митигация 2: single-flight / request coalescing.</strong> Распределённые локи координируют через флоту; single-flight — внутри одного процесса. Паттерн: in-process map <code>key → in-flight Promise</code>. Когда нужен значение, проверь map. Если Promise уже в полёте — верни его (запрос подписывается на ту же вычисление). Если нет — создай новый Promise, запусти rebuild, положи в map, верни. После resolve — удали из map. В стандартной библиотеке Go это <code>singleflight.Group.Do</code>; в Node — <code>p-memoize</code> в той же форме. Single-flight намного дешевле распределённого лока — нет сетевого round-trip, координация в памяти. Дедуплицирует только внутри одного процесса: фло из 10 нод всё равно имеет 10 параллельных rebuild на истечении, но каждая нода схлопывает собственное стадо из тысячи запросов в один. Комбинируй с per-key локом для полного покрытия.</p>
    <p><strong>Митигация 3: probabilistic early expiration (XFetch).</strong> Vattani et al. (VLDB 2015) предложили подход без координации: каждое чтение вероятностно решает, обновлять ли кеш заранее, в зависимости от близости истечения. Формула: refresh если <code>-beta * delta * ln(random()) &gt; time_to_expire</code>, где <code>delta</code> — типичная длительность rebuild в секундах, <code>random()</code> — равномерное случайное в (0,1), <code>beta</code> — настроечная константа (по умолчанию 1.0). С приближением TTL вероятность растёт, и какой-то «удачливый» читатель обновляет кеш до истечения, пока остальных обслуживает ещё-валидный кеш. В среднем — ровно один ранний refresh на TTL-окно, размазанный случайно. Никаких локов, координации, осведомлённости о флоте — каждый читатель решает независимо. Подвох: XFetch работает только при достаточной частоте чтений, чтобы «какой-то читатель» поймал вероятностный порог до TTL. Для холодных ключей со спорадическими чтениями XFetch может промахнуться по окну и сделать stampede как наивный TTL.</p>
    <p><strong>Митигация 4: stale-while-revalidate.</strong> RFC 5861 определяет cache-директиву «отдавай stale значение до N секунд, пока обновляешь в фоне». Серверная сторона хранит не только значение и его TTL, но и более длинное stale-grace-окно. На чтение после TTL, но в пределах stale-grace, кеш возвращает stale-значение немедленно и ставит в очередь фоновый refresh. Пользователь видит один быстрый ответ со слегка устаревшими данными; кеш переполняется для следующего читателя. CDN (Cloudflare, Fastly, Akamai) поставляют SWR годами; ISR в Next.js — это SWR для полных страниц. Компромисс: читатели терпят немного staleness. Паттерн явно принимает, что кешированное представление может отставать от source of truth на stale-grace-окно — обычно ок для product listing, контента, всего, что не требует strong consistency.</p>
    <p><strong>Facebook memcache leases: production-эталон.</strong> Nishtala et al. (NSDI 2013) описывают подход Facebook как «memcache leases»: при miss кеш возвращает 64-битный lease token вместе с null. Только клиент, держащий токен, может записать новое значение. Параллельные miss-клиенты на тот же ключ получают miss, но без lease — им говорят ждать. Дополнительно: lease-ы тротлятся — ключ получает не более одного lease раз в 10 секунд. Заявленное влияние: пиковый QPS БД упал с 17K до 1.3K — примерно 13× редукция. Lease — это lock + throttle в одном механизме. Memcache реализует server-side; Redis нативного эквивалента не имеет, но моделируется через <code>SET lease:key uuid EX 10 NX</code> плюс клиентскую логику проверки uuid перед записью.</p>
    <p><strong>Композиция: defence in depth.</strong> Production-защита от stampede редко использует одну митигацию. Канонический стек: SWR на edge (Cloudflare или ваш CDN) поглощает основную массу expiry-трафика, отдавая stale; XFetch на origin-кеш-слое предотвращает stampede следующего слоя, обновляя до истечения; single-flight в каждом инстансе приложения схлопывает остаточное стадо; per-key распределённый лок сериализует rebuild через флот для ультра-горячих ключей. Каждый слой снижает размер стада на порядок. Полностью собранная конфигурация берёт 10000 параллельных miss-ов и превращает в один rebuild где-то в стеке — каждый другой запрос вернул stale-but-acceptable значение или ждал на in-flight rebuild.</p>
    <p><strong>Детектирование stampede в production.</strong> Отпечаток резкий: at-TTL-boundary пики CPU БД, query count и request latency, с регулярной периодичностью, совпадающей со значением TTL. TTL 60 с даёт 60-секундные пики; TTL 300 с — каждые пять минут. Метрики: <code>cache_miss_total</code> rate (нормальный кеш — низкий и ровный, stamped — резкие периодические пики), <code>db_query_rate</code> p99 (резкие пики на TTL-границах — downstream stampede), <code>rebuild_duration_seconds</code> (длинные хвосты на границе — contention). Митигации оставляют следы: SWR — <code>cache_stale_serve_total</code> (ненулевой во время refresh); single-flight — <code>singleflight_subscriber_count_p99</code> (число выше 1 — coalescing работал); лок — <code>lock_wait_total</code> и <code>lock_acquire_duration</code>. Без инструментации stampede невидим до того, как вызовет outage.</p>
    <p><strong>Негативное кеширование и miss-шторма.</strong> Та же форма stampede применима, когда ответ — «не найдено». Если приложение кеширует null из БД с тем же TTL, что положительные результаты, поток запросов на несуществующие ключи производит инверсный stampede: каждый промах кеша — это miss-lookup в БД, который под высокой параллельностью перегружает БД так же полно, как положительные промахи. Митигация в двух частях: кешируй sentinel «нет такой строки» с намного более коротким TTL (5–30 с против положительного 60–300 с), чтобы черн памяти был ограничен; и используй Bloom-фильтр перед кешем, чтобы отклонять lookup для ключей, которые точно не существуют (false-positive ~1% — ок; фильтр пересоздаётся при ребилде таблицы). Без негативного кеширования атакующий чеканит случайные несуществующие ключи (например, случайные UUID в URL), усиливая нагрузку на БД на порядки — задокументированный паттерн атаки, поразивший несколько CDN-сайтов в 2024.</p>
    <p><strong>Pre-warming и cache-priming.</strong> Когда кеш-слой перезапускается (deploy, eviction, restart машины), он стартует пустым. Каждый входящий запрос промахивается и бьёт в БД. Период восстановления — собственный мини-stampede: если перезапустить на пиковом трафике, получишь full-traffic origin-спайк. Production-кеши избегают это pre-warming на старте: проиграть вчерашние топ-N URL в новый кеш до приёма публичного трафика. Edge-ноды Cloudflare pre-warm-ятся из соседних POP; Redis-as-cache деплои используют startup-скрипт, читающий «топ 1000 ключей» из audit-лога и прогревающий кеш. Pre-warming — единственный безопасный deploy-стратегия для cache-tier апгрейдов: blue-green кеш-инстансы, прогреть green, переключить трафик. Cold-start stampede — самая частая причина post-deploy сбоев у высокотрафиковых сайтов.</p>
    <p><strong>Hot-key shedding и адаптивные стратегии.</strong> Некоторые production-системы (DynamoDB Accelerator, Caffeine с adaptive admission) детектируют «горячие» ключи на лету и применяют усиленную защиту только к ним. Идея: 99% ключей имеют слабый трафик и не нуждаются в локе/lease — их можно обслуживать наивным cache-aside без штрафа за координацию. 1% горячих ключей даёт 99% riska stampede — на них и нужны все механизмы. Адаптивная политика трекает per-key RPS sliding window (например, последние 60 с) и переключает горячие в «защищённый режим»: single-flight + lock + SWR. Tradeoff: нужен дополнительный учёт per-key — но это копеечно (Caffeine использует frequency sketch размером ~10 КБ на миллион ключей). Без адаптации либо тратишь координацию на холодные ключи (медленно для 99%), либо не защищаешь горячие (stampede на 1%). Адаптация — единственный способ получить и то и другое.</p>
    <p><strong>Per-tier eviction и связь с stampede.</strong> Eviction-политика (LRU, LFU, TinyLFU, ARC) определяет, какие ключи кеш выкидывает при нехватке памяти. Наивная LRU создаёт собственный stampede-вектор: при заполнении кеша одна горячая запись может вытеснить другую горячую, и обе следующих запроса промахиваются — каскадное промахание, особенно болезненное под давлением памяти. TinyLFU (используется в Caffeine) — admission filter: новый ключ попадает в кеш только если frequency-sketch говорит, что он будет переиспользован. Это защищает горячий working set от вытеснения cold-key потоком. Связь со stampede: правильная eviction-политика снижает базовый miss-rate, что снижает amplitude любого stampede. LRU + miss-amplification атака = катастрофа; TinyLFU + та же атака = слабая деградация. Production-кеши без admission filter уязвимы к cache pollution attacks, специально проектируемых заполнить кеш cold-keys и вытеснить hot working set. Стандартный паттерн атаки: атакующий генерирует поток уникальных query-параметров на одну страницу, форсируя кеш создать миллион уникальных записей и вытеснить реально-горячие. Защита — нормализация ключа кеша (отбросить нерелевантные query-параметры до hash-ключа) или admission filter, отказывающий записи с low-frequency сигналом.</p>
    <p><strong>Backpressure и rebuild-приоритеты.</strong> Когда rebuild-путь под нагрузкой, не все rebuild равны. Главная страница, виденная всеми пользователями, важнее чем пользовательский профиль, виденный одним. Production-кеши добавляют priority-queue к rebuild-очереди: high-priority ключи (топ-1000 по RPS) ребилдятся first; low-priority — last или вообще отказываются с явным fallback. Реализуется как weighted priority queue перед thread pool, исполняющим rebuild. Cara может также сигнализировать backpressure upstream: вернуть 503 на low-priority ключи, пока high-priority обслуживается. Это inversion of «всё равно важно» — система признаёт, что под насыщением некоторое падение качества выгоднее, чем равномерный коллапс. Stripe публиковал свой rebuild-priority шаблон в инженерных постах — критично для платёжных API, где «отказать в красивой странице» лучше, чем «отказать в платеже».</p>

    <p><strong>Вывод XFetch: почему экспонента оптимальна.</strong> Vattani et al. (VLDB 2015) формулируют проблему: дан ключ кеша с TTL <code>t</code> и стоимостью rebuild <code>delta</code>, спланируй refresh так, чтобы (a) кеш редко истекал под нагрузкой, (b) ровно один refresh на TTL-окно в среднем, (c) никакой координации между читателями. Распределение, удовлетворяющее всем трём — экспоненциальное. Правило решения: <code>refresh ← random_exp(beta * delta) ≥ time_to_expire</code>, что упрощается до <code>refresh ← -beta * delta * ln(random()) ≥ time_to_expire</code>. Ожидаемая доля чтений, триггерящих ранний refresh, интегрированная по TTL-окну, равна одному. Variance — точно variance экспоненциального. Параметр <code>beta</code> регулирует агрессию: меньше beta — раньше refresh (больше staleness-avoidance, больше пустой работы), больше beta — позже (ближе к TTL, меньше окно refresh). Оригинальная работа доказывает: ни один coordination-free алгоритм с этими гарантиями не побьёт экспоненту по expected work; любое более жёсткое правило требует либо координации, либо большей variance.</p>
    <p><strong>Memcache leases Facebook: алгоритм в деталях.</strong> Memcache lease — 64-битный токен, возвращаемый вместе с cache miss. Протокол: клиент читает ключ, получает null плюс lease-token. Только клиент с валидным токеном на ключ может делать SET. Сервер трекает последний выданный lease на ключ; SET с несовпадающим токеном тихо игнорируется. Throttle: memcache-сервер выдаёт не более одного lease на ключ за 10 секунд. Если второй miss приходит в пределах 10с, сервер возвращает null без lease, и клиент отступает (ждёт 100мс-1с, ретраит GET — к тому моменту другой клиент скорее всего записал значение). Параллельные miss-handlers распределены по флоту, self-координируются через ownership lease; только один пишет, остальные обслуживают предыдущее (stale) значение или отступают. Nishtala et al. (NSDI 2013) сообщают 17K → 1.3K QPS редукция на пике. Механизм заодно фиксит race с инвалидацией: SET от старого read тихо игнорируется, потому что lease стал невалидным в момент инвалидации значения.</p>
    <p><strong>Cloudflare и Fastly request collapsing на edge.</strong> Production CDN реализуют single-flight на кеш-слое: когда edge видит N одновременных miss на один путь, она форвардит ровно один origin-запрос и пайпит ответ всем N ожидающим client-соединениям. Cloudflare называет это «request coalescing»; Fastly — «request collapsing». Механизм — часть lifecycle кеша: miss входит в состояние «stitching», originating один upstream fetch; новые misses на тот же ключ во время stitching подсоединяются к in-flight fetch. Ответ разливается на все подключённые соединения одновременно. Эффект на edge: вирусный контент-event (10М зрителей хитят один URL) производит один origin-fetch, не 10М. Обе CDN публикуют, что request collapsing превращает sudden-traffic инциденты в low-impact события на origin; без него каждый CDN miss = upstream load.</p>
    <p><strong>Семантика stale-while-revalidate: RFC 5861.</strong> Cache-Control extensions в RFC 5861 добавляют два значения: <code>stale-while-revalidate=N</code> (отдавай stale-ответ до N секунд, пока revalidate в фоне) и <code>stale-if-error=N</code> (отдавай stale-ответ до N секунд, если revalidate упал). Вместе они формируют поведение кеша на истечении: когда кешированный ответ за <code>max-age</code>, но в пределах stale-while-revalidate, кеш возвращает его немедленно и асинхронно инициирует fetch к origin. Cloudflare реализует на edge; Vercel ISR — та же форма на framework-уровне; Apollo GraphQL кеширование использует для нормализованных cache-entries. Дизайн-компромисс: пользователь всегда видит быстрый ответ, source-of-truth асинхронно согласуется. Критично для content/feed API; непригодно для эндпоинтов, требующих strong consistency (баланс счёта, vote count, всё, что влияет на business logic).</p>
    <p><strong>Cache-Aside, Read-Through, Write-Through и их stampede-профили.</strong> Cache-aside (приложение владеет чтениями и записями в кеш) — самая stampede-prone форма: каждый читатель проверяет кеш, на miss читает БД и пишет кеш, без встроенной координации. Read-through (библиотека кеша прозрачно фетчит из БД на miss) может встроить single-flight, если библиотека реализует (Caffeine, Redis с redisson_client_side_caching, Apollo RestDataSource). Write-through (каждая запись бьёт и БД и кеш) убирает класс stampede, держа кеш всегда-свежим — ценой удвоенной write-latency. Write-back (запись в кеш, async в БД) имеет свою stampede-форму: бёрсты cache-writes могут заливать БД асинхронно. Выбирай по access pattern: cache-aside для read-heavy с терпимым staleness, write-through для транзакционного state, write-back для high-write throughput.</p>
    <p><strong>Негативное кеширование и miss-amplification атаки.</strong> Тонкая production-ловушка: если БД возвращает «нет такой строки», и приложение кеширует null, появляются два режима отказа. Первый: вредоносный клиент запрашивает случайные несуществующие ключи, чтобы наполнить кеш null (cache-poison-by-flood). Второй: после реального INSERT кеш всё ещё имеет null, и новая строка невидима до истечения TTL. Митигация: явный sentinel «missing» с коротким TTL (5–30с, намного короче положительного) и per-key write-through invalidation, удаляющая негативную запись на INSERT. Некоторые кеши (Redis с bloom-фильтрами, DynamoDB с item-not-found cache) поддерживают нативно. Другая форма — DDoS запросами на много холодных ключей для амплификации DB misses — реальный паттерн атаки «cache miss attack», поразивший CDN в 2024 и вызвавший минимум два крупных публичных инцидента.</p>
    <p><strong>Реальные production-сбои.</strong> Reddit 2017: feed-cache изменение без single-flight дало 3× DB-пики на каждом TTL; откатили за час после того, как on-call запейджили по CPU БД. Shopify 2020: Black Friday flash-sale страница с TTL 30с без SWR; вся storefront-edge имела multi-second outage на каждой TTL-границе первые 10 минут — пофиксили деплоем stale-grace 5мин. Twitter 2022: timeline cache stampede от unrelated invalidation-бага; инвалидация триггерила 30М параллельных rebuild и DB-pool насытился 4 часа. Cloudflare 2024 раскрыл coalescing-баг в KV-кеше, кратко позволявший N запросам на тот же ключ обойти coalescing в окне деплоя. Паттерн всех четырёх: stampede-защита либо отсутствовала, либо мис-сконфигурена, либо имела баг, побеждающий её под нагрузкой — и цена была outage, пропорциональный gap-у защиты.</p>
    <p><strong>Инструментация для наблюдаемости.</strong> Minimum-viable инструментация для stampede-защиты: <code>cache_request_total</code> по outcome (hit/miss/stale) и префиксу ключа, <code>cache_rebuild_duration_seconds</code> гистограмма с p50/p99/p99.9, <code>cache_lock_acquired_total</code> и <code>cache_lock_wait_seconds</code>, <code>cache_singleflight_subscriber_count</code> гистограмма (длинный хвост — coalescing делает реальную работу), <code>cache_swr_stale_serve_total</code> (ненулевой во время refresh-окон), <code>cache_swr_background_refresh_total</code> и per-key версия, <code>cache_lease_throttled_total</code> для memcache leases. Алерты на три сигнала: (1) cache_miss rate выше N × steady_state (stampede в процессе или близко), (2) DB QPS p99 выше K × p50 (пилообразный от boundary-пиков), (3) cache_lock_wait_seconds_p99 выше длительности rebuild (локи в очереди). Без этого первый признак stampede — это БД, пейджущая on-call.</p>
    <p><strong>Дизайн TTL за пределами статических значений.</strong> Per-key TTL jitter: вместо TTL=60 для каждого ключа — TTL=uniform(45, 75), чтобы разные ключи истекали в разное время. Фло из 1000 ключей с jittered TTL даёт плавную кривую нагрузки на БД вместо синхронизированных пиков. Production-кеши (Caffeine, Memcached, Redis с manual jitter) поддерживают либо нативно, либо через wrapper. Динамический TTL: укорачивай TTL, когда кеш-item переиспользован в lifetime, удлиняй когда редкие чтения — adaptive caches типа Caffeine W-TinyLFU реализуют. Per-tier TTL: короткий на edge (CDN, ~секунды), длиннее на app-cache (Redis, ~минуты), самый длинный на warm-cache backing store (S3, ~дни). Каждый tier поглощает трафик на своей границе, и даже если все истекают близко, нижний слой обслуживает miss верхнего без round-trip к БД.</p>
    <p><strong>Кросс-протокол композиция: cache + CDN + DB.</strong> Современный стек имеет минимум три cache-слоя. Browser cache (per-user, микросекунды) поглощает reload-бёрсты. CDN (per-edge, миллисекунды) поглощает вирусный трафик с SWR + request coalescing. App-cache (Redis, ~мс) поглощает API-shape трафик с single-flight + lock. БД (~десятки мс, медленная истина) видит только то, что верхние слои не поглотили. Stampede на любом tier пропагируется на следующий; SWR на CDN поглощает CDN-уровень expiry; single-flight на app поглощает app-уровень; lock на app поглощает cross-app-instance. Full-stack правило: stampede каждого tier должен быть локально ограничен, чтобы tier ниже видел один rebuild на N misses, независимо от N. Если любой tier ломает это, сбой каскадирует вниз.</p>
    <p><strong>Метастабильная форма сбоя.</strong> Cache stampede может протолкнуть систему в метастабильное состояние, из которого она не восстанавливается, даже когда исходная причина ушла. Последовательность: TTL истекает, стадо бьёт БД, CPU БД 100%, запросы в очереди, queue-depth растёт за timeout, запросы таймаутят, клиенты ретраят (часто с exponential backoff, но backoff не применяется, потому что они считают, что таймаут был их виной), ретраи умножают стадо, queue растёт дальше, латентность вверх, больше таймаутов, больше ретраев. Система теперь в self-sustaining storm, где кеш не успевает ребилдить, потому что БД занята обслуживанием ретраев. Восстановление требует либо (a) load shedding на front door (возвращать 503 немедленно при перегрузке, чтобы сломать retry-loop), (b) circuit-breaking rebuild-пути (отдавать stale forever, пока БД не восстановится), либо (c) рестарт application-серверов, чтобы сбросить in-flight ретраи. Bouman et al. (2024) формализовали как metastability-паттерн; митигация та же, что и для любого метастабильного сбоя: явный «kill the herd» сигнал, переопределяющий нормальное поведение кеша во время шторма.</p>
