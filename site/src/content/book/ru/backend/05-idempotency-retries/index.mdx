Жизненный цикл запроса (<a href="/ru/backend/01-request-lifecycle/">01-request-lifecycle</a>) заканчивается отправкой ответа. Но что если клиент его так и не увидел — TCP RST, 504 от балансировщика, телефон потерял сигнал в середине POST? Клиент повторит. Если твой эндпоинт создаёт state, пользователь только что заплатил дважды.

<Crux>Как сделать так, чтобы каждый retry-safe POST стоил пользователю ровно одного исхода, даже если сеть проглотила ответ.</Crux>

Интернет не гарантирует, что запрос обработан ровно один раз. Он гарантирует "at-least-once", если клиент повторяет до явного ответа, и "at-most-once", если не повторяет вообще. Приложение должно перекинуть мост через этот разрыв. Мост называется идемпотентностью: спроектируй POST так, чтобы двойная обработка была наблюдаемо неотличима от одной, и дай клиенту спокойно ретраить.

    <p><strong>Что реально несёт заголовок Idempotency-Key.</strong> Идемпотентный ключ — это непрозрачная клиентская строка, обычно 16-байтный UUID v4, отрендеренный в 36 символов, передаваемый в HTTP-заголовке <code>Idempotency-Key</code>. Клиент выбирает один свежий ключ на логическую операцию, не на запрос: каждый retry той же операции переиспользует тот же ключ. Stripe популяризировал конвенцию; Square, PayPal, Adyen и IETF-черновик "The Idempotency-Key HTTP Header Field" (draft-ietf-httpapi-idempotency-key-header) сходятся примерно на одной форме. Сервер обращается с ключом как с primary lookup-токеном "уже обрабатывал?".</p>
    <p><strong>Серверный state machine.</strong> Когда запрос с Idempotency-Key прилетает на сервер, он проходит четыре состояния. <strong>(1) New</strong>: строки с этим ключом нет. Сервер пишет <code>(key, request_fingerprint, status=in_progress, expires_at)</code> в одной транзакции с собственно бизнес-работой (или прямо перед ней), обрабатывает работу, потом обновляет строку body ответа и кодом статуса. <strong>(2) In flight</strong>: строка с status=in_progress существует. У сервера два варианта — вернуть <code>409 Conflict</code> сразу (подход Stripe), чтобы клиент откатился, или коротко заблокироваться в ожидании завершения in-flight (некоторые платёжные гейтвеи делают так с коротким таймаутом). <strong>(3) Replay</strong>: строка с status=completed и сохранённым body. Сервер возвращает кешированный ответ с исходным кодом статуса, не перезапуская бизнес-логику. <strong>(4) Mismatch</strong>: строка с тем же ключом, но другим fingerprint (клиент переиспользовал ключ для другой операции). Сервер возвращает <code>422 Unprocessable Entity</code> с объяснением; приложение должно сгенерировать новый ключ для новой операции.</p>
    <p><strong>Fingerprint запроса важен.</strong> Fingerprint — это хеш метода запроса, пути, query, body и любых заголовков, которые сервер считает частью идентичности операции. Stripe хеширует body, но не заголовки; платёжные API, зависящие от <code>Stripe-Account</code> заголовка, явно его добавляют. Fingerprint ловит класс клиентских багов: код переиспользует idempotency-key, но меняет amount или recipient. Без fingerprint check второй запрос молча проиграл бы первый ответ, и второй amount был бы потерян. Цена — одна SHA-256 на запрос (микросекунды) — дешёвая страховка от тихой потери реального изменения.</p>
    <p><strong>Где хранить кеш.</strong> Простейшая реализация — таблица Postgres: <code>idempotency_keys (key TEXT PRIMARY KEY, fingerprint TEXT, response_body JSONB, response_status INT, status TEXT, expires_at TIMESTAMPTZ)</code>. Индекс по key. Дневная cleanup-задача удаляет строки за expires_at. Stripe держит ключи 24 часа; их API v2 расширил до 30 дней. На больших нагрузках кеш переезжает в Redis с TTL на каждый ключ — но Redis может потерять ключи на failover, поэтому платёжные API, несущие юридическую ответственность за двойные списания, обычно держат каноничную запись в транзакционной базе и используют Redis только как read-through cache.</p>
    <p><strong>Стратегия retry на клиенте.</strong> Клиентская сторона симметрична: не ретрай без backoff. Минимально жизнеспособный цикл — "exponential backoff with jitter": каждая попытка ждёт <code>random_between(0, min(cap, base × 2^attempt))</code> перед следующим ретраем. <code>base</code> обычно 100–500мс, <code>cap</code> обычно 30–60с, число попыток ограничено 3–6 в зависимости от критичности операции. Jitter обязателен: без него падение сервиса, который флапит 5000 клиентов на одну и ту же отметку в 2 секунды, бьёт сервер сильнее исходного сбоя. С полным jitter эти 5000 ретраев равномерно размазываются по 2-секундному окну, сглаживая нагрузку. Реализации: AWS SDK <code>StandardRetryStrategy</code>, Tenacity (Python), Resilience4j (Java), npm <code>retry</code>, встроенный gRPC retry config.</p>
    <p><strong>Какие HTTP-методы идемпотентны по спецификации.</strong> RFC 9110 §9.2.2 говорит явно: GET, HEAD, PUT, DELETE и OPTIONS идемпотентны по определению. POST — нет. PATCH условно идемпотентен — зависит от семантики patch-документа. Для платёжных API "POST + idempotency key" — идиома, потому что POST — естественный глагол для "создать списание", но операция должна быть безопасна для retry. PUT (идемпотентен по REST-семантике) иногда используется вместо POST для "обновить или создать с этим id" workflow.</p>
    <p><strong>At-least-once + idempotent processing = effectively-once.</strong> Настоящая exactly-once-доставка через сеть невозможна (Two Generals' Problem — обе стороны не могут одновременно согласиться, что что-то произошло без дополнительных раундов коммуникации). Production-системы соглашаются на at-least-once-доставку (retry до подтверждения) плюс идемпотентную обработку (сервер дедуплицирует). В комбинации наблюдаемое поведение — exactly-once: операция происходит один раз, сколько бы retry ни было, остаются no-op. Kafka, AWS SQS, Stripe webhooks, RabbitMQ, GCP Pub/Sub — все доставляют at-least-once и инструктируют консумеров дедуплицировать. Работа инженера приложения — сделать консумера действительно идемпотентным: не просто "второе сообщение возвращает тот же ответ", а "второе сообщение не имеет никакого наблюдаемого side effect кроме проигрывания первого ответа".</p>
    <p><strong>Прикладные паттерны на стороне клиента.</strong> Клиент идемпотентного API типично оборачивает каждый POST в retry-loop с jitter, capped budget и deadline — три самостоятельных инструмента, каждый из которых работает на свой класс отказа, и без любого из них защитный контур остаётся дырявым. Реализации: AWS SDK v3 (<code>maxAttempts</code> + <code>retryMode=standard|adaptive</code>), gRPC retry config через service-config JSON (<code>maxAttempts</code>, <code>initialBackoff</code>, <code>maxBackoff</code>, <code>backoffMultiplier</code>), HTTP-клиент Axios + <code>axios-retry</code>, Go <code>retryablehttp</code>, Rust <code>reqwest-retry</code>. Что важно настроить: condition для retry (5xx и timeout — да; 4xx — нет, потому что клиент сломан); deadline (общее время на операцию, чтобы retry не прятал outage); retry budget (token-bucket из allowed retry per second), который ломает цикл, если бэкенд не отвечает несколько секунд подряд. Без budget retry-петля превращается из защиты в усилитель outage.</p>
    <p><strong>Серверная защита от retry storm.</strong> Хороший сервер не только дедуплицирует, но и просит клиента притормозить. HTTP стандартный механизм — заголовок <code>Retry-After</code> в ответе 429 (Too Many Requests) или 503 (Service Unavailable): значение в секундах или absolute date, сообщающее "перестань ретраить хотя бы N секунд". Хорошо настроенный клиент уважает Retry-After перед использованием своего собственного backoff. gRPC использует трейлер <code>grpc-retry-pushback-ms</code> для того же. Серверная сторона также внедряет rate-limiting на per-client уровне (429 c указанием remaining budget), что превращает retry storm в graceful degradation: каждый клиент получает 429 с Retry-After, ждёт указанное время, разрозненно возвращается.</p>
    <p><strong>Интеграция с service mesh и edge.</strong> На уровне инфраструктуры Envoy и Istio выставляют retry-policy per-route: <code>retries.attempts</code>, <code>retries.perTryTimeout</code>, <code>retries.retryOn</code> (например, <code>5xx,reset,connect-failure,refused-stream</code>), и retry-budget, общий для кластера. AWS API Gateway имеет встроенную поддержку идемпотентности с 2023 года с TTL до 10 минут per-stage. Cloudflare Workers выставляют <code>Cache.put</code> с TTL-примитивом, который некоторые команды переиспользуют как дешёвый idempotency-кеш для нефинансовых нагрузок. Паттерн един: делегируй retry + idempotency на уровень платформы, где можешь; падай на application-level middleware, где не можешь. Ручная реализация на каждом эндпоинте — неправильный дефолт.</p>
    <p><strong>Тестирование идемпотентности.</strong> Idempotent endpoint без теста идемпотентности — это вера, а не свойство. Минимально приемлемый тест: интеграционный тест отправляет один и тот же POST с одним и тем же Idempotency-Key дважды (с микро-задержкой между запросами) и утверждает, что (1) оба ответа имеют один и тот же status + body, (2) бизнес-side-effect случился ровно один раз (например, в платёжной БД ровно одна строка charge). Расширенный тест добавляет случайные сбои сети между первой попыткой и retry, чтобы убедиться, что сервер корректно идёт по path replay даже если первая попытка не завершила запись в кеш. Stripe внутренне использует тест chaos-нагрузки с инжекцией задержек и сбоев на каждом этапе, чтобы поверхность гонок не разрослась незаметно. Без этих тестов первая production-гонка становится первым обнаружением проблемы.</p>
    <p><strong>DLQ и poison-сообщения.</strong> Не все сбои восстанавливаются retry. Часть сообщений отравлена — некорректные данные, нарушенные schema, бизнес-инварианты невыполнимы. Бесконечный retry такого сообщения блокирует партицию очереди (особенно в FIFO Kafka), а вместе с ней — все последующие сообщения. Решение — dead-letter queue (DLQ): после N попыток обработки сообщение переезжает в отдельную очередь для разбора человеком, а основной поток продолжает идти. Production-настройки: N = 3-5 попыток, DLQ retention 7-30 дней, алерт при росте DLQ глубины, runbook для типов poison-сообщений (schema-ломка, недостающие зависимости, expired-business-id). Без DLQ retry-петля превращается в гарантированную остановку конвейера.</p>
    <p><strong>Какие коды ошибок ретраить, а какие — нет.</strong> 5xx (особенно 502, 503, 504) — почти всегда transient, ретраить с jitter. 429 Too Many Requests — ретраить, но обязательно уважая Retry-After. Network timeout / connection refused / reset — ретраить с подозрением на серверный outage. 4xx (кроме 408 Request Timeout и 429) — НЕ ретраить, потому что клиент сам некорректен и retry даст тот же 4xx. 410 Gone — НЕ ретраить, ресурс окончательно отсутствует. 401 Unauthorized — refresh token и ретрай ровно один раз, не больше. Идемпотентные методы (GET, HEAD, PUT, DELETE) безопасно ретраить даже без явного idempotency-key; POST требует ключ. Документация HTTP-клиента должна явно перечислять условие retry — необъяснённый "retry на любую ошибку" чаще всего и есть тот источник retry storm, который потом валит сервис.</p>
    <p><strong>Связь с circuit breaker.</strong> Retry и circuit breaker — это пара. Retry даёт второй шанс одиночной попытке; circuit breaker даёт паузу всему call site, когда retry-budget исчерпан. Канонический паттерн: caller оборачивает downstream-вызов в circuit breaker (например, Hystrix, Resilience4j, opossum для Node, gobreaker для Go); breaker отслеживает rate сбоев, и когда он переходит порог (например, 50% failures за окно 30с с минимум 20 запросами), breaker открывается — на короткое время все вызовы fail-fast без попытки. Через cooldown (несколько секунд) breaker переходит в half-open, пробует один пробный запрос, и либо закрывается обратно (downstream вернулся), либо снова открывается. Без circuit breaker retry-петля каждую секунду бьёт о больной downstream; с breaker downstream получает передышку, нужную для восстановления. Подробнее эту тему развивает следующий piece про circuit breaker — здесь важно лишь запомнить, что retry без breaker и budget — это рецепт усиленного outage.</p>
    <p><strong>Fallback и graceful degradation.</strong> Даже при исчерпанном retry-budget и открытом circuit-breaker система не обязательно должна возвращать пользователю голую ошибку. Хороший паттерн — fallback: при сбое основной операции возвращается кешированный/устаревший/упрощённый ответ. Примеры: рекомендательный сервис недоступен — показываем bestseller-список из кеша; payment-gateway падает — переключаемся на backup-провайдера; analytics-сервис тормозит — отдаём приближённый счётчик из Redis вместо точного из ClickHouse. Fallback требует явного решения "что приемлемо в degraded режиме" и часто обнажает скрытые зависимости (рекомендатель оказывается обязательным, потому что без него корзина не открывается). Production-зрелость = иметь fallback path для каждой не-критичной зависимости и регулярно его тестировать через chaos engineering — иначе fallback в момент outage обнаружится сломанным, и команда столкнётся с двойным сбоем: и основной путь не работает, и резервный тоже отказал, потому что давно перестал быть совместим с продакшеном.</p>

  <Fragment slot="senior">
    <p><strong>Гонки внутри idempotency-кеша.</strong> Два запроса с тем же ключом могут гоняться внутри сервера. Наивный "SELECT then INSERT if not exists, else replay" неатомарен: между SELECT и INSERT второй запрос может проскочить, и оба решат, что они первые. Фикс в Postgres — <code>INSERT ... ON CONFLICT (key) DO NOTHING RETURNING *</code> — атомарный insert-or-noop. Если RETURNING пустой, второй запрос проиграл гонку. Он перечитывает строку и либо ждёт завершения in-progress (с коротким таймаутом и fallback в 409), либо возвращает 409 сразу. Документированное поведение Stripe на конкурентный in-flight: вернуть 409 с body <code>{"{\"error\": \"idempotency key in use\"}"}</code> и дать клиенту отступить. Это корректно: клиент владеет retry-бюджетом; работа сервера — отказаться делать дублирующуюся работу.</p>
    <p><strong>Postgres advisory lock vs row lock.</strong> Некоторые реализации используют <code>pg_advisory_xact_lock(hashtext(key))</code>, чтобы сериализовать конкурентные попытки на одном ключе. Плюс: чище семантики ON CONFLICT, единый путь lock-and-go. Минус: hashtext — 64-битный, поэтому коллизии возможны на масштабе (10⁻¹⁰ при 10М ключей/день — обычно приемлемо, но security-критичные пути используют полный ключ в unique-индексе). Любой подход должен держать блокировку на весь запрос, включая внешние API-вызовы, что может занимать десятки-сотни миллисекунд — следи за исчерпанием пула и мониторь <code>pg_locks</code> на инцидентах.</p>
    <p><strong>Распределённый кеш: Redis Cluster vs база.</strong> На очень высокой write-нагрузке (>10к req/s на шард) синхронная запись в Postgres на запрос становится узким местом. Production-системы переносят idempotency-кеш в Redis Cluster с примитивом <code>SETNX key value EX ttl</code>: атомарный set-if-not-exists с TTL. Redis Cluster шардирует по hash ключа, каждый запрос попадает на одну ноду. Проблема — durability: Redis по умолчанию делает async fsync, поэтому крах в течение миллисекунд после записи может потерять запись. Платёжные API, несущие юридическую ответственность за двойные списания, держат каноничную запись в транзакционной базе и используют Redis только как хот-pass оптимизацию — Redis miss проваливается в базу. Чистый Redis приемлем для нефинансовых нагрузок (регистрации, аналитические события), где влияние редкого дубликата — это шум в логах, а не клиентская ошибка.</p>
    <p><strong>Outbox в деталях.</strong> Каноничная dual-write проблема: приложение хочет (1) обновить свою базу и (2) опубликовать событие в Kafka, атомарно. Делать в последовательности ломается в любую сторону — записать DB сначала, потом Kafka, и крах между ними оставит Kafka молчащей; записать Kafka сначала, потом DB, и крах оставит фантомное событие. Outbox решает это записью события В базу как "outbox" строки в той же транзакции что бизнес-запись. Отдельный outbox-relay процесс полит outbox-таблицу (или хвостит WAL через logical replication) и публикует события в Kafka, помечая строку published на broker ack. At-least-once доставка relay — это норма, потому что консумеры дедуплицируют через собственный idempotency key события. Паттерны: Debezium читает Postgres WAL и продуцирует Kafka-топик, убирая overhead опроса. AWS SAM имеет встроенный DynamoDB-streams → Lambda → EventBridge вариант. Стек CDC + outbox — это "правильный путь" к effectively-once доставке сообщений в микросервисах.</p>
    <p><strong>Inbox на консумерах.</strong> Зеркальный паттерн: консумер читает поток, который может доставлять одно и то же событие дважды. Inbox говорит: перед применением бизнес-эффекта события запиши event_id в таблицу <code>processed_events</code> в той же транзакции, что бизнес-запись. Если id уже существует, пропусти бизнес-запись. Это делает обработку консумера effectively-once без координации с брокером. Подводный камень: inbox-таблица растёт вечно, если не партиционировать или архивировать. Production-деплои партиционируют inbox по timestamp события и дропают партиции старше retention window брокера (обычно 7–14 дней).</p>
    <p><strong>Jitter math: full, equal, decorrelated.</strong> AWS Architecture Blog популяризировал три варианта jitter. <strong>Full jitter</strong>: <code>delay = random(0, min(cap, base × 2^attempt))</code> — самое плавное распределение, проще всего реализовать, рекомендация по умолчанию. <strong>Equal jitter</strong>: <code>delay = (base × 2^attempt)/2 + random(0, (base × 2^attempt)/2)</code> — половина детерминирована, половина случайна. Сгладит нижнюю границу, сложнее рассуждать. <strong>Decorrelated jitter</strong>: <code>delay = min(cap, random(base, prev_delay × 3))</code> — окно каждого retry зависит от предыдущей задержки, растёт органично; часто используется в AWS SDK v3. Эмпирические данные AWS показывают, что full jitter и decorrelated jitter дают почти идентичные профили нагрузки; выбирай тот, который твой runtime поддерживает нативно. Избегай "exponential backoff without jitter" — это thundering-herd ловушка.</p>
    <p><strong>Где НЕ надо ретраить.</strong> Retry имеет смысл для transient-сбоев: 5xx, network timeout, 429 Too Many Requests. Не имеет смысла для 4xx (запрос клиента некорректен; retry даст тот же 4xx) или для 410 Gone (ресурс окончательно отсутствует). Некоторые библиотеки наивно ретраят всё не-2xx, порождая retry storm на клиентские баги. Идемпотентные retry также должны иметь budget: capped attempt count плюс глобальный deadline. Tail-latency статьи от Netflix и Google показывают, что uncapped retry усиливают tail latency до outage. Правильный паттерн — "retry budget": token-bucket из allowed retry per second по всему call site; когда bucket опустошён, клиент ломает circuit и возвращает детерминированную ошибку.</p>
    <p><strong>Наблюдаемость idempotency + retry.</strong> Минимально-жизнеспособный дашборд выдаёт: <code>idempotency_key_total</code> со слайсом по outcome (new / replay / 409 / 422), <code>retry_attempt_total</code> со слайсом по номеру попытки, <code>retry_delay_seconds_bucket</code> как гистограмма реальных задержек, <code>outbox_lag_seconds</code> (насколько устаревший outbox relay), <code>dead_letter_queue_depth</code>, и <code>http_request_outcome</code> со слайсом по классу статуса (2xx / 4xx / 5xx / timeout). Всплеск retry-3 предшествует outage на минуты — канареечные клиенты уже платят цену проблемы до того, как пользователи это заметят. Растущий outbox_lag означает, что relay или downstream падают; алерт на lag &gt; 30с. Растущий DLQ — это постоянный сбой: poison-сообщения, которые никакое количество retry не починит; нужен человеческий review.</p>
    <p><strong>Production failure stories.</strong> Stripe 2017: переключение idempotency-кеша с одного Redis-кластера на другой ненадолго потеряло in-flight ключи, что привело к нескольким двойным списаниям; Stripe добавил Postgres-бэкенд как постоянный инвариант. Knight Capital 2012: отсутствующий feature-flag плюс агрессивные retry против биржевого фида превратили deploy-глитч в $440M непреднамеренных торгов за 45 минут. AWS S3 сентябрь 2017: внутренняя подсистема возвращала 500 во время outage; агрессивные retry-политики клиентов усилили падение по всему региону, пока AWS не опубликовал guideline по добавлению jitter. GitHub 2018: failover базы потерял lease на outbox-relay; события копились в outbox 2 минуты, потом флашились разом — само-нанесённый thundering herd на консумере. Все истории об одном корне: at-least-once доставка без идемпотентных консумеров ИЛИ retry без jitter.</p>
    <p><strong>История: от MQ Series до gRPC retry policy.</strong> IBM MQ Series в 1980-х шипал "guaranteed delivery" с at-most-once + транзакциями, но latency и сложность сделали это неработоспособным для веба. Пост Stripe 2014 года про idempotency keys популяризировал at-least-once + dedupe паттерн для HTTP API. RFC-черновики последовали: <code>draft-idempotency-header</code> в 2020, уточнения через 2022, парковка под <code>draft-ietf-httpapi-idempotency-key-header</code> в 2024. gRPC принял machine-readable retry policy в service-config JSON около 2019, открыв <code>maxAttempts</code>, <code>initialBackoff</code>, <code>maxBackoff</code>, <code>backoffMultiplier</code> per RPC. Envoy и Istio выставили retry budget, retry-on условия и per-route retry policy. Паттерн универсален: клиент backoff + retry; сервер дедуплицирует; observability покрывает обе стороны.</p>
    <p><strong>Cross-protocol: HTTP, gRPC, Kafka.</strong> HTTP Idempotency-Key заголовок — конвенция. gRPC использует трейлер <code>grpc-retry-pushback-ms</code>, чтобы предложить backoff, и service-config <code>retryPolicy</code> для клиентского поведения. Kafka открывает идемпотентного producer (<code>enable.idempotence=true</code>), который гарантирует at-most-once доставку per-partition через producer-side sequence number, плюс транзакции для cross-partition атомарности. SQS имеет свой <code>MessageDeduplicationId</code> для FIFO-очередей. Общая нить — "токен, идентифицирующий операцию независимо от попытки транспорта" и серверный state machine, отображающий этот токен в исходы.</p>
    <p><strong>Deployment patterns: middleware vs ручная реализация.</strong> Ручная реализация idempotency в каждом эндпоинте — неправильный дефолт; через три недели у тебя несогласованные формулы fingerprint и несовместимые TTL по сервисам. Middleware-библиотеки делают это один раз: Stripe <code>idempotent-requests</code> middleware (открыт), <code>AspNetCore.Idempotency</code>, <code>express-idempotency</code>, <code>django-idempotency-key</code>, <code>fastapi-idempotency</code>. Middleware читает заголовок, вычисляет fingerprint, проверяет кеш, либо проигрывает, либо маршрутизирует в обработчик, потом пишет ответ. Обработчик ни о чём не знает. На уровне service mesh Envoy и Istio имеют request-id-based dedup примитивы для sidecars; для serverless AWS API Gateway имеет встроенную идемпотентность с 2023.</p>
    <p><strong>Производственный аудит и compliance.</strong> Платёжные провайдеры (Stripe, PayPal, Square) удерживают idempotency-ключи от 24 часов до 30 дней по compliance-причинам. PCI DSS не требует точного TTL, но регуляторы ожидают, что любой charge поддаётся аудиту в течение минимум 30 дней — а это означает, что idempotency-логи должны не только дедуплицировать, но и сохранять достаточно метаданных, чтобы доказать "этот ключ был использован тогда-то, привёл к charge X, retry Y вернул кешированный ответ". Структура аудит-лога: <code>(timestamp, key_prefix, customer_id, operation_type, fingerprint_hash, outcome, response_status)</code>. PII (полный body) НЕ хранится; хранится только fingerprint-хеш + outcome. Хранение в отдельной audit-таблице с retention по compliance (обычно 7-10 лет для финансовых данных, отдельно от 30-дневного hot-кеша). Дополнительно production-системы пишут аудит-trail в WORM-хранилище (write-once read-many) — S3 Object Lock, GCP Bucket Lock — чтобы обеспечить неизменяемость записей для регуляторного аудита, и в случае спорного charge доказать, что система действительно вернула идемпотентный ответ, а не выполнила операцию дважды.</p>

Композиция атомарности Postgres + at-least-once Kafka + идемпотентных консумеров — production-способ получить effectively-once семантику через границу dual-write.</p>,
        },
      ]}
    />
  </Fragment>
</TierAccordion>

<KeyTakeaway>Настоящая exactly-once невозможна по сети. Production добирается через at-least-once + идемпотентность (сервер дедуплицирует по ключу + outbox/inbox) + jittered retry — наблюдаемое поведение становится exactly-once.</KeyTakeaway>
