N+1 был конкретной формой — round-trip'ы, умноженные на N. Batching обобщает фикс: любая операция с почти фиксированной per-call ценой может быть амортизирована группировкой. Kafka producers батчат сообщения, syscall'ы батчатся через io_uring, Postgres батчит inserts через COPY, Redis батчит через pipelining. Тот же рычаг, тот же tradeoff: бо́льшее окно = выше throughput + выше tail-latency для items в начале.

<Crux>Per-op фикс. цена доминирует? Батч. Окно = размер и max wait; бо́льшие батчи покупают throughput, платят tail-latency.</Crux>

У каждой операции есть фиксированная цена (header, ACK, syscall transition, log flush, planner overhead) и переменная цена (payload size). Когда фиксированная доминирует и rate высок, per-op throughput floor — это фиксированная цена. Batching сворачивает фикс. цену N операций в одну. Production-системы используют это везде: TCP Nagle, Kafka linger.ms, Postgres COPY, Redis pipelining, io_uring submission queues, syslog buffering. Сеньорный вопрос никогда не «батчить или нет», а «какой размер окна максимизирует throughput, не ломая SLO tail latency?».

    <p><strong>Двумерное окно.</strong> У каждой batching-системы два knob'а: max-size (байты или records) и max-wait (время). Что наступило первым — шлёт батч. Без max-size медленный producer держит батч до истечения времени, теряя throughput. Без max-wait producer с медленным потоком держит первый item бесконечно. Kafka: <code>batch.size</code> + <code>linger.ms</code>; AWS SDK: <code>maxBatchItems</code> + <code>maxBatchWindowMillis</code>; io_uring: queue depth + polling intervals. Сеньорное правило: max-size доминирует при полной нагрузке (батч заполняется до timer'а), max-wait ограничивает latency в sparse-периоды. Defaults: 10-100 мс wait, 64 КБ - 1 МБ size, тюнятся replay'ем production-трафика в staging.</p>
    <p><strong>Амортизация фикс. цены: математика.</strong> Пусть операция имеет фикс. цену F (per-call overhead, скажем 50 мкс syscall + 100 мкс network) и переменную V*n (n — payload size, V — байты/мкс rate). Total время для N отдельных операций: N * (F + V*n). Total для одного батча N: F + V*(N*n). Speedup ratio: (N*F + V*N*n) / (F + V*N*n). Когда F доминирует (малые payloads), speedup → N. Когда V доминирует (большие payloads), speedup → 1. Для типичных малых payloads (~1KB, ~50 мкс RTT), батч 100 items уменьшает wall time с ~5 мс до ~150 мкс — 33x. Break-even ≈ F = V*n; выше — батч выигрывает; ниже — не важно. Сеньорный тюнинг меряет F и V для конкретной операции до тюнинга окна.</p>
    <p><strong>Kafka producer batching, в деталях.</strong> Каноничный паттерн в distributed-системах. Producer накапливает сообщения per (topic, partition); при batch.size или истечении linger.ms — батч шлётся как один ProduceRequest. linger.ms default 0 (без ожидания); throughput-чувствительные workload'ы — 5-100 мс. batch.size default 16 КБ; high-volume topics — 64-512 КБ. Network call: один TCP send per batch; broker пишет один record per message, но disk write — один fsync per batch (если acks=all). На 100k+ msg/sec/topic batching доминирует и producer CPU, и broker disk performance. Compression (lz4/snappy) применяется per-batch — бо́льшие батчи лучше сжимаются. Full chain: app produce → producer buffer → batch sent → broker receives → compression checked → written to segment + replicated → ACK returned.</p>
    <p><strong>Database bulk inserts.</strong> Postgres COPY бьёт INSERT VALUES (...), (...), ..., который бьёт один INSERT per row. COPY: стримит данные в custom protocol, обходит parser per-row, один transaction commit. INSERT VALUES multi-row: один parse + один plan + один commit; ~5-50k rows. Single-row INSERT: parse + plan + commit per row; ~1-5k rows/sec. Конкретно: 1M строк ~10 сек single-row, ~2 сек multi-row, ~0,5 сек COPY. ORM выставляют это: ActiveRecord <code>insert_all</code>, Django <code>bulk_create</code>, SQLAlchemy <code>Session.execute(insert, list_of_dicts)</code>. Используй для любого bulk-пути; не для single-row interactive, где простота важнее throughput.</p>
    <p><strong>Syscall batching: io_uring и предшественники.</strong> Традиционный POSIX I/O — один syscall на операцию: read(), write(), recv(), send(). Каждый стоит ~1-5 мкс context switch. Для сервиса с 100k I/O ops/sec — 100-500 мс/сек в syscall transitions. Batched syscall: <code>readv</code>/<code>writev</code> — multiple ranges в одном вызове; <code>sendmmsg</code>/<code>recvmmsg</code> — multiple UDP packets; <code>io_uring</code> (Linux 5.1+) — submit N операций в kernel-shared ring, reap результаты из completion ring, потенциально zero syscalls per op в polling mode. Production: Netflix 30%+ CPU reduction на TLS proxies через io_uring; Ceph + БД репортуют 20-50% throughput gain. Цена: API незнаком, security CVE были, иногда отключён в container environments. Сеньорный выбор: io_uring для новых high-I/O workload'ов на современных kernel'ах; writev/sendmmsg как portable fallback.</p>
    <p><strong>Failure modes: poison pill и head-of-line blocking.</strong> Два классических hazard'а. (1) Poison pill — один плохой item в батче валит весь батч. Пример: Kafka producer batch с одним oversized message — все rejected. Митигация: validate items до батча; size-bound каждый item; retry split-batches. (2) Head-of-line blocking — медленная обработка одного батча держит все за ним. Пример: метрики ingest батчат 100 metrics per HTTP POST; если один POST медленный, следующий ждёт. Митигация: parallel batch dispatch (multiple in-flight), per-key sharding, async batching (без ожидания ACK перед следующим). Production-grade имеет оба: validation + parallel dispatch.</p>
    <p><strong>Adaptive batching.</strong> Static окна работают для steady-load; dynamic нагрузки выигрывают от адаптации. Алгоритм: мониторь batch fill rate и downstream latency; если downstream slow, уменьшай batch size; если downstream fast, увеличивай. Реализации: Kafka producer <code>delivery.timeout.ms</code> back-pressure; AWS Lambda concurrent execution scaling by queue depth; HTTP/2 stream prioritisation. Принцип: окно достаточно широкое, чтобы амортизировать фикс. цену, но не шире, чем downstream способен поглотить. Adaptive сложнее реализовать и тюнить, но окупается для workload'ов с daily/diurnal вариацией (метрики 10x выше в рабочие часы).</p>
    <p><strong>Observability для батчинга.</strong> Production-grade observability трекает четыре per-batch метрики. (1) Batch size histogram — реально ли батчи заполняются или попадают в timer? p50 и p99 в records и bytes. (2) Batch wait time — как долго items ждали до отправки. (3) Buffer depth gauge — текущие items в in-memory буфере; спайки = downstream backpressure. (4) Drop count — items, выброшенные при overflow; должно быть 0; ненулевое — back-pressure сигнал. Dashboard layout: time series всех четырёх с алертами на drop count &gt; 0 и buffer depth &gt; 80% cap. Без этих метрик batched-системы непрозрачны операторам; с ними — отлаживаемы в production.</p>
    <p><strong>Per-runtime batching primitives.</strong> Каждый рантайм поставляет batching API. Node.js: setImmediate/process.nextTick для micro-batching на event-loop tick boundaries, stream.cork()/uncork() для batched writes. Go: bufio.Writer для buffered writes с explicit Flush(); channels + select + ticker для time-windowed batching; sync.Pool для buffer reuse. Java: BufferedOutputStream, Kafka producer config, Spring @Scheduled fixed-delay для time batching. Python: asyncio.Queue с batched consumers, asyncpg executemany для batched DB inserts. Rust: tokio mpsc channels с batching adaptors. Каждый даёт те же примитивы: bounded buffer, max-size + max-wait, explicit flush. Сеньорное код-ревью новых high-rate write путей включает «применён ли standard batching-примитив языка?» — обычно ответ «нет», и добавление — one-PR fix.</p>
    <p><strong>Pipelining vs batching: связанная, но отдельная оптимизация.</strong> Pipelining шлёт N requests без ожидания каждого ACK; протокол разруливает ordering и matching responses. Redis pipelining, HTTP/1.1 pipelining, gRPC client streaming, MySQL pipeline mode — все так. Отличие от batching'а: каждый request имеет свой header + ACK, просто шлются back-to-back. Throughput gain — от заполнения in-flight window, не от амортизации фикс. цены в merged операции. Комбинируй: batched requests, отправленные в pipeline. Redis MGET комбинирует оба — multiple keys в одной команде (batched), и pipelining Redis позволяет fire'ить несколько MGETs без ожидания. Best total throughput: batch + pipeline. Сеньорный тюнинг отмечает обе оси: сколько ops per request (batch size), сколько requests in flight (pipeline depth).</p>
    <p><strong>Кросс-уровневое batching: nested batching внутри одной системы.</strong> Production-системы часто имеют batching на multiple layers, амортизирующих фикс. цену на каждом. Пример: gRPC client с client-side message-batching → HTTP/2 framing → TCP segmentation offload → NIC tx-batching. Каждый слой амортизирует свою фикс. цену. Чистый эффект: один логический операционный API call (вы зовёте client.SendBatch(items)) превращается в кардинально меньшее количество operations на каждом нижнем слое. Сеньорный insight: при дизайне batching на одном слое смотри также на слой ниже — иногда нижний слой уже делает batching и ваш application-level batching duplicate; иногда нижний слой не делает и application-level batching essential. Профилирование с -e syscalls + iostat показывает, где batching действительно работает в стеке. Дополнительно: для каждого layer'а свои метрики — application-level считает batch sizes в operation units, kernel-level — в syscall counts, NIC-level — в packets-per-interrupt. Disjoint метрики; нужно мониторить все, чтобы понимать, где cost уходит. Cеньорный сервис ставит alerts на drift каждого: application drop count, syscall rate spike, NIC interrupt rate. Регрессия одного слоя обычно невидима на другом — поэтому каждый требует отдельной observability. Production-grade batching — это не одна оптимизация, а каскад их через стек. Команды, видящие batching как single-layer оптимизацию, обычно упускают 30-60% потенциального gain'а на нижних уровнях. Сеньорный аудит: пройти стек сверху вниз, на каждом слое спросить «где amortising fixed cost, где per-item», документировать. Часто application-batch правильно, но lower layer не настроен (sendfile вместо writev, ALB без HTTP/2, отсутствие TSO на NIC) — и amortisation, начавшаяся на app-уровне, теряется на уровне ниже. Каскадный дизайн — отличительная черта зрелой инфраструктуры; ad-hoc batching на одном слое — типичная незрелость. Конкретный пример: e-commerce checkout-сервис, у которого application-level Kafka producer batches с linger.ms=10, но broker запущен на VM без TSO и с small TCP send buffer — broker-side overhead на per-packet ACK обработке съедает 40% gain'а, который application-batch дал. Audit показал: NIC tx-queue regularly draining wait, kernel /proc/net/snmp показывает TCP retransmits на 0,3% — выше нормы 0,05%. Fix: TSO/GSO включены в guest, sysctl net.core.wmem_max поднят, TCP_NODELAY где нужен, NIC moved на SR-IOV. Дополнительные 40% gain без изменения application-кода. Урок: смотри на стек как на цепь, а не на единственное звено. Каждое звено имеет свой батч-механизм; пропуск одного — теряешь весь выигрыш. Сеньорный подход документирует layer-карту: чем batches каждый слой, какие knob'ы выставлены, на каком monitoring завязан. Без карты команда плавает между слоями, не зная, какой влияет на текущий incident; с картой триаж идёт от topmost-видимого симптома вниз по слою. Зрелые SRE-команды поддерживают эту карту как часть on-call-документации сервиса; обновляют при каждом архитектурном изменении. Слои добавляются, knob'ы перетягиваются — карта меняется, и без её актуальности диагноз сбоит на следующем инциденте. Это типичный артефакт зрелой production-инженерии: документация, дисциплинированно поддерживаемая той же командой, которая её использует на регулярной основе, а не написанная и забытая.</p>

  <Fragment slot="senior">
    <p><strong>Nagle's algorithm и оригинальный batching tradeoff.</strong> RFC 896 от John Nagle (1984): TCP буферизует малые outbound-сегменты до прихода ACK или заполнения буфера до MSS. Мотивация та же, что у Kafka: 1-байтные telnet keystrokes создавали 40-байт TCP/IP headers — забивали ранние сети. Nagle батчит малые writes в один сегмент, амортизируя header cost. Tradeoff тот же: interactive applications ждут next write или ACK, страдает tail latency. TCP_NODELAY отключает Nagle; современные протоколы (HTTP/2, gRPC) обычно ставят TCP_NODELAY и делают application-level batching для finer-control. Линия от Nagle 1984 через Kafka linger.ms (2011) до io_uring submission queues (2019) — один непрерывный паттерн.</p>
    <p><strong>io_uring deep dive.</strong> io_uring (Linux 5.1+, 2019) — самый мощный generic batching-примитив в kernel. Две кольцевые буфера, mmap'd между user и kernel: submission queue (SQ) и completion queue (CQ). User пушит io_uring_sqe в SQ; kernel читает, выполняет, постит io_uring_cqe в CQ. В default mode user вызывает io_uring_enter() — kernel обрабатывает все SQ entries в batch. В polled mode (IORING_SETUP_SQPOLL) kernel thread polls SQ — user submit'ит ops с zero syscalls. Результат: на 1M ops/sec традиционный read/write жжёт ~1 мс/сек на syscalls; io_uring polled mode — почти ноль. Adoption: PostgreSQL 17 добавил io_uring backend, Ceph experimental, Netflix async-profiler репортует 5-15% steady-state CPU reduction на TLS proxies. Security CVE (CVE-2023-2598, CVE-2024-0582, и др.) привели к отключению io_uring некоторыми container runtimes; сеньорные команды трекают и взвешивают per deployment.</p>
    <p><strong>Latency-throughput Pareto frontier.</strong> Batching — самая явная tradeoff-кривая в performance: каждая (throughput, latency) точка достижима варьированием окна. Без batching: lowest latency, throughput ограничен fixed cost. Infinite batching: max theoretical throughput, latency = ∞ для первого item. Сеньорный workflow: определи SLO latency ceiling, найди самое большое окно, остающееся под ним — это throughput-maximising operating point под constraint. График: x = batch wait time, y1 = throughput (растёт с batch size, plateau при downstream saturation), y2 = p99 latency (растёт линейно). Intersection (y2 = SLO ceiling) с (x = batch wait) — твоё оптимальное окно. Adaptive системы трекают кривую динамически; static — тюнят раз и принимают drift.</p>
    <p><strong>Batch coalescing и request deduplication.</strong> Специализированный batching для cache/lookup. Когда multiple concurrent requests запрашивают тот же ключ, coalesce в один батч. Пример: cache miss. Worker A misses cache для K, грузит из DB; worker B тоже miss для K — joins A's pending request. Возвращает тот же результат обоим. Реализации: singleflight (Go's golang.org/x/sync/singleflight), Caffeine AsyncLoadingCache (Java), request collapsing в Varnish/CDN edge. Production impact: hot cache miss с 100 concurrent → 1 DB query вместо 100, предотвращает thundering-herd. С DataLoader (из N+1): «все requests в окне 10 мс для любых ключей → один batched DB query». С cache stampede protection — устраняет класс cascading failures.</p>
    <p><strong>Batch failure isolation.</strong> Batch — all-or-nothing transaction во многих системах (Kafka batch atomic; Postgres COPY один commit). Один item ломает весь батч — всё валится. Senior дизайн использует три паттерна limit blast radius: (1) Pre-validation — каждый item shape/size checked до батча; oversized/malformed rejected immediately. (2) Split-and-retry — на failure producer делит батч пополам, retries каждую; recursively локализует bad item. Kafka producer делает через custom retry; AWS SDKs встраивают. (3) Per-item ACK — некоторые протоколы (Kafka exactly-once, AWS Kinesis) возвращают per-item success/failure в batch response — callers могут re-batch только failures. Без этого один bad item в batch 1000 либо дропает 1000 valid либо stall'ит producer'а вечно retrying. Реальные инциденты: AWS Lambda batch event source retried entire batches на single-item failures — cascading retries и SQS dead-letter queue спайки.</p>
    <p><strong>Backpressure и bounded queues.</strong> Batching producers буферизуют в памяти; unbounded buffer — memory leak. Backpressure: когда downstream не успевает, buffer producer'а полнится; без bounds — OOM. Три production-grade паттерна: (1) Bounded queue с block: producer блокирует когда buffer full, applying back-pressure upstream. Reactive Streams, Akka Streams, RxJava. (2) Bounded с drop: producer дропает items когда buffer full, incrementing 'dropped' counter. Метрики-агенты обычно — лучше потерять метрики, чем крашнуться. (3) Bounded со spill-to-disk: producer флашит oldest items на disk-backed queue. Fluentd, Vector, Filebeat для log shipping — durability over latency. Выбор зависит от workload'а: interactive paths — block, fire-and-forget metrics — drop, audit logs — spill-to-disk.</p>
    <p><strong>Безопасность: batch-amplified DoS и replay risks.</strong> Batching может амплифицировать attack-векторы. (1) Compression bomb: атакующий шлёт батч highly-compressible payloads; receiver разворачивает в гигантскую память. Real CVE: CVE-2018-10872 (Kafka decompression bomb). Митигация: cap'ить decompressed batch size, не только compressed. (2) Replay risk: sniffed батч можно reply'ить — N records once vs replaying N requests. Митигация: per-batch nonce + idempotency token. (3) Reordering attacks: batched messages могут приходить out-of-order между батчами. Митигация: explicit sequence numbers + reordering на receiver.</p>
    <p><strong>Production-провалы.</strong> Lyft 2019: Kinesis batched consumer отставал в peak; batch size unbounded → OOM. Fix: bounded + backpressure. Stripe 2020: Postgres COPY failed когда одна row в 50k COPY violated constraint; весь батч rolled back. Fix: pre-validation + bisection retry. Pinterest 2018: Kafka producer с linger.ms=100 hit p99 SLO violation в low-traffic (items ждали 100 мс таймера при 1 msg/sec). Fix: adaptive linger. Discord 2021: gateway потерял пару секунд presence events во время deploy; users видели flapping presence. Fix: WAL-style buffer flush на shutdown signal. Паттерн: у каждой batched-системы есть story про неверное окно для ситуации; зрелые команды имеют observability и adjustability built in.</p>
    <p><strong>История и линия.</strong> Batching старше performance-инженерии как дисциплины. 1960-е — IBM tape systems батчили writes по tape-block size. 1970-е — early БД с group commit. 1984 — Nagle's algorithm. 1990-е — Sybase/Oracle bulk loaders, X11 protocol request batching. 2000-е — TCP segmentation offload (TSO) в NIC, generic receive offload (GRO). 2010-е — Kafka linger, Redis pipelining, AWS Kinesis batch APIs. 2020-е — io_uring, AWS Lambda batching, GraphQL DataLoader. Каждое поколение открывало тот же урок в новом слое: фикс. цена — враг, амортизация — рычаг, единственный design-вопрос — размер окна. Сеньоры распознают паттерн мгновенно в любой новой системе — самая reusable performance-идея после profiling'а.</p>
    <p><strong>Картина целиком.</strong> Batching — самая generally-applicable performance-техника в distributed-системах. Слой ниже конкретных протоколов (N+1 fixes — special case; GC compaction — другой; bundle splitting — ещё). Паттерн именует фикс. цену, амортизирует по N операций, принимает bounded latency penalty. Фрагменты главы: profile-first, hot-paths, GC, N+1, этот, дальше bundle budgets. Капстоун плетёт. Чтение профиля + правильное семейство фикса — consistent loop; batching — семья всякий раз, когда цена «фиксирована per call».</p>
