CS-учебники преподают big-O как универсальную линзу производительности: O(log N) бьёт O(N), O(N) бьёт O(N²), конец истории. Современные CPU не согласны. Память в 100 раз медленнее L1-кеша. Branch mispredictions стоят 15-30 циклов. «Медленный» O(N) linear scan на contiguous memory регулярно бьёт «быстрый» O(log N) binary search на tree of pointers — потому что linear scan остаётся в cache, а tree трешит RAM. Big-O остаётся правильной отправной моделью; cache hierarchy — правда, которая шипится в production.

<Crux>Big-O асимптотический. Cache locality реальная. Тот же O(N²): row-major 300мс, column-major 2800мс — тот же алгоритм, 9x медленнее.</Crux>

Ментальная модель: современный CPU — не uniform memory machine. L1 cache сидит в 1 цикле (sub-nanosecond), L2 около 5 циклов, L3 около 15 циклов, main memory 100-300 циклов. Pattern доступа, трогающий предсказуемые, contiguous байты, кормит hardware prefetcher и остаётся в L1; pattern, прыгающий между distant pointers, миссит каждый уровень и платит full RAM latency на каждом шаге. Big-O считает logical operations, как если бы каждая занимала одинаковое время. В реальности wall-clock cost каждой операции варьируется в 100x в зависимости от того, где сидят её данные. Первый рефлекс senior frontend или backend performance engineer не «сделать O(log N)»; он «сделать working set влезающим в cache и access pattern friendly к prefetcher».

    <p><strong>Что это в одном предложении.</strong> Big-O complexity считает операции, но современные CPU больше заботятся о том, где сидят данные — быстрый cache или медленная память — и этот gap может перевернуть, какой алгоритм выиграет.</p>
    <p><strong>Почему важно.</strong> Выбор «теоретически быстрого» алгоритма может сделать твой код в 10x медленнее, если он разбрасывает данные по памяти. Выбор «медленного» алгоритма, трогающего contiguous data, может победить — даже когда big-O говорит, что не должен.</p>
    <p><strong>Метафора.</strong> В библиотеке 10 книг на твоём столе (L1 cache), 100 на ближайшей полке (L2), 10000 в той же комнате (L3) и 10 миллионов в складе в двух кварталах (RAM). «Быстрый» алгоритм, нуждающийся идти на склад на каждом шаге, проигрывает «медленному», обрабатывающему каждую книгу на столе по порядку. Расстояние важнее, чем количество операций. Стол в 100x быстрее достичь, чем склад — то же, что L1 cache vs main memory.</p>
    <p><strong>Bea и Sven.</strong> <PersonaTag id="bea" lang="ru" /> разработчик бенчмаркает два типа list в JS: Array из 1М чисел и linked list из 1М узлов. Итерация Array — 2мс; итерация linked list — 35мс. Оба O(N). <PersonaTag id="sven" lang="ru" /> CPU объясняет: Array сидит в contiguous памяти, влезает в cache, prefetcher грузит следующий chunk, пока ты обрабатываешь текущий. Linked list разбрасывает узлы по heap; каждый .next pointer прыгает в случайную память, каждый шаг платит cache miss. Тот же big-O, разница в 17x.</p>
    <p><strong>Сценарий.</strong> Matrix multiply на 10000x10000 doubles. Row-major и column-major циклы оба O(N²). Row-major трогает array[i][0], array[i][1], array[i][2]... — contiguous в памяти, cache-friendly. Column-major трогает array[0][j], array[1][j], array[2][j]... — каждый шаг прыгает 80000 байт (10000 doubles), свежая cache line каждый раз. Row-major: 300мс. Column-major: 2800мс. Тот же алгоритм, 9x медленнее, только от смены order доступа.</p>

    <p><strong>Cache hierarchy в числах.</strong> Современные x86 и ARM CPU делят одну широкую форму. L1 cache: 32-64 KB per core, 3-5 циклов latency (около 1нс на 5GHz), private каждому ядру. L2: 256KB до 1MB per core (Intel Raptor Lake P-cores 2MB, AMD Zen 5 остаётся на 1MB для lower latency), 10-15 циклов. L3: 4-64MB shared через все ядра, 30-50 циклов. Main memory (DDR5-6000): 70-100нс, 200-300 циклов. Фактор между L1 и RAM — примерно 100x по latency, что и есть доминирующий рычаг в реальной perf-настройке. Один cache miss стоит больше, чем 30 floating-point operations занимают в registers.</p>
    <p><strong>Cache lines: единица transfer.</strong> Data не двигается между RAM и cache по одному байту. Двигается cache lines — 64 байта на x86 и большинстве ARM (некоторые Apple Silicon и ARM server cores используют 128 байт). Чтение байта на адресе X грузит байты X до X+63 в cache, все сразу. Поэтому sequential access так быстр: читай байт 0, вся 0-63 line теперь в L1; читай байты 1-63 далее, каждый — free hit. Также поэтому «false sharing» больно в multi-threaded коде: два thread, пишущие в разные variables в одной cache line, всё равно invalidate-ят L1-копии друг друга, ping-pong-ит line между cores на ~30-50 циклов per ping. Фикс — alignment: размести per-thread state как минимум 64 байта apart.</p>
    <p><strong>Big-O assume-ит uniform cost.</strong> Big-O analysis model treats каждую операцию как занимающую constant time. На современном hardware — wild approximation. Cache hit стоит 1-15 циклов; cache miss стоит 100-300 циклов. Две операции с тем же «instruction count» могут различаться в 100x по wall-clock time. Big-O всё ещё полезен — для предсказания того, как cost растёт с N — но constant factor, который он игнорирует, и есть разница между влезает в L1 (fast constant) и миссит каждую line (slow constant). Для маленького N constants доминируют полностью; O(log N) tree может не побить O(N) array, пока N не в миллионах.</p>
    <p><strong>Array vs linked list: канонический случай.</strong> Итерация std::vector из 1М int: около 2мс. Итерация std::list из 1М int: около 35мс. Тот же O(N) complexity, 17x runtime разница. Vector — одна contiguous аллокация; prefetcher заполняет L1 впереди CPU. List nodes отдельно heap-allocated; каждое .next dereference — likely cache miss. Ещё хуже для trees: red-black tree из 1М int с случайным insertion order имеет узлы scattered по всему heap. Linear scan бьёт binary search, пока N не настолько большое, что array становится too big to scan. Production rule of thumb: предпочитай arrays / vectors над linked structures, если нет специфической причины (mid-list inserts dominate, lock-free needs и т.д.).</p>
    <p><strong>Row-major vs column-major.</strong> 2D массив <code>arr[i][j]</code> в C / Java / Rust / Python (numpy default) layout row by row: <code>arr[0][0]</code>, <code>arr[0][1]</code>, ..., <code>arr[0][N-1]</code>, <code>arr[1][0]</code>, и т.д. Цикл <code>for i: for j: arr[i][j]</code> трогает addresses по порядку — cache-friendly. Цикл <code>for j: for i: arr[i][j]</code> прыгает N*sizeof(elem) байт per step — cache-hostile. На 10000x10000 doubles: 300мс vs 2800мс. Тот же instruction count, тот же логический алгоритм, 9x slowdown. Fortran defaults на column-major; ВСЕГДА проверяй конвенцию языка перед предположением layout. Cache-oblivious blocking (process matrix в tiles ~64 rows, чтобы каждый tile влезал в L2) даёт оба row и column directions быстрыми для той же code shape.</p>
    <p><strong>Branch prediction.</strong> Каждый if/else, loop boundary и function call — branch, который CPU должен предсказать. Modern branch predictors замечательные — 95-99% accuracy на большинстве реального кода. Но misprediction стоит 10-30 циклов на современном x86, иногда больше на глубоких pipelines (Zen 2 pipeline — 19 stages). Для непредсказуемых branches (например, if на random data), misprediction rate растёт до ~50% и каждый miss flushes pipeline. Канонический пример: сортировка array перед суммированием только элементов выше threshold. Unsorted версия миссит на каждом сравнении (~50% miss rate); sorted версия предсказывает правильно почти всегда после threshold crossing. Тот же цикл, тот же O(N), часто 2-3x speedup просто от sorting first (несмотря на O(N log N) sort cost).</p>
    <p><strong>Branchless code.</strong> Когда branches непредсказуемы, удаление их быстрее. Замени <code>if (x &gt; 0) y = a else y = b</code> на <code>y = (x &gt; 0) * a + (x &lt;= 0) * b</code>, или используй conditional move (CMOV на x86). Branchless версия всегда вычисляет обе стороны; branched версия skipает одну, но платит mispredict cost когда не права. Tipping point: если branch предсказуем (95%+), branched быстрее. Если непредсказуем (50/50), branchless выигрывает в 2-5x. Компиляторы иногда выбирают это автоматически; иногда нет, нужен explicit <code>__builtin_expect</code> или PGO data. Частое в sort partition, packet-classification loops, image-processing inner loops.</p>
    <p><strong>SIMD и data layout.</strong> Современные CPU имеют wide vector registers (256-bit AVX2, 512-bit AVX-512, 128-bit NEON на ARM). Одна инструкция может оперировать на 4-8 floats сразу. Чтобы использовать их, data должна быть laid out в правильной shape — обычно «structure of arrays» (SoA) скорее, чем «array of structures» (AoS). SoA: <code>xs[N], ys[N], zs[N]</code>. AoS: <code>Points[N] &#123; x, y, z &#125;</code>. SoA layout позволяет SIMD unit грузить 8 xs за один цикл и оперировать на них параллельно; AoS layout требует gather/scatter, намного медленнее. Game engines, ML inference, audio processing — все предпочитают SoA. V8 hot loops в браузерах используют SoA через TypedArrays по той же причине — см. V8-internals piece в этой главе.</p>
    <p><strong>Profile-guided thinking.</strong> Первый шаг в любом perf debug — не оптимизация — это measurement. Tools: <code>perf stat</code> (Linux) показывает cache hit rate, IPC, branch miss rate. <code>perf record</code> samples hot functions. Intel VTune добавляет per-line cache miss attribution. Apple Instruments эквивалент на macOS. <code>cachegrind</code> симулирует cache behaviour для fine-grained analysis. Цель: identify, является ли bottleneck cache misses, branch mispredictions, instruction issue rate или memory bandwidth. У каждого разные фиксы. «Оптимизация» без measuring — guessing; измерения превращают guesses в engineering.</p>
    <p><strong>Memory bandwidth как отдельный constraint.</strong> Cache hit rate — одна ось; memory bandwidth — другая. Workload, стримящий через 100GB памяти, будет bound RAM bandwidth (~50-100 GB/s на современных DDR5 systems) независимо от cache behaviour. Bandwidth-bound code фиксится снижением data volume (более компактные types, compression, on-the-fly computation вместо materialised tables), не улучшением cache locality. Две метрики часто появляются вместе, но требуют разных фиксов; <code>perf stat</code> <code>cache-misses</code> vs <code>mem-loads-retired.l3-miss</code> разделяет их.</p>
    <p><strong>NUMA: когда multi-socket мешает.</strong> Servers с 2+ CPU sockets — Non-Uniform Memory Access: каждый socket имеет local RAM на ~70нс, remote (other socket) RAM на ~120-150нс. Thread, аллоцирующий на socket 0, но работающий на socket 1, платит remote-access tax на каждой load. Митигации: pin threads на sockets (taskset, hwloc), аллоцируй на local NUMA node (numactl, allocator NUMA awareness), распределяй работу так, чтобы каждый thread трогал data со своего local socket. Database engines (Postgres, MySQL, Mongo) и JVMs экспонируют NUMA флаги. Mis-configured: 2-socket box может работать медленнее 1-socket для memory-bound workloads.</p>
    <p><strong>Vectorisation и auto-vec.</strong> Компиляторы auto-vectorise простые циклы над arrays в SIMD instructions, когда data layout позволяет (нет aliasing, contiguous, predictable trip count). Auto-vec defeats: pointers, которые могут alias (используй <code>restrict</code> в C, mark types правильно в Rust), data-dependent inner branches, variable trip counts. Проверь, что компилятор emit-нул через <code>-fopt-info-vec</code> (GCC) или <code>-Rpass=loop-vectorize</code> (Clang). Для циклов, которые fail auto-vec, manual SIMD intrinsics (AVX2, NEON) или libraries (Highway, simd-everywhere) закрывают gap. Cold counter to auto-vec: не форсируй через #pragma, если loop имеет correctness-relevant edge cases — auto-vec для них нуждается в careful guards.</p>
    <p><strong>Inlining и instruction cache.</strong> Aggressive inlining помогает branch prediction и убирает call overhead, но bloats code size — что бьёт по instruction cache (I-cache, обычно 32-64 KB per core). Функция, вызываемая из 100 мест, после inline добавляет 100 копий своего body в binary; если hot, эти копии загрязняют I-cache, evict-ируя other hot functions. Фикс — selective: inline tiny functions (1-3 строки) свободно, inline larger functions только на горячих call paths. Profile-guided optimisation (PGO) делает эти решения автоматически — без PGO компилятор defaults на «inline what fits the heuristic», что может быть неправильно.</p>
    <p><strong>Allocator awareness и arena allocation.</strong> Default heap аллокаторы (malloc, JS new) разбрасывают объекты по адресному пространству непредсказуемо. Для perf-критичных hot paths это враг cache locality. Arena allocator выделяет один большой блок памяти и роздает из него последовательно — все объекты живут рядом, prefetcher работает, иторация cache-friendly. Игровые движки, PostgreSQL (memory contexts), Rust (typed_arena, bumpalo) активно используют arenas. Trade: arena освобождается одним блоком, не per-object — подходит для request-scoped или frame-scoped аллокаций. Для долгоживущих данных используй pool allocator (фиксированный размер per slot, переиспользует).</p>
    <p><strong>Cold paths и hot/cold split.</strong> Внутри одной функции часть пути hot (95% вызовов), часть cold (error handling, edge cases). Компилятор по умолчанию emit-ит код подряд, и cold path занимает место в I-cache рядом с hot. Аннотация <code>[[likely]]</code> / <code>__builtin_expect</code> подсказывает компилятору переставить ветки: hot path в начало, cold вынесен в конец секции. PGO делает то же автоматически. Дополнительно — выделять cold path в отдельную функцию с attribute <code>cold</code> — компилятор положит её в отдельную секцию binary, hot loop не платит I-cache штраф за неё. Метрика для отслеживания: <code>L1-icache-load-misses</code> в perf stat — если она растёт после изменения, hot/cold split нарушился. Это часто пропускают: оптимизировали data layout, но забыли проверить instruction-cache влияние, и общий выигрыш меньше ожидаемого.</p>

  <Fragment slot="senior">
    <p><strong>Hardware prefetcher behaviour.</strong> Современные CPU имеют несколько hardware prefetchers: sequential, детектирующий forward strides, stride detector, ловящий «every Nth byte» паттерны, и на некоторых chips content-based prefetcher, следующий pointer-like values. Sequential prefetcher kicks in после 2-3 consecutive cache misses в том же direction; раз активен, prefetcher prefetches до 16 lines вперёд. Defeating его: random access или access patterns с stride слишком длинным для detection. Помогая ему: держи hot loop stride маленьким (≤256 байт) и consistent. Software prefetch через <code>__builtin_prefetch</code> — manual escape hatch — useful, когда знаешь access pattern, но hardware не может infer (например, graph traversals, где next node data-dependent).</p>
    <p><strong>TLB и page-level locality.</strong> За пределами L1/L2/L3 Translation Lookaside Buffer (TLB) кеширует virtual-to-physical address translations. TLB miss стоит 5-50 циклов для page walk. Workloads, трогающие random pages (каждая ~4KB), blow out TLB, даже если data влезает в L3. Митигации: huge pages (2MB или 1GB pages уменьшают TLB pressure в 512x или 256000x), allocator awareness (jemalloc / mimalloc batch related allocations в ту же page region). Для high-perf кода, трогающего gigabytes — databases, ML inference, image processing — huge pages могут быть 10-20% win независимо от cache locality.</p>
    <p><strong>Cache associativity и conflict misses.</strong> Caches не fully associative — каждая cache line может быть placed только в нескольких specific «ways» (обычно 8-16 way associative для L1). Если много hot addresses случайно map в тот же set, они evict друг друга, хотя plenty cache empty elsewhere. Классический пример: stride pattern, совпадающий с cache size modulo. Митигация: pad data structures на extra cache line для разрыва alignment patterns, randomise large array alignments, используй cache-oblivious data layouts. <code>cachegrind</code> репортит D1mr/D1mw (L1 miss rate) и DLmr/DLmw (LL miss rate) per source line, экспонируя, где conflict misses happen.</p>
    <p><strong>Branch prediction алгоритмы.</strong> Modern predictors sophisticated. Branch target buffer (BTB): кеширует target address недавних indirect branches. Pattern History Table (PHT): трекает per-branch taken/not-taken history. TAGE (TAgged GEometric) predictor: combines multiple history lengths, used в современных Intel и AMD. Hit rates 95-99% типичны на реальном коде. Hard cases: data-dependent branches (sort, filter), virtual function calls с high polymorphism, очень длинные pipelines (Apple M1/M2/M3 имеет 10+ stages). Cost miss — pipeline depth — на 20 stages с multi-issue miss может wasted 40+ slots, equivalent выполнению 40 ops без progress.</p>
    <p><strong>Memory-level parallelism (MLP).</strong> Современные CPU могут иметь 8-16 cache misses outstanding одновременно. Если miss pattern твоего кода позволяет CPU issue independent loads вперёд, latency stacks параллельно — 10 misses не стоят 1000 циклов, стоят ~150 циклов (одна miss latency + dispatch slots). Dependent-load chains (pointer chasing: A.next.next.next) defeat MLP полностью, потому что каждая load нуждается в результате предыдущей. Independent-load patterns (array of indices, scatter/gather) получают full parallelism. Optimising для MLP — уровень выше optimising только для cache hit rate; tools типа <code>perf c2c</code> на Linux показывают MLP behaviour. ARM PMU counters экспонируют similar метрики на Apple Silicon.</p>
    <p><strong>Non-temporal stores и streaming.</strong> Streaming через gigabytes памяти (memcpy-like workloads) не benefit-ит от caching data — оно read once и discarded. Non-temporal store instructions (<code>movntps</code> на x86, similar на ARM) bypass cache и пишут directly в memory, freeing cache для hot data. Компиляторы могут emit их через <code>__builtin_nontemporal_store</code>. Для bandwidth-bound workloads (DB scans, log processing), non-temporal stores улучшают sustained bandwidth в 20-30%, не загрязняя L3 one-shot data.</p>
    <p><strong>Cache-oblivious алгоритмы.</strong> Cache-oblivious алгоритм performs well на каждом cache level без знания specific sizes. Канонический пример: recursive blocked matrix multiply. Вместо трёх nested loops, рекурсивно делим matrix на 4 sub-matrices; recurse до base case. На каждом recursion level активная sub-matrix влезает в some cache level naturally — хотя алгоритм не знает в какой. Результат: cache-friendly behaviour от L1 через L3 одновременно. Применимо к sort (cache-oblivious mergesort), search trees (cache-oblivious B-trees), transposes, FFT. 2-4x speedup над naive часто доминирует cleverness cost.</p>
    <p><strong>Profile-guided optimisation (PGO).</strong> Компиляторы улучшаются, given runtime data. Build binary с instrumentation, run representative workload, recompile, используя collected profile. PGO улучшения: better inlining decisions (inline hot callees, не cold), branch prediction hints baked в code layout (predicted-taken branches placed sequentially), reorder basic blocks для держания hot paths contiguous (better i-cache locality), function placement (group co-called functions в соседних pages). Real workloads видят 10-30% speedups от PGO. Cost: build pipeline complexity, нужен representative profiling workload. Used heavily в Chrome, Firefox, Postgres, Linux kernel.</p>
    <p><strong>Real production failures.</strong> Discord 2023: Rust struct refactor переместил hot field в конец 96-byte структуры, толкая его через cache line boundary. p99 latency на message-render path вырос 40%. Пофикшено reordering полей для держания hot ones в первых 64 байтах. Mojang Minecraft Java edition 2018: internal data structure был HashMap маленьких entities; замена на contiguous array (entity component system, ECS) дала 3-5x throughput. Discord 2024 game-server: ECS layout в сочетании с SIMD-aware structs delivered другой 2x. Bun 2024 startup time regression: новая dependency добавила HashMap на cold path, который из-за allocation order blew L1 cache во время JIT warmup; пофикшено lazy-init. Паттерн: cache-related perf bugs прячутся как «small» code changes, двигающие байты, не меняя алгоритм.</p>
    <p><strong>Observability для cache и branch perf.</strong> Essential set: <code>perf stat -e cache-misses,cache-references,branch-misses,branches,cycles,instructions</code>. Compute IPC (instructions / cycles): ниже 1.0 indicates memory-bound workload; 2-4 healthy compute-bound. Compute L1/LLC miss rate: 1% L1 misses acceptable; 10%+ indicates layout problem. Compute branch miss rate: 1-2% normal; 5%+ means unpredictable branch dominates. Linux <code>perf top</code> показывает per-symbol miss attribution. Intel VTune и AMD uProf добавляют per-line attribution. Для production: BPF-based profilers (BCC <code>cachestat</code>, <code>llcstat</code>) sample без instrumenting; ARM PMU и Apple Instruments экспонируют те же metrics на этих платформах.</p>
    <p><strong>Большой урок: design для hardware.</strong> Современные CPU награждают locality и predictability. Big-O остаётся правильной моделью для scalability с N; молчит о constant factors, варьирующихся в 100x с layout. Performance-engineering loop: measure (perf, VTune), identify dominant cost (cache miss, branch miss, bandwidth, instruction issue), choose matching fix (layout, branch removal, prefetch, SIMD), measure again. Избегай ловушки «я просто использую better-big-O алгоритм» без measuring — production reality в том, что constants dominate well into миллионы для многих problem sizes. Senior performance engineer думает в cache lines first, big-O second.</p>
    <p><strong>Co-location: data и code вместе.</strong> Cache locality применяется не только к data structures, но и к instruction layout. Functions called вместе должны жить рядом друг с другом в binary; PGO arranges это автоматически based на call frequency. Для очень hot inner loops «warm starts» — running actual representative workload at startup для population cache — превращают cold-start regressions в invisible. Linux kernel использует это для boot-critical paths; Postgres имеет connection-pool warming. Принцип: caches reward second-and-following accesses, поэтому engineering trick — обеспечить, что first access happens до того, как пользователи увидят latency.</p>
    <p><strong>SIMD-friendly data alignment.</strong> AVX-512 требует 64-byte alignment для самых быстрых load инструкций; AVX2 — 32-byte; NEON — 16-byte. Misaligned access работает, но медленнее (split-load penalty). Компилятор не всегда align-ит автоматически — для structs нужны атрибуты (<code>alignas(64)</code> в C++, <code>#[repr(align(64))]</code> в Rust). При allocation: <code>posix_memalign</code>, <code>std::aligned_alloc</code>, или allocator с alignment-параметром. Mismatch alignment — частая причина «SIMD не дал ожидаемого speedup» — на профилировщике видишь, что инструкции выполняются, но latency хуже теоретического. Для критичных циклов всегда verify alignment через <code>(uintptr_t)ptr % 64 == 0</code> assertion перед SIMD load. В Rust та же проверка делается через <code>ptr.is_aligned()</code> или <code>std::intrinsics::assume()</code> для compiler-hint оптимизаций. В hot path лучше делать assertion на dev-build и unsafe-предположение на release — компилятор тогда не emit-ит fallback-путь для misaligned случая, instructions становятся на 10-20% быстрее, и эта разница часто решает, попадает ли SIMD-loop в frame budget или вылетает на render-стороне.
