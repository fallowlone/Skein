Server-side batching покрыл амортизацию фикс. цены. На клиенте фикс. цена — байты, которые ваш код просит браузер скачать, распарсить, скомпилировать и выполнить до того, как страница станет usable. Эта цена ложится тяжелее всего на mid-range мобильные на медленных сетях — median user во многих рынках. Bundle budgets — это дисциплина измерения этих байтов per route, capping'а их и enforcing cap'а в CI time.

<Crux>JS bundle байты = parse + compile + execute на CPU юзера. Mid-range мобильное = 4-8x медленнее dev-лэптопа. Поставь бюджет, enforce.</Crux>

1 МБ JavaScript bundle — это не 1 МБ цены. Это download (медленно на мобильном), parse (V8 проходит каждый байт), compile (JIT генерирует bytecode потом optimised code), execute (запускается startup-логика). На быстром лэптопе цепочка sub-секунда; на median Android на 4G — 5-15 секунд до interactive. Core Web Vitals — LCP, INP, CLS — квантифицируют то, что чувствует юзер; bundle budgets — рычаг, двигающий их. Сеньорная frontend-работа трактует байты как finite resource с per-route caps, а не как side-effect feature-разработки.

  <Fragment slot="middle">
    <p><strong>Цена JavaScript: download, parse, compile, execute.</strong> У каждой фазы своя цена. Download: bandwidth-limited; 200 КБ gzip'd на 4G ~150-500 мс. Parse: V8 парсит ~1-2 МБ/сек на high-end лэптопе, ~200-400 КБ/сек на median Android — bundle 500 КБ un-gzip'd = ~1,5-2 с parse на mid-range mobile. Compile: V8 pipeline (Ignition → Sparkplug → TurboFan) компилирует каждую функцию при первом вызове; total растёт примерно линейно с размером кода. Execute: top-level код (framework init, store creation, route registration) бежит synchronously, блокируя main thread. Для типового React + Redux app — 100-500 мс execution до interactive. Полная цепь на mid-range mobile для 500 КБ un-gzip'd: download 800 мс + parse 1,5 с + compile 300 мс + execute 400 мс ≈ 3 секунды до того, как юзер может кликнуть. Каждая фаза — отдельный рычаг; bundle budgets cap'ят total.</p>
    <p><strong>Core Web Vitals и что они меряют.</strong> Три основные Google-метрики user-perceived performance. LCP (Largest Contentful Paint): время до рендера самого большого видимого элемента above the fold. Target: &lt; 2,5 с. Тяжёлый JS, блокирующий main thread, задерживает render — LCP страдает. INP (Interaction to Next Paint, заменил FID в 2024): worst-case latency от user input до следующего visual update. Target: &lt; 200 мс. JS execution, удерживающий main thread на длительные периоды, портит INP. CLS (Cumulative Layout Shift): сколько страница «прыгает» во время load. Target: &lt; 0,1. Поздно прибывающие fonts, images без размеров, JS, вставляющий above-the-fold контент — всё портит CLS. Bundle budgets помогают всем трём: меньше JS = меньше parse+execute = лучше LCP и INP. CLS в основном layout/image issue, фиксится резервированием места.</p>
    <p><strong>Code splitting стратегии.</strong> Самое эффективное уменьшение bundle'а. Route-level: каждый route — свой JS chunk; navigating /settings не качает /editor's bundle. Component-level: компоненты, рендерящиеся условно (modals, drawers, dialogs) грузятся только при использовании. Vendor-splitting: third-party библиотеки в отдельном chunk, кэшируемом отдельно от app кода. Webpack splitChunks, Vite automatic, Next.js per-route chunks, Remix resource routes — каждый современный bundler даёт эти примитивы. Senior pattern: каждый route — свой bundle, vendor libraries split out, любой компонент &gt; 30 КБ lazy-loaded если не на critical path.</p>
    <p><strong>Tree shaking и dead code elimination.</strong> Когда модуль экспортирует много функций, а импортируешь только одну, современные bundler'ы должны удалить unused — «tree shaking». Требует ES modules, pure-marker annotations (`/* #__PURE__ */`), static analysis bundler'а. Real-world traps: модуль с side effects на import (setting `window.foo = ...` at module scope) не tree-shak'ится. lodash main bundle включает все функции; `import _ from 'lodash'` — всё (70 КБ+); `import debounce from 'lodash/debounce'` — только debounce (2 КБ). Configuration: webpack `optimization.usedExports`, Rollup built-in, esbuild `--tree-shaking=true`. Senior verification: открыть bundle analyzer (`source-map-explorer`, `webpack-bundle-analyzer`, `vite-bundle-visualizer`), убедиться что unused exports отсутствуют.</p>
    <p><strong>Compression: gzip vs brotli, static vs dynamic.</strong> Text-based assets (JS, CSS, JSON, SVG) сжимаются 60-80% gzip, 70-90% brotli. Static compression (pre-compressed at build, отдаётся с Content-Encoding header) ничего не стоит at request time. Dynamic compression (сервер сжимает on the fly) стоит CPU per request — типично 5-30 мс brotli, 1-5 мс gzip. Senior choice: static brotli для assets, где build раз и serve много; dynamic gzip для HTML responses, varying per user. Современные CDN делают это автоматически и кэшируют compressed-версию. Verify with `curl -I -H "Accept-Encoding: br" your-asset-url`, check Content-Encoding response header.</p>
    <p><strong>Critical path vs deferred.</strong> Не все байты равны. Critical path: JS, нужный для рендера первого meaningful view (framework init, root component, above-the-fold data). Deferred: JS для interactions, не происходящих на first paint (modals, settings panels, admin tools). Senior pattern: держи critical path под 80-100 КБ gzip'd; defer всё остальное через dynamic `import()`. React `React.lazy`, Vue `defineAsyncComponent`, Svelte lazy loading — все используют тот же dynamic-import примитив. Результат: First Contentful Paint быстро; остальной app качается в фоне.</p>
    <p><strong>Third-party scripts: тихий убийца бюджета.</strong> Analytics, ads, customer-support widgets, A/B testing — third-party scripts часто доминируют bundle. Не в вашем repo, но шлются каждому юзеру. Частые offenders: Segment (~150 КБ), Hotjar (~200 КБ), full-page Optimizely (~400 КБ), Intercom widget (~200 КБ), Google Tag Manager с несколькими tags (~500 КБ+). Mitigation: load с `async` или `defer` (не блокировать render), gate by interaction (грузить chat-widget только при клике на 'help'), self-host critical analytics, audit ежеквартально для удаления unused vendors. PartyTown — recent technique, запускающая third-party scripts в Web Worker, чтобы не блокировать main thread. Сеньорные команды держат «third-party budget» отдельно от app bundle budget.</p>
    <p><strong>Images, fonts, static assets.</strong> JS часто доминирует parse cost, но images и fonts могут доминировать total bytes. Images: современные форматы (AVIF 30-50% меньше JPEG, WebP 20-30% меньше), responsive `srcset`, lazy-load below-the-fold images с `loading="lazy"`. Fonts: subset до actually-used символов (FontTools `pyftsubset` отрезает ~70%); `font-display: swap` для рендера fallback-текста сразу; preload critical fonts. CSS: critical CSS inline в head; остальной stylesheet — async. Каждый класс assets заслуживает свой бюджет; объединение в «total page weight» прячет per-class регрессии.</p>
    <p><strong>Mobile testing на практике.</strong> Самая частая причина «great in dev, slow in prod» — тестирование только на машине разработчика. Production-grade mobile testing — четыре слоя. (1) Chrome DevTools CPU throttling — set to 4x slowdown для approximate mid-range Android. Быстрая проверка во время разработки. (2) Real device testing — держать физический Moto G4 / Pixel 3a / similar mid-range Android в команде. Lighthouse mobile emulation близко, но не ловит real-device quirks (GPU, memory pressure, thermal throttling). (3) BrowserStack или similar device cloud для QA — автоматические тесты на десятках реальных устройств. (4) RUM с device-class breakdowns — segment dashboards by device tier. Команды, отгружающие в global markets, routinely имеют 60-80% юзеров на mid-range или старше; тестирование только на flagship систематически недооценивает real-user experience.</p>
    <p><strong>Правило 100 КБ бюджета.</strong> Industry-standard recommendation: держи initial JS под 100-170 КБ gzip'd для fast first interactive на mid-range mobile. Источник: Google Web Fundamentals + empirical data Lighthouse/WebPageTest. Математика: 170 КБ gzip'd ≈ 500 КБ un-gzip'd. Parse на mid-range Android ≈ 1,5 с. Plus compile и execute ≈ 2-2,5 с total. Add network download (~500 мс on 4G) = ~3 с к interactive. Верхняя граница, удерживающая LCP под 2,5 с. За 170 КБ каждые дополнительные 100 КБ примерно добавляют 300-500 мс к LCP на median устройстве. Разные routes могут иметь разные бюджеты — marketing tight (50-100 КБ), dashboard medium (150-250 КБ), admin tools relaxed (300-500 КБ) — но homepage всегда самое жёсткое ограничение, потому что conversion там.</p>
    <p><strong>Lighthouse vs PageSpeed Insights vs RUM.</strong> Три инструмента, измеряющих CWV; каждый имеет свою роль. Lighthouse: synthetic test в DevTools или CLI; full audit на dev-машине с throttling. Хорош для PR-time проверки. PageSpeed Insights: Google-managed Lighthouse run + field data из CrUX (Chrome User Experience Report). Field data — реальные agregated metrics от Chrome users. Полезен для public-facing анализа. RUM: твой собственный sampling реальных юзеров. Самый точный, но требует setup. Сеньорный паттерн: Lighthouse в CI для catch regressions перед merge, RUM в production для catch regressions, не пойманных в CI, PageSpeed Insights раз в квартал для cross-reference. Каждый ловит разные классы проблем; ни один не replaces других.</p>
    <p><strong>Image и font optimisation в деталях.</strong> Images типично 50-80% страничных байтов; их оптимизация — high-leverage. AVIF: 30-50% меньше JPEG того же качества, supported в Chrome/Firefox/Safari. WebP: 20-30% меньше, older browser support. Стратегия: serve AVIF с WebP fallback с JPEG fallback через `&lt;picture&gt;`. Responsive images: `srcset` шлёт mobile 800px image, desktop — 1920px. Lazy loading: `loading="lazy"` на all below-the-fold images. Format choice: photographs — JPEG/AVIF/WebP, graphics — SVG, иконки — SVG sprite или icon font. Fonts: WOFF2 (вместо WOFF1) — 30% меньше. Subset до actually-used символов: full Cyrillic font ~600 КБ, subset до needed glyphs ~80 КБ. `font-display: swap` — fallback text сразу, swap to custom font после load (small CLS). Preload critical fonts с `&lt;link rel="preload" as="font"&gt;`. Variable fonts: один файл, multiple weights/styles — replaces 5-6 separate font files. Сеньорный workflow: budget на images/fonts отдельно от JS, audit per route раз в квартал.</p>
    <p><strong>Service worker и offline-first.</strong> Service worker — JS, бегущий в background browser thread, intercepting network requests. Use case: cache assets aggressively, serve stale-while-revalidate, offline support. Workbox (Google library) abstracts patterns. Strategy для bundle budgets: cache всё static assets с long max-age (1 year); use content-hash в filename для invalidation; service worker serves cache-first для assets, network-first для HTML. Result: second visit nearly instant (всё из cache); deploys invalidate via new hash в HTML. Tradeoff: SW добавляет complexity, debug harder, stale cache bugs. PWA frameworks (Workbox, vite-plugin-pwa, next-pwa) handle most concerns automatically. Сеньорный pattern: SW для всех production frontend apps; cache strategy documented; manual cache-bust path для emergency rollback. Альтернатива SW: server-side ETag/Cache-Control с aggressive immutable headers на content-hashed файлы — даёт 80% выигрыша без SW сложности. Выбирай SW когда offline-first действительно нужен; иначе headers достаточно.</p>

    <p><strong>V8 tiered compilation pipeline.</strong> V8 (JS engine в Chrome, Node, большинстве Chromium) компилирует JS через multiple tiers. Ignition — bytecode interpreter; most code runs там изначально. Sparkplug (added 2021) — non-optimising baseline JIT, компилирующий bytecode в machine code с no inlining — fast to compile, ~5x faster to run than Ignition. Maglev (added 2023) — mid-tier optimising JIT. TurboFan — top-tier optimising compiler с full inlining и speculative optimisation. Каждая функция движется up tiers как становится hotter. Implications для bundle budgets: код, который бежит только at startup (framework init, route setup) остаётся в Ignition/Sparkplug — fast to compile, slow to run. Critical hot loops (event handlers, render functions) eventually reach TurboFan и run near-native. Total: bundle size affects parse + Ignition compile, но execution speed зависит от того, reach ли hot функции optimised tiers. Сеньорные frontend perf engineers profile с --trace-deopt / Chrome Performance tab — какие функции stuck in low tiers; иногда fix — shape stabilisation, не bundle reduction.</p>
    <p><strong>HTTP/2 + HTTP/3 priorities и resource waterfall.</strong> Современные протоколы дают серверу prioritise responses. HTTP/2 имеет stream priorities; HTTP/3 (over QUIC) имеет explicit Extensible Priorities (RFC 9218). Браузеры шлют hints (CSS в head — "highest", lazy-loaded images — "lowest"). Сервер, honouring priorities, шлёт critical resources первыми даже если requested last. CDNs (Cloudflare, Fastly) реализуют. Interaction с bundles: small critical bundle, competing с large deferred bundle за bandwidth — starved без priorities; с priorities critical ships first. Verify в Chrome network panel "Priority" column. Сеньорная infra: ensure CDN шлёт priority hints и HTTP/3 prioritisation; misconfigured HTTP/3 priority может стереть 20-30% bundle-split benefits, потому что браузер всё равно качает big chunk перед small.</p>
    <p><strong>Preload, prefetch, modulepreload, 103 Early Hints.</strong> Четыре директивы, говорящие браузеру fetch'ить resources earlier. `&lt;link rel="preload"&gt;`: download immediately, high priority. Используй для critical CSS, fonts, hero images. `&lt;link rel="prefetch"&gt;`: download at idle priority для next navigation. Используй для likely-next-route resources. `&lt;link rel="modulepreload"&gt;`: download AND parse-compile module ahead. Используй для ESM modules, которые будут imported. HTTP `103 Early Hints` (RFC 8297): server шлёт 103 response с `Link: ...; rel=preload` перед final HTML, говоря браузеру start fetching critical resources, пока server строит остальное. Cloudflare, Fastly, Vercel реализуют 103. Combined с bundle splitting: send preload hints для route critical chunks в 103, потом ship HTML; user gets 100-500 мс head start. Большинство production teams ещё не используют Early Hints; сеньоры должны.</p>

    <p><strong>Tree-shaking pitfalls и как production-grade builds verify.</strong> Tree-shaking звучит автоматическим, но имеет много failure modes. Pitfall 1: side effects. Module с code at module scope (`if (typeof window !== 'undefined') window.foo = bar`) не tree-shak'ится — bundler keeps the whole module to preserve side effect. Solution: mark package as `"sideEffects": false` в package.json или use `/* #__PURE__ */`. Pitfall 2: CJS interop. CJS exports — runtime values; require() prevents tree-shaking. Solution: use ESM-only. Pitfall 3: re-exports. `export * from './module'` re-exports everything; даже если один consumer uses один export, whole module survives. Solution: explicit named re-exports. Pitfall 4: dynamic imports, которые not really dynamic. `await import('./module')` где `./module` — literal — tree-shakeable; `await import(name)` где name dynamic — prevents shaking. Production verification: after every build, run bundle analyzer и grep heaviest imports; confirm они actually used. Некоторые teams add CI checks, fail'ящие если specific large libraries (moment, lodash full) appear в bundle.</p>
    <p><strong>Безопасность доставки bundle'а.</strong> Subresource Integrity (SRI): `&lt;script src="..." integrity="sha384-..."&gt;` атрибут позволяет браузеру verify, что script не tampered. Без SRI compromised CDN может ship malicious JS всем users; с SRI браузер rejects script если hash не match. Production-grade: SRI на все third-party scripts; build-time SRI generation для first-party. CSP (Content Security Policy): restricts откуда scripts могут come. `script-src 'self' https://cdn.example.com;` блокирует inline scripts и arbitrary domains, preventing XSS-injected scripts даже если они попали в DOM. Common misconfiguration: `'unsafe-inline'` allows inline scripts, defeating CSP. Сеньорные teams set strict CSP, use nonces или hashes для intentional inline scripts. Third-party scripts — extra scrutiny: каждый embedded analytics или widget потенциально имеет access к page DOM, cookies, localStorage. Quarterly audit: list every third-party domain в CSP, justify каждый, review vendor track record.</p>
