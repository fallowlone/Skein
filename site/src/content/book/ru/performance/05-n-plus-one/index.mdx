Когда hot-paths классифицирует bottleneck как syscall-bound или I/O-bound — много мелких round-trip'ов доминируют wall-clock — этот фрагмент даёт семейство правок. Textbook-пример — N+1 query, но та же форма везде: HTTP fan-out, gRPC-микросервисные вызовы, file-read'ы в цикле, cache-lookup'ы в цикле. Одна логическая операция, которой должен быть один вызов, становится N+1.

<Crux>Один trip = быстро. N+1 trip'ов = медленно. Каждый round-trip платит RTT; один запрос на 100 строк бьёт 100 запросов по одной.</Crux>

N+1-проблема — самый частый production-perf баг в любом приложении, трогающем БД. Пользователь просит «покажи список заказов с именами клиентов»; ORM спокойно делает один запрос на orders, потом по одному запросу на каждый order для fetch клиента — 1 + N запросов. С 50 заказами на странице — 51 DB round-trip на один рендер. Каждый round-trip платит сетевой RTT (1-5 мс внутри DC, 10-50 мс cross-region) плюс query-overhead. Страница, которая должна делаться за 20 мс, делается за 500 мс — и инженер не находит это в CPU-профиле, потому что цена распределена по многим быстрым вызовам.

    <p><strong>Что это одной фразой.</strong> Когда одна логическая операция (загрузить страницу, отрендерить список) превращается во множество маленьких вызовов БД или другого сервиса — вместо одного большего вызова, получающего всё сразу.</p>
    <p><strong>Почему важно.</strong> Каждый round-trip платит фиксированную цену (сетевое время, query-overhead). 50 маленьких запросов в 30-50 раз медленнее, чем один запрос, забирающий те же данные. Страница ощущается медленной, при этом ни одна функция не медленная.</p>
    <p><strong>Метафора.</strong> Готовите пасту, нужны чеснок, масло, соль, базилик. Вариант A: пойти в кладовую один раз, взять все четыре, вернуться. Вариант B: пойти за чесноком, вернуться; пойти за маслом, вернуться; и так далее. Вариант B делает ту же работу, но платит «прогулку» четыре раза. Вариант A — один раз. N+1 — это вариант B; batch loading — вариант A. Прогулка — это round-trip; задача — уменьшить число прогулок.</p>

    <p><strong>Почему ORM поставляют N+1 по умолчанию.</strong> ORM выставляют модель, где каждый объект имеет поля и отношения, доступные как обычные свойства. <code>order.customer</code> читается, будто это обычный атрибут; под капотом ORM триггерит запрос, если customer ещё не загружен. Это «lazy loading» — удобно (не нужно объявлять заранее, что вам нужно), но это источник N+1. Цикл по orders, доступ к <code>order.customer.name</code> на каждом — N запросов без написания N запросов. ORM, стремящиеся максимально к прозрачности (Active Record, Django ORM, классические Hibernate-сессии), особенно подвержены этой ловушке. Паттерн настолько универсален, что каждый крупный ORM поставляет явные anti-N+1 фичи: Rails <code>includes()</code>, Django <code>select_related()</code> / <code>prefetch_related()</code>, SQLAlchemy <code>joinedload()</code> / <code>selectinload()</code>, Hibernate <code>FetchType.EAGER</code> / <code>@BatchSize</code> / <code>EntityGraph</code>, Prisma <code>include</code>, GraphQL DataLoader. Каждый — своя форма «скажи ORM заранее, что понадобится, чтобы он сделал один-два запроса вместо N+1».</p>
    <p><strong>Четыре семейства фиксов.</strong> (1) JOIN — забрать parent и child одним запросом (<code>SELECT * FROM orders o JOIN customers c ON o.customer_id = c.id</code>). Один round-trip, но result set дублирует parent-колонки на каждую child-строку. Хорошо для one-to-one или маленьких one-to-many. Плохо, когда one-to-many fan-out велик (parent с 100 children = 100 строк parent-данных, повторённых 100x). (2) IN — два round-trip'а: сначала фетч parents, потом <code>SELECT * FROM customers WHERE id IN (1, 2, 3, ...)</code>. Избегает дублирования, масштабируется с parent-count. Плохо, когда IN-список растёт огромным (многие DB имеют практические лимиты ~1000-10000 элементов; Postgres держит длиннее, но query plan меняется). (3) Preload / eager fetch — batched-загрузка ORM-уровня, триггерится одной директивой (Rails .includes, Django .select_related, SQLAlchemy joinedload). Под капотом ORM выбирает JOIN или IN; вы декларируете intent, ORM выбирает тактику. (4) DataLoader / batch loader — request-scoped паттерн: вместо немедленных запросов, queueing child ID по всему запросу, батч в один запрос, когда event loop yield'ит. Изначально GraphQL-native (Facebook dataloader, 2015), но применимо к любой request-response системе. Лучше всего для GraphQL, fan-out API или любого контекста, где много частей одного запроса нуждаются в похожих данных.</p>
    <p><strong>Детект в профилях и трейсах.</strong> N+1 прячется от CPU-профилей. Правильные инструменты: (а) DB query log с timestamp'ами — Postgres <code>log_min_duration_statement=0</code> логирует каждый запрос; MySQL slow log; SQL Server extended events. Grep по request-id; десятки похожих запросов на один запрос — это N+1. (б) APM tracing (Datadog, New Relic, Tempo + auto-instrumentation): trace-водопад показывает DB-span'ы inline с code-span'ами; ряд из 50 похожих DB-span'ов на одном запросе кричит N+1. (в) ORM-side инструментирование: Rails имеет <code>strict_loading</code>, бросающий при lazy-load на рендере; Hibernate имеет <code>spring.jpa.show-sql</code> + N+1-детект в Hibernate Statistics. (г) Кастомное middleware, считающее queries-per-request, алертящее при превышении (типично: 20 на запрос — warning в dev, 50 — fail CI). Strict mode + CI-гейт — сеньорный паттерн: ловить N+1 на PR-time, не в production.</p>
    <p><strong>Математика: почему N+1 убивает p99.</strong> RTT до БД типично 0,5-5 мс intra-DC, 10-50 мс cross-region. Страница с 50 запросами платит 50 × RTT serial wall-clock — минимум 25 мс intra-DC, 500 мс - 2,5 с cross-region. Даже с batch-фиксами query count × per-round-trip cost — доминирующий фактор. p99 хуже среднего, потому что RTT сам имеет хвост (любой из 50 запросов, попавший на медленный planner, locking blip или сетевой jitter, добавляет свой хвост к хвосту страницы). Страница на 50 запросах амплифицирует любой DB tail-latency на ~50x на уровне страницы. Переход с 51 на 2 запроса не просто множит mean на 25; он устраняет 49 шансов попасть в DB-хвост. Production-команды на per-request query budget'ах (например, max 5 запросов на рендер) держат стабильный p99 даже при флуктуации отдельных запросов.</p>
    <p><strong>Cross-protocol: N+1 не только SQL.</strong> Та же форма в HTTP fan-out (микросервис, дёргающий 10 других на запрос), gRPC-стриминге с per-row RPC, Redis-lookup'ах в цикле (один Redis GET на item вместо одного MGET), file-read'ах (open/read/close на файл вместо одного batch-read или mmap), даже Kafka producer-отправках (одна send на сообщение вместо batched). Семейство фиксов то же: собрать, батчить, отправить раз, распределить результаты. Для Redis: MGET / pipelined команды. Для HTTP: GraphQL batched queries или aggregator-сервис. Для gRPC: streaming RPC или batch RPC. Для file I/O: io_uring batched submission. Протокол меняется; паттерн — нет.</p>
    <p><strong>Цена фиксов: payload bloat и cardinality.</strong> У каждого фикса своя цена. JOIN: result set раздувается, потому что parent-строки дублируются на каждую child. Запрос, возвращающий 1000 orders с 5 line-items каждый, как JOIN, возвращает 5000 строк, где 4000 колонок — повтор parent-данных. Сетевая пропускная способность + parsing-цена могут перекрыть round-trip экономию. IN list: хорошо работает до ~1000 элементов; дальше DB query planning меняется, некоторые движки имеют hard-limit'ы (Oracle исторически 1000; Postgres держит длиннее, но planner-цена растёт). DataLoader: per-request память на batch queue, latency от event-loop ожидания, сложность кэширования. Preload (eager): слишком агрессивный preload фетчит данные, которые запрос не использует — wasted I/O. Сеньорный тюнинг выбирает семью фиксов по форме workload'а: one-to-one → JOIN, one-to-many fan-out → IN или selectinload, request-scoped multi-source → DataLoader.</p>
    <p><strong>1+1 пол и когда даже один лишний trip важен.</strong> Минимальное число round-trip'ов на parent+child страницу — 1 (один JOIN-запрос) или 2 (parent, потом batched children). Для большинства workload'ов 2 — норма; IN проще JOIN и избегает result-set дублирования. Для latency-extreme путей (HFT, gaming, real-time bidding), где каждая миллисекунда считается, даже 1+1 много; команды пре-вычисляют denormalised views (materialized views, write-time денормализация, CQRS read models), чтобы страница фетчила одним запросом всё готовое. Tradeoff: write-side сложность + storage cost за read-side simplicity + latency. Сеньорные команды выбирают CQRS / denormalisation только для путей, где latency win оправдывает сложность; для остального 2-3 запроса на запрос — комфортный пол.</p>
    <p><strong>CI test-time gate.</strong> Самый leveraged anti-N+1 механизм — ловить регрессию на PR-time, не в production. Rails: `bullet` gem в test-mode raises на lazy-loaded relation в рендере — controller-тест с N+1 fail'ит. Django: `silk` middleware в test-settings или кастомный query-counter (`assertNumQueries(N)`). SQLAlchemy: `strict_loading_for_polymorphic` + ассерт на query count. Hibernate: `org.hibernate.Statistics` для assert query count per test. Паттерн один: PR триггерит тесты, тесты делают запросы, query counter превышает per-endpoint threshold, тест fail'ит, PR не мерджится. Production-команды с таким гейтом репортуют 70-90% сокращение N+1 инцидентов, доходящих до production. Стартовая цена: 1-2 недели (инструментирование + чистка исторических N+1). Ongoing maintenance: тривиально — гейт бежит в CI.</p>
    <p><strong>Параллелизация: fan-out вариант.</strong> Форма N+1 расширяется на non-database fan-out: 8 downstream-сервисов serial = 8x latency vs 1x для slowest. Фикс — concurrency: Promise.all (JS), errgroup.Wait (Go), CompletableFuture.allOf (Java), asyncio.gather (Python). То же структурное изменение: вместо `result1 = service1.call(); result2 = service2.call(); ...` — `[r1, r2, ...] = await Promise.all([service1.call(), service2.call(), ...])`. Wall-clock = max(latencies) вместо sum(latencies). Ограничения: сервисы со strict-зависимостями остаются serial; failure-handling должен учитывать partial-failure (часть успешна, часть нет — какой response?); coordination-overhead малый, но ненулевой. Сеньорное код-ревью для любого service-fan-out: флагать любой await/wait в loop'е по service-вызовам. Фикс — один diff, одна декларативная parallel-collect.</p>
    <p><strong>Анатомия observability: что именно мониторить.</strong> Production-grade observability для N+1 строится на трёх метриках. (1) Queries-per-request histogram by endpoint — публикуется middleware на каждом успешном запросе. Группировка по controller#action; визуализация p50/p99/max. Алерт при p99 endpoint'а &gt; 20 или росте &gt; 50% неделя-над-неделей. (2) Database span count per request — captured APM (Datadog auto-instrumentation, Tempo, Honeycomb). Trace-водопад показывает сразу, что один запрос делает 100 DB-вызовов. Алерт при росте per-endpoint p95 на &gt; 30%. (3) Connection pool wait time — pgbouncer cl_waiting metric или Rails ActiveRecord pool stats. Pool wait &gt; 10мс — leading indicator, что N+1 endpoint держит соединения дольше, чем pool успевает rotating. Три метрики вместе диагностируют 95% случаев за минуты вместо часов. Дашборд layout: per-endpoint table с p99 query count + p99 latency + pool-wait, сортируемая по любому столбцу. On-call открывает таблицу при page-out, видит top-3 нарушителя, выбирает один для немедленной правки.</p>
    <p><strong>Структурные альтернативы: когда даже batch недостаточен.</strong> Для путей с latency-extreme требованиями (high-frequency trading, real-time bidding, live-видео) даже 2-3 запроса дороги. Денормализация — выход. Counter cache (Rails counter_cache, Django annotate + cache, Mongo precomputed counters): хранит derived-данные в parent-записи; вместо count() на каждый запрос — одно SELECT поля. Materialized view (Postgres MATERIALIZED VIEW, Snowflake, ClickHouse): пре-вычисляет complex join + aggregation; страница фетчит одним запросом полностью готовый view. CQRS read model: write-side обновляет normalised схему, event-handler пишет в read-optimised таблицу с предварительно joined-данными. Tradeoff: write-side сложность и storage cost. Когда применять: read p99 SLO &lt; 50 мс на тяжёлых join'ах И read-load в 1000+ раз больше write-load. Для balanced workload'ов ORM eager-loading проще и достаточно. Дополнительный сигнал: если команда обсуждает CQRS на путях с read-load &lt; 100x write-load, обычно это преждевременная оптимизация — eager-load на 2-3 запроса покрывает 99% workload'ов с куда меньшей операционной ценой. Денормализация должна следовать за измеримой невозможностью попасть в SLO, а не за подозрением, что «может быть быстрее». Архитектурный выбор обратим только формально: read-model раз введённый редко удаляется, и его поддержка стоит engineering-времени каждый квартал. Сеньорный фильтр: показать измерение, показать SLO-bound, показать невозможность eager-load решить — тогда денормализация оправдана. Без этого тройного критерия архитектура просто растёт без выигрыша, и через год команда платит сложностью за фикс, которого можно было избежать одной .includes-директивой.</p>

    <p><strong>Внутренности DataLoader.</strong> Facebook dataloader (2015) стал каноничным паттерном. Механизм: в request-scope код зовёт <code>loader.load(id)</code>, возвращающий Promise. Loader не исполняет немедленно — queue'ит ID в batch. Когда event loop доходит до next-tick (после текущей синхронной работы), loader выстреливает один batched-запрос (<code>SELECT * FROM users WHERE id IN (queued_ids)</code>), получает все результаты, резолвит каждый Promise соответствующей строкой. Паттерн даёт три свойства: (1) автоматический батчинг — много load() вызовов = один запрос, (2) автоматический кэш — повторный load(id) внутри запроса возвращает кэш, без второго запроса, (3) request-scope — кэш scoped на запрос, stale-данные не утекают. Реализации: graphql/dataloader (Node), graphql-java/dataloader (Java), aiodataloader (Python), Promise.from в C#. Паттерн фундаментально привязан к async/promise рантаймам, потому что опирается на event-loop ticks; синхронные кодбазы нуждаются в explicit batch-coordination.</p>
    <p><strong>Prepared statements и parse-once кэш.</strong> Даже когда N+1 неизбежен (legacy-код, exploratory queries), prepared statements режут overhead. Каждый unparameterised запрос проходит parse + plan + bind + execute; prepared statements делают parse + plan один раз, потом bind + execute много раз. PostgreSQL: <code>PREPARE myquery AS SELECT ...</code> потом <code>EXECUTE myquery(?)</code>. MySQL имеет эквивалент. ORM используют prepared statements по умолчанию для parameterised-запросов — ORM-side binding параметров (?, $1, :name) — это и есть prepared-statement-протокол. Экономия: типично 30-50% на повторный запрос на Postgres в зависимости от сложности. Для сервиса с тысячами повторных запросов в секунду prepared statements могут уронить DB CPU на 10-30%. Tradeoff: connection-pool affinity (prepared statements connection-scoped в некоторых setup'ах; pgbouncer transaction mode отключает). Сеньоры знают, в каком mode pool гоняется и prepared ли их горячие запросы.</p>
    <p><strong>Connection pool exhaustion как downstream failure mode.</strong> N+1-bound сервис с 50 запросами на запрос и connection pool size 25 — каждый запрос держит соединение через 50 serial-запросов. Throughput pool'а ограничен (медленный запрос × pool size). Под нагрузкой запросы queue'ятся, ожидая соединений; latency tail-spiral'ит; eventual 503. Проксимальный фикс: убрать N+1, чтобы каждый запрос держал соединение 2-5 запросов вместо 50, освобождая pool. Диагностическая сигнатура: метрика saturation pool'а высокая, query latency стабильна, request queue растёт. Production-grade observability отслеживает per-pool active-connection ratio + queue depth; алерт при ratio > 80% sustained или queue > 0 более секунд. Тот же паттерн в HTTP-client pools, gRPC connection pools, Redis pools — любом pooled-ресурсе, где hold-time — bottleneck.</p>
    <p><strong>Cardinality, selectivity и изменения query plan.</strong> Фиксы N+1 могут изменить query plan БД неожиданно. <code>WHERE id IN (1, 2, ..., 1000)</code> может быть planned иначе, чем <code>WHERE id = 1</code> — Postgres может переключиться с index lookup на bitmap scan на seq scan в зависимости от selectivity-оценок. Hibernate "subselect" loading: <code>SELECT * FROM child WHERE parent_id IN (SELECT id FROM parent WHERE ...)</code> может дать совсем другой plan, чем основной parent-запрос. Сеньорная production-дисциплина: после фикса N+1 запусти EXPLAIN ANALYZE на новом запросе с production-data-sizes; убедись, что plan не регрессирует на edge case'ах (очень маленькие parent-сеты, очень большие, специальные параметры). Фикс, работающий на 50 строк, может деградировать на 5000 из-за plan-flip. Инструменты: Postgres pg_stat_statements + auto_explain.log_min_duration; MySQL performance_schema; SQL Server query store. Алерт на нестабильность плана на горячих запросах.</p>
    <p><strong>Микросервисный вариант: синхронный fan-out.</strong> Когда приложение разделено на микросервисы, N+1 поднимается по стеку. «Profile aggregator» зовёт user-service, preferences-service, posts-service, notifications-service... серийно, через HTTP/gRPC. Та же проблема; round-trip теперь сетевой вместо TCP-to-localhost-Postgres, и стоит 1-10 мс вместо 0,5 мс. Фиксы: (1) параллелизация — все вызовы concurrent, max(latencies). Просто, немедленно, не уменьшает работу. (2) BFF / aggregator — отдельный сервис, зовущий downstream и возвращающий один composed-ответ; клиент делает один вызов. (3) Push-side denormalisation — downstream-сервисы публикуют события; aggregator держит read-optimised view локально. (4) GraphQL federation — одна схема через сервисы, GraphQL gateway батчит downstream. У каждого tradeoff'ы в consistency, latency, operational complexity. Сеньорный выбор: параллелизация внутри сервисов (дёшево), BFF для product-shaped ответов (среднее), federation для org-wide consistency (дорого, но reusable).</p>
    <p><strong>Безопасность: query amplification как DoS.</strong> N+1-путь может быть attack-вектором. Если публичный эндпоинт даёт юзеру просить N items, и handler делает N+1 запросов на item, атакующий может уронить БД одним большим запросом. Реальные CVE: Strapi 2021 (CVE-2021-32820: deeply-nested filter мог амплифицировать запросы 1000x), различные GraphQL-провайдеры (циклические запросы дают экспоненциальный resolver-expansion), ранние Hasura (permission-фильтры неправильно ограничены). Митигации: query depth limits в GraphQL (apollo-validation-rules имеет graphql-depth-limit, graphql-query-complexity); per-request query budget на framework-уровне (Rails strict_loading + max queries middleware); cost analysis на GraphQL (apollo @cost директивы, Hasura automatic complexity analysis). Security framing: любой user-controlled параметр, мультиплицирующий query count, — DoS-вектор. Сеньорное код-ревью ORM-кода включает «может ли это амплифицировать запросы под hostile input».</p>
    <p><strong>Альтернатива denormalisation.</strong> Когда даже 2-3 запроса дороги, денормализуй. Counter caches (Rails counter_cache, Django annotations, Mongo aggregations) хранят derived-данные в parent (posts_count на user) вместо вычисления per-request. CQRS read models дублируют write-side данные в purpose-built read-структуры. Materialized views (Postgres, BigQuery, ClickHouse, Snowflake) пре-вычисляют joins и aggregations. Каждый убирает round-trip'ы платой за сложность на write-time. Tradeoff: staleness (read-view отстаёт от write на мс-секунды), storage (держите несколько копий derived), maintenance (derivation logic должен оставаться корректным при schema-evolution). Сеньорные команды используют denormalisation для путей, где latency SLO bound враждебен (read p99 < 50 мс на тяжёлых join'ах) или load read-dominant (10000x reads vs writes). Для balanced workload'ов ORM eager-loading достаточно.</p>
    <p><strong>История имени N+1.</strong> Термин вошёл в мейнстрим программирования около 2003-2005 с подъёмом ORM — особенно Active Record (Rails 2004) и Hibernate (Java, 2001+). Сам паттерн существовал в любой системе с lazy-loading: ORM 1990-х (TopLink, EOF), старые O-R bridges, даже hand-written JDBC-код, случайно итерирующий lazy-fetched relations. Имя «N+1» отражает worst case: 1 запрос на parent-collection, потом 1 на parent = 1 + N. К 2005-2008 паттерн в каждом Rails/Hibernate-учебнике; к 2010 — каноничный interview-вопрос. Подъём GraphQL (2015+) принёс вторую волну (resolver-per-field) и каноничный фикс (DataLoader). Форма теперь повторяется в каждом новом data-access framework'е — Prisma добавил include в 2020, каждый современный ORM поставляет. Паттерн старый; имя держится, потому что паттерн держится. Сеньоры знают, что «no N+1» — shorthand для «я валидировал query count».</p>
    <p><strong>Production-провалы.</strong> Shopify 2016 — checkout-страница случайно регрессировала к N+1 на shipping-расчётах; outage. Slack 2018 — message-search попал в deeply-nested join, взорвавший query plan под search-result fan-out. Discord 2020 — GraphQL N+1 заставил per-channel resolvers fan-out'ить на permissions-сервис; DataLoader retrofit уронил DB-нагрузку на 40%. GitHub 2021 — repo-settings грузила 200+ запросов на рендер после refactor'а, введшего lazy-loading; reverted, потом отрефакторили с proper preload. LinkedIn 2023 — feed-aggregator делал 8-way serial RPC fan-out; распараллелили, p99 упал 6x. У каждой крупной engineering-org есть N+1 retro; паттерн повторяется при введении нового слоя или ORM. Runbook-запись в каждой зрелой команде: «страница медленная → query count первым; ищи N+1 до всего остального».</p>
    <p><strong>Картина целиком.</strong> N+1 — семья фиксов для I/O-bound hot path'ов, где цена распределена по многим маленьким round-trip'ам. Диагноз — «много trip'ов, каждый быстрый»; фикс — «меньше trip'ов, батчем». Следующий фрагмент (batching) обобщает это на не-I/O контексты: когда много мелких операций доминируют, батч их. Капстоун плетёт N+1 детект + GC pressure + bundle budgets + profile-first в service-wide практику. Framework главы — profile, classify, apply right family, verify — применим и здесь: идентифицируй round-trip-цену, выбери JOIN/IN/preload/DataLoader, верифицируй падение query count, релизь diff.</p>
    <Misconception id="mc-orm-magic-2">
      <p><strong>«Добавлю индекс — починю N+1».</strong> Нет. Индексы делают отдельные запросы быстрее; N+1 — про КОЛИЧЕСТВО, не про скорость. Даже с идеальными индексами 100 запросов × 2 мс RTT = 200 мс — не меняется индексом. Фикс — меньше запросов, не быстрые запросы.</p>
