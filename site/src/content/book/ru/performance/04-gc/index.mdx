Когда фрагмент про hot paths классифицирует bottleneck как allocation-bound, семейство правок указывает сюда. GC — runtime-налог, который ваш код платит за память, запрошенную у кучи; чем больше и шумнее запрос, тем громче налог. Современные коллекторы впечатляют — sub-миллисекундные паузы рутинны в Go, JVM ZGC и .NET server GC — но ни один алгоритм не делает аллокации бесплатными. Ваш p99 формируется этим, измеряете вы это или нет.

<Crux>GC возвращает недостижимую память. Пауза, throughput и размер кучи — 3-way tradeoff. Давление аллокаций — то, чем управляешь ты.</Crux>

Сборщик мусора обменивает CPU на memory safety: проходит кучу, маркирует достижимое от корней (регистры, стеки, глобалы) и возвращает остальное. Три рычага всегда в напряжении: время паузы (как долго приложение остановлено), throughput (сколько CPU GC забирает у вашего кода), размер кучи (сколько overhead-памяти нужно коллектору для эффективной работы). Минимизировать все три нельзя; выбираешь, что важно для workload'а. Сеньоры знают, какой коллектор едет в их рантайме, какие knob'ы он выставляет, и как читать его сигнал в production.

    <p><strong>Что это одной фразой.</strong> GC освобождает память, которую ваш код аллоцировал, но больше не использует — чтобы не управлять ею вручную — и работа GC проявляется как паузы или дополнительный CPU.</p>
    <p><strong>Почему важно.</strong> Если ваш код много аллоцирует, GC много работает, и рантайм периодически останавливает программу для уборки. Паузы становятся спайками latency в сервисе; чем выше rate аллокаций, тем больше спайки.</p>
    <p><strong>Метафора.</strong> Кухня ресторана: повара (ваш код) производят грязную посуду (аллокации). Посудомойщик (GC) её моет. Если повара генерят посуду быстрее, чем мойщик чистит, посуда копится — рано или поздно кухне приходится остановиться, пока раковина не разгрузится. Современный посудомойщик (concurrent GC) моет, пока повара работают; старый (stop-the-world) заставляет всех ждать. Даже лучший посудомойщик стоит воды и электричества (CPU). Путь к быстрой кухне — не магический посудомойщик; путь — повара, переиспользующие тарелки.</p>
    <p><strong>Bea и Sven.</strong> <PersonaTag id="bea" lang="ru" /> видит, что p99 latency взлетает до 800 мс каждые несколько секунд. <PersonaTag id="sven" lang="ru" /> открывает GC-лог: паузы 600-700 мс каждые 4 секунды. Правка: TTL кэша + лимит размера. Память ограничена; GC перестаёт thrash'ить; latency стабилизируется.</p>

    <p><strong>Mark and sweep, основа.</strong> Каждый tracing GC следует одному скелету. Кратко паузим приложение, собираем GC-корни: активные CPU-регистры, стеки каждого потока, глобальные переменные, JNI-handles. От этих корней проходим граф ссылок — каждый достижимый объект «живой»; все остальные — «мусор». Маркируем живые (флип бита в заголовке или в side-table). После marking — sweep: проходим кучу, возвращаем память немаркированных объектов во free-list. Варианты compact'ят (двигают живые вместе, убирая фрагментацию) и используют bump-pointer аллокацию для быстрых последующих allocs. Наивный алгоритм — «stop-the-world mark-and-sweep» — паузим всё, маркируем, sweep'им, возобновляем. Общая пауза растёт с размером кучи: куча 32 ГБ может занять секунды, что неприемлемо для latency-чувствительного сервиса. Каждый современный GC — вариант, уменьшающий эту паузу.</p>
    <p><strong>Generational hypothesis.</strong> Самое важное эмпирическое наблюдение в GC-исследовании: большинство объектов умирают молодыми. Приходит запрос, аллоцирует кучу временных объектов (распарсенное тело, промежуточные строки, response builders), отдаёт ответ, отбрасывает их. Выжившие — долгоживущие (кэши, конфигурация, пулы соединений). Generational-коллекторы разделяют кучу на young generation (маленькая, собирается часто) и old generation (большая, собирается редко). Аллокации идут в young; выжившие «промоутятся» в old после нескольких циклов. Young-gen collection дешева — она маленькая; old-gen — редка, потому что большинство объектов туда не доживает. Рантаймы, реализующие generational hypothesis: V8 (Scavenger для young, Mark-Compact для old), JVM Parallel/G1/Shenandoah, .NET (gen 0, 1, 2). Контрпример: GC Go — non-generational (одна куча, concurrent tri-color), принимающий более высокую per-cycle цену за упрощённый рантайм и равномерные паузы. Гипотеза всё равно информирует production: даже в Go код, аллоцирующий короткоживущие объекты в тугих циклах, создаёт больше GC-pressure, чем долгоживущее состояние. Рычаг тот же: уменьшить короткоживущие аллокации.</p>
    <p><strong>Concurrent и incremental collection.</strong> Чтобы получить паузы ниже 10 мс на multi-GB кучах, marking должен происходить ПОКА приложение работает. Это concurrent marking: GC бежит как параллельный поток, проходя граф объектов рядом с mutator-потоками (приложение). Челлендж: приложение может изменять ссылки во время marking'а («mutation»), поэтому GC нужен write barrier — небольшой код, выполняющийся при каждой записи ссылки, который сообщает GC о новой ссылке, чтобы он ничего не пропустил. Варианты: snapshot-at-the-beginning (SATB, в G1, Shenandoah, ZGC) трактует все ссылки на GC-start как живые и трекает удаления; incremental-update (в CMS, классический V8 mark-compact) трекает вставки. У каждого свои cost-quality tradeoff'ы. Concurrent GC обменивают память (write barrier cost ~2-10% CPU, плюс snapshot/remembered-set space) на короткие паузы. Современные lowest-pause коллекторы — ZGC, Shenandoah, .NET server GC — попадают в sub-миллисекундные STW-фазы даже на multi-сотни-ГБ кучах.</p>
    <p><strong>Тур по рантаймам.</strong> Go: concurrent tri-color non-generational mark-sweep, без compaction (аллокатор — tcmalloc-вариант). Триггерится rate'ом аллокаций; pacer держит STW-паузы под 1 мс. GOGC env var управляет целью роста кучи (default 100% = удвоить кучу до следующего GC); GOMEMLIMIT (1.19+, soft cap) позволяет ограничить память. JVM (современная): G1 default для большинства серверов, region-based, generational с concurrent marking'ом, паузы 10-50 мс типично; ZGC (JEP 333, JEP 377) целится в sub-мс паузы на кучах до 16 ТБ, использует colored pointers + load barriers; Shenandoah (Red Hat) похожие цели с Brooks pointers. Тюнится через -XX:MaxGCPauseMillis (G1) и heap-size флаги. V8: generational Scavenger для young (semi-space copying), Mark-Compact для old, проект Orinoco добавил concurrent marking + parallel compaction (2017+), чтобы попадать в ≤10 мс паузы на типичных web-workload'ах; куча капается per-isolate (default ~1.5 ГБ в Node, конфигурируется через --max-old-space-size). .NET: workstation/server GC, generational (gen 0/1/2 + LOH), background concurrent marking; тюнится через GCSettings.LatencyMode и runtime knobs. CPython: reference counting (отбрасывает объект при refcount=0, без большой паузы) + cycle collector (разруливает циклы ссылок через tracing); GIL сериализует мутацию, но ref-count'ы стоят ~10-20% throughput. GC каждого рантайма отражает культуру языка и целевые workload'ы.</p>
    <p><strong>Three-way tradeoff: пауза, throughput, куча.</strong> Каждый коллектор выбирает два из трёх. Stop-the-world parallel GC (JVM ParallelGC): отличный throughput, низкая память, ужасная пауза. ZGC: отличная пауза, OK throughput, больше памяти. G1: сбалансирован по всем трём, без экстремов. Concurrent коллектор Go: отличная пауза, чуть хуже throughput, OK память. Tradeoff фундаментален: короткие паузы требуют concurrent-работы и write barriers, стоящих CPU и памяти; throughput-focused коллекторы батчат всё в один STW-проход. Выбор GC, таким образом, — вопрос workload'а. Batch-сервисы, не заботящиеся о latency, хотят throughput → ParallelGC. Latency-чувствительные интерактивные сервисы хотят короткие паузы → ZGC, Shenandoah, GC Go. Memory-constrained сервисы хотят компактности → меньше выборов, часто ручной тюнинг или принимаем более длинные паузы. Неверный выбор может стоить 30-50% throughput или 10x p99 latency.</p>
    <p><strong>Давление аллокаций как leading indicator.</strong> Если ваш сервис аллоцирует 1 ГБ/с, GC будет занят независимо от того, какой коллектор едет. Давление аллокаций — upstream-причина; время паузы — симптом. Уменьшение давления аллокаций имеет unbounded upside; тюнинг GC — bounded (оптимизируете цену работы; работа никуда не уходит). Сеньорный паттерн: когда GC широк в профиле, дальше смотри allocation-профиль. Самый широкий leaf в alloc-профиле — ваша цель. Правки (по приоритету): (1) устранить аллокацию полностью (in-place мутация, struct-of-arrays); (2) пулить/переиспользовать (sync.Pool в Go, object pools в Java/JS); (3) escape analysis — пусть компилятор стек-аллоцирует вместо heap (работает в Go, .NET, частично в JVM с escape-анализом C2); (4) уменьшить аллокацию (меньший struct, меньший buffer, меньшая строка); (5) убрать аллокацию с hot path (вычислить один раз, переиспользовать).</p>
    <p><strong>Pacing и soft memory limit.</strong> Современные коллекторы pacing'ятся: предсказывают, когда нужно стартовать следующий GC, чтобы успеть до заполнения кучи. Pacer Go (переписан в 1.18, уточнён в 1.20 с GOMEMLIMIT) смешивает сигналы CPU-usage и роста кучи. JVM G1 pause-time goal направляет pacer на удержание пауз под целевой. Правильная установка важна: в Go GOGC=100 значит GC запускается при удвоении кучи с последнего цикла — нормально для лёгких workload'ов, дорого для high-allocation сервисов. GOMEMLIMIT (soft cap) позволяет сказать «не расти больше 8 ГиБ» — коллектор становится агрессивнее, приближаясь к лимиту, меняя throughput на соблюдение cap'а. В JVM -XX:MaxGCPauseMillis=50 говорит G1 гнаться за 50 мс паузами; задание слишком низкого вынуждает слишком частую коллекцию. Сеньорный тюнинг: мониторь распределение пауз + rate аллокаций, установи GOMEMLIMIT или max-heap на фактический bound workload'а + 25% буфер, оставь default pacer-параметры, если нет конкретной причины.</p>
    <p><strong>Форма кучи и различие live-set.</strong> Total heap (RSS) — не то же, что live set (достижимые байты). RSS 4 ГБ может иметь только 800 МБ live; остальные 3,2 ГБ — мусор, ждущий следующего цикла, или фрагментация, или зарезервированные runtime'ом arena. Live-set гонит цену GC: время marking'а пропорционально живым байтам, не total heap. Коллекторы выставляют live-set по-разному: runtime.MemStats.HeapLive Go (с 1.20), MemoryUsage.getUsed() JVM после GC, getHeapStatistics().used_heap_size V8 после full GC. Сеньорный тюнинг таргетит live-set, не RSS — размер кучи в ~1,5-2x live-set — каноничное правило. Меньшие соотношения триггерят частый GC; бо́льшие — тратят память без пропорционального latency-выигрыша. Workload'ы с большим колеблющимся live-set (кэши, in-memory агрегации) нуждаются в верхней границе; маленькие steady-state — дешевле.</p>
    <p><strong>Observability аллокаций по языкам.</strong> Без per-runtime инструментирования диагностируешь вслепую. Go: пакет runtime/metrics + /debug/pprof/allocs scrape каждые 30с. JVM: JFR ObjectAllocationInNewTLAB events + async-profiler -e alloc; Micrometer jvm_gc_pause_seconds и jvm_gc_memory_allocated_bytes_total в Prometheus. V8/Node: --trace-gc + v8.getHeapStatistics() polling каждые 15с; PerformanceObserver perf_hooks для типа 'gc' захватывает каждую паузу. .NET: GC.GetTotalAllocatedBytes() rate + dotnet-counters live-readout. По всем паттерн алерта один: alloc rate, трендящийся > service-specific порог (типично 300-500 МБ/с/ядро) >5 минут. Leading-indicator дашборд пары alloc rate с p99 latency на одном графике — когда расходятся, GC — подозреваемый; когда коррелируют, уменьшение аллокаций — следующий фикс.</p>
    <p><strong>Объект-pooling: когда работает и когда нет.</strong> sync.Pool в Go, Apache Commons Pool в Java, объект-пулы в .NET — паттерн переиспользования аллокаций для уменьшения GC pressure. Работает, когда объекты дорогие в создании и используются короткое время в hot path: bytes.Buffer'ы, JSON-encoder'ы, regexp-объекты, scratch slice'ы. Не работает или вредит, когда: объекты дешёвые в создании (выигрыш меньше overhead'а пула), объекты долго живут (пул не освобождает память, держит её зря), pooling вызывает thread-coordination overhead больше allocation savings. Сеньорное правило: pool только то, что профиль показал как hot allocation. Не делай pool'инг превентивно. sync.Pool Go хорош тем, что GC может drain'ить пул между циклами — память не теряется навсегда; объект-пулы JVM/.NET держат память до явного освобождения. Дополнительный риск: race-condition'ы при возврате объекта в пул — если поток A вернул в пул, а поток B уже его взял до того, как A освободил state, два потока работают с одним объектом одновременно. Защита: чистить state при Get(), не при Put(); проверять, что объект не shared между goroutine'ами/потоками. sync.Pool Go даёт гарантию thread-safe Put/Get, но не state-cleanup — это ответственность вызывающего кода. В JVM/.NET pool-библиотеки часто включают reset-хуки. Производственный паттерн: pool + benchmark до/после; если allocation profile не показал заметного снижения, откатить pool — он добавляет сложность без выигрыша. Pooling — оптимизация по данным, не по интуиции. Третий критерий: pool'ить только то, чьё создание входит в топ-5 alloc-профиля; для всего остального overhead pool'а перевешивает выигрыш. Эмпирически в Go-сервисах pooling даёт измеримый выигрыш только для bytes.Buffer'ов на JSON-encoder'ах, scratch-slice'ов в hot loop'ах и крупных протобуф-сообщений в high-RPS RPC-обработчиках; за пределами этих категорий sync.Pool обычно усложняет код без выигрыша. В JVM похожая картина: ByteBuffer-пулы в Netty/gRPC, регекспы и форматтеры дат окупают pool'инг; большинство POJO — нет, потому что allocation-цена объекта сопоставима с управлением пулом.</p>

Измерение в production: per-runtime knobs. Go: runtime.MemStats.Mallocs (count аллокаций) и TotalAlloc (cumulative bytes), экспонируется через expvar/Prometheus; rate изменения — rate аллокаций. JVM: jstat -gcutil, или JFR ObjectAllocationInNewTLAB events, или async-profiler -e alloc. V8: --trace-gc + heap-snapshot delta по времени; process.memoryUsage().heapUsed Node в сочетании с HeapStatistics. .NET: PerfView allocation events или runtime counters через dotnet-counters. Production-grade observability стеки (Datadog APM, New Relic, Honeycomb) отгружают per-service alloc-rate дашборды.     <p><strong>Tri-color marking и write barrier.</strong> Tri-color абстракция (Dijkstra 1978) — формальная основа concurrent GC. Объекты классифицируются как white (ещё не посещён, кандидат на collection), grey (посещён, но children не просканированы), black (посещён, все children просканированы). Marking движется, перенося grey в black, маркируя white-детей grey. Инвариант: black-объект никогда не ссылается на white напрямую. Concurrent marking рискует нарушить инвариант, когда mutator записывает ссылку с black на white после того, как black был просканирован. Write barrier поддерживает инвариант одним из двух способов: (а) snapshot-at-the-beginning (SATB): барьер маркирует СТАРУЮ ссылку (становящуюся мусором), так что коллектор трактует её как живую этот цикл. Используется G1, Shenandoah, ZGC. (б) Incremental-update (Dijkstra-style): барьер маркирует НОВУЮ ссылку, так что она не пропускается. Используется CMS, классическим V8 mark-compact. SATB более консервативен (держит чуть больше мусора один цикл дольше), но даёт коллектору более сильные гарантии завершения marking'а. Go использует гибридный Yuasa-style SATB барьер. Цена барьера — ~2-10% CPU overhead, платится на каждую запись ссылки — цена concurrent marking'а. Сеньоры должны знать, какой барьер их рантайм использует; это влияет на паттерны аллокаций и write-heavy hot paths.</p>
    <p><strong>Pacer redesign в Go.</strong> Переписывание GC pacer в Go 1.18 (proposal 44167, автор Michael Knyszek) заменило эвристику на closed-loop control system. Старый pacer оценивал, когда стартовать следующий цикл, чтобы он успевал до удвоения кучи; имел нестабильность на высоких rate'ах и принимал плохие решения на cgo-heavy workload'ах. Новый pacer использует PI controller (proportional-integral) на сигналах heap-growth и CPU-utilisation плюс soft cap GOMEMLIMIT (1.19+). Когда вы задаёте GOMEMLIMIT=8GiB, pacer затягивает GC, чтобы не превысить cap, даже ценой большей CPU в GC. Redesign снизил вариативность пауз Go на ~50% на реальных workload'ах и сделал GOMEMLIMIT жизнеспособной заменой ручному GOGC. Сеньоры, гоняющие Go в контейнерах, должны установить GOMEMLIMIT в ~90% memory limit контейнера и дать pacer'у сделать остальное. GOGC=off опасно (имеет смысл только для memory-bounded batch-задач, освобождающих память через выход процесса). Чтение: GopherCon-доклады Knyszek, особенно 2022 о дизайне GOMEMLIMIT в 1.19.</p>
    <p><strong>ZGC и трюк colored pointer.</strong> ZGC (JEP 333, JDK 11+; production-ready в JDK 15) добивается sub-мс пауз на multi-TB кучах через load barriers и colored pointers. «Colored pointer» упаковывает метаданные в сам 64-битный указатель: ZGC использует биты 0-41 на адрес (heap max ~4 ТБ), биты 42-45 — состояние marking'а («good» цвета vs «bad»). Каждая загрузка из кучи идёт через барьер (несколько лишних инструкций), проверяющий цвет; если «bad» (relocated или pending), барьер триггерит slow path для обновления указателя. Поскольку барьер исполняется inline на каждой load, приложение участвует в работе GC в крошечных инкрементах вместо ожидания больших STW-фаз. Результат: marking, relocation, reference processing — всё concurrent с приложением; STW-фазы ограничены root scanning (sub-мс даже на огромных кучах). Tradeoff — CPU overhead (load barriers стоят ~5-15% CPU) и чуть больше памяти (color metadata + multi-mapped кучи для быстрой relocation). Generational ZGC (JEP 439, JDK 21+) добавляет young generation, делая ZGC конкурентным и по throughput. Shenandoah (Red Hat) использует Brooks pointers (forwarding pointers в заголовках объектов) для похожего эффекта с другими tradeoff'ами.</p>
    <p><strong>V8 Orinoco и инкрементальная работа.</strong> Проект Orinoco V8 (старт 2017) перевёл GC V8 с в основном STW на в основном concurrent. Ключевые куски: concurrent marking (mark-фаза бежит на background-потоке параллельно с JS-исполнением; write barriers поддерживают консистентность), parallel compaction (несколько потоков двигают объекты параллельно в STW-фазе), young-gen scavenger parallelism (несколько потоков эвакуируют young heap параллельно). Результат: типовые web-workload'ы видят паузы ≤10 мс, с большей частью marking'а, скрытой в фоне. Memory overhead: ~5-15% на marking infrastructure (write barriers, marking worklist). Node.js наследует эти выигрыши по умолчанию; тюнинг через --max-old-space-size и --max-semi-space-size. Команда V8 отгружает дальнейшие уточнения (concurrent allocation, lazy resource reclamation, эволюция Orinoco в MinorMC для minor GC). Команды, пишущие high-throughput Node-сервисы, должны отслеживать V8 release notes по Orinoco — крупные изменения могут существенно менять характеристики производительности между версиями Node.</p>
    <p><strong>Production observability для GC.</strong> Per-runtime телеметрия на дашборды. Go: runtime.ReadMemStats выставляет PauseTotalNs (cumulative pause), NumGC (count циклов), HeapAlloc (текущая куча), Mallocs/Frees (rate); экспонируется через expvar или Prometheus client. GODEBUG=gctrace=1 логирует каждый цикл в stderr — полезно в dev, выключаем в prod. JVM: -Xlog:gc*:file=gc.log:time,uptime,level,tags ротирует GC-логи с полной детализацией; JFR захватывает GC events для offline-анализа; Micrometer/Prometheus JVM metrics экспонируют gc.pause histogram, gc.memory.allocated rate. V8/Node: process.memoryUsage().heapUsed, v8.getHeapStatistics(), node --trace-gc для verbose-логирования в stderr; perf_hooks.PerformanceObserver с типом 'gc' захватывает события пауз программно. .NET: GC.GetTotalAllocatedBytes() + EventCounters для событий GC. Сеньорный паттерн дашборда: alloc-rate по времени + pause-duration histogram + GC CPU share + heap-size growth — эти четыре панели диагностируют большинство GC-driven latency-проблем за пять минут. Привязка к SLO burns: регрессии GC-пауз — leading indicator для tail-latency SLO нарушений.</p>
    <p><strong>Безопасность: allocation-driven DoS и heap exhaustion.</strong> Атакующий, заставляющий сервер аллоцировать большие объекты, может довести его до OOM или crippling GC overhead. Векторы: oversized request bodies (распарсить 100 МБ JSON, чтобы найти одно плохое поле), unbounded query results (вернуть все строки, когда ожидалась пагинация), regex bombs (backtracking аллоцирует промежуточное состояние), zip-bomb-style декомпрессии (маленький вход → огромное расширение). Митигации: enforce'ить размер тел запросов на gateway (например, 1 МБ default, больше на специфичных эндпоинтах с явным auth); ограничить размер query-результатов server-side; использовать RE2-based regex-движки без backtracking; валидировать compression ratio. Heap-exhaustion DoS в OWASP Top 10 server-side векторов. Production-дисциплина: каждый allocation site, масштабирующийся с attacker-controlled input, получает bound. Linux-ядро использует kmem_cache limits + cgroup memory caps; application-код должен зеркалить: per-request memory tracking с hard limits и явной обработкой overflow.</p>
    <p><strong>Edge case'ы.</strong> Finalizer storms: регистрация многих объектов с финализаторами (Java Object.finalize, runtime.SetFinalizer Go, JS FinalizationRegistry) требует от GC будить отдельные потоки для их запуска; burst финализируемых в тугом цикле может стопорить коллектор, пока finalizer queue не разгрузится. Правка: избегать финализаторов; использовать явные close() / Disposable. Pinned objects: объекты, не способные двигаться (DMA-буферы, JNI pinned arrays, V8 typed-array external memory), не дают коллектору compact'ить вокруг них. Leak pinned-объектов фрагментирует кучу, вызывает OOM на низкой утилизации. Правка: явный lifecycle для pinning'а, аудит JNI / native interop. Reference loops: циклы между объектами с custom destruction (WeakRef-цепочки в JS, mutual references в Python) могут предотвращать reclamation даже с cycle collector'ами, если loop включает финализаторы. Правка: WeakRef где уместно; избегать mutual strong references. У каждого edge case рантайм-специфичная сигнатура; сеньоры трекают их как «GC tail bugs» и добавляют в runbook'и.</p>
    <p><strong>История: 1960 → 2024 в пять шагов.</strong> 1960: Lisp McCarthy вводит mark-sweep — первый software GC, batch и медленный. 1970: copying collector Cheney — делит кучу, копирует живых, free — bump-pointer (всё ещё влияет на V8 Scavenger). 1984: статья Ungar про generational hypothesis (Berkeley Smalltalk) — большинство объектов умирают молодыми, эксплуатируй. 1990-е: incremental и concurrent GC (Baker, Yuasa, абстрактный framework Dijkstra) — паузы падают с секунд до десятков мс. 2010-е: low-pause concurrent коллекторы (G1, ZGC, Shenandoah, tri-color Go, V8 Orinoco) — sub-мс паузы на multi-ГБ кучах. 2020-е: closed-loop pacers (Go), generational интеграция в ZGC, energy/cost-aware тюнинг (cloud workloads). Каждое поколение снижало pause cost на порядок. Следующий фронтьер: NUMA-aware GC, persistent-memory-aware GC, GPU-memory-aware GC для ML-workload'ов. Сеньоры знают линию достаточно, чтобы читать документацию современного коллектора и узнавать, чьи tradeoff'ы какого поколения описывают доки.</p>
    <p><strong>Production-истории.</strong> Discord 2020: tail latency chat-сервиса — GC паузы; переход на улучшенный pacer Go 1.14 уронил p99 на 40%. LinkedIn 2018: переключение большого Kafka-кластера с CMS на G1, p99 latency упал 25-50%, operator-нагрузка снизилась. Cloudflare 2020: V8 Worker isolate регрессировал из-за Orinoco-апдейта, увеличившего background marking; откатили. Twitter 2019: finalizer storm вызвал OOM в JVM-сервисе; заменили явным Closeable. Netflix 2022: задеплоили ZGC по Cassandra-флоту; p99 read latency улучшилось 5-10x без application-кода. Stripe 2023: Go-сервис впервые достиг GOMEMLIMIT во время спайка трафика; pacer удержал память, но throughput упал 15% — диагностировали и починили уменьшением аллокаций на hot path. Паттерн: у каждого крупного production-сервиса есть GC-история, часто не одна. Сеньоры исходят из предположения, что GC будет вопросом; цель — знать, когда он ответ.</p>
    <p><strong>Картина целиком.</strong> GC — runtime-механизм, стоящий за allocation-bound hot path'ами из прошлого фрагмента. Уменьшение давления аллокаций — долговременный рычаг; тюнинг коллектора — второпорядковая оптимизация. Следующий фрагмент (N+1) атакует другой класс hot path'ов — повторное I/O — но тот же паттерн применим: диагностируй root cause, уменьши работу, докажи правку diff'ом профиля. Прогрессия главы продолжается: профилируй → классифицируй → применяй правильную семью правок → верифицируй. GC — семья для allocation-bound; N+1 — для повторного I/O; batching — для syscall-bound; bundle budgets — для client-side нагрузки. Капстоун плетёт их.</p>
    <Misconception id="mc-tune-first">
