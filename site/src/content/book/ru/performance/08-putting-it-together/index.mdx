Семь фрагментов собрали toolkit: profile-first называет bottleneck, hot-paths классифицирует, GC обрабатывает allocation pressure, N+1 — round-trip-storm, cache vs big-O — memory locality, batching амортизирует любую фикс-цену-per-call, bundle budgets ограничивают client-side байты. Капстоун плетёт их в service-wide практику. Не чек-лист — дисциплина: measure, classify, apply right family, verify, enforce, repeat.

<Crux>Performance — цикл, не проект. Profile, classify, fix, verify, enforce. Фрагменты — toolkit; цикл делает их работающими.</Crux>

Сеньорный инженер использует все семь fluidly. SLO burn fires; он тянется к профилю (01); flame graph показывает hotspot; классифицирует (02) как allocation-bound, I/O-bound или client-side; нужная семья фикса (03-07) применяется. Потом CI gate enforces bound, чтобы next deploy не регрессировал. Каждый фрагмент reusable; цикл делает performance property команды, а не one-time tuning effort, который decays.

    <p><strong>Что это одной фразой.</strong> Performance — не один фикс, а повторяющийся цикл: измерь, найди bottleneck, применить правильный фикс, верифицируй, защити от регрессий.</p>
    <p><strong>Почему важно.</strong> Команды без цикла пишут быстрый код раз, потом медленно скатываются. Команды с циклом держатся быстрыми год за годом.</p>
    <p><strong>Метафора.</strong> Performance — как уборка кухни, а не покраска комнаты. Покрасил раз — стоит. Кухня грязнится снова и снова, нужно мыть continuously. Каждый фрагмент — инструмент: profiler (свет), hot-paths (метла), GC (посудомойка), N+1 (компактор), batcher (рейка для тарелок), bundle budget (лимит полки).     <p><strong>Unified loop.</strong> Каждое perf-расследование следует той же структуре независимо от того, где bottleneck. Шаг 1 — observe: симптом (SLO burn, RUM regression, user complaint, dashboard alert) говорит, что-то не так, но не что. Шаг 2 — profile: capture данные подходящие симптому — server-side flame graph для CPU spikes, off-CPU для latency spikes с low CPU, allocation profile для memory growth, network waterfall для slow page loads, bundle analyzer для client bloat. Шаг 3 — classify: назови bottleneck по семье. CPU-algorithmic, allocation-bound, cache-bound (03-cache-vs-bigo), lock-bound, I/O-bound (N+1), syscall-bound (batching), JIT-deopt, client-bundle-bound. У каждой семьи known техники. Шаг 4 — predict: Амдал предскажет улучшение headline metric. Если предсказание ниже SLO bound — не тот hotspot; обратно к шагу 2. Шаг 5 — apply fix из playbook'а семьи. Шаг 6 — verify: пере-профиль; локальный hotspot сжался И headline улучшилось. Шаг 7 — enforce: CI gate, alert, runbook entry. Шаг 8 — move on: найти следующий bottleneck. Цикл никогда не кончается; только мигрирует между слоями.</p>
    <p><strong>Cross-layer reasoning.</strong> Реальный bottleneck редко в одном слое. Slow checkout: 30% JS bundle parse, 20% backend N+1, 15% GC backend, 35% backend compute. 10x на одном даёт только Amdahl-bounded wins на total. Сеньорный workflow атакует параллельно: client-team — bundle, backend — queries + allocations, infra — runtime. Compound effect — победа: 2x на каждом из трёх слоёв = 8x total. Без cross-layer reasoning команды stall: «мы уже оптимизировали свою часть» становится ответом, когда проблема в другой команде. Framework главы даёт каждой команде vocabulary говорить о своём слое способом, понятным другим командам.</p>
    <p><strong>Compounding loop.</strong> Выигрыши одного фрагмента часто включают выигрыши другого. Уменьшение аллокаций (04) уменьшает GC pause variability — предыдущий N+1 fix (05) держит p99 steadier. Code-splitting bundle (07) уменьшает parse-execute, lowering main-thread blocking, improving INP — incidentally делает Web Workers полезнее (main thread свободнее). Batching (06) уменьшает syscall transitions, освобождая CPU для прикладной работы. Никто из фрагментов независим; они composing. Сеньор замечает, когда фикс одного bottleneck'а unlocks easier wins другого. Flame-graph diff после deploy показывает: фикс GC-пути не просто сжимает frame, а shift'ит time spent, часто revealing следующую цель.</p>
    <p><strong>SLO и budget abstraction.</strong> Service Level Objectives квантифицируют «fast enough». Per-service: «p99 под 200 мс, 99% времени, на 30 днях». Error budget (1% за 30 дней = 7,2 часа допустимой degradation) говорит, сколько риска можно взять. Perf-фиксы тратят или экономят budget — fix, dropping p99 с 500 мс до 180 мс, создаёт room для новых фич. Bundle budget (07), query budget (05), allocation budget (04) — subsidiary budgets, roll up to SLO. Когда per-route/per-component budgets met — headline SLO met. Когда sub-budgets drift — SLO первый страдает. Зрелые команды ladder budgets: SLO at top, route/page в середине, per-feature at bottom — каждый PR accountable to closest budget.</p>
    <p><strong>Observability стек: четыре сигнала плюс profiling.</strong> Production-grade нужен пять data streams. (1) Metrics (Prometheus + Grafana): p50/p99 latency, throughput, error rate, CPU/memory. (2) Logs (Loki/ELK): structured, queryable, joinable с metrics. (3) Traces (Tempo/Jaeger/Datadog APM): per-request waterfall. (4) Profiles (Pyroscope/Parca/Datadog Profiling): continuous CPU + allocation, joinable с traces. (5) RUM (Sentry/Datadog RUM): CWV с real user devices. Unified dashboard на сеньорном уровне показывает все пять в одном view, time-aligned, чтобы SLO burn можно было drill from metric → trace → span → profile → code в под пять минут.</p>
    <p><strong>Pre-merge gates: ловить до релиза.</strong> Самый дешёвый fix — тот, что не доходит до production. PR-time gates: bundle-size check (07) fail'ит PR'ы over per-route limit; query-count gate (05) fail'ит PR'ы с N+1; allocation-diff gate (04) fail'ит PR'ы с регрессией alloc rate; load-test diff (01) fail'ит PR'ы с p99 regression на critical paths. Каждый gate в CI, 1-5 минут, fires per PR. Кумулятивно: 90%+ would-be регрессий caught before merge. Оставшиеся 10% — RUM/alerts after deploy и reverted в часах. Сеньорный staffing: small platform team строит и поддерживает gates; product teams own routes и отвечают на gate failures фиксами (не disable'ами). Disabling gate требует explicit sign-off и exit plan.</p>
    <p><strong>Performance как leading indicator.</strong> Perf-метрики часто регрессируют до функциональных. Query, занимающий 200 мс вместо 50, может ещё корректно возвращать — но в следующем месяце time out'нет под нагрузкой и станет outage. Bundle, растущий 10% в месяц, может ещё грузиться сегодня — но в следующем году mid-range mobile не сможет render. Сеньорные команды трактуют perf-регрессии как outage precursors: расследовать сразу, не после SLO burn. Каждый release ships с perf review: (a) bundle delta, (b) p99 delta, (c) allocation rate delta, (d) CWV delta. Review в pre-deploy gates ловит slide до того, как станет следующим incident'ом.</p>
    <p><strong>Toil reduction через цикл.</strong> SRE framework «toil reduction» спрашивает: какая manual work повторяется, автоматизируема, растёт со scale? Perf firefighting — классический toil — pageout в 3 AM, manual triage, fix, повтор через 3 месяца. Цикл конвертирует toil в инфраструктуру. CI gates бегут каждый PR с zero human effort. RUM alerts включают trace links, on-call прыгает на ответ. Runbook entries делают новые on-call effective на день 1. Toil ratio (доля engineer time на toil vs project work) — сеньорный leading indicator: здоровая команда держит toil под 50% per SRE; многие команды сидят 70-80% pre-discipline, 20-30% post. Инвестиция в observability + gates + runbooks окупается не только меньшим числом incidents, но и reclaimed engineer-time.</p>
    <p><strong>Composability семи фрагментов.</strong> Toolkit — не чек-лист, а vocabulary. Каждый фрагмент именует класс bottleneck и семью фиксов. Сеньор, читая профиль, видит паттерны: «выглядит как piece-02 hot-path classification, specifically allocation-bound (04) с гарниром N+1 (05)». Vocabulary позволяет инженерам разных специальностей (frontend, backend, infra, SRE) говорить о complex multi-layer проблеме без потери precision. Без shared vocabulary разговоры скатываются в «backend медленный» / «нет, frontend медленный»; с ним — «backend имеет 30% allocation-bound hotspot в auth-middleware, frontend имеет 200 КБ bundle regression на dashboard — ни один отдельно не объясняет p99, но вместе объясняют». Composability — то, что делает семи-piece toolkit сеньор-multiplier, а не junior cookbook.</p>
    <p><strong>Compounding effect over time.</strong> Perf-дисциплина compound'ится. Год 1: инвестиция в toolkit + loop. Много foundational work, modest visible wins. Год 2: gates ловят регрессии at PR time; mean-time-to-detect падает; engineering culture сдвигается. Год 3: performance table stakes; new hires onboard в loop; команда известна fast software; competitive advantage compounds. Математика: каждый год's регрессии caught at PR time would have cost 5-20 engineer-days в production firefighting; over 3 years — hundreds engineer-days saved. Multiply by infrastructure savings (каждый 2x throughput halves bill), plus reduced churn (fast software — recruiting/retention advantage). Full ROI of perf discipline hard to measure в single quarter, но plainly visible across years. Команды, начавшие эту дисциплину 5 лет назад, сейчас shipping software, которое competitors не могут match по perceived quality.</p>
    <p><strong>Распределение pieces по обязанностям ролям.</strong> На зрелой platform каждая роль владеет частью toolkit'а. Frontend engineers: pieces 02 + 07 (hot paths + bundle budgets). Backend engineers: pieces 02 + 04 + 05 + 06 (hot paths + GC + N+1 + batching). SREs / DevOps: piece 01 (profile-first инфраструктура), плюс enforcement gates. Platform engineers: piece 03 (cache vs big-O — фундаментальные паттерны), плюс observability stack. Performance specialists: вся семёрка + meta-практика. Это позволяет масштабировать дисциплину без одной команды-bottleneck'а: каждая роль владеет своими фрагментами, общается с другими через общий vocabulary, и платформа инвестирует в shared infrastructure. Без распределения performance становится либо «работа одной героической команды», которая выгорает, либо «никто не отвечает», что приводит к деградации. С распределением performance становится infrastructure, как security или reliability. Каждый инженер знает свою часть toolkit'а; каждый PR проходит через знакомые gates; каждое incident retro закрывается новой gate'ой в своей семье. Это масштабируемая модель — работает для команды из 10 инженеров и для организации из 1000. Ключ — что инвестиция в shared infrastructure (observability, gates, runbooks) делается раз и используется бесконечно; индивидуальные команды учат только свои пиллары, не всё сразу.</p>
    <p><strong>Контр-индикаторы зрелости.</strong> Несколько симптомов показывают, что у команды нет performance-дисциплины. (1) Регрессии находят пользователи. Если первая весточка о slowdown — Twitter-жалоба или customer support ticket, observability отсутствует. У зрелой команды alerts срабатывают до того, как пользователь замечает. (2) On-call тратит часы на root cause. Если диагноз medium-severity perf-инцидента занимает больше 30 минут — observability stack неполный или runbook не существует. (3) То же class регрессии возвращается каждые 3-6 месяцев. Если bundle vs queries vs GC проблемы циклятся — enforcement gates отсутствуют. (4) Никто не знает SLO. Если команда не может назвать p99-цель для своих критических endpoints, performance не приоритезируется на product-уровне. (5) Perf-работа всегда «после фич». Если performance investment откладывается каждый sprint в пользу features, дисциплины нет — есть intent, который никогда не происходит. Если узнаёшь 2+ из 5, performance-дисциплина либо отсутствует, либо в зачаточном состоянии — первая инвестиция должна быть в её построение.</p>
    <p><strong>Меры успеха.</strong> Зрелую performance-программу можно измерить четырьмя количественными метриками: (а) Pre-merge regression catch rate — fraction регрессий, пойманных CI gate до merge. Target 90%+; меньше 70% значит CI gates недостаточны. (б) Median time-to-root-cause — от alert до named function/component. Target &lt; 15 минут; больше часа значит observability неполная. (в) SLO compliance — fraction времени, когда сервис в SLO. Target 99%+ для критических сервисов. (г) Engineer-time on perf as steady-state — % engineer-time на performance работу. Healthy: 5-10%. Crisis mode (firefighting): 20-40%. Если crisis mode persistent, программа в reactive режиме, не proactive. Эти четыре метрики, треккаемые ежеквартально, дают объективную картину здоровья дисциплины.     <p><strong>Unified observability stack в деталях.</strong> Production-grade perf-practice в 2026 ships пять интегрированных data streams. (1) Metrics: Prometheus или commercial equivalent. Per-endpoint p50/p95/p99/p99,9 latency, throughput, error rate, CPU/memory/network. Refresh 15-60 секунд. Retention 13 месяцев для trend analysis. (2) Logs: Loki, ELK, Splunk, Datadog Logs. Structured (JSON), correlated с trace-id. Retention 7-90 дней. (3) Traces: Tempo, Jaeger, Datadog APM, Honeycomb. Per-request waterfall с span attributes. Tail sampling. Joined to logs и profiles через trace-id. (4) Profiles: Pyroscope, Parca, Polar Signals, Datadog Profiling. Continuous CPU + allocation. Tagged с trace-id at sample time. (5) RUM: Sentry Browser, Datadog RUM, Cloudflare Web Analytics. CWV + page metrics + interaction breakdowns. Сеньорный dashboard ties них вместе: SLO burn alert links to Tempo trace slow request, which links to Pyroscope profile burning minutes, which links to source code hot function. On-call diagnostic time drops с часов до минут. OpenTelemetry standardises wire formats; vendors implement OTel ingestion, team может swap pieces без потери данных.</p>
    <p><strong>OpenTelemetry's role.</strong> OTel (open-source observability standard CNCF) defines: (a) wire format (OTLP) для metrics, logs, traces, profiles, (b) SDK для instrumenting applications, (c) Collector pipeline. Production teams: instrument с OTel SDKs в каждом service; send all telemetry to Collector; Collector routes к backends. Decouples application code от vendor choices — switching с Datadog на self-hosted stack — one config change. Profile signal (RFC-track 2024-2026) brings continuous profiling в OTel standard. Сеньоры adopt OTel для new services by default; older services migrate gradually. Investment pays off when vendor contracts renew или telemetry costs need redistribute.</p>
    <p><strong>Экономика performance.</strong> Performance — cost lever, не только UX-lever. Concrete: service с 10x better throughput needs 10% infrastructure для same load. AWS bill scales с vCPU + memory + bandwidth — 2x perf improvement halves bill. Real: Discord Rust rewrite of Go service в 2020 cut hosting bill ~70%. Cloudflare Pages optimised cold-start sub-100ms, dropping reserved instances on demand — 60% cost reduction. Stripe documents server-side profile-first programme returns $5-10 saved infrastructure per engineer-hour invested. Сеньорное framing: каждая perf-investment justifies на трёх осях — (a) UX improvement, (b) infrastructure cost reduction, (c) engineering time savings. Most leveraged hits все три.</p>
    <p><strong>SRE practices и error-budget loop.</strong> Google SRE book formalised connection между performance, reliability, product velocity. SLO: target like "99,9% requests под 200 мс на 30 днях". Error budget: 0,1% = ~43 минуты/месяц allowed degradation. Healthy budget — ship features faster; exhausted — focus на reliability/performance until recovers. Quantitative tradeoff. Каждый release ships с predicted error budget impact; releases burning &gt; X% remaining budget require explicit risk acceptance. Implementations: Google Sloth, Nobl9, custom SLOAggregator. Error-budget loop sits above семи фрагментов — tells team когда invest в performance vs features. Mature engineering orgs measure entire planning cycle на error budgets.</p>
    <p><strong>Performance-first культура.</strong> Some companies bake perf в product culture. Examples: Stripe "performance budget gates the deploy", AWS Well-Architected Framework, Cloudflare engineering blog. Cultural mechanics: (a) performance part of every PR review, не separate; (b) regression incidents — blameless retros, не blame-and-fire; (c) engineers recognised для perf contributions в promotion; (d) company tracks performance как top-level metric. Без культуры семь фрагментов — tools без users. С культурой tools становятся reflexes. Команды без perf-культуры eventually decay; с ней sustain over decades. Cultural investment — highest-leverage решение senior engineering leader для long-term system health.</p>
    <p><strong>Capacity planning встречается с performance.</strong> Capacity отвечает «сколько серверов?». Performance — «сколько каждый handle?». Compose: capacity = load / per-server throughput. 2x per-server throughput halves capacity needed. Senior planning ties: когда команда commits фичу, predict perf impact, translate в capacity. Без loop capacity surprises hit at peak: Black Friday, working last year, fails this year потому что performance regressed off-season. Mature teams run capacity projections quarterly с explicit perf assumptions; validate с load tests + production observation. Pyroscope per-service CPU-share dashboard — input в capacity planning.</p>

São Paulo юзер на mid-range Android over 4G имеет wildly different perf chars чем San Francisco юзер на MacBook over fibre. Сеньоры measure by segment: P75 LCP for São Paulo vs SF vs Berlin vs Mumbai. Optimisations helping one segment may not help другому — CDN edge in Mumbai помогает Indian users, но не parse cost on Snapdragon 4-series. Сеньорная strategy: identify worst-served segment (часто mid-range mobile growth markets), optimise для него, optimisations помогают всем как side effect. Optimising для median high-end laptop в HQ countries leaves long tail с worse experience. Performance — global responsibility.</p>
